### OS-001：fork 后父子进程共享什么，是否复制父进程内容？

**常见问法**

- fork 一个进程，父子共享什么？
- 子进程会复制父进程的内容吗？
- 谈谈 fork 的原理。

#### 面试回答

一句话：地址空间各是各的，物理内存先共用、真要写的时候才分开。

- fork 后父子各有独立的虚拟地址空间，初始内容相同。
- Linux 通常用写时复制（COW，Copy-On-Write）共用底层物理页：只读不复制，谁写入谁另拿一份私有页。
- 文件描述符表本身会复制，但表里的描述符指向同一个 open file description（内核里那条“打开文件记录”），所以文件偏移和相关状态是共享的。
- 显式建立的共享内存照样共享；普通堆栈变量的改动不会同步到另一个进程。

#### 技术细节

**复制的到底是什么**

- 复制的是进程视图和必要的管理结构，不是立刻把全部物理内存搬一份。
- 但这不等于免费：页表和内核结构仍要新建，有实际成本。

**返回值与 PID**

- 父子拥有不同的 PID。
- fork 在父进程返回子进程的 PID，在子进程返回 0。

**共享语义的分支**

- COW 页在写入时触发缺页处理，从而拿到一份私有页。
- 用 `MAP_SHARED` 建立的映射不走这套语义，保留共享。

**多线程进程 fork 的坑**

- 子进程只保留调用 fork 的那个线程。
- 继承下来的锁可能停在不可用的状态。
- 所以通常应尽快 exec，并遵守相关接口对 fork 后可调用范围的限制。

#### 深挖追问

1. **子进程会复制父进程内容吗？**（面经实际出现；[[面经/拼多多/一面/0001#Q14：fork 后父子进程共享什么，子进程是否复制父进程内容？|MJ003 Q14]]）

   不是完全不复制，也不是马上把所有内存复制一份。逻辑上初始地址空间内容相同，物理页通常延迟到真正写入时才复制。

2. **子进程 close 一个文件描述符，父进程还能用吗？**（补充练习）

   通常能。两边的描述符表各自独立，子进程关闭只是让引用计数减一，不会把父进程自己的那个描述符删掉。

### OS-002：子进程结束后，父进程需要处理吗？

**常见问法**

- 子进程结束后，父进程需不需要处理？

#### 面试回答

- 需要处理。父进程通常要用 wait 或 waitpid 回收子进程的退出状态，不回收的话这条退出记录会一直留着，就成了僵尸进程。
- 常见做法：监听 SIGCHLD，在信号处理里循环做非阻塞回收，别一次只处理掉一个退出事件。
- 也可以明确配置自动回收机制，这样就不用逐个 wait；代价是可能再也拿不到退出状态。

#### 技术细节

**僵尸进程还留着什么**

- 进程已经停止执行，大部分资源也释放了。
- 还留着的是 PID 和退出信息，等父进程来取。

**回收怎么写**

- 用 `waitpid(-1, &status, WNOHANG)` 配循环，把当前已经退出的子进程都收掉。
- 返回值：0 表示还有子进程、只是暂时没退出；-1 要区分是 EINTR（被信号打断）还是 ECHILD（已经没有子进程了）。

**为什么必须是循环**

- SIGCHLD 可能被合并，多个子进程同时退出时未必收到多个信号。
- 所以不能假定“每个信号对应一个子进程”。

**两个容易混的点**

- Linux 下显式把 SIGCHLD 设成 `SIG_IGN`、或者用 `SA_NOCLDWAIT`，会影响僵尸是否保留；但默认的信号处置不能简单等同于“显式忽略”。
- 孤儿进程跟僵尸不是一回事：孤儿是父进程先没了，通常由 subreaper 或 init 之类的进程接管。

#### 深挖追问

1. **能用 kill 杀掉僵尸进程吗？**（补充练习）

   不能。僵尸进程已经退出了，kill 没法让它再退出一次。要清掉这条记录，得由父进程（或接管它的进程）把退出状态回收走。

2. **为什么用循环 waitpid？**（补充练习）

   因为一次 SIGCHLD 可能对应多个子进程退出。要一直回收到“没有可回收项”为止，否则剩下那些还留在僵尸态。

### OS-003：4 GB 内存机器连续申请四次 1 GB，一定会 OOM 吗？

**常见问法**

- 分四次，每次分配 1 GB，系统内存只有 4 GB，这时会爆吗？

- 进程调用 malloc 后，操作系统立即分配物理内存吗？

#### 面试回答

不一定。关键是分清“申请虚拟地址空间”和“真正触碰物理页”这两件事。

- malloc／mmap 返回成功，通常只是给了虚拟地址，物理页还没落实。
- 真正大量写入页面时，才可能出现回收、换页，甚至 OOM。
- 也可能在申请阶段就直接失败——这取决于 Linux 的 overcommit（超额提交）策略。
- 结果还受 swap、进程自身的地址空间限制、容器内存配额影响。
- 别把 4 GB 当成全能给这个进程：系统本身也要占内存。

#### 技术细节

**申请和触碰是两件事**

- malloc／mmap 返回成功，并不代表全部物理页都已经分配。
- 想看出差别，就对比两个实验：只申请不写、逐页写入。

**overcommit 的三种策略**

- `overcommit_memory` 取值 0 是启发式判断，1 是宽松提交，2 是限制提交。
- 具体可提交额度不只看内存，swap 等因素同样会影响。

**先撞上的可能不是物理内存**

- 容器里 cgroup 的内存限制可能比主机容量小得多。
- 32 位进程的地址空间也可能先成为约束。

**怎么判断而不是猜**

- 依次检查返回值、RSS（真正驻留的物理内存）、系统提交量和 OOM 事件。
- 要区分“分配调用失败”和“分配成功、随后进程被终止”这两种结果。

**malloc 不是每次都进内核**

- 命中分配器已经持有的空闲块时，直接返回，不需要调内核。
- 需要新映射时，拿到虚拟地址也不代表页已驻留，首次访问才触发按需分配。
- 反过来也别说满：分配器复用的那些页可能本来就带着物理页，所以不能讲成“malloc 之后绝对没有物理内存”。

**做实验的边界**

- 这题只讨论原理，不要在自己的主机上跑耗尽内存的实验。

#### 深挖追问

1. **只读新分配区域和逐页写入一样吗？**（补充练习）

   不一定一样。读新分配的匿名内存可能走共享零页这类优化；写入更直接地触发私有物理页的分配。

2. **free 后 RSS 一定立即下降吗？**（补充练习）

   不一定。free 只是还给分配器，分配器为了复用往往先留着。归还给应用堆和归还给内核是两个阶段，RSS 不一定马上掉。

3. **malloc 后操作系统立即分配物理内存吗？**（面经实际出现；[[面经/百度/三面/0001#Q07：进程调用 malloc 后，操作系统立即分配物理内存吗？|MJ010 · 百度 · 三面 · Q07]]）

   不保证。可能复用已有的物理页，也可能只建立虚拟映射、把分配推迟；具体取决于分配器和系统的提交策略。

### OS-004：write 返回后，文件里立刻有数据吗？

**常见问法**

- write（字符串）后，文件里立刻就会有吗？

#### 面试回答

要分两件事：可见性和持久化。

- 对普通本地文件，一次成功的 write 通常是把数据交给内核页缓存（内核在内存里的那份文件缓存）。
- 所以后面去读能读到已写入的部分，但这不代表数据已经落到持久介质上。
- 要求持久化就得显式用 fsync 或 fdatasync，并且检查它返回的错误。
- 如果调的是带用户态缓冲的库函数，中间还多一步：先 flush 到内核，再谈落盘。

#### 技术细节

**别忽略短写**

- write 可能短写，也可能被中断。
- 返回值是实际写入的字节数，所以要循环把剩余部分写完。

**fflush 替不了 fsync**

- fflush 只是把 stdio 的用户态缓冲交给底层，管不到持久化这一步。

**目录项也要持久化**

- 新建或重命名文件时，除了数据本身，目录项还有独立的持久化要求，必要时得同步所在目录。
- 远程文件系统和存储设备有各自的额外语义，不能一概按本地磁盘讲。

**两处容易说过头**

- 别把“磁盘没落盘”说成“其他进程必然读不到”。
- 也不能只调用 close 就宣称断电不丢数据。

**本题的前提**

- 原题“write（字符串）”没给语言和 API，这里以 POSIX 普通文件为基准回答，这个前提要说明。

#### 深挖追问

1. **fsync 文件后新文件名一定持久了吗？**（补充练习）

   不一定。目录项有自己独立的持久化要求，所以可靠的创建、重命名流程还要考虑同步所在的目录。

2. **write 返回的长度小于请求长度怎么办？**（补充练习）

   按返回值推进偏移，继续把剩余数据写完。同时处理 EINTR（被信号打断）、真正的错误，以及适用场景下的 EAGAIN。

### OS-005：进程、线程和协程有什么区别，协程适合什么场景？

**常见问法**

- 进程、线程和协程有什么区别，协程适合什么场景？

- 进程、线程、协程有什么区别，进程间如何通信？

- 进程、线程、协程有什么区别？
- 谈谈协程。
- 操作系统的线程和 Java 线程是什么关系？

- 进程和线程的区别是什么？

- PDF 解析、模型调用、网络 IO 分别适合进程／线程／协程哪种？

#### 面试回答

一句话：进程管隔离，线程管执行，协程是用户态自己调度的轻量执行单元。

- 进程：资源与地址空间的隔离单位。
- 线程：进程内的执行单元。同进程的线程共享堆等资源，但各有自己的调用栈和执行状态。
- 协程：由语言运行时或库管理暂停、恢复和调度，通常比内核线程轻得多。
- 适用场景：大量网络请求这类 I/O 等待占比高的并发任务，用少量线程就能承载很多等待中的工作。
- 别背错：CPU 密集任务要想多核并行，仍然需要多个真正在执行的线程或进程。

#### 技术细节

**调度者不同**

- 这里以常见 Linux 线程为前提：线程由内核调度。
- 协程的模型随语言而异，无栈、有栈都有，调度策略也各不相同。

**协程轻在哪**

- 切换时通常只保存必要的执行状态，不直接触发一次内核线程切换。
- 但这不等于绕开内核：网络等待、系统调用仍然涉及内核。

**一条必须记住的坑**

- 单线程跑协程时，直接执行阻塞调用可能把整个事件循环卡住。
- Go 等运行时有各自的处理机制，不能一概而论。

**并发不等于并行**

- 协程省的是切换成本，共享可变数据仍然可能有竞态。

#### 深挖追问

1. **协程适合什么场景？**（面经实际出现；[[面经/百度/一面/0003#Q02：进程、线程和协程有什么区别，协程适合什么场景？|MJ006 · 百度 · 一面 · Q02]]）

   适合等待占比高的任务：高并发网络服务、并发调用下游这类。

   - 前提是配合异步 I/O 或运行时调度。
   - 同时要限制并发数、处理好取消。
   - 别把所有阻塞操作直接丢进单线程事件循环。

2. **PDF 解析、模型调用、网络 IO 各选哪种执行单元？**（面经实际出现；[[面经/帆软/一面/0001#Q07：PDF 解析、模型调用、网络 IO 分别适合进程／线程／协程哪种？三者区别与开销对比？|MJ022 · 帆软 · 一面 · Q07]]）

   先按负载类型分：

   - PDF 解析是 CPU 密集：要并行就得多进程。它隔离强、崩溃互不影响，正好当解析不可信文档的安全边界；Python 受 GIL 限制更是必须多进程。Java 侧也可以用按核数限并发的线程池。
   - 模型调用和网络 IO 是等待占比高：用协程／异步 IO，少量线程承载海量等待最合适。Java 场景可以用虚拟线程，或者用线程池把阻塞调用包起来。

   再记开销对比：

   - 进程：切换与通信最重，隔离最好。
   - 线程：共享堆、切换较轻，但有竞态。
   - 协程：用户态调度、切换最轻，单线程内天然无竞争；代价是阻塞调用会卡住整个循环，而且吃不到多核。

3. **进程和线程分别由谁调度？线程的执行逻辑是进程控制还是开发者代码控制？**（面经实际出现；[[面经/点点互动/一面/0001#Q18：多线程同步有哪些方式？进程和线程的区别、分别由谁调度？|MJ064 · 点点互动 · 一面 · Q18]]。原素材未记回答，以下为参考）

   - 调度都由操作系统做：Linux 里调度的基本单位是内核线程（task），进程只是资源的容器；什么时候在哪个核上跑、跑多久，由调度器决定。
   - 协程才是「自己调度」：由语言运行时或库在用户态决定暂停与恢复。
   - 执行逻辑归开发者：代码里的锁、条件变量、队列决定线程间的先后与协作；OS 只保证单线程内的顺序，不保证线程间的相对时序。
   - 一句收口：时序由 OS 分配 CPU，正确性由同步原语保证——两者别混。

4. **操作系统的线程和 Java 线程是什么关系？**（面经实际出现；[[面经/快手/二面/0001#Q02：操作系统的线程和 Java 线程是什么关系？|MJ087 · 快手 · 二面 · Q02]]）

   HotSpot 采用 1:1 模型：每条 Java 线程背后就是一个内核线程，Linux 上经 `pthread_create` 创建，调度完全交给 OS，JVM 不做用户态线程复用。

   - 所以 Java 线程“贵”：每条要内核栈＋JVM 栈（`-Xss` 默认约 1MB 虚拟预留），线程数受 OS 与内存约束——这正是线程池存在的前提。
   - `Thread.State`（RUNNABLE／BLOCKED／WAITING…）是 JVM 自己的抽象，与内核调度状态不一一对应：BLOCKED 和 WAITING 在内核里都是阻塞等待，RUNNABLE 可能正在跑也可能在就绪队列。
   - 变化点：JDK 21 虚拟线程（JEP 444）改成 M:N——大量虚拟线程挂载在少量载体线程（内核线程）上，阻塞 IO 时卸载、不占内核线程；这是 Java 第一次引入类协程的用户态调度。展开见 [[专题题库/Java并发#JUC-017：Go 的协程在 Java 有类似方案吗？|JUC-017：Go 的协程在 Java 有类似方案吗？]]。

### OS-006：什么是系统调用，用户态和内核态有什么区别？

**常见问法**

- 什么是系统调用，用户态和内核态有什么区别？

- 用户态和内核态有什么区别？

- 操作系统有用户态和内核态，分别讲一下是什么。

#### 面试回答

- 系统调用：用户程序请求内核服务的受控入口，比如读写文件、创建进程、操作网络。
- 用户态：权限受限，不能任意访问内核内存，也不能执行特权操作。
- 内核态：可以按硬件权限执行资源管理这类操作。
- 一次过程：程序通过系统调用指令进入内核，内核检查参数和权限、执行服务，再返回用户态。

#### 技术细节

**先说清两个态是什么**

- 用户态／内核态描述的是 CPU 的执行权限，不是两个互相独立的进程。

**开销在哪一层**

- 一次系统调用有模式切换、保存和恢复状态的开销。
- 但不必发生线程或进程的调度切换，这是两件事。

**库函数和系统调用不是一一对应**

- 缓冲 I/O 可能把多次调用合并掉。
- 部分服务可以经 vDSO（内核映射到用户态的一段辅助代码）完成。
- malloc 也不必每次向内核申请。

**进内核的不只有系统调用**

- 中断、异常同样会引发进入内核，不能都算成应用主动发起的系统调用。

#### 深挖追问

1. **系统调用一定会切换到另一个进程吗？**（补充练习）

   不一定。服务可以在当前线程的上下文里做完；只有阻塞、调度这类条件出现时，才可能切换到别的执行任务。

2. **为什么要区分两种权限，进内核一定慢吗？**（面经实际出现；[[面经/美团/一面/0001#Q03：操作系统的用户态和内核态分别是什么？|MJ031 · 美团 · 一面 · Q03]]）

   区分的目的是隔离与保护：用户程序不能直接改页表、访问别人的内存或发特权指令，否则任何一个进程都能拖垮全系统。

   进内核的成本要分清贵在哪：

   - 固定成本是保存寄存器、检查参数和权限，通常几百纳秒量级。
   - 真正贵的是随之而来的阻塞、拷贝和可能的调度。
   - 所以优化方向是**减少次数**（缓冲 I/O、批量 syscall、vDSO、io_uring、零拷贝），而不是“别进内核”。

### OS-007：进程间通信有哪些方式，如何选择？

**常见问法**

- 进程间通信有哪些方式，如何选择？

- 线程之间怎么通信？那进程间的通信方式呢？
- 进程间同步有哪些方式？
- 进程间通信的数据传输流程大概是怎样的？怎么让数据从一个进程传到另一个进程？

#### 面试回答

- 常用六种：管道、命名管道、消息队列、共享内存、信号、Socket。
- 共享内存适合批量共享数据，但同步要另外做。
- 信号偏向事件通知。
- Socket 同机、跨机都能用。
- 问「进程间同步」时：信号量、共享内存配锁、文件锁、管道／信号的时序耦合，这四类。

#### 技术细节

**每种方式擅长什么**

- 管道：适合字节流传递。匿名管道常用于有继承关系的进程，FIFO（命名管道）可以通过路径把进程连起来。
- 消息队列：保留消息边界。
- 共享内存：让进程映射到同一块内存，互斥量、信号量等协调手段要自己加。
- 信号：异步通知，不适合传大块数据。
- Socket：Unix domain Socket（同机用的域套接字）适合同机双向通信，网络 Socket 可以跨机。

**怎么选**

- 按这几点权衡：数据量、要不要边界、怎么同步、生命周期、是否跨主机。

**进程间同步的具体手段**

- POSIX／System V 信号量：内核维护的计数对象，P／V 原子操作；既能互斥也能按次序放行，是跨进程同步的正牌工具。
- 共享内存＋锁：在共享内存段上放 pthread 互斥锁（必须开 `pthread_mutexattr_setpshared` 的进程共享属性）或直接用信号量护住临界区。
- 文件锁（flock／fcntl）：拿一个双方都能打开的文件当锁；fcntl 支持记录锁，可锁文件的某一段。
- 管道／Socket：读端阻塞到写端有数据，「等待」本身就是一种同步；写端关闭读端读到 EOF，还能感知对端退出。
- 信号：只能传递「事件发生了」，不能承载状态判断；用它做同步极易丢（信号不排队），适合中断长任务而非保护临界区。

#### 深挖追问

1. **共享内存是否不需要同步？**（补充练习）

   仍需要。共享只解决了“数据放在哪、谁能看到”这个载体问题；读写的先后次序和原子性还得靠同步协议来保护。

2. **进程间同步方式和线程同步方式为什么大多不通用？**（面经实际出现；[[面经/点点互动/一面/0001#Q19：进程间同步有哪些方式？|MJ064 · 点点互动 · 一面 · Q19]]。原素材未记回答，以下为参考）

   普通互斥锁、条件变量活在进程的地址空间里，别的进程看不见；跨进程要换成有内核标识的对象（命名信号量、共享内存段上的 pshared 锁、文件锁）。线程同步手段汇总见 [[#OS-024：多线程之间同步有哪些方式？|OS-024：多线程之间同步有哪些方式？]]。

3. **数据到底是怎么从一个进程传到另一个进程的？**（面经实际出现；[[面经/快手/一面/0001#Q12：进程间通信的方式有哪些？数据是怎么从一个进程传到另一个进程的？|MJ086 · 快手 · 一面 · Q12]]）

   两个进程虚拟地址空间互相不可见，数据只有两条路：经内核中转，或映射同一份物理内存。

   - 管道／Socket：写方系统调用把数据从用户态拷进内核缓冲区，读方再从内核缓冲区拷到自己用户态——两次拷贝，内核是中间人；消息队列同理，只是按消息边界组织。
   - 共享内存：`mmap` 把同一块物理页框映射进两个进程的地址空间，之后读写直达同一内存、零拷贝——最快，但同步要自己配信号量／锁。
   - 信号：不搬数据，只在目标进程挂起一个事件编号。
   - 跨主机：走网络 Socket，数据再经内核协议栈封装发送。
   - 一句收口：除共享内存外都是“拷进内核、再拷出来”；省拷贝就用共享内存，代价是同步责任转给自己。

### OS-008：Linux 进程地址空间与物理内存布局如何区分？

**常见问法**

- Linux 进程地址空间与物理内存布局如何区分？

#### 面试回答

这题的“内存分布”没说清是哪一个，先确认口径。

- 如果问进程虚拟地址空间：常见有代码、只读数据、已初始化数据、BSS、堆、文件或匿名映射，以及线程栈；这些虚拟地址由页表映射到物理页。
- 如果问系统物理内存：涉及物理页、NUMA 节点和 zone、页分配器、内核对象分配、页缓存。
- 别把进程的地址布局当成 RAM 里连续排列的固定分区。
- 具体地址会随架构、ASLR（地址空间布局随机化）和进程而变。

#### 技术细节

**各段放什么（常见 Linux ELF 用户进程）**

- 代码与只读数据：通常是只读映射。
- data：保存已初始化的静态数据。
- BSS：表示零初始化的区域。
- 动态分配：走 brk 管理的堆，或者用 mmap 建立映射。
- 栈：每个线程有自己的栈。

**怎么看**

- 可以从 /proc/PID/maps 查看映射区间、权限、对应文件以及堆栈标识。
- 它是虚拟地址的映射清单，不是物理 RAM 的分布图。

**两条容易说错的边界**

- 地址空间本来就有空洞，映射也是按需建立的，申请了虚拟空间不代表全部物理页已驻留。
- 原题含义待确认：不要用固定的 3G／1G 分界去描述所有架构。

#### 深挖追问

1. **虚拟地址连续是否代表物理内存连续？**（补充练习）

   不代表。页表可以把连续的虚拟页映射到分散的不同物理页。要把进程侧的映射和物理侧的分配分层解释。

### OS-009：线程切换需要保存哪些 CPU 上下文？

**常见问法**

- 线程切换时 CPU 需要保存哪些上下文？

#### 面试回答

保存的是“够把执行恢复起来”的寄存器和调度状态，不是把整个堆复制一遍。

- 具体包括：程序计数器、栈指针、通用寄存器、标志寄存器，以及必要的浮点或向量寄存器状态。
- 保存哪些由体系结构、内核和调用约定共同决定，没有一份放之四海的清单。

#### 技术细节

**同进程线程切换**

- 通常共享同一份地址空间。
- 但每个线程各有执行栈、内核栈和线程局部状态，这些要分开保存。

**跨进程切换**

- 可能还需要切换与地址空间相关的状态。

**谁在保存**

- 一部分状态由硬件异常入口保存，一部分由内核调度代码保存。

**一条容易说过头的**

- TLB（页表缓存）和 CPU 缓存受影响，是性能层面的成本。
- 这不等于把整个缓存序列化保存下来。

#### 深挖追问

1. **同进程线程切换是否完全没成本？**（补充练习）

   不是完全没成本。仍然要保存和恢复寄存器、要走调度，还可能降低缓存局部性。

### OS-011：缺页异常和普通硬件中断有什么区别？

**常见问法**

- 缺页中断和普通中断有什么区别？

#### 面试回答

差别在“谁触发的”。

- 缺页：执行指令、访问某个虚拟地址时同步触发的异常。
- 通常说的普通外部中断：来自计时器或设备，跟当前指令访问哪个地址没有直接关系。
- 结局也不同：内核如果能补齐映射或处理写时复制，就恢复执行原来的指令；否则报告访问错误。

#### 技术细节

**分类上的说法**

- “缺页中断”是常用叫法。
- 严格分类上它是同步异常，和普通硬件中断那种异步外部信号不是一类。

**都会走这条路径的情况**

- 页不在内存、写时复制、权限违规，都可能进入相关的异常处理路径。

**两种缺页成本差很多**

- minor fault（次缺页）可以不读磁盘。
- major fault（主缺页）才涉及必需的 I/O。

**别推过头**

- 缺页不等于内存耗尽。
- 也不意味着就是非法地址。

#### 深挖追问

1. **缺页一定要从磁盘读吗？**（补充练习）

   不一定。零填充、已经在页缓存里的页面、写时复制这几种都能不读磁盘就补上映射。

### OS-012：什么是内存抖动，工作集模型如何缓解？

**常见问法**

- 什么是抖动，工作集模型如何缓解？

#### 面试回答

- 抖动：活跃进程需要的页面超过可用的物理页，于是频繁缺页、不停换入换出。
- 表现是时间大量花在调页上，有效计算反而很少。
- 工作集的对策：用最近一段访问历史，估计进程正在使用的是哪些页面。
- 再据此尽量给活跃任务留够页框。

#### 技术细节

**工作集怎么定义**

- W(t,Δ)：在给定观察窗口内访问过的那些页的集合。
- 窗口过小会漏掉局部性，过大会混进早就用不到的过时页。

**真不够用时怎么办**

- 总需求超出容量时，出路是减少并发的活跃进程、推迟任务，或者增加内存。
- 继续提高多道程序度（同时驻留在内存里的进程数）只会更抖。

**口径限制**

- 工作集是模型和管理上的依据。
- 不要宣称现代 Linux 精确按这套教科书算法运行。

#### 深挖追问

1. **为何增加并发可能降低吞吐？**（补充练习）

   会。更多活跃工作集一起去抢有限的页框，会引起调页和 I/O 拥塞，把并发带来的收益压过去。

### OS-013：FIFO、LRU 和 Clock 页面置换有什么特点？

**常见问法**

- FIFO、LRU、Clock 页面置换算法各有什么特点？

#### 面试回答

三个一句话：

- FIFO：淘汰最早进来的页。实现简单，但不利用近期访问信息，可能出现 Belady 异常。
- LRU：淘汰最久未访问的页。符合时间局部性，代价是精确维护有成本。
- Clock：环形扫描引用位，给近期访问过的页第二次机会，是一种低成本的近似。

#### 技术细节

**Clock 具体怎么走**

- 扫到引用位为 1 的页：清零，继续往后扫。
- 扫到引用位为 0 的页：选它作为候选。
- 增强变体会再考虑脏位，因为脏页还牵涉写回成本。

**和 Belady 异常的关系**

- 精确 LRU 有栈性质，增加页框不会出现 FIFO 那样的 Belady 异常。
- Clock 只是近似，不等于精确 LRU。

**口径限制**

- 这里讨论的是教材算法，不要把结论当成所有系统的实际实现。

#### 深挖追问

1. **FIFO 为什么会有 Belady 异常？**（补充练习）

   因为它只按进入顺序淘汰，不保证小容量的页集合始终包含在大容量的页集合里。增加页框会改变淘汰顺序，某些访问串反而缺页更多。

### OS-014：死锁的四个必要条件是什么，如何处理？

**常见问法**

- 死锁的四个必要条件是什么？

- 什么是死锁？

#### 面试回答

四个必要条件：互斥、占有且等待、不可剥夺、循环等待。

- 互斥：资源同一时刻只能由一个执行单元使用。
- 占有且等待：手里已经占着部分资源，同时再去等其他资源。
- 不可剥夺：已分配的资源不能被外部强制收回。
- 循环等待：等待关系连成一个闭环。

四者同时成立才可能发生死锁，破坏其中任意一个即可预防。

#### 技术细节

**四条破坏路径，各对应一个条件**

- 破坏循环等待：规定固定的全局加锁顺序。
- 破坏占有且等待：一次申请全部必要资源；或者申请失败时先释放已持有的资源。
- 破坏不可剥夺：在资源允许的前提下支持抢占。
- 避免：用 Banker（银行家）这类策略做判断。
- 还有一条事后路线：允许它发生，检测等待图中的环，再选择事务／进程回滚恢复。

**数据库场景的分工**

- 数据库通常靠死锁检测选出牺牲者。
- 应用侧要重试完整事务。

**一个具体例子**

- 线程 A 先锁资源 1 再等资源 2，线程 B 先锁资源 2 再等资源 1，就形成循环等待。
- 规定两者都先锁编号较小的资源，这个环就消除了。

**超时和诊断的边界**

- 超时可解除长期等待，但可能把慢操作误判为死锁，也不保证环在业务层从未形成。
- 实际诊断要结合线程栈、锁持有者或数据库死锁日志，不能仅凭“请求很慢”断言死锁。

#### 深挖追问

1. **死锁与饥饿有什么区别？**（补充练习）

   区别在“谁卡住”。

   - 死锁：一组执行单元互相等待，没有外力就不会推进。
   - 饥饿：某个执行单元长期拿不到调度或资源，但系统中其他工作仍可能持续推进。

2. **超时能否从根本上预防死锁？**（补充练习）

   不能。超时通常算检测或恢复手段，还会误伤只是执行较慢的请求；预防要破坏必要条件。

3. **Java 里怎么确认“真的是死锁”而不是慢？**（面经实际出现；[[面经/美团/一面/0001#Q06：什么是死锁？|MJ031 · 美团 · 一面 · Q06]]）

   抓线程栈看等待关系。

   - `jstack <pid>` 会在末尾直接输出 “Found one Java-level deadlock”，并列出互相持有的 monitor。
   - 程序内可用 `ThreadMXBean.findDeadlockedThreads()` 拿到线程 ID 数组。
   - 判据是闭环：“线程 A 持有 X 等 Y、线程 B 持有 Y 等 X”，再配合 `Thread.getState()` 为 BLOCKED／WAITED 且长期不变。
   - 只有“响应慢”而没有闭环证据不能断言死锁，可能是锁竞争激烈、外部依赖卡住或 GC 停顿。

   完整处理策略见 [[#OS-017：死锁如何预防、避免、检测和恢复？|OS-017：死锁如何预防、避免、检测和恢复？]]。

### OS-015：并发和并行有什么区别，IO 密集型适合哪种？

**常见问法**

- 并发和并行是什么，有什么区别？
- IO 密集型适合并发还是并行？

#### 面试回答

- 并发：同一时间窗口内多个任务都在推进。单核上靠时间片交替，任一时刻其实只有一个任务在执行。
- 并行：多个任务在多个核上同一时刻物理执行。
- 一句话：并发是一种处理多任务的程序结构，并行是利用多核同时执行的运行状态。

IO 密集型适合用高并发组织：

- 耗时大头在等待设备与网络，不占 CPU。
- 异步 I/O、事件循环或协程，能用少量线程承载大量等待中的连接。
- 盲目开很多并行线程，只会增加上下文切换开销。

CPU 密集型要提升吞吐必须靠多核并行，单靠并发结构不会更快。收尾一句准确说法：IO 密集的边际收益来自并发，CPU 密集的吞吐来自并行，真实服务往往两者兼有。

#### 技术细节

**并发不等于“多线程”**

- 单线程事件循环靠非阻塞 I/O 也能承载上万连接数（参见 [[专题题库/Linux#LINUX-002：select、poll、epoll 有什么区别？|LINUX-002：select、poll、epoll 有什么区别？]]）。
- 线程数也不必等于核数。

**在途任务数怎么估**

- IO 密集常按“并发量≈目标 QPS×平均延迟”估算所需在途任务数。
- 再结合连接池与下游容量设上限。

**并行度为什么低于核数**

- 并行度受核数约束。
- 但共享可变数据的锁竞争、伪共享和 Amdahl 定律，会让加速比低于核数。

**协程的位置**

- 协程适合把“等待”从线程里剥离出来。
- 但单线程运行时里执行一个阻塞调用会卡住整个循环（Go 等有专门处理，见 OS-005）。

**两个常见误区**

- 把“提高并发数”当成万能：过并发只会加剧切换、内存和下游过载，需要限流与背压。
- 把 CPU 密集交给事件循环：不会变快，因为被计算任务独占时无人让出。

#### 深挖追问

1. **IO 密集型开线程越多越好吗？**（补充练习）

   不是。超过等待与切换带来的收益后，更多线程只增加内存和调度成本。改用异步 I/O，或者有界线程池＋限流。

2. **纯并发结构能让 CPU 密集任务变快吗？**（补充练习）

   不能。它只是把同一段时间复用起来。计算吞吐要提上去需要多核并行，还得处理数据分片与竞争。

### OS-016：操作系统有哪些基本功能？

**常见问法**

- 先说一下操作系统有哪些功能。
- 操作系统的作用是什么？

#### 面试回答

操作系统有两个身份：对上是屏蔽硬件差异的统一抽象接口，对下是全局限价的资源管理者。功能按管理对象分六块：

- 进程／线程管理：创建撤销、调度、切换、同步与通信。
- 内存管理：地址映射、分配回收、虚拟内存与页面置换。
- 文件管理：目录、空间分配、读写与权限。
- 设备管理：驱动抽象、缓冲、I/O 调度与假脱机。
- 网络与进程间通信。
- 安全保护：身份认证、隔离与访问控制。

一句话概括：把硬件的复用、共享与安全隔离统一收口，让应用不必、也不被允许直接碰硬件。

#### 技术细节

**每块各举一个典型机制，避免只报名词**

- 进程管理：PCB（进程控制块）、上下文切换，以及调度算法（CFS 等）。
- 内存管理：分页分段、MMU 地址翻译、缺页处理，还有 LRU／Clock 置换（见 OS-013）。
- 文件系统：索引节点、journal 日志与页缓存（写回语义见 OS-004）。
- 设备管理：中断、DMA 与 I/O 队列。
- 安全：用户态／内核态权限边界（OS-006）、uid／GID 与命名空间隔离。

**易错点一：这件事到底谁做的**

- 虚拟内存、分页、调度、文件系统这些“功能”由内核提供。
- 但用户态看到的很多能力，实际落在运行时库、守护进程或内核旁路（vDSO、io_uring、DPDK）里。
- 说“操作系统做了 X”的时候，要区分内核态与用户态的职责。

**易错点二：教材口径和实现口径不一致**

- 现代操作系统的功能在持续演进，比如透明大页、cgroup 资源控制属于资源管理，不在传统“五大功能”的表述里。
- 所以回答时先说明自己按经典分类展开。

#### 深挖追问

1. **操作系统和虚拟机管理器（Hypervisor）的功能边界有什么不同？**（补充练习）

   管的层级不同。

   - 操作系统：管理单机硬件，为进程划分资源。
   - Hypervisor：把“物理机”本身虚拟化，为多个客户机 OS 分配虚拟的 CPU／内存／设备。
   - Hypervisor 还分两类：Type-1 直接跑在硬件上，Type-2 仍依赖宿主 OS。

   容器不复制这一层：它共享宿主内核，靠 namespace＋cgroup 做视图与配额隔离（参见 [[专题题库/容器与编排#CLOUD-001：Docker 容器和虚拟机有什么区别，为什么更轻量？|CLOUD-001：Docker 容器和虚拟机有什么区别，为什么更轻量？]]）。

2. **为什么说操作系统是“资源管理者”而不是“程序库”？**（补充练习）

   因为资源是多方在抢同一份有限资源。只有内核掌握全局视图与抢占权，才能做仲裁、配额和优先级。

   程序库只服务单个进程，没法跨进程去约束别人。这也是特权指令必须收进内核态的原因。

### OS-017：死锁如何预防、避免、检测和恢复？

**常见问法**

- 怎么样避免产生死锁？还有别的吗？
- 如果发生了死锁，要怎么解除或恢复？
- 死锁的处理策略有哪些？

#### 面试回答

四条路线，按“事前—事中—事后”排：

- 预防：静态破坏四个必要条件之一。应用层最常用的是固定全局加锁顺序（破坏循环等待），以及一次申请齐所需资源、或申请失败就先释放已持有的资源（破坏占有且等待）；锁超时和可抢占锁破坏不可剥夺。
- 避免：分配时动态判断会不会进入不安全状态（Banker 算法类）。它需要预知最大资源需求，通用系统里很少真正落地。
- 检测：允许死锁发生，周期性或不定期扫描资源分配图／等待图找环。
- 恢复：破坏不可剥夺，回滚或杀掉环上的牺牲者并释放资源。

工程实践的主流是“预防为主＋检测恢复兜底”，不追求严格避免。

#### 技术细节

**预防：要能落到代码约定**

- 把所有锁排一个全局次序（按资源 ID、按加锁层级），所有路径都按同一顺序获取。
- 锁范围尽量小；不要在持锁时调用可能反向加锁的外部接口，比如回调、RPC、消息处理。
- 需要多把锁时用 `tryLock(timeout)` 组合，拿不到就全部释放再重试。
- 重试要带退避，避免活锁。

**避免：代价卡在信息上**

- 要知道每个任务的资源上限，并且每次分配都做安全性检查。
- 开销大、信息又常不可得，所以教科书算法与线上实现差距明显。

**检测：各层各有抓手**

- Java：可直接用 `jstack` 线程 dump 里的 “Found one Java-level deadlock” 段，或者 `ThreadMXBean.findDeadlockedThreads()`。
- JDBC／MySQL 侧：查 `SHOW ENGINE INNODB STATUS` 的 LATEST DETECTED DEADLOCK。
- InnoDB 自带 wait-for graph（等待图）检测，并主动回滚代价较小的事务。
- 分布式场景（跨服务互相持锁等待）没有全局等待图，一般靠超时、租约（如 Redis 锁的 TTL＋fencing token）和业务侧对账来兜。

**恢复：四种手段及副作用**

- 杀进程／线程：最简单，代价是丢未提交的工作，应用必须能容错重启局部任务。
- 回滚事务：数据库自动选 undo 量小的牺牲者；业务要重试**完整事务**，而不是只重放报错那条语句。
- 抢占资源：把资源从持有者剥夺给他人。只有状态可回退的资源（如数据库锁）可行，普通内存／文件锁不可行。
- 重启实例：无法在线解除时的最后手段；恢复后仍要修加锁顺序防复发。

**超时算哪一类**

- 它属于“解除等待”的手段，不是预防。
- 一方面可能把只是慢的操作误判为死锁，另一方面可能让两个请求同时超时后互相重复撤销。
- 所以超时解套要求业务幂等，并保留事后一致性核对。

#### 深挖追问

1. **预防、避免、检测三者的区别是什么？**（面经实际出现；[[面经/美团/一面/0001#Q07：怎么避免产生死锁？还有别的办法吗？|MJ031 · 美团 · 一面 · Q07]]）

   三者在“约束强度、运行时开销、所需信息”上依次让步。

   - 预防：静态破坏必要条件，保证永不发生。
   - 避免：分配时动态判断，拒绝会通向死锁的分配；结果也是不发生，但前提是要预知需求。
   - 检测：允许发生，之后再找环处理。

2. **银行家算法在真实系统里用得多吗？**（补充练习）

   很少，两个原因：

   - 信息拿不到：要求提前声明各资源的最大需求。
   - 代价太大：每次分配都要做 O(n×m) 安全性检查，而真实系统的资源粒度动态、数量可变。

   实际更多用配额、限流、租约与优先级抢占，达到类似“不进不安全状态”的效果。

3. **MySQL 死锁发生了，应用该怎么写？**（面经实际出现；[[面经/美团/一面/0001#Q08：发生了死锁要怎么解除或恢复？|MJ031 · 美团 · 一面 · Q08]]）

   三件事：

   - 捕获 1213 这个死锁错误码，按有限次数、带退避地重试**整个事务**。
   - 重试前不要假设上一次的部分写入还在，引擎已经回滚了该事务。
   - 同时排查 SQL 顺序与索引：索引没走对会让锁范围从行锁扩大为大量行甚至间隙锁。很多“莫名死锁”实际是加锁顺序＋扫描范围问题，只调超时参数掩盖不了。

4. **只有超时没有检测，会不会漏掉问题？**（补充练习）

   会。超时解套后系统看似恢复，但等待环的成因没被记录，高并发下会以“偶发慢请求”的形式反复出现。

   线上要保留线程栈采样、锁等待统计与数据库死锁日志，事后能定位到具体持锁路径才算闭环。

### OS-018：什么是 I/O 零拷贝，sendfile 和 mmap 如何减少拷贝？

**常见问法**

- I/O 的“零拷贝”技术是指什么？

#### 面试回答

以“把磁盘文件通过 socket 发送出去”为例，先说传统路径：

- `read()`：DMA 把数据从磁盘读进**内核页缓存**，再把页缓存拷进**用户态缓冲区**。
- `write()`：又把用户缓冲区拷回**内核 socket 缓冲区**，最后 DMA 从 socket 缓冲区发到网卡。
- 合计 4 次拷贝、2 次上下文切换，其中“内核↔用户”来回那两次纯属浪费。

**零拷贝**要省掉的，就是 CPU 参与的这部分用户态／内核态冗余拷贝：

- **`sendfile()`**：数据全程留在内核，从页缓存直接送到 socket；配合 scatter-gather DMA，网卡这边可做到 CPU 零次拷贝。一次系统调用完成。
- **`mmap()` + `write()`**：把文件映射进用户地址空间，省掉 `read` 那次“拷到用户缓冲区”的拷贝（仍有 socket 缓冲一次拷贝）。适合还要对数据做处理／共享的场景。
- **`splice()`／`tee()`**：用管道在内核态搬数据。

收益：减少拷贝次数与上下文切换、降低 CPU 与内存带宽占用。典型使用者：Kafka（用 `sendfile` 做日志复制／消费）、Nginx 静态文件、Netty 的 `FileRegion`。

#### 技术细节

**“零拷贝”零的是哪一次**

- 不等于“一次拷贝都没有”。
- 指的是 CPU 不再负责把数据在用户态和内核态之间来回搬。
- DMA 从磁盘到页缓存、从缓冲到网卡仍然照做，但这些不占 CPU。
- 经典四次拷贝里，被消除的只有第 2、3 次（内核↔用户）。

**`mmap` 还是 `sendfile`**

- 需要读取并处理内容（改、算、共享）：用 `mmap`。
- 纯“搬运”透传：用 `sendfile` 更省。

**`mmap` 的三个坑**

- 文件被截断后再访问越界页，会拿到 `SIGBUS`。
- 小文件场景：页表与映射建立本身有开销，`mmap` 未必比 `read`／`write` 快。
- 脏页写回由内核异步控制，需要 `msync` 才保证落盘时机。

#### 深挖追问

1. **零拷贝为什么能提升 Kafka／Nginx 这类吞吐？**（补充练习）

   因为它们主要做“数据搬运”，不是计算。

   - `sendfile` 让数据不进用户态，省掉两次拷贝和一半系统调用。
   - 还减少了页缓存与 socket 缓冲之间的一致性开销。
   - 省下来的 CPU 就能留给网络与磁盘 I/O 本身。

### OS-019：单核 CPU 如何同时运行多个程序？死循环程序系统会怎么处理？

**常见问法**

- 操作系统里这么多程序同时在执行，为什么单核机器上不会卡住？
- 写了个死循环程序一直执行，会出现什么现象？单核操作系统会有什么表现？
- 不需要人为干预（重启、按键）的话，操作系统本身会怎么处理这个程序？

#### 面试回答

单核不卡住，靠的是抢占式调度：

- “同时执行”是宏观错觉：任一时刻只有一个程序在跑，调度器用时钟中断周期性收回 CPU，换下一个就绪进程上场——时间片轮转的现代形态是 CFS 按虚拟运行时间均衡分配（OS-015 的并发口径）。
- 切换本身是微秒级动作（保存什么见 OS-009），远小于人感知的粒度，所以多任务看起来顺滑。
- 关键点：用户程序无法霸占 CPU，因为时钟中断是外部硬件事件，一定会打断执行流进调度器——除非内核代码关了中断。

死循环程序的表现分三层：

- 现象：该进程 CPU 占用顶满单核（100%），整机变慢但不停摆——其它进程仍按调度拿到时间片，只是响应变差。
- 系统自身处理：不会杀它。内核视角这只是个行为正常的 CPU 密集任务，“跑太久”本身不是异常；公平调度就是防线，高优先级任务来了随时抢占。OOM 也帮不上忙——它管内存不管 CPU。
- 例外必须说：死循环发生在内核态且绕开调度点，才真会冻住系统——Linux 用 watchdog 检测 soft lockup 打印告警堆栈，可按参数升级成 panic 重启；这是内核自保，不是替你修 bug。

#### 技术细节

**中断为什么收得回 CPU**

- 时钟中断是硬件定时器发出的外部事件，与正在执行的代码无关，用户态死循环挡不住它；每次中断返回用户态前内核都有调度检查点。
- 主动让位的写法（sleep／yield／阻塞 IO）只是“礼貌”，不是调度的前提条件。

**CFS 没有固定时间片**

- 现代 Linux 用虚拟运行时间（vruntime）记账：谁累计占用少谁先跑，权重由 nice 值换算——所以准确说法是“按比例均衡”，不是“每人 10ms 轮一圈”。
- 死循环进程会把整机算力份额吃满自己那一份权重，调低它的 nice 可以压缩它的份额——这就是“nice 降优先级”的实际含义。

**哪些情况调度器真管不了**

- 内核态关闭抢占／关中断的长循环：直接延迟所有时钟中断处理，可能触发 hard lockup（NMI watchdog 检测）。
- 优先级反转与实时任务垄断（SCHED_FIFO 写错能饿死一切）——都属于内核态／策略层问题，不是普通用户程序死循环。
- 容器环境补充：cgroup 按配额限 CPU 时间，死循环表现为被打满 quota 后被限流（throttling），宿主机不受牵连。

**答题分层法**

- 这类“系统会怎么办”题按三层给：机制层（调度与中断）→ 现象层（卡顿程度、可否恢复）→ 边界层（内核算不算、多核变不变）。连环追问（现象→单核表现→系统自处理）就是在逼你走到第 3 层。

#### 深挖追问

1. **多核机器上一个核死循环，其它核上的任务受影响吗？**（补充练习）

   基本不受影响：每个核独立跑自己的时间片轮转，死循环只吃满所在核；受影响的场景是它和其它任务共享末级缓存／内存带宽，或它持有锁导致别人等——CPU 之外还有资源竞争这层。

2. **调度器会不会因为“它只算不出错”而把它换下去？抢占的时机有哪些？**（补充练习）

   会换——抢占只看“该不该换”，不看“有没有错”：时钟中断到点、有更高优先级任务唤醒、主动阻塞这三类是主要时机。反过来说，一个纯计算进程和交互式进程抢 CPU 时，交互性由调度类与权重保障，不靠“检测到没进展”。

### OS-020：操作系统的分页机制是怎么工作的？

**常见问法**

- 谈谈操作系统存储的分页机制，越详细越好。

#### 面试回答

“越详细越好”就给完整流水线，六步报完：

- 动机：每个进程拿到“连续虚拟地址空间”的假象，实际物理内存是离散块——分页同时买到隔离、保护和“内存可超配”（能换入换出）。
- 单位：页＝定长块（常见 4KB）；虚拟侧叫页（page），物理侧叫页框（frame）。虚拟地址切成“页号＋页内偏移”，偏移不参与翻译、原样拼进物理地址——块内连续性是白送的。
- 翻译：MMU 硬件查页表；页表项存页框号＋状态位（存在、读写、用户态、脏位、访问位），权限不符或不存在就陷入内核。
- 多级页表：稀疏地址空间不配整张平表，x86-64 用 4／5 级树、只建用得到的分支；代价是一次翻译多次访存，所以配页遍历缓存。
- TLB：缓存最近的页→帧映射，miss 才走页遍历；进程切换配合 ASID 少冲刷。
- 与缺页协作：PTE“不存在”不是事故——按需分配、COW、换页回读、堆首次触碰全靠缺页处理完成（流程见 OS-011）；非法访问才发 SIGSEGV。

主动收边：分页有内部碎片（平均半页／映射）；置换策略（访问位／脏位驱动的 Clock，OS-013）建在这套机制之上。

#### 技术细节

**地址结构怎么算**

- 4KB 页时低 12 位就是偏移（2^12）；虚拟地址高位逐级做页表索引——每级 9 位管 512 项。
- “页内偏移不翻译”解释了为什么相邻虚拟页可以落在任意物理帧上，也解释了为什么对齐访问跨页边界可能一半成功一半缺页。

**多级页表省在哪**

- 平表要为整个地址空间（如 48 位虚拟位宽）预留条目；树形只要子树为空就不建表页，稀疏大地址空间的表开销从“地址空间大小”降到“实际映射量的函数”。
- 中间级表页可共享（多个进程映射同一段内核地址），这也是 ASID／PCID 存在的背景。

**TLB 的真实成本**

- TLB miss 一次要多次串行内存访问走页表，比命中贵几个数量级——大页（2MB／1GB）的价值就是单条 TLB 覆盖范围×512／×26 万。
- 透明大页（THP）默认开但会带来合并卡顿与内存压缩毛刺；数据库类负载常显式关闭或改用显式 HugePage——工程加分点，标明是实践口径非规范。

**换页与页替换的配合**

- 物理页不足时，内核按访问位（recently used）和脏位（要不要写回）选牺牲页——LRU 的近似实现（两级 List／Clock-Pro 等）都建立在 PTE 状态位之上（见 OS-013）。
- 缺页→分配→置换→回写，这条链把“分页”从地址翻译升级成虚拟内存系统。

#### 深挖追问

1. **分页和分段到底差在哪？**（补充练习）

   - 段：变长、按程序视角（代码段／栈段）切，保护语义直观，但会产生外部碎片、要动态归并。
   - 页：定长、纯硬件视角，有内部碎片但没有外部碎片，置换与映射都按块算。
   - 现代 x86-64 基本“分页为主、分段退化成兼容层”，特权隔离改由页表权限位承担。

2. **为什么 mmap 共享内存能当 IPC 用？**（补充练习）

   两个进程的不同虚拟页映射到同一物理页框——一方写入另一方经自己的映射立刻可见（同步语义见 OS-021，并发控制靠锁/信号量，见 OS-007）。映射关系本身成了通信信道，这正说明“虚拟→物理”这层间接是特性不是开销。

### OS-021：同步与异步、阻塞与非阻塞怎么区分？操作系统和 Java 分别如何实现？

**常见问法**

- 谈谈同步和异步，自己怎么理解的。
- 操作系统中、Java 中是如何实现同步与异步的？

#### 面试回答

先把两对概念钉在两条轴上（混掉就全盘输）：

- 阻塞／非阻塞——看发起调用那一瞬：不等到结果不返回的是阻塞；立刻返回、自己继续干的是非阻塞。
- 同步／异步——看结果怎么到你手里：结果由你这次调用“自己等出来”的是同步；完成方通过回调、置位、发信号主动通知的是异步。
- 组合矩阵：阻塞同步＝普通 `read()`；非阻塞同步＝`O_NONBLOCK` 轮询或 epoll 循环（等待被复用，收割仍在调用方线程）；异步＝io_uring／POSIX AIO（内核干完回填完成队列通知你）。
- 一句话本质：异步不消灭“等”，只是把“等”从当前线程挪到别处完成，再换成通知。

操作系统实现：

- 同步阻塞：线程挂到等待队列，数据就绪被唤醒。
- 事件通知原语：信号、signal 回调——OS 层的异步通知形态。
- 真异步 I/O：io_uring 的 SQE／CQE 双环；POSIX AIO 是历史方案；epoll 严格说是同步复用（POSIX 口径），别叫它异步 I/O。

Java 实现：

- 同步协作：方法调用天然同步；线程间等待唤醒（`wait`／`notify`、`Condition`、`park`）也是“自己等结果”的同步语义（见 JUC-008）。
- 异步形态：`CompletableFuture` 回调链、Netty `ChannelFuture`＋事件循环、Servlet 异步处理释放工作线程；`Future.get()` 是“异步执行、同步收割”的混合体，说清这一点很加分。
- 收尾边界：虚拟线程（JDK 21）把“阻塞”变便宜了，但代码语义仍是同步——别把它讲成异步。

#### 技术细节

**为什么 epoll 常被说错**

- 它解决的是“一个线程等一万个 fd 里谁就绪”——等待被批量化；收到通知后仍要自己 `read()` 把数据同步搬上来。
- io_uring 连搬运都交给内核，完成后你只从 CQ 拿“好了”事件——这才满足“完成方干活”的异步定义。

**Java 异步的三种收割方式**

- 阻塞等：`future.get()`（占着当前线程）。
- 回调链：`thenApplyAsync` 系列（完成线程执行你的逻辑，注意别在回调里做重阻塞）。
- 结构化合并：`allOf`／`anyOf` 编排多任务。
- 共同纪律：回调线程池要有界，异常要显式接管，否则错误被吞在链尾。

**同步≠串行，异步≠高并发**

- 并发是任务推进结构，并行才是多核同时执行（OS-015 口径）。
- 异步的价值是给“大量等待中的任务”省线程，CPU 密集任务换异步不会更快——先分负载类型再谈选型。

#### 深挖追问

1. **异步编程一定比同步快吗？**（补充练习）

   不。单请求路径上异步多了队列、上下文切换和回调调度，反而更慢；收益在高并发下的线程占用与内存。CPU 密集用它零收益。答题落点：按负载选型，不按流行度选型。

2. **网络请求里的同步／异步和这题是一回事吗？**（补充练习）

   同族但层面不同：HTTP 的“同步请求—响应”对比 SSE／WebSocket 推送，说的是协议交互模式（见 NET-016）；本题说的是线程等待与完成通知机制。被追问时先分层再作答。

### OS-022：ARM 芯片和英特尔（x86）芯片有什么区别？

**常见问法**

- ARM 芯片和英特尔芯片有什么区别？

#### 面试回答

分四层答，别停在“一个省电一个性能强”：

- 指令集传统：ARM 属 RISC 路线——定长指令、加载／存储式、解码简单、易做多核高能效；x86 属 CISC——变长指令、四十年向后兼容、复杂指令多。现代两者互相吸收（x86 内部微解码成类 RISC 的 μop 执行，ARM 也加了不少复杂指令），差别更多在生态与惯性。
- 功耗与场景：ARM 能效优先，统治手机与嵌入式，并已进入服务器与 PC（Apple Silicon、云厂商 ARM 实例）；x86 单线程峰值与存量软件生态强，仍在传统服务器／PC 主流。
- 商业模式：ARM 只卖 IP 授权，各家自研核（高通／苹果／AWS），生态分散但迭代灵活；Intel 设计制造一体（IDM 模式），绑定 Windows-x86 生态。
- 对软件与 Java 的影响：同一份字节码换架构不用重编，但本地依赖（JNI、netty-tcnative 之类）要按架构出产物；原子指令实现不同（x86 `lock cmpxchg` 强内存序 vs ARM LL／SC 弱内存序，内存模型差异正好解释 volatile／屏障为何在 ARM 上更“有活干”）；性能是负载相关，不做绝对论断。

#### 技术细节

**别背的过时叙事**

- “RISC 一定比 CISC 快”“ARM 做不了服务器”都是过去式：性能取决于微架构与工艺，不取决于指令集标签；AWS Graviton、Ampere 已在云上有规模份额（以当期公开信息为准）。
- 弱内存序要单独记一句：x86 上“几乎不重排”的错觉会掩盖代码里的同步缺陷，换到 ARM 才暴露——多线程 bug 跨架构复测的价值就在这。

**与操作系统交叉点**

- 系统调用号、信号布局、页大小（ARM64 常见 16K／64K 页）随架构变；容器镜像要按架构出多平台构建（linux／arm64 与 amd64）——“同一镜像跑不了另一种芯片”是部署侧最常见的实感差异。

**答题收口模板**

- 指令集哲学一句＋功耗生态一句＋商业模式一句＋“对我们写程序的影响”一句——最后一句最加分，显示你知道这题为什么问。

#### 深挖追问

1. **为什么手机不用 x86 而长期用 ARM？**（补充练习）

   功耗墙：手机是电池供电＋无风扇散热，能效比（性能／瓦）优先于峰值；x86 的历史包袱（兼容层、复杂解码）不利于做小核阵列。Intel 也曾尝试手机 SoC（Atom），败在生态与功耗竞争力。

2. **Mac 转 ARM 后老 x86 软件怎么跑？**（补充练习）

   Rosetta 2 做指令级翻译（一次性预翻译为主）＋虚拟环境补系统调用，性能有折损但日常无感——说明架构迁移的瓶颈通常在生态兼容，不在硅片。

### OS-023：32 位和 64 位操作系统有什么区别？

**常见问法**

- 说一下 32 位操作系统和 64 位操作系统的区别。

#### 面试回答

根子在 CPU 通用寄存器宽度和指针位宽，寻址上限只是它带出来的结果。

- 字长：32 位 CPU 一次处理 32 位数据，指针占 4 字节；64 位一次处理 64 位，指针占 8 字节。
- 可寻址内存：32 位是 2^32 = 4GB，且这 4GB 还要被设备占用、单进程用户空间更少；64 位虚拟地址空间极大，实际由硬件实现的地址位数截断。
- 兼容方向：64 位系统能靠兼容层（如 Windows 的 WoW64）跑 32 位程序；32 位系统跑不了 64 位程序，内核与驱动位数必须匹配。
- 性能与代价：64 位一次能搬更多数据、通用寄存器更多，大整数和加密更快；代价是指针与对象更大，内存占用和缓存压力上升。

一句话记法：不是“64 位=能插更大内存条”，而是“寄存器/指针宽度变了，寻址、容量、数据吞吐一起变”。

#### 技术细节

**寻址上限是推导出来的，不是配置出来的**

- 指针宽度决定可表示的地址数：32 位指针 → 4G 个地址。
- 64 位也拿不到 2^64：x86-64 目前用 48 位虚拟地址（规范地址约 256TB），架构预留可扩展到 57 位。

**32 位机器装 4GB 内存为什么显示用不满**

- 一部分地址空间要映射给设备（显卡显存、PCIe 设备的 MMIO），可用物理内存被压到 3~3.5GB 左右。
- 单进程可用的用户地址空间还要再切：Windows 32 位默认用户 2GB／内核 2GB，Linux 常见 3G／1G 划分。

**性能不能只说“64 位更快”**

- 变快：一次处理 64 位、可寻址大内存、调用约定用寄存器传更多参数（System V AMD64 ABI 前 6 个整型参数走寄存器）。
- 可能变慢：指针和数据膨胀导致同缓存容量下能装的元素更少，指针密集型负载命中率下降。

**Java 场景要能接上（体现你真做过）**

- 64 位 HotSpot 默认开压缩指针（Compressed Oops），对象引用仍按 4 字节存，堆小于约 32GB 时几乎不亏内存。
- 堆超过约 32GB 会关闭压缩指针，引用变 8 字节，对象头／线程栈开销上升——这也是“大堆反而单位内存效率下降”的实例。

**别说过头**

- 别说“64 位程序一定比 32 位快”；纯 32 位整型的小数据量运算差异不明显。
- 别说“32 位就绝对只能有 4GB 内存”：PAE 让 32 位 CPU 物理寻址扩到更大，但单个进程虚拟地址仍受 32 位限制。

#### 深挖追问

1. **64 位系统一定比 32 位快吗？**（补充练习）

   不一定。优势在大整数、大内存、寄存器传参；劣势在指针与数据膨胀带来的内存占用和缓存压力。指针密集、工作集接近缓存大小的负载，64 位可能反而更慢。

2. **32 位进程能访问超过 4GB 的内存吗？**（补充练习）

   单个进程的虚拟地址就 32 位，直接寻址上限 4GB。要处理更大数据只能靠内存映射文件分段换入换出、或改用 64 位进程。

3. **为什么装了 64 位系统还要跑 32 位程序，怎么跑的？**（补充练习）

   历史兼容：大量旧软件、插件、只有 32 位版本的库。Windows 用 WoW64、Linux 用多arch 库（`lib32`）做隔离与翻译，让 32 位程序在 64 位内核上运行。

### OS-024：多线程之间同步有哪些方式？

**常见问法**

- 多线程之间同步有哪些方式？
- 线程同步的手段有哪些，怎么选？

#### 面试回答

结论：按用途分两类记——互斥类保证「同一时刻只有一个在改」，协调类保证「按条件、按次序一起走」。

- 互斥锁／递归锁：保护临界区；递归锁允许同线程重入。
- 条件变量：配合互斥锁做「等待-唤醒」，生产者-消费者的标准件。
- 信号量：计数控制并发度，P／V 操作，不要求同一线程释放。
- 读写锁：读共享、写独占，适合读多写少。
- 自旋锁：忙等不换线程，只适合极短临界区。
- 原子操作／CAS：无锁计数器、标志位。
- 屏障（barrier）：多线程互相等待到齐再一起走。
- 一句选型：保护数据用锁，等条件用条件变量，限并发度用信号量，短临界区用自旋或原子。

#### 技术细节

**条件变量为什么必须配锁**

- `wait` 的语义是「原子地释放锁并挂起」——把「检查条件」和「进入等待」中间的竞态窗口关掉。
- 被唤醒后要重新抢锁并再次检查条件，所以代码惯例是 `while (!ready) cv.wait(lk)` 而不是 if——防虚假唤醒和条件被别人抢先改掉。

**锁的层次**

- 悲观互斥：Mutex／递归锁／自旋锁／读写锁，竞争失败就阻塞或忙等。
- 无锁手段：原子变量、CAS 重试循环；冲突高时活锁风险要评估。
- 只通知不传数据：条件变量、futex（Linux 下用户态锁的底层大多建在它上面）。

**Java 世界的对应物**

- JUC 锁（ReentrantLock 等）、synchronized、Semaphore、CountDownLatch／CyclicBarrier、BlockingQueue、volatile＋原子类。
- 细节见 [[专题题库/Java并发#JUC-022：CountDownLatch 解决什么问题，和 CyclicBarrier、Semaphore 怎么区分？|JUC-022：CountDownLatch 与 CyclicBarrier、Semaphore 的区分]]。

**容易混的一对**

- 同步（协调次序、互斥访问）≠ 通信（传数据）；管道、消息队列是通信手段，常常顺便实现了同步。

#### 深挖追问

1. **自旋锁什么时候比互斥锁好？**（补充练习）

   临界区只有几条指令、且锁持有时间远小于一次上下文切换开销时；否则忙等白烧 CPU，还拖累同核其他线程。

2. **这些方式为什么大多不能跨进程？**（补充练习）

   锁对象、条件变量、进程内信号量活在进程的地址空间里，别的进程看不见；跨进程要换成有内核标识的对象（System V／POSIX 信号量、文件锁），见 [[#OS-007：进程间通信有哪些方式，如何选择？|OS-007：进程间通信有哪些方式，如何选择？]]。

### OS-025：二维数组按行遍历与按列遍历为什么性能差异大？

**常见问法**

- 二维数组按行遍历和按列遍历在性能上有什么差异？
- 除了内存的因素，还有其它什么原因吗？

#### 面试回答

结论：按行遍历快、按列遍历慢，核心是访存局部性——C／Java 的二维数组按行主序存放，按行访问连续命中缓存行，按列访问每取一个元素就跳一整行，缓存几乎全 miss。

- 量化直觉：一次 miss 拉回整条缓存行（常见 64B，int 数组装 16 个元素）——按行等于“16 次访问付 1 次 miss”，按列则是 16 次 miss。
- 除“内存”外的其它原因（原题追问）：硬件预取器只认规律顺序流、按列的跨步地址它跟不上；TLB 每次要覆盖更多页；乱序执行隐藏 miss 的能力也被大跨度访问打穿。
- Java 还有一层：`int[][]` 是“引用的数组”，行本身也分散在堆上，按列遍历先 miss 行引用再 miss 数据，双重惩罚。
- 工程对策：真要列操作就转置后按行扫、循环分块（tiling）把活跃数据压进缓存行，或改一维数组 `i*cols+j` 摊平。

#### 技术细节

**行主序是语言／布局约定，不是硬件规律**

- C／Java／Python（NumPy 默认 C 序）行主序；Fortran、MATLAB、R、OpenGL GLSL 列主序——同一段算法换个语言，最优遍历方向可能反过来。
- 行主序下 `a[i][j]` 相邻 j 的地址相邻；列遍历的步长＝一行字节数，动辄几 KB，远超硬件预取器能跟进的窗口。

**“除内存外”的三层原因怎么说满（追问的标准结构）**

- 缓存行利用：顺序访问有效载荷 100%，跨步访问一条 64B 行只用 4B（int），带宽浪费 16 倍。
- 硬件预取：L1/L2 预取器对 stride=1 的流最有效；大跨步退化为按需加载，延迟藏不住。
- 地址翻译与乱序：页表项按访问的页复用，跨行访问来回踩不同页（TLB miss）；乱序窗口能重排的 miss 数量有限，跨步流会填满它。

**量级参考与验证方式**

- 大矩阵列遍历慢 3～10 倍是常见观测区间（取决于行宽与缓存层级），别说成固定倍数。
- 能报工具更显真做过：`perf stat` 看 cache-misses／dTLB-load-misses，改一版转置前后对比耗时——面试讲实验设计即可，不必有实测截图。

**与 Java 特性叠加的两个易混点**

- 边界检查开销在两种遍历里都存在，不是差异来源；差异只在访存模式——别把“按列慢”甩锅给 bounds check。
- 大数组 GC 视角：一维大数组会进 humongous／老年代复制成本不同，与遍历性能无关，被追问“还有其它开销吗”时再分层说。

#### 深挖追问

1. **编译器为什么不能把按列遍历自动优化成按行？**（补充练习）

   循环交换（loop interchange）在数组访问无依赖、边界不穿越时会做，但 Java 的别名与越界语义让很多交换不合法；访存模式是运行时行为，编译器补不了缓存行——最终还得靠数据布局。

2. **缓存行大小怎么确认？会不会影响并发场景？**（补充练习）

   Linux 下 `lscpu`／`/sys/devices/system/cpu/cpu0/cache/index0/size、coherency_line_size` 可查。并发共享变量落在同一行会伪共享（false sharing），用 `@Contended`／字段填充隔离——那是另一类“缓存行惹的祸”，被追问时可主动区分。
