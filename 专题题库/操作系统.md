### OS-001：fork 后父子进程共享什么，是否复制父进程内容？

**常见问法**

- fork 一个进程，父子共享什么？
- 子进程会复制父进程的内容吗？

#### 面试回答

fork 后父子进程具有独立虚拟地址空间，初始内容相同，Linux 通常用写时复制共享物理页，写入时再分离。文件描述符表会复制，但对应描述符指向同一 open file description，因此共享文件偏移和相关状态。显式共享内存仍可共享；普通堆栈变量的修改不会直接同步到另一进程。

#### 技术细节

复制的是进程视图和必要管理结构，并非立刻复制全部物理内存；页表及内核结构仍有成本。父子拥有不同 PID，fork 在父进程返回子 PID、在子进程返回 0。COW 页面写入触发缺页处理并获得私有页，MAP_SHARED 则保留共享语义。多线程进程 fork 后，子进程只保留调用线程，继承的锁可能处于不可用状态，通常应尽快 exec 并遵守相关接口限制。

#### 深挖追问

1. **子进程会复制父进程内容吗？**（面经实际出现；[[面经/拼多多/一面/0001#Q14：fork 后父子进程共享什么，子进程是否复制父进程内容？|MJ003 Q14]]）

   逻辑上初始地址空间内容相同，物理页通常延迟到写入才复制；不是完全不复制，也不是马上复制所有内存。

2. **子进程 close 一个文件描述符，父进程还能用吗？**（补充练习）

   通常能，各自描述符表独立；关闭减少引用，不会直接删除父进程自己的描述符。

### OS-002：子进程结束后，父进程需要处理吗？

**常见问法**

- 子进程结束后，父进程需不需要处理？

#### 面试回答

通常需要通过 wait 或 waitpid 回收子进程的退出状态，否则退出记录可能保留成僵尸进程。父进程可以监听 SIGCHLD 后循环非阻塞回收，避免只处理一个退出事件。若明确配置了自动回收机制，则可不逐个等待，但也可能无法再获得退出状态。

#### 技术细节

僵尸进程已停止执行，大部分资源已释放，但 PID 和退出信息仍保留。waitpid(-1, &status, WNOHANG) 可循环回收当前已退出子进程；返回 0 表示还有子进程但暂未退出，-1 需区分 EINTR 与 ECHILD。SIGCHLD 可能合并，不能假定每个信号对应一个子进程。Linux 下显式 SIG_IGN 或 SA_NOCLDWAIT 可影响僵尸保留；默认信号处置不能简单等同于显式忽略。孤儿进程与僵尸不同，孤儿通常由 subreaper 或 init 等接管。

#### 深挖追问

1. **能用 kill 杀掉僵尸进程吗？**（补充练习）

   不能让已经退出的进程再退出；需由父进程或接管者回收其状态。

2. **为什么用循环 waitpid？**（补充练习）

   一次信号可能代表多个子进程退出，需要一直回收到没有可回收项。

### OS-003：4 GB 内存机器连续申请四次 1 GB，一定会 OOM 吗？

**常见问法**

- 分四次，每次分配 1 GB，系统内存只有 4 GB，这时会爆吗？

- 进程调用 malloc 后，操作系统立即分配物理内存吗？

#### 面试回答

不一定，要区分申请虚拟地址空间与实际触碰物理页。Linux 的 overcommit 策略、swap、进程地址空间限制和容器配额都会影响结果。申请可能成功，真正写入大量页面时才出现回收、换页或 OOM；严格提交策略也可能在申请阶段失败。系统本身也占内存，不能认为 4 GB 都能给这个进程。

#### 技术细节

malloc/mmap 返回成功并不代表全部物理页已经分配；应比较只申请、逐页写入两种实验。Linux overcommit_memory 的 0 为启发式、1 为宽松提交、2 为限制提交，具体可提交额度还受 swap 等因素影响。cgroup 内存限制可能小于主机容量；32 位地址空间也可能先成为约束。检查返回值、RSS、提交量及 OOM 事件，区分分配失败和随后进程被终止。此题仅讨论原理，不应在用户主机上执行耗尽内存实验。

malloc 不是每次都调用内核：可从分配器已持有的空闲块返回。需要新映射时，得到虚拟地址也不代表所有页已驻留；首次访问可能触发按需分配。分配器重用的页可能已经有物理页，因此也不能说 malloc 后绝对没有物理内存。

#### 深挖追问

1. **只读新分配区域和逐页写入一样吗？**（补充练习）

   不一定，匿名内存读取可能利用共享零页等优化，写入更直接触发私有物理页分配。

2. **free 后 RSS 一定立即下降吗？**（补充练习）

   不一定，分配器可能保留内存以复用，归还应用堆与归还内核是不同阶段。

3. **malloc 后操作系统立即分配物理内存吗？**（面经实际出现；[[面经/百度/三面/0001#Q07：进程调用 malloc 后，操作系统立即分配物理内存吗？|MJ010 · 百度 · 三面 · Q07]]）

   不保证；可能复用已有物理页，也可能只建立虚拟映射并延迟分配，取决于分配器和系统策略。

### OS-004：write 返回后，文件里立刻有数据吗？

**常见问法**

- write（字符串）后，文件里立刻就会有吗？

#### 面试回答

要区分可见性和持久化。对普通本地文件，成功的 write 通常把数据交给内核页缓存，后续读取可看到已写入部分，但不代表数据已经落到持久介质。若要求持久化，需要正确使用 fsync 或 fdatasync 并检查错误；如果调用的是带用户态缓冲的库函数，还需区分 flush 到内核这一步。

#### 技术细节

write 可能短写或被中断，返回值是实际写入字节数，应循环处理剩余部分。fflush 只把 stdio 缓冲交给底层，不能代替 fsync。新建或重命名文件还涉及目录项持久化，必要时同步目录；远程文件系统和存储设备具有额外语义。不要把“磁盘没落盘”说成“其他进程必然读不到”，也不能只调用 close 就宣称断电不丢。原题 write（字符串）未给语言和 API，回答以 POSIX 普通文件为基准并说明前提。

#### 深挖追问

1. **fsync 文件后新文件名一定持久了吗？**（补充练习）

   目录项有独立持久化要求，可靠创建或重命名流程还需考虑同步所在目录。

2. **write 返回的长度小于请求长度怎么办？**（补充练习）

   推进偏移并继续写剩余数据，处理 EINTR、错误和适用场景下的 EAGAIN。

### OS-005：进程、线程和协程有什么区别，协程适合什么场景？

**常见问法**

- 进程、线程和协程有什么区别，协程适合什么场景？

- 进程、线程、协程有什么区别，进程间如何通信？

- 进程、线程、协程有什么区别？

- 进程和线程的区别是什么？

- PDF 解析、模型调用、网络 IO 分别适合进程／线程／协程哪种？

#### 面试回答

进程是资源与地址空间的隔离单位；线程是进程内的执行单元，同进程线程共享堆等资源，各有调用栈和执行状态；协程由语言运行时或库管理暂停、恢复与调度，通常比内核线程更轻。协程适合大量网络请求等 I/O 等待较多的并发任务，能用较少线程承载很多等待中的工作；CPU 密集任务要想多核并行，仍需多个实际执行线程或进程。

#### 技术细节

以常见 Linux 线程为前提，线程由内核调度；协程模型随语言而异，有无栈、有栈和不同调度策略。协程切换通常保存必要执行状态而不直接触发内核线程切换，但网络等待、系统调用仍涉及内核。单线程协程若直接执行阻塞调用，可能阻塞整个事件循环；Go 等运行时有不同处理机制。共享可变数据仍可能有竞态，并发不等于并行。

#### 深挖追问

1. **协程适合什么场景？**（面经实际出现；[[面经/百度/一面/0003#Q02：进程、线程和协程有什么区别，协程适合什么场景？|MJ006 · 百度 · 一面 · Q02]]）

   高并发网络服务、并发调用下游等等待占比高的任务；需配合异步 I/O 或运行时调度，限制并发数并处理取消，避免把所有阻塞操作直接放入单线程事件循环。

2. **PDF 解析、模型调用、网络 IO 各选哪种执行单元？**（面经实际出现；[[面经/帆软/一面/0001#Q07：PDF 解析、模型调用、网络 IO 分别适合进程／线程／协程哪种？三者区别与开销对比？|MJ022 · 帆软 · 一面 · Q07]]）

   先分负载：PDF 解析 CPU 密集，要并行就得多进程（隔离强、崩溃互不影响，适合解析不可信文档的安全边界；Python 受 GIL 更是必须多进程）或 Java 按核数限并发的线程池；模型调用与网络 IO 等待占比高，协程/异步 IO 用少量线程承载海量等待最合适（Java 场景可用虚拟线程或线程池包裹阻塞调用）。开销对比：进程切换与通信最重、隔离最好；线程共享堆切换较轻但有竞态；协程用户态调度切换最轻、单线程内天然无竞争，但阻塞调用会卡住整个循环且不吃多核。

### OS-006：什么是系统调用，用户态和内核态有什么区别？

**常见问法**

- 什么是系统调用，用户态和内核态有什么区别？

- 用户态和内核态有什么区别？

- 操作系统有用户态和内核态，分别讲一下是什么。

#### 面试回答

系统调用是用户程序请求内核服务的受控入口，例如读写文件、创建进程和操作网络。用户态权限受限，不能任意访问内核内存或执行特权操作；内核态可按硬件权限执行资源管理操作。程序通过系统调用指令进入内核，内核检查参数和权限、执行服务并返回用户态。

#### 技术细节

用户态／内核态描述 CPU 执行权限，不是两个互相独立的进程。一次系统调用有模式切换与保存恢复状态的开销，但不必发生线程或进程调度切换。库函数不与系统调用一一对应：缓冲 I/O 可能合并多次调用，部分服务可经 vDSO 完成；malloc 也不必每次向内核申请。中断、异常同样可引发进入内核，不能全部称为应用主动系统调用。

#### 深挖追问

1. **系统调用一定会切换到另一个进程吗？**（补充练习）

   不一定；可在当前线程上下文完成服务，只有阻塞或调度等条件才可能切换执行任务。

2. **为什么要区分两种权限，进内核一定慢吗？**（面经实际出现；[[面经/美团/一面/0001#Q03：操作系统的用户态和内核态分别是什么？|MJ031 · 美团 · 一面 · Q03]]）

   区分的目的是隔离与保护——用户程序不能直接改页表、访问别人内存或发特权指令，否则任何进程都能拖垮全系统。进入内核本身有保存寄存器、检查参数和权限的固定成本，通常几百纳秒量级；真正贵的是随之而来的阻塞、拷贝和可能的调度，因此优化方向是**减少次数**（缓冲 I/O、批量 syscall、vDSO、io_uring、零拷贝）而不是“别进内核”。

### OS-007：进程间通信有哪些方式，如何选择？

**常见问法**

- 进程间通信有哪些方式，如何选择？

- 线程之间怎么通信？那进程间的通信方式呢？

#### 面试回答

进程间可用管道、命名管道、消息队列、共享内存、信号和 Socket。共享内存适合批量共享数据但要另做同步；信号偏向事件通知，Socket 可用于同机或跨机通信。

#### 技术细节

管道适合字节流传递，匿名管道常用于有继承关系的进程，FIFO 可通过路径连接进程；消息队列保留消息边界；共享内存让进程映射共同内存，需要互斥量或信号量等协调访问；信号用于异步通知，不适合传大块数据；Unix domain Socket 适合同机双向通信，网络 Socket 可跨机。选择时考虑数据量、边界、同步、生命周期和是否跨主机。

### OS-008：Linux 进程地址空间与物理内存布局如何区分？

**常见问法**

- Linux 进程地址空间与物理内存布局如何区分？

#### 面试回答

### OS-012：什么是内存抖动，工作集模型如何缓解？

**常见问法**

### OS-013：FIFO、LRU 和 Clock 页面置换有什么特点？

**常见问法**

- FIFO、LRU、Clock 页面置换算法各有什么特点？

#### 面试回答

FIFO 淘汰最早进入的页面，简单但不利用近期访问，并可能出现 Belady 异常。LRU 淘汰最久未访问的页面，符合时间局部性但精确维护有成本。Clock 环形扫描引用位，给近期访问页第二次机会，是低成本近似。

#### 技术细节

Clock 扫到引用位为 1 的页就清零并继续，为 0 则选作候选；增强变体还考虑脏位与写回成本。精确 LRU 有栈性质，增加页框不会出现 FIFO 那样的 Belady 异常；Clock 不等于精确 LRU。这里讨论教材算法，不把它们当作所有系统的实际实现。

#### 深挖追问

1. **FIFO 为什么会有 Belady 异常？**（补充练习）

   它不保证小容量缓存集合始终包含于大容量集合，增加页框改变淘汰顺序，某些访问串反而缺页更多。

### OS-014：死锁的四个必要条件是什么，如何处理？

**常见问法**

- 死锁的四个必要条件是什么？

- 什么是死锁？

#### 面试回答

四个必要条件是互斥、占有且等待、不可剥夺和循环等待。互斥指资源同一时刻只能由一个执行单元使用；占有且等待指持有部分资源时继续等待其他资源；不可剥夺指已分配资源不能被外部强制收回；循环等待指等待关系形成闭环。四者同时成立才可能发生死锁，破坏任意一个即可预防。

#### 技术细节

常见处理思路包括：通过固定的全局加锁顺序破坏循环等待；一次申请全部必要资源或申请失败时释放已持有资源，破坏占有且等待；在资源允许时支持抢占；通过 Banker 等策略做避免；或允许发生后检测等待图中的环，并选择事务／进程回滚恢复。数据库常通过死锁检测选择牺牲者，应用应重试完整事务。超时可解除长期等待，但可能把慢操作误判为死锁，也不保证环在业务层从未形成。

例如线程 A 先锁资源 1 再等资源 2，线程 B 先锁资源 2 再等资源 1，就形成循环等待。将两者都规定为先锁编号较小资源，能消除这个环。实际诊断需结合线程栈、锁持有者或数据库死锁日志，不能仅凭“请求很慢”断言死锁。

#### 深挖追问

1. **死锁与饥饿有什么区别？**（补充练习）

   死锁中的一组执行单元互相等待，若无外力不会推进；饥饿是某个执行单元长期得不到调度或资源，系统中其他工作仍可能持续推进。

2. **超时能否从根本上预防死锁？**（补充练习）

   不能。超时通常是检测或恢复手段，还会误伤只是执行较慢的请求；预防需破坏必要条件。

3. **Java 里怎么确认“真的是死锁”而不是慢？**（面经实际出现；[[面经/美团/一面/0001#Q06：什么是死锁？|MJ031 · 美团 · 一面 · Q06]]）

   抓线程栈看等待关系：`jstack <pid>` 会在末尾直接输出 “Found one Java-level deadlock” 并列出互相持有的 monitor；程序内可用 `ThreadMXBean.findDeadlockedThreads()` 拿到线程 ID 数组。判据是“线程 A 持有 X 等 Y、线程 B 持有 Y 等 X”这种闭环，配合 `Thread.getState()` 为 BLOCKED/WAITED 且长期不变。只有“响应慢”而没有闭环证据不能断言死锁，可能是锁竞争激烈、外部依赖卡住或 GC 停顿。完整处理策略见 [[#OS-017：死锁如何预防、避免、检测和恢复？|OS-017：死锁如何预防、避免、检测和恢复？]]。

### OS-015：并发和并行有什么区别，IO 密集型适合哪种？

**常见问法**

- 并发和并行是什么，有什么区别？
- IO 密集型适合并发还是并行？

#### 面试回答

并发是同一时间窗口内多个任务都在推进——单核上靠时间片交替，任一时刻其实只有一个任务在执行；并行是多个任务在多个核上同一时刻物理执行。一句话：并发是一种处理多任务的程序结构，并行是利用多核同时执行的运行状态。IO 密集型任务耗时大头在等待设备与网络、不占 CPU，适合用高并发组织——异步 I/O、事件循环或协程能用少量线程承载大量等待中的连接，盲目开很多并行线程只会增加上下文切换开销。CPU 密集型要提升吞吐必须靠多核并行，单靠并发结构不会更快。准确说法是：IO 密集的边际收益来自并发，CPU 密集的吞吐来自并行，真实服务往往两者兼有。

#### 技术细节

并发不等于“多线程”：单线程事件循环靠非阻塞 I/O 也能承载上万连接数（参见 [[专题题库/Linux#LINUX-002：select、poll、epoll 有什么区别？|LINUX-002：select、poll、epoll 有什么区别？]]）；线程数也不必等于核数，IO 密集常按“并发量≈目标 QPS×平均延迟”估算所需在途任务数，再结合连接池与下游容量设上限。并行度受核数约束，但共享可变数据的锁竞争、伪共享和 Amdahl 定律会让加速比低于核数。协程适合把“等待”从线程里剥离，但单线程运行时里执行一个阻塞调用会卡住整个循环（Go 等有专门处理，见 OS-005）。误区是把“提高并发数”当成万能：过并发只会加剧切换、内存和下游过载，需限流与背压。CPU 密集交给事件循环不会变快，因为无人让出时被计算任务独占。

#### 深挖追问

1. **IO 密集型开线程越多越好吗？**（补充练习）

   否。超过等待与切换收益后，更多线程只增内存与调度成本；应用异步 I/O 或有界线程池＋限流。

2. **纯并发结构能让 CPU 密集任务变快吗？**（补充练习）

   不能。它只是复用同一段时间，计算吞吐要提上去需要多核并行，且要处理数据分片与竞争。

### OS-016：操作系统有哪些基本功能？

**常见问法**

- 先说一下操作系统有哪些功能。
- 操作系统的作用是什么？

#### 面试回答

操作系统有两个身份：对上是屏蔽硬件差异的统一抽象接口，对下是全局限价的资源管理者。功能按管理对象分六块——进程/线程管理（创建撤销、调度、切换、同步与通信）、内存管理（地址映射、分配回收、虚拟内存与页面置换）、文件管理（目录、空间分配、读写与权限）、设备管理（驱动抽象、缓冲、I/O 调度与假脱机）、网络与进程间通信、安全保护（身份认证、隔离与访问控制）。一句话概括：把硬件的复用、共享与安全隔离统一收口，让应用不必也不允许直接碰硬件。

#### 技术细节

各子系统的典型机制值得各举一例，避免只报名词：进程管理含 PCB 与上下文切换、调度算法（CFS 等）；内存管理含分页分段、MMU 地址翻译、缺页处理与 LRU/Clock 置换（见 OS-013）；文件系统含索引节点、journal 日志与页缓存（写回语义见 OS-004）；设备管理含中断、DMA 与 I/O 队列；安全含用户态/内核态权限边界（OS-006）、uid/GID 与命名空间隔离。
两处易错点：① 虚拟内存、分页、调度、文件系统这些“功能”由内核提供，但用户态看到的很多能力实际落在运行时库、守护进程或内核旁路（vDSO、io_uring、DPDK）里，说“操作系统做了 X”时要区分内核态与用户态职责；② 现代操作系统功能持续演进（如透明大页、cgroup 资源控制属于资源管理而非传统“五大功能”表述），教材口径与实现口径不完全一致，回答时先说明按经典分类展开。

#### 深挖追问

1. **操作系统和虚拟机管理器（Hypervisor）的功能边界有什么不同？**（补充练习）

   操作系统管理单机硬件并为进程划资源；Hypervisor 把“物理机”本身虚拟化，为多个客户机 OS 分配虚拟 CPU/内存/设备，Type-1 直接跑在硬件上、Type-2 仍依赖宿主 OS。容器不复制这一层——它共享宿主内核，靠 namespace＋cgroup 做视图与配额隔离（参见 [[专题题库/容器与编排#CLOUD-001：Docker 容器和虚拟机有什么区别，为什么更轻量？|CLOUD-001：Docker 容器和虚拟机有什么区别，为什么更轻量？]]）。

2. **为什么说操作系统是“资源管理者”而不是“程序库”？**（补充练习）

   多个执行单元竞争同一份有限资源，只有内核掌握全局视图与抢占权，能做仲裁、配额与优先级；程序库只服务单个进程，无法跨进程约束。这也是特权指令必须收进内核态的原因。

### OS-017：死锁如何预防、避免、检测和恢复？

**常见问法**

- 怎么样避免产生死锁？还有别的吗？
- 如果发生了死锁，要怎么解除或恢复？
- 死锁的处理策略有哪些？

#### 面试回答

四条路线按“事前—事中—事后”排：① 预防——静态破坏四个必要条件之一，应用层最常用的是固定全局加锁顺序（破坏循环等待）和一次申请齐所需资源或申请失败先释放已持有资源（破坏占有且等待），锁超时与可抢占锁破坏不可剥夺；② 避免——分配时动态判断是否会进入不安全状态（Banker 算法类），需要预知最大资源需求，通用系统里很少真正落地；③ 检测——允许死锁发生，周期性或不定期扫描资源分配图/等待图找环；④ 恢复——破坏不可剥夺，回滚或杀掉环上的牺牲者并释放资源。工程实践主流是“预防为主＋检测恢复兜底”，不追求严格避免。

#### 技术细节

**预防**要能落到代码约定：把所有锁排一个全局次序（按资源 ID、按加锁层级），所有路径都按同一顺序获取；锁范围尽量小、不要在持锁时调用可能反向加锁的外部接口（回调、RPC、消息处理）；需要多锁时用 `tryLock(timeout)` 组合，拿不到就全部释放重试，注意重试要带退避避免活锁。
**避免**的代价是要知道每个任务的资源上限并每次分配做安全性检查，开销大且信息常不可得，所以教科书算法与线上实现差距明显。
**检测**：Java 可直接用 `jstack` 线程 dump 里的 “Found one Java-level deadlock” 段，或 `ThreadMXBean.findDeadlockedThreads()`；JDBC/MySQL 侧查 `SHOW ENGINE INNODB STATUS` 的 LATEST DETECTED DEADLOCK；InnoDB 自带 wait-for graph 检测并主动回滚代价较小的事务；分布式场景（跨服务互相持锁等待）没有全局等待图，一般靠超时、租约（如 Redis 锁的 TTL＋fencing token）和业务侧对账来兜。
**恢复**四种手段及副作用：杀进程/线程（最简单，丢未提交工作，应用必须能容错重启局部任务）、回滚事务（数据库自动选 undo 量小的牺牲者，业务要重试**完整事务**而不是只重放报错那条语句）、抢占资源（把资源从持有者剥夺给他人，只有状态可回退的资源如数据库锁可行，普通内存/文件锁不可行）、重启实例（无法在线解除时的最后手段，恢复后仍要修加锁顺序防复发）。
超时属于“解除等待”的手段而不是预防：它可能把只是慢的操作误判为死锁，也可能让两个请求同时超时后互相重复撤销，因此超时解套要求业务幂等，并保留事后一致性核对。

#### 深挖追问

1. **预防、避免、检测三者的区别是什么？**（面经实际出现；[[面经/美团/一面/0001#Q07：怎么避免产生死锁？还有别的办法吗？|MJ031 · 美团 · 一面 · Q07]]）

   预防是静态破坏必要条件（永不发生）；避免是分配时动态判断并拒绝会通向死锁的分配（不发生但需预知需求）；检测允许发生再找环处理。三者在“约束强度、运行时开销、所需信息”上依次让步。

2. **银行家算法在真实系统里用得多吗？**（补充练习）

   很少。它要求提前声明各资源的最大需求且在每次分配做 O(n×m) 安全性检查，真实系统资源粒度动态、数量可变，代价与信息可得性都不划算；实际更多用配额、限流、租约与优先级抢占达到类似“不进不安全状态”的效果。

3. **MySQL 死锁发生了，应用该怎么写？**（面经实际出现；[[面经/美团/一面/0001#Q08：发生了死锁要怎么解除或恢复？|MJ031 · 美团 · 一面 · Q08]]）

   捕获 1213 死锁错误码后按有限次数、带退避地重试**整个事务**；重试前不要假设上一次的部分写入仍在（引擎已回滚该事务）；同时排查 SQL 顺序与索引——索引没走对会让锁范围从行锁扩大为大量行甚至间隙锁，很多“莫名死锁”实际是加锁顺序＋扫描范围问题，只调超时参数掩盖不了。

4. **只有超时没有检测，会不会漏掉问题？**（补充练习）

   会。超时解套后系统看似恢复，但等待环的成因没被记录，高并发下会以“偶发慢请求”的形式反复出现；线上要保留线程栈采样、锁等待统计与数据库死锁日志，事后能定位到具体持锁路径才算闭环。

### OS-018：什么是 I/O 零拷贝，sendfile 和 mmap 如何减少拷贝？

**常见问法**

- I/O 的“零拷贝”技术是指什么？

#### 面试回答

以“把磁盘文件通过 socket 发送出去”为例，传统路径是：`read()` 让 DMA 把数据从磁盘读进**内核页缓存**，再把页缓存拷进**用户态缓冲区**；`write()` 又把用户缓冲区拷回**内核 socket 缓冲区**，最后 DMA 从 socket 缓冲区发到网卡——共 4 次拷贝、2 次上下文切换，其中“内核↔用户”来回那两次纯属浪费。**零拷贝**的目标就是省掉 CPU 参与的用户态/内核态冗余拷贝：

- **`sendfile()`**：数据全程留在内核，从页缓存直接送到 socket，配合 scatter-gather DMA 网卡可做到 CPU 零次拷贝；一次系统调用完成。
- **`mmap()` + `write()`**：把文件映射进用户地址空间，省掉 `read` 那次“拷到用户缓冲区”的拷贝（仍有 socket 缓冲一次拷贝），适合还要对数据做处理/共享的场景。
- **`splice()`/`tee()`**：用管道在内核态搬数据。

收益：减少拷贝次数与上下文切换、降低 CPU 与内存带宽占用。典型使用者：Kafka（`sendfile` 做日志复制/消费）、Nginx 静态文件、Netty 的 `FileRegion`。

#### 技术细节

“零拷贝”不等于“一次拷贝都没有”，而是“CPU 不再负责把数据在用户态和内核态之间来回搬”——DMA 从磁盘到页缓存、从缓冲到网卡仍由 DMA 完成，这不占 CPU。经典四次拷贝里只有第 2、3 次（内核↔用户）被消除。要不要用 `mmap` 还是 `sendfile`：需要读取并处理内容（改、算、共享）用 `mmap`；纯“搬运”透传用 `sendfile` 更省。`mmap` 的坑：文件被截断后再访问越界页会 `SIGBUS`；小文件因页表与映射建立开销，`mmap` 未必比 `read/write` 快；脏页写回由内核异步控制，需 `msync` 才保证落盘时机。

#### 深挖追问

1. **零拷贝为什么能提升 Kafka／Nginx 这类吞吐？**（补充练习）

   它们主要做“数据搬运”而非计算，`sendfile` 让数据不进用户态，省掉两次拷贝＋一半系统调用，并减少页缓存与 socket 缓冲之间的一致性开销，因而能把 CPU 留给网络与磁盘 I/O 本身。
