### ES-001：Elasticsearch 底层搜索用的什么数据结构，倒排索引如何工作？

**常见问法**

- ES 底层的搜索数据结构了解吗？
- 具体讲一下倒排索引的算法或者数据结构。

- 为什么 ES 要使用倒排索引，它相比顺序扫描的好处是什么？

#### 面试回答

倒排索引把“文档→词”的正排翻转为“词→文档列表”：term 字典（词典树）映射到 postings list——含该词的有序文档 ID 序列及其词频、位置信息。查询 `后端 AND 面试` 就是取两条 postings 求交集：term 在字典中有序、postings 按 doc ID 升序，交集用双指针归并，长列表配跳表指针按块跨跳，不必逐个比对。postings 存的是差值（delta 编码）再分块压缩（FOR／PFor 类位压缩），相邻 doc ID 差值小，省空间又固化了有序性。term 字典用 FST（有限状态转换机）把共享前缀的词典压到很小、可常驻内存，磁盘项按块加载。对比 MySQL：B+ 树适合精确与最左前缀匹配，任意词项组合需要指数级索引条目，所以全文检索必须换倒排结构。加分项是报出一次查询的完整路径：分词→词项查字典→跳表定位→BM25 打分（词频、逆文档频率、字段长度归一）→命中文档从存储侧取回；排序聚合不走倒排，走 doc values 列存。

#### 技术细节

- 组成清单：term dictionary（FST）、postings（delta＋分块压缩＋跳表）、positions／offsets（短语与高亮需要）、term frequencies 与 norms（打分）、doc values（列式正排，排序／聚合／脚本用）、_source（原始 JSON，返回与重建索引用）。
- 段（segment）不可变：写入进 in-memory buffer，refresh（默认约 1s）生成新段可搜——所以 ES 是“近实时”不是实时；删除是记墓碑段，更新是删旧加新，后台 merge 合并小段并物理清除。段不可变换来无锁并发读与顺序写，代价是删除更新有延迟、需要 merge 预算。
- 多条件查询执行：filter 子句先算（位图缓存、无打分），must 子句走打分交集，coordinate 节点汇总各分片 top-N 归并。
- 深分页成本：from+size 语义下每个分片都要返回 from+size 条给协调节点合并，越深放大越狠——解法见 [[#ES-002：binlog 监听同步到 ES 的架构里，ES 起什么作用，高流量搜索如何承接？|ES-002]] 的 search_after。

#### 深挖追问

1. **FST 为什么适合做 term 字典？**（补充练习）

   词典共享前缀与后缀，FST 把有公共子序列的词压成一张有向无环图，内存占用比哈希表小一个量级，还能支持前缀枚举与范围扫描；term 排序是字典序，范围查询与自动补全顺路可得。

2. **为什么 doc values 是列存而不是直接用倒排或 _source 排序？**（补充练习）

   排序／聚合要按字段值遍历全部命中文档：_source 要先解 JSON、倒排结构方向反了；列存把同一字段的值连续存放，顺序 IO＋向量化处理，还能用 file cache 常驻页缓存。

3. **倒排索引对高基数数值字段为什么不划算？**（补充练习）

   每个不同值一条 term、一条 postings，字典爆炸；数值范围查询用 BKD 树（Lucene 的 points 结构）而非倒排——答题时能区分“文本倒排、数值 BKD、正排 doc values”三条索引路径是深度信号。

4. **不建索引、直接顺序扫描（如 `LIKE '%kw%'`）行不行，差在哪？**（面经实际出现；[[面经/小红书/一面/0001#Q07：MySQL 和 Elasticsearch 有什么区别、各自适用什么场景；ES 为什么要用倒排索引，相比顺序扫描好在哪？|MJ040 · 小红书 · 一面 · Q07]]）

   三重差距：一是代价——顺序扫描要读遍文档／行，成本随数据量线性增长，倒排的代价与命中的 posting 规模相关而不是与全表行数相关；二是能力——中缀匹配的 `LIKE '%kw%'` 用不上 B+ 树（只能前缀），也拿不到分词、词频与位置信息，因此没有相关性打分、短语匹配和高亮；三是并发——扫描期间占用大量 IO 与缓冲池，搜索与交易互抢资源。倒排的补偿是它把“找词”变成查字典＋归并有序列表，但要把代价一起说：建索引与段合并吃 IO、更新要重写段所以近实时、占额外磁盘，所以它服务读模型而不是替代主存储。

### ES-002：binlog 监听同步到 ES 的架构里，ES 起什么作用，高流量搜索如何承接？

**常见问法**

- 用 binlog 监听后，数据更新到 ES，那你的 ES 在这里的作用是什么？
- ES 面向用户提供的功能是搜索什么内容的？
- 流量最高的时候会直接打到 ES 吗？

#### 面试回答

ES 在这条链路里承担“搜索读模型”：事实源仍是 MySQL，canal 类组件订阅 binlog 把变更同步进 ES，业务写不改一行代码；之所以要 ES，是因为需求里存在 B+ 树解决不了的查询——分词全文匹配、多字段任意组合过滤、相关性排序与聚合统计，LIKE 全表扫描在数据量上不可用，而 ES 用倒排索引把它们做成毫秒级（原理见 [[#ES-001：Elasticsearch 底层搜索用的什么数据结构，倒排索引如何工作？|ES-001：倒排索引如何工作]]）。选 CDC 而不是业务双写的理由：双写侵入每个写入口、失败补偿逻辑散落，CDC 以 binlog 为单一事实源集中同步，接受秒级最终一致——搜索场景对“新数据多久可搜到”的容忍度要与产品对齐。面向用户搜索的内容属项目事实，按【商品／帖子／文档等，写清索引字段与更新频率】填写。流量最高时不直接裸打 ES：入口对热点查询加结果缓存（key 含查询参数与版本），ES 侧靠副本分片水平扩读、按容量压测定分片数，filter 缓存复用高频过滤，写入洪峰走 bulk 攒批；同时设护栏——深分页改 search_after 游标、复杂查询限额、过载时熔断降级到兜底页或缓存旧结果，大促前预热段缓存与新索引。

#### 技术细节

- 同步链路要点：binlog 行事件→解析→转换（拼接多表字段需宽表建模或 nested／join 权衡）→bulk 写入；按主键 hash 分区保同键有序，失败重放依赖幂等的 upsert 语义（以文档 ID 覆盖写）；对账任务定期比对 MySQL 与 ES 计数与抽样字段，CDC 延迟监控与优化见 [[专题题库/系统设计#SYS-024：canal／binlog 订阅同步延迟如何归因与优化？|SYS-024：canal 同步延迟归因]]。
- ES 的写入代价：refresh／translog／merge 决定它是“近实时读模型”而非存储引擎，不能当数据库用；数据规模上去了先问“该不该缓在 ES”，明细与指标分离的取舍见 [[专题题库/系统设计#SYS-022：千万到亿级 trace／日志如何存储与检索？|SYS-022：亿级日志存储检索]]。
- 承接读流量三件套：副本分片（扩读）、请求级缓存（高频聚合 size=0 查询可命中 request cache）、过滤位图缓存；结果级缓存放应用层，因为 ES 自身不缓存打分结果集。
- 深分页：`from+size` 每分片取 from+size 条再归并，页越深放大越狠；search_after 带上一页排序值作游标（排序必须加唯一 tiebreaker 字段），配合时间／租户过滤限制扫描面——与 MySQL 大分页的 seek 法同思路（见 [[专题题库/MySQL#MYSQL-019：大分页查询怎么优化？|MYSQL-019：大分页优化]]）。

#### 深挖追问

1. **为什么流量最高时反而更要避免“直打 ES”？**（面经实际出现；[[面经/虾皮/一面/0001#Q07：binlog 监听后数据更新到 ES，ES 的作用是什么、搜索什么内容、流量最高时直接打到 ES 吗？|MJ036 · 虾皮 · 一面 · Q07]]）

   ES 单次打分查询 CPU 开销大、且查询之间互相争抢分片线程池，洪峰下慢查询堆积会雪崩式拖垮整个集群——所以高流量先问“能不能不查 ES”（缓存、降级），必须查的限并发、限复杂度，而不是加机器硬扛。

2. **同步延迟期间用户搜不到刚发布的内容怎么办？**（补充练习；与 [[专题题库/系统设计#SYS-024：canal／binlog 订阅同步延迟如何归因与优化？|SYS-024]] 的归因思路共用）

   产品层兜底：发布成功页直接回显详情（读主库）、个人中心走 DB 实时查询，搜索入口接受秒级延迟；技术上压缩链路延迟（增量 bulk 攒批窗口、监控位点）并向业务暴露“可搜索延迟”SLA。

3. **ES 挂了这条链路怎么降级？**（补充练习；口径见 [[专题题库/系统设计#SYS-015：数据库故障无法写入时如何降级与恢复？|SYS-015：数据库故障降级]] 的故障预算思维）

   搜索功能降级为“不可用但页面活着”：返回缓存的热门列表或分类导航，引导用户走精确过滤；写入链路（binlog→ES）可暂停堆积，恢复后按位点追平，ES 无需回补事务语义。

4. **MySQL 和 Elasticsearch 有什么区别，各自适用什么场景？**（面经实际出现；[[面经/小红书/一面/0001#Q07：MySQL 和 Elasticsearch 有什么区别、各自适用什么场景；ES 为什么要用倒排索引，相比顺序扫描好在哪？|MJ040 · 小红书 · 一面 · Q07]]）

   按“职责—模型—一致性—擅长查询”四层答：职责上 MySQL 是事务型主存（写入与业务真相），ES 是检索与分析的读模型；数据模型是行＋固定 schema vs JSON 文档＋动态映射与分词；一致性上 MySQL 有事务、唯一约束与强一致读，ES 没有跨文档事务、写入近实时（refresh 后可见）、更新是重写段；查询能力上 MySQL 擅长精确匹配、范围与 join（B+ 树），ES 擅长全文与相关性排序、任意字段组合过滤、高亮与聚合，但深分页、高基数聚合与频繁更新是它的短板。结论口径是“两者搭配而不是二选一”：写走 MySQL、搜索走 ES、用 CDC 同步并接受秒级延迟；只要事务与唯一性的数据不要放 ES，需要分词与聚合的查询不要硬压给 MySQL。
