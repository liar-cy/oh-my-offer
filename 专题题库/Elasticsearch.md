### ES-001：Elasticsearch 底层搜索用的什么数据结构，倒排索引如何工作？

**常见问法**

- ES 底层的搜索数据结构了解吗？
- 为什么 ES 能支持叶子查询和复合查询？
- 数据分布在多个分片上，范围查询的内部实现逻辑？
- 具体讲一下倒排索引的算法或者数据结构。
- ES 是怎么实现高效检索的？

- 为什么 ES 要使用倒排索引，它相比顺序扫描的好处是什么？

- 项目中 ES 的叶子查询是如何实现的？

#### 面试回答

一句话：倒排索引把“文档 → 词”的正排，翻转成“词 → 文档列表”。

- 结构：term 字典（词典树）映射到 postings list —— 含该词的有序文档 ID 序列，外加词频、位置信息。
- 举个例子：查 `后端 AND 面试`，就是取两条 postings 求交集。因为 term 在字典中有序、postings 按 doc ID 升序，交集用双指针归并就行；长列表再配跳表指针按块跨跳，不必逐个比对。
- 存储：postings 存的是差值（delta 编码）再分块压缩（FOR／PFor 类位压缩）。相邻 doc ID 差值很小，既省空间又固化了有序性。
- term 字典：用 FST（有限状态转换机）把共享前缀的词典压到很小，可以常驻内存，磁盘项按块加载。
- 对比 MySQL：B+ 树适合精确与最左前缀匹配，任意词项组合需要指数级索引条目，所以全文检索必须换倒排结构。

想加分就把一次查询的完整路径报出来：分词 → 词项查字典 → 跳表定位 → BM25 打分（词频、逆文档频率、字段长度归一）→ 命中文档从存储侧取回。补一句边界：排序聚合不走倒排，走 doc values 列存。

#### 技术细节

**索引里到底存了哪几样东西**

- term dictionary（词典，用 FST 存）。
- postings：delta＋分块压缩＋跳表。
- positions／offsets：短语匹配和高亮需要。
- term frequencies 与 norms：打分用。
- doc values：列式正排，排序／聚合／脚本用。
- _source：原始 JSON，返回结果和重建索引用。

**段（segment）不可变带来的取舍**

- 写入先进 in-memory buffer，refresh（默认约 1s）生成新段才可搜 —— 所以 ES 是“近实时”，不是实时。
- 删除是记墓碑段，更新是删旧加新，后台 merge 负责合并小段并物理清除。
- 换来的好处是无锁并发读和顺序写；代价是删除更新有延迟，还要留出 merge 的资源预算。

**多条件查询怎么执行**

- filter 子句先算：走位图缓存、不参与打分。
- must 子句走带打分的交集。
- 最后由 coordinate 节点汇总各分片的 top-N 做归并。

**深分页为什么贵**

- `from+size` 语义下，每个分片都要返回 from+size 条给协调节点合并，页越深放大越狠。
- 解法见 [[#ES-002：binlog 监听同步到 ES 的架构里，ES 起什么作用，高流量搜索如何承接？|ES-002]] 的 search_after。

#### 深挖追问

1. **FST 为什么适合做 term 字典？**（补充练习）

   因为词典里大量词共享前缀和后缀，FST 就把有公共子序列的词压成一张有向无环图。结果是内存占用比哈希表小一个量级，同时还能支持前缀枚举与范围扫描。另外 term 本身按字典序排列，范围查询与自动补全顺路可得。

2. **为什么 doc values 是列存而不是直接用倒排或 _source 排序？**（补充练习）

   因为排序／聚合要按字段值遍历全部命中文档，这个方向和倒排刚好相反；用 _source 还得先解一遍 JSON。列存把同一字段的值连续存放，好处是顺序 IO、可向量化处理，还能用 file cache 常驻页缓存。

3. **倒排索引对高基数数值字段为什么不划算？**（补充练习）

   每个不同值都要存一条 term、一条 postings，字典直接爆炸。数值范围查询走的是 BKD 树（Lucene 的 points 结构），而不是倒排。答题时能区分“文本走倒排、数值走 BKD、正排走 doc values”这三条索引路径，就是深度信号。

4. **不建索引、直接顺序扫描（如 `LIKE '%kw%'`）行不行，差在哪？**（面经实际出现；[[面经/小红书/一面/0001#Q07：MySQL 和 Elasticsearch 有什么区别、各自适用什么场景；ES 为什么要用倒排索引，相比顺序扫描好在哪？|MJ040 · 小红书 · 一面 · Q07]]）

   差在三重：

   - 代价：顺序扫描要读遍文档／行，成本随数据量线性增长；倒排的代价与命中的 posting 规模相关，而不是与全表行数相关。
   - 能力：中缀匹配的 `LIKE '%kw%'` 用不上 B+ 树（只能前缀），也拿不到分词、词频与位置信息，因此没有相关性打分、短语匹配和高亮。
   - 并发：扫描期间占用大量 IO 与缓冲池，搜索与交易互抢资源。

   倒排的补偿是它把“找词”变成查字典＋归并有序列表，但代价要一起说：建索引与段合并吃 IO、更新要重写段所以只是近实时、还要占额外磁盘。所以它服务读模型，而不是替代主存储。

5. **ES 的数据查询是在内存里还是磁盘上？**（面经实际出现；[[面经/菜鸟集团/一面/0001#Q06：ES 怎么实现高效检索？数据查询是在内存还是磁盘？|MJ084 · 菜鸟集团 · 一面 · Q06]]）

   分层答，没有非此即彼：磁盘是事实源，内存分三块各有用途——term 词典的 FST 等元数据常驻 JVM 堆；段数据（postings、doc values）存在磁盘，靠 Lucene 的 mmap／顺序读让 OS page cache 充当热数据缓存，所谓“查询走内存”实际是“热页恰好还在页缓存里”；fielddata／请求缓存才是真正进 JVM 堆的部分，所以要控基数与请求量，否则 Full GC。

   加分收束：容量规划的口径是“堆只放元数据、内存大头留给文件页缓存、监控看 cached_memory 与 pagecache 命中率”——把“内存还是磁盘”升维成“缓存分层”。

### ES-002：binlog 监听同步到 ES 的架构里，ES 起什么作用，高流量搜索如何承接？

**常见问法**

- 用 binlog 监听后，数据更新到 ES，那你的 ES 在这里的作用是什么？
- ES 面向用户提供的功能是搜索什么内容的？
- 流量最高的时候会直接打到 ES 吗？
- 项目里同步到 ES 不走 binlog、改用 RabbitMQ 发变更消息行不行？

#### 面试回答

先定位 ES 的角色：它承担“搜索读模型”。事实源仍然是 MySQL，canal 这类组件订阅 binlog 把变更同步进 ES，业务写一行代码都不用改。

- 为什么非要 ES：需求里有 B+ 树解决不了的查询 —— 分词全文匹配、多字段任意组合过滤、相关性排序、聚合统计。LIKE 全表扫描在数据量上不可用，ES 用倒排索引把它们做到毫秒级（原理见 [[#ES-001：Elasticsearch 底层搜索用的什么数据结构，倒排索引如何工作？|ES-001：倒排索引如何工作]]）。
- 为什么用 CDC 而不是业务双写：双写会侵入每个写入口，失败补偿逻辑散落各处；CDC 以 binlog 为单一事实源集中同步。代价是接受秒级最终一致 —— 搜索场景能容忍“新数据多久可搜到”，这点要和业务对齐。
- 搜什么内容属于项目事实，按【商品／帖子／文档等，写清索引字段与更新频率】填写。

流量最高时不直接裸打 ES，前面几条是减量和扩容，最后一条是护栏：

- 入口减量：对热点查询加结果缓存，key 含查询参数与版本。
- ES 扩读：靠副本分片水平扩读，分片数按容量压测定。
- 过滤复用：高频过滤走 filter 缓存。
- 写入削峰：洪峰走 bulk 攒批。
- 护栏：深分页改 search_after 游标、复杂查询限额、过载时熔断降级到兜底页或缓存旧结果；大促前预热段缓存与新索引。

#### 技术细节

**同步链路怎么走**

- 流程是：binlog 行事件 → 解析 → 转换 → bulk 写入。转换这一步要小心：拼接多表字段需要宽表建模，或者在 nested／join 之间做权衡。
- 顺序与幂等：按主键 hash 分区，保证同一个 key 的事件有序；失败重放依赖幂等的 upsert 语义，也就是以文档 ID 覆盖写。
- 兜底：用对账任务定期比对 MySQL 与 ES 的计数和抽样字段。
- CDC 延迟的监控与优化见 [[专题题库/系统设计#SYS-024：canal／binlog 订阅同步延迟如何归因与优化？|SYS-024：canal 同步延迟归因]]。

**ES 自己的写入代价**

- refresh／translog／merge 这些机制决定了它是“近实时读模型”，不是存储引擎，不能当数据库用。
- 数据规模上去后，第一个问题应该是“该不该缓在 ES”。明细与指标分离的取舍见 [[专题题库/系统设计#SYS-022：千万到亿级 trace／日志如何存储与检索？|SYS-022：亿级日志存储检索]]。

**承接读流量的三件套**

- 副本分片：水平扩读。
- 请求级缓存：高频的聚合 size=0 查询可以命中 request cache。
- 过滤位图缓存：复用高频过滤条件。
- 结果级缓存要放应用层 —— ES 自己不缓存打分后的结果集。

**深分页怎么处理**

- `from+size` 的代价：每个分片都要取 from+size 条再归并，页越深放大越狠。
- search_after 带上一页的排序值当游标，排序必须再加一个唯一字段做 tiebreaker；配合时间／租户过滤限制扫描面。
- 这和 MySQL 大分页的 seek 法是同一思路（见 [[专题题库/MySQL#MYSQL-019：大分页查询怎么优化？|MYSQL-019：大分页优化]]）。

#### 深挖追问

1. **为什么流量最高时反而更要避免“直打 ES”？**（面经实际出现；[[面经/虾皮/一面/0001#Q07：binlog 监听后数据更新到 ES，ES 的作用是什么、搜索什么内容、流量最高时直接打到 ES 吗？|MJ036 · 虾皮 · 一面 · Q07]]）

   因为 ES 的开销结构不适合硬扛洪峰：单次打分查询 CPU 很重，查询之间还要互相争抢分片线程池。洪峰下慢查询一堆积，就会雪崩式拖垮整个集群。

   所以高流量时先问“能不能不查 ES”（走缓存、走降级），必须查的限并发、限复杂度，而不是加机器硬扛。

2. **同步延迟期间用户搜不到刚发布的内容怎么办？**（补充练习；与 [[专题题库/系统设计#SYS-024：canal／binlog 订阅同步延迟如何归因与优化？|SYS-024]] 的归因思路共用）

   先从产品层兜底：发布成功页直接回显详情（读主库），个人中心走 DB 实时查询，搜索入口接受秒级延迟。

   技术上再压链路延迟（增量 bulk 的攒批窗口、监控位点），并向业务暴露“可搜索延迟”的 SLA。

3. **ES 挂了这条链路怎么降级？**（补充练习；口径见 [[专题题库/系统设计#SYS-015：数据库故障无法写入时如何降级与恢复？|SYS-015：数据库故障降级]] 的故障预算思维）

   目标是“搜索功能不可用，但页面还活着”：返回缓存的热门列表或分类导航，引导用户走精确过滤。

   写入链路（binlog→ES）可以暂停让它堆积，恢复后按位点追平 —— ES 不需要回补事务语义。

4. **MySQL 和 Elasticsearch 有什么区别，各自适用什么场景？**（面经实际出现；[[面经/小红书/一面/0001#Q07：MySQL 和 Elasticsearch 有什么区别、各自适用什么场景；ES 为什么要用倒排索引，相比顺序扫描好在哪？|MJ040 · 小红书 · 一面 · Q07]]）

   按“职责 — 数据模型 — 一致性 — 擅长的查询”四层来答：

   - 职责：MySQL 是事务型主存，管写入和业务真相；ES 是检索与分析的读模型。
   - 数据模型：MySQL 是行＋固定 schema；ES 是 JSON 文档＋动态映射与分词。
   - 一致性：MySQL 有事务、唯一约束和强一致读；ES 没有跨文档事务，写入是近实时（refresh 后才可见），更新等于重写段。
   - 擅长的查询：MySQL 擅长精确匹配、范围和 join（靠 B+ 树）；ES 擅长全文与相关性排序、任意字段组合过滤、高亮与聚合。反过来，深分页、高基数聚合和频繁更新是它的短板。

   结论口径是“两者搭配，不是二选一”：写走 MySQL、搜索走 ES、用 CDC 同步并接受秒级延迟。只要事务与唯一性的数据不要放 ES，需要分词与聚合的查询也不要硬压给 MySQL。

### ES-003：ES 索引的分片和副本一般怎么设置？

**常见问法**

- ES 建立索引时，副本和分片一般怎么设置？

#### 面试回答

先立两条硬事实，再给设置口径：

- 主分片数建索引时定、之后不可改（改只能 shrink／split／reindex）；副本数随时可动态调。
- 分片不是免费的：每个分片是一个独立 Lucene 实例，有固定堆内存开销、参与每次集群级元数据广播；搜索要“分片内结果→协调节点归并”。

设置经验值：

- 主分片：按“预估总数据量÷目标单分片大小”定——日志检索类单分片 30～50GB，搜索类偏小（20～30GB）让单分片查询更快；同时保证分片总数能被节点数大致均匀分配。
- 副本：默认 1 起步（扛单分片故障＋分摊读）；批量导入期临时调 0，导完再拉起；读 QPS 高的热点索引可加副本扩读容量。
- 写密集权衡：副本数＝写放大部分（一条写要进 1＋replica 个分片），吞吐敏感场景副本从简，优先换更强硬件。

#### 技术细节

**分片数量的反直觉边界**

- 不是越多越好：5 个节点 1000 个空分片比每节点 1 个分片慢——每分片的段缓存、translog、线程调度都要摊钱；集群级 `cluster.max_shards_per_node` 也有上限。
- 时序索引（按天滚动）是例外思路：每天新建索引，分片数按“当天数据量”算，天然可回缩、老索引可 freeze／降副本。

**副本到底防什么**

- 副本是完整拷贝：故障转移（分配副本为主）＋读扩展两条用途；但它防不了误删索引、mapping 配错、勒索删库——这些要靠 snapshot 仓库（快照才是备份）。
- 读写语义：写要等 primary＋in-sync 副本确认（`wait_for_active_shards`）才返回，默认只保证 primary——强耐久要求要显式调。

**routing 与热点**

- 文档按 `hash(routing) % 分片数` 落片，默认 routing＝id；按租户／用户 ID 定制 routing 可让同类查询只打单片（提速），代价是热租户倾斜与再平衡受限——面试提到这层双向权衡就到位了。

**答题收尾模板**

- “先问数据量、读写比、增长模型，再给分片副本数字”——这题考的就是不做假设直接报数的反面。

#### 深挖追问

1. **分片大小超了 50GB 会怎样？**（补充练习）

   恢复与迁移变慢（分片是复制／rebalance 的原子单位）、段合并占用长、单分片故障影响面大；应提前按增长曲线预留分片数，事后只能 split／reindex 收拾。

2. **想零停机调整主分片数怎么办？**（补充练习）

   没有原地魔法：新建正确分片数的索引，`_reindex` 或别名原子切换迁移数据；这也是“建索引前先算数”的理由。写路径持续入新索引、查询走别名，是时序场景的常规做法。

### ES-004：ES 数据分布在多个分片上，范围查询内部怎么执行？

**常见问法**

- [[面经/淘天/一面/0002#Q25：ES 数据分布在不同分片上，范围查询的内部实现逻辑？|MJ071 · 淘天 · 一面 · Q25]]
- 分片之间没有全局有序，范围查询怎么保证结果正确？

#### 面试回答

结论：scatter-and-gather——正确性不靠“数据按值分布”，只靠“每个分片都能独立回答这个查询”。

- 协调节点把同一个 range 查询广播到所有分片（或被路由／索引裁剪后的那批）。
- 各分片在自己的段上用 BKD 树圈出匹配文档，返回带分数的局部结果。
- 协调节点归并出全局 top-N。

- 分片存的是哈希／路由切片，不是按值区间——所以范围查询天然是“全分片广播”，没有“剪掉不相干分片”这回事（除非按业务做了区间路由）。
- 各分片本地：数值／日期／geo 字段不走倒排，走 doc_values 列存＋BKD 树（多维点集树），按区间求交得到 doc ID 集合（位图／迭代器）。
- 汇总阶段：排序查询每分片返回 top-(from+size)，协调节点做全局归并；分页深了放大成 N×(from+size)，改 `search_after`。
- 聚合阶段：局部聚合上收合并——terms 有近似误差（调 `shard_size` 缓解），数值 sum／min／max 精确，百分位是 TDigest 近似。

#### 技术细节

**BKD 树要点（被追问“range 怎么这么快”时用）**

- Point 类型的值编码成可比较的字节串后建 BKD（批量 KD 树），叶节点按块存点集；区间查询在树上剪枝，只访问可能相交的子树。
- 与倒排的分工：keyword／text 走倒排求 term，数值／日期／geo 走 BKD＋doc_values——这就是“同一个 where 里各字段各走各的索引结构”的原因。
- `range` 在 text 字段上不可用（需要 `mapping` 出正确类型），这也是新人常踩的坑。

**协调节点的归并成本**

- 合并发生在堆上：每分片一个游标，弹全局最小／最大，代价约 O(分片数 × log 分片数) 级别，瓶颈其实在网络传输的候选量。
- `preference`、路由与过滤能缩小参与分片数；“按租户路由到固定分片”是减少广播放大最常见的手段。

**容易说过头的两处**

- 别说“ES 范围查询像 B+ 树那样定位区间然后顺序扫”——段内没有可扫描的全局有序值列，是 BKD 剪枝＋doc ID 位图。
- 别说“分片数越多查询越快”：每个分片都有一套倒排与字典开销，范围类查询是广播模型，分片过多反而放大协调成本。

#### 深挖追问

1. **为什么更新和删除不影响进行中的范围查询？**（补充练习）

   段是不可变的：删除记在墓碑位图、更新是“删旧段文档＋新段写入”，查询在快照上合并“命中集 − 墓碑”，所以读不加锁；代价是刚删的文档仍占资源，直到 merge。

2. **时间序列数据怎么利用这个模型提速？**（面经实际出现的延伸；[[面经/淘天/一面/0002#Q25：ES 数据分布在不同分片上，范围查询的内部实现逻辑？|MJ071 · 淘天 · 一面 · Q25]]）

   按天／月建索引＋别名查询裁剪：范围条件转成“只查相关索引”，比同索引内 range 过滤省掉无关分片的广播与候选排序；配合 ILP／时序索引（1.x 起）进一步压缩。

### ES-005：Elasticsearch 和 Lucene 是什么关系？

**常见问法**

- [[面经/菜鸟集团/一面/0001#Q05：项目中用到 ES，谈谈 ES 和 Lucene 的关系|MJ084 · 菜鸟集团 · 一面 · Q05]]
- ES 底层就是 Lucene 吗？那 ES 多了什么？

#### 面试回答

结论：Lucene 是搜索核心库——倒排索引、段、打分、查询执行都在它这一层；ES 是把它包装成分布式产品的引擎服务——REST API、文档模型、分片副本、集群治理与聚合框架都是 ES 加的。

- Lucene 给的能力：term 字典（FST）＋postings（delta 压缩＋跳表）、段不可变与近实时 refresh、BM25 打分、数值 BKD 树与 doc values 列存。
- ES 加的能力：JSON 文档与 mapping／分词器配置；索引→分片→副本的数据分布与路由；查询的跨节点 scatter-and-gather 与全局归并；集群发现、再平衡、快照恢复；聚合框架与插件生态（安全、告警、Kibana）。
- 一次查询的分层视角：ES 把请求路由到相关分片，每个分片内部就是一次普通的 Lucene 本地检索，局部结果回到协调节点归并——“ES 的分布式、Lucene 的单节点”。
- 谱系一句：OpenSearch 是 ES 的许可证分叉同源产品；Solr 同样包 Lucene 但生态独立——类比口径可展示知道全景。

#### 技术细节

**边界要说得准（被追问处）**

- 分片不是 Lucene 索引的别名那么简单：一个分片＝一个完整 Lucene 实例（自己的段集合、translog 在 ES 层）。
- 写入链路的分工：ES 负责路由（`hash(routing) % 分片数`）＋副本复制（primary→replica），Lucene 只负责把文档写进本实例的段。
- 版本耦合：ES 大版本会跟进 Lucene 大版本（如 ES 8.x 跟 Lucene 9）；“Lucene 的能力边界”决定 ES 不做的事——比如段不可变带来的近实时与更新即重写。

**容易说过头的地方**

- 别说“ES 自己实现倒排索引”——所有倒排读写都是 Lucene 代码在跑。
- 别说“Lucene 是数据库”——它没有分布式与事务语义，副本、持久化恢复（translog）都在 ES 层。

#### 深挖追问

1. **为什么不直接用 Lucene，要架一层 ES？**（补充练习；与 [[#ES-002：binlog 监听同步到 ES 的架构里，ES 起什么作用，高流量搜索如何承接？|ES-002]] 的规模视角呼应）

   裸 Lucene 三个硬限制：单机容量与吞吐上限、进程内库形态没有服务边界、集群化（复制、故障转移、再平衡）与运维（发现、监控、快照）全要自研。

   ES 把这些做成默认能力，代价是重量级——极端轻量的嵌入式场景（单机 App 内搜索）确实会直接用 Lucene／SQLite FTS。

### ES-006：搜索系统怎么处理深分页？（ES、MySQL 与产品级策略）

**常见问法**

- [[面经/菜鸟集团/一面/0001#Q07：MySQL 有深分页，ES 会有吗？limit 100,100 实际检索多少行？MySQL 深分页处理手段？Google／百度这类大型产品怎么处理深分页？|MJ084 · 菜鸟集团 · 一面 · Q07]]
- ES 的 from+size 为什么页越深越慢？

#### 面试回答

结论：深分页在两类系统里都存在，机制不同。

- MySQL 的 offset 是“扫出来再扔掉”；ES 是“每个分片都要取 from+size 条候选给协调节点归并”，成本被分片数放大。
- 技术缓解之外，真正的答案在产品层：大型搜索产品根本不让你翻深页。

- MySQL 口径：`LIMIT 100,100` 引擎实际处理 200 行；二级索引非覆盖时 200 行全回表。手段＝游标化（`WHERE id > last LIMIT n`）＋延迟关联（覆盖索引先取主键再回表）＋限定最大页深。
- ES 口径：from+size 的总候选≈分片数×(from+size)——排序、内存与网络都线性涨；所以默认 `index.max_result_window=10000` 直接封顶。
- ES 深翻的两把钥匙：`search_after`（带上一页排序值＋唯一 tiebreaker 的游标，适合无限下拉）；scroll／PIT＋search_after（全量导出快照语义）。
- 大型产品的做法：搜索引擎只给前几十页／约前 1000 条，再深直接拒绝——深层页点击率极低、还喂爬虫；feed 流取消“页”的概念，一律 cursor 下拉；后台遍历走异步分批任务，不占在线接口。
- 收尾句：能改交互就先改交互，改不了才上游标；“把 offset 做快”从来不是终解。

#### 技术细节

**为什么产品敢砍深页**

- 相关性排序下第 30 页之后的结果点击量断崖式趋零，用户真实行为是改写关键词而不是翻页——产品数据和成本模型共同支持截断。
- 截断同时是反爬：大 offset 遍历是低成本批量拉取，限制页深＝限制白嫖带宽。

**游标化的实现约束（面试易被追）**

- 游标要求排序键可定位且稳定：时间＋ID 复合游标最常见；排序中途数据变化会跳页／重复，游标要带快照时刻或唯一 tiebreaker。
- 游标只支持“顺序翻页”，不支持跳页——跳页需求本身就是产品信号：要么改成筛选（按时间分片），要么导出走离线。
- ES 的 search_after 依赖索引内有序且唯一的排序组合；深翻＋实时排序字段变化会漂移，这是它和 scroll 的一致性差异。

**和 MySQL 深分页的同异**

- 同：都是“先取丢弃再返回”的浪费；都要靠“记住上次位置”消掉 offset。
- 异：ES 的浪费按分片数放大（scatter-and-gather），MySQL 在单节点内；所以 ES 的 10000 上限是结构性保护，不只是参数保守。

#### 深挖追问

1. **客户端要“跳到第 50 页”怎么办？**（面经未追问；产品折中口径）

   给筛选不给跳页：按时间／分类把大集合切小，每片内部再翻页——总候选规模降下来后，from+size 在浅水区够用；真需要全量遍历的诉求是导出场景，异步任务＋流式游标满足，别为极端交互改在线查询模型。
