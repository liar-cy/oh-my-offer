### ES-001：Elasticsearch 底层搜索用的什么数据结构，倒排索引如何工作？

**常见问法**

- ES 底层的搜索数据结构了解吗？
- 具体讲一下倒排索引的算法或者数据结构。

- 为什么 ES 要使用倒排索引，它相比顺序扫描的好处是什么？

#### 面试回答

一句话：倒排索引把“文档 → 词”的正排，翻转成“词 → 文档列表”。

- 结构：term 字典（词典树）映射到 postings list —— 含该词的有序文档 ID 序列，外加词频、位置信息。
- 举个例子：查 `后端 AND 面试`，就是取两条 postings 求交集。因为 term 在字典中有序、postings 按 doc ID 升序，交集用双指针归并就行；长列表再配跳表指针按块跨跳，不必逐个比对。
- 存储：postings 存的是差值（delta 编码）再分块压缩（FOR／PFor 类位压缩）。相邻 doc ID 差值很小，既省空间又固化了有序性。
- term 字典：用 FST（有限状态转换机）把共享前缀的词典压到很小，可以常驻内存，磁盘项按块加载。
- 对比 MySQL：B+ 树适合精确与最左前缀匹配，任意词项组合需要指数级索引条目，所以全文检索必须换倒排结构。

想加分就把一次查询的完整路径报出来：分词 → 词项查字典 → 跳表定位 → BM25 打分（词频、逆文档频率、字段长度归一）→ 命中文档从存储侧取回。补一句边界：排序聚合不走倒排，走 doc values 列存。

#### 技术细节

**索引里到底存了哪几样东西**

- term dictionary（词典，用 FST 存）。
- postings：delta＋分块压缩＋跳表。
- positions／offsets：短语匹配和高亮需要。
- term frequencies 与 norms：打分用。
- doc values：列式正排，排序／聚合／脚本用。
- _source：原始 JSON，返回结果和重建索引用。

**段（segment）不可变带来的取舍**

- 写入先进 in-memory buffer，refresh（默认约 1s）生成新段才可搜 —— 所以 ES 是“近实时”，不是实时。
- 删除是记墓碑段，更新是删旧加新，后台 merge 负责合并小段并物理清除。
- 换来的好处是无锁并发读和顺序写；代价是删除更新有延迟，还要留出 merge 的资源预算。

**多条件查询怎么执行**

- filter 子句先算：走位图缓存、不参与打分。
- must 子句走带打分的交集。
- 最后由 coordinate 节点汇总各分片的 top-N 做归并。

**深分页为什么贵**

- `from+size` 语义下，每个分片都要返回 from+size 条给协调节点合并，页越深放大越狠。
- 解法见 [[#ES-002：binlog 监听同步到 ES 的架构里，ES 起什么作用，高流量搜索如何承接？|ES-002]] 的 search_after。

#### 深挖追问

1. **FST 为什么适合做 term 字典？**（补充练习）

   因为词典里大量词共享前缀和后缀，FST 就把有公共子序列的词压成一张有向无环图。结果是内存占用比哈希表小一个量级，同时还能支持前缀枚举与范围扫描。另外 term 本身按字典序排列，范围查询与自动补全顺路可得。

2. **为什么 doc values 是列存而不是直接用倒排或 _source 排序？**（补充练习）

   因为排序／聚合要按字段值遍历全部命中文档，这个方向和倒排刚好相反；用 _source 还得先解一遍 JSON。列存把同一字段的值连续存放，好处是顺序 IO、可向量化处理，还能用 file cache 常驻页缓存。

3. **倒排索引对高基数数值字段为什么不划算？**（补充练习）

   每个不同值都要存一条 term、一条 postings，字典直接爆炸。数值范围查询走的是 BKD 树（Lucene 的 points 结构），而不是倒排。答题时能区分“文本走倒排、数值走 BKD、正排走 doc values”这三条索引路径，就是深度信号。

4. **不建索引、直接顺序扫描（如 `LIKE '%kw%'`）行不行，差在哪？**（面经实际出现；[[面经/小红书/一面/0001#Q07：MySQL 和 Elasticsearch 有什么区别、各自适用什么场景；ES 为什么要用倒排索引，相比顺序扫描好在哪？|MJ040 · 小红书 · 一面 · Q07]]）

   差在三重：

   - 代价：顺序扫描要读遍文档／行，成本随数据量线性增长；倒排的代价与命中的 posting 规模相关，而不是与全表行数相关。
   - 能力：中缀匹配的 `LIKE '%kw%'` 用不上 B+ 树（只能前缀），也拿不到分词、词频与位置信息，因此没有相关性打分、短语匹配和高亮。
   - 并发：扫描期间占用大量 IO 与缓冲池，搜索与交易互抢资源。

   倒排的补偿是它把“找词”变成查字典＋归并有序列表，但代价要一起说：建索引与段合并吃 IO、更新要重写段所以只是近实时、还要占额外磁盘。所以它服务读模型，而不是替代主存储。

### ES-002：binlog 监听同步到 ES 的架构里，ES 起什么作用，高流量搜索如何承接？

**常见问法**

- 用 binlog 监听后，数据更新到 ES，那你的 ES 在这里的作用是什么？
- ES 面向用户提供的功能是搜索什么内容的？
- 流量最高的时候会直接打到 ES 吗？

#### 面试回答

先定位 ES 的角色：它承担“搜索读模型”。事实源仍然是 MySQL，canal 这类组件订阅 binlog 把变更同步进 ES，业务写一行代码都不用改。

- 为什么非要 ES：需求里有 B+ 树解决不了的查询 —— 分词全文匹配、多字段任意组合过滤、相关性排序、聚合统计。LIKE 全表扫描在数据量上不可用，ES 用倒排索引把它们做到毫秒级（原理见 [[#ES-001：Elasticsearch 底层搜索用的什么数据结构，倒排索引如何工作？|ES-001：倒排索引如何工作]]）。
- 为什么用 CDC 而不是业务双写：双写会侵入每个写入口，失败补偿逻辑散落各处；CDC 以 binlog 为单一事实源集中同步。代价是接受秒级最终一致 —— 搜索场景能容忍“新数据多久可搜到”，这点要和业务对齐。
- 搜什么内容属于项目事实，按【商品／帖子／文档等，写清索引字段与更新频率】填写。

流量最高时不直接裸打 ES，前面几条是减量和扩容，最后一条是护栏：

- 入口减量：对热点查询加结果缓存，key 含查询参数与版本。
- ES 扩读：靠副本分片水平扩读，分片数按容量压测定。
- 过滤复用：高频过滤走 filter 缓存。
- 写入削峰：洪峰走 bulk 攒批。
- 护栏：深分页改 search_after 游标、复杂查询限额、过载时熔断降级到兜底页或缓存旧结果；大促前预热段缓存与新索引。

#### 技术细节

**同步链路怎么走**

- 流程是：binlog 行事件 → 解析 → 转换 → bulk 写入。转换这一步要小心：拼接多表字段需要宽表建模，或者在 nested／join 之间做权衡。
- 顺序与幂等：按主键 hash 分区，保证同一个 key 的事件有序；失败重放依赖幂等的 upsert 语义，也就是以文档 ID 覆盖写。
- 兜底：用对账任务定期比对 MySQL 与 ES 的计数和抽样字段。
- CDC 延迟的监控与优化见 [[专题题库/系统设计#SYS-024：canal／binlog 订阅同步延迟如何归因与优化？|SYS-024：canal 同步延迟归因]]。

**ES 自己的写入代价**

- refresh／translog／merge 这些机制决定了它是“近实时读模型”，不是存储引擎，不能当数据库用。
- 数据规模上去后，第一个问题应该是“该不该缓在 ES”。明细与指标分离的取舍见 [[专题题库/系统设计#SYS-022：千万到亿级 trace／日志如何存储与检索？|SYS-022：亿级日志存储检索]]。

**承接读流量的三件套**

- 副本分片：水平扩读。
- 请求级缓存：高频的聚合 size=0 查询可以命中 request cache。
- 过滤位图缓存：复用高频过滤条件。
- 结果级缓存要放应用层 —— ES 自己不缓存打分后的结果集。

**深分页怎么处理**

- `from+size` 的代价：每个分片都要取 from+size 条再归并，页越深放大越狠。
- search_after 带上一页的排序值当游标，排序必须再加一个唯一字段做 tiebreaker；配合时间／租户过滤限制扫描面。
- 这和 MySQL 大分页的 seek 法是同一思路（见 [[专题题库/MySQL#MYSQL-019：大分页查询怎么优化？|MYSQL-019：大分页优化]]）。

#### 深挖追问

1. **为什么流量最高时反而更要避免“直打 ES”？**（面经实际出现；[[面经/虾皮/一面/0001#Q07：binlog 监听后数据更新到 ES，ES 的作用是什么、搜索什么内容、流量最高时直接打到 ES 吗？|MJ036 · 虾皮 · 一面 · Q07]]）

   因为 ES 的开销结构不适合硬扛洪峰：单次打分查询 CPU 很重，查询之间还要互相争抢分片线程池。洪峰下慢查询一堆积，就会雪崩式拖垮整个集群。

   所以高流量时先问“能不能不查 ES”（走缓存、走降级），必须查的限并发、限复杂度，而不是加机器硬扛。

2. **同步延迟期间用户搜不到刚发布的内容怎么办？**（补充练习；与 [[专题题库/系统设计#SYS-024：canal／binlog 订阅同步延迟如何归因与优化？|SYS-024]] 的归因思路共用）

   先从产品层兜底：发布成功页直接回显详情（读主库），个人中心走 DB 实时查询，搜索入口接受秒级延迟。

   技术上再压链路延迟（增量 bulk 的攒批窗口、监控位点），并向业务暴露“可搜索延迟”的 SLA。

3. **ES 挂了这条链路怎么降级？**（补充练习；口径见 [[专题题库/系统设计#SYS-015：数据库故障无法写入时如何降级与恢复？|SYS-015：数据库故障降级]] 的故障预算思维）

   目标是“搜索功能不可用，但页面还活着”：返回缓存的热门列表或分类导航，引导用户走精确过滤。

   写入链路（binlog→ES）可以暂停让它堆积，恢复后按位点追平 —— ES 不需要回补事务语义。

4. **MySQL 和 Elasticsearch 有什么区别，各自适用什么场景？**（面经实际出现；[[面经/小红书/一面/0001#Q07：MySQL 和 Elasticsearch 有什么区别、各自适用什么场景；ES 为什么要用倒排索引，相比顺序扫描好在哪？|MJ040 · 小红书 · 一面 · Q07]]）

   按“职责 — 数据模型 — 一致性 — 擅长的查询”四层来答：

   - 职责：MySQL 是事务型主存，管写入和业务真相；ES 是检索与分析的读模型。
   - 数据模型：MySQL 是行＋固定 schema；ES 是 JSON 文档＋动态映射与分词。
   - 一致性：MySQL 有事务、唯一约束和强一致读；ES 没有跨文档事务，写入是近实时（refresh 后才可见），更新等于重写段。
   - 擅长的查询：MySQL 擅长精确匹配、范围和 join（靠 B+ 树）；ES 擅长全文与相关性排序、任意字段组合过滤、高亮与聚合。反过来，深分页、高基数聚合和频繁更新是它的短板。

   结论口径是“两者搭配，不是二选一”：写走 MySQL、搜索走 ES、用 CDC 同步并接受秒级延迟。只要事务与唯一性的数据不要放 ES，需要分词与聚合的查询也不要硬压给 MySQL。
