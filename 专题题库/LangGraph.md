### LG-001：为什么选择 LangGraph，它解决什么问题？

**常见问法**

- 为什么用 LangGraph 框架？

- 介绍一下 LangGraph 这个框架。

#### 面试回答

如果项目需要长流程、循环、条件分支或人工确认，我会选择 LangGraph，用 state 表示共享状态、node 表示处理步骤、edge 表示转移关系，并按需要配置 checkpoint 实现状态保存与恢复。如果只是一次检索加生成，用简单流程也足够。项目中的选择理由要对应真实需求。

#### 技术细节

本题按 LangGraph 官方概念回答，具体 API 以项目版本为准。需要区分图状态、检查点和外部副作用：恢复执行并不等于数据库写入或消息发送天然 exactly-once；有副作用的节点应考虑幂等键或结果记录。状态累积策略会影响消息是否不断膨胀；路由条件、终止条件与循环上限应可观察。优点应通过失败恢复或多阶段任务场景说明，而非声称框架总是性能更好。

#### 深挖追问

1. **checkpoint 保存后能任意重跑吗？**（补充练习）

   应考虑恢复位置和外部副作用，重放节点可能重复调用外部服务，需要幂等或去重设计。

2. **什么时候不需要图框架？**（补充练习）

   任务步骤少、无分支和恢复需求时，直接函数组合通常更容易维护。

3. **从固定 Workflow 改造为 LangGraph 中心调度，思路是什么？**（面经实际出现；[[面经/帆软/二面/0001#Q04：从 Workflow 改造为 LangGraph 中心调度 Agent，改造思路是什么？|MJ023 · 帆软 · 二面 · Q04]]）

   先盘点原节点：输入输出、依赖、状态与副作用，区分确定性代码、模型调用与人工环节；再把流程控制从硬编码改为图——state 承载共享上下文，节点封装原步骤（确定性实现不重做），边表达条件流转，循环/重规划显式建模，配 checkpoint 获得中断恢复。改造收益用同一任务集对比成功率、时延与维护成本验证；强顺序合规流程可保留原编排。

4. **为什么用图结构编排，if-else 不行吗？**（面经实际出现；[[面经/字节/一面/0007#Q01：LangGraph 的特征是什么，为什么用图结构编排，if-else 不行吗？|MJ026 · 字节 · 一面 · Q01]]）

   if-else 能表达任何分支，问题在复杂流程后的工程属性：转移关系散落各处不可枚举、难可视化、循环与中断恢复要手写状态机。图把“拓扑”变成一等公民——节点/边可单测、checkpoint 恢复与并行汇合由运行时承载。分支少且稳定时 if-else 更直接，别为架构而架构；出现循环、恢复、多分支汇合再上图。

### LG-002：Spring AI Alibaba Graph 的底层原理是什么？

**常见问法**

- 讲一下 Spring AI Alibaba Graph 的底层原理。

- 怎么用 Graph 框架来设计和控制任务流程的？

#### 面试回答

它是 Spring AI Alibaba 在 Spring AI 之上提供的工作流／多 Agent 编排引擎，官方文档自述设计受 LangGraph 启发：应用建模为状态图（StateGraph）而非链。四个支柱：① 节点与边——Node 封装一段逻辑（模型调用、工具调用或普通 Java 函数），普通边定直连、条件边按状态路由；② 共享状态 OverAllState——节点间不直接传消息，节点返回“状态增量”，框架按每个 key 注册的合并策略（Replace 覆盖／Append 追加）写回全局状态，并行分支对同一 key 的写入语义由此决定；③ compile()——把声明式拓扑编译为可执行图并校验（起点终点可达、路由完整）；④ 超步执行——每一超步运行全部激活节点、合并状态、计算下一批节点，循环与并行天然可表达；配 Checkpoint 持久化（按 threadId 保存每步状态快照）支持中断恢复与 human-in-the-loop，输出走 Reactor Flux 流式。与 ChatClient 链式编排的本质区别：链是一趟性数据流水线，图把分支、回环、状态回溯与暂停续跑做成框架能力，控制流从代码外移为声明。落地成本主要在状态设计：key 粒度、合并策略与节点幂等是踩坑集中区。

#### 技术细节

- 概念对照（Graph≈LangGraph）：StateGraph≈Graph 定义、NodeAction≈node 函数、Edge/条件边≈router、OverAllState＋KeyStrategy≈channels/reducer、CheckpointSaver≈checkpointer、interrupt／resume≈human-in-the-loop。用过任一方可用另一方的词汇解释。
- 与纯代码 if-else 编排的差别不在“能不能”，而在可观测与可恢复：图结构可导出、每超步有状态快照，失败从 checkpoint 续跑而不是整链重放；复杂 Agent 拓扑（反思循环、多分支路由）用链式代码会退化成手写状态机。
- 并行分支：同一超步内互不依赖的节点并发执行，返回的增量按 key 合并——若两个分支写同一 key 且策略是 Replace，结果不确定，这是文档明示要自己避免的坑；需要汇聚就用 Append 或在下游节点合并。
- 版本口径：Spring AI Alibaba 1.x（文档查证日见下），底层构建在 Spring AI 的 ChatClient／工具抽象与 Project Reactor 之上；API 仍在演进，答“原理”时以状态图执行模型为主干，类名细节标注按所用版本文档。

#### 深挖追问

1. **为什么并行分支写同一状态 key 要特别小心？**（补充练习）

   Replace 策略下两个分支同超步写入时后写覆盖先写、顺序不定；要么给分支各自独立 key 下游再汇聚，要么用 Append 保全部值——本质是“无锁并发下的写冲突”，图引擎没有替你仲裁的默认义务。

2. **它和直接用 LangGraph（Python）怎么选？**（补充练习；见 [[#LG-001：为什么选择 LangGraph，它解决什么问题？|LG-001：为什么选择 LangGraph]]）

   执行模型同源，选择主要看技术栈：Java／Spring 生态（服务治理、既有后端团队）选 Spring AI Alibaba Graph，Python 生态与 LangChain 工具链选 LangGraph；两边的图、状态、checkpoint 概念可以互换解释。

3. **节点状态具体管哪些东西，持久化又是怎么落地的？**（面经实际出现；[[面经/字节/一面/0010#Q04：Graph 中的“自动化状态管理”具体管理哪些状态？这些状态是如何持久化的？|MJ042 · 字节 · 一面 · Q04]]）

   四类：① 业务共享状态（输入、改写后的查询、各节点中间产物、累计计数如步数与 token 用量、控制位如下一分支与是否待人工确认）；② 消息与会话历史，通常按追加合并；③ 执行上下文（threadId、超步序号、当前激活节点集合），这类由运行时维护，业务不该自己存；④ 依赖资源（LLM 客户端、连接池、句柄）不属于状态，塞进 State 会被写进快照，恢复时拿到失效连接。持久化按超步做检查点：每个超步结束把该 threadId 的 State 快照交给 CheckpointSaver（内存／Redis／数据库），恢复时按 threadId 取最近快照续跑，因此能做人工审批挂起与状态回溯。三个约束要一起说：每个 key 要注册合并策略（并行分支同时写同一 key 用 Replace 会互相覆盖、顺序不定）、节点要幂等（从检查点重放可能重复执行副作用，写库与发消息要么带去重键要么独立成节点）、快照会随轮次膨胀（大字段外置存储，State 只放引用）。
