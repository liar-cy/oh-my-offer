### LG-001：为什么选择 LangGraph，它解决什么问题？

**常见问法**

- 为什么用 LangGraph 框架？

- 介绍一下 LangGraph 这个框架。

#### 面试回答

- 什么时候选：项目里有长流程、循环、条件分支或人工确认时，我会选 LangGraph。
- 概念怎么落：state 表示共享状态、node 表示处理步骤、edge 表示转移关系，再按需配置 checkpoint 实现状态保存与恢复。
- 什么时候不选：只是一次检索加生成，用简单流程就够了。选择理由要对应到项目里的真实需求。

#### 技术细节

**答题口径**

- 本题按 LangGraph 官方概念回答，具体 API 以项目所用版本为准。

**图状态、检查点、外部副作用要分清**

- 恢复执行不等于数据库写入或消息发送天然 exactly-once（一次且仅一次）。
- 有副作用的节点应考虑幂等键或结果记录。

**状态与流程控制**

- 状态的累积策略会影响消息是否不断膨胀。
- 路由条件、终止条件与循环上限都应该做成可观察的。

**优点怎么讲**

- 优点要通过失败恢复或多阶段任务这类场景来说明，而不是声称框架总是性能更好。

#### 深挖追问

1. **checkpoint 保存后能任意重跑吗？**（补充练习）

   不能想当然。要看恢复位置和外部副作用：重放节点可能重复调用外部服务，所以要靠幂等或去重设计兜住。

2. **什么时候不需要图框架？**（补充练习）

   任务步骤少、没有分支也没有恢复需求时，直接函数组合通常更容易维护。

3. **从固定 Workflow 改造为 LangGraph 中心调度，思路是什么？**（面经实际出现；[[面经/帆软/二面/0001#Q04：从 Workflow 改造为 LangGraph 中心调度 Agent，改造思路是什么？|MJ023 · 帆软 · 二面 · Q04]]）

   分三步说：

   - 先盘点原节点：输入输出、依赖、状态与副作用，区分清楚哪些是确定性代码、哪些是模型调用、哪些是人工环节。
   - 再把流程控制从硬编码改成图：state 承载共享上下文，节点封装原步骤（确定性实现不重做），边表达条件流转，循环／重规划显式建模，配 checkpoint 获得中断恢复。
   - 改造收益用同一任务集对比成功率、时延与维护成本来验证；强顺序的合规流程可以保留原编排。

4. **为什么用图结构编排，if-else 不行吗？**（面经实际出现；[[面经/字节/一面/0007#Q01：LangGraph 的特征是什么，为什么用图结构编排，if-else 不行吗？|MJ026 · 字节 · 一面 · Q01]]）

   先承认：if-else 能表达任何分支。问题出在流程变复杂之后的工程属性上：

   - 转移关系散落各处，不可枚举，也难可视化。
   - 循环和中断恢复要自己手写状态机。

   图的价值是把“拓扑”变成一等公民：节点／边可以单测，checkpoint 恢复和并行汇合交给运行时承载。

   选型口径：分支少且稳定时 if-else 更直接，别为了架构而架构；出现循环、恢复、多分支汇合再上图。

### LG-002：Spring AI Alibaba Graph 的底层原理是什么？

**常见问法**

- 讲一下 Spring AI Alibaba Graph 的底层原理。

- 怎么用 Graph 框架来设计和控制任务流程的？

#### 面试回答

它是 Spring AI Alibaba 在 Spring AI 之上提供的工作流／多 Agent 编排引擎，官方文档自述设计受 LangGraph 启发：应用建模为状态图（StateGraph），而不是链。四个支柱：

- 节点与边：Node 封装一段逻辑（模型调用、工具调用或普通 Java 函数）；普通边定直连，条件边按状态路由。
- 共享状态 OverAllState：节点间不直接传消息，节点只返回“状态增量”，框架按每个 key 注册的合并策略（Replace 覆盖／Append 追加）写回全局状态。并行分支对同一 key 的写入语义，就由这个策略决定。
- compile()：把声明式拓扑编译成可执行图，同时做校验（起点终点可达、路由完整）。
- 超步执行：每一超步运行全部激活节点、合并状态、再计算下一批节点，所以循环与并行天然可表达。配上 Checkpoint 持久化（按 threadId 保存每步状态快照），就能做中断恢复和 human-in-the-loop（人在回路）；输出走 Reactor Flux 流式。

和 ChatClient 链式编排的本质区别：链是一趟性数据流水线，图把分支、回环、状态回溯与暂停续跑做成了框架能力，控制流从代码里外移成了声明。落地成本主要在状态设计 —— key 粒度、合并策略与节点幂等是踩坑集中区。

#### 技术细节

**概念对照（Graph ≈ LangGraph）**

- StateGraph ≈ Graph 定义，NodeAction ≈ node 函数，Edge／条件边 ≈ router。
- OverAllState＋KeyStrategy ≈ channels／reducer，CheckpointSaver ≈ checkpointer，interrupt／resume ≈ human-in-the-loop。
- 用过其中一方，就能用另一方的词汇来解释。

**和纯代码 if-else 编排的差别**

- 差别不在“能不能表达”，而在可观测与可恢复：图结构可以导出，每个超步都有状态快照，失败时从 checkpoint 续跑，而不是整链重放。
- 反过来，复杂 Agent 拓扑（反思循环、多分支路由）用链式代码写，会退化成自己手写一套状态机。

**并行分支的坑**

- 同一超步内互不依赖的节点并发执行，返回的增量按 key 合并。
- 如果两个分支写同一个 key、策略又是 Replace，结果就不确定 —— 这是文档明示要自己避免的坑。需要汇聚时，要么用 Append，要么放到下游节点里合并。

**版本口径**

- Spring AI Alibaba 1.x（文档查证日见下），底层构建在 Spring AI 的 ChatClient／工具抽象与 Project Reactor 之上。
- API 仍在演进：答“原理”时以状态图执行模型为主干，类名细节标注按所用版本的技术文档。

#### 深挖追问

1. **为什么并行分支写同一状态 key 要特别小心？**（补充练习）

   本质是无锁并发下的写冲突：Replace 策略时，两个分支在同一超步写入，后写会覆盖先写，而且顺序不定。

   解法两条：要么给每个分支各自独立的 key，到下游再汇聚；要么用 Append 把全部值都保住。图引擎默认没有替你仲裁这项义务。

2. **它和直接用 LangGraph（Python）怎么选？**（补充练习；见 [[#LG-001：为什么选择 LangGraph，它解决什么问题？|LG-001：为什么选择 LangGraph]]）

   执行模型同源，所以主要看技术栈：Java／Spring 生态（服务治理、既有后端团队）选 Spring AI Alibaba Graph；Python 生态和 LangChain 工具链选 LangGraph。两边的图、状态、checkpoint 概念可以互相解释。

3. **节点状态具体管哪些东西，持久化又是怎么落地的？**（面经实际出现；[[面经/字节/一面/0010#Q04：Graph 中的“自动化状态管理”具体管理哪些状态？这些状态是如何持久化的？|MJ042 · 字节 · 一面 · Q04]]）

   状态分四类：

   - 业务共享状态：输入、改写后的查询、各节点的中间产物、累计计数（如步数与 token 用量）、控制位（如下一分支、是否待人工确认）。
   - 消息与会话历史：通常按追加合并。
   - 执行上下文：threadId、超步序号、当前激活节点集合。这类由运行时维护，业务不该自己存。
   - 依赖资源：LLM 客户端、连接池、句柄。它们不属于状态 —— 塞进 State 就会被写进快照，恢复时拿到的是已经失效的连接。

   持久化按超步做检查点：每个超步结束，把该 threadId 的 State 快照交给 CheckpointSaver（内存／Redis／数据库）；恢复时按 threadId 取最近的快照续跑。因此才能实现人工审批挂起和状态回溯。

   还有三个约束要一起说：

   - 每个 key 都要注册合并策略：并行分支同时写同一 key，用 Replace 会互相覆盖、顺序不定。
   - 节点要幂等：从检查点重放可能重复执行副作用，写库和发消息要么带去重键，要么独立成一个节点。
   - 快照会随轮次膨胀：大字段外置到别的存储，State 里只放引用。
