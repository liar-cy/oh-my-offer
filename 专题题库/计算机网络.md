### NET-001：从输入网址到页面显示，经历哪些步骤？

**常见问法**

- 从输入 www.baidu.com 到显示的整个流程是什么？

- 浏览器输入 URL 到页面显示经历什么，涉及哪些协议？

- 浏览器输入 URL 到服务端返回页面的完整链路是什么？

#### 面试回答

浏览器解析 URL、处理缓存或 HTTPS 升级策略，需要联网时解析域名并建立或复用连接。以 HTTPS over TCP 为例，经过 TCP 和 TLS 握手后发送 HTTP 请求，服务器返回响应；浏览器解析 HTML、CSS，执行脚本，构建页面并进行布局、绘制和合成。HTTP/3 使用 QUIC，不能说所有网页请求都先建 TCP 连接。

#### 技术细节

原文“从输入 www.baidu.com 到现实”按上下文纠正为“显示”，不把该域名当作需要实测的服务。DNS 可命中多级缓存，递归解析器按需查询；拿到地址后还需路由和本地链路寻址。连接可能复用，重定向和子资源会引入额外请求。解析 HTML 形成 DOM，CSS 形成样式信息，脚本可能改变 DOM 或影响解析；页面渲染是渐进过程，不是所有资源到齐才统一显示。网络请求链路与浏览器渲染阶段应分层讲清。

#### 深挖追问

1. **第一次访问一定要查询远程 DNS 吗？**（补充练习）

   不一定，浏览器、系统或解析器可能命中缓存，也可能存在预解析。

2. **服务器返回 200 就表示页面已显示吗？**（补充练习）

   不表示，浏览器还要解析、执行和渲染，子资源也可能失败。

### NET-002：HTTP 和 HTTPS 有什么区别，证书如何验证？

**常见问法**

- HTTP 和 HTTPS 有什么区别，TLS 握手如何进行？
- HTTP 和 HTTPS 的区别是什么？
- 为什么能判别证书？
- 每次都要去远程查验证书吗？

- HTTP 和 HTTPS 有什么区别，HTTPS 如何保证安全？

- HTTPS 建立连接的完整流程是什么？

#### 面试回答

HTTPS 在 HTTP 通信中使用 TLS 提供传输机密性、完整性和身份认证。客户端检查证书链能否到达信任根、域名是否匹配、有效期及用途等，握手中还验证对方掌握相应私钥。验证签名主要在本地完成，不需要每次远程询问 CA；吊销状态检查可能使用缓存、OCSP stapling 或浏览器机制，取决于客户端策略。

以基于 TCP、证书认证的 TLS 1.3 完整握手为例：客户端发 ClientHello，携带支持版本、算法和 key share；服务端回 ServerHello 选择参数和 key share，双方派生握手密钥；服务端发送加密的 EncryptedExtensions、Certificate、CertificateVerify 和 Finished；客户端验证证书及握手证明，再发 Finished，随后用应用流量密钥保护 HTTP 数据。

#### 技术细节

不要把证书里的公钥等同于大流量业务数据的直接加密密钥。以 TLS 1.3 为例，握手协商密钥并认证握手内容，后续使用对称密钥保护记录；握手算法和旧版 RSA 密钥交换的叙述不同。证书链验证、主机名校验和吊销检查是不同环节。客户端可能需要补全中间证书或取得吊销信息，也可能利用本地数据；不能回答“一定每次联网”或“永远不联网”。HTTPS 保护传输，不保证服务端业务没有漏洞。

上述流程限定 TLS 1.3 非 PSK 恢复、无客户端证书认证的常规握手；协商不合适可能有 HelloRetryRequest。TLS 1.2 的 ECDHE 完整握手消息不同，不能把旧式 RSA 加密预主密钥流程套到 TLS 1.3；TLS 1.3 的 0-RTT 是恢复场景的可选能力，并有重放风险。默认端口 HTTP 为 80、HTTPS 为 443，但端口可配置。

#### 深挖追问

1. **为什么能相信证书？**（面经实际出现；[[面经/拼多多/一面/0001#Q09：HTTP 和 HTTPS 有什么区别，如何验证证书，需要每次远程查验吗？|MJ003 Q09]]）

   以客户端信任库中的根为信任起点，逐级验证签名和约束，再核对目标域名及握手私钥证明。

2. **每次都去远程查证书吗？**（面经实际出现；[[面经/拼多多/一面/0001#Q09：HTTP 和 HTTPS 有什么区别，如何验证证书，需要每次远程查验吗？|MJ003 Q09]]）

   不需要每次远程验签；吊销和链补全等网络行为取决于缓存、服务端提供的信息及客户端策略。

3. **TLS 握手过程是什么？**（面经实际出现；[[面经/百度/一面/0003#Q01：HTTP 和 HTTPS 有什么区别，TLS 握手如何进行？|MJ006 · 百度 · 一面 · Q01]]）

   TLS 1.3 常规证书握手按 ClientHello → ServerHello → 服务端加密认证消息与 Finished → 客户端 Finished 展开；密钥交换、证书验证和对握手内容的认证各有职责。

4. **非对称加密算法知道哪些？加代理抓包会有什么影响？**（面经实际出现；[[面经/字节/一面/0007#Q07：HTTP 和 HTTPS 有什么区别，非对称加密算法知道哪些，加代理抓包有什么影响？|MJ026 · 字节 · 一面 · Q07]]）

   常见：RSA（密钥交换/签名，逐步被弃用于交换）、ECC/ECDSA（同强度密钥更短，主流证书）、Ed25519、国密 SM2；现代 TLS 握手实际以 (EC)DHE 做前向安全的密钥协商，非对称主要用于证书签名验证与身份认证。抓包代理（mitmproxy/Fiddler/公司网关）是受控中间人：终止两段 TLS、用自签 CA 现场重签证书，客户端必须信任该根证书才看得到明文，否则握手校验失败；生产 App 常用证书固定（pinning）对抗，抓不到包多是这个原因，不是“HTTPS 无法抓”。

### NET-003：TCP 和 UDP 有什么区别？

**常见问法**

- TCP 和 UDP 的区别是什么？

- TCP 和 UDP 有什么区别？

#### 面试回答

TCP 是面向连接的可靠有序字节流，提供重传、流量控制和拥塞控制，但不保留消息边界。UDP 是无连接数据报，保留报文边界，协议本身不保证送达、有序或去重。选择取决于业务是否需要这些语义及延迟要求，不能简单说 UDP 一定更快或只能用于不可靠业务。

#### 技术细节

TCP 应用需要自定义长度头、分隔符或固定长度等消息 framing。UDP 应用要处理丢包、乱序及超过接收缓冲的数据报截断；可以在其上实现可靠协议，例如 QUIC，因此“基于 UDP”不代表上层没有可靠传输。TCP 的可靠性是连接内字节交付，不等于应用已持久化或处理成功。TCP 头部通常至少 20 字节，UDP 为 8 字节，但首部差异不是性能结论的全部依据。

#### 深挖追问

1. **UDP 可以 connect 吗？**（补充练习）

   可以，socket API 的 connect 可设置默认对端和相关过滤语义，不会变成 TCP 式握手连接。

2. **为什么 TCP 有所谓粘包？**（补充练习）

   它是字节流，多次发送与接收调用没有一一对应边界，需要应用协议自行分帧。

### NET-004：TCP 四次挥手与 TIME_WAIT 是什么？

**常见问法**

- TCP 四次挥手的过程是什么？
- 什么是 TIME_WAIT？
- 为什么要进行 TIME_WAIT？

- TCP 四次挥手如何进行，第二次和第三次能否合并？

#### 面试回答

正常关闭时，一方发 FIN，对端 ACK；对端完成发送后再发 FIN，主动关闭方 ACK 并进入 TIME_WAIT。两个方向独立关闭，所以常见四个报文，ACK 与 FIN 也可能合并。TIME_WAIT 通常持续 2MSL，让最后 ACK 丢失时仍能确认重传 FIN，并降低旧连接报文影响后续同四元组连接的风险。

#### 技术细节

主动关闭方通常经历 FIN_WAIT_1、FIN_WAIT_2、TIME_WAIT，被动关闭方经历 CLOSE_WAIT、LAST_ACK。CLOSE_WAIT 长期堆积常提示应用没关闭已收到 FIN 的连接，不能与 TIME_WAIT 混淆。主动关闭方不一定是客户端；同时关闭也可能让双方进入 TIME_WAIT。协议的 MSL 与具体系统计时常量不同，不背一个固定秒数当作所有系统规则。贸然调整复用参数可能改变连接语义，应先查连接生命周期。

原题“第二次和第三次为什么不能合并”带有不准确前提：确认收到 FIN 不代表本方已结束发送；若本方仍有数据，则先 ACK 后 FIN；若已具备关闭条件，ACK 与 FIN 可以合并。

#### 深挖追问

1. **为什么要等 2MSL？**（面经实际出现；[[面经/百度/一面/0001#Q09：TCP 四次挥手是什么过程，TIME_WAIT 为什么要等待？|MJ002 Q09]]）

   为最终确认的重传和旧报文消退提供时间，是关闭协议的一部分，不是等待业务处理完成。

2. **被动关闭方收到 FIN 后还能发数据吗？**（补充练习）

   可以，FIN 关闭一个发送方向，另一方向仍可发送剩余数据。

3. **为什么第二次与第三次通常分开发？**（面经实际出现；[[面经/百度/一面/0005#Q07：TCP 四次挥手如何进行，第二次和第三次能否合并？|MJ008 · 百度 · 一面 · Q07]]）

   确认对方发送结束与本方发送结束是两个事件，因此经常分开；条件允许时可以合并。

### NET-005：服务器断开后，客户端会有什么表现？

**常见问法**

- 服务器断了之后有什么表现？

#### 面试回答

要分正常关闭、复位和突然失联。收到正常 FIN 后，客户端先读完已缓冲数据，recv 才返回 0；收到 RST 可能报连接重置。若断电或网络黑洞没有任何报文到达，客户端未必立即知道，有数据发送时可能经历重传并最终超时，空闲时需要 keepalive 或应用心跳与超时机制发现。

#### 技术细节

“服务器断了”并不是单一事件：进程正常退出时内核可能执行关闭，主机掉电则无法主动发送 FIN。send 成功也可能只是数据进入本机发送缓冲，不证明对端在线或业务成功。读超时、连接超时与请求总超时处理不同阶段；心跳可反映应用响应，TCP keepalive 主要探测连接活性。重试还要考虑上次请求是否已产生副作用，必要时使用幂等标识。

#### 深挖追问

1. **第一次写成功，第二次才报错正常吗？**（补充练习）

   可能，错误到达与应用写入异步发生；一次本地写成功不是对端处理确认。

2. **只有心跳就能证明业务可用吗？**（补充练习）

   不能，心跳路径成功不保证所有依赖正常，需要与请求级状态及超时配合。

### NET-006：TCP 如何保证可靠传输？

**常见问法**

- 什么是 TCP 滑动窗口，丢包后如何处理？
- TCP 怎么保证可靠传输？

#### 面试回答

TCP 通过序号、确认、校验和、重传与接收端重排去重提供可靠有序交付。TCP 滑动窗口允许发送方在收到确认前连续发送一段范围内的数据，不必每发一段就等待 ACK。ACK 推进已确认边界，窗口随之滑动；接收窗口 rwnd 限制接收方容量，拥塞窗口 cwnd 限制网络中的在途数据。丢包可通过重传超时或重复 ACK、SACK 等线索检测并重传，接收方缓存乱序数据、去重，最终按序交付。连接永久中断时仍会报错；TCP 确认不代表远端业务已处理或持久化。

#### 技术细节

确认的是连接中的数据接收，而非远端应用已经消费或写盘。接收窗口反映接收侧容量，拥塞窗口反映发送侧对网络承载能力的估计；发送还受在途数据影响。重复 ACK、SACK 等可帮助识别丢失区间，RTO 根据 RTT 等估计。按序交付可能让后续已到数据等待前面的缺口。TCP 校验和用于传输差错检测，不是抵御恶意篡改的认证机制。

简化看，在途数据上限受 min(rwnd,cwnd) 约束，新发送额度还要扣除已在途字节。累计 ACK 指向下一个期望字节，SACK 补充已收到的非连续区间。经典快速重传可由三个重复 ACK 触发，但现代实现也有其他丢失检测机制；不能认为每次丢包必有三个重复 ACK。超时会重传并调整拥塞控制，丢 ACK 不等于对应数据必重传，后续累计 ACK 可能已覆盖它。

#### 深挖追问

1. **收到 ACK 就能删除业务重试记录吗？**（补充练习）

   通常不能，应等待应用层的业务确认，并按幂等与持久化要求定义完成条件。

2. **流量控制和拥塞控制有什么不同？**（面经实际出现；[[面经/字节/一面/0004#Q19：介绍一下 TCP 的拥塞控制和流量控制。|MJ014 · 字节 · 一面 · Q19]]）

   前者避免压垮接收方（rwnd），后者避免压垮网络（cwnd），两者同时约束可发送数据；完整机制见 [[专题题库/计算机网络#NET-017：TCP 拥塞控制和流量控制如何工作，有什么区别？|NET-017：TCP 拥塞控制和流量控制如何工作，有什么区别？]]。

3. **丢包了怎么处理？**（面经实际出现；[[面经/百度/一面/0003#Q06：什么是 TCP 滑动窗口，丢包后如何处理？|MJ006 · 百度 · 一面 · Q06]]）

### NET-007：大文件如何通过 TCP 传输，TCP／IP 一次最多传多少？

**常见问法**

- 一个很大的文件，TCP 可以一次传完吗？
- TCP 一次最大传多少？
- IP 一次传多少？

#### 面试回答

大文件可以通过同一 TCP 连接持续传输，但不是一个 TCP 段发完。应用一次 write 的长度、TCP 单段数据量和 IP 包大小是不同概念。TCP 按 MSS 等限制分段，MSS 受对端通告和路径 MTU 约束。常见 MTU 1500、IPv4 无选项且 TCP 无选项时，单段数据通常为 1460 字节，这不是固定通用上限。

#### 技术细节

IPv4 总长度字段为 16 位，单数据报最多 65535 字节，包含 IP 头；TCP 数据上限还需扣除 IP 和 TCP 头，不能把 65535 直接当 payload。IPv6 普通包的 payload length 最多 65535 字节，不含固定 40 字节头，扩展头占 payload；jumbo payload 是额外机制。IPv4 可能分片，IPv6 路由器不做分片；实际传输通常尽量避免 IP 分片。send 可能短写，大文件需循环发送或使用适用的零拷贝接口；TSO/GSO 也会让本机抓包看见比线上段更大的数据单元。

1. **很大的文件可以一次传完吗？**（面经实际出现；[[面经/拼多多/一面/0001#Q12：TCP 如何传大文件，一次写入、TCP 单段和 IP 包的大小有什么区别？|MJ003 Q12]]）

   一个连接可以传完；一个段不行。一次系统调用也不能保证提交全部数据，更不能保证对端已接收。

### NET-008：ICMP 是什么，有什么作用？

**常见问法**

- ICMP 知道吗？

#### 面试回答

2. **traceroute 中某跳星号意味着后续不可达吗？**（补充练习）

### NET-009：Socket 编程的基本流程与关键问题是什么？

**常见问法**

- Socket 编程。

#### 面试回答

### NET-010：TCP 三次握手如何进行，握手期间能携带数据吗？

**常见问法**

- TCP 为什么需要三次握手，两次行不行？
- 三次握手的过程是什么？
- 握手期间可以传参数吗？

#### 面试回答

客户端发 SYN，seq=x；服务端回 SYN+ACK，seq=y、ack=x+1；客户端回 ACK，ack=y+1，双方建立连接。它让双方确认初始序号及双向通信状态。握手报文可有 MSS、窗口扩大等 TCP 选项；第三次 ACK 可携带应用数据。普通连接不会依赖首个 SYN 交付业务参数，TCP Fast Open 等机制则允许在特定条件下提前发送数据。

两次握手时，服务端还不知道客户端是否收到自己的初始序号、是否仍参与当前连接；第三次确认完成双向序号同步，也避免仅凭延迟到达的旧 SYN 就认为连接已建立。

#### 技术细节

不带数据时第三次 ACK 的 seq 通常为 x+1，SYN 占一个序号，纯 ACK 不占。服务端收到最终确认前通常处于 SYN_RECEIVED，客户端收到 SYN+ACK 并发送确认后进入 ESTABLISHED；应用可写与对端处理时机仍依赖实现。“参数”可能指 TCP 选项，也可能指 HTTP 查询参数或应用 payload，必须区分。TCP 规范允许 SYN 携数据但对交付有约束，TFO 通过协商／Cookie 等让支持端在完整握手前处理数据，不代表所有首连 SYN 都可任意承载应用请求。涉及提前处理的数据还需考虑重放和幂等。

不能只背“确认双方收发能力”：关键还包括双方独立初始序号的确认与旧重复连接请求的处理。普通被动打开时，服务端发出 SYN+ACK 后处于 SYN_RECEIVED，收到有效最终 ACK 才进入 ESTABLISHED；第三次 ACK 丢失可通过 SYN+ACK 重传及后续有效确认恢复。

#### 深挖追问

1. **握手期间可以传参数吗？**（面经实际出现；[[面经/北京某上市公司/一面/0001#Q16：TCP 三次握手如何进行，握手期间可以传参数或数据吗？|MJ004 一面 Q16]]）

   TCP 选项本就在握手中协商；应用数据第三次 ACK 可携带，SYN 数据需解释规范与 TFO 等实现条件。

2. **为什么不是两次握手？**（面经实际出现；[[面经/百度/一面/0003#Q05：TCP 为什么需要三次握手，两次行不行？|MJ006 · 百度 · 一面 · Q05]]）

   两次不足以让服务端确认客户端已收到自己的初始序号并继续参与当前连接，第三次确认完成序号同步。

3. **第三次握手的 ACK 丢了，连接还能建成吗？客户端紧接着发数据会怎样？**（面经实际出现；[[面经/字节/二面/0002#Q03：TCP 三次握手中第三次握手的 ACK 丢失，协议如何恢复？若客户端随后立即发数据且早于重传的 ACK 到达服务端，服务端能否正确处理，怎么优化？|MJ042 · 字节 · 二面 · Q03]]）

   状态不对称是关键：客户端发完 ACK 即进入 ESTABLISHED，服务端仍停在 SYN_RECEIVED，且已分配连接控制块。恢复靠服务端重复重传第二个报文（SYN＋ACK），指数退避且有重试上限（Linux 由握手重试次数参数控制，默认几次），超过上限就丢弃该 TCB 释放资源，客户端此后收到的会是 RST。若 ACK 在窗口内补到则正常转入 ESTABLISHED。客户端随后发数据通常能被正确处理：SYN 占一个序号，第一个数据字节的序号正好是服务端期望值，该报文自带的 ACK 直接把状态推进到 ESTABLISHED——数据报文本身补完了第三次握手，不必等那个丢失的 ACK；旧连接的乱序报文靠序号窗口判定丢弃，这也是 TIME_WAIT 存在的原因之一。优化分三侧：客户端用连接池复用、开 TCP Fast Open 让 SYN 带请求体省一个 RTT；服务端调低 SYN 重传与半连接超时以更快回收、用 SYN Cookie 抵御洪泛（不预先分配 TCB）、限单源连接数与空闲超时；应用侧显式设超时并按幂等重试，因为“连接是否还活着”从错误码上区分不出来。

### NET-011：DNS 解析过程是什么，递归和迭代有什么区别？

**常见问法**

- DNS 解析过程是什么，递归和迭代有什么区别？

#### 面试回答

客户端先检查适用的本地缓存和主机映射，未命中时通常向递归解析器查询。解析器有缓存就直接返回，否则按需从根、顶级域到权威服务器逐级查询，拿到目标记录后缓存并返回。递归是委托对方返回最终结果或错误；迭代是对方返回已有答案或下一步应询问的服务器，由查询方继续追踪。常见模式是客户端向解析器递归查询，解析器向各级服务器迭代查询。

#### 技术细节

例如查询 www.example.com 的 A／AAAA 记录，根通常返回 .com 的委派信息，.com 返回 example.com 权威服务器信息，权威服务器返回记录；已有委派缓存时可跳过前面步骤。CNAME 需要继续解析别名目标；缓存遵守 TTL，否定结果也可能缓存。DNS 不只是“域名转 IP”，还有 MX 等记录；传输也不限于 UDP，存在 TCP、DoT、DoH。转发型解析器也可能向上游递归查询。

#### 深挖追问

1. **递归和迭代分别由谁继续查询？**（面经实际出现；[[面经/百度/一面/0003#Q07：DNS 解析过程是什么，递归和迭代有什么区别？|MJ006 · 百度 · 一面 · Q07]]）

   递归由受托服务器完成剩余解析；迭代由查询者依据 referral 继续问，实际部署可以组合缓存、转发和迭代。

2. **常见的 DNS 记录类型有哪些，你最常用哪种？**（面经实际出现；[[面经/字节/一面/0010#Q17：讲一下 DNS 的工作原理；常见的 DNS 记录类型有哪些，你用得比较多的是哪一种？|MJ042 · 字节 · 一面 · Q17]]）

   A（→IPv4）、AAAA（→IPv6）、CNAME（规范别名，指向另一个域名，不能与同名其他记录共存，业务域名指到 CDN／负载均衡就靠它）、NS（该域的权威服务器）、MX（邮件交换，带优先级）、TXT（任意文本，SPF／DKIM／`_dmarc` 与域名归属验证都放这里）、PTR（反解 IP→域名，邮件与风控校验常用）、SRV（服务定位：协议＋端口＋权重）、CAA（限定可为本域签发证书的 CA）。实际最常碰的是 A／AAAA 与 CNAME，其次是部署邮件或验证域名归属时的 TXT／MX，配证书时用到 CAA。加分点是说出解析结果的不确定性：CNAME 链要续查、多条 A 记录按轮询或就近返回、否定答案也会被缓存，以及切流量时 DNS 不可靠——TTL 只约束缓存过期，客户端缓存不受控，所以秒级摘流量必须靠网关或负载均衡侧的手段。

### NET-012：Cookie、Session 和 Token 有什么区别？

**常见问法**

- Cookie、Session 和 Token 有什么区别？
- Cookie 和 Token 如何维持登录态？

#### 面试回答

Cookie 是浏览器保存并按域、路径等规则随请求发送数据的机制；Session 是维护会话状态的方案，常见做法是服务端保存状态、客户端用 Cookie 携带 session ID；Token 是代表身份或授权的凭证，可以是服务端查询的不透明值，也可以是带签名的自包含令牌。三者不互斥，Cookie 可以承载 session ID，也可以承载 Token，Token 不等于 JWT。

#### 技术细节

Session 适合集中控制过期和注销，多实例要共享会话存储或采取路由策略。自包含 Token 可减少逐次查会话，但立即撤销常需黑名单、版本号等状态或短有效期。JWT 签名不等于加密；服务端须验证签名、有效期、签发方、受众等约束。HttpOnly 限制脚本读取 Cookie，Secure 限定安全传输，SameSite 约束跨站发送；凭证如何存储和发送，决定相应 CSRF／XSS 风险。

#### 深挖追问

1. **用 Token 就不需要防 CSRF 了吗？**（补充练习）

   不一定。若 Token 放在浏览器自动携带的 Cookie 里，仍需防 CSRF；显式 Authorization 头通常降低这类自动携带风险，但仍要防 XSS 和错误的跨域配置。

### NET-013：OSI 七层与 TCP/IP 四层如何映射？

**常见问法**

- OSI 七层与 TCP/IP 四层如何映射？

- TCP/IP 四层模型有哪些，每层作用及对应协议？

#### 面试回答

OSI 从低到高是物理、数据链路、网络、传输、会话、表示、应用层。常见 TCP/IP 四层模型把物理和数据链路归入链路层，网络层对应网际层，传输层对应传输层，会话、表示和应用层归入应用层。OSI 偏参考分层，TCP/IP 围绕互联网协议体系组织；映射是教学上的概括，实际协议职责不总能严格一一对应。

#### 技术细节

常见四层映射如下；某些教材拆出物理层称五层模型，需先说明口径。

| OSI | TCP/IP 四层 | 示例或职责 |
| --- | --- | --- |
| 应用、表示、会话 | 应用层 | HTTP、DNS；应用数据表达与会话功能由具体协议实现 |
| 传输 | 传输层 | TCP、UDP |
| 网络 | 网际层 | IP、ICMP |
| 数据链路、物理 | 链路层 | 以太网、Wi-Fi、介质传输 |

### NET-014：HTTP 各版本特性与常见状态码是什么？

**常见问法**

- HTTP 各版本特性与常见状态码是什么？
- HTTP 503 和 504 有什么区别？

- HTTP 状态码有哪些？5 开头的呢？

#### 面试回答

HTTP 是应用层请求／响应协议，定义方法、资源、状态码和表示等语义，本身无状态。HTTP/1.0 通常每次请求建连接；HTTP/1.1 默认持久连接，支持管线化但响应仍按序；HTTP/2 用二进制帧、多路复用和 HPACK 压缩头部，仍受 TCP 丢包带来的连接级队头阻塞影响；HTTP/3 基于 QUIC，降低跨流传输队头阻塞，使用 QPACK。状态码分 1xx 信息、2xx 成功、3xx 重定向、4xx 客户端错误、5xx 服务端错误：如 200、201、204，301、302、304、307、308，400、401、403、404、405、409、429，500、502、503、504。304 表示缓存验证后无需重传表示，不是页面重定向。

#### 技术细节

HTTP 语义与传输表达应分开：HTTP/2 多路复用解决 HTTP/1.1 请求响应串行的限制，但 TCP 丢包仍可影响所有流；QUIC 提供独立流交付，不能据此声称没有拥塞、流内等待或任何应用依赖。

| 状态码 | 含义 |
| --- | --- |
| 200／201／204 | 成功／资源已创建／无响应内容 |
| 301／302 | 永久／临时重定向，某些方法在重定向时可被改写 |
| 307／308 | 临时／永久重定向，保持请求方法 |
| 304 | 条件请求验证未修改，可复用缓存表示 |
| 400／401／403／404 | 请求错误／缺少有效认证凭据／拒绝执行／资源未找到或不愿披露 |
| 405／409／429 | 方法不允许／资源状态冲突／请求过多 |
| 500／502／503／504 | 内部错误／网关收到无效上游响应／暂时不可用／网关等待上游超时 |

状态码表示协议层处理结果，不替代业务响应的具体契约。

#### 深挖追问

1. **HTTP/2 是否完全消除了队头阻塞？**（补充练习）

   没有。不同流可以复用一个连接，但底层 TCP 字节流缺口仍阻塞后续字节交付。

2. **503 和 504 有什么区别？**（面经实际出现；[[面经/百度/一面/0007#Q03：HTTP 状态码如何分类，503 和 504 有什么区别？|MJ009 · 百度 · 一面 · Q03]]）

   503 表示服务当前暂时无法处理请求，常见于过载或维护；504 表示网关或代理等待上游响应超时。`Retry-After` 可用于说明 503 后建议多久再试，但并非每个 503 都一定携带。

3. **500／502／503／504 怎么快速区分错误来源？**（面经实际出现；[[面经/美团/一面/0001#Q10：HTTP 状态码有哪些？5 开头的呢？|MJ031 · 美团 · 一面 · Q10]]）

   按责任方区分：500 是本服务处理时抛出的通用内部错误；502 是本服务作为网关／代理时从上游拿到了无效响应（上游崩溃、返回不合规报文）；503 是本服务明确表示当前承接不了（过载、维护、限流降级）；504 是上游在超时窗口内没有响应。排障含义不同——502／504 先查上游与网关配置，503 先查本服务容量与开关，500 查本服务异常日志。

### NET-015：如何通过 IP 地址解析链路层地址？

**常见问法**

- 如何通过 IP 地址解析链路层地址？

#### 面试回答

按以太网 MAC 地址理解“物理地址”：IPv4 主机先查邻居缓存，若无记录，通过 ARP 在本地链路广播请求，由目标回复其 MAC。路由判断目标不在本地链路时，需要解析的是下一跳网关的 MAC，不是远程服务器的 MAC；ARP 广播不会跨路由器传遍互联网。IPv6 使用基于 ICMPv6 的邻居发现，不使用 ARP。

#### 技术细节

回答前提是以太网 MAC 地址而非主机内存地址。发送前先查路由确定下一跳，再查询或解析邻居地址，最后封装链路帧。ARP 请求使用本地链路广播，普通应答通常单播返回，邻居表会缓存结果。互联网目标通常只能解析网关的 MAC；每跳重新封装链路帧。ARP 本身缺乏可信身份认证，不能把其映射视为不可伪造。IPv6 邻居发现使用 Neighbor Solicitation／Advertisement 等机制。

#### 深挖追问

1. **远程服务器 IP 能直接 ARP 到它的 MAC 吗？**（补充练习）

   不能跨路由广播解析；本机通常取得下一跳网关的链路地址。

### NET-016：SSE 和 WebSocket 有什么区别，如何选择？

**常见问法**

- SSE 和 WebSocket 有什么区别？
- 什么情况使用 SSE，什么情况使用 WebSocket？

- WebSocket 断开重连如何设计？

- 能介绍一下 SSE 是什么吗？

#### 面试回答

SSE 使用 HTTP 响应流和 `text/event-stream`，浏览器通过 `EventSource` 持续接收服务端事件，主要解决服务端向客户端单向推送；上行通常继续走普通 HTTP。WebSocket 经握手后形成双方都能主动发送文本或二进制消息的双向通道。服务端通知、进度或 LLM token 流通常用 SSE 更简单；即时聊天、协同编辑、游戏和高频双向控制更适合 WebSocket。

#### 技术细节

SSE 事件可包含 `data`、`event`、`id` 和 `retry` 字段，浏览器原生接口有重连及 `Last-Event-ID` 相关语义，但应用仍要处理事件是否可重放、代理缓冲、空闲超时、心跳和慢客户端。它承载 UTF-8 文本事件；二进制需编码或改用其他通道。WebSocket 在成功握手后以消息／帧双向传输，支持文本和二进制及 ping／pong 控制帧；应用需自行设计重连、消息确认、鉴权刷新、背压和跨实例连接路由。

选择不能只看“实时”：还要看上行频率、载荷类型、浏览器或非浏览器客户端、反向代理支持、连接数与网关治理。两者都不能自动保证业务消息恰好一次；断线重连后用事件 ID、序列号和幂等处理恢复。

#### 深挖追问

1. **LLM 流式输出为什么常用 SSE？**（补充练习）

   主数据方向通常是服务端持续向客户端输出文本，客户端只需另一个 HTTP 请求提交输入，SSE 的协议和基础设施成本较低。

2. **SSE 中间断开了怎么办？**（面经实际出现；[[面经/字节/一面/0004#Q17：SSE 中间断开了怎么办？|MJ014 · 字节 · 一面 · Q17]]）

   浏览器 `EventSource` 会自动重连，间隔可由服务端 `retry` 字段控制，重连请求带 `Last-Event-ID` 头；服务端给事件发 id，可重放场景按 id 续推漏发事件。LLM 流式文本这类不可重放内容，按消息 ID 重新拉取已生成部分再接续生成或整段重来，客户端按 id 去重保幂等。另需心跳注释行防代理空闲断连，并定义产出快于消费时的背压与断开策略。

3. **WebSocket 断开重连如何设计？**（面经实际出现；[[面经/帆软/一面/0001#Q09：WebSocket 断开重连如何设计？|MJ022 · 帆软 · 一面 · Q09]]）

   检测靠应用层心跳（ping/pong＋超时判定，TCP 不告诉你“对端假死”）；重连用指数退避＋随机抖动＋上限，结合页面可见性/网络恢复事件立即尝试；恢复要重新鉴权（token 可能过期）、携带最后消息序号或会话 ID 补拉断连期增量、客户端有界队列暂存待发；重复收发按序列号幂等去重。协议层重连成功不等于业务会话还在，会话恢复是应用自己设计的。

### NET-017：TCP 拥塞控制和流量控制如何工作，有什么区别？

**常见问法**

- 介绍一下 TCP 的拥塞控制和流量控制。

#### 面试回答

流量控制防压垮接收方：接收方在每个 ACK 中通告接收窗口 rwnd，发送方未确认在途数据不超过它；窗口缩为 0 后发送方周期发零窗口探测，接收方有空位再发窗口更新。拥塞控制防压垮网络本身：发送方维护拥塞窗口 cwnd，作为对网络可承载在途量的估计，实际发送受 min(rwnd, cwnd) 约束。经典算法四段：慢启动把 cwnd 从初始小窗口随确认指数增长到阈值 ssthresh；之后进入拥塞避免做加性增长；收到三个重复 ACK 快速重传并以快恢复减半重建；RTO 超时则大幅收缩重进慢启动。区别一句话：rwnd 由接收端缓冲决定、保护对端；cwnd 由发送端依据丢包等网络信号自适应、保护网络。

#### 技术细节

慢启动“每收到一个 ACK 增一个 MSS”导致按往返轮次指数增长；初始窗一般取约 10×MSS（RFC 6928）。AIMD（加性增、乘性减）让多个流公平共享瓶颈；ssthresh 在丢包后按当前窗口减半。快恢复下 cwnd 从新阈值起步而非回到 1，避免不必要的全速重启。RTO 由 RTT 测量与方差估计（Jacobson/Karels 一类算法），超时判丢比重复 ACK 更严重、收缩更狠。窗口缩放（RFC 7323）解决高带宽时延积下 16 位窗口不够；零窗口期间的探测定时器防止更新报文丢失造成僵局。现代实现要区分：Linux 默认 CUBIC 基于丢包，BBR 改用带宽×RTT 建模主动测吞吐，二者面对深缓冲或随机丢包的行为不同；回答经典算法时可顺带点明实现差异。SSE／LLM 流式场景受 cwnd 与 RTT 影响，应用层背压与 TCP 流控是不同层的问题（可关联 [[专题题库/计算机网络#NET-006：TCP 如何保证可靠传输？|NET-006：TCP 如何保证可靠传输？]]）。

#### 深挖追问

1. **为什么慢启动指数增长、拥塞避免线性增长？**（补充练习）

   指数阶段快速逼近可用带宽，线性阶段在饱和点附近精细试探；乘性减使流间收敛到公平份额。

2. **接收窗口很大还会拥塞吗？**（补充练习）

   会。rwnd 只说明接收端装得下，中间链路或队列可能已饱和，丢包时 cwnd 仍会收缩。

3. **收到 ACK 就能删掉重传记录吗？**（补充练习）

   不能把 TCP 确认当业务完成，应用层确认与幂等设计见 NET-006。

### NET-019：HTTP 有哪些请求方法，GET 和 POST 有什么区别？

**常见问法**

- HTTP 协议有哪些请求方法？讲一下 GET 和 POST 的区别。
- 哪一个请求的参数是放到请求体里的？
- PUT、POST、PATCH 有什么区别？

#### 面试回答

标准方法有 GET、POST、PUT、PATCH、DELETE、HEAD、OPTIONS、TRACE。GET 与 POST 的区别按语义讲最稳：GET 用于读取资源，语义上安全且幂等，可被缓存和收藏，参数主要放在 URL 查询串里；POST 用于把数据提交给服务端处理，非幂等，默认不缓存，参数放在请求体里。所以“哪个方法的参数放请求体”答案是 POST——PUT、PATCH 这类带载荷的方法同样用请求体，由 Content-Type 描述编码。其余常被说成“区别”的点要限定条件：URL 长度限制来自浏览器和服务器实现而不是协议规定；GET 的查询串会进访问日志、浏览器历史和 Referer，因此不宜放敏感信息；“GET 比 POST 安全”“只有 POST 能传中文”都是误解，两者在 HTTP 下都是明文，加密要靠 TLS。

#### 技术细节

方法名只是**语义约定**，不约束报文结构：GET 允许带请求体但接收方普遍忽略或不支持（浏览器 fetch/XHR 不允许 GET 带 body，多数服务端框架不解析），POST 也可以只用查询串——把 POST 当“传输数据的唯一方式”是常见误区，正确说法是“需要传载荷的方法有 POST/PUT/PATCH，语义上 POST 最常用”。幂等与安全（safe）都是对服务端的**要求**，协议本身不强制：写错的接口用 GET 改数据，爬虫和预取就会造成事故，反之 POST 也可以设计成幂等（带幂等键，见 [[专题题库/系统设计#SYS-013：接口幂等性如何设计，重复提交订单怎么处理？|SYS-013：接口幂等性如何设计，重复提交订单怎么处理？]]）。
其他方法要点：HEAD 与 GET 相同但不返回响应体，用于探测与取头部；OPTIONS 用于查询支持的方法，也是 CORS 预检所用；PUT 语义是**整体替换**且幂等，PATCH 是局部更新且不要求幂等；DELETE 幂等（多次删除同一资源结果状态一致，实现可以返回 404）。浏览器表单只能发 GET/POST，REST 风格里的 PUT/DELETE 通常由 fetch/axios 或方法覆盖（`_method`）发出。缓存角度：GET 响应可按 Cache-Control 缓存，POST 响应默认不可重用。

#### 深挖追问

1. **GET 能不能带请求体？**（补充练习）

   协议层不禁止，但实践中不可依赖：浏览器主流 API 不提供 GET 带 body 的方式，服务端框架常忽略；需要载荷就用 POST 并把数据放 body 或查询串。

2. **表单提交和 axios 发的请求有什么区别？**（补充练习）

   表单是浏览器原生行为，只支持 GET/POST，编码为 `application/x-www-form-urlencoded` 或 `multipart/form-data`；axios/fetch 可任意方法、可自定义头与 `application/json`，也因此会触发 CORS 预检（自定义头或非简单方法时先发 OPTIONS）。

3. **为什么说 REST 里 DELETE 是幂等的？**（补充练习）

   幂等指同一请求执行一次与多次对服务器状态的影响相同：重复删除同一资源后该资源都处于“已删除”状态。实现上第二次删除常返回 404 或 204，业务要保持这种“结果一致”而不是产生新副作用。

### NET-018：调用大模型 API 会经过哪些互联网协议？

**常见问法**

- 调用 LLM 的时候会涉及到哪些互联网协议？

#### 面试回答

按协议栈自底向上串一条真实链路：域名解析用 DNS（UDP 为主，可 DoH/DoT）；传输层 TCP（HTTP/1.1、HTTP/2 之上）或 QUIC/UDP（HTTP/3）；安全层 TLS 完成证书认证与对称加密通道；应用层是 HTTPS＋REST/JSON，流式输出用 SSE（`text/event-stream`），双向高频场景可用 WebSocket，服务间调用常见 gRPC（HTTP/2 多路复用）；企业网络出口还有 HTTP CONNECT 代理与 VPN；再往外可能经过 CDN、负载均衡与 API 网关。答题按“解析→可靠传输→加密→应用协议→流式语义”展开，每层能被追问。

#### 技术细节

流式相关最常追问：SSE 是 HTTP 响应流上的文本事件协议，单向服务端推送，走普通 HTTP 栈、代理要禁用缓冲；WebSocket 经握手升级为独立全双工帧协议，不再受 HTTP 语义约束；gRPC 依赖 HTTP/2 的多路复用与二进制帧，解决队头阻塞要靠 HTTP/2 或 QUIC。TLS 部分可衔接证书链验证与中间人代理（见 [[专题题库/计算机网络#NET-002：HTTP 和 HTTPS 有什么区别，证书如何验证？|NET-002：HTTP 和 HTTPS 有什么区别，证书如何验证？]]）。超时与重试语义在应用层：HTTP 超时是“结果未知”不是失败，幂等键设计见 [[专题题库/系统设计#SYS-018：HTTP 接口如何从业务层兜底请求丢失与重试？|SYS-018：HTTP 接口如何从业务层兜底请求丢失与重试？]]。各家 SDK 的 keep-alive 连接复用直接影响尾延迟，值得在工程实践中提一句。

#### 深挖追问

1. **为什么大模型服务普遍用 SSE 而不是 WebSocket 输出 token？**（补充练习）

   主方向是服务端单向推送，SSE 复用 HTTP 栈与基础设施、实现和网关成本更低；需要上行取消/多路交互时才值得上 WebSocket（见 [[专题题库/计算机网络#NET-016：SSE 和 WebSocket 有什么区别，如何选择？|NET-016：SSE 和 WebSocket 有什么区别，如何选择？]]）。

### NET-020：一台服务器理论上能建立多少 TCP 连接，真实限制是什么？

**常见问法**

- 假设一台服务器所有资源无限，理论上能同时建立多少个 TCP 连接？
- 单机能扛多少长连接，受什么限制？
- C10K／C100K 的瓶颈到底在哪？

#### 面试回答

先把“资源无限”这个前提拆开看，这题考的是能否识别真实约束而不是报一个天文数字。连接的身份是四元组（源 IP、源端口、目的 IP、目的端口），所以纯理论上限是四元组的组合数：固定一个本机 IP、一个对端 IP 与端口时，受本地可绑定端口数限制（IPv4 的 16 位端口，去掉占用后约 6 万多量级）；多绑几个源 IP 或多目的端口就是线性倍乘；IPv4 地址全空间是 2^32，两端相乘看似天文级——但这些都不是工程约束，把答案停在这里就是没答到点上。

真实限制按“先到哪条”排：① 文件描述符（每连接一个 fd，进程级 `ulimit -n`／`RLIMIT_NOFILE` 与系统级 `fs.file-max`）；② 内存（每连接的发送／接收缓冲与连接控制块元数据，按 `tcp_rmem`／`tcp_wmem` 与是否启用了 `tcp_moderate` 一类自适应窗口而定，百万连接即使每连接几 KB 也要几十 GB）；③ 本地端口耗尽——只发生在作为客户端主动出连接时（TIME_WAIT 占用端口），服务端接受连接不消耗本地端口，这个区分是高价值答案；④ 中间设备与内核的连接跟踪表、epoll 等事件机制的容量与唤醒成本；⑤ 应用层每连接的读写缓冲区、业务线程占用。所以正确的收口是：若 fd、内存、内核表真的无限，上限由四元组空间决定；实践中先到的是内存与 fd，所以要做的是每连接瘦身（收敛默认缓冲、及时关闭空闲连接）、用边缘触发与批量处理降低唤醒开销、必要时靠多 IP／多进程分片，并用连接数与内存指标做准入控制，而不是等 OOM。

#### 技术细节

内存账要会估：一条 TCP 连接的内核开销至少包括两个 sk_buff 队列、收发缓冲与连接结构，最小几百字节到数 KB；若开启 `SO_RCVBUF`／`SO_SNDBUF` 固定大值（如各 4MB），一万连接就要几十 GB——所以高并发接入层的第一课是不要把缓冲写死，用默认自适应或按业务量设定。用户态还会再加：每连接的解析状态、TLS 会话（握手后的记录缓冲与证书链，成本更高）、业务对象与定时器，这些常常比内核开销更大。

单进程 fd 上限之外还有中断与软中断：连接数上去后每个包的唤醒成本与 CPU 缓存失效会放大，靠 RPS／RSS 多队列网卡分流、`epoll` 边缘触发批量收、以及减少空闲连接的定时器精度（用时间轮或分层哈希定时器）。真正到百万级长连接时常见做法是分层：接入层只做转发与心跳、把状态收敛到少数后端；或者用 eBPF／DPDK 绕开内核协议栈（代价是工程复杂度与可观测性损失）。

与半连接队列的关系要点一下：新建速率（CPS）与并发连接数是两个指标——SYN 队列（`tcp_max_syn_backlog`）与 accept 队列（`somaxconn` 与 `listen` backlog 取小）限制的是每秒能建立多少新连接，长连接服务被“瞬时重连风暴”打挂往往不是并发数超限而是建立速率超了队列，客户端加抖动重连、服务端把 `accept4` 提前与 backlog 调大才是对症手段（与 NET-010 握手丢包恢复同源）。

#### 深挖追问

1. **为什么服务端不会遇到本地端口耗尽，客户端会？**（补充练习）

   服务端 accept 出来的连接，四元组里“目的端口”是它监听的端口、源端口由客户端决定，服务端不需要为自己选端口；客户端主动 connect 时必须为每个连接占一个本地端口（同一四元组唯一），所以外呼型服务在 TIME_WAIT 未释放时会耗尽可用端口，解法是复用连接、扩源 IP、或启用 `tcp_tw_reuse`（仅对出连接有效且依赖时间戳）。

2. **65535 个端口是不是意味着单机最多 6 万连接？**（补充练习）

   不是。这个说法混用了“本端端口数”和“连接数”：服务端接受连接不受本端端口限制，只受 fd／内存等约束，百万级并发连接完全可能；只有作为客户端、且对端与本地 IP 都固定时，端口数才构成硬上限。

3. **怎么验证自己的服务能扛多少连接？**（补充练习）

   压测要同时看并发连接数与新建速率两条曲线，观察点为 fd 使用率、`ss -s`／`netstat` 的连接状态分布、内存与每连接缓冲实际占用、软中断与 CPU 利用率、以及 accept 队列溢出计数（`netstat -s` 里的 overflow 指标）；把结论写成“在 X 内存与 Y CPS 下可稳定维持 N 连接”，而不是单说“扛了 10 万”。
