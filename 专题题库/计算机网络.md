### NET-001：从输入网址到页面显示，经历哪些步骤？

**常见问法**

- 从输入 www.baidu.com 到显示的整个流程是什么？

- 浏览器输入 URL 到页面显示经历什么，涉及哪些协议？

- 浏览器输入 URL 到服务端返回页面的完整链路是什么？
- 浏览器中键入一个 URL，按下回车后的执行链路是怎样的？

#### 面试回答

一句话：先解析 URL、看缓存，真要联网才去解析域名建连接，拿到响应后浏览器再渲染。

- 准备阶段：浏览器解析 URL，处理本地缓存和 HTTPS 升级策略；需要联网时才解析域名、建立或复用连接。
- 网络阶段：以 HTTPS over TCP（跑在 TCP 上的 HTTPS）为例，先做 TCP 握手、再做 TLS 握手，然后发 HTTP 请求，服务器返回响应。
- 渲染阶段：解析 HTML 和 CSS、执行脚本，构建页面，再走布局、绘制、合成。
- 一个坑：HTTP/3 走的是 QUIC，不能说所有网页请求都先建 TCP 连接。

#### 技术细节

**原文口径**

- 原文“从输入 www.baidu.com 到现实”按上下文纠正为“显示”，不把该域名当作需要实测的服务。

**网络这一半**

- DNS 可以命中多级缓存，递归解析器按需再去查询。
- 拿到地址不等于就能通信：后面还需要路由和本地链路寻址。
- 连接可能复用，不用每次重新握手；重定向和子资源会引入额外请求。

**渲染这一半**

- 解析 HTML 形成 DOM，解析 CSS 形成样式信息，脚本可能改变 DOM 或影响解析过程。
- 页面渲染是渐进过程，不是所有资源到齐才统一显示。

**怎么讲**

- 答题时把网络请求链路与浏览器渲染阶段分层讲清，别混成一段。

#### 深挖追问

1. **第一次访问一定要查询远程 DNS 吗？**（补充练习）

   不一定。浏览器、系统或递归解析器都可能命中缓存，也可能做过预解析。

2. **服务器返回 200 就表示页面已显示吗？**（补充练习）

   不表示。200 只是这个响应的结果，浏览器还要解析、执行和渲染，子资源也可能失败。

### NET-002：HTTP 和 HTTPS 有什么区别，证书如何验证？

**常见问法**

- HTTP 和 HTTPS 有什么区别，TLS 握手如何进行？
- HTTP 和 HTTPS 的区别是什么？
- 为什么能判别证书？
- 每次都要去远程查验证书吗？

- HTTP 和 HTTPS 有什么区别，HTTPS 如何保证安全？

- HTTPS 建立连接的完整流程是什么？

#### 面试回答

HTTPS 就是 HTTP 外面套一层 TLS，换来三件事：传输机密性、完整性、身份认证。

- 证书凭什么信：客户端检查证书链能否到达信任根、域名是否匹配、有效期及用途等；握手中还会验证对方确实掌握相应私钥。
- 不用每次问 CA：验证签名主要在本地完成。吊销状态检查可能使用缓存、OCSP stapling（服务端把吊销结果捎带下来）或浏览器自带机制，取决于客户端策略。

以基于 TCP、证书认证的 TLS 1.3 完整握手为例，消息顺序是：

- 客户端发 ClientHello：携带支持的版本、算法和 key share（自己的密钥共享参数）。
- 服务端回 ServerHello：选定参数并给出 key share，双方各自派生握手密钥。
- 服务端再发一组已加密的消息：EncryptedExtensions、Certificate、CertificateVerify、Finished。
- 客户端验证证书及握手证明，再发 Finished，随后用应用流量密钥保护 HTTP 数据。

#### 技术细节

**别把证书公钥当成业务数据的加密密钥**

- 证书里的公钥，不是拿来直接加密大流量业务数据的密钥。
- 以 TLS 1.3 为例：握手负责协商密钥并认证握手内容，后续记录用对称密钥保护。
- 所以握手用的算法，和旧版 RSA 密钥交换那套叙述不一样，不要混着讲。

**证书这块其实是三个环节**

- 证书链验证、主机名校验、吊销检查是不同环节，别一句“验证证书”带过。
- 客户端可能需要补全中间证书或取得吊销信息，也可能直接用本地数据；不能回答“一定每次联网”或“永远不联网”。

**上面那套握手的适用前提**

- 限定 TLS 1.3 非 PSK（预共享密钥）恢复、无客户端证书认证的常规握手。
- 参数协商不合适时，可能出现 HelloRetryRequest。
- TLS 1.2 的 ECDHE 完整握手消息与此不同，不能把旧式“RSA 加密预主密钥”的流程套到 TLS 1.3。
- TLS 1.3 的 0-RTT 是恢复场景下的可选能力，并且有重放风险。

**两个容易说过头的地方**

- 默认端口 HTTP 为 80、HTTPS 为 443，但端口可配置。
- HTTPS 保护的是传输，不保证服务端业务没有漏洞。

#### 深挖追问

1. **为什么能相信证书？**（面经实际出现；[[面经/拼多多/一面/0001#Q09：HTTP 和 HTTPS 有什么区别，如何验证证书，需要每次远程查验吗？|MJ003 Q09]]）

   因为信任的起点是客户端信任库里的根证书。从根往下逐级验签名和约束，再核对目标域名，最后靠握手里的私钥证明确认对方真的持有这把私钥。

2. **每次都去远程查证书吗？**（面经实际出现；[[面经/拼多多/一面/0001#Q09：HTTP 和 HTTPS 有什么区别，如何验证证书，需要每次远程查验吗？|MJ003 Q09]]）

   不需要每次远程验签。会不会发起网络请求，取决于缓存、服务端提供的信息以及客户端策略；吊销检查和链补全都是这个逻辑，不是一句“一定联网”能概括。

3. **TLS 握手过程是什么？**（面经实际出现；[[面经/百度/一面/0003#Q01：HTTP 和 HTTPS 有什么区别，TLS 握手如何进行？|MJ006 · 百度 · 一面 · Q01]]）

   按 TLS 1.3 常规证书握手讲：ClientHello → ServerHello → 服务端加密的认证消息与 Finished → 客户端 Finished。里面三件事各有各的职责：密钥交换、证书验证、对握手内容的认证。

4. **非对称加密算法知道哪些？加代理抓包会有什么影响？**（面经实际出现；[[面经/字节/一面/0007#Q07：HTTP 和 HTTPS 有什么区别，非对称加密算法知道哪些，加代理抓包有什么影响？|MJ026 · 字节 · 一面 · Q07]]）

   算法先报常见的四种：RSA（用于密钥交换／签名，交换用途正在被逐步弃用）、ECC／ECDSA（同强度下密钥更短，现在的主流证书）、Ed25519、国密 SM2。

   - 但现代 TLS 握手实际用 (EC)DHE 做密钥协商，图的是前向安全；非对称算法主要用在证书签名验证和身份认证上。
   - 抓包代理（mitmproxy／Fiddler／公司网关）是一个受控的中间人：它终止两段 TLS，用自己的自签 CA 现场重签一张证书。
   - 所以客户端必须信任那把根证书才看得到明文，否则握手校验直接失败。
   - 生产 App 常用证书固定（pinning）来对抗，抓不到包多数是这个原因，不是“HTTPS 无法抓”。

### NET-003：TCP 和 UDP 有什么区别？

**常见问法**

- TCP 和 UDP 的区别是什么？

- TCP 和 UDP 有什么区别？
- TCP 和 UDP 的区别，以及对应的使用场景？

#### 面试回答

- TCP：面向连接，提供可靠、有序的字节流，自带重传、流量控制和拥塞控制；但它不保留消息边界。
- UDP：无连接的数据报，保留报文边界；协议本身不保证送达、不保证有序、也不去重。
- 选型看业务的需要：要不要这些语义、对延迟要求多高。
- 别顺口说成“UDP 一定更快”或者“UDP 只能用于不可靠业务”，这两句都不严谨。

#### 技术细节

**TCP 侧要自己做分帧**

- 字节流没有边界，应用得靠自定义长度头、分隔符或固定长度等方式做消息 framing（把字节流切成一条条消息）。

**UDP 侧要自己兜住这些坑**

- 得处理丢包、乱序，以及数据报超过接收缓冲时被截断。
- 但可以在 UDP 之上实现可靠协议，例如 QUIC；所以“基于 UDP”不代表上层没有可靠传输。

**别把可靠性说满**

- TCP 的可靠性指的是连接内的字节交付，不等于应用已经把数据持久化或处理成功。

**首部大小只是其中一项**

- TCP 头部通常至少 20 字节，UDP 为 8 字节。
- 但首部差异不是“谁性能更好”这个结论的全部依据。

#### 深挖追问

1. **UDP 可以 connect 吗？**（补充练习）

   可以。socket API 上的 connect 只是设置默认对端和相关的过滤语义，并不会变成 TCP 那种握手建立的连接。

2. **为什么 TCP 有所谓粘包？**（补充练习）

   因为它是字节流：多次发送和多次接收调用之间没有一一对应的边界。要一条一条消息，就得应用协议自己分帧。

### NET-004：TCP 四次挥手与 TIME_WAIT 是什么？

**常见问法**

- TCP 四次挥手的过程是什么？
- 什么是 TIME_WAIT？
- 为什么要进行 TIME_WAIT？

- TCP 四次挥手如何进行，第二次和第三次能否合并？
- 为什么 TCP 要采用四次挥手而不是三次？
- 挥手两次或三次分别会有什么问题？

#### 面试回答

正常关闭按报文讲：

- 一方发 FIN，对端回 ACK。
- 对端把自己那边也发完了，再发一个 FIN；主动关闭方回 ACK，然后进入 TIME_WAIT。
- 两个方向是独立关闭的，所以常见是四个报文；ACK 和 FIN 在某些情况下也可以合并。
- TIME_WAIT 通常持续 2MSL（最大报文段生存时间的两倍）：一是最后的 ACK 丢了还能重传确认 FIN，二是降低旧连接的报文影响后续同四元组连接的风险。

#### 技术细节

**两边的状态序列**

- 主动关闭方通常经历 FIN_WAIT_1、FIN_WAIT_2、TIME_WAIT。
- 被动关闭方经历 CLOSE_WAIT、LAST_ACK。

**一个容易混的状态**

- CLOSE_WAIT 长期堆积，通常提示应用没去关闭那些已经收到 FIN 的连接；这跟 TIME_WAIT 不是一回事，别混淆。

**三个容易说死的点**

- 主动关闭方不一定是客户端，服务端也可以主动关。
- 双方同时关闭时，也可能两边都进入 TIME_WAIT。
- 协议里的 MSL 和具体操作系统的计时常量不同，不要背一个固定秒数当成所有系统的规则。

**调参数之前**

- 贸然调整连接复用相关参数可能改变连接语义，应先把连接生命周期查清楚。

**原题前提要纠正**

- 原题“第二次和第三次为什么不能合并”带着不准确的前提。
- 确认收到对方的 FIN，不代表本方已经结束发送。
- 本方还有数据要发时，就先 ACK、之后再来一个 FIN；已经具备关闭条件时，ACK 和 FIN 可以合并。

#### 深挖追问

1. **为什么要等 2MSL？**（面经实际出现；[[面经/百度/一面/0001#Q09：TCP 四次挥手是什么过程，TIME_WAIT 为什么要等待？|MJ002 Q09]]）

   为了给两件事留时间：最后那个确认还能被重传，旧连接的报文也自然消退。这属于关闭协议本身的一部分，不是在等业务处理完成。

2. **被动关闭方收到 FIN 后还能发数据吗？**（补充练习）

   可以。FIN 只关闭一个发送方向，另一个方向仍然可以把剩余数据发完。

3. **为什么第二次与第三次通常分开发？**（面经实际出现；[[面经/百度/一面/0005#Q07：TCP 四次挥手如何进行，第二次和第三次能否合并？|MJ008 · 百度 · 一面 · Q07]]）

   因为这是两个独立事件：确认对方发送结束，和本方自己发送结束。所以通常分开发；本方已具备关闭条件时，ACK 和 FIN 就可以合并。

### NET-005：服务器断开后，客户端会有什么表现？

**常见问法**

- 服务器断了之后有什么表现？

#### 面试回答

先分清三种情况：正常关闭、复位、突然失联。

- 正常 FIN：客户端要先把已经缓冲的数据读完，recv 才返回 0。
- 收到 RST：可能直接报连接重置。
- 断电或网络黑洞（什么报文都没有）：客户端未必能立即知道。有数据要发时会经历重传并最终超时。
- 连接一直空闲时，就得靠 keepalive 或应用层心跳加超时机制才能发现。

#### 技术细节

**“断了”不是一个事件**

- 进程正常退出时，内核可能执行连接的关闭流程。
- 主机直接掉电，就没办法主动发出 FIN。

**一次写成功说明不了什么**

- send 返回成功，可能只是数据进了本机发送缓冲，既不证明对端在线，也不证明业务成功。

**超时要分层配**

- 读超时、连接超时、请求总超时管的是不同阶段。
- 心跳能反映应用是否还在响应，TCP keepalive 主要探测的是连接活性，两者含义不同。

**重试的副作用**

- 重试前要考虑上一次请求是不是已经产生了副作用，必要时用幂等标识。

#### 深挖追问

1. **第一次写成功，第二次才报错正常吗？**（补充练习）

   可能，这属于正常现象。错误到达和应用写入是异步发生的，一次本地写成功并不代表对端已经处理确认。

2. **只有心跳就能证明业务可用吗？**（补充练习）

   不能。心跳那条路径成功，不保证所有依赖都正常，还要配合请求级的状态和超时一起判断。

### NET-006：TCP 如何保证可靠传输？

**常见问法**

- 什么是 TCP 滑动窗口，丢包后如何处理？
- TCP 怎么保证可靠传输？

#### 面试回答

TCP 靠一套机制组合起来保证可靠有序：序号、确认、校验和、重传，加上接收端的重排和去重。

- 滑动窗口：发送方在收到确认之前，可以连续发一段范围内的数据，不必每发一段就停下来等 ACK。
- 窗口怎么动：ACK 推进已确认边界，窗口跟着滑动；接收窗口 rwnd 限制接收方的容量，拥塞窗口 cwnd 限制在网络里的在途数据。
- 丢包怎么办：通过重传超时、重复 ACK、SACK（选择性确认）这类线索检测出来再重传。
- 接收端：乱序的数据先缓存着，重复的去掉，最后按序交给应用。
- 两句边界：连接永久中断时照样会报错；TCP 的确认也不代表远端业务已处理或已持久化。

#### 技术细节

**确认的到底是什么**

- 确认的是连接里的数据接收，不是远端应用已经消费或已经写盘。

**两个窗口各管一头**

- 接收窗口 rwnd 反映接收侧的容量，拥塞窗口 cwnd 是发送侧对网络承载能力的估计。
- 实际能不能发，还看在途数据的影响。简化看，在途数据上限受 min(rwnd, cwnd) 约束，新发送的额度还要扣掉已经在途的字节。

**丢包怎么被发现**

- 重复 ACK、SACK 等线索可以帮助识别丢失的区间；RTO（重传超时）按 RTT 等因素估计出来。
- 经典快速重传可以由三个重复 ACK 触发，但现代实现还有别的丢失检测机制；不能认为每次丢包都必然出现三个重复 ACK。

**按序交付的代价**

- 后面的数据即使已经到了，也可能要等前面那个缺口补上才能交付。

**按序号排序与拼接（乱序处理）**

- 每个 TCP 段带 seq（本段第一个字节的序号）＋数据长度，接收端据此把段放到字节流的正确位置；缺口未补齐之前不向上交付。
- 累计 ACK 指向「下一个期望字节」，SACK 块补充已收到的非连续区间，发送方只重传真正缺的那段。
- 例：期望 x+10，先到的是 x+20 长 10 的段——缓存并回 ACK x+10（带 SACK x+20~x+30）；x+10~x+19 补到后两块连成交付。
- 重复段：序号整体落在已确认区间内，直接丢弃。

**几个容易说过头的点**

- TCP 校验和用于传输差错检测，不是抵御恶意篡改的认证机制。
- 累计 ACK 指向下一个期望的字节，SACK 补充已经收到的非连续区间。
- 超时不只是重传，还会调整拥塞控制；但丢了 ACK 不等于对应数据必然重传，后续的累计 ACK 可能已经把它覆盖了。

#### 深挖追问

1. **收到 ACK 就能删除业务重试记录吗？**（补充练习）

   通常不能。ACK 只说明对端收到了字节，业务是否完成要等应用层的确认，完成条件按幂等和持久化要求来定义。

2. **流量控制和拥塞控制有什么不同？**（面经实际出现；[[面经/字节/一面/0004#Q19：介绍一下 TCP 的拥塞控制和流量控制。|MJ014 · 字节 · 一面 · Q19]]）

   一个防接收方、一个防网络：前者用 rwnd 避免压垮接收方，后者用 cwnd 避免压垮网络，两者同时约束可发送的数据。完整机制见 [[专题题库/计算机网络#NET-017：TCP 拥塞控制和流量控制如何工作，有什么区别？|NET-017：TCP 拥塞控制和流量控制如何工作，有什么区别？]]。

3. **丢包了怎么处理？**（面经实际出现；[[面经/百度/一面/0003#Q06：什么是 TCP 滑动窗口，丢包后如何处理？|MJ006 · 百度 · 一面 · Q06]]）

   先检测缺口再重传：依据超时或确认信息判断丢了哪一段，重传之后按拥塞控制调整发送节奏。接收端这边对乱序段缓存、对重复段去重，直到能按序交付为止。

4. **什么情况下会产生丢包？**（面经实际出现；[[面经/腾讯/一面/0001#Q09：什么情况下会产生丢包？丢包后 TCP 怎么处理？|MJ046 · 腾讯 · 一面 · Q09]]）

   按“谁丢的”分四类：

   - 转发设备主动丢弃：网络拥塞时路由器／交换机缓冲队列满（大头），或限速／RED 类队列管理策略丢弃。
   - 链路损坏：比特翻转使校验（FCS 等）失败，帧在链路层就被扔掉——无线干扰、线缆质量差时概率高。
   - 接收主机侧丢弃：网卡环形缓冲溢出（应用收得慢）、iptables／nftables 按规则 DROP。
   - 配置与策略黑洞：路由不可达被静默丢弃、防火墙策略、MTU 不匹配带 DF 的包被丢（PMTUD 黑洞）。
   - TCP 的处理见上一问；对业务而言重点是：重传让“传多久”不确定，所以大传输必须分片＋续传＋幂等，把丢包当常态而不是异常。

### NET-007：大文件如何通过 TCP 传输，TCP／IP 一次最多传多少？

**常见问法**

- 一个很大的文件，TCP 可以一次传完吗？
- TCP 一次最大传多少？
- IP 一次传多少？

#### 面试回答

- 同一 TCP 连接可以持续把大文件传完，但不是“一个 TCP 段发完”。
- 三个概念要分开：应用一次 write 的长度、TCP 单段的数据量、IP 包的大小。
- TCP 按 MSS（最大报文段长度）等限制分段，MSS 又受对端通告和路径 MTU 约束。
- 举个常见数：MTU 1500、IPv4 无选项且 TCP 无选项时，单段数据通常是 1460 字节 —— 这不是一个通用的固定上限。

#### 技术细节

**IPv4 的 65535 不等于 payload**

- IPv4 总长度字段是 16 位，单个数据报最多 65535 字节，而且这个数包含 IP 头。
- TCP 能带的数据还要再扣掉 IP 头和 TCP 头，不能把 65535 直接当 payload。

**IPv6 的口径不同**

- IPv6 普通包的 payload length 最多 65535 字节，不含固定的 40 字节头；扩展头要算进 payload。
- jumbo payload（超大载荷）是额外的一套机制。

**分片**

- IPv4 可能分片，IPv6 的路由器不做分片。
- 实际传输通常尽量避免 IP 分片。

**发送侧还有两件事**

- send 可能短写：返回的字节数少于请求量，大文件要循环发送，或者用适用的零拷贝接口。
- TSO／GSO（网卡和内核的大包分段卸载）会让本机抓包看到比线上实际段更大的数据单元，别据此判断 MSS。

#### 深挖追问

1. **很大的文件可以一次传完吗？**（面经实际出现；[[面经/拼多多/一面/0001#Q12：TCP 如何传大文件，一次写入、TCP 单段和 IP 包的大小有什么区别？|MJ003 Q12]]）

   一个连接可以传完，一个段不行。还要补一句：一次系统调用既不保证把数据全部提交，更不保证对端已经收到。

2. **TCP 和 IP 的最大长度能报一个数吗？**（面经实际出现；[[面经/拼多多/一面/0001#Q12：TCP 如何传大文件，一次写入、TCP 单段和 IP 包的大小有什么区别？|MJ003 Q12]]）

   不能直接报数。要先说清协议版本、首部长度、MTU，以及你说的“一次”指的是系统调用、TCP 段还是 IP 数据报。

### NET-008：ICMP 是什么，有什么作用？

**常见问法**

- ICMP 知道吗？

#### 面试回答

ICMP（互联网控制报文协议）做两件事：报告错误、支持诊断。

- 常见报文：目的不可达、TTL 超时、Echo 请求与响应。
- ping 用 Echo 检查可达性；traceroute 利用逐跳的 TTL 和超时信息看路径。
- 两句边界：ICMP 不是跑在 TCP 或 UDP 端口上的服务；ping 不通也不能直接下结论说网站不可用，可能是被策略过滤了。

#### 技术细节

**差错报文里带什么**

- ICMP 差错消息通常携带触发问题的那个数据包的信息，供上层定位是哪次通信出的问题。

**和路径 MTU 发现的关系**

- IPv4“需要分片但 DF 位置位”的反馈，以及 IPv6 的 Packet Too Big，都和路径 MTU 发现有关。
- 把这些反馈全部屏蔽掉，可能造成黑洞：包在中间被丢了，发送方却收不到任何提示。

**IPv4 和 IPv6 不是一套编号**

- ICMPv6 与 IPv4 的 ICMP 并不完全相同，它还承担邻居发现等功能。
- 两边的类型编号不能混用。

**诊断结论要留余地**

- 网络设备可能对 ICMP 限速或者干脆不回复，所以诊断结果要结合应用层的连接表现一起看。

#### 深挖追问

1. **ping 通说明 TCP 端口开放吗？**（补充练习）

   不说明。两者检查的是不同路径、不同协议的行为，还要单独测目标端口和应用响应。

2. **traceroute 中某跳星号意味着后续不可达吗？**（补充练习）

   不一定。中间路由器可能不回应诊断报文，但照样正常转发流量。

### NET-009：Socket 编程的基本流程与关键问题是什么？

**常见问法**

- Socket 编程。

#### 面试回答

- TCP 服务端：socket → bind → listen → accept，之后用 accept 出来的新连接描述符收发。
- TCP 客户端：socket → connect，然后收发。
- 注意监听 socket 和连接 socket 是两个不同的对象。
- 代码层面必须处理的：短读短写、EOF、错误、超时、消息边界。
- 并发连接多时，配合非阻塞 I/O 和 epoll，而不是每个连接都阻塞在那儿等。

#### 技术细节

**先说答题范围**

- 原题只有“socket 编程”，这里按基础流程作答，不推断当时曾要求某种服务端实现。

**接收：按协议累计，不按调用次数**

- 接收循环要把数据按协议累计起来：例如先读固定长度的头，再按头里的长度读 body。
- 不能把一次 recv 的返回当成一条完整消息。

**返回值怎么读**

- read／recv 返回正数：是本次实际读到的字节数。
- 返回 0：在 TCP 流上代表有序 EOF。
- 返回 -1：还要区分 EINTR、EAGAIN 和真正的错误。

**发送侧**

- 发送要不断推进偏移，直到全部写完或者等待可写事件。
- 同时设置合理的消息上限和背压。

**UDP 不一样**

- UDP 用 sendto／recvfrom 等接口，保留报文边界，也没有 accept 这套流程。

#### 深挖追问

1. **accept 返回的 socket 用来做什么？**（补充练习）

   用来和某一个已经建立的客户端连接通信；原来的监听 socket 继续接收其他连接。

2. **可写事件一直触发怎么办？**（补充练习）

   只在确实有待发送数据时才关注可写事件，发完就把这个关注关掉；否则事件循环会一直空转。

### NET-010：TCP 三次握手如何进行，握手期间能携带数据吗？

**常见问法**

- TCP 为什么需要三次握手，两次行不行？
- 三次握手的过程是什么？
- 握手期间可以传参数吗？
- TCP 的序列号是怎么生成的？发送方初始序列号 x、发 10 字节数据，对方回什么 ACK？

#### 面试回答

三次握手按序号讲：

- 客户端发 SYN，seq=x。
- 服务端回 SYN+ACK，seq=y、ack=x+1。
- 客户端回 ACK，ack=y+1，双方连接建立。
- 这一步的作用：双方各自确认对方的初始序号，也确认双向通信状态。

握手期间能不能带东西：

- 握手报文可以带 MSS、窗口扩大等 TCP 选项。
- 第三次 ACK 可以携带应用数据。
- 但普通连接不会依赖首个 SYN 去交付业务参数；TCP Fast Open 这类机制才允许在特定条件下提前发送数据。

两次握手为什么不够：服务端还不知道客户端有没有收到自己的初始序号、是否仍参与当前连接。第三次确认才完成双向序号同步，也避免仅凭一个延迟到达的旧 SYN 就认为连接已经建立。

#### 技术细节

**序号和状态怎么算**

- SYN 占一个序号，纯 ACK 不占；所以不带数据时，第三次 ACK 的 seq 通常是 x+1。
- 服务端在收到最终确认前通常处于 SYN_RECEIVED；客户端收到 SYN+ACK、发出确认后进入 ESTABLISHED。
- 应用什么时候可写、对端什么时候处理，仍然依赖具体实现。

**“参数”有三种含义，必须先区分**

- 可能指 TCP 选项，也可能指 HTTP 查询参数，或者是应用自己的 payload。

**SYN 带数据是有条件的**

- TCP 规范允许 SYN 携数据，但对交付有约束。
- TFO（TCP Fast Open）通过协商／Cookie 等机制，让支持端在完整握手之前就处理数据；这不代表所有首连的 SYN 都可以任意承载应用请求。
- 被提前处理的数据还要考虑重放和幂等。

**别只背“确认双方收发能力”**

- 关键还包括两件事：双方各自独立初始序号的确认，以及对旧的重复连接请求的处理。
- 普通被动打开时，服务端发出 SYN+ACK 后处于 SYN_RECEIVED，收到有效的最终 ACK 才进入 ESTABLISHED。
- 第三次 ACK 丢失，可以通过 SYN+ACK 重传以及后续的有效确认来恢复。

#### 深挖追问

1. **握手期间可以传参数吗？**（面经实际出现；[[面经/北京某上市公司/一面/0001#Q16：TCP 三次握手如何进行，握手期间可以传参数或数据吗？|MJ004 一面 Q16]]）

   分三层说：TCP 选项本来就在握手里协商；应用数据可以由第三次 ACK 携带；SYN 直接带数据，则要讲清规范约束和 TFO 等实现条件。

2. **为什么不是两次握手？**（面经实际出现；[[面经/百度/一面/0003#Q05：TCP 为什么需要三次握手，两次行不行？|MJ006 · 百度 · 一面 · Q05]]）

   两次不够。服务端无法确认客户端已经收到自己的初始序号、并且还在参与当前连接；第三次确认才完成序号同步。

3. **第三次握手的 ACK 丢了，连接还能建成吗？客户端紧接着发数据会怎样？**（面经实际出现；[[面经/字节/二面/0002#Q03：TCP 三次握手中第三次握手的 ACK 丢失，协议如何恢复？若客户端随后立即发数据且早于重传的 ACK 到达服务端，服务端能否正确处理，怎么优化？|MJ042 · 字节 · 二面 · Q03]]）

   关键是两侧状态不对称：

   - 客户端发完 ACK 就进入 ESTABLISHED，服务端仍停在 SYN_RECEIVED，而且已经分配了连接控制块。
   - 恢复靠服务端反复重传第二个报文（SYN+ACK）：指数退避，且有重试上限（Linux 由握手重试次数参数控制，默认几次）。
   - 超过上限就丢弃这个 TCB、释放资源，客户端此后收到的是 RST；如果 ACK 在这个窗口内补到，就正常转入 ESTABLISHED。

   客户端随后发数据通常能被正确处理：

   - SYN 占一个序号，所以第一个数据字节的序号正好是服务端期望的值。
   - 这个数据报文自带的 ACK 会把状态直接推进到 ESTABLISHED —— 数据报文本身补完了第三次握手，不必等那个丢失的 ACK。
   - 旧连接的乱序报文靠序号窗口判定丢弃，这也是 TIME_WAIT 存在的原因之一。

   优化分三侧：

   - 客户端：用连接池复用，开 TCP Fast Open 让 SYN 带请求体，省一个 RTT。
   - 服务端：调低 SYN 重传与半连接超时以更快回收，用 SYN Cookie 抵御洪泛（不预先分配 TCB），限制单源连接数与空闲超时。
   - 应用侧：显式设超时并按幂等重试，因为“连接是否还活着”从错误码上区分不出来。

4. **序列号是怎么生成的？初始序号 x、发 10 字节数据，对方回什么 ACK？**（面经实际出现；[[面经/点点互动/一面/0001#Q13：TCP 序列号怎么生成？发 10 字节后 ACK 是多少，乱序到达如何靠序列号拼接？|MJ064 · 点点互动 · 一面 · Q13]]。原素材未记回答，以下为参考）

   - ISN（初始序号）生成：RFC 6528 建议「每秒递增 25 万（约 4 微秒 +1）的计数器，再混入按连接四元组计算的随机偏移」；不是固定 0，也不是纯随机。
   - 为什么要随机化：防止上一个连接遗留的报文被新连接误收（历史报文），也提高序号猜测／盲注入攻击的成本。
   - ACK 计算先说前提：若 x 是握手完成后第一个数据字节的序号（SYN 已消耗 x），这 10 字节占 x～x+9，服务端回 ack=x+10。
   - 若题意指首包 seq=x 且该包带 10 字节数据：SYN 本身占一个序号，数据实际从 x+1 开始，ack=x+11。
   - 考试式追问里两种口径都主动讲出来，比只报一个数稳。ACK 是「期望的下一个字节序号」，不是「收到的段数＋1」。

5. **乱序到达的段怎么靠序号拼接？**（面经实际出现；[[面经/点点互动/一面/0001#Q13：TCP 序列号怎么生成？发 10 字节后 ACK 是多少，乱序到达如何靠序列号拼接？|MJ064 · 点点互动 · 一面 · Q13]]。原素材未记回答，以下为参考）

   每个段带 seq＋长度，接收端按序号放进重排缓冲区，累计 ACK 只推进到连续边界，缺口用 SACK 上报；详见 [[#NET-006：TCP 如何保证可靠传输？|NET-006：TCP 如何保证可靠传输？]]。

### NET-011：DNS 解析过程是什么，递归和迭代有什么区别？

**常见问法**

- DNS 解析过程是什么，递归和迭代有什么区别？
- 往外发请求时会经过哪些行为？比如发 DNS 请求，更细节的网络行为有哪些？

#### 面试回答

- 客户端：先查适用的本地缓存和主机映射；未命中就通常向递归解析器发查询。
- 解析器：自己有缓存就直接返回；否则按需从根、顶级域一路问到权威服务器，拿到目标记录后缓存并返回。
- 递归和迭代的区别：递归是把“返回最终结果或错误”整个委托给对方；迭代是对方只给已有答案或下一步该问谁，由查询方继续追。
- 常见组合：客户端向解析器递归查询，解析器再向各级服务器迭代查询。

#### 技术细节

**一次逐级查询长什么样**

- 例如查 www.example.com 的 A／AAAA 记录：根通常返回 .com 的委派信息，.com 返回 example.com 权威服务器的信息，权威服务器给出记录。
- 已经有委派缓存时，前面的步骤可以跳过。

**几个容易漏的行为**

- CNAME 命中后要继续解析别名的目标。
- 缓存遵守 TTL；否定结果（查无此名）也会被缓存。

**别把 DNS 说窄了**

- DNS 不只是“域名转 IP”，还有 MX 等其他记录类型。
- 传输也不限于 UDP，还存在 TCP、DoT（DNS over TLS）、DoH（DNS over HTTPS）。
- 转发型解析器也可能向上游做递归查询。

#### 深挖追问

1. **递归和迭代分别由谁继续查询？**（面经实际出现；[[面经/百度/一面/0003#Q07：DNS 解析过程是什么，递归和迭代有什么区别？|MJ006 · 百度 · 一面 · Q07]]）

   递归：由受托的那台服务器完成剩余解析。迭代：由查询者拿着 referral（下一跳指引）自己继续问。实际部署会把缓存、转发和迭代组合起来用。

2. **常见的 DNS 记录类型有哪些，你最常用哪种？**（面经实际出现；[[面经/字节/一面/0010#Q17：讲一下 DNS 的工作原理；常见的 DNS 记录类型有哪些，你用得比较多的是哪一种？|MJ042 · 字节 · 一面 · Q17]]）

   先报类型：

   - A（→IPv4）、AAAA（→IPv6）。
   - CNAME：规范别名，指向另一个域名，不能与同名其他记录共存；业务域名指到 CDN／负载均衡就靠它。
   - NS：该域的权威服务器。MX：邮件交换，带优先级。
   - TXT：任意文本，SPF／DKIM／`_dmarc` 和域名归属验证都放这里。
   - PTR：反解 IP→域名，邮件与风控校验常用。
   - SRV：服务定位，协议＋端口＋权重。CAA：限定哪些 CA 可以为本域签发证书。

   自己最常用的：A／AAAA 和 CNAME 最多，其次是部署邮件或验证域名归属时的 TXT／MX，配证书时会用到 CAA。

   加分点是把解析结果的不确定性说出来：

   - CNAME 链要一路续查；多条 A 记录按轮询或就近返回；否定答案也会被缓存。
   - 切流量时 DNS 不可靠：TTL 只约束缓存什么时候过期，客户端的缓存并不受你控制。要秒级摘流量，得靠网关或负载均衡侧的手段。

### NET-012：Cookie、Session 和 Token 有什么区别？

**常见问法**

- Cookie、Session 和 Token 有什么区别？
- Cookie 和 Token 如何维持登录态？

#### 面试回答

三个词不是一个层面的东西，先各给一句定义：

- Cookie：浏览器保存数据、并按域和路径这些规则随请求带上去的机制。
- Session：维护会话状态的方案；常见做法是服务端存状态，客户端用 Cookie 携带 session ID。
- Token：代表身份或授权的凭证，可以是服务端要去查的不透明值，也可以是自带签名的自包含令牌。
- 三者不互斥：Cookie 里可以放 session ID，也可以放 Token；另外，Token 不等于 JWT。

#### 技术细节

**Session 这一侧**

- 好处是集中控制过期和注销。
- 代价是多实例要共享会话存储，或者采取路由策略。

**自包含 Token 这一侧**

- 好处是不必每次都去查会话。
- 但想做到立即撤销，通常还是得维护黑名单、版本号这类状态，或者把有效期设短。
- JWT 的签名不等于加密；服务端必须验证签名、有效期、签发方、受众等约束。

**Cookie 的三个属性**

- HttpOnly：限制脚本读取。
- Secure：限定只能在安全传输下发送。
- SameSite：约束跨站时是否发送。
- 凭证存在哪、怎么发出去，直接决定了相应的 CSRF／XSS 风险有多大。

#### 深挖追问

1. **用 Token 就不需要防 CSRF 了吗？**（补充练习）

   不一定。关键看 Token 放在哪里：放在浏览器会自动携带的 Cookie 里，就仍然要防 CSRF。改用显式的 Authorization 头通常能降低这类自动携带风险，但 XSS 和错误的跨域配置还得单独防。

2. **服务端 Session 外置后（如 Spring Session），存的到底是什么？**（面经实际出现；[[面经/收钱吧/一面/0001#Q07：Spring Session 中存储的是什么数据？|MJ068 · 收钱吧 · 一面 · Q07]]）

   存的是会话元数据（id、创建／最后访问时间、空闲超时、principalName）＋attribute 键值对；客户端 Cookie 只有一个会话 ID。对象要序列化进共享存储，所以属性必须可序列化且体积小——字段与序列化细节见 [[专题题库/Spring#SPRING-014：Spring Session 中存储的是什么数据？|SPRING-014：Spring Session 存储内容]]。

### NET-013：OSI 七层与 TCP/IP 四层如何映射？

**常见问法**

- OSI 七层与 TCP/IP 四层如何映射？

- TCP/IP 四层模型有哪些，每层作用及对应协议？

#### 面试回答

- OSI 从低到高七层：物理、数据链路、网络、传输、会话、表示、应用。
- 常见的 TCP/IP 四层模型这样归并：物理和数据链路合进链路层，网络层对应网际层，传输层还是传输层，会话、表示、应用归进应用层。
- 两者的定位不同：OSI 是参考分层，TCP/IP 是围绕互联网协议体系组织出来的。
- 补一句边界：这个映射是教学上的概括，实际协议的职责不总能严格一一对应。

#### 技术细节

**先说口径**

- 下面是常见的四层映射；某些教材会把物理层单独拆出来称五层模型，讲之前要先说明用的哪一种口径。

| OSI | TCP/IP 四层 | 示例或职责 |
| --- | --- | --- |
| 应用、表示、会话 | 应用层 | HTTP、DNS；应用数据表达与会话功能由具体协议实现 |
| 传输 | 传输层 | TCP、UDP |
| 网络 | 网际层 | IP、ICMP |
| 数据链路、物理 | 链路层 | 以太网、Wi-Fi、介质传输 |

**封装的顺序**

- 应用消息 → 传输层段或数据报 → IP 包 → 链路帧。
- 链路帧在不同跳上可能重新封装，所以不要把各层的地址混为一谈。

#### 深挖追问

1. **OSI 与 TCP/IP 是严格一一对应吗？**（补充练习）

   不是。七层参考模型和互联网协议实现的分层粒度本来就不同，通常的做法是把上三层和下两层合并来解释。

### NET-014：HTTP 各版本特性与常见状态码是什么？

**常见问法**

- HTTP 各版本特性与常见状态码是什么？
- HTTP 503 和 504 有什么区别？
- HTTP/1.0、HTTP/1.1、HTTP/2.0 版本的差异？

- HTTP 状态码有哪些？5 开头的呢？
- HTTP 返回码 302 是什么意思？

#### 面试回答

HTTP 是应用层的请求／响应协议：定义方法、资源、状态码和表示这些语义，本身是无状态的。

各版本按“解决上一版什么问题”来讲：

- HTTP/1.0：通常每次请求都建一条连接。
- HTTP/1.1：默认持久连接，支持管线化，但响应仍然要按顺序返回。
- HTTP/2：改成二进制帧，支持多路复用，用 HPACK 压缩头部；但仍然受 TCP 丢包带来的连接级队头阻塞影响。
- HTTP/3：基于 QUIC，使用 QPACK，降低了跨流的传输层队头阻塞。

状态码按第一位分类：

- 1xx 信息、2xx 成功、3xx 重定向、4xx 客户端错误、5xx 服务端错误。
- 常见的：200、201、204；301、302、304、307、308；400、401、403、404、405、409、429；500、502、503、504。
- 别搞错：304 是缓存验证后不需要重传表示，不是页面重定向。

#### 技术细节

**语义和传输表达要分开讲**

- HTTP/2 的多路复用解决的是 HTTP/1.1 请求响应串行的限制，但底下 TCP 一旦丢包，仍然会影响这条连接上的所有流。
- QUIC 提供的是按流独立交付，但不能据此声称“没有拥塞、没有流内等待、也没有任何应用层依赖”。

**常见状态码对照**

| 状态码 | 含义 |
| --- | --- |
| 200／201／204 | 成功／资源已创建／无响应内容 |
| 301／302 | 永久／临时重定向，某些方法在重定向时可被改写 |
| 307／308 | 临时／永久重定向，保持请求方法 |
| 304 | 条件请求验证未修改，可复用缓存表示 |
| 400／401／403／404 | 请求错误／缺少有效认证凭据／拒绝执行／资源未找到或不愿披露 |
| 405／409／429 | 方法不允许／资源状态冲突／请求过多 |
| 500／502／503／504 | 内部错误／网关收到无效上游响应／暂时不可用／网关等待上游超时 |

**连接复用：Keep-Alive**

- 连接什么时候断：任何一方主动关闭（服务端回 `Connection: close`、进程退出、网络中断），或空闲超过服务端 keep-alive 超时；HTTP 层不维持心跳，断开就是 TCP 层 FIN／RST。
- 短连接：一次请求-响应用一条新建再关闭的 TCP 连接，握手挥手开销按请求重复付；HTTP/1.0 默认如此。
- 持久连接：HTTP/1.1 默认开启，一条 TCP 顺序承载多个请求；`Keep-Alive: timeout=5, max=1000` 只是双方约定超时与次数的提示字段，不是强制。
- 别混淆：HTTP 的 Keep-Alive 是应用层的连接复用；TCP 的 SO_KEEPALIVE（默认两小时量级的探活）是传输层保活，两者名字像、机制无关。

**一条边界**

- 状态码表示的是协议层的处理结果，它不替代业务响应的具体契约。

#### 深挖追问

1. **HTTP/2 是否完全消除了队头阻塞？**（补充练习）

   没有。不同流可以复用同一条连接，但底层 TCP 是字节流，一处缺口仍会阻塞后续字节的交付。

2. **503 和 504 有什么区别？**（面经实际出现；[[面经/百度/一面/0007#Q03：HTTP 状态码如何分类，503 和 504 有什么区别？|MJ009 · 百度 · 一面 · Q03]]）

   503 是服务当前暂时无法处理请求，常见于过载或维护；504 是网关或代理等待上游响应超时。`Retry-After` 可以用来告诉客户端 503 之后多久再试，但并非每个 503 都一定带这个头。

3. **500／502／503／504 怎么快速区分错误来源？**（面经实际出现；[[面经/美团/一面/0001#Q10：HTTP 状态码有哪些？5 开头的呢？|MJ031 · 美团 · 一面 · Q10]]）

   按责任方区分：

   - 500：本服务处理时抛出的通用内部错误。
   - 502：本服务作为网关／代理时，从上游拿到了无效响应（上游崩溃、返回不合规报文）。
   - 503：本服务明确表示当前承接不了（过载、维护、限流降级）。
   - 504：上游在超时窗口内没有响应。

   排障含义也就跟着不同 —— 502／504 先查上游和网关配置，503 先查本服务的容量和开关，500 查本服务的异常日志。

4. **HTTP 连接什么时候断开？什么是短连接？Keep-Alive 字段的作用是什么？**（面经实际出现；[[面经/点点互动/一面/0001#Q11：HTTP 连接什么时候断开？什么是短连接？Keep-Alive 字段的作用是什么？|MJ064 · 点点互动 · 一面 · Q11]]。原素材未记回答，以下为参考）

   - 断开：一方主动关（`Connection: close`、进程退出）或空闲超时；TCP 层对应 FIN／RST。
   - 短连接：每个请求新建并关闭一条 TCP 连接（HTTP/1.0 默认），握手挥手开销按请求重复付。
   - Keep-Alive：让一条 TCP 承载多个请求的复用机制，HTTP/1.1 默认开启；`Keep-Alive:` 头只是超时／次数的提示。
   - 和 TCP 层的 SO_KEEPALIVE 探活不是一回事，被追问时主动区分。

### NET-015：如何通过 IP 地址解析链路层地址？

**常见问法**

- 如何通过 IP 地址解析链路层地址？

#### 面试回答

先把“物理地址”按以太网 MAC 地址来理解，然后分两种目标：

- 目标在本地链路：IPv4 主机先查邻居缓存；没有记录就用 ARP 在本地链路广播请求，由目标回复自己的 MAC。
- 目标不在本地链路：要解析的是下一跳网关的 MAC，不是远程服务器的 MAC。ARP 广播不会跨过路由器传遍互联网。
- IPv6：不用 ARP，改用基于 ICMPv6 的邻居发现。

#### 技术细节

**先明确前提**

- 这里的“物理地址”指以太网 MAC 地址，不是主机内存地址；回答前要把这句口径说出来。

**完整的发送顺序**

- 先查路由确定下一跳，再查询或解析邻居地址，最后才封装链路帧。

**ARP 报文怎么走**

- 请求用本地链路广播，普通应答通常单播返回，结果会缓存在邻居表里。
- 目标是互联网地址时，本机通常只能解析出网关的 MAC；链路帧在每一跳都会重新封装。

**一条安全边界**

- ARP 本身缺乏可信身份认证，不能把它的映射关系当成不可伪造。

**IPv6 侧**

- IPv6 邻居发现使用 Neighbor Solicitation／Advertisement 等机制。

#### 深挖追问

1. **远程服务器 IP 能直接 ARP 到它的 MAC 吗？**（补充练习）

   不能。ARP 不会跨路由广播去解析，本机拿到的通常是下一跳网关的链路地址。

### NET-016：SSE 和 WebSocket 有什么区别，如何选择？

**常见问法**

- SSE 和 WebSocket 有什么区别？
- 什么情况使用 SSE，什么情况使用 WebSocket？

- WebSocket 断开重连如何设计？
- 如何设计 WebSocket 实现多人同时编辑？（通道选型，设计主线见 SYS-030）
- WebSocket 的握手与帧是怎么工作的？（详见 NET-022）

- 能介绍一下 SSE 是什么吗？
- 为什么 HTTP 只能请求-响应，WebSocket 能主动推送数据？
- WebSocket 和 Socket 分别属于哪一层的协议？

#### 面试回答

- SSE：走 HTTP 响应流，内容类型是 `text/event-stream`，浏览器用 `EventSource` 持续接收服务端事件。它主要解决服务端到客户端的单向推送，上行通常还是走普通 HTTP。
- WebSocket：握手完成之后是一条双向通道，两边都能主动发文本或二进制消息。
- 选型：服务端通知、进度、LLM 的 token 流这类场景，用 SSE 更简单；即时聊天、协同编辑、游戏、高频双向控制更适合 WebSocket。

#### 技术细节

**SSE 的格式与自带能力**

- 事件可以包含 `data`、`event`、`id`、`retry` 字段。
- 浏览器原生接口自带重连，并有 `Last-Event-ID` 相关语义。
- 但它承载的是 UTF-8 文本事件；要传二进制，得先编码或者改用其他通道。

**用了 SSE，应用仍要自己处理的**

- 事件是否可重放、代理缓冲、空闲超时、心跳、慢客户端。

**WebSocket 要自己设计的**

- 成功握手后以消息／帧双向传输，支持文本和二进制，也有 ping／pong 控制帧。
- 但重连、消息确认、鉴权刷新、背压、跨实例的连接路由，都得应用自己做。

**选型别只看“实时”**

- 还要看上行频率、载荷类型、客户端是浏览器还是非浏览器、反向代理是否支持、连接数和网关治理。

**一条共同边界**

- 两者都不会自动保证业务消息“恰好一次”。断线重连之后，要靠事件 ID、序列号和幂等处理来恢复。

#### 深挖追问

1. **LLM 流式输出为什么常用 SSE？**（补充练习）

   因为主数据方向就是服务端持续往客户端输出文本，客户端只需要另一个 HTTP 请求把输入提交上去。SSE 直接复用 HTTP 协议和现成基础设施，成本更低。

2. **SSE 中间断开了怎么办？**（面经实际出现；[[面经/字节/一面/0004#Q17：SSE 中间断开了怎么办？|MJ014 · 字节 · 一面 · Q17]]）

   先靠协议自带的恢复：

   - 浏览器 `EventSource` 会自动重连，间隔可以由服务端的 `retry` 字段控制，重连请求会带上 `Last-Event-ID` 头。
   - 服务端给每个事件发 id；可重放的场景就按 id 续推漏掉的事件。

   内容不可重放时（比如 LLM 流式文本）：按消息 ID 重新拉取已生成的部分再接续生成，或者整段重来，客户端按 id 去重保幂等。

   另外两件事要配：用心跳注释行防止代理因空闲断连；产出快于消费时，要定义好背压和断开策略。

3. **WebSocket 断开重连如何设计？**（面经实际出现；[[面经/帆软/一面/0001#Q09：WebSocket 断开重连如何设计？|MJ022 · 帆软 · 一面 · Q09]]）

   分几块讲：

   - 检测：用应用层心跳（ping／pong 加超时判定），因为 TCP 不会告诉你“对端假死”。
   - 重连：指数退避＋随机抖动＋上限，再结合页面可见性／网络恢复事件立即试一次。
   - 恢复：重新鉴权（token 可能已过期），带上最后消息序号或会话 ID 补拉断连期间的增量，客户端用有界队列暂存待发消息。
   - 去重：重复收发按序列号做幂等去重。
   - 收口：协议层重连成功不等于业务会话还在，会话恢复要应用自己设计。

4. **为什么 HTTP 只能请求-响应，WebSocket 能主动推送？**（面经实际出现；[[面经/点点互动/一面/0001#Q09：为什么 HTTP 只能请求-响应，WebSocket 能主动推送数据？|MJ064 · 点点互动 · 一面 · Q09]]。原素材未记回答，以下为参考）

   - 这是协议语义而非 TCP 限制：HTTP 把交互定义成「请求事务」，每个响应必须挂在一个请求上，事务结束连接就闲置；服务端没有「发一条无请求可回的消息」的报文类型。
   - 底层 TCP 从来是全双工的，所以 HTTP 的单向只是上层约定——轮询、长轮询都是在客户端侧「造请求」来近似推送。
   - WebSocket 握手升级为独立帧协议后，双方随时可发帧（文本／二进制／ping／pong），不再存在请求-响应绑定。
   - 补一句：能推送不等于可靠推送，消息确认与断线补偿仍要应用层设计。

### NET-017：TCP 拥塞控制和流量控制如何工作，有什么区别？

**常见问法**

- 介绍一下 TCP 的拥塞控制和流量控制。
- 上传数据时说的“网络问题”包括哪些？有哪些网络因素会影响吞吐？

#### 面试回答

先说两套控制各防谁：

- 流量控制防压垮接收方：接收方在每个 ACK 里通告接收窗口 rwnd，发送方的未确认在途数据不超过它。窗口缩到 0 之后，发送方周期性发零窗口探测，接收方有空位再发窗口更新。
- 拥塞控制防压垮网络本身：发送方维护拥塞窗口 cwnd，它是对“网络能承载多少在途数据”的估计。实际发送量受 min(rwnd, cwnd) 约束。

经典算法四段：

- 慢启动：cwnd 从初始的小窗口开始，随确认按指数增长，一直到阈值 ssthresh。
- 拥塞避免：之后改成加性增长。
- 快重传＋快恢复：收到三个重复 ACK 就快速重传，并把窗口减半后重建。
- 超时：RTO 超时则大幅收缩，重进慢启动。

一句话区别：rwnd 由接收端缓冲决定，保护的是对端；cwnd 由发送端根据丢包等网络信号自适应，保护的是网络。

#### 技术细节

**慢启动为什么是指数**

- 因为“每收到一个 ACK 就增一个 MSS”，一轮往返下来窗口就翻一倍，所以按往返轮次指数增长。
- 初始窗一般取约 10×MSS（RFC 6928）。

**AIMD 与阈值**

- AIMD（加性增、乘性减）让多条流公平地共享瓶颈。
- ssthresh 在丢包后按当前窗口减半。
- 快恢复下，cwnd 从新阈值起步而不是回到 1，避免不必要的全速重启。

**RTO 怎么来**

- 由 RTT 测量和方差估计得出（Jacobson／Karels 一类算法）。
- 超时判丢比重复 ACK 更严重，所以收缩也更狠。

**窗口本身的两个补充机制**

- 窗口缩放（RFC 7323）解决高带宽时延积下 16 位窗口字段不够用的问题。
- 零窗口期间的探测定时器，防止窗口更新报文丢失造成双方僵住。

**现代实现要区分**

- Linux 默认的 CUBIC 是基于丢包的；BBR 改用带宽×RTT 建模，主动测吞吐。
- 两者面对深缓冲或随机丢包时行为不同；回答经典算法时可以顺带点明这个实现差异。

**和上层的关系**

- SSE／LLM 这类流式场景，同样会受 cwnd 和 RTT 影响。
- 应用层的背压和 TCP 的流量控制是不同层的问题（可关联 [[专题题库/计算机网络#NET-006：TCP 如何保证可靠传输？|NET-006：TCP 如何保证可靠传输？]]）。

#### 深挖追问

1. **为什么慢启动指数增长、拥塞避免线性增长？**（补充练习）

   两个阶段目标不同：指数阶段要尽快逼近可用带宽，线性阶段是在饱和点附近做精细试探。再配上乘性减，多条流才会收敛到公平的份额。

2. **接收窗口很大还会拥塞吗？**（补充练习）

   会。rwnd 大只说明接收端装得下，中间链路或队列可能已经饱和；一旦丢包，cwnd 照样收缩。

3. **收到 ACK 就能删掉重传记录吗？**（补充练习）

   不能。TCP 的确认不等于业务完成，应用层的确认和幂等设计见 NET-006。

### NET-019：HTTP 有哪些请求方法，GET 和 POST 有什么区别？

**常见问法**

- HTTP 协议有哪些请求方法？讲一下 GET 和 POST 的区别。
- 哪一个请求的参数是放到请求体里的？
- PUT、POST、PATCH 有什么区别？
- HTTP 请求的传参方式有哪些？（报文结构视角见 NET-023）

#### 面试回答

标准方法有：GET、POST、PUT、PATCH、DELETE、HEAD、OPTIONS、TRACE。

GET 和 POST 的区别，按语义讲最稳：

- GET：读取资源，语义上安全且幂等，可以被缓存、被收藏，参数主要放在 URL 查询串里。
- POST：把数据提交给服务端处理，非幂等，默认不缓存，参数放在请求体里。
- 所以“哪个方法的参数放请求体”的答案是 POST；PUT、PATCH 这类带载荷的方法同样用请求体，由 Content-Type 描述编码。

其余常被说成“区别”的点，都要限定条件：

- URL 长度限制来自浏览器和服务器实现，而不是协议规定。
- GET 的查询串会进访问日志、浏览器历史和 Referer，因此不宜放敏感信息。
- “GET 比 POST 安全”“只有 POST 能传中文”都是误解：两者在 HTTP 下都是明文，加密要靠 TLS。

#### 技术细节

**方法名不约束报文结构**

- 方法名只是**语义约定**：GET 允许带请求体，但接收方普遍忽略或不支持（浏览器 fetch／XHR 不允许 GET 带 body，多数服务端框架不解析）；POST 也可以只用查询串。
- 把 POST 当“传输数据的唯一方式”是常见误区。正确说法是“需要传载荷的方法有 POST／PUT／PATCH，语义上 POST 最常用”。

**幂等与安全是对服务端的要求**

- 幂等与安全（safe）都是对服务端的**要求**，协议本身不强制。
- 写错的接口用 GET 改数据，爬虫和预取就会造成事故；反之 POST 也可以设计成幂等（带幂等键，见 [[专题题库/系统设计#SYS-013：接口幂等性如何设计，重复提交订单怎么处理？|SYS-013：接口幂等性如何设计，重复提交订单怎么处理？]]）。

**其他方法要点**

- HEAD：与 GET 相同但不返回响应体，用于探测与取头部。
- OPTIONS：用于查询支持的方法，也是 CORS 预检所用。
- PUT：语义是**整体替换**且幂等。PATCH：局部更新且不要求幂等。
- DELETE：幂等 —— 多次删除同一资源的结果状态一致，实现可以返回 404。
- 浏览器表单只能发 GET／POST，REST 风格里的 PUT／DELETE 通常由 fetch／axios 或方法覆盖（`_method`）发出。
- 缓存角度：GET 响应可按 Cache-Control 缓存，POST 响应默认不可重用。

#### 深挖追问

1. **GET 能不能带请求体？**（补充练习）

   协议层不禁止，但实践中不能依赖：浏览器主流 API 没有提供 GET 带 body 的方式，服务端框架也常直接忽略。要传载荷就用 POST，把数据放 body 或查询串。

2. **表单提交和 axios 发的请求有什么区别？**（补充练习）

   表单是浏览器原生行为，只支持 GET／POST，编码固定是 `application/x-www-form-urlencoded` 或 `multipart/form-data`。axios／fetch 可以用任意方法、自定义头、发 `application/json`；也正因为如此会触发 CORS 预检 —— 用了自定义头或不属于简单方法时，浏览器会先发一个 OPTIONS。

3. **为什么说 REST 里 DELETE 是幂等的？**（补充练习）

   幂等的定义是：同一请求执行一次与多次，对服务器状态的影响相同。重复删除同一资源后，该资源都处于“已删除”状态，所以满足。实现上第二次删除常返回 404 或 204，业务要保证的是这种“结果一致”，而不是产生新的副作用。

### NET-018：调用大模型 API 会经过哪些互联网协议？

**常见问法**

- 调用 LLM 的时候会涉及到哪些互联网协议？

#### 面试回答

按协议栈自底向上串一条真实链路：

- 解析：域名解析用 DNS，以 UDP 为主，也可以走 DoH／DoT。
- 传输：HTTP/1.1、HTTP/2 之下是 TCP；HTTP/3 之下是 QUIC over UDP。
- 加密：TLS 负责证书认证，并建立起对称加密通道。
- 应用：HTTPS＋REST／JSON；流式输出用 SSE（`text/event-stream`），双向高频场景可用 WebSocket，服务间调用常见 gRPC（跑在 HTTP/2 多路复用之上）。
- 企业网络出口：还有 HTTP CONNECT 代理与 VPN；再往外可能经过 CDN、负载均衡与 API 网关。

答题顺序按“解析→可靠传输→加密→应用协议→流式语义”展开，保证每一层都接得住追问。

#### 技术细节

**流式这一块最常被追问**

- SSE：HTTP 响应流上的文本事件协议，服务端单向推送，走普通 HTTP 栈，代理要禁用缓冲。
- WebSocket：握手之后升级成独立的全双工帧协议，不再受 HTTP 语义约束。
- gRPC：依赖 HTTP/2 的多路复用与二进制帧；要解决队头阻塞，得靠 HTTP/2 或 QUIC。

**TLS 这一块**

- 可以顺势衔接到证书链验证与中间人代理，见 [[专题题库/计算机网络#NET-002：HTTP 和 HTTPS 有什么区别，证书如何验证？|NET-002：HTTP 和 HTTPS 有什么区别，证书如何验证？]]。

**超时与重试是应用层语义**

- HTTP 超时是“结果未知”，不是失败；幂等键的设计见 [[专题题库/系统设计#SYS-018：HTTP 接口如何从业务层兜底请求丢失与重试？|SYS-018：HTTP 接口如何从业务层兜底请求丢失与重试？]]。

**工程实践可以提一句**

- 各家 SDK 的 keep-alive 连接复用，直接影响尾延迟。

1. **为什么大模型服务普遍用 SSE 而不是 WebSocket 输出 token？**（补充练习）

### NET-020：一台服务器理论上能建立多少 TCP 连接，真实限制是什么？

**常见问法**

- 假设一台服务器所有资源无限，理论上能同时建立多少个 TCP 连接？
- 单机能扛多少长连接，受什么限制？
- C10K／C100K 的瓶颈到底在哪？

#### 面试回答

先把“资源无限”这个前提拆开看：这题考的是能不能识别真实约束，而不是报一个天文数字。

理论上限那一层：

- 连接的身份是四元组（源 IP、源端口、目的 IP、目的端口），所以纯理论上限就是四元组的组合数。
- 固定一个本机 IP、一个对端 IP 与端口时，受本地可绑定端口数限制（IPv4 的端口是 16 位，去掉占用后大约 6 万多量级）。
- 多绑几个源 IP 或多目的端口就是线性倍乘；IPv4 地址全空间是 2^32，两端相乘看着是天文级。
- 但这些都不是工程约束，把答案停在这里就是没答到点上。

真实限制按“先到哪条”排：

- 文件描述符：每连接一个 fd，看进程级 `ulimit -n`／`RLIMIT_NOFILE` 和系统级 `fs.file-max`。
- 内存：每连接的发送／接收缓冲加连接控制块元数据，按 `tcp_rmem`／`tcp_wmem` 与是否启用了 `tcp_moderate` 一类自适应窗口而定。百万连接即使每连接几 KB，也要几十 GB。
- 本地端口耗尽：只发生在作为客户端主动出连接时（TIME_WAIT 占用端口）；服务端接受连接不消耗本地端口 —— 这个区分是高价值答案。
- 中间设备与内核的连接跟踪表，以及 epoll 等事件机制的容量与唤醒成本。
- 应用层自己那份：每连接的读写缓冲区、业务线程占用。

正确的收口：如果 fd、内存、内核表真的无限，上限就由四元组空间决定；实践中先到的是内存与 fd。所以要做的四件事是 —— 每连接瘦身（收敛默认缓冲、及时关闭空闲连接）、用边缘触发与批量处理降低唤醒开销、必要时靠多 IP／多进程分片、用连接数和内存指标做准入控制，而不是等 OOM。

#### 技术细节

**内存账要会估**

- 一条 TCP 连接的内核开销，至少包括两个 sk_buff 队列、收发缓冲和连接结构，最小是几百字节到数 KB。
- 若把 `SO_RCVBUF`／`SO_SNDBUF` 设成固定大值（例如各 4MB），一万连接就要几十 GB。
- 所以高并发接入层的第一课是不要把缓冲写死：用默认的自适应，或者按业务量来设定。
- 用户态还会再加一层：每连接的解析状态、TLS 会话（握手后的记录缓冲与证书链，成本更高）、业务对象和定时器 —— 这些常常比内核开销更大。

**单进程 fd 上限之外还有中断**

- 连接数上去后，每个包的唤醒成本和 CPU 缓存失效会被放大，这是中断与软中断的开销。
- 对策：RPS／RSS 多队列网卡分流、`epoll` 边缘触发批量收，以及降低空闲连接的定时器精度（用时间轮或分层哈希定时器）。

**真到百万级长连接时的常见做法**

- 分层：接入层只做转发与心跳，把状态收敛到少数后端。
- 或者用 eBPF／DPDK 绕开内核协议栈，代价是工程复杂度与可观测性损失。

**别把并发数和新建速率混成一件事**

- SYN 队列（`tcp_max_syn_backlog`）和 accept 队列（`somaxconn` 与 `listen` backlog 取小）限制的是每秒能建立多少新连接，跟并发连接数是两个指标。
- 长连接服务被“瞬时重连风暴”打挂，往往不是并发数超限，而是建立速率超了队列。
- 对症手段：客户端加抖动重连；服务端把 `accept4` 提前、把 backlog 调大。（与 NET-010 握手丢包恢复同源）

#### 深挖追问

1. **为什么服务端不会遇到本地端口耗尽，客户端会？**（补充练习）

   区别在谁选端口：

   - 服务端 accept 出来的连接，四元组里的“目的端口”就是它监听的端口，源端口由客户端决定，服务端不需要为自己选端口。
   - 客户端主动 connect 时，必须为每个连接占一个本地端口（同一四元组要唯一）。

   所以外呼型服务在 TIME_WAIT 未释放时会耗尽可用端口。解法是复用连接、扩源 IP，或启用 `tcp_tw_reuse`（仅对出连接有效，且依赖时间戳）。

2. **65535 个端口是不是意味着单机最多 6 万连接？**（补充练习）

   不是。这个说法混用了“本端端口数”和“连接数”：服务端接受连接不受本端端口限制，只受 fd／内存等约束，百万级并发连接完全可能。只有作为客户端、并且对端与本地 IP 都固定时，端口数才构成硬上限。

3. **怎么验证自己的服务能扛多少连接？**（补充练习）

   并发连接数和新建速率两条曲线要同时压。观察点：

   - fd 使用率；`ss -s`／`netstat` 的连接状态分布。
   - 内存与每连接缓冲的实际占用。
   - 软中断与 CPU 利用率。
   - accept 队列溢出计数（`netstat -s` 里的 overflow 指标）。

   结论要写成“在 X 内存与 Y CPS 下可稳定维持 N 连接”，而不是单说“扛了 10 万”。

### NET-021：WebSocket 和 Socket 分别属于哪一层，是什么关系？

**常见问法**

- WebSocket 和 Socket 分别属于哪一层的协议？WebSocket 是否包含 Socket 层？谈谈他俩的区别。
- Socket 是不是应用层协议？

#### 面试回答

结论：Socket 不是应用层协议，它是操作系统把传输层（TCP／UDP）暴露给应用的编程接口；WebSocket 是应用层协议，跑在 TCP 之上。

- 分层位置：TCP/IP 四层里，HTTP、WebSocket 在应用层；Socket 接口服务于传输层，本身不属于任何协议层。
- 关系不是「包含」而是「基于」：WebSocket 客户端先经 Socket API 建好 TCP 连接，再在这条连接上发 HTTP Upgrade 握手，之后改走自己的帧协议。
- 区别一句话：Socket 是抽象（一组 API：socket／connect／send／recv），WebSocket 是协议（定义了握手、帧格式、掩码、关闭流程）。

#### 技术细节

**分层对照**

| TCP/IP 四层 | 例子 |
| --- | --- |
| 应用层 | HTTP、DNS、WebSocket |
| 传输层 | TCP、UDP；Socket 接口把这一层暴露给应用 |
| 网际层 | IP |
| 链路层 | 以太网、Wi-Fi |

**WebSocket 复用 HTTP 只在握手这一步**

- 升级请求带 `Upgrade: websocket`、`Connection: Upgrade` 和 `Sec-WebSocket-Key`，服务端回 101 Switching Protocols。
- 握手完成后报文格式与 HTTP 再无关系：WebSocket 自己定义了帧（opcode 区分文本／二进制／ping／pong／关闭、FIN 位支持分片、客户端到服务端的数据帧必须掩码）。
- 掩码的目的：防止代理把连接里的字节误判成 HTTP／缓存投毒（RFC 6455 §5.3／§10.3）。

**为什么要有 WebSocket 这层协议**

- 裸 TCP 是字节流，没有消息边界；每条 WebSocket 消息是完整的一帧或一组分片帧。
- 还要鉴权 Origin（防跨域劫持）、心跳（ping／pong）、状态码关闭握手，这些裸 Socket 都得自己造。

**容易混的两点**

- 名字像不等于同层：Socket 与 WebSocket 的关系，类似「文件描述符」和「某种文件格式」。
- WebSocket 只定义了 over TCP；把「双向实时通道」搬到 QUIC 上是另一套独立机制（WebTransport，IETF 草案阶段），别说成 WebSocket 也依赖 UDP。

#### 深挖追问

1. **为什么不直接用 Socket 写实时通信，还要定义一个 WebSocket？**（补充练习）

   裸 TCP 没有消息边界、Origin 鉴权和浏览器生态的标准化接口，都得自己造；WebSocket 把这些收进协议。

2. **WebSocket 握手失败会怎样？**（补充练习）

   服务端不支持升级时按 HTTP 返回错误（如 400／426），连接就还是一条普通 HTTP 会话，客户端要按普通错误处理。

3. **WebSocket 和 HTTP／Socket 各属于哪一层？**（面经实际出现；[[面经/点点互动/一面/0001#Q08：WebSocket 和 Socket 分别属于哪一层的协议，两者是什么关系、有什么区别？|MJ064 · 点点互动 · 一面 · Q08]]。原素材未记回答，以下为参考）

   HTTP 与 WebSocket 都是应用层协议；Socket 是传输层之上的编程接口，不分层。见 [[#NET-013：OSI 七层与 TCP/IP 四层如何映射？|NET-013：OSI 七层与 TCP/IP 四层如何映射？]]。

### NET-022：WebSocket 的底层原理是什么？连接是怎么建立的？

**常见问法**

- [[面经/收钱吧/二面/0001#Q05：WebSocket 的底层原理与连接建立过程|MJ069 · 收钱吧 · 二面 · Q05]]
- WebSocket 握手具体交换了什么？为什么要带一个 Key？
- WebSocket 是怎样的一个协议？建立连接的过程采用的是什么协议？

#### 面试回答

结论：WebSocket 是跑在 TCP 上的应用层消息协议；连接用一次 HTTP Upgrade 握手建立，之后同一条连接改跑 WS 帧，脱离 HTTP 语义。

- 握手：客户端在 HTTP GET 里带 `Upgrade: websocket`、`Connection: Upgrade`、`Sec-WebSocket-Version: 13` 和随机 `Sec-WebSocket-Key`（Base64 的 16 字节）。
- 应答：服务端接受后回 `101 Switching Protocols`＋`Sec-WebSocket-Accept`——把 Key 拼上固定 GUID 做 SHA-1 再 Base64；101 即握手成功。
- 帧通信：opcode 区分文本／二进制／ping／pong／close 帧；客户端→服务端的帧必须掩码（防中间设备误解析与缓存投毒），服务端下行不掩码；大消息用分片帧续传。
- 保活与关闭：ping／pong 心跳探活（Nginx 等中间层默认 60 秒空闲会掐连接）；关闭走 close 帧四次挥手式收尾。

#### 技术细节

**Key／Accept 校验防什么**

- 不是为了加密——是防止一个不会说 WS 的端点（普通 HTTP 客户端、缓存代理）误升级为持久连接；握手响应证明服务端确实理解本次升级。

**为什么要复用 HTTP 起步**

- 借 80／443 端口与既有代理、鉴权（Cookie／Header 直接带上）设施穿透网络；握手完成后这条 TCP 就是纯 WS 通道。

**帧层要自己面对的工程问题**

- 半开连接：拔网线不发 close 帧，对端只能靠心跳超时发现——服务端要有 idle 判定与客户端重连策略。
- 背压与重连：库的发送缓冲会堆积，慢客户端要主动断；重连后按“已应用版本”补拉增量（协同场景见 SYS-030 口径）。
- 鉴权时效：JWT 过期要能在连接内刷新凭证；跨实例路由要粘性会话或网关广播（“选哪条通道”见 NET-016）。

**容易说错的三点**

- “WebSocket 是四层协议”：它是应用层消息协议，四层是 TCP。
- 握手“是 HTTP API 调用”：只是借 HTTP 报文格式完成协议升级，101 之后没有请求／响应语义。
- “有了 WS 就不用心跳”：中间层闲置超时与半开检测都要求应用层 ping／pong。

#### 深挖追问

1. **WSS 和 HTTPS 的证书验证是一回事吗？**（补充练习）

   TLS 层完全同 HTTPS（证书链校验、SNI）；WSS＝WS over TLS，握手加密发生在 Upgrade 之前。

2. **为什么客户端帧要掩码而服务端不用？**（补充练习）

   掩码（RFC 6455）针对“客户端可控流量进入代理栈”的历史问题（与 HTTP 消息走私同源）；服务端下行帧本就受控，不必付这个开销。

### NET-023：HTTP 请求报文由哪几部分组成，传参方式有哪些？

**常见问法**

- HTTP 的请求信息（请求报文）里面有哪些内容？请求行里面有哪些具体的内容？
- HTTP 请求过程中的传参方式是怎样的？

#### 面试回答

结论：请求报文四部分——请求行、请求头部、空行、请求体；请求行含方法、请求目标（URI）、HTTP 版本三项，空格分隔。

- 例：`POST /user/login HTTP/1.1`——方法／目标／版本各一物，缺一不可。
- 请求头每行“名字: 值”（Host、Content-Type、Content-Length、Cookie…）；空行是头部与正文的强制分界。
- 传参四个位置：URL 查询串（?k=v&k2=v2）、URL 路径段（/user/{id}）、请求头、请求体（form／JSON／multipart 文件）。
- GET 走查询串受 URL 长度与缓存日志约束；POST 走请求体容量宽松——方法与参数位置是两回事，别答成“GET 不能传 body”。

#### 技术细节

**报文结构的准确口径（HTTP/1.1）**

- 请求行也叫起始行（start line）；版本写法必须是 `HTTP/x.y`，冒号空格是分隔符。
- 头部不分“大小写敏感”：字段名不区分大小写，但约定首字母大写；同名多值可逗号合并或重复行。
- 空行不能省：没有正文的请求也保留到空行为止；正文是否有、有多长由 `Content-Length`／`Transfer-Encoding: chunked` 决定，不靠连接关闭。
- 响应报文同构：把“请求行”换成“状态行”（版本、状态码、原因短语）。

**传参方式与编码约束**

- 查询串：`application/x-www-form-urlencoded` 的百分号编码规则同样适用；中文、`&`／`=`／空格必须转义，否则参数被截断——现场常被追问“为什么参数少了”。
- 数组与嵌套对象无标准协议级表示，重复 key（`tag=a&tag=b`）、逗号分隔或 JSON-in-query 都是前后端约定。
- 路径参数（RESTful）走 URL 模板；请求头传参（`Authorization`、`X-Request-Id`）适合横切信息，不适合业务主参数。
- 请求体形态看 `Content-Type`：表单 urlencoded、`multipart/form-data`（文件上传）、`application/json`（现代 API 主流）；服务端按声明解析，声明与实际不符直接 4xx。

**安全与可见性差异（追问的高频落点）**

- 查询串会出现在浏览器历史、服务端与 CDN 访问日志、Referer 里——令牌与敏感数据放 header 或 body。
- URL 总长：协议无硬性规定，实践中浏览器／服务器普遍在 2K～8K 截断（Tomcat `maxHttpHeaderSize` 等参数可配），所以查询串“按会超限设计”。
- 幂等与安全语义（GET 可缓存可收藏、POST 不可）见 NET-019，本报文结构题不展开。

#### 深挖追问

1. **请求头里为什么必须有 Host？**（补充练习）

   HTTP/1.0 一台 IP 只对应一台虚拟主机；1.1 起多域名共享同一 IP＋端口，`Host` 告诉服务器要访问哪个站点，虚拟主机路由、证书选择都靠它。缺 Host 的 1.1 请求服务器可回 400。

2. **GET 和 POST 在报文上的真实区别？**（面经实际出现；与 [[面经/字节/一面/0010#Q16：HTTP 请求中 GET 和 POST 方法的区别是什么？|MJ042 · 字节 · 一面 · Q16]] 同一考察带的报文视角；语义与规范口径见 NET-019）

   报文层面只差两点：方法名不同；参数位置约定不同（GET 在请求行 URL，POST 通常在 body）。所谓“GET 比 POST 安全／POST 能传更多”都是推论不是协议规定——HTTPS 加密后才谈传输安全，GET 也能带 body（但没人实现可靠），展开见 NET-019。

3. **上传一个文件，报文长什么样？**（补充练习）

   `POST` ＋ `Content-Type: multipart/form-data; boundary=…`；body 按 boundary 分节，文件部分自带子头部（文件名、真实 MIME）与二进制内容；`Content-Length` 是整包长度。大文件另走分片上传协议，见 SYS-007。
