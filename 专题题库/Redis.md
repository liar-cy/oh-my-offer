#### 面试回答

五种常见类型，先说用途：

- String：简单缓存或计数。
- Hash：存对象的字段。
- List：列表。
- Set：去重集合。
- Sorted Set：排行榜。

另外还有四类能力：Bitmap 做签到、HyperLogLog 做近似去重计数、GEO 做地理位置、Stream 做消息流。选型时看操作方式、精度、数据量和可靠性需求，不只看名称。

底层编码（以 Redis 7.2 为版本基线）：

- String：`int` 保存可表示的整数；`embstr` 与 `raw` 使用不同的对象和字符串内存布局。
- Hash：小对象可用 `listpack`，超过条件转哈希表。
- List：用 `quicklist`，它的紧凑节点使用 `listpack`。
- Set：可用 `intset`、`listpack` 或哈希表。
- ZSet：可用 `listpack`，或跳表加字典，兼顾排序范围和成员定位。
- Bitmap 建立在字符串上，GEO 基于 ZSet，HyperLogLog 是概率计数表示，Stream 的条目用 radix tree（基数树）与 listpack 组织。别把它们都记成独立容器类型。

后续版本的 List 等编码已有差异，要用 `OBJECT ENCODING` 和部署版本核对，不固定背阈值。

#### 技术细节

**秒杀扣库存怎么落**

- 单个券批次的计数通常用 String。
- 校验和扣减放在一次 Lua 执行里：先确认库存存在、数量合法、余额足够，再扣减。
- 多个字段要联合更新时，也可以用 Hash。
- 单条 `DECR` 是原子的，但它允许扣成负数，不能代替“判断＋扣减”的原子条件逻辑。

**脚本原子性的边界**

- 原子执行不意味着自动回滚：脚本出错前已经完成的写入不会撤销，所以要先校验再修改。
- 脚本也不提供跨 Redis 与数据库的原子事务。
- 前提是支持 EVAL 的 Redis 2.6+；集群里多键脚本还要遵守同槽约束，具体实现结合部署版本。

**对外类型与内部编码要分开看**

- Hash 不一定始终由普通哈希表实现，编码会受版本、大小和配置影响。

**几条容易说过头的边界**

- List 的简单队列操作，不自动提供业务确认与重试。
- Stream 消费组也要处理 pending、确认和重复消费。
- Sorted Set 按分数排序，同分成员的顺序要自己处理。
- HyperLogLog 是近似基数统计，不能枚举成员。
- Bitmap 适合较稠密的整数 ID，极大稀疏 ID 可能浪费空间。
- 新增概率数据结构能不能用，还要检查部署版本。

#### 深挖追问

1. **排行榜为什么选 ZSet？**（补充练习）

   它支持按分数更新、排名和范围读取，但仍要定义同分排序、时间窗口及大键规模。

2. **缓存对象用 String 还是 Hash？**（补充练习）

   整体读取可序列化为 String，字段级更新可考虑 Hash，结合访问模式、过期需求及内存测量选择。

3. **秒杀扣库存最适合哪种数据类型？**（面经实际出现；[[面经/百度/一面/0002#Q06：Redis 常见数据类型有哪些，秒杀扣库存选哪一种？|MJ005 · 百度 · 一面 · Q06]]）

   单批次计数通常选 String，配合原子条件扣减；类型本身不保证幂等或跨组件一致性，参见 [[专题题库/系统设计#SYS-004：Redis 预占与 MySQL 异步扣库存如何实现最终一致？|库存一致性]]。

4. **类型和底层编码是一一对应吗？**（面经实际出现；[[面经/百度/一面/0005#Q16：Redis 有哪些数据类型，底层如何实现？|MJ008 · 百度 · 一面 · Q16]]）

   不是，编码会按值、元素数量、大小阈值及版本选择或转换；对外命令语义相对稳定。

5. **用 Redis 设计一个统计次数的功能，怎么选结构？**（面经实际出现；[[面经/字节/一面/0007#Q10：用 Redis 设计一个功能统计次数。|MJ026 · 字节 · 一面 · Q10]]）

   先问口径再选结构，不同口径对应不同做法：

   - 精确计数：`INCRBY`＋按维度拼 key＋TTL／定期落库归档。
   - 精确去重计数：Set，内存随基数线性涨，量大要评估。
   - 近似 UV：HyperLogLog，固定约 12KB、标准误差约 0.81%，适合“量级监控够用”的大基数。
   - 连续状态（签到）：Bitmap 位运算。
   - 多维分析：实时层留 Redis，明细异步进数仓。

   Set 与 HLL 之间怎么选，决定因素是误差与容量。

6. **Redis 为什么快？**（面经实际出现；[[面经/帆软/一面/0002#Q08：Redis 为什么快，有哪些数据结构，String 用的什么结构？|MJ027 · 帆软 · 一面 · Q08]]）

   四层原因：

   - 纯内存操作。
   - 命令在单线程模型内顺序执行，没有锁竞争、没有线程上下文切换；网络 IO 由 epoll（事件驱动的多路复用）承担，6.0 之后读写与响应可以多线程，但命令执行仍是单线程。
   - 数据结构针对场景高度优化，还会按规模自动切换编码。
   - 协议简单，加上 pipeline 摊薄网络往返。

   别把“单线程”说成全部：持久化、过期删除等仍有额外线程／子进程参与。线程模型与 IO 多路复用的完整流程见 [[#REDIS-012：Redis 的网络层和命令执行是同一个线程吗？IO 多路复用的原理是什么？|REDIS-012：Redis 的网络层和命令执行是同一个线程吗？]]。

7. **Redis 和 MySQL 有什么区别，为什么不能拿 Redis 当主存？**（面经实际出现；[[面经/点点互动/一面/0001#Q15：Redis 和 MySQL 的区别是什么？|MJ064 · 点点互动 · 一面 · Q15]]。原素材未记回答，以下为参考）

   - 介质：MySQL 数据在磁盘（Buffer Pool 缓存热页），Redis 以内存为主、落盘只用于重启恢复。
   - 模型：MySQL 是关系模型＋SQL＋行级事务（ACID、可回滚）；Redis 是键值与结构化命令，MULTI／Lua 只是打包执行，没有回滚。
   - 性能与容量：Redis 微秒级、十万级 QPS，容量受内存上限约束；MySQL 毫秒级、单表上千万行仍可行，容量看磁盘。
   - 可靠性：Redis 的 RDB／AOF 有窗口丢数据（异步落盘），恢复能力弱于 MySQL 的 redo＋binlog；所以 MySQL 当真相源，Redis 当加速层。
   - 一致性问题走缓存一致性方案，见 [[专题题库/系统设计#SYS-009：多级缓存如何保持一致，并在 Redis 故障时降级？|SYS-009：多级缓存一致性与降级]]。

8. **MySQL、Redis、本地缓存分别什么时候用？**（面经实际出现；[[面经/京东TET/二面/0001#Q10：MySQL、Redis、本地缓存的使用场景；三者结合一致性有损失，怎么保证？|MJ089 · 京东 TET · 二面 · Q10]]）

   按“可靠性／共享性／延迟”三个维度分工，不是三选一：

   - MySQL：事实源。要事务、要复杂查询、要不能丢的数据放这里；容量换可靠性，读放大靠索引与分片解决。
   - Redis：跨实例共享的加速层。热点读、计数器、排行榜、分布式锁、会话（Spring Session）这类需要多机一致视图＋数据结构的场景；持久化是兜底不是账本。
   - 本地缓存（Caffeine）：进程内层。零网络、纳秒级读、只被本进程看见，适合极热且小的只读数据、字典配置、渲染中间结果；各实例一份，天然引入陈旧窗口。
   - 组合判断：能不能容忍有界陈旧？能不能接受各实例不一致？这两个问题决定要不要本地层；数据量与访问均匀度决定本地层收益大小（见 SYS-009）。
   - 补一句边界：Redis 不是用来“少写 MySQL”的万能挡板，写入密集的链路加 Redis 往往只增加不一致面。

### REDIS-002：缓存穿透是什么，布隆过滤器能完全解决吗？

#### 面试回答

三个问题分开说，别混：

- 穿透：请求的是不存在的数据，每次都绕过缓存打到数据库。招是参数校验、短期空值缓存、布隆过滤器、限流。
- 击穿：某个热点 key 一失效，大量请求同时回源。招是互斥重建、请求合并、提前刷新，业务允许时先返回旧值、异步更新。
- 雪崩：大量 key 集中过期，或者缓存服务整体不可用，造成大范围回源。招是打散 TTL、提升缓存可用性，再用限流、熔断降级和回源并发限制保护数据库。

最后一句要补上：布隆过滤器有假阳性，不能“完全”解决穿透；数据更新时还得同步过滤器和空值缓存。

#### 技术细节

**布隆过滤器：不会漏判，但会误判**

- 在正确插入、且状态没被破坏的前提下，标准布隆过滤器没有假阴性：说不存在的就一定不存在。
- 反过来不成立：说存在的可能是假阳性，系统漏同步新增 key 时，还会把真实数据误拒掉。

**误判率由什么决定**

- 三个量：位数组大小 m、哈希次数 k、插入量 n。
- 近似公式是 `(1-exp(-kn/m))^k`。

**删除是它的短板**

- 普通布隆过滤器不支持直接安全删除。
- 真有删除需求，要用别的结构或者靠重建策略。

**空值缓存的一条边界**

- 要区分“不存在”与“数据库异常”，查询异常不能被长期当成不存在。
- 新增数据后，既要更新过滤器，也要处理掉之前缓存的空值。

**击穿和雪崩不是一回事**

- 击穿是单个热点 key 失效；雪崩是大量 key 或缓存服务同时失效。

**各方案的适用边界**

- 互斥重建要约束等待时间，并处理重建失败；单机锁在多实例部署下只能合并各自进程内的请求。
- 逻辑过期是拿“接受短暂旧值”换可用性，不能用在任意强一致场景。
- TTL 抖动只能缓解集中过期，解决不了 Redis 整体故障；主从或集群也不替代回源限流。

#### 深挖追问

1. **布隆判断存在，数据库却没有怎么办？**（面经实际出现；[[面经/百度/一面/0001#Q07：什么是缓存穿透，如何解决，布隆过滤器能完全解决吗？|MJ002 Q07]]）

   按正常未命中路径查询，必要时缓存空值并限流，这是允许的假阳性。

2. **数据新增了但过滤器没更新怎么办？**（补充练习）

   设计更新顺序和补偿机制，避免直接把未同步导致的否定结果当永久事实。

3. **三种缓存问题分别怎么解决？**（面经实际出现；[[面经/百度/一面/0003#Q12：缓存穿透、击穿和雪崩有什么区别，如何解决？|MJ006 · 百度 · 一面 · Q12]]）

   按各自的成因分开处理：

   - 穿透（查不存在的数据）：参数校验、空值缓存、布隆过滤。
   - 击穿（热点失效）：合并重建，业务允许时适当返回旧值。
   - 雪崩（大范围失效）：打散过期时间、提升缓存可用性，并控制回源。

4. **击穿为什么用逻辑过期而不用互斥锁？**（面经实际出现；[[面经/百度/二面/0003#Q07：为什么使用逻辑过期方案，而不用互斥锁？|MJ020 · 百度 · 二面 · Q07]]）

   图的是延迟平稳，代价是明确容忍一段旧数据。

   - 互斥锁：重建期间其他请求全部阻塞，DB 慢或重建失败时线程堆积、出现延迟尖刺，还要额外处理锁失效。
   - 逻辑过期：所有请求先拿旧值，由抢到重建权的那个异步任务去刷新，时延平稳。
   - 适用条件：读多且可以短暂陈旧的热点（商品详情）适合逻辑过期；余额、库存这类不能读旧值的数据必须互斥重建或直接读权威源。

5. **项目里真的遇到过缓存穿透吗？**（面经实际出现；[[面经/美团/一面/0002#Q05：Redis 使用过程中遇到过缓存穿透吗？出现不一致的情况吗？|MJ032 · 美团 · 一面 · Q05]]）

   本地部署、流量可控时不会自然发生，但**用不存在的 ID 压测就能复现**：拿随机大 ID 打接口，缓存永不命中，DB 的 QPS 与 RT 会同步抬起来。

   答这题的正确姿势是“自然流量没遇到＋我主动构造复现过＋当时怎么挡”，挡法是三层：

   - 参数校验先挡掉非法 ID。
   - 空值缓存覆盖小范围的不存在数据：用短 TTL，并且区分“不存在”与“查询异常”。
   - 布隆过滤器留给大基数场景，同时说明假阳性和新增数据要同步的问题。

   只答“没遇到过”，等于放弃这题的展示机会。

6. **除了随机化 TTL，还有什么补充方案解决缓存雪崩？**（面经实际出现；[[面经/帆软/二面/0002#Q04：什么是缓存雪崩，怎么解决？除随机化 TTL 还有什么补充方案？|MJ035 · 帆软 · 二面 · Q04]]）

   先说结论：TTL 打散只覆盖“集中过期”这一种成因，服务不可用型雪崩要靠“可用性＋限流降级”的组合拳。按层给方案：

   - 缓存层：做高可用，哨兵／集群加副本；再加本地缓存 Caffeine 兜住热点，这样 Redis 整体故障时还有第一道防线。
   - 回源层：做限流，互斥重建、请求合并，用信号量控制在途回源并发，让请求在 DB 前面排队。
   - 业务层：做降级，返回适当旧值、静态兜底、熔断。
   - 运营层：做预热，重启或大促前主动装填；对热点 key 用“永不过期＋后台异步刷新”这种主动模式。

### REDIS-003：Redis 有哪些持久化方式，RDB 和 AOF 有什么区别？

**常见问法**

- [[面经/美团/一面/0002#Q24：Redis 数据持久化，两种方式各自介绍|MJ032 · 美团 · 一面 · Q24]]
- Redis 有哪些持久化方式，RDB 和 AOF 有什么区别？

- 混合持久化机制是如何工作的？
- Redis 两种持久化方式的区别以及对应的优缺点？
- 持久化过程的 SAVE 和 BGSAVE 有什么区别？为什么 BGSAVE 要 fork 子进程执行？

#### 面试回答

两种持久化各有取舍：

- RDB：保存某一时刻的数据快照。文件通常紧凑，适合备份和快速加载；代价是故障时可能丢掉最近一次快照之后的写入。
- AOF：记录写操作，恢复时靠回放。持久性由 fsync（把缓冲区数据同步落盘）策略决定；文件通常更大，还需要重写。
- 两者可以同时开，也有“RDB 基础数据＋AOF 增量”的混合形式。

选型时说清三个衡量维度：能接受多少数据丢失、恢复要多久、运行时有多大开销。

#### 技术细节

**RDB 快照怎么生成**

- `SAVE` 是阻塞式的，主线程直接做快照。
- `BGSAVE` 通常 fork 出子进程，靠写时复制生成快照。
- 别忽略代价：fork 本身和写时复制仍可能带来停顿和内存压力。

**AOF 的三档 fsync 策略**

- `always`：每追加一批命令就同步一次。
- `everysec`：通常每秒同步一次，故障时可能丢掉约一秒的写入。
- `no`：交给操作系统决定什么时候刷盘。
- 具体能做到什么持久性，还受配置和底层存储影响。

**AOF 重写不是翻历史**

- 重写是依据“当前数据”重新生成一份紧凑表示，不是把全部历史日志复制一遍。

**版本差异与恢复优先级**

- Redis 7.0 起采用多部分 AOF，用 base 文件、增量文件和 manifest（清单）一起管理。
- 同时开启 RDB 与 AOF 时，重启优先用 AOF 恢复。

#### 深挖追问

1. **RDB 和 AOF 的主要取舍是什么？**（面经实际出现；[[面经/百度/一面/0003#Q13：Redis 有哪些持久化方式，RDB 和 AOF 有什么区别？|MJ006 · 百度 · 一面 · Q13]]）

   RDB 偏向紧凑快照和恢复效率，AOF 可用更频繁同步缩小丢失窗口，但有写入、空间及重写成本；两者都需要考虑实际磁盘和备份策略。

2. **混合持久化机制是如何工作的？**（面经实际出现；[[面经/帆软/二面/0002#Q01：Redis 的 RDB 和 AOF 有什么区别，混合持久化如何工作？|MJ035 · 帆软 · 二面 · Q01]]）

   开启 `aof-use-rdb-preamble` 之后，混合形式就出现在 AOF 重写那一刻：

   - 重写开始时，先把当前全量数据以 RDB 二进制格式写进新 AOF 文件的头部，当作 base。
   - 重写期间产生的增量命令，再以命令格式追加在文件尾部。
   - 重启恢复时，先载入头部的 RDB base，再回放尾部的少量增量命令。

   收益是两头都拿到：文件更小；恢复走 RDB 的快速载入再补少量命令；同时保留 AOF 那个较小的丢失窗口。7.0 起多部分 AOF 把 base／增量／manifest 拆成文件管理，混合形态就成了默认机制的一部分。

### REDIS-004：Redis 如何实现固定窗口、滑动窗口、令牌桶与漏桶限流？

**常见问法**

- Redis 有哪些限流算法，如何实现？

- 限流部分怎么实现的，为什么要用 AOP 和注解？
- 流量控制怎么做的？
- 常见的限流算法有哪些？滑动窗口相对固定窗口为什么要滑动，主要解决什么问题？

#### 面试回答

几个算法各说一句，再补一句 Redis 实现的共同要求：

- 固定窗口：用一个计数器统计窗口内的请求。实现最简单，但窗口交界处会突发。
- 滑动日志：记录最近一段时间里的每个请求。更精确，代价是占更多内存。
- 滑动窗口计数：把时间切成分桶来近似，精度和开销折中。
- 令牌桶：按固定速率往桶里放令牌，允许桶容量范围内的突发。
- 漏桶：以稳定速率处理请求，超过桶容量就排队或拒绝。

落到 Redis 上，读取、判断、更新这三步必须做成一个原子操作，否则并发请求会一起通过。

#### 技术细节

**固定窗口怎么写**

- key 里带上时间窗标识，在一个 Lua 脚本里做 `INCR`，并在首次计数时设置过期。
- 不要把 `INCR` 和 `EXPIRE` 拆成两次调用：中间失败就会留下一个永不过期的计数 key。

**滑动日志怎么写**

- 用 ZSET：时间戳当 score，每个请求一个唯一标识。
- 一个脚本内按顺序完成四步：清掉窗口外的记录、统计数量、判断是否超限、把本次请求加进去。

**令牌桶怎么存状态**

- 保存两个值：剩余令牌数、上次补充时间。
- 每次按 `elapsed × rate` 补充并封顶，令牌足够才扣减。

**漏桶容易讲漏的一点**

- 想真正平滑下游流量，除了计数判断，还得有队列和按速率执行的消费者。
- 只做计数判断，并不会自动平滑下游。

**三个要提前定的东西与一条边界**

- 要确定限流维度（用户／接口等）、时间来源，以及 Redis 故障时的策略。
- Lua 原子执行不等于故障切换后配额绝不丢失。
- Redis Cluster 里，脚本涉及到的多个 key 应该落在同一个槽。

#### 深挖追问

1. **为什么单条 INCR 原子还不够？**（补充练习）

   判断额度、扣减及设置过期是组合逻辑，拆开会产生竞态或残留状态，需要一起执行。

2. **为什么要用 AOP 和注解实现限流，有哪些作用？**（面经实际出现；[[面经/京东健康/一面/0001#Q10：限流部分怎么实现的，为什么要用 AOP 和注解，有哪些作用？|MJ018 · 京东健康 · 一面 · Q10]]）

   因为限流是横切关注点，不该写进业务方法里。分工是：

   - 注解声明规则：接口标识、阈值、窗口、降级行为。
   - 切面在方法执行前统一取参、调用限流器，超限就抛异常交给全局处理。

   这样做的收益：业务代码无侵入、规则集中可配置、新接口加个注解就能接入。

   代价与边界也要说清：

   - 依赖代理机制，自调用不走切面，会直接失效。
   - 注解的值是静态的，动态规则需要再接配置中心。
   - 切面本身要保持轻量；限流判断失败时是放行还是拒绝，策略得先定下来。

### REDIS-005：Redis 的过期删除与内存淘汰策略有什么区别？

**常见问法**

- Redis 的过期淘汰策略是什么？
- Redis 如何删除过期 key，内存满了又如何处理？
- Redis 有哪些常用的淘汰算法？
- 谈谈 Redis 的 LRU 底层实现。
- Redis 的过期删除策略是什么？

#### 面试回答

这是两套机制，先分开说：

- 过期删除管“已经到期的数据”：key 超过 TTL 后，访问时惰性删除，另外还有周期性的抽样主动过期。
- 内存淘汰管“内存不够用”：数据集达到 `maxmemory` 后，按 `maxmemory-policy` 挑 key 删掉腾空间。
- 淘汰策略的几类选项：不淘汰、面向所有 key 的 LRU／LFU／随机、只面向带 TTL 的 key 的对应策略，以及优先淘汰剩余 TTL 较短的 key。

一句话记法：前者是“到期了怎么清”，后者是“没到期但内存满了踢谁”。

#### 技术细节

**两种删除各自的职责**

- 惰性删除保证：访问到期的 key 时一定不会返回旧值。
- 但那些“永不再被访问”的过期 key，还是得靠主动周期清理才会释放内存。
- 主动过期是抽样扫描，并根据结果自适应地继续扫，在延迟和清理速度之间取舍 —— 它不是在到期瞬间遍历全部 key。

**一条时钟边界**

- TTL 是以绝对时间的形式持久化的，所以系统时钟异常会直接影响过期判断。

**淘汰策略怎么分**

- 统一由 `maxmemory-policy` 配置。
- `noeviction`：不淘汰，在需要写入新数据时直接返回错误。
- `allkeys-lru`、`allkeys-lfu`、`allkeys-random`：面向全部 key。
- 对应的 `volatile-*`：只从设置了 TTL 的 key 里挑；另有 `volatile-ttl`，按剩余 TTL 长短选。
- 当前官方文档还列出 LRM（least recently modified，最近最少修改）策略，部署是否支持要按具体版本确认。

**一个容易说错的实现细节**

- LRU 与 LFU 都是用近似采样实现的，别描述成“维护了所有 key 的精确全局链表”。

**选型建议**

- 纯缓存场景：常评估 `allkeys-lru` 或 `allkeys-lfu`。
- 混存了不可淘汰的状态：先做数据隔离和容量设计，不能只靠 `volatile-*` 兜底。

#### 深挖追问

1. **key 到期后是否一定立即释放内存？**（补充练习）

   不一定在到期时刻同步删除；访问时会惰性处理，后台主动过期也会逐步清理。业务读取不会把已过期 key 当有效值返回。

2. **设置了 TTL 就一定不会触发内存淘汰吗？**（补充练习）

   不是。TTL 负责生命周期，达到 `maxmemory` 时仍可能按配置淘汰尚未到期的 key。

### REDIS-006：Redis 分布式锁如何正确加锁、解锁和续期？

**常见问法**

- Redis 分布式锁怎么实现？
- 删除锁为什么校验值并使用 Lua？
- 锁过期但业务未完成怎么办？

- SETNX 的 value 可以随便传吗，有什么要求？

- 分布式场景下锁的死锁、锁超时释放怎么处理？
- SET NX EX 为什么要原子执行？
- Redis 做分布式锁用什么命令？PX 和 EX 的区别？
- 锁过期了会怎样，如何避免锁过期带来的问题？
- 集群里存锁的节点挂掉，如何避免锁丢失？
- 如何利用 Redis 去设计分布式锁？需要注意哪些地方？
- 抢到锁的服务线程挂了，一直不释放怎么办？
- 多人协作场景具体怎么加锁？用 Redis 还是其它？锁什么、粒度怎样？

#### 面试回答

单实例的基础实现，说清三件事：

- 加锁：`SET key token NX PX ttl` 一条命令原子地做完“互斥获取＋设置过期”。token 对每次加锁都要唯一。
- 解锁：先确认当前值还是自己的 token，再删。否则会出现旧持有者误删“超时后被别人新拿到”的锁。
- 怎么保证“比较＋删除”原子：Redis 8.4 之前通常写 Lua 脚本；8.4 起可以直接用官方提供的条件删除能力。

最后补一句 TTL 的口径：它应该覆盖常见执行时间并留余量，但锁只是一份有时限的租约，不是业务进程活着就一直有效。

#### 技术细节

**为什么不能先 `GET` 再 `DEL`**

- 这是两条命令，中间那段时间锁可能已经过期并被别人拿走。
- 所以“比较 token ＋删除”必须在 Redis 内原子完成。

**续期怎么做，边界在哪**

- 业务时长不可预测时，可以由看门狗续期：先确认 token 匹配，再延长过期时间。
- 续期要有约束：限制续期次数，并且记录失败。
- 别以为续了就安全：长时间 GC 暂停、进程失联或网络分区，仍可能让旧持有者在失锁之后继续操作。

**失锁后怎么拦住旧持有者**

- 对数据库这类关键资源，用单调递增的 fencing token 或资源版本号，由资源侧拒绝旧持有者。
- 不加这一层，即使锁服务已经判断出有新持有者，也阻止不了旧进程提交。

**这套方案的保证范围**

- Redis 官方说明：单实例方案在部分故障下保证有限；多实例 Redlock 同样有时钟和故障模型的前提。
- 要求严格一致时，要先明确可接受的故障语义，再评估具备一致性协议和 fencing 能力的协调服务。
- 不管选哪种：都要设置获取超时、用随机退避，并让被保护的操作自身尽量幂等。

#### 深挖追问

1. **为什么删除锁要校验值？**（面经实际出现；[[面经/字节/一面/0001#Q17：Redis 分布式锁如何实现，过期与解锁有哪些风险？|MJ011 · 字节 · 一面 · Q17]]）

   防止客户端在自己的锁已过期后误删另一客户端重新获得的锁。

2. **为什么用 Lua？**（面经实际出现；同上来源）

   在 Redis 8.4 之前用脚本把读取、比较和删除作为一次原子执行，消除命令间竞态；应按部署版本说明条件删除新命令是否可用。

3. **锁过期但业务未完成怎么办？**（面经实际出现；同上来源）

   可有限续期并在资源侧使用 fencing／版本校验；不能只延长一个固定 TTL 后假定永不失锁。

4. **PX 和 EX 有什么区别？为什么必须和 NX 同一条命令？**（面经实际出现；[[面经/淘天/一面/0002#Q09：Redis 做分布式锁用什么命令？PX 和 EX 的区别？|MJ071 · 淘天 · 一面 · Q09]]）

   - PX 毫秒、EX 秒，只差单位；两者都是把过期记成绝对时刻。短锁与限流窗口要毫秒精度就用 PX。
   - “设值＋过期”必须原子：先 SETNX 再 EXPIRE 的话，两步之间进程崩溃就留下一把永不过期的锁；`SET key val NX PX ttl` 一条命令完成互斥与租约。

5. **Redis 集群／主从挂掉，锁会不会丢？怎么兜底？**（面经实际出现；[[面经/淘天/一面/0002#Q11：Redis 集群存储锁实例，节点挂掉时如何避免锁丢失？|MJ071 · 淘天 · 一面 · Q11]]）

   会丢——锁只是主节点内存里的一条 key，主从是异步复制：主加锁成功还没同步就宕机，从升主后没有这把锁，第二个人又能加上。

   - Redlock（向 N 个独立节点多数派加锁）能压缩这个窗口，但受时钟漂移与进程暂停影响，社区对其安全性有明确争议，不能当成严格保证。
   - 工程口径：把 Redis 锁当“性能屏障”，正确性放资源侧——fencing token／数据库条件更新／唯一约束，保证“即使并发也不出错”；要强互斥换 CP 协调服务（ZooKeeper 临时顺序节点、etcd Lease）。

### REDIS-007：Redis 如何组织键值数据，逻辑类型与内部编码有什么区别？

**常见问法**

- Redis 里面的数据是怎么存的？
- Redis 的数据类型和底层结构是什么关系？
- Redis 的 hash 的底层实现是什么？压缩列表和哈希表有什么优劣？
- 缓存的数据结构是什么？（项目本地缓存与 Redis 编码双口径）
- Redis 的哈希数据结构有哪些实现方式？

#### 面试回答

- 存储层面：Redis 逻辑上维护一张 key 到值对象的映射。key 是二进制安全的字节序列，value 对外呈现为 String、List、Hash、Set、Sorted Set、Stream 等逻辑类型。
- 两者的分工：逻辑类型决定能用哪些命令、是什么语义；内部编码是 Redis 按值的大小和内容自己选的内存表示，用来权衡空间和操作效率。
- 一条关键点：编码达到阈值时会自动转换，但对外命令语义不变。

想知道某个 key 现在是什么编码，用 `OBJECT ENCODING key` 看。

#### 技术细节

**各类型当前的编码（以官方当前文档为准）**

- String：`int`、`embstr` 或 `raw`。
- List：Redis 7.0 起小值编码是 listpack；通用表示是 quicklist，由多个 listpack 组成。
- Set：`intset`、`hashtable`；Redis 7.2 起小集合还可以用 listpack。
- Hash：listpack 或 hashtable。
- Sorted Set：listpack 或 skiplist（跳表）编码。
- Stream：用基数树来组织 listpack。

**版本差异**

- Redis 6.2 及更旧的版本里，小的 List／Hash／Sorted Set 看到的还是 ziplist。
- 所以不能脱离版本去背“唯一结构”。

**别把几个层次混在一起**

- 键空间映射、过期信息、内存里的值结构、持久化，是四个不同的层次。
- RDB 把某个时点的数据集写成快照，AOF 记录能重建状态的写操作：它们解决的是重启恢复，不等于内存里的逻辑类型或编码。

**阈值不要硬背**

- 紧凑编码转成通用编码的具体阈值，受版本和配置影响，要查部署配置。

#### 深挖追问

1. **为什么同一个 Hash 会有不同内部编码？**（补充练习）

   小 Hash 用紧凑结构节省指针和分配开销；当元素数或值大小超过配置条件时，转为通用结构以维持操作性能。

2. **RDB 和 AOF 是 Redis 的数据结构吗？**（补充练习）

   不是。它们是持久化与恢复机制；值的逻辑类型和内存编码是另一层概念。

3. **hash 的两种编码各有什么优劣？什么时候切换？**（面经实际出现；[[面经/滴滴/一面/0001#Q08：Redis 的 hash 底层实现是什么？压缩列表和哈希表各有什么优劣？|MJ045 · 滴滴 · 一面 · Q08]]）

   - listpack（6.2 前的旧形态是 ziplist“压缩列表”，面试说压缩列表多半指这条线）：一段连续内存存所有域值对，无逐元素指针，省内存；代价是查找按遍历 O(n)，改动可能 realloc。ziplist 有连锁更新隐患，listpack 逐项元数据的设计把它消掉了——这是版本差异点，值得主动说。
   - hashtable：真哈希表（链地址法），读写平均 O(1)，适合大 hash；每个 entry 有指针与字典元数据开销，负载因子驱动 rehash（渐进式）。
   - 切换：元素数或单个字符串长度超过 `hash-max-listpack-entries`／`hash-max-listpack-value`（默认量级 128／64，以部署配置为准）就转 hashtable；转换单向，缩回去不会转回。
   - 一句总结：小 hash 空间优先、大 hash 时间优先，阈值是两条曲线的交点。

### REDIS-008：Redisson 解决了什么问题，底层是怎么实现的？

**常见问法**

- Redisson 解决了什么问题，它的底层是怎么实现的？
- Redisson 分布式锁底层如何实现，看门狗怎么续期？

#### 面试回答

先说它解决什么：手写 Redis 分布式锁，要自己处理加锁解锁的原子性、校验持有者防误删、过期续期、可重入计数、等锁方式这些点，命令一拆开就有竞态窗口。

Redisson 做的事是把锁、读写锁、信号量、闭锁、限流器这类分布式协调原语，封装成 Java 对象。上面那些边界它都有经过设计的实现，应用不用再逐条处理。

底层核心是三件事：

- 所有状态变更都用 Lua 脚本，在 Redis 内原子执行。
- 可重入锁用 Hash 存状态：field 是“客户端＋线程”的标识，value 是重入次数。
- 没指定过期时间的锁由看门狗自动续期；等锁的客户端是订阅解锁通知后再去竞争，不是纯轮询。

#### 技术细节

**RLock 在 Redis 里长什么样**

- 一个锁 key 对应一个 Redis Hash。
- field 形如“客户端 UUID:线程 ID”，value 是重入次数。

**加锁和解锁脚本各做什么**

- 加锁脚本一次完成三件事：锁不存在就创建、同一线程重入就递增、被别人持有就返回剩余 TTL。
- 解锁脚本先校验 field，再递减，减到 0 才删除 key。
- 所以应用不需要自己去拼 `GET`＋`SET`。

**看门狗怎么续期**

- 默认锁租约 `lockWatchdogTimeout` 是 30 秒。
- 调用 `lock()` 不带 leaseTime 时，后台大约每 1/3 个租约（约 10 秒）续期一次。
- 客户端进程崩溃就没人续期了，锁到期自动释放，不会把资源永久锁死。
- 但别把它当保险：长时间 GC 停顿或网络失联仍可能失锁，关键资源还是要 fencing token（见 [[专题题库/Redis#REDIS-006：Redis 分布式锁如何正确加锁、解锁和续期？|REDIS-006：Redis 分布式锁如何正确加锁、解锁和续期？]]）。

**等锁是怎么实现的**

- 客户端订阅这把锁的解锁通知频道，收到消息后再去尝试获取，同时配合超时退避。
- 这样比轮询省开销。

**它管的不只是锁**

- 除锁之外，还在 Redis 之上提供对象与集合抽象：Map、Bloom filter、RateLimiter、分布式对象服务等。
- 所以它解决的是“用 Redis 做分布式协调”这个通用问题，锁只是其中最常用的一部分。

**口径提醒**

- 默认值、续期周期和脚本语义，都以所用版本的文档为准。

#### 深挖追问

1. **Redisson 相比自己写 SETNX＋Lua 锁强在哪？**（面经实际出现；[[面经/字节/一面/0004#Q01：Redisson 解决了什么问题，底层是怎么实现的？|MJ014 · 字节 · 一面 · Q01]]）

   原子脚本、可重入、看门狗续期、基于订阅通知的等锁、公平锁／读写锁／RedLock 等实现都内置且经过测试；手写方案要自己覆盖误删、过期、重入、等待风暴等全部边界。

2. **客户端宕机后没解锁的锁怎么办？**（补充练习）

   带 leaseTime 到期自动释放；看门狗模式约 30 秒内失效（默认值可配），因为进程死后无人续期。恢复快的业务应显式指定较短 leaseTime。

3. **看门狗续期能保证锁永不丢吗？**（补充练习）

   不能。STW 停顿超过续期周期、与 Redis 网络中断仍会失锁，旧持有者可能在失锁后继续操作，故副作用操作仍需幂等或资源侧版本校验。

### REDIS-009：需要缓存的数据特别大（big value）怎么办？

**常见问法**

- 需要缓存的数据特别大怎么办？
- 针对 Redis 哈希数据结构的大 Key 问题，如何解决？

#### 面试回答

先分清问题：“单个值大”还是“总量大”，两类的处理不一样。

单值大（big value）：

- 拆分：按字段或 hash 分片拆成多个 key，读写可以并行。
- 换格式：用紧凑序列化（protobuf／kryo 替代 JSON 字符串），或者压缩后再存。
- 外置：内容大到不适合放 Redis 时，把数据放对象存储／数据库，Redis 只缓存引用和元数据。
- 读取侧按分片或字段拉取，不要整块搬运。

总量大：

- 只缓存热子集，配 TTL 淘汰。
- 叠加本地缓存做分级，冷数据回源时限流。

危害也要能讲出来：大 value 会让单线程的命令传输与复制时间变长、RT 抖动、集群内存和流量不均、带宽被打满。改完用 `redis-cli --bigkeys`／`MEMORY USAGE`／RDB 分析工具验证。

多大算“特别大”、具体怎么拆，按【项目实际】给数字。

#### 技术细节

**多大算 big value**

- 经验口径常把 value 超过 10KB 级、集合元素上万的 key 列为候选。
- 阈值随版本和部署评估，不要背死数字。

**危害的机制**

- 命令执行是单线程的，大 value 的读写、主从 repl（复制）和 AOF 重写都会放大长尾。
- 集群下，大 key 所在的那个分片要承担不成比例的流量和内存，容易成瓶颈甚至 OOM。
- `DEL` 一个大 key 阻塞很明显，要用 `UNLINK` 异步回收。

**拆分时不要漏掉的两件事**

- 要保证同一次业务读能聚齐所有分片，靠编号规则或索引结构。
- 一整组分片要设置相近的 TTL，防止出现半新半旧的数据。

**两个容易忽略的权衡**

- 压缩是在 CPU 和网络之间做权衡：热点的小 value 未必值得压。
- 把“大而全”的缓存改成“按需子集”时，回源放大的风险要交给限流和预热来对冲（击穿类缓解见 [[#REDIS-002：缓存穿透是什么，布隆过滤器能完全解决吗？|REDIS-002：缓存穿透与击穿]]）。

**和本地缓存怎么分工**

- 大对象只放一层，要么本地、要么 Redis。
- 每一层都复制一份大 value，等于把带宽问题翻倍。

#### 深挖追问

1. **热点 key（big 不一定是热点）和 big value 的处理有什么不同？**（补充练习）

   两者解决的不是同一个矛盾：

   - 热点 key 解决“访问集中”：多级缓存、本地副本、拆键分摊请求。
   - big value 解决“搬运与内存放大”：拆分、压缩、外置引用。

   一个 key 可以既大又热，所以两路措施要同时上。

2. **Hash 类型的大 Key（field 数量巨大）有什么专项处理？**（面经实际出现；[[面经/小米/二面/0001#Q12：Redis 的哈希数据结构有哪些实现方式？出现大 Key 问题如何解决？|MJ079 · 小米 · 二面 · Q12]]）

   上面“拆分／压缩／外置”的口径对 hash 同样成立，另加三条命令侧纪律：

   - 读禁 `HGETALL`：按需用 `HMGET` 取字段子集，全量遍历用 `HSCAN` 分批（COUNT 控制步长），避免单命令长时间占住主线程。
   - 写批量用 pipeline 分片提交，别让一次 `HSET` 塞上千 field。
   - 删除用 `UNLINK` 异步回收；治理后按“field 数上限”立 key 规范（如单 hash 不超过万级），从源头防再生。

### REDIS-010：什么是热 Key，为什么危险，如何探测与解决？

**常见问法**

- 高并发场景下“热 Key”问题会对系统产生什么影响？怎么解决？
- 单个商品详情被疯狂访问，Redis 集群明明还有余量却延迟飙升，为什么？
- 怎么定义热 Key？判断依据是什么？在哪里统计访问次数、阈值在哪里比较？多机分布式环境怎么处理？
- 某个短链是热点、又是新建的，缓存里没有，所有请求都打到数据库，这种场景怎么解决？

#### 面试回答

热 Key 就是某个 key 的访问量远超其它 key，典型来源：秒杀商品详情、爆款内容、活动配置、全局开关。

危险点不在数据大，而在访问集中：

- Redis 单线程执行命令，Cluster 又按 slot 分片，一个 key 只能落在一个分片上。
- 于是这个分片的 CPU／网卡／连接被打满：集群整体 QPS 不高，但这个节点延迟飙升，同节点的其它 key 也被拖慢。
- 第二层风险是失效重建风暴：key 过期的瞬间大量请求穿透到数据库，形成级联雪崩。
- 写热同理：单 key 或数据库单行的写会串行化，并把锁竞争放大。

解决按“探测→分摊→下沉”三层说：

- 探测：靠监控与统计（客户端埋点、`redis-cli --hotkeys`／`--bigkeys` 采样、云托管的热 key 分析），第一步先分清是读热还是写热。
- 分摊：多级缓存（把热数据放进应用进程的本地缓存，用短 TTL＋异步刷新容忍短暂陈旧，这是最有效的一招）；拆 key 打散（`key#0..N` 加随机后缀，让请求散到不同分片）；只读副本、多副本 key 分摊读。
- 下沉与兜底：逻辑过期或互斥重建防击穿、请求合并（singleflight）、活动前预热；写热用攒批或异步队列合并写。

最后必须补一句代价：本地缓存换来的是一致性窗口，做了多级缓存就要配套失效广播（见 [[专题题库/系统设计#SYS-009：多级缓存如何保持一致，并在 Redis 故障时降级？|SYS-009：多级缓存如何保持一致]]），不能只说“加个本地缓存”。

#### 技术细节

**读热为什么摊不平**

- Redis 的命令执行是单线程的（6.0 之后网络 I/O 可以多线程，但命令执行仍然串行），所以同一个 key 的访问没法靠并行摊开。
- Cluster 又按 key 的 CRC16 槽位分片，热点天生无法分散，倾斜的那个分片会先饱和。
- 这和 big value 落在同一分片是两类问题（[[#REDIS-009：需要缓存的数据特别大（big value）怎么办？|REDIS-009：big value 怎么办]]：一个解决“访问集中”，一个解决“搬运与内存放大”；同一个 key 可以既大又热，两路措施要同时上）。

**拆 key 的做法与约束**

- 做法：把详情／库存拆成 N 份，客户端随机选一个后缀，读侧的分摊确实有效。
- 前提：业务能接受“聚合多份结果”，库存这类还要汇总才能判断余量。
- 约束：写侧必须一次更新所有分片，否则分片之间会不一致。
- 副本 key（`key#replica-i`）是同一份数据多写几份，读时随机选一份，代价仍然是写放大。

**重建方案的取舍**

- 逻辑过期：把重建从请求路径挪到后台，延迟平稳，但会读到旧值。
- 互斥锁：保证只回源一次，但有等待开销和锁失效风险（与 [[#REDIS-006：Redis 分布式锁如何正确加锁、解锁和续期？|REDIS-006：分布式锁]] 的失效边界同源）；穿透类的背景见 [[#REDIS-002：缓存穿透是什么，布隆过滤器能完全解决吗？|REDIS-002：缓存穿透]]。

**写热要换一套思路**

- 合并写：本地攒批后一次写回。
- 计数类的写：改成按分片各自计数，再汇总。
- 或者用消息队列异步落库。
- 纯缓存手段对写热基本无效。
- 多活／同城容灾场景还可以把只读的热数据下沉到就近机房或 CDN 边缘，进一步减少跨网络往返。

**探测的实操口径**

- 最准的是按 QPS 做 Top-N 统计，数据来源用网关或客户端埋点。
- Redis 侧用 `INFO commandstats`、慢日志和云监控的热 key 报表做辅助。
- `MONITOR` 只能在低峰期短时间开，它本身就是性能杀手。

#### 深挖追问

1. **热 Key 和大 Key 是一回事吗？**（补充练习）

   不是，两件事的区别在问题和指标上：

   - 问题：大 Key 是单次操作搬运量大、会阻塞、内存分布不均；热 Key 是访问集中，把单个分片打饱和。
   - 识别指标：一个看 value 体积和元素数量，一个看 QPS 的倾斜程度。

2. **加了本地缓存后数据不一致怎么办？**（补充练习）

   先把可容忍的陈旧窗口定下来（热 Key 场景通常是秒级），再选手段：

   - 短 TTL＋异步刷新，把不一致压在一个窗口内。
   - 数据变更时广播失效：走消息、Redis keyspace 通知或自研通知。
   - 关键判定（库存、权限）必要时保留服务端强校验。

3. **拆 key 分摊会带来什么新问题？**（面经实际出现；[[面经/阿里国际/一面/0001#Q05：高并发场景下热 Key 问题会对系统产生什么影响，怎么解决？|MJ038 · 阿里国际 · 一面 · Q05]] 的延伸）

   带来两类新问题：

   - 写放大与一致性：更新要覆盖全部分片或所有副本。
   - 语义变复杂：总余量、排名这类汇总结果要在应用层聚合。

   所以拆 key 通常是和本地缓存搭配用，而不是单独用。

4. **“统计 key 访问次数、和阈值比较”具体在哪里做？**（面经实际出现；[[面经/腾讯/一面/0001#Q05：怎么定义热 Key、判断依据是什么？访问次数在哪里统计、阈值在哪里比较？分布式多机环境怎么处理？|MJ046 · 腾讯 · 一面 · Q05]]）

   三个候选位置，各有成本：

   - 业务代码／网关埋点：每次访问对 key 计数（放滑动窗口里），最灵活、口径最贴业务；判断与 Top-N 汇总放聚合组件，不放请求路径——阈值比较是运维决策，不该给每个请求加开销。
   - Redis 自带统计：`maxmemory-policy` 设为 LFU 后 `OBJECT FREQ`／`redis-cli --hotkeys` 能读近似频次，零改造但受淘汰策略约束、且只看 Redis 侧流量。
   - 云托管／代理层的热 Key 实时分析（主流云厂商 Redis 监控普遍提供，具体能力以各厂商当期文档为准），精度取决于采样。
   - 判据口径：绝对 QPS Top-N 之外，看“单分片流量占比倾斜度”更早发现问题。

5. **业务代码是单机视角，多机部署时统计怎么聚合？**（面经实际出现；[[面经/腾讯/一面/0001#Q05：怎么定义热 Key、判断依据是什么？访问次数在哪里统计、阈值在哪里比较？分布式多机环境怎么处理？|MJ046 · 腾讯 · 一面 · Q05]]）

   负载均衡会把同一 key 的流量打散到各实例，单机计数器看到的是全局的一份碎片，必须聚合：

   - 本地增量计数＋定时（秒级）合并上报，中心侧滑窗聚合出全局 Top-N，再下发热点名单供各实例本地缓存／告警——统计走异步旁路，不进请求路径。
   - 全量上报太贵时上采样＋heavy hitter 结构（Count-Min Sketch／Space Saving），内存恒定还能保住 Top 精度。
   - 也可以用现成组件替代自研：网关层统计、Flink 类实时聚合，或云数据库自带的热 Key 分析。

6. **热点 key 是新建的、缓存里从来没有过，怎么办？**（面经实际出现；[[面经/字节/一面/0011#Q12：新短链是热点且 Redis 没缓存，请求全打到数据库，这种场景怎么解决？|MJ066 · 字节 · 一面 · Q12]]。原素材未记回答，以下为参考）

   这一类的成因和前面两类都不同，先分清再谈解法：

   - 不是穿透：数据真实存在，布隆过滤器帮不上忙。
   - 不是过期击穿：key 从没进过缓存，谈不上「过期」。
   - 是「首次访问即热」：投放、转发或推送让新 key 上线第一秒就是洪峰。

   解法按写侧与读侧各一条：

   - 写侧预热：创建成功即写缓存（并广播让各实例本地缓存装载），把首次访问的代价付在写路径上。
   - 读侧合并：同 key 并发回源用 singleflight 收敛成一个请求，其余等待共享结果；DB 前置连接池与并发上限，超限降级。
   - 再加一道容量护栏：入口按 key 维度限频，防止一个异常热点吃光整个分片的处理能力。

### REDIS-011：Redis 有哪些部署模式，单实例／主从／哨兵／Cluster 怎么选？

**常见问法**

- 服务里 Redis 是怎么部署的？单实例、主从、哨兵还是集群？
- 哨兵和 Cluster 有什么区别，什么时候用哪个？
- 谈谈 Redis 从哪些方面可以保证高可用？
- 为什么需要把主从模式升级为集群模式？

#### 面试回答

按“可用性”和“容量／并发”两条线递进，报清自己用的那档和为什么：

- 单实例：一台，最简，无高可用，宕机即不可用，通常只在本地开发用。
- 主从（Replication）：一主多从，读写分离＋数据冗余；但故障切换要人工，写仍是单点，数据量不受扩展。
- 哨兵（Sentinel）：在主从之上部署哨兵集群，自动做监控、故障发现和主从切换（自动 failover），解决“高可用”；仍是单写入点、不能水平扩数据。
- 集群（Cluster）：多主多从，数据按 16384 个哈希槽分片，读写都能水平扩展、每个分片还能再挂从做高可用，解决“数据量大＋高并发”。

选型一句话：要高可用但数据不大→哨兵；数据量大、并发高→Cluster；生产环境基本不用裸单实例。

#### 技术细节

**主从：复制的是数据不是调度**

- 从节点全量（首次 RDB＋增量 backlog）同步主节点；读写分离能把读压力分摊到从，但要接受主从延迟导致的读到旧值。
- 主挂了不会自动切，运维手动 `REPLICAOF NO ONE` 提升——这是它和高可用的关键差距。

**哨兵解决的是“自动切换”**

- 主观下线（单个哨兵认为挂了）→ 客观下线（达到 `quorum` 个哨兵都这么认为）→ 哨兵间选举一个 leader 执行 failover，挑一个从提升为新主并让其它从跟随。
- 哨兵本身要奇数个、且 ≥3，分布在不同的物理机／可用区，避免单机全挂或票数相等。
- 客户端不直连 Redis，而是先问哨兵拿当前主地址。

**Cluster 解决的是“扩展＋分片高可用”**

- key 用 `CRC16(key) mod 16384` 映射到槽，槽分配给各主节点；扩容时迁移槽即可。
- 访问到非本节点持有的 key，返回 `MOVED`／`ASK` 重定向，客户端要能处理。
- 每个分片各自一主多从，主挂由该分片的从自动升主——把“哨兵的自动切换”做进了每个分片。
- 限制：跨槽的多 key 操作（如 `MGET`、事务）要用 hash tag `{}` 强制同槽。

**容易说错的点**

- 别说“Cluster 一定比哨兵好”：小数据量、强一致跨 key 操作多的场景，Cluster 的多 key 限制反而是负担，哨兵更合适。
- 哨兵不做数据分片，它管的仍是“一主多从”，别把它当成扩容方案。

#### 深挖追问

1. **主从复制和哨兵能一起用吗？**（面经实际出现的延伸）

   能——哨兵本来就设计在主从集群上：平时靠主从做读写分离和冗余，哨兵只在主故障时介入自动切换。二者是“数据复制”和“高可用调度”两层，不冲突。

2. **Cluster 下怎么做分布式锁？**（补充练习）

   单实例锁语义在 Cluster 上不天然成立（锁可能因主从切换丢失）。要更强保证用 Redlock（多独立节点过半加锁成功），但它也有争议；能不用跨分片锁就不用，详见 REDIS-006。

### REDIS-012：Redis 的网络层和命令执行是同一个线程吗？IO 多路复用的原理是什么？

**常见问法**

- Redis 的网络层和业务层是否共用同一个线程？
- Redis 是单线程的还是多线程的？
- 线程池里多个线程同时对同一个 Redis 做 put，可以吗？
- Redis 处理消息的流程是什么？IO 多路复用的原理是什么？
- Redis 有哪些使用多线程的场景？
- 为什么 Redis 单线程还能支撑高并发？

#### 面试回答

结论：命令执行始终在主线程；6.0 起网络读写可以开多个 I/O 线程，但解析出的命令仍串行回到主线程执行。

- 6.0 之前：socket 的读写和命令执行都在主线程的事件循环里。
- 6.0 之后：`io-threads` 默认 1（关闭）；开启后 I／O 线程只负责并发读、解析协议和写回，执行命令仍是单线程。
- 7.4 起多了 `io-threads-always-on`，可以按负载动态启用 I/O 多线程，口径没变。
- 为什么这样拆：瓶颈常在 syscall 密集的读写与协议解析，放多线程分摊；命令执行保持单线程才能免锁、保证单命令原子性。

#### 技术细节

**事件循环的构成**

- 文件事件：epoll 监听客户端连接的可读／可写。
- 时间事件：周期任务——serverCron 做过期清理、rehash、统计、主从心跳。
- Redis 自己的 ae 事件库把两类事件排进同一个循环，每轮先处理 IO、再按时间触发任务。

**一条消息的完整流程**

- epoll_wait 返回可读事件。
- I/O 线程（或主线程）从 socket 读入缓冲、按 RESP 协议解析出命令。
- 命令按接收顺序排进待执行队列。
- 主线程逐条执行命令、写入回复缓冲。
- 由 I/O 线程并发把响应写回 socket，减少数据在 socket 发送缓冲里的停留时间。

**IO 多路复用原理**

- 解决的问题：一个线程要同时照看成千上万个连接，不能一连接一线程（线程爆炸），也不能轮流 read（大部分空转）。
- 做法：把多个 fd 注册进内核的一个监听集合（epoll 实例），线程阻塞在 epoll_wait；内核在某个 fd 就绪时把它挂到就绪链表，wait 只返回就绪列表。
- 对比 select／poll：两者要把全量 fd 集合拷进内核并 O(n) 遍历；epoll 用红黑树管理注册 fd、回调收集就绪项，成本随「就绪数」而非「总数」增长。
- LT／ET：边缘触发只在状态变化时通知一次，必须一口气读到 EAGAIN；Redis 的事件库对读写事件做了相应封装。

**别把「单线程」说死**

- bgsave 是 fork 出的子进程；AOF fsync、lazyfree／UNLINK 的异步回收、主从复制的发送都有额外线程参与。
- 准确说法：**命令执行**单线程。

**单线程的代价**

- 一个慢命令（大 key 的 O(N) 操作、KEYS）会阻塞其后所有客户端——所以有 slowlog 和大 Key 治理，见 [[#REDIS-009：需要缓存的数据特别大（big value）怎么办？|REDIS-009：需要缓存的数据特别大（big value）怎么办？]]。
- 单核打满后加线程救不了命令执行，只能横向分片。

#### 深挖追问

1. **多线程 I/O 会不会打乱命令顺序？**（补充练习）

   不会打乱执行顺序：并发只发生在读写与解析，命令入队按到达序，执行仍由主线程串行完成。

2. **Redis 的 I/O 线程默认是开的吗？**（补充练习）

   不是，`io-threads` 默认 1；要压测证明瓶颈在网络读写后再调，线程数设为核数的一个较小比例（常见 1/4～1/2），具体以部署版本官方建议和压测结果为准。

### REDIS-013：Redis 的 Set 和 ZSet 有什么区别，跳表怎么插入元素？

**常见问法**

- Redis 的 Set 和 ZSet 区别？
- 跳表插入一个元素的过程？
- 谈谈 Redis 的 ZSet 的底层实现。
- ZSet 插入一个元素的时间复杂度是多少？完整插入过程讲一遍（含代码级步骤）。
- 排行榜为什么用 ZSet 而不是 Set？
- 查有序集合里元素的个数，命令是什么、复杂度多少？取某个元素的分数呢？

#### 面试回答

结论：Set 只管「在不在」，无序、成员唯一；ZSet 给每个成员挂一个分数并按分数排序，支持排名和区间查询。

- Set 编码：intset（纯整数且小规模）、listpack（7.2 起小集合）、hashtable。
- ZSet 编码：小集合 listpack；规模上去后「跳表＋哈希表」双结构并存。
- 跳表插入：随机定层数 → 从高到低逐层找插入位置 → 逐层改前驱指针，平均 O(log n)。
- 选型直觉：去重、交并差用 Set；排行榜、按时间取区间（延时队列）用 ZSet。

#### 技术细节

**能力对比**

| 维度 | Set | ZSet |
| --- | --- | --- |
| 排序 | 无序 | 按分数有序 |
| 判存在 | O(1) | 经字典 O(1) |
| 排名／区间 | 不支持 | O(log n)＋输出规模 |
| 集合运算 | 交并差 | 按字典序做交并（权重可聚合） |

**ZSet 双结构的目的**

- 跳表负责「按分数找」：ZRANGE、ZRANGEBYSCORE、排名。
- 哈希表负责「按成员找分数」：ZSCORE 平均 O(1)；没有它，查一个成员的分数要遍历跳表。
- 两者共享同一批成员对象，内存换时间。

**跳表插入的准确过程**

1. 定层数：抛硬币——有 1/4 概率升一层（Redis 实现 `SKIPLIST_P = 4`），上限默认 32 层。
2. 找位置：从表头最高层出发，`当前层的下一个节点分数 < 新元素` 就右移（记录跨度），不能再右就下沉一层，直到第 0 层。
3. 同分按字典序比较成员名，保证顺序确定。
4. 把每层停住的「前驱节点」记进 update 数组、跨度记进 rank 数组。
5. 创建新节点（层数＝随机层数＋1），从下往上逐层把前驱的 next 指向自己、自己的 next 指向原后继，并修正 span。
6. 用 rank 数组算出新节点的名次，写进各层的跨度调整值——跨度维护正确，`ZRANK` 才能靠累加跨度得到排名。

**为什么 Redis 选跳表而不是红黑树／B+ 树**

- 范围查询：找到起点后沿第 0 层链表顺序走，红黑树要中序回溯，实现繁琐。
- 实现与调试成本低，无旋转、无再平衡。
- 排名计算：跳表节点自带跨度，累加即排名；红黑树要加子树大小字段。
- 并发友好性在这里不是理由（Redis 命令单线程）。

**容易说错的点**

- 「跳表查询 O(log n)」是期望复杂度，靠随机层数保证平衡；最坏退化到 O(n) 的概率极低但存在。
- 小 ZSet 根本不用跳表（listpack），背结构要带规模条件。
- 分数相同不代表无序可省：Redis 对同分成员按字典序排，讲插入流程要提这一句。

#### 深挖追问

1. **ZSet 的跳表为什么每个节点要存 backward 指针？**（补充练习）

   便于反向遍历（ZREVRANGE）和从尾部取值（ZPOPMAX 一类操作）；没有它，找到某节点后要回看前驱只能从头扫。

2. **同一个成员分数更新，跳表怎么处理？**（补充练习）

   先从旧位置删除再按新分数插入——跳表不支持原地改键；字典里的分数同步更新。

3. **Set 判存在和 ZSet 判存在有什么区别？**（补充练习）

   Set 命中哈希／intset 即完成；ZSet 查成员走配套字典 O(1)，两者都不用碰跳表。

4. **查 ZSet 元素个数、查某个元素的分数，各用什么命令、什么复杂度？**（面经实际出现；[[面经/快手/一面/0001#Q14：ZSet 的具体实现？数据量大时为什么用跳表不用压缩列表？查元素个数和分数的命令与复杂度？|MJ086 · 快手 · 一面 · Q14]]）

   - 个数：`ZCARD key`，O(1)——结构里维护着元素计数，不用遍历。
   - 某成员的分数：`ZSCORE key member`，O(1)——走的是配套的 member→score 哈希表。
   - 别和 `ZRANK`（取排名）混：排名要沿跳表累加跨度得到，平均 O(log n)。
   - 数据量大时为什么不用压缩列表（listpack）也在这题链条里：listpack 按分数查找和插入都要线性扫描 O(n)，跳表是平均 O(log n) 且范围查询沿第 0 层顺走；哈希表补上按成员 O(1) 查分数，双结构互补。

### REDIS-014：被问“谈谈对 Redis 的理解”怎么组织回答？

**常见问法**

- 谈谈对 Redis 的理解。
- 你对 Redis 了解到什么程度？（开放引言题）

#### 面试回答

结论：按“是什么→为什么快→能干什么→用要注意什么”四层各讲一两句，把深挖权交给面试官，哪层被追就展开哪层。

- 是什么：基于内存的键值数据结构服务器，常见角色是缓存、计数器、分布式协调，同时支持持久化落盘。
- 为什么快：数据在内存；命令执行单线程、没有锁竞争；IO 多路复用撑大量连接；内部编码（quicklist／跳表／intset 等）按规模择优。
- 能干什么：五种基本类型加 Bitmap／HyperLogLog／GEO／Stream，落点要说真实场景——缓存、排行榜、签到、限流、分布式锁。
- 注意点：容量有界要配过期与淘汰；缓存与数据库的一致性策略；穿透／击穿／雪崩三类故障；big key 与热 key 治理。

#### 技术细节

**“是什么”要说区别于普通 Map 和 Memcached**

- 数据结构语义在服务端：Hash 取一个字段、ZSet 取一段排名，命令直接完成，不用捞回客户端再算——这是对“纯 KV（Memcached）”的主要差异点。
- 不只是缓存：协调（分布式锁／信号量）、计数、轻量消息（Stream、发布订阅）都是常用形态；比较 Memcached 说“场景不同”，别说“秒杀它”。
- 有持久化：RDB／AOF 让它能充当有恢复能力的存储层，不只有“重启就没了”的缓存层（细节见 REDIS-003）。

**“为什么快”每一句都要带限定**

- 主因是内存操作纳秒级；单线程执行免除上下文切换与锁竞争——这两句顺序别反，“单线程”本身不是快的来源。
- IO 多路复用解决的是“几万连接不卡死”，不等于命令执行更快；线程模型细节见 REDIS-012。
- 可补一个客户端侧加分点：pipeline 批量发送减少往返，是压延迟的常用手段。

**“能干什么”必须锚回项目**

- 每个类型配一个自己动过的场景：【String 缓存＋TTL／Set 幂等去重／ZSet 排行榜／Bitmap 签到】——【】内换成真实经历，说不出场景就不如少列类型。
- 用过缓存的顺手带一句一致性怎么做的、过期时间怎么定的（对应 REDIS-002／003），这句话最能区分“背过”和“用过”。

**“注意点”是生产视角的得分区**

- 过期与淘汰：惰性删除＋定期删除两条腿，内存打满看 `maxmemory-policy`（见 REDIS-005）。
- 一致性：删除缓存再写库＋过期兜底、延迟双删、订阅 binlog 补偿——没有绝对强一致，说清业务能接受哪种不一致窗口。
- 高可用：主从＋哨兵或 Cluster（见 REDIS-011）；同时如实说异步复制可能丢数据——丢锁风险的展开见 REDIS-006。
- 防护面：穿透／击穿／雪崩（REDIS-002）、big value（REDIS-009）、热 key（REDIS-010）各留一句钩子，等面试官挑。

#### 深挖追问

1. **既然命令单线程，为什么还快？多线程不会更快吗？**（补充练习；这题常被拿来验证“为什么快”是不是背的）

   瓶颈不在 CPU 计算：内存操作极快，多线程的收益被锁竞争和上下文切换吃掉，单线程反而省去同步成本。真要挖并行度，是 IO 线程解析协议（io-threads，默认关闭）和后台线程处理 AOF／UNLINK 这类活，命令执行仍然单线程——见 REDIS-012。

2. **Redis 是内存数据库，会不会把内存吃光？**（补充练习）

   有上界：`maxmemory` 固定容量，到达后按淘汰策略驱逐键；再叠加过期删除，内存不会无界涨。反例是设了 noeviction 又塞满——表现是写命令直接报错，不是“吃光整机内存”。展开见 REDIS-005。
