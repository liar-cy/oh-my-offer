### REDIS-001：Redis 有哪些数据类型，分别用于哪些场景？

**常见问法**

- Redis 中有哪些数据结构，经常用在哪些场景？

- Redis 有哪些数据类型，底层如何实现？

- 项目中的 Redis 是怎么用的，存了哪些数据？

- 介绍下 Redis 的常用数据类型。
- Redis 除了缓存还有什么作用？

- 用 Redis 设计一个统计次数的功能。

- Redis 为什么快，有哪些数据结构，String 用的什么结构？

#### 面试回答

常见类型有 String、Hash、List、Set、Sorted Set，分别适合简单缓存或计数、对象字段、列表、去重集合和排行榜；还有 Bitmap、HyperLogLog、GEO、Stream 等能力，可用于签到、近似去重计数、地理位置和消息流。选型时看操作方式、精度、数据量及可靠性需求，不只看名称。

以 Redis 7.2 为版本基线：String 的 int 保存可表示的整数，embstr 与 raw 使用不同对象和字符串内存布局；Hash 小对象可用 listpack，超过条件转哈希表；List 用 quicklist，其紧凑节点使用 listpack；Set 可用 intset、listpack 或哈希表；ZSet 可用 listpack，或跳表加字典以兼顾排序范围和成员定位。Bitmap 建立在字符串上，GEO 基于 ZSet，HyperLogLog 是概率计数表示；Stream 的条目采用 radix tree 与 listpack 组织；不能都按独立容器类型记忆。后续版本的 List 等编码已有差异，需用 OBJECT ENCODING 和部署版本核对，不固定背阈值。

#### 技术细节

秒杀库存：单个券批次计数通常使用 String；用 Lua 在一次执行中校验库存存在、数量合法和余额足够后再扣减，多个字段联合更新也可用 Hash。单条 DECR 原子，但会允许负数，不能代替“判断＋扣减”的原子条件逻辑。脚本原子执行不意味着自动回滚脚本出错前已经完成的写入，应先校验再修改；脚本也不提供跨 Redis 与数据库的原子事务。以支持 EVAL 的 Redis 2.6+ 为前提，集群多键脚本还需遵守同槽约束，具体实现需结合部署版本。

区分对外数据类型与内部编码：Hash 不一定始终由普通哈希表实现，编码会受版本、大小和配置影响。List 的简单队列操作不自动提供业务确认与重试；Stream 消费组也需要处理 pending、确认和重复消费。Sorted Set 按分数排序并处理同分成员顺序；HyperLogLog 是近似基数统计，不能枚举成员。Bitmap 适合较稠密整数 ID，极大稀疏 ID 可能浪费空间。新增概率数据结构的可用性还需检查部署版本。

#### 深挖追问

1. **排行榜为什么选 ZSet？**（补充练习）

   它支持按分数更新、排名和范围读取，但仍要定义同分排序、时间窗口及大键规模。

2. **缓存对象用 String 还是 Hash？**（补充练习）

   整体读取可序列化为 String，字段级更新可考虑 Hash，结合访问模式、过期需求及内存测量选择。

3. **秒杀扣库存最适合哪种数据类型？**（面经实际出现；[[面经/百度/一面/0002#Q06：Redis 常见数据类型有哪些，秒杀扣库存选哪一种？|MJ005 · 百度 · 一面 · Q06]]）

   单批次计数通常选 String，配合原子条件扣减；类型本身不保证幂等或跨组件一致性，参见 [[专题题库/系统设计#SYS-004：Redis 预占与 MySQL 异步扣库存如何实现最终一致？|库存一致性]]。

4. **类型和底层编码是一一对应吗？**（面经实际出现；[[面经/百度/一面/0005#Q16：Redis 有哪些数据类型，底层如何实现？|MJ008 · 百度 · 一面 · Q16]]）

   不是，编码会按值、元素数量、大小阈值及版本选择或转换；对外命令语义相对稳定。

5. **用 Redis 设计一个统计次数的功能，怎么选结构？**（面经实际出现；[[面经/字节/一面/0007#Q10：用 Redis 设计一个功能统计次数。|MJ026 · 字节 · 一面 · Q10]]）

   先问口径再选结构：精确计数用 `INCRBY`＋按维度拼 key＋TTL/定期落库归档；精确去重计数用 Set（内存随基数线性涨，量大要评估）；近似 UV 用 HyperLogLog（固定约 12KB、标准误差约 0.81%），适合量级监控够用的大基数；连续状态（签到）用 Bitmap 位运算；多维分析实时层留 Redis、明细异步进数仓。误差与容量是 Set 与 HLL 之间选择的决定因素。

6. **Redis 为什么快？**（面经实际出现；[[面经/帆软/一面/0002#Q08：Redis 为什么快，有哪些数据结构，String 用的什么结构？|MJ027 · 帆软 · 一面 · Q08]]）

   四层：纯内存操作；命令在单线程模型内顺序执行，无锁竞争、无线程上下文切换（网络 IO 由 epoll 事件驱动多路复用，6.0 后读写与响应可多线程、命令执行仍单线程）；数据结构针对场景高度优化、按规模自动切换编码；协议简单＋pipeline 摊薄网络往返。别把“单线程”说成全部——持久化、过期删除等仍有额外线程/子进程参与。

### REDIS-002：缓存穿透是什么，布隆过滤器能完全解决吗？

**常见问法**

- [[面经/美团/一面/0002#Q05：Redis 使用过程中遇到过缓存穿透吗？出现不一致的情况吗？|MJ032 · 美团 · 一面 · Q05]]
- 缓存穿透、击穿和雪崩有什么区别，如何解决？
- 缓存穿透是什么？
- 缓存穿透怎么解决？
- 布隆过滤器可以完全解决缓存穿透吗？

- 项目中如何解决缓存穿透、缓存击穿和缓存一致性问题？

- 项目怎么解决缓存击穿问题的？为什么用逻辑过期而不用互斥锁？

- 讲一下布隆过滤器。

- 什么是缓存雪崩，怎么解决？除了随机化 TTL 还有什么补充方案？

#### 面试回答

穿透是请求不存在的数据，反复绕过缓存查数据库，可用参数校验、短期空值缓存、布隆过滤器和限流。击穿是单个热点 key 失效后，大量请求同时回源，可用互斥重建、请求合并、提前刷新，或在业务允许时返回旧值并异步更新。雪崩是大量 key 集中过期或缓存服务不可用，造成大范围回源，要打散 TTL、提升缓存可用性，并通过限流、熔断降级和回源并发限制保护数据库。布隆过滤器有假阳性，不能完全解决穿透，数据更新时还需同步过滤器与空值缓存。

#### 技术细节

标准布隆过滤器在正确插入且未破坏状态的前提下没有假阴性，但系统漏同步新增 key 会误拒绝真实数据。位数组大小 m、哈希次数 k、插入量 n 决定误判率，近似为 (1-exp(-kn/m))^k。普通布隆不支持直接安全删除，删除场景需其他结构或重建策略。空值缓存要区别不存在与数据库异常，异常不能被长期当作不存在；新增数据后需更新过滤器并处理旧空值。缓存击穿是热点 key 失效，雪崩是大量 key 或缓存服务同时失效，不是同一个问题。

互斥重建需约束等待时间，并处理重建失败；多实例单机锁只能合并各自进程内请求。逻辑过期方案以接受短暂旧值换取可用性，不能用于任意强一致场景。TTL 抖动只能缓解集中过期，不能解决 Redis 整体故障；主从或集群也不替代回源限流。穿透中的空值缓存应区分数据库异常与真实不存在，布隆过滤器有假阳性，新增数据需同步更新。

#### 深挖追问

1. **布隆判断存在，数据库却没有怎么办？**（面经实际出现；[[面经/百度/一面/0001#Q07：什么是缓存穿透，如何解决，布隆过滤器能完全解决吗？|MJ002 Q07]]）

   按正常未命中路径查询，必要时缓存空值并限流，这是允许的假阳性。

2. **数据新增了但过滤器没更新怎么办？**（补充练习）

   设计更新顺序和补偿机制，避免直接把未同步导致的否定结果当永久事实。

3. **三种缓存问题分别怎么解决？**（面经实际出现；[[面经/百度/一面/0003#Q12：缓存穿透、击穿和雪崩有什么区别，如何解决？|MJ006 · 百度 · 一面 · Q12]]）

   不存在的数据做校验、空值缓存和过滤；热点失效合并重建并允许适当旧值；大范围失效打散过期、提升可用性并控制回源。

4. **击穿为什么用逻辑过期而不用互斥锁？**（面经实际出现；[[面经/百度/二面/0003#Q07：为什么使用逻辑过期方案，而不用互斥锁？|MJ020 · 百度 · 二面 · Q07]]）

   互斥锁重建期间其他请求阻塞，DB 慢或重建失败时线程堆积、延迟尖刺，还要处理锁失效；逻辑过期让所有请求先拿旧值、由抢到重建权的异步任务刷新，时延平稳，代价是明确容忍一段旧数据。读多且可短暂陈旧的热点（商品详情）适合逻辑过期；余额、库存等不能读旧值的数据必须互斥重建或直接读权威源。

5. **项目里真的遇到过缓存穿透吗？**（面经实际出现；[[面经/美团/一面/0002#Q05：Redis 使用过程中遇到过缓存穿透吗？出现不一致的情况吗？|MJ032 · 美团 · 一面 · Q05]]）

   本地部署、流量可控时不会自然发生，但**用不存在的 ID 压测就能复现**：随机大 ID 打接口，缓存永不命中，DB QPS 与 RT 同步抬起来。答这题的正确姿势是“自然流量没遇到＋我主动构造复现过＋当时怎么挡”：参数校验先挡非法 ID，空值缓存（短 TTL、区分“不存在”与“查询异常”）覆盖小范围不存在数据，布隆过滤器用于大基数场景并说明假阳性与新增同步问题。只答“没遇到过”等于放弃这题的展示机会。

6. **除了随机化 TTL，还有什么补充方案解决缓存雪崩？**（面经实际出现；[[面经/帆软/二面/0002#Q04：什么是缓存雪崩，怎么解决？除随机化 TTL 还有什么补充方案？|MJ035 · 帆软 · 二面 · Q04]]）

   按层给：缓存层高可用（哨兵／集群＋副本，本地缓存 Caffeine 兜底热点，Redis 整体故障仍有第一道防线）；回源层限流（互斥重建、请求合并、信号量控制在途回源并发，DB 前排队）；业务层降级（返回适当旧值、静态兜底、熔断）；运营层预热（重启或大促前主动装填）与热点 key 永不过期＋后台异步刷新的主动模式。TTL 打散只覆盖“集中过期”一种成因，服务不可用型雪崩靠可用性＋限流降级组合拳。

### REDIS-003：Redis 有哪些持久化方式，RDB 和 AOF 有什么区别？

**常见问法**

- [[面经/美团/一面/0002#Q24：Redis 数据持久化，两种方式各自介绍|MJ032 · 美团 · 一面 · Q24]]
- Redis 有哪些持久化方式，RDB 和 AOF 有什么区别？

- 混合持久化机制是如何工作的？

#### 面试回答

RDB 保存某一时刻的数据快照，文件通常紧凑、适合备份和快速加载，但故障可能丢失最近快照后的写入；AOF 记录写操作，通过回放恢复，持久性由 fsync 策略决定，文件通常更大并需重写。两者可同时使用，也有 RDB 基础数据加 AOF 增量的混合形式；选择要结合能接受的数据丢失、恢复时间和运行开销。

#### 技术细节

SAVE 阻塞执行快照，BGSAVE 通常 fork 子进程利用写时复制生成快照，fork 与写时复制仍可能带来停顿和内存压力。AOF 的 always 在追加批次后同步，everysec 通常每秒同步、故障可能丢约一秒写入，no 交给操作系统；具体持久性仍受配置和存储影响。重写依据当前数据生成紧凑表示，并非简单复制全部历史日志。Redis 7.0 起采用多部分 AOF，用 base、增量文件与 manifest 管理；同时启用时重启优先使用 AOF 恢复。

#### 深挖追问

1. **RDB 和 AOF 的主要取舍是什么？**（面经实际出现；[[面经/百度/一面/0003#Q13：Redis 有哪些持久化方式，RDB 和 AOF 有什么区别？|MJ006 · 百度 · 一面 · Q13]]）

   RDB 偏向紧凑快照和恢复效率，AOF 可用更频繁同步缩小丢失窗口，但有写入、空间及重写成本；两者都需要考虑实际磁盘和备份策略。

2. **混合持久化机制是如何工作的？**（面经实际出现；[[面经/帆软/二面/0002#Q01：Redis 的 RDB 和 AOF 有什么区别，混合持久化如何工作？|MJ035 · 帆软 · 二面 · Q01]]）

   开启 `aof-use-rdb-preamble` 后，AOF 重写的瞬间先把当前全量数据以 RDB 二进制格式写入新 AOF 文件头部作为 base，重写期间的增量命令再以命令格式追加在尾部；重启恢复时载入 RDB base 后回放尾部增量。收益：文件更小、恢复先走 RDB 快速载入再补少量命令，同时保留 AOF 的小丢失窗口；7.0 起多部分 AOF 把 base／增量／manifest 拆成文件管理，混合形态成为默认机制的一部分。

### REDIS-004：Redis 如何实现固定窗口、滑动窗口、令牌桶与漏桶限流？

**常见问法**

- Redis 有哪些限流算法，如何实现？

- 限流部分怎么实现的，为什么要用 AOP 和注解？
- 流量控制怎么做的？

#### 面试回答

固定窗口用计数器统计窗口内请求，简单但窗口交界会突发；滑动日志记录最近一段时间的请求，更精确但占用更多内存；滑动窗口计数用分桶近似。令牌桶按速率补充令牌，允许桶容量范围内的突发；漏桶以稳定速率处理，超过容量排队或拒绝。Redis 中要把读取、判断、更新作为原子操作，避免并发请求同时通过。

#### 技术细节

固定窗口可用带时间窗标识的 key，Lua 内执行 INCR 并在首次计数时设置过期；分开调用 INCR 和 EXPIRE 会有中途失败导致无过期的风险。滑动日志用 ZSET：清除窗口外记录、统计、判断并加入唯一请求标识，在一个脚本内完成，时间戳作为 score。令牌桶保存剩余令牌与上次补充时间，按 elapsed × rate 补充并封顶，足够则扣减。漏桶若用于平滑实际流出还需队列与按速率执行的消费者，只有计数判断不会自动平滑下游流量。确定用户／接口等限流维度、时间来源和 Redis 故障时策略；Lua 原子执行不等于故障切换后配额绝不丢失。Redis Cluster 中脚本涉及的多 key 应在同一槽。

2. **为什么要用 AOP 和注解实现限流，有哪些作用？**（面经实际出现；[[面经/京东健康/一面/0001#Q10：限流部分怎么实现的，为什么要用 AOP 和注解，有哪些作用？|MJ018 · 京东健康 · 一面 · Q10]]）

### REDIS-005：Redis 的过期删除与内存淘汰策略有什么区别？

**常见问法**

- Redis 的过期淘汰策略是什么？
- Redis 如何删除过期 key，内存满了又如何处理？
- Redis 有哪些常用的淘汰算法？

#### 面试回答

过期删除与内存淘汰是两套机制。key 超过 TTL 后，Redis 会在访问时惰性删除，并周期性抽样执行主动过期；这处理的是已经到期的数据。内存淘汰是在数据集达到 `maxmemory` 后，按 `maxmemory-policy` 选择 key 腾出空间；策略包括不淘汰、对所有 key 或仅带 TTL 的 key 使用 LRU、LFU、随机淘汰，以及优先淘汰剩余 TTL 较短的 key。

#### 技术细节

惰性删除保证访问到期 key 时不返回旧值，但永不再访问的过期 key 仍需主动周期清理。主动过期采用抽样并自适应继续扫描，在延迟与清理速度间取舍，不是到期瞬间遍历全部 key。TTL 以绝对时间信息持久化；系统时钟异常会影响过期判断。

内存策略通过 `maxmemory-policy` 配置：`noeviction` 在需要增加数据时返回错误；常见的 `allkeys-lru`、`allkeys-lfu`、`allkeys-random` 面向全部 key；相应 `volatile-*` 只从设置了 TTL 的 key 中选择，另有 `volatile-ttl`。当前官方文档还列出 LRM（least recently modified）策略，部署是否支持需按具体版本确认。LRU 与 LFU 使用近似采样实现，不应描述成维护所有 key 的精确全局链表。若用 Redis 作为纯缓存，常评估 `allkeys-lru` 或 `allkeys-lfu`；若混存不可淘汰状态，需先做数据隔离和容量设计，不能只依赖 `volatile-*` 兜底。

#### 深挖追问

1. **key 到期后是否一定立即释放内存？**（补充练习）

   不一定在到期时刻同步删除；访问时会惰性处理，后台主动过期也会逐步清理。业务读取不会把已过期 key 当有效值返回。

2. **设置了 TTL 就一定不会触发内存淘汰吗？**（补充练习）

   不是。TTL 负责生命周期，达到 `maxmemory` 时仍可能按配置淘汰尚未到期的 key。

### REDIS-006：Redis 分布式锁如何正确加锁、解锁和续期？

**常见问法**

- Redis 分布式锁怎么实现？
- 删除锁为什么校验值并使用 Lua？
- 锁过期但业务未完成怎么办？

- SETNX 的 value 可以随便传吗，有什么要求？

- 分布式场景下锁的死锁、锁超时释放怎么处理？
- SET NX EX 为什么要原子执行？
- 抢到锁的服务线程挂了，一直不释放怎么办？

#### 面试回答

单实例基础实现用 `SET key token NX PX ttl` 原子完成互斥获取与过期设置，token 对每次加锁唯一。释放时先确认当前值仍是自己的 token 再删除，避免旧持有者误删超时后由别人新获得的锁。Redis 8.4 之前通常用 Lua 将比较与删除原子化；8.4 起可使用官方提供的条件删除能力。TTL 应覆盖常见执行时间并留余量，但锁只是有时限的租约，不是业务进程存活期间永久有效。

#### 技术细节

`GET` 后再 `DEL` 是两条命令，中间锁可能过期并被别人获得，因此必须原子比较删除。业务时间不可预测时，可由看门狗在确认 token 匹配后续期，并限制续期次数、记录失败；长时间 GC 暂停、进程失联或网络分区仍可能让旧持有者在失锁后继续操作。对数据库等关键资源使用单调递增 fencing token 或资源版本，在资源侧拒绝旧持有者；否则即使锁服务判断已有新持有者，也阻止不了旧进程提交。

Redis 官方说明单实例方案在部分故障下保证有限，多实例 Redlock 也有时钟与故障模型前提。要求严格一致时需明确可接受的故障语义，并评估具备一致性协议与 fencing 的协调服务。无论采用哪种方案，都要设置获取超时、随机退避，并让受保护操作自身尽量幂等。

#### 深挖追问

1. **为什么删除锁要校验值？**（面经实际出现；[[面经/字节/一面/0001#Q17：Redis 分布式锁如何实现，过期与解锁有哪些风险？|MJ011 · 字节 · 一面 · Q17]]）

   防止客户端在自己的锁已过期后误删另一客户端重新获得的锁。

2. **为什么用 Lua？**（面经实际出现；同上来源）

   在 Redis 8.4 之前用脚本把读取、比较和删除作为一次原子执行，消除命令间竞态；应按部署版本说明条件删除新命令是否可用。

3. **锁过期但业务未完成怎么办？**（面经实际出现；同上来源）

   可有限续期并在资源侧使用 fencing／版本校验；不能只延长一个固定 TTL 后假定永不失锁。

### REDIS-007：Redis 如何组织键值数据，逻辑类型与内部编码有什么区别？

**常见问法**

- Redis 里面的数据是怎么存的？
- Redis 的数据类型和底层结构是什么关系？

#### 面试回答

Redis 在逻辑上维护 key 到值对象的映射，key 是二进制安全的字节序列，value 对外呈现 String、List、Hash、Set、Sorted Set 和 Stream 等逻辑类型。逻辑类型决定可用命令和语义；内部编码是 Redis 根据值的大小与内容选择的内存表示，用于权衡空间和操作效率，达到阈值时可自动转换，不改变对外命令语义。当前 key 的实际编码可用 `OBJECT ENCODING key` 查看。

#### 技术细节

以官方当前文档为准：String 可为 `int`、`embstr` 或 `raw`；List 在 Redis 7.0 起的小值编码为 listpack，通用表示为由 listpack 组成的 quicklist；Set 可用 intset、hashtable，Redis 7.2 起还可对小集合使用 listpack；Hash 可用 listpack 或 hashtable；Sorted Set 可用 listpack 或 skiplist 编码；Stream 使用基数树组织 listpack。Redis 6.2 及更旧版本中，小 List／Hash／Sorted Set 可见 ziplist，因此不能脱离版本背诵唯一结构。

键空间映射、过期信息、内存值结构与持久化是不同层次。RDB 将某个时点的数据集写入快照，AOF 记录可用于重建状态的写操作；它们解决重启恢复，不等于内存中的逻辑类型或编码。紧凑编码转为通用编码的具体阈值受版本和配置影响，应查部署配置而不硬背数字。

#### 深挖追问

1. **为什么同一个 Hash 会有不同内部编码？**（补充练习）

   小 Hash 用紧凑结构节省指针和分配开销；当元素数或值大小超过配置条件时，转为通用结构以维持操作性能。

2. **RDB 和 AOF 是 Redis 的数据结构吗？**（补充练习）

   不是。它们是持久化与恢复机制；值的逻辑类型和内存编码是另一层概念。

### REDIS-008：Redisson 解决了什么问题，底层是怎么实现的？

**常见问法**

- Redisson 解决了什么问题，它的底层是怎么实现的？
- Redisson 分布式锁底层如何实现，看门狗怎么续期？

#### 面试回答

手写 Redis 分布式锁要自己处理加锁解锁的原子性、校验持有者防误删、过期续期、可重入计数和等锁方式，命令拆开就有竞态窗口。Redisson 把锁、读写锁、信号量、闭锁、限流器等分布式协调原语封装成 Java 对象，这些边界都有经过设计的实现，应用不再逐条处理。底层核心三件事：所有状态变更用 Lua 脚本在 Redis 内原子执行；可重入锁用 Hash 存状态——field 是客户端加线程标识，value 是重入次数；对未指定过期时间的锁由看门狗自动续期，等锁的客户端订阅解锁通知再竞争而不是纯轮询。

#### 技术细节

以 RLock 为例：锁 key 对应一个 Redis Hash，field 形如「客户端 UUID:线程 ID」，value 为重入次数；加锁脚本一次完成「不存在则创建、同线程则递增、他人持有则返回剩余 TTL」，解锁脚本校验 field 后递减、归零才删除，因此不需要应用自己拼 GET＋SET。默认锁租约 `lockWatchdogTimeout` 为 30 秒：调用 `lock()` 不带 leaseTime 时后台约每 1/3 租约（约 10 秒）续期一次；客户端进程崩溃则停止续期，锁到期自动释放，不会永久锁死资源——长时间 GC 停顿或网络失联仍可能失锁，关键资源仍需 fencing token（见 [[专题题库/Redis#REDIS-006：Redis 分布式锁如何正确加锁、解锁和续期？|REDIS-006：Redis 分布式锁如何正确加锁、解锁和续期？]]）。等锁实现是订阅该锁的解锁通知频道，收到消息后再尝试获取，配合超时退避，降低轮询开销。除锁外还提供 Redis 之上的对象与集合抽象（Map、Bloom filter、RateLimiter、分布式对象服务等），所以它解决的是「用 Redis 做分布式协调」的通用问题，锁只是最常用部分。默认值、续期周期和脚本语义以所用版本文档为准。

#### 深挖追问

1. **Redisson 相比自己写 SETNX＋Lua 锁强在哪？**（面经实际出现；[[面经/字节/一面/0004#Q01：Redisson 解决了什么问题，底层是怎么实现的？|MJ014 · 字节 · 一面 · Q01]]）

   原子脚本、可重入、看门狗续期、基于订阅通知的等锁、公平锁／读写锁／RedLock 等实现都内置且经过测试；手写方案要自己覆盖误删、过期、重入、等待风暴等全部边界。

2. **客户端宕机后没解锁的锁怎么办？**（补充练习）

   带 leaseTime 到期自动释放；看门狗模式约 30 秒内失效（默认值可配），因为进程死后无人续期。恢复快的业务应显式指定较短 leaseTime。

3. **看门狗续期能保证锁永不丢吗？**（补充练习）

   不能。STW 停顿超过续期周期、与 Redis 网络中断仍会失锁，旧持有者可能在失锁后继续操作，故副作用操作仍需幂等或资源侧版本校验。

### REDIS-009：需要缓存的数据特别大（big value）怎么办？

**常见问法**

- 需要缓存的数据特别大怎么办？

#### 面试回答

先分清是“单个值大”还是“总量大”。单值大（big value）：按字段或 hash 分片拆成多个 key 并行读写；换紧凑序列化（protobuf／kryo 替代 JSON 字符串）或压缩后存储；内容大到不适合放 Redis 时外置到对象存储/数据库，Redis 只缓存引用与元数据；读取侧按分片或字段拉取，不做整块搬运。总量大：只缓存热子集＋TTL 淘汰，叠加本地缓存分级，冷数据回源限流。还要能讲危害：大 value 让单线程的命令传输与复制时间变长、RT 抖动、集群内存与流量不均、带宽打满；改完用 `redis-cli --bigkeys`／`MEMORY USAGE`／RDB 分析工具验证。多大算“特别大”与具体拆法按【项目实际】给数。

#### 技术细节

经验口径常把 value 超过 10KB 级、集合元素上万的 key 列为候选（阈值随版本与部署评估，不背死数字）。危害机制：命令执行虽单线程，大 value 的读写、主从 repl 与 AOF 重写都会放大长尾；集群下大 key 所在分片承担不成比例的流量与内存，易成瓶颈甚至 OOM；`DEL` 大 key 阻塞明显，用 `UNLINK` 异步回收。拆分设计要保证同一次业务读能聚齐分片（编号规则或索引结构），并整组设置相近 TTL 防半新半旧；压缩要在 CPU 与网络之间权衡，热点小 value 未必值得。删除“大而全”缓存改“按需子集”时，回源放大风险交给限流与预热对冲（击穿类缓解见 [[#REDIS-002：缓存穿透是什么，布隆过滤器能完全解决吗？|REDIS-002：缓存穿透与击穿]]）。与本地缓存的分工：大对象只放一层（本地或 Redis），层层复制大 value 会把带宽问题翻倍。

#### 深挖追问

1. **热点 key（big 不一定是热点）和 big value 的处理有什么不同？**（补充练习）

   热点 key 解决“访问集中”：多级缓存、本地副本、拆键分摊请求；big value 解决“搬运与内存放大”：拆分、压缩、外置引用。一个 key 可以既大又热，两路措施要同时上。

### REDIS-010：什么是热 Key，为什么危险，如何探测与解决？

**常见问法**

- 高并发场景下“热 Key”问题会对系统产生什么影响？怎么解决？
- 单个商品详情被疯狂访问，Redis 集群明明还有余量却延迟飙升，为什么？

#### 面试回答

热 Key 是某个 key 的访问量远超其它 key，典型来源是秒杀商品详情、爆款内容、活动配置、全局开关。危险点不在数据大而在访问集中：Redis 单线程执行命令，Cluster 又按 slot 分片，一个 key 只能落在一个分片上，于是该分片的 CPU／网卡／连接被打满，表现为集群整体 QPS 不高但这个节点延迟飙升、同节点其它 key 被拖慢；其次是失效重建风暴——过期瞬间大量请求穿透到数据库形成级联雪崩；写热 key 同理，单 key 或数据库单行的写会串行化并放大锁竞争。解决按“探测→分摊→下沉”三层：探测靠监控与统计（客户端埋点、`redis-cli --hotkeys`／`--bigkeys` 采样、云托管的热 key 分析），先分清读热还是写热；分摊靠多级缓存（把热数据放进应用进程本地缓存，用短 TTL＋异步刷新容忍短暂陈旧，这是最有效的一招）、拆 key 打散（`key#0..N` 随机后缀让请求散到不同分片）、只读副本与多副本 key 分摊读；下沉与兜底靠逻辑过期或互斥重建防击穿、请求合并（singleflight）、活动前预热、写热用攒批或异步队列合并写。必须补一句代价：本地缓存换来一致性窗口，多级缓存就要配套失效广播（见 [[专题题库/系统设计#SYS-009：多级缓存如何保持一致，并在 Redis 故障时降级？|SYS-009：多级缓存如何保持一致]]），不能只说“加个本地缓存”。

#### 技术细节

读热的机制成因：Redis 命令执行单线程（网络 I/O 多线程在 6.0 之后，但命令执行仍串行），所以同一 key 的访问无法靠并行摊平；Cluster 按 key 的 CRC16 槽位分片，热点天然无法分散，倾斜分片先饱和——这与 big value 落在同一分片是两类问题（[[#REDIS-009：需要缓存的数据特别大（big value）怎么办？|REDIS-009：big value 怎么办]]：一个解决“访问集中”，一个解决“搬运与内存放大”，同一 key 可以既大又热，两路措施要同时上）。

拆 key 的做法与约束：把详情／库存拆成 N 份并让客户端随机选后缀，读侧分摊有效，但要求业务能接受“聚合多份结果”（库存类要汇总判断余量），且写侧要一次更新所有分片，否则出现分片间不一致；副本 key（`key#replica-i`）由同一份数据多写，读时随机选一份，代价仍是写放大。逻辑过期与互斥重建的取舍：逻辑过期把重建从请求路径移到后台，延迟平稳但会读到旧值；互斥锁保证只回源一次但有等待与锁失效风险（与 [[#REDIS-006：Redis 分布式锁如何正确加锁、解锁和续期？|REDIS-006：分布式锁]] 的失效边界同源），穿透类背景见 [[#REDIS-002：缓存穿透是什么，布隆过滤器能完全解决吗？|REDIS-002：缓存穿透]]。

写热的处理思路不同：合并写（本地攒批后一次写回）、把“计数”类写改成按分片计数再汇总、或用消息队列异步落库；纯缓存手段对写热基本无效。多活／同城容灾场景下还可把只读热数据下沉到就近机房或 CDN 边缘，进一步减少跨网络往返。探测的实操口径：按 QPS Top-N 统计 key（网关或客户端埋点最准）、Redis 侧 `INFO commandstats`／慢日志与云监控的热 key 报表辅助，`MONITOR` 只能在低峰短时用，自身就是性能杀手。

#### 深挖追问

1. **热 Key 和大 Key 是一回事吗？**（补充练习）

   不是。大 Key 的问题是单次操作搬运量大、阻塞与内存不均；热 Key 的问题是访问集中导致单分片饱和。识别指标也不同：一个看 value 体积与元素数，一个看 QPS 倾斜。

2. **加了本地缓存后数据不一致怎么办？**（补充练习）

   先明确可容忍的陈旧窗口：热 Key 场景通常是秒级；再用短 TTL＋异步刷新、变更时广播失效（消息或 Redis keyspace／自研通知）、必要时给关键判定（库存、权限）保留服务端强校验。

3. **拆 key 分摊会带来什么新问题？**（面经实际出现；[[面经/阿里国际/一面/0001#Q05：高并发场景下热 Key 问题会对系统产生什么影响，怎么解决？|MJ038 · 阿里国际 · 一面 · Q05]] 的延伸）

   写放大与一致性：更新要覆盖全部分片或副本；汇总类语义（总余量、排名）需要在应用层聚合，逻辑变复杂。所以拆 key 常与本地缓存组合使用，而不是单独用。
