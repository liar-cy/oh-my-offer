### WEBSEC-001：CSRF 和 XSS 有什么区别，如何防御？

**常见问法**

- CSRF 和 XSS 有什么区别，如何防御？

- 什么是 XSS 攻击，如何防御？

#### 面试回答

先记一句区别：XSS 是“代码被执行”，CSRF 是“请求被冒用”。

- XSS：不可信的内容被当成脚本，在受害站点的上下文里执行。
- CSRF：诱导一个已登录的浏览器，带着会自动携带的凭证去发本意之外的请求。

防 XSS：

- 按上下文分别正确编码：HTML、属性、URL、脚本各自的编码规则不一样。
- 用安全的 DOM API，富文本交给可信的清洗器。
- 再配合 CSP（Content-Security-Policy，内容安全策略）兜底。

防 CSRF：

- 状态修改的请求要校验 CSRF Token。
- 结合 Origin／Referer 校验和 SameSite Cookie。
- 不要用 GET 去执行状态修改。

#### 技术细节

**XSS 的三种形态**

- 反射型、存储型、DOM 型。
- 只过滤 `script` 字符串这种关键字不可靠；要避免的是危险的插入点本身。

**HttpOnly 的边界**

- 它能降低 Cookie 被脚本直接读取的风险。
- 但阻止不了恶意脚本代用户发请求。

**CSRF Token 的要点**

- Token 要与会话绑定、不可预测，并且由服务端验证。
- 也可以按部署情况改用签名的双提交方案。

**两个容易说错的地方**

- CORS 不是通用的 CSRF 防线：跨站请求可能已经发出去了，只是浏览器读不到响应。
- XSS 一旦成立，很多 CSRF 防御都会被绕掉，所以两者要同时处理。

#### 深挖追问

1. **两种攻击的防御重点分别是什么？**（面经实际出现；[[面经/百度/一面/0003#Q14：CSRF 和 XSS 有什么区别，如何防御？|MJ006 · 百度 · 一面 · Q14]]）

   各一句：

   - XSS：让不可信输入始终只作为数据出现，不被当成代码执行。
   - CSRF：要证明状态修改的请求确实来自用户的合法交互，并约束浏览器自动携带凭证的跨站使用。

### WEBSEC-002：密码如何安全存储，常见方案有哪些问题？

**常见问法**

- 密码的加密存储用的什么方案？可能有哪些问题？有没有更优的方案？
- 对用户的密码进行加密存储，那用户忘记密码了怎么办？为什么选 MD5＋盐？登录时怎么判断输入的密码正确？
- 项目中 MD5＋盐主要解决什么问题？
- 当前的密码存储方式，拿到数据库权限能否破解出用户密码？

#### 面试回答

先纠口径：密码不是“加密存储”，而是“哈希存储”——系统根本不需要还原密码。可逆加密方案（AES 等）一旦密钥泄露就是全量明文暴露，应直接否定。

- 基础线：慢哈希＋每个用户一把随机盐，例如 BCrypt（cost 可调）。
- 不够用：裸 MD5／SHA，即使加盐也能被 GPU 高速离线爆破，只是成本略高。
- 更优：Argon2id（内存硬函数，对 GPU／ASIC 更不友好，是当前 OWASP 推荐）、scrypt。
- 工程上再叠几层：登录限流与失败锁定防在线爆破；服务端 pepper 或用 KMS 保护；算法与 cost 要能随硬件进步升级；再配合泄露口令库检测。
- 项目里实际用了什么，按【真实实现】说明。

#### 技术细节

**盐和 pepper 各管什么**

- 盐要随机、唯一，并且和哈希一起存储。作用是让彩虹表失效，同时保证同一个密码得到不同的哈希。
- pepper 是整个服务端的秘密，可以加在哈希前面或后面；要额外管理它的泄露风险和轮换。

**慢哈希的成本怎么定**

- 迭代次数、内存这些成本参数，一般压到单次验证约百毫秒量级。
- 原理是：攻击者离线爆破的总代价被放大，而正常登录的体验还能接受。

**存量哈希怎么升级（Spring Security）**

- `PasswordEncoder` 支持 `DelegatingPasswordEncoder`：按前缀识别旧算法的哈希。
- 用户下次登录或改密时渐进升级成最新算法，避免一刀切地强制重置。

**两道容易跑偏的边界**

- 哈希防不了弱口令本身；强度校验和撞库检测是另一层。
- 本题问的是存储。登录态保持（Cookie／Token）是另一个话题，不要混答成 HTTPS 传输加密。

#### 深挖追问

1. **密码是“加密存储”的，用户把密码忘了怎么办？**（面经实际出现；[[面经/腾讯/一面/0001#Q03：密码加密存储后用户忘记了怎么办？为什么选 MD5＋盐？登录时怎么校验密码正确？|MJ046 · 腾讯 · 一面 · Q03]]）

   没有“找回”，只有重置：哈希单向，系统本来就不该能还原明文——保留可还原能力，等于把一把能全量泄露的钥匙留在手里。

   - 标准流程：短信／邮箱等已有凭据验身份 → 发一次性有效（限时、单次）的重置链接 → 设新密码，同时更新盐与哈希 → 使旧密码哈希之外的旧登录态全部失效。
   - 若被反问“为什么不做成可解密直接告诉用户”：展示明文口令本身就是反模式，等于承认存储可还原。

2. **为什么选 MD5＋盐？登录时怎么判断输入的密码对？**（面经实际出现；[[面经/腾讯/一面/0001#Q03：密码加密存储后用户忘记了怎么办？为什么选 MD5＋盐？登录时怎么校验密码正确？|MJ046 · 腾讯 · 一面 · Q03]]）

   答题先承认它“对的一半”再给不足：

   - 对的一半：盐随机唯一、随哈希记录一起存，让同密码产生不同哈希，彩虹表失效。
   - 不足的一半：MD5 太快了——攻击者拿到库后 GPU 每秒可算海量候选，盐只提高“逐用户”成本，挡不住离线暴力；所以现代口径换慢哈希 BCrypt／scrypt／Argon2id，再配登录限流与失败锁定。
   - 校验流程：按用户 ID 取存储记录（盐＋哈希）→ 用同一算法重算 `hash(输入密码＋盐)` → 与存储哈希做等时比较（防时序侧信道）→ 通过才签发登录态；算法或 cost 升级过的账号，登录成功瞬间顺手重哈希迁移（见上文 DelegatingPasswordEncoder）。

3. **“有了数据库权限，能不能把用户密码破解出来？”**（面经实际出现；[[面经/收钱吧/一面/0001#Q05：当前的密码存储方式，拿到数据库权限能否破解出用户密码？|MJ068 · 收钱吧 · 一面 · Q05]]）

   如实分开两件事：哈希不可逆，谈不上“还原”；能做的只有离线爆破，成败取决于口令强度与哈希速度。

   - 现实威胁：字典＋规则变异、GPU 穷举；MD5／SHA 这类快哈希，加盐只挡住彩虹表与跨用户批量命中，挡不住对单个弱口令的高速尝试。
   - 把成本抬上去：慢哈希（BCrypt cost、Argon2id 内存硬）、登录限流与失败锁定、强度校验与泄露口令库拦截、pepper／KMS 让拖库不等于拿到全部秘密。
   - 口径建议：承认现状再给迁移路径（DelegatingPasswordEncoder 渐进升级），比声称“我们很安全”可信。

### WEBSEC-003：跨域问题是什么，CORS 怎么解决？

**常见问法**

- 跨域问题怎么解决？

#### 面试回答

跨域是浏览器同源策略带来的限制。先纠正一个常见误解：请求其实已经发出去了，是浏览器拦下了响应，服务端的 401／302 照常发生。

- 什么算跨域：协议、域名、端口，任一项不同就是跨域。
- 标准解法是 CORS：服务端在响应头里声明许可，`Access-Control-Allow-Origin` 指定允许的来源。
- 非简单请求（自定义头、PUT／DELETE、常见的 JSON POST）浏览器会先发 OPTIONS 预检；服务端要应答允许的方法和头，还可以用 `Max-Age` 缓存预检结果。
- 要带 Cookie 的跨域（`credentials: include`）：Origin 必须是明确的值、不能是 `*`，服务端还要回 `Allow-Credentials: true`；这种情况要和 CSRF 防护一起设计。
- 开发期的代理（devServer／Nginx 转发）是同域化的绕过手段，不是生产方案；JSONP 只支持 GET，已基本淘汰。

#### 技术细节

**预检有没有，取决于是不是简单请求**

- 判定看方法和请求头的白名单。
- 排障时“GET 能通、POST 报 CORS”，多半是预检没过或者 `Allow-Headers` 没配。

**通配与凭据互斥**

- `Allow-Origin: *` 与凭据模式不能一起用。
- 要放行一组子域，回的必须是一个具体的 Origin。服务端动态回显前先校验白名单，随意回显等于把防护关掉。

**报错位置容易看错**

- 响应里缺 CORS 头时，浏览器控制台会报错，但 Network 里能看到响应。定位时别被“请求失败”这个说法误导。

**其他各自有细节的场景**

- 字体、`window.open` 之后的引用、iframe 都不一样；iframe 另外受 `frame-ancestors`／`X-Frame-Options` 约束。

**在哪里统一加头**

- 用服务端框架的 `CorsFilter` 或在网关统一加头，适合集中治理。
- 注意别和 Nginx 层重复添加，头里出现多个值会让浏览器报错。

#### 深挖追问

1. **同主域不同子域（a.example.com 调 b.example.com）还要 CORS 吗？**（补充练习）

   仍然是跨域，接口照样需要 CORS。另外两件事分开处理：

   - 共享 Cookie：可以用 domain 收窄 Cookie 的作用域，这是老办法。
   - 页面之间通信：用 postMessage。
   - 接口层：还是走 CORS，或者在网关做同域化。

### WEBSEC-004：如何用 JWT 完成用户认证？改密后如何让旧令牌失效？

**常见问法**

- 讲一下项目中使用 JWT 令牌完成用户认证的整体过程。
- 用户在后端修改了密码，如何让他之前的一些 JWT 令牌失效？

#### 面试回答

认证流程分五步说：

- 登录：服务端校验凭据，密码是 bcrypt 一类的哈希（见 WEBSEC-002）。
- 签发：通过后生成 JWT，结构是 `Base64Url(header).Base64Url(payload).signature`；payload 里放 sub（用户 ID）、iat／exp 这些声明。
- 签名：用服务端密钥 HMAC（HS256，单体应用），或者非对称私钥（RS256，多服务／开放平台，公钥经 JWKS 分发），签的是前两段。
- 携带与校验：返回客户端保存，请求时放 `Authorization: Bearer <token>`；网关或拦截器逐请求验签、校验 exp／iss／aud，通过后把 userId 注入上下文，不再查会话表。
- 续期：过期前用 refresh token 换新的 access token。

一句评价：JWT 的价值是无状态、可横向扩展、多服务之间免共享会话；代价是“签发即有效、撤销不即时”。这正好引出第二问。

改密后让旧令牌失效，我给三个由轻到重的方案：

- 给 access token 很短的有效期（分钟级），让旧令牌自然过期；同时改密时撤销全部 refresh token。
- 在用户记录上维护 token 版本号，或者用 `password_changed_at` 声明：签发时写进去，验签后再比对该值 —— 改密就整体失效。
- 在 Redis 维护 jti 黑名单／白名单，改密时让所有会话失效。精确，但引入了状态，等于部分回到 Session。

按项目真实约束选：内部管理后台用黑名单，C 端高并发用短有效期＋版本号。

#### 技术细节

**令牌里能放什么**

- 签名不是加密：payload 只是 Base64Url 编码，不是密文，任何人都能解码。
- 所以敏感信息不能放进去，比如手机号、权限明细。
- 权限要么放服务端，要么放 claim，但每次都以服务端为准刷新。

**校验必须显式固定算法**

- 拒绝 `alg: none`，不要信任 header 里写的算法字段。
- 否则会被算法混淆攻击：拿公钥当成 HMAC 的密钥来伪造令牌。
- 校验顺序：验签 → 时间 → iss／aud → 业务版本。

**存哪里取决于威胁模型**

- localStorage：没有 CSRF 的问题，但 XSS 一上来就直接把令牌偷走。
- HttpOnly＋SameSite 的 Cookie：XSS 读不到，但要配 CSRF 防护（见 WEBSEC-001），还得处理 CORS 的 credentials（见 WEBSEC-003）。

**撤销方案要算规模账**

- 黑名单的容量和 access token 的 TTL 成正比：TTL 60s 的令牌，jti 只需要存 60s。所以“用短 TTL 把黑名单压到可忽略”是标准组合拳。
- 版本号方案的代价是每次验签多读一次用户记录。可以靠本地缓存，或者把版本塞进令牌、再低频核对来摊薄。

**改密、踢人时要同步做的三件事**

- 更新密码哈希、撤销 refresh 链、（按需）失效记住登录的设备表。
- 常见漏答是只讲令牌层、不讲 refresh：攻击者真正用来续命的是 refresh token。

#### 深挖追问

1. **JWT 放 Cookie 还是 localStorage？**（补充练习）

   看威胁模型：怕 XSS 偷令牌就放 HttpOnly Cookie，同时把 CSRF 防护补上；纯 API 或移动端就放安全存储里携带。CSRF 这一侧可以用 SameSite（Strict）或者双提交 token 来缓解。

2. **无状态 JWT 怎么做“单点登录互踢”？**（补充练习）

   纯自包含的令牌做不到实时互踢，必须落到服务端状态：把每个用户当前有效的会话 ID（jti）白名单放 Redis，验签之后再比对。版本号方案则天然能实现“新登录作废旧版本”。

3. **payload 里的 exp 到了，正在处理的长请求会怎样？**（补充练习）

   认证只发生在请求入口，所以进入业务逻辑后令牌过期，不影响这个请求跑完。要注意的是流式或异步任务：如果中途还要再鉴权，看的是续期后的凭证；别把访问校验埋在任务中间，才想起来令牌已经过期。

### WEBSEC-005：微信扫码登录的完整流程与原理是什么？

**常见问法**

- 请详细说明微信扫码登录的完整流程和背后发生的原理。
- PC 上没有登录，手机扫一下码是怎么让 PC 登录上的？
- 二维码登录为什么不会被别人冒用？

#### 面试回答

先立住关键前提：PC 端是未登录的，手机 App 上已经有登录态。所以扫码登录的本质是“让已认证的一端，替未认证的一端完成一次身份授权”，而不是把账号凭据在两端之间传。实现这个前提的是一张票据（ticket／二维码 ID）的状态机：待扫码 → 已扫码待确认 → 已确认 → 已消费。状态存在服务端（通常是带 TTL 的 Redis），两端都只向服务端读写这个状态。

完整流程六步：

- PC 打开登录页，向后端申请二维码。后端生成一个随机不可猜、一次性、短有效期（60～120 秒）的 ticket，把指向 H5 确认页的 URL（含 ticket 与业务参数）编码成二维码返回给 PC 展示。
- PC 开始查状态：最简是带 ticket 的短轮询（1～2 秒一次，配合过期时间停止），也可以用 SSE／WebSocket 让服务端推送。
- 用户用手机 App 扫码。App 携带自身登录态请求服务端，服务端校验域名与参数合法后，把该 ticket 置为“已扫码待确认”；PC 收到状态变化，就显示“已扫码，请在手机上确认”。
- 用户在手机上点确认。服务端把 ticket 置为“已确认”，并绑定当前用户身份。
- PC 感知到已确认后，用 ticket 换一个一次性 code。服务端校验后立即消费该 ticket，并给 PC 签发 PC 侧登录态（`Set-Cookie` 或下发 JWT），前端跳转进入已登录页。
- 二维码过期或用户取消，状态就终止；PC 提示刷新，重新申请。

原理层面的几个要点：

- ticket 是与用户身份解耦的中间凭证：必须随机、短时效、一次性消费，这样被截获也无法复用。
- 确认动作只能由已登录的移动端发起，服务端据此授权；PC 全程接触不到用户凭据。
- `state` 一类参数与固定回调域名，用于防 CSRF 与钓鱼跳转。
- 二维码内容不带任何凭据，并且走 HTTPS。
- 旧令牌与登录态生命周期按 [[#WEBSEC-004：如何用 JWT 完成用户认证？改密后如何让旧令牌失效？|WEBSEC-004]] 的机制控制。

#### 技术细节

**时序上必须点到的三个竞态**

- “确认前 PC 就换来登录态”：不允许。服务端只接受状态为已确认的 ticket，并且换 code 的接口要幂等、一次性。
- “同一 ticket 被重复消费”：用原子的状态流转（CAS 或 Redis 原子命令）保证，只有一个请求能从已确认改成已消费。
- “扫码后不确认／超时”：状态要有 TTL。PC 侧轮询超时后要能刷新新二维码并丢弃旧 ticket，否则会出现旧码被复用。

**安全面还要能补三点**

- 跨站与二维码钓鱼：攻击者把自家登录页的二维码贴出来诱导用户扫，本质是把用户当成授权者。缓解办法是确认页明确显示登录的设备与地理位置信息，并要求用户主动确认。
- App 侧参数篡改：有人改 URL 里的业务参数。服务端不信任二维码参数，只按 ticket 查服务端记录。
- 未登录 App 扫码：给出“请先登录”，而不是让 PC 侧误判失败。

**风控层面可以再加的**

- 新设备或异常 IP 触发二次验证。
- 扫码端与 PC 端地理位置差异过大时提示。
- 异地频繁扫码登录做限流。

**登录态下发环节按端而定**

- Web 用 Cookie（HttpOnly、Secure、SameSite，见 [[专题题库/计算机网络#NET-012：Cookie、Session 和 Token 有什么区别？|NET-012：Cookie、Session 和 Token 有什么区别]]）时，要防会话固定，并在登录后换新会话 ID。
- 下发 JWT，则用短有效期加刷新机制。
- 整条链路里，PC 换 code 那一步等价于一次 OAuth2 风格的授权码交换。把“授权码换令牌”而不是“直接给登录态”作为对外接口，理由是同一套：授权码一次性、可绑定回跳地址、可在服务端审计。

#### 深挖追问

1. **为什么不用手机直接把账号密码传给 PC？**（面经实际出现；[[面经/字节/一面/0009#Q12：请详细说明微信扫码登录的完整流程和背后的原理。|MJ041 · 字节 · 一面 · Q12]] 的延伸）

   那会把长期凭据暴露在跨端通道里，而且限定不了授权范围与时长；一旦 PC 端被控，就等同账号沦陷。票据模型正相反：授权是一次性、短期、可撤销、可审计的，用户身份始终只存在于已认证的移动端。

2. **轮询和长连接推送，这个场景选哪个？**（补充练习）

   两条各有代价：

   - 轮询：实现最简单、对网关友好；代价是每个打开登录页的客户端都要持续发请求，并发量随未登录页面数放大。
   - SSE：省掉重复请求，状态变化也能即时到达；但要处理断线重连与代理缓冲。

   用户量大的产品通常“轮询起步＋超时降频”，或者用长连接。按自家网关能力选，并且能说出各自的负载形态。

3. **PC 已经登录状态下再打开这个页面会怎样？**（补充练习）

   正常实现应该先检测已有登录态、直接跳转，不再申请二维码。如果仍然允许生成，就要保证两点：ticket 与被授权用户绑定；换出的登录态不覆盖更高权限的既有会话。否则就成了“用低信任端覆盖当前会话”。

### WEBSEC-006：什么是 SQL 注入，有哪些防范措施？

**常见问法**

- 什么是 SQL 注入？有哪些防范措施？
- 为什么 `#{}` 能防注入而 `${}` 不能？
- 参数化查询之后还需要做什么？

#### 面试回答

机制只有一句：SQL 注入是攻击者把数据伪装成语句结构提交。拼接 SQL 时，用户输入里的引号、注释符、布尔表达式或 `UNION` 改变了原本的语义，导致越权读、数据篡改甚至命令执行。

- 根因：把不可信输入当成代码来解释。
- 所以修复方向不是“过滤坏字符”，而是让数据永远不以代码的身份进入语句。

典型形态要说得出几种：

- `' or '1'='1` 绕过登录条件。
- `' --` 或 `#` 注释掉后续条件。
- `UNION SELECT` 拖库。
- 报错函数回显库结构。
- 时间盲注（用 `sleep` 判定布尔）与堆叠语句（取决于驱动是否允许多语句）。
- 还有一种容易被忽略的二阶注入：数据先被“安全地”存进库，下次从库里取出拼进 SQL 时才发作。

防范措施按有效性排序：

- 参数化查询／预编译是首选：值始终以绑定参数传递，不进语句文本。ORM 也要用它的参数占位，例如 MyBatis 里 `#{}` 是占位符绑定、`${}` 是字符串直接替换，会引入注入。
- 标识符与结构部分只能靠白名单：表名、列名、`ORDER BY` 方向、分页大小这类没法用占位符表达，必须映射到枚举常量，而不是做转义。
- 输入校验与类型约束：长度、字符集、数值型必须能转成数字。它能缩小攻击面，但不能替代上面两条。
- 最小权限：业务账号不给 DDL、系统表与文件读写权限；只读场景用只读账号；Web 层不用数据库超级用户。
- 减少可利用面：关闭详细错误回显（对外只给错误码与 traceId）、不打印拼接后的完整 SQL 到前端、禁用多语句执行。
- 纵深防御：WAF、SQL 审计与异常流量告警能拦能查，但都存在被绕过的风险，不能作为唯一手段；敏感接口另加限流与二次确认来降低损失。

收口要能自陈边界：“参数化不等于万事大吉”——标识符、`LIKE` 通配符（`%`、`_` 要转义并按需处理）、动态列名与排序位仍要单独处理；二阶注入要靠“取值处同样不拼接”来防。

#### 技术细节

**为什么预编译真的有效**

- 以 `?` 占位符走 prepared statement 时，SQL 的语法结构在服务器解析阶段就固定了。
- 参数只在执行阶段作为“值”填入，永远不参与语法分析。所以引号闭合、注释符这些攻击手法失去意义。
- 一个提醒：各家驱动实现有差异，有的是在客户端拼接完才发送。所以要说得出“用了 ORM／预编译接口”这个事实，而不是笼统讲“我参数化了”。

**常见“伪防护”，要能点名反驳**

- 只过滤单引号或关键字：可用编码、注释切分、大小写与二次拼接绕过。
- 只靠 `addslashes`／字符串转义：字符集与上下文不同时失效，而且完全不管数值型注入。
- 只靠存储过程：内部若仍拼接 SQL，一样有洞。
- 只靠 WAF：可被编码与语义变形绕过，并且不提供最小权限。

**两个能关联起来讲的具体机制**

- MyBatis 的 `${}` 与 `#{}` 差别见 [[专题题库/MyBatis#MYBATIS-001：MyBatis 中 ＃{ } 与 ${ } 有什么区别？|MYBATIS-001：＃{ } 与 ${ } 的区别]]。
- ORM／动态 SQL 生成器（如 MyBatis-Plus 条件构造、JPA Criteria）同样存在“拼接片段”的入口，要用字段白名单接口。

**和 XSS 摆在一起讲最清楚**

- 两者都是“数据被当成代码解释”，只是解释器分别是 SQL 引擎与浏览器。
- 所以防御范式一致：结构化输出（参数化／上下文转义）优先于黑名单过滤（见 [[#WEBSEC-001：CSRF 和 XSS 有什么区别，如何防御？|WEBSEC-001：CSRF 和 XSS 有什么区别，如何防御？]]）。

#### 深挖追问

1. **`${}` 在什么场景下必须用，怎么安全地用？**（面经实际出现；[[面经/字节/一面/0010#Q15：什么是 SQL 注入？有哪些防范措施？|MJ042 · 字节 · 一面 · Q15]] 的延伸）

   结构位置的占位符替代不了：动态表名、列名、排序方向。安全用法是：入参只允许枚举值，服务层做一次白名单映射（前端传 `createTime`→SQL 里写死 `` `create_time` `` 的映射表），映射不到就直接拒绝，绝不把用户字符串塞进 SQL。

2. **怎么验证自己的系统有没有注入点？**（补充练习）

   分两头查：

   - 静态：看是否还存在字符串拼接 SQL 与 `${}`／原生查询入口，靠代码扫描＋grep 关键字。
   - 运行时：在测试环境用 sqlmap 一类工具做授权范围内的验证，同时看日志里有没有出现异常的语法错误。

   核心是建立“不允许手写拼接”的评审红线，而不是一次性扫干净。

3. **ORM 用了是不是就不用担心？**（补充练习）

   不是。ORM 的默认 CRUD 路径通常是参数化的，但“灵活查询”的入口往往是自家人写的拼接：原生 SQL、动态片段、排序字段透传、批量拼接 IN 列表、导出报表。历史上多数实际注入案例就出在这些边缘接口与后台管理功能里。
