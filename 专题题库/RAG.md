### RAG-001：知识库问答系统如何设计？

**常见问法**

- RAG 的流程是什么，如何缓解大模型幻觉？
- 知识库是怎么做的？

- RAG、向量模型和 LLM 幻觉是什么？

- RAG 的概念原理是什么，内容在库里是怎么存储、怎么建的？
- RAG 相比直接使用一个向量数据库，就是多了切块和重排吗？

- 你觉得 RAG 中最难的是什么？
- 文档怎么存的，粒度多大，用的什么数据库？

- 谈谈对 RAG 的理解，你认为它主要解决了哪些问题？

#### 面试回答

RAG 把外部证据检索接入生成。离线解析清洗文档、分块并保留来源，建立向量或关键词索引；在线理解问题、召回、过滤、重排并组装上下文，让模型依据证据作答和引用。缓解幻觉要同时改善证据质量和答案约束：使用可靠且及时的资料，检查检索是否命中，要求结论有证据，证据不足时明确无法回答，并校验引用是否真正支持结论。RAG 能降低幻觉，不能保证消除。检索与引用还需实施权限过滤；项目回答应替换为真实实现与评测结果。

#### 技术细节

分块需保留标题路径、文档 ID、版本、页码、权限及父子块关联，避免答案无法定位。文本、表格和图片应按其结构处理，不能只把所有字符拼起来。检索可采用关键词与向量混合召回，再重排去冗余；权限条件应贯穿召回和关联扩展。评测拆成召回是否命中、证据是否足够、答案是否被支持，分别看 Recall@k、引用正确率、任务成功率、延迟和成本。文档更新要同步清理旧块与失效索引。

补充幻觉评测：把“没检索到正确证据”和“有证据却生成错误”分开测试；准备无答案、过时材料、冲突事实等样本，评估召回、答案忠实度、引用支持率和适当拒答。低温采样只影响随机性，不保证事实正确；模型自评也不能替代可核对的证据与人工抽检。以上是通用工程答题方法，未声称候选人已实现这些措施。

幻觉可表现为不符合外部事实，或不忠实于提供的证据；流畅与高置信措辞都不代表正确。RAG 仍可能因知识过时、召回遗漏、冲突证据或生成偏离而出错，应在检索与生成两段分别评测。

#### 深挖追问

1. **没有检索到证据怎么办？**（补充练习）

   明确证据不足，必要时澄清问题或扩大检索范围，不把模型常识伪装成库内结论。

2. **chunk 越大越好吗？**（补充练习）

   大块保留上下文但降低检索粒度并占用预算；小块定位准确却可能丢关系，可用小块召回、父块补全，并通过评测选大小。

3. **如何缓解 LLM 幻觉？**（面经实际出现；[[面经/百度/一面/0003#Q19：RAG 的流程是什么，如何缓解大模型幻觉？|MJ006 · 百度 · 一面 · Q19]]）

   提高检索证据的相关性、时效性和完整性，让答案逐项对齐证据并校验引用；无证据或证据冲突时拒答或明确不确定，通过针对性评测定位问题。

4. **LLM 幻觉是什么？**（面经实际出现；[[面经/百度/一面/0005#Q21：RAG、向量模型和 LLM 幻觉是什么？|MJ008 · 百度 · 一面 · Q21]]）

   指生成看似合理却与事实或证据不符的内容；检索增强提供证据，但生成仍需核验。

5. **RAG 相比直接用向量数据库，只是多了切块和重排吗？**（面经实际出现；[[面经/字节/一面/0005#Q11：RAG 相比直接使用一个向量数据库，就是多了切块和重排吗？|MJ015 · 字节 · 一面 · Q11]]）

   不是。向量数据库只承担存储与近邻检索；RAG 还包括查询理解与改写、混合召回、权限与元数据过滤、重排去冗余、上下文组装与预算控制、引用约束与拒答，以及离线的数据治理、增量更新和分层评测。切块与重排只是其中两个环节。

6. **PDF 中的插图怎么处理，后续怎么扩展多模态？**（面经实际出现；[[面经/帆软/二面/0001#Q11：PDF 中插图如何处理，后续怎么扩展多模态能力？|MJ023 · 帆软 · 二面 · Q11]]）

   抽出原图并保留页码、位置与所属章节上下文；图内信息按类型走 OCR（文字型）或视觉模型生成描述/结构化数据（流程/示意图），文本化后连同图引用入索引——检索命中文本、展示回源原图，图注与正文绑定不拆开。扩展多模态先建含图任务评测集拿基线，再选支持图像输入的模型或 OCR＋文本模型混合链路，报告含图成功率与信息提取准确率增量；“支持上传”不等于“支持理解”。

7. **对文档的解析做了哪些优化？**（面经实际出现；[[面经/帆软/一面/0002#Q05：对文档的解析做了哪些优化？|MJ027 · 帆软 · 一面 · Q05]]）

   解析质量决定召回上限：版式还原（标题层级、分栏阅读顺序）、表格结构化保存而非拉平成文本、图片 OCR/图注提取并与正文位置绑定、页眉页脚水印等模板元素去噪（按版式位置判定，见 [[专题题库/RAG#RAG-003：PPT 文档如何去噪？|RAG-003：PPT 文档如何去噪？]]）、扫描页判定与低置信标注、按文档类型分管线、保留原文坐标与版本供回溯；每项改动用“有效信息保留率＋检索指标”对照验证，做到哪些按【真实实现】说。

8. **RAG 主要解决了哪些问题？**（面经实际出现；[[面经/小红书/一面/0001#Q09：谈谈对 RAG 的理解，它主要解决了哪些问题？|MJ040 · 小红书 · 一面 · Q09]]）

   四条主线：知识截止与时效（换文档比重训便宜）、私域与长尾知识（模型没见过的内部文档、规范、代码）、幻觉与可追溯（结论要求有证据、能给引用、可审计）、上下文与成本约束（检索把有限窗口聚焦到相关片段，并按权限过滤来源）。同时要说边界：不保证消除幻觉、不提升多跳推理能力（要靠 Agent 式迭代检索）、召回质量是上限——数据治理与评测做不好时，换更强的生成模型也救不回来。

### RAG-002：如何做跨文档关联分析？

**常见问法**

- 怎么做跨文档的关联分析？

#### 面试回答

我会先建立可追溯的关联：文档引用、统一实体 ID、主题、时间和版本等，再根据问题检索种子证据，沿关系补充其他文档并重排，最后按证据逐步合成答案。简单场景可以用元数据和多轮检索，关系复杂时再考虑图结构；只做向量相似检索不等于完成了跨文档推理。

#### 技术细节

以“某功能由谁负责、目前上线情况”为例，可分别检索设计文档中的负责人、发布记录中的版本及日期，再用功能 ID 关联。实体消歧要处理同名系统、部门别名和版本差异。关联边保留出处及置信信息，避免模型抽取错误被当作事实。限定扩展深度、候选数量与上下文预算；按用户权限过滤所有关联节点。答案中为每项结论保留对应证据，并展示冲突而非盲目融合。

#### 深挖追问

1. **两篇文档互相矛盾怎么办？**（补充练习）

   比较适用范围、版本、时间和来源权威性；无法消解时并列说明，不单凭相似度选择结论。

2. **为什么不直接拼接所有文档？**（补充练习）

   会带来上下文超限、冗余和干扰，且难以控制权限和定位证据。先按问题选证据再合成更可评测。

3. **为什么要用到图数据库？**（面经实际出现；[[面经/字节/轮次未知/0001#Q23：为什么要用到图数据库？|MJ021 · 字节 · 轮次未知 · Q23]]）

   当“关系本身是答案的一部分”时图更合适：多跳关联（A 的系统依赖谁、谁负责 B）、实体关系密集、需要沿边取证并展示路径。先问不用图能否解决——关系表＋多轮检索、元数据关联常已够用；上图的代价是实体抽取与消歧质量决定图质量、双写同步与权限维护复杂，不为“看起来高级”而上。

### RAG-003：PPT 文档如何去噪？

**常见问法**

- PPT 文档怎么去噪声？

#### 面试回答

我会结合版式和跨页重复信息去噪：识别页眉页脚、页码和重复模板元素，保留标题层级、正文、表格及图注；扫描页再用 OCR，并检查阅读顺序。规则不能只按“重复就删”，因为标题、业务术语和单位也可能重复，我会抽样对比清洗前后是否丢失有效信息。

#### 技术细节

先提取文本框位置、字体、占位符、页码与母版关系。位于稳定区域且跨多数页面重复的元素可作为噪声候选；图表中的数值、图例、单位及对应标题应组合保存。分栏页面需恢复阅读顺序，避免按 XML 顺序直接拼接。以人工标注小样本评估噪声删除率和有效信息保留率，再比较检索表现。此处描述可选设计，不表示原项目已有这些实现。

#### 深挖追问

1. **重复页标题也要删吗？**（补充练习）

   不应一律删除，标题提供章节语境；可存入元数据，并减少正文中的机械重复。

2. **纯图片的 PPT 怎么办？**（补充练习）

   使用 OCR 或视觉解析，保留页码和布局；低置信结果标注或复核，不能将误识别数值直接入库。

### RAG-004：知识库如何检测重复文档与重复片段？

**常见问法**

- 怎么检测重复？

- 库里面的数据是有重复的吗？

#### 面试回答

我会分层处理：文件哈希判断完全相同的文件；规范化文本后计算哈希识别格式不同但内容相同的材料；近重复用词片段指纹或向量相似度筛候选，再结合差异判断。去重粒度可以是文档、页面或 chunk，但要保留所有来源和版本关系。

#### 技术细节

文本规范化可统一空白和编码，不能粗暴删除数字或单位。MinHash 适合近似集合重合，SimHash 可筛文本指纹相近项，embedding 更偏语义相似；相似不等于相同，版本更新中的一个数字差异也可能关键。对候选比较实体、日期、否定词和数值，再决定合并、保留新版或标注冲突。召回阶段也可按内容簇减少上下文冗余，而不物理删除原有来源。

#### 深挖追问

1. **如何选相似度阈值？**（补充练习）

   在标注的重复／非重复样本上评估误合并和漏检，按文档类型调参，不套固定通用阈值。

2. **同内容但不同权限能合并吗？**（补充练习）

   可以共享内部内容表示，但必须保留独立来源授权，检索和引用不能因此扩大可见范围。

### RAG-005：查询时为什么使用 embedding，如何使用？

**常见问法**

- query 的时候有没有用 embedding？

- RAG、向量模型和 LLM 幻觉是什么？

- 向量检索的原理是什么？
- 哪些信息进行了向量化存储？

- 向量化的原理是什么？embedding 模型是怎么来的，为什么要叫向量？
- embedding 模型使用的是什么？

- Embedding 是什么，你们用的哪个模型？

- RAG 里面的向量化是怎么做的？

#### 面试回答

做向量检索时，我会把 query 用与文档向量兼容的 embedding 模型编码，在相同向量空间检索，再结合关键词召回和重排。embedding 能帮助匹配不同措辞的语义，但不能保证事实正确，专有名词、编号和精确条件通常还需要关键词或结构化过滤。

#### 技术细节

向量索引通常只返回近邻候选，相关性还依赖模型训练域、切块、向量归一化、相似度度量和 ANN 参数。更换模型一般需要重建文档向量，不能只换查询端。多轮对话可先生成独立检索问题，但保留原条件以避免改写漂移。通过包含同义词、缩写、精确编号和跨文档问题的评测集，对比纯关键词、纯向量与混合检索。

向量模型将文本映射为数值向量用于语义相似性计算，区别于直接生成答案的模型；并非任意两个相同维度模型的向量都可比较。应使用同一或明确兼容的查询／文档编码体系，按业务数据评估召回和重排效果。实际模型名称、版本、维度与训练领域应如实说明，不能替候选人指定用过的型号。

向量化对象通常是具有语义检索价值的内容单元，例如标题加正文切片、规范问题与答案摘要，以及图片 OCR／图注等可检索文本；实际项目需逐项说明。文档 ID、租户、权限、版本、时间、语言、来源等保留为结构化 metadata，用于过滤、更新和追溯，不应仅塞入 embedding。订单号等精确标识优先使用关键词或结构化索引。每条向量需关联原文和 embedding 模型版本，内容或模型变化时重建或失效旧向量。

工程化落地的四个要点（被追问“向量化具体怎么做的”时要能答）：① 批处理与吞吐——按模型输入上限切窗、批量编码并做失败重试与限流，本地部署要能报出每秒向量化条数与 GPU 占用；② 归一化与度量——向量归一化后内积即余弦相似度，索引与查询端必须用同一度量，否则分数不可比；③ 索引与参数——ANN 索引（HNSW、IVF 类）在召回率、内存与延迟之间调参，索引选择与向量库选型绑定（见 [[专题题库/RAG#RAG-007：pgvector 与 Qdrant 如何比较和选型？|RAG-007：pgvector 与 Qdrant 如何比较和选型？]]）；④ 增量维护——按内容哈希判断是否需要重算，更新走同一 ID 的 upsert 并同步删除旧向量，删除文档要连带清理其块与向量；换 embedding 模型等于全库重建，需双写灰度后用同一评测集比较召回再切读，不能只换查询端。

#### 深挖追问

1. **每次查询都需要重新生成文档 embedding 吗？**（补充练习）

   不需要，文档向量在入库或更新时生成；查询时通常只编码 query，可按模型版本和权限相关上下文谨慎缓存。

2. **相似度最高就一定正确吗？**（补充练习）

   不是，近邻只代表表示空间接近，还需校验实体、时间、条件及答案证据。

3. **向量模型在 RAG 中做什么？**（面经实际出现；[[面经/百度/一面/0005#Q21：RAG、向量模型和 LLM 幻觉是什么？|MJ008 · 百度 · 一面 · Q21]]）

   编码文档与查询，支持语义召回；它给出相似候选，不能保证候选事实正确。

4. **哪些信息进行了向量化存储？**（面经实际出现；[[面经/字节/一面/0001#Q07：哪些信息进行了向量化存储？|MJ011 · 字节 · 一面 · Q07]]）

   按真实项目列出用于语义召回的文本单元；精确标识、权限和版本等另存结构化字段，并保留向量到原文的映射。

5. **向量化的原理是什么，embedding 模型怎么来的，为什么叫向量？**（面经实际出现；[[面经/字节/一面/0005#Q08：向量化的原理是什么？embedding 模型是怎么来的，为什么要叫向量？|MJ015 · 字节 · 一面 · Q08]]）

   embedding 模型在大规模语料上以对比学习等方式训练：语义相近的文本对被拉近、无关对被推远，文本经编码器输出固定维度的实数数组，各维度是学到的隐式特征，不存在“第 N 维＝某含义”的人工定义；称“向量”只因它是方向与幅度均有意义的数值数组，可用余弦相似度等度量。模型来自商用 API 或开源部署，是否领域微调按项目说明。

6. **RAG 里面的向量化是怎么做的？**（面经实际出现；[[面经/阿里国际/二面/0001#Q07：RAG 里面的向量化是怎么做的？|MJ038 · 阿里国际 · 二面 · Q07]]）

   按“选模型→决定向量化什么→入库工程化→检索与更新”四步答，模型名称、维度、批量与索引参数按【真实实现】填：选型看业务语言、维度、token 上限、成本与是否私有化，最终以自己评测集上的召回定；语义单元（标题路径＋正文切片）入向量，精确标识与权限版本留 metadata；批量编码控吞吐与重试、归一化后统一度量、ANN 索引调召回—延迟权衡；内容与模型变更都要重建或失效旧向量，换模型基本等于全库重建。

### RAG-006：如何设计垂直业务 RAG 路由与多 Agent 知识库复用？

**常见问法**

- RAG 仅接收关键词或业务单号，如何路由知识库并供多个业务 Agent 复用？

#### 面试回答

项目实际实现需要填写【调用身份来源、业务映射、知识库划分、检索策略】。如果让我设计，业务单号先经过鉴权，再查询业务系统确定租户、模块和文档范围；关键词结合调用方已授权的业务上下文确定候选库，再做关键词与向量混合检索、重排。多个 Agent 可以复用同一套检索服务和接口契约，通过服务端配置选择知识域与权限范围；复用接口不要求所有模块混用同一个物理库。如果除了关键词外没有任何身份或业务上下文，又存在同名业务，就无法保证唯一匹配，需要补充上下文或返回歧义。

#### 技术细节

单号是精确标识，优先结构化查询，不能仅用 embedding 找近似单号。外部参数少不代表内部条件少：网关认证信息、服务凭据和服务端配置可提供身份，但不能信任调用者随意声明的 tenant_id。建议建立“业务类型／模块 → 知识集合、过滤规则、检索配置”的映射，文档元数据携带租户、模块、实体 ID、版本和访问范围。Qdrant 可用 payload 条件过滤，过滤表达式本身并不代替授权。路由置信度低时澄清；记录命中库、引用和无结果原因，用带业务标签的评测集检查跨库误召回。不同 embedding 模型的向量不能直接放入同一搜索空间比较。

#### 深挖追问

1. **同业务线各模块的 Agent 是否复用一套 RAG 接口？**（面经实际出现；[[面经/百度/一面/0002#Q01：RAG 仅接收关键词或业务单号，如何路由知识库并供多个业务 Agent 复用？|MJ005 · 百度 · 一面 · Q01]]）

   可以复用服务能力，模块配置、权限和知识生命周期分别管理；存在不同保密边界、模型或资源隔离要求时分集合或分实例，调用契约仍可统一。

2. **如何避免缓存答案串租户？**（补充练习）

   缓存键和命中校验纳入权限范围、业务域与知识版本；同一关键词并不代表相同可见证据。

### RAG-007：pgvector 与 Qdrant 如何比较和选型？

**常见问法**

- pgvector 与 Qdrant 有什么区别？

- 向量数据库对比做过吗，Qdrant 性能、量级和瓶颈如何？

- 项目的向量库分层设计，选型原因？

- 项目为什么选择 PGVector 而不是 ES 来做向量数据库，ES 可以吗？

#### 面试回答

pgvector 是 PostgreSQL 的向量扩展，便于把向量与业务表放在一起，用 SQL、关联查询和数据库事务处理；Qdrant 是专门的向量检索服务，围绕向量、payload 过滤及检索 API 组织数据。已有 PostgreSQL、关系查询和事务协同需求强时可以先评估 pgvector；希望独立管理向量服务时可以评估 Qdrant。最终要在相同数据、召回率和过滤条件下比较延迟、资源与运维成本，不能仅凭产品类型断言谁更快。

#### 技术细节

pgvector 支持精确检索以及 HNSW、IVFFlat 近似索引。ANN 与过滤组合时可能返回不足 k 条；0.8.0 起支持迭代索引扫描，可继续寻找候选，但仍受扫描上限约束。Qdrant 提供向量搜索及 payload 过滤，业务库与它分离时需要自行维护数据更新、删除和版本同步。评测要固定向量模型、距离度量、数据量、过滤选择率、并发、Recall@k 和 P95／P99 延迟，并测量索引构建与更新成本。本文按 pgvector 0.8.x 和查证时 Qdrant 官方文档说明，实际项目版本未知。

Elasticsearch 也能做向量检索，不要答成“ES 不能”：`dense_vector` 字段支持近似 kNN（HNSW，可选 cosine／dot_product 等度量）与精确打分检索（`script_score`），并提供 int8／int4 等量化选项降内存（官方文档说明 9.0 起浮点向量默认走 int8_hnsw，具体以部署版本为准）。它在同一索引里还能叠加 BM25 关键词检索，做“向量＋全文”混合召回是它的强项。反过来说清为什么小项目仍选 pgvector 更划算：① 向量与原文、metadata、权限标签同库同表，过滤与近邻检索一条 SQL 完成，行级权限与 join 天然可用；② 写入与更新在一个事务里，向量不会与原文分叉，省掉一套同步链路；③ 已有 Postgres 时不额外引入集群、分片与映射运维；④ 数据量与并发在 pgvector 能力范围内时，ES 带来的收益抵不上多一个有状态组件的成本。会改变结论的边界：向量到千万到亿级、需要分片扩缩与高并发写入、要求 GPU 或极致低延迟、或项目本来就有 ES 集群并需要混合检索——这时优先专用向量库或复用 ES，而不是把 pgvector 硬撑到极限（量级与指标口径同 RAG-008）。

#### 深挖追问

1. **换成 Qdrant 就能提高答案准确率吗？**（补充练习）

   不能保证。还要看 embedding、切块、召回配置与重排；应先定位检索和生成哪个环节造成错误。

2. **已有 MySQL 的情况下，为什么不顺手也用 ES 存向量？**（面经实际出现；[[面经/小红书/一面/0001#Q08：项目为什么选 PGVector 而不是 ES 做向量数据库，ES 可以吗？|MJ040 · 小红书 · 一面 · Q08]]）

   技术上可行，代价是链路：向量与业务数据分处两库，权限与版本过滤要么在应用层做两次查询再合并、要么维护一份冗余同步；数据变更要双写或走 CDC，一致性窗口与对账成本都回来（同 [[专题题库/Elasticsearch#ES-002：binlog 监听同步到 ES 的架构里，ES 起什么作用，高流量搜索如何承接？|ES-002]] 的同步链路负担）。只有当项目本来就有 ES 且需要关键词＋向量混合检索时才划算，否则为向量单独引入一套有状态集群是净增复杂度。

3. **为什么选 HNSW 而不是 IVFFlat，参数怎么定？**（面经实际出现；[[面经/字节/一面/0010#Q08：PGVector 选了哪种向量索引（HNSW），为什么？|MJ042 · 字节 · 一面 · Q08]]）

   IVFFlat 要先训练聚类中心、查询时靠 `probes` 决定扫多少个簇，建索引快、内存省，但数据分布漂移后要重建，召回对 probes 敏感；HNSW 是多层可导航小世界图，从上层粗定位逐层下降，召回—延迟曲线更好，代价是构建更慢更耗内存、写入要维护图。参数上 `m` 控制每点邻居数（影响图质量与内存）、`ef_construction` 影响建图质量、`ef_search` 是查询期在精度与延迟间的旋钮。选 HNSW 的合理理由是：在线延迟要求高且要稳定召回、数据是批量导入而非高频写、建索引时间在可接受范围。要主动给边界：小数据量（几万条以下）HNSW 相对全表精确扫描未必有收益；ANN 叠加元数据过滤可能返回不足 k 条，新版 pgvector 的迭代索引扫描能缓解但有扫描上限，权限过滤严格时要允许降级为精确扫描；换 embedding 模型等于全库重建索引。

### RAG-008：如何定义并评测检索成功率？

**常见问法**

- [[面经/美团/一面/0002#Q10：日志检索你具体是怎么检验的？|MJ032 · 美团 · 一面 · Q10]]
- 检索成功率提升至 85%，数据口径是怎么定义的？
- 评测集和验证集应如何使用？

- 怎么量化回答效果（检索的效果、回答的效果）？

- 检索的时候有没有遇到什么问题，怎么调试的？

- 用户反馈知识库效果不好，怎么确定是问法不对还是索引建得不好？

- 如何评测这个 RAG 引擎的具体效果？

#### 面试回答

先定义“成功”是哪一层。检索层可用 Hit@k 表示 top-k 中是否至少出现一个标注相关片段，用 Recall@k 表示相关证据被召回的比例；重排和最终回答另算 NDCG、引用支持率或任务正确率。所谓 85% 必须同时给出指标名、k、样本量、数据范围、基线和统计窗口。例如“固定测试集 200 条查询上 Hit@5 从 72% 提升到 85%”，不能把人工感觉或最终答案流畅度叫检索成功率。

#### 技术细节

数据集从真实查询按业务类型、难度、语言、时效性和有无答案分层采样，由明确规则标注可支持答案的文档／片段；同一模板或近重复问题不能跨集合泄漏。开发集用于实现和排错，验证集用于选择切块、embedding、混合检索权重、top-k 和阈值，最终测试集在方案冻结后报告一次。若持续查看测试结果再调参，测试集事实上已变成验证集，应另留新样本。

评测时固定语料版本和权限条件，报告宏／分组指标、失败类型及波动；样本较少时给出置信区间或至少原始成功数。离线命中提升还应结合线上无结果率、点击／采纳或人工抽检，但线上反馈存在位置偏差，不能自动当标准答案。若一个问题需多段证据，仅命中任意一段的 Hit@k 不足以代表完整检索成功。

生成层与端到端的评测口径（被问“整个引擎效果怎么评”时要能补齐）：生成层看忠实度（结论是否被所给证据支持、引用是否真的指向支持它的片段）、答案相关性、以及该拒答时有没有拒答——无答案、材料过时、事实冲突三类困难样本必须单独统计（见 [[专题题库/RAG#RAG-001：知识库问答系统如何设计？|RAG-001：知识库问答系统如何设计？]]）；可用 RAGAS 一类自动指标与 LLM-as-judge 跑回归，但评委要先与人工标注对齐（同一批样本比一致性，分歧样本人工裁决），否则只是把模型偏见规模化。端到端再叠任务成功率（用户是否真的完成了事）、延迟与单次成本（见 [[专题题库/RAG#RAG-017：RAG 一次问答的端到端延迟如何拆解，检索为什么慢、怎么优化？|RAG-017：端到端延迟拆解]]）。指标框架的通行做法是把“检索质量”和“生成质量”分开归因，参考 RAGAS 等评估框架的维度划分，而不是只报一个笼统准确率。

#### 深挖追问

1. **评测集和验证集有什么区别？**（面经实际出现；[[面经/字节/一面/0001#Q06：检索成功率提升至 85％ 的数据口径如何定义？|MJ011 · 字节 · 一面 · Q06]]）

   验证集参与方案选择和阈值调整；最终评测／测试集不参与调优，用于估计泛化效果。反复据其改方案会造成泄漏。

2. **最终答案正确能说明检索成功吗？**（补充练习）

   不能。模型可能依靠参数知识答对，也可能在正确证据下答错；检索与生成需分层评测。

3. **检索的时候遇到什么问题，怎么调试的？**（面经实际出现；[[面经/帆软/一面/0002#Q04：检索的时候有没有遇到什么问题，怎么调试的？|MJ027 · 帆软 · 一面 · Q04]]）

   按【真实经历】答，通用路径：问题先分类——“没检到”（召回失败）、“检到了但不对”（排序/冗余/权限）、“检对了答错”（生成不忠实）；拿原始 query 复现→看 top-k 明细与分数→对照标注片段算 Hit@k/Recall@k→定位切块、embedding 域不匹配、过滤条件还是重排问题；bad case 沉淀成回归集，改动逐项消融。常见坑：问答措辞鸿沟、元数据过滤误杀、近重复块挤占 top-k。

4. **效果不好怎么确定是问法不对还是索引建得不好？**（面经实际出现；[[面经/帆软/一面/0002#Q06：用户反馈知识库效果不好，怎么确定是问法不对还是索引建得不好？|MJ027 · 帆软 · 一面 · Q06]]）

   做归因实验：用人工改写成文档措辞的“标准问法”查同一知识——标准问法能检到而用户问法检不到，问题在查询侧（问法/改写/召回覆盖）；标准问法也检不到，问题在索引侧（没入库、解析丢失、切块破坏语义、embedding 不匹配）。再按意图聚类统计失败分布，两侧各自修，改动全部进回归集对比。

5. **日志检索的效果你具体怎么检验？**（面经实际出现；[[面经/美团/一面/0002#Q10：日志检索你具体是怎么检验的？|MJ032 · 美团 · 一面 · Q10]]）

   分“检索得对不对”和“结论有没有用”两层。做法：从历史故障整理【N】组「自然语言提问 → 应命中的日志／traceId／时间窗」，覆盖字段别名、相对时间表达、跨服务关联，以及“日志里根本没有”的负样本；判据上召回层看命中率与 top-k 覆盖，端到端看是否定位到正确根因（答案里的 traceId／错误类型与标注一致），负样本必须回答“没有相关日志”而不是编造；再按环节归因（查询改写错、时间窗算错、字段映射缺、索引没命中、上下文过长淹没证据），并记录耗时、扫描量与 token 成本，对比“人工上 Kibana 查”的节省。改动跑固定集合防回归，同时抽样人工复核，因为自动判据本身可能错。

6. **怎么设计对比实验证明某个模块真的有用？**（面经实际出现；[[面经/阿里国际/二面/0001#Q06：具体使用了哪些知识、如何评估这些知识的质量；有没有自建知识库做对比实验来评估效果？|MJ038 · 阿里国际 · 二面 · Q06]]）

   三项纪律：一次只动一个变量（关掉重排、换切块粒度、去掉改写、换 embedding 模型各成一组），语料版本与评测集冻结不变，指标口径与样本量先定后跑；报告写清基线是什么（如纯向量 Top-5）以及分组指标而不只是总分。缺任一项就只是“换了个写法又跑了一遍”，说服不了面试官；确实没做对照组就如实说只做了 badcase 分析（数据来源与治理见 [[专题题库/RAG#RAG-016：RAG 的知识与数据从哪里来，如何治理并评估来源质量？|RAG-016：知识与数据来源治理]]）。

### RAG-009：向量召回后为什么还要重排，直接取前几个不行吗？

**常见问法**

- 从向量数据库检索完之后为什么要经过重排？
- 向量检索本来就代表语义相关性，直接取前几个不行吗，为什么还要另一个重排？
- 重排模型使用的是什么？

#### 面试回答

向量召回快但粗：embedding 用双塔结构把 query 和文档各自独立编码，相似度只表示表示空间接近，对否定词、精确条件和多约束组合不敏感，且 ANN 索引返回的是近似近邻。重排模型把 query 与候选文档拼在一起逐对打分，能量化两者交互，明显更准但慢，不可能扫全库。所以工程上用“检索—重排”两段：先召回较大候选集，再精排截断到能进上下文的几条，同时去冗余。直接取向量前几名等于接受粗排误差和重复内容进入 Prompt。

#### 技术细节

双塔 embedding 的文档向量可离线预计算，检索是近似最近邻查找，毫秒级；cross-encoder 重排每个 query—文档对都要过一次模型，成本随候选数线性增长，候选集大小与延迟预算要一起定。重排的增益按任务评测：用 NDCG、MRR 或引用支持率对比“向量 top-k 直接给”与“召回 n 重排取 k”，同时看嵌入分数与人工相关性判断的错位样本（字面相似但答非所问、同主题冗余段落）。相似度分数跨模型、跨领域不可直接比较，阈值不能照搬。项目所用 embedding／重排模型名称与版本按【真实选型】回答：embedding 按召回、维度、语言与成本选，重排按精度提升与推理延迟选，换 embedding 模型需重建全库向量。

#### 深挖追问

1. **召回集取多大合适？**（补充练习）

   在评测上比较不同 n 的 Recall@n 与端到端延迟、重排成本，取“相关证据几乎都进候选”的最小 n，没有普适值。

2. **有了重排还需要关键词检索吗？**（补充练习）

   常需要。专有名词、编号等精确条件靠关键词召回更稳，混合召回后统一重排，见 [[专题题库/RAG#RAG-005：查询时为什么使用 embedding，如何使用？|RAG-005：查询时为什么使用 embedding，如何使用？]]。

3. **项目里没做重排，怎么解释才算合理？**（面经实际出现；[[面经/字节/一面/0010#Q09：了解 Rerank 重排序吗，为什么项目中没有实现？|MJ042 · 字节 · 一面 · Q09]]）

   给一个有判断的取舍而不是“没来得及”：① 延迟与成本不允许——cross-encoder 要对每个候选过一次模型，几十条候选就是几百毫秒，在线链路预算放不下；② 瓶颈不在排序层——badcase 统计显示主要失败是“该检的没检到”（数据缺失、切块破坏语义、硬匹配漏召），这时修召回的收益远大于精排；③ 语料小且单一，TopK 已基本覆盖答案所在片段。收口给触发条件：当召回指标达标、失败变成“检到了但排在后面”时，重排的增量就会出现，届时用同一评测集做有／无重排的消融，并按延迟定候选数。

### RAG-010：切块切断语义时如何补全召回上下文？

**常见问法**

- 文档切块把完整语义切断了，召回内容一半是断的，怎么优化？

- 文档切割策略有哪些，怎么规避语义被切割掉的问题？

#### 面试回答

核心思路是把“召回单元”和“给模型的上下文单元”解耦：按标题、段落、代码块等结构切分并保留少量重叠，小块负责精准命中；命中后不直接只喂该小块，而是返回其父块或前后相邻块补全语义；再给每个 chunk 前缀拼上文档标题路径与摘要，让孤立片段自带语境。表格、图注和跨段引用保持完整或单独建摘要索引。改动后用标注片段的召回与答案完整性指标验证，不凭感觉调块大小。

#### 技术细节

固定长度硬切最省事，但会把条件句、步骤序列和指代拆开；结构感知切分按标题层级、段落、句子边界回退。父子分块（小块检索、父块提供上下文）与 LangChain ParentDocumentRetriever 一类实现思路相同，父块大小仍受上下文预算约束。contextual retrieval 是用模型为每个 chunk 生成上下文说明再拼接编码，可提升召回相关性但增加入库成本。重叠切分只缓解边界断裂，重复内容会占预算并造成冗余，需与去冗余重排配合。保留 chunk 的顺序号、页码和父子 ID 才能做邻块扩展与引用定位，见 [[专题题库/RAG#RAG-001：知识库问答系统如何设计？|RAG-001：知识库问答系统如何设计？]]。

#### 深挖追问

1. **为什么不一开始就整篇文档入库？**（补充练习）

   长文档编码后语义被平均、定位粗，命中后超预算或需截断；分块＋父块补全兼顾召回精度与上下文完整。

2. **chunk 多大合适，不同文档类型要不要分开切？**（面经实际出现；[[面经/字节/一面/0010#Q07：切片大小是多少？不同文档类型有不同的切片方法吗？|MJ042 · 字节 · 一面 · Q07]]）

   没有普适值，它由检索粒度与生成预算两头夹出来：大块保上下文但定位不准、占预算，小块定位准但丢关系。做法是语义边界优先（按标题层级、段落、列表项、代码函数），给目标区间（常见几百 token 量级，按【真实值】填）、相邻块留少量重叠、每块前缀拼标题路径与摘要，并用标注片段的召回与答案完整性指标调参。类型必须分开：长文按结构递归切；表格按表或“表头＋行组”成块并保留表头绑定，不能拉平成文本流；FAQ 一条一块（问句本身是检索键）；代码按函数或文件切并保留路径与签名；PPT／PDF 先去噪再按版式分块、插图走 OCR 并与位置绑定；条款类要按“第 X 条”独立成块。最后给可验证的收口：按类型分层建评测集，看每类命中率，才知道是哪类切法在拖后腿。

### RAG-011：RAG 链路有哪些数据增强与效果提升手段？

**常见问法**

- RAG 数据增强的手段有哪些？

- 多路召回是什么？
- 如何润色 query，目的是什么？

- 用户的问题重写应该怎么设计？

#### 面试回答

“数据增强”口径先与面试官确认，这里按“提升 RAG 效果的数据与检索增强手段”回答，分四段：文档侧——结构化解析、保留标题路径、为 chunk 生成摘要与假设问题、父子块关联；查询侧——查询改写、多查询扩展、复杂问题拆子问题、HyDE 先生成假设文档再检索；检索侧——关键词与向量混合召回、元数据过滤、图关联扩展、重排去冗余；生成侧——引用约束、置信度输出与拒答。每种手段都要在评测集上证明增益并控制延迟成本，不是叠满就好。

#### 技术细节

文档侧增强改变索引内容：假设问题（doc2query 思路）把“用户可能怎么问”预先写入索引，缓解问答措辞不对称；摘要索引先粗后细。查询侧增强发生在检索前：多轮对话先归一化指代与省略，HyDE 用模型生成的答案草稿去检索相似文档，适合专业问法与文档措辞差异大的场景，但草稿质量决定效果。检索侧与生成侧手段分别对应 RAG-009 重排与 RAG-001 的证据约束。训练数据增强（为 embedding／重排模型造微调样本）是另一层含义，若面试官指这个需说明正样本构造、难负例挖掘与去污评测。题意按常见口径理解，原面试未给定义。

#### 深挖追问

1. **这些增强怎么决定上哪个？**（补充练习）

   先按失败类型定位：召回没命中优先查询侧与混合召回，命中了但上下文断裂优先切块与组装，证据对答案还错才动生成约束，逐项做消融比较。

2. **多路召回是什么，为什么需要？**（面经实际出现；[[面经/字节/轮次未知/0001#Q21：多路召回是什么？|MJ021 · 字节 · 轮次未知 · Q21]]）

   同一查询用多条互补路径并行召回再融合去重：关键词（精确术语／编号）、向量（语义改写）、多查询扩展、元数据／时间过滤、图关联、子块定位＋父块补全。单一检索器各有盲区，多路提覆盖率；融合后统一重排控精度，各路 top-k 与权重在评测集上调。

3. **多路召回的分数怎么合并，RRF 是什么？**（面经实际出现；[[面经/字节/一面/0010#Q05：RAG 引擎中的“混合检索策略”是怎么实现的，检索结果如何合并或重排？|MJ042 · 字节 · 一面 · Q05]]）

   向量相似度与 BM25 分数量纲不同，直接相加等于拿两套不可比的数比大小。两条路：一是各自归一化（min-max 或排名归一）后加权，权重在标注集上调；二是倒数排名融合 RRF，按候选在各路里的名次给分 `score = Σ 1/(k + rank)`（k 常取 60 量级），只用名次不依赖分数尺度，实现简单、鲁棒，是默认起手。合并后必须按文档 ID＋跨度或内容哈希去重（重复块同时挤占 top-k 是常见效果损失），再交给重排精排，并叠加来源权威度、时效与权限偏置；各路 TopN 要大于最终 k（2～5 倍），否则融合没有意义。改动一律在同一评测集上比对纯向量、纯关键词、融合、融合＋重排四档，逐项归因。

### RAG-012：Deep Search／深度检索是什么，和普通 RAG 有什么区别？

**常见问法**

- Deep Search 知道是啥吗？

#### 面试回答

先说明这不是有唯一标准的术语，常见指“深度检索／深度研究”类产品形态：Agent 接到任务后多轮“改写查询→搜索→阅读结果→再检索”，跨来源交叉验证、汇总信息，最后产出带引用的研究报告，2025-02 起 OpenAI、Perplexity 等相继推出 Deep Research 类功能。与普通 RAG 的区别在于检索不再是一次召回：有规划、有中间结论、按证据缺口迭代补查，运行时间从秒级到几十分钟级。具体产品实现以官方说明为准，不猜测内部机制。

#### 技术细节

深度检索是 Agent 循环（见 [[专题题库/Agent开发#AGENT-009：如何设计 Agent 整体架构与 ReAct 循环？|AGENT-009：如何设计 Agent 整体架构与 ReAct 循环？]]）在检索任务上的实例化：查询策略由模型根据已读内容动态调整，工具含搜索、网页阅读、文件解析，状态记录已覆盖与未解决的子问题，需要步数、时长与费用预算及引用校验。评测看报告的事实正确性、引用支持率、信息覆盖度与耗时成本；它适合开放、多跳、需要综合多来源的问题，简单事实查询用一次 RAG 更快更便宜。RAG 与深度检索不是替代关系，深度检索内部常复用 RAG 召回组件。

#### 深挖追问

1. **为什么 Deep Research 类任务要跑几十分钟？**（补充练习）

   多轮检索、逐页阅读和交叉验证都是串并混合的模型调用与网络操作，覆盖度目标决定了迭代次数，与一次召回即答的时延模型完全不同。

### RAG-013：text2sql 怎么实现，如何提高准确率？

**常见问法**

- text2sql 怎么做的？怎么提高准确率？

#### 面试回答

链路：schema 准备（表、列注释、枚举取值、指标口径整理成可检索的元数据）→按问题检索相关表与字段→Prompt 生成 SQL→执行前静态校验（语法解析、表列存在性、禁写操作、必带 LIMIT）→小样本试跑与结果合理性检查→执行返回。提准确率的核心不是换更大模型：给足“业务黑话→字段”的映射与 few-shot 典型问答对；复杂问题拆子查询分步生成；执行报错带错误信息回炉重写；高频稳定的问法沉淀为参数化模板或视图。评测用带标准 SQL 的测试集，按执行结果等价判定（同一数据快照上比对结果），而不是比对 SQL 字符串。

#### 技术细节

schema 是最大瓶颈：列名无语义、注释缺失时模型只能猜，先做元数据治理收益最高；宽表全量塞 Prompt 超预算，需先检索相关表再注入。歧义口径（“活跃用户”的定义）应在业务术语表里显式登记，检索时随 schema 注入；无法消解时向用户澄清而不是默认猜测。安全边界：只读账号、行级权限过滤下推到生成的 SQL、超时与扫描量限制——模型输出不可信输入。多轮修正（execution-guided）与自我校验能提分但增加延迟，按场景取舍。项目准确率数字必须带测试集规模与口径（见 [[专题题库/RAG#RAG-008：如何定义并评测检索成功率？|RAG-008：如何定义并评测检索成功率？]]）。

#### 深挖追问

1. **为什么不直接让模型全库生成 SQL？**（补充练习）

   表多时 schema 超预算、选错表概率大、权限不可控；先检索定位相关表再生成，错误面小且可校验。

### RAG-014：LLM Wiki 是什么，和 RAG 有什么区别？

**常见问法**

- LLM Wiki 相比 RAG 有什么区别，LLM Wiki 是怎么做的？
- RAG＋语义＋关键词＋GraphRAG 相比 LLM Wiki 有什么区别？
- LLM Wiki 的存储形式是什么？

#### 面试回答

“LLM Wiki”不是有唯一标准定义的公开术语，先与面试官确认指代，本题按“由 LLM 生成并维护的结构化知识条目层”这一常见理解作答。与 RAG 的核心区别在“整理知识”发生的时机：RAG 在查询时——相似度检索原始片段、打包进上下文再生成，语料本身不被消化；LLM Wiki 在入库时——由模型把原始资料改写成规范条目（摘要、定义、步骤、FAQ），维护条目间链接与更新合并，查询时更像“找条目读条目”，可用关键词与链接导航而未必依赖向量相似度。它把“检索质量问题”前移成“条目质量问题”：答案更凝练、跨文档信息可预先融合；代价是生成式条目可能引入改写偏差，必须保留原文引用可回溯，更新管线也要版本化。两者常组合：Wiki 层做主干知识，RAG 兜原文长尾。

#### 技术细节

存储按“条目”组织而不是按原文 chunk：每个条目一行/一文档，字段通常含标题、正文（模型改写的规范表述）、来源引用（原文件＋位置，可回溯）、版本与更新时间、条目间链接（父主题/相关条目）、生效状态；检索友好形态是“条目正文再切块入向量库＋结构化字段入关系库”，或叠加图谱/链接索引支持导航。与 RAG 库的关键差别是存储单元为“被整理过的知识对象”，因此必须有来源映射与版本链，防止改写失真无法追责。与“混合召回＋GraphRAG”路线不在同一维度竞争：左边是查询时把召回做强（语义补精确词盲区、图预构建支持多跳），LLM Wiki 是入库时把知识整理好；共同点是都提前做了某种“编译”，也都引入“编译期出错”的新风险。按知识形态选择：事实密集、关系复杂、多跳问题→GraphRAG（见 [[专题题库/RAG#RAG-002：如何做跨文档关联分析？|RAG-002：如何做跨文档关联分析？]]）；文档型知识、问答与操作指引→Wiki 化条目＋检索兜底；小规模语料先用普通 RAG 验证，不默认全都要。项目实际表结构与实现按【真实方案】填写。

#### 深挖追问

1. **改写出的条目怎么防止失真？**（补充练习）

   每条保留原文引用与位置，展示与追责都回溯源文；入库抽样人审＋冲突检测，更新走版本链可回滚。

### RAG-015：知识库内容庞杂、类型多样时，如何判断并优先提供最相关的知识？

**常见问法**

- 如果知识库的内容非常庞杂，包括多种类型，如何智能地判断和优先提供最相关的知识？
- 知识库里文档、表格、FAQ、代码都有，检索怎么知道该查哪一类？

#### 面试回答

思路是“入库时就分好类、查询时做路由、融合时给优先级”，而不是把所有片段混进一个向量库比相似度分数。三步：① 入库侧打标——每条知识登记类型（制度文档／操作指引／FAQ／表格／代码／图表）、来源权威度、时效与生效状态、权限域，这些是结构化 metadata 而不是塞进 embedding；② 查询侧识别——用规则加轻量模型（或小 LLM）判断问题该问哪类知识、要不要走结构化查询（数值、清单类问题更适合 SQL／表格检索而不是向量），据此选库选索引并下推过滤条件，判不准时多路并行召回而不是押一条；③ 融合与优先级——各路结果统一重排，排序不只看语义相关，还叠加来源权威度、时效、权限与用户上下文，并按类型给 top-k 名额，避免海量 FAQ 挤掉少量权威规范；同一事实多来源冲突时按“新版覆盖旧版、权威源优先”仲裁并显式提示。要主动交代风险：路由判错会让本该检到的直接漏检，所以宁可保守多召回再重排，也别在路由层做硬闸。

#### 技术细节

类型打标在解析阶段完成最省事：文档自带结构信息（来源系统、扩展名、模板、目录、发布渠道），可按规则赋类型与权威度，规则覆盖不到的再用分类模型或 LLM 批量归类，结果回写 metadata 供人审。分类体系不宜过细，先用“决定检索方式”的那几类（长文／结构化表／问答对／代码／图文）起步，随着 badcase 增长再拆。

查询侧的三种判定形态各有取舍：规则与关键词命中（快、可解释、覆盖不了新问法）、嵌入相似度做意图分类（便宜、要维护样例）、LLM 分类或函数式路由（覆盖广、但增加一次模型调用的延迟与成本，见 [[专题题库/RAG#RAG-017：RAG 一次问答的端到端延迟如何拆解，检索为什么慢、怎么优化？|RAG-017：RAG 端到端延迟如何拆解]]）。判定结果建议留痕（记录最终走了哪条路、置信度），否则线上无法归因“漏检是路由错还是索引差”。路由与多库复用的业务侧设计见 [[专题题库/RAG#RAG-006：如何设计垂直业务 RAG 路由与多 Agent 知识库复用？|RAG-006：垂直业务 RAG 路由]]。

优先级仲裁要写成可解释的规则而不是玄学分数：`最终排序 = f(重排相关性, 来源权威度, 时效, 权限与上下文匹配)`，其中权威度与时效用离散档位（如规范文档＞手册＞FAQ＞聊天记录；生效中＞归档）乘性或加性偏置，具体权重在标注评测集上调，且必须固定语料版本再比较。配额（每类最多占几个名额）解决“量大压过质”；跨类型互补时，表格与代码的命中结果要连同上下文一起给模型（如表头、所属文件），否则模型读到一堆无归属的数字。冲突检测与去重的前置工作见 [[专题题库/RAG#RAG-004：知识库如何检测重复文档与重复片段？|RAG-004：重复文档与片段检测]]，多路召回与增强手段见 [[专题题库/RAG#RAG-011：RAG 链路有哪些数据增强与效果提升手段？|RAG-011：数据增强与效果提升手段]]。

评测必须按类型分层看：整体 Hit@k 上升可能只是 FAQ 类变好而规范文档变差；同时统计路由判错率与“判对但没检到”的比例，才能判断该修分类器还是修索引（归因方法见 [[专题题库/RAG#RAG-008：如何定义并评测检索成功率？|RAG-008：如何定义并评测检索成功率]]）。

#### 深挖追问

1. **类型判断错了怎么办？**（面经实际出现；[[面经/阿里国际/一面/0001#Q11：知识库内容庞杂、包含多种类型时，如何智能判断并优先提供最相关的知识？|MJ038 · 阿里国际 · 一面 · Q11]] 的延伸）

   路由只用于“加权重与选路径”，不做“硬开关”：置信度不足时并行召回多类，让重排与配额决定最终顺序；同时把判错样本回流成分类器的训练与评测数据。

2. **为什么不干脆把所有内容塞进一个库，让重排模型统一排序？**（补充练习）

   小库混排确实更简单，但表格与代码的语义嵌入质量差、精确标识（编号、字段名）靠向量召回不稳，且元数据过滤（权限、时效）仍需结构化字段；混排会把过滤压力全压到重排阶段，候选数一多延迟与成本都涨。

3. **多种知识说法冲突，模型该听谁的？**（补充练习）

   入库时按生效状态与权威度定序、检索时同事实只保留高优版本并在上下文中显式标注来源与日期；无法判定时让模型输出冲突并提示用户核对，而不是自行融合成第三种说法。

### RAG-016：RAG 的知识与数据从哪里来，如何治理并评估来源质量？

**常见问法**

- 用于 RAG 的数据是从哪里来的？
- 具体使用了哪些知识？如何评估这些知识的质量？
- 知识库的数据怎么采集、更新，来源可信度怎么分级？

#### 面试回答

先如实盘点来源与获取方式，再讲治理与质量，这是这道题的得分点。来源按【本项目实际】列：论文与技术文档、内部 Wiki 与规范、项目代码与配置、公开网页与标准、FAQ 与工单历史等；获取方式三类——人工整理上传、脚本批量抓取、通过接口或数据变更同步（全量导入加增量更新，增量靠变更事件、时间戳轮询或 CDC）。治理讲四件：去重（同文多版本、近重复片段）、版本与生效状态（新版覆盖旧版且可回溯）、时效（打标过期）、权限域（来源与用户权限要带进检索）。质量分两层评估：内容层看来源是否权威、是否最新、是否互相冲突、能否回溯到原文；效果层用分层评测看每类知识在检索里到底有没有用——检不到就归因到“没入库／解析丢失／切块破坏语义／问法与文档措辞有鸿沟”。最后给边界：数据规模与覆盖范围有多大、因来源单一导致长尾问题检不到，是这版的已知局限。把“用公开数据集跑通实验”说成“构建了企业级知识库”是这题最容易翻车的地方。

#### 技术细节

不同来源的入库管线差别很大，要分开设计：文档与网页重点是版式还原与噪声剔除（页眉页脚水印模板段落），表格重点是结构化保存而不是拉平成文本，FAQ 天然按问答对成块，代码按函数或文件切片并保留路径，图片走 OCR／图注再与位置绑定（见 [[专题题库/RAG#RAG-003：PPT 文档如何去噪？|RAG-003：PPT 文档如何去噪]]、[[专题题库/RAG#RAG-001：知识库问答系统如何设计？|RAG-001：知识库问答系统如何设计？]]）。同步链路的可靠性是工程题：抓取要处理反爬与失败重试、内容哈希去重决定要不要重算 embedding；接口同步要明确触发方式与幂等；数据库变更走 CDC 时延迟与乱序要归因（见 [[专题题库/系统设计#SYS-024：canal／binlog 订阅同步延迟如何归因与优化？|SYS-024：binlog 订阅延迟归因]]）。删除与更新同样重要——文档下架或改版后，旧块与失效向量必须一起清理，否则答案会引用已废弃内容，这类“幽灵知识”是最难查的线上问题。

来源可信度分级要有规则依据而不是拍脑袋：按发布主体（规范发布方＞内部权威文档＞普通贡献内容＞聊天记录）、是否有审核流程、是否带版本与生效日期、被引用次数与最近更新时间组合打分，把分值写进 metadata 供检索排序与仲裁使用（见 [[专题题库/RAG#RAG-015：知识库内容庞杂、类型多样时，如何判断并优先提供最相关的知识？|RAG-015：多类型知识的优先级仲裁]]）。重复与冲突的检测手段见 [[专题题库/RAG#RAG-004：知识库如何检测重复文档与重复片段？|RAG-004：重复文档与片段检测]]。

合规与权限不是可选段落：数据是否允许用于训练或检索外发、是否含个人信息与密钥（入库前要扫描脱敏）、跨租户与跨部门可见性要在召回阶段下推过滤而不是生成后再遮。评测与上线指标的完整口径见 [[专题题库/RAG#RAG-008：如何定义并评测检索成功率？|RAG-008：如何定义并评测检索成功率]]。

#### 深挖追问

1. **有没有自建知识库做对比实验来评估效果？**（面经实际出现；[[面经/阿里国际/二面/0001#Q06：具体使用了哪些知识、如何评估这些知识的质量；有没有自建知识库做对比实验来评估效果？|MJ038 · 阿里国际 · 二面 · Q06]]）

   按真实情况答。做法是固定同一批测试问题与语料版本，做有／无某模块的消融（关掉重排、换切块粒度、去掉查询改写、换 embedding 模型、加或不去噪声），逐项比较指标增量并报告样本量；只有对照组和可复现评测集才叫实验。确实没做过就明说“只做了单链路验证与 badcase 分析，缺对照组是不足”，比编数字安全。

2. **哪些数据不适合进知识库？**（补充练习）

   无授权或含敏感信息（凭据、个人隐私、未公开经营数据）、无法确定生效版本的历史讨论、纯口头无出处且不可回溯的结论；这类内容即便能提升召回率也不该入库，或必须先脱敏与打标为不可引用。

3. **知识更新后怎么保证答案不引用旧版？**（补充练习）

   内容哈希判定是否重算、按文档 ID 整组替换旧块并删除其向量、给条目带生效时间与版本、检索侧默认过滤非生效状态，再加定时一致性巡检（索引与源库对账）兜住漏更新的脏块。

### RAG-017：RAG 一次问答的端到端延迟如何拆解，检索为什么慢、怎么优化？

**常见问法**

- 系统生成一次回答反馈大概需要多长时间？
- 知识检索过程为什么会花费这么长时间？你预估每个步骤的时间是多少？
- RAG 链路的延迟怎么优化？

#### 面试回答

先给分步瀑布再报总数，比只说一个平均数可信。典型链路的耗时结构大致是：问题改写或意图判断若走一次模型调用，几十毫秒到秒级（用小模型或规则可压到几十毫秒）；查询向量化几毫秒到几十毫秒；ANN 召回通常几毫秒到几十毫秒，但多路召回串行就会叠加，关键词检索与元数据过滤也算在这段；重排若用 cross-encoder，每个候选都要过一次模型，耗时随候选数线性增长，几十到几百毫秒；上下文组装基本可忽略；生成阶段占大头，取决于输出长度与是否流式，常占端到端七成以上。所以“检索为什么慢”的真因往往不是向量算得慢，而是：串行调了多次模型（改写、路由、判断各一次）、多路召回串行、重排候选过多、检索服务冷启或网络往返多跳、权限过滤导致回表查询、以及大结果集与序列化开销。归因方法是按步骤打点记录 P50／P95 与各步 token 数，画瀑布找最长那段；优化顺序按收益排：并行化独立步骤、砍掉非必要的模型调用、限制重排候选数、缓存可复用的查询与向量结果、生成侧流式先出正文、简单问题走轻量链路。真实数字必须按【本项目实测】口径说清是端到端还是仅检索、是 P50 还是 P95。

#### 技术细节

各段的主导因素：embedding 编码受模型大小、输入长度与批处理影响，本地部署还要看 GPU／批队列；ANN 延迟由索引类型与参数决定（HNSW 的候选邻居数、IVF 的列数），召回率与延迟是一对可调权衡（见 [[专题题库/RAG#RAG-007：pgvector 与 Qdrant 如何比较和选型？|RAG-007：pgvector 与 Qdrant 选型]]）；关键词检索与混合召回的叠加成本见 [[专题题库/RAG#RAG-011：RAG 链路有哪些数据增强与效果提升手段？|RAG-011：数据增强与效果提升手段]]；重排的候选数—延迟关系是线性的，所以“先粗召回 TopN 再重排 TopK”的两段式几乎是必选项（见 [[专题题库/RAG#RAG-009：向量召回后为什么还要重排，直接取前几个不行吗？|RAG-009：为什么召回后还要重排]]）。

优化手段与副作用要一起讲：并行化要求召回彼此独立且下游能扛住瞬时并发；缓存查询向量与结果要看命中率与陈旧风险（改写后的 query 分散会让缓存形同虚设，可只对归一化后的热点问法缓存，Prompt 前缀复用见 [[专题题库/大模型基础#LLM-006：Prompt Caching 是什么？|LLM-006：Prompt Caching]]）；分级链路按问题难度选择模型（意图识别用小模型，见 [[专题题库/Agent开发#AGENT-020：小模型是否足以完成意图识别？|AGENT-020：小模型做意图识别]]）；流式与乐观输出改善的是体感延迟（首 token）而非总时长，做验收时要区分两者。多跳与迭代检索会把耗时放大一个量级，这类取舍见 [[专题题库/RAG#RAG-012：Deep Search／深度检索是什么，和普通 RAG 有什么区别？|RAG-012：Deep Search 与普通 RAG]]。

报数与容量口径：给分位数不给平均（P95 才反映长尾）、注明测试环境与并发度（单请求延迟与并发下延迟不同）、区分首次请求与命中缓存；成本要与延迟一起看（候选数、输出 token 数直接决定费用，见 [[专题题库/Agent开发#AGENT-029：如何降低大模型调用成本？|AGENT-029：如何降低大模型调用成本]]）。若被追问“你怎么知道是检索慢”，答案只能是分段埋点数据，不是猜测。

#### 深挖追问

1. **检索阶段真的需要几百毫秒吗，瓶颈在哪？**（面经实际出现；[[面经/阿里国际/二面/0001#Q09：系统生成一次回答大概需要多长时间？知识检索为什么花这么久，各步骤耗时怎么预估？|MJ038 · 阿里国际 · 二面 · Q09]]）

   纯向量检索通常只有毫秒到几十毫秒级；一旦检索段很慢，优先怀疑它偷偷包含了模型调用（改写、路由、判断）、多路串行、重排候选过多、或跨网络多跳与冷启动，而不是怀疑向量算法本身。

2. **首 token 延迟和总耗时怎么分别优化？**（补充练习）

   首 token 靠减少前置步骤（并行召回、跳过非必要模型调用、短上下文）、以及流式透出去改善；总耗时靠控制生成长度、模板化引用段与限制候选，验收时两个指标都要报。

3. **延迟和效果冲突时怎么决策？**（补充练习）

   用分层链路加预算：简单高频问题走轻量路径并设超时兜底（超时退回纯检索摘要或缓存答案），复杂问题允许高延迟；决策依据是分类别的延迟—指标曲线，而不是全局平均值。
