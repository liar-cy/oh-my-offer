### JVM-001：JVM 运行时内存区域与 Java 内存模型有什么区别？

**常见问法**

- [[面经/美团/一面/0002#Q14：JVM 内存结构介绍一下|MJ032 · 美团 · 一面 · Q14]]
- JVM 内存模型如何理解，垃圾回收算法有哪些？

- Java 如何管理内存，堆与 G1 垃圾回收如何工作？

- Java 的 JVM 内存分成哪些区域？直接内存是由 JVM 管理的吗？哪些区域可能发生 OOM？

#### 面试回答

原文“JVM 内存模型”有歧义，先说清问的是哪一个：

- 如果问运行时内存区域：线程私有的有程序计数器、虚拟机栈、本地方法栈；共享的有堆和方法区。运行时常量池属于方法区，HotSpot 的元空间是方法区的一种实现。
- 如果问 JMM（Java 内存模型）：讲的是共享变量的可见性、有序性和 happens-before，不能用堆栈分区去答。

别把两者混着说：一个是“内存怎么分区”，一个是“多线程之间怎么看见彼此的写”。

#### 技术细节

**回答前提与规范口径**

- 本题按 Java SE 21 规范说明两种可能的含义，原面试官的意图未确认。
- 虚拟机栈由一个个栈帧组成，栈帧里有局部变量表、操作数栈等。
- 方法区是规范里的概念，不能直接等同于 HotSpot 的某个实现结构。
- 直接内存也不是规范规定的独立运行时区域。

**JMM 这边要说的**

- 能建立 happens-before 的两组操作：volatile 写与随后的读、监视器解锁与随后的加锁。
- 一个易错点：volatile 不会让 `i++` 自动变成原子操作。

**为什么不能只盯着堆**

- 对象和数组通常在堆里分配、由 GC 管理，但线程栈、HotSpot 元空间、直接内存和运行时的本地分配同样消耗进程内存。
- 堆里一直保留着没用的对象引用，就是逻辑内存泄漏 —— GC 不能回收仍然可达的对象。
- 所以容器限额要覆盖上面全部开销，`Xmx` 不是 Java 进程的总内存上限。

#### 深挖追问

1. **JMM 和 JVM 运行时数据区是同一件事吗？**（补充练习）

   不是。前者定义线程间内存交互与可见性约束，后者描述 JVM 执行需要的存储区域；原题意图未确认，因此两种解释都标注为回答前提。

2. **Java 内存管理为什么不能只看堆？**（面经实际出现；[[面经/百度/一面/0005#Q18：Java 如何管理内存，堆与 G1 垃圾回收如何工作？|MJ008 · 百度 · 一面 · Q18]]）

   因为堆外区域和线程栈同样占用资源，堆未满时也可能遇到本地内存不足或容器内存限制。

3. **直接内存是由 JVM 管理的吗？**（面经实际出现；[[面经/帆软/二面/0002#Q08：JVM 内存分哪些区域，直接内存由 JVM 管理吗，哪些区域会 OOM？|MJ035 · 帆软 · 二面 · Q08]]）

   分两层看，结论是“JVM 进程分配、GC 间接触发释放”。

   - 它本身不是 JVMS（Java 虚拟机规范）里的运行时数据区：在堆外，由 native 分配（走 `Unsafe`），不进堆，GC 也不会移动它。
   - 但 `DirectByteBuffer` 这个对象在堆上，它挂的 Cleaner 会在对象被回收时释放那块 native 内存；用量还受 `-XX:MaxDirectMemorySize` 的记账限额约束。
   - 一个细节：NIO 分配失败之前，会先主动调一次 `System.gc()` 再重试。

4. **哪些区域可能发生 OOM？**（面经实际出现；同上来源）

   除程序计数器外都可能，各自的报错不一样：

   - 堆：`Java heap space`。
   - 虚拟机栈：超出 `-Xss` 一般是 `StackOverflowError`；实现支持动态扩展时，扩不出来会抛 OOM。
   - 方法区／元空间：`MetaspaceSize` 打满，或者类加载器泄漏。
   - 直接内存：超过 `MaxDirectMemorySize`。
   - native 线程创建：`unable to create new native thread`，受操作系统的线程数和内存限制。

   要补一句：程序计数器是规范里唯一不会抛 OOM 的区域。

### JVM-002：垃圾回收如何判断对象存活，常见回收算法有哪些？

**常见问法**

- JVM 内存模型如何理解，垃圾回收算法有哪些？

- JVM 的垃圾回收机制是什么？

- 能介绍一下 Java 的 GC 机制吗？

#### 面试回答

分两步说：先判活，再选算法。

- 判活：从 GC Roots 出发做可达性分析，不可达的即可回收。
- 标记—清除：不移动存活对象，但会留下碎片。
- 复制：把存活对象搬到另一块空间，适合存活率低的区域，代价是要预留额外空间。
- 标记—整理：移动存活对象把空间压实，碎片少了，但有搬迁成本。

最后把概念层次分清：分代收集是“按对象寿命组织回收”的策略，G1、ZGC 这些是具体收集器，别把它们当成算法名称并列说。

#### 技术细节

**GC Roots 具体是哪些**

- 可以包括：活动线程栈里的引用、类的静态字段引用、JNI 引用等。
- 注意口径：具体根集合由 JVM 实现和当时的运行状态决定，不是一份固定清单。

**为什么不用引用计数**

- 它难以直接处理循环引用，所以不是 Java 堆回收的主要判活方式。

**“并行”和“并发”别混**

- 并行：多个 GC 线程一起干活。
- 并发：回收阶段可以和应用程序同时运行。
- 补充一句：号称并发的收集器，仍然可能有暂停阶段。

**选型看什么**

- 看暂停时间、吞吐量、内存占用和堆规模这四个维度。
- 别用“新生代复制、老年代整理”这一句话去套所有现代收集器。

#### 深挖追问

1. **垃圾回收算法有哪些？**（面经实际出现；[[面经/百度/一面/0003#Q15：JVM 内存模型如何理解，垃圾回收算法有哪些？|MJ006 · 百度 · 一面 · Q15]]）

   常见基础算法是标记清除、复制和标记整理；再区分判活方法、分代策略以及具体收集器的实现组合。

### JVM-003：G1 如何管理堆并完成垃圾回收？

**常见问法**

- G1 如何管理堆并完成垃圾回收？

#### 面试回答

以 HotSpot JDK 21 的 G1 为例，四句话：

- 堆的划法：堆被划成多个 Region，年轻代和老年代只是逻辑上的区分。
- 怎么决定收谁：靠并发标记评估各个区域的存活量。
- 怎么收：在暂停中把选定区域的存活对象疏散（复制）出去。
- 除了 Young GC：年轻代回收之后，还能做带上部分老年代区域的混合回收（Mixed GC）。

补一句边界：暂停目标是尽力满足，不是硬实时保证，G1 也不是全程无暂停。

#### 技术细节

**Region 的划法**

- 仍以 HotSpot JDK 21 为基线：所有 Region 大小相同。
- 年轻代和老年代是逻辑集合，不要求物理上连续。

**一轮回收发生了什么**

- 并发标记先评估各区域的存活量。
- 疏散暂停期间，把存活对象复制到其他 Region。
- 混合回收选的是年轻代，加上一部分老年代 Region。

**跨 Region 的引用怎么处理**

- 靠 remembered sets（记忆集）这类记录，避免为了几个跨区引用去扫整个堆。
- 记忆集由写屏障参与维护；标记本身采用 SATB（snapshot-at-the-beginning，标记开始时拍快照）的思路。

**大对象是另一个规则**

- 达到大对象阈值的对象按 humongous（大对象）处理，阈值大约是半个 Region，具体边界要结合实现看。
- 这会影响连续空间的需求。

**两句边界与调优口径**

- 暂停目标不保证每次都达成；疏散时空间不够等情况，可能触发代价更高的回收。
- 调优要从 GC 日志、分配速率、存活量和延迟目标出发，不要凭空调参。

#### 深挖追问

1. **G1 是完全并发、不会暂停吗？**（补充练习）

   不是，并发标记可与应用重叠，但疏散及部分标记阶段需要暂停；目标暂停时间是调度目标而非硬上限。

### JVM-004：JVM 如何实现 Java 的跨平台运行？

**常见问法**

- JVM 跨平台的原理是什么？
- Java 为什么能做到“一次编译，到处运行”？

#### 面试回答

- 编译产物：Java 源码通常先编译成平台无关的 class 字节码。
- 谁来跑：每个操作系统和硬件平台都有自己的 JVM 实现，负责加载、校验，再用解释器或 JIT（运行时编译）编译器把字节码转成本机指令，同时实现规范规定的运行时行为。

所以结论要说准：跨平台的是符合约束的字节码和 Java API 语义，JVM 本身仍是平台相关的原生程序。

#### 技术细节

**字节码为什么不绑平台**

- class 文件用的是规范定义的二进制格式和指令集，不直接绑定某一种 CPU 指令集。

**从 class 文件到执行**

- 类加载器负责把类取进来；验证阶段检查格式、类型和控制流等约束。
- 执行引擎先解释那些热点还不明显的代码，再把热点方法用 JIT 编译成目标机器码。

**平台相关的部分藏在哪**

- 垃圾回收、线程映射、系统调用，都是具体 JVM 和操作系统的配合实现。
- 但对应用暴露出来的，是相对统一的 Java 语义。

**“一次编译，到处运行”的前提**

- 目标平台要有兼容的 Java 运行环境。
- 代码使用的 Java 版本和依赖也要兼容；class 文件版本高于运行时支持的版本，同样不能直接运行。

**哪些东西会引入平台差异**

- JNI／JNA、本地动态库、路径分隔符、默认字符集、文件权限、大小写敏感、平台命令。

#### 深挖追问

1. **JVM 本身是跨平台的吗？**（补充练习）

   JVM 的规范和行为目标跨平台，但具体 JVM 可执行文件必须针对操作系统和 CPU 构建；同一个 JVM 二进制通常不能直接用于所有平台。

2. **Java 字节码总是被解释执行吗？**（补充练习）

   不是。常见 JVM 会结合解释执行与 JIT，把热点代码编译为本机指令；也可能使用 AOT 等方式，具体策略取决于实现。

### JVM-005：有 GC 的 Java 为什么还会内存泄漏，如何定位？

**常见问法**

- 既然有 GC，为什么还会出现内存泄漏？

#### 面试回答

一句话：GC 只回收从 GC Roots 不可达的对象，业务上已经没用、但仍被可达引用“合法”持有的对象，GC 不会也不该回收 —— 这就是 Java 的内存泄漏，更准确叫“无界留存”。

典型来源背这几类：

- 只增不删的集合和本地缓存。
- 没注销的监听器与回调、没关闭的资源。
- 非静态内部类隐式持有外部实例。
- 线程池场景下 ThreadLocal 没 `remove()`。
- static 集合长期累积。
- equals／hashCode 实现有误，导致 Map 的键命不中、删不掉。

最后补一句范围：堆外的直接内存和线程栈不归堆的 GC 管，`Xmx` 不是进程的总内存上限。

#### 技术细节

**怎么判断是真的在泄漏**

- 看趋势：Full GC 之后老年代占用还在持续抬升，每次回收量越来越小。
- 最终表现是 OOM，或者 GC 变得很频繁。

**定位路径**

- 第一步用 GC 日志确认趋势。
- 第二步用 `jmap` 或在线诊断抓堆转储（heap dump）。
- 第三步用 MAT 这类工具看支配树和 GC Roots 的引用链，回答“谁还引用着它”。

**修的时候对着持有方下手**

- 缓存加容量上限和逐出策略。
- 监听器跟着生命周期注销。
- 资源用 try-with-resources。
- ThreadLocal 用完 `remove()`。
- 避免内部类持有外部的大对象。

**一句话本质，外加一条边界**

- 这不是 GC 算法失效，而是“可达性判定”和业务上“是否还需要”这两套语义不一致。
- 容器里被 OOM 杀掉时，还要查堆外、元空间、线程数和 native 内存。

#### 深挖追问

1. **内存泄漏和 OOM 是一回事吗？**（补充练习）

   不是。泄漏是逐渐累积的过程，OOM 是结果之一；泄漏也可能表现为 GC 时间变长、吞吐下降而不一定立刻崩溃。

2. **WeakHashMap／软引用能根治吗？**（补充练习）

   只能缓解特定场景；键值语义、引用队列清理和业务生命周期仍需自己管，误用反而引入难排查的提前回收。

### JVM-006：Java 对象内存大小怎么估算，基本类型占几个字节？

**常见问法**

- Java 对象内存大小怎么估算？
- Java 基本数据类型占用字节大小。

- 怎么计算一个对象的大小？

#### 面试回答

先说前提：按 HotSpot 64 位、开启压缩指针（默认，堆小于 32G 时）来估算。

- 对象头：Mark Word 8 字节＋压缩类指针 4 字节。
- 实例字段按类型宽度排：boolean／byte 1、char／short 2、int／float 4、long／double 8；引用类型字段 4 字节。
- 最后补齐到 8 字节对齐。

举个例子：一个 int 加一个引用的对象，约等于 12＋4＋4＝20，补齐成 24 字节。

两个口径要交代：基本类型的裸宽度是 JVMS 没规定、由实现决定的（boolean 字段通常 1 字节，`boolean[]` 每元素 1 字节）；答题时注明“以 HotSpot 为例”，要实测就用 JOL 工具。

#### 技术细节

**先分清两种 size**

- shallow size：对象自身占的字节，不含它引用出去的目标。
- retained size：把只有它独占引用的整片对象图都算上。
- 堆分析工具报的是后者 —— 这才解释得了“一个集合吃掉半个堆”。

**几个会影响布局的细节**

- 数组多一个长度字段，通常 4 字节，计入头部之后再对齐。
- String 在 JDK 9+ 用 `byte[]`＋coder（Latin-1 用单字节存储），比 JDK 8 的 `char[]` 省一半。
- 没开压缩指针时（大堆或 `-XX:-UseCompressedOops`）：引用 8 字节、类指针也 8 字节。
- 压缩类指针本身还有对齐前提。

**估算用来干什么**

- 容量规划时按“对象数 × retained”估堆水位。
- 再用 `-XX:+HeapDumpOnOutOfMemoryError` 和 MAT 去验证，别对着字段表心算大对象图。

#### 深挖追问

1. **为什么 long 在 32 位 JVM 上读写可能不原子？**（补充练习）

   因为 64 位值要拆成两次 32 位访问。JVMS 规定 long／double 的读写默认非原子，除非声明 volatile —— 这属于内存模型的条款，和对象大小估算不是一个层面。

### JVM-007：类加载的过程是什么，双亲委派是什么？

**常见问法**

- 类加载的过程是什么？

#### 面试回答

类加载分五步：加载 → 验证 → 准备 → 解析 → 初始化，其中后三步合称链接。

- 加载：类加载器把字节流读进来（来源可以是 class 文件、jar、网络或运行期生成），在方法区建 Class 对象作为入口。
- 验证：查格式、元数据、字节码语义和控制流。
- 准备：给类变量分配内存并置零值；编译期常量在这一步就已经是终值。
- 解析：把符号引用换成直接引用，动态绑定的场景可以延后。
- 初始化：执行 `<clinit>`，也就是静态赋值和静态块按书写顺序跑一遍。

初始化由首次主动使用触发，JVM 保证它只执行一次且线程安全 —— 静态内部类式单例用的就是这一点。

查找顺序按双亲委派：Bootstrap → 应用类加载器 → 自定义加载器，每一级都先问父加载器。这么设计是为了让核心类不被篡改，并保证一个类在 JVM 内唯一。

#### 技术细节

**类的身份怎么判定**

- 一个类由“加载器＋类名”共同确定身份，这是双亲委派相关的判定口径。

**什么时候算主动使用**

- new、静态字段／方法访问、反射、主类等，算主动使用，会触发初始化。
- 两个细节：子类初始化会先触发父类；但通过子类去引用静态字段，不算对子类的使用。

**“打破双亲委派”是正常设计，不是事故**

- 说“打破”之前，要先讲清是哪个场景，常见的是这三类：
  - SPI／线程上下文类加载器：父加载器需要去加载子路径上的 provider 类。
  - OSGi／模块化容器：用的是网状委派。
  - 热部署与 Agent 字节码增强：都要自定义委派。

**一条排查线索**

- 同名类被两个加载器各自加载过，就会出现 ClassCastException、`instanceof` 为 false。

**版本口径**

- JDK 9+ 模块化之后，内部加载器结构有调整（比如平台类加载器），说明时按所用版本讲。

#### 深挖追问

1. **创建类／实例化对象有几种方法？**（面经实际出现；[[面经/携程/一面/0001#Q11：创建类有几种方法？|MJ028 · 携程 · 一面 · Q11]]）

   原题有歧义，先确认口径，两种答案都要备好。

   - 问“创建对象”：new（常规路径）、反射 `Class`／`Constructor.newInstance`、clone（绕过构造器，需要实现 Cloneable）、反序列化（同样绕过构造器，readObject 要做校验）、MethodHandle 等。
   - 问“生成一个新类”：正常编译产出、JDK 动态代理（按接口）／CGLIB（生成子类）、字节码框架 ASM／Javassist／ByteBuddy（AOP 与探针的基础）、运行期源码编译（`javax.tools.JavaCompiler`、Groovy 脚本）。

   这题接在类加载语境后面时，多半问的是后者。

2. **双亲委派为什么不算“严格从顶到底加载”？**（补充练习）

   是“先委托父级尝试”，父级加载不了才自己加载；且存在反向委派（线程上下文类加载器），说成“所有类都由 Bootstrap 加载”是错的。

### JVM-008：CMS 和 G1 有什么区别，各自执行步骤与适用场景？

**常见问法**

- 先说 JVM 垃圾回收，判断垃圾、回收算法、优劣、分代，常见垃圾回收器，CMS 和 G1 的特点和各自执行步骤、各自使用场景。
- CMS 和 G1 怎么选？

#### 面试回答

建议按“判活 → 算法 → 分代 → CMS 的步骤与缺陷 → G1 的步骤与优势 → 选型”的顺序说，并交代所用的 JDK 版本。

**判活**

- 用可达性分析：从 GC Roots（活动线程栈上的引用、静态字段、JNI 引用等）向下遍历，不可达的就可以回收。
- 引用计数难以处理循环引用，不是 Java 堆的判活方式。

**算法**：三种各有代价

- 标记—清除：不搬对象，但会产生碎片。
- 复制：没有碎片，成本与存活对象数量成正比，适合存活率低的年轻代，代价是要牺牲一块空间。
- 标记—整理：既无碎片也不留空洞，代价是移动和引用更新，暂停时间更长。

**分代**

- 建立在“多数对象朝生夕死”的弱分代假说上。
- 新生代用复制：Eden＋两块 Survivor，Minor GC 只扫年轻区，所以快。
- 老年代用标记—整理；跨代引用靠记忆集，避免全堆扫描。

**CMS（并发标记清除）**：目标就是低停顿，四步走

- 初始标记：短暂 STW，只标 GC Roots 直接引用的对象。
- 并发标记：和用户线程同时遍历引用图。
- 重新标记：再一次短暂 STW，修正并发期间变化的引用，走的是增量更新思路。
- 并发清除：与用户线程并发回收，不移动对象。

代价是跟着低停顿一起来的：

- 并发阶段要抢 CPU，还得预留堆空间。
- 标记之后新产生的对象成了**浮动垃圾**，只能等下轮。
- 不整理，所以**碎片**会一路累积。
- 并发期间分配不过来，就触发 Concurrent Mode Failure，退化成单线程 Full GC。

版本要主动补：CMS 在 JDK 9 被标记废弃（JEP 291）、JDK 14 移除。所以答完要说“现在默认是 G1”，不然显得停在 JDK 8。

**G1**

- 堆被切成等大的 Region，年轻／老年代只是逻辑分组。
- 流程：Young GC；堆占用达到阈值时进入并发标记周期（初始标记借用一次 Young 暂停、并发标记、最终重标记、清理空 Region）；然后是 Mixed GC，一次回收年轻代加一批垃圾最多的老年代 Region —— “Garbage First”这个名字就是这么来的。
- 它靠记忆集控制跨区扫描，用 SATB 保证并发标记的正确性，并且把**停顿时间做成可调目标**（`MaxGCPauseMillis`，默认约 200ms，是调度目标不是硬上限）。
- 适用：大堆、延迟敏感的服务；JDK 9 起是默认收集器。
- 代价：复制和写屏障的开销；humongous 对象（超过约半个 Region）处理不好，会带来空间紧张和额外回收。

**场景**

- 小堆、吞吐优先的批处理：Parallel GC。
- 中等以上的堆、要控停顿：G1。
- 要求亚毫秒级暂停的超大堆：ZGC（JDK 21 起有分代 ZGC）或 Shenandoah。

#### 技术细节

**两者最容易混的一点**

- CMS 是**并发清除、不移动对象**，所以会留碎片，后面可能靠 Full GC 来整理。
- G1 是**并发标记＋在暂停里复制整理**，所以没有碎片问题，但每次回收都要搬对象。

**“停顿可预测”这句话怎么说才准**

- 它的依据是：G1 会按每个 Region 的回收价值（垃圾占比和预测耗时）排序，据此选回收集（CSet）。
- 这是调度上的选择，不是承诺：分配速率突然升高、或者存活对象太多时，目标就会满足不了。

**观察手段要能报出来**

- `-Xlog:gc*`（JDK 9+ 的统一日志格式）：看暂停分布和各阶段耗时。
- `jstat -gcutil`：看代际占比和 GC 次数的趋势。
- `jmap`／`-XX:+HeapDumpOnOutOfMemoryError` 取 dump，再用 MAT 看支配树。
- `async-profiler`：看分配热点。

**该不该换收集器，看症状**

- CMS 频繁出现 Concurrent Mode Failure，或者有很长的 Full GC：换 G1。
- G1 的暂停目标总是达不到、同时老年代回收效率低：去查大对象和分配速率，而不是盲目把停顿目标调小。

#### 深挖追问

1. **CMS 为什么需要预留空间，预留多少？**（补充练习）

   因为并发清除期间用户线程还在分配新对象，这部分“浮动垃圾”本轮回收不了，必须留出余量。

   - 什么时候启动并发收集，由 `-XX:CMSInitiatingOccupancyFraction` 决定（默认约 68%，指老年代占用比例）。
   - 还要配 `-XX:+UseCMSInitiatingOccupancyOnly`，否则会被自适应策略覆盖掉。
   - 调参的两难：设太高容易触发并发失败退化，设太低则回收频繁、吞吐下降。

2. **G1 的 Mixed GC 什么时候触发，回收哪些 Region？**（补充练习）

   在并发标记周期结束之后触发。那时 G1 已经知道每个 Region 的存活量和回收耗时，于是：

   - 按暂停目标挑出“价值最高”的一批老年代 Region，连同年轻代一起做疏散回收。
   - 几轮 Mixed 之后，才完成这一轮全堆标记周期对应的回收。
   - 没被选中的 Region 留到下个周期 —— 所以 G1 从来不追求一次回收整个堆。

3. **为什么 G1 需要写屏障，代价是什么？**（补充练习）

   并发标记期间引用关系一直在变，有两件事必须记下来：

   - 跨 Region 的引用，用来维护记忆集。
   - 标记期间的赋值，也就是 SATB，用来防止漏标。

   这两件事都靠写屏障：在堆上的引用被更新时插一段记录逻辑。代价是每条引用赋值要多执行几条指令，屏障本身也占 CPU —— 这就是 G1 吞吐通常低于 Parallel 的原因之一。

4. **分代 ZGC 解决了什么问题？**（补充练习）

   解决的是非分代 ZGC 把短命对象的成本摊到全堆的问题。

   - 之前：所有对象一视同仁，回收吞吐有限，分配速率一高就容易跟不上。
   - 之后：分代 ZGC（JDK 21 的 JEP 439）让年轻代走更便宜的路径，回收吞吐更高，分配停顿的风险也更低。

   能不能用，取决于所用的 JDK 版本和参数。

### JVM-009：项目部署时 JVM 怎么调优，从哪里入手？

**常见问法**

- 你项目部署的时候，有尝试对 JVM 进行调优吗？
- 线上 JVM 参数怎么定？

- 谈谈你对 JVM 调优的理解，有哪些常见的调优参数或方法？
- 在启动命令中调整 JVM 参数，怎么做？

#### 面试回答

原则只有一句：**先测量再改参数，改完必须用同一场景复测**，而不是背一串 `-XX` 选项。落地是四步：

- 第一步，定目标：这个服务在意的是吞吐、P99 延迟还是内存占用，三者会互相冲突。
- 第二步，建基线：开 `-Xlog:gc*` 输出 GC 日志，记录暂停分布、GC 频率、老年代增长趋势；同时看进程 RSS 是否已经接近容器限额。
- 第三步，对症处理，看症状下药：
  - 堆太小导致频繁 Young GC 或 Full GC：加大堆，并把 `-Xms` 和 `-Xmx` 固定成一样，避免运行中扩容带来抖动。
  - 容器环境：用 `MaxRAMPercentage` 让堆随限额伸缩，而不是写死绝对值。
  - 老年代一直涨：取 heap dump 找支配对象，常见是无上限缓存、ThreadLocal 没 `remove()`、大集合、静态引用。
  - Full GC 后老年代几乎不降：内存泄漏，或者 Metaspace 不足。
  - 单次暂停过长：检查大对象和分配尖峰，再考虑换收集器或调 G1 的 `MaxGCPauseMillis`。
- 第四步，复测与留档：用同一个压测场景对比 P99、吞吐、GC 暂停和错误率，把参数和结论记下来，避免下次从头猜。

被问“你实际调过什么”时，按真实经历答：【部署形态＋JDK 版本＋改了什么参数或代码＋前后数字】。没做过线上调优就直说“我只调过堆大小和 GC 日志，没做过参数级调优”，然后讲清该看哪些指标 —— 这比编一个“把 Xmx 从 512M 调到 2G，效果翻倍”安全得多。

#### 技术细节

**容器里的内存账**

- `Xmx` 只是堆的上限，进程实际占用还要再加上：元空间、线程栈（线程数 × 栈大小）、直接内存（NIO／Netty 池外）、JIT 代码缓存，以及 GC 结构自身的开销。
- 容器被 OOMKilled，常见原因就是这套总开销超过了 limit，而堆使用率看着还很正常。
- 排查方向：`-XX:MaxMetaspaceSize`、`-Xss`、直接内存上限（`MaxDirectMemorySize`）和 Netty 的池外内存统计。
- 必要时开 Native Memory Tracking：`-XX:NativeMemoryTracking=summary`，再用 `jcmd ... VM.native_memory` 看。

**GC 参数的合理默认**

- 现代 JDK 里，G1 配 `MaxRAMPercentage`（比如 50～75）通常比手写分代大小更好。
- `-Xmn` 固定年轻代会削弱 G1 的自适应，`-XX:NewRatio` 这类也要慎用。
- `-XX:+UseStringDeduplication`、`-XX:+AlwaysPreTouch` 各有适用场景：前者省内存但耗 CPU，后者降低启动后的抖动但要预留内存。
- 总原则是**能不设就不设**：每加一个参数，都要能说出它解决的是哪个观测到的问题。

**代码层面的收益往往大于参数**

- 减少分配：复用缓冲、别在循环里造大集合、用批量拉取代替 N+1。
- 给缓存加上限和淘汰策略。
- 及时释放监听器和线程池。
- 避免 `synchronized` 长临界区，以及阻塞 IO 独占线程；JDK 21 起可以考虑虚拟线程，见 [[专题题库/Java并发#JUC-014：Java 有哪些实现线程安全的手段？|JUC-014：Java 有哪些实现线程安全的手段？]]。

**参数怎么落地到启动命令**

- 位置有讲究：所有 HotSpot 参数必须写在 `-jar app.jar` 或主类之前。写在主类之后，会被当成 `args` 传给程序，不生效。
- 常见形式：`java -Xms4g -Xmx4g -XX:MaxMetaspaceSize=512m -Xss512k -XX:+UseG1GC -XX:MaxGCPauseMillis=200 -XX:ParallelGCThreads=8 -XX:ConcGCThreads=2 -Xlog:gc*:file=logs/gc.log:time,uptime:filecount=5,filesize=20m -jar app.jar`
- 工程上不在命令行里手写，而是走环境变量：
  - 脚本用 `JAVA_OPTS`／`JAVA_TOOL_OPTIONS`，后者由 JVM 自动读取，容器和部分启动器常用。
  - Dockerfile 里 `ENTRYPOINT ["sh","-c","java $JAVA_OPTS -jar app.jar"]`。
  - Kubernetes 用 `env` 注入。
- 容器场景优先 `-XX:MaxRAMPercentage` 按比例给堆，换资源规格时不用改参数。
- GC 线程侧有两个常用旋钮：
  - `ParallelGCThreads`：STW 阶段的并行工作线程数，默认按 CPU 数推导；容器里 CPU 配额小或被其他进程争抢时，可能需要显式设定。
  - `ConcGCThreads`：并发标记阶段的线程数，调高可以换更短的并发阶段，但会抢业务 CPU。
- 版本口径：JDK 9 起统一用 `-Xlog` 这套日志框架，`-XX:+PrintGCDetails`、`-Xloggc` 这类旧参数已经废弃。
- 一个别自相矛盾的点：`-XX:+UseAdaptiveSizePolicy` 这类自动行为，要和手写的 `-Xmn` 一起解释，不能一边说“交给 G1 自适应”，一边又把年轻代固定住。

**能否在运行期改参数**

- 绝大多数启动参数只在 JVM 初始化时读一次，改完必须重启 —— 这也是调优要留发布窗口的原因。
- 运行期能动的只有诊断项和少数实验性开关，例如 `jcmd <pid> GC.heap_hint`、`jcmd <pid> VM.set_flag`（要求该 flag 可管理，而且需要相应权限）、动态调整日志级别。
- 验证参数是否真的生效，用 `jcmd <pid> VM.flags` 或 `VM.command_line`，别靠“应该生效了”。

**验证口径**

- 压测要固定输入分布和并发度，对比同一套指标：P50／P99／P999、吞吐、GC 暂停时长与次数、RSS。只报“感觉快了”不算结论。
- 冷启动和预热（JIT 编译、缓存预热）要单独看，否则会把预热期的抖动算进稳态。

#### 深挖追问

1. **Full GC 频繁怎么定位？**（补充练习）

   两步走，原因不同解法完全不同，不能一律“调大堆”。

   - 先看日志判断触发原因：分配失败、元空间、`System.gc()`、显式调用，还是晋升失败。
   - 再看堆 dump 里老年代被什么占住，同时确认有没有大对象直接进老年代、Survivor 太小导致过早晋升。

2. **`System.gc()` 能禁用吗？**（补充练习）

   能禁，但要留个心眼。

   - `-XX:+DisableExplicitGC` 可以屏蔽显式调用；代价是部分堆外内存（NIO 直接缓冲）本来就依赖显式 GC 来触发清理，禁掉可能造成池外内存堆积。
   - 更稳的做法是 `-XX:+ExplicitGCInvokesConcurrent`：显式调用走并发回收，而不是全堆 STW。

3. **怎么判断该换收集器还是该改代码？**（补充练习）

   看瓶颈性质，两种症状对应两种做法：

   - 存活对象本身就多、回收后老年代降不下来：换收集器只是把问题推后，要改的是分配和缓存策略。
   - 对象生命周期健康，只是单次暂停超过目标：这时候换更现代的收集器、或者调暂停目标才有意义。

### JVM-010：常见的 GC 算法有哪些，回收器随 JDK 版本如何演进？

**常见问法**

- 讲一下你已知的所有 GC 算法，总结一下 GC 算法在不同 JDK 版本中的迭代方向是什么？
- 不同版本的 GC 有什么主要特点（CMS、G1、ZGC）？

#### 面试回答

**判活**：可达性分析，从 GC Roots 出发不可达即可回收。

**基础算法**四种，各说一句代价：

- 标记—清除：不移动对象，但会有碎片。
- 复制：没有碎片，但要空出半区，适合存活率低的年轻代。
- 标记—整理：无碎片也不留空洞，代价是移动和引用更新，比较贵。
- 分代收集：建立在弱分代假说上，年轻代走复制、老年代走标记—整理，跨代引用靠记忆集。

**回收器的演进主线**：从“吞吐优先、整堆长时间 STW”，走向“与用户线程并发、停顿更短且可预测”。

- Serial／Parallel（Serial Old）：单线程／多线程、全程 STW，吞吐优先，适合小堆或批处理。
- CMS：并发标记清除，第一次把停顿压到几十毫秒级；代价是碎片、浮动垃圾和 Concurrent Mode Failure；JDK 9 废弃、JDK 14 移除。
- G1：Region 化的堆＋可预测的停顿目标（`-XX:MaxGCPauseMillis`）＋Mixed GC，JDK 9 起是默认。
- ZGC／Shenandoah：并发标记＋并发整理（ZGC 用着色指针，Shenandoah 用 Brooks 指针），停顿降到亚毫秒，而且基本不随堆大小增长；ZGC 在 JDK 15 生产可用，JDK 21 引入分代 ZGC。

一句话收尾：**迭代主线是“缩短并稳定停顿、支持更大堆、把更多工作放进并发阶段”，同时靠分代和写／读屏障保住并发下的正确性**。

#### 技术细节

**为什么要发明这些新机制**

- 并发回收时，对象图和引用一直在变，所以要多做一层保证：不漏标、不错标。
- CMS 的做法是增量更新，靠重标记阶段修正；G1／ZGC 用 SATB，也就是并发标记期间保留旧引用的快照。
- 并发整理还有另一个难题：对象正在被用户线程访问，怎么安全搬走。ZGC 靠读屏障＋着色指针，在访问的瞬间自愈引用。
- 一句话总结：这些都是“为了并发不停顿”付出的实现复杂度。

**吞吐和延迟是一对权衡**

- 越追求低停顿，屏障和并发阶段吃掉的 CPU 就越多。
- 所以在纯吞吐场景下，Parallel 依然胜过 G1／ZGC。

**近年的方向是分代回归**

- 分代 ZGC 就是这个思路，因为“年轻代快速回收”这条路的收益太大。

**版本口径要记牢，不然容易答错**

- 默认收集器从 JDK 9 起是 G1。
- 分代 ZGC 要到 JDK 21，参数是 `-XX:+UseZGC -XX:+ZGenerational`。
- 具体的默认值和参数，以所用 JDK 版本的文档为准。

#### 深挖追问

1. **G1 相比 CMS 主要改进了什么？**（面经实际出现）

   两处关键改动，都是对着 CMS 的短板来的：

   - G1 用 Region＋复制整理，消掉了 CMS 的碎片问题；再把停顿做成可调目标、按回收价值选回收集（CSet），从而实现“可预测”。
   - 反过来说，CMS 是并发清除、不做整理，也没有停顿目标。

   （详见 [[#JVM-008：CMS 和 G1 有什么区别，各自执行步骤与适用场景？|JVM-008：CMS 和 G1 有什么区别]]）

2. **ZGC 怎么做到停顿不随堆大小增长？**（补充练习）

   因为几乎没有什么“必须扫完整个堆”的停顿阶段：

   - 标记、整理、引用修正这几步，基本都和用户线程并发进行。
   - STW 只剩几个固定的根扫描点，所以停顿时长和堆大小近似无关。
   - 代价是读屏障和染色指针：吞吐会有折损，还要额外付出内存元数据的开销。

### JVM-011：对象在 JVM 中的生命周期是怎样的，何时晋升老年代？

**常见问法**

- 讲一下对象在 JVM 中生命周期。
- 新生代的 S0/S1 有什么用，什么时候要去老年代？

#### 面试回答

**一条生命周期线**

- 出生：`new` 出来的对象先在 Eden 分配，每个线程有自己的 TLAB（Thread Local Allocation Buffer，私有本地分配缓冲），避免抢指针。
- 第一轮 Minor GC：用复制算法把可达对象搬进 Survivor，年龄加 1；年龄记在对象头的 Mark Word 里。
- 之后在两块 Survivor 之间反复熬过若干轮，最后晋升老年代，长期驻留。
- 终点：老年代回收（Full GC，或 G1 的 mixed GC）时，不可达的对象被清除。这期间会经过可达性分析（JVM-002）和 finalize 终结方法 —— 只执行一次、不保证及时，规范已经不鼓励使用。

**晋升老年代的时机，四条缺一条回答就不完整**

- 年龄到了：达到 `MaxTenuringThreshold`，默认 15。
- 动态年龄判定：Survivor 里“年龄小于等于某个值”的对象总空间超过 Survivor 的一半，那么年龄大于等于该值的直接晋升。
- 大对象直达：由 `-XX:PretenureSizeThreshold` 控制（这是 Serial／ParNew 的口径；G1 按 Region 分配，超大数据走 Humongous），目的是省掉在 Survivor 之间的白拷贝。
- Survivor 装不下：Minor GC 之后放不下的，靠分配担保直接进老年代。

**S0／S1 为什么要两块**

- 复制算法要求“从一块活区倒进另一块空区”，两块 Survivor 每轮互换角色。
- 任一时刻恰好有一块是空区，可以容纳幸存者 —— 这就是零碎片、以及 GC 成本只和存活对象数（而不是区域大小）成正比的来源。
- 实践中按弱分代假设定成 Eden:S0:S1＝8:1:1，浪费从理论上的 50% 压到 20%。

#### 技术细节

**对象不一定真的在堆上**

- 逃逸分析开启时（发生在 JIT 层，Server 编译器默认开），不逃逸的对象可以被标量替换彻底拆散成寄存器／栈上的局部量，锁也可能被消除。
- 这时它的生命周期就不再是“入堆、之后可回收”，而是根本不存在。

**年龄不是创建时间的均匀刻度**

- GC 越频繁晋升越快，应用启动期和流量高峰的晋升速率并不一样。
- 调优要看年龄分布直方图：`-XX:+PrintTenuringDistribution`，或者直接看 GC 日志里的 age table。

**From／To 是动态角色**

- Survivor 平时只有一块在用，另一块只在回收那一瞬充当目的地。
- 所以参数里的 From／To 是动态角色，不是 S0／S1 的固定分工；“S0 空了进 S1”只是对某一瞬的描述，不是稳态。

**寿命分布本身就是设计信号**

- 大量对象熬不过第一轮 Minor GC（朝生夕死），说明分配是合理的。
- 大量对象集中卡在年龄 15，说明 Survivor 太小或者 GC 太稀 —— 结果是过早晋升和老年代快速增长。

#### 深挖追问

1. **为什么 Survivor 要两块而不是一块？**（面经实际出现；[[面经/美团/一面/0003#Q10：对象在 JVM 中的生命周期；新生代 S0/S1 的作用与晋升老年代的时机。|MJ037 · 美团 · 一面 · Q10]]）

   因为复制算法要同时做到“把幸存的拷走”和“把死掉的整块清掉”，一块自相似的结构做不到。

   - 必须源区和空区分开：回收时把活对象拷进空区，源区整块清零 —— 顺带天然完成了压缩。
   - 只有一块的话，就只能走滑窗整理（Stevenson／C++ 那种半区方案）或者改用它标记—整理，而这正是复制算法放弃掉的那条路。

2. **Minor GC 后对象在 Survivor 之间如何移动？**（面经实际出现；同上来源）

   从 From 复制进 To，Eden 里活下来的对象也进 To。

   - 一轮结束后角色互换：这一轮的 To 变成下一轮的 From，对象年龄加 1。
   - 如果 To 装满了，超龄或超额的对象就提前晋升，也就是分配担保。

3. **CMS／G1 还讲不讲 Eden/S0/S1？**（补充练习）

   讲，分代语义一直保留，变的只是划分方式：

   - G1 不再有固定的物理分区，Region 动态充当 Eden／Survivor／Old（见 JVM-003）；“晋升”也就变成了对象从 young 角色的 Region 被复制进 old 角色的 Region。
   - 分代版 ZGC（JDK 21 起）同样有年轻代和老年代之分。
