### JVM-001：JVM 运行时内存区域与 Java 内存模型有什么区别？

**常见问法**

- [[面经/美团/一面/0002#Q14：JVM 内存结构介绍一下|MJ032 · 美团 · 一面 · Q14]]
- JVM 内存模型如何理解，垃圾回收算法有哪些？

- Java 如何管理内存，堆与 G1 垃圾回收如何工作？

- Java 的 JVM 内存分成哪些区域？直接内存是由 JVM 管理的吗？哪些区域可能发生 OOM？

#### 面试回答

原文“JVM 内存模型”有歧义。如果问运行时内存区域：线程私有的有程序计数器、虚拟机栈和本地方法栈，共享的有堆和方法区，运行时常量池属于方法区；HotSpot 的元空间是方法区的一种实现。如果问 JMM，则讲共享变量的可见性、有序性与 happens-before，不能用堆栈分区代替。

#### 技术细节

本题按 Java SE 21 规范说明两种可能含义，未确认原面试官意图。虚拟机栈由栈帧组成，含局部变量表、操作数栈等；方法区是规范概念，不能直接等同于某个 HotSpot 实现结构，直接内存也不是规范规定的独立运行时区域。JMM 中 volatile 写与后续读、监视器解锁与后续加锁可建立 happens-before；volatile 不让 i++ 自动成为原子操作。

Java 内存管理不能只看堆：对象与数组通常在堆内分配并由 GC 管理，线程栈、HotSpot 元空间、直接内存和运行时本地分配也消耗进程内存。堆中持续保留无用对象引用会导致逻辑内存泄漏，GC 不能回收仍可达的对象。容器限额应覆盖所有这些开销，Xmx 不是 Java 进程总内存上限。

#### 深挖追问

1. **JMM 和 JVM 运行时数据区是同一件事吗？**（补充练习）

   不是。前者定义线程间内存交互与可见性约束，后者描述 JVM 执行需要的存储区域；原题意图未确认，因此两种解释都标注为回答前提。

2. **Java 内存管理为什么不能只看堆？**（面经实际出现；[[面经/百度/一面/0005#Q18：Java 如何管理内存，堆与 G1 垃圾回收如何工作？|MJ008 · 百度 · 一面 · Q18]]）

   因为堆外区域和线程栈同样占用资源，堆未满时也可能遇到本地内存不足或容器内存限制。

3. **直接内存是由 JVM 管理的吗？**（面经实际出现；[[面经/帆软/二面/0002#Q08：JVM 内存分哪些区域，直接内存由 JVM 管理吗，哪些区域会 OOM？|MJ035 · 帆软 · 二面 · Q08]]）

   分两层：直接内存不是 JVMS 规范的运行时数据区，在堆外，由 native 分配（Unsafe），不存堆里、GC 不移动它；但 DirectByteBuffer 对象在堆上，其 Cleaner 在对象被回收时释放 native 内存，用量还受 -XX:MaxDirectMemorySize 记账限额。所以口径是“JVM 进程分配、GC 间接触发释放”，NIO 分配失败前会先主动 System.gc() 重试。

4. **哪些区域可能发生 OOM？**（面经实际出现；同上来源）

   堆（Java heap space）、虚拟机栈（超 -Xss 一般 StackOverflowError，可动态扩展的实现会抛 OOM）、方法区／元空间（MetaspaceSize 打满或类加载器泄漏）、直接内存（超 MaxDirectMemorySize）、native 线程创建（unable to create new native thread，受 OS 线程数与内存限制）；程序计数器是规范中唯一不抛 OOM 的区域。

### JVM-002：垃圾回收如何判断对象存活，常见回收算法有哪些？

**常见问法**

- JVM 内存模型如何理解，垃圾回收算法有哪些？

- JVM 的垃圾回收机制是什么？

- 能介绍一下 Java 的 GC 机制吗？

#### 面试回答

垃圾回收一般先从 GC Roots 做可达性分析，再采用标记清除、复制或标记整理等算法回收。标记清除不移动存活对象但会留下碎片；复制将存活对象搬到另一块空间，适合存活率较低的区域但需额外空间；标记整理移动存活对象以压缩空间，减少碎片但有搬迁成本。分代收集是按对象寿命组织回收的策略，G1、ZGC 等则是具体收集器，不能混为算法名称。

#### 技术细节

GC Roots 可包括活动线程栈中的引用、类的静态字段引用及 JNI 引用等；具体根集合由 JVM 实现和运行状态决定。引用计数难以直接处理循环引用，不是 Java 堆回收的主要判活方式。并行指多个 GC 线程同时工作，并发指回收阶段可与应用同时运行；并发收集器仍可能包含暂停阶段。选型依据暂停、吞吐、内存占用和堆规模，不能只按“新生代复制、老年代整理”覆盖所有现代收集器。

#### 深挖追问

1. **垃圾回收算法有哪些？**（面经实际出现；[[面经/百度/一面/0003#Q15：JVM 内存模型如何理解，垃圾回收算法有哪些？|MJ006 · 百度 · 一面 · Q15]]）

   常见基础算法是标记清除、复制和标记整理；再区分判活方法、分代策略以及具体收集器的实现组合。

### JVM-003：G1 如何管理堆并完成垃圾回收？

**常见问法**

- G1 如何管理堆并完成垃圾回收？

#### 面试回答

以 HotSpot JDK 21 G1 为例，堆划成多个 Region，逻辑上区分年轻代与老年代，通过并发标记评估存活量，并在暂停中疏散选定区域的存活对象；年轻代回收后还可进行包含部分老年代区域的混合回收。暂停目标是尽力满足，不是硬实时保证，G1 也不是全程无暂停。

#### 技术细节

以 HotSpot JDK 21 为基线，Region 大小相同，年轻代和老年代是逻辑集合而非必须连续。并发标记评估区域存活量，疏散暂停把存活对象复制到其他 Region；混合回收选择年轻代及部分老年代 Region。跨区引用通过 remembered sets 等记录以减少全堆扫描，写屏障参与维护；标记采用 SATB 思路。达到大对象阈值（约半个 Region，边界需结合具体实现）的对象按 humongous 对象处理，可能影响连续空间需求。暂停目标不保证每次达成，疏散空间不足等情况可能触发更昂贵的回收；调优应从 GC 日志、分配速率、存活量和延迟目标出发。

#### 深挖追问

1. **G1 是完全并发、不会暂停吗？**（补充练习）

   不是，并发标记可与应用重叠，但疏散及部分标记阶段需要暂停；目标暂停时间是调度目标而非硬上限。

### JVM-004：JVM 如何实现 Java 的跨平台运行？

**常见问法**

- JVM 跨平台的原理是什么？
- Java 为什么能做到“一次编译，到处运行”？

#### 面试回答

Java 源码通常先编译为平台无关的 class 字节码；各操作系统和硬件平台提供各自实现的 JVM，负责加载、校验并以解释器或 JIT 编译器把字节码转换成本机指令，同时实现规范规定的运行时行为。因此跨平台的是符合约束的字节码与 Java API 语义，JVM 本身仍是平台相关的原生程序。

#### 技术细节

class 文件采用规范定义的二进制格式和指令集，不直接绑定某一 CPU 指令集。类加载器获取类，验证阶段检查格式、类型与控制流等约束；执行引擎可以解释热点尚不明显的代码，再把热点方法 JIT 编译为目标机器码。垃圾回收、线程映射和系统调用由具体 JVM 与操作系统配合实现，但对应用暴露相对统一的 Java 语义。

“一次编译，到处运行”有前提：目标平台要有兼容的 Java 运行环境，代码使用的 Java 版本和依赖要兼容。JNI／JNA、本地动态库、路径分隔符、默认字符集、文件权限、大小写敏感和平台命令都会引入差异；class 文件版本高于运行时支持版本也不能直接运行。

#### 深挖追问

1. **JVM 本身是跨平台的吗？**（补充练习）

   JVM 的规范和行为目标跨平台，但具体 JVM 可执行文件必须针对操作系统和 CPU 构建；同一个 JVM 二进制通常不能直接用于所有平台。

2. **Java 字节码总是被解释执行吗？**（补充练习）

   不是。常见 JVM 会结合解释执行与 JIT，把热点代码编译为本机指令；也可能使用 AOT 等方式，具体策略取决于实现。

### JVM-005：有 GC 的 Java 为什么还会内存泄漏，如何定位？

**常见问法**

- 既然有 GC，为什么还会出现内存泄漏？

#### 面试回答

GC 只回收从 GC Roots 不可达的对象。业务上已无用但仍被可达引用“合法”持有的对象，GC 不会也不该回收，这就是 Java 的内存泄漏（更准确说是“无界留存”）。典型来源：只增不删的集合与本地缓存、未注销的监听器与回调、未关闭的资源、非静态内部类隐式持有外部实例、线程池场景下 ThreadLocal 未 remove、static 集合长期累积、equals／hashCode 实现有误导致 Map 键无法命中删除。另外堆外直接内存、线程栈不受堆 GC 管辖，Xmx 不是进程总内存上限。

#### 技术细节

判断特征：Full GC 后老年代占用持续抬升、回收量越来越小，最终 OOM 或频繁 GC。定位路径：GC 日志确认趋势→`jmap`／在线诊断抓堆转储→MAT 等工具看支配树与 GC Roots 引用链，找到“谁还引用着它”。修复对应持有方：缓存加容量与逐出策略、监听器随生命周期注销、资源用 try-with-resources、ThreadLocal 用完 remove、避免内部类持有外部大对象。这类泄漏不是 GC 算法失效，而是可达性判定与业务“是否还需要”语义不一致；容器 OOM 还要检查堆外、元空间、线程数与 native 内存。

#### 深挖追问

1. **内存泄漏和 OOM 是一回事吗？**（补充练习）

   不是。泄漏是逐渐累积的过程，OOM 是结果之一；泄漏也可能表现为 GC 时间变长、吞吐下降而不一定立刻崩溃。

2. **WeakHashMap／软引用能根治吗？**（补充练习）

   只能缓解特定场景；键值语义、引用队列清理和业务生命周期仍需自己管，误用反而引入难排查的提前回收。

### JVM-006：Java 对象内存大小怎么估算，基本类型占几个字节？

**常见问法**

- Java 对象内存大小怎么估算？
- Java 基本数据类型占用字节大小。

- 怎么计算一个对象的大小？

#### 面试回答

按 HotSpot 64 位、开启压缩指针（默认，堆 <32G）估算：对象头＝Mark Word 8 字节＋压缩类指针 4 字节；实例字段按类型宽度排列（boolean/byte 1、char/short 2、int/float 4、long/double 8），引用类型字段 4 字节；最后补齐到 8 字节对齐。例：一个 int＋一个引用的对象 ≈ 12＋4＋4＝20→24 字节。裸类型宽度是 JVMS 未规定、由实现决定的口径（boolean 字段通常 1 字节、boolean[] 每元素 1 字节），答题注明“以 HotSpot 为例”，实测用 JOL 工具。

#### 技术细节

区分 shallow size（对象自身占用，不含引用目标）与 retained size（含独占引用的整片对象图），堆分析工具报的是后者才能解释“一个集合吃掉半个堆”。数组另有长度字段（通常 4 字节，计入头部后对齐）；String 在 JDK 9+ 用 byte[]＋coder（Latin-1 单字节存储），比 JDK 8 的 char[] 省一半。未开启压缩指针（大堆或 `-XX:-UseCompressedOops`）时引用 8 字节、类指针 8 字节；压缩类指针还有对齐前提。估算用途：容量规划时按“对象数×retained”估堆水位，配合 `-XX:+HeapDumpOnOutOfMemoryError` 与 MAT 验证，不凭字段表心算大对象图。

#### 深挖追问

1. **为什么 long 在 32 位 JVM 上读写可能不原子？**（补充练习）

   64 位值需两次 32 位访问；JVMS 规定 long/double 非原子读写，除非 volatile——这是内存模型条款，与对象大小估算不同层面。

### JVM-007：类加载的过程是什么，双亲委派是什么？

**常见问法**

- 类加载的过程是什么？

#### 面试回答

类加载分五步：加载→验证→准备→解析→初始化（后三步合称链接）。加载：类加载器按字节流（class 文件、jar、网络或运行期生成）读取并在方法区建 Class 对象作为入口；验证：格式、元数据、字节码语义与控制流检查；准备：为类变量分配内存并置零值，编译期常量此时已是终值；解析：符号引用替换为直接引用，动态绑定场景可延后；初始化：执行 `<clinit>`（静态赋值与静态块按书写顺序），由首次主动使用触发，JVM 保证其仅执行一次且线程安全——静态内部类式单例正是利用这一点。查找顺序按双亲委派：Bootstrap→应用类加载器→自定义加载器逐级先问父级，保证核心类不被篡改、类在 JVM 内唯一。

#### 技术细节

“一个类由加载器＋类名共同确定身份”，这是双亲委派的判定口径。启动时机：new、静态字段/方法访问、反射、主类等算主动使用；子类初始化会先触发父类，但经子类引用静态字段不算对子类的使用。双亲委派被“打破”是正常设计而非事故：SPI/线程上下文类加载器（父加载器要加载子路径的 provider 类）、OSGi／模块化容器的网状委派、热部署与 Agent 字节码增强都要自定义委派——面试说“打破”前先说清是哪个场景。同名类被两个加载器各自加载会引发 ClassCastException 与 instanceof 为 false，这是排查线索。JDK 9+ 模块化后内部加载器结构有调整（平台类加载器等），口径按所用版本说明。

#### 深挖追问

1. **创建类／实例化对象有几种方法？**（面经实际出现；[[面经/携程/一面/0001#Q11：创建类有几种方法？|MJ028 · 携程 · 一面 · Q11]]）

   原题有歧义，先确认口径。若问“创建对象”：new（常规路径）、反射 Class／Constructor.newInstance、clone（绕过构造器，需 Cloneable）、反序列化（同样绕过构造器，readObject 需校验）、MethodHandle 等。若问“生成一个新类”：正常编译产出、JDK 动态代理（按接口）／CGLIB（生成子类）、字节码框架 ASM／Javassist／ByteBuddy（AOP 与探针基础）、运行期源码编译（javax.tools.JavaCompiler、Groovy 脚本）。接在类加载语境后多指后者，但两种答案都该备好。

2. **双亲委派为什么不算“严格从顶到底加载”？**（补充练习）

   是“先委托父级尝试”，父级加载不了才自己加载；且存在反向委派（线程上下文类加载器），说成“所有类都由 Bootstrap 加载”是错的。

### JVM-008：CMS 和 G1 有什么区别，各自执行步骤与适用场景？

**常见问法**

- 先说 JVM 垃圾回收，判断垃圾、回收算法、优劣、分代，常见垃圾回收器，CMS 和 G1 的特点和各自执行步骤、各自使用场景。
- CMS 和 G1 怎么选？

#### 面试回答

**判活**用可达性分析：从 GC Roots（活动线程栈上的引用、静态字段、JNI 引用等）向下遍历，不可达即可回收；引用计数难以处理循环引用，不是 Java 堆的判活方式。**算法**三种各有代价：标记—清除不搬对象但产生碎片；复制无碎片、成本与存活对象数成正比，适合存活率低的年轻代，但要牺牲一块空间；标记—整理无碎片且不留空洞，代价是移动与引用更新，暂停更久。**分代**建立在“多数对象朝生夕死”的弱分代假说上：新生代用复制（Eden＋两块 Survivor，Minor GC 只扫年轻区所以快），老年代用标记—整理，跨代引用靠记忆集避免全堆扫描。

**CMS（并发标记清除）**目标是低停顿：① 初始标记——短暂 STW，只标 GC Roots 直接引用的对象；② 并发标记——与用户线程同时遍历引用图；③ 重新标记——再次短暂 STW，修正并发期间变化的引用（增量更新思路）；④ 并发清除——与用户线程并发回收，不移动对象。代价随之而来：并发阶段抢 CPU、要预留堆空间，标记后新产生的**浮动垃圾**只能等下轮，不整理导致**碎片**累积，并发期间分配不过来会触发 Concurrent Mode Failure 退化成单线程 Full GC。它在 JDK 9 被标记废弃（JEP 291）、JDK 14 移除，所以答完要主动说明“现在默认是 G1”，否则显得停在 JDK 8。

**G1**把堆切成等大 Region，年轻／老年代只是逻辑分组；流程是 Young GC →（堆占用达到阈值时）并发标记周期（初始标记借用一次 Young 暂停、并发标记、最终重标记、清理空 Region）→ Mixed GC（一次回收年轻代加一批垃圾最多的老年代 Region，“Garbage First”得名于此）。它靠记忆集控制跨区扫描、用 SATB 保证并发标记正确性，并把**停顿时间做成可调目标**（`MaxGCPauseMillis`，默认约 200ms，是调度目标而非硬上限），适合大堆与延迟敏感的服务，JDK 9 起为默认收集器。代价是复制与写屏障开销、humongous 对象（超过约半个 Region）处理不当会造成空间紧张与额外回收。

**场景**：小堆、吞吐优先的批处理 → Parallel GC；中等以上堆、要控停顿 → G1；要求亚毫秒级暂停的超大堆 → ZGC（JDK 21 起有分代 ZGC）或 Shenandoah。答题顺序建议“判活 → 算法 → 分代 → CMS 步骤与缺陷 → G1 步骤与优势 → 选型”，并说明所用 JDK 版本。

#### 技术细节

两者最容易混的点：CMS 是**并发清除不移动**，所以有碎片、后续可能 Full GC 整理；G1 是**并发标记＋暂停内复制整理**，所以没有碎片问题但每次回收都要搬对象。G1 的“停顿可预测”来自它按 Region 的回收价值（垃圾占比与预测耗时）排序选择回收集（CSet），不是承诺；分配速率突然升高或存活对象过多时会无法满足目标。

观察手段要能说出来：`-Xlog:gc*`（统一日志格式，JDK 9+）看暂停分布与各阶段耗时，`jstat -gcutil` 看代际占比与 GC 次数趋势，`jmap`／`-XX:+HeapDumpOnOutOfMemoryError` 取 dump 用 MAT 分析支配树，`async-profiler` 看分配热点。判断“该不该换收集器”的依据是症状：CMS 频繁 Concurrent Mode Failure 或长 Full GC → 换 G1；G1 暂停目标总达不到且老年代回收效率低 → 检查大对象与分配速率，而不是盲目调小停顿目标。

#### 深挖追问

1. **CMS 为什么需要预留空间，预留多少？**（补充练习）

   并发清除期间用户线程还在分配新对象，这部分“浮动垃圾”本轮不能回收，所以必须留余量；由 `-XX:CMSInitiatingOccupancyFraction`（默认约 68%）决定老年代占用到多少就启动并发收集，配 `-XX:+UseCMSInitiatingOccupancyOnly` 才不被自适应策略覆盖。设太高容易触发并发失败退化，太低则回收频繁、吞吐下降。

2. **G1 的 Mixed GC 什么时候触发，回收哪些 Region？**（补充练习）

   并发标记周期结束后，G1 已知每个 Region 的存活量与回收耗时，于是按暂停目标挑选“价值最高”的一批老年代 Region，连同年轻代一起做疏散回收，几轮 Mixed 后完成一次全堆标记周期的回收；没被选中的 Region 留到下个周期，所以 G1 不追求一次回收整个堆。

3. **为什么 G1 需要写屏障，代价是什么？**（补充练习）

   并发标记期间引用关系在变，需要记录跨 Region 引用（维护记忆集）和标记期间的赋值（SATB 防漏标），这两件事都靠写屏障在堆引用更新时插一段记录逻辑；代价是每条引用赋值多几条指令，且屏障本身占用 CPU——这也是 G1 吞吐通常低于 Parallel 的原因之一。

4. **分代 ZGC 解决了什么问题？**（补充练习）

   非分代 ZGC 对所有对象一视同仁，短命对象的回收成本被摊到全堆，且回收吞吐有限、分配速率高时容易跟不上；分代 ZGC（JDK 21 的 JEP 439）让年轻代走更便宜的路径，提高回收吞吐并降低分配停顿风险。具体是否可用取决于所用 JDK 版本与参数。

### JVM-009：项目部署时 JVM 怎么调优，从哪里入手？

**常见问法**

- 你项目部署的时候，有尝试对 JVM 进行调优吗？
- 线上 JVM 参数怎么定？

- 谈谈你对 JVM 调优的理解，有哪些常见的调优参数或方法？
- 在启动命令中调整 JVM 参数，怎么做？

#### 面试回答

原则是**先测量再改参数，改完必须用同一场景复测**，而不是背一串 `-XX` 选项。四步：① 定目标——这个服务在意的是吞吐、P99 延迟还是内存占用，三者会互相冲突；② 建基线——开 `-Xlog:gc*` 输出 GC 日志，记录暂停分布、GC 频率、老年代增长趋势，同时看进程 RSS 是否接近容器限额；③ 对症处理——堆太小导致频繁 Young GC 或 Full GC 就加大堆并固定 `-Xms=-Xmx` 避免运行中扩容抖动，容器里用 `MaxRAMPercentage` 让堆随限额伸缩而不是写死绝对值；老年代涨不停 → 取 heap dump 找支配对象（无上限缓存、ThreadLocal 未 `remove()`、大集合、静态引用）；Full GC 后老年代几乎不降 → 内存泄漏或 Metaspace 不足；单次暂停过长 → 检查大对象与分配尖峰，考虑换／调 G1 的 `MaxGCPauseMillis`；④ 复测与留档——同压测场景对比 P99、吞吐、GC 暂停与错误率，记下参数与结论，避免下次从头猜。

被问“你实际调过什么”时按真实经历答：【部署形态＋JDK 版本＋改了什么参数或代码＋前后数字】。没有做过线上调优就直说“我只调过堆与 GC 日志、没有做过参数级调优”，然后讲清该看哪些指标——比编一个“把 Xmx 从 512M 调到 2G 效果翻倍”安全得多。

#### 技术细节

**容器里的内存账**：`Xmx` 只是堆上限，进程实际占用还要加元空间、线程栈（线程数 × 栈大小）、直接内存（NIO／Netty 池外）、JIT 代码缓存与 GC 结构开销。容器 OOMKilled 常见原因是这套总开销超过 limit，而堆使用率看着很正常——排查方向是 `-XX:MaxMetaspaceSize`、`-Xss`、直接内存上限（`MaxDirectMemorySize`）与 Netty 池外内存统计，必要时用 Native Memory Tracking（`-XX:NativeMemoryTracking=summary` ＋ `jcmd ... VM.native_memory`）。

**GC 参数的合理默认**：现代 JDK 里 G1 配 `MaxRAMPercentage`（如 50～75）通常比手写分代大小更好；`-Xmn` 固定年轻代会削弱 G1 的自适应，`-XX:NewRatio` 之类要慎用；`-XX:+UseStringDeduplication`、`-XX:+AlwaysPreTouch` 各有适用场景（前者省内存但耗 CPU，后者降低启动后抖动但要预留内存）。原则是**能不设就不设**，每加一个参数都要能说出它解决哪个观测到的问题。

**代码层面的收益往往大于参数**：减少分配（复用缓冲、避免在循环里造大集合、批量拉取代替 N+1）、给缓存加上限与淘汰策略、及时释放监听与线程池、避免 `synchronized` 长临界区与阻塞 IO 独占线程（JDK 21 起可考虑虚拟线程，见 [[专题题库/Java并发#JUC-014：Java 有哪些实现线程安全的手段？|JUC-014：Java 有哪些实现线程安全的手段？]]）。

**参数怎么落地到启动命令**：所有 HotSpot 参数必须写在 `-jar app.jar` 或主类之前——写在主类之后会被当成 `args` 传给程序而不生效。常见形式：`java -Xms4g -Xmx4g -XX:MaxMetaspaceSize=512m -Xss512k -XX:+UseG1GC -XX:MaxGCPauseMillis=200 -XX:ParallelGCThreads=8 -XX:ConcGCThreads=2 -Xlog:gc*:file=logs/gc.log:time,uptime:filecount=5,filesize=20m -jar app.jar`。工程上不在命令行里手写，而是走环境变量：脚本用 `JAVA_OPTS`／`JAVA_TOOL_OPTIONS`（后者由 JVM 自动读取，容器与部分启动器常用），Dockerfile 里 `ENTRYPOINT ["sh","-c","java $JAVA_OPTS -jar app.jar"]`，Kubernetes 用 `env` 注入；容器场景优先 `-XX:MaxRAMPercentage` 按比例给堆，换资源规格时不必改参数。GC 线程侧的两个常用旋钮：`ParallelGCThreads`（STW 阶段并行工作线程数，默认按 CPU 数推导，容器里 CPU 配额小或被其他进程争抢时可能需要显式设定）与 `ConcGCThreads`（并发标记阶段线程数，调高换更短的并发阶段但抢业务 CPU）。版本口径：JDK 9 起统一用 `-Xlog` 统一日志框架，`-XX:+PrintGCDetails`、`-Xloggc` 这类旧参数已废弃；`-XX:+UseAdaptiveSizePolicy` 之类的自动行为要与手写 `-Xmn` 一起解释，避免一边说“交给 G1 自适应”一边又固定年轻代。

**能否在运行期改参数**：绝大多数启动参数只在 JVM 初始化时读取，改完必须重启（这也是调优要留发布窗口的原因）；运行期可动的只有诊断与少数实验性开关，例如 `jcmd <pid> GC.heap_hint`、`jcmd <pid> VM.set_flag`（要求该 flag 可管理且需相应权限）、动态调整日志级别等。验证参数是否真的生效用 `jcmd <pid> VM.flags` 或 `VM.command_line`，别靠“应该生效了”。

**验证口径**：压测要固定输入分布与并发度，对比同指标（P50／P99／P999、吞吐、GC 暂停时长与次数、RSS）；只报“感觉快了”不算结论。冷启动与预热（JIT 编译、缓存预热）要单独看，否则会把预热期的抖动算进稳态。

#### 深挖追问

1. **Full GC 频繁怎么定位？**（补充练习）

   先看日志判断触发原因（分配失败、元空间、`System.gc()`、显式调用或晋升失败），再看堆 dump 里老年代被什么占住，以及是否有大对象直接进老年代、Survivor 太小导致过早晋升。原因不同解法完全不同，不能一律“调大堆”。

2. **`System.gc()` 能禁用吗？**（补充练习）

   `-XX:+DisableExplicitGC` 可以屏蔽显式调用，但部分堆外内存（NIO 直接缓冲）依赖显式 GC 触发清理，禁掉可能造成池外内存堆积；更稳的做法是 `-XX:+ExplicitGCInvokesConcurrent`，让显式调用走并发回收而不是全堆 STW。

3. **怎么判断该换收集器还是该改代码？**（补充练习）

   看瓶颈性质：如果存活对象本身就多、回收后老年代降不下来，换收集器只会把问题推后，要改分配与缓存策略；如果对象生命周期健康、只是单次暂停超目标，换更现代的收集器或调暂停目标才有意义。

### JVM-010：常见的 GC 算法有哪些，回收器随 JDK 版本如何演进？

**常见问法**

- 讲一下你已知的所有 GC 算法，总结一下 GC 算法在不同 JDK 版本中的迭代方向是什么？
- 不同版本的 GC 有什么主要特点（CMS、G1、ZGC）？

#### 面试回答

**判活**用可达性分析（GC Roots 出发不可达即可回收）。**基础算法**四种：标记—清除（不移动但有碎片）、复制（无碎片、要空出半区、适合低存活年轻代）、标记—整理（无碎片不留空洞、移动与引用更新贵）、分代收集（弱分代假说：年轻代复制＋老年代标记—整理，跨代引用靠记忆集）。**回收器演进方向**：从“吞吐优先、整堆长时间 STW”走向“与用户线程并发、停顿更短且可预测”。

- Serial／Parallel（Serial Old）：单线程／多线程、全程 STW，吞吐优先，适合小堆或批处理。
- CMS：并发标记清除，首次把停顿压到几十毫秒级，代价是碎片、浮动垃圾、Concurrent Mode Failure；JDK 9 废弃、14 移除。
- G1：Region 化堆＋可预测停顿目标（`-XX:MaxGCPauseMillis`）＋Mixed GC，JDK 9 起默认。
- ZGC／Shenandoah：并发标记—并发整理（ZGC 用着色指针、Shenandoah 用 Brooks 指针），停顿降到亚毫秒且基本不随堆大小增长；ZGC 在 JDK 15 生产可用、JDK 21 引入分代 ZGC。

一句话收尾：**迭代主线是“缩短并稳定停顿、支持更大堆、把更多工作放到并发阶段”，同时用分代与写/读屏障保住并发正确性**。

#### 技术细节

演进为什么需要新机制：并发回收时对象图和引用在变，要额外保证不漏标不错标——CMS 用增量更新（重标记修正），G1/ZGC 用 SATB（并发标记期间保留旧引用快照）；并发整理需要能把正在被用户线程访问的对象安全搬走——ZGC 靠读屏障＋着色指针在访问时自愈引用。这些都是“为了并发不停顿”付出的实现复杂度。吞吐与延迟是一对权衡：越追求低停顿，屏障与并发阶段吃的 CPU 越多，Parallel 在纯吞吐场景仍胜过 G1/ZGC。分代回归是近年的方向（分代 ZGC），因为“年轻代快速回收”这条路收益太大。

版本口径要记牢以免答错：默认收集器在 JDK 9 起为 G1；`-XX:+UseZGC -XX:+ZGenerational` 到 JDK 21 才有分代 ZGC；具体默认与参数以所用 JDK 版本文档为准。

#### 深挖追问

1. **G1 相比 CMS 主要改进了什么？**（面经实际出现）

   G1 用 Region＋复制整理消除 CMS 的碎片问题，并把停顿做成可调目标、按回收价值选集（CSet）实现可预测；CMS 并发清除不整理、无停顿目标。（详见 [[#JVM-008：CMS 和 G1 有什么区别，各自执行步骤与适用场景？|JVM-008：CMS 和 G1 有什么区别]]）

2. **ZGC 怎么做到停顿不随堆大小增长？**（补充练习）

   把标记、整理、引用修正几乎全部与用户线程并发，STW 只在几个固定根扫描点，停顿与堆大小近似无关；代价是读屏障与染色指针带来的吞吐折损和内存元数据开销。

### JVM-011：对象在 JVM 中的生命周期是怎样的，何时晋升老年代？

**常见问法**

- 讲一下对象在 JVM 中生命周期。
- 新生代的 S0/S1 有什么用，什么时候要去老年代？

#### 面试回答

一条生命周期线：`new` 出来的对象先在 Eden 分配（每线程有 TLAB 私有的本地分配缓冲，避免指针竞争）；Minor GC 用复制算法把可达对象搬进 Survivor 并把年龄＋1（年龄记在对象头 Mark Word）；在 Survivor 之间反复熬过若干轮后晋升老年代，长期驻留；老年代回收（Full GC 或 G1 的 mixed GC）时不可达即被清除，期间经历可达性分析（JVM-002）与 finalize 终结（仅一次、不保证及时，规范已不鼓励）。晋升老年代的时机有四条，缺一条回答就不完整：① 年龄达到 MaxTenuringThreshold（默认 15）；② 动态年龄判定——Survivor 中“年龄≤某值”的对象总空间超过 Survivor 一半，≥该年龄的直接晋升；③ 大对象直达（`-XX:PretenureSizeThreshold`，Serial／ParNew 口径；G1 按 Region 分配、超大数据进 Humongous），防其在 Survivor 间白拷贝；④ Minor GC 后 Survivor 放不下，靠分配担保直接进老年。S0/S1 的作用：复制算法要求“从一块活区倒进另一块空区”，两块 Survivor 每轮互换了角色——任一时刻恰有一块为空区可容纳幸存者，这就是零碎片、GC 成本只与存活对象数（而非区大小）成正比的来源；实践按弱分代假设定 Eden:S0:S1＝8:1:1，浪费从理论 50% 压到 20%。

#### 技术细节

- 对象并非一定在堆上：逃逸分析开启（JIT 层，Server 编译器默认开）时，不逃逸对象可被标量替换彻底拆散成寄存器／栈上局部量、锁可被消除——生命周期从“入堆可回收”变为“根本不存在”。
- 年龄≠创建时间均匀刻度：GC 频繁时晋升快，应用启动期与流量高峰的晋升速率不同，调优看“年龄分布直方图”（`-XX:+PrintTenuringDistribution`／GC 日志中的 age table）。
- Survivor 只有一个在用、另一个在回收瞬间充当目的地，参数里 From/To 是动态角色，不是 S0/S1 固定分工；说“S0 空了进 S1”是对一瞬的描述，不是稳态。
- “对象寿命分布”是设计信号：大量对象熬不过第一轮 Minor GC（朝生夕死）说明分配合理；大量对象集中卡在年龄 15 说明 Survivor 太小或 GC 太稀，会制造过早晋升与老年代快速增长。

#### 深挖追问

1. **为什么 Survivor 要两块而不是一块？**（面经实际出现；[[面经/美团/一面/0003#Q10：对象在 JVM 中的生命周期；新生代 S0/S1 的作用与晋升老年代的时机。|MJ037 · 美团 · 一面 · Q10]]）

   一块自相似结构做不到“原地复制幸存、整体清空死区”：需要源区与空区分离，回收时把活对象拷到空区、源区整块清零，同时天然完成压缩。单区方案只能滑窗整理（Stevenson/C++ 式半区）或转向标记—整理，正是复制算法放弃了的那条路。

2. **Minor GC 后对象在 Survivor 之间如何移动？**（面经实际出现；同上来源）

   从 From 复制进 To（Eden 存活者也进 To），随后 To 成为下轮 From——年龄＋1、区角色互换；To 满则超龄或超额对象提前晋升（分配担保）。

3. **CMS／G1 还讲不讲 Eden/S0/S1？**（补充练习）

   讲，分代语义保留；G1 不再固定物理划分，Region 动态充当 Eden／Survivor／Old（JVM-003），“晋升”变成对象从 young 角色 Region 复制进 old 角色 Region；ZGC 分代版（JDK 21 起）同样有年轻／老年之分。
