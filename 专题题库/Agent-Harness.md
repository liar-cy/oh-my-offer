### HARNESS-001：什么是上下文工程，项目中如何落地？

**常见问法**

- 有没有涉及上下文工程？

- Agent 的上下文一般由哪些内容组成？
- 上下文过长时如何继续对话，怎样有重点地压缩？

- 项目的上下文如何设计？

- Agent 开发如何控制上下文长度？

#### 面试回答

上下文工程就一句话：为模型的每次调用选择、组织和维护所需的信息。它管的内容包括：

- 指令、用户问题、对话历史。
- 检索证据、工具结果、任务状态。

我的做法：

- 按任务预算选相关内容。
- 压缩长历史，但保留关键事实和来源。
- 控制工具输出长度。

实际经历要说明自己做过哪一部分、怎样验证效果。

#### 技术细节

**先分清“窗口容量”和“有效利用能力”**

- 把稳定规则、当前目标、约束、证据和工具结果分区组织。
- 对旧历史做摘要时，保留决策及未完成事项；完整事实交给外部状态存储承载。
- 工具输出可以分页、截断，并给可回查标识。
- 检索文档属于数据，不应自动提升为高优先级指令。

**上下文的组成**

- 指令、目标、历史、Skill、工具定义及结果、检索证据、计划状态和召回记忆。
- 外部持久数据只有被加载后才进入模型窗口。

**预算与保留优先级**

- 预算要预留输出与工具往返的空间。
- 优先保留：目标、约束、有效授权范围、关键标识、决定、未完成项、失败原因、证据入口。
- 可删减：重复讨论与可回查的长输出。

**摘要怎么写、怎么用**

- 用结构化摘要加近期消息继续，保留工具调用和结果的关联。
- 事实、假设、已执行与待执行应明确区分。
- 摘要后回读关键状态，避免递归摘要造成事实漂移。

**评测口径**

- 覆盖长会话中的信息遗漏、冲突指令、引用正确率和 token 成本。

#### 深挖追问

1. **它和提示词工程有什么区别？**（补充练习）

   提示词工程侧重指令表达；上下文工程还包括检索、状态、记忆、工具输出和生命周期管理。

2. **摘要会丢信息怎么办？**（补充练习）

   保留原记录的回查入口，对金额、ID、条件等结构化保存，摘要只承担导航和压缩作用。

3. **Agent 上下文有哪些内容？**（面经实际出现；[[面经/百度/一面/0004#Q10：Agent 的上下文一般由哪些内容组成？|MJ007 · 百度 · 一面 · Q10]]）

   通常包括：

   - 系统和开发者指令、当前用户目标、相关对话历史。
   - 已加载的 Skill、工具定义与调用结果。
   - 文件或检索证据、任务计划和状态，以及按需召回的记忆。

   两条边界要划清：

   - 区分模型当前实际收到的内容与系统外部保存的完整历史：有文件或数据库，不代表其内容已在窗口里。
   - 保留来源和指令层级：让外部资料作为证据，而非自动成为高优先级指令。

4. **内容过长时如何继续，多种信息要如何有重点地压缩？**（面经实际出现；[[面经/百度/一面/0004#Q11：上下文过长时如何继续对话，怎样有重点地压缩？|MJ007 · 百度 · 一面 · Q11]]）

   会在耗尽窗口前按 token 预算处理，并预留输出和工具往返空间。顺序分两步：

   - 第一步管加载：按需加载文件与工具定义，限制检索数量，分页或缩减冗长工具输出。
   - 第二步做摘要：对旧对话做结构化摘要，结合近期消息与外部状态继续会话。

   压缩不能一视同仁：

   - 优先保留：当前目标、用户约束、有效授权范围、关键事实和标识、已做决定、未完成事项、失败原因及证据入口。
   - 可以缩减：重复讨论和可重新读取的长日志。

   摘要的写法和验证：

   - 区分已完成与计划、事实与推测，保留工具请求与结果的关联。
   - 重新读取关键状态、验证后再继续。
   - 底线：压缩只能降低信息损失风险，不能保证无限无损对话。

### HARNESS-002：如何比较 OpenCode、Claude Code、Codex 与模型 API 的上下文机制？

**常见问法**

- OpenCode、Claude Code、Codex、DeepSeek 的上下文机制有什么差异？

- Claude Code 的 memory 和上下文是怎么做的？

#### 面试回答

先区分产品层次：

- OpenCode、Claude Code、Codex 是带运行循环和上下文管理的编码 Agent 产品。
- “DeepSeek”未说明具体产品，这里暂按模型 API 理解。

各家机制（按 2026-09-13 查到的滚动官方文档）：

- OpenCode：有 compaction.auto、prune、reserved 等配置。
- Claude Code：会清理旧工具输出并按需摘要，支持 /compact 指定关注内容。
- Codex：有 model_auto_compact_token_limit 自动压缩阈值配置。

两句纪律：

- 模型 API 的上下文窗口与缓存能力，不能直接当作 Agent 的摘要、状态恢复和长期记忆机制。
- DeepSeek 指代及具体上下文实现待确认，不猜测其内部压缩算法。

#### 技术细节

比较维度包括加载入口、预算与触发条件、压缩对象、持久状态、恢复方式和可配置项。以下是官方滚动文档在 2026-09-13 的查证快照，不代表面试时版本或候选人已使用。

| 对象 | 已查证机制与边界 |
| --- | --- |
| OpenCode | compaction.auto 控制自动压缩，prune 控制旧工具输出清理，reserved 留出压缩缓冲；默认值随版本核对。 |
| Claude Code | 靠近窗口上限时先清理旧工具输出，再按需摘要；/compact 可提供压缩关注点，长期规则可放 CLAUDE.md。 |
| Codex | model_auto_compact_token_limit 配置自动历史压缩阈值；具体压缩实现取决于产品与模型提供方，不能假设只是普通文本摘要。 |
| DeepSeek | 原文指代不明。模型 API、聊天产品及第三方接入它的 Agent 不是同一个层次；具体产品、版本和机制待确认。 |

通用概念上，分清三件事：

- 前缀缓存：复用计算。
- 语义压缩：减少或重表达输入。
- 长期记忆：跨会话保存可检索信息。

三者不能互相替代。DeepSeek 官方缓存页本次未能读取全文，故不据此断言具体行为。

#### 深挖追问

1. **这些对象都能直接称为 Agent 框架吗？**（补充练习）

   不能。先确定是编码 Agent 产品、编排库还是模型 API，再在同一层次比较；否则会把宿主能力误归给底层模型。

### HARNESS-003：Memory 与外部知识如何接入、检索及更新冲突事实？

**常见问法**

- [[面经/美团/一面/0002#Q08：记忆是怎么实现的，补充的上下文介绍一下（RAG）|MJ032 · 美团 · 一面 · Q08]]
- 当前 Skill 是否使用 Memory 或第三方知识？
- Memory 如何检索和更新，用户从北京搬到上海后怎样处理旧记录？

- 记忆怎么按需读取？

- 长短期记忆是怎么做的，记忆怎么存、粒度多少、怎么用？

- Agent 的会话记忆、短期长期记忆是如何持久化存储的？
- 用户偏好是如何提取的？

#### 面试回答

实际接入情况未知，应分别填写【会话状态存储】、【跨会话 Memory】和【第三方知识来源及检索方式】。先把两个“不自动等于”说清：

- Skill 自带参考文档属于可加载知识，不自动等于会学习更新的 Memory。
- 工具取回的日志是当前证据，也不自动成为长期记忆。

如果尚未接入就明确说明。若已接入，应描述：何时检索、身份与权限过滤、如何注入当前上下文、来源与版本，以及哪些内容允许持久保存。

检索和更新我会这样讲：

- 召回：先按用户身份、记忆类型和有效时间过滤，再结合关键词、语义相关性及可信度，不只按向量相似度。
- 更新冲突事实：用户明确说已搬到上海后，把“当前居住城市”更新为上海，给北京记录设置失效状态或结束时间；若业务需要且允许保留历史，保存它作为过去居住记录。
- 别过度解读：只说去上海出差不能覆盖居住地，生效日期不明也不要编造。
- 写入纪律：做去重、冲突判断及版本控制；更新后同步检索索引和缓存，避免旧北京记录继续作为现状返回。
- 长期记忆还应支持用户纠正和删除。

#### 技术细节

以下是设计方案，非某框架强制标准。

**先分三类数据**

- 会话短期状态、跨会话用户事实及偏好、第三方领域知识。

**长期事实怎么存**

- 可保存 user_id、属性、值、来源、记录时间、有效起止时间、状态和版本。
- 注意：记录时间不等于事实生效时间。

**检索路径**

- 先按身份权限与有效性过滤。
- 结构化属性可直接查当前值；非结构化经历可混合召回并重排。
- 按预算注入相关内容，并保留来源。

**写入路径**

- 先抽取候选事实，再核对实体、语义与冲突，做幂等更新。
- 必要时用事务或版本比较，避免并发覆盖。

**冲突更新示例**

- 用户明确搬家后：北京事实置为历史、上海置为当前。
- 只知搬家事实却不知道日期：记录未知，不杜撰日期。

**变更之后**

- 同步索引与缓存；对用户删除请求，也要处理派生索引。

#### 深挖追问

1. **用户从北京搬到上海后，原来的北京信息怎么办？**（面经实际出现；[[面经/百度/一面/0004#Q14：Memory 如何检索和更新，用户从北京搬到上海后怎样处理旧记录？|MJ007 · 百度 · 一面 · Q14]]）

   当前居住地应变为上海，北京不再参与当前事实检索；历史是否保留取决于用途和保存策略。出差、旅游或含糊表述不能当作搬家。

2. **记忆怎么按需读取？**（面经实际出现；[[面经/字节/一面/0004#Q06：记忆怎么按需读取？|MJ014 · 字节 · 一面 · Q06]]）

   核心是不全量注入：

   - 召回：先按用户身份、记忆类型和有效性强过滤，再用关键词与语义混合召回、重排取前几条。
   - 注入：按当前任务的 token 预算来，保留来源和生效时间；长尾内容只给摘要与回查句柄，需要时再读取全文。
   - 捷径：结构化当前属性（如所在地、语言偏好）可直接查键值，不必走向量检索。
   - 维护：记忆更新后要同步重建索引与缓存，避免旧事实继续命中。

3. **用户偏好是如何提取的？**（面经实际出现；[[面经/字节/一面/0004#Q02：模型选用、鉴权、上下文处理、偏好提取、记忆系统与主流 Agent 实现方案如何设计？|MJ014 · 字节 · 一面 · Q02]]）

   - 流程：会话后从对话中抽取候选偏好，经去重、实体与冲突校验后写入，记录来源、生效时间和版本。
   - 门槛：一次性表达、上下文依赖强的说法不升级为长期偏好，需要用户明确或反复表达才持久化。
   - 纪律：写入应幂等，允许用户查询、纠正和删除；抽取质量要用样例评测验证。
   - 具体项目实现方式待补充。

4. **记忆是怎么实现的，补充的上下文介绍一下？**（面经实际出现；[[面经/美团/一面/0002#Q08：记忆是怎么实现的，补充的上下文介绍一下（RAG）|MJ032 · 美团 · 一面 · Q08]]）

   分两层说：

   - 会话内记忆：历史＋中间结果按 token 预算裁剪。保留系统指令、最近若干轮与被引用的关键结论；超预算时摘要压缩或丢弃，必要时用结构化笔记保住硬约束。
   - 跨会话记忆：写进外部存储（向量库＋键值／关系表），按相关性召回注入。冲突事实要带时间与来源，更新时覆盖当前值但保留历史版本，避免模型同时看到矛盾内容。

   补充的上下文走 RAG 链路：切块保留语义边界 → 向量化 → 查询改写与召回 → 重排取 top-k → 带出处拼装进 prompt。注入要控量并留预算给工具返回，否则无关片段会稀释指令。

   项目实际口径按【存储、切块策略、召回条数、token 预算】填。

### HARNESS-004：如何从零设计 Coding Agent？

**常见问法**

- 如何设计类似 cc 或 code 的 Coding Agent？
- 从零设计 Coding Agent 会怎么做？

- 让你实现一个类似 Copilot 的代码生成工具，大致思路是怎样的？如何让它达到较高的准确度？

#### 面试回答

先确定三件事：编码任务、仓库范围、验收方式。再搭闭环：

- 工具链：读取与搜索代码、生成补丁、执行构建测试、检查 diff。
- 分工：模型负责提出动作；运行时管理上下文、执行权限、任务状态与预算。
- 迭代：每次改动根据测试和实际行为反馈继续修。

#### 技术细节

**最小实现怎么起步**

- 从单任务单工作目录开始，加入文件工具、受约束的命令执行、版本差异查看及任务恢复记录。
- 上下文优先放需求、项目规则、相关代码与失败输出。
- 工具运行应隔离依赖和凭据。

**验收怎么看**

- 同时看需求满足、回归和修改范围，不能只看测试退出码。

**表述边界**

- 原图“cc 或 code”指代未确认，不据此声称复刻某产品内部实现。

#### 三种产品形态要先分清（被问“做一个类 Copilot 的代码生成工具”时）

行内补全、对话式生成、Agent 式改造是三档不同的工程约束：

- 行内补全：要求在几十到几百毫秒内出结果、输入窗口小、以采纳率衡量好坏。核心技术是上下文选择（光标前后、当前文件、仓库内相关片段、最近编辑历史）、fill-in-the-middle 式前后文编码、候选缓存与前缀复用、超时与取消——用户继续敲键就要丢弃上一次请求。
- 对话式生成：容忍秒级。重点是把需求转成可验收的规格并输出 diff。
- Agent 式改造：容忍分钟级。靠“读—改—跑—验”闭环与测试反馈保证正确性。

答“怎么提高准确度”时按四件事组织：

- 上下文质量：检索对的相关代码与项目规范，比塞满窗口重要。
- 输出协议与修改范围约束：只改该改的、禁止顺手重构。
- 可执行验证：编译、lint、单测、沙箱运行，不通过不交付。
- 反馈闭环与评测：离线任务集加线上采纳率与构建通过率，被拒与回滚样本回流；重点盯幻觉 API（调用不存在的接口）这类高频错误。

指标上补全看采纳率与留存、Agent 看任务成功率与回归，两者不可混用。

#### 深挖追问

1. **如何处理长任务？**（补充练习）

   保存已完成步骤、证据位置、未解决错误和当前代码状态；摘要后回读关键文件再继续。

2. **code-generation 是怎么做的，如何确保准确性？**（面经实际出现；[[面经/字节/轮次未知/0001#Q29：code-generation 是怎么做的，如何确保准确性？|MJ021 · 字节 · 轮次未知 · Q29]]）

   闭环一口气讲完：需求 → 上下文构建（相关文件、接口签名、项目规范）→ 按 diff／完整文件协议生成 → 可执行验证（编译、lint、单测、沙箱运行）→ 失败信息回传迭代修复 → 人工 review 兜底。

   准确性的关键不是换更强模型，而是“能跑测试绝不靠肉眼”：验证不通过不交付；同时约束修改范围，防止顺手重构引入回归。

3. **Harness 分为哪些模块，除了 runtime 还有什么？**（面经实际出现；[[面经/字节/一面/0007#Q05：Harness 分为哪些模块，除了 runtime 还有什么，比如评测？|MJ026 · 字节 · 一面 · Q05]]）

   六块：

   - 运行时/循环：上下文组装、动作解析、工具执行、状态与预算。
   - 上下文管理：压缩、按需加载、检索注入。
   - 工具与权限：schema 校验、鉴权、沙箱、结果校验。
   - 状态与记忆：会话持久化、检查点恢复、长期记忆。
   - 评测：任务集、指标、回归与线上反馈闭环。
   - 可观测与治理：轨迹、成本、延迟、告警。

   评测与可观测常被低估，但决定迭代速度——没有评测的 harness 改动全凭感觉。

4. **做行内代码补全和做 Coding Agent，工程难点有什么不同？**（面经实际出现；[[面经/阿里国际/二面/0001#Q14：让你实现一个类似 Copilot 的代码生成工具，大致思路是怎样的？如何让它达到较高的准确度？|MJ038 · 阿里国际 · 二面 · Q14]]）

   难点不在同一处：

   - 补全：难在延迟与上下文预算——要在几十到几百毫秒内出结果，靠窗口选择、缓存与前缀复用、流式输出与请求取消；评价用采纳率。
   - Agent：难在状态与验证——多步循环、工具权限、失败回退与回归判定；评价用任务成功率。

   答“提高准确度”不要只说换更大模型：可执行验证（编译、测试、沙箱）与修改范围约束的收益远大于堆模型。

### HARNESS-005：如何隔离多个 Agent 任务的上下文？

**常见问法**

- 多任务之间如何隔离上下文？

- 平台访问量变大，如何避免不同用户会话互相干扰？

#### 面试回答

- 按租户、用户、会话和任务建立独立状态命名空间，每次只加载该身份有权访问的记录；共享知识只读或明确授权。
- 别只想到消息历史：消息历史分开还不够，缓存、检索、临时文件、工具会话和回调也必须绑定任务。

#### 技术细节

**任务标识与验证**

- 异步消息携带可信任务标识，并在服务端验证；不能接受模型随意指定别人的 taskId。

**并发与清理**

- 并发更新用版本号或事务，防止旧结果覆盖新状态。
- 任务完成后清理临时资源。

**共享的边界**

- 共享记忆需明确可见范围。
- 线程局部变量无法独立解决跨进程与持久存储隔离。

#### 深挖追问

1. **只给 Prompt 写“不要混淆任务”够吗？**（补充练习）

   不够，权限过滤和存储隔离要由应用执行，并测试跨任务检索与回调。

### HARNESS-006：Agent 记忆系统用 Redis 有什么好处，边界在哪里？

**常见问法**

- 记忆系统为什么用 Redis，有什么好处？

#### 面试回答

Redis 适合作为记忆的低延迟热层：

- 读写在内存完成，时延稳定，支持 TTL 自动过期。
- 数据结构贴合会话状态的访问模式：String 存序列化的近期消息、Hash 存属性型偏好、ZSet 按时间或重要性排序、Set／Stream 做标签与事件。
- 多个 Agent 实例可共享同一份状态。

后半句要诚实：项目是否真的只用 Redis，需按【实际存储架构】说明。如果只有 Redis，应讲清它承担哪一层，不暗示它具备向量检索等原生没有的能力。

#### 技术细节

**Redis 合适放什么**

- 会话短期状态：近期消息、任务上下文、锁与限流计数。
- 键按租户/用户/会话/任务分命名空间，配合过期时间控制容量，见 [[专题题库/Agent-Harness#HARNESS-005：如何隔离多个 Agent 任务的上下文？|HARNESS-005：如何隔离多个 Agent 任务的上下文？]]。

**Redis 不擅长的地方**

- 语义检索需向量相似度；Redis 的向量搜索是较新的模块能力，是否满足召回要求要与专用方案对比验证。
- 跨会话长期事实更稳的做法：数据库（或带版本的记录）保存主数据、可重建的索引层做检索，Redis 只作缓存加速。

**持久化边界**

- RDB 有丢失窗口；AOF 重放慢且体积大。
- maxmemory 淘汰策略可能把未落盘的记忆直接驱逐。
- 宕机后从 Redis 恢复的能力受持久化配置约束，见 [[专题题库/系统设计#SYS-012：服务器宕机如何发现与恢复，Agent 宕机有何不同？|SYS-012：服务器宕机如何发现与恢复，Agent 宕机有何不同？]]。

选型按数据生命周期、访问模式、容量与一致性要求比较，不因为“快”就把所有层都塞进 Redis。

#### 深挖追问

1. **只用 Redis 存长期记忆有什么风险？**（补充练习）

   语义检索、按内容查询和历史版本管理都要自建或用外部系统；持久化与淘汰策略可能丢数据，主数据建议放可查询、可备份的存储。

2. **Redis 里记忆条目怎么组织？**（补充练习）

   按命名空间键存结构化条目并设 TTL；需要检索时维护可重建的索引，键里保留用户与任务标识供服务端权限过滤。

### HARNESS-007：用户修改历史对话时如何做增量更新与缓存复用？

**常见问法**

- 用户中途修改历史对话，如何实现增量更新，避免全部重新跑一遍？缓存复用的设计思路？

#### 面试回答

把会话从“一条线性文本”改成“带依赖的图”：

- 消息按 ID 存储并支持版本／分支。
- 每个派生物都登记它依赖哪些消息：分段摘要、检索索引块、Agent 中间状态与检查点、已生成产物。

修改一条历史消息时做依赖驱动失效，只有受影响子树重算：

- 摘要只重算覆盖该消息的段。
- 向量索引只重建变更 chunk。
- Agent 从对应检查点续跑；未受影响的直接复用。

缓存这一层：键用输入内容哈希（含版本），Prompt 前缀缓存命中到分叉点为止；重算任务幂等、限流排队，避免一次编辑触发全链路风暴。

#### 技术细节

**前提：把“派生”变成显式记录**

- 每个派生条目存 source_message_ids＋input_hash。
- 修改后按引用关系反查失效集，而不是靠时间戳猜。

**分支语义先与产品对齐**

- 修改历史是替换原分支，还是产生新分支（类 ChatGPT 编辑消息）？
- 旧分支的缓存与索引可延迟清理，但要能回滚。

**重放的坑**

- 重放 Agent 步骤时，外部副作用不可简单重跑：从检查点恢复前先核对副作用状态（见 [[专题题库/Agent开发#AGENT-014：Agent 工作流故障如何定位和恢复？|AGENT-014：Agent 工作流故障如何定位和恢复？]]）。

**摘要结构要能局部重组**

- 长会话的分段摘要设计成每段独立、顶层摘要引用段结果；否则一处改动连锁全部重算。

#### 深挖追问

1. **为什么不干脆每次全量重算？**（补充练习）

   小会话可行且更简单；长链路、多派生物或重算含昂贵模型调用/外部副作用时，全量重算的时延、成本与风险都不可接受，才需要依赖失效设计。

### HARNESS-008：什么是 Agent Harness，它解决什么问题？

**常见问法**

- 什么是 Agent Harness，它解决什么问题？
- 同一模型，为什么不同 Agent 产品表现差很多？

#### 面试回答

Agent Harness（也叫 agent loop／脚手架／运行框架）是包在大模型外面的那层工程系统——它不负责“聪明”，负责让不够稳定、会出错、按量计费的模型能被可靠地驱动去干活。

模型只是一个“输入文本→输出文本”的函数，没有手、没有记忆、不会自己重试。Harness 就是给它装上手和神经系统，核心职责：

- 上下文管理：组装 system prompt、工具定义、历史、检索结果，控窗口大小与缓存复用。
- 循环编排：驱动“模型→工具→观察→再模型”的回合，管终止条件、预算和防原地打转。
- 工具执行：解析模型给出的调用意图，校验参数、鉴权、真正执行、把结果结构化回填。
- 状态与记忆：跨步骤／跨会话保存进度与事实。
- 观测、容错与恢复：记录每一步、失败重试、可暂停恢复。
- 成本与延迟控制：限流、路由、缓存。

一句话收口：模型决定“能力上限”，Harness 决定“实际能用出来多少”——同一模型换个 Harness，产品体验可能天差地别。

#### 技术细节

**Harness 与“框架”的关系**

- LangChain／LangGraph／Spring AI 这类是“构建 Harness 的框架/库”；Harness 是最终那套运行系统的总称，包含但不止于框架——还包括你自己的编排、护栏、工具与运维。
- 别把“用了 LangChain”等同于“有完整 Harness”：终止控制、鉴权、观测、恢复这些往往得自己补。

**判断 Harness 做得好不好的点**

- 上下文是否精简且不丢关键信息（见 HARNESS-001 上下文工程）。
- 循环是否可终止、能否检测无进展、有没有预算护栏（见 AGENT-009）。
- 工具调用是否“执行前校验、执行后验证”，鉴权是否在宿主侧。
- 失败是否可观测、可恢复，成本是否可控。

**为什么它是 AI 应用岗的核心考点**

- 模型能力大家都能调 API 拿到，拉开差距的正是这层工程——把不确定的模型约束成确定可交付的系统。

#### 深挖追问

1. **Coding Agent 是不是就是一种 Harness？**（补充练习）

   是 Harness 的一个具体形态：它把“读代码、改文件、跑测试、看报错再改”这套循环和工具专门化。从零搭的过程见 HARNESS-004。

2. **上下文工程和 Harness 什么关系？**（补充练习）

   上下文工程是 Harness 的一个子系统／一层能力——决定每轮喂给模型什么、怎么压缩复用，是 Harness 里最影响效果的部分之一（见 HARNESS-001）。
