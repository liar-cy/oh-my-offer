### GO-001：是否会 Go，goroutine 的底层实现是什么？

**常见问法**

- 是否会 Go，goroutine 的底层实现是什么？

- 讲一下 GMP 模型；P 的本地队列为空或不为空时分别怎么调度 G？

- 是否会 Go？

- 实习的时候利用 Go 框架实现这些功能的优势是什么？

- 如果让你用 Java 开发同样的需求，架构上有什么要注意的地方，需要用到什么技术来达到类似的效果？

#### 面试回答

熟悉程度按真实情况填写：“我对 Go 的掌握程度是【入门／项目使用／生产经验】，实际用过【具体功能或项目】，对 goroutine 已理解【调度与同步内容】。”

技术部分就一句骨架：goroutine 是 Go 运行时管理的轻量执行单元，以 G 表示；M 是操作系统线程，P 是执行 Go 代码所需的调度资源。展开说：

- 运行时把很多 G 调度到很多 M 上执行。
- M 要先持有 P，才能执行 Go 代码。
- 整体靠运行队列、工作窃取、网络轮询这些机制协调并发。

#### 技术细节

**口径与依据**

- 以查证日 Go 官方 runtime 源码的 GMP 模型为准，具体队列细节可能随版本变化。

**G 和 P 各管什么**

- G 保存栈与调度状态，栈可以按需增长。
- P 的数量由 `GOMAXPROCS` 控制；别背错：它不是 goroutine 或 OS 线程数的上限。

**阻塞时运行时做什么**

- 可轮询的网络 I/O 等待：运行时可以挂起 G，让 M 去执行其他 G。
- 阻塞系统调用：可能真的阻塞 M，这时运行时会把 P 转交其他 M。所以不能说“系统调用绝不阻塞线程”。
- Go 也不是只靠主动让出的协作式调度，现代运行时支持抢占。

**轻量的另一面**

- 无限创建 G 仍然会耗内存，要处理取消、限流和泄漏。

#### 深挖追问

1. **goroutine 底层如何调度？**（面经实际出现；[[面经/百度/一面/0003#Q20：是否会 Go，goroutine 的底层实现是什么？|MJ006 · 百度 · 一面 · Q20]]）

   先记三个角色：G 是任务，M 是线程，P 提供执行 Go 代码的资源。获取路径：运行时从本地队列、全局队列、工作窃取这些路径拿到可运行的 G；等待中的 G 在事件结束后被唤醒。

2. **用 Go 框架实现业务功能的优势是什么？**（面经实际出现；[[面经/帆软/一面/0003#Q02：实习经历介绍：用 Go 框架实现功能有什么优势？|MJ035 · 帆软 · 一面 · Q02]]）

   三条主线：

   - 并发表达：goroutine＋channel 让 IO 密集的并发代码写得直白安全。
   - 部署形态：编译成单个静态二进制、无运行时依赖，容器镜像小、内存占用低、弹性伸缩友好。
   - 工程效率：标准库覆盖 HTTP／JSON 等常用能力，编译快、格式与错误处理规范统一。

   加分项是主动说边界：泛型与生态成熟度弱于 Java，复杂业务分层不如 Spring 体系完备，ORM 等基建需要更多自研。

3. **同样的需求改用 Java，架构上要注意什么？**（面经实际出现；[[面经/帆软/一面/0003#Q03：如果改用 Java 开发同样的需求，架构上要注意什么、用什么技术达到类似效果？|MJ035 · 帆软 · 一面 · Q03]]）

   三条线一一对应：

   - 并发模型：线程池＋BlockingQueue 近似 channel 语义；JDK 21 起用虚拟线程找回“一请求一线程”写法（见 [[专题题库/Java并发#JUC-017：Go 的协程在 Java 有类似方案吗？|JUC-017：Go 的协程在 Java 有类似方案吗？]]）。
   - 分层与依赖：Spring Boot 的 DI／事务／横切替代 Go 的显式组合；共享可变状态增多，要按锁与线程安全手段收敛（JUC-014）。
   - 部署运维：jar＋JVM 要管堆内外内存与容器 limit 匹配、JIT 预热；换来的是 JFR／Arthas 级运行时观测。

4. **P 的本地队列为空或不为空时，分别怎么取 G？**（面经实际出现；[[面经/字节/一面/0009#Q07：讲一下 GMP 模型；P 的本地队列为空或不为空时，它会怎么调度 G？|MJ041 · 字节 · 一面 · Q07]]）

   不为空时：

   - 直接从本地队列取，这一步无锁，是并发开销低的关键。
   - 其中 `runnext`（下一个优先执行的 G）会被优先安排，用来降低调度延迟。

   为空时依次往下走：

   - 全局队列：一次取若干个，摊薄加锁成本。
   - `netpoll`：取已经就绪的 G。
   - 工作窃取：随机挑别的 P，通常偷其本地队列的一半。
   - 都拿不到：M 进入自旋等待，自旋 M 的数量有上限，避免空转烧 CPU。
   - 最终无 G 可跑：M park 到调度器等待队列，等新 G 入队时被唤醒。

   两个防饿死与防阻塞机制要一起说：

   - 每 61 次调度强制检查一次全局队列，防饿死。
   - `sysmon` 是不绑定 P 的监控线程（约 10ms 轮询）：抢占运行过久的 G（协作式抢占依赖栈检查点）、接手长时间阻塞在系统调用上的 P（hand off 给其他 M）、驱动 netpoll。

   细节以所用 Go 版本文档为准。

### GO-002：Go 的 channel 是什么、并发安全吗，和 Mutex 怎么取舍？

**常见问法**

- 详细讲一下 Golang 中 Channel 的概念和作用，它是否是并发安全的？
- Channel 和传统的锁（Mutex）在实现并发控制时有什么区别？各自的适用场景是什么？

#### 面试回答

channel 是运行时提供的、带元素类型与容量的 goroutine 间通信队列：发送方写入、接收方读出，实现数据的传递与同步。

- 底层是 `hchan` 结构：一块环形缓冲（`buf` 加 `qcount`／`sendx`／`recvx` 读写游标）、两个等待队列（阻塞的发送方 `sendq`、接收方 `recvq`），再加一把保护自身字段的互斥锁。
- 语义分三类：
  - 无缓冲 channel 是同步握手，发送必须等到有人接收，等于一次“所有权交接”。
  - 有缓冲 channel 在缓冲未满时立即返回，起解耦与削峰作用。
  - `select` 配合 `default` 可做非阻塞收发与超时控制。

“是否并发安全”分两层答：

- channel 自身安全：多个 goroutine 并发向同一 channel 收发由运行时加锁保护，不会破坏内部结构，也不要求调用方额外加锁。
- 但“用了 channel 就没有竞态”不成立：竞争可能发生在 channel 之外的共享变量上。

另有一组明确的错误行为要能报出来：

- 向已关闭的 channel 发送：panic。
- 从已关闭的 channel 接收：立即得到零值加 `false`，所以要用 `v, ok` 判关闭，而不是靠值本身。
- 向 nil channel 收发：永久阻塞；`select` 里的 nil case 相当于被禁用。
- 重复 `close`：panic。
- 多生产者场景：关闭权必须唯一约定，由协调方在所有人都发完之后关，或用 `sync.WaitGroup` 配合。

与 Mutex 的区别不是谁更安全，而是抽象层次不同：

- mutex 保护共享状态：所有访问者竞争同一把锁，原地读写同一份数据。适合缓存、计数器、复合数据结构，以及必须原子的“读—改—写”。
- channel 传递数据的所有权与事件。适合流水线分段、任务分发、限流（带缓冲 channel 当令牌桶）、取消与完成信号广播。
- 取舍判据一句话：状态要被多方原地读写→用锁；数据要交给下一个处理者，或要表达“某件事发生了”→用 channel。
- 还要能说出反例证明不是教条：用 channel 做全局计数，会平白引入一个串行化的 goroutine；用 mutex 保护只写一次的 map，反而更简单直接。Go 的“不要通过共享内存来通信，要……”是指导，真实项目里 `Mutex`／`RWMutex` 用得比 channel 更多。

#### 技术细节

**必须记住的六格收发行为**（无缓冲／有缓冲／已关闭／nil 各自的收发）

- 正常收发：按语义阻塞或传递。
- `close` 之后：接收会先排空缓冲、再返回零值加 false；发送则 panic。
- nil channel：收发都永久阻塞。

**由谁关、什么时候关**

- `close` 由发送方负责，且只在“确实需要让接收方结束 range”时关。
- 不关也没错：靠 `context` 取消或让 GC 回收是常见写法；滥用 close 反而是 bug 高发点。

**用 channel 的典型坑**

- 忘记消费导致 goroutine 泄漏：发送阻塞、无人接收，这个 goroutine 永远挂起，且它持有的资源不释放。
- select 在多个就绪 case 间是伪随机选择，不能依赖顺序。
- range 一个永远不会被关闭的 channel 会死锁。
- 把大对象塞进 channel 等于传引用，跨 goroutine 修改仍然要同步。
- 取消与超时用 `context.Context` 加 `done` channel，而不是自己造信号量协议。

**对照 Java 口径**（跨语言岗位常被追问）

- channel ≈ 阻塞队列（`BlockingQueue`）＋显式锁，但没有 Java 的 `poll/offer` 超时族与生产者-消费者模板那么直接。
- mutex 两边语义一致；Go 里要靠 `sync.Mutex` 显式包住临界区，没有 `synchronized` 的隐式监视器与可重入语义——Go 的锁不可重入，重入即自锁死。
- 限流场景两边都落到信号量：Go 用 `errgroup.SetLimit` 或带缓冲 channel；Java 用 `Semaphore`／固定线程池（见 [[专题题库/Java并发#JUC-020：如何写一个限制最大并发数的并发任务处理器？|JUC-020：限制最大并发的任务处理器]]）。

#### 深挖追问

1. **无缓冲 channel 的收发是同时完成的吗？**（补充练习）

   是，一次交接。发送方阻塞到有接收方就绪，运行时把值直接拷贝给接收方并唤醒对方——两边在同一个同步点完成。所以它也常被当作“会合点”，用来对齐两个 goroutine。

2. **为什么多生产者时不能随便 close？**（面经实际出现；[[面经/字节/一面/0009#Q06：讲讲 Golang 中 Channel 的概念与作用，它是否并发安全；Channel 和 Mutex 在并发控制上有什么区别、各自适用什么场景？|MJ041 · 字节 · 一面 · Q06]] 的延伸）

   不能随便关：close 是广播语义，关掉后所有发送方都会 panic；而多个生产者没人知道谁“最后”发完。两种正确做法：

   - 由协调方统一关闭：例如 `WaitGroup` 等待全部生产者结束后再 close。
   - 干脆不用 close 结束接收：改用 `context` 取消加 select 分支。

3. **channel 能替代锁吗？**（补充练习）

   不能一概替代：

   - channel 可以通过“把状态交给单一 goroutine 独占修改”消除锁（actor／分片写法），代价是每次读写都要一次通信往返并可能阻塞。
   - 高频读、需要原子读—改—写、或要保护多个字段一致性的场景，直接用锁更短也更便宜。
   - 选型的判据是“数据在谁手里”，而不是“哪个更时髦”。

### GO-003：Java 与 Go 最大的差别是什么，GMP 与 Java 多线程模型怎么对比？

**常见问法**

- Java 和 Go 最大的不同是什么？
- Go 的并发模型（GMP）与 Java 的多线程模型有何区别？
- Go 的泛型和 Java 的泛型相比有什么区别？你主要用的 Go 是哪个版本？

#### 面试回答

“最大的不同”给一条主线，别变成语言优劣之争：Go 是为“在容器里跑大量并发 IO 服务”设计的现代语言，Java 是长在成熟 JVM 生态上的企业级平台。落到写代码的差别有五点：

- 并发原语：goroutine＋channel 是语言级的；Java 靠线程＋共享内存＋锁与 JUC。
- 错误处理：Go 是显式 error 返回值、`panic` 不是错误控制流；Java 是受检／非受检异常。
- 内存与运行形态：Go 是静态二进制，协程栈几 KB 起、按需增长，GC 偏低延迟；Java 需 JVM，栈大小由参数定，GC 调优空间大但要管堆内外内存。
- 类型系统：Go 是结构化类型＋隐式实现接口＋泛型晚到；Java 是名义类型＋泛型擦除＋注解与反射生态厚重。
- 工程约定：Go 靠格式统一、组合与小接口；Java 靠框架与依赖注入。

结论收在“按场景选语言”，并给出自己会怎么选的依据。

并发模型的差别是技术核心：

- Go 是 GMP：G 是协程，M 是内核线程，P 是执行 Go 代码所需的调度上下文（数量由 `GOMAXPROCS` 决定），M 必须绑 P 才跑业务代码。
- G 阻塞在 channel 或网络 IO 时，运行时挂起它并让 M 去跑别的 G；阻塞在系统调用时，P 与 M 解绑交给其他 M。所以“一请求一协程”成本极低，调度发生在用户态。
- Java 传统模型是 1:1 映射到内核线程：创建与切换要进内核、栈默认 MB 级，几百到几千线程就有明显调度与内存开销。因此靠线程池＋有界队列＋拒绝策略复用线程，并发语义用 `synchronized`／JUC 锁与原子类保护共享内存。

真正的分水岭不是“协程更轻”，而是通信范式：

- Go 鼓励把数据交给某个 goroutine 独占，通过 channel 传所有权与事件；Java 习惯共享对象加锁。
- JDK 21 的虚拟线程已经在收敛这个差距（用户态调度＋阻塞时让出载体线程），但并发语义仍是共享内存＋锁，且要处理 `synchronized` pin 载体线程等限制（见 JUC-017）。

#### 技术细节

**泛型对比的四条差别**（常被连带追问）

- 名义还是结构：Java 泛型是名义类型，要显式 `implements`，约束写 `extends`；Go 是结构化类型，满足方法集就隐式实现接口，类型参数约束只能是方法集或类型联合，不能声明“继承某类”。
- 运行时表示：Java 泛型在字节码层被类型擦除，`List<String>` 与 `List<Integer>` 运行时是同一个类——因此不能 `new T()`、不能对类型参数 `instanceof`、基本类型必须装箱；Go 泛型采用受限单态化（按字典共享代码），对基本类型无需装箱。
- 型变规则：Java 有 `? extends T`／`? super T` 的 PECS 型变规则；Go 没有通配符，且泛型类型不做型变（`Set[int]` 不是 `Set[int64]` 的子类型）。
- 复杂度从哪来：Java 泛型的复杂度来自兼容未参数化的历史代码；Go 泛型刻意保守，不支持特化生成不同机器码等高级特性。

答完要能自陈一句：“所以我更倾向用接口表达能力、只在容器与算法复用时才加类型参数”。

**版本：报了号就要说得出实际差异**

- 1.18：引入泛型。
- 1.21：有 `min`／`max` 内建函数与 `slices`／`maps` 标准库包，泛型到这才真正好用；同版本还改了 toolchain 版本选择机制。
- 1.22：`for` 循环变量改为每轮迭代新建——直接影响闭包与 goroutine 捕获旧值的经典 bug；同时把 `net/http` 的 `ServeMux` 路由模式匹配补齐（支持方法与通配段）。
- 更晚版本的调度器与 GC 细节以官方发布说明为准，不要凭印象说“更快了”。

**对照 Java 侧的其它高频差异**（挑两三个能落地举例的讲）

- 内存布局：Java 是对象头＋压缩指针；Go 结构体紧凑、无继承只有组合，接口值是 `iface`／`eface` 双指针。
- GC 触发：Java 看堆占用与策略、可调参；Go 由 `GOGC`／`GOMEMLIMIT` 控制。
- 可观测性：Java 有 JFR／Arthas 这类成熟运行时工具，Go 靠 pprof 与 metrics，各有顺手处。
- 依赖管理：Go module 是单一版本选择；Maven 有冲突调解与 `dependencyManagement`。

#### 深挖追问

1. **Go 里没有 try/finally 和异常，资源与错误处理怎么写才不难看？**（面经实际出现；[[面经/字节/一面/0010#Q10：Java 和 Go 最大的不同是什么？Go 的并发模型（GMP）与 Java 的多线程模型有何区别？|MJ042 · 字节 · 一面 · Q10]] 的延伸）

   释放靠 `defer`：后进先出，参数在 defer 时求值。错误用 `if err != nil { return fmt.Errorf("...: %w", err) }` 逐层包装，再用 `errors.Is`／`errors.As` 判定。跨层想“抛”的冲动通常意味着接口设计有问题——把可能失败的操作切小，让调用方在能处理的地方处理。

2. **同样一个高并发 IO 服务，两种语言的容量规划差异在哪？**（补充练习）

   - Java 侧：要算线程数与栈占用、GC 停顿与堆内外内存、连接池大小。
   - Go 侧：协程成本几乎可以忽略，瓶颈转移到连接数、文件描述符、下游容量与 GC 的堆目标；`GOMEMLIMIT` 与容器 limit 要留元数据余量。
   - 两边共同点：都必须显式设超时与限并发，语言不会替你解决下游容量。

3. **Go 的结构化类型有什么坑？**（补充练习）

   坑在“意外实现”：隐式满足接口意味着多了同名方法就被当成实现了 `Reader`，接口越宽耦合越广。所以实践是：接口定义在消费方、保持小（一到三个方法）、只暴露需要的能力——这也是 Go 里“接受接口、返回结构体”这句谚语的由来。

### GO-004：Go 的数组、slice 与 map 底层结构与区别是什么？

**常见问法**

- Go 的数组、slice 与 map 的底层数据结构与区别？
- 为什么 slice 传给函数后原数据可能被改掉，什么时候不会？
- Go 的 map 是并发安全的吗？遍历顺序为什么随机？

#### 面试回答

三者一句话分辨：

- 数组：定长的值类型。
- slice：定长数组之上的可变长视图。
- map：内建哈希表。

数组：

- `[3]int` 与 `[4]int` 是不同类型——长度属于类型。
- 赋值与传参整体复制，所以很少直接当参数用，主要作为 slice 的底层存储存在。

slice：

- 它只是一个描述符：指向底层数组的指针、len、cap；赋值和传参只复制描述符，多个 slice 可以共享同一段底层数组。
- 两个必须讲清的行为：`append` 超过 cap 时分配新数组并拷贝，此后原 slice 与新 slice 不再共享、看不到彼此的写入；未超过 cap 时它们仍指向同一段数组，会互相影响。
- 想安全地交出去：`copy` 成新 slice，或用 `s[:n:n]` 把 cap 钉住，逼 append 必然复制。
- 再切片还可能造成内存驻留：切掉的头部数组段仍被引用，无法释放。

map：运行时 `hmap`——桶数组（每桶最多 8 个键值槽）＋溢出桶，用 key 哈希的低 bits 选桶、高 bits 存签名，带负载因子触发的增量扩容（倍增或等规模搬移）。要点按“能不能用”组织：

- 非并发安全：Go 1.6 之后检测到并发写直接 `fatal error: concurrent map writes`——不是 panic，recover 不住。
  - 共享写要 `sync.Mutex`／`RWMutex`。
  - 读多写少可 `sync.Map`。
  - 高并发常见做法是按 key 哈希分片、各配一把锁。
- 遍历顺序刻意随机化：每轮从随机桶与随机槽位起，不能依赖。
- 键必须是可比较类型：slice、map、函数不可作键。
- 删除键不会立即缩容；读不存在的 key 返回零值，判断存在要用 `v, ok := m[k]`。

性能上：slice 顺序访问连续内存、缓存友好、还能预分配避免反复扩容（已知规模就 `make([]T, 0, n)`）；map 每次访问有哈希计算与桶内比较、并可能指针追逐，还会产生更多垃圾。所以“用 map 还是切片＋排序”要按访问模式选。

#### 技术细节

**`make([]T, len, cap)` 的 len 与 cap 语义**（容易写错）

- len 决定可直接下标访问的范围：对超出 len 的索引赋值会越界。
- 用 `s[i] =` 填数据时：要么 len 给够，要么改用 `append`。

**扩容策略**

- 由运行时决定：小 slice 大致翻倍，大容量增幅趋缓，且会做内存大小对齐。
- 别把“两倍”当规范引用；需要精确行为就自己预分配。

**字符串与 byte slice 的转换**

- `string(b)` 与 `[]byte(s)` 默认都会拷贝，热路径上要避免反复转换。
- `unsafe` 或零拷贝手段有正确性前提：数据不被修改、生命周期可控。面试里说出“知道有这条路但不轻易走”，比硬用更稳。

**结构体切片和指针切片的取舍**

- `[]T`：内存连续、缓存友好，但复制与原地修改要留意。
- `[]*T`：元素可独立共享，但 GC 压力与指针开销更高。

**map 的 value 是结构体**

- 不能直接改它的字段：`m[k].Field = x` 不可寻址。
- 要么先取出、改完再写回，要么把 value 定义成指针／改用其他容器。

**与 Java 对照**（让答案更完整）

- Java：
  - 数组同样是定长对象。
  - `ArrayList` 是封装了扩容的引用类型。
  - `HashMap` 是数组＋链表到红黑树（负载因子 0.75，链表长度到阈值树化）。
- Go：没有泛型集合包装层——slice 直接承载数组语义、map 是语言内建而非库。所以“集合的行为”要靠约定与规范（锁、分片、预分配）自己保证。
- Go 的 map 用溢出桶而不是链表，这一点常成为追问对比点。

#### 深挖追问

1. **为什么 Go 要设计成“数组是值类型、slice 是视图”？**（面经实际出现；[[面经/字节/一面/0010#Q12：Go 的数组、slice 与 map 的底层数据结构与区别。|MJ042 · 字节 · 一面 · Q12]] 的延伸）

   值语义让数组可比较、可作 map 键、传参无副作用，但复制成本随长度线性增长。实际并发与流式代码需要“引用一段数据”的能力，这由 slice 承担。把两者分开是刻意取舍：

   - 长度属于类型：保证静态安全。
   - 视图：提供零拷贝的灵活性，代价是别名行为必须由程序员负责。

2. **`sync.Map` 什么时候该用，什么时候不该？**（补充练习）

   不是“并发就用它”，分情况：

   - 适合：读多写少且键集合稳定（读命中无锁的路径），或各 goroutine 操作不相交键集的场景。
   - 不适合：写多、需要批量遍历一致性或复合操作——反而更慢。直接用分片锁＋普通 map 通常更好，因为它还能表达“批量替换”的语义。

3. **map 的负载因子为什么不是越小越好？**（补充练习）

   - 调低确实更少冲突、查找更快，但桶数与内存上升、扩容与 GC 压力增大。
   - Go 的桶内 8 槽设计就是“多数桶装几个键”的折中，溢出链过长才扩容。
   - 答题时给“按 key 规模与读写比压测定”比给一个魔法数字更可信。
