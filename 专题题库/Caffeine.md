### CAFFEINE-001：从 Caffeine 获取对象是深拷贝还是浅拷贝？

**常见问法**

- 从 Caffeine 获取对象是深拷贝还是浅拷贝？

#### 面试回答

都不是 —— 普通本地 Caffeine Cache 命中时返回的就是缓存值那个对象的引用，不做任何拷贝。

- 不深拷贝：不会复制对象内部的数据。
- 也不浅拷贝：连一个新的外层对象都没有创建，拿到的还是同一个引用。
- 后果：改返回的可变对象，其他读取者看到的缓存内容会被直接影响。
- 别背错：缓存容器线程安全，不代表里面装的可变对象也线程安全。
- 做法：优先存不可变值，或者在返回前明确做一次防御性复制。

#### 技术细节

**适用范围**

- 只讨论普通的本地 Cache／LoadingCache，没有叠加自定义序列化、复制适配器等额外处理。

**读写各做什么**

- put 保存值，getIfPresent 或命中缓存的 get 取回当前值。
- 加载、刷新、显式替换都可能更新引用，所以不是“同一个 key 永远是同一个对象”。
- 源码层面是读取节点的 value 并返回，默认不执行 clone，也不走序列化往返。

**套了封装层要多看一眼**

- 如果通过 Spring Cache 或其他封装使用，得去检查封装层自己的策略。

**别把共享引用说成浅拷贝**

- 这里只是拿到同一个引用，不是浅拷贝；深浅拷贝概念参见 [[专题题库/Java基础#JAVA-003：深拷贝、浅拷贝与引用赋值有什么区别？|Java 对象复制]]，不要把仅共享引用误称浅拷贝。

#### 深挖追问

1. **获取后改 List，其他线程会看到变化吗？**（补充练习）

   很可能就是同一个 List，改了对方立刻能看到。除了内容互相干扰，还有对象内部的数据竞争和可见性问题，所以要用不可变值或者统一同步。

2. **直接修改缓存对象会触发正常更新语义吗？**（补充练习）

   不能据此假定。直接改对象不等于走了一次缓存写入，刷新、过期、权重是否按 put 更新都不确定；需要更新时显式替换值，并检查自己的配置语义。

### CAFFEINE-002：缓存淘汰策略 LRU、LFU、W-TinyLFU 有什么区别，自研策略怎么比较？

**常见问法**

- 你们的淘汰策略相较于 LRU 或 LFU 的优势在哪里？
- 淘汰策略的设计依据来源是什么？有无其他比较的模型？
- LRU 和 LFU 各有什么问题，Caffeine 为什么用 W-TinyLFU？

#### 面试回答

结论：LRU 只看「最近」，一次扫描就会把真热点挤掉；LFU 只看「累计频次」，老热点赖着不走、新条目进不来。W-TinyLFU 用频率做准入、用分代做老化，把两者的短板互补。

- LRU 的失效场景：批处理、爬虫、全表扫描这类一次性流量（scan pollution），命中率高但复用距离远的负载上表现差。
- LFU 的失效场景：突发变热的短生命周期 key 长期占位；需要额外解决频次衰减和计数内存开销。
- W-TinyLFU：新数据先进一个很小的 admission window，只有频率估计赢过主缓存里最「弱」的候选时才准入；主缓存用 SLRU 分冷热两段。
- 讲自己策略时的正确说法：在【某类访问分布】的 trace 上，字节命中率比 LRU 高【x 个百分点】、对扫描流量的抗扰更好；数字必须来自实测或回放。
- 依据来源（这题的题眼）：策略不是拍脑袋，而是从【真实或采样访问日志的热度分布与复用距离】推出来的。

#### 技术细节

**W-TinyLFU 的构成（以 Caffeine 与 TinyLFU 论文口径为准）**

- 4-bit CountMin Sketch：每个 key 占 4 bit 的计数器组，用来估计访问频率；优点是有界内存，代价是会因哈希冲突高估（不会低估）。
- 老化（aging）：计数器整体按周期折半衰减，让「历史热度」不再永久占优，新晋热点才有机会进入。
- 准入判决（TinyLFU rule）：候选进入主缓存前，与将被驱逐的victim 比频率；频率不够就被拒。
- Doorkeeper（布隆过滤器）：记录最近被拒绝过的 key，避免一次性访问反复尝试准入、白白搅动主缓存。
- 主缓存 SLRU：分 probation（试用）与 protected（受保护）两段，命中试用段才晋升；窗口只占很小比例（论文与实现里是「小窗口」量级，具体比例随版本和配置变化，别说成固定值）。

**为什么说它比严格 LRU 更适合并发环境**

- 严格 LRU 要求每次命中都移动到链表头，多线程下是一把全局锁或大量 CAS；Caffeine 用「近似 ＋ 缓冲区批量应用」把这部分开销摊掉。
- 所以选型收益是两条：命中率（策略本身）与吞吐（实现的并发代价）。只讲命中率会漏一半。

**可比较的模型族（被追问「还有别的吗」时报这些）**

- LRU／LFU／FIFO：基线，实现简单。
- 2Q、SLRU：用多队列区分冷热与一次性访问。
- ARC、LIRS：同时兼顾 recency 与 frequency，对扫描型负载稳；ARC 自适应调整 LRU/LFU 两段大小，LIRS 用「插入栈距离」概念。
- TinyLFU／W-TinyLFU：概率计数＋准入，适合大容量、有扫描流量的本地缓存。
- SIEVE、TINY：近几年提出的更轻量策略，目标是用比 LRU 更低的维护开销拿到更好的命中率（SIEVE 靠一个指针快速清掉低价值条目）；知道它们想解决什么即可，别声称项目里用过。
- 理论上限：Belady 最优（离线，知道未来访问）常用来给命中率画天花板；LRU-stack distance 用来解释「同一 trace 下不同容量的命中率」。

**怎么比较才有说服力（评估方法论）**

- 用 trace 回放：采集线上访问日志（key＋时间，必要时带对象大小），在固定容量下离线跑各策略，比命中率。
- 指标口径：字节命中率优先于条数命中率；同时记录回源 QPS、驱逐次数、CPU／内存开销。
- workload 分型测试：稳定热点型、扫描污染型、突发上新型各跑一遍，避免只在一种分布上占优。
- 结论要带条件：「在【扫描流量占比高】的场景下比 LRU 提升 x 个百分点」，不给无条件结论。
- 上线验证：灰度双跑或 A／B，对比线上 P99 与回源量，而不完全信任回放数字。

**容易被追问倒的地方**

- 「你的策略优于 LRU」——需要给出对比对象、trace 来源与容量；否则就是主观判断。
- 「频率是怎么统计的」——要能说出是精确计数还是概率计数，以及衰减周期怎么定。
- 「命中率和延迟不是一回事」——命中率提升不代表尾延迟改善，驱逐风暴与回源合并同样影响 P99（见 [[#CAFFEINE-003：温数据反复驱逐与加载引起的缓存抖动怎么控制？|CAFFEINE-003：缓存抖动控制]]）。

#### 深挖追问

1. **淘汰策略的设计依据来源是什么？**（面经实际出现；[[面经/字节/一面/0011#Q06：淘汰策略的设计依据是什么，有没有其他可比较的模型？|MJ066 · 字节 · 一面 · Q06]]。原素材未记回答，以下为参考）

   来自访问日志的统计：复用距离分布、热度长尾程度、扫描流量占比、对象大小分布。项目事实按【真实的日志来源与统计口径】填，不要说成「凭经验」。

2. **为什么不用严格 LRU？**（补充练习）

   严格 LRU 每次命中都要移动链表节点，高并发下同步成本明显；近似 LRU（分段采样、访问缓冲区批量应用）几乎不损失命中率，却省下大量锁竞争。

3. **LFU 的「老热点不肯走」怎么解决？**（补充练习）

   靠衰减：按周期把计数折半（或滑动窗口计数），历史热度会自然退场；这也是 CountMin 老化存在的理由。

4. **怎么防止一次性访问污染缓存？**（补充练习）

   准入判决：新 key 先进小窗口，只有频率估计超过主缓存里将被驱逐的候选才晋升；再加 doorkeeper 记录刚被拒绝的 key，避免它反复尝试。

### CAFFEINE-003：温数据反复驱逐与加载引起的缓存抖动怎么控制？

**常见问法**

- 在你设计的淘汰策略里，温数据被驱逐和加载时会不会导致系统波动？怎么解决？
- 缓存命中率周期性抖动、回源流量尖峰怎么排查和治理？

#### 面试回答

结论：会，这是缓存颠簸（thrash）——一批卡在淘汰边界上的温数据反复被驱逐又回源，表现为 P99 周期性尖刺和回源 QPS 抖动。

- 根因通常是工作集略大于缓存容量，或淘汰是一刀切（一次驱逐一大片同代数据）。
- 控制手段四组：准入（不让一次性数据直接进主缓存）、滞回（水位分高低两条线，不一到阈值就猛驱逐）、限速加载（后台预热别挤占前台）、分层（温数据落 SSD 而不是每次回源）。
- 兜底：同一 key 的并发回源用请求合并（singleflight）收敛成一个，加熔断与并发上限，避免回源风暴。
- 一句收口：波动要能用指标看见——字节命中率、回源 QPS、驱逐次数与加载带宽，四条曲线对齐时间点才能确认是抖动。

#### 技术细节

**抖动的三种典型形态**

- 边界震荡：容量刚好小于工作集，LRU 式策略会持续驱逐「刚可能再被用到」的条目，命中率对容量极其敏感（LRU-stack 曲线陡峭段）。
- 批量失效：同 TTL 的一批 key 同时过期，回源尖峰呈锯齿状；解法是 TTL 加随机抖动。
- 加载挤占：驱逐后前台请求触发同步加载，占满线程池与带宽，反过来又拖慢正常请求，形成正反馈。

**对应的设计手段**

- 准入控制：新条目先进窗口，频率达标才进主缓存；doorkeeper 挡住刚被拒绝的一次性 key（见 [[#CAFFEINE-002：缓存淘汰策略 LRU、LFU、W-TinyLFU 有什么区别，自研策略怎么比较？|CAFFEINE-002：淘汰策略对比与评估]]）。
- 滞回与分代：驱逐按高／低水位触发，一次只清一代，避免同时驱逐一批相关 key 造成连锁回源。
- 分层缓存：热在内存、温在本地 SSD 或下一级缓存，加载代价从「回源」降到「读盘」。
- 预热限速：批量加载走独立线程池＋令牌桶限速，明确不与前台请求争资源。
- 请求合并：同 key 并发只放一个回源请求，其余等待共享结果；配合超时与降级，防止等待堆积。

**怎么判断「是抖动而不是容量不足」**

- 看驱逐量与命中率是否同步振荡：抖动是振荡，容量不足是整体水位低。
- 做容量扫描实验：容量增加一档，命中率跳变说明是工作集超出；只是缓慢上升说明是策略边界效应。
- 复现用回放：把线上 trace 回放进候选策略，直接观察驱逐频率。

**容易说过头的地方**

- 「加大缓存就好了」：工作集若持续大于容量，加大只是推迟抖动，成本和收益要一起算。
- 「预热一定能压住」：无节制的预热会把带宽打满，反而放大前台尾延迟——限速和优先级是前提。
- 别把本地缓存说成零代价：它带来的是一致性窗口和多实例内存放大（见 [[#CAFFEINE-001：从 Caffeine 获取对象是深拷贝还是浅拷贝？|CAFFEINE-001：深浅拷贝]] 与 [[专题题库/系统设计#SYS-009：多级缓存如何保持一致，并在 Redis 故障时降级？|SYS-009：多级缓存一致性]]）。

#### 深挖追问

1. **驱逐时的加载是同步还是异步？**（补充练习）

   前台同步加载会拉长该请求延迟、并占住线程；常见折中是同步加载首请求（带请求合并）＋异步预取其后可能用到的关联数据。

2. **怎么给淘汰加滞回？**（补充练习）

   设两条水位线：超过高水位才开始批量驱逐，降到低水位以下停止；或要求候选被连续判定为「低价值」N 次才驱逐，避免单次访问就让它进进出出。

3. **命中率没变但 P99 变差，可能是抖动吗？**（补充练习）

   可能是：加载路径阻塞、回源并发放大或锁竞争都会伤尾延迟而不动平均命中率。要看回源耗时分布与线程池排队长度。
