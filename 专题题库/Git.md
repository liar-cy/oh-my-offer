### GIT-001：git merge 和 git rebase 有什么区别，各在什么场景用？

**常见问法**

- git merge 和 git rebase 的区别？

#### 面试回答

一句话：都能把两条分支接上，区别在“历史怎么记”。

- merge：在共同祖先之外新建一个合并提交，两条真实历史线都保留——忠实，但分叉多了历史像麻花。
- rebase：把当前分支的提交逐个“重放”到目标分支顶端，得到一条线性历史——干净，但提交哈希全部改变，属于改写历史。
- 由此推出两条纪律：已推送给别人、公共分支上的提交不要 rebase（别人基于旧哈希的历史会炸）；rebase 后强推用 `--force-with-lease`，别用裸 `--force` 覆盖他人提交。

#### 技术细节

**合并提交与快进**

- 两边都有新提交时 merge 生成双父的合并提交；目标分支没有新东西时 merge 会快进（fast-forward），只是移动指针、不产生新提交。
- 团队协作里常用 `--no-ff` 强制保留合并提交，让特性分支在历史上一眼可辨。

**冲突发生的次数不同**

- merge：冲突集中在合并提交这一步解决一次。
- rebase：按提交逐个重放，可能每一步都要解一遍冲突；中断可 `--continue`／`--abort`／`--skip`。

**为什么 rebase 历史“更好”但也有代价**

- 线性历史让 `git bisect`、review、回溯都省事——这是它存在的理由。
- 代价是“真实开发过程”被抹掉，且哈希变化会让已分发的分支互相打架：所以口径统一为“本地未推送的提交随便 rebase，已共享的提交只用 merge”。

**团队落地建议（面试收尾用）**

- 特性分支追主干：`git rebase main`（保持本地整洁）。
- 特性分支并回主干：MR／PR 走 merge（平台保留合并线索），或团队约定 squash merge 把特性压成一条线性提交。
- 哪种都行，关键是全组一致——这题加分点恰恰是表态“约定比工具之争重要”。

#### 深挖追问

1. **rebase 之后测试范围为什么要重跑？**（补充练习）

   重放后的提交序列与合并后的树内容未必逐一对应，冲突解决也引入了新改动；等价性只对“最终快照”大致成立，中间提交状态是重组出来的。

2. **squash merge 和 rebase 后 fast-forward 合并有何区别？**（补充练习）

   squash 把整条分支压成主干上的一个提交（特性内部历史丢弃）；rebase＋ff 合并保留每个提交、逐条落进主干。前者适合碎提交多的特性分支，后者适合要求主干可精确 bisect 的团队。
