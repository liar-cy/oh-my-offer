### MYSQL-001：MySQL 事务有哪些隔离级别？

**常见问法**

- [[面经/美团/一面/0002#Q23：MySQL 事务特性逐个展开：原子性、隔离性、持久性、隔离机制、MVCC、间隙锁|MJ032 · 美团 · 一面 · Q23]]
- MySQL 的事务分为哪几种？

- 事务隔离级别有哪些，分别解决了什么问题？
- RR 级别如何解决幻读？

- MySQL 事务如何开启，ACID 和隔离级别是什么？

- MySQL 的事务是什么？有哪些特性？

#### 面试回答

如果这里问的是隔离级别，有读未提交、读已提交、可重复读和串行化，InnoDB 默认是可重复读。它们主要权衡并发与读一致性；InnoDB 结合 MVCC 和锁实现相应语义。如果您指的是提交方式或分布式事务类型，我可以按那个维度回答，ACID 四个特性则不是四种事务。

#### 技术细节

原题“事务分几种”未明确分类，本条按隔离级别整理并保留歧义。读未提交可能脏读；读已提交的一致性读通常每次建立新快照；可重复读通常复用首次一致性读建立的快照。锁定读不是快照读，在 RR 下可用 next-key lock 等控制范围并发；不能简单声称 MVCC 解决所有形式的幻读。串行化约束更强、并发代价更高。以下依据 MySQL 8.4 InnoDB；不要将 Spring 传播行为和数据库隔离级别混在一起。

补充：脏读是读到别人未提交的值；不可重复读是重读同一记录发现已提交变化；幻读强调同一条件的结果集合出现新增或消失。按标准最低隔离保证理解：RU 可有三类异常，RC 避免脏读，RR 避免脏读和不可重复读但标准不要求完全排除幻读，Serializable 再提供串行化约束。InnoDB 的具体实现比这个简表更细。

RR 下，普通一致性 SELECT 通常复用首次一致性读的 read view，因此不看到后来提交的新行；这不是阻止别人插入。SELECT ... FOR UPDATE 等范围锁定读根据执行计划采用 next-key／gap 等锁限制相关间隙插入。完整唯一键命中等场景可缩小为记录锁，不能说 RR 的每次 SELECT 都加间隙锁。混用快照读与当前读、或事务自己进行写入，会改变可见结果；实际范围控制还要结合索引。具体锁分类见 [[#MYSQL-005：MySQL 中有哪些锁，如何分类？|InnoDB 锁]]。

事务控制以 MySQL 8.4 InnoDB 为例：START TRANSACTION 开启，COMMIT 提交，ROLLBACK 回滚；autocommit 默认开启时，单条适用语句可独立提交。SET autocommit=0 影响会话，需要每轮显式结束事务；许多 DDL 会隐式提交。存储程序中的 BEGIN 还可能是复合语句块，不与事务开启混同。ACID 的一致性是满足约束，不是所有副本任何时刻一致；业务不变量仍需正确 SQL 与约束实现。

#### 深挖追问

1. **ACID 分别是什么？**（补充练习）

   原子性、一致性、隔离性、持久性；它们描述事务性质，而非互斥的四种类别。

2. **RR 下两次查询一定相同吗？**（补充练习）

   不能无条件保证；需看快照读还是锁定读、事务自身是否写入等条件。普通一致性读与当前读不要混用同一解释。

3. **RR 级别如何处理幻读？**（面经实际出现；[[面经/北京某上市公司/一面/0001#Q13：事务隔离级别分别解决什么问题，InnoDB RR 如何处理幻读？|MJ004 一面 Q13]]）

   快照读通过一致性视图保持结果，范围锁定读通过适用的 next-key／gap 锁阻止相关插入；这两条路径的语义不同，不能简单说“所有幻读都被 MVCC 消灭”。

4. **如何开启事务并解释 ACID？**（面经实际出现；[[面经/百度/一面/0005#Q14：MySQL 事务如何开启，ACID 和隔离级别是什么？|MJ008 · 百度 · 一面 · Q14]]）

   以 InnoDB 为前提，可用 START TRANSACTION 或普通 SQL 中的 BEGIN 开始事务，COMMIT 提交、ROLLBACK 回滚；也可设置 autocommit=0，但要理解会话持续事务语义。ACID 是原子性、一致性、隔离性、持久性：一组修改整体完成或回滚，维护业务约束，控制并发可见性，保证提交后的持久性。隔离级别为读未提交、读已提交、可重复读和串行化，InnoDB 默认可重复读。具体读语义还要区分快照读和锁定读；持久性承诺取决于日志刷盘等配置。

5. **读已提交是怎么避免脏读的？RC 和可重复读的核心差异是什么？**（面经实际出现；[[面经/帆软/二面/0002#Q11：MySQL 的读已提交怎么避免脏读，RC 和 RR 的核心差异是什么？|MJ035 · 帆软 · 二面 · Q11]]）

   RC 避免脏读不靠加读锁，靠 MVCC 可见性：快照读沿版本链跳过未提交版本、只取对本语句可见的最近已提交版本，未提交数据永远读不到。RC 与 RR 的核心差异是 ReadView 生成时机——RC 每条语句新建（能看到期间提交，允许不可重复读），RR 事务首次一致性读建一份复用（重读稳定）；RR 还在当前读路径用间隙锁／next-key lock 抑制幻读，代价是锁冲突更高；RC 另有基于行格式 binlog 的限制。

### MYSQL-002：如何查询所有已记录科目成绩都大于 80 的人员？

**常见问法**

- 表有姓名、科目、分数字段，查询分数都大于 80 分的人员名单。

#### 面试回答

我会按人员分组，在 HAVING 中限制最小成绩大于 80。如果 NULL 也视为不合格，再要求 COUNT(score)=COUNT(*)。题目只有姓名字段时暂按姓名标识人员；真实表应使用 student_id，避免同名合并。这个查询检查已有成绩，不能证明没有缺考科目。

#### 技术细节

设表为 scores(name, subject, score)，NULL 视为不合格：

```sql
SELECT name
FROM scores
GROUP BY name
HAVING MIN(score) > 80
   AND COUNT(score) = COUNT(*);
```

WHERE score > 80 会先删掉低分行，导致有不合格科目的人被误选；HAVING 是聚合后判断。MIN 忽略 NULL，因此额外计数用于排除含 NULL 的组。若要求所有必修科目均有成绩，还要连接应修科目清单，按科目去重并判断是否缺项；多次考试则先明确取最新、最高还是每次都要达标。

#### 深挖追问

1. **只有姓名能准确区分人员吗？**（补充练习）

   不能处理同名，生产查询应按唯一人员 ID 分组，再取姓名展示。

2. **80 分算满足吗？**（补充练习）

   不满足，原题是严格大于 80；等于 80 的人员应排除。

### MYSQL-003：MySQL 有哪些日志，redo log 和 binlog 如何保持一致？

**常见问法**

- redo log、undo log 和 binlog 分别有什么作用？
- MySQL 日志有哪些？
- 为什么 redo log 和 binlog 要有两个？
- redo log 和 binlog 不一致怎么解决？

- MySQL 事务的原子性底层如何实现？

#### 面试回答

MySQL 常见日志有错误、慢查询、通用查询和 binlog，InnoDB 还有 redo、undo 等。redo 用于崩溃恢复，binlog 用于复制和基于备份的时间点恢复，职责不能互相替代。启用 binlog 时，InnoDB 提交通过内部两阶段提交协调：prepare、写入 binlog、完成引擎提交；崩溃恢复时根据日志中的事务状态决定提交或回滚。

#### 技术细节

redo 记录引擎层恢复所需的修改，空间循环复用；binlog 记录服务层变更事件，支持行或语句等格式，并按文件保留。undo 服务于回滚和历史版本读取，不是 binlog 的替代。概念上，已 prepare 但未完成提交的事务，可根据有效 binlog 事务记录作恢复决策；实际还存在组提交与刷盘阶段。强持久性常结合 innodb_flush_log_at_trx_commit=1、sync_binlog=1，仍依赖存储正确兑现同步写。已发生介质损坏或历史配置导致数据分歧时，应查日志、备份和复制状态恢复，不能简单“补一个 commit”或删日志。

#### 深挖追问

1. **为什么要两个日志？**（面经实际出现；[[面经/百度/一面/0001#Q04：MySQL 有哪些日志，为什么同时需要 redo log 和 binlog，如何保持一致？|MJ002 Q04]]）

   一个服务于存储引擎的物理恢复，一个服务于逻辑变更复制与恢复，数据格式和保留方式不同。

2. **只有 prepare、binlog 没有完整事务记录怎么办？**（面经实际出现；[[面经/百度/一面/0001#Q04：MySQL 有哪些日志，为什么同时需要 redo log 和 binlog，如何保持一致？|MJ002 Q04]]）

   按崩溃恢复协议判断为未完成提交并回滚；不能只凭 prepare 将其视为成功。

3. **事务的原子性底层如何实现？**（面经实际出现；[[面经/百度/一面/0008#Q02：MySQL 的原子性底层如何实现？|MJ019 · 百度 · 一面 · Q02]]）

   靠 undo log：修改前记录撤销信息，回滚沿 undo 链逆向恢复旧版本；提交后 undo 延迟清理以继续服务 MVCC。原子性（undo）与持久性（redo＋WAL）分工不同，崩溃恢复时未提交事务用 undo 回滚、已提交未落盘的用 redo 重放。

### MYSQL-004：InnoDB 索引为什么用 B+ 树，而不是 B 树或哈希表？

**常见问法**

- [[面经/美团/一面/0002#Q11：MySQL 索引的数据结构是 B+ 树，能介绍一下 B+ 树吗？|MJ032 · 美团 · 一面 · Q11]]
- MySQL 索引用什么数据结构，为什么不用 B 树和 HashMap？

- MySQL 索引底层是怎么实现的？
- 索引是什么，有哪些结构和分类？
- 聚簇索引和非聚簇索引是什么？

- 表到千万级查询很慢是什么原因，回表是什么？

#### 面试回答

InnoDB 常用索引采用 B+ 树，非叶节点主要保存导航信息，扇出大、树高低，叶子层有序连接，适合磁盘分页访问和范围扫描。B 树也能用于索引，但内部节点存数据会影响扇出；哈希擅长等值查找，不适合有序遍历和范围查询。不能把 Java HashMap 直接等同于数据库索引。

#### 技术细节

聚簇索引的叶子保存整行，二级索引叶子保存索引列及主键值，缺少所需字段时需要回表。覆盖索引可减少回表，联合索引的键顺序影响可利用的前缀和排序。B+ 树的优势基于页布局、缓存局部性与范围访问，不是“任何时候都比哈希快”。MySQL 不同引擎和索引类型并非都用同一种结构；本题限定常见 InnoDB B-tree 索引，不将全文、空间索引混为一谈。

#### 深挖追问

1. **为什么主键不宜太长？**（补充练习）

   二级索引包含主键，主键过长会增加索引体积与缓存压力。

2. **B 树完全不能做范围查询吗？**（补充练习）

   可以，区别在于遍历和页布局代价；不能把“不擅长”误说成“不支持”。

3. **回表是什么，回表多为什么会慢？**（面经实际出现；[[面经/帆软/一面/0002#Q10：表到千万级查询很慢是什么原因，回表是什么？|MJ027 · 帆软 · 一面 · Q10]]）

   二级索引叶子只存索引列＋主键值，需要其他列时按主键再查一次聚簇索引取整行，这一跳就是回表；命中行数多时变成大量按主键的随机 I/O。缓解：覆盖索引让所需列都在索引内免回表，延迟关联先只查本页主键再回表把次数压到页大小（见 [[#MYSQL-010：什么是覆盖索引，如何设计索引？|MYSQL-010：什么是覆盖索引，如何设计索引？]]、[[#MYSQL-019：大分页查询怎么优化？|MYSQL-019：大分页查询怎么优化？]]）。

### MYSQL-005：MySQL 中有哪些锁，如何分类？

**常见问法**

- MySQL 中有哪几种锁？

- 介绍一下常见的锁，乐观锁和悲观锁是什么？

#### 面试回答

要先说明分类维度。MySQL 有全局读锁、表锁和元数据锁等；InnoDB 的行级并发控制包含共享／排他记录锁，以及 gap、next-key、插入意向等机制，还有表级意向锁。共享／排他描述兼容模式，记录／间隙描述锁定范围，不能把它们当成同一层互斥分类。

#### 技术细节

同一库存行的并发更新：UPDATE 自动申请排他锁；不同事务对同一记录的共享锁可兼容，排他锁与共享／排他锁冲突。普通一致性 SELECT 通常不加记录锁，FOR SHARE 与 FOR UPDATE 则分别属于共享／排他锁定读。十个事务争一行会出现锁等待、吞吐受限或等待超时；只有循环等待才构成死锁，并不是线程数多就必然死锁。锁一般持有到事务结束，具体范围由访问路径及隔离级别决定。

已有锁不代表所有写法都正确：两个事务普通 SELECT 都读到 10，再分别 UPDATE SET stock = 9，后一次可能覆盖前一次的业务效果。可用 stock = stock - quantity AND stock >= quantity 的条件扣减，或同一事务内 SELECT ... FOR UPDATE 后计算更新；优化方案见 [[#MYSQL-007：如何优化秒杀库存更新与热点行锁竞争？|热点库存优化]]。

以 MySQL 8.4 InnoDB 为主：记录锁锁索引记录，gap 锁约束间隙插入，next-key 是记录与前间隙组合；IS/IX 表级意向锁表示后续对记录加锁的意图。完整唯一索引等值命中常可缩小为记录锁，范围及未命中情况需结合执行计划、隔离级别判断。普通一致性 SELECT 通常依靠 MVCC 而不加记录锁，但仍可能持有 MDL；FOR UPDATE 则是锁定读。没有合适索引可能扩大扫描和锁范围，不应描述成必然发生“锁升级”。AUTO-INC 锁模式与自增分配有关。

#### 深挖追问

1. **间隙锁会锁住已经存在的记录吗？**（补充练习）

   纯 gap 锁针对间隙插入，记录本身由记录锁控制；next-key 同时含两部分。

2. **为什么 SELECT 会阻塞 DDL？**（补充练习）

   事务可能持有表的元数据锁，DDL 需要不兼容的 MDL，这与是否有行锁不同。

3. **读写锁是否一致，悲观行锁竞争有什么表现？**（面经实际出现；[[面经/百度/一面/0002#Q12：多个线程修改同一行库存时如何加锁，读写锁及竞争表现有何不同？|MJ005 · 百度 · 一面 · Q12]]）

   需区分快照读与锁定读；S 锁可共享，X 锁互斥，冲突事务等待持锁者结束。单行排队不是死锁；多资源循环等待才需要死锁检测和事务重试。

### MYSQL-006：MySQL 索引有哪些类型？

**常见问法**

- MySQL 索引有哪些类型？

- 索引是什么，有哪些结构和分类？

#### 面试回答

可以从不同维度回答：约束上有主键、唯一和普通索引；列组合上有单列与联合索引；InnoDB 存储组织上有聚簇与二级索引；用途上还有全文、空间等。一个联合唯一二级索引同时属于多个维度，不应把这些名称当成互斥类别。常见结构选型可继续讲 B+ 树。

#### 技术细节

主键要求唯一且非 NULL；MySQL 唯一索引通常允许多个 NULL，需要与业务唯一规则区分。InnoDB 聚簇索引叶子保存行数据，二级索引包含主键；联合键按定义的列序组织，最左前缀影响检索可用性。覆盖索引是某次查询所需列都能由索引提供的访问条件，不是独立 CREATE INDEX 类型。前缀索引、函数索引、降序和不可见索引属于额外定义或优化选项，支持情况看版本与引擎。索引会增加写入和存储成本。

底层原因参见 [[#MYSQL-004：InnoDB 索引为什么用 B+ 树，而不是 B 树或哈希表？|B+ 树与聚簇／二级索引]]。

索引是为查询提供定位路径的数据结构，用空间和写入维护成本换取部分查询的访问效率；未命中合适访问条件或选择率较差时，优化器可能选全表扫描。先解释用途，再从约束、列组合、存储组织等不同维度分类。

#### 深挖追问

1. **联合索引 (a,b) 可以只按 b 高效定位吗？**（补充练习）

   通常不能像按最左前缀那样直接定位，优化器可能采用其他访问方式，需看执行计划。

2. **建很多索引是不是更快？**（补充练习）

   只可能改善部分读路径，同时增加写维护和空间开销，应依据查询模式选。

3. **索引是什么？**（面经实际出现；[[面经/百度/一面/0005#Q15：索引是什么，有哪些结构和分类？|MJ008 · 百度 · 一面 · Q15]]）

   帮助定位记录和减少扫描的访问结构，但会占空间并增加更新成本，不保证每次查询都使用。

4. **聚簇索引和非聚簇索引有什么区别？**（面经实际出现；[[面经/百度/一面/0007#Q08：聚簇索引和非聚簇索引是什么？|MJ009 · 百度 · 一面 · Q08]]）

   以 InnoDB 为前提，聚簇索引叶子保存整行并决定行的存储组织；二级索引叶子保存索引列和聚簇主键值，未覆盖查询列时需按主键回表。不同引擎的组织方式不能一概而论。

### MYSQL-007：如何优化秒杀库存更新与热点行锁竞争？

**常见问法**

- MySQL 如何优化高并发库存扣减及热点单行锁排队？

#### 面试回答

先用主键或合适唯一索引定位库存，执行带 stock >= quantity 条件的原地扣减，检查影响行数，并把事务缩短到必要的扣减与记录写入。用唯一业务键防重复领取，监控锁等待和慢 SQL，控制消费并发与连接池。单行写入本身要串行，继续扩线程不能突破这条瓶颈；可以按活动、库存桶分配互不重叠额度，或按同一库存键排队、谨慎合并扣减。读写分离和增加普通索引都不能直接解决同一行的写锁竞争。

#### 技术细节

示例基于 MySQL 8.4 InnoDB，假设 quantity 是已校验的正整数：

```sql
UPDATE coupon_stock
SET stock = stock - :quantity
WHERE id = :batch_id AND stock >= :quantity;
```

这是绑定参数示意，实际 JDBC 可使用问号占位符。影响行数为 1 才代表本次条件扣减成功；发券记录失败要回滚同一事务。减少无关二级索引和长事务有助于减少写入成本；多行更新采用固定顺序，并在死锁后重试完整事务。库存分桶必须满足各桶额度总和不超过总量，热点桶不足时需要有约束的调拨；乐观版本号在高冲突下可能造成大量重试。批量扣减可以减少往返，但必须保留每个请求的分配结果、幂等和失败处理，不把整个批次只记成一个计数。

#### 深挖追问

1. **频繁单行更新导致锁排队如何优化？**（面经实际出现；[[面经/百度/一面/0002#Q10：MySQL 如何优化高并发库存扣减及热点单行锁排队？|MJ005 · 百度 · 一面 · Q10]]）

   先减少持锁时间和无效请求，再按业务允许的粒度拆额度或串行调度同一键；不能依靠连接池翻倍解除同一行串行约束。

#### 技术细节

以下对应查证时 HikariCP 官方 README；原项目连接池及版本未知，不给通用默认数值。

| 参数 | 含义与约束 |
| --- | --- |

| minimumIdle | 尽力维持的最小空闲连接数，影响突发流量时的建连。 |
| connectionTimeout | 等待池中可用连接的时间，不是查询执行上限。 |

| autoCommit、transactionIsolation | 控制默认事务行为，要与框架事务管理匹配。 |
| leakDetectionThreshold | 超时未归还连接时输出诊断信息，不等于自动终止业务。 |

### MYSQL-009：MySQL 的 InnoDB 和 MyISAM 有什么区别？

**常见问法**

- MySQL 的 InnoDB 和 MyISAM 有什么区别？

#### 面试回答

以 MySQL 8.4 为例，InnoDB 支持事务、MVCC、行级锁和外键，并用 redo 等实现崩溃恢复，适合常见并发事务业务；MyISAM 不支持事务与外键，主要使用表级锁，没有 InnoDB 那样的事务崩溃恢复能力。InnoDB 按聚簇索引组织行，二级索引包含主键；MyISAM 索引和数据分离，索引定位数据记录。

#### 技术细节

InnoDB 的行级锁不代表没有表级意向锁、元数据锁等；也不代表所有读都加行锁。MyISAM 可以进行表检查与修复，但不能等同于事务原子恢复。MyISAM 可快速取得无 WHERE 的精确整表行数；InnoDB 需要考虑事务可见性，不能维护适用于所有事务的单一精确计数。不能笼统说 MyISAM 读一定更快，或 InnoDB 不支持全文索引；应依据事务、并发、可靠性和查询模式选型。

#### 深挖追问

1. **为什么事务业务通常选 InnoDB？**（补充练习）

   它提供提交回滚、并发隔离和崩溃恢复等关键语义；MyISAM 的表级锁与非事务模型不适合直接承担同等要求。

### MYSQL-010：什么是覆盖索引，如何设计索引？

**常见问法**

- 什么是覆盖索引，如何设计索引？

- MySQL 的覆盖索引、前缀索引、索引下推分别是什么？

#### 面试回答

覆盖索引指某条查询所需的列都可由一个索引提供，通常能减少回表；它是查询和索引的关系，并非独立索引类型。设计索引要从高频 SQL 的过滤、连接、排序与返回列出发，考虑联合索引列序和最左前缀，再结合选择性、写入成本与执行计划验证，不能给每个字段都建索引。

#### 技术细节

以 MySQL 8.4 InnoDB 为例，查询 WHERE tenant_id=? AND status=? ORDER BY created_at LIMIT 20，可评估 (tenant_id,status,created_at)；若只返回这些列和主键 id，二级索引已带主键，可能形成覆盖。等值条件后安排范围或排序列是常见起点，但范围边界后的列能否用于定位、过滤或排序要分别分析。不要机械按区分度从高到低排序，需兼顾可复用前缀。EXPLAIN 的 Using index 常表示覆盖，Using index condition 是索引条件下推，不能混同；实际还可能为 MVCC 可见性访问聚簇记录。避免过宽与冗余索引，并用代表性数据检验读收益和写成本。

#### 深挖追问

1. **覆盖索引是不是一定完全不访问聚簇记录？**（补充练习）

   从所需列看不必回表取额外字段，但 InnoDB 的事务可见性检查等仍可能访问聚簇记录；口述时说“通常减少回表”，不作绝对保证。

### MYSQL-011：MySQL 服务层与存储引擎架构是什么？

**常见问法**

- MySQL 服务层与存储引擎架构是什么？

#### 面试回答

以 MySQL 8.4 为例，可分客户端连接与认证、SQL 服务层和存储引擎层。SQL 服务层负责解析、优化与执行协调，存储引擎负责具体数据和索引访问；InnoDB 还提供事务、锁、MVCC、缓冲池及崩溃恢复。查询通过执行计划访问引擎取得行并返回结果；不能把 MySQL 服务层和 InnoDB 当成同一个模块，也不要在现代 8.x 查询流程中加入已移除的 Query Cache。

#### 技术细节

以一次 SELECT 为线索：连接认证→解析与语义检查→优化访问路径和连接顺序→执行器调用存储引擎接口→引擎经缓冲池或磁盘访问记录→返回结果。优化计划不保证总是最佳，要结合 EXPLAIN 与实际数据。服务层与引擎分工允许表使用不同引擎；binlog 属于服务层，InnoDB 的 redo、undo 和数据页服务于其事务机制。MySQL 8.x 已移除 Query Cache，缓冲池仍然存在，二者不是同一缓存。

1. **存储引擎只负责读写磁盘吗？**（补充练习）

   不只。InnoDB 同时维护缓冲池、索引、锁和事务恢复等，服务层通过接口协调访问。

### MYSQL-012：MySQL 如何存储、查询和索引 JSON？

**常见问法**

- MySQL 如何存储、查询和索引 JSON？

#### 面试回答

MySQL 8.4 可以用原生 JSON 列，写入会检查文档是否合法，内部使用适合访问成员的二进制表示；也可以用 TEXT 保存原始文本，但那不自动提供 JSON 类型的校验和访问优化。可用 JSON_EXTRACT 或箭头操作符读取路径，用 JSON_SET 更新字段。需要按字段检索时，可以抽取标量到生成列再建索引；频繁关联、约束和排序的稳定字段通常适合独立关系列。

#### 技术细节

以 MySQL 8.4 为例：

```sql
CREATE TABLE event_demo (id BIGINT PRIMARY KEY, payload JSON);
INSERT INTO event_demo VALUES (1, JSON_OBJECT('city', 'Shanghai'));
SELECT payload->>'$.city' FROM event_demo WHERE id = 1;
UPDATE event_demo SET payload = JSON_SET(payload, '$.city', 'Beijing') WHERE id = 1;
```

箭头双大于号可获得去引号后的值。原生 JSON 不等于任意文本保真容器，若必须保留原始格式应另存原文；SQL NULL 和 JSON null 也不同。JSON 列不能直接当普通标量列建立整个文档的常规索引，可在提取标量的生成列上建索引；数组另有多值索引机制，适用约束需按版本查证。

1. **JSON 格式文本放进 TEXT 和 JSON 列一样吗？**（补充练习）

### MYSQL-013：CHAR 和 VARCHAR 的长度与尾空格语义有何区别？

**常见问法**

- CHAR 和 VARCHAR 的长度与尾空格语义有何区别？

#### 面试回答

CHAR(M) 表达固定字符长度，VARCHAR(M) 表达最长 M 个字符的变长字符串；M 不是固定字节数，存储还受字符集和行格式影响。CHAR 有补齐及读取时处理尾空格的语义，VARCHAR 保存实际内容并额外记录长度，通常保留尾空格。适合长度稳定的值可考虑 CHAR，长度变化大的文本可考虑 VARCHAR；比较时尾空格是否有意义还取决于排序规则，不能说固定长就一定更快。

   不是，定义长度按字符；多字节字符集可能需要更多字节，并有长度元数据。

### MYSQL-014：InnoDB 的 MVCC 如何工作？

- 数据库中的 MVCC 是什么？

#### 面试回答

MVCC 让一致性读依据可见性规则读取行的合适版本，减少读写互相阻塞。以 MySQL 8.4 InnoDB 为例，行记录关联事务 ID 和回滚指针，通过 undo 链查旧版本，再依据 Read View 判断可见性；锁定读和写操作还要使用锁。

#### 深挖追问

1. **可重复读是否在 BEGIN 时必然建立快照？**（补充练习）

### MYSQL-015：如何排查和优化慢 SQL？

**常见问法**

- [[面经/美团/一面/0002#Q25：慢查询怎么定位，SQL 如何优化？|MJ032 · 美团 · 一面 · Q25]]

- 查询数据库接口 RT 越来越高怎么处理？

#### 面试回答

先定位再优化：从监控、调用链和慢查询日志确认具体 SQL、参数、频率、耗时分布和业务影响，同时区分数据库执行、锁等待、连接池等待与网络延迟。对可复现语句查看 `EXPLAIN`，在安全环境按需执行 `EXPLAIN ANALYZE`，检查估算与实际行数、访问路径、连接顺序、排序、临时表、回表和循环次数。再针对证据调整 SQL、索引、数据访问量或事务范围，最后用代表性数据压测并观察上线指标，确认收益且没有明显写放大或回归。

#### 技术细节

慢查询日志由阈值和扫描行数等条件筛选，日志顺序不等同于语句开始顺序；应结合摘要工具或可观测平台按总耗时、平均耗时、P95／P99、次数和扫描行数排序，而不只盯单次最慢语句。`EXPLAIN` 给出计划，`EXPLAIN ANALYZE` 会实际执行并返回迭代器耗时、实际行数和循环次数，生产环境使用前必须评估读写副作用与负载。

常见原因包括缺少或选错索引、联合索引列序不匹配、对索引列做不利于定位的表达式、返回或扫描过多数据、连接与子查询计划不佳、排序或临时表开销、统计信息失真、锁竞争、长事务、缓存命中变化和资源饱和。优化措施必须对症：减少 `SELECT *` 和无用扫描，设计可复用而不过宽的索引，改写分页或批处理方式，缩短事务并统一加锁顺序，必要时更新统计信息或调整数据模型。索引会增加存储和写维护成本，不能把“加索引”当成固定答案。

   核心是 `type`（访问类型，区分 const/ref/range/index/ALL）、`key`／`possible_keys`（实际用的索引与候选，判断是否选错）、`rows`×`filtered`（预估扫描与过滤后行数量级）、`Extra`（Using index 覆盖、Using index condition 下推、Using where 回表后过滤、Using filesort／Using temporary 排序分组代价）、`key_len`（联合索引实际使用长度，定位左前缀断点）；`id`／`select_type` 用于子查询结构。EXPLAIN 是估算，统计信息过期时与实际偏差大，可更新 ANALYZE TABLE 或安全环境用 EXPLAIN ANALYZE 核对。

### MYSQL-016：多条件过滤并排序时如何设计联合索引？

**常见问法**

- `WHERE language='粤语' AND time>1990 AND style='慢歌' ORDER BY score DESC` 如何建索引？
- score 是否加入联合索引，language 和 style 谁放前面？

#### 面试回答

先看数据分布、返回列、是否有 `LIMIT` 及其他高频查询，再给候选索引并实测。两个等值条件通常排在范围列之前；`language` 与 `style` 的内部顺序不能只靠名称决定，要看选择性和其他查询对左前缀的复用。若重点是按年份快速过滤，可试 `(language, style, time)`，但 `time` 是范围后通常不能再利用后续 `score` 的顺序消除排序。若有较小 `LIMIT` 且高分记录很快满足年份条件，可试 `(language, style, score DESC, time)`，按 score 顺序扫描并过滤 time。没有 `LIMIT` 或命中量很大时结论可能相反。

#### 技术细节

MySQL 8.4 InnoDB 的联合 B-tree 按 key part 依次排序。等值前缀固定后，索引才可能继续服务后续范围或排序；一个范围访问与另一个排序目标通常存在取舍。`score` 加入索引不是免费：会增加索引宽度、写放大和维护成本，也不等于覆盖查询，是否回表还取决于 `SELECT` 列。降序 key part 可让相应方向前向扫描，但 MySQL 也能在适用情况下反向扫描索引。

候选方案应在代表性数据上比较 `EXPLAIN ANALYZE` 的实际扫描行数、是否 filesort、回表、耗时及写入影响。选择性可查看统计信息并用实际基数／频率分布验证；“高区分度永远放最前”不是规则，因为列序还决定可复用前缀和排序能力。若查询不含 `LIMIT` 且返回大量行，索引顺序扫描也未必优于过滤后排序。

#### 深挖追问

1. **language 和 style 谁放前面？**（面经实际出现；[[面经/字节/一面/0001#Q16：多条件过滤并按 score 排序的 SQL 如何设计联合索引？|MJ011 · 字节 · 一面 · Q16]]）

   对这条同时使用两列等值条件的 SQL，两者都位于范围／排序列前时，内部顺序常需结合选择性和其他查询的左前缀复用决定；用真实分布和执行计划验证。

2. **score 必须建进联合索引吗？**（面经实际出现；同上来源）

### MYSQL-017：乐观锁和悲观锁如何实现与选择？

**常见问法**

- 乐观锁实现逻辑是什么？
- 悲观锁代码怎么写？

- 乐观锁和悲观锁是什么，分别有哪些优缺点？

#### 面试回答

乐观锁假设冲突较少，读取时不长期占锁，提交更新时用版本号或原值校验是否仍未变化；条件更新影响 1 行才成功，影响 0 行表示冲突，应重读后有限重试或返回冲突。悲观锁假设竞争较强，在事务内先用 `SELECT ... FOR UPDATE` 锁定目标记录，再校验并更新，提交或回滚时释放。乐观锁减少等待但高冲突下可能反复失败；悲观锁能串行化竞争更新，但会阻塞并带来等待和死锁风险。选择取决于冲突率、临界区长度、失败成本与一致性要求。

#### 技术细节

以 MySQL 8.4 InnoDB 的库存行为例，乐观锁可写成：

```sql
SELECT stock, version FROM product_stock WHERE id = ?;

UPDATE product_stock
SET stock = ?, version = version + 1
WHERE id = ? AND version = ?;
```

应用必须检查更新行数，并保证业务幂等、限制重试次数。若只是扣减库存，`UPDATE ... SET stock = stock - ? WHERE id = ? AND stock >= ?` 也能把校验与修改合成一个原子条件更新，不一定需要显式 version。悲观锁示例：

```sql
START TRANSACTION;
SELECT stock FROM product_stock WHERE id = ? FOR UPDATE;
UPDATE product_stock SET stock = ? WHERE id = ?;
COMMIT;
```

锁定读和更新必须在同一事务与连接中。`FOR UPDATE` 锁的实际范围取决于索引、条件和隔离级别；应使用合适索引、缩短事务，并对多行资源采用稳定加锁顺序。Spring 中通常由 `@Transactional` 包住查询和更新，不能只在一个已结束的仓储调用上加注解就假定锁仍然存在。

#### 深挖追问

1. **乐观锁更新失败后应该无限重试吗？**（补充练习）

   不应该。应根据业务重读、退避并限制次数；高冲突持续失败时要考虑条件原子更新、排队或悲观锁，而不是制造重试风暴。

### MYSQL-018：什么是最左前缀匹配法则，什么时候会失效？

**常见问法**

- 最左前缀匹配法则是什么，什么时候会失效？

- 索引失效的常见场景有哪些？
- 查询能不能匹配联合索引？

#### 面试回答

联合索引的 B+ 树键按列定义顺序排序，查询要从最左列开始连续匹配才能利用有序性定位：对 (a,b,c)，条件覆盖 a、a＋b、a＋b＋c 的等值前缀都能定位；只给 b 或 c 条件时无法从树根确定区间，通常用不上该索引定位。等值前缀之后遇到范围条件，范围列再往后的列不能再用于定位——a=1 AND b>2 AND c=3 只用 (a,b) 定位，c 在索引内过滤或回表验证。所谓“失效”的常见触发：跳过前导列、范围切断后续列、对索引列套函数或表达式、字符串列与数字比较发生隐式类型转换、LIKE 以百分号开头。严谨表述是“不能用于定位”，优化器仍可能把它当覆盖索引扫描，或走 Skip Scan 等特例；用不用、用到第几列以 EXPLAIN 为准。

#### 技术细节

等值不只是 `=`：`IN` 在范围优化中也可按多个等值区间处理。表达式失效示例：`WHERE YEAR(d)=2020` 用不上 d 索引，改写成 d 的日期范围即可；隐式转换方向决定后果——utf8 列与 latin1 值或字符串列与数字比较时，转换施加在列侧会使索引不可定位，常量侧转换则无碍。前导列无等值条件时，MySQL 8.0（8.0.13 起，8.4 文档仍保留）的 Skip Scan 可对前导列的每个离散值做多个小区间扫描，`Extra` 显示 `Using index for skip scan`，但要求前导列离散值少且查询能被索引覆盖，不能背成“跳列也没事”。`a=1 AND c=3` 跳过 b 时，若走的是覆盖索引，索引内过滤仍然高效——“失效”不等于“完全不被使用”。LIKE 前缀通配符无法定位有序结构，考虑全文、n-gram 或改业务检索方式；OR 混合无索引列通常导致全表扫描。排序同理：`WHERE a=? ORDER BY c` 中间缺 b 时无法用索引序消 filesort，除非过滤后行数极少。

#### 深挖追问

1. **a=1 AND c=3（跳过 b）时索引 (a,b,c) 完全没用吗？**（补充练习）

   不是：a 仍可定位，c 条件可在索引内过滤（ICP）；若查询列被索引覆盖还能免回表，只是 c 不能参与树定位。

2. **为什么范围条件后面的列“失效”？**（补充练习）

   索引按 (a,b,c) 全局有序，b 取一段区间时 c 只在每个 b 值内部有序，无法定义 c 的单一区间；优化器退化为过滤。

3. **“区分度高的列放最前”对吗？**（补充练习）

   不是通用规则。列序先满足高频查询的左前缀复用与排序方向，再在选择性等价候选中比较选择性与实测（见 [[专题题库/MySQL#MYSQL-016：多条件过滤并排序时如何设计联合索引？|MYSQL-016：多条件过滤并排序时如何设计联合索引？]]）。

### MYSQL-019：大分页查询怎么优化？

**常见问法**

- 大分页查询怎么优化？

- 大数据的分页查询会出现什么问题，怎么解决？

#### 面试回答

`LIMIT n OFFSET m` 在大偏移时要把前 m 行扫出来再丢弃，二级索引分页还伴随海量回表，延迟随页深线性增长。核心手段是 seek 法（书签／游标分页）：不再传页码，带上上一页最后一行的排序键值，用 `WHERE (排序列, id) > (?, ?) ORDER BY 排序列, id LIMIT n` 直接走索引定位，代价是不支持任意跳页。必须保留页码语义时用延迟关联：先用覆盖索引的子查询 `SELECT id ... LIMIT n OFFSET m` 拿到本页主键，再回表取整行，减少扫描行宽与回表随机 I/O。导出场景不走在线分页，用流式批次或离线索引（如 ES）；业务上限制最大页深、去掉精确总数也常见。

#### 技术细节

延迟关联示例：`SELECT t.* FROM t JOIN (SELECT id FROM t ORDER BY id LIMIT 10 OFFSET 1000000) x ON t.id = x.id`——offset 扫描仍在，但只扫窄索引，收益来自避免宽行回表。Seek 游标要求排序确定性：非唯一列排序必须追加唯一列做 tiebreaker，否则翻页会漏行或重复；游标值要能序列化进请求。深页的 `COUNT(*)` 同样昂贵，可改为“下一页”导航、近似计数或预计算。一级页游标失效场景：排序列值在翻页期间被更新，需业务容忍或用快照／版本号。MySQL 没有原生 keyset 语法，游标由应用层构造；服务端游标可用游标 ID 映射到上次位置。

#### 深挖追问

1. **seek 分页没法跳到第 100 页怎么办？**（补充练习）

   确认跳页是否真实需求；确需时限制最大页深、走支持定位的检索系统（ES search_after 之外还有游标快照），或预计算页起点集合。

2. **为什么二级索引大分页比主键分页更慢？**（补充练习）

   每行还要按主键回表，offset 丢弃的行也逐一回表，随机 I/O 被放大；覆盖索引或延迟关联可显著缓解。

### MYSQL-021：什么是前缀索引和索引下推（ICP）？

**常见问法**

- MySQL 的覆盖索引、前缀索引、索引下推分别是什么？

#### 面试回答

前缀索引：只对字符串列的前 N 个字符建索引（如 INDEX(email(6))），索引更小、写入更快，但区分度下降——N 用 `COUNT(DISTINCT LEFT(col,n))/COUNT(*)` 与全长选择性比较选取；前缀索引无法覆盖该列完整值（命中后仍要回表核对），也不能支持该列完整的 ORDER BY／GROUP BY 语义。索引下推（ICP，MySQL 5.6+）：使用联合索引时，无法参与范围定位的后续列条件（如 (name,age) 上 `name LIKE '张%' AND age=20` 的 age 条件）由存储引擎在索引层先判断，不满足直接跳过，减少回表次数；EXPLAIN Extra 显示 `Using index condition`。覆盖索引见 [[专题题库/MySQL#MYSQL-010：什么是覆盖索引，如何设计索引？|MYSQL-010：什么是覆盖索引，如何设计索引？]]。

#### 技术细节

前缀长度是“区分度换空间”的权衡：过短导致大量候选回表，过长收益趋零；BLOB／TEXT 只能前缀索引。ICP 只作用于二级索引读，主键扫描与覆盖索引不需要；它减少回表但不改变访问类型量级，ICP 过滤后 rows 估算仍可能偏大。5.7+ 优化器还有 MRR 等其他机制，不要与 ICP 混称“下推”；8.0 部分场景（如派生表条件下推）是另一层优化。三者共同点都是围绕“少读数据、少回表”，判断收益都以 EXPLAIN 与实际压测为准。

#### 深挖追问

1. **前缀索引还能加速 LIKE 'abc%' 吗？**（补充练习）

   能，最左前缀匹配仍适用；但 LIKE '%abc' 前置通配用不上，且前缀命中后完整值还要回表核对。

### MYSQL-022：MySQL 主从复制的数据同步流程是怎样的？

**常见问法**

- [[面经/美团/一面/0002#Q26：MySQL 主从，读取可能数据不一致，你觉得怎么解决？|MJ032 · 美团 · 一面 · Q26]]
- MySQL 的主从复制数据同步流程是怎样的？

- 主从复制是同步的吗？
- 针对主从同步延迟，如何从业务层设计优化？

#### 面试回答

三个线程接力：主库事务提交时写 binlog；从库配置 `CHANGE REPLICATION SOURCE` 后，主库为每个从库起 binlog dump 线程，按位点（File+Position）或 GTID 发送事件；从库 IO 线程接收并追加到 relay log；SQL 线程读取 relay log 重放事件，应用后更新复制进度。复制默认异步——主库提交不等任何从库，宕机可能丢最后事务；半同步（lossless 配置）要求至少一个从库确认收到落 relay log 后主库才返回客户端；从库回放可开并行复制（按组／按表等策略）降低延迟。

#### 技术细节

binlog 格式 ROW（默认）记录行变更前后镜像，STATEMENT 有不确定函数风险，MIXED 折中。主从延迟（Seconds_Behind_Source）来源：从库单事务重放串行度、大事务、从库负载、网络；读从库要接受读到旧数据，读己之写场景走主库、GTID 等待（`WAIT_FOR_EXECUTED_GTID_SET`）或半同步。故障切换时异步复制可能永久丢未送达事件，半同步在超时后降级异步仍有窗口——按 RPO 要求选架构并演练。行重放与主库并发提交的顺序性由组提交／LOGICAL_CLOCK 等机制协调，细节随版本变化，按 8.4 文档核对。

#### 深挖追问

1. **从库会读到脏数据吗？**（补充练习）

   不是脏读，而是旧数据：复制延迟导致从库尚未重放已提交事务；主从一致性监控（pt-table-checksum 类）定期核对。

2. **不改中间件，业务层怎么消化主从延迟？**（面经实际出现；[[面经/百度/二面/0003#Q09：针对主从同步延迟，如何从业务层设计优化？|MJ020 · 百度 · 二面 · Q09]]）

   按“读己之写”的重要性分级路由：写后立读的关键接口强制走主库（注解／Hint／事务内自动主库标记）；会话粘性——用户写后短时间内的读都走主库或缓存；需要“至少读到某版本”时用 GTID／位点等待；前端提交成功页先展示本地已知数据；从库查空不立即判“不存在”，主库复核一次。全量读主库等于放弃读写分离，分级才是关键。

### MYSQL-023：SELECT FOR UPDATE 未命中行后并发 INSERT，锁会怎么冲突？

**常见问法**

- 两个事务同时执行，说明它们的执行流程，失败还是成功？

#### 面试回答

场景：主键 id 已有 1,3,5,10,15,20；事务 A `SELECT * FROM t WHERE id=7 FOR UPDATE`（行不存在），事务 B 随后 INSERT 6、8、11。RR 隔离级别下，A 的点查未命中不是“不加锁”，而是在应插入位置加 gap lock 锁住间隙 (5,10)，A 语句成功；B 的 INSERT 6 申请该间隙内的插入意向锁，与 gap lock 冲突被阻塞——B 事务内后续的 8、11 因语句顺序执行而一起等待。结果取决于时序：A 在 B 超时前提交或回滚，B 继续且三条插入都成功；等待超过 `innodb_lock_wait_timeout`（默认 50s）则 B 报锁超时错误，该语句失败，事务是否整体回滚由应用的错误处理决定。

#### 技术细节

口径要分隔离级别：RC 及以上关闭 gap lock（RC 无间隙锁，仅外键／唯一键检查等场景例外），A 未命中不加间隙锁，B 直接成功——所以这题先确认隔离级别再下结论。gap lock 只防“插入进间隙”，不防读；两个事务对同一间隙都只持有 gap lock（共享属性）可共存，冲突发生在插入意向锁。11 落在间隙 (10,15)，与 A 无冲突，只是被 B 事务内前序阻塞连带等待。若 B 改为先插 11 再插 6，则 11 先成功。唯一键冲突时另有锁语义（S 锁等），不与本场景混谈。现场答题先复述前提（RR、autocommit=0、两事务并发交错从 A 开始），再给分支结论。

#### 深挖追问

1. **A 查询改成 WHERE id>5 AND id<10 FOR UPDATE 结果不同吗？**（补充练习）

   同方向：范围锁定读对覆盖的间隙／记录加 next-key 类锁，B 的 6、8 仍被阻塞；具体锁范围与执行计划（走哪个索引）有关。

### MYSQL-024：多个字段单独建索引和建联合索引有什么区别？

**常见问法**

- 联合索引场景下，单独给字段建索引和建联合索引有什么区别？

#### 面试回答

单列索引各自独立：任一单列条件都能用，多列组合查询最多靠 index_merge（排序合并／交集合并），执行不稳定、常多次回表；联合索引按列序服务左前缀组合：一条 (a,b,c) 索引同时支持 a、a+b、a+b+c 的定位与覆盖，多条件一次收敛，通常更快、回表更少。代价与限制：联合索引只服务以首列开头（或能构成前缀）的查询，单独查 b、c 用不上；列序设计（等值前、范围后、选择性）决定覆盖面；索引数量本身有写入放大与空间成本。选择依据是真实查询组合分布：高频一起出现的条件做联合索引，各列独立查询多才保留单列，并用冗余索引检查（(a) 与 (a,b) 并存时前者常可删）收敛。

#### 技术细节

MySQL 优化器按统计信息选路：即使每列都有单列索引，组合条件的 index_merge 也常因回表代价被放弃而退回全表扫，联合索引的“索引内过滤＋少回表”优势在大表明显。范围列之后的联合索引列不再用于定位（见 [[专题题库/MySQL#MYSQL-018：什么是最左前缀匹配法则，什么时候会失效？|MYSQL-018：什么是最左前缀匹配法则，什么时候会失效？]]），但可受益于索引下推在索引层先过滤（见 [[专题题库/MySQL#MYSQL-021：什么是前缀索引和索引下推（ICP）？|MYSQL-021：什么是前缀索引和索引下推（ICP）？]]）。等值列在联合索引内部的顺序对“能否命中”通常不敏感（都是等值），但对其他查询组合的复用性敏感——把被单独查询或作范围起点的列放前。判断收益以代表性 SQL 的 EXPLAIN（key、key_len、rows、Extra）与压测为准，不靠直觉堆索引。

   看组合：等值集合内部顺序不破坏命中，但若该列要独立被查询或作为范围起点，放前面才有复用性。

### MYSQL-025：行式存储与列式存储有什么区别，各适用什么场景？

**常见问法**

- 行式存储与列式存储的区别，适用场景？

#### 面试回答

行式存储把一行的各列连续存放：读写整行实体快，适合 OLTP——点查、按主键更新、事务插入，代表 MySQL/PostgreSQL。列式存储把同一列的值连续存放：列内类型相同、重复模式多，压缩率高；分析查询只读所需列并可跳过无关数据（min/max 等粗索引），大范围聚合快，代表 ClickHouse、Parquet 类数仓格式。代价对称：列式的更新/删除要重写文件或走合并（LSM 类），不适合高频小事务与整行读；行式做大范围聚合要扫全行，I/O 放大。混合架构常见：行存做交易主库，异步同步到列存做分析。

#### 技术细节

行式“取一行快、扫一列慢”（每行都要触碰）；列式“扫一列快、拼一行慢”（跨列文件/块重组）。列存的排序与分区（如按时间分区＋按常用过滤列排序）决定扫描裁剪效果；压缩收益来自同类型连续存储（RLE、字典编码）。MySQL 侧 InnoDB 是行存，但并行查询／列存索引类能力（如 HeatWave、列存索引形态）说明二者是布局选择而非产品阵营；答题别把“列存＝某数据库”。选型看负载形态：TP 与 AP 的读写比例、事务要求、查询列跨度，别用单一“性能更好”下结论。

#### 深挖追问

1. **列存为什么常配 LSM 或批量导入？**（补充练习）

   原位更新会破坏列的连续布局；追加写＋后台合并（或微批导入）才能同时保住写入吞吐与扫描压缩收益。

### MYSQL-026：三层 B+ 树能存多少数据，怎么估算？

**常见问法**

- [[面经/美团/一面/0002#Q12：一行数据 1KB、主键 bigint、树高约 3 层，大概多少数据量，怎么思考？|MJ032 · 美团 · 一面 · Q12]]
- 三层高的 B+ 树能存储多少数据？

#### 面试回答

这是估算题，先摆假设再算，别背常数。以 InnoDB 默认页 16KB 为例：非叶节点存（索引列＋页指针），bigint 主键约 8＋6≈14 字节/项，一页可放约 1170～1200 个分叉；叶子节点存整行，若行平均 1KB，一页约放 16 行。三层＝根 1200 × 第二层 1200 × 每叶 16 行 ≈ 2300 万行——这就是“三层 B+ 树约撑两千万行”的口径。追问必答敏感性：行更小（100B）叶子每页约 160 行，同三层可到两亿级；主键越宽分叉越少；估算依赖页大小、行宽与填充率，报数前先问条件。

#### 技术细节

假设逐项可换：页大小由 `innodb_page_size` 决定（默认 16KB）；非叶项大小＝索引列宽度＋页指针（InnoDB 约 6 字节），还要扣除页头页尾与填充开销，取整时为约数；叶行数＝页可用空间÷平均行大小，行含 NULL 位图、变长头与事务隐藏列（DB_TRX_ID、DB_ROLL_PTR 等），实际比列定义宽。二级索引树更矮胖：叶子只存索引列＋主键，同样三层能放远多于聚簇索引的键值。树高与查询 I/O 的关系：三层意味着一次主键等值查找最多 3 次页访问，根与上层节点通常常驻缓冲池，真正落盘的往往只有叶层——这也是“数据量千万级仍很快、上亿后树变四层才开始明显”的机制解释，与 [[#MYSQL-004：InnoDB 索引为什么用 B+ 树，而不是 B 树或哈希表？|MYSQL-004：InnoDB 索引为什么用 B+ 树？]] 的扇出论证相连。

#### 深挖追问

1. **为什么常说主键用自增 int/bigint 而不是 UUID？**（补充练习）

   主键宽度直接进入每个非叶项和每个二级索引叶子；越宽扇出越小、树越高，且随机主键造成页分裂碎片，进一步拉低有效密度。

### MYSQL-027：事务的 ACID 分别由什么机制保证？

**常见问法**

- MySQL 事务，事务特性逐个解释展开：原子性、隔离性、持久性、隔离机制、MVCC、间隙锁。
- ACID 分别靠什么实现？
- 数据库是怎么保证事务的原子性的？

#### 面试回答

**原子性（Atomicity）**——事务里的修改要么全生效要么全撤销，靠 **undo log**：改数据前先把旧值写进 undo，回滚时按 undo 逆向恢复；undo 也遵循先写日志再改数据的顺序，所以崩溃时未提交事务同样能被回滚掉。**持久性（Durability）**——提交后数据不丢，靠 **redo log ＋ WAL**：先写 redo 再改内存页，崩溃后重放 redo 把已提交事务补回；强度由 `innodb_flush_log_at_trx_commit` 决定（=1 每次提交刷盘，最安全；=2 只写到 OS 缓存；=0 由后台每秒刷），再配 binlog 与双写缓冲（防页断裂）。**隔离性（Isolation）**——并发事务互不干扰，靠**锁 ＋ MVCC**：写与当前读用行锁／间隙锁互斥，普通 SELECT 走快照读不加锁。**一致性（Consistency）**——数据满足约束与业务不变量，它是目标而不是某个具体机制：由前三个特性加上主键／唯一／外键／非空约束、触发器以及正确的 SQL 共同达成。

面试时最容易被抓的两句话：一是“ACID 不是四种事务”，二是“隔离性不等于串行执行”——MVCC 让读不阻塞写，代价是读到的可能是快照而非最新值，这正是 RC 与 RR 的差别所在。

#### 技术细节

**undo 与版本链是同一份数据的两种用途**：undo 里保存的历史版本通过行内的回滚指针串成版本链，回滚时倒着走，快照读时按 read view 顺着找第一个可见版本——所以“回滚能力”和“MVCC 读历史”共用 undo。区别在于 purge 线程何时能清理 undo：仍被任何活跃快照需要就不能删。

**redo 与 binlog 的一致性**：InnoDB 提交走两阶段——redo 进入 prepare 并刷盘 → 写 binlog → redo 提交；崩溃恢复时以“binlog 是否完整”决定该事务提交还是回滚，否则会出现“库改了但从库没收到 binlog”或反之。`binlog_order_commits`、`sync_binlog` 等参数决定这一链路的性能与耐久折中。

**隔离机制的粒度**：隔离级别（RU／RC／RR／串行化）定义允许哪些异常（脏读、不可重复读、幻读）；InnoDB 在 RR 下用 next-key lock（记录锁＋间隙锁）限制范围内的插入来防当前读的幻读，普通快照读靠 read view 复用事务首次建立的快照，所以“别人插了新行我看不见”，但并不阻止对方插入——把 MVCC 说成“彻底解决幻读”不准确。间隙锁的范围依赖索引与执行计划：条件走索引时锁相关区间，走不到索引时可能锁住扫描到的大量记录，这是锁等待与死锁的常见根因（详见 [[专题题库/MySQL#MYSQL-005：MySQL 中有哪些锁，如何分类？|MYSQL-005：MySQL 中有哪些锁]]）。

**一致性还要看业务层**：余额扣减与流水写入必须同事务，跨服务则退化为最终一致（幂等＋对账＋补偿，见 [[专题题库/系统设计#SYS-010：如何保证数据库写入与消息发送的一致性？|SYS-010：数据库写入与消息一致性]]）；数据库约束挡不住“状态机跳变”，那要靠条件更新（`where status = 'PENDING'`）表达。

#### 深挖追问

1. **为什么 RR 下重读结果不变，却还可能出现幻读？**（面经实际出现；[[面经/美团/一面/0002#Q23：MySQL 事务特性逐个展开：原子性、隔离性、持久性、隔离机制、MVCC、间隙锁|MJ032 · 美团 · 一面 · Q23]]）

   快照读与当前读混用造成的：事务先快照读看到 N 行（按首次 read view），别的事务插入并提交，随后本事务执行 `UPDATE`／`SELECT ... FOR UPDATE` 这类当前读，会看到新行并可能把它改掉，之后再次快照读因为 read view 未变仍“看不见”那行——表现为更新影响了看不到的数据。防的是当前读路径上的幻读（next-key lock），不是快照读的可见性规则。

2. **undo log 会不会把表撑大？**（补充练习）

   会。长事务或未及时提交的事务会一直持有 undo 与旧版本，导致 undo 表空间膨胀、版本链变长使快照读变慢，还会阻塞 vacuum／purge。生产要监控最长事务运行时间、避免在事务里做 RPC 或大批量循环，必要时把报表类长查询路由到从库并降低隔离级别。

3. **RC 与 RR 在复制上有什么不同风险？**（补充练习）

   官方口径是**READ COMMITTED 只支持基于行的二进制日志**（配 `binlog_format=MIXED` 时服务器自动改用 row-based），因为 RC 下同一事务的多次一致性读可能落在不同快照上，语句日志无法安全复制；RR 才可以用 STATEMENT／MIXED。这也是很多互联网场景选 RC ＋ ROW 组合的原因：间隙锁范围更小、锁冲突更少，代价是要自己处理不可重复读，且行格式 binlog 体积更大。

4. **原子性单独被问到时怎么展开？**（面经实际出现；[[面经/帆软/二面/0002#Q10：数据库是怎么保证事务的原子性的？|MJ035 · 帆软 · 二面 · Q10]]）

   只答 undo 一条链：改动前把旧值写 undo（WAL 顺序，先日志后页）→ 回滚按 undo 逆向撤销 → 崩溃恢复时对未提交事务回滚，等价“要么全做要么全不做”；补一句与 redo 的分工（redo 管已提交不丢，undo 管未提交可撤）与 purge 时机即可，不必把隔离性持久性也背进去。

### MYSQL-028：分组聚合后按聚合值过滤、以及取组内 Top1 的 SQL 怎么写？

**常见问法**

- 有订单表、订单明细表、商品表，统计每个商家销售额超过 10 万的商品。
- 查询每个商家销售额最高的商品。
- 组内最大值那一行怎么取，并列怎么办？

#### 面试回答

两句口径先问清：销售额按明细的 `单价×数量` 还是明细里的成交字段、要不要排除已退款或已取消的订单——口径没定就写 SQL，答案会被判定为没做过真实需求。

第一步是“多表连接＋按维度分组”，第二步按目标分两种写法。求“聚合值满足条件的分组”：条件作用在聚合结果上，必须写在 HAVING，不能写在 WHERE——`WHERE` 里不能出现 `SUM(...)`，而且语义是“先删行再分组”，会把该组其他行提前删掉。

```sql
SELECT o.merchant_id, oi.product_id, SUM(oi.price * oi.quantity) AS sales
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
WHERE o.status = 'PAID'
GROUP BY o.merchant_id, oi.product_id
HAVING SUM(oi.price * oi.quantity) > 100000;
```

分组键必须同时含商家与商品，否则同款商品跨商家会被合并；开启 `ONLY_FULL_GROUP_BY` 时 SELECT 里的非聚合列都得进 GROUP BY（或改用 `MAX(name)` 之类聚合）。

求“每组内最大那一行”不能简单 `GROUP BY merchant_id` 后取 `MAX(sales)`——那样其他列会落到不确定的行上。首选窗口函数：先在派生结果上按商家分组、销售额降序排名，再取 `rk = 1`。

```sql
WITH sales AS (
  SELECT o.merchant_id, oi.product_id, SUM(oi.price * oi.quantity) AS sales
  FROM orders o JOIN order_items oi ON oi.order_id = o.id
  WHERE o.status = 'PAID'
  GROUP BY o.merchant_id, oi.product_id
), ranked AS (
  SELECT merchant_id, product_id, sales,
         RANK() OVER (PARTITION BY merchant_id ORDER BY sales DESC) AS rk
  FROM sales
)
SELECT merchant_id, product_id, sales FROM ranked WHERE rk = 1;
```

要能解释排序函数的选择：`RANK()` 与 `DENSE_RANK()` 会保留并列（一个商家可能返回多行），`ROW_NUMBER()` 强制唯一，用它就必须给一个确定性的次级排序键（如 `product_id`），否则同一份数据两次跑结果可能不同。老版本 MySQL（5.7 及以前无窗口函数）走“自连接派生表”：先按商家聚合出 `MAX(sales)`，再与上一步的明细聚合结果按 `merchant_id AND sales` 连接，此时并列会一起出来，要唯一就得再加规则。

#### 技术细节

数据量大时的性能点是这题的真实考点：两层聚合都要扫全量明细，线上通常不允许每次实时算。做法是给“商家＋时间”维度的汇总表（按天预聚合到商家×商品），查询只扫汇总表；索引上要保证 `orders` 按 `(merchant_id, status)`、`order_items` 按 `order_id` 有支撑索引，避免连接时按主键之外做全表扫；窗口函数产生的排序是内存／临时表排序，数据规模大时要看执行计划里的 filesort 成本。

口径类陷阱点名：① 用 `LEFT JOIN` 还是 `INNER JOIN`——只有订单没有明细的商家、没有价格的明细行，聚合结果会不同；② `SUM` 遇到 NULL 会跳过，若某明细价格为 NULL，销售额会被低估，必要时 `SUM(COALESCE(price*quantity,0))`；③ 浮点金额（`DOUBLE`）累加有精度问题，金额应存 `DECIMAL`，否则“超过 10 万”的边界判定不可靠；④ 时间窗口未定义（“每个商家”是否限定最近 30 天）会让结果差一个量级，这属于必须现场澄清的口径而不是实现细节。

#### 深挖追问

1. **“每个商家总销售额超过 10 万，列出这些商家的所有商品”和原题有何区别？**（面经实际出现；[[面经/字节/二面/0002#Q05：给定订单表、订单明细表、商品表，编写 SQL 统计每个商家销售额超过 10 万的商品。|MJ042 · 字节 · 二面 · Q05]] 的延伸）

   两种口径：原题是先按“商家×商品”分组后过滤（阈值作用在商品级销售额上）；这句描述是先按商家分组筛出商家集合，再展开其商品，得用子查询或 CTE 两步，把 `HAVING SUM(...) > 100000` 作用在 `GROUP BY merchant_id` 上再回连。说清差别比写对一条 SQL 更能证明理解。

2. **并列第一到底该留几个？**（补充练习）

   业务语义决定：报表与榜单场景通常要 `ROW_NUMBER()` 定一个确定规则（并列按商品 ID 或上架时间），否则用户每次刷新看到不同结果；分析场景更关心“有几件并列”，用 `RANK()` 并保留行数。先把规则问出来再选函数。

3. **为什么 `WHERE status='PAID'` 不能写在 HAVING 里？**（补充练习）

   语义层面 HAVING 是“分组后对组做筛选”，`status` 是行级属性、与聚合无关；写在 HAVING 里要靠 `MAX(status)` 这类变通表达，既难读又可能因分组内值不同而出错。行级过滤尽量放 WHERE，让优化器能提前缩集合并命中索引。

### MYSQL-029：如何判断表结构是否符合 3NF，什么时候该反范式？

**常见问法**

- 上述表结构是否符合 3NF？
- 讲讲三大范式，第三范式的判据是什么？
- 冗余字段／快照字段算不算违反范式，为什么业务里还这么做？

#### 面试回答

定义说准是第一步。1NF 要求属性不可再分——不在一个字段里塞逗号分隔的多值；2NF 要求非主属性完全依赖候选键，联合主键下不能只依赖其中一部分（以 `(order_id, product_id)` 为主键的明细表里放 `product_name`，它只依赖 `product_id`，就违反 2NF）；3NF 要求非主属性不传递依赖候选键：A→B→C 时 C 不该留在依赖 A 的表里。一句判据：每个非主属性都“直接且完全”依赖主键、且彼此无关——所谓 the key, the whole key, and nothing but the key。

拿订单三表判：商家名、商品名不在订单表里，明细表按“这一单这一件”存 `price` 与 `quantity`，看着符合 3NF。但要能点出两处常见违规：订单表冗余 `merchant_name` 是传递依赖（订单→商家→商家名），违反 3NF；订单表存 `total_amount` 而它可由明细求和推出，属于可由其他非主属性导出的派生值，同样违反 3NF。

结论要落在权衡上，不要死守范式：范式的收益是消除冗余与更新异常（改商家名不用回写历史订单）、写路径简单；代价是读要多表 JOIN、聚合与分析类查询放大。真实业务会刻意反范式，两种典型理由：① 历史语义必须冻结——订单要保存成交时的单价与商品名快照，因为商品价会变、名字会改，用当前价反推历史订单金额是错的，这不是“没做好范式”，而是“这两个字段本来依赖的是‘这一单’而不是‘这个商品’”，把 `price` 放在明细表里其实完全合规；② 读侧性能——冗余统计列、汇总表、宽表给报表与搜索用，代价是必须有维护手段（同事务更新、binlog／CDC 同步＋对账），否则就变成不一致的隐患。收口给判断：先让写入语义正确（范式帮你把依赖关系表达清楚），再按读侧证据决定冗余，并且每处冗余都要能说出它由谁负责维护。

#### 技术细节

判断练习的可操作方法：列出候选键→写出每个非主属性的依赖→找三种味道——部分依赖（联合键里的一半）、传递依赖（A→B→C）、派生属性（能由同行其他列算出来）。派生属性严格说属于更细粒度的规范化讨论（有时归到 EFN／BCNF 的讨论范围），面试里说“可导出的字段是冗余”即可，重点是能说出它对更新的影响。

BCNF 与 3NF 的差别是常见延伸：BCNF 要求每个决定因素都是候选键（不允许“非主属性决定另一个非主属性”这类情况），比 3NF 更严格，某些表在 BCNF 下无法做到既无损分解又保持依赖，所以工程上普遍以 3NF 为界。反例要能举一个：`（学生, 课程）→ 讲师`、`讲师 → 课程`（每个讲师只教一门课）里，“讲师”决定“课程”但讲师不是候选键，这就是 BCNF 被违反的情形。

反范式的维护手段要能具体说：同事务内更新（简单但有锁范围与一致性窗口）、binlog／CDC 异步同步（解耦但要接受延迟并对账）、生成列或视图（数据库内表达式派生，避免应用层两处写）、汇总表加水位与定时校准（对账任务比对明细求和）。选哪种取决于“读侧能不能容忍旧值”。

#### 深挖追问

1. **那订单表里的 `total_amount` 到底该不该存？**（面经实际出现；[[面经/字节/二面/0002#Q06：上述表结构是否符合 3NF？|MJ042 · 字节 · 二面 · Q06]]）

   范式上是冗余（可由明细导出），工程上常常要存：结算、风控与列表页都需要它，实时求和代价高。取舍标准是“谁负责保证它与明细一致”——明细只在同一事务里变更就同步更新，否则要么加对账要么改成不落库的物化视图／汇总表，绝不能靠应用层两处各自写。

2. **只查商品名为什么会扯到范式？**（补充练习）

   因为“要不要把 `product_name` 复制到订单明细”正是范式与快照语义的冲突点：为了展示历史名必须复制（违反 3NF），为了改名字后统一生效就不能复制（符合 3NF）。先问业务“商品改名后历史订单要显示新名还是当时的名字”，答案决定表结构——这类问题答成“取决于业务”才是对的。

3. **怎么向面试官证明你的表设计合理？**（补充练习）

   给出依赖关系而不是结论：每个字段的决定因素是谁、哪些字段属于“快照”而非“引用”、查询走什么路径、有没有对账兜底；再说明如果流量或数据量变化，会先动哪一处（加索引还是加汇总表）。有这套因果链，范式之争就不容易被问倒。
