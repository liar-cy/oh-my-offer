### MYSQL-001：MySQL 事务有哪些隔离级别？

**常见问法**

- [[面经/美团/一面/0002#Q23：MySQL 事务特性逐个展开：原子性、隔离性、持久性、隔离机制、MVCC、间隙锁|MJ032 · 美团 · 一面 · Q23]]
- MySQL 的事务分为哪几种？

- 事务隔离级别有哪些，分别解决了什么问题？
- RR 级别如何解决幻读？

- MySQL 事务如何开启，ACID 和隔离级别是什么？

- MySQL 的事务是什么？有哪些特性？

#### 面试回答

如果这里问的是隔离级别，一共四档，从松到严：

- 读未提交：可能读到别人还没提交的值，也就是脏读。
- 读已提交：只读已提交的数据，一致性读通常每条语句建立一个新快照。
- 可重复读：InnoDB 默认级别，同一事务里重读通常复用首次建立的快照。
- 串行化：约束更强，并发代价也更高。

选哪一档本质是在并发能力和读一致性之间权衡；InnoDB 结合 MVCC（多版本并发控制）和锁来实现相应语义。顺带澄清：ACID 是事务的四个特性，不是四种事务。如果您指的是提交方式或分布式事务类型，我可以按那个维度回答。

#### 技术细节

**分类口径先说清**

- 原题“事务分几种”没有明确分类维度，本条按隔离级别整理并保留歧义。
- 下面依据 MySQL 8.4 InnoDB。
- 别把 Spring 的传播行为和数据库的隔离级别混在一起讲，这是两套东西。

**四类读异常先定义**

- 脏读：读到别人未提交的值。
- 不可重复读：重读同一记录，发现它已被别的事务提交修改。
- 幻读：同一查询条件重做，结果集合出现新增或消失的行。

**按标准的最低隔离保证理解**

- 读未提交：上面三类异常都可能出现。
- 读已提交：避免脏读；一致性读通常每次建立新快照。
- 可重复读：避免脏读和不可重复读；通常复用首次一致性读建立的快照；标准不要求它完全排除幻读。
- 串行化（Serializable）：再提供串行化约束，约束更强、并发代价更高。
- InnoDB 的具体实现比这张简表更细。

**RR 下“重读不变”和“防幻读”是两条路径**

- 快照读这条：普通一致性 SELECT 通常复用首次一致性读的 read view（一致性读视图），所以看不到后来提交的新行。
- 但这只是“我看不见”，不是阻止别人插入。
- 当前读这条：SELECT ... FOR UPDATE 等范围锁定读不是快照读，会根据执行计划采用 next-key／gap 等锁限制相关间隙插入，用这类锁控制范围并发。
- 边界：完整唯一键命中等场景可缩小为记录锁，不能说 RR 的每次 SELECT 都加间隙锁。
- 所以不能简单声称 MVCC 解决所有形式的幻读。
- 混用快照读与当前读、或事务自己进行写入，会改变可见结果；实际范围控制还要结合索引。具体锁分类见 [[#MYSQL-005：MySQL 中有哪些锁，如何分类？|InnoDB 锁]]。

**事务怎么开启和结束**

- 以 MySQL 8.4 InnoDB 为例：START TRANSACTION 开启，COMMIT 提交，ROLLBACK 回滚。
- autocommit 默认开启时，单条适用语句可独立提交。
- SET autocommit=0 影响会话，需要每轮显式结束事务；许多 DDL 会隐式提交。
- 存储程序中的 BEGIN 还可能是复合语句块，不与事务开启混同。

**一致性这个词别用偏**

- ACID 的一致性是满足约束，不是所有副本任何时刻一致。
- 业务不变量仍需正确 SQL 与约束实现。

#### 深挖追问

1. **ACID 分别是什么？**（补充练习）

   原子性、一致性、隔离性、持久性；它们描述事务性质，而非互斥的四种类别。

2. **RR 下两次查询一定相同吗？**（补充练习）

   不能无条件保证；需看快照读还是锁定读、事务自身是否写入等条件。普通一致性读与当前读不要混用同一解释。

3. **RR 级别如何处理幻读？**（面经实际出现；[[面经/北京某上市公司/一面/0001#Q13：事务隔离级别分别解决什么问题，InnoDB RR 如何处理幻读？|MJ004 一面 Q13]]）

   两条路径分开说，语义不同：

   - 快照读：通过一致性视图保持结果稳定。
   - 范围锁定读：通过适用的 next-key／gap 锁阻止相关插入。

   所以不能简单说“所有幻读都被 MVCC 消灭”。

4. **如何开启事务并解释 ACID？**（面经实际出现；[[面经/百度/一面/0005#Q14：MySQL 事务如何开启，ACID 和隔离级别是什么？|MJ008 · 百度 · 一面 · Q14]]）

   分两段说。

   开启事务：以 InnoDB 为前提，可用 START TRANSACTION 或普通 SQL 中的 BEGIN 开始，COMMIT 提交、ROLLBACK 回滚；也可设置 autocommit=0，但要理解这是会话持续事务语义。

   ACID 四个特性：
   - 原子性：一组修改整体完成或回滚。
   - 一致性：维护业务约束。
   - 隔离性：控制并发可见性。
   - 持久性：保证提交后的修改持久。

   隔离级别为读未提交、读已提交、可重复读和串行化，InnoDB 默认可重复读。最后补两句边界：具体读语义还要区分快照读和锁定读；持久性承诺取决于日志刷盘等配置。

5. **读已提交是怎么避免脏读的？RC 和可重复读的核心差异是什么？**（面经实际出现；[[面经/帆软/二面/0002#Q11：MySQL 的读已提交怎么避免脏读，RC 和 RR 的核心差异是什么？|MJ035 · 帆软 · 二面 · Q11]]）

   先纠正一个常见误区：RC 避免脏读不靠加读锁，靠 MVCC 的可见性判断。快照读沿版本链跳过未提交版本，只取对本语句可见的最近已提交版本，所以未提交数据永远读不到。

   RC 与 RR 的核心差异在 ReadView（一致性读视图）的生成时机：

   - RC：每条语句新建一份，因此能看到期间别人提交的修改，也允许不可重复读。
   - RR：事务首次一致性读时建一份并复用，所以重读结果稳定。

   还有一点：RR 在当前读路径上用间隙锁／next-key lock 抑制幻读，代价是锁冲突更高；RC 另有基于行格式 binlog 的限制。

### MYSQL-002：如何查询所有已记录科目成绩都大于 80 的人员？

**常见问法**

- 表有姓名、科目、分数字段，查询分数都大于 80 分的人员名单。

#### 面试回答

我会按人员分组，在 HAVING 里限制最小成绩大于 80：

- 核心一句：`GROUP BY 人员 HAVING MIN(score) > 80`，最小值都过线，说明每一科都过线。
- 如果 NULL 也算不合格，再加一个条件 `COUNT(score) = COUNT(*)`，把有缺考记录的组排掉。
- 口径说明：题目只给了姓名字段，所以暂按姓名标识人员；真实表应该用 student_id，避免同名被合并。
- 还得说清这条查询的边界：它只检查已记录的成绩，不能证明没有缺考科目。

#### 技术细节

设表为 scores(name, subject, score)，NULL 视为不合格：

```sql
SELECT name
FROM scores
GROUP BY name
HAVING MIN(score) > 80
   AND COUNT(score) = COUNT(*);
```

**为什么不能用 WHERE 过滤**

- `WHERE score > 80` 会先删掉低分行，剩下的人当然都大于 80，有不合格科目的人被误选出来。
- HAVING 是聚合之后再判断整组，这才是“所有科目都大于 80”的语义。

**为什么还要加一个计数条件**

- MIN 会忽略 NULL：只要有一条有效成绩过线，含 NULL 的组也可能被选中。
- 所以用 `COUNT(score) = COUNT(*)` 判断“有效成绩条数等于总条数”，把含 NULL 的组排除掉。

**题目口径没覆盖到的两种扩展**

- 如果要求所有必修科目都有成绩：还要连接应修科目清单，按科目去重并判断是否缺项。
- 如果一个人有多次考试记录：先明确取最新、取最高，还是每次都要达标，再决定聚合方式。

#### 深挖追问

1. **只有姓名能准确区分人员吗？**（补充练习）

   不能处理同名，生产查询应按唯一人员 ID 分组，再取姓名展示。

2. **80 分算满足吗？**（补充练习）

   不满足，原题是严格大于 80；等于 80 的人员应排除。

### MYSQL-003：MySQL 有哪些日志，redo log 和 binlog 如何保持一致？

**常见问法**

- redo log、undo log 和 binlog 分别有什么作用？
- MySQL 日志有哪些？
- 为什么 redo log 和 binlog 要有两个？
- redo log 和 binlog 不一致怎么解决？

- MySQL 事务的原子性底层如何实现？

#### 面试回答

日志分两组说：

- 服务层：错误日志、慢查询日志、通用查询日志，以及 binlog（二进制日志）。
- InnoDB 引擎层：还有 redo log（重做日志）、undo log（回滚日志）等。

redo 管崩溃恢复，binlog 管复制和基于备份的时间点恢复，两个职责不能互相替代。启用 binlog 时，InnoDB 的提交靠内部两阶段提交协调：redo 先 prepare、再写 binlog、最后完成引擎提交。崩溃恢复时，根据日志里记录的事务状态决定是提交还是回滚。

#### 技术细节

**三类日志各管什么**

- redo log：记录引擎层恢复所需的修改，空间是循环复用的。
- binlog：记录服务层的变更事件，支持行或语句等格式，按文件保留。
- undo log：服务于回滚和历史版本读取，它不是 binlog 的替代品。

**两阶段提交怎么对齐两份日志**

- 概念上，已经 prepare 但还没完成提交的事务，可以根据有没有有效的 binlog 事务记录来做恢复决策。
- 实际实现里还存在组提交与刷盘阶段，不是只有“prepare—写 binlog—提交”这三步裸跑。

**持久性靠哪两个参数**

- 强持久性常结合 `innodb_flush_log_at_trx_commit=1` 和 `sync_binlog=1`。
- 即使这样，仍然依赖存储设备正确兑现同步写。

**真的出现数据分歧时**

- 已经发生介质损坏，或历史配置导致数据分歧时，要去查日志、备份和复制状态来恢复。
- 不能简单地“补一个 commit”或者删日志把问题盖过去。

#### 深挖追问

1. **为什么要两个日志？**（面经实际出现；[[面经/百度/一面/0001#Q04：MySQL 有哪些日志，为什么同时需要 redo log 和 binlog，如何保持一致？|MJ002 Q04]]）

   一个服务于存储引擎的物理恢复，一个服务于逻辑变更复制与恢复，数据格式和保留方式不同。

2. **只有 prepare、binlog 没有完整事务记录怎么办？**（面经实际出现；[[面经/百度/一面/0001#Q04：MySQL 有哪些日志，为什么同时需要 redo log 和 binlog，如何保持一致？|MJ002 Q04]]）

   按崩溃恢复协议判断为未完成提交并回滚；不能只凭 prepare 将其视为成功。

3. **事务的原子性底层如何实现？**（面经实际出现；[[面经/百度/一面/0008#Q02：MySQL 的原子性底层如何实现？|MJ019 · 百度 · 一面 · Q02]]）

   靠 undo log（回滚日志）。

   - 修改前先记录撤销信息，回滚时沿 undo 链逆向恢复旧版本。
   - 提交后 undo 延迟清理，是为了继续给 MVCC 读历史版本用。
   - 分工别记混：原子性靠 undo，持久性靠 redo＋WAL（先写日志再改数据）。崩溃恢复时，未提交的事务用 undo 回滚，已提交但还没落盘的用 redo 重放。

### MYSQL-004：InnoDB 索引为什么用 B+ 树，而不是 B 树或哈希表？

**常见问法**

- [[面经/美团/一面/0002#Q11：MySQL 索引的数据结构是 B+ 树，能介绍一下 B+ 树吗？|MJ032 · 美团 · 一面 · Q11]]
- MySQL 索引用什么数据结构，为什么不用 B 树和 HashMap？

- MySQL 索引底层是怎么实现的？
- 索引是什么，有哪些结构和分类？
- 聚簇索引和非聚簇索引是什么？

- 表到千万级查询很慢是什么原因，回表是什么？

#### 面试回答

InnoDB 常用的索引用 B+ 树，我会分三层讲：

- 结构特点：非叶节点主要保存导航信息，扇出大、树高低；叶子层有序连接。
- 由此带来的好处：适合磁盘分页访问，也适合范围扫描。
- 对比 B 树：B 树也能做索引，但内部节点存数据会影响扇出。
- 对比哈希：哈希擅长等值查找，不适合有序遍历和范围查询。

最后补一句严谨的话：不能把 Java 的 HashMap 直接等同于数据库索引。

#### 技术细节

**非叶节点怎么把人引到叶子**

- 导航项只有「键值＋子页指针」：每个子页指针管一段键区间，且区间互不重叠、按序排列。
- 查找过程：在节点内对键做二分，找到「最大的 ≤ 搜索值」的键，沿它的子页指针下降；一层层到叶子后，再在叶子页内定位记录。
- 找得到的原因：树满足 BST 式区间不变式，比较结果唯一确定走哪条分支，不需要试探。
- 扇出为什么大：非叶不存行数据，一个 16KB 页能放上千个导航项；树矮＝磁盘 IO 次数少（三层约两千万行，见 [[#MYSQL-026：三层 B+ 树能存多少数据，怎么估算？|MYSQL-026：三层 B+ 树能存多少数据，怎么估算？]]）。

**B+ 树相对 B 树的得与失**

- 得 1：非叶不存数据 → 扇出更大、树更矮、IO 更少。
- 得 2：叶子双向链表串联 → 范围查询定位起点后顺链扫描，不用回父节点做中序。
- 得 3：所有查询都走到叶子 → 路径等长、延迟稳定。
- 失：热键不会像 B 树那样「命中内部节点提前返回」，任何查找固定走满树高。
- 讲对比时给全这三得一失，别说成 B+ 树全面碾压 B 树。

**聚簇索引和二级索引的区别**

- 聚簇索引的叶子保存整行。
- 二级索引的叶子保存索引列及主键值；缺所需字段时就要回表。
- 覆盖索引可以减少回表。
- 联合索引的键顺序，决定能利用多长的前缀以及能不能直接取到有序性做排序。

**B+ 树优势的使用边界**

- 优势基于页布局、缓存局部性与范围访问，不是“任何时候都比哈希快”。
- MySQL 不同引擎和索引类型并非都用同一种结构。
- 本题限定常见的 InnoDB B-tree 索引，不将全文索引、空间索引混为一谈。

#### 深挖追问

1. **为什么主键不宜太长？**（补充练习）

   二级索引包含主键，主键过长会增加索引体积与缓存压力。

2. **B 树完全不能做范围查询吗？**（补充练习）

   可以，区别在于遍历和页布局代价；不能把“不擅长”误说成“不支持”。

3. **回表是什么，回表多为什么会慢？**（面经实际出现；[[面经/帆软/一面/0002#Q10：表到千万级查询很慢是什么原因，回表是什么？|MJ027 · 帆软 · 一面 · Q10]]）

   回表就是“拿着主键再查一次聚簇索引”。

   - 为什么会有这一跳：二级索引叶子只存索引列＋主键值，需要其他列时，要按主键再查一次聚簇索引取整行。
   - 为什么多了会慢：命中行数一多，这一跳就变成大量按主键的随机 I/O。
   - 两条缓解思路：覆盖索引让所需列都在索引里，直接免回表；延迟关联先只查本页的主键再回表，把回表次数压到页大小（见 [[#MYSQL-010：什么是覆盖索引，如何设计索引？|MYSQL-010：什么是覆盖索引，如何设计索引？]]、[[#MYSQL-019：大分页查询怎么优化？|MYSQL-019：大分页查询怎么优化？]]）。

4. **B+ 树怎么通过非叶子节点找到对应的叶子？和 B 树的区别？**（面经实际出现；[[面经/点点互动/一面/0001#Q20：MySQL 索引的底层实现是什么？B+ 树如何找到叶子节点，和 B 树有什么区别？|MJ064 · 点点互动 · 一面 · Q20]]。原素材未记回答，以下为参考）

   - 每个非叶项是「键值＋子页指针」，子页管的键区间互不重叠；节点内二分找到「最大的 ≤ 目标值」的项，沿指针下降，直到叶子再定位记录。
   - 对 B 树：非叶也存数据 → 扇出小、树更高；叶子无链表 → 范围查询靠中序回溯。
   - B+ 树换取的是矮树＋顺链范围扫描＋等长路径；代价是内部节点永远不命中、必到叶子——这面「旗」主动举出来比背结论加分。

### MYSQL-005：MySQL 中有哪些锁，如何分类？

**常见问法**

- MySQL 中有哪几种锁？

- 介绍一下常见的锁，乐观锁和悲观锁是什么？

- MySQL 的间隙锁是解决什么问题的？原理是怎样的？

#### 面试回答

回答这题要先说清分类维度，不然容易讲成一锅粥：

- 按层级看：MySQL 有全局读锁、表锁和元数据锁（MDL）等。
- InnoDB 的行级并发控制：包含共享／排他记录锁，以及 gap、next-key、插入意向等机制，另外还有表级意向锁。
- 两套维度不要混着说：共享／排他描述的是锁之间的兼容模式，记录／间隙描述的是锁定的范围，不能把它们当成同一层的互斥分类。

#### 技术细节

**同一个库存行上锁怎么互相作用**

- UPDATE 会自动申请排他锁。
- 兼容性：不同事务对同一记录的共享锁可以共存；排他锁和共享锁、排他锁都冲突。
- 锁一般持有到事务结束，具体范围由访问路径和隔离级别决定。

**读操作加不加锁**

- 普通一致性 SELECT 通常不加记录锁。
- FOR SHARE 与 FOR UPDATE 才分别是共享、排他的锁定读。

**锁竞争的表现与死锁的界线**

- 十个事务争同一行，表现为锁等待、吞吐受限或等待超时。
- 只有出现循环等待才构成死锁，不是线程数多就必然死锁。

**有锁不等于写法就对**

- 两个事务都用普通 SELECT 读到库存 10，再各自 UPDATE SET stock = 9，后一次会把前一次的业务效果覆盖掉。
- 两种正确写法：用 `stock = stock - quantity AND stock >= quantity` 做条件扣减；或者在同一事务里先 SELECT ... FOR UPDATE 再计算更新。
- 更进一步的优化方案见 [[#MYSQL-007：如何优化秒杀库存更新与热点行锁竞争？|热点库存优化]]。

**InnoDB 各类锁的适用范围（以 MySQL 8.4 为主）**

- 记录锁：锁住索引记录。
- gap 锁：约束间隙里的插入。
- next-key 锁：记录锁与前边间隙的组合。
- IS/IX 表级意向锁：表示后续要在记录上加锁的意图。
- 完整唯一索引等值命中这类场景常可缩小为记录锁；范围查询和未命中的情况要结合执行计划、隔离级别判断。
- 普通一致性 SELECT 通常依靠 MVCC（多版本并发控制）而不加记录锁，但仍可能持有 MDL；FOR UPDATE 则是锁定读。
- 没有合适索引时可能扩大扫描和锁的范围，但不应描述成必然发生“锁升级”。
- AUTO-INC 锁的模式和自增列的分配方式有关。

#### 深挖追问

1. **间隙锁会锁住已经存在的记录吗？**（补充练习）

   纯 gap 锁针对间隙插入，记录本身由记录锁控制；next-key 同时含两部分。

2. **为什么 SELECT 会阻塞 DDL？**（补充练习）

   事务可能持有表的元数据锁，DDL 需要不兼容的 MDL，这与是否有行锁不同。

3. **读写锁是否一致，悲观行锁竞争有什么表现？**（面经实际出现；[[面经/百度/一面/0002#Q12：多个线程修改同一行库存时如何加锁，读写锁及竞争表现有何不同？|MJ005 · 百度 · 一面 · Q12]]）

   先把读写锁的对比落到 MySQL 上：这里要区分快照读和锁定读。

   - S 锁（共享锁）可以多个事务同时持有，X 锁（排他锁）互斥；冲突的事务要等持锁者结束。
   - 单行排队不是死锁；多个资源之间出现循环等待才需要死锁检测和事务重试。

4. **间隙锁到底是解决什么问题的？原理讲一下。**（面经实际出现；[[面经/虾皮/一面/0002#Q17：MySQL 的间隙锁是解决什么问题的？原理是怎样的？|MJ048 · 虾皮 · 一面 · Q17]]）

   问题：RR 隔离级别下，只锁“已存在的行”挡不住别人往查询范围的空隙里 INSERT——两次范围当前读之间冒出新行，就是幻影行。gap 锁把“索引记录之间的开区间”也锁住，专门拦插入。

   原理三件套：

   - 锁定单位：record lock 锁记录、gap lock 锁相邻键值之间的间隙（彼此兼容，都是“占坑防插”）、next-key lock＝记录锁＋前面间隙，是 RR 当前读的默认粒度。
   - 拦截机制：INSERT 前要先拿插入意图锁（insert intention），与落在目标间隙上的 gap 锁冲突就排队——所以是“读方锁间隙、写方在间隙门口等”。
   - 例：`SELECT ... WHERE id BETWEEN 10 AND 20 FOR UPDATE` 锁住范围内记录及 (0,10)、(20,+) 相邻间隙，他人插 id=15 或 20 附近被挡。

   代价口径：锁范围放大→并发插入冲突与死锁概率上升（经典死锁形态：两事务各持不相邻 gap 锁，再互插对方间隙）；因此不少团队用 RC＋row binlog 放弃间隙锁，幻读防线移到业务条件更新。

### MYSQL-006：MySQL 索引有哪些类型？

**常见问法**

- MySQL 索引有哪些类型？

- 索引是什么，有哪些结构和分类？

#### 面试回答

这题我会先声明“按维度分”，因为这些名称是交叉的：

- 按约束：主键索引、唯一索引、普通索引。
- 按列组合：单列索引、联合索引。
- 按 InnoDB 的存储组织：聚簇索引与二级索引。
- 按用途：还有全文索引、空间索引等。

一个“联合唯一二级索引”同时属于多个维度，所以不能把这些名称当成互斥类别。结构选型那部分可以继续讲 B+ 树。

#### 技术细节

**先说清索引是什么**

- 索引是为查询提供定位路径的数据结构，用空间和写入的维护成本，换部分查询的访问效率。
- 未命中合适的访问条件、或者选择率较差时，优化器可能仍然选全表扫描。
- 所以口述时先讲用途，再从约束、列组合、存储组织等维度分类。

**各个维度上的细节与边界**

- 主键要求唯一且非 NULL。
- MySQL 的唯一索引通常允许多个 NULL，这要和业务上的唯一规则区分开。
- InnoDB 聚簇索引的叶子保存行数据，二级索引里包含主键。
- 联合键按定义的列序组织，最左前缀影响能用上的检索范围。
- 覆盖索引是“某次查询所需列都能由索引提供”这个访问条件，不是一个独立的 CREATE INDEX 类型。
- 前缀索引、函数索引、降序索引和不可见索引属于额外的定义或优化选项，支持情况要看版本与引擎。
- 成本别忘了：索引会增加写入和存储开销。

**底层原因**

参见 [[#MYSQL-004：InnoDB 索引为什么用 B+ 树，而不是 B 树或哈希表？|B+ 树与聚簇／二级索引]]。

#### 深挖追问

1. **联合索引 (a,b) 可以只按 b 高效定位吗？**（补充练习）

   通常不能像按最左前缀那样直接定位，优化器可能采用其他访问方式，需看执行计划。

2. **建很多索引是不是更快？**（补充练习）

   只可能改善部分读路径，同时增加写维护和空间开销，应依据查询模式选。

3. **索引是什么？**（面经实际出现；[[面经/百度/一面/0005#Q15：索引是什么，有哪些结构和分类？|MJ008 · 百度 · 一面 · Q15]]）

   帮助定位记录和减少扫描的访问结构，但会占空间并增加更新成本，不保证每次查询都使用。

### MYSQL-007：如何优化秒杀库存更新与热点行锁竞争？

**常见问法**

- MySQL 如何优化高并发库存扣减及热点单行锁排队？

#### 面试回答

先给数据库这一层的标准动作：

- 用主键或合适的唯一索引定位库存。
- 执行带 `stock >= quantity` 条件的原地扣减，做完检查影响行数。
- 事务缩短到必要的扣减与记录写入。
- 用唯一业务键防重复领取，再配上锁等待、慢 SQL 的监控，并控制消费并发与连接池。

再说为什么不能硬堆并发：单行写入本身要串行，继续加线程突破不了这条瓶颈。真要提量只有两条路——按活动、库存桶分配互不重叠的额度；或者按同一库存键排队、谨慎地合并扣减。

别踩的坑：读写分离和增加普通索引，都不能直接解决同一行的写锁竞争。

#### 技术细节

示例基于 MySQL 8.4 InnoDB，假设 quantity 是已校验的正整数：

```sql
UPDATE coupon_stock
SET stock = stock - :quantity
WHERE id = :batch_id AND stock >= :quantity;
```

**这条 SQL 的读法**

- 这是绑定参数示意，实际 JDBC 可以使用问号占位符。
- 影响行数为 1，才代表本次条件扣减成功。
- 发券记录写失败时，要把同一事务回滚掉。

**减少锁竞争和写成本的常规手段**

- 减少无关的二级索引、避免长事务，都能降低写入成本。
- 多行更新采用固定顺序，撞死锁后重试整个事务。

**分桶和乐观版本号的前提条件**

- 库存分桶必须满足：各桶额度总和不超过总量；热点桶不够时，需要有约束的调拨机制。
- 乐观版本号在高冲突下可能造成大量重试。

**批量扣减的边界**

- 批量确实能减少往返，但必须保留每个请求的分配结果、幂等和失败处理。
- 不能把整个批次只记成一个计数。

#### 深挖追问

1. **频繁单行更新导致锁排队如何优化？**（面经实际出现；[[面经/百度/一面/0002#Q10：MySQL 如何优化高并发库存扣减及热点单行锁排队？|MJ005 · 百度 · 一面 · Q10]]）

### MYSQL-008：JDBC 连接池核心参数如何配置和调优？

**常见问法**

- JDBC 连接池常用核心参数有哪些？

#### 面试回答

第一句话先摆前提：JDBC 规范里没有统一的池参数名，所以要先确认用的是哪个连接池。

以 HikariCP 为例，核心参数是这几个：

- 容量与空闲：maximumPoolSize、minimumIdle。
- 超时：connectionTimeout、idleTimeout、maxLifetime，另有 validationTimeout、keepaliveTime。
- 事务相关：还要检查 autoCommit 和 transactionIsolation。

池大小怎么定：取决于数据库能承受的并发、每条连接被持有的时间，以及应用实例的数量。这里有个容易说错的点——连接获取超时不是 SQL 执行超时。

调优看指标：活跃连接、等待连接、事务耗时和数据库负载。别把“连接数越大”理解成性能越好。

#### 技术细节

以下对应查证时 HikariCP 官方 README；原项目连接池及版本未知，不给通用默认数值。

| 参数 | 含义与约束 |
| --- | --- |
| maximumPoolSize | 最大总连接数，包含空闲和使用中的连接；各实例池上限之和要考虑数据库连接预算。 |
| minimumIdle | 尽力维持的最小空闲连接数，影响突发流量时的建连。 |
| connectionTimeout | 等待池中可用连接的时间，不是查询执行上限。 |
| idleTimeout | 空闲回收时间，在 minimumIdle 小于 maximumPoolSize 时起作用。 |
| maxLifetime | 连接最大寿命；使用中的连接在归还后退役，应短于外部连接寿命限制。 |
| validationTimeout | 存活检测超时，应小于 connectionTimeout。 |
| keepaliveTime | 对空闲连接探活，需小于 maxLifetime。 |
| autoCommit、transactionIsolation | 控制默认事务行为，要与框架事务管理匹配。 |
| leakDetectionThreshold | 超时未归还连接时输出诊断信息，不等于自动终止业务。 |

**三个容易混淆的超时**

- 查询超时、驱动 socket 超时、池获取超时是三层，要分别设置。

**池大小怎么估**

- 初步估计：平均并发需求 ≈ 吞吐量 × 连接持有时间。
- 再用压测确定实际边界。

**一条常见的误用**

- 不要把外部 RPC 调用放进长时间持有数据库连接的事务里。

### MYSQL-009：MySQL 的 InnoDB 和 MyISAM 有什么区别？

**常见问法**

- MySQL 的 InnoDB 和 MyISAM 有什么区别？

#### 面试回答

以 MySQL 8.4 为例，差别集中在三块：

- 事务与恢复：InnoDB 支持事务、MVCC、行级锁和外键，并用 redo 等实现崩溃恢复，适合常见并发事务业务；MyISAM 不支持事务与外键，也没有 InnoDB 那样的事务崩溃恢复能力。
- 锁粒度：MyISAM 主要使用表级锁。
- 存储组织：InnoDB 按聚簇索引组织行，二级索引包含主键；MyISAM 索引和数据分离，由索引定位数据记录。

#### 技术细节

**几个容易说过头的地方**

- InnoDB 有行级锁，不代表没有表级意向锁、元数据锁等，也不代表所有读都加行锁。
- MyISAM 可以做表检查与修复，但这不能等同于事务的原子恢复。
- 行数统计：MyISAM 可快速取得无 WHERE 的精确整表行数；InnoDB 要考虑事务可见性，不能维护一个适用于所有事务的单一精确计数。
- 不能笼统说 MyISAM 读一定更快，也不能说 InnoDB 不支持全文索引。

**选型口径**

- 依据事务、并发、可靠性和查询模式来选。

#### 深挖追问

1. **为什么事务业务通常选 InnoDB？**（补充练习）

   它提供提交回滚、并发隔离和崩溃恢复等关键语义；MyISAM 的表级锁与非事务模型不适合直接承担同等要求。

### MYSQL-010：什么是覆盖索引，如何设计索引？

**常见问法**

- 什么是覆盖索引，如何设计索引？
- 主键等值查询时，`select *` 和 `select id` 效率一样吗？为什么？

- MySQL 的覆盖索引、前缀索引、索引下推分别是什么？

#### 面试回答

覆盖索引的定义要先说准：某条查询所需的列，都可以由一个索引提供，通常就能减少回表。

- 它是查询和索引之间的关系，不是一个独立的索引类型。

设计索引我会按四步走：

- 先看高频 SQL：过滤、连接、排序、返回列分别是哪些。
- 再定联合索引的列序，考虑最左前缀。
- 然后结合选择性、写入成本评估。
- 最后用执行计划验证。不能给每个字段都建索引。

#### 技术细节

**一个具体例子**

- 以 MySQL 8.4 InnoDB 为例，查询 `WHERE tenant_id=? AND status=? ORDER BY created_at LIMIT 20`，可以评估 `(tenant_id, status, created_at)`。
- 如果只返回这些列和主键 id，而二级索引本身已带主键，就可能形成覆盖。

**列序怎么排**

- 常见起点是：等值条件在前，后面接范围或排序列。
- 但范围边界之后的列能不能用于定位、过滤或排序，要分别分析，不能一概而论。
- 也别机械地按区分度从高到低排，还要兼顾能被其他查询复用的前缀。

**在 EXPLAIN 里怎么认**

- `Using index` 常表示覆盖。
- `Using index condition` 是索引条件下推，两者不能混同。
- 即使覆盖，实际仍可能为了 MVCC 可见性去访问聚簇记录。

**成本侧**

- 避免过宽与冗余索引。
- 用代表性数据检验读收益和写成本。

#### 深挖追问

1. **覆盖索引是不是一定完全不访问聚簇记录？**（补充练习）

   从所需列看不必回表取额外字段，但 InnoDB 的事务可见性检查等仍可能访问聚簇记录；口述时说“通常减少回表”，不作绝对保证。

### MYSQL-011：MySQL 服务层与存储引擎架构是什么？

**常见问法**

- MySQL 服务层与存储引擎架构是什么？

#### 面试回答

以 MySQL 8.4 为例，从外到里三层：

- 客户端连接与认证层。
- SQL 服务层：负责解析、优化和执行协调。
- 存储引擎层：负责具体的数据和索引访问；InnoDB 在这之上还提供事务、锁、MVCC、缓冲池和崩溃恢复。

一次查询的走法是：执行计划决定怎么访问，再调引擎接口取行、返回结果。

两个边界要说清：不能把 MySQL 服务层和 InnoDB 当成同一个模块；也不要在现代 8.x 的查询流程里再提 Query Cache，它已经被移除了。

#### 技术细节

**一次 SELECT 的完整链路**

- 第一步，连接认证。
- 第二步，解析与语义检查。
- 第三步，优化访问路径和连接顺序。
- 第四步，执行器调用存储引擎接口。
- 第五步，引擎经缓冲池或磁盘访问记录。
- 第六步，返回结果。

**分工带来的两个结论**

- 服务层和引擎是分开的，所以同一库里不同表可以用不同引擎。
- 归属要分清：binlog 属于服务层；InnoDB 的 redo、undo 和数据页服务于它自己的事务机制。

**两条常见误答**

- 优化器给出的计划不保证总是最佳，要结合 EXPLAIN 和实际数据看。
- MySQL 8.x 已移除 Query Cache，但缓冲池仍然存在，两者不是同一个缓存。

#### 深挖追问

1. **存储引擎只负责读写磁盘吗？**（补充练习）

   不只。InnoDB 同时维护缓冲池、索引、锁和事务恢复等，服务层通过接口协调访问。

### MYSQL-012：MySQL 如何存储、查询和索引 JSON？

**常见问法**

- MySQL 如何存储、查询和索引 JSON？

#### 面试回答

存和取分开说：

- 存：MySQL 8.4 可以用原生 JSON 列，写入时会检查文档是否合法，内部用适合按成员访问的二进制表示。也可以用 TEXT 存原始文本，但它不会自动给你 JSON 的类型校验和访问优化。
- 取：读路径用 JSON_EXTRACT 或箭头操作符，改字段用 JSON_SET。
- 要按字段检索：把标量抽到生成列（由表达式派生的列），再在生成列上建索引。
- 选型判断：需要频繁关联、加约束、排序的稳定字段，通常还是拆成独立的关系列更合适。

#### 技术细节

以 MySQL 8.4 为例：

```sql
CREATE TABLE event_demo (id BIGINT PRIMARY KEY, payload JSON);
INSERT INTO event_demo VALUES (1, JSON_OBJECT('city', 'Shanghai'));
SELECT payload->>'$.city' FROM event_demo WHERE id = 1;
UPDATE event_demo SET payload = JSON_SET(payload, '$.city', 'Beijing') WHERE id = 1;
```

**语法与两个易错点**

- 箭头双大于号（`->>`）可以拿到去掉引号后的值。
- 原生 JSON 不等于“任意文本保真容器”：如果必须保留原始格式，要另外存一份原文。
- SQL NULL 和 JSON null 也是两回事。

**索引怎么建**

- JSON 列不能像普通标量列那样，给整个文档建一个常规索引。
- 可行做法：在提取标量的生成列上建索引。
- 数组另有多值索引机制，适用约束需要按版本查证。

#### 深挖追问

1. **JSON 格式文本放进 TEXT 和 JSON 列一样吗？**（补充练习）

   不一样，JSON 列有类型校验、内部表示与专用函数语义；TEXT 主要保存文本。

### MYSQL-013：CHAR 和 VARCHAR 的长度与尾空格语义有何区别？

**常见问法**

- CHAR 和 VARCHAR 的长度与尾空格语义有何区别？

#### 面试回答

先把长度单位说准：

- CHAR(M) 表示固定 M 个字符，VARCHAR(M) 表示最长 M 个字符的变长字符串；这个 M 是字符数，不是固定字节数。
- 实际存储还受字符集和行格式影响。
- 尾空格语义不同：CHAR 有补齐、读取时处理尾空格的规则；VARCHAR 保存实际内容并额外记录长度，通常保留尾空格。
- 选型：长度稳定的值可以考虑 CHAR，长度变化大的文本考虑 VARCHAR。
- 补一句：比较时尾空格有没有意义，还取决于排序规则；所以不能说固定长度就一定更快。

#### 技术细节

**长度上限**

- 以 MySQL 8.4 为基线：CHAR 的上限是 255 个字符。
- VARCHAR 的有效上限还要受整行大小和字符集制约。

**长度前缀**

- VARCHAR 用 1 或 2 字节记录长度，取决于最大可能的字节长度。
- 判断这一点不能只看字符数是否超过 255。

**两个容易混的“尾空格”**

- CHAR 读取时的尾空格处理，和字符串比较时的尾空格语义，是两件事。
- 后一件依赖排序规则的 PAD SPACE／NO PAD 属性。

**字节占用**

- 物理字节占用还受引擎和行格式影响，不能把 CHAR(M) 一概称为占 M 字节。

#### 深挖追问

1. **VARCHAR(100) 最多就是 100 字节吗？**（补充练习）

   不是，定义长度按字符；多字节字符集可能需要更多字节，并有长度元数据。

### MYSQL-014：InnoDB 的 MVCC 如何工作？

**常见问法**

- 数据库中的 MVCC 是什么？

- 讲一下 MySQL 的 MVCC 机制的实现原理。

#### 面试回答

MVCC（多版本并发控制）解决的是“读别挡住写、写别挡住读”：一致性读按可见性规则去读行的某个合适版本，减少读写互相阻塞。

以 MySQL 8.4 InnoDB 为例，实现三件套：

- 每行记录关联事务 ID 和回滚指针。
- 顺着回滚指针走 undo 链，就能拿到旧版本。
- 再用 Read View（一致性读视图）判断哪个版本对我可见。

要说清的边界：锁定读和写操作仍然要使用锁。

#### 技术细节

**快照什么时候建（这是 RC 和 RR 的差别）**

- 读已提交：通常每次一致性读都建立新快照。
- 可重复读：通常复用首次一致性读建立的快照。
- 事务自己写入的数据有特殊可见性规则。

**旧版本什么时候能清**

- 只有不再被任何活跃读视图需要时，旧版本才能清理。
- 所以长事务会延迟清理。

**两个不能说过头的地方**

- MVCC 不能概括成“所有读都不加锁”。
- 它也不能代替唯一约束和并发写控制。

#### 深挖追问

1. **可重复读是否在 BEGIN 时必然建立快照？**（补充练习）

   通常在首次一致性读时建立；显式一致性快照等语法另有语义，需按事务启动方式说明。

### MYSQL-015：如何排查和优化慢 SQL？

**常见问法**

- [[面经/美团/一面/0002#Q25：慢查询怎么定位，SQL 如何优化？|MJ032 · 美团 · 一面 · Q25]]
- 慢 SQL 的处理思路是什么？

- 如何定位和优化慢 SQL 语句？
- 使用 EXPLAIN 分析慢 SQL 时，哪些字段比较重要？

- 千万级数据库等值过滤、范围查询慢，怎么排查优化？
- 查询数据库接口 RT 越来越高怎么处理？

#### 面试回答

我的原则是先定位再优化，按四步走：

- 第一步，确认是哪条 SQL：从监控、调用链和慢查询日志拿到具体语句、参数、频率、耗时分布和业务影响。
- 第二步，确认慢在哪一层：区分数据库执行、锁等待、连接池等待和网络延迟。
- 第三步，看执行计划：对可复现的语句查 `EXPLAIN`，在安全环境按需执行 `EXPLAIN ANALYZE`，检查估算与实际行数、访问路径、连接顺序、排序、临时表、回表和循环次数。
- 第四步，改完要验证：针对证据调整 SQL、索引、数据访问量或事务范围，再用代表性数据压测，并观察上线指标，确认有收益且没有明显写放大或回归。

#### 技术细节

**看慢查询日志的方法**

- 日志由阈值和扫描行数等条件筛选出来。
- 日志顺序不等同于语句开始顺序。
- 分析时结合摘要工具或可观测平台，按总耗时、平均耗时、P95／P99、次数和扫描行数排序，不要只盯单次最慢的那条。

**EXPLAIN 和 EXPLAIN ANALYZE 的区别**

- `EXPLAIN` 只给出计划。
- `EXPLAIN ANALYZE` 会实际执行语句，返回迭代器耗时、实际行数和循环次数。
- 因此在生产用它之前必须评估读写副作用和负载。

**常见原因清单**

- 索引类：缺少或选错索引、联合索引列序不匹配、对索引列做了不利于定位的表达式。
- 数据量类：返回或扫描过多数据。
- 计划类：连接与子查询计划不佳、排序或临时表开销、统计信息失真。
- 并发与资源类：锁竞争、长事务、缓存命中变化、资源饱和。

**对应的优化手段（必须对症）**

- 减少 `SELECT *` 和无用扫描。
- 设计可复用而不过宽的索引。
- 改写分页或批处理方式。
- 缩短事务并统一加锁顺序。
- 必要时更新统计信息或调整数据模型。
- 提醒：索引会增加存储和写维护成本，不能把“加索引”当成固定答案。

#### 深挖追问

1. **执行计划走了索引，为什么仍然慢？**（补充练习）

   可能扫描或回表行数仍很多，选择性低，排序、连接、锁等待或 I/O 才是瓶颈；需要结合实际行数、循环、等待事件和整体负载判断。

2. **为什么不直接在生产执行 `EXPLAIN ANALYZE`？**（补充练习）

   它会实际执行被分析语句并可能产生高负载；支持的语句范围与行为还随版本而异。应优先在安全环境复现，生产上先用普通 `EXPLAIN`、现有监控及针对运行连接的诊断手段。

3. **EXPLAIN 输出里哪些字段比较重要？**（面经实际出现；[[面经/百度/一面/0008#Q06：使用 EXPLAIN 分析慢 SQL 时，哪些字段比较重要？|MJ019 · 百度 · 一面 · Q06]]）

   按重要性排，先看这几个：

   - `type`：访问类型，用来区分 const／ref／range／index／ALL。
   - `key`／`possible_keys`：实际用的索引和候选索引，判断有没有选错。
   - `rows`×`filtered`：预估扫描行数，以及过滤后剩下的行数量级。
   - `Extra`：`Using index` 表示覆盖，`Using index condition` 表示索引条件下推，`Using where` 是回表后过滤，`Using filesort`／`Using temporary` 说明排序或分组有代价。
   - `key_len`：联合索引实际用上的长度，用它定位最左前缀断在第几列。
   - `id`／`select_type`：用来看子查询的结构。

   最后一句口径：EXPLAIN 给的是估算，统计信息过期时和实际偏差会很大。可以更新统计信息（ANALYZE TABLE），或在安全环境用 EXPLAIN ANALYZE 核对。

### MYSQL-016：多条件过滤并排序时如何设计联合索引？

**常见问法**

- `WHERE language='粤语' AND time>1990 AND style='慢歌' ORDER BY score DESC` 如何建索引？
- score 是否加入联合索引，language 和 style 谁放前面？

#### 面试回答

这题我不会直接报索引，先问四件事：数据分布、返回列、有没有 `LIMIT`、还有哪些高频查询；然后给候选并实测。

- 通用排法：两个等值条件通常排在范围列之前。
- 但 `language` 与 `style` 谁在前，不能只靠列名决定，要看选择性和其他查询对左前缀的复用。
- 方案 A：重点是按年份快速过滤时，试 `(language, style, time)`。代价是 `time` 是范围条件，它后面的 `score` 通常不能再用来消除排序。
- 方案 B：`LIMIT` 较小、且高分记录很快能满足年份条件时，试 `(language, style, score DESC, time)`，按 score 顺序扫描并过滤 time。
- 边界：没有 `LIMIT` 或命中量很大时，结论可能相反。

#### 技术细节

**B+ 树的有序性决定了能做到哪一步**

- MySQL 8.4 InnoDB 的联合 B-tree 按 key part 依次排序。
- 只有等值前缀固定下来，索引才可能继续服务后续的范围或排序。
- 所以“用一个范围访问”和“用同一个索引排序”之间通常存在取舍。

**把 score 加进索引不是免费的**

- 会增加索引宽度、写放大和维护成本。
- 也不等于覆盖查询：还要不要回表，取决于 `SELECT` 的列。
- 降序 key part 可以让相应方向做前向扫描；另外 MySQL 在适用情况下也能反向扫描索引。

**候选方案怎么比较**

- 在代表性数据上用 `EXPLAIN ANALYZE` 比：实际扫描行数、是否 filesort、回表、耗时，以及写入影响。
- 选择性可以看统计信息，再用实际的基数／频率分布验证。
- 别背错：“高区分度永远放最前”不是规则，因为列序同时还决定可复用的前缀和排序能力。
- 若查询不含 `LIMIT` 且返回大量行，按索引顺序扫描也未必优于过滤后再排序。

#### 深挖追问

1. **language 和 style 谁放前面？**（面经实际出现；[[面经/字节/一面/0001#Q16：多条件过滤并按 score 排序的 SQL 如何设计联合索引？|MJ011 · 字节 · 一面 · Q16]]）

   这条 SQL 里两列都是等值条件，又都排在范围／排序列之前；这种情况下内部顺序：

   - 需要结合两列的选择性，以及其他查询对左前缀的复用来决定。
   - 最后用真实分布和执行计划验证。

2. **score 必须建进联合索引吗？**（面经实际出现；同上来源）

   不必须。是否加入取决于 `LIMIT`、年份过滤后行数、排序成本、回表和写入代价；应比较不同候选索引。

3. **面试现场给一段 SQL，如何决定在哪些列上建索引？**（面经实际出现；[[面经/字节/一面/0004#Q13：给出一段 SQL，可以在什么位置建立索引？|MJ014 · 字节 · 一面 · Q13]]。原 SQL 未记录，按方法论回答）

   - 第一步，把 SQL 拆成等值过滤列、范围列、连接列、排序列和返回列。
   - 第二步，排列序：等值列靠前；范围列之后的列通常不能再用于定位和消序。同时看其他高频查询对左前缀的复用。
   - 第三步，用覆盖索引消掉回表，按选择性筛掉不合适的候选。
   - 第四步，用代表性数据跑 `EXPLAIN ANALYZE`，再算上写入成本收敛结论。

### MYSQL-017：乐观锁和悲观锁如何实现与选择？

**常见问法**

- 乐观锁实现逻辑是什么？
- 悲观锁代码怎么写？

- 乐观锁和悲观锁是什么，分别有哪些优缺点？

#### 面试回答

两种锁的差别就在对冲突的假设上：乐观锁假设冲突较少，悲观锁假设竞争较强。

- 乐观锁：读取时不长期占锁，提交更新时再用版本号或原值校验“是不是仍然没变”。条件更新影响 1 行才算成功，影响 0 行表示冲突，这时应重读后有限重试，或者直接返回冲突。
- 悲观锁：在事务内先用 `SELECT ... FOR UPDATE` 锁定目标记录，再校验并更新，提交或回滚时释放。

各自的代价：

- 乐观锁减少等待，但高冲突下可能反复失败。
- 悲观锁能把竞争的更新串行化，但会阻塞，带来等待和死锁风险。

所以选择看四件事：冲突率、临界区长度、失败成本和一致性要求。

#### 技术细节

以 MySQL 8.4 InnoDB 的库存行为例，乐观锁可写成：

```sql
SELECT stock, version FROM product_stock WHERE id = ?;

UPDATE product_stock
SET stock = ?, version = version + 1
WHERE id = ? AND version = ?;
```

**用乐观锁必须配套的三件事**

- 应用要检查更新行数。
- 要保证业务幂等。
- 要限制重试次数。

**一个可以省掉 version 的写法**

- 如果只是扣减库存，`UPDATE ... SET stock = stock - ? WHERE id = ? AND stock >= ?` 就能把校验和修改合成一次原子的条件更新，不一定需要显式的 version 字段。

悲观锁示例：

```sql
START TRANSACTION;
SELECT stock FROM product_stock WHERE id = ? FOR UPDATE;
UPDATE product_stock SET stock = ? WHERE id = ?;
COMMIT;
```

**用悲观锁的三个前提**

- 锁定读和更新必须在同一个事务、同一个连接里。
- `FOR UPDATE` 实际锁到的范围取决于索引、条件和隔离级别：要用合适的索引、把事务缩短，多行资源采用稳定的加锁顺序。
- Spring 里通常由 `@Transactional` 把查询和更新一起包住；不能只在一个已经结束的仓储调用上加了注解，就假定锁还存在。

#### 深挖追问

1. **乐观锁更新失败后应该无限重试吗？**（补充练习）

   不应该。应根据业务重读、退避并限制次数；高冲突持续失败时要考虑条件原子更新、排队或悲观锁，而不是制造重试风暴。

2. **悲观锁代码怎么写？**（面经实际出现；[[面经/字节/一面/0002#Q01：项目中乐观锁如何实现，悲观锁代码怎么写？|MJ012 · 字节 · 一面 · Q01]]）

   在明确事务边界内执行锁定读和更新，并让提交／回滚释放锁；仅写 `FOR UPDATE` 而查询不在事务中，不能保证后续业务仍受该锁保护。

### MYSQL-018：什么是最左前缀匹配法则，什么时候会失效？

**常见问法**

- 最左前缀匹配法则是什么，什么时候会失效？

- 索引失效的常见场景有哪些？
- 查询能不能匹配联合索引？

- 给 sex＋mail_id 两个等值条件，联合索引怎么建、谁放前面？
- `province_id>5 AND mail_id=10`、等值前缀后接范围、`ORDER BY` 第三列／跳列——这四类查询分别怎么走索引？

#### 面试回答

先说法则本身：联合索引的 B+ 树键按列定义顺序排序，查询要从最左列开始连续匹配，才能利用有序性定位。

- 以 (a,b,c) 为例：条件覆盖 a、a＋b、a＋b＋c 这些等值前缀，都能定位。
- 只给 b 或 c 的条件：从树根就没法确定区间，通常用不上这个索引定位。
- 等值前缀之后一旦遇到范围条件，范围列再往后的列就不能再用于定位。例子：`a=1 AND b>2 AND c=3` 只用 (a,b) 定位，c 是在索引内过滤或者回表验证。

再说“失效”的常见触发点：跳过前导列、范围切断后续列、对索引列套函数或表达式、字符串列与数字比较发生隐式类型转换、LIKE 以百分号开头。

最后把话说严谨：准确表述是“不能用于定位”。优化器仍可能把它当覆盖索引扫描，或者走 Skip Scan 这类特例；到底用不用、用到第几列，以 EXPLAIN 为准。

#### 技术细节

**等值比你想的宽一点**

- 等值不只是 `=`：`IN` 在范围优化中也可以按多个等值区间来处理。

**表达式和隐式转换怎么破**

- 表达式示例：`WHERE YEAR(d)=2020` 用不上 d 的索引，改写成 d 的日期范围就可以。
- 隐式转换要看方向：utf8 列与 latin1 值比较，或者字符串列与数字比较时，转换施加在列侧会让索引不可定位；施加在常量侧则没有妨碍。

**Skip Scan：跳过前导列的特例**

- 适用前提：前导列没有等值条件。
- 版本：MySQL 8.0（8.0.13 起，8.4 文档仍保留）。
- 做法：对前导列的每个离散值做多个小区间扫描，`Extra` 里显示 `Using index for skip scan`。
- 约束：要求前导列离散值少，并且查询能被索引覆盖，不能背成“跳列也没事”。

**“失效”不等于“完全不被使用”**

- `a=1 AND c=3` 跳过了 b：如果走的是覆盖索引，索引内过滤仍然高效。

**另外两类写法**

- LIKE 以百分号开头这类前缀通配，无法在有序结构上定位；可以考虑全文索引、n-gram，或者改业务的检索方式。
- OR 里混合没有索引的列，通常会导致全表扫描。

**排序是同一套道理**

- `WHERE a=? ORDER BY c` 中间缺了 b，就没法用索引的顺序消掉 filesort。
- 例外情况：过滤后行数极少时，代价可以忽略。

**四类查询走法速查（拼多多二面判例）**

设联合索引列序如题所述，结论先给、依据在括号：

- `(province_id, mail_id)`，`WHERE mail_id=10 AND province_id>5`：首列即范围，只能按 province_id 圈区间；mail_id 不参与树定位，走 ICP 在索引层过滤。（“范围切断后续列”）
- `(province_id, city_id, mail_id)`，`WHERE mail_id>=10 AND province_id=5 AND city_id=10`：等值条件书写顺序无关，优化器整理成 province＝5、city＝10 两等值前缀＋mail_id 范围，三列全用于定位。
- 同上索引，`WHERE province_id=5 AND city_id=10 ORDER BY mail_id`：两等值钉死后组内 mail_id 天然升序，排序由索引给出、无 filesort。
- 同上索引，`WHERE province_id=5 AND mail_id=10 ORDER BY city_id`：city_id 是“被 mail_id 等值条件跳开”的那列，(city_id, mail_id) 复合序里挑出 mail_id=10 的行不整体按 city 有序，必须 filesort。

#### 深挖追问

1. **a=1 AND c=3（跳过 b）时索引 (a,b,c) 完全没用吗？**（补充练习）

   不是：a 仍可定位，c 条件可在索引内过滤（ICP）；若查询列被索引覆盖还能免回表，只是 c 不能参与树定位。

2. **为什么范围条件后面的列“失效”？**（补充练习）

   索引按 (a,b,c) 全局有序，b 取一段区间时 c 只在每个 b 值内部有序，无法定义 c 的单一区间；优化器退化为过滤。

3. **“区分度高的列放最前”对吗？**（补充练习）

   不是通用规则。列序先满足高频查询的左前缀复用与排序方向，再在选择性等价候选中比较选择性与实测（见 [[专题题库/MySQL#MYSQL-016：多条件过滤并排序时如何设计联合索引？|MYSQL-016：多条件过滤并排序时如何设计联合索引？]]）。

4. **`user(sex, mail_id)`，`where sex=1 and mail_id=10` 这索引你怎么建？**（面经实际出现；[[面经/拼多多/二面/0001#Q05：user 表有 sex 和 mail_id 两列，`select * from user where sex=1 and mail_id=10` 你会怎么建索引？|MJ049 · 拼多多 · 二面 · Q05]]）

   建联合索引 `(mail_id, sex)`，不给 sex 单建：

   - 本条 SQL 两条件都是等值，(sex, mail_id) 同样两列全用——列序对这一句无差别；差别在未来的复用与选择性。
   - mail_id（邮编）离散度高且可能单独被查，放前缀能服务“只按 mail_id”的查询；sex 只有几个值，单独走索引信息量太小。
   - 严谨收口：`select *` 必回表，覆盖不划算就别硬凑；“高区分度放前”在这里恰好与复用方向一致，但通用依据是上一条追问说的“先服务查询模式，再比选择性”。

### MYSQL-019：大分页查询怎么优化？

**常见问法**

- 大分页查询怎么优化？

- 大数据的分页查询会出现什么问题，怎么解决？

#### 面试回答

先说问题出在哪：`LIMIT n OFFSET m` 在大偏移时要把前 m 行扫出来再丢弃；如果走的是二级索引分页，还伴随海量回表。结果是延迟随页深线性增长。

核心手段是 seek 法（书签／游标分页）：

- 做法：不再传页码，而是带上上一页最后一行的排序键值，用 `WHERE (排序列, id) > (?, ?) ORDER BY 排序列, id LIMIT n` 直接走索引定位。
- 代价：不支持任意跳页。

必须保留页码语义时用延迟关联：

- 先用覆盖索引的子查询 `SELECT id ... LIMIT n OFFSET m` 拿到本页主键，再回表取整行。
- 收益来自减少扫描的行宽和回表带来的随机 I/O。

再补两种实际做法：导出场景不走在线分页，用流式批次或离线索引（如 ES）；业务上限制最大页深、去掉精确总数也常见。

#### 技术细节

**延迟关联怎么起作用**

- 示例：`SELECT t.* FROM t JOIN (SELECT id FROM t ORDER BY id LIMIT 10 OFFSET 1000000) x ON t.id = x.id`
- offset 的扫描仍然在，但只扫窄索引；收益来自避免宽行回表。

**Seek 游标的两个前提**

- 排序必须有确定性：按非唯一列排序时必须追加一个唯一列做 tiebreaker（并列打破列），否则翻页会漏行或重复。
- 游标值要能序列化进请求。

**别忘了深页的计数**

- `COUNT(*)` 到了深页同样昂贵，可以改成“下一页”导航、近似计数或预计算。

**游标会失效的场景**

- 排序列的值在翻页期间被更新。这时需要业务能容忍，或者改用快照／版本号。

**实现层面**

- MySQL 没有原生的 keyset 语法，游标要由应用层构造。
- 服务端游标可以用一个游标 ID 映射到上次的位置。

#### 深挖追问

1. **seek 分页没法跳到第 100 页怎么办？**（补充练习）

   确认跳页是否真实需求；确需时限制最大页深、走支持定位的检索系统（ES search_after 之外还有游标快照），或预计算页起点集合。

2. **为什么二级索引大分页比主键分页更慢？**（补充练习）

   每行还要按主键回表，offset 丢弃的行也逐一回表，随机 I/O 被放大；覆盖索引或延迟关联可显著缓解。

### MYSQL-021：什么是前缀索引和索引下推（ICP）？

**常见问法**

- MySQL 的覆盖索引、前缀索引、索引下推分别是什么？

#### 面试回答

两个概念分开讲。

前缀索引：

- 只对字符串列的前 N 个字符建索引，比如 `INDEX(email(6))`。
- 好处是索引更小、写入更快；代价是区分度下降。
- N 怎么选：用 `COUNT(DISTINCT LEFT(col,n))/COUNT(*)` 算不同前缀长度的选择性，和全长的选择性比较来定。
- 两条限制：前缀索引覆盖不了该列的完整值（命中后仍要回表核对），也不支持这一列完整的 ORDER BY／GROUP BY 语义。

索引下推（ICP，Index Condition Pushdown，MySQL 5.6+）：

- 场景：用联合索引时，那些参与不了范围定位的后续列条件，比如 (name,age) 上 `name LIKE '张%' AND age=20` 里的 age 条件。
- 做法：这些条件由存储引擎在索引层先判断，不满足直接跳过，从而减少回表次数。
- 认法：EXPLAIN 的 Extra 显示 `Using index condition`。

覆盖索引见 [[专题题库/MySQL#MYSQL-010：什么是覆盖索引，如何设计索引？|MYSQL-010：什么是覆盖索引，如何设计索引？]]。

#### 技术细节

**前缀长度的权衡**

- 本质是“拿区分度换空间”：过短会有大量候选要回表，过长收益趋近于零。
- BLOB／TEXT 这类列只能用前缀索引。

**ICP 的适用边界**

- 只作用于二级索引读；主键扫描和覆盖索引都不需要它。
- 它减少回表次数，但不改变访问类型的量级；ICP 过滤之后 rows 估算仍可能偏大。

**不要混称“下推”的其他机制**

- 5.7+ 优化器还有 MRR 等机制，不要和 ICP 混着叫“下推”。
- 8.0 部分场景（如派生表条件下推）属于另一层优化。

**三者的共同口径**

- 覆盖索引、前缀索引、ICP 都是在做“少读数据、少回表”。
- 判断收益一律以 EXPLAIN 和实际压测为准。

#### 深挖追问

1. **前缀索引还能加速 LIKE 'abc%' 吗？**（补充练习）

   能，最左前缀匹配仍适用；但 LIKE '%abc' 前置通配用不上，且前缀命中后完整值还要回表核对。

### MYSQL-022：MySQL 主从复制的数据同步流程是怎样的？

**常见问法**

- [[面经/美团/一面/0002#Q26：MySQL 主从，读取可能数据不一致，你觉得怎么解决？|MJ032 · 美团 · 一面 · Q26]]
- MySQL 的主从复制数据同步流程是怎样的？

- 主从复制是同步的吗？
- 针对主从同步延迟，如何从业务层设计优化？

#### 面试回答

一句话：三个线程接力把主库的 binlog 搬到从库重放。

- 主库：事务提交时写 binlog。
- 主库 dump 线程：从库配好 `CHANGE REPLICATION SOURCE` 后，主库为每个从库起一个 binlog dump 线程，按位点（File+Position）或 GTID 把事件发出去。
- 从库 IO 线程：接收事件并追加到 relay log（中继日志）。
- 从库 SQL 线程：读 relay log 重放事件，应用完更新复制进度。

再说“是不是同步的”：

- 默认是异步：主库提交不等任何从库，宕机时可能丢掉最后的事务。
- 半同步（lossless 配置）：要求至少一个从库确认收到并落 relay log，主库才返回客户端。
- 从库回放可以开并行复制（按组／按表等策略）来降低延迟。

#### 技术细节

**binlog 三种格式**

- ROW：默认格式，记录行变更的前后镜像。
- STATEMENT：有不确定函数（结果依赖执行环境）的风险。
- MIXED：折中方案。

**主从延迟从哪来（看 Seconds_Behind_Source）**

- 从库单事务重放的串行程度、大事务、从库自身负载、网络。

**读到旧数据怎么办**

- 前提：读从库就要接受可能读到旧数据。
- 读己之写的场景：走主库、用 GTID 等待（`WAIT_FOR_EXECUTED_GTID_SET`），或者用半同步。

**数据安全口径**

- 故障切换时，异步复制可能永久丢掉没送达的事件。
- 半同步超时后会降级成异步，所以仍有窗口。
- 结论：按 RPO（恢复点目标）要求选架构，并且要演练。

**重放顺序由谁保证**

- 行重放与主库并发提交之间的顺序性，由组提交／LOGICAL_CLOCK 等机制协调。
- 细节随版本变化，按 8.4 文档核对。

#### 深挖追问

1. **从库会读到脏数据吗？**（补充练习）

   不是脏读，而是旧数据：复制延迟导致从库尚未重放已提交事务；主从一致性监控（pt-table-checksum 类）定期核对。

2. **不改中间件，业务层怎么消化主从延迟？**（面经实际出现；[[面经/百度/二面/0003#Q09：针对主从同步延迟，如何从业务层设计优化？|MJ020 · 百度 · 二面 · Q09]]）

   思路是按“读己之写”的重要性做分级路由，而不是全部读主库：

   - 写后立读的关键接口：强制走主库（注解、Hint，或事务内自动打主库标记）。
   - 会话粘性：用户写完短时间内，它的读都走主库或走缓存。
   - 需要“至少读到某个版本”时：用 GTID／位点等待。
   - 前端兜底：提交成功页先展示本地已知数据。
   - 从库查空时：不立即判定“不存在”，回主库复核一次。

   最后一句结论：全部读主库等于放弃读写分离，分级才是关键。

### MYSQL-023：SELECT FOR UPDATE 未命中行后并发 INSERT，锁会怎么冲突？

**常见问法**

- 两个事务同时执行，说明它们的执行流程，失败还是成功？

#### 面试回答

先把场景摆出来：主键 id 已有 1,3,5,10,15,20；事务 A 执行 `SELECT * FROM t WHERE id=7 FOR UPDATE`（这行不存在），事务 B 随后 INSERT 6、8、11。

- A 未命中不等于“不加锁”：RR 隔离级别下，A 会在本该插入的位置加 gap lock，锁住间隙 (5,10)，A 这条语句成功。
- B 的 INSERT 6 要在这个间隙里申请插入意向锁，和 gap lock 冲突，于是被阻塞；B 事务里后续的 8、11 因为语句按顺序执行，也一起等。
- 结论要看时序：A 在 B 超时前提交或回滚，B 就继续，三条插入都成功。
- 等待超过 `innodb_lock_wait_timeout`（默认 50s）时，B 报锁超时错误，这条语句失败；整个事务是否回滚，由应用的错误处理决定。

#### 技术细节

**第一步：先确认隔离级别**

- 口径要分隔离级别：RC 及以上关闭 gap lock（RC 没有间隙锁，只有外键／唯一键检查等场景例外）。
- 换成 RC，A 未命中就不加间隙锁，B 直接成功。所以这题要先问隔离级别再下结论。

**gap lock 到底挡什么**

- 只防“插入进间隙”，不防读。
- 两个事务对同一间隙都只持有 gap lock（共享属性）时可以共存，冲突发生在插入意向锁那一步。

**11 这行为什么结论不同**

- 11 落在间隙 (10,15)，与 A 没有冲突，它只是被 B 事务内前序语句连带阻塞。
- 如果 B 改成先插 11 再插 6，那就是 11 先成功。

**不要混谈的情况**

- 唯一键冲突时另有锁语义（例如 S 锁），不和这个场景混在一起讲。

**现场答题的顺序**

- 先复述前提：RR、autocommit=0、两个事务并发交错且从 A 开始。
- 再给分支结论。

#### 深挖追问

1. **A 查询改成 WHERE id>5 AND id<10 FOR UPDATE 结果不同吗？**（补充练习）

   同方向：范围锁定读对覆盖的间隙／记录加 next-key 类锁，B 的 6、8 仍被阻塞；具体锁范围与执行计划（走哪个索引）有关。

### MYSQL-024：多个字段单独建索引和建联合索引有什么区别？

**常见问法**

- 联合索引场景下，单独给字段建索引和建联合索引有什么区别？

#### 面试回答

两种做法的差别：

- 单列索引各自独立：任一单列条件都能用上；多列组合查询最多靠 index_merge（排序合并／交集合并），执行不稳定，而且常常多次回表。
- 联合索引按列序服务左前缀组合：一条 (a,b,c) 同时支持 a、a+b、a+b+c 的定位与覆盖，多条件一次收敛，通常更快、回表更少。

联合索引的代价与限制也要一起说：

- 只服务以首列开头（或能构成前缀）的查询，单独查 b、c 用不上。
- 列序设计（等值在前、范围在后、再看选择性）决定覆盖面。
- 索引数量本身有写入放大和空间成本。

选择依据是真实的查询组合分布：

- 高频一起出现的条件做联合索引；各列独立查询多才保留单列索引。
- 再做一次冗余索引检查：(a) 和 (a,b) 并存时，前者通常可以删。

#### 技术细节

**优化器实际会怎么选**

- MySQL 优化器按统计信息选路。
- 即使每一列都有单列索引，组合条件的 index_merge 也常因为回表代价被放弃，退回全表扫描。
- 联合索引“索引内过滤＋少回表”的优势，在大表上才明显。

**联合索引内部的列序**

- 范围列之后的索引列不再用于定位（见 [[专题题库/MySQL#MYSQL-018：什么是最左前缀匹配法则，什么时候会失效？|MYSQL-018：什么是最左前缀匹配法则，什么时候会失效？]]），但能受益于索引下推，在索引层先过滤（见 [[专题题库/MySQL#MYSQL-021：什么是前缀索引和索引下推（ICP）？|MYSQL-021：什么是前缀索引和索引下推（ICP）？]]）。
- 等值列之间的顺序，对“能不能命中”通常不敏感（都是等值）；但对其他查询组合的复用性敏感。
- 所以把会被单独查询、或者作为范围起点的列放前面。

**怎么下结论**

- 以代表性 SQL 的 EXPLAIN（key、key_len、rows、Extra）和压测为准，不靠直觉堆索引。

#### 深挖追问

1. **把常用列放最后行不行？**（补充练习）

   看组合：等值集合内部顺序不破坏命中，但若该列要独立被查询或作为范围起点，放前面才有复用性。

### MYSQL-025：行式存储与列式存储有什么区别，各适用什么场景？

**常见问法**

- 行式存储与列式存储的区别，适用场景？

#### 面试回答

差别就在“什么连续存放”：

- 行式：一行的各列连续存放。读写整行实体快，适合 OLTP（联机事务处理）——点查、按主键更新、事务插入；代表是 MySQL／PostgreSQL。
- 列式：同一列的值连续存放。列内类型相同、重复模式多，所以压缩率高；分析查询只读所需列，还能跳过无关数据（靠 min／max 这类粗索引），大范围聚合很快；代表是 ClickHouse、Parquet 这类数仓格式。

代价是对称的：

- 列式的更新／删除要重写文件或走合并（LSM 类结构），不适合高频小事务和整行读。
- 行式做大范围聚合要扫全行，I/O 被放大。

现实里常见混合架构：行存做交易主库，异步同步到列存做分析。

#### 技术细节

**一句话对比**

- 行式：取一行快、扫一列慢，因为每一行都要触碰。
- 列式：扫一列快、拼一行慢，因为要跨列的文件／块重组。

**列存的两个收益点**

- 扫描裁剪的效果，取决于排序与分区，比如按时间分区＋按常用过滤列排序。
- 压缩收益来自同类型连续存储，例如 RLE、字典编码。

**别把布局说成阵营**

- MySQL 侧 InnoDB 是行存，但并行查询／列存索引这类能力（如 HeatWave、列存索引形态）说明二者只是布局选择。
- 答题时别把“列存＝某个数据库”。

**选型口径**

- 看负载形态：TP 与 AP 的读写比例、事务要求、查询列跨度。
- 别用一句“性能更好”下结论。

#### 深挖追问

1. **列存为什么常配 LSM 或批量导入？**（补充练习）

   原位更新会破坏列的连续布局；追加写＋后台合并（或微批导入）才能同时保住写入吞吐与扫描压缩收益。

### MYSQL-026：三层 B+ 树能存多少数据，怎么估算？

**常见问法**

- [[面经/美团/一面/0002#Q12：一行数据 1KB、主键 bigint、树高约 3 层，大概多少数据量，怎么思考？|MJ032 · 美团 · 一面 · Q12]]
- 三层高的 B+ 树能存储多少数据？

#### 面试回答

这是估算题，先摆假设再算，别背常数。以 InnoDB 默认页 16KB 为例：

- 非叶节点存“索引列＋页指针”：bigint 主键约 8＋6≈14 字节一项，一页可放约 1170～1200 个分叉。
- 叶子节点存整行：如果一行平均 1KB，一页大约放 16 行。
- 相乘：三层＝根 1200 × 第二层 1200 × 每叶 16 行 ≈ 2300 万行。这就是“三层 B+ 树约撑两千万行”这个口径的由来。

被追问时必须能讲敏感性：

- 行更小（100B）时，叶子一页约 160 行，同样三层可以到两亿级。
- 主键越宽，分叉越少。
- 整个估算依赖页大小、行宽和填充率，所以报数之前先问条件。

#### 技术细节

**假设逐项都可以替换**

- 页大小：由 `innodb_page_size` 决定，默认 16KB。
- 非叶一项的大小＝索引列宽度＋页指针（InnoDB 约 6 字节），还要扣除页头页尾和填充开销，所以取整出来是约数。
- 叶行数＝页可用空间 ÷ 平均行大小。注意一行里还有 NULL 位图、变长头和事务隐藏列（DB_TRX_ID、DB_ROLL_PTR 等），实际比列定义更宽。

**二级索引树更矮胖**

- 叶子只存索引列＋主键，同样三层能放下的键值远多于聚簇索引。

**树高和查询 I/O 的关系**

- 三层意味着一次主键等值查找最多 3 次页访问。
- 根和上层节点通常常驻缓冲池，真正落盘的往往只有叶层。
- 这解释了“数据量千万级仍然很快、上亿后树变四层才开始明显”，也接得上 [[#MYSQL-004：InnoDB 索引为什么用 B+ 树，而不是 B 树或哈希表？|MYSQL-004：InnoDB 索引为什么用 B+ 树？]] 里的扇出论证。

#### 深挖追问

1. **为什么常说主键用自增 int/bigint 而不是 UUID？**（补充练习）

   主键宽度直接进入每个非叶项和每个二级索引叶子；越宽扇出越小、树越高，且随机主键造成页分裂碎片，进一步拉低有效密度。

### MYSQL-027：事务的 ACID 分别由什么机制保证？

**常见问法**

- MySQL 事务，事务特性逐个解释展开：原子性、隔离性、持久性、隔离机制、MVCC、间隙锁。
- ACID 分别靠什么实现？
- 数据库是怎么保证事务的原子性的？

#### 面试回答

按四个特性逐个说，每个先说靠什么机制：

- 原子性（Atomicity）：事务里的修改要么全生效、要么全撤销，靠 **undo log**。改数据前先把旧值写进 undo，回滚时按 undo 逆向恢复。undo 本身也遵循“先写日志再改数据”的顺序，所以崩溃时未提交的事务同样能被回滚掉。
- 持久性（Durability）：提交后数据不丢，靠 **redo log ＋ WAL**（先写日志再改数据）。先写 redo 再改内存页，崩溃后重放 redo，把已提交事务补回来。强度由 `innodb_flush_log_at_trx_commit` 决定：=1 每次提交刷盘，最安全；=2 只写到 OS 缓存；=0 由后台每秒刷。外面再配 binlog 和双写缓冲（防页断裂）。
- 隔离性（Isolation）：并发事务互不干扰，靠**锁 ＋ MVCC**。写和当前读用行锁／间隙锁互斥，普通 SELECT 走快照读不加锁。
- 一致性（Consistency）：数据满足约束和业务不变量。它是目标，不是某个具体机制——由前三个特性，加上主键／唯一／外键／非空约束、触发器以及正确的 SQL 共同达成。

面试时最容易被抓的两句话：

- “ACID 不是四种事务。”
- “隔离性不等于串行执行”——MVCC 让读不阻塞写，代价是读到的可能是快照而不是最新值，这正是 RC 与 RR 的差别所在。

#### 技术细节

**undo 与版本链是同一份数据的两种用途**

- undo 里保存的历史版本，通过行内的回滚指针串成版本链。
- 回滚时倒着走这条链；快照读时按 read view 顺着找第一个可见版本。所以“回滚能力”和“MVCC 读历史”共用 undo。
- 什么时候能清：purge 线程只有在这些 undo 不再被任何活跃快照需要时才能删掉。

**redo 与 binlog 的一致性**

- InnoDB 提交走两阶段：redo 进入 prepare 并刷盘 → 写 binlog → redo 提交。
- 崩溃恢复时以“binlog 是否完整”决定这个事务是提交还是回滚，否则会出现“库改了但从库没收到 binlog”或者反过来。
- `binlog_order_commits`、`sync_binlog` 等参数决定这条链路的性能与耐久折中。

**隔离机制的粒度**

- 隔离级别（RU／RC／RR／串行化）定义的是允许哪些异常：脏读、不可重复读、幻读。
- InnoDB 在 RR 下用 next-key lock（记录锁＋间隙锁）限制范围内的插入，来防当前读的幻读。
- 普通快照读靠 read view 复用事务首次建立的快照，所以“别人插了新行我看不见”，但这并不阻止对方插入。把 MVCC 说成“彻底解决幻读”是不准确的。
- 间隙锁的范围依赖索引与执行计划：条件走索引时锁相关区间；走不到索引时可能锁住扫描到的大量记录，这是锁等待与死锁的常见根因（详见 [[专题题库/MySQL#MYSQL-005：MySQL 中有哪些锁，如何分类？|MYSQL-005：MySQL 中有哪些锁]]）。

**一致性还要看业务层**

- 余额扣减与流水写入必须在同一个事务里；跨服务时退化为最终一致（幂等＋对账＋补偿，见 [[专题题库/系统设计#SYS-010：如何保证数据库写入与消息发送的一致性？|SYS-010：数据库写入与消息一致性]]）。
- 数据库约束挡不住“状态机跳变”，那要靠条件更新（`where status = 'PENDING'`）来表达。

#### 深挖追问

1. **为什么 RR 下重读结果不变，却还可能出现幻读？**（面经实际出现；[[面经/美团/一面/0002#Q23：MySQL 事务特性逐个展开：原子性、隔离性、持久性、隔离机制、MVCC、间隙锁|MJ032 · 美团 · 一面 · Q23]]）

   根因是快照读和当前读混用。流程是这样：

   - 事务先做快照读，按首次建立的 read view 看到 N 行。
   - 别的事务插入一行并提交。
   - 本事务接着执行 `UPDATE`／`SELECT ... FOR UPDATE` 这类当前读，就能看到那行新数据，还可能把它改掉。
   - 之后再快照读，因为 read view 没变，仍然“看不见”那行——表现就是更新影响了看不到的数据。

   一句话收口：RR 防幻读防的是当前读路径（靠 next-key lock），并不是快照读的可见性规则。

2. **undo log 会不会把表撑大？**（补充练习）

   会，而且不止撑 undo 表空间。

   - 机制：长事务或未及时提交的事务会一直持有 undo 和旧版本，导致 undo 表空间膨胀；版本链变长会让快照读变慢；还会阻塞 vacuum／purge。
   - 生产做法：监控最长事务的运行时间，避免在事务里做 RPC 或大批量循环；必要时把报表类长查询路由到从库，并降低隔离级别。

3. **RC 与 RR 在复制上有什么不同风险？**（补充练习）

   先记官方口径：**READ COMMITTED 只支持基于行的二进制日志**。

   - 配 `binlog_format=MIXED` 时，服务器会自动改用 row-based。
   - 原因是 RC 下同一事务的多次一致性读可能落在不同快照上，语句日志没法安全复制；RR 才可以用 STATEMENT／MIXED。

   这也解释了一个常见选型：很多互联网场景用 RC ＋ ROW，因为间隙锁范围更小、锁冲突更少。代价有两条——不可重复读要自己处理，行格式 binlog 的体积也更大。

4. **原子性单独被问到时怎么展开？**（面经实际出现；[[面经/帆软/二面/0002#Q10：数据库是怎么保证事务的原子性的？|MJ035 · 帆软 · 二面 · Q10]]）

   只答 undo 这一条链就够：

   - 改动前把旧值写进 undo，这是 WAL 顺序（先日志后页）。
   - 回滚时按 undo 逆向撤销。
   - 崩溃恢复时对未提交的事务回滚，效果等价于“要么全做、要么全不做”。

   再补两句就能收口：与 redo 的分工（redo 管已提交不丢，undo 管未提交可撤）、undo 的 purge 时机。不用把隔离性和持久性也背进去。

### MYSQL-028：分组聚合后按聚合值过滤、以及取组内 Top1 的 SQL 怎么写？

**常见问法**

- 有订单表、订单明细表、商品表，统计每个商家销售额超过 10 万的商品。
- 查询每个商家销售额最高的商品。
- 组内最大值那一行怎么取，并列怎么办？

#### 面试回答

先把两句口径问清：

- 销售额是按明细的 `单价×数量`，还是按明细里的成交字段？
- 要不要排除已退款或已取消的订单？

口径没定就写 SQL，会被判定成没做过真实需求。

写法分两步：第一步都是“多表连接＋按维度分组”，第二步按目标选写法。

目标是“聚合值满足条件的分组”时，条件作用在聚合结果上，必须写在 HAVING 里：

- `WHERE` 里不能出现 `SUM(...)`。
- 而且 WHERE 的语义是“先删行再分组”，会把该组其他行提前删掉。

```sql
SELECT o.merchant_id, oi.product_id, SUM(oi.price * oi.quantity) AS sales
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
WHERE o.status = 'PAID'
GROUP BY o.merchant_id, oi.product_id
HAVING SUM(oi.price * oi.quantity) > 100000;
```

这条 SQL 有两个细节要主动讲出来：

- 分组键必须同时含商家与商品，否则同款商品跨商家会被合并。
- 开启 `ONLY_FULL_GROUP_BY` 时，SELECT 里的非聚合列都得进 GROUP BY，或者改用 `MAX(name)` 这类聚合。

如果目标换成“每组内最大那一行”：

- 不能简单 `GROUP BY merchant_id` 再取 `MAX(sales)`，那样其他列会落到不确定的行上。
- 首选窗口函数：先在派生结果上按商家分组、按销售额降序排名，再取 `rk = 1`。

```sql
WITH sales AS (
  SELECT o.merchant_id, oi.product_id, SUM(oi.price * oi.quantity) AS sales
  FROM orders o JOIN order_items oi ON oi.order_id = o.id
  WHERE o.status = 'PAID'
  GROUP BY o.merchant_id, oi.product_id
), ranked AS (
  SELECT merchant_id, product_id, sales,
         RANK() OVER (PARTITION BY merchant_id ORDER BY sales DESC) AS rk
  FROM sales
)
SELECT merchant_id, product_id, sales FROM ranked WHERE rk = 1;
```

窗口函数要能解释为什么选它：

- `RANK()` 和 `DENSE_RANK()` 会保留并列，一个商家可能返回多行。
- `ROW_NUMBER()` 强制唯一。用它就必须给一个确定性的次级排序键（比如 `product_id`），否则同一份数据跑两次结果可能不同。

老版本 MySQL（5.7 及以前没有窗口函数）走“自连接派生表”：

- 先按商家聚合出 `MAX(sales)`，再和上一步的明细聚合结果按 `merchant_id AND sales` 连接。
- 这种写法并列会一起出来，要唯一就得再加规则。

#### 技术细节

**性能：这题数据量大时才是真正的考点**

- 两层聚合都要扫全量明细，线上通常不允许每次实时算。
- 做法：加一张“商家＋时间”维度的汇总表，按天预聚合到商家×商品，查询只扫汇总表。
- 索引要撑住连接：`orders` 按 `(merchant_id, status)`、`order_items` 按 `order_id` 有支撑索引，避免连接时在主键之外做全表扫。
- 窗口函数带来的排序是内存／临时表排序，数据规模大时要看执行计划里的 filesort 成本。

**口径类陷阱（四个要点名）**

- 连接方式：用 `LEFT JOIN` 还是 `INNER JOIN` 结果不同——只有订单没有明细的商家、没有价格的明细行，都会改变聚合结果。
- NULL 处理：`SUM` 遇到 NULL 会跳过，某条明细价格为 NULL 时销售额会被低估，必要时写 `SUM(COALESCE(price*quantity,0))`。
- 金额精度：浮点金额（`DOUBLE`）累加有精度问题，金额应该存 `DECIMAL`，否则“超过 10 万”这种边界判定不可靠。
- 时间窗口：口径里没定义“每个商家”是否限定最近 30 天，结果会差一个量级。这属于必须现场澄清的口径，不是实现细节。

- 多条件过滤与排序的联合索引顺序见 [[专题题库/MySQL#MYSQL-016：多条件过滤并排序时如何设计联合索引？|MYSQL-016：联合索引设计]]。

#### 深挖追问

1. **“每个商家总销售额超过 10 万，列出这些商家的所有商品”和原题有何区别？**（面经实际出现；[[面经/字节/二面/0002#Q05：给定订单表、订单明细表、商品表，编写 SQL 统计每个商家销售额超过 10 万的商品。|MJ042 · 字节 · 二面 · Q05]] 的延伸）

   这是两种口径，别混：

   - 原题：先按“商家×商品”分组再过滤，阈值作用在商品级销售额上。
   - 这句描述：先按商家分组筛出商家集合，再展开它的商品。得用子查询或 CTE 两步——把 `HAVING SUM(...) > 100000` 作用在 `GROUP BY merchant_id` 上，再回连。

   现场说清这个差别，比写对一条 SQL 更能证明你理解。

2. **并列第一到底该留几个？**（补充练习）

   由业务语义决定，先把规则问出来再选函数：

   - 报表和榜单：通常要 `ROW_NUMBER()` 配一个确定的并列规则（按商品 ID 或上架时间），否则用户每次刷新看到的结果不同。
   - 分析场景：更关心“有几件并列”，用 `RANK()` 并把行数保留下来。

3. **为什么 `WHERE status='PAID'` 不能写在 HAVING 里？**（补充练习）

   语义层面 HAVING 是“分组后对组做筛选”，`status` 是行级属性、与聚合无关；写在 HAVING 里要靠 `MAX(status)` 这类变通表达，既难读又可能因分组内值不同而出错。行级过滤尽量放 WHERE，让优化器能提前缩集合并命中索引。

### MYSQL-029：如何判断表结构是否符合 3NF，什么时候该反范式？

**常见问法**

- 上述表结构是否符合 3NF？
- 讲讲三大范式，第三范式的判据是什么？
- 冗余字段／快照字段算不算违反范式，为什么业务里还这么做？

#### 面试回答

第一步把定义说准：

- 1NF：属性不可再分——不要在一个字段里塞逗号分隔的多值。
- 2NF：非主属性要完全依赖候选键，联合主键下不能只依赖其中一部分。例子：以 `(order_id, product_id)` 为主键的明细表里放 `product_name`，它只依赖 `product_id`，就违反 2NF。
- 3NF：非主属性不能传递依赖候选键。A→B→C 时，C 不该留在依赖 A 的表里。
- 一句判据：每个非主属性都“直接且完全”依赖主键、并且彼此无关——所谓 the key, the whole key, and nothing but the key。

再拿订单三表实际判一遍：商家名、商品名不在订单表里，明细表按“这一单这一件”存 `price` 与 `quantity`，看着符合 3NF。但要能点出两处常见违规：

- 订单表冗余 `merchant_name`：这是传递依赖（订单→商家→商家名），违反 3NF。
- 订单表存 `total_amount`：它能由明细求和推出，属于可由其他非主属性导出的派生值，同样违反 3NF。

结论要落在权衡上，不要死守范式：

- 范式的收益：消除冗余和更新异常（改商家名不用回写历史订单），写路径简单。
- 范式的代价：读要多表 JOIN，聚合与分析类查询被放大。

真实业务会刻意反范式，两个典型理由：

- 历史语义必须冻结。订单要保存成交时的单价与商品名快照，因为商品价会变、名字会改，用当前价反推历史订单金额是错的。这不是“没做好范式”，而是这两个字段本来依赖的是“这一单”而不是“这个商品”——把 `price` 放在明细表里其实完全合规。
- 读侧性能。冗余统计列、汇总表、宽表是给报表和搜索用的，代价是必须有维护手段（同事务更新、binlog／CDC 同步＋对账），否则就变成不一致的隐患。

收口的判断：先让写入语义正确（范式帮你把依赖关系表达清楚），再按读侧证据决定冗余，并且每处冗余都要能说出它由谁负责维护。

#### 技术细节

**怎么动手判：三步找三种味道**

- 先列出候选键，再写出每个非主属性的依赖，然后找三类问题：部分依赖（只依赖联合键里的一半）、传递依赖（A→B→C）、派生属性（能由同行其他列算出来）。
- 派生属性严格说属于更细粒度的规范化讨论（有时归到 EFN／BCNF 的范围）。面试里说“可导出的字段是冗余”就够了，重点是要能说出它对更新的影响。

**BCNF 与 3NF 的差别（常见延伸）**

- BCNF 要求每个决定因素都是候选键，不允许“非主属性决定另一个非主属性”这类情况，比 3NF 更严格。
- 有些表在 BCNF 下做不到既无损分解又保持依赖，所以工程上普遍以 3NF 为界。
- 反例要能举一个：`（学生, 课程）→ 讲师`、`讲师 → 课程`（每个讲师只教一门课）里，“讲师”决定“课程”，但讲师不是候选键，这就是违反 BCNF 的情形。

**反范式的维护手段要能具体说**

- 同事务内更新：简单，但有锁范围与一致性窗口。
- binlog／CDC 异步同步：解耦，但要接受延迟并做对账。
- 生成列或视图：在数据库内用表达式派生，避免应用层两处写。
- 汇总表加水位与定时校准：由对账任务去比对明细求和。
- 选哪种，取决于“读侧能不能容忍旧值”。

#### 深挖追问

1. **那订单表里的 `total_amount` 到底该不该存？**（面经实际出现；[[面经/字节/二面/0002#Q06：上述表结构是否符合 3NF？|MJ042 · 字节 · 二面 · Q06]]）

   两个层面分开答：范式上它是冗余（可由明细导出），工程上常常必须存——结算、风控和列表页都要用它，每次实时求和代价高。

   取舍标准就一句：谁负责保证它和明细一致。

   - 明细只在同一事务里变更：那就同事务同步更新。
   - 做不到：要么加对账，要么改成不落库的物化视图／汇总表。
   - 绝对不行：靠应用层两处各自写。

2. **只查商品名为什么会扯到范式？**（补充练习）

   冲突点在“要不要把 `product_name` 复制到订单明细”：

   - 要展示历史名，就必须复制（违反 3NF）。
   - 要改名后统一生效，就不能复制（符合 3NF）。

   所以先问业务：“商品改名后，历史订单显示新名还是当时的名字？”答案决定表结构。这类问题答成“取决于业务”才是对的。

3. **怎么向面试官证明你的表设计合理？**（补充练习）

   给依赖关系，不要只给结论：

   - 每个字段的决定因素是谁。
   - 哪些字段属于“快照”而不是“引用”。
   - 查询走什么路径，有没有对账兜底。
   - 如果流量或数据量变化，会先动哪一处（加索引还是加汇总表）。

   有这套因果链，范式之争就不容易被问倒。

### MYSQL-030：如何按取值区间给行分桶并统计每桶数量？

**常见问法**

- 一共 1000 件商品，价格范围 (0,1000) 元，写 SQL 分别求价格在 (0,10)、(10,120)、(120,1000) 的商品数量。（table：item_tab，columns：id,name,desc,price）

#### 面试回答

通用解法一行话：用 `CASE WHEN` 给每行打桶标签，再按标签 `GROUP BY` 计数：

```sql
SELECT CASE
         WHEN price > 0   AND price < 10    THEN '(0,10)'
         WHEN price >= 10 AND price < 120   THEN '[10,120)'
         WHEN price >= 120 AND price < 1000 THEN '[120,1000)'
         ELSE 'other'
       END AS price_range,
       COUNT(*) AS cnt
FROM item_tab
GROUP BY price_range;
```

- 先把端点口径说破：题面写开区间，但 10、120 归哪边、≤0／≥1000／NULL 怎么算，都要声明假设（上式按左闭右开＋other 兜底）。
- 变体“三列计数一行展示”：`SUM(price < 10)` 风格（MySQL 布尔即 0/1）或三个 `SUM(CASE WHEN ... THEN 1 ELSE 0 END)`，适合只关心三个数。
- 变体“空桶也要显示 0”：CASE 分桶天然丢掉空区间——需要造区间派生表 LEFT JOIN 原表，或按列展开写法。

#### 技术细节

**GROUP BY 用别名还是重复表达式**

- MySQL 允许 `GROUP BY price_range`（按 SELECT 别名分组），标准 SQL 要重复整个 CASE——两种都认识，跨库面试（尤其 PostgreSQL）写全表达式更保险。

**NULL 的落点**

- 所有比较对 NULL 都是 unknown，`price IS NULL` 的行会掉进 `ELSE 'other'`——被追问“边界外去哪了”时指这里；不想混入就用 `IS NULL` 单独一桶。

**大表上的执行方式**

- 全表扫一遍、每行一次 CASE、按基数很小的桶做聚合：无索引可用时就是扫描成本；桶很多（按值域分 1000 桶）时可 `FLOOR(price/10)` 直接算桶号代替一长串 CASE。
- 与 MYSQL-028 同族：这题是“按条件分桶聚合”；“组内 Top1／HAVING 过滤”是窗口与聚合函数的另一半，面试常连问。

#### 深挖追问

1. **要求输出固定顺序的桶怎么办？**（补充练习）

   桶名带序号前缀（`1_(0,10)`…）再 ORDER BY，或 `ORDER BY FIELD(price_range, ...)`／CASE 排秩；GROUP BY 不保证顺序，ORDER BY 才保证。

2. **怎么验证结果对？**（补充练习）

   各桶（含 other）计数之和应等于 `COUNT(*)`；抽样手算边界值（price=10、NULL）。在不能执行 SQL 的环境（如虾皮手撕 IDE），这就是口述自检方案。

### MYSQL-031：一条 SQL 语句的执行过程是怎样的？

**常见问法**

- 讲一下一条 SQL 语句从客户端输入到结果返回的执行过程。

#### 面试回答

MySQL 架构是“Server 层 ＋ 存储引擎层”，一条语句按顺序穿过各组件。以 InnoDB 的查询为例：

- 连接器：建立 TCP 连接、认证用户名密码、载入该用户的权限，之后每次访问都拿它做权限校验。
- 查询缓存：命中就直接返回结果——但 MySQL 8.0 起已彻底移除这个模块（表一变就整体失效、命中率太低），8.0 之前才有。
- 分析器：词法分析认出关键字、表名、列名，语法分析判断语句结构是否合法。
- 优化器：在多个可用索引之间选一个、决定多表连接顺序，生成执行计划（可用 `EXPLAIN` 看它的选择）。
- 执行器：先按表结构判断列权限，再调用存储引擎的接口一行行取记录、边取边按 where 过滤。
- 存储引擎（InnoDB）：按索引定位数据，数据页命中缓冲池（Buffer Pool）就直接用、未命中就读盘进池，把行返回给执行器。

一句话主线：连接器→（查询缓存，8.0 已删）→分析器→优化器→执行器→存储引擎。

#### 技术细节

**更新语句额外要写日志（这半段最能拉开区分度）**

- 走上前半段流程后，执行器调用引擎接口写入一行，InnoDB 的落盘要协调三份东西：内存数据页、redo log、binlog。
- redo log：InnoDB 独有，是物理 WAL 日志，崩溃后能恢复已提交但未刷盘的修改，保证持久性。
- binlog：Server 层的归档日志，记录逻辑变更，用于主从复制与数据恢复（见 MYSQL-022）。
- 两者用“两阶段提交”（redo prepare→写 binlog→redo commit）保证一致，避免主从拿到不同数据。

**权限校验发生在两处，别混**

- 连接器建连时确认“能不能连进来、有这个库表权限”。
- 执行器执行时确认“这条语句能不能访问到这些列”，防止建连后权限变了仍按旧权限放行。

**长连接与内存**

- 长连接省去反复建连认证，但连接的临时表、buffer 等只在断开时释放，长时间不断开可能让内存涨——可用 `mysql_reset_connection` 或周期性重连缓解。

**容易说过头的地方**

- 不要说“MySQL 有查询缓存所以很快”：8.0 已移除，答的时候要按版本说清。
- 优化器选索引不一定顺从你的预期：统计信息偏差可能选错，必要时用 `FORCE INDEX` 或统计信息重算，这是追问点。

#### 深挖追问

1. **为什么 MySQL 8.0 要删掉查询缓存？**（补充练习）

   查询缓存按整条语句文本精确匹配，且表一有更新就把相关缓存全部失效，在写多、参数化的 OLTP 场景命中率极低，失效逻辑反而成瓶颈，索性移除。

2. **`EXPLAIN` 里能看到这条链路的哪一段？**（补充练习）

   主要看优化器的选择：`type`（访问类型）、`key`（实际用的索引）、`rows`（预估扫描行）、`Extra`。它反映的是执行计划，不含连接器与执行器逐行取数。

3. **redo log 和 binlog 为什么不能合并成一份？**（面经实际出现的延伸）

   职责不同：redo log 是 InnoDB 的物理日志、用于崩溃恢复、循环写；binlog 是 Server 层的逻辑归档日志、全库共用、追加写、给从库回放。合并会既丢引擎无关性又难做恢复与复制。

4. **SQL 查询语句里各子句的逻辑执行顺序是什么？**（面经实际出现；[[面经/招银云创/一面/0001#Q10：SQL 查询语句的执行顺序是怎样的？|MJ055 · 招银云创 · 一面 · Q10]]）

   这是与本话题“架构执行链路”不同的另一层含义——问的是各子句谁先算：

   - 逻辑顺序：FROM／JOIN → WHERE → GROUP BY → 聚合函数 → HAVING → SELECT（算表达式、定输出列）→ DISTINCT → ORDER BY → LIMIT。
   - 书写顺序却是 SELECT 在最前，所以别把“写法顺序”当“执行顺序”。
   - 由此解释两个常问点：WHERE 里用不了 SELECT 定义的别名（SELECT 还没执行）；GROUP BY／HAVING 里能用聚合别名，因为它们在 SELECT 附近执行。
   - 排序用的 ORDER BY 在 SELECT 之后，所以能引用输出列／别名。

### MYSQL-032：线上频繁出现数据库连接失败，怎么排查、可能有哪些原因？

**常见问法**

- 线上系统频繁报数据库连接失败，排查思路和可能原因？

#### 面试回答

先分清是“网络连不上 DB”还是“连得上但拿不到连接”，再按连接池、数据库、网络三层缩小范围。

- 看异常类型定位：`Communications link failure` 多为连接被中断／空闲被回收；`Connection refused` 是端口没监听／DB 挂了；`Too many connections` 是 DB 连接数到顶；获取超时是连接池被打满。
- 连接池侧：活跃连接是否等于最大连接、等待是否超时；常见诱因是慢 SQL 长时间占用连接、或连接泄漏（借出没归还）。
- 数据库侧：`max_connections` 是否到顶、是否刚做过重启／主从切换、`wait_timeout` 把空闲连接服务端断开但客户端还在用。
- 网络侧：安全组／防火墙、DNS、连接被 LB 限、跨网抖动。
- 资源侧：DB 实例 CPU／内存／磁盘打满导致拒绝新连接。

落点：给一条排查动线（异常类型→连接池指标→`SHOW PROCESSLIST`→监控曲线定位时间点），再给兜底（连接池校验与重试、慢 SQL 治理、熔断降级）。

#### 技术细节

**空闲连接被单侧回收（最高频的一类）**

- DB 的 `wait_timeout` 到点会关连接，但连接池不知道，拿到已失效连接就报 `Communications link failure`。
- 对策：连接池配置的“连接最大存活时间”要小于 DB 的 `wait_timeout`；开启取用前探活（`testOnBorrow` 或 `validationQuery=SELECT 1`，Druid 用 `testWhileIdle`＋心跳）。

**连接池打满 vs 连接数到顶**

- 池打满：现象是应用侧获取连接超时，DB 连接数未必高——多半是慢 SQL 或并发超过池容量。
- DB 端 `Too many connections`：是所有应用的总连接超了 `max_connections`——要看是否连接数配置过小、或某服务泄漏。

**排查抓手**

- `SHOW PROCESSLIST` 看当前连接在跑什么、有没有大量 Sleep／长事务。
- 看连接池监控（活跃、空闲、等待数）与应用异常发生的时间点，对齐 DB 侧监控（QPS、连接数、慢查询、CPU）。

**别说过头**

- 别说“加大 `max_connections` 就好”：连接不是越多越好，过多会加剧 DB 上下文切换和内存压力，根因常在慢 SQL／泄漏。

#### 深挖追问

1. **主从切换瞬间大量连接失败正常吗，怎么处理？**（补充练习）

   正常——切换窗口旧主不可写。客户端要配自动重连＋读写路由对拓扑变化的感知（或走代理层），并保证切换期间写请求有明确失败语义与重试幂等。

2. **怎么快速判断是不是连接泄漏？**（补充练习）

   看连接池“活跃连接数”是否只增不减、借出后长时间不归还，配 Druid 的 `removeAbandoned` 或打印借还栈定位未关闭的 Connection／未提交的 Statement。

### MYSQL-033：数据库内存占用高，可能有哪些原因，怎么定位？

**常见问法**

- 数据库（MySQL）内存占用高，可能是什么原因？

#### 面试回答

先分清是数据库进程吃内存，还是应用侧内存高；这里按 MySQL 服务端答，常见原因分四类：

- 缓冲池配得大：InnoDB `innodb_buffer_pool_size` 本就是内存大户，这是正常且应该的，但要给系统和连接留余量。
- 连接数 × 会话级缓冲区：每个连接会用到 `sort_buffer_size`、`join_buffer_size`、`read_buffer_size`、`thread_stack` 等，连接暴涨时这些会成倍叠加。
- 大查询／慢 SQL：大范围扫描、无 LIMIT、`SELECT *` 捞大结果、排序分组、临时表，短时占大量内存。
- 临时表与内存表：内存临时表多或超限转磁盘；MEMORY 引擎表本身就常驻内存。

定位：看内存曲线是否与连接数、慢查询数量同步上涨；`SHOW PROCESSLIST` 抓重查询，核对“会话 buffer × 最大连接数”是否已超物理内存。

#### 技术细节

**缓冲池不是越大越好**

- 常见经验值是物理内存的 50%～70%（专用 DB 机可更高），但要给连接内存、OS page cache、其它进程留空间；配太大反而触发 OS 换页或 OOM。

**连接内存要按“最坏并发”估**

- 真实占用 ≈ 缓冲池 + `max_connections` × 各类会话 buffer（一次查询可能同时用 sort＋join＋read 多个 buffer）。
- 所以“连接数失控”比“某个参数太大”更容易把内存顶爆——治理连接数常比调大内存更有效。

**大查询的证据**

- 内存突增常伴随 `Sort_...`、`Create_tmp_table` 等状态计数飙升，或某条 SQL 扫描行数异常；定位到具体 SQL 再决定加索引、改写还是限流。

**别把话说死**

- “内存高就是内存泄漏”是最常见的误判：绝大多数是缓冲池＋连接数＋大查询的正常占用，先排这三样再谈泄漏。

#### 深挖追问

1. **怎么区分正常占用和异常增长？**（补充练习）

   看趋势与相关性：缓冲池会在启动后快速涨到配置值再平稳，属正常；若内存随连接数或慢查询持续爬升不回落，才指向会话内存堆积或泄漏。

2. **一个库被多条大查询打满内存，先做什么？**（补充练习）

   先止血：kill 掉失控的长查询、必要时限流入口；再治理：给这些 SQL 加索引／分页、给会话级 buffer 设合理值、约束 `max_connections`。

3. **主存 100G，对 200G 的表全表扫描，会把内存吃光吗？**（面经实际出现；[[面经/途虎养车/一面/0001#Q12：主存 100G，对 200G 的表做全表扫描，会吃光内存吗？为什么？|MJ070 · 途虎养车 · 一面 · Q12]]）

   不会。“表比内存大”不等于“扫描要把表装进内存”：

   - 扫描是流式的：InnoDB 沿聚簇索引逐页读取、server 层逐行取回、按批发给客户端，不存在整表驻留。
   - 缓冲池是固定容量的：`innodb_buffer_pool_size` 封顶，全扫描走热端插入防污染（8.0 的 medium-size 扫描另有分块策略），页进页出有界。
   - 会涨的部分都有上限：连接级缓冲、排序缓冲、内部临时表超 `temptable_max_ram` 后转 InnoDB 临时表落盘（见 [[#MYSQL-035：MySQL 什么时候会使用内部临时表？|MYSQL-035]]）。
   - 真正的风险在客户端：把结果集全 fetch 进应用内存才会打爆——大扫描要 LIMIT／流式消费（fetchSize）；扫描冲刷缓冲池带来的是性能抖动，不是内存耗尽。

### MYSQL-034：数据库调优可以从哪些方面入手？

**常见问法**

- 实践过程中，有哪些方面可以实现数据库调优？
- 数据库调优你会从哪些层面考虑？

#### 面试回答

结论：调优按「先量再改、由近及远」分五层——SQL 与索引、库表结构、事务与锁、配置与容量、架构。

- SQL 与索引：抓慢查询、看执行计划，让查询走上覆盖索引和最左前缀，改写深分页与大结果集。
- 库表结构：字段类型收窄、避免隐式转换、必要时反范式冗余换掉 join。
- 事务与锁：缩短事务、统一加锁顺序防死锁、热点行靠排队或拆分降低争用。
- 配置与容量：缓冲池、连接数与连接池、日志刷盘策略；先有指标再动参数。
- 架构：读写分离扩读、缓存挡热点、单表容量到顶再分库分表。
- 讲完清单要收到事实上：我真正做过的是【某条慢 SQL／某个索引改造】，效果是【可核对的数字】。

#### 技术细节

**为什么顺序是「由近及远」**

- 前两层（SQL／索引、库表）改的是单条查询的代价，收益快、风险小、可回滚。
- 中间一层（事务与锁）改的是并发行为，需要压测和灰度验证。
- 后两层（配置、架构）影响全局，属于容量问题才动的刀，不是慢的通用解药。

**每层的具体抓手**

- 观测入口：慢查询日志（`slow_query_log`＋`long_query_time`）、`EXPLAIN`／`EXPLAIN ANALYZE`、`performance_schema`；先确认瓶颈是扫描量、排序、锁等待还是 IO。
- SQL：只取需要的列、避免函数套在索引列上、把 `OR`／`IN` 拆成可走索引的形式、分页用延迟关联把回表压到页大小。
- 索引：联合索引按「等值列在前、排序列紧随、范围列最后」排布；覆盖索引消除回表；冗余索引拖慢写入要定期清理。
- 结构与类型：`INT` 能放下就别用 `BIGINT`，定长短串用 `CHAR`，`NULL` 会让索引与统计变复杂；大字段垂直拆表。
- 事务与锁：事务里不放 RPC 与文件 IO；多表加锁统一顺序；更新热点行（库存、计数）改成异步合并或分片行。
- 配置：InnoDB 缓冲池（`innodb_buffer_pool_size`，官方默认 128MB）是首要参数；专用数据库实例通常远大于默认值，但取值要按工作集、系统页缓存余量和重启恢复代价试出来，没有可背的通用百分比。
- 连接数上限要和 Web／线程池规模对齐，否则现象是「连接打满」而不是「数据库慢」。
- 架构：读写分离挡读流量、Redis 挡热点、分库分表解决单表容量与写入瓶颈（见 [[专题题库/系统设计#SYS-011：什么时候需要分片查询，如何定位与优化查询瓶颈？|SYS-011：什么时候需要分片查询]]、[[专题题库/系统设计#SYS-023：哈希分表扩容有什么问题，一致性哈希怎么工作？|SYS-023：哈希分表与一致性哈希]]）。

**动手前的三个前提**

- 先有基线：没有压测／线上指标就谈不上「优化了 10 倍」。
- 先看数据量级：千行表的慢往往是环境问题，亿行表的慢才是结构问题。
- 区分「慢」与「抖」：慢看执行计划，抖先看锁等待、刷盘与复制延迟。

**容易说过头的地方**

- 索引不是越多越好：每次写入都要维护二级索引，空间换时间的说法在写多读少时可能倒挂。
- 加缓冲池不等于解决慢 SQL：全表扫描的工作集再怎么缓存也撑不住，先改查询。
- 分库分表是最后手段：它把简单问题变成路由、扩容、跨片事务和一致性问题。
- 「MySQL 参数调优大全」式改动风险高：生产只动被证据指向的参数，并保留回滚方案。

#### 深挖追问

1. **线上说数据库 CPU 打满，你先看什么？**（补充练习）

   先看是不是「少量 SQL 打爆」：`SHOW PROCESSLIST`／`performance_schema` 找当前高消耗语句，取执行计划确认是否全表扫描或排序溢出；确认后再决定是杀语句、加索引还是限流。

2. **加完索引没变快，可能是什么原因？**（补充练习）

   常见四类：优化器按统计信息判断走索引更贵（统计过期或区分度低）、查询条件让索引失效（函数、隐式类型转换、前导通配）、真正的瓶颈在锁等待或 IO 而不是扫描、回表次数过大导致随机 IO 反而更慢。

3. **调优效果怎么汇报成量化结果？**（面经实际出现；[[面经/阳光电源/一面/0001#Q04：实践过程中，有哪些方面可以做数据库调优？|MJ065 · 阳光电源 · 一面 · Q04]]。原素材未记回答，以下为参考）

   给同一口径的前后对比：同一条 SQL、同一数据量、同一缓冲池状态下，记录 P99 延迟、扫描行数（`EXPLAIN` 的 rows 或实际 `rows_examined`）和 CPU 占用；只说「快了很多」等于没说。

### MYSQL-035：MySQL 什么时候会使用内部临时表？

**常见问法**

- [[面经/途虎养车/一面/0001#Q11：MySQL 什么时候会用到内部临时表？|MJ070 · 途虎养车 · 一面 · Q11]]
- EXPLAIN 里的 Using temporary 是什么意思？

#### 面试回答

结论：当排序／分组无法靠索引顺序完成、或要先物化中间结果时，优化器建内部临时表；执行计划 Extra 出现 `Using temporary` 就是信号。

- 高频场景一：`GROUP BY` 与 `ORDER BY` 列集合不一致、分组列没有可用索引——先按分组列在临时表里聚合，再排序输出。
- 高频场景二：`DISTINCT` 加排序、`UNION`（非 ALL）去重、派生表／CTE 物化、窗口函数按分区计算帧。
- 存放位置：先建在内存（MySQL 8 默认 TempTable 引擎），超过阈值转磁盘上的 InnoDB 临时表——不是“内存表放不下就报错过”。
- 验证手段：EXPLAIN ANALYZE 看实际行与临时开销；`Created_tmp_tables` 与 `Created_tmp_disk_tables` 的增量看内存／磁盘比例。

#### 技术细节

**版本差异要报准**

- MySQL 8.0.16 起内部临时表默认改用 TempTable 引擎（此前 MEMORY 引擎不支持 BLOB／TEXT，含大字段查询直接落盘）； spills 到 InnoDB 的行为也随版本有调整，以所用版本文档为准。
- 相关参数：`temptable_max_ram`（TempTable 内存上限，默认约 1G，可超出进程常规内存）、临时表超限后转 InnoDB（受 `internal_tmp_mem_storage_engine` 等控制）。

**“用临时表”不等于“要优化”**

- 小结果集的分组临时表成本很低；只有行数大、落盘、并发高时才值得动。
- 磁盘临时表比例突然上升，先想两件事：有没有新上线的大分组 SQL；有没有字段类型变更（如 group 列变成 TEXT）导致内存路径失效。

**消除手段按优先级**

- 建索引让分组／排序走有序索引（能覆盖更佳）：`Using temporary`／`filesort` 双双消失。
- 改写 SQL：`UNION` 明确改 `UNION ALL`＋业务去重；派生表能下推过滤就先下推。
- 缩结果：少 `SELECT *`、分组前先过滤，别把过滤留给临时表之后。

#### 深挖追问

1. **`GROUP BY a ORDER BY b` 一个联合索引能救吗？**（面经实际出现的延伸；[[面经/途虎养车/一面/0001#Q11：MySQL 什么时候会用到内部临时表？|MJ070 · 途虎养车 · 一面 · Q11]]）

   视条件而定：`WHERE a=?` 之外若按 b 排序，`(a,b)` 顺序扫描可免临时表；a 是范围分组、b 又要排序时通常仍需临时表——先看 EXPLAIN 再定，不背“一定能／一定不能”。

2. **临时表会影响主从复制吗？**（补充练习）

   内部临时表不写 binlog、不参与复制；但会话级 `CREATE TEMPORARY TABLE` 在 ROW 格式下同样不进 binlog，基于语句复制时会有差异（STMT 格式曾要求特殊处理），跨版本口径以文档为准。

### MYSQL-036：MySQL 怎么快速复制一张表（结构＋数据）？

**常见问法**

- [[面经/途虎养车/一面/0001#Q10：MySQL 如何快速复制一张表（结构＋数据）？|MJ070 · 途虎养车 · 一面 · Q10]]
- 想把线上表拷一份到测试库，怎么做？

#### 面试回答

结论：两条常用语法各有缺口——`CREATE TABLE ... LIKE` 完整复制结构但不带数据；`CREATE TABLE ... SELECT` 带数据却丢索引；“结构＋数据”要组合两条语句。

- 推荐组合：`CREATE TABLE t2 LIKE t1;` 再 `INSERT INTO t2 SELECT * FROM t1;`——主键、二级索引、AUTO_INCREMENT、charset 都随 LIKE 保留。
- 陷阱版：`CREATE TABLE t2 AS SELECT * FROM t1` 把列降级为普通列，索引与主键丢失；它走的是快速装载路径，做备份表可以、做同构副本不行。
- 只复制结构：`CREATE TABLE t2 SELECT * FROM t1 WHERE 1=0`（或 LIKE）；跨库／跨实例导结构用 `SHOW CREATE TABLE` 取 DDL 后改名执行。
- 数据量大：低峰执行，或 mysqldump（`--no-create-info` 只导数据）／`SELECT ... INTO OUTFILE`＋`LOAD DATA`，比裸 INSERT SELECT 更可控。

#### 技术细节

**LIKE 复制了什么、没复制什么**

- 复制：列定义、索引、约束、AUTO_INCREMENT 计数器值不复制（新表从初始状态起算）；表空间／加密属性随定义。
- 不复制：外键定义与触发器（官方明确不复制），分区定义会随建表语句带上但外键缺失要自己补。

**INSERT ... SELECT 的并发与锁**

- 源表：InnoDB 会对读到的行加共享锁（配合默认隔离级别时可能范围锁），复制期间写源表可能被阻塞。
- 目标表：非空目标表会拿独占元数据锁；大事务还会撑大 undo／binlog，从库回放延迟跟着上升——大表要么分批要么走离线导出。
- 自增列冲突：目标表 AUTO_INCREMENT 会被插入推进，别假设它从 1 开始。

**“快”的正确打开方式**

- 同实例内最快：LIKE＋INSERT SELECT（无跨网络）。
- 跨实例：mysqldump 单表（加 `--single-transaction` 避免锁表，依赖一致性快照）或 SELECT INTO OUTFILE＋LOAD DATA（注意 secure_file_priv 权限）。
- 只想拿一份查询副本：临时表（`CREATE TEMPORARY TABLE`，会话结束自动清理）够用且不动 schema。

#### 深挖追问

1. **复制大表要不要关 binlog？**（补充练习）

   复制表结构／备份场景不要凭手感关——binlog 是下游订阅与恢复链路的一部分（见 [[#MYSQL-022：MySQL 主从复制的数据同步流程是怎样的？|MYSQL-022：复制链路]]）；真要减量，用 `binlog_format=ROW` 下的行事件压缩或按库表过滤，并和 DBA 确认。

2. **`LIKE` 出来的新表为什么 AUTO_INCREMENT 是 0？**（补充练习）

   官方行为：`CREATE TABLE ... LIKE` 会保留该属性但计数器本身不继承当前值；插数据后从现有最大值继续，不需要“手工对齐”。
