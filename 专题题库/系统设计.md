### SYS-001：如何设计文件存储与下载链路？

**常见问法**

- 项目中的文件下载与文件存储如何落地？

#### 面试回答

先如实说明【文件存在哪里、元数据表、下载鉴权、实际采用的返回方式】。

一种常用设计是：

- 文件内容放对象存储，数据库只存元数据：文件 ID、对象键、所有者、大小、状态。
- 下载时拿文件 ID 查元数据，先校验访问权限。
- 然后返回一个短期签名地址，或者由后端流式转发文件内容。

单机磁盘也能用于简单部署，但多实例要解决共享访问、持久化和备份，不能默认每台机器上都有同一个文件。

#### 技术细节

**上传的写入顺序**

- 先登记“待完成”状态，再写对象存储，最后标记为可用。
- 数据库事务不会自动覆盖对象存储，所以写入失败、孤儿文件、删除重试都要单独处理。

**下载入口的两条约束**

- 不直接接受调用方传入的任意服务器路径。
- 原始文件名只用于展示，对象键独立生成。

**大文件与断点续传**

- 大文件走流式传输，避免一次性读入堆内存。
- 需要断点续传时，先确认存储或中间的代理是否支持 Range 请求。

**预签名 URL 的有效期边界**

- S3 预签名 URL 是一种“有时效的持有者凭据”，谁拿到谁能访问。
- 它的有效期还受签名所用凭据自身有效性的限制。
- 用户失去登录态，不必然使已经发出的 URL 立即失效。
- 需要更严格的实时鉴权时，改用后端代理下载。

#### 深挖追问

1. **文件和元数据写入只成功一边怎么办？**（补充练习）

   用状态机、幂等重试和定期清理来兜住部分成功。只有确认可用的对象才允许被下载。

### SYS-002：优惠券秒杀从低流量升级为高并发时如何整体设计？

**常见问法**

- B 端优惠券秒杀改为高 QPS 的 C 端场景，如何整体改造？

- 秒杀流程怎么改进的，为什么要改为异步实现？

- 服务端同时收到大量请求，怎么处理？

#### 面试回答

我会先明确峰值流量、可售数量、限领规则和响应时限，再用压测定位瓶颈，然后分四层改造：

- 服务器层：无状态扩容、负载均衡、资源监控。
- 代码层：减少同步调用和重复查询，控制线程池、连接池和超时。
- 中间件层：预热活动数据，原子预占库存，用 MQ 削峰，由数据库约束最终扣减。
- 业务层：入口限流、资格校验、防重复领取、排队反馈、售罄后关闭入口。

改造还要和产品、运营确认排队多久、失败如何通知、活动开关怎么控制。验收看成功率、尾延迟和数据正确性。

#### 技术细节

**先画状态流，再按步设准入**

- 流程是：进入活动 → 资格检查 → 预占 → 受理 → 落库发券 → 结果查询。
- 准入按每一步的吞吐容量来设，不是只在最外面限一道流。
- 静态活动页可以缓存或放 CDN（内容分发网络），但核心扣券请求仍需服务端验证。

**容量不能只量一个数**

- 不能只看网关 QPS（每秒请求数）。
- 还要同时量出数据库锁等待、CPU、连接池等待、MQ 最老消息年龄。

**压测与扩容的两处易错**

- 压测要覆盖热点单券、重复点击、超卖校验、依赖故障。
- 扩容应用前先确认下游容量；否则新增实例只会加剧数据库竞争。

   受理成功只表示请求进入了可追踪的处理流程，不等于领到券。发券成功要以事务落库的终态为准，页面用请求 ID 查询结果，避免把还在排队误报成领取完成。

### SYS-003：秒杀中 MQ 如何削峰，消费者如何完成发券？

**常见问法**

- [[面经/美团/一面/0002#Q06：RabbitMQ 发奖，怎么确保奖品会被发放（发奖可靠性）？|MJ032 · 美团 · 一面 · Q06]]
- 消息队列放在秒杀哪个环节，消费者执行哪些业务逻辑？
- RabbitMQ 用在什么业务，消费端如何跨机器幂等？

- 如何使用 Kafka 解决消息的重复消费问题？

- 异步秒杀如何实现的？

#### 面试回答

MQ（消息队列）放在“预占之后、落库之前”。一次请求的走法是：

- 前置：资格校验、幂等检查、库存预占。
- 投递：把任务消息发给 MQ，消息带请求 ID、用户、活动、券批次和数量。
- 消费：消费者校验任务和预占状态，在一个数据库事务里完成幂等判定、条件扣库存、写领取记录和结果状态。
- 确认：事务提交后再确认消息；通知等外部动作另行异步处理。

重复消息直接返回已记录的结果，暂时性失败走重试，永久失败进入可追踪的失败或补偿流程。

#### 技术细节

**幂等靠哪两层约束**

- 请求 ID 上的唯一约束：防止同一任务重复执行。
- “活动＋用户”上的业务唯一约束：落实限领一次。
- 如果活动允许多领，就要换成相应的额度设计。
- 处理状态建议持久化，区分处理中、成功、失败、已释放。

**一个容易写错的幂等实现**

- 并发重复消费时，“先查不存在再插入”保证不了幂等。
- 应依赖唯一约束或条件状态变更，并把失败事务正确回滚。

**RabbitMQ 的两种确认**

- publisher confirm 确认发布侧，consumer ack 确认消费侧；前者不意味着业务完成。
- 自动确认、或者先 ack 再提交事务，都可能导致业务丢失。
- MQ 的具体产品及版本原图未提供，这里以 RabbitMQ 手动确认语义举例。

**通用幂等伪代码**

- 在数据库事务内按稳定的 `message_id` 插入消费记录，唯一约束冲突表示已处理。
- 插入成功后，再执行带业务唯一约束或条件版本的业务变更。
- 事务提交后再 ack。
- 业务事务回滚时，消费记录也应一起回滚。

**幂等 ID 存在哪里**

- 不能只存在单机内存，要放在所有消费者共享的持久化存储里。
- 这样消息由另一台机器重新消费时，仍然能判断出已经处理过。
- 长时间处理可以增加“处理中”状态和租约，但接管时的竞态仍需处理。

#### 深挖追问

1. **消费者收到消息后具体要做什么？**（面经实际出现；[[面经/百度/一面/0002#Q05：消息队列放在秒杀哪个环节，消费者执行哪些业务逻辑？|MJ005 · 百度 · 一面 · Q05]]）

2. **事务已提交但 ack 丢失怎么办？**（补充练习）

   消息会被重投。消费者查询持久化的成功记录，确认消息即可，不再次扣减库存。

3. **用什么存储幂等 ID，其他机器重新消费怎么办？**（面经实际出现；[[面经/字节/一面/0001#Q13：RabbitMQ 用于什么业务，消费端如何实现跨机器幂等？|MJ011 · 字节 · 一面 · Q13]]）

   用消费者共享的持久化数据库表，或与业务状态同事务的唯一键；不能只用进程内集合。其他实例重新消费时会命中相同唯一约束，读取既有终态。

4. **怎么确保奖品一定会被发放（发奖可靠性）？**（面经实际出现；[[面经/美团/一面/0002#Q06：RabbitMQ 发奖，怎么确保奖品会被发放（发奖可靠性）？|MJ032 · 美团 · 一面 · Q06]]）

   按“三段不丢＋一段不重＋对账”答：

   - 生产端：先在同一本地事务里落“待发放”状态再发消息，或用事务 outbox 把消息与业务变更写在一起，并开 publisher confirm。
   - Broker 端：队列与消息持久化，必要时配仲裁队列。
   - 消费端：手动 ack，且**事务提交后才 ack**；失败 nack 有重试上限，超限进死信并告警。
   - 不重复发：靠稳定业务唯一键＋唯一约束或条件状态更新。不能只在单机内存记 ID，消息可能被别的机器重投。
   - 对账：比对“应发”与“实发”，差异自动补发或人工兜底。

   收尾口径是：“至少一次＋幂等＋对账”才是可交付的可靠性。

### SYS-004：Redis 预占与 MySQL 异步扣库存如何实现最终一致？

**常见问法**

- Redis 预扣后异步扣 MySQL，MQ 消费失败如何保证一致性？

#### 面试回答

先说清两边各自代表什么：Redis 里的数值是可预占额度，MySQL 记录最终领取事实，两者允许存在可解释的处理中差额。

- 每次预占都带唯一请求 ID、数量和状态。
- 消费者用本地事务加幂等约束扣库存、写领取记录。
- 短暂失败可以重试；确定无法完成时，才按状态机释放预占。

还要处理三个窗口：预占成功但消息没发出、落库成功但确认丢失导致的重投、补偿与迟到消费的竞争。收敛手段是可恢复的任务记录、终态互斥和定期对账。不能简单地一失败就给 Redis 加一。

#### 技术细节

**一条可选的恢复路径**

- 先写持久化的 PENDING 意图。
- Redis 侧用请求 ID 做幂等预占。
- 预占成功后把意图置为 RESERVED，并在同一个数据库事务里写 outbox，由投递器发送。

**这套方案的代价与边界**

- 写意图会带来数据库开销，要纳入压测。
- 若改用 Redis 里的预占记录和待投递结构，就要明确它的持久化、复制以及故障后的丢失边界。
- 普通数据库 outbox 不会自动让此前那次 Redis 操作变原子。PENDING 的恢复任务仍要按请求 ID 查明状态或重试预占。

**终态互斥**

- 消费者与取消任务在同一行持久化任务上争用条件状态转换。
- 成功发券和取消只能有一个终态。

**取消与回补**

- 取消时先确认已经不可再发券，再执行释放动作回补 Redis。
- 释放动作要可重试、按请求 ID 去重。
- 回补超时时先去查询结果，不能盲目重复加库存。
- 提交结果未知时先查持久化终态，不能把网络超时当成事务失败。

**对账的算法**

- 按已发券、未完成预占、已取消、释放记录四类计算差额。
- 不要拿 MySQL 剩余量直接覆盖 Redis，那会抹去仍在队列中的预占。

#### 深挖追问

1. **MQ 消费失败是否立即回滚 Redis？**（面经实际出现；[[面经/百度/一面/0002#Q07：Redis 预扣后异步扣 MySQL，MQ 消费失败如何保证一致性？|MJ005 · 百度 · 一面 · Q07]]）

   不立即回补。可重试错误保持预占状态；永久失败先完成互斥取消，再做幂等释放。提交是否成功不明确时，先核实终态。

2. **只用重试能保证最终一致吗？**（补充练习）

   不能。还要保证任务可恢复、业务幂等、补偿可重试，并识别出消息未投递、长期失败、持久化丢失这几类缺口。

### SYS-005：秒杀消息积压如何定位与消化？

**常见问法**

- 秒杀高峰消息大量堆积怎么办？
- MQ 积压如何发现并恢复？
- Kafka 消息堆积怎么办？
- 无论是什么 MQ，遇到消息积压一般有哪些处理手段？
- 项目里消息队列的监控怎么做的？（监控侧详见 [[#SYS-049：项目中消息队列的监控怎么做？消息延迟、消息堆积如何监控与处理？|SYS-049：MQ 监控]]）

#### 面试回答

我会按“先看指标、再找瓶颈、两头下手”的顺序处理：

- 先看四个指标：生产速率、消费速率、最老消息等待时间、失败重试比例。
- 再定位瓶颈：消费者 CPU、数据库锁、连接池，还是下游调用。
- 能并行的任务，按活动或库存分片增加消费者，同时调整批量与预取。
- 如果瓶颈是同一库存行被锁住，盲目加消费者反而更慢。
- 另一头压入口：限流，按业务承诺控制最长排队时间。
- 隔离反复失败的消息，给已受理用户展示处理状态。

#### 技术细节

**清空时间的估算**

- 记当前积压为 B，持续进入速率为 λ，可稳定处理速率为 μ。
- μ 大于 λ 时，理想清空时间约为 B／(μ−λ)。
- μ 不大于 λ 时只能降入口速率，或提高实际处理能力。

**积压要拆成三类看**

- 未投递积压、已投递未确认、反复重试，三类的处置动作不同。
- 只看一个队列长度指标分不清是哪一类。

**预取（prefetch）怎么调**

- 预取太大会让慢消费者占住大量任务，太小可能吞吐不足。
- RabbitMQ 的 prefetch 要结合确认模式和消费者数量来配置。

**两条别做的事**

- 不能直接删除过期业务消息而不结算它的预占。
- 迁移队列、增加分片、放宽顺序要求时，都要保留请求 ID 和终态约束。

#### 深挖追问

1. **增加消费者为什么可能无效？**（补充练习）

   因为瓶颈不在消费者数量上。若是单行库存写锁、数据库 I/O 或下游限额，加消费者只会增加等待；应先缩短事务，或拆分受控库存额度。

2. **如何发现积压？**（面经实际出现；[[面经/字节/一面/0001#Q14：如何发现并恢复 MQ 消息积压？|MJ011 · 字节 · 一面 · Q14]]）

   对这几项告警：ready、unacked、最老消息年龄、生产／消费速率、重投失败率，并与消费者及下游资源指标关联。单看队列长度无法区分慢消费和未确认。

3. **“一条数据的增删改拆成三个队列消费，顺序会乱怎么办”？**（面经实际出现；[[面经/收钱吧/二面/0001#Q11：增删改各建一个队列让 ES 消费，如何保证消费顺序与执行顺序一致？|MJ069 · 收钱吧 · 二面 · Q11]]）

   按操作类型拆队列从方向上就错了：顺序需求只存在于同一实体内部。改成按实体键路由同一队列＋单消费者串行，再带单调版本号拒绝旧变更——完整口径见 [[#SYS-055：项目中用 RabbitMQ 给 ES 和 MySQL 做数据同步怎么实现？拆队列后顺序不一致怎么办？|SYS-055：按实体路由保序]]。

### SYS-006：Redis 不可用时秒杀如何降级且避免超卖？

**常见问法**

- Redis 宕机时如何降级并继续校验库存？

#### 面试回答

一句话：先止血，再按数据库实测容量决定是否保留小流量领取。

- 入口：先做熔断和强限流。
- 领取：在 MySQL 里用带库存下限条件的 UPDATE 加唯一领取约束，在一个事务内完成扣减及发券。
- 超出容量的部分：返回稍后重试，或暂停活动。
- 存量：切换前还要处理已有的 Redis 预占和 MQ 在途任务。要么停止旧路径新增并完成结算，要么给降级路径划定独立且不重叠的库存额度。

两个不能：不能把全部流量直接压到数据库，也不能靠各实例本地缓存各扣各的库存。

#### 技术细节

**为什么只靠数据库条件扣减还不够**

- 最终的条件扣减确实能守住不超卖。
- 但若忽略在途预占，新请求可能抢走已受理任务的额度。
- 因此降级时还要定义清楚对用户的排队承诺。

**旧预占状态查不到时**

- 可以暂停新领取，继续消费持久化任务并对账。
- 若必须两条路径并行，就用预先分配且总和受约束的配额，并明确归属与回收协议。

**切回 Redis 的顺序**

- 先重建未完成的预占和可售额度，再放开入口。
- 切换要有统一的活动模式或版本控制，避免旧实例继续走过时路径。

**展示与扣减分开**

- 页面库存可以暂时展示缓存值。
- 真正的领取必须经过权威扣减。

1. **还能用什么组件做库存校验？**（面经实际出现；[[面经/百度/一面/0002#Q09：Redis 宕机时如何降级并继续校验库存？|MJ005 · 百度 · 一面 · Q09]]）

   - MySQL 条件更新可以承担小流量的权威扣减。
   - 可靠队列可以承载排队，预分配的非重叠令牌也可以限额。
   - 但队列和本地计数本身不会自动保证全局库存正确。

### SYS-007：分片上传与断点续传如何设计？

**常见问法**

- 项目如何实现分片上传与断点续传？
- 有一批约 1G 的数据，怎么快速上传到对象存储？上传过程要考虑哪些点？具体怎么分片？数据都是二进制的，怎么按关键字算哈希分片？
- 假设每次都能上传成功，瓶颈会在哪里？网络问题包括哪些因素？怎么克服？

#### 面试回答

服务端先创建上传会话，绑定用户、文件大小与分片规则，之后三步走：

- 客户端按分片编号上传，服务端记录哪些分片已确认。
- 恢复时查询已完成编号，只补缺失的片。
- 最后校验完整性，完成合并或提交。

项目真实协议与存储未知，以下是通用方案。

#### 技术细节

**分片的标识与重传**

- uploadId 加分片号唯一标识一个分片。
- 重传同一内容应当幂等。
- 内容冲突时要拒绝，或事先明确替换规则。

**对象存储分片的具体切法**

- 按字节偏移定长切：第 i 片＝[i×size, (i+1)×size)，不需要任何内容语义边界。
- 片大小受平台约束（S3／COS 类：单片最小 5MB、最多 10000 片）；1G 取 10～100MB 一片是常见档位。
- 每片返回独立校验值（如分片 ETag），Complete 时提交片号＋校验清单；顺序由片号决定，并发乱序上传也能正确组装。

**“按关键字哈希分片”要先纠偏**

- 这是把两种“分片”混在一起了：文件分片（大对象切块上传）按偏移切，不存在路由问题；数据路由（这个对象放哪个节点／分表）才谈哈希。
- 路由输入不需要“提取关键字”：二进制直接对整片内容算摘要（MD5／SHA-256，content hash 用于去重与完整性），或用业务侧对象名／ID 作路由键——哈希函数的输入本来就可以是任意字节序列。
- 只有日志类固定结构数据才会“取某字段做 partition key”，与对象存储上传无关；面试遇到这问，先澄清口径再答。

**完成时的校验**

- 检查分片数量、长度与摘要。
- 用原子操作标记文件可用，防止并发重复合并。

**会话的安全边界**

- 上传会话要鉴权，并清理过期的临时块。
- 文件摘要帮助验证完整性，但不代替访问授权。

#### 深挖追问

1. **分片传完但完成响应丢了怎么办？**（补充练习）

   先查询上传状态，再用幂等的完成接口重试。不要无条件重建整个文件。

2. **假设每片都能传成功，瓶颈在哪？网络侧要看哪些因素？**（面经实际出现；[[面经/腾讯/一面/0001#Q08：假设每次都上传成功，瓶颈在哪？网络问题包括哪些因素？怎么克服硬件和网络问题？|MJ046 · 腾讯 · 一面 · Q08]]）

   按“上限→通道→两端”排序：

   - 上限：客户端上行带宽——所有并发加起来也超不过这条物理管道。
   - 通道：单条 TCP 连接吞吐受带宽时延积约束（窗口×MSS÷RTT），高 RTT 下一条连接远吃不满带宽，所以要多连接并发；丢包与抖动通过重传和拥塞窗口收缩间接压吞吐（见 NET-006／NET-017）。
   - 两端：本地磁盘顺序读、TLS 加解密 CPU、对象存储的接收与合并开销、服务端限流。
   - 克服：并发分片打满带宽；断点续传＋片级幂等重试兜住丢包与抖动；就近接入点／传输加速降 RTT；有 CPU 余量时压缩上传换带宽。

### SYS-008：如何解释 QPS、延迟水位并设计可信压测？

**常见问法**

- 5000 QPS 怎么来的，会不会全命中缓存？
- 压测观测哪些指标，如何体现多级架构？
- 响应时间 20 ms 是 P50、P90 还是 P99？
- 系统并发量和用户量是多少？

#### 面试回答

一句话：QPS 和响应时间都不能单独报，必须绑定上下文。

- 上下文包括：测试环境、请求模型、数据规模、并发、持续时间、成功率、延迟分位数。
- 5000 QPS 要说明是峰值还是稳定吞吐、单实例还是集群、客户端是否已经成为瓶颈。
- 20 ms 也要说明是客户端端到端的 P50、P95 还是 P99。平均值或 P50 代表不了尾延迟。

我的做法是先以接近生产的流量配比建立基线，再逐步加压到延迟或错误率达到验收边界，而不是只报工具显示的最大数字。

#### 技术细节

**场景要拆开压**

缓存系统至少拆分出这几类场景，并记录每层的命中率与请求数：

- 全命中本地缓存、命中 Redis、回源数据库。
- 冷热混合、热点 key、依赖故障。

**怎么证明多级架构有贡献**

- 做对照：关闭 L1（本地缓存）、关闭 L2（Redis），或者调整命中率。
- 比较吞吐、P95／P99、数据库回源量和资源消耗。
- 预热结果与冷启动结果分别报告，避免全命中的最短路径掩盖系统能力。

**观测面清单**

- 压测端：实际发送量、成功率、超时、延迟分布。
- 网关／负载均衡：排队、连接。
- 应用：CPU、内存、GC、线程池／事件循环、连接池。
- 本地缓存：命中、逐出。
- Redis：延迟、命中、连接、热点。
- 数据库：QPS、连接、锁等待、慢查询、I/O。
- MQ、网络与下游错误。

**两个容易漏掉的口径**

- 压测端与服务端的时钟、采样窗口和请求 ID 需要可对齐。
- 开放与闭合负载模型语义不同：高延迟下固定并发可能自动降低请求率，要说明用的哪种工具模型。

#### 深挖追问

1. **如果 5000 QPS 全命中本地缓存，结果还有意义吗？**（面经实际出现；[[面经/字节/一面/0001#Q09：5000 QPS 如何测得，怎样证明多级缓存架构有效？|MJ011 · 字节 · 一面 · Q09]]）

   只有限定意义：它只说明该命中路径的上限，不能代表混合流量或回源能力。需要报告分层命中，并补充对照场景。

2. **20 ms 应报哪个水位？**（面经实际出现；[[面经/字节/一面/0001#Q12：接口响应时间 20 ms 对应哪个延迟水位？|MJ011 · 字节 · 一面 · Q12]]）

   同时报告 P50、P95／P99 和成功率，并注明统计窗口与测量位置。单个平均数不足以描述性能。

### SYS-009：多级缓存如何保持一致，并在 Redis 故障时降级？

**常见问法**

- [[面经/美团/一面/0002#Q04：MySQL 和 Redis 数据一致性怎么保证？出现短暂不一致怎么考虑？|MJ032 · 美团 · 一面 · Q04]]
- 本地缓存如何保证一致，不同机器之间如何同步？
- Redis 挂了本地缓存能撑多久，系统如何降级？
- 如何保证 Redis 与数据库的数据一致性？

- 如何保证 Redis 和 MySQL 的数据一致性？
- 有没有更好的方案保证数据一致性？

- 项目里 Redis 主要用来干嘛？缓存策略是怎样的？
- 为什么设计成先更新 Redis 再更新 Caffeine？这种更新策略会有一致性问题吗？
- 介绍一下项目中多级缓存的设计流程。

#### 面试回答

先和业务定义清楚“一致性”和可接受的陈旧时间，再选方案。读多写少的常见做法是以数据库为事实源：

- 写事务提交后，删除或更新 Redis。
- 再通过消息或数据库变更日志，向各实例广播本地缓存失效。
- 本地缓存项用较短 TTL（过期时间）加版本号兜底。

两点要注意：不同实例不能靠各自的 TTL 保证“同时一致”；失效消息的消费要幂等、可重试，并监控延迟和失败。强一致的读写应绕过本地缓存，或走一条真能提供所需一致性的数据路径。

#### 技术细节

**两个动作之间的故障窗口**

- 更新数据库和删除缓存是两步，中间存在故障窗口。
- cache-aside 的常见写法：先提交数据库，再删除缓存。
- 如果反过来先删缓存：随后并发读可能回填旧值，而数据库最后才更新完，旧缓存就会继续存在。
- 先更新数据库也仍可能删缓存失败，这时用事务 outbox、数据库变更日志／CDC（变更数据捕获）、可靠重试和定期校准来驱动失效。
- 不要在数据库回滚之前，提前发布不可撤回的更新事件。

**仍然存在的竞态**

- 并发读写仍可能让旧值回填，处理手段是 key 版本、短 TTL、条件写或延迟二次失效，按业务容忍度选复杂度。
- 延迟双删只能缩小部分竞态窗口：延迟时长难以普适确定，也不能替代失败重试与监控。

**失效消息与热点重建**

- 缓存事件携带实体 ID 和版本，实例只接受不旧于当前版本的变更。
- 热点重建用请求合并和限流，避免每台机器同时回源。

**Redis 故障时的降级**

- 先快速熔断，而不是让线程堆积。
- 允许陈旧的读：在明确的 stale 上限内使用 L1。
- L1 未命中：按数据库实测容量限流回源，必要时返回稍后重试。
- 关键写或强一致查询：选择失败、排队，或切至预先验证过的备用系统。

**L1 能撑多久**

- 取决于 TTL、预热覆盖、逐出、内存及数据变更频率，没有固定答案。

**恢复时**

- 限速回填，观察回源量、旧值年龄和错误率，避免流量瞬间冲击 Redis 或数据库。

#### 深挖追问

1. **如何保证所有机器同时删除本地缓存？**（面经实际出现；[[面经/字节/一面/0001#Q10：本地缓存及多机器之间如何保证数据一致性？|MJ011 · 字节 · 一面 · Q10]]）

   做不到物理上同时删。实际是靠可重试的失效事件、版本和 TTL 实现有界最终一致。需要强一致时，不要从各实例的 L1 直接读。

2. **Redis 挂了，本地缓存能撑多久？**（面经实际出现；[[面经/字节/一面/0001#Q11：Redis 故障后本地缓存能支撑多久，系统如何降级？|MJ011 · 字节 · 一面 · Q11]]）

   不给固定时间。它由数据可陈旧窗口、覆盖率、TTL 与容量决定，应该通过故障演练测出来，而不是给一个脱离系统参数的数字。

3. **删除缓存、延迟双删和消息补偿分别解决什么？**（面经实际出现；[[面经/字节/一面/0002#Q02：如何保证 Redis 与数据库的数据一致性？|MJ012 · 字节 · 一面 · Q02]]）

   三件事各管一段：

   - 数据库提交后删除缓存：让后续读取重建。
   - 延迟二次删除：尝试清除竞态期间回填的旧值，但它不是严格的一致性证明。
   - outbox／CDC 或可靠消息重试：补上“数据库已提交但失效未完成”的故障窗口。

   三者仍要结合幂等、监控、TTL 和业务一致性要求来选。

4. **出现短暂不一致，业务上怎么考虑？**（面经实际出现；[[面经/美团/一面/0002#Q04：MySQL 和 Redis 数据一致性怎么保证？出现短暂不一致怎么考虑？|MJ032 · 美团 · 一面 · Q04]]）

   先按数据分类，而不是先选技术：

   - 只影响展示的值（活动文案、商品详情）：允许有界陈旧，把 TTL 设成业务可容忍的最大陈旧时间即可。
   - 涉及资损的判断（库存是否够、是否已领取）：不能以缓存为准，必须回到 DB 的条件更新或唯一约束，缓存只做前置过滤。

   再给收敛手段：写后关键读走主库或直接读库、缓存带版本号、延迟二次删除、失败重试与定时对账。

   最后配监控：缓存与库的差异率、失效失败数、陈旧时间分布。这样“窗口有多长”是一个可观测的数字，而不是估计。

5. **先更新 Redis、后更新本地 Caffeine，这个写序会有一致性问题吗？**（面经实际出现；[[面经/腾讯/一面/0001#Q04：项目里 Redis 用来干嘛、怎么缓存？为什么先更新 Redis 再更新 Caffeine？会有一致性问题吗？|MJ046 · 腾讯 · 一面 · Q04]]）

   会——两层写入不可能原子，中间窗口内本实例可能读旧本地值、其他实例可能读旧 Redis 值。答写序前先立这个原则：正确性不能押在顺序上。

   - 先 Redis 后本地的合理性：Redis 是共享层（影响所有实例），先把它推新，不一致面最大的一段先收敛；本地层只影响本进程，且天然有短 TTL 兜底，甚至可以“不主动更新、只失效”。
   - 更稳的姿势：DB 事务提交→更新／删除 Redis→对自己和其他实例的本地缓存发失效通知（按版本号消费），本地“更新”不如“失效让读路径重建”，避免半写状态。
   - 若失效通知失败：短 TTL 封顶陈旧窗口＋对账修复；强一致要求的读写直接绕过缓存层。
   - 收尾一句：多级缓存买到的是性能，付出的是“有界不一致”，参数（TTL／版本）就是那个“界”。

### SYS-010：如何保证数据库写入与消息发送的一致性？

**常见问法**

- 业务要求生产者写数据和发消息都必须成功，怎么处理？

#### 面试回答

一句话：普通数据库事务不能原子覆盖 RabbitMQ 的发布，所以用 transactional outbox（事务发件箱）。

- 在同一个本地事务中写业务数据与 outbox 消息。
- 事务成功后由投递器持续发送，收到 publisher confirm 后标记已发送。
- 投递器崩溃或确认丢失会导致重发，因此消息要用稳定的业务 ID，消费者必须幂等。

它保证的是“最终把已提交业务对应的消息发出”，不是跨数据库和 broker 的瞬时强原子提交。

#### 技术细节

**outbox 表至少要存什么**

- messageId、聚合／业务 ID、类型、payload 或引用、状态、重试次数、下次时间。

**投递器为什么会重复发**

- 用认领状态或跳锁可以避免重复并发处理，但超时恢复仍会重复发送。
- 根本原因是：确认标记与发送无法组成同一个原子动作。
- 所以去重落到消费者侧，通过唯一约束或条件状态更新完成。

**publisher confirm 的语义边界**

- 它只确认发布端到 RabbitMQ 及相应队列侧的接收语义，不表示消费者业务已完成。
- 不可路由消息还需结合 mandatory／return 等机制处理。

**请求是否要等 broker**

- 如果必须等 broker 接收后才返回，可以在业务提交后同步等待投递确认。
- 确认失败时数据库事实已经存在：应返回处理中或失败可查询的状态，由后台继续重试或按业务补偿，不能假装已回滚数据库。

**想要严格的“都成功或都失败”**

- 需要先明确故障模型。二阶段提交往往带来可用性和性能代价。
- 而且 RabbitMQ 的确认机制并不等于通用 XA。
- 业务常用组合是：本地原子写入＋最终投递＋幂等消费，由此取得可恢复的一致性。

#### 深挖追问

1. **publisher confirm 成功是否表示消费完成？**（补充练习）

   不是。发布确认与消费确认彼此独立，业务完成要由消费者状态或响应另行确认。

2. **消息会不会重复？**（补充练习）

   会。发送成功但确认丢失、消费者处理成功但 ack 丢失，这两种情况都可能重投。因此生产端的稳定消息 ID 和消费端的幂等都不可以省略。

### SYS-011：什么时候需要分片查询，如何定位与优化查询瓶颈？

**常见问法**

- 为什么要使用分片查询？如果不用分片查询，系统查询的瓶颈在哪里？如何优化？

#### 面试回答

分片是把超过单节点容量或吞吐上限的数据与访问压力分散到多个节点，它不是所有慢查询的默认解法。

- 先定位：看查询计划、慢查询，以及 CPU／I/O／内存／缓存指标。
- 判断瓶颈属于哪一类：全扫描、索引不匹配、排序聚合、锁竞争、热点，还是硬件容量问题。
- 先做单节点优化：索引、查询改写、分区裁剪、限制返回量、缓存、读扩展。
- 单节点仍然无法承载时，再分片。

#### 技术细节

**分片键怎么选**

- 要同时考虑五点：分布是否均匀、高频查询能否定位到单片、写入热点、数据共置、后续扩容。

**散射查询的代价**

- 命中分片键时，路由层可以直接访问目标片。
- 缺少分片键的查询可能散射到所有片，再对结果排序或聚合。
- 这时尾延迟受最慢分片影响；深分页会让每个片都取出大量候选数据。
- 改法：尽量改成携带分片条件的查询，使用游标分页、预聚合／派生索引，并限制扇出数。

**分片引入的成本**

- 跨片事务、全局唯一性、联表、再平衡、故障放大。
- 热点分片不会因为“总片数更多”就自动解决；需要调整键设计、拆热点、缓存或限流。

原面经未指定数据库或搜索引擎，这里仅给出通用分片思路，产品具体路由与一致性语义待补充。

#### 深挖追问

1. **分片数越多查询越快吗？**（补充练习）

   不一定。单片查询确实可以靠扩容变快，但散射查询的网络开销、结果合并和尾延迟往往随扇出增大而变差。

2. **怎么判断分片键选得好不好？**（补充练习）

   看这几项指标：数据量和 QPS 的分片偏斜、单片命中率、跨片查询比例、热点，以及扩容时的迁移代价。

### SYS-012：服务器宕机如何发现与恢复，Agent 宕机有何不同？

**常见问法**

- 服务器宕机了怎么办、怎么恢复？

- Agent 服务的高可用、稳健性是怎么保证的？

#### 面试回答

先区分宕机的对象：进程崩溃、机器故障，还是可用区／网络整体不可用。

- 发现靠多层探活：进程健康检查、负载均衡摘除不健康实例、分布式共识与副本状态监控，再配合告警。
- 恢复目标是两件事：把流量切到健康副本，并让故障节点上的状态可接续。
- 为此应用尽量无状态，会话与任务状态放共享存储，数据靠副本保障。
- 故障后由编排系统自动重建或切换实例，之后再验证下游容量。

Agent 项目还要说明任务级恢复，见 [[专题题库/Agent开发#AGENT-014：Agent 工作流故障如何定位和恢复？|AGENT-014：Agent 工作流故障如何定位和恢复？]]。实际平台与演练情况按【真实部署】补充。

#### 技术细节

**Kubernetes 的三种探针（滚动文档 2026-09-19 查证）**

- 以 Kubernetes 为例：livenessProbe 失败重启容器，readinessProbe 失败仅摘除流量，startupProbe 保护慢启动进程。
- 节点失联后，控制器在超时后把 Pod 调度到其他节点。
- 注意这提供的是“重新拉起”，不是自动恢复应用内部状态。状态必须由外部持久化与副本机制承载。

**数据层的恢复**

- 数据库侧靠主从复制与故障转移，Redis 同样以副本和高可用机制缩短恢复时间。
- 异步复制故障切换可能丢最后写入，需按业务容忍度选复制策略。
- 持久化边界见 [[专题题库/Redis#REDIS-003：Redis 有哪些持久化方式，RDB 和 AOF 有什么区别？|REDIS-003：Redis 有哪些持久化方式，RDB 和 AOF 有什么区别？]]。

**恢复流程里容易漏的三件事**

- 锁与租约要超时释放。
- 消息会重投，消费要幂等。
- 缓存要冷启动预热，防止切换瞬间雪崩。

故障演练才能真正验证这些假设。

**Agent 宕机的额外边界**

- 模型或工具调用可能已产生副作用，但响应丢失，不能默认重跑安全。
- 恢复要从已验证的检查点继续，并按任务 ID 核对实际状态。

#### 深挖追问

1. **宕机后正在执行的任务怎么办？**（面经实际出现；[[面经/字节/一面/0004#Q04：服务器宕机了怎么办、怎么恢复，Agent 宕机了怎么办？|MJ014 · 字节 · 一面 · Q04]]）

   取决于任务状态是否外置。

   - 有持久化队列／任务表＋租约超时：其他实例可以认领续跑。
   - 只存在进程内存：任务会丢失。

   所以长任务要分段保存检查点，恢复时先查副作用，再决定重试还是继续。

2. **健康检查失败一定要重启进程吗？**（补充练习）

   不一定。先区分就绪与存活的语义：依赖抖动适合摘流量＋退避重试，进程死锁或不可恢复错误才重启。全部重启还可能放大故障。

### SYS-013：接口幂等性如何设计，重复提交订单怎么处理？

**常见问法**

- 有没有做幂等性设计？比如用户连续点击两个提交订单，怎么做？

- 服务端同时收到大量请求，如何保证请求幂等性？

#### 面试回答

用户连点两次提交、客户端超时重试、MQ 重投，都可能造成重复下单。通用组合是四层：

- 一次性 token：提交前先申请，Redis 存、提交时原子核销。拿不到或核销失败即重复请求，直接返回首次结果。
- 数据层业务唯一键兜底：用户＋活动、请求号的唯一索引。重复插入命中约束后，查询并返回已有订单。
- 状态机条件更新：只有处于前置状态时才允许流转。
- 强冲突场景用分布式锁，把同一业务键的请求串行化。

前端按钮置灰与内存标记只能优化体验，不是正确性保证。

#### 技术细节

**幂等标识从哪来**

- 要来自稳定的业务语义（请求号、订单号），不能是随机生成的新值。
- 去重记录与业务写入必须在同一个数据库事务里，或者放在共享的持久化存储中。
- 单机内存 Map 在多实例下会失效。

**核销怎么做到原子**

- token 核销用 Redis Lua／`GETDEL`，或用数据库唯一键消费来保证原子。

**重复请求返回什么**

- 响应应与首次一致：返回已创建的订单，而不是报错。
- 顺序是先查已有结果，再决定动作。
- 并发两请求同时到达时，唯一索引是最后防线：捕获重复键冲突后回查返回。

**两种“重复”要分清**

- “相同请求重试”和“不同请求恰好参数相同”不是一回事。
- 后者可能需要显式带 requestId。

#### 深挖追问

1. **为什么唯一索引还不够，要再加 token？**（补充练习）

   因为唯一约束兜的是正确性，兜不了代价：冲突如果发生在扣减或外部调用之后，代价已经产生。token 在入口处提前拦截，减少无效竞争与副作用。

### SYS-014：MQ 消息发送延迟或失败如何优化与补偿？

**常见问法**

- 如果 MQ 因为网络等原因发送消息延迟，如何优化？
- MQ 发送消息失败，是回滚还是重试？
- MQ 中的脏数据怎么处理？

- 消息队列发送消息失败怎么处理，有没有脏数据存留，怎么处理？

#### 面试回答

分两件事说：延迟怎么优化，失败是回滚还是重试。

延迟先定位环节：

- 建连开销：用长连接与连接池消除。
- 往返多：改异步发送＋回调，并聚合批量。
- 网络抖动：设超时＋按幂等键做有限重试。
- 实时性仍不满足就换路径：本地消息表／outbox 先落库、后台补发；或小流量场景直接同步写库绕过 MQ。

失败是回滚还是重试，看业务语义：

- 通知类消息：失败不应回滚已提交的业务，落库后补偿重试。
- 消息本身是业务生效前提（扣款指令）：同步确认，失败即回滚。

一条原则：不能让“发送结果未知”被简单当作失败或成功。

#### 技术细节

**发送超时属于结果未知**

- 超时不代表消息没到达 broker，它可能已经送达。
- 重试必须携带同一个幂等标识，由消费端去重。
- 通用做法见 [[专题题库/系统设计#SYS-010：如何保证数据库写入与消息发送的一致性？|SYS-010：如何保证数据库写入与消息发送的一致性？]]。

**脏数据先分口径**

- 过期或已取消的业务数据：消息带版本号／时间戳，消费时与当前状态比较后丢弃并留痕。
- 格式坏的消息：进死信队列人工排查，不无限重试。
- 重复消息：靠幂等消费解决。

**补偿任务自己的护栏**

- 要有速率限制与最大重试次数，超限进失败流程。
- 否则系统恢复时，补偿本身会形成洪峰造成二次冲击。

#### 深挖追问

1. **异步发送丢了消息谁负责？**（补充练习）

   靠回调确认＋本地持久化兜底。只有在收到 broker 确认后才标记完成；进程崩溃前未确认的消息，由启动扫描补发。

### SYS-015：数据库故障无法写入时如何降级与恢复？

**常见问法**

- 如果数据库故障导致无法写入，怎么处理？

#### 面试回答

先快速发现（连接超时、写失败率告警），交给高可用机制切换主库。切换窗口内按业务分级降级：

- 读请求：走缓存或只读副本。
- 资金等强一致业务的写请求：直接失败返回稍后重试，绝不本地记账假装成功。
- 允许短暂缓冲的业务：把请求写入本地消息表／持久队列，恢复后按幂等补偿落库。
- 纯增值操作（日志、统计）：可以丢弃或延后。

恢复后先限速回放积压，再对账核对缓冲与最终数据。“最多丢什么”要事先与业务约定。

#### 技术细节

**应用侧要点**

- 连接池要快速失败并熔断，避免线程堆积放大故障。
- 写请求携带幂等键，补偿时才能安全重放。
- 缓冲存储如果与应用同机，进程损坏仍会丢。重要业务的缓冲要独立持久化，比如另一存储介质或消息服务。

**主从切换的坑**

- 主从异步复制切换可能丢最后写入。
- 切换后需以新主为准对账，不能双写旧主。

**与缓存故障降级的区别**

- 缓存降级见 [[专题题库/系统设计#SYS-006：Redis 不可用时秒杀如何降级且避免超卖？|SYS-006：Redis 不可用时秒杀如何降级且避免超卖？]]。
- 数据库是事实源，所以降级空间更小。
- 多数方案本质是“把同步写改成可恢复的延迟写”，正确性依赖幂等与对账。

最后，切换、缓冲与回放链路要靠故障演练验证，纸面方案不可信。

#### 深挖追问

1. **为什么不直接切从库继续写？**（补充练习）

   不能。从库通常只读，而且存在复制延迟与拓扑不确定的问题。写必须落到唯一事实源，正确做法是提升新主，再处理未复制事务的差异。

### SYS-016：Kafka 如何做到不丢消息与不重复消费？

**常见问法**

- 如何使用 Kafka 解决消息丢失问题？
- Kafka 发送消息时因网络问题出现消息丢失，如何解决？
- 如何使用 Kafka 解决消息的重复消费问题？

#### 面试回答

丢失按三段链路各自加固：

- 生产端：`acks=all`（等待 ISR 全部确认）＋`retries`＋`enable.idempotence=true`。重试按 pid＋sequence 去重，不产生重复。
- broker 端：`replication.factor≥3`、`min.insync.replicas≥2`、关闭 `unclean.leader.election.enable`。宁可拒绝写入，也不让落后副本上位丢数据。
- 消费端：关闭自动提交，业务处理成功后再手动提交 offset。

重复消费无法根除：重试、rebalance 时的双消费者、提交失败都会重放。正确姿势是接受 at-least-once，用稳定业务键在共享持久化存储做消费幂等（唯一约束／条件状态更新）。确实要求处理与提交原子时，再用事务性消费（read_committed）。

#### 技术细节

**网络原因的“发送丢失”多是结果未知**

- 超时不代表 broker 未写入。
- 重试必须由幂等生产者兜底。
- `delivery.timeout.ms` 之内，客户端会自动处理 leader 切换与可重试错误。
- 时间耗尽后，回调里要落库或进补偿队列，不能只记日志。

**幂等生产者的覆盖范围**

- 只保证单分区、单会话内去重，跨会话与换 topic 不覆盖。
- 开启幂等要求 `acks=all`。

**持久化真正依赖什么**

- Kafka 持久化靠多副本＋OS 页缓存异步刷盘。
- 单 broker 掉电靠副本兜底，不要指望把 `flush.messages` 调成同步来换性能。

**缓解 rebalance 引发的重复**

- 设置合理的 `max.poll.interval.ms`。
- 尽快提交。
- 用静态成员或独立消费者架构。

通用原理（outbox、脏数据、回滚还是重试）见 [[专题题库/系统设计#SYS-014：MQ 消息发送延迟或失败如何优化与补偿？|SYS-014：MQ 消息发送延迟或失败如何优化与补偿？]]，参数以所用 Kafka 版本文档为准。

#### 深挖追问

1. **acks=all 和 min.insync.replicas 是什么关系？**（补充练习）

   两者要组合才有效。

   - `acks=all` 是“等 ISR 全部确认”的请求语义，实际等待几个副本由 ISR 大小决定。
   - `min.insync.replicas` 规定 ISR 小于该值时直接拒写。
   - 合起来才构成“至少两副本落盘”的保证。

### SYS-017：秒杀如何防止超卖，为什么用 Redis＋Lua 而不是加锁？

**常见问法**

- 项目如何实现防止超卖？为什么用 Redis 和 Lua 脚本，而不用锁？

#### 面试回答

底线是一句话：“检查余量＋扣减”必须原子执行，且以权威数据为准。常见做两层：

- Redis 层：预热库存，扣减用 Lua 脚本一次执行判断与 DECR。Redis 顺序执行脚本，天然原子，返回成功才继续下单。
- 数据库最终防线：条件 UPDATE（`SET stock=stock-n WHERE stock>=n`），按影响行数判断。

为什么不用锁：

- 秒杀是单个热点 key 的高并发写。悲观锁把请求排队串行化，吞吐受持锁时长限制；锁的获取和释放本身还要处理过期、续期与误删。
- 乐观锁用版本号，高冲突下会出现重试风暴。
- 而“判断＋扣减”可以下推成一条原子操作，Lua 没有等待、路径最短。

代价与边界：Redis 里的是预占额度，不是事实源。宕机恢复、少发超发都要靠持久化、对账与数据库条件更新兜底（见 [[专题题库/系统设计#SYS-004：Redis 预占与 MySQL 异步扣库存如何实现最终一致？|SYS-004：Redis 预占与 MySQL 异步扣库存如何实现最终一致？]]）。

#### 技术细节

**Lua 脚本与 key 设计**

- 脚本要短小、无阻塞 IO，避免拖慢 Redis 单线程。
- 库存 key 设计带活动与批次维度。
- 加售罄标记提前拦截，减少无谓扣减。

**为什么还要把判断前移到 Redis**

- 数据库条件更新即使不用 Redis，也能守住不超卖。
- 但热点行锁排队会限制吞吐，所以高并发场景才把判断前移。

**锁并非不能用**

- 正确性上，Redisson 锁＋双重检查也成立。
- 但为了同一个目标引入锁的生命周期管理（TTL、续期、重入、解锁原子性），成本更高、吞吐更差。
- 这是“能下推为原子原语的逻辑不要拿锁串行化”的典型例子。

相关路径：Redis 故障降级见 [[专题题库/系统设计#SYS-006：Redis 不可用时秒杀如何降级且避免超卖？|SYS-006：Redis 不可用时秒杀如何降级且避免超卖？]]，行锁优化见 [[专题题库/MySQL#MYSQL-007：如何优化秒杀库存更新与热点行锁竞争？|MYSQL-007：如何优化秒杀库存更新与热点行锁竞争？]]。

#### 深挖追问

1. **Lua 扣减成功但后续下单失败，库存怎么回来？**（补充练习）

   按请求号做幂等释放。取消流程确认后回补 Redis 额度，回补本身可重试且不会重复加。不能一失败就立刻盲目 INCR。

### SYS-018：HTTP 接口如何从业务层兜底请求丢失与重试？

**常见问法**

- 使用 HTTP 设计接口时，针对可能出现的请求丢失问题，怎么从业务层设计优化？

- 接口超时如何处理？

#### 面试回答

不改协议与中间件，从业务设计兜住三类情况：请求可能没到、到了但响应没回、重试造成放大。五个抓手：

- 幂等性：写接口要求客户端生成 requestId／业务唯一键，服务端持久化去重并缓存首次结果。超时重发不会产生第二次副作用。
- 状态性：长操作拆成“受理＋查询”。先落受理记录并返回受理号（202），客户端轮询或推送拿终态；响应丢失也能凭受理号恢复认知。
- 重试策略：只有幂等接口才自动重试，用指数退避＋次数上限。非幂等的失败引导客户端“先查询确认再决定”。
- 限流与背压：入口和下游分设限额与有界队列。过载时返回明确的可重试错误码与 Retry-After，而不是拖死依赖。
- 对账兜底：与异步任务、外部回执定期核对，识别“客户端以为丢了但服务端已执行”的差异，并按业务补偿。

#### 技术细节

**先把“超时”这件事说对**

- HTTP 超时是“结果未知”，不是“失败”：请求可能已被完整执行。
- 因此幂等键要贯穿到消息与落库层（与 [[专题题库/系统设计#SYS-013：接口幂等性如何设计，重复提交订单怎么处理？|SYS-013：接口幂等性如何设计，重复提交订单怎么处理？]] 同一套机制）。

**方法与状态机**

- GET／HEAD 天然安全；POST 需要显式的 Idempotency-Key 类设计。
- 状态机让重复流转可判定：仅前置状态可迁移。

**受理号与轮询**

- 受理号要能查，并且有保留期。
- 轮询要有上限与退避，避免丢失风暴。

**限流的两种契约**

- 要区分“拒绝并提示重试”与“排队等待”。
- 给客户端的契约（错误码、Retry-After）要稳定。

**对账**

- 对账窗口按业务时效定。
- 差异处理动作本身也要幂等。

#### 深挖追问

1. **客户端不配合传 requestId 怎么办？**（补充练习）

   用可推导的业务天然键（用户＋活动＋时间窗等）做去重，或者在网关按会话与操作生成。没有稳定标识就无法区分重试与新请求，所以要在设计评审时把幂等契约前置。

### SYS-019：内存有限且结果可复用，如何兼顾并发、延迟与稳定性？

**常见问法**

- 系统有 N 类请求，峰值占用量已知；同类请求在依赖资源未变化时结果一致，机器内存有限，如何兼顾并发、延迟与稳定性？
- n 个请求分两批到达，完整请求耗时 1 分钟，30 秒时依赖资源发生变更，多长时间完成？

#### 面试回答

这是容量规划＋结果缓存题，我按“先量化、再隔离、后优化”四步答：

- 按类设内存配额。每类请求的峰值内存占用已知，配额总和留出安全水位（栈、元空间、临时对象）。这样任何一类打满只会降级自己，而不是拖垮整机。
- 按类建结果缓存。key 必须含依赖资源版本（依赖未变结果才有效），并设容量上限＋LRU／TTL 逐出。未命中时限并发回源（singleflight，同一 key 只放一个请求去回源），命中直接秒回。
- 并发与延迟：高命中率的类优先驻留内存，计算并行度受 CPU 与内存双重约束。
- 稳定性：配额超限走排队或慢路径，而不是 OOM。监控命中率、内存水位与 P95 延迟，按流量动态调配额。

#### 技术细节

**依赖变更怎么失效（本组变体的关键）**

- 对应“30 秒时资源变更”那一问：计算开始时记录依赖版本快照。
- 写缓存时校验版本是否仍为当前；跨越变更算出的旧结果直接作废，不进缓存。
- 这比“全量重算”省，比“不校验”正确。

**开放场景题怎么答（n 请求分两批、耗时 1 分钟、中途变更）**

- 先澄清条件再分情形：两批的到达时刻、并行度是否足够、变更前结果是否作废。
- 口径一：并行足够且旧结果作废——第一批 60s 算完作废、重算至 120s，第二批 30～90s，总 120s。
- 口径二：变更不影响已算结果——90s。
- 这类题的答案价值在口径表和快照失效的设计，不在猜一个数。

#### 深挖追问

1. **为什么不干脆全缓存？**（补充练习）

   因为内存有限时，全缓存必然带来驱逐抖动或 OOM。要按“命中率×计算成本”排优先级做准入，才能同时守住延迟与稳定性。

### SYS-020：多类请求的任务队列如何保证公平、防止一类占满资源？

**常见问法**

- 如何设计任务队列，处理多类请求，保证公平性，防止一类请求把资源占满？

#### 面试回答

核心是隔离＋加权调度：

- 隔离：每类请求有独立子队列和并发配额（bulkhead，舱壁隔离）。单类积压只影响自己。
- 加权调度：调度层按权重轮转各类（WFQ／deficit round-robin 思路）。高优先级类多分带宽，低优先级类有保底份额，防止饿死。
- worker 按资源画像分组：CPU 型与 IO 型隔离，防止一类长任务占满线程。
- 队列有界＋准入控制：满了就快速拒绝或降级，并返回明确的可重试信号。
- 监控各类的排队时长与完成率，权重可以动态调整。

如果同类任务可以合并或批处理，再加一层聚合，进一步降占用。

#### 技术细节

**为什么单纯排队不够**

- 纯 FIFO 的问题是一个慢类型造成头部阻塞。
- 只设按类并发上限、没有调度权重，仍然会“先到者吃满”。

**优先级与公平要一起设计**

- 严格优先级会饿死低优先级。
- 需要 aging（等待越久权重越高）或者分层配额。

**分布式多实例的额外问题**

- 需要集中式配额（如 Redis 计数），或者按任务键分片。
- 单机内存队列解决不了跨实例的公平性。

**重试会伪装成流量**

- 失败重试也占配额。
- 重试风暴会伪装成“某类流量暴涨”，所以退避与上限必须计入调度预算。

以下为通用设计，非某现成组件行为。

#### 深挖追问

### SYS-021：缓存如何设计，需要考虑哪些方面？

**常见问法**

- 缓存如何设计？需要考虑什么？
- 项目中多级缓存的设计流程讲一下（层级、读写路径、失效与降级）。

#### 面试回答

我会按清单逐项和业务对齐：

- 缓存什么：用命中率与计算成本选对象，不是能缓就缓。
- key 与粒度：含租户／版本前缀，避免整页大对象。键设计决定失效能力。
- 读写模式：以 cache-aside 为主，先提交数据库再删缓存。
- 一致性与陈旧上限：失效驱动（重试队列／binlog 订阅）＋TTL 兜底，并明确业务可忍多旧。
- 容量与逐出：设上限、用 LRU 类策略、做内存预算与告警。
- 异常场景：穿透（空值／布隆）、击穿（互斥或逻辑过期）、雪崩（TTL 打散＋高可用＋回源限流）。
- 冷启动预热与回源保护。
- 观测治理：命中率、逐出率、P99、大 key、权限与脱敏。

开放题的结构是：先问业务容忍度，再挑其中三点深入。

#### 技术细节

**先算收益，再决定要不要缓**

- 缓存收益＝命中率×回源成本，两个都低就不值得缓。
- 写多读少或强一致数据，缓存放大了不一致窗口，慎入。
- 多级缓存在这里（本地→Redis→DB）要额外处理跨级失效一致性，见 [[专题题库/系统设计#SYS-009：多级缓存如何保持一致，并在 Redis 故障时降级？|SYS-009：多级缓存如何保持一致，并在 Redis 故障时降级？]]。

**失效机制怎么分工**

- TTL 是最后防线，不是主机制。
- 失效消息要幂等、可重试。

**缓存自己挂了怎么办**

- 降级路径（L1 能撑多久、直连 DB 的限流容量）必须演练过，否则“加速层”会变成“放大器”。
- Redis 侧异常三大问题的具体方案见 [[专题题库/Redis#REDIS-002：缓存穿透是什么，布隆过滤器能完全解决吗？|REDIS-002：缓存穿透是什么，布隆过滤器能完全解决吗？]]。

1. **缓存和数据库双写，先动哪个？**（补充练习）

   常规是先提交数据库、再删缓存。先删缓存会被并发读回填旧值；先更新缓存则要处理并发写序与计算成本。

### SYS-022：千万到亿级 trace／日志如何存储与检索？

**常见问法**

- trace 数据如何存储、检索？千万／亿级日志量级怎么优化查询性能？

#### 面试回答

分三块说：怎么写进来、怎么查、量级大了怎么扛。

- 写入通道：trace 按结构化模型（traceId／spanId／属性，OTel 类）经采集 agent→消息队列→批量写入，用来削峰并解耦业务进程。
- 检索需求分两类：按 traceId 精确拉取是点查，靠主键／倒排索引；按条件聚合分析（慢请求分布、错误率趋势）走列存 OLAP。
- 量级上来后按“热—温—冷”分层：近几天数据在 ES／ClickHouse 支持交互查询；历史数据落对象存储（Parquet 按天＋租户分区），查询按时间路由。
- 还要控制数据量本身：头部采样保底错误与慢请求、尾部采样按规则保留完整链路、降 DEBUG 级冗余。

#### 技术细节

**查询优化的优先级**

- 先用强制过滤条件（时间范围、租户、服务名）做分区裁剪。
- 再做 traceId 索引点查。
- 聚合走列存与物化视图。
- 避免高基数全文检索。

**ES 类系统的两个坑**

- mapping 爆炸。
- 深分页成本高。

**超大规模的常见拆法**

- 把“明细检索”和“指标聚合”分开：明细进列存／对象存储，指标预聚合进时序库。

**治理要与存储设计同步定**

- 日志与 trace 的保留期。
- 脱敏（Prompt 与用户数据可能敏感）。
- 合规删除。

**亿级以上再谈成本**

- 压缩编码、冷热分层自动迁移、采样率随量动态调整。

以下为通用设计，项目量级与组件按【真实系统】说明。

### SYS-023：哈希分表扩容有什么问题，一致性哈希怎么工作？

**常见问法**

- 哈希分表扩容有什么问题？一致性哈希算法原理？

#### 面试回答

`hash(key) % N` 的问题出在扩容：N 一变，几乎所有键的归属都变，等于全量迁移，在线做代价高、风险大。

一致性哈希的解法是：

- 把键与节点都映射到同一个哈希环上，键顺时针找最近的节点。
- 新增节点时，只从顺时针方向的旧节点接走一小段区间；下线同理。迁移量约 1/N。
- 裸环会造成分布不均与热点，用虚拟节点缓解（每物理节点映射上百个虚拟像打散）。

工程落地还要处理三件事：

- 迁移期双写＋数据校验＋灰度切流。
- 路由表版本一致。
- 业务热点键——哈希再均匀也挡不住单键高 QPS，需要缓存／拆键。

#### 技术细节

**两类替代方案**

- 倍数扩容：表数 2N 翻倍时，只有“新半区”需要迁移。实现简单，但一次就得翻倍。
- 槽位映射：Redis Cluster 的 16384 slot。键→槽固定，迁移按槽粒度搬运，路由集中管理。
- 两者本质相同：把“改 N 全炸”变成“按区间／槽局部搬”。

**一致性哈希的参数**

- 虚拟节点数、哈希函数都要按实际数据分布去实测偏斜。

**别忘了更靠前的问题**

- 分片键选择仍是第一性问题，见 [[专题题库/系统设计#SYS-011：什么时候需要分片查询，如何定位与优化查询瓶颈？|SYS-011：什么时候需要分片查询，如何定位与优化查询瓶颈？]]。

#### 深挖追问

1. **扩容迁移进行中，读写落在旧片还是新片？**（补充练习）

   按迁移状态机走：双写新旧＋以旧读为准，校验追平后切读，最后停写旧片。任何一步都要可回退，避免“半迁移”悬挂。

### SYS-024：canal／binlog 订阅同步延迟如何归因与优化？

**常见问法**

- canal 同步 500ms 延迟怎么来的，怎么优化？

- canal 和 Kafka 怎么结合使用的，解决了什么问题？

- 同步延迟（如 500ms）是怎么测试出来的？

#### 面试回答

先拆链路归因，再按最长那段优化，并且说清延迟数字的统计口径。

canal 的工作原理是：伪装成 MySQL 的 replica，注册后 dump 拉 binlog，解析成行事件，再投递到目标（Redis、ES、MQ 等）。端到端延迟＝主库提交到目标可见，逐段可能是：

- dump 网络与主库压力。
- 解析吞吐：解析与投递默认接近单管道，大事务／宽表行放大时会排队。
- 攒批与轮询间隔：批量写入天然要多等一个批次窗口。
- 目标端写入能力与排队。
- 位点被 DDL 或大事务卡住。

判断方向：500ms 若稳定出现，优先怀疑“统计／攒批窗口”这类固定开销；抖动大才怀疑积压。

优化和归因一一对应：只订阅需要的库表列、按主键 hash 分区并行 sink（同键保序）、缩短或事件化攒批、拆大事务、按段埋点（拉取延迟／解析耗时／sink 积压），然后集中治最长那段。

项目链路结构与实测数字按【真实实现】说。

#### 技术细节

**归因的先行指标**

- canal 侧看位点推进与 dump 连接状态。
- MySQL 侧对照 binlog 产生位置与已解析位置的差。
- 下游看写入 TPS 与队列深度。

**“500ms”这个数字的常见陷阱**

- 监控采样心跳周期本身就是 500ms（例如每 500ms 聚合一次）。
- 把 P50 报成 P99。
- 含了消费端业务处理时间，和纯同步延迟混在一起。
- 所以报数前先定义清楚“从哪到哪”。

**保序约束决定并行度上限**

- 同一行的变更必须按提交序应用；ROW 格式带主键，可以按主键分区。
- 要求全局限序就只能单管道。
- DDL 与事务边界会强制形成栅栏。

**各环节自己的延迟贡献**

- canal adapter／客户端的批量参数（batch、buffer）。
- 目标端的机制，例如 ES refresh、Redis pipeline。

**延迟与可靠性之间的交换**

- 追求更低延迟常意味着更小批量与更多确认开销，也可能引入乱序风险。
- 优化后用对账任务验证最终一致。

#### 深挖追问

1. **为什么不用双写而是 canal 同步？**（补充练习）

   双写会把同步逻辑侵入业务，失败补偿也复杂；CDC 以 binlog 为单一事实源、业务零改动，代价是引入组件运维与秒级／亚秒级延迟。按能否容忍延迟选择，参见 [[专题题库/系统设计#SYS-009：多级缓存如何保持一致，并在 Redis 故障时降级？|SYS-009：多级缓存如何保持一致]] 的 CDC 失效方案。

2. **延迟突然从 500ms 涨到几十秒怎么查？**（补充练习）

   两步走：先看位点是否停住（大事务／DDL／连接断开重投），再看 sink 端是否排队（目标库写入劣化、限流）。目的是区分“解析慢”和“下游消化不动”，再对应扩容、拆批或修下游。

3. **canal 和 Kafka 怎么结合，解决什么问题？**（面经实际出现；[[面经/传音控股/一面/0001#Q02：canal 和 Kafka 怎么结合使用的，解决了什么问题？|MJ029 · 传音控股 · 一面 · Q02]]）

   链路是：canal server 解析 binlog → 投 Kafka topic → 各下游用独立 consumer group 消费。

   - 价值：采集端与消费端解耦、一对多广播、Kafka 缓冲削峰与位点重放、下游故障不阻塞采集。
   - 保序约束：同一行／同一 key 要落同一分区才有序，跨分区没有全局序。
   - 投递语义：引入 Kafka 后是“至少一次”，所以消费端要幂等。
   - 口径约束：延迟统计要把 Kafka 这一跳也算进去（见 [[#SYS-016：Kafka 如何做到不丢消息与不重复消费？|SYS-016：Kafka 不丢不重]]）。

4. **这个延迟是怎么测出来的？**（面经实际出现；[[面经/传音控股/一面/0001#Q03：500ms 同步延迟怎么测试的？|MJ029 · 传音控股 · 一面 · Q03]]）

   两种测法：

   - 事件带时间戳：取 binlog 提交时间或注入标记字段，消费落库后算 now−事件时间，按窗口出 P50／P99。
   - 探针法：定时写探测行，轮询目标端查到即计时，测的是完整链路。

   三个要避免的口径错误：把心跳／采集间隔当端到端、只报均值、压测与生产批量参数不一致。

### SYS-025：创建订单等同步接口耗时很长，链路如何优化？

**常见问法**

- 创建订单耗时很长怎么办？

#### 面试回答

先用链路追踪把耗时拆开定位：参数校验、风控、优惠计算、库存、支付前处理、落库、发消息。然后按五类下手：

- 并行化：互相独立的校验与查询改异步 RPC／CompletableFuture，把串行的“瀑布”压成最慢那个分支。
- 副作用外移：通知、积分、埋点、报表移出同步链路改 MQ 异步，用户确认点只留必要状态。
- 热点数据前置：运费、汇率、活动价格做预计算或缓存，减少在线计算与查询。
- 数据库侧：拆长事务缩短持锁、合并批量小写、订单号号段预取避免每次取号。
- 超时预算：全链路的超时预算分配给各个环节并监控。

约束有两条：异步化的部分必须幂等、可查、可对账（配合状态机，见 [[#SYS-013：接口幂等性如何设计，重复提交订单怎么处理？|SYS-013：接口幂等性如何设计]]）；优化收益用同口径压测与 trace 前后对比来验证。

#### 技术细节

**先分清是哪种慢**

- “单请求真慢”还是“高负载下排队慢”。
- 后者是容量与隔离问题，扩容、限流、线程池／连接池治理优先，硬优化代码无效。

**并行化的三个注意**

- 上下文传递：trace、事务不能跨线程复用。
- 失败聚合：并行分支的结果要统一聚合判定。
- 总超时：任一分支超预算就先返回降级。

**事务拆分的边界**

- 边界是“必须原子的事实”：扣库存＋写订单明细在同库时仍需同一个事务。
- 不能为了快把一致性拆开。
- 跨服务用 saga／本地事务表＋消息（见 [[#SYS-010：如何保证数据库写入与消息发送的一致性？|SYS-010：如何保证数据库写入与消息发送的一致性？]]）。

**前端体验优化**

- 先建单后确认、分步提交，本质是把耗时移出关键路径。
- 这要先和业务确认语义是否可接受。

#### 深挖追问

1. **订单主流程里哪些步骤坚决不能异步化？**（补充练习）

   影响“下单是否成立”的事实写入不能异步：订单落库、防超卖的权威扣减，要在同步路径里做完，或者同步等待其结果。只有通知、积分、统计这类可补偿的副作用才适合异步。

### SYS-026：熔断的触发时机与恢复时机怎么定，下游无法降级怎么办？

**常见问法**

- 项目里怎么用熔断的，熔断时机、恢复时机？
- 下游接口无法降级怎么办？

#### 面试回答

熔断的触发按“滑动窗口统计＋最小样本量”：

- 窗口内错误率或慢调用比例超阈值，并且请求数达到最小调用量，才打开。
- 没有最小量这一条，低流量下一个错误就会误熔断。

打开之后：

- 打开期间请求快速失败走 fallback，不再消耗资源去等故障依赖。
- 超时后进入半开，放行少量探测请求。成功率与延迟达标就关闭、恢复全量（恢复初期常做小流量爬坡，防二次打垮）；仍失败则重新打开并延长窗口。

落地用 Sentinel／Resilience4j 类组件，按依赖单独配置。阈值来自该依赖的历史基线与压测，不是抄默认值。

一个边界：熔断解决的是“快速失败、防线程堆积拖垮自己”，不保证“请求不丢”，必须与超时、幂等重试、异步补偿组合使用。

至于下游“无法降级”的调用：

- 先确认是业务不允许失败，还是当初没做预案。
- 真不允许失败，就把“同步可用”换成“可延迟完成”：超时＋幂等＋有限重试仍失败，则受理转后台重试队列／死信＋告警＋人工出口，用户侧显示处理中。
- 连延迟都不允许，那就是强同步依赖：只能提升依赖自身的可用性与容量，并准备业务止损预案。

#### 技术细节

**三态是一台状态机，参数互相牵制**

- 熔断器三态：closed／open／half-open。
- 窗口长度决定统计灵敏度。
- 最小请求量防小样本误判。
- 慢调用阈值要与该依赖的 SLO 对齐。
- open 时长要大于依赖恢复的典型时间。

**和相邻机制的分工**

- 超时管“单请求最多等多久”。
- 重试管“这次失败再来一次”。
- 限流管“进来多少”。
- 熔断管“还要不要继续打过去”。
- 降级管“打不过时给用户什么”。
- 五件事一起设计才有完整预案。重试要设上限并加退避，否则会和熔断互相放大，形成重试风暴。

**fallback 自身的约束**

- 熔断的 fallback 本身要轻量，并且不可再依赖那个故障方。

**监控要看得见“带病运行”**

- 把熔断触发次数、持续时长与恢复过程做成指标与事件，触发即告警。
- 否则会出现“系统一直带病快速失败，却没人知道”。

#### 深挖追问

1. **熔断和限流有什么区别，为什么常一起出现？**（补充练习）

   方向不同：限流针对入口流量，保护自己不过载；熔断针对出口依赖，不被下游拖死。下游故障时入口流量照常进来、出口快速失败，两个机制互补，单用任何一个都留缺口。

### SYS-027：如何设计一个可靠的系统？

**常见问法**

- 怎么设计一个可靠的系统？

#### 面试回答

先给口径：可靠性＝定义 SLO（可用性目标、故障恢复时间 RTO、数据丢失容忍 RPO）之后，让单点故障不放大成用户故障。框架是五步：

- 冗余去单点：服务多实例（跨机／跨可用区）、依赖用集群与主从、容量按 N-1 设计。
- 依赖治理：所有跨网络调用带超时，重试加退避与上限，配熔断、限流与分级降级预案；再做故障隔离（独立线程池／舱壁），防止互相拖垮。
- 状态正确性：幂等键贯穿、可重放，状态机约束流转，关键链路做对账补偿；异步化要配最终一致机制。
- 可观测：指标／日志／链路追踪加告警，先于用户发现问题（见 [[#SYS-022：千万到亿级 trace／日志如何存储与检索？|SYS-022：trace／日志如何存储与检索]]）。
- 验证与预案：压测摸容量、故障演练验证切换真的能切、备份可恢复且能回滚。

面试时结合自己项目挑一条链路讲透“检测→隔离→恢复→对账”，比背清单可信。

#### 技术细节

**换成“故障预算”思维**

- 可靠性不是消灭故障，而是控制故障影响的三个维度：范围×时长×数据损失。

**六个常见反模式**

- 只堆冗余不做演练，切换路径从未验证。
- 超时不设预算，导致层层放大。
- 重试无上限，形成风暴。
- 降级预案只写在文档里，没有开关。
- 监控只报“机器活着”，不看业务成功率。
- 嘴上说无状态，但本地盘／内存里藏着状态。

**恢复手段分层**

- 请求级：重试／兜底。
- 进程级：重启／摘除，见 [[#SYS-012：服务器宕机如何发现与恢复，Agent 宕机有何不同？|SYS-012：服务器宕机如何发现与恢复]]。
- 数据级：备份恢复／对账修复，见 [[#SYS-015：数据库故障无法写入时如何降级与恢复？|SYS-015：数据库故障降级与恢复]]。

**成本要一起报**

- 多活、双写、热备都在花钱。
- 投入按 SLO 定，不按恐惧定。

#### 深挖追问

1. **99.9% 和 99.99% 的差距落在哪些设计上？**（补充练习）

   每加一个 9，要改的东西都在量级上：故障检测与切换要从分钟级到秒级，冗余从单机房到多机房，发布与变更要可灰度可回滚，而且要靠演练持续证明。不是简单“多加几台机器”。

### SYS-028：营销抽奖的规则树与责任链如何设计，为什么这样设计？

**常见问法**

- 介绍一下营销项目，遇到什么问题、怎么实现的（抽奖业务、规则树、责任链），为什么要这样设计？
- 规则很多、经常变，怎么组织代码？

#### 面试回答

先讲触发问题：活动规则（时间窗、渠道、新老用户、参与次数、黑名单、奖品条件）会不断叠加。写成一串 if-else 之后，每次改动都要动同一个方法，回归面覆盖全量规则；规则之间的先后依赖（黑名单必须先于概率抽取）也藏在代码顺序里，出错难定位。

解法是**按“规则的表达形态”分两层**：

- **责任链**管流程型校验（能不能参与）：
  - 一个节点一条规则，顺序显式声明。
  - 命中即短路，并返回结构化的拒绝原因（原因码＋文案）。运营排查“用户为什么没抽中”时就有据可查。
  - 节点无状态、可单测、可按活动组合。
- **规则树**管条件型判定（能中哪一档）：
  - 把奖品中奖条件表达成布尔组合：AND／OR／NOT 内部节点＋叶子条件（字段、算子、值）。
  - 配置化存储，运行时把用户上下文喂给树求值。
  - 新增条件只改配置，主干不动。

为什么不是只用一种：

- 责任链是线性顺序＋短路语义，表达不了“（A 且 B）或 C”这种嵌套布尔。
- 规则树是表达式求值，不承载“按顺序执行、命中即终止并返回错误码”的流程控制。
- 链管准入、树管资格，职责不同，硬合并会让两者都变形。

代价必须一起说：

- 责任链的风险是顺序配置错误：顺序错即逻辑错，需要顺序断言测试。
- 责任链还有上下文对象膨胀：多个节点各自查库会把 RT 叠加，要前置一次性加载。
- 规则树的风险是配置错误与解释执行开销：要保存时静态校验＋表达式编译缓存＋子树结果复用。
- 规则外置后，运营误配的影响面变大：要配灰度、生效时间窗、变更审计、一键回滚。

被问“为什么不上 Drools／Aviator”：当前规则量级下自研树更可控、依赖更少；等出现决策表、热更新、非技术同学维护规则的真实需求再引入引擎。这是取舍，不是“自研更高级”。

#### 技术细节

**责任链落地**

- 节点接口只暴露一个方法（如 `check(ctx)` 返回继续／终止）。
- 链由配置装配（枚举数组或库表排序字段），拒绝原因用枚举而不是字符串。
- 上下文对象只放本轮已加载的事实（用户画像、参与次数、活动配置），节点不产生副作用。
- 日志记录“走到哪个节点、为什么终止”，这是排查上的关键收益。

**规则树落地**

- 三种节点：组合节点（AND／OR，可加 NOT）、叶子节点（字段＋算子＋值）、可选的优先级／权重节点。
- 求值时对 AND 短路，并对同一用户上下文缓存子树结果。
- 表达式来源可用 JSON（前端可视化配置友好）或字符串 DSL（配解析器）。
- 两者都要在保存时校验：字段是否存在、算子是否合法、有无恒假／孤立分支、值域是否越界。
- 上线前用历史数据回放，预估命中率变化。

**与库存、发奖的边界**

- 树和链只做判定，不产生业务写入。
- 判定通过后按顺序走：扣库存（条件更新或 Redis Lua，见 [[专题题库/系统设计#SYS-017：秒杀如何防止超卖，为什么用 Redis＋Lua 而不是加锁？|SYS-017：秒杀如何防止超卖]]）→ 写中奖记录（幂等键）→ 异步发奖（见 [[专题题库/系统设计#SYS-003：秒杀中 MQ 如何削峰，消费者如何完成发券？|SYS-003：MQ 削峰与消费端发券]]）。
- **概率抽取与规则树要分开**：树决定“有没有资格中这一档”，加权随机决定“这一档里中哪个”。混在一起运营就无法预测中奖率，也做不了库存与预算控制。

**验证方法**

- 改造前后做双跑对比：同一批输入分别走旧实现与新实现，比对拒绝原因码分布与中奖结果。
- 差异要逐条归因：是修掉了老 bug，还是引入了新问题。
- 保留旧链路开关，以便快速回退。

#### 深挖追问

1. **规则树和责任链是不是重复设计？**（面经实际出现；[[面经/美团/一面/0002#Q02：介绍一下营销项目，遇到什么问题、怎么实现的（抽奖业务、规则树、责任链），为什么要这样设计？|MJ032 · 美团 · 一面 · Q02]]）

   不是。链解决“按什么顺序执行、何时终止”，树解决“条件如何布尔组合”。判断依据是需求形态：出现嵌套条件就需要树，出现顺序依赖与短路就需要链。只用 if-else 去表达这两件事，才会真的变成不可维护的重复。

2. **为什么不把规则直接写进配置文件里的 SpEL／Aviator 表达式？**（补充练习）

   可以，而且很多团队就是这么做的。要补的是治理能力，四件事：

   - 表达式在保存时静态校验。
   - 执行时有超时与异常兜底，一条坏表达式不能拖垮请求。
   - 可观测：记录实际求值路径。
   - 版本与回滚。

   裸配表达式的风险不是性能，而是“没人知道线上现在生效的是哪一版”。

3. **规则量级涨到几百条时架构怎么演进？**（补充练习）

   - 先做分组与索引：按活动／人群先粗筛再细判，避免每条都求值。
   - 再考虑决策表或规则引擎（Drools 等）带来的 Rete 网络复用与热更新。
   - 同时把“规则命中统计”做成产品能力，让运营能看到每条规则拦了多少、误拦多少。否则规则只增不减，最终不可维护。

### SYS-029：如何设计一个分布式服务系统（服务拆分、注册发现、远程调用与容错）？

**常见问法**

- 让你设计一个分布式服务系统，你大概会怎么设计？
- 项目里分了哪些服务，服务之间是怎么远程调用的？
- 如果把现有系统升级为分布式系统，你会如何设计改造？怎么保证数据不丢、不重、具备容错能力？

#### 面试回答

先问需求与约束再谈架构：QPS／数据量、读写比、一致性要求、延迟目标、可用性预算，这些决定后面每一个选择。通用分层骨架：

1. **服务拆分**：按业务域／单一职责切。边界依据是变更频率、团队归属和扩缩容粒度，只有这三处不同才拆。能单体的别过度微服务化，分布式单体是最差结果。
2. **通信**：同步调用（RPC／HTTP）走必须在请求内拿到结果的关键链路；异步、解耦、削峰用 MQ。
3. **注册发现与配置**：实例启动时把自己注册到注册中心（Nacos／ZooKeeper／Consul），下线或健康检查失败时被摘除；调用方通过服务名发现可用地址；配置中心统一下发可变配置。
4. **负载均衡**：可以放客户端（Ribbon／Dubbo 的 LB），也可以放服务端／网关（DNS、LVS、反向代理）分摊流量。策略有轮询、随机加权、最少连接、一致性哈希。
5. **接入层网关**：路由、鉴权、限流、灰度。
6. **数据层**：缓存（本地＋分布式多级，注意一致性）、分库分表、主从与读写分离、冷热分离。
7. **一致性与容错**：跨网络调用一律带超时，重试加退避与上限，配熔断、降级、隔离；跨服务数据用最终一致＋幂等＋对账（见 SYS-013、SYS-027）。
8. **可观测与运维**：指标／日志／链路追踪＋告警，灰度发布、压测定容量、故障演练验证切换。
9. **高可用**：去单点、多副本、多可用区部署。

收尾：先保证“单链路正确”，再用冗余、隔离和可观测把故障影响控制在 SLO 预算内——与可靠系统设计（SYS-027）同一套思路。

#### 技术细节

**一次远程调用经历了什么（最常被追问，要能画出来）**

- 调用方拿到接口代理。
- 序列化参数：JSON，或 protobuf／Hessian 二进制。
- 从注册中心缓存的地址列表里，用负载均衡选一台。
- 建立或复用长连接发送。
- 服务端从线程池取线程，反序列化后执行。
- 原路返回，全程配超时与重试。
- 可观测性里最关键的是把 traceId 透传进每一跳，这样才能还原整条调用链。

**服务拆分的代价要主动说**

- 进程内方法调用变成分布式调用后，失去事务与强一致，多了网络不确定性与部分失败。
- 排查也从看一个栈变成看全链路。
- 所以拆分的收益（独立部署、独立扩缩、团队边界）必须大于这些成本。

**注册中心的 AP 与 CP**

- AP 型（Eureka，偏可用）与 CP 型（ZooKeeper／etcd，偏一致）在网络分区时行为不同。
- 服务发现一般选 AP：宁可拿到略旧的地址，也不要整体不可用。

#### 深挖追问

1. **服务越来越多，如何避免“分布式单体”？**（补充练习）

   三条：

   - 按限界上下文划清数据所有权，服务间只走接口不共享库表。
   - 用契约（接口／消息 schema）版本化，保证服务能独立演进。
   - 能同步拿到的强一致越少越好，跨服务优先用编排／协同＋最终一致。

2. **同步 RPC 和异步 MQ 怎么选？**（补充练习）

   调用方必须立即拿到结果、且下游可用时用同步 RPC。只需“把事做完”不要求即时返回，或者要削峰／解耦／广播给多方时用 MQ。异步化之后必须补上幂等消费、重试与对账（见 SYS-010、SYS-016）。

3. **服务实例怎么注册与保活，调用方如何第一时间感知上下线？**（面经实际出现；[[面经/字节/一面/0009#Q13：微服务架构中服务发现和负载均衡如何实现；注册中心（Nacos、Consul）如何工作，实例如何注册与保活（心跳机制）？|MJ041 · 字节 · 一面 · Q13]]）

   按实例类型分两条路：

   - 临时实例（Nacos ephemeral、Eureka）：客户端启动时注册，之后周期发心跳续约（Nacos 默认约 5 秒一次）。服务端按阈值判定——约 15 秒未收到标为不健康、约 30 秒未收到直接摘除。这类系统按 AP 取舍，分区时优先让调用方仍能拿到列表，代价是可能推给已经挂掉的实例。
   - 持久实例（Consul 默认健康检查、Nacos 非临时实例）：由服务端主动探活（TCP／HTTP 检查），失败只标不健康、不自动删记录。
   - ZooKeeper／etcd 是第三种形态：靠会话与临时节点，session 过期节点即消失，属 CP，注册场景要谨慎选。

   变更感知分拉与推：

   - 拉：客户端定时全量或增量拉（Eureka 约 30 秒），实现简单但有窗口延迟。
   - 推：Nacos 变更推送加拉取兜底、ZK／etcd watch、Consul blocking query。

   三个工程细节才见生产经验：

   - 实例下线要先摘流量再停进程，否则调用方仍持旧列表。
   - 注册中心抖动或自我保护阈值触发时会保留不健康实例，调用侧必须有重试与熔断兜底。
   - 本地缓存快照能在注册中心不可用时继续调用，但列表变更后要能重建连接池。

4. **把一个已有单机系统升级为分布式系统，改造顺序怎么排？怎么保证数据不丢、不重、有容错？**（面经实际出现；[[面经/字节/一面/0011#Q03：把项目 1 升级为分布式系统如何设计改造，怎么保证数据不丢、不重、有容错能力？|MJ066 · 字节 · 一面 · Q03]]。原素材未记回答，以下为参考）

   改造视角和从零设计不同，难点在「已有的隐式状态」：

   - 第一步是拆状态：找出藏在本地盘、内存队列、定时任务单机锁、文件缓存里的状态，外置（共享存储／KV）或改成可重建。
   - 第二步定分片：按 key 哈希（一致性哈希减少迁移面）或按业务维度分片，让同一实体的变更落同一分片，才谈得上局部有序。
   - 第三步管写入语义：先落持久化日志或副本确认再回成功（不丢）；每条写入带唯一幂等键，重放时判重（不重）。
   - 第四步做容错：副本数与读写策略、心跳与故障检测、自动切主与再平衡；调用侧配超时、指数退避重试与熔断。
   - 第五步留收敛手段：对账与补偿任务必须存在——分布式的假设不是「不出错」，而是「出错后能收敛回一致」。
   - 分片扩容与数据搬迁见 [[#SYS-023：哈希分表扩容有什么问题，一致性哈希怎么工作？|SYS-023]]，整体可靠性预算见 [[#SYS-027：如何设计一个可靠的系统？|SYS-027]]。

### SYS-030：多实例之间如何同步文件或文档状态（如表格）？

**常见问法**

- 给你一个 RPC 场景，把 A 实例上的文件信息同步到 B 实例（例如表格），你该怎么设计？

#### 面试回答

先澄清“同步的是什么”：是整份文件字节，还是结构化数据（表格的单元格／操作）？这决定方案。通用骨架：

1. **先定权威源**：首选把事实放共享存储（数据库／对象存储），A、B 只是无状态计算节点。这样“同步”退化为“都读权威源最新”，最省心、天然幂等。若题目强制“实例间直接同步”再走第 2 步。
2. **同步增量而非全量**：结构化表格不传整份文件，传“带版本号的变更／操作日志（op log）”，接收方按版本拉取或接收增量并回放。大文件本体走对象存储传引用，只同步元数据。
3. **传输方式推拉结合**：
   - 实时性高用推送：A 直接 RPC 推给 B，或经 MQ／pub-sub 广播给多个 B。
   - 可容忍延迟用 B 定时拉：能合批、削峰。
   - 混合模式最常见——变更事件推送＋按版本拉全量对齐。
4. **冲突解决**：并发编辑要明确模型，三选一：
   - last-write-wins（按时间戳／版本）。
   - 按操作合并：协同表格用 OT／CRDT。
   - 行级锁串行化。
   - 跨实例是最终一致：先保证收敛，再谈延迟。
5. **可靠性**：每次同步带幂等 ID＋单调版本，接收端对乱序、重复、丢失用版本判重与断点续传（见 SYS-013）。失败要有对账／重放兜底——防止“漏同步”比防止“重复同步”更难。

一句话答法：权威源 → 增量（版本／oplog）→ 传输（推拉／MQ）→ 冲突模型（LWW／OT／CRDT）→ 幂等与对账。

#### 技术细节

**两个最常见的坑**

- 把它当“传文件”去做全量拷贝，带宽和延迟都会爆炸。
- 只传变更却不带版本：网络重传或乱序到达时，状态会被旧数据覆盖。

**版本号怎么让重放变安全**

- 版本号／序列号是让“应用一条变更”既幂等又可判序的关键。
- 接收方记录自己已应用到的版本，然后分三种情况：
  - `v ≤ 已应用`：直接丢弃。
  - `v == 已应用+1`：顺序应用。
  - `v > 已应用+1`：说明有缺口，去拉全量或请求补发。

**协同编辑是特化难题**

- 多人实时改同一张表时，并发操作会互相影响，LWW 会丢掉别人的改动。
- 工业方案是 OT（操作变换，中心化服务器定序）或 CRDT（无中心、操作可交换收敛）。
- 代价是实现复杂度与元数据膨胀。

**什么时候不必上 OT／CRDT**

- 如果题目只是“一份数据在 A 改、同步给 B 展示”，版本化增量＋单写者即可。
- 先问清是否多人并发写再决定，过度设计也是失分点。

#### 深挖追问

1. **怎么保证同步操作只执行一次？**（面经实际出现）

   给每次操作一个全局幂等 ID＋单调版本。接收端用“已处理集合（Redis SETNX／DB 唯一索引）或版本比较”判重，判重与应用要在同一个原子步骤内完成。详见 SYS-013。
   来源：[[面经/字节/一面/0008#Q04：怎么保证同步操作只执行一次（幂等性）？|MJ033 · 字节 · 一面 · Q04]]

2. **B 实例宕机恢复后如何补齐漏掉的同步？**（补充练习）

   靠权威源＋版本号对账。B 记录本地已应用版本，重启后向权威源／A 请求“该版本之后的增量”；缺口过大则先拉一次全量快照，再续增量。对账任务周期性比对版本水位并触发补同步。

3. **为什么优先共享存储而不是实例间直接同步？**（补充练习）

   因为共享权威源把 N×N 的实例间同步问题降为“多读一写”，天然收敛、还少一套一致性协议。实例间直接同步只在“数据本就在实例本地、无法集中”或极低延迟的点对点场景才用，复杂度高得多。

### SYS-031：如何理解 CAP 定理，为什么保证 CP 会损失可用性？

**常见问法**

- 讲一下你对 CAP 原理的理解。
- 为什么保证 CP 的情况下，A 就会损失呢？讲一下这块的逻辑。

#### 面试回答

CAP 说的是：一个读写了共享数据的分布式系统，在发生网络分区时，一致性（这里特指线性一致）与可用性（每个请求都收到非错误的正常响应）不可能同时保全。

前提要讲对：分区不是可选项。广域网里丢包、延迟抖动必然存在，P 必须容。所以真实的抉择是分区那一刻在 C 和 A 里二选一。

为什么选 CP 必然损失 A：

- 分区把集群切成互不通信的组。
- 若各组都照常接受读写，愈合时同一份数据会出现分叉版本，强一致被破坏。
- 要守住 C，就必须让至少一部分节点拒绝写入甚至读取（返回错误或进只读等待追平）。
- 被拒绝的请求得不到正常响应，按定义就是丧失可用性。

典型对子：

- ZooKeeper／etcd 是 CP：分区中小部分侧无法写入，选主期间整体短暂不可写。
- DNS／Cassandra 偏 AP：两侧各自可写，愈合后靠时间戳或冲突合并收敛。

落点：工程上不是全局的二值选择，而是按数据项配置。余额扣减走 CP 语义（甚至退回单机事务），Feed 流、点赞数走 AP＋最终一致。另外 CAP 只描述分区那一刻，平时还有一致性与延迟的权衡，答题带出 PACELC 口径会更完整。

#### 技术细节

**定理侧的出处**

- Brewer 提出，Gilbert 与 Lynch 在 2002 年给出证明。
- 证明的构造就是“分区两侧各接受一个写，愈合后要么违反线性一致、要么必有一侧没响应”，所以上面的直觉是有严格形式的。

**三个字母的定义都有限定域**

- C：所有客户端看到的操作全局有序且实时（线性一致），不是 ACID 里那个 C。
- A：每个发给“非故障节点”的请求都能在有限时间内收到“有用的”（非错误）响应。
- P：任意链路可以丢包、延迟任意久，但节点不宕机。

**两个常见误读要能纠正**

- “三选二”不等于平时也只有两项——无分区时 C 和 A 可以同时很好。
- 也不能拿“网络做好点就不分区”当解：跨机房故障与交换设备抖动不受控制。

**Quorum 不是跳出定理的折中**

- Quorum（如 RF3＋W＋Q>N）常被当作“折中”，其实它仍落在光谱上。
- 网络健康时，它可以同时满足 C 与 A。
- 分区时，W＋Q>N 的定义决定了不可达侧要么写不进、要么读不到——本质还是分区时刻选 C。

**PACELC 补全另一维**

- 分区时：在 E（最终一致）或 C 之间选。
- 无分区时：要在 L（低延迟）与 C 之间权衡。
- ELASTIC 类系统与 Spanner 类系统就差在这一步，后者用时钟同步换外部一致性。

#### 深挖追问

1. **为什么“分区时两侧都继续服务”一定破坏线性一致？**（补充练习）

   两侧各自接受的写，会形成两个不能互相感知的全序历史。愈合后只有两条路，而两条都出界：

   - 丢弃一侧：等价于拒绝了那部分请求的持久化，违反“收到有用响应”的隐含承诺。
   - 合并：会得出与真实时间顺序矛盾的序。

   所以定理说必须二选一。

2. **业务上怎么落地“按数据项选 CP／AP”？**（补充练习；与 [[#SYS-027：如何设计一个可靠的系统？|SYS-027：如何设计一个可靠的系统？]] 的故障预算思路一致）

   按“错误响应的代价”与“短暂不可用的代价”哪个更高来划档：

   - 钱与库存这类写错代价高的，放强一致链路（主库事务或 CP 协调）。
   - 偏好、计数、Feed 这类可自愈的，放 AP＋异步收敛。
   - 跨档交互用 outbox／消息解耦，避免一个请求同时硬依赖两种语义。

3. **AP 系统分区愈合后怎么收敛？**（补充练习）

   - Cassandra 类：用 last-write-wins（墙钟或逻辑时钟）＋读修复／反熵。冲突被静默覆盖，所以需要业务保证“可覆盖”。
   - 更严格的场景：用向量时钟检测并发写，冲突时返回多分支交上层合并（dynamo 的 siblings 处理）。
   - 结论：没有免费的收敛，冲突解决策略本身就是业务决策。

### SYS-032：Kafka 有哪些特性，与 RabbitMQ 有何区别，为什么吞吐高？

**常见问法**

- Kafka 特性，与 RabbitMQ 的区别？
- Kafka 高吞吐量的原因？
- RabbitMQ、Kafka、RocketMQ 三者怎么选型，项目为什么用 RabbitMQ？

#### 面试回答

先把定性说清楚：

- Kafka 是分布式提交日志：topic 拆成分区，分区内 append-only、有序持久化；消费者按 offset 拉取，消息“消费后仍在”，可重放、可回溯。
- RabbitMQ 是经典 broker 队列模型：exchange 按路由规则分发进 queue，消息取出即消失。

Kafka 的特性：分区并行、消费者组（组内分摊、组间广播）、副本 ISR、Connect／Streams 生态。

与 RabbitMQ 的取舍按五个维度答：

- 模型：Kafka 是日志，RabbitMQ 是路由队列。
- 投递方式：Kafka 用 pull＋长轮询，RabbitMQ 用 push。
- 顺序粒度：Kafka 只保证分区内有序，由 key 路由决定落到哪个分区。
- 延迟与吞吐：RabbitMQ 微秒级低延迟、万级 TPS；Kafka 毫秒级、百万级 TPS。
- 功能风格：RabbitMQ 擅长复杂路由、死信、优先级这些队列语义；Kafka 擅长流式管道与重放。

选型一句话：业务消息、需要精细路由和低延迟在线响应选 RabbitMQ；日志采集、行为事件流、大数据管道、需要回溯重放选 Kafka。

高吞吐有四大支柱：

- 顺序写磁盘＋OS 页缓存：追加写把随机 IO 变成顺序写，读写的热数据都走 page cache 不进用户态，磁盘吞吐逼近内存。
- 零拷贝 sendfile：消费时数据从页缓存直达网卡，省掉内核到用户的来回拷贝。
- 分区即并行：生产和消费都按分区水平扩展，吞吐随分区数近线性增长。
- 批量＋压缩：producer 攒批（linger／batch.size）、broker 按批原样存储与传输、consumer 拉批，压缩（lz4／zstd）在批的粒度做，摊薄每条消息的网络与协议开销。

另外 pull 模式本身也有贡献：消费速率由消费者自主掌握，批量获取减少往返。

#### 技术细节

**磁盘写为什么还快**

- Kafka 靠页缓存＋顺序写＋group commit 批量刷盘（可以用 acks 换耐久度）。
- 消息以压缩批的格式直接进页缓存，避免在 JVM 堆内缓冲大对象的复制。
- 这就是它敢用普通机械盘跑高吞吐的原因。
- 对照反面：RabbitMQ 每条消息要过 Erlang 进程与队列结构，per-message 开销天然更大。

**零拷贝链路的精确口径**

- `FileChannel.transferTo` → 页缓存 → DMA 到网卡。
- 跳过了用户态的两次拷贝与两次上下文切换（见 [[专题题库/操作系统#OS-018：什么是 I/O 零拷贝，sendfile 和 mmap 如何减少拷贝？|OS-018：零拷贝]]）。

**高吞吐不等于高可靠**

- 默认 acks=1／retries 可能丢消息或产生重复。
- 要耐久就得 acks=all＋min.insync.replicas＋幂等 producer／事务（见 [[#SYS-016：Kafka 如何做到不丢消息与不重复消费？|SYS-016：Kafka 不丢不重]]）。
- 批与 linger 提吞吐也提延迟，二者是同一条旋钮的两端。

**分区数影响顺序与并行**

- key 哈希决定进哪个分区，同 key 有序。
- 分区过多会拖慢故障恢复与端到端延迟，再平衡成本也上升——扩分区不是免费加速。

#### 深挖追问

1. **为什么不直接说 Kafka 是“消息队列”？**（补充练习）

   因为语义不同：队列消费即删、状态在 broker；Kafka 是日志，数据留存与消费进度（offset）解耦，同一份数据可以被多个组独立重放。把它当 RabbitMQ 用，会丢掉它最值钱的重放能力，还会为不需要的路由语义买单。

2. **Kafka 支持延迟消息／优先级吗？**（补充练习）

   原生不支持：没有 per-message 的延迟投递，也没有优先级队列（分区内是 FIFO）。这类需求要么用 RabbitMQ 的 TTL＋死信／优先级队列，要么在 Kafka 外用分级 topic＋调度消费者模拟。承认“这不是它的强项、该换工具”，比硬凑方案更加分。

3. **RabbitMQ、Kafka、RocketMQ 怎么选型，为什么选 RabbitMQ？**（面经实际出现；[[面经/钉钉/电话面/0001#Q04：消息队列为什么选 RabbitMQ，而不是 Kafka 或 RocketMQ？|MJ053 · 钉钉 · 电话面 · Q04]]）

   三者定位不同，按维度选而不是按名气选：

   - 吞吐：Kafka ≫ RocketMQ ＞ RabbitMQ。RabbitMQ 万级 TPS、微秒级低延迟；Kafka 面向百万级日志流。
   - 路由：RabbitMQ 的 exchange（direct／topic／fanout／headers）最灵活；Kafka、RocketMQ 主要按 topic＋tag 粗路由。
   - 特化能力：RocketMQ 强在事务消息、顺序消息、定时／延迟消息，电商交易链路成熟；Kafka 强在重放与流处理生态（Connect／Streams）。
   - 运维与生态：RabbitMQ 部署轻、Spring AMQP 开箱即用；Kafka 依赖 ZK／KRaft 与分区运维更重；RocketMQ 偏阿里系 Namesrv＋Broker。
   - 选型口径：在线业务消息、要灵活路由和低延迟、量级不极端 → RabbitMQ；日志／行为事件流、要高吞吐和回溯 → Kafka；分布式事务、严格顺序、海量削峰 → RocketMQ。

   答“为什么用 RabbitMQ”时，落点是“我们的消息量级和延迟要求它够用、路由模型贴合业务、团队用 Spring AMQP 成本最低”，而不是贬低另外两个。

### SYS-033：秒杀抢购如何防刷，前端防刷能挡什么、直连接口刷单怎么防？

**常见问法**

- 前端防刷能解决哪些问题，有哪些局限性？
- 如果用户不通过浏览器界面，而是直接模拟或调用后端接口进行刷单，如何防范？
- 秒杀怎么防止黄牛和脚本刷单？

#### 面试回答

先把定位说准：前端防刷不是安全边界，只是成本与体验优化。

- 它能挡掉误点连点、初级脚本和低质量流量。
- 它挡不住有组织的刷单，因为前端逻辑全部可绕过。

真正的防盗刷必须在服务端，思路是“不信任任何自称合法的请求”：

- 接口不裸露：下单要先换一次性准入令牌。
- 请求加签防重放。
- 限购规则在服务端硬校验。
- 风控按行为与账号画像评分。
- 事后处罚与名单沉淀。

所有防刷都是概率与成本的博弈，目标是把“绕过前端”的边际收益压到低于收益，而不是一劳永逸地识别机器人。

#### 技术细节

**前端层能解决什么**

- 按钮置灰与节流，防重复提交。
- 页面与素材缓存，降低无效负载。
- 验证码／滑块／答题，抬高人工与初级脚本的成本。
- 按钮态按服务端时间判定，避免提前打接口（见 [[专题题库/系统设计#SYS-036：秒杀开始前的页面刷新与流量冲击如何承接（静态化、CDN、预热、兜底）？|SYS-036：秒杀开始前的页面刷新与流量冲击如何承接]]）。

**前端的局限要说全**

- JS 可逆向，参数可自造。
- 验证码可打码，或走协议破解。
- 无头浏览器可伪装 UA 与指纹。
- 请求可以脱端重放。
- 所以前端手段一律只当“减速带”，不能作为放行依据。

**服务端层的四类机制**

- 凭证化：把“看活动”和“提交订单”拆开。下单需先领取与服务端会话／活动绑定的**一次性令牌**（用过即废、短时效），脚本没有合法上下文就拿不到令牌；它同时天然承担幂等（与 [[专题题库/系统设计#SYS-013：接口幂等性如何设计，重复提交订单怎么处理？|SYS-013：接口幂等性如何设计]] 同源）。
- 完整性与防重放：参数＋时间戳＋nonce 签名。服务端校验签名、限时间窗，并对 nonce 去重，防止改价、改数量、重放他人请求。密钥下发与前端持有的局限要有意识：签名只能抬高成本，防不住已经逆向出算法的对手。
- 业务硬校验：按用户、账号、设备、SKU、时间窗计算已购量，库存与限购判定全在服务端事务里。
- 风控与处置：
  - 看三类特征：行为序列（点击节奏、是否有浏览过程、无浏览直接下单）、设备指纹与网络信誉（机房／代理池 IP、同出口聚集）、账号画像与团伙关联（同收货信息、同支付账户）。
  - 用评分结果驱动处置：放行／排队／出验证／拒绝。
  - 事后动作：异步处罚与黑名单回灌；异常订单侧支持人工审核与回收。

**治理面别漏**

- 防刷规则要能灰度与回滚。
- 误杀真实用户比放过脚本代价更高。
- 需要监控“被拦截后申诉率”，并按活动调阈值。

#### 深挖追问

1. **前端做了验证码和按钮置灰，为什么还不够？**（面经实际出现；[[面经/阿里国际/一面/0001#Q03：前端防刷能解决哪些问题、有哪些局限；用户不走浏览器直接模拟或调用后端接口刷单怎么防？|MJ038 · 阿里国际 · 一面 · Q03]]）

   因为攻击面已经换到了协议层：脚本不走 UI，直接构造 HTTP 请求，前端的一切限制都不在它的执行路径里。验证码本身也有打码与绕过成本，同样只是提高成本而非阻断。

2. **一次性令牌会不会也被脚本先领再用？**（补充练习）

   会。所以令牌要绑定服务端侧的上下文（会话、活动、设备或 IP 特征、领取时间窗），并限制使用次数与有效期；再配合“申请令牌”这个动作本身的限流与风控评分，让“批量拿令牌”先成为瓶颈。

3. **怎么区分真实用户和脚本，又不误伤？**（补充练习）

   不做二值判定，做分级：低风险放行、可疑加验证或排队、高风险拒绝。用申诉率与人工抽检度量误伤，规则灰度上线。对同一出口 IP 的正常密集用户群要放宽（见 [[专题题库/系统设计#SYS-034：同一出口 IP 下大量真实用户同时抢购，限流怎么设计才不误伤？|SYS-034：同一出口 IP 下限流怎么设计]]）。

4. **防刷和限流是一回事吗？**（补充练习）

   不是。限流保护系统容量：按维度控制速率，超出快速失败。防刷识别恶意主体并剥夺其收益：对方可能速率很低但意图恶意，比如定时脚本。一个请求可能通过限流却被风控拦截，反之亦然，两套机制的指标与处置手段都不同。

### SYS-034：同一出口 IP 下大量真实用户同时抢购，限流怎么设计才不误伤？

**常见问法**

- 在应对局域网下（同一 IP）大量用户同时抢购的场景时，怎么设计 IP 限流策略？
- 校园网、公司内网出口都是同一个 IP，秒杀限流怎么不误杀真实用户？

#### 面试回答

关键判断是：IP 不等于用户。NAT 出口、校园网、企业专线、代理池，让同一 IP 背后可能是几百个真实用户，也可能是少量脚本在换 IP。所以 IP 只能当异常维度用，不能当唯一限流键。

设计四步：

- 主维度用身份：UID、设备指纹、账号信誉，做一人一配额。
- IP／CIDR 维度做兜底阈值：按该 IP 历史正常并发基线放大设阈，并按同 C 段归并聚合。
- 超阈值时分级处置，而不是直接拒绝服务：增量请求降级为排队、出验证或收紧可见库存；可疑比例越高就越严。
- 最后度量误伤：被限流后的申诉量、同 IP 真实用户的成功率。阈值随流量曲线动态调整，不是一次拍定。

#### 技术细节

**限流维度组合要显式设计**

- 以“维度＋活动”拼 key：UID＋活动、设备＋活动、IP／CIDR＋活动。
- 算法侧固定窗口／滑动窗口／令牌桶／漏桶的实现与取舍见 [[专题题库/Redis#REDIS-004：Redis 如何实现固定窗口、滑动窗口、令牌桶与漏桶限流？|REDIS-004：Redis 如何实现各类限流算法]]。
- 集中式计数放 Redis，保证多实例一致；判定收口在网关或统一切面。
- 本地缓存兜底：以防 Redis 抖动时退化为宽松放行＋核心链路保护（见 [[专题题库/系统设计#SYS-006：Redis 不可用时秒杀如何降级且避免超卖？|SYS-006：Redis 不可用时秒杀如何降级]]）。

**IP 侧的两个细节**

- IP 聚合用 CIDR 而不是精确匹配：既避免被换 IP 绕过，也避免对同一出口逐个统计。
- 白名单登记已知机构出口（校园网、企业）走宽松策略，配合账号维度的限购保证公平。

**“不误伤”的三条机制化做法**

- 只降速不断服务：超配额的请求进排队或返回可重试提示，而不是硬 429。
- 配额按份额而非绝对值：同一 IP 下按历史正常用户数分配额度，真实密集用户群整体放行，只有异常超量部分受限。
- 判定用比例与画像：同 IP 内新注册账号占比、无浏览直接下单的比例、请求节奏一致性（脚本的方差极小）这些特征组合，而不是单看 QPS 峰值。

**别忘了限流组件自己会变热点**

- Cluster 下要注意限流 key 的分片集中问题：热点活动的计数 key 要按维度分桶。
- 否则限流组件自己先成了热 Key（见 [[专题题库/Redis#REDIS-010：什么是热 Key，为什么危险，如何探测与解决？|REDIS-010：什么是热 Key]]）。

#### 深挖追问

1. **为什么不直接按 IP 限死每秒几个请求？**（面经实际出现；[[面经/阿里国际/一面/0001#Q04：局域网下（同一 IP）大量用户同时抢购，IP 限流策略怎么设计？|MJ038 · 阿里国际 · 一面 · Q04]]）

   因为该策略同时犯两类错：校园网／企业出口的几百个真实用户会被集体误杀，而用代理池分散流量的脚本几乎不受影响。IP 的价值在异常检测与配额兜底，不在主限流维度。

2. **脚本用海量住宅 IP 呢？**（补充练习）

   这时单 IP 维度失效，要转到账号与设备维度、行为一致性（同一操作序列的方差），以及成交侧约束（收货信息、支付账户聚集度、限购），再配合事后取消与名单回灌。这也是防刷要落到风控而不只是限流的原因（见 [[专题题库/系统设计#SYS-033：秒杀抢购如何防刷，前端防刷能挡什么、直连接口刷单怎么防？|SYS-033：秒杀抢购如何防刷]]）。

3. **Redis 计数挂了怎么办？**（补充练习）

   退化为本地限流：单机阈值＝集群阈值／实例数，精度差但能挡住量级。同时收紧活动开关与库存保护，宁可少卖不可超卖。恢复后重建计数窗口。

### SYS-035：秒杀全链路除下单外还有哪些性能瓶颈，如何逐层定位？

**常见问法**

- 除了“下单”环节，整个秒杀链路中还有哪些环节可能存在性能瓶颈或挑战？
- 一个高并发活动，你怎么判断瓶颈在哪一层？

#### 面试回答

按请求走过的顺序盘一遍，比只盯下单更能体现容量意识。逐层的瓶颈点：

- 静态层：页面与素材没上 CDN 时，回源带宽先满；渲染慢会导致用户在开抢瞬间集中重试。
- 接入层：连接数与 TLS 握手风暴；限流组件自身成为串行点。
- 鉴权层：token 校验与会话查询是每个请求必经的同步依赖，打爆就放大成全站故障。
- 资格校验层：会员、券、黑名单常是跨服务的同步 RPC，一个慢下游就拖住线程池。
- 库存层：Redis 单 key 串行与集群单分片热点、数据库热点行锁。
- 订单与存储层：主键生成、分库分表写集中、单库写上限、从库延迟造成“已下单查不到”。
- 消息层：分区数限制消费并行度、积压与最老消息年龄。
- 下游依赖：积分、券、风控、推送被流量放大。
- 外部回调：支付回调乱序，要求状态机幂等。
- 任务与运维：对账回补、库存释放、活动开关的时效。

定位方法是统一的：逐层压测找最小容量的那个环节，并算出各层水位。只看网关 QPS 会误判。配套超时、熔断、可观测与活动开关兜底。

#### 技术细节

**每类瓶颈要能报出对应指标**

- CPU／网卡打满与单分片倾斜，对应热 Key（[[专题题库/Redis#REDIS-010：什么是热 Key，为什么危险，如何探测与解决？|REDIS-010：什么是热 Key]]）。
- 数据库侧看锁等待与 TPS 上限（[[专题题库/MySQL#MYSQL-007：如何优化秒杀库存更新与热点行锁竞争？|MYSQL-007：如何优化热点行锁竞争]]）。
- 消息侧看积压量与最老消息年龄（[[专题题库/系统设计#SYS-005：秒杀消息积压如何定位与消化？|SYS-005：秒杀消息积压如何定位与消化]]）。
- 接口耗时看分段瀑布，而不是总耗时（[[专题题库/系统设计#SYS-025：创建订单等同步接口耗时很长，链路如何优化？|SYS-025：创建订单链路耗时优化]]、[[专题题库/系统设计#SYS-008：如何解释 QPS、延迟水位并设计可信压测？|SYS-008：QPS、延迟水位与可信压测]]）。

**优化手段的通用顺序**

- 先去掉同步依赖：能异步就异步，能前置校验就别查库。
- 再合并与缓存重复读。
- 然后打散写集中：分库分表键、库存分片。
- 最后才扩容：新增实例若不解决下游容量，只会加剧数据库竞争（SYS-002 的教训）。

**两个容易被忽略的软瓶颈**

- 线程池与连接池配置：下游一慢就耗尽，表现为“QPS 上不去但 CPU 空闲”。
- 活动开关与降级路径有没有演练过：真实故障时靠的是开关，而不是临场改代码。

#### 深挖追问

1. **这些瓶颈里哪个最常被漏掉？**（补充练习）

   站外与鉴权链路最常漏：会话／token 校验和权限查询被当成“基础能力”。但在秒杀流量下，它们是每个请求都要打的同步依赖，容量规划时经常被排除在活动压测范围之外。

2. **怎么证明你找到的是真瓶颈？**（补充练习）

   要给出因果，而不只是相关：

   - 单变量压测：固定其他层容量，逐层加压，看哪层指标先饱和。
   - 瓶颈消除后总吞吐随之上升。
   - 线上故障表现与压测结论一致。

   只说“加了机器就快了”不算定位。

3. **秒杀活动前的容量准备怎么做？**（补充练习）

   按压测水位扩容并留安全余量，然后四件事一起做：

   - 预热缓存／连接池／JIT／凭据。
   - 配好限流阈值与降级开关，并演练一遍。
   - 明确活动开关与止损口径。
   - 开抢前的流量承接见 [[专题题库/系统设计#SYS-036：秒杀开始前的页面刷新与流量冲击如何承接（静态化、CDN、预热、兜底）？|SYS-036：秒杀开始前的流量冲击如何承接]]。

### SYS-036：秒杀开始前的页面刷新与流量冲击如何承接（静态化、CDN、预热、兜底）？

**常见问法**

- 在秒杀活动正式开始前，如何应对用户不断刷新页面等行为带来的流量冲击？
- 活动还没开始，几十万人反复刷页面，后端怎么扛？

#### 面试回答

开抢前的流量特征是“读多、写零、高度重复”，处理原则是让这些请求根本不落到业务链路上：

- 页面与数据静态化上 CDN。
- 动态接口只留“是否开始、是否售罄、我的状态”这类极小查询。
- 时间口径统一到服务端，未开始直接返回统一结果，不回源。
- 对同一时刻的并发相同查询做请求合并。
- 活动前完成缓存与容量预热，并准备静态兜底页与降级路径。
- 刷新类只读接口与下单类写接口的配额分开统计，防止刷页面挤占写路径额度。

一句话收口：开抢前靠“把重复读往上层收敛”，开抢后才轮到限流与削峰兜底。

#### 技术细节

**静态化分层**

- 活动详情、规则文案、商品图与静态资源生成静态文件，走 CDN 与浏览器缓存。
- 把“千人不同”的部分（个人状态、是否已购）拆成独立小接口异步加载，让主页面保持可缓存。这是页面静态化能否成立的关键拆分。
- CDN 要同时配回源保护：回源限流与回源合并。否则缓存过期或命中率下降的瞬间，回源就会打穿源站。

**时间同步**

- 按钮可用性由服务端下发时间或服务端判定控制。
- 客户端时钟偏差与提前请求都不能触发真实写路径。
- 开抢前的提前打接口，本质是防刷问题，见 [[专题题库/系统设计#SYS-033：秒杀抢购如何防刷，前端防刷能挡什么、直连接口刷单怎么防？|SYS-033：秒杀抢购如何防刷]]。

**请求整形**

- 把固定间隔轮询改成带随机抖动的退避，避免整点同拍。
- 前端节流合并重复刷新。
- 服务端对同 key 的并发查询用请求合并（singleflight，只回源一次，其余等待复用）——与缓存击穿的互斥重建是同一手法（见 [[专题题库/Redis#REDIS-002：缓存穿透是什么，布隆过滤器能完全解决吗？|REDIS-002：缓存穿透与击穿处理]]）。

**预热**

- 热点数据提前进 Redis 与应用本地缓存。
- 连接池、线程池、JIT 与下游凭据缓存一并暖机，按压测水位扩容。
- 本地缓存短 TTL 会引入一致性窗口，需要配失效广播（[[专题题库/系统设计#SYS-009：多级缓存如何保持一致，并在 Redis 故障时降级？|SYS-009：多级缓存如何保持一致]]）。

**兜底**

- 详情查询失败时返回缓存旧值或默认文案，而不是报错打穿 DB。
- 准备静态兜底页与活动开关。

**异常流量治理**

- 高频刷新的 IP／设备走风控评分，降速或出验证。
- 但对真实用户只记指标、不断服务（误伤口径见 [[专题题库/系统设计#SYS-034：同一出口 IP 下大量真实用户同时抢购，限流怎么设计才不误伤？|SYS-034：同一出口 IP 下限流怎么设计]]）。

#### 深挖追问

1. **为什么不干脆禁止刷新？**（补充练习）

   因为刷新是用户确认“抢到没有”的自然行为，禁止会转成客服与投诉成本。工程上要做的是让刷新的读代价趋近于零（缓存与静态化），再对超常频率限流，而不是禁功能。

2. **CDN 缓存了页面，为什么后端还会被打挂？**（补充练习）

   因为把动态部分和鉴权部分也留在了主文档里，页面不可缓存，所有请求都得回源。解法是拆分静态主页面与异步小接口，并配回源保护与请求合并。

3. **开抢瞬间的“同拍”问题怎么处理？**（补充练习）

   三层各管一段：

   - 客户端侧：随机抖动与节流。
   - 服务端侧：请求合并与短 TTL 缓存。
   - 存储侧：库存与热点 key 打散（[[专题题库/Redis#REDIS-010：什么是热 Key，为什么危险，如何探测与解决？|REDIS-010：什么是热 Key]]）。

   只做客户端抖动，仍会把并发压力传到服务端。

### SYS-037：如何设计搜索框的实时输入联想（自动补全）？

**常见问法**

- 如何实现一个类似淘宝搜索框的实时商品名称模糊搜索功能？
- 实时输入联想与输入完成后点击搜索，在技术实现上有什么本质区别？
- 自动补全怎么支持拼音、首字母和错别字？

#### 面试回答

先把需求量化再谈结构：

- 每敲一个字符都要在几十毫秒内返回少量候选（一般 10 条以内），要求稳定快于一次完整搜索。
- 匹配要能覆盖前缀、拼音与少量容错。
- 排序以热度为主，可叠类目与个性化。
- 候选来自受控词表，而不是全库扫描。

分四层设计：

- 候选池与离线加工：
  - 从商品标题、类目词、历史高频 query 里构建词表，做规范化（大小写、全半角、繁简、空格与标点）。
  - 为每个词生成多个索引键：原词、全拼、首字母，必要时加 n-gram 或编辑距离容错键。
  - 热度分由点击与成交统计加时间衰减算出，离线批量生成、可回滚。
- 在线检索：
  - 首选前缀型结构：Elasticsearch 的 completion suggester（底层 FST 常驻内存，前缀匹配代价随输入长度而非词典规模增长，支持权重排序与多分析器拼音字段），或自建 Trie／FST 服务。
  - 再对超热前缀加一层 Redis ZSet 结果缓存（前缀→Top-N，短 TTL，头部前缀命中率极高）。
  - 纯子串与纠错匹配要走弱索引或 n-gram＋打分，只作为前缀未命中时的降级，因为它的代价高一个量级。
- 请求形态：
  - 客户端做 150～300ms 防抖。
  - 连续输入时取消上一次请求，或带序列号丢弃过期响应；否则会出现“输入越短结果越新”的乱序。
  - 请求超时兜底返回热门词，而不是返回空。
- 治理与验证：
  - 看词表更新的时效与回滚、无结果率、P95／P99 延迟、缓存命中率。
  - 还要按前缀长度看时延曲线。
  - 规模数字按【真实项目】填写。

“联想与点击搜索有什么本质区别”是这题的关键追问：

- 联想是高频、低延迟、小结果集、以候选词为产物的前缀查询。每次按键都可能触发，所以并发被放大数倍；必须靠常驻内存结构与缓存，结果可以容忍陈旧。
- 点击搜索是一次完整查询。要跑多字段过滤与相关性打分、聚合、个性化与分页，访问全量索引；结果要尽量新鲜，延迟预算可以放宽到百毫秒级。
- 两者常不共用同一条链路。用同一套硬扛，要么联想把打分集群打挂，要么正式搜索为迁就延迟牺牲排序质量。

#### 技术细节

**前缀匹配的三种承载方式各有代价**

- Trie：直观，但节点指针开销大。中文场景要靠压缩（双数组 Trie 或 FST）才可用。
- FST：把公共前缀与后缀都共享，内存小，且天然支持字典序范围扫描。代价是构建重、更新要重建，所以适合“离线全量生成＋定期发布”。
- 倒排＋`prefix` 查询：实现最省事，但延迟与内存受词表规模影响，需要限制字段与结果数。
- ES 的 completion 字段要放在专门的 suggest 索引里，不能开 doc values 之外的实时刷新幻想；词表更新走别名切换索引更稳。

**排序与个性化**

- 热度是主特征，但要防“长尾永不露出”：加探索位，或按前缀做冷启动兜底。
- 点击回流要处理位置偏差（排在第一的被点得多不代表更好），常用同前缀下的相对偏好或去偏统计。
- 个性化按用户画像与近期行为加权，但必须能降级成全局热度（新用户与关闭个性化的场景）。

**容量与稳定性**

- 联想接口的 QPS 常是主搜索的数倍，要单独限流与配额，别和正式搜索共用一个线程池（一个慢会拖垮另一个）。
- 缓存键要包含归一化前缀与语言／人群分桶，但分桶过细会让命中率崩塌。
- 超时要设得比正式搜索更短（例如 50ms 级），超时直接返回缓存或热门词。
- 词表更新期间的双写与切换，要保证候选不会突然变空。
- 模糊与纠错要有阈值控制：过度纠错会返回不相关词，宁可无结果也不误导，电商场景尤其如此。
- 协议与请求形态的选择见 [[专题题库/计算机网络#NET-016：SSE 和 WebSocket 有什么区别，如何选择？|NET-016：SSE 和 WebSocket 有什么区别，如何选择]]（联想场景用短请求＋取消即可，不必上长连接）。

#### 深挖追问

1. **词表多大能用内存装下，多大就要换方案？**（补充练习）

   要给估算过程而不是结论。量级估算：千万级短词经 FST／双数组 Trie 压缩后，通常在百 MB 到数 GB 区间，可以常驻；到亿级或需要复杂相关性时，改用分布式检索服务、分片前缀路由，或退化为“热词进内存＋长尾走倒排”的两级结构。

2. **为什么用户输入很短时结果反而更难做好？**（面经实际出现；[[面经/字节/一面/0009#Q10：如何实现一个类似淘宝搜索框的实时商品名称模糊搜索；实时输入联想与输入完成后点击搜索在技术实现上有什么本质区别？|MJ041 · 字节 · 一面 · Q10]] 的延伸）

   两个原因叠加：一个字符的前缀候选量极大、信息量几乎为零，排序只能靠热度与个性化先验；同时这一档请求量最大（所有人都会走到）。所以常见做法是超短输入直接返回运营配置的热门榜单，不做实时计算，把算力留给长度≥2 的请求。

3. **怎么衡量联想做得好不好？**（补充练习）

   - 离线：候选覆盖率（用户最终搜索词是否出现在其前缀的候选里）与排序命中（MRR／Top-1 命中率）。
   - 在线：补全点击率、输入完成前的放弃率，以及由此带来的搜索耗时下降。
   - 还要盯无结果率与延迟分位。

   只报“点击率提升”而不说口径与实验设计，会被继续追问。

### SYS-038：如何设计一个 RPC 框架，性能优化有哪些抓手？

**常见问法**

- 了解 RPC 框架吗？让你设计一个 RPC 框架，应该包含哪些关键部分？为什么？
- 为了提高 RPC 传输的性能，可以在哪些方面做优化？

#### 面试回答

设计题按“一次远程调用要跨过哪些坎”拆模块，每个都答“缺了会怎样”：

- 服务代理：让用户像调本地方法一样调远程——动态代理把接口方法转成请求；没有它，业务代码就得手写网络调用。
- 序列化：对象↔字节；要可插拔（JSON 调试友好，protobuf／Hessian 紧凑快速），跨语言时选型决定协议形态。
- 网络与协议：长连接＋自定义二进制协议头（魔数、版本、序列化类型、消息类型、请求 ID、长度）；长度字段解决粘包拆包，请求 ID 让响应乱序也能配对；底座通常是 Netty 这类 NIO 框架。
- 服务发现：注册中心＋心跳剔除，消费端拿到 provider 列表；没有它，调用方只能写死 IP。
- 路由与负载均衡：随机／轮询／加权／最少活跃／一致性哈希，叠加同机房优先、灰度标签路由。
- 容错与治理：超时是第一保险（重试必须配幂等）、快速失败／故障转移／降级策略；再加限流与鉴权。
- 异步化底座：请求发出即返回 future，响应到达按 ID 唤醒——不做这步，并发上限被同步阻塞钉死。
- 收尾：Dubbo／gRPC／Thrift 就是这套骨架的不同装配，能对照实例比空谈架构有说服力（服务治理背景见 SYS-029）。

#### 技术细节

**性能优化按“一次调用的耗时构成”逐项压**

- 序列化：换二进制＋schema（protobuf）；接口动态代理与序列化器的结果要缓存，别每次反射现算。
- 连接：长连接复用＋多路复用（同一条连接并行多请求，靠请求 ID 区分），消灭 TCP 建连与队头等待。
- 协议：头部紧凑定长、字段对齐；大包才压缩（压缩本身花 CPU，小包负收益）。
- IO：epoll／io_uring 事件驱动、避免用户态多次拷贝（堆外缓冲＋零拷贝 writev／sendfile 思路，OS-018 同源）。
- 线程模型：IO 线程与业务线程池分离，慢业务不堵事件循环；不同服务按池隔离。
- 寻址：注册信息本地缓存＋长轮询／watch 增量更新，把“查注册中心”从每次调用里拿掉。
- 进阶：连接预热、TCP_NODELAY、内核旁路（RDMA／DPDK）属于特定规模才谈的手段，面试点到为止。

**协议头为什么必须有版本与序列化类型**

- 线上永远新老版本共存：版本字段让兼容策略有处安放；序列化类型字段让“换协议不换框架”成为可能——这两个字段是“可演进性”的最低成本投资。

**容易漏的非功能项**

- 可观测性：调用链 traceId 透传进协议头，配合指标出慢调用看板；没有观测的框架上线就是黑盒。
- 优雅停机：先摘流量再退连接；注册中心下线事件要等消费端感知。

#### 深挖追问

1. **RPC 和 HTTP API 怎么选？**（补充练习）

   内网服务间高频调用选 RPC（二进制紧凑、长连接多路复用、治理配套）；对外开放／跨组织选 HTTP（通用、缓存与网关生态齐全）。gRPC 本质是“HTTP/2 上跑 protobuf”，是两者的折中。

2. **同步调用为什么危险，超时到底该谁定？**（补充练习）

   同步链路过长会做故障乘法（每层等待叠加，雪崩）；超时预算要从入口总预算逐层分配（下游超时必须小于上游），调用方定“可容忍上限”，提供方文档给“典型耗时”——两头都要有数。

### SYS-039：Zookeeper 和 Raft 这类一致性协议是怎么回事？

**常见问法**

- 知道 Zookeeper 和 Raft 这些一致性协议吗？

#### 面试回答

第一步就把“系统 vs 协议”分清：

- Zookeeper 是分布式协调系统（数据结构是 znode 树＋事务），它内部共识用的是 ZAB 协议；Raft 才是共识协议本身——被问“ZK 的协议叫什么”答 ZAB 是本题第一道分水岭。
- 一句话本质：共识＝一组节点对“操作日志的顺序”达成一致，让整组对外表现得像一台不会出错的机器（replicated state machine）——选主只是给日志定序权一个唯一归属，日志多数派确认才算提交。
- Raft 两块：选主（term 任期＋随机超时选举＋一票一任期）；日志复制（leader 收请求→append→过半 ack→commit→顺序应用）。
- 多数派（quorum）为什么防脑裂：网络分区最多切出一个能凑齐 N/2+1 的侧，另一侧选不出主、写不进去——牺牲分区那侧的可用性换不写错（CP，对照 SYS-031）。
- 用途报场景：分布式锁／选主（ZK 临时顺序节点）、注册中心与配置（etcd＝Raft 系）、Kafka 控制器迁移（KRaft 去 ZK）都是这套机制的应用层。

#### 技术细节

**共识 ≠ 线性一致的读**

- ZK 的读默认走被访问的 follower，可能读到旧状态；要线性一致读得 `sync()` 或走新加的 read 机制——“用了 CP 协议所以读永远新”是常见过头话。
- 写侧同理：客户端拿到“写成功”要过 leader＋多数派这一跳；会话超时窗口内临时节点消失，锁的“ fencing token／单调序号”兜底要另做。

**和 2PC 的区别是这题的高频追问**

- 2PC 有协调者单点＋参与者同步阻塞（协调者挂了大家悬着）；共识协议去中心化：任何多数派子集可继续推进，挂掉重新加入后靠日志追平——它把“谁来决定”也变成被共识的对象。
- TCC／Saga 解决的是另一问题（业务层分布式事务，见 SYS-041），不要拿共识协议去混答。

**ZAB 与 Raft 的细节差**

- ZAB 聚焦崩溃恢复（先同步 leader 历史再服务）＋原子广播，epoch 式的事务编号；Raft 把成员变更（joint consensus）和日志补齐规则设计得更教科书化，生态靠论文与 etcd／TiKV 等实现。
- Paxos 是理论源头（多轮提案、无主也可推进但实践中通常也上 leader）；面试不必展开三轮细节，报得出谱系即可。

#### 深挖追问

1. **Kafka 为什么从 ZK 迁到 KRaft？**（补充练习）

   元数据变更要过 ZK 与 broker 心跳两套通道，规模上限与运维复杂度都被 ZK 卡住；KRaft 把控制器也纳入 Raft 日志，元数据变更本身可回放、可扩展，还少养一套外部依赖。

2. **etcd 的 Raft 和 ZK 的 ZAB 怎么选？**（补充练习）

   接口与生态优先：Kubernetes 体系默认 etcd（gRPC＋lease＋watch）；已有 ZK 生态（Dubbo 注册、Kafka 老版本、HBase）沿用 ZK。协议层差异不足以做决策，运维与生态才是。

### SYS-040：消息队列的 exactly-once 是怎么做到的？

**常见问法**

- 消息队列中 exactly-once（恰好一次／仅一次）是怎么做到的？

#### 面试回答

先破概念：网络上“只投递一次”物理做不到（任何确认都可能丢），工程上的 exactly-once 指**效果恰好一次**——不丢＋重复不改变结果：

- 生产侧：确认机制保不丢（at-least-once）；Kafka 幂等生产者用 PID＋分区序列号让重发在 broker 端去重——只解决“单分区单会话”的重复。
- 消费侧：处理成功再提交 offset 防丢；宕机重启必然有重复窗口，所以最终防线是消费幂等——唯一业务键（订单号）去重表、状态机版本号、天然幂等的 SQL（`UPDATE ... WHERE version=?`）。
- 事务形态：把“提交 offset”和“写出业务结果”塞进同一个事务——本地事务表／outbox（MySQL 事务里写结果＋发消息记录，另一条链路可靠投递）；Kafka read-process-write 用事务把 offset 提交与输出写绑定（EOS 只在 Kafka 闭环内成立）；Flink 两阶段提交把 checkpoint 作为事务协调点对齐 source offset 与 sink。
- 收口一句：跨系统（DB＋MQ＋外部 API）就没有免费的 exactly-once，只有“至少一次投递＋全链路幂等”拼出来的效果一次——先设计幂等，再选投递语义。

#### 技术细节

**为什么 at-most-once 不算解决方案**

- 发送后不等确认（fire-and-forget）确实“最多一次”，但代价是允许丢——除日志打点这类可弃数据，业务链路不可接受；三档语义要按“丢了会怎样／重了会怎样”选，不是按名字好听。

**幂等的三个实现层次**

- 存储层唯一约束：插入去重表＋唯一索引，冲突即已处理——最简单可靠。
- 状态机层：只允许合法迁移（重复消息遇到非预期状态直接 ack 丢弃并计数告警）。
- 计算层：幂等函数（同输入多次处理结果一致），金额汇总这类用“按事件重算”代替“增量累加”。

**Kafka 事务的边界**

- 事务原子性覆盖“同组消费＋多分区产出”，且不包含外部系统；把 MySQL 写塞进 Kafka 事务是做不到的——那种需求回到 outbox／事务消息（半消息＋回查）方案。
- 幂等生产者默认开着也防不了“业务重发不同消息”——它是会话内去重，不是业务去重。

#### 深挖追问

1. **消费失败重投会不会把幂等设计绕过？**（补充练习）

   不会，前提幂等键选得对：重投消息必须携带同一业务唯一键（而不是 MQ 自己生成的新 ID）；重试包装层换新消息体的场景要在生产侧固定幂等键。

2. **延迟与 exactly-once 冲突吗？**（补充练习）

   事务提交才能对外可见，端到端延迟被事务周期拉高——所以行情推送这类“过时即无意义”的场景宁可 at-most-once；语义选择跟着业务代价走。

### SYS-041：数据库的一致性、分布式事务的一致性、复制的一致性是一回事吗？

**常见问法**

- 你怎么理解数据库中的一致性？
- 分布式事务的一致性和数据库的一致性有什么区别？

#### 面试回答

同一个词三个坐标系，先分层再对比：

- 数据库 ACID 的 C（单库内）：事务把数据从一个合法状态搬到下一个合法状态——约束不被违反（唯一、外键、业务不变量如转账两边总额）；它是目标不是机制，由 AID＋正确 SQL 共同兑现。
- 分布式事务的一致（跨库／跨服务）：多个本地事务“要么都成要么都败”——协调者缺席时单机机制保不了跨边界，只能协议逼近：2PC／3PC（同步阻塞、协调者单点）、TCC（业务层 Try-Confirm-Cancel 三接口）、Saga（正向链＋补偿链）、事务消息／本地消息表（放弃强一致换最终一致）。
- 复制一致性（多副本读到什么）：强一致读／会话一致／最终一致——主从延迟、多活回灌都属这层，与“事务原子不原子”无关。
- 三句对比收尾：作用对象（单库数据状态 vs 跨边界事务结果 vs 副本间可见值）；实现手段（锁日志 MVCC vs 协调协议与补偿逻辑 vs 复制协议）；强度现实（DBMS 能承诺 vs 多数只能最终一致，强一致要付吞吐与可用性）。

#### 技术细节

**2PC 的“一致”卡在哪**

- commit 决策前的 suspend 阶段参与者攥着锁等待——协调者此刻宕机，其余参与者无法自作主张（阻塞）；3PC 加超时与 CanCommit 缓解但仍需假设网络时界；共识协议（SYS-039）把决策者本身复制起来才真正消除单点阻塞。

**TCC／Saga 的一致是“业务语义”的**

- TCC 的 Cancel 要可重复执行且防悬挂（空回滚、迟到 Try）；Saga 补偿不是回滚——发出去的短信补不回来，补偿逻辑是“做一件反向的事”，业务上要提前设计成可反向。
- 这层含义：分布式事务的一致性是业务不变量级别的，不是存储引擎 undo 级别的。

**面试陷阱句**

- “分布式事务保证强一致”——过话：多数方案只保证最终一致＋收敛时限；要强一致得限制单库事务或上共识存储，写清代价再承诺。

#### 深挖追问

1. **Seata 这类框架属于哪种？**（补充练习）

   AT 模式近似“自动化的 2PC＋反向 SQL 补偿”（全局锁隔离），TCC／Saga／XA 各有实现——选型看隔离要求与是否接受反向补偿；它没有消除 CAP 约束，只是把协议成本工程化。

### SYS-042：Kafka 消费者 Rebalance 的机制与触发时机是什么，怎么减少影响？

**常见问法**

- Kafka 的 Rebalance 机制了解吗？什么时候会触发？
- 频繁 Rebalance 有什么危害，怎么避免？

#### 面试回答

Rebalance 是消费者组内重新分配“谁消费哪些分区”的协调过程，核心目标是同一分区在任意时刻只被组内一个消费者持有。

触发时机分三类：

- 组成员变化：新消费者加入、消费者正常离组、或消费者被协调器判定失效（`session.timeout.ms` 内没发心跳）。
- 订阅的 topic 分区数变化：新增了分区，需要重新分给组内成员。
- 消费太慢被踢：在 `max.poll.interval.ms` 内没处理完上一批、没有再次 `poll`，被判定“卡死”而移出组。

过程一句话：Group Coordinator 选组内一个消费者当 leader，由 leader 按分配策略（range／roundrobin／sticky／cooperative-sticky）算出分配方案，交回 coordinator 下发给所有成员。

#### 技术细节

**为什么 Rebalance 是“昂贵的”**

- 经典 eager 协议（`assignor` 默认走的是先全收再分配）在重分配前会 revoke 所有分区，期间整个组停止消费——所谓 stop-the-world。
- 处理到一半的消息会被回滚到上次提交的 offset，重分配后由新 owner 重新拉取，带来重复消费，所以消费逻辑要幂等。

**cooperative（增量）再均衡**

- 新协议（`ConsumerCooperativeRebalance`／KIP-429）改为分多轮、只回收“要换主”的分区，其余分区继续消费，避免一次性全部暂停。
- 用 `group.protocol=consumer`（新一代服务端分配，KIP-848）能进一步降低大组的 Rebalance 抖动。

**参数怎么调**

- `session.timeout.ms` 与 `heartbeat.interval.ms`：心跳间隔一般设成超时的 1/3，太小易误判网络抖动、太大故障发现慢。
- `max.poll.interval.ms`：单批处理必须在此时间内做完，批太大就调小 `max.poll.records`，别把重逻辑放 poll 循环里。
- `enable.auto.commit`：自动提交按间隔触发，可能与处理进度错位；要精确控制就手动提交 offset。

**避免把它当调优的万能药**

- 频繁 Rebalance 通常是消费慢或实例反复重启的信号，应优先解决处理耗时／部署健康度，而不只是放大超时参数。

#### 深挖追问

1. **Rebalance 期间怎么保证不重复、不丢消息？**（补充练习）

   Kafka 只给“至少一次”，端到端要靠：消费端处理完再手动提交 offset（配合幂等消费或唯一键），避免“提交了但没处理”或“处理了没提交”。

2. **消费者组里消费者比分区多会怎样？**（补充练习）

   多出来的消费者空闲无分区可消费——并行度上限是分区数，加消费者超过分区数不会提升吞吐，只会增加 Rebalance 面。

### SYS-043：RocketMQ 的延迟消息是怎么实现的？

**常见问法**

- RocketMQ 延迟消息底层原理、如何实现？
- 定时／延迟消息在分布式下怎么调度处理？

#### 面试回答

延迟消息＝发送后到设定时间才对消费者可见。开源 RocketMQ 4.x 是固定延迟级别（18 级：1s、5s、10s、30s、1m、2m…2h），不是任意时刻。

实现靠“先藏后放回”：

- 发送时把消息的实际 topic／queue 存进消息属性，然后把消息改写投递到内部 topic `SCHEDULE_TOPIC_XXXX`，不同延迟级别对应不同队列（queueId = level − 1）。此时普通消费者订阅不到它。
- Broker 侧 `ScheduleMessageService` 为每个延迟级别起一个定时任务，按队列顺序扫描，用“当前时间 − 消息存储时间 ≥ 该级别延迟时长”判断到期。
- 到期的消息还原真实 topic／queue，重新写入正常队列，这时才对消费者可见、可被消费。

#### 技术细节

**为什么用队列分隔级别**

- 同一队列内的消息存储时间单调递增，扫描只需从头判断第一条是否到期，到一条就顺序取一批，无需对全部消息排序或建索引。

**分布式任务怎么处理（本题真正问的点）**

- 没有中心调度器：延迟消息就存在各 Broker 自己的 commitlog 里，`ScheduleMessageService` 只扫描本机存储，天然是“按存储分片、各自本地处理”，不需要跨节点协调。
- 主从下由 Master 负责到期重新投递，Slave 只做数据备份，避免同一消息被两个节点各放回一次造成重复。
- 到期精度受扫描周期（默认约 1s 级）影响，是“秒级近似”，别承诺严格准时。

**版本差异要说清**

- 4.x：只有固定 18 级，业务要任意延迟得自己映射到最近级别，或用多次短延迟接力。
- 5.x：支持任意时间定时消息，底层用时间轮（Timing Wheel）＋专门的定时消息存储层，精度与灵活性更好。

**与其他方案的对比**

- RabbitMQ 用 TTL＋死信队列（DLX）模拟延迟；Redis 用 zset 按到期时间排序＋轮询；Kafka 原生不支持延迟，需分级 topic＋调度消费者。RocketMQ 是少数把延迟／定时做成一等能力的 MQ。

#### 深挖追问

1. **时间轮为什么适合定时任务？**（补充练习）

   把到期时间映射到环上的槽位，指针每 tick 前进一格处理该槽任务，插入／到期触发接近 O(1)，避免“每次取堆顶”的 O(log n)；层级时间轮用进位表示更长的延时。

2. **延迟消息投递失败或重复怎么办？**（补充练习）

   到期重投本质是一次普通发送，仍受 RocketMQ“至少一次”约束，消费端要做幂等；Broker 宕机重启后 `ScheduleMessageService` 会从存储进度继续扫描，不丢已落盘的延迟消息。

### SYS-044：数据同步用 Canal（CDC）还是业务发 MQ，怎么选与怎么量化对比？

**常见问法**

- ES 与 MySQL 的数据同步，基于 Canal 和基于 MQ 两种方案哪个更好？如何做对比测试得到量化结果？
- 同步链路选 CDC 还是业务双写发消息，怎么论证？

#### 面试回答

结论：这题常是概念混淆题——Canal 是「变更怎么采集」（CDC，伪装成 MySQL 从库读 binlog），MQ 是「消息怎么传输」，两者常常是上下游而非竞品。

- 把问题还原成真正的选择：变更采集靠**集中订阅 binlog**，还是靠**业务代码在写库后发同步消息**。
- CDC 侧优点：业务写入口零改动、不会漏掉别处的写（运维脚本、其他服务直连库）、binlog 是单一事实源。
- CDC 侧代价：多一套组件要运维、延迟受解析与攒批影响、表结构变更要同步维护映射。
- 业务发消息侧优点：链路自己可控、消息能带业务语义与上下文、不引入中间件；代价是每个写入口都要改，漏一处就永久不一致，还要处理事务与发送的先后（本地消息表／事务消息）。
- 选型口径：写入口多或改不动、能容忍秒级 → 偏 CDC；写入口少且可控、需要业务语义 → 偏 MQ；要一对多广播与削峰就组合「Canal → MQ → 多下游」。

#### 技术细节

**两个方案的链路**

- CDC：业务写 MySQL →（主库）binlog → Canal server 解析行事件 →（可选投 MQ 缓冲）→ 消费者 bulk 写 ES。
- 业务双写：业务在同一流程里「写 MySQL ＋ 发 MQ」→ 消费者写 ES。

**CDC 的隐性约束**

- 只拿得到「行变了」，拿不到「为什么变」；下游需要业务上下文时得靠额外字段或再查一次。
- 依赖 ROW 格式与主键；表结构变更（DDL）期间映射要跟上，否则整条链路阻塞。
- 保序靠按主键 hash 分区；跨分区没有全局顺序，追求全局限序就只能退回单管道。
- 运维面：位点管理、断线重投、大事务回放、canal server 高可用。

**业务双写的隐性成本**

- 先写库后发消息：消息可能丢（进程在两步之间挂掉）；先发消息后写库：回滚了消息已出去。
- 本地消息表：与业务写同事务落一条待发表达「至少一次」，定时任务重投，消费端必须幂等。
- 事务消息（RocketMQ）：半消息＋本地事务＋回查，同样只保证至少一次，消费端仍要幂等。
- 遗漏风险随写入口数量线性增长，这是它最难被验收的部分。

**对比测试怎么设计才有量化结论**

1. 固定变量：同一份数据、同一读写模型、同一硬件与 ES 集群配置，两条链路各独立跑一遍，只换「变更采集方式」这一项。
2. 定义指标（每条都要有口径）：
   - 端到端延迟：主库提交 → 目标端可查，用带事件时间戳或探针行测，报 P50／P99，不报均值。
   - 吞吐：持续写入下能跟得住的最大 TPS，以及开始积压的拐点。
   - 一致性：对账作业统计的差异条数与收敛时间（跑完后多久两边相等）。
   - 故障表现：停消费端 5 分钟、杀同步进程、DDL 变更三种场景各自的恢复时间与是否需要人工补数。
   - 成本：代码改动量与接入工时、运维组件数、告警项数量。
3. 负载形态分三种跑：恒定 TPS（基线）、阶梯上升（找拐点）、突发洪峰（看积压与恢复）。
4. 结论写成条件句：「在【写入口数量／可容忍延迟／数据量级】下选 X」，不给无条件答案。

**容易说过头的地方**

- 「CDC 零延迟」：CDC 也有解析与攒批开销，亚秒级是常见量级而非零。
- 「业务双写更简单所以更好」：单看一次写入是简单，看全部写入口和补偿逻辑就反过来。
- 「上了 MQ 就有序」：只有同 key 落同分区才有序；也别忘了引入 MQ 后语义是至少一次。
- 「Canal 和 MQ 二选一」：真实系统常常是 Canal 投 MQ，把两者当链路上的两段来比较是错的框架。

### SYS-045：如何设计一个支持几十万 QPS 的短链系统？

**常见问法**

- 设计一个短链系统，点击短 URL 能跳转到长 URL，支持几十万 QPS，要保证高可用和稳定，怎么设计？
- 短链服务怎么扛读流量？跳转用 301 还是 302？

#### 面试回答

结论：短链是「一次写、反复读」的 KV 查询系统——发号与编码只在创建时做，读路径只做查表＋跳转，几十万 QPS 靠多级缓存和无状态横向扩。

- 链路：用户点击 → DNS／CDN 或四层入口 → 无状态跳转服务查映射 → 302 到长链。
- 写路径：生成 ID → 编码成短码 → 落库（真相源）→ 同步预热缓存；跳转接口不写任何状态。
- 读路径：进程内本地缓存 → Redis 分片 → KV／MySQL 分片，越靠前越便宜。
- 高可用：服务多实例多机房、缓存与存储多副本、入口限流熔断、缓存不可用时降级读 DB 并限并发。
- 稳定性：短码定长、字符集固定；跳转必须可统计，所以默认用 302 而不是会被浏览器长期缓存的 301。

#### 技术细节

**先问清三件事，设计才会不同**

- 读写比例：短链通常是几千比一，决定成本全压在读侧。
- 是否需要点击统计：要统计就不能让浏览器长期缓存跳转（301 会被缓存，后续点击不再访问服务端）；度量场景基本选 302／307。
- 是否允许重复创建：同一长链多次创建是复用同一短码，还是各给一个新短码——前者需要按长链建唯一索引或哈希分桶去重，代价是写路径多一次查询。

**容量估算的讲法**

- 先给量级再给依据：几十万 QPS 的读，单进程本地缓存命中可撑大部分；出网请求按命中率折算，Redis 分片数按单分片安全 QPS 除出来。
- 存储侧按写入 TPS 与保留期估算行数，而不是按读 QPS 估算——读靠缓存。
- 一句话带过带宽：跳转响应很小，瓶颈通常在连接数与查询次数，不在字节数。

**分层缓存为什么这样排**

- 本地缓存：纳秒到微秒级、不出网，是几十万 QPS 能落地的主力；代价是一致性窗口和每台机器的内存占用。
- Redis：容纳全量热集合，扛本地未命中；单 key 过热要拆副本 key 或用多分片（见 [[#SYS-009：多级缓存如何保持一致，并在 Redis 故障时降级？|SYS-009：多级缓存一致性与降级]]）。
- 持久层：按短码分片（哈希或范围），只承接缓存未命中与写。

**高可用与故障预案**

- Redis 整体不可用：本地缓存续命＋DB 读取限并发，超过阈值直接返回兜底页，避免连接池被拖死。
- 某机房故障：DNS／全局负载均衡切流量；短码是无状态的，切过去就能读，不需要数据搬迁。
- 缓存重建风暴：同 key 并发回源用请求合并（singleflight）收敛成一个（见 [[#SYS-020：多类请求的任务队列如何保证公平、防止一类占满资源？|SYS-020]] 的配额思路与 [[专题题库/Redis#REDIS-010：什么是热 Key，为什么危险，如何探测与解决？|REDIS-010：热 Key]]）。
- 发布与回滚：映射数据结构只加不减，新老版本可共存。

**运维面容易被忽略的点**

- 短码要防枚举：如果 ID 单调且编码保序，攻击者可以批量猜测相邻短码；要么加随机化，要么在入口限频＋异常流量封禁。
- 长链要有校验与白名单策略，否则短链服务会被拿来跳转钓鱼站点——这是内容安全问题，不是性能问题。
- 跳转日志本身就是数据产品：异步落盘（消息队列→数仓），不要在请求线程里同步写。

**容易说过头的地方**

- 「加 Redis 就够扛几十万 QPS」：单分片热点仍然会打爆，要配合本地缓存与热 key 打散。
- 「用 CDN 缓存跳转」：CDN 缓存 302 会让点击统计丢失，是否可缓存要按业务口径决定。
- 不要承诺「强一致的短链缓存」：缓存与库之间存在窗口，能接受的前提是短码一旦生成就不变更指向。

#### 深挖追问

1. **短链服务要不要做鉴权和限频？**（补充练习）

   读跳转一般不鉴权（用户点击无会话），但要按 IP／UA 限频防爬；创建接口必须鉴权，并按调用方配额限流，否则会被刷爆存储。

2. **一个短码对应的长链要改了，怎么处理？**（补充练习）

   短码不变、改映射是危险操作：缓存与 CDN 里的旧值会让不同用户跳到不同目标。稳妥做法是新增短码并让新入口用新码，旧码保留只读，过期后再回收。

3. **跳转服务需不需要预取长链的 DNS／连接？**（补充练习）

   不需要。302 只是把地址交给浏览器，服务端不去拉长链内容；真正需要预取的是点击日志落库和长链有效性巡检这类旁路任务。

4. **新建的短链刚投放就是热点，缓存里没有怎么办？**（面经实际出现；[[面经/字节/一面/0011#Q12：新短链是热点且 Redis 没缓存，请求全打到数据库，这种场景怎么解决？|MJ066 · 字节 · 一面 · Q12]]。原素材未记回答，以下为参考）

   这是「首次访问即热」，不是穿透也不是过期击穿：靠写时预热＋读时请求合并＋DB 并发上限处理，展开见 [[#SYS-045：如何设计一个支持几十万 QPS 的短链系统？|SYS-045]] 与 [[专题题库/Redis#REDIS-010：什么是热 Key，为什么危险，如何探测与解决？|REDIS-010：热 Key]]。

### SYS-046：分布式 ID 怎么发——自增 ID 扛得住吗、号段模式、雪花算法与字符串编码

**常见问法**

- 基于数据库的自增 ID 去做，数据库能扛住压力吗？
- 通常不会直接暴露 ID，需要把 ID 映射成一段字符串作为短链，应该怎么做？
- 用雪花算法得到的是 64 位整数，如何把它编码成字符串？
- 分布式 ID 有哪些方案，怎么选？

#### 面试回答

结论：数据库自增扛读不扛写——发号是单行争锁的串行点，量级到千级 TPS 就要改成号段预取或独立发号服务。

- 号段模式：一次从库里取一批（如 1000 个）在内存中发放，用完再取下一批；DB 压力按号段大小成比例下降。
- 双 buffer：当前号段消耗到阈值就异步预取下一段，避免用完瞬间的取号毛刺。
- 雪花算法：不依赖 DB，本地生成 64 位整数——符号位＋毫秒时间戳＋机器号＋序列号；代价是要解决时钟回拨与机器号分配。
- 其他：多库不同步长（简单但有空洞）、Redis INCR（快但引入持久化与可用性依赖）。
- 编码成字符串：定长十进制太长，一般 Base62 压到 11 位内，或按字段分段编码（可解释、长度固定）。

#### 技术细节

**自增 ID 为什么是串行点**

- 单表 AUTO_INCREMENT 需要为每个新行分配递增值，高并发插入在同一表的索引尾部争抢，且事务回滚会造成空洞。
- 主从架构下所有写落主库，发号 TPS 就等于主库写 TPS 的一部分，无法靠加从库扩展。
- 结论口径：自增 ID 作为「表内主键」没问题，作为「对外短码的唯一来源」要先做号段化。

**号段模式的关键实现点**

- 表结构：`(biz_tag, max_id, step)`，取段语句是 `UPDATE ... SET max_id=max_id+step WHERE biz_tag=?` 后读回，一个事务完成。
- 双 buffer：持有当前段与下一段两个内存区间，消耗到一定比例（常见 10%～20% 量级，按实现调）异步加载下一段。
- 失效行为：进程重启会丢掉未用完的号段——只是空洞，不影响唯一性；DB 短时不可用时，剩余号段还能撑一阵，这是它的优点。
- 参考实现：美团 Leaf 的 segment 模式（另有基于 ZooKeeper 的 snowflake 模式分配 worker id）。

**雪花算法的位分配与约束**

- 常见布局：1 位符号 ＋ 41 位毫秒时间差（约 69 年）＋ 10 位机器号（1024 个节点）＋ 12 位同毫秒序列（4096 个），拼成 64 位整数。
- 时钟回拨：小回拨可以等待或把回拨量记下来在恢复前禁用；大回拨要么报警停发，要么切备用位段——不能简单「继续发」，否则可能重复。
- 机器号分配：容器环境 IP 会变，需要注册中心或配置中心显式分配（Leaf-snowflake 用 ZK 顺序节点）。
- 趋势递增不等于全局有序：跨机器、跨毫秒只保证整体随时间上升，单机内严格递增。

**64 位整数怎么变短字符串**

- 十进制字符串最长 20 位（int64 上限约 9.2×10^18），太长；Base62 下 62^11 ≈ 5.2×10^19 > int64 上限，所以最长 11 个字符。
- 想要更短就少放信息：只编码「业务前缀＋时间差分桶＋序列」并按需要的字符集定长，比整包 Base62 更短，但必须保证映射唯一。
- 分段编码更利于排障：把时间戳、机器号、序列分别编码后拼接，长度固定、可读回，适合日志排查。
- 编码是可逆的进制转换，不是哈希：见 [[专题题库/算法与数据结构#ALG-048：如何做 ID 与短字符串之间的进制转换（Base62 编解码）？|ALG-048：Base62 编解码与进制转换]]。

**哈希映射和编码映射的区别（这题的常见误区）**

- 编码（进制转换）：一对一可逆，不产生冲突，长度由数值范围决定。
- 哈希（如把长链 URL 哈希成短码）：会冲突、也会把已删除的码位占用，需要「冲突重试＋唯一索引校验」，且不可逆，仍需存映射。
- 所以短链系统一般用「先发号、再编码」，把冲突问题消掉，而不是靠哈希去撞。

**选型口径**

- 只要唯一、不要求趋势递增：UUID 或随机数即可，但作为主键会让 B+ 树写入散乱（作为主键会让 B+ 树写入散乱，见 [[专题题库/MySQL#MYSQL-026：三层 B+ 树能存多少数据，怎么估算？|MYSQL-026：三层 B+ 树容量估算]]）。
- 要趋势递增＋高并发发号：号段服务。
- 要完全本地生成、低延迟：雪花，接受 worker 管理与回拨处理成本。

#### 深挖追问

1. **号段用完时 DB 正好不可用怎么办？**（补充练习）

   只能让请求排队或失败——所以实现里要用双 buffer 提前预取，并把「取段失败」做成有退避的重试；号段步数是可用性缓冲，越大越抗 DB 抖动、但重启丢号越多。

2. **发号服务自己变成单点怎么办？**（补充练习）

   发号服务无状态多实例部署，靠底层存储（DB 行锁／ZK／Redis）保证不同实例拿到的号段不重叠；这也是为什么「纯内存自增多实例」一定错。

3. **短码要不要防遍历？**（面经实际出现；[[面经/字节/一面/0011#Q12：新短链是热点且 Redis 没缓存，请求全打到数据库，这种场景怎么解决？|MJ066 · 字节 · 一面 · Q12]]。原素材未记回答，以下为参考）

   趋势递增的 ID 直接编码就是可枚举的：相邻短码可被批量猜测。常见做法是短码层面加扰动（打乱字符表、按 key 加盐置换），或在入口做频率限制＋异常封禁——需要严格不可预测时，改用随机短码＋唯一索引冲突重试。

### SYS-047：数据迁移引擎如何设计，任务挂掉后怎么保证不丢、不乱序？

**常见问法**

- 数据迁移引擎是如何设计的？
- 异步迁移过程中如果任务挂掉了，怎么保证数据迁移成功、不丢失、顺序不乱？

#### 面试回答

结论：迁移按五步走——全量快照、增量追平、双写对账、切流、下线；可靠性靠「位点先落盘＋按 key 分区保序＋目标端幂等 upsert」。

- 拆分单元：按主键区间或分片切成可独立完成的小任务，每个任务有自己的状态（待迁移／进行中／已校验）。
- 不丢：每条数据的读取位点（或任务完成标记）先持久化再提交进度；进程重启从最后确认位点续跑。
- 不重：目标端用按主键 upsert 或带去重键的幂等写，重放同一条不会产生两份。
- 不乱序：同一 key 的变更必须落同一分区、由同一条串行队列应用；跨 key 不承诺全局顺序。
- 校验与补偿：迁移后比行数、抽样比字段，差异记录进补偿任务；切换期保留回滚窗口。

#### 技术细节

**两类迁移，方案不同**

- 一次性搬迁（换库、分库分表扩容）：全量＋增量追平＋切流，重点是「切」的动作可回退。
- 持续同步（CDC、跨机房、异构索引）：长期存在的链路，重点是延迟、位点管理与对账（见 [[#SYS-044：数据同步用 Canal（CDC）还是业务发 MQ，怎么选与怎么量化对比？|SYS-044]]、[[#SYS-024：canal／binlog 订阅同步延迟如何归因与优化？|SYS-024]]）。

**崩溃恢复的三个必备件**

- 位点／检查点：记「已确认应用到目标端的最后位置」，落 WAL 或元数据表；位点必须与幂等粒度一致，否则会重复应用或漏应用。
- 任务状态机：每个分片任务有明确状态与可重入的执行体；失败重试不靠「接着上次内存状态」，靠重新读取位点。
- 幂等写：目标端以主键或业务唯一键覆盖写；无法覆盖写的存储要维护「已应用 ID 集合」判重。

**顺序保证的真实边界**

- 只有分区内有序：按 key 的哈希分区让同一实体的变更进同一队列，这是可承受的并行度上限。
- 要求全局有序就只能单分区单线程，吞吐直接封顶；DDL、事务边界会形成栅栏。
- 「顺序」还包含读侧可见性：迁移期双读时，未切流的读请求仍以旧库为准，避免读到只写了一半的数据。

**一致性怎么验**

- 行数级：两边 count 对比，粗筛。
- 内容级：分桶校验和（按主键范围算 crc／sum），定位差异区间后再逐行比对。
- 业务级：关键实体的抽样读回比对，覆盖索引字段与映射字段。
- 校验本身要限流，否则对账查询会打爆生产库。

**切流动作怎么设计才安全**

- 双写窗口：先让写同时落两边（或以旧库为准＋异步同步到新库），确认稳定后切读，最后停旧写。
- 灰度：按租户／流量比例逐步切，切每一步都可回退；任何一步都不能出现「半迁移」悬挂状态（参见 [[#SYS-023：哈希分表扩容有什么问题，一致性哈希怎么工作？|SYS-023]] 的迁移状态机）。
- 保留回滚窗口：旧库不立刻下线，出问题时能回切并补差异。

**容易说过头的地方**

- 「有重试就保证不丢」：重试只在「有位点＋幂等」的前提下等于不丢；否则是重复或漏处理。
- 「迁移完就一致」：追平增量有窗口，切流前的最后一轮对账才是结论来源。
- 「迁移期间不用管业务写」：两边同时可写会互相覆盖，必须指定单一写入口或做双写收敛。

#### 深挖追问

1. **迁移任务反复失败、位点推进不下去怎么排查？**（补充练习）

   先看是「某条数据致命错误」还是「目标端整体劣化」：单条毒数据要进死信／隔离表并跳过（人工修），整体问题先查目标端写入能力、锁与限流，再调并行度。

2. **怎么衡量迁移是否完成？**（补充练习）

   给三个可核对指标：位点差归零（增量延迟）、分桶校验和一致、业务抽样查询一致；只有前两个为 0 才能宣布切流。

### SYS-048：RabbitMQ 如何避免消息的重复消费？

**常见问法**

- [[面经/网易云音乐/一面/0001#Q08：项目中使用 RabbitMQ 如何避免消息的重复消费？|MJ067 · 网易云音乐 · 一面 · Q08]]
- 项目中如何使用 RabbitMQ 避免消息的重复消费？

#### 面试回答

结论：RabbitMQ 做不到“exactly-once 投递”，重复消费无法在 MQ 层面根除；通用口径是接受 at-least-once，在消费端做业务幂等。

- 先说清重复从哪来：手动 ack 模式下，未确认消息在 channel／连接关闭时会自动重入队列；消费者处理完但 ack 没送达就掉线，重启后同一条消息再来一遍。
- auto-ack（automatic acknowledgment）模式不会重复，但它是 fire-and-forget——消息一出队就可能丢，可靠性反而更差。
- 所以正解不是“消除重投”，而是让重复执行没有副作用：用稳定业务键做消费幂等。
- 幂等三档按可靠性排：数据库唯一约束兜底；状态机条件更新；已处理标记与业务写入同一事务。
- 补一句配套：用 redelivered 标记和 `x-delivery-count` 限制重试次数，反复失败的消息进死信队列，防重投风暴。

#### 技术细节

**RabbitMQ 的重投语义**

- 官方口径：任何未确认（unacked）的投递，在 channel 或连接关闭时自动重新入队。
- 这意味着只要用手动确认＋消费失败 nack 重投，重复就是设计的一部分，不是 bug。
- 重投的消息带 `redelivered=true` 标记，可以用来区分首投和重投。

**幂等实现的三档**

- 唯一约束：给消息带业务唯一键（订单号＋事件类型），消费落库靠唯一索引挡重复，插入冲突即视为已处理。
- 条件更新：`update ... set status=后态 where id=? and status=前态`，影响行数为 0 说明已处理过，天然幂等。
- 消费记录表：`（consumer 名, message 业务键）` 唯一索引，和业务写入放同一事务，防止“标记成功但业务失败”。

**容易踩的坑**

- 只用 Redis setnx／分布式锁判重：判重标记和业务写入不在一个事务里，标记打了、业务失败回滚，后续重复消息会被标记吞掉——从“重复消费”变成“丢消费”，更糟。
- 用 RabbitMQ 的消息 ID 判重要谨慎：投递次数与消息 ID 不是一一对应（publisher 重试会产生新消息），判重键要用业务键。
- 别说 RabbitMQ 有“消费端幂等生产者”这种机制：幂等 producer（producer 侧去重）是 Kafka 的能力，两者别混（见 [[#SYS-016：Kafka 如何做到不丢消息与不重复消费？|SYS-016：Kafka 不丢不重]]）。

**重投风暴的隔离**

- 对反复失败的消息不要无限 requeue——官方明确警告“全部消费者都 requeue 会形成重投循环，烧掉大量 CPU”。
- 做法：队列配死信交换机（DLX），消费端 nack 时 `requeue=false`；或用 `x-delivery-count` header 超过阈值后转入人工处理队列。

#### 深挖追问

1. **消费者处理成功但 ack 前宕机，消息会怎样？**（补充练习）

   channel 关闭时该未确认消息自动重入队列，由其他消费者重新消费——这就是“至少一次”的来源，所以消费逻辑必须幂等。

2. **RabbitMQ 能做到 exactly-once 吗？**（面经实际出现的延伸；[[面经/网易云音乐/一面/0001#Q08：项目中使用 RabbitMQ 如何避免消息的重复消费？|MJ067 · 网易云音乐 · 一面 · Q08]]）

   投递层面不能。exactly-once 语义要么靠“at-least-once＋消费幂等”在效果上等价，要么依赖事务性机制把处理与确认绑成原子操作；RabbitMQ 没有 Kafka 式的事务性消费，通用讨论见 [[#SYS-040：消息队列的 exactly-once 是怎么做到的？|SYS-040：exactly-once]]。

### SYS-049：项目中消息队列的监控怎么做？消息延迟、消息堆积如何监控与处理？

**常见问法**

- [[面经/网易云音乐/一面/0001#Q10：项目中消息队列的监控怎么做？消息延迟、消息堆积等如何监控和处理？|MJ067 · 网易云音乐 · 一面 · Q10]]
- 项目里 MQ 的延迟和堆积怎么发现、怎么处理？

#### 面试回答

结论：指标先行——盯 ready 堆积数、unacked 数、最老消息年龄、生产／消费速率、发送确认失败率这五个；采集用 `rabbitmq_prometheus` 插件接 Prometheus＋Grafana，异常走 Alertmanager 告警。

- 先分类再处理：ready 增长是消费跟不上或掉线；unacked 堆积是消费者拿到消息卡住；用户真正感知的延迟看最老消息年龄，不是队列总长度。
- 定位三步：消费端是否活着（consumer 数、错误日志）→ 单条耗时是否变长（下游变慢、锁等待）→ 生产端是否突增（活动、重试风暴）。
- 处置：扩消费者实例或提高并发；瓶颈在下游（如同一行锁争用）时先解瓶颈再扩；反复失败的消息隔离进死信队列。
- 告警口径：延迟按业务 SLO 定阈值，堆积按增长速率告警而不是绝对值。

#### 技术细节

**五个指标各暴露什么问题**

- ready（unscheduled＋unacked 里的待投部分）增长：消费能力小于生产能力的总症状。
- unacked 增长但不消化：消费者进程活着但卡住（慢查询、锁、下游超时），这时看队列长度会误判。
- 最老消息年龄（head of the queue 的等待时间）：等价于 Kafka 的 consumer lag，是直接对用户承诺的延迟口径。
- 生产／消费速率曲线：分开展示才能看出“入口暴涨”还是“消费塌陷”。
- publisher confirm 失败／return 数：发送侧丢消息的早期信号，不等消费端发现。

**RabbitMQ 的采集手段**

- 官方 Prometheus 插件 `rabbitmq_prometheus`（内置于发行版）暴露 `/metrics`，队列级指标如 `rabbitmq_queue_messages_ready`、`rabbitmq_queue_messages_unacked`、`rabbitmq_queue_messages_confirm` 等。
- 或用 management HTTP API／`rabbitmqadmin list queues` 定时拉取；stats_event 可做变更推送。
- “消息延迟”没有现成的端到端指标：常用替代是最老消息等待时间，或在消息体带生产时间戳、消费时算差值上报直方图。

**告警与处置的配套**

- 队列长度告警设绝对值＋增长斜率双条件，避免稳态高水位误报。
- 消费延迟告警对齐业务 SLO（例如“消息从入队到处理完 ≤N 秒”），阈值写进告警规则而不是口头承诺。
- 死信队列本身也要监控：DLQ 只进不出等于把事故延后。
- 积压消化的通用估算（清空时间 B／(μ−λ)）与三类积压拆分见 [[#SYS-005：秒杀消息积压如何定位与消化？|SYS-005：消息积压定位与消化]]，本题不重复展开。

**发送侧监控**

- 监控发送异常：connection 断开、channel 出错、confirm 超时未回。
- 发送失败要落库或进补偿队列，配合 [[#SYS-014：MQ 消息发送延迟或失败如何优化与补偿？|SYS-014：发送延迟与失败补偿]] 的补偿链路。

#### 深挖追问

1. **只看队列长度为什么不够？**（面经实际出现；[[面经/网易云音乐/一面/0001#Q10：项目中消息队列的监控怎么做？消息延迟、消息堆积等如何监控和处理？|MJ067 · 网易云音乐 · 一面 · Q10]]）

   队列长度分不清“未投递积压”“已投递未确认”“反复重试”三类，三者处置动作完全不同；要配合 unacked、最老消息年龄、消费速率一起看（同 SYS-005 的口径）。

2. **怎么监控“消息有没有被真正消费”？**（补充练习）

   消费端上报处理计数与失败计数（Micrometer counter），对账“发送数≈消费成功数＋死信数”；差值持续扩大即消费链路有洞。

### SYS-050：如何为项目设计服务与接口报错监控？哪些指标能快速感应异常、怎么评估影响面？

**常见问法**

- [[面经/网易云音乐/一面/0001#Q11：回顾项目 3，可在哪些地方加入服务监控、接口报错监控？有哪些指标能快速感应并评估影响面？|MJ067 · 网易云音乐 · 一面 · Q11]]
- 你的项目复盘的话，监控体系怎么补？

#### 面试回答

结论：按四层布控——入口接口、业务服务、中间件（MQ／缓存／DB）、资源与 JVM；收口到四个黄金信号：错误率、延迟、流量、饱和度。

- 能快速感应异常的指标：接口错误率与状态码分布、P99 延迟、QPS 突增突降、MQ 堆积与最老消息年龄、慢 SQL 数、GC 停顿时长。
- 报错监控怎么建：日志结构化＋错误计数告警，每个接口配错误率阈值与环比突增规则；traceId 贯穿请求，报错能下钻到具体下游。
- 影响面评估三要素：该链路流量占比、是否主链路、失败的后果（可自动重试还是资损／数据错误）。
- 复盘项目时按“当时缺什么、补哪条指标、能提前多久发现”来讲，落到【项目 3 的真实链路】填写。

#### 技术细节

**四层布控各看什么**

- 入口层：QPS、成功率、P50／P99 延迟、状态码分布——用户感知最直接，告警优先级最高。
- 业务层：核心动作计数（下单量、支付成功率、消息发送／消费比）——指标异常但系统层正常时，问题在业务逻辑。
- 中间件层：MQ 堆积（SYS-049）、缓存命中率与淘汰、DB 慢查询与连接池使用率。
- 资源层：CPU／内存／磁盘 IO／网络，JVM 侧 GC 停顿、堆占用、线程数——饱和度类信号，恶化通常先于错误率。

**“快速感应”的指标怎么选**

- 领先指标（异常发生瞬间就动）：错误率、5xx／超时计数、消息发送失败。
- 伴随指标（确认传播范围）：P99 延迟、队列堆积、下游调用错误。
- 滞后指标（事后复盘用）：资损金额、投诉量。
- 告警用领先指标，定位靠伴随指标——只用滞后指标等于没监控。

**报错监控的工程做法**

- Spring Boot 技术栈常见组合：Micrometer 出指标（HTTP／JVM／连接池自带）→ Prometheus 抓取 → Grafana 展示 → Alertmanager 告警；Actuator 暴露端点。
- 错误聚类：按“接口＋异常类型＋错误码”聚合计数，突增规则用环比（如 5 分钟前 10 倍）而非固定阈值，能抓住新出现的错误。
- 链路下钻：traceId 进 MDC 打进每行日志，接 SkyWalking／Zipkin 一类链路系统，报错能定位到第几跳、哪个下游。

**影响面怎么评估**

- 广度：受影响接口占入口流量比例、涉及用户数（错误率 × 该接口用户量）。
- 深度：是否主链路（登录、下单），失败后果分级——可重试无感／需人工补偿／直接资损。
- 传导：列依赖拓扑，看该服务故障会阻塞哪些下游（弱依赖可降级则影响收敛）。
- 一句话汇报口径：【多少用户】在【哪条链路】上遇到【什么失败】，预计【能否自动恢复】。

**常见说过头的地方**

- 别承诺“上了监控就不会出事”：监控缩短发现与定位时间（MTTD／MTTR），不替代限流、降级、对账这些防线。
- 告警要有分级与响应人，全员群轰炸等于没有告警。

#### 深挖追问

1. **错误率阈值怎么定不误报？**（补充练习）

   基线＋双条件：取过去数周同时段错误率基线，超过基线且绝对值破线才告警；新接口冷启动期用宽松阈值。

2. **只监控 5xx 够吗？**（补充练习）

   不够。业务失败常返回 200＋错误码，要在响应体层埋业务错误计数；超时和网关层错误也要单独统计。

### SYS-051：Sentinel 有哪些限流方式？底层原理是什么，怎么观测？

**常见问法**

- [[面经/收钱吧/一面/0001#Q12：Sentinel 有哪些限流方式？区别和使用场景？|MJ068 · 收钱吧 · 一面 · Q12]]
- [[面经/收钱吧/一面/0001#Q13：Sentinel 底层的实现原理|MJ068 · 收钱吧 · 一面 · Q13]]
- 限流熔断过程中产生的数据是如何传输给 Dashboard 控制台的？
- 如何观测某个资源是不是被限流或熔断了？

#### 面试回答

结论：Sentinel 的“限流方法”不是并列几招，而是“统计口径 × 流控效果 × 流控模式”三个维度的组合；底层是一条“滑动窗口统计 → 责任链判定”的流水线。

- 统计口径（`grade`）：QPS 限流（默认，管入口速率）与并发线程数限流（管下游饱和，适合慢依赖保护）。
- 流控效果（`controlBehavior`）：快速失败（普通接口）、Warm Up 预热（冷启动，缓存／连接未就绪）、排队等待（漏桶整形，脉冲流量平滑，适合秒杀削峰）。
- 流控模式（`strategy`）：直接（拦本资源）、关联（下游饱和时限上游）、链路（只限指定入口路径进来的调用）。
- 熔断降级另有一套规则：慢调用比例、异常比例、异常数三种策略，触发后进入熔断时长，再半开探测恢复。
- 观测：Dashboard 看簇点链路与实时监控，代码侧捕获 `BlockException` 子类区分限流／降级，生产告警靠自建 Metrics 导出。

#### 技术细节

**滑动窗口：LeapArray**

- 统计基于 `windowIntervalMs`（默认 1000ms）切成 `sampleCount`（默认 2）个桶的滑动窗口，桶到龄滚动重置。
- 每个桶记 pass／exception／block／success 计数与 RT 合计；QPS、平均 RT、异常比例都从窗口聚合得出。
- 相比固定窗口，滑动窗口把“边界突刺”打散，不会在窗口切换瞬间放过两倍流量。

**责任链：SlotChain**

- 一次资源调用依次穿过：NodeSelectorSlot（构建调用树）、ClusterBuilderSlot（按资源聚合统计节点）、StatisticSlot（实时写窗口指标）、FlowSlot／DegradeSlot／SystemSlot（规则判定），最后才是真实业务。
- 链由 `SlotChainBuilder` 装配，规则扩展就是往链上插新 Slot——说“Sentinel 是插件化责任链”指的就是这个结构。
- 判定核心 `DefaultController`：直接比较当前窗口聚合值与阈值；Warm Up 按冷启动因子（默认 3 倍起步慢慢抬），排队等待把请求按固定速率放（内部是 Guava RateLimiter 风格的漏桶）。

**规则与熔断的关键参数**

- 流控规则字段：`resource、grade、count、strategy、controlBehavior、limitApp（按调用来源区分）、clusterMode`。
- 熔断规则字段：`grade（慢比例／异常比例／异常数）、slowRatioThreshold、count（时长或阈值）、minRequestAmount（最小样本量，防小流量误熔断）、statIntervalMs、timeWindow（熔断时长）`。
- 系统保护规则按 Load／平均 RT／线程数／入口 QPS 做整机兜底，Adaptive 模式（PB 流控）是较新版本加的。

**Dashboard 的数据通路：拉，不是推**

- 客户端启动后向 Dashboard 发心跳注册（transport 层，默认心跳间隔 5 秒），Dashboard 因此知道有哪些实例。
- 指标留在客户端内存（近 1 分钟按 10 秒粒度＋更长周期聚合），Dashboard 通过 HTTP API 定时拉取——命令端口默认 8719，接口如 `/metric.json`；页面上看到的统计值就是这些窗口聚合。
- 规则在控制台修改后也经该通道下发；默认存内存，重启丢——生产要把规则放 Nacos／ZooKeeper 等持久化数据源。
- 推论：Dashboard 是诊断工具不是监控系统，不做长期存储与告警；生产观测要 Micrometer 导出 `BlockException` 等计数接 Prometheus（见 [[#SYS-050：如何为项目设计服务与接口报错监控？哪些指标能快速感应异常、怎么评估影响面？|SYS-050：报错监控与告警]]）。

**与其它限流手段的分工**

- 网关／Nginx 层限总量，Sentinel 在应用内按资源细粒度限流＋熔断，Redis 实现跨实例的全局配额（窗口／令牌桶算法见 [[专题题库/Redis#REDIS-004：Redis 如何实现固定窗口、滑动窗口、令牌桶与漏桶限流？|REDIS-004：Redis 限流算法]]）。
- Sentinel 默认单机独立计数；要全局阈值需开集群限流（token server），或把配额判断前移到网关／Redis。

### SYS-052：Seata 的 AT 模式底层是如何工作来保证原子性与一致性的？

**常见问法**

- [[面经/收钱吧/二面/0001#Q14：项目中用 Seata 解决分布式事务，采用的是哪种事务模式？它如何保证原子性和一致性？|MJ069 · 收钱吧 · 二面 · Q14]]
- Seata AT 模式的一阶段、二阶段分别做了什么？

#### 面试回答

结论：AT 是“自动化的两阶段”——一阶段连本地事务一起提交（附带 undo log 与全局锁），二阶段绝大多数只做异步清理；回滚才用前镜像反向补偿。

- 三个角色：TC（事务协调者，独立 server）、TM（事务管理者，`@GlobalTransactional` 发起方）、RM（资源管理者，每个被代理的数据源）。
- 一阶段：拦截 SQL 生成前后镜像，把 undo_log 与业务 DML 放进同一个本地事务提交；提交前向 TC 申请该语句涉及行的全局锁；成功后分支注册并立即释放本地行锁。
- 二阶段提交：TC 通知各分支，AT 只需异步删除 undo_log（业务数据一阶段已落库），所以“全局提交”很快。
- 二阶段回滚：用 undo_log 前镜像生成反向 SQL 写回；写之前先校验后镜像是否仍一致（防脏写），校验不过转人工。
- 一致性口径：靠全局锁防跨事务脏写；默认全局视角存在脏读，是最终一致而非强一致。

#### 技术细节

**为什么一阶段敢直接提交**

- 因为 undo_log 与业务数据同库同事务，原子性由本地事务保证；全局决定权在 TC，分支只欠“能不能反悔”的答案。
- 本地行锁一阶段就释放，锁持有时间短——这是 AT 对比传统 2PC（全程持锁）的核心性能优势。

**全局锁解决什么、不解决什么**

- 解决：两个全局事务改同一行时，后提交者必须等前者二阶段结束，防“丢更新式”的脏写。
- 不解决：读。全局读默认读得到未决分支已提交的中间态（脏读）；要读已提交得走 `select for update`（被代理后加全局锁读）或提高隔离级别配置。
- 热点行上全局锁会排队，AT 的高并发写场景要评估；官方也建议对冲突大的业务改用 TCC。

**undo_log 与脏写校验**

- `undo_log` 表建在每个业务库：记录 `xid／branch_id、上下文（SQL 类型）、before image、after image`。
- 回滚时比较当前行与 after image：一致才用 before image 覆盖；不一致说明有外部脏写，回滚失败进入人工处理——宁可停下也不悄悄错。

**模式选型一句话**

- AT：单库是 MySQL 等支持本地事务的 relation DB、想让业务零侵入；TCC：要跨资源／高性能定制（Try-Confirm-Cancel 三个接口自己写）；Saga：长流程、以补偿为常态；XA：需要与外部强一致（如银行）时牺牲性能换无中间态。

#### 深挖追问

1. **AT 和 2PC 是什么关系？**（补充练习）

   神似形不同：AT 把传统 2PC 的“一阶段 prepare 挂起、全程持锁”改造成“一阶段本地提交＋undo log＋全局锁”，协调者从内嵌变成独立 TC，回滚从协议变成补偿。

2. **为什么需要全局锁，本地锁不够吗？**（面经实际出现的延伸）

   本地行锁随一阶段提交就释放了，其他全局事务的分支此时可以写同一行；全局锁是 TC 层面的跨连接／跨服务互斥，把“全局事务可见性窗口”内的写冲突挡住。

### SYS-053：Nacos 的服务注册与服务发现原理是什么？

**常见问法**

- [[面经/收钱吧/一面/0001#Q15：Nacos 服务注册、服务发现的原理|MJ068 · 收钱吧 · 一面 · Q15]]
- 服务实例挂了，Nacos 多久能把流量摘掉？

#### 面试回答

结论：注册＝“实例上报元数据＋心跳保活”，发现＝“订阅＋本地缓存＋变更推送”；一致性按实例类型分成 AP 与 CP 两条路。

- 临时实例：启动时调注册接口上报，之后周期性发心跳（beat，默认 5 秒一次量级）；服务端超时未收到先标不健康（约 15 秒），再超时直接剔除（约 30 秒）——阈值以所用版本文档为准。
- 持久实例：注册后不由客户端保活，Nacos 服务端主动探测（TCP／HTTP／MySQL 方式），不健康只改标记不删实例。
- 发现：消费方订阅服务名，本地缓存实例表；列表变更时服务端推送通知，消费方再拉全量，调用端负载均衡自行选实例。
- 一致性：临时实例元数据走 AP 的 Distro 协议（节点间异步复制，分区时仍可读到旧列表）；持久实例走 CP 的 Raft（JRaft）系协议。

#### 技术细节

**Distro 为什么适合注册中心**

- 每个节点可独立写本地分片，再异步复制给集群其他节点；读永远可由任意节点应答。
- 网络分区时可用性优先：宁可给出略旧的实例列表，也不拒绝服务发现——这与 ZooKeeper（CP，分区时可能整体不可写不可读）形成对照（CAP 口径见 [[#SYS-031：如何理解 CAP 定理，为什么保证 CP 会损失可用性？|SYS-031]]）。

**客户端侧的容错**

- 本地缓存＋订阅推送：即使 Nacos 集群短时不可用，已有列表还能撑住调用（客户端有快照文件）。
- 健康视图与流量摘除是两件事：标不健康后推送新列表，调用端的重载策略（如 NacosRule for Ribbon／LoadBalancer）决定权重与过滤。

**Nacos 不只是注册中心**

- 同名服务下还承担配置中心（长轮询配置变更推送）、命名空间／分组隔离（环境隔离）；面试报“我们用 Nacos 做注册＋配置”时要把两条链路分开讲。

**和 Eureka／ZK／Consul 的一句话对比**

- Eureka 同样 AP 心跳模型；ZooKeeper CP、临时节点依赖会话（session 过期即删）；Consul 用 Raft＋侧边代理健康检查。选型看：要 CP 的强一致注册，还是 AP 的高可用可读。

#### 深挖追问

1. **心跳间隔与剔除阈值能配吗？配错会怎样？**（补充练习）

   可配（如 `preserved.heart.beat.interval / timeout`、`preserved.ip.delete.timeout` 类参数，名称随版本变化）。间隔过长→故障摘除慢，用户侧持续 5xx；过短→网络抖动误杀健康实例，流量来回迁移。

2. **服务实例列表推送到调用端，和从网关解析有什么区别？**（面经实际出现的延伸）

   客户端发现（SDK 拉列表、自己负载均衡）与网关集中转发（只解析 VIP／服务名走一侧）在故障半径、语言栈依赖、灰度控制上不同；细节见 [[#SYS-029：如何设计一个分布式服务系统（服务拆分、注册发现、远程调用与容错）？|SYS-029：注册与发现]]。

### SYS-054：购物车同时参加满减与满折，如何算出并展示最优价格？

**常见问法**

- [[面经/收钱吧/一面/0001#Q14：购物车多商品参加满减与满折活动，如何展示最优价格？|MJ068 · 收钱吧 · 一面 · Q14]]
- 购物车凑单怎么算最省？

#### 面试回答

结论：这是“凑单组合优化”问题，先定规模再选算法——商品数小就枚举活动组合试算，要精确最优用分组背包 DP，线上工程靠预计算缓存＋服务端重算兜底。

- 建模：购物车 N 个商品，每个商品可归属满减档或满折活动（或不参与），目标是总实付最低；本质是带门槛约束的分组选择。
- 小 N（≤10 量级）：直接枚举分组组合逐个试算取最优，实现简单、口径可解释。
- 要精确最优：转成分组背包——按活动分组，组内选参与组合，容量是金额约束，价值是优惠额；复杂度随档位与商品数增长。
- 工程红线先说三条：金额一律用“分”做整数运算；优惠分摊到商品要能对上账；展示价与下单价分离，下单以服务端重算为准。

#### 技术细节

**为什么不能贪心“哪个优惠力度大用哪个”**

- 满减有门槛，力度最大的档可能要求凑更多；单件维度看局部最优，组合维度可能整体更差（典型反例：凑 300-50 反而不如两件走 200-40＋单独折扣）。
- 贪心只在“活动之间完全独立、无门槛叠加约束”时才等价于最优。

**活动叠加与互斥规则先行**

- 先拉齐平台规则：同享／互斥／取最优单条；这决定解空间形状——互斥则每档只选一，同享才需要组合优化。
- 门槛判定要用“参与活动的商品金额子集”而不是整车金额，凑单计算里这是最常见的实现 bug。

**缓存与失效策略**

- 购物车变更（加购／改数量／领券）触发该用户该购物车的优惠组合预计算，缓存结果与版本号；结算页直接读，避免实时算 DP 拖长 RT。
- 活动配置变更要能批量失效关联预计算；否则出现“页面最优价、下单变贵”的投诉。

**展示层要交代口径**

- “已按最优组合计算”要展示省了多少钱、还差多少到下一档——引导凑单同时暴露计算口径，避免用户以为被套路。
- 优惠金额分摊（按比例尾差挂最后一件）要与退款、发票口径一致，不然部分退款会算错。

#### 深挖追问

1. **如果活动上千条、购物车几十件，还怎么算？**（补充练习）

   先剪枝（按门槛把不可能命中的活动滤掉、同类活动保留占优的）、再分层（先算品类级优惠叠加顺序，再在组内枚举），必要时近似算法＋离线评估误差上限；实时算不动就改成 T+0 定时预计算＋展示“预计最优”。

2. **为什么下单必须重算，不能信购物车页的价格？**（面经实际出现的延伸）

   价格依赖活动状态、券库存、用户身份等易变条件，展示与下单之间存在时间窗；重算＋差异确认弹窗是资金安全的必要防线（幂等与防改价见 [[#SYS-013：接口幂等性如何设计，重复提交订单怎么处理？|SYS-013]]）。

### SYS-055：项目中用 RabbitMQ 给 ES 和 MySQL 做数据同步怎么实现？拆队列后顺序不一致怎么办？

**常见问法**

- [[面经/收钱吧/二面/0001#Q10：项目中用 RabbitMQ 给 ES 和 MySQL 做数据同步怎么实现？有无更好办法？|MJ069 · 收钱吧 · 二面 · Q10]]
- [[面经/收钱吧/二面/0001#Q11：增删改各建一个队列让 ES 消费，如何保证消费顺序与执行顺序一致？|MJ069 · 收钱吧 · 二面 · Q11]]

#### 面试回答

结论：同步链路可选“业务双写发 MQ”或“Canal 订阅 binlog”；但无论哪条，顺序一致性都要求“同一实体的变更走同一个队列并由单消费者串行处理”——按操作类型拆队列是方向性错误。

- 双写实现：更新 MySQL 的同一事务里写本地消息表，提交后投 MQ；消费端把变更写入 ES（按 doc id 幂等 upsert／delete）。
- 双写死穴：每个写入口都要记得发（漏一个永久不一致）、库成功消息失败要补偿；运维要盯对账。
- 更稳的默认项：Canal 伪装 MySQL 从库读 binlog → 投 MQ → 消费写 ES；业务零改动、不漏旁路写入（选型与量化对比见 SYS-044）。
- 顺序问题：拆队列后“先增后删”可能被 ES 消费成“先删后增”，留下幽灵文档；必须按实体主键路由同一队列＋单消费者串行，并用版本号拒绝旧变更。

#### 技术细节

**为什么按“实体”而不是按“操作类型”分队列**

- 顺序需求只存在于同一实体的变更之间；不同实体的变更本来就可并行。
- 按实体（doc id 哈希）路由让单队列只承载一个实体的偏序，队列内天然 FIFO＋单消费者＝保序；并发度=实体数，吞吐不受损。
- 类比 Kafka 就是“同 key 同分区”，RabbitMQ 用 routing key=doc id ＋每队列单消费者达到同样效果。

**版本号拒绝旧数据**

- 消息携带单调递增版本（binlog 位点／GTID、更新时间戳＋自增序列、数据库版本号列）。
- ES 侧用 `version_type=external` 或脚本比较：旧版本写入直接被拒，不依赖“消息刚好按序到达”。
- 有了版本兜底，偶发乱序只造成重试，不造成错误终态。

**乱序与丢失的兜底**

- 全量重建：离线任务从 MySQL 扫表按批 bulk 写 ES，用于初始化与不一致修复（索引别名切换做无感重建）。
- 定时对账：抽样比对 MySQL 与 ES 文档数、关键更新时间；差异率是这条链路的北极星指标。
- 失败处理：写 ES 失败重试进死信，人工或自动补偿；别让消息堆积悄悄吃掉变更。

**RabbitMQ 在这条链路里的交换机用法**

- 常规用 topic（routing key 带业务前缀）或按 doc id 做 direct；变更广播类（让各实例清本地缓存）用 fanout。
- 四种交换机：direct（精确匹配）、topic（`*`／`#` 通配）、fanout（忽略 key 广播）、headers（按头部属性匹配，性能差用得少）；另有无名 default 交换机按 routing key 直投同名队列，以及 DLX（死信交换机）承接不可路由／被拒绝的消息。
- 交换机只决定“进哪个队列”，保序要靠“队列单消费者＋按实体路由”，两者别混着承诺。

#### 深挖追问

1. **Canal 和双写 MQ 到底怎么选？**（面经实际出现；[[面经/收钱吧/二面/0001#Q10：项目中用 RabbitMQ 给 ES 和 MySQL 做数据同步怎么实现？有无更好办法？|MJ069 · 收钱吧 · 二面 · Q10]]）

   按“能否容忍漏改／是否改得动写入口／运维成本”三点选：Canal 零侵入、不漏旁路写入，但多一套组件和延迟归因工作；双写可控、能带业务语义，但漏一个入口就永久错。完整对比与量化实验口径见 [[#SYS-044：数据同步用 Canal（CDC）还是业务发 MQ，怎么选与怎么量化对比？|SYS-044]]。

2. **单队列单消费者保序，吞吐不够怎么办？**（补充练习）

   提高队列数按 doc id 分片（同一实体仍固定落一个队列），消费端并行度=队列数；顺序只要求“实体内偏序”，不要为全局顺序牺牲并发。

3. **ES 写入是实时的吗？同步链路怎么定义“多久可见”？**（补充练习）

   ES 默认 refresh（约 1 秒）后才可搜，同步的“秒级延迟”要含这段；口径按 SYS-024 的延迟归因来量，别把可搜索延迟算成 MQ 传输。
