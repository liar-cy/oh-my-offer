### SYS-001：如何设计文件存储与下载链路？

**常见问法**

- 项目中的文件下载与文件存储如何落地？

#### 面试回答

应先如实说明【文件存在哪里、元数据表、下载鉴权、实际采用的返回方式】。一种常用设计是文件内容放对象存储，数据库记录文件 ID、对象键、所有者、大小和状态；下载时用文件 ID 查元数据并校验访问权限，再返回短期签名地址或由后端流式转发。单机磁盘也能用于简单部署，但多实例要解决共享访问、持久化和备份，不能默认每台机器都有同一文件。

#### 技术细节

上传可先登记待完成状态，再写对象并标记可用；数据库事务不自动覆盖对象存储，需要处理写入失败、孤儿文件和删除重试。下载入口不直接接受任意服务器路径；原始文件名用于展示，对象键独立生成。大文件流式传输，避免一次读入堆内存；需要断点续传时验证存储或代理是否支持 Range。S3 预签名 URL 是有时效的持有者凭据，其有效期还受签名凭据有效性限制；失去登录态不必然使已发出的 URL 立即失效。更严格的实时鉴权可采用代理下载。

#### 深挖追问

1. **文件和元数据写入只成功一边怎么办？**（补充练习）

   用状态机、幂等重试和定期清理处理部分成功，只有确认可用的对象才允许下载。

### SYS-002：优惠券秒杀从低流量升级为高并发时如何整体设计？

**常见问法**

- B 端优惠券秒杀改为高 QPS 的 C 端场景，如何整体改造？

- 秒杀流程怎么改进的，为什么要改为异步实现？

- 服务端同时收到大量请求，怎么处理？

#### 面试回答

我会先明确峰值流量、可售数量、限领规则和响应时限，再压测定位瓶颈。服务器层做无状态扩容、负载均衡与资源监控；代码层减少同步调用和重复查询，控制线程池、连接池及超时；中间件层预热活动数据，原子预占库存，通过 MQ 削峰，数据库约束最终扣减；业务层做入口限流、资格校验、防重复领取、排队反馈及售罄关闭。改造要和产品、运营确认排队多久、失败如何通知及活动开关，并以成功率、尾延迟和数据正确性验收。

#### 技术细节

先画出“进入活动 → 资格检查 → 预占 → 受理 → 落库发券 → 结果查询”的状态流，再按每一步的吞吐容量设置准入。静态活动页可缓存或放 CDN，核心扣券请求仍需服务端验证。容量不能只看网关 QPS，应同时量出数据库锁等待、CPU、连接池等待和 MQ 最老消息年龄。压测要覆盖热点单券、重复点击、超卖校验和依赖故障；扩容应用前确认下游容量，否则新增实例只会增加数据库竞争。以下是可选系统设计，不是该候选人实际上线成果。

1. **秒杀入口返回什么才算成功？**（补充练习）

### SYS-003：秒杀中 MQ 如何削峰，消费者如何完成发券？

**常见问法**

- [[面经/美团/一面/0002#Q06：RabbitMQ 发奖，怎么确保奖品会被发放（发奖可靠性）？|MJ032 · 美团 · 一面 · Q06]]
- 消息队列放在秒杀哪个环节，消费者执行哪些业务逻辑？
- RabbitMQ 用在什么业务，消费端如何跨机器幂等？

- 如何使用 Kafka 解决消息的重复消费问题？

- 异步秒杀如何实现的？

#### 面试回答

常见做法是在资格校验、幂等检查和库存预占后，将带请求 ID、用户、活动、券批次和数量的任务投递 MQ，由消费者完成落库发券。消费者校验任务与预占状态，在一个数据库事务中完成幂等判定、条件扣库存、写领取记录和结果状态，提交后再确认消息；通知等外部动作可另行异步处理。重复消息直接返回已记录结果，暂时失败重试，永久失败进入可追踪的失败或补偿流程。

#### 技术细节

请求 ID 唯一约束防止同一任务重复执行，“活动＋用户”的业务唯一约束落实限领一次；如果允许多领，需要相应额度设计。建议使用持久化处理状态区分处理中、成功、失败、已释放。并发重复消费不能依靠“先查不存在再插入”保证幂等，应依赖唯一约束或条件状态变更，并正确回滚失败事务。RabbitMQ 的 publisher confirm 和 consumer ack 分别确认发布与消费，前者不意味着业务完成；自动确认或先 ack 再提交可能导致业务丢失。MQ 的具体产品及版本原图未提供，这里以 RabbitMQ 手动确认语义举例。

通用幂等伪代码是：在数据库事务内按稳定 `message_id` 插入消费记录，唯一约束冲突表示已处理；插入成功后执行带业务唯一约束或条件版本的业务变更，事务提交后再 ack。幂等 ID 不能只存在单机内存，应放在所有消费者共享的持久化存储，因此消息由另一台机器重新消费时仍能判断。若业务事务回滚，消费记录也应回滚；长时间处理可增加处理中状态和租约，但仍需处理接管竞态。

#### 深挖追问

1. **消费者收到消息后具体要做什么？**（面经实际出现；[[面经/百度/一面/0002#Q05：消息队列放在秒杀哪个环节，消费者执行哪些业务逻辑？|MJ005 · 百度 · 一面 · Q05]]）

   读取任务与终态，验证必要业务条件，以唯一键认领处理，在本地事务内扣减和发券、记录终态；事务提交后 ack。失败分类处理，外部通知不占用库存行锁。

2. **事务已提交但 ack 丢失怎么办？**（补充练习）

   消息可能重投，消费者查询持久化成功记录并确认消息，不再次扣减库存。

3. **用什么存储幂等 ID，其他机器重新消费怎么办？**（面经实际出现；[[面经/字节/一面/0001#Q13：RabbitMQ 用于什么业务，消费端如何实现跨机器幂等？|MJ011 · 字节 · 一面 · Q13]]）

   使用消费者共享的持久化数据库表或与业务状态同事务的唯一键；不能只用进程内集合。其他实例会命中相同唯一约束并读取既有终态。

4. **怎么确保奖品一定会被发放（发奖可靠性）？**（面经实际出现；[[面经/美团/一面/0002#Q06：RabbitMQ 发奖，怎么确保奖品会被发放（发奖可靠性）？|MJ032 · 美团 · 一面 · Q06]]）

   按“三段不丢＋一段不重＋对账”答：生产端先在同一本地事务里落“待发放”状态再发消息，或用事务 outbox 把消息与业务变更写在一起，并开 publisher confirm；Broker 端队列与消息持久化、必要时配仲裁队列；消费端手动 ack，且**事务提交后才 ack**，失败 nack 有重试上限、超限进死信并告警；不重复发靠稳定业务唯一键＋唯一约束或条件状态更新（不能只在单机内存记 ID，消息可能被别的机器重投）。最后一定要有对账：比对“应发”与“实发”，差异自动补发或人工兜底——“至少一次＋幂等＋对账”才是可交付的可靠性口径。

### SYS-004：Redis 预占与 MySQL 异步扣库存如何实现最终一致？

**常见问法**

- Redis 预扣后异步扣 MySQL，MQ 消费失败如何保证一致性？

#### 面试回答

我会将 Redis 数值定义为可预占额度，MySQL 记录最终领取事实，两者允许有可解释的处理中差额。每次预占都有唯一请求 ID、数量和状态，消费者用本地事务和幂等约束扣库存、写领取记录；短暂失败可重试，确定无法完成时才按状态机释放预占。还要处理预占成功但消息没发出的窗口、落库成功但确认丢失的重投，以及补偿与迟到消费的竞争，通过可恢复任务记录、终态互斥和定期对账收敛，不能简单失败就给 Redis 加一。

#### 技术细节

可选恢复方案是先写持久化 PENDING 意图，Redis 用请求 ID 幂等预占，随后把意图置为 RESERVED 并在同一数据库事务写 outbox，由投递器发送。写意图带来数据库开销，应纳入压测；若采用 Redis 中的预占记录和待投递结构，则需明确其持久化、复制及故障后的丢失边界。普通数据库 outbox 并不自动使此前的 Redis 操作原子化，PENDING 的恢复任务仍要按请求 ID 查明或重试预占。

消费者与取消任务在持久化任务行上争用条件状态转换，成功发券和取消只能有一个终态。取消先确认不可再发券，再通过可重试、按请求 ID 去重的释放动作回补 Redis；回补超时要查询结果，不能盲目重复加库存。若提交结果未知，先查持久化终态，不能把网络超时当事务失败。对账按已发券、未完成预占、已取消和释放记录计算差额，不拿 MySQL 剩余量直接覆盖 Redis，否则会抹去仍在队列中的预占。

#### 深挖追问

1. **MQ 消费失败是否立即回滚 Redis？**（面经实际出现；[[面经/百度/一面/0002#Q07：Redis 预扣后异步扣 MySQL，MQ 消费失败如何保证一致性？|MJ005 · 百度 · 一面 · Q07]]）

   不立即回补。可重试错误保持预占；永久失败先完成互斥取消再幂等释放。提交是否成功不明确时先核实终态。

2. **只用重试能保证最终一致吗？**（补充练习）

   不能。还需保证任务可恢复、业务幂等、补偿可重试，并识别消息未投递、长期失败和持久化丢失等缺口。

### SYS-005：秒杀消息积压如何定位与消化？

**常见问法**

- 秒杀高峰消息大量堆积怎么办？
- MQ 积压如何发现并恢复？
- Kafka 消息堆积怎么办？

#### 面试回答

我会先看生产速率、消费速率、最老消息等待时间和失败重试比例，再定位消费者 CPU、数据库锁、连接池或下游调用瓶颈。能并行的任务按活动或库存分片增加消费者，并调整批量与预取；同一库存行被锁住时，盲目加消费者反而更慢。同时在入口限流，按业务承诺控制最长排队时间，隔离反复失败的消息，给已受理用户展示处理状态。

#### 技术细节

若当前积压 B、持续进入速率 λ、可稳定处理速率 μ，且 μ 大于 λ，则理想清空时间约为 B／(μ−λ)；否则需降入口速率或提高实际处理能力。区分未投递积压、已投递未确认和反复重试，不能只看一个队列长度。预取太大会让慢消费者占住大量任务，太小可能吞吐不足；RabbitMQ 的 prefetch 要结合确认模式和消费者数配置。不能直接删除过期业务消息而不结算它的预占；迁移队列、增加分片或放宽顺序要求都要保留请求 ID 和终态约束。

#### 深挖追问

1. **增加消费者为什么可能无效？**（补充练习）

   瓶颈若是单行库存写锁、数据库 I/O 或下游限额，消费者只会增加等待；应先缩短事务或拆分受控库存额度。

2. **如何发现积压？**（面经实际出现；[[面经/字节/一面/0001#Q14：如何发现并恢复 MQ 消息积压？|MJ011 · 字节 · 一面 · Q14]]）

   对 ready、unacked、最老消息年龄、生产／消费速率和重投失败率告警，并与消费者及下游资源指标关联；单看队列长度无法区分慢消费和未确认。

#### 面试回答

先对入口熔断和强限流，再按数据库实测容量决定是否保留小流量领取。可在 MySQL 中用带库存下限条件的 UPDATE 和唯一领取约束，在一个事务内完成扣减及发券；超出容量返回稍后重试或暂停活动。切换前还要处理已有 Redis 预占和 MQ 在途任务，停止旧路径新增并完成结算，或给降级路径划定独立且不重叠的库存额度。不能把全部流量直接压到数据库，也不能靠各实例本地缓存各扣各的库存。

#### 技术细节

### SYS-008：如何解释 QPS、延迟水位并设计可信压测？

**常见问法**

- 5000 QPS 怎么来的，会不会全命中缓存？
- 压测观测哪些指标，如何体现多级架构？
- 响应时间 20 ms 是 P50、P90 还是 P99？
- 系统并发量和用户量是多少？

#### 面试回答

QPS 和响应时间必须绑定测试环境、请求模型、数据规模、并发、持续时间、成功率与延迟分位数说明。5000 QPS 是峰值还是稳定吞吐、单实例还是集群、客户端是否成为瓶颈都要明确；20 ms 也必须说明是客户端端到端的 P50、P95 或 P99。平均值或 P50 无法代表尾延迟。我会先以接近生产的流量配比建立基线，再逐步加压到延迟或错误率达到验收边界，而不是只报工具显示的最大数字。

#### 技术细节

缓存系统至少拆分全命中本地缓存、命中 Redis、回源数据库、冷热混合、热点 key 和依赖故障场景；记录每层命中率与请求数。通过关闭 L1、关闭 L2 或调整命中率做对照，比较吞吐、P95／P99、数据库回源量和资源消耗，才能说明多级架构贡献。预热结果与冷启动结果分别报告，避免全命中最短路径掩盖系统能力。

观测包括：压测端的实际发送量、成功率、超时和延迟分布；网关／负载均衡的排队与连接；应用 CPU、内存、GC、线程池／事件循环和连接池；本地缓存命中与逐出；Redis 延迟、命中、连接及热点；数据库 QPS、连接、锁等待、慢查询和 I/O；MQ、网络与下游错误。压测端与服务端时钟、采样窗口和请求 ID 需可对齐。开放与闭合负载模型语义不同，高延迟下固定并发可能自动降低请求率，应说明工具模型。

1. **如果 5000 QPS 全命中本地缓存，结果还有意义吗？**（面经实际出现；[[面经/字节/一面/0001#Q09：5000 QPS 如何测得，怎样证明多级缓存架构有效？|MJ011 · 字节 · 一面 · Q09]]）

   它只说明该命中路径的上限，不能代表混合流量或回源能力；需报告分层命中并补充对照场景。

2. **20 ms 应报哪个水位？**（面经实际出现；[[面经/字节/一面/0001#Q12：接口响应时间 20 ms 对应哪个延迟水位？|MJ011 · 字节 · 一面 · Q12]]）

### SYS-009：多级缓存如何保持一致，并在 Redis 故障时降级？

**常见问法**

- [[面经/美团/一面/0002#Q04：MySQL 和 Redis 数据一致性怎么保证？出现短暂不一致怎么考虑？|MJ032 · 美团 · 一面 · Q04]]
- 本地缓存如何保证一致，不同机器之间如何同步？
- Redis 挂了本地缓存能撑多久，系统如何降级？
- 如何保证 Redis 与数据库的数据一致性？

- 如何保证 Redis 和 MySQL 的数据一致性？
- 有没有更好的方案保证数据一致性？

#### 面试回答

先按业务定义一致性和可接受陈旧时间。常见读多写少场景以数据库为事实源：写事务提交后删除或更新 Redis，再通过消息或数据库变更日志向各实例广播本地缓存失效；本地项使用较短 TTL 和版本兜底。不同实例不能靠各自 TTL 保证同时一致，消息消费需幂等、可重试并有延迟和失败监控。强一致读写应绕过本地缓存或采用能提供所需一致性的数据路径。

#### 技术细节

更新数据库与删除缓存之间有故障窗口。cache-aside 的常见写法是先提交数据库，再删除缓存；若先删缓存，随后并发读可能回填旧值，最后数据库才更新，旧缓存会继续存在。先更新数据库也仍可能删缓存失败，可采用事务 outbox、数据库变更日志／CDC、可靠重试及定期校准驱动失效；不要在数据库回滚前提前发布不可撤回的更新事件。并发读写仍可能让旧值回填，需结合 key 版本、短 TTL、条件写或延迟二次失效处理，并根据业务容忍度选择复杂度。延迟双删只能缩小部分竞态窗口，延迟难以普适确定，也不能替代失败重试与监控。缓存事件携带实体 ID 和版本；实例只接受不旧于当前版本的变更。热点重建用请求合并和限流，避免每台机器同时回源。

Redis 故障时先快速熔断而非让线程堆积。允许陈旧的读可在明确 stale 上限内使用 L1；未命中按数据库实测容量限流回源，必要时返回稍后重试。关键写或强一致查询选择失败、排队或切至预先验证的备用系统。L1 能支撑多久取决于 TTL、预热覆盖、逐出、内存及数据变更频率，没有固定答案。恢复时限速回填并观察回源量、旧值年龄和错误率，避免流量瞬间冲击 Redis 或数据库。

#### 深挖追问

1. **如何保证所有机器同时删除本地缓存？**（面经实际出现；[[面经/字节/一面/0001#Q10：本地缓存及多机器之间如何保证数据一致性？|MJ011 · 字节 · 一面 · Q10]]）

   通常不能保证物理同时；通过可重试失效事件、版本与 TTL 实现有界最终一致。需要强一致时不要从各实例 L1 直接读。

2. **Redis 挂了，本地缓存能撑多久？**（面经实际出现；[[面经/字节/一面/0001#Q11：Redis 故障后本地缓存能支撑多久，系统如何降级？|MJ011 · 字节 · 一面 · Q11]]）

   由数据可陈旧窗口、覆盖率、TTL 与容量决定；应通过故障演练测出，而不是给脱离系统参数的固定时间。

3. **删除缓存、延迟双删和消息补偿分别解决什么？**（面经实际出现；[[面经/字节/一面/0002#Q02：如何保证 Redis 与数据库的数据一致性？|MJ012 · 字节 · 一面 · Q02]]）

   数据库提交后删除缓存用于让后续读取重建；延迟二次删除尝试清除竞态期间回填的旧值，但不是严格一致性证明；outbox／CDC 或可靠消息重试用于恢复“数据库已提交但失效未完成”的故障窗口。三者仍要结合幂等、监控、TTL 和业务一致性要求选择。

4. **出现短暂不一致，业务上怎么考虑？**（面经实际出现；[[面经/美团/一面/0002#Q04：MySQL 和 Redis 数据一致性怎么保证？出现短暂不一致怎么考虑？|MJ032 · 美团 · 一面 · Q04]]）

   先按数据分类而不是先选技术：只影响展示的值（活动文案、商品详情）允许有界陈旧，把 TTL 设成业务可容忍的最大陈旧时间即可；涉及资损的判断（库存是否够、是否已领取）不能以缓存为准，必须回到 DB 的条件更新或唯一约束，缓存只做前置过滤。再给收敛手段：写后关键读走主库或直接读库、缓存带版本号、延迟二次删除、失败重试与定时对账；并配监控（缓存与库的差异率、失效失败数、陈旧时间分布），让“窗口有多长”是可观测数字而不是估计。

### SYS-010：如何保证数据库写入与消息发送的一致性？

**常见问法**

- 业务要求生产者写数据和发消息都必须成功，怎么处理？

#### 面试回答

普通数据库事务不能原子覆盖 RabbitMQ 发布。常见方案是 transactional outbox：在同一个本地事务中写业务数据与 outbox 消息，事务成功后由投递器持续发送；收到 publisher confirm 后标记已发送。投递器崩溃或确认丢失会重发，因此消息用稳定业务 ID，消费者必须幂等。它保证最终把已提交业务对应的消息发出，不是跨数据库和 broker 的瞬时强原子提交。

#### 技术细节

outbox 表至少记录 messageId、聚合／业务 ID、类型、payload 或引用、状态、重试次数和下次时间。投递器用认领状态或跳锁避免重复并发处理，但超时恢复仍会重复发送；确认标记与发送无法组成同一原子动作，所以消费者通过唯一约束或条件状态更新去重。publisher confirm 只确认发布端到 RabbitMQ 及相应队列侧的接收语义，不表示消费者业务已完成；不可路由消息还需结合 mandatory／return 等机制处理。

如果请求必须等 broker 接收后才返回，可在业务提交后同步等待投递确认；若确认失败，数据库事实已经存在，应返回处理中或失败可查询状态，并由后台继续重试或按业务补偿，不能假装已回滚数据库。跨组件“都成功或都失败”的严格语义需要明确故障模型，二阶段提交往往带来可用性和性能代价，而且 RabbitMQ 的确认机制并不等于通用 XA。业务常用本地原子写入＋最终投递＋幂等消费取得可恢复的一致性。

#### 深挖追问

1. **publisher confirm 成功是否表示消费完成？**（补充练习）

   不是。发布确认与消费确认彼此独立；业务完成要由消费者状态或响应另行确认。

2. **消息会不会重复？**（补充练习）

   会。发送成功但确认丢失、消费者处理成功但 ack 丢失都可能重投，因此生产消息 ID 和消费幂等不可省略。

### SYS-011：什么时候需要分片查询，如何定位与优化查询瓶颈？

**常见问法**

- 为什么要使用分片查询？如果不用分片查询，系统查询的瓶颈在哪里？如何优化？

#### 面试回答

分片是为了把超过单节点容量或吞吐上限的数据与访问压力分散到多个节点，不是所有慢查询的默认解法。我会先用查询计划、慢查询和 CPU／I/O／内存／缓存指标确认是全扫描、索引不匹配、排序聚合、锁竞争、热点还是硬件容量问题。先通过索引、查询改写、分区裁剪、限制返回量、缓存或读扩展优化；单节点仍无法承载时再分片。

#### 技术细节

分片键要同时考虑分布均匀、高频查询能否定位单片、写入热点、数据共置和后续扩容。命中分片键时，路由层可直接访问目标片；缺少分片键的查询可能散射到所有片，再对结果排序或聚合。此时尾延迟受最慢分片影响，深分页会让各片都取出大量候选数据；应尽量改成携带分片条件的查询，使用游标分页、预聚合／派生索引，并限制扇出数。

分片引入跨片事务、全局唯一性、联表、再平衡和故障放大等成本。热点分片不能通过“总片数更多”自动解决；需调整键设计、拆热点、缓存或限流。原面经未指定数据库或搜索引擎，这里仅给出通用分片思路，产品具体路由与一致性语义待补充。

#### 深挖追问

1. **分片数越多查询越快吗？**（补充练习）

   不一定。单片查询可以扩容，但散射查询的网络、合并和尾延迟往往随扇出增大。

2. **怎么判断分片键选得好不好？**（补充练习）

   检查数据量和 QPS 的分片偏斜、单片命中率、跨片查询比例、热点以及扩容迁移代价。

### SYS-012：服务器宕机如何发现与恢复，Agent 宕机有何不同？

**常见问法**

- 服务器宕机了怎么办、怎么恢复？

- Agent 服务的高可用、稳健性是怎么保证的？

#### 面试回答

先区分宕机对象：进程崩溃、机器故障还是可用区／网络整体不可用。发现靠多层探活——进程健康检查、负载均衡摘除不健康实例、分布式共识与副本状态监控，配合告警。恢复目标是把流量切到健康副本并让故障节点上的状态可接续：应用尽量无状态，会话与任务状态放共享存储，数据靠副本保障，故障后由编排系统自动重建或切换实例，再验证下游容量。Agent 项目还要说明任务级恢复，见 [[专题题库/Agent开发#AGENT-014：Agent 工作流故障如何定位和恢复？|AGENT-014：Agent 工作流故障如何定位和恢复？]]。实际平台与演练情况按【真实部署】补充。

#### 技术细节

以 Kubernetes 为例（滚动文档 2026-09-19 查证）：livenessProbe 失败重启容器，readinessProbe 失败仅摘除流量，startupProbe 保护慢启动进程；节点失联后控制器在超时后把 Pod 调度到其他节点。注意这提供的是“重新拉起”而非自动恢复应用内部状态——状态必须由外部持久化与副本机制承载。数据库侧靠主从复制与故障转移，Redis 同样以副本和高可用机制缩短恢复时间；异步复制故障切换可能丢最后写入，需按业务容忍度选复制策略，持久化边界见 [[专题题库/Redis#REDIS-003：Redis 有哪些持久化方式，RDB 和 AOF 有什么区别？|REDIS-003：Redis 有哪些持久化方式，RDB 和 AOF 有什么区别？]]。恢复流程要处理锁与租约超时释放、消息重投与幂等、缓存冷启动预热，防止切换瞬间雪崩；故障演练才能验证假设。Agent 宕机的额外边界：模型或工具调用可能已产生副作用但响应丢失，不能默认重跑安全，恢复要从已验证检查点继续并按任务 ID 核对实际状态。

#### 深挖追问

1. **宕机后正在执行的任务怎么办？**（面经实际出现；[[面经/字节/一面/0004#Q04：服务器宕机了怎么办、怎么恢复，Agent 宕机了怎么办？|MJ014 · 字节 · 一面 · Q04]]）

   取决于任务状态是否外置：持久化队列／任务表＋租约超时可让其他实例认领续跑；只存在进程内存的任务会丢失，因此长任务要分段保存检查点，恢复时先查副作用再决定重试或继续。

2. **健康检查失败一定要重启进程吗？**（补充练习）

   不一定。先区分就绪与存活语义：依赖抖动适合摘流量＋退避重试，进程死锁或不可恢复错误才重启；全部重启还可能放大故障。

### SYS-013：接口幂等性如何设计，重复提交订单怎么处理？

**常见问法**

- 有没有做幂等性设计？比如用户连续点击两个提交订单，怎么做？

- 服务端同时收到大量请求，如何保证请求幂等性？

#### 面试回答

用户连点两次提交、客户端超时重试、MQ 重投都可能造成重复下单。通用组合：① 提交前发一次性 token（Redis 存、提交时原子核销），拿不到或核销失败即重复请求，直接返回首次结果；② 数据层业务唯一键兜底（用户＋活动、请求号唯一索引），重复插入命中约束后查询并返回已有订单；③ 状态机条件更新，只有前置状态才允许流转；④ 强冲突场景用分布式锁串行化同一业务键。前端按钮置灰与内存标记只能优化体验，不是正确性保证。

#### 技术细节

幂等标识要来自稳定业务语义（请求号、订单号），不能是随机生成的新值；去重记录与业务写入须在同一数据库事务或共享持久化存储中，单机内存 Map 在多实例下失效。token 核销用 Redis Lua／`GETDEL` 或数据库唯一键消费保证原子。重复请求的响应应与首次一致（返回已创建订单而非报错），需先查已有结果再决定动作。并发两请求同时到达时，唯一索引是最后防线：捕获重复键冲突后回查返回。接口设计还要区分“相同请求重试”与“不同请求恰好参数相同”，后者可能需要显式 requestId。

#### 深挖追问

1. **为什么唯一索引还不够，要再加 token？**（补充练习）

   唯一约束兜底正确性，但冲突发生在扣减／外部调用之后代价已经产生；token 在入口处提前拦截，减少无效竞争与副作用。

### SYS-014：MQ 消息发送延迟或失败如何优化与补偿？

**常见问法**

- 如果 MQ 因为网络等原因发送消息延迟，如何优化？
- MQ 发送消息失败，是回滚还是重试？
- MQ 中的脏数据怎么处理？

- 消息队列发送消息失败怎么处理，有没有脏数据存留，怎么处理？

#### 面试回答

延迟优化先定位环节：建连开销用长连接与连接池消除；往返多改异步发送＋回调并聚合批量；网络抖动设超时＋按幂等键有限重试；实时性仍不满足就换路径——本地消息表／outbox 先落库后台补发，或小流量场景直接同步写库绕过 MQ。发送失败是回滚还是重试看业务语义：通知类消息失败不应回滚已提交的业务，落库补偿重试；消息是业务生效前提（扣款指令）则同步确认失败即回滚。原则是不能让“发送结果未知”被简单当作失败或成功。

#### 技术细节

发送超时属于结果未知：消息可能已到达 broker，重试必须携带同一幂等标识，由消费端去重（见 [[专题题库/系统设计#SYS-010：如何保证数据库写入与消息发送的一致性？|SYS-010：如何保证数据库写入与消息发送的一致性？]]）。脏数据处理先确认口径：过期或已取消的业务数据，消息带版本号／时间戳，消费时与当前状态比较后丢弃并留痕；格式坏消息进死信队列人工排查，不无限重试；重复消息靠幂等消费。补偿任务要有速率限制与最大重试次数，超限进失败流程，防止恢复时洪峰二次冲击。

#### 深挖追问

1. **异步发送丢了消息谁负责？**（补充练习）

   回调确认＋本地持久化兜底：仅收到 broker 确认后标记完成，进程崩溃前未确认的由启动扫描补发。

### SYS-015：数据库故障无法写入时如何降级与恢复？

**常见问法**

- 如果数据库故障导致无法写入，怎么处理？

#### 面试回答

先快速发现（连接超时、写失败率告警）并交给高可用机制切换主库；切换窗口内按业务分级降级：读请求走缓存或只读副本；写请求区分处理——资金等强一致业务直接失败返回稍后重试，绝不本地记账假装成功；允许短暂缓冲的业务把请求写入本地消息表／持久队列，恢复后按幂等补偿落库；纯增值操作（日志、统计）可丢弃或延后。恢复后先限速回放积压，再对账核对缓冲与最终数据，明确“最多丢什么”要事先与业务约定。

#### 技术细节

应用侧要点：连接池快速失败与熔断（避免线程堆积放大故障）、写请求携带幂等键使补偿可安全重放、缓冲存储与应用同机则进程损坏仍会丢，重要业务缓冲要独立持久化（如另一存储介质或消息服务）。主从异步复制切换可能丢最后写入，切换后需以新主为准对账，不能双写旧主。与缓存故障降级（见 [[专题题库/系统设计#SYS-006：Redis 不可用时秒杀如何降级且避免超卖？|SYS-006：Redis 不可用时秒杀如何降级且避免超卖？]]）相比，数据库是事实源，降级空间更小：多数方案本质是“把同步写改成可恢复的延迟写”，正确性依赖幂等与对账。故障演练验证切换、缓冲与回放链路，纸面方案不可信。

#### 深挖追问

1. **为什么不直接切从库继续写？**（补充练习）

   从库通常只读且存在复制延迟与拓扑不确定；写必须落到唯一事实源，正确做法是提升新主并处理未复制事务的差异。

### SYS-016：Kafka 如何做到不丢消息与不重复消费？

**常见问法**

- 如何使用 Kafka 解决消息丢失问题？
- Kafka 发送消息时因网络问题出现消息丢失，如何解决？
- 如何使用 Kafka 解决消息的重复消费问题？

#### 面试回答

丢失按三段链路加固：生产端 `acks=all`（等待 ISR 全部确认）＋`retries`＋`enable.idempotence=true`，重试按 pid＋sequence 去重不产生重复；broker 端 `replication.factor≥3`、`min.insync.replicas≥2`、关闭 `unclean.leader.election.enable`——宁可拒绝写入也不让落后副本上位丢数据；消费端关闭自动提交，业务处理成功后再手动提交 offset。重复消费无法根除（重试、rebalance 双消费者、提交失败都会重放），正确姿势是接受 at-least-once，用稳定业务键在共享持久化存储做消费幂等（唯一约束／条件状态更新），要求处理与提交原子时再用事务性消费（read_committed）。

#### 技术细节

网络原因的“发送丢失”多是结果未知：超时不代表 broker 未写入，重试必须幂等生产者兜底；`delivery.timeout.ms` 内客户端自动处理 leader 切换与可重试错误，耗尽后回调里要落库／进补偿队列，不能只记日志。幂等生产者只保证单分区、单会话内去重，跨会话与换 topic 不覆盖；开启幂等要求 `acks=all`。Kafka 持久化依赖多副本＋OS 页缓存异步刷盘，单 broker 掉电靠副本兜底，不要指望 `flush.messages` 调成同步换性能。消费端 rebalance 引发重复的缓解：合理 `max.poll.interval.ms`、尽快提交、静态成员或独立消费者架构。通用原理（outbox、脏数据、回滚还是重试）见 [[专题题库/系统设计#SYS-014：MQ 消息发送延迟或失败如何优化与补偿？|SYS-014：MQ 消息发送延迟或失败如何优化与补偿？]]，参数以所用 Kafka 版本文档为准。

#### 深挖追问

1. **acks=all 和 min.insync.replicas 是什么关系？**（补充练习）

   acks=all 是“等 ISR 全部确认”的请求语义，实际等待几个副本由 ISR 大小决定；`min.insync.replicas` 规定 ISR 小于该值时直接拒写，两者组合才有“至少两副本落盘”的保证。

### SYS-017：秒杀如何防止超卖，为什么用 Redis＋Lua 而不是加锁？

**常见问法**

- 项目如何实现防止超卖？为什么用 Redis 和 Lua 脚本，而不用锁？

#### 面试回答

防超卖的底线是“检查余量＋扣减”原子执行，且以权威数据为准。常见两层：Redis 预热库存，扣减用 Lua 脚本一次执行判断与 DECR——Redis 顺序执行脚本，天然原子，返回成功才继续下单；数据库最终防线用条件 UPDATE（`SET stock=stock-n WHERE stock>=n`，按影响行数判断）。为什么不用锁：秒杀是单热点 key 的高并发写，悲观锁把请求排队串行化，吞吐受持锁时长限制，锁的获取释放本身还要处理过期、续期与误删；乐观锁版本号在高冲突下重试风暴；而“判断＋扣减”可以下推成一条原子操作，Lua 无等待、路径最短。代价与边界：Redis 是预占额度不是事实源，宕机恢复、少发超发要靠持久化、对账与数据库条件更新兜底（见 [[专题题库/系统设计#SYS-004：Redis 预占与 MySQL 异步扣库存如何实现最终一致？|SYS-004：Redis 预占与 MySQL 异步扣库存如何实现最终一致？]]）。

#### 技术细节

Lua 脚本要短小、无阻塞 IO，避免拖慢 Redis 单线程；库存 key 设计带活动与批次维度，售罄标记提前拦截减少无谓扣减。数据库条件更新即使不用 Redis 也能守住不超卖，但热点行锁排队限制吞吐，所以高并发才把判断前移到 Redis。锁并非不能用——正确性上 Redisson 锁＋双重检查也成立，但为同一目标引入锁生命周期管理（TTL、续期、重入、解锁原子性）成本更高、吞吐更差，这是“能下推为原子原语的逻辑不要拿锁串行化”的典型例子。Redis 故障降级路径见 [[专题题库/系统设计#SYS-006：Redis 不可用时秒杀如何降级且避免超卖？|SYS-006：Redis 不可用时秒杀如何降级且避免超卖？]]，行锁优化见 [[专题题库/MySQL#MYSQL-007：如何优化秒杀库存更新与热点行锁竞争？|MYSQL-007：如何优化秒杀库存更新与热点行锁竞争？]]。

#### 深挖追问

1. **Lua 扣减成功但后续下单失败，库存怎么回来？**（补充练习）

   按请求号做幂等释放：取消流程确认后回补 Redis 额度，回补本身可重试且不重复加；不能失败就立刻盲目 INCR。

### SYS-018：HTTP 接口如何从业务层兜底请求丢失与重试？

**常见问法**

- 使用 HTTP 设计接口时，针对可能出现的请求丢失问题，怎么从业务层设计优化？

- 接口超时如何处理？

#### 面试回答

不改协议与中间件，从业务设计兜住三类情况：请求可能没到、到了但响应没回、重试造成放大。① 幂等性：写接口要求客户端生成 requestId／业务唯一键，服务端持久化去重并缓存首次结果，超时重发不产生第二次副作用；② 状态性：长操作拆成“受理＋查询”——先落受理记录返回受理号（202），客户端轮询或推送拿终态，响应丢失也能凭受理号恢复认知；③ 重试策略：仅幂等接口自动重试，指数退避＋次数上限，非幂等失败引导“先查询确认再决定”；④ 限流与背压：入口和下游分设限额与有界队列，过载返回明确可重试错误码与 Retry-After，而不是拖死依赖；⑤ 对账兜底：与异步任务、外部回执定期核对，识别“客户端以为丢了但服务端已执行”的差异并按业务补偿。

#### 技术细节

HTTP 超时是“结果未知”不是“失败”：请求可能已被完整执行，因此幂等键要贯穿到消息与落库层（与 [[专题题库/系统设计#SYS-013：接口幂等性如何设计，重复提交订单怎么处理？|SYS-013：接口幂等性如何设计，重复提交订单怎么处理？]] 同一套机制）。GET／HEAD 天然安全，POST 需显式 Idempotency-Key 类设计；状态机让重复流转可判定（仅前置状态可迁移）。受理号要能查、有保留期；轮询要有上限与退避，避免丢失风暴。限流区分“拒绝并提示重试”与“排队等待”，给客户端的契约（错误码、Retry-After）要稳定。对账窗口按业务时效定，差异处理动作本身也要幂等。

#### 深挖追问

1. **客户端不配合传 requestId 怎么办？**（补充练习）

   用可推导的业务天然键（用户＋活动＋时间窗等）做去重，或在网关按会话与操作生成；没有稳定标识就无法区分重试与新请求，需在设计评审时把幂等契约前置。

### SYS-019：内存有限且结果可复用，如何兼顾并发、延迟与稳定性？

**常见问法**

- 系统有 N 类请求，峰值占用量已知；同类请求在依赖资源未变化时结果一致，机器内存有限，如何兼顾并发、延迟与稳定性？
- n 个请求分两批到达，完整请求耗时 1 分钟，30 秒时依赖资源发生变更，多长时间完成？

#### 面试回答

这是容量规划＋结果缓存题，按“先量化、再隔离、后优化”答：① 每类请求的峰值内存占用已知→按类设内存配额，总和留出安全水位（栈、元空间、临时对象），任何一类打满只会降级自己而不是拖垮整机；② 同类结果可复用→按类建结果缓存，key 必须含依赖资源版本（依赖未变结果才有效），设容量上限＋LRU/TTL 逐出；未命中限并发回源（singleflight），命中直接秒回；③ 并发与延迟：高命中率类优先驻留内存，计算并行度受 CPU 与内存双约束；④ 稳定性：配额超限走排队或慢路径而不是 OOM，监控命中率、内存水位与 P95 延迟，按流量动态调配额。

#### 技术细节

依赖变更的失效处理是本组变体（“30 秒时资源变更”）的关键：计算开始时记录依赖版本快照，写缓存时校验版本是否仍为当前——跨越变更算出的旧结果直接作废，不进缓存；这比“全量重算”省，比“不校验”正确。开放场景题（n 请求两批到达、耗时 1 分钟、中途变更）先澄清条件再分情形：两批到达时刻、并行度是否足够、变更前结果是否作废。典型口径：并行足够且旧结果作废→第一批 60s 算完作废、重算至 120s，第二批 30～90s，总 120s；变更不影响已算结果→90s。答案价值在口径表与快照失效设计，不在猜一个数。

#### 深挖追问

1. **为什么不干脆全缓存？**（补充练习）

   内存有限时全缓存必然驱逐抖动或 OOM；按命中率×计算成本排优先级准入，才同时守住延迟与稳定性。

### SYS-020：多类请求的任务队列如何保证公平、防止一类占满资源？

**常见问法**

- 如何设计任务队列，处理多类请求，保证公平性，防止一类请求把资源占满？

#### 面试回答

隔离＋加权调度：每类请求独立子队列与并发配额（bulkhead），单类积压只影响自己；调度层按权重轮转各类（WFQ／deficit round-robin 思路），高优先级类多分带宽、低优先级类保底份额防饿死；worker 按资源画像分组（CPU 型与 IO 型隔离），防止一类长任务占满线程；队列有界＋准入控制，满了快速拒绝或降级并返回明确可重试信号；监控各类排队时长与完成率，权重可动态调整。若同类任务可合并或批处理，加一层聚合进一步降占用。

#### 技术细节

纯 FIFO 的问题是一个慢类型头部阻塞；按类并发上限若无调度权重，仍会“先到者吃满”。优先级与公平要同时设计：严格优先级会饿死低优先级，需 aging（等待越久权重越高）或分层配额。分布式多实例场景还需集中式配额（如 Redis 计数）或按任务键分片，单机内存队列不解决跨实例公平。失败重试也占配额，重试风暴会伪装成“某类流量暴涨”，退避与上限必须计入调度预算。以下为通用设计，非某现成组件行为。

1. **一类请求突发暴涨，其他类延迟已经升高，先做什么？**（补充练习）

### SYS-021：缓存如何设计，需要考虑哪些方面？

**常见问法**

- 缓存如何设计？需要考虑什么？

#### 面试回答

按清单逐项与业务对齐：① 缓存什么——用命中率与计算成本选对象，不是能缓就缓；② key 与粒度——含租户/版本前缀，避免整页大对象，键设计决定失效能力；③ 读写模式——cache-aside 为主：先提交数据库再删缓存；④ 一致性与陈旧上限——失效驱动（重试队列/binlog 订阅）＋TTL 兜底，明确业务可忍多旧；⑤ 容量与逐出——上限、LRU 类策略、内存预算与告警；⑥ 异常场景——穿透（空值/布隆）、击穿（互斥或逻辑过期）、雪崩（TTL 打散＋高可用＋回源限流）；⑦ 冷启动预热与回源保护；⑧ 观测治理——命中率、逐出率、P99、大 key、权限与脱敏。开放题按“先问业务容忍度，再挑三点深入”的结构回答。

#### 技术细节

缓存收益＝命中率×回源成本，两个都低就不值得缓；多级缓存在这里（本地→Redis→DB）要额外处理跨级失效一致性（见 [[专题题库/系统设计#SYS-009：多级缓存如何保持一致，并在 Redis 故障时降级？|SYS-009：多级缓存如何保持一致，并在 Redis 故障时降级？]]）。写多读少或强一致数据缓存放大了不一致窗口，慎入。TTL 是最后防线不是主机制；失效消息要幂等可重试。缓存自身故障的降级路径（L1 撑多久、直连 DB 的限流容量）必须演练过，否则“加速层”变“放大器”。Redis 侧异常三大问题的具体方案见 [[专题题库/Redis#REDIS-002：缓存穿透是什么，布隆过滤器能完全解决吗？|REDIS-002：缓存穿透是什么，布隆过滤器能完全解决吗？]]。

- trace 数据如何存储、检索？千万／亿级日志量级怎么优化查询性能？

#### 面试回答

写入通道：trace 按结构化模型（traceId／spanId／属性，OTel 类）经采集 agent→消息队列→批量写入，削峰并解耦业务进程。检索需求分两类：按 traceId 精确拉取（点查，靠主键/倒排索引）与按条件聚合分析（慢请求分布、错误率趋势，走列存 OLAP）。量级上来后按“热—温—冷”分层：近几天数据在 ES／ClickHouse 支持交互查询，历史数据落对象存储（Parquet 按天＋租户分区），查询按时间路由。控制数据量本身：头部采样保底错误与慢请求、尾部采样按规则保留完整链路、降 DEBUG 级冗余。

#### 技术细节

查询优化优先级：强制过滤条件（时间范围、租户、服务名）做分区裁剪→traceId 索引点查→聚合走列存与物化视图→避免高基数全文检索。ES 类系统注意 mapping 爆炸与深分页成本，超大规模常把“明细检索”和“指标聚合”拆开：明细进列存/对象存储，指标预聚合进时序库。日志与 trace 的保留期、脱敏（Prompt 与用户数据可能敏感）和合规删除要与存储设计同步定。亿级以上再谈成本：压缩编码、冷热分层自动迁移、采样率随量动态调整。以下为通用设计，项目量级与组件按【真实系统】说明。

#### 深挖追问

1. **采样会不会丢掉要排查的那条？**（补充练习）

   会，所以错误与慢请求强制保留（尾部采样规则优先），并保留原始日志按 traceId 回捞的通道。

### SYS-023：哈希分表扩容有什么问题，一致性哈希怎么工作？

**常见问法**

- 哈希分表扩容有什么问题？一致性哈希算法原理？

#### 面试回答

`hash(key) % N` 的问题在扩容：N 变化后几乎所有键的归属都变，等于全量迁移，在线做代价高、风险大。一致性哈希把键与节点都映射到同一个哈希环，键顺时针找最近节点；新增节点只从顺时针方向的旧节点接走一小段区间，下线同理，迁移量约 1/N。裸环会造成分布不均与热点，用虚拟节点（每物理节点映射上百个虚拟像打散）缓解。工程落地还要处理：迁移期双写＋数据校验＋灰度切流、路由表版本一致、业务热点键（哈希再均匀也挡不住单键高 QPS，需缓存/拆键）。

#### 技术细节

替代方案对比：倍数扩容（表数 2N 翻倍时只有“新半区”需要迁移，实现简单但一次翻倍）；槽位映射（Redis Cluster 的 16384 slot：键→槽固定，迁移按槽粒度搬运，路由集中管理）——本质上都是把“改 N 全炸”变成“按区间/槽局部搬”。一致性哈希的参数（虚拟节点数、哈希函数）要按数据分布实测偏斜；分片键选择仍是第一性问题，见 [[专题题库/系统设计#SYS-011：什么时候需要分片查询，如何定位与优化查询瓶颈？|SYS-011：什么时候需要分片查询，如何定位与优化查询瓶颈？]]。

#### 深挖追问

1. **扩容迁移进行中，读写落在旧片还是新片？**（补充练习）

   按迁移状态机：双写新旧＋以旧读为准，校验追平后切读，最后停写旧片；任何一步可回退，避免“半迁移”悬挂。

### SYS-024：canal／binlog 订阅同步延迟如何归因与优化？

**常见问法**

- canal 同步 500ms 延迟怎么来的，怎么优化？

- canal 和 Kafka 怎么结合使用的，解决了什么问题？

- 同步延迟（如 500ms）是怎么测试出来的？

#### 面试回答

先拆链路归因，再按最长段优化，并说明延迟数字的统计口径。canal 伪装成 MySQL 的 replica 注册 dump 拉 binlog，解析成行事件后投递到目标（Redis、ES、MQ 等）。端到端延迟＝主库提交到目标可见，逐段可能是：dump 网络与主库压力、解析吞吐（解析与投递默认接近单管道，大事务/宽表行放大时排队）、攒批与轮询间隔（批量写入天然多等一个批次窗口）、目标端写入能力与排队、位点被 DDL 或大事务卡住。500ms 若稳定出现，优先怀疑“统计/攒批窗口”这类固定开销；抖动大才怀疑积压。优化对应：只订阅需要的库表列、按主键 hash 分区并行 sink（同键保序）、缩短或事件化攒批、拆大事务、按段埋点（拉取延迟／解析耗时／sink 积压）治最长那段。项目链路结构与实测数字按【真实实现】说。

#### 技术细节

归因先行指标：canal 侧看位点推进与 dump 连接状态，MySQL 侧对照 binlog 产生位置与已解析位置差，下游看写入 TPS 与队列深度。“500ms”常见陷阱：监控采样心跳周期本身（如每 500ms 聚合一次）、把 P50 报成 P99、含消费端业务处理时间与纯同步延迟混在一起——报数前先定义从哪到哪。保序约束决定并行度上限：同一行的变更必须按提交序应用（ROW 格式带主键可按键分区），全局限序则只能单管道；DDL 与事务边界会强制栅栏。canal adapter／客户端的批量参数（batch、buffer）与目标端（如 ES refresh、Redis pipeline）各有自己的延迟贡献。延迟与可靠性交换：追求更低延迟常意味着更小批量与更多确认开销，也可能引入乱序风险，优化后用对账任务验证最终一致。

#### 深挖追问

1. **为什么不用双写而是 canal 同步？**（补充练习）

   双写把同步逻辑侵入业务、失败补偿复杂；CDC 以 binlog 为单一事实源、业务零改动，代价是引入组件运维与秒级/亚秒级延迟——按能否容忍延迟选择，参见 [[专题题库/系统设计#SYS-009：多级缓存如何保持一致，并在 Redis 故障时降级？|SYS-009：多级缓存如何保持一致]] 的 CDC 失效方案。

2. **延迟突然从 500ms 涨到几十秒怎么查？**（补充练习）

   先看位点是否停住（大事务/DDL/连接断开重投），再看 sink 端是否排队（目标库写入劣化、限流），区分“解析慢”与“下游消化不动”，对应扩容、拆批或修下游。

3. **canal 和 Kafka 怎么结合，解决什么问题？**（面经实际出现；[[面经/传音控股/一面/0001#Q02：canal 和 Kafka 怎么结合使用的，解决了什么问题？|MJ029 · 传音控股 · 一面 · Q02]]）

   canal server 解析 binlog → 投 Kafka topic → 各下游用独立 consumer group 消费。价值：采集端与消费端解耦、一对多广播、Kafka 缓冲削峰与位点重放、下游故障不阻塞采集。代价与约束：同一行/同一 key 要落同一分区保序，跨分区无全局序；引入 Kafka 后是“至少一次”，消费端要幂等；延迟统计口径要把 Kafka 这一跳也算进去（见 [[#SYS-016：Kafka 如何做到不丢消息与不重复消费？|SYS-016：Kafka 不丢不重]]）。

4. **这个延迟是怎么测出来的？**（面经实际出现；[[面经/传音控股/一面/0001#Q03：500ms 同步延迟怎么测试的？|MJ029 · 传音控股 · 一面 · Q03]]）

   两种法：① 事件带时间戳——取 binlog 提交时间或注入标记字段，消费落库后算 now−事件时间，按窗口出 P50/P99；② 探针法——定时写探测行，轮询目标端查到即计时，测完整链路。避免把心跳/采集间隔当端到端、只报均值、压测与生产批量参数不一致。

### SYS-025：创建订单等同步接口耗时很长，链路如何优化？

**常见问法**

- 创建订单耗时很长怎么办？

#### 面试回答

先用链路追踪把耗时拆开定位（参数校验、风控、优惠计算、库存、支付前处理、落库、发消息），再分类下手：① 互相独立的校验与查询并行化（异步 RPC／CompletableFuture），把串行的“瀑布”压成最慢分支；② 非核心副作用（通知、积分、埋点、报表）移出同步链路改 MQ 异步，用户确认点只留必要状态；③ 热点数据前置——运费、汇率、活动价格预计算或缓存，减少在线计算与查询；④ 数据库侧拆长事务缩短持锁、合并批量小写、订单号号段预取避免每次取号；⑤ 全链路超时预算分配给各环节并监控。约束：异步化部分必须幂等、可查、可对账（配合状态机，见 [[#SYS-013：接口幂等性如何设计，重复提交订单怎么处理？|SYS-013：接口幂等性如何设计]]）；优化收益用同口径压测与 trace 前后对比验证。

#### 技术细节

耗时问题先分“单请求真慢”还是“高负载下排队慢”：后者是容量与隔离问题，扩容、限流、线程池/连接池治理优先，硬优化代码无效。并行化注意上下文传递（trace、事务不能跨线程复用）、失败聚合与总超时（任一分支超预算先返回降级）。事务拆分的边界是“必须原子的事实”（扣库存＋写订单明细同库时仍需同事务），不能为了快把一致性拆开；跨服务用 saga／本地事务表＋消息（见 [[#SYS-010：如何保证数据库写入与消息发送的一致性？|SYS-010：如何保证数据库写入与消息发送的一致性？]]）。前端体验优化（先建单后确认、分步提交）本质是把耗时移出关键路径，要和业务确认语义可接受。

#### 深挖追问

1. **订单主流程里哪些步骤坚决不能异步化？**（补充练习）

   影响“下单是否成立”的事实写入（订单落库、防超卖的权威扣减）要在同步路径或同步等待其结果；通知、积分、统计这类可补偿副作用才适合异步。

### SYS-026：熔断的触发时机与恢复时机怎么定，下游无法降级怎么办？

**常见问法**

- 项目里怎么用熔断的，熔断时机、恢复时机？
- 下游接口无法降级怎么办？

#### 面试回答

熔断按“滑动窗口统计＋最小样本量”触发：窗口内错误率或慢调用比例超阈值且请求数达到最小调用量才打开——没有最小量，低流量下一个错误就会误熔断。打开期间请求快速失败走 fallback，不再消耗资源等故障依赖；超时后进入半开，放行少量探测请求，成功率与延迟达标即关闭恢复全量（恢复初期常小流量爬坡防二次打垮），仍失败则重新打开并延长窗口。落地用 Sentinel／Resilience4j 类组件按依赖单独配置（阈值来自该依赖的历史基线与压测，不是抄默认值）。边界：熔断解决“快速失败、防线程堆积拖垮自己”，不保证“请求不丢”，必须与超时、幂等重试、异步补偿组合。下游“无法降级”的调用：先确认是业务不允许失败还是没做预案；真不允许就把同步可用换成“可延迟完成”——超时＋幂等＋有限重试仍失败则受理转后台重试队列/死信＋告警＋人工出口，用户侧显示处理中；连延迟都不允许即强同步依赖，只能提升依赖自身可用性与容量并准备业务止损预案。

#### 技术细节

熔断器三态（closed／open／half-open）是状态机，关键参数互相牵制：窗口长度决定统计灵敏度，最小请求量防小样本误判，慢调用阈值要与该依赖的 SLO 对齐，open 时长要大于依赖恢复的典型时间。与相关机制的分工：超时管“单请求最多等多久”，重试管“这次失败再来一次”，限流管“进来多少”，熔断管“还要不要继续打过去”，降级管“打不过时给用户什么”——五件事一起设计才有完整预案，重试要设上限并加退避，否则与熔断互相放大（重试风暴）。熔断 fallback 本身要轻量且不可再依赖故障方。监控上把熔断触发次数、持续时长与恢复过程做成指标与事件，触发即告警，避免“系统一直带病快速失败没人知道”。

#### 深挖追问

1. **熔断和限流有什么区别，为什么常一起出现？**（补充练习）

   限流针对入口流量（保护自己不过载），熔断针对出口依赖（不被下游拖死）；下游故障时入口流量照常进来、出口快速失败，两个机制互补，单用任何一个都留缺口。

### SYS-027：如何设计一个可靠的系统？

**常见问法**

- 怎么设计一个可靠的系统？

#### 面试回答

先给口径：可靠性＝定义 SLO（可用性目标、故障恢复时间 RTO、数据丢失容忍 RPO）之后，让单点故障不放大成用户故障。框架五步：① 冗余去单点——服务多实例（跨机/跨可用区）、依赖用集群与主从、容量按 N-1 设计；② 依赖治理——所有跨网络调用带超时，重试加退避与上限，配熔断、限流与分级降级预案，故障隔离（独立线程池/舱壁）防互相拖垮；③ 状态正确性——幂等键贯穿可重放、状态机约束流转、关键链路对账补偿，异步化配最终一致机制；④ 可观测——指标／日志／链路追踪加告警，先于用户发现问题（见 [[#SYS-022：千万到亿级 trace／日志如何存储与检索？|SYS-022：trace／日志如何存储与检索]]）；⑤ 验证与预案——压测摸容量、故障演练验证切换真的能切、备份可恢复且能回滚。面试结合自己项目挑一条链路讲透“检测→隔离→恢复→对账”，比背清单可信。

#### 技术细节

可靠性是“故障预算”思维：不是消灭故障，而是控制故障影响的范围×时长×数据损失三个维度。常见反模式：只堆冗余不做演练（切换路径从未验证）、超时不设预算（层层放大）、重试无上限（风暴）、降级预案只写在文档没开关、监控只报“机器活着”不看业务成功率、把“无状态”挂在嘴上但本地盘/内存里藏着状态。恢复手段分层：请求级（重试/兜底）、进程级（重启/摘除，见 [[#SYS-012：服务器宕机如何发现与恢复，Agent 宕机有何不同？|SYS-012：服务器宕机如何发现与恢复]]）、数据级（备份恢复/对账修复，见 [[#SYS-015：数据库故障无法写入时如何降级与恢复？|SYS-015：数据库故障降级与恢复]]）。成本要一起报：多活、双写、热备都在花钱，按 SLO 定投入，不按恐惧定。

#### 深挖追问

1. **99.9% 和 99.99% 的差距落在哪些设计上？**（补充练习）

   每加一个 9，故障检测与切换要从分钟级到秒级、冗余从单机房到多机房、发布与变更要可灰度可回滚，且要靠演练持续证明——不是简单“多加几台机器”。

### SYS-028：营销抽奖的规则树与责任链如何设计，为什么这样设计？

**常见问法**

- 介绍一下营销项目，遇到什么问题、怎么实现的（抽奖业务、规则树、责任链），为什么要这样设计？
- 规则很多、经常变，怎么组织代码？

#### 面试回答

先讲触发问题：活动规则（时间窗、渠道、新老用户、参与次数、黑名单、奖品条件）会不断叠加，写成一串 if-else 后每次改动都要动同一个方法、回归面覆盖全量规则，规则之间的先后依赖（黑名单必须先于概率抽取）也藏在代码顺序里，出错难定位。解法是**按“规则的表达形态”分两层**：

- **责任链**管流程型校验（能不能参与）：一个节点一条规则，顺序显式声明，命中即短路并返回结构化拒绝原因（原因码＋文案），运营排查“用户为什么没抽中”时有据可查；节点无状态、可单测、可按活动组合。
- **规则树**管条件型判定（能中哪一档）：把奖品中奖条件表达成布尔组合（AND／OR／NOT 内部节点＋叶子条件：字段、算子、值），配置化存储，运行时把用户上下文喂给树求值；新增条件只改配置，主干不动。

为什么不是只用一个：责任链是线性顺序＋短路语义，表达不了“（A 且 B）或 C”这种嵌套布尔；规则树是表达式求值，不承载“按顺序执行、命中即终止并返回错误码”的流程控制。链管准入、树管资格，职责不同，硬合并会让两者都变形。

代价必须一起说：责任链的风险是顺序配置错误（顺序错即逻辑错，需要顺序断言测试）和上下文对象膨胀（多个节点各自查库会把 RT 叠加，要前置一次性加载）；规则树的风险是配置错误与解释执行开销（保存时静态校验＋表达式编译缓存＋子树结果复用），以及规则外置后运营误配的影响面变大（要配灰度、生效时间窗、变更审计、一键回滚）。被问“为什么不上 Drools／Aviator”：当前规则量级自研树更可控、依赖更少；等出现决策表、热更新、非技术同学维护规则的真实需求再引入引擎——这是取舍，不是“自研更高级”。

#### 技术细节

**责任链落地**：节点接口只暴露一个方法（如 `check(ctx)` 返回继续／终止），链由配置装配（枚举数组或库表排序字段），拒绝原因用枚举而不是字符串；上下文对象只放本轮已加载的事实（用户画像、参与次数、活动配置），节点不产生副作用；日志记录“走到哪个节点、为什么终止”，这是排查的关键收益。

**规则树落地**：三种节点——组合节点（AND／OR，可加 NOT）、叶子节点（字段＋算子＋值）、可选优先级／权重节点。求值时对 AND 短路、对同一用户上下文缓存子树结果。表达式来源可用 JSON（前端可视化配置友好）或字符串 DSL（配解析器），两者都要在保存时校验：字段是否存在、算子是否合法、有无恒假／孤立分支、值域是否越界；上线前用历史数据回放预估命中率变化。

**与库存、发奖的边界**：树和链只做判定，不产生业务写入；判定通过后按顺序走扣库存（条件更新或 Redis Lua，见 [[专题题库/系统设计#SYS-017：秒杀如何防止超卖，为什么用 Redis＋Lua 而不是加锁？|SYS-017：秒杀如何防止超卖]]）→ 写中奖记录（幂等键）→ 异步发奖（见 [[专题题库/系统设计#SYS-003：秒杀中 MQ 如何削峰，消费者如何完成发券？|SYS-003：MQ 削峰与消费端发券]]）。**概率抽取与规则树要分开**：树决定“有没有资格中这一档”，加权随机决定“这一档里中哪个”，混在一起运营就无法预测中奖率，也做不了库存与预算控制。

**验证方法**：改造前后做双跑对比——同一批输入分别走旧实现与新实现，比对拒绝原因码分布与中奖结果，差异逐条归因（是修掉老 bug 还是引入新问题）；保留旧链路开关以便快速回退。

#### 深挖追问

1. **规则树和责任链是不是重复设计？**（面经实际出现；[[面经/美团/一面/0002#Q02：介绍一下营销项目，遇到什么问题、怎么实现的（抽奖业务、规则树、责任链），为什么要这样设计？|MJ032 · 美团 · 一面 · Q02]]）

   不是。链解决“按什么顺序执行、何时终止”，树解决“条件如何布尔组合”。判断依据是需求形态：出现嵌套条件就需要树，出现顺序依赖与短路就需要链；只用 if-else 表达两者，才会真的变成不可维护的重复。

2. **为什么不把规则直接写进配置文件里的 SpEL／Aviator 表达式？**（补充练习）

   可以，且很多团队就是这么做的。要补的是治理：表达式在保存时静态校验、执行时超时与异常兜底（一条坏表达式不能拖垮请求）、可观测（记录实际求值路径）、以及版本与回滚。裸配表达式的风险不是性能而是“没人知道线上现在生效的是哪一版”。

3. **规则量级涨到几百条时架构怎么演进？**（补充练习）

   先做分组与索引（按活动／人群先粗筛再细判，避免每条都求值），再考虑决策表或规则引擎（Drools 等）带来的 Rete 网络复用与热更新；同时把“规则命中统计”做成产品能力，让运营能看到每条规则拦了多少、误拦多少，否则规则只增不减最终不可维护。

### SYS-029：如何设计一个分布式服务系统（服务拆分、注册发现、远程调用与容错）？

**常见问法**

- 让你设计一个分布式服务系统，你大概会怎么设计？
- 项目里分了哪些服务，服务之间是怎么远程调用的？

#### 面试回答

先问需求与约束再谈架构——QPS／数据量、读写比、一致性要求、延迟目标、可用性预算决定后面每一个选择。通用分层骨架：

1. **服务拆分**：按业务域／单一职责切，边界依据是变更频率、团队归属和扩缩容粒度不同的地方才拆；能单体的别过度微服务化（分布式单体最差）。
2. **通信**：同步调用（RPC／HTTP）走必须在请求内拿结果的关键链路；异步、解耦、削峰用 MQ。
3. **注册发现与配置**：实例启动把自己注册到注册中心（Nacos／ZooKeeper／Consul），下线或健康检查失败被摘除；调用方通过服务名发现可用地址；配置中心统一下发可变配置。
4. **负载均衡**：客户端（Ribbon／Dubbo 的 LB）或服务端／网关（DNS、LVS、反向代理）分摊流量，策略有轮询、随机加权、最少连接、一致性哈希。
5. **接入层网关**：路由、鉴权、限流、灰度。
6. **数据层**：缓存（本地＋分布式多级，注意一致性）、分库分表、主从与读写分离、冷热分离。
7. **一致性与容错**：跨网络调用一律带超时，重试加退避与上限，配熔断、降级、隔离；跨服务数据用最终一致＋幂等＋对账（见 SYS-013、SYS-027）。
8. **可观测与运维**：指标／日志／链路追踪＋告警，灰度发布、压测定容量、故障演练验证切换。
9. **高可用**：去单点、多副本、多可用区部署。

收尾：先保证“单链路正确”，再用冗余、隔离和可观测把故障影响控制在 SLO 预算内——与可靠系统设计（SYS-027）同一套思路。

#### 技术细节

“远程调用一次经历了什么”是最常被追问的点，要能画出来：调用方拿到接口代理 → 序列化参数（JSON 或 protobuf／Hessian 二进制）→ 从注册中心缓存的地址列表里负载均衡选一台 → 建立／复用长连接发送 → 服务端从线程池取线程反序列化执行 → 原路返回，配超时与重试。可观测性里最关键的是把 traceId 透传进每一跳，才能还原整条调用链。

服务拆分的代价要主动说：进程内方法调用变成分布式调用后，失去事务与强一致、多了网络不确定性与部分失败，排查从看一个栈变成看全链路——所以拆分的收益（独立部署、独立扩缩、团队边界）必须大于这些成本。注册中心对比：AP 型（Eureka，偏可用）与 CP 型（ZooKeeper／etcd，偏一致）在网络分区时行为不同，服务发现一般选 AP（宁可拿到略旧地址也不要整体不可用）。

#### 深挖追问

1. **服务越来越多，如何避免“分布式单体”？**（补充练习）

   按限界上下文划清数据所有权，服务间只走接口不共享库表；用契约（接口／消息 schema）版本化保证独立演进；能同步拿到的强一致越少越好，跨服务优先编排／协同＋最终一致。

2. **同步 RPC 和异步 MQ 怎么选？**（补充练习）

   调用方必须立即拿到结果、且下游可用时用同步 RPC；只需“把事做完”不要求即时返回、或要削峰／解耦／广播多方时用 MQ。异步化后必须补上幂等消费、重试与对账（见 SYS-010、SYS-016）。

3. **服务实例怎么注册与保活，调用方如何第一时间感知上下线？**（面经实际出现；[[面经/字节/一面/0009#Q13：微服务架构中服务发现和负载均衡如何实现；注册中心（Nacos、Consul）如何工作，实例如何注册与保活（心跳机制）？|MJ041 · 字节 · 一面 · Q13]]）

   按实例类型分两条路。临时实例（Nacos ephemeral、Eureka）：客户端启动时注册、之后周期发心跳续约（Nacos 默认约 5 秒一次），服务端按阈值判定——约 15 秒未收到标为不健康、约 30 秒未收到直接摘除；这类系统按 AP 取舍，分区时优先让调用方仍能拿到列表，代价是可能推给已经挂掉的实例。持久实例（Consul 默认健康检查、Nacos 非临时实例）：由服务端主动探活（TCP／HTTP 检查），失败只标不健康、不自动删记录。ZooKeeper／etcd 是第三种形态——靠会话与临时节点，session 过期节点即消失，属 CP，注册场景要谨慎选。变更感知分拉（客户端定时全量或增量拉，Eureka 约 30 秒，实现简单但有窗口延迟）与推（Nacos 变更推送加拉取兜底、ZK／etcd watch、Consul blocking query）。三个工程细节才见生产经验：实例下线要先摘流量再停进程，否则调用方仍持旧列表；注册中心抖动或自我保护阈值触发时会保留不健康实例，调用侧必须有重试与熔断兜底；本地缓存快照能在注册中心不可用时继续调用，但列表变更后要能重建连接池。

### SYS-030：多实例之间如何同步文件或文档状态（如表格）？

**常见问法**

- 给你一个 RPC 场景，把 A 实例上的文件信息同步到 B 实例（例如表格），你该怎么设计？

#### 面试回答

先澄清“同步的是什么”：是整份文件字节，还是结构化数据（表格的单元格／操作）？这决定方案。通用骨架：

1. **先定权威源**：首选把事实放共享存储（数据库／对象存储），A、B 只是无状态计算节点，“同步”退化为“都读权威源最新”，最省心、天然幂等。若题目强制“实例间直接同步”再走 2。
2. **同步增量而非全量**：结构化表格不传整份文件，传“带版本号的变更／操作日志（op log）”，接收方按版本拉取或接收增量并回放；大文件本体走对象存储传引用，只同步元数据。
3. **传输方式推拉结合**：实时性高用推送（A 直接 RPC 推给 B，或经 MQ／pub-sub 广播给多个 B）；可容忍延迟用 B 定时拉（能合批、削峰）；混合模式最常见——变更事件推送＋按版本拉全量对齐。
4. **冲突解决**：并发编辑要明确模型——last-write-wins（按时间戳／版本）、按操作合并（协同表格用 OT／CRDT）、或行级锁串行化。跨实例是最终一致：先保证收敛，再谈延迟。
5. **可靠性**：每次同步带幂等 ID＋单调版本，接收端对乱序、重复、丢失用版本判重与断点续传（见 SYS-013）；失败要有对账／重放兜底，防止“漏同步”比防止“重复同步”更难。

一句话答法：权威源 → 增量（版本/oplog）→ 传输（推拉/MQ）→ 冲突模型（LWW/OT/CRDT）→ 幂等与对账。

#### 技术细节

“文件信息同步到另一实例”最常见的两个坑：一是把它当“传文件”去做全量拷贝，带宽和延迟都爆炸；二是只传变更却不带版本，网络重传或乱序到达时状态被旧数据覆盖。版本号／序列号是让“应用一条变更”幂等且可判序的关键：接收方记录已应用到的版本，`v ≤ 已应用` 直接丢弃，`v == 已应用+1` 顺序应用，`v > 已应用+1` 说明有缺口去拉全量或请求补发。

协同编辑（多人实时改同一张表）是特化难题：并发操作会互相影响，LWW 会丢别人的改动，工业方案是 OT（操作变换，中心化服务器定序）或 CRDT（无中心、操作可交换收敛），代价是实现复杂度与元数据膨胀。若题目只是“一份数据在 A 改、同步给 B 展示”，不必上 OT／CRDT，版本化增量＋单写者即可，先问清是否多人并发写再决定，过度设计也是失分点。

#### 深挖追问

1. **怎么保证同步操作只执行一次？**（面经实际出现）

   给每次操作一个全局幂等 ID＋单调版本，接收端用“已处理集合（Redis SETNX／DB 唯一索引）或版本比较”判重，判重与应用要在同一原子步骤内完成；详见 SYS-013。
   来源：[[面经/字节/一面/0008#Q04：怎么保证同步操作只执行一次（幂等性）？|MJ033 · 字节 · 一面 · Q04]]

2. **B 实例宕机恢复后如何补齐漏掉的同步？**（补充练习）

   靠权威源＋版本号对账：B 记录本地已应用版本，重启后向权威源／A 请求“该版本之后的增量”，缺口过大则拉一次全量快照再续增量；对账任务周期性比对版本水位并触发补同步。

3. **为什么优先共享存储而不是实例间直接同步？**（补充练习）

   共享权威源把 N×N 的实例间同步问题降为“多读一写”，天然收敛、少一套一致性协议；实例间直接同步只在“数据本就在实例本地、无法集中”或极低延迟点对点场景才用，复杂度高得多。

### SYS-031：如何理解 CAP 定理，为什么保证 CP 会损失可用性？

**常见问法**

- 讲一下你对 CAP 原理的理解。
- 为什么保证 CP 的情况下，A 就会损失呢？讲一下这块的逻辑。

#### 面试回答

CAP 说的是一个读写了共享数据的分布式系统，在发生网络分区时，一致性（这里特指线性一致）与可用性（每个请求都收到非错误的正常响应）不可能同时保全。前提要讲对：分区不是可选项，广域网里丢包、延迟抖动必然存在，P 必须容，所以真实抉择是分区那一刻在 C 和 A 里二选一。为什么选 CP 必然损失 A：分区把集群切成互不通信的组，若各组都照常接受读写，愈合时同一份数据出现分叉版本、强一致被破坏；要守住 C，就必须让至少一部分节点拒绝写入甚至读取（返回错误或进只读等待追平），被拒绝的请求得不到正常响应——按定义即丧失可用性。典型对子：ZooKeeper／etcd 是 CP，分区中小部分侧无法写入、选主期间整体短暂不可写；DNS／Cassandra 偏 AP，两侧各自可写，愈合后靠时间戳或冲突合并收敛。落点：工程上不是全局二值选择，而是按数据项配置——余额扣减走 CP 语义（甚至退回单机事务），Feed 流、点赞数走 AP＋最终一致；CAP 只描述分区时刻，平时还有一致性与延迟的权衡，答题带出 PACELC 口径会更完整。

#### 技术细节

- 定理侧：Brewer 提出、Gilbert 与 Lynch 2002 年给出证明；证明构造就是“分区两侧各接受一个写，愈合后要么违反线性一致、要么必有一侧没响应”，所以上面的直觉有严格形式。
- 三者的定义都有限定域：C 指所有客户端看到的操作全局有序且实时（线性一致），不是 ACID 里那个 C；A 指每个发给“非故障节点”的请求都能在有限时间内收到“有用的”（非错误）响应；P 指任意链路可以丢包、延迟任意久但节点不宕机。
- 常见误读要能纠正：“三选二”不等于平时也只有两项——无分区时 C 和 A 可以同时很好；也不能拿“网络做好点就不分区”当解，跨机房故障与交换设备抖动不受控制。
- Quorum（如 RF3＋W＋Q>N）常被当作“折中”，其实它仍落在光谱上：网络健康时同时满足 C 与 A，分区时 W＋Q>N 的定义决定了不可达侧要么写不进要么读不到——本质还是分区时刻选 C。
- PACELC 补全另一维：分区时 P 选 E（最终一致）或 C；无分区时要在 L（低延迟）与 C 之间权衡（ELASTIC 类系统与 Spanner 类系统差在这一步，后者用时钟同步换外部一致性）。

#### 深挖追问

1. **为什么“分区时两侧都继续服务”一定破坏线性一致？**（补充练习）

   两侧各自接受的写形成两个不能互相感知的全序历史；愈合后要么丢弃一侧（等价于拒绝了那部分请求的持久化，违反“收到有用响应”的隐含承诺），要么合并出与真实时间顺序矛盾的序——两种都出界，所以定理说必须二选一。

2. **业务上怎么落地“按数据项选 CP／AP”？**（补充练习；与 [[#SYS-027：如何设计一个可靠的系统？|SYS-027：如何设计一个可靠的系统？]] 的故障预算思路一致）

   按“错误响应的代价 vs 短暂不可用的代价”划档：钱与库存这类写错代价高的放强一致链路（主库事务或 CP 协调），偏好、计数、Feed 这类可自愈的放 AP＋异步收敛；跨档交互用 outbox／消息解耦，避免一个请求同时硬依赖两种语义。

3. **AP 系统分区愈合后怎么收敛？**（补充练习）

   Cassandra 类用 last-write-wins（墙钟或逻辑时钟）＋读修复／反熵，冲突被静默覆盖，需要业务保证可覆盖性；更严格场景用向量时钟检测并发写、冲突返回多分支交上层合并（dynamo 的 siblings 处理）。没有免费的收敛，冲突解决策略本身就是业务决策。

### SYS-032：Kafka 有哪些特性，与 RabbitMQ 有何区别，为什么吞吐高？

**常见问法**

- Kafka 特性，与 RabbitMQ 的区别？
- Kafka 高吞吐量的原因？

#### 面试回答

定性先说清：Kafka 是分布式提交日志——topic 拆成分区，分区内 append-only、有序持久化，消费者按 offset 拉取，消息“消费后仍在”，可重放可回溯；RabbitMQ 是经典 broker 队列模型——exchange 按路由规则分发进 queue，消息取出即消失。特性上 Kafka 有分区并行、消费者组（组内分摊、组间广播）、副本 ISR、Connect／Streams 生态。与 RabbitMQ 的取舍从五个维度答：模型（日志 vs 路由队列）、投递方式（pull＋长轮询 vs push）、顺序粒度（Kafka 只保证分区内有序，key 路由决定）、延迟与吞吐（Rabbit 微秒级低延迟、万级 TPS；Kafka 毫秒级、百万级 TPS）、功能风格（Rabbit 擅长复杂路由、死信、优先级等队列语义，Kafka 擅长流式管道与重放）。选型一句话：业务消息、需要精细路由和低延迟在线响应选 RabbitMQ；日志采集、行为事件流、大数据管道、需要回溯重放选 Kafka。高吞吐四大支柱：① 顺序写磁盘＋OS 页缓存——追加写把随机 IO 变顺序，读写热数据都走 page cache 不进用户态，磁盘吞吐逼近内存；② 零拷贝 sendfile——消费时数据从页缓存直达网卡，省掉内核到用户的来回拷贝；③ 分区即并行——生产和消费都按分区水平扩展，吞吐随分区数近线性增长；④ 批量＋压缩——producer 攒批（linger／batch.size）、broker 按批原样存储与传输、consumer 拉批，压缩（lz4／zstd）在批粒度做，摊薄每消息的网络与协议开销。pull 模式还让消费速率自主、批量获取减少往返。

#### 技术细节

- “磁盘写为什么还快”要说透：Kafka 靠页缓存＋顺序写＋group commit 批量刷盘（可配 acks 换耐久），并且消息以压缩批格式直接进页缓存，避免 JVM 堆内缓冲复制大对象——这是它敢用普通机械盘跑高吞吐的原因；对照反面：Rabbit 每条消息要过 Erlang 进程与队列结构，per-message 开销天然大。
- 零拷贝链路精确口径：`FileChannel.transferTo` → 页缓存 → DMA 到网卡，跳过用户态两次拷贝与两次上下文切换（见 [[专题题库/操作系统#OS-018：什么是 I/O 零拷贝，sendfile 和 mmap 如何减少拷贝？|OS-018：零拷贝]]）。
- 高吞吐≠高可靠：默认 acks=1／retries 可能丢或重复，耐久要 acks=all＋min.insync.replicas＋幂等 producer／事务（见 [[#SYS-016：Kafka 如何做到不丢消息与不重复消费？|SYS-016：Kafka 不丢不重]]）；批与 linger 提吞吐也提延迟，二者是同一条旋钮的两端。
- 分区数影响顺序与并行：key 哈希决定进哪个分区，同 key 有序；分区过多拖慢故障恢复与端到端延迟，且再平衡成本上升——扩分区不是免费加速。

#### 深挖追问

1. **为什么不直接说 Kafka 是“消息队列”？**（补充练习）

   语义差异：队列消费即删、状态在 broker；Kafka 是日志，数据留存与消费进度（offset）解耦，同一份数据可被多个组独立重放——把它当 Rabbit 用会丢掉它最值钱的重放能力，也会为不需要的路由语义买单。

2. **Kafka 支持延迟消息／优先级吗？**（补充练习）

   原生不支持：无 per-message 延迟投递与优先级队列（分区内 FIFO），这类需求要么用 Rabbit 的 TTL＋死信／优先级队列，要么在 Kafka 外用分级 topic＋调度消费者模拟。承认“这不是它的强项、该换工具”比硬凑方案更加分。

### SYS-033：秒杀抢购如何防刷，前端防刷能挡什么、直连接口刷单怎么防？

**常见问法**

- 前端防刷能解决哪些问题，有哪些局限性？
- 如果用户不通过浏览器界面，而是直接模拟或调用后端接口进行刷单，如何防范？
- 秒杀怎么防止黄牛和脚本刷单？

#### 面试回答

先把定位说准：前端防刷不是安全边界，只是成本与体验优化——它能挡掉误点连点、初级脚本和低质量流量，挡不住有组织的刷单，因为前端逻辑全部可绕过。真正防盗刷必须在服务端，思路是“不信任任何自称合法的请求”：接口不裸露（下单要先换一次性准入令牌）、请求加签防重放、限购规则在服务端硬校验、风控按行为与账号画像评分、事后处罚与名单沉淀。所有防刷都是概率与成本的博弈，目标是把“绕过前端”的边际收益压到低于收益，而不是一劳永逸地识别机器人。

#### 技术细节

前端层能解决的：按钮置灰与节流防重复提交、页面与素材缓存降低无效负载、验证码／滑块／答题抬高人工与初级脚本成本、按钮态按服务端时间判定避免提前打接口（见 [[专题题库/系统设计#SYS-036：秒杀开始前的页面刷新与流量冲击如何承接（静态化、CDN、预热、兜底）？|SYS-036：秒杀开始前的页面刷新与流量冲击如何承接]]）。局限要说全：JS 可逆向、参数可自造、验证码可打码或走协议破解、无头浏览器可伪装 UA 与指纹、请求可脱端重放，因此前端手段一律只当“减速带”，不能作为放行依据。

服务端层的四类机制：① 凭证化——把“看活动”和“提交订单”拆开，下单需先领取与服务端会话／活动绑定的**一次性令牌**（用过即废、短时效），脚本没有合法上下文就拿不到令牌，同时天然承担幂等（与 [[专题题库/系统设计#SYS-013：接口幂等性如何设计，重复提交订单怎么处理？|SYS-013：接口幂等性如何设计]] 同源）；② 完整性与防重放——参数＋时间戳＋nonce 签名，服务端校验签名、限时间窗并对 nonce 去重，防止改价、改数量、重放他人请求（密钥下发与前端持有的局限要有意识：签名只能抬高成本，不能防住逆向了算法的对手）；③ 业务硬校验——按用户、账号、设备、SKU、时间窗计算已购量，库存与限购判定全在服务端事务里；④ 风控与处置——行为序列特征（点击节奏、是否有浏览过程、无浏览直接下单）、设备指纹与网络信誉（机房／代理池 IP、同出口聚集）、账号画像与团伙关联（同收货信息、同支付账户）、评分结果驱动放行／排队／出验证／拒绝，异步处罚与黑名单回灌，异常订单侧支持人工审核与回收。治理面别漏：防刷规则要能灰度与回滚，误杀真实用户比放过脚本代价更高，需监控“被拦截后申诉率”并按活动调阈值。

#### 深挖追问

1. **前端做了验证码和按钮置灰，为什么还不够？**（面经实际出现；[[面经/阿里国际/一面/0001#Q03：前端防刷能解决哪些问题、有哪些局限；用户不走浏览器直接模拟或调用后端接口刷单怎么防？|MJ038 · 阿里国际 · 一面 · Q03]]）

   因为攻击面已经换到了协议层：脚本不走 UI，直接构造 HTTP 请求，前端的一切限制都不在它执行路径里；验证码本身有打码与绕过成本，也只是提高成本而非阻断。

2. **一次性令牌会不会也被脚本先领再用？**（补充练习）

   会，所以令牌要绑定服务端侧的上下文（会话、活动、设备或 IP 特征、领取时间窗）并限制使用次数与有效期，配合申请令牌本身的限流与风控评分，让“批量拿令牌”先成为瓶颈。

3. **怎么区分真实用户和脚本，又不误伤？**（补充练习）

   不做二值判定，做分级：低风险放行、可疑加验证或排队、高风险拒绝；用申诉率与人工抽检度量误伤，规则灰度上线，且对同一出口 IP 的正常密集用户群要放宽（见 [[专题题库/系统设计#SYS-034：同一出口 IP 下大量真实用户同时抢购，限流怎么设计才不误伤？|SYS-034：同一出口 IP 下限流怎么设计]]）。

4. **防刷和限流是一回事吗？**（补充练习）

   不是。限流保护系统容量（按维度控制速率，超出快速失败），防刷识别恶意主体并剥夺其收益（可能速率很低但意图恶意，如定时脚本）。一个请求可能通过限流却被风控拦截，反之亦然，两套机制的指标与处置手段都不同。

### SYS-034：同一出口 IP 下大量真实用户同时抢购，限流怎么设计才不误伤？

**常见问法**

- 在应对局域网下（同一 IP）大量用户同时抢购的场景时，怎么设计 IP 限流策略？
- 校园网、公司内网出口都是同一个 IP，秒杀限流怎么不误杀真实用户？

#### 面试回答

关键判断是 IP 不等于用户：NAT 出口、校园网、企业专线、代理池让同一 IP 背后可能是几百个真实用户，也可能是少量脚本换 IP。所以 IP 只能当异常维度用，不能当唯一限流键。设计四步：主维度用身份（UID、设备指纹、账号信誉）做一人一配额；IP／CIDR 维度做兜底阈值，按该 IP 历史正常并发基线放大设阈，并按同 C 段归并聚合；超阈值时分级处置而不是直接拒绝服务——增量请求降级为排队、出验证或收紧可见库存，可疑比例越高越严；最后度量误伤（被限流后的申诉量、同 IP 真实用户成功率），阈值随流量曲线动态调整而非一次拍定。

#### 技术细节

限流维度组合要显式设计：以“维度＋活动”拼 key（UID＋活动、设备＋活动、IP／CIDR＋活动），算法侧固定窗口／滑动窗口／令牌桶／漏桶的实现与取舍见 [[专题题库/Redis#REDIS-004：Redis 如何实现固定窗口、滑动窗口、令牌桶与漏桶限流？|REDIS-004：Redis 如何实现各类限流算法]]；集中式计数放 Redis 保证多实例一致，判定收口在网关或统一切面，本地缓存兜底以防 Redis 抖动时退化为宽松放行＋核心链路保护（见 [[专题题库/系统设计#SYS-006：Redis 不可用时秒杀如何降级且避免超卖？|SYS-006：Redis 不可用时秒杀如何降级]]）。IP 聚合用 CIDR 而不是精确匹配，避免被换 IP 绕过，也避免对同一出口逐个统计；白名单登记已知机构出口（校园网、企业）走宽松策略，配合账号维度的限购保证公平。

“不误伤”的机制化做法有三条：一是只降速不断服务——超配额请求进排队或返回可重试提示，而不是硬 429；二是配额按份额而非绝对值——同一 IP 下按历史正常用户数分配额度，真实密集用户群整体放行、异常超量部分受限；三是判定用比例与画像——同 IP 内新注册账号占比、无浏览直接下单比例、请求节奏一致性（脚本的方差极小）这些特征组合，而不是单看 QPS 峰值。Cluster 下注意限流 key 的分片集中问题：热点活动的计数 key 要按维度分桶，否则限流组件自己先成了热 Key（见 [[专题题库/Redis#REDIS-010：什么是热 Key，为什么危险，如何探测与解决？|REDIS-010：什么是热 Key]]）。

#### 深挖追问

1. **为什么不直接按 IP 限死每秒几个请求？**（面经实际出现；[[面经/阿里国际/一面/0001#Q04：局域网下（同一 IP）大量用户同时抢购，IP 限流策略怎么设计？|MJ038 · 阿里国际 · 一面 · Q04]]）

   因为该策略同时犯两类错：校园网／企业出口的几百个真实用户会被集体误杀，而用代理池分散流量的脚本几乎不受影响。IP 的价值在异常检测与配额兜底，不在主限流维度。

2. **脚本用海量住宅 IP 呢？**（补充练习）

   单 IP 维度失效，要转到账号与设备维度、行为一致性（同一操作序列的方差）、以及成交侧约束（收货信息、支付账户聚集度、限购），配合事后取消与名单回灌——这也是防刷要落到风控而不只是限流的原因（见 [[专题题库/系统设计#SYS-033：秒杀抢购如何防刷，前端防刷能挡什么、直连接口刷单怎么防？|SYS-033：秒杀抢购如何防刷]]）。

3. **Redis 计数挂了怎么办？**（补充练习）

   退化为本地限流（单机阈值＝集群阈值／实例数，精度差但能挡住量级），同时收紧活动开关与库存保护，宁可少卖不可超卖；恢复后重建计数窗口。

### SYS-035：秒杀全链路除下单外还有哪些性能瓶颈，如何逐层定位？

**常见问法**

- 除了“下单”环节，整个秒杀链路中还有哪些环节可能存在性能瓶颈或挑战？
- 一个高并发活动，你怎么判断瓶颈在哪一层？

#### 面试回答

按请求走过的顺序盘一遍比只盯下单更能体现容量意识：静态层（页面与素材未上 CDN 时回源带宽先满，渲染慢导致用户在开抢瞬间集中重试）、接入层（连接数与 TLS 握手风暴、限流组件自身成为串行点）、鉴权层（token 校验与会话查询是每请求必经的同步依赖，打爆就放大成全站故障）、资格校验层（会员、券、黑名单常是跨服务同步 RPC，一个慢下游拖住线程池）、库存层（Redis 单 key 串行与集群单分片热点、数据库热点行锁）、订单与存储层（主键生成、分库分表写集中、单库写上限、从库延迟造成“已下单查不到”）、消息层（分区数限制消费并行度、积压与最老消息年龄）、下游依赖（积分、券、风控、推送被流量放大）、外部回调（支付回调乱序要求状态机幂等）、任务与运维（对账回补、库存释放、活动开关时效）。定位方法是统一的：逐层压测找最小容量环节并算各层水位，只看网关 QPS 会误判；配套超时、熔断、可观测与活动开关兜底。

#### 技术细节

每类瓶颈对应的观测指标要能报出来：CPU／网卡打满与单分片倾斜对应热 Key（[[专题题库/Redis#REDIS-010：什么是热 Key，为什么危险，如何探测与解决？|REDIS-010：什么是热 Key]]）；数据库侧看锁等待与 TPS 上限（[[专题题库/MySQL#MYSQL-007：如何优化秒杀库存更新与热点行锁竞争？|MYSQL-007：如何优化热点行锁竞争]]）；消息侧看积压量与最老消息年龄（[[专题题库/系统设计#SYS-005：秒杀消息积压如何定位与消化？|SYS-005：秒杀消息积压如何定位与消化]]）；接口耗时看分段瀑布而不是总耗时（[[专题题库/系统设计#SYS-025：创建订单等同步接口耗时很长，链路如何优化？|SYS-025：创建订单链路耗时优化]]、[[专题题库/系统设计#SYS-008：如何解释 QPS、延迟水位并设计可信压测？|SYS-008：QPS、延迟水位与可信压测]]）。

优化手段的通用顺序是：先去掉同步依赖（能异步就异步、能前置校验就别查库）、再合并与缓存重复读、然后打散写集中（分库分表键、库存分片）、最后才扩容——新增实例若不解决下游容量，只会加剧数据库竞争（SYS-002 的教训）。还有两个容易被忽略的软瓶颈：线程池与连接池配置（下游一慢就耗尽，表现为“QPS 上不去但 CPU 空闲”）、以及活动开关与降级路径是否演练过（真实故障时靠的是开关而不是临场改代码）。

#### 深挖追问

1. **这些瓶颈里哪个最常被漏掉？**（补充练习）

   从站外与鉴权链路最常漏：会话／token 校验和权限查询被当成“基础能力”，秒杀流量下它们是每个请求都打的同步依赖，容量规划时经常被排除在活动压测范围之外。

2. **怎么证明你找到的是真瓶颈？**（补充练习）

   给出因果而不只是相关：单变量压测（固定其他层容量，逐层加压看哪层指标先饱和）、瓶颈消除后总吞吐随之上升、且线上故障与压测结论一致；只说“加了机器就快了”不算定位。

3. **秒杀活动前的容量准备怎么做？**（补充练习）

   按压测水位扩容并留安全余量，预热缓存／连接池／JIT／凭据，配好限流阈值与降级开关并演练，明确活动开关与止损口径（见 [[专题题库/系统设计#SYS-036：秒杀开始前的页面刷新与流量冲击如何承接（静态化、CDN、预热、兜底）？|SYS-036：秒杀开始前的流量冲击如何承接]]）。

### SYS-036：秒杀开始前的页面刷新与流量冲击如何承接（静态化、CDN、预热、兜底）？

**常见问法**

- 在秒杀活动正式开始前，如何应对用户不断刷新页面等行为带来的流量冲击？
- 活动还没开始，几十万人反复刷页面，后端怎么扛？

#### 面试回答

开抢前的流量特征是“读多写零且高度重复”，处理原则是让这些请求根本不落到业务链路：页面与数据静态化上 CDN，动态接口只留“是否开始、是否售罄、我的状态”这类极小查询；时间口径统一到服务端，未开始直接返回统一结果不回源；对同一时刻的并发相同查询做请求合并；活动前完成缓存与容量预热，并准备静态兜底页与降级路径；刷新类只读接口与下单类写接口的配额分开统计，防止刷页面挤占写路径额度。一句话收口：开抢前靠“把重复读往上层收敛”，开抢后才轮到限流与削峰兜底。

#### 技术细节

静态化分层：活动详情、规则文案、商品图与静态资源生成静态文件走 CDN 与浏览器缓存；把“千人不同”的部分（个人状态、是否已购）拆成独立小接口异步加载，让主页面保持可缓存——这是页面静态化能否成立的关键拆分。CDN 要同时配回源保护：回源限流与回源合并，否则缓存过期或命中率下降瞬间回源打穿源站。时间同步：按钮可用性由服务端下发时间或服务端判定控制，客户端时钟偏差与提前请求都不能触发真实写路径（开抢前的提前打接口，本质是防刷问题，见 [[专题题库/系统设计#SYS-033：秒杀抢购如何防刷，前端防刷能挡什么、直连接口刷单怎么防？|SYS-033：秒杀抢购如何防刷]]）。

请求整形：把固定间隔轮询改成带随机抖动的退避（避免整点同拍），前端节流合并重复刷新，服务端对同 key 并发查询用请求合并（singleflight，只回源一次，其余等待复用）——与缓存击穿的互斥重建是同一手法（见 [[专题题库/Redis#REDIS-002：缓存穿透是什么，布隆过滤器能完全解决吗？|REDIS-002：缓存穿透与击穿处理]]）。预热：热点数据提前进 Redis 与应用本地缓存，连接池、线程池、JIT 与下游凭据缓存一并暖机，按压测水位扩容；本地缓存短 TTL 会引入一致性窗口，需配失效广播（[[专题题库/系统设计#SYS-009：多级缓存如何保持一致，并在 Redis 故障时降级？|SYS-009：多级缓存如何保持一致]]）。兜底：详情查询失败返回缓存旧值或默认文案而不是报错打穿 DB，准备静态兜底页与活动开关。异常流量治理：高频刷新的 IP／设备走风控评分降速或出验证，但对真实用户只记指标不断服务（误伤口径见 [[专题题库/系统设计#SYS-034：同一出口 IP 下大量真实用户同时抢购，限流怎么设计才不误伤？|SYS-034：同一出口 IP 下限流怎么设计]]）。

#### 深挖追问

1. **为什么不干脆禁止刷新？**（补充练习）

   刷新是用户确认“抢到没有”的自然行为，禁止会转成客服与投诉成本；工程上要做的是让刷新的读代价趋近于零（缓存与静态化），再对超常频率限流，而不是禁功能。

2. **CDN 缓存了页面，为什么后端还会被打挂？**（补充练习）

   因为把动态部分和鉴权部分也留在主文档里，页面不可缓存，所有请求都回源；解法是拆分静态主页面与异步小接口，并配回源保护与请求合并。

3. **开抢瞬间的“同拍”问题怎么处理？**（补充练习）

   客户端侧随机抖动与节流、服务端侧请求合并与短 TTL 缓存、库存与热点 key 打散（[[专题题库/Redis#REDIS-010：什么是热 Key，为什么危险，如何探测与解决？|REDIS-010：什么是热 Key]]）；三者各管一段，只做客户端抖动仍会把并发压力传到服务端。

### SYS-037：如何设计搜索框的实时输入联想（自动补全）？

**常见问法**

- 如何实现一个类似淘宝搜索框的实时商品名称模糊搜索功能？
- 实时输入联想与输入完成后点击搜索，在技术实现上有什么本质区别？
- 自动补全怎么支持拼音、首字母和错别字？

#### 面试回答

先把需求量化再谈结构：每敲一个字符都要在几十毫秒内返回少量候选（一般 10 条以内），要求稳定快于一次完整搜索；匹配要能覆盖前缀、拼音与少量容错；排序以热度为主，可叠类目与个性化；候选来自受控词表而不是全库扫描。

分四层设计：① 候选池与离线加工——从商品标题、类目词、历史高频 query 里构建词表，做规范化（大小写、全半角、繁简、空格与标点），并为每个词生成多个索引键：原词、全拼、首字母、必要时 n-gram 或编辑距离容错键；热度分由点击与成交统计加时间衰减算出，离线批量生成、可回滚。② 在线检索——首选前缀型结构：Elasticsearch 的 completion suggester（底层 FST 常驻内存，前缀匹配代价随输入长度而非词典规模增长，支持权重排序与多分析器拼音字段），或自建 Trie／FST 服务；再对超热前缀加一层 Redis ZSet 结果缓存（前缀→Top-N，短 TTL，头部前缀命中率极高）。纯子串与纠错匹配要走弱索引或 n-gram＋打分，只作为前缀未命中时的降级，因为它的代价高一个量级。③ 请求形态——客户端 150～300ms 防抖、连续输入时取消上一次请求或带序列号丢弃过期响应（否则会出现“输入越短结果越新”的乱序）、请求超时兜底返回热门词而不是空。④ 治理与验证——词表更新的时效与回滚、无结果率、P95／P99 延迟、缓存命中率、以及按前缀长度看时延曲线。规模数字按【真实项目】填写。

“联想与点击搜索有什么本质区别”是这题的关键追问：联想是高频、低延迟、小结果集、以候选词为产物的前缀查询，每次按键都可能触发，所以并发被放大数倍、必须靠常驻内存结构与缓存、结果可容忍陈旧；点击搜索是一次完整查询，要跑多字段过滤与相关性打分、聚合、个性化与分页，访问全量索引、结果要尽量新鲜、延迟预算可以放宽到百毫秒级。两者常不共用同一条链路——用同一套硬扛，要么联想把打分集群打挂，要么正式搜索为迁就延迟牺牲排序质量。

#### 技术细节

前缀匹配的三种承载方式各有代价：Trie 直观但节点指针开销大，中文场景要靠压缩（双数组 Trie 或 FST）才可用；FST 把公共前缀与后缀都共享，内存小且天然支持字典序范围扫描，代价是构建重、更新要重建，所以适合“离线全量生成＋定期发布”；倒排＋`prefix` 查询实现最省事但延迟与内存受词表规模影响，需要限制字段与结果数。ES completion 字段要放在专门的 suggest 索引里、不能开 doc values 之外的实时刷新幻想，词表更新走别名切换索引更稳。

排序与个性化：热度是主特征，但要防“长尾永不露出”——加探索位或按前缀做冷启动兜底；点击回流要处理位置偏差（排在第一的被点得多不代表更好），常用同前缀下的相对偏好或去偏统计；个性化按用户画像与近期行为加权，但必须能降级成全局热度（新用户与关闭个性化的场景）。

容量与稳定性：联想接口的 QPS 常是主搜索的数倍，要单独限流与配额，别和正式搜索共用一个线程池（一个慢会拖垮另一个）；缓存键要包含归一化前缀与语言／人群分桶，但分桶过细会让命中率崩塌；超时要设得比正式搜索更短（例如 50ms 级），超时直接返回缓存或热门词；词表更新期间的双写与切换要保证候选不会突然变空。模糊与纠错要有阈值控制——过度纠错会返回不相关词，宁可无结果也不误导，尤其在电商场景。协议与请求形态的选择见 [[专题题库/计算机网络#NET-016：SSE 和 WebSocket 有什么区别，如何选择？|NET-016：SSE 和 WebSocket 有什么区别，如何选择]]（联想场景用短请求＋取消即可，不必上长连接）。

#### 深挖追问

1. **词表多大能用内存装下，多大就要换方案？**（补充练习）

   量级估算：千万级短词经 FST／双数组 Trie 压缩后通常在百 MB 到数 GB 区间，可常驻；到亿级或需要复杂相关性时，改用分布式检索服务、分片前缀路由，或退化为“热词进内存＋长尾走倒排”两级结构。答题要给估算过程而不是结论。

2. **为什么用户输入很短时结果反而更难做好？**（面经实际出现；[[面经/字节/一面/0009#Q10：如何实现一个类似淘宝搜索框的实时商品名称模糊搜索；实时输入联想与输入完成后点击搜索在技术实现上有什么本质区别？|MJ041 · 字节 · 一面 · Q10]] 的延伸）

   一个字符的前缀候选量极大且信息量几乎为零，排序只能靠热度与个性化先验；同时这一档请求量最大（所有人都会走到），所以常见做法是超短输入直接返回运营配置的热门榜单，不做实时计算，把算力留给长度≥2 的请求。

3. **怎么衡量联想做得好不好？**（补充练习）

   离线看候选覆盖率（用户最终搜索词是否出现在其前缀的候选里）与排序命中（MRR／Top-1 命中率）；在线看补全点击率、输入完成前的放弃率、以及由此带来的搜索耗时下降；还要盯无结果率与延迟分位。只报“点击率提升”而不说口径与实验设计会被追问。
