### CLOUD-001：Docker 容器和虚拟机有什么区别，为什么更轻量？

**常见问法**

- Docker 容器和虚拟机有什么区别，为什么更轻量？

- Docker 是什么，如何实现隔离和资源限制，如何进入容器？

#### 面试回答

- 传统虚拟机：虚拟化出一套硬件，上面跑一个独立的客户操作系统内核。
- 常见的 Linux Docker 容器：本质是一个被隔离的进程，共享宿主的 Linux 内核。用 namespace 隔离资源视图，用 cgroup 约束资源额度，再靠镜像带上应用和依赖。

之所以更轻量，是因为容器通常不用为每个实例启动完整客户内核，所以启动快、额外资源开销较少 —— 但要讲清楚：它的隔离方式和虚拟机不同，不是“小号虚拟机”。

- 隔离靠 Linux namespace：把 PID、网络、挂载点、IPC、UTS 等资源视图隔开；user namespace 涉及用户身份映射，具体是否启用依配置而定。限资源靠 cgroup 控制额度，再用 capabilities、seccomp 等限制权限与系统调用。
- 进容器用 `docker exec -it 容器名 sh`，它是在运行中的容器里新建一个 shell 进程；能不能用 `bash` 要看镜像里有没有。`attach` 是连接主进程的输入输出，别和 `exec` 混为一谈。
- 限额看 `docker run` 的 `--memory=512m`、`--cpus=1.5` 这类参数：CPU 配额不等于绑定某个核，要指定 CPU 集合得用 `--cpuset-cpus`。
- 补充一条边界：镜像做得极简、连 shell 都没有时，`exec sh` 会失败。

#### 技术细节

**镜像和内核是两件事**

- 镜像里可以包含某个发行版的用户空间文件，但这不代表每个容器都有自己的内核。
- 镜像用分层存储和写时复制，相同层不用重复存，这也是省空间的原因之一。

**三个容易说过头的地方**

- Docker 是容器工具与运行平台，不能把这个名字直接等同于所有容器技术。
- Docker Desktop 在 macOS／Windows 上跑 Linux 容器时，通常中间还有一层 Linux 虚拟机，所以不能说“整个环境绝不用虚拟机”。
- 容器仍有网络、存储和资源管理的开销，也不能直接运行依赖不兼容内核的任意系统。

#### 深挖追问

1. **为什么容器通常比虚拟机轻量？**（面经实际出现；[[面经/百度/一面/0003#Q17：Docker 容器和虚拟机有什么区别，为什么更轻量？|MJ006 · 百度 · 一面 · Q17]]）

   因为容器实例主要多出来的是应用进程和必要的用户空间，不用重复跑一整个客户内核。但“轻”不等于零成本：实际开销仍取决于镜像、宿主平台和应用本身。

2. **容器如何隔离、限资源并进入交互环境？**（面经实际出现；[[面经/百度/一面/0005#Q19：Docker 是什么，如何实现隔离和资源限制，如何进入容器？|MJ008 · 百度 · 一面 · Q19]]）

   先说定位：Docker 提供构建、分发和运行容器的工具。常见 Linux 容器共享宿主内核，具体分三件事：

   - 隔离：namespace 把进程号、网络、挂载点等视图隔开。
   - 限资源：cgroup 限制 CPU、内存等资源，再结合 capabilities 等约束权限。
   - 用户空间和依赖：由镜像提供。

   进入交互环境：运行中的容器用 `docker exec -it 容器名 sh` 启动一个交互 shell，镜像里有 bash 时才用 bash。限额用启动参数 `--memory`、`--cpus` 分别设置内存和 CPU。两条边界要一起说：网络隔离不等于资源限额；容器的内存预算也不能只按 JVM 堆来设。

3. **Docker 做中间件本地化部署，常见踩坑有哪些？**（面经实际出现；[[面经/帆软/二面/0001#Q07：Docker 做中间件本地化部署，遇到过什么问题？|MJ023 · 帆软 · 二面 · Q07]]）

   高频问题这几类：

   - 端口映射与服务名解析：宿主机和容器的网络视角不一样。
   - 忘记挂 volume：容器一重建数据就没了。
   - 镜像 tag 不锁定：版本会漂移。
   - arm Mac 跑 x86 镜像：靠模拟运行，有兼容性问题。
   - 内存／CPU 配额与 JVM 参数不匹配：会被 OOMKill。
   - 时区与字符集差异。
   - compose 启动顺序：应用先于依赖就绪，需要 healthcheck ＋ 条件等待。

   回答按“现象 → 定位 → 解决 → 固化进 compose／文档”组织，并且只讲亲自踩过的坑。

### CLOUD-002：Kubernetes 是什么，解决什么问题？

**常见问法**

- Kubernetes 是什么，解决什么问题？

- 是否了解 Kubernetes？

#### 面试回答

- Kubernetes 是容器化应用的编排平台。用法是声明式：你写下期望状态，控制器持续把实际状态协调过去。
- 它解决的问题：多节点上的应用调度、副本管理、故障后重建、服务发现与负载分发、滚动发布、扩缩容。
- 和 Docker 的分工：Docker 侧重构建与运行容器，Kubernetes 侧重管理集群中的工作负载，两者关注的层次不同。

#### 技术细节

**三个核心对象**

- Pod：基本调度单元，里面可以放需要共同运行的多个容器。
- Deployment：管无状态应用的副本数和滚动更新。
- Service：Pod 一直在变，Service 提供一个稳定的访问入口。

**一次声明在集群里怎么走**

- 控制平面通过 API 接收声明。
- 调度器挑节点。
- 节点上的 kubelet 协调容器运行时。
- 控制器不断对比期望状态和实际状态，有差异就持续协调过去。

**别把能力说满**

- 故障后能不能重建，取决于检测是否生效、有没有可用容量、配置对不对；扩容同理，依赖指标和策略。
- 挂了持久卷，不等于自动有数据库一致性和备份。
- Kubernetes 也不会替你构建业务镜像，或修复应用逻辑。

#### 深挖追问

1. **它怎样维持应用副本数？**（补充练习）

   靠控制器循环：发现实际副本少于声明值，就创建替代 Pod，再由调度器安排节点、kubelet 启动工作负载。新副本什么时候能接收流量，由就绪检查决定。

### CLOUD-003：单机 Docker 容器如何通过网络通信？

**常见问法**

- 单机 Docker 容器如何通过网络通信？

#### 面试回答

- 常用方式：把两个容器接入同一个用户自定义 bridge 网络，用容器名或网络别名解析对方，再访问对方的容器端口。
- 底层：Linux 上一般经 veth 与软件网桥转发，通常不需要先把端口发布到宿主机。
- 两个要点：服务要监听容器可访问的地址；某个容器里的 localhost 指的是它自己的网络命名空间，不是另一个容器。
- 边界：不同网络的容器不能默认互通，需要明确共享网络，或者走路由与发布端口的方案。

#### 技术细节

以 Linux Docker Engine 用户自定义 bridge 为例：

```sh
docker network create app-net
docker network connect app-net container-a
docker network connect app-net container-b
```

**示例的前提和用法**

- 前提：这两个容器已经存在并且在运行。
- 用法：之后 A 可以用 B 的容器名或网络别名，加上服务端口访问 B。
- 应用要监听可访问的接口，例如 0.0.0.0。

**三个容易混的点**

- 名称解析是用户自定义 bridge 提供的能力，默认 bridge 的行为不一样。
- 发布端口主要解决“从网络外部访问”；容器内部互访不该误用宿主上映射出来的端口。
- Linux 的 veth／网桥转发只是常见实现，不代表 host 模式或共享 network namespace 的模式。只有共享网络命名空间的容器，才可能通过同一个 localhost 互访。

#### 深挖追问

1. **同机两个容器能直接用 localhost 通信吗？**（补充练习）

   默认不行 —— 两个容器各自有独立的网络命名空间，localhost 只能回到自己。正确做法是访问对方的容器名或 IP。想让它们共用 localhost，得显式配成共享网络命名空间，那是另一种配置。
