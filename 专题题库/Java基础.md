### JAVA-001：什么是反射，有哪些应用与安全边界？

**常见问法**

- 什么是反射？
- 反射有什么安全隐患？
- 反射有哪些应用场景？

#### 面试回答

反射允许程序在运行时获取类、字段、方法和构造器的信息，并创建对象或调用方法。常用于依赖注入、ORM 映射、序列化和插件装配。它可能突破原有封装并把部分错误推迟到运行时，但不是无条件越过所有访问限制；类名或方法名若由不可信输入决定，还可能调用到不该暴露的能力。

#### 技术细节

通过 Class 获取元信息，再用 Constructor、Method、Field 操作。getDeclaredMethods 可看到本类声明的不同可见性方法，getMethods 主要返回 public 方法并包括继承成员；能发现不等于能调用。Java 9+ 模块机制下 setAccessible(true) 也可能失败，Java 17 对未开放包的深反射有明确限制。只对经过白名单映射的类型和操作反射，不把任意请求参数变成类名调用。性能取决于调用方式、缓存及 JIT，不能只背“反射慢若干倍”。

#### 深挖追问

1. **反射可以访问所有 private 字段吗？**（补充练习）

   不能无条件做到，语言访问检查可在许可范围内抑制，但模块开放和特定 final 字段限制仍存在。

2. **框架为什么使用反射？**（补充练习）

   框架需要在运行时根据配置、类型和注解装配用户类，不应为每个业务类手写固定调用。

### JAVA-002：什么是序列化与反序列化，能否用于深拷贝？

**常见问法**

- 什么是序列化与反序列化？
- 序列化和反序列化是深拷贝还是浅拷贝？

#### 面试回答

序列化把对象状态编码为可保存或传输的数据，反序列化按格式重建对象。完整地序列化并反序列化对象图，通常可得到独立的可变对象图，用作深拷贝手段；但它们本身不是“深浅拷贝”的同义词。transient、自定义读写及 readResolve 等会改变结果，不能保证每种序列化都完整复制所有字段。

#### 技术细节

以下重点说明 Java 原生 Serializable。默认机制处理非 static、非 transient 状态，使用对象句柄保留图内共享引用和循环；不要求把同一对象的每条引用都复制成不同对象。可达的普通成员对象也需可序列化，否则可能失败。serialVersionUID 参与兼容校验，不等于自动兼容任意字段变化。枚举、对象替换钩子及非序列化父类初始化有特殊规则。不反序列化未经约束的不可信原生对象流；输入过滤与格式选择应限制可构造类型和资源消耗。

#### 深挖追问

1. **序列化复制后 transient 字段也保留吗？**（补充练习）

   默认不会，需看自定义读写逻辑；因此不适合无条件充当通用对象克隆器。

2. **readResolve 返回单例还是深拷贝吗？**（补充练习）

   返回的可能是既有对象，身份独立性不再成立，要按实际重建规则判断。

### JAVA-003：深拷贝、浅拷贝与引用赋值有什么区别？

**常见问法**

- 深拷贝和浅拷贝有什么区别？

#### 面试回答

引用赋值只是让两个变量指向同一个对象；浅拷贝创建新外层对象，但引用字段仍指向原来的成员对象；深拷贝则复制需要独立的可变对象图。Object.clone 默认是字段级浅拷贝，数组或集合复制也不意味着元素一起深拷贝。判断时看对象身份和修改是否互相影响。

#### 技术细节

例如 User 内含可变 Address，浅拷贝后两个 User 不同，但 address 仍相同；修改 address.city 会互相影响。深拷贝可用复制构造器或显式映射，遇到环与共享节点需维护原对象到新对象的映射。String 等不可变对象通常可以安全共享，不必机械复制。`new ArrayList<>(old)` 创建新列表但复用元素。缓存直接返回原对象属于引用共享，不应硬归为“浅拷贝”。

#### 深挖追问

1. **怎么验证深拷贝？**（补充练习）

   分别检查外层身份、可变子对象身份，再修改复制品的子对象，确认原对象保持不变。

2. **Bean 属性复制工具一定是深拷贝吗？**（补充练习）

   不一定，常见属性复制只赋值引用，应检查具体库约定并为嵌套可变字段单独处理。

### JAVA-004：Java 接口中可以定义哪些方法？

**常见问法**

- 接口中可以定义哪些方法？

- 接口里可以有静态方法或静态变量吗？方法可以有默认实现吗？

#### 面试回答

Java 8 起接口可以有 public abstract 抽象方法、default 默认实例方法和 static 方法；Java 9 起还可以有 private 实例方法与 private static 方法供内部复用。接口不能声明构造器，private 方法不能是 abstract，接口 static 方法通常通过接口名调用，不像默认方法那样被实现类继承。

#### 技术细节

以 Java 17 为基准：普通无方法体声明隐含 public abstract；default 必须有方法体；private 方法同样需要实现且不能从外部访问。抽象方法允许泛型和 throws 声明，这不是额外的方法类别。两个接口提供冲突默认实现时，实现类需要显式解决；类继承中的适用方法通常优先于接口默认实现。接口字段隐含 public static final，但字段规则不要混入方法分类。

#### 深挖追问

1. **为什么要引入 private 方法？**（补充练习）

   让多个默认或静态方法共享实现，同时不把辅助逻辑暴露给调用方。

2. **接口静态方法能用实现类对象调用吗？**（补充练习）

   不能将其作为继承的实例方法调用，应使用声明它的接口名。

### JAVA-005：包装类型是什么，包装类型缓存有什么影响？

**常见问法**

- 说一下包装类型，包装类型的缓存是什么？

#### 面试回答

八种基本类型对应 Byte、Short、Integer、Long、Float、Double、Character、Boolean，包装对象用于泛型、集合和可空值等场景。Integer.valueOf 保证缓存 -128 到 127，并允许缓存更多；不能认为所有包装类型缓存都一样。比较数值应按类型使用 equals 或拆箱，两个包装对象用 == 比较的是身份。

#### 技术细节

自动装箱通常调用 valueOf，拆箱调用相应取值方法，null 拆箱会抛 NullPointerException。Java 17 常见实现中 Byte、Short、Long、Character、Boolean 也有各自缓存策略，Float、Double 没有这种小整数装箱身份保证；不要依赖缓存之外的对象身份。Integer 与 Long 即便数学值相等，equals 也不同。缓存对象可共享且不可变，不应拿包装对象当业务锁；更不能靠“127 相等、128 不等”替代正确比较。

#### 深挖追问

1. **Integer a=127,b=127，a==b 为什么通常成立？**（补充练习）

   该范围的自动装箱复用缓存对象；范围外不能把身份关系当作通用保证。

2. **Integer 与 int 用 == 呢？**（补充练习）

   通常会拆箱后比较数值，但 Integer 为 null 时会抛异常。

### JAVA-006：高精度小数用什么类型，BigDecimal 有哪些坑？

**常见问法**

- 存储小数需要高精度用什么类型？

#### 面试回答

Java 中精确十进制计算通常使用 BigDecimal，建议用字符串构造，或理解语义后使用 valueOf(double)，避免 new BigDecimal(0.1) 把二进制浮点误差带入。除法需明确精度和舍入规则；BigDecimal 不可变，运算返回新对象。数据库中通常配合 DECIMAL，并统一业务的小数位规则。

#### 技术细节

BigDecimal 用任意精度整数和 scale 表示十进制值。`new BigDecimal("0.1").add(new BigDecimal("0.2"))` 得到精确 0.3；valueOf(double) 利用该 double 的字符串表示，不会恢复在更早浮点计算中已经丢失的信息。1/3 不能有限表示，未给舍入条件可能抛 ArithmeticException。equals 同时看值和 scale，2.0 与 2.00 的 equals 为 false、compareTo 为 0；作为 Map key 时需统一表示。金额还需定义币种和舍入时点。

#### 深挖追问

1. **只比较金额大小用什么？**（补充练习）

   通常使用 compareTo；是否保留不同 scale 的业务差异要另行定义。

2. **BigDecimal 是否永远不会丢精度？**（补充练习）

   不是，MathContext、setScale 和除法舍入会按规则改变精度，只是变化可控。

### JAVA-007：Python 和 Java 做项目有什么主要区别？

**常见问法**

- Python 和 Java 写项目有什么主要区别？

#### 面试回答

Python 通常以动态类型和简洁表达提升原型迭代效率，Java 以静态类型、编译期检查和 JVM 生态支撑大型服务维护。两者都能写后端；选型看团队、依赖、性能与部署约束，不能简单说 Python 只能做脚本或 Java 一定快。

### JAVA-008：接口和抽象类有什么共同点和区别？

**常见问法**

- 接口和抽象类的共同点和区别？
- 什么时候用抽象类，什么时候用接口？

#### 面试回答

共同点：两者都是抽象类型，都不能被直接实例化（抽象类不能 new，接口不能 new，但都能当引用类型），都可以声明抽象方法强制实现方补齐，都支持多态，都可以写泛型和 `throws` 声明。
区别主要有四条：① 关系语义——抽象类表达 is-a，是“半成品骨架”，接口表达 can-do 的能力契约；② 状态——抽象类可以有实例字段和构造器（供子类 `super(...)` 初始化继承来的状态），接口里的字段只能是 `public static final` 常量，没有实例状态也没有构造器；③ 继承数量——类只能单继承抽象类，接口可以多实现；④ 成员可见性——抽象类方法可以是 private/包级/protected/public，接口方法只能 public（default 也需 public；private 方法仅限接口内部复用）。
选型口径：多个实现共享字段和流程骨架（模板方法）用抽象类；只约定能力、需要被不同体系混用、或要做解耦和可替换实现（依赖注入面向接口）用接口。Java 8 的 default 方法和 Java 17 的 sealed 让两者边界变模糊，但“能否携带实例状态、能否多继承”仍是硬区别。

#### 技术细节

接口能力按版本演进（以 Java 17 为基准）：Java 8 起允许 `default` 实例方法与 `static` 方法，Java 9 起允许 `private` 实例与静态方法做内部复用；接口可以含 `static final` 字段，但**不能**声明实例字段和构造器，也不能初始化块。抽象类必须有至少一个抽象方法才被禁止实例化？不——抽象类即使没有抽象方法也不能实例化（`abstract` 修饰本身就是约束），这是常见误区。
default 方法的解析规则要能答：类继承来的实现优先于接口默认实现（“类胜出”）；两个接口提供同名 default 时，实现类**必须**显式重写，否则编译错误；重写时可用 `接口名.super.方法()` 指定调用某个父接口的默认实现。
sealed 接口/类（Java 17）可以限定 `permits` 的实现集合，配合 `record` 与 switch 模式匹配可以表达代数数据类型：接口负责“有哪些变体”，抽象类负责“共享哪些状态和算法”， sealed 负责“变体封闭”。

#### 深挖追问

1. **接口里可以有静态变量吗？**（面经实际出现；[[面经/美团/一面/0001#Q20：接口和抽象类的共同点和区别？接口里能有静态方法、静态变量吗？方法能有默认实现吗？|MJ031 · 美团 · 一面 · Q20]]）

   可以写字段但语义受限：接口字段的修饰符隐含 `public static final`，写 `static int X = 1` 或不写修饰符结果都是常量，不能声明非 final 的静态可变变量，也没有实例字段。想放共享常量用接口是可以的，但工程上更推荐枚举或专门的常量类，避免被实现类“继承”进命名空间。

2. **接口的方法可以有默认实现吗？**（面经实际出现；[[面经/美团/一面/0001#Q20：接口和抽象类的共同点和区别？接口里能有静态方法、静态变量吗？方法能有默认实现吗？|MJ031 · 美团 · 一面 · Q20]]）

   Java 8 起可以，即 `default` 方法，实现类不重写就直接继承；引入动机是库演进（给 `Collection` 加 `stream()` 而不破坏既有实现）。两个接口给了冲突默认实现时实现类必须重写解决。

3. **抽象类一定要写 abstract 类吗，能全是具体方法？**（补充练习）

   可以，抽象类不必含抽象方法；只要类是 `abstract` 就不能实例化，常用于“只提供受保护的构造器与静态工厂”的场景（如枚举式基类、`Random` 之外的一些 JDK 类）。

4. **接口怎么表达需要状态的能力？**（补充练习）

   用 default 方法＋抽象访问器：接口声明 `getX()` 等抽象方法来“借”实现类的状态，default 逻辑建立在访问器之上（`Collection.stream()` 就是这种写法）。这样既不承诺字段布局，也能共享算法。

### JAVA-009：Java 面向对象有哪些特性，现代 Java 新增了哪些能力？

**常见问法**

- Java 是面向对象编程，那它现在的特性是什么？
- Java 的面向对象有哪些特性？
- 最近几个 Java 版本新增了什么语言特性？

#### 面试回答

面向对象层面是封装、继承、多态、抽象四件事：封装靠访问控制与不变量收口，继承用 `extends`/`implements` 复用类型与实现，多态分编译期重载和运行期由方法表分派的决定实现，抽象靠接口和抽象类隔离变化；配套能力是泛型（编译期类型检查、运行期类型擦除）、注解与反射、内部类。
“现在的 Java”是这题重点：Java 8 的 Lambda、Stream、Optional 和接口 default 方法；Java 10 的 `var`；Java 15/16 定型的 `record` 不可变数据载体与文本块，Java 16 的 `instanceof` 模式匹配；Java 17 的 `sealed` 密封类型；Java 21 的 switch 模式匹配与 record 解构定型、虚拟线程、Sequenced Collection；Java 22/23 的 FFM API 定型、未命名变量与模式；Java 24 的 Stream Gatherers 定型；Java 25（LTS）把 Scoped Values、紧凑源文件、模块化 import、灵活构造器体转正，基本类型模式匹配与结构化并发仍在预览。
一句话收口：Java 仍是面向对象为主，但已经融合函数式与值类型风格——`record`＋`sealed`＋模式匹配组合出代数数据类型写法，虚拟线程改变了阻塞式并发的成本结构。仍在预览的能力（截至 JDK 25）：基本类型模式匹配、结构化并发、稳定值；值对象/值类这条线尚未定型。

#### 技术细节

按“版本 → 能力 → 为什么有用”组织更利于口述，注意区分定型与预览：

| 版本 | 代表能力 | 说明 |
| --- | --- | --- |
| 8 | Lambda／Stream／Optional、接口 default、`java.time` | 函数式风格进入语言；接口可携带实现 |
| 10/11 | `var`、局部变量类型推断、HTTP Client | 仅局部变量，字段仍要显式类型 |
| 15/16 | `record`、文本块、`instanceof` 模式匹配定型 | record 自带规范构造器、equals/hashCode/toString |
| 17 | `sealed` 密封类与接口 | 与 record 配合枚举全部子类型 |
| 21 | switch 模式匹配与 record 解构定型、虚拟线程、Sequenced Collection | 虚拟线程让“一请求一线程”的阻塞写法可扩展 |
| 22/23 | FFM API 定型（22）、未命名变量与模式定型（23） | 非托管内存访问无需 JNI；`_` 占位 |
| 24 | Stream Gatherers 定型、紧凑对象头等 | 自定义中间流操作 |
| 25（LTS） | Scoped Values、紧凑源文件、模块化 import 声明、灵活构造器体定型；结构化并发仍是预览（第五轮） | 预览特性不要说成已稳定 |

三个易错点：① 泛型是编译期机制，运行期擦除，因此不能 `new T()`、不能 `T.class`、协变要用通配符 `? extends`；② 多态的“运行期分派”只对实例方法生效，字段与静态方法按编译期类型解析，重写（override）和重载（overload）别混；③ 截至 JDK 25，结构化并发与“原始类型参与模式匹配”仍是预览，值对象（Value Objects，JEP 401）未进入 JDK 25、被重新安排到后续版本做预览——讲这几项时必须加“预览”限定，并按面试时实际使用的 JDK 版本说明。
可延伸的工程面特性：模块化（Java 9 JPMS）、GraalVM 原生镜像与 AOT（Java 24/25 的 AOT 能力演进）、分代 ZGC/Shenandoah 等 GC 演进——如果面试官想问的其实是“Java 现在还能做什么”，用这一层收束。

#### 深挖追问

1. **为什么说 Java 不是纯面向对象语言？**（补充练习）

   存在基本类型与静态成员这类不依附对象的成员，加上 Lambda、Stream 与函数式接口，Java 实际是面向对象为主、融合函数式与值语义的多范式语言。

2. **`record` 和 Lombok 的 `@Data`、普通 POJO 怎么选？**（补充练习）

   `record` 是语言级不可变数据载体：字段 `final`、访问器名即字段名、自动等值语义，适合值与 DTO；缺点是浅不可变（可变字段内容仍可变）且不能继承。Lombok 靠注解处理器生成样板代码，能保持可变 POJO 与继承，但依赖构建插件、调试时源码与生成物不同步。

3. **虚拟线程会取代线程池吗？**（补充练习）

   不取代但改变用法：虚拟线程适合“大量阻塞任务”，不再需要靠池复用线程来控成本；但要限制下游并发时仍需 `Semaphore` 或有界队列，且不能用它包裹 `synchronized` 长临界区之外的阻塞（JDK 24 起 `synchronized` 已不再钉住载体线程，需按版本说明）。

### JAVA-010：单例模式有哪些写法，懒汉式如何保证线程安全？

**常见问法**

- 单例模式了解吗，具体有什么应用？
- 手撕：实现一个懒加载的单例，多线程同时创建会不会重复创建？

#### 面试回答

单例保证“一个类只有一个实例，并提供全局访问点”。常见写法按“线程安全怎么来”排：

1. **饿汉式**——`static` 字段里直接 `new`，类加载即创建，天然线程安全，但没有懒加载、不用也占内存。
2. **懒汉式（无锁）**——`getInstance` 判空再创建，延迟加载但多线程不安全（两个线程都看到 `null` 会各建一个）。
3. **双重检查锁（DCL）**——`volatile` 字段＋外层判空＋`synchronized`＋内层再判空，兼顾懒加载、线程安全与性能，手撕常考。
4. **静态内部类（Holder）**——外部类加载时不初始化，第一次 `getInstance` 触发内部类加载，靠 JVM 类初始化保证线程安全＋懒加载，写法简洁、推荐。
5. **枚举**——`enum` 单例，天然防反射与反序列化破坏，《Effective Java》推荐。

**应用**：Spring 容器 Bean 默认作用域即单例；线程池、`Runtime`、`Logger`、配置对象、连接池、本地缓存等“全局唯一且共享”的对象。收尾补边界：单例是共享可变状态，多线程访问要么无状态要么自己保证线程安全；单例过多会隐藏依赖、加大测试难度。

#### 技术细节

DCL 的两个判空各有用途：外层避免每次调用都进同步块（性能），内层保证真正持锁后仍只有一个线程创建。`volatile` 不可省——`new Singleton()` 可拆成「分配内存 → 初始化 → 把引用赋给变量」三步，编译器/CPU 可能把「初始化」和「赋引用」重排序，导致别的线程在外层判空看到非 null 引用却拿到未初始化完的半成品对象；`volatile` 的禁止重排序＋可见性语义正好堵住这个窗口，少了它 DCL 在理论上是坏的（《Effective Java》与 JDK 文档均以此为戒）。

无锁懒加载首选 Holder：把实例放进静态内部类的 `static` 字段，外部类初始化不触及它，第一次 `getInstance` 才加载内部类，`<clinit>` 由 JVM 加锁保证只执行一次——不用写 `synchronized` 就同时拿到懒加载与线程安全。

#### 深挖追问

1. **多个线程同时进入懒汉式 `getInstance` 会不会创建出多个实例？**（面经实际出现）

   只判空不加锁会——两个线程可能同时通过 `if (instance == null)`，各自 `new` 一个，返回不同对象。用 DCL（加锁＋二次判空）或 Holder／枚举（靠类初始化）即可避免。候选人现场答“借 Redis 锁的思路，先到的持锁、后到的放弃”，方向（要互斥）对但表述偏分布式，未落到语言内的 `synchronized` 双检锁。
   来源：[[面经/字节/一面/0008#Q09：手撕：实现一个懒加载的单例（追问：多线程同时创建会重复创建吗）|MJ033 · 字节 · 一面 · Q09]]

2. **`readResolve` 是干什么的？**（补充练习）

   序列化会绕过构造生成新对象，破坏单例；实现 `private Object readResolve()` 返回既有实例可在反序列化时恢复单例。枚举天然免疫这一点，这也是推荐枚举的原因之一。

3. **反射能破坏单例吗，怎么防？**（补充练习）

   反射可调用私有构造再造实例。枚举构造反射会抛异常，天然防护；普通单例可在构造里判“已存在实例则抛异常”来缓解，但最省心还是用枚举。

### JAVA-011：常用的 JDK 版本有哪些，版本之间主要差在哪？

**常见问法**

- 平时使用的 JDK 版本有哪些？不同版本有哪些区别？

#### 面试回答

先报自己真用过的版本，再讲主线差异，别逐版本背清单。常提的是几个 LTS：

- **JDK 8**：分水岭，Lambda／Stream／`Optional`、新日期时间 API、`HashMap` 红黑树化；存量系统占比最大，很多框架仍以 8 为基线。
- **JDK 11**：8 之后首个 LTS，模块化（JPMS，9 引入）落地、标准 `HttpClient`、`var` 局部变量推断、G1 成为默认收集器并增强、字符串改进。
- **JDK 17**：主流新基线，`record`、`sealed` 类、`instanceof` 模式匹配、Switch 表达式增强；**Spring Boot 3 / Spring 6 最低要求 17**。
- **JDK 21**：LTS，**虚拟线程（Project Loom）**、分代 ZGC、SequencedCollection、switch 模式匹配与记录模式。

一句话概括差异方向：语言更简洁（var/record/sealed/模式匹配）、并发与 GC 能力升级（G1 默认→ZGC 分代→虚拟线程）、以及工程生态门槛（Boot 3 要 17）。回答时说明“新项目为什么上 17／21、老系统为什么留在 8”。

#### 技术细节

区分“语言/库变化”和“平台/工具链变化”两类：泛型、注解、模块化、垃圾回收器属于平台演进；Stream、var、record、sealed、模式匹配、虚拟线程 API 属于语言与库演进。非 LTS 版本（9、10、12…16、18…20）通常不长期采用，面试不必细讲，能说出“每半年发一版、每几年一个 LTS（8/11/17/21）”即可。选版本还要看依赖库兼容（老公司中间件可能不支持 11+ 的模块化或移除的 `javax`→`jakarta` 命名空间，Boot 3 换 `jakarta` 是典型迁移成本）。

#### 深挖追问

1. **JDK 和 JRE、JVM 有什么区别？**（补充练习）

   JVM 执行字节码；JRE 是运行所需类库＋JVM；JDK 在 JRE 之上再加编译器 `javac`、调试打包等开发工具。开发装 JDK，纯运行环境理论上 JRE 足够（新版本分发已弱化独立 JRE 概念）。

2. **为什么 Spring Boot 3 要求 JDK 17 起步？**（补充练习）

   Boot 3 基于 Spring 6，用了更高版本的语言能力、切换到 `jakarta.*` 命名空间（Jakarta EE 9+），并把基线抬到 17 这个 LTS；沿用 Boot 2 才能留在 JDK 8。
