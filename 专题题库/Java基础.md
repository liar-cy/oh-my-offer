### JAVA-001：什么是反射，有哪些应用与安全边界？

**常见问法**

- 什么是反射？
- 反射有什么安全隐患？
- 反射有哪些应用场景？

#### 面试回答

反射就是程序在运行时才去拿类的信息：类有哪些字段、哪些方法、哪些构造器，然后据此创建对象或调用方法。

- 常见用途：依赖注入、ORM 映射、序列化、插件装配。
- 代价：会突破原有封装，还把一部分错误从编译期推迟到运行时。
- 但它是“有条件”的能力，不是无条件越过所有访问限制。
- 安全边界：类名或方法名如果由不可信输入决定，可能调用到不该暴露的能力。

#### 技术细节

**怎么用**

- 先拿到 `Class` 对象读取元信息，再通过 `Constructor`、`Method`、`Field` 这三个入口去创建对象、调方法、读写字段。

**两种取方法的差别**

- `getDeclaredMethods`：能看到本类声明的方法，各种可见性都算，但不含继承来的成员。
- `getMethods`：主要返回 public 方法，并且包含从父类和接口继承来的成员。
- 能“发现”不等于能“调用”，真要调用还得过访问检查这一关。

**模块机制带来的限制**

- Java 9 引入模块机制之后，`setAccessible(true)` 也可能直接失败。
- Java 17 对未开放包的深反射有明确限制。

**安全与性能的口径**

- 只对经过白名单映射的类型和操作做反射，不要把任意请求参数变成类名去调用。
- 性能取决于调用方式、有没有缓存、以及 JIT（即时编译）的情况，不能只背一句“反射慢若干倍”。

#### 深挖追问

1. **反射可以访问所有 private 字段吗？**（补充练习）

   不能无条件做到。语言的访问检查可以在许可范围内抑制掉，但还有两道限制仍在：模块是否开放了这个包，以及特定 `final` 字段的规则。

2. **框架为什么使用反射？**（补充练习）

   因为框架编译时并不知道运行时要装配哪些用户类。它只能在运行时按配置、类型和注解去找类、调方法，不可能为每个业务类手写一份固定调用。

### JAVA-002：什么是序列化与反序列化，能否用于深拷贝？

**常见问法**

- 什么是序列化与反序列化？
- 序列化和反序列化是深拷贝还是浅拷贝？
- 存储用户信息时涉及序列化和反序列化，这有什么作用？
- 二进制序列化和 JSON 序列化有什么差异？分别适配什么场景？（见 JAVA-020）

#### 面试回答

序列化是把对象状态编码成能存、能传的数据；反序列化是照着这个格式把对象重新建出来。

- 能不能当深拷贝用：把整张对象图完整序列化再反序列化，通常能得到一份独立的可变对象图，所以可以作为一种深拷贝手段。
- 但别把它当“深浅拷贝”的同义词，这两个概念不是一回事。
- 会改变结果的因素：`transient` 字段、自定义读写逻辑、`readResolve` 等钩子。
- 所以不能保证每种序列化都把每个字段都完整复制一遍。

#### 技术细节

以下重点说明 Java 原生 `Serializable`。

**默认机制复制哪些内容**

- 只处理非 `static`、非 `transient` 的状态。
- 内部用对象句柄记录已经写过的对象，因此图内的共享引用和循环结构都能保留下来。
- 也就是说，它不要求把同一个对象的每条引用都复制成不同对象——这一点和“深拷贝就是每条引用都新建”的直觉不一样。
- 图上可达的普通成员对象也得可序列化，否则整个流程可能失败。

**serialVersionUID 的作用范围**

- 它参与兼容校验，但校验通过不等于任意字段变化都能自动兼容。

**几处特殊规则**

- 枚举、对象替换钩子（如 `writeReplace`／`readResolve`）、以及非可序列化父类的初始化，都有各自的特殊规则。

**安全边界**

- 不要反序列化未经约束的、不可信的原生对象流。
- 输入过滤和格式选择要限制住“能构造哪些类型”和“能用多少资源”。

#### 深挖追问

1. **序列化复制后 transient 字段也保留吗？**（补充练习）

   默认不会保留，具体要看有没有自定义读写逻辑把它补回来。也正因为这一点，序列化不适合无条件充当通用的对象克隆器。

2. **readResolve 返回单例还是深拷贝吗？**（补充练习）

   不一定，返回的可能是既有对象。一旦是既有对象，“复制品与原对象身份独立”这个前提就不成立了，要按实际的重建规则来判断。

### JAVA-003：深拷贝、浅拷贝与引用赋值有什么区别？

**常见问法**

- 深拷贝和浅拷贝有什么区别？

#### 面试回答

三者差别在“复制到哪一层”：

- 引用赋值：只是两个变量指向同一个对象，根本没产生新对象。
- 浅拷贝：新建了外层对象，但引用字段仍然指向原来的成员对象。
- 深拷贝：把需要独立的可变对象图整个复制一遍。

两个容易忘的点：`Object.clone` 默认是字段级浅拷贝；数组或集合复制过一层，也不代表里面的元素跟着一起深拷贝了。判断时只看两件事——对象身份是否不同，以及改一边会不会影响另一边。

#### 技术细节

**一个具体例子**

- `User` 里含一个可变的 `Address`。浅拷贝后两个 `User` 对象确实不同，但它们的 `address` 还是同一个。
- 这时改 `address.city`，两边都会变——这就是浅拷贝的典型后果。

**深拷贝怎么写**

- 常用手段是复制构造器，或者显式做一遍字段映射。
- 遇到环和共享节点时，必须维护一张“原对象 → 新对象”的映射表，否则会死循环或者把共享结构拆散。

**不用复制的情况**

- `String` 这类不可变对象通常可以安全共享，不必机械地再复制一份。

**两个容易说错的边界**

- `new ArrayList<>(old)` 只是创建了新列表，元素仍是原来那批对象的引用。
- 缓存直接返回原对象，属于引用共享，不该硬归成“浅拷贝”。

#### 深挖追问

1. **怎么验证深拷贝？**（补充练习）

   分三步验证：先比对两个外层对象的身份不同，再比对可变子对象的身份也不同，最后改一下复制品里的子对象，确认原对象没有任何变化。

2. **Bean 属性复制工具一定是深拷贝吗？**（补充练习）

   不一定。常见的属性复制基本只做引用赋值，嵌套的可变字段仍然共享。要看具体库的约定，嵌套可变字段得单独处理。

### JAVA-004：Java 接口中可以定义哪些方法？

**常见问法**

- 接口中可以定义哪些方法？

- 接口里可以有静态方法或静态变量吗？方法可以有默认实现吗？

#### 面试回答

按版本说能定义哪几类方法：

- Java 8 起：`public abstract` 抽象方法、`default` 默认实例方法、`static` 方法。
- Java 9 起：还能写 `private` 实例方法和 `private static` 方法，给接口内部复用。

三条限制要补上：接口不能声明构造器；`private` 方法不能同时是 `abstract`；接口的 `static` 方法一般通过接口名调用，它不像默认方法那样被实现类继承。

#### 技术细节

以 Java 17 为基准。

**各类方法的规则**

- 普通的、不写方法体的声明，隐含 `public abstract`。
- `default` 方法必须有方法体。
- `private` 方法同样要有实现，而且不能从接口外部访问。
- 抽象方法可以带泛型和 `throws` 声明——这只是修饰，不构成另一类方法。

**冲突怎么解决**

- 两个接口给了冲突的默认实现时，实现类必须显式把它解决掉。
- 一般情况下，类继承里能适用的方法优先于接口的默认实现。

**别把字段规则混进来**

- 接口的字段隐含 `public static final`，但这是字段规则，不要混进方法的分类里讲。

#### 深挖追问

1. **为什么要引入 private 方法？**（补充练习）

   为了在接口内部复用实现：让多个 `default` 方法或 `static` 方法共享同一段逻辑，又不把这段辅助逻辑暴露给调用方。

2. **接口静态方法能用实现类对象调用吗？**（补充练习）

   不能。它不会作为继承来的实例方法被调用，只能用声明它的那个接口名来调用。

### JAVA-005：包装类型是什么，包装类型缓存有什么影响？

**常见问法**

- 说一下包装类型，包装类型的缓存是什么？
- Java 中 `long` 和 `Long` 有什么区别？性能上呢？

#### 面试回答

八种基本类型各有一个包装类：Byte、Short、Integer、Long、Float、Double、Character、Boolean。用在泛型、集合和可空值这类场景里。

- 缓存：`Integer.valueOf` 保证缓存 -128 到 127，也允许缓存更多；但不能认为所有包装类型的缓存规则都一样。
- 比较：要按类型用 `equals` 或者拆箱比数值。两个包装对象之间用 `==` 比的是身份，不是数值。

#### 技术细节

**装箱和拆箱底层调了什么**

- 自动装箱通常调用 `valueOf`；拆箱调用对应的取值方法（如 `intValue`）。
- 包装值为 `null` 时拆箱会抛 `NullPointerException`。

**各类型的缓存策略并不一致**

- Java 17 的常见实现里，Byte、Short、Long、Character、Boolean 也各有自己的缓存策略。
- Float、Double 没有这种“小整数装箱后身份可复用”的保证。
- 结论：不要依赖缓存范围之外的对象身份。

**equals 的跨类型边界**

- `Integer` 和 `Long` 即使数学上的值相等，`equals` 结果也不同。

**三条别用错**

- 缓存对象既可共享又不可变，所以不要拿包装对象当业务锁。
- 更不要靠“127 相等、128 不等”这种观察结论去替代正确的比较写法。

#### 深挖追问

1. **Integer a=127,b=127，a==b 为什么通常成立？**（补充练习）

   因为这个范围内的自动装箱会复用同一个缓存对象，所以两个变量的身份相同。范围外就不能把这种身份关系当成通用保证。

2. **Integer 与 int 用 == 呢？**（补充练习）

   通常会先把 `Integer` 拆箱，再按数值比较。但 `Integer` 为 `null` 时会抛异常。

3. **`long` 和 `Long` 有什么区别？性能上呢？**（面经实际出现；[[面经/帆软/二面/0003#Q03：Java 中 long 和 Long 有什么区别？性能上呢？|MJ052 · 帆软 · 二面 · Q03]]）

   先说定位：`long` 是 8 字节基本类型，`Long` 是它的包装对象。

   - 存储与语义：`long` 直接存值、不能为 `null`；`Long` 是堆上对象（含对象头），能表示“无值”，用于泛型、集合和可空字段。
   - 比较：`Long` 之间 `==` 比对象身份，缓存范围（-128~127）外不相等，比值用 `equals`；`Long` 与 `long` 比较会拆箱按数值。
   - 性能：`Long` 有装箱／拆箱与堆分配开销，还多一层指针跳转；数组场景 `long[]` 连续存原始值，比 `Long[]`（一堆对象引用）省内存、缓存友好得多。
   - 风险：对可能为 `null` 的 `Long` 直接参与运算或拆箱会抛 NPE。
   - 收口：默认用 `long`，只有在“必须放进泛型／集合”或“需要表达 null”时才用 `Long`。

### JAVA-006：高精度小数用什么类型，BigDecimal 有哪些坑？

**常见问法**

- 存储小数需要高精度用什么类型？

#### 面试回答

Java 里要做精确十进制计算，通常用 `BigDecimal`。

- 怎么构造：建议用字符串构造；或者理解语义之后再用 `valueOf(double)`。别写 `new BigDecimal(0.1)`，那会把二进制浮点的误差一起带进来。
- 除法：必须明确精度和舍入规则。
- 不可变：每次运算返回新对象，原对象不变。
- 落库：数据库通常配 `DECIMAL` 类型，并且把业务侧的小数位规则统一约定下来。

#### 技术细节

**它怎么表示一个数**

- 用一个任意精度的整数（unscaled value）加一个 `scale`（小数点位置）来表示十进制值。

**构造方式的差别**

- `new BigDecimal("0.1").add(new BigDecimal("0.2"))` 得到精确的 0.3。
- `valueOf(double)` 用的是这个 double 的字符串表示形式。
- 但它救不回更早的浮点计算里已经丢掉的信息——已经丢的就是丢了。

**必须给舍入条件的情况**

- 1/3 这种无法有限表示的结果，如果不给舍入条件，可能直接抛 `ArithmeticException`。

**equals 和 compareTo 不等价**

- `equals` 同时看值和 `scale`：2.0 与 2.00 的 `equals` 是 `false`，`compareTo` 是 0。
- 因此把 `BigDecimal` 当作 Map 的 key 时，要先统一表示形式。

**金额场景还要额外定什么**

- 除了数值本身，还要定义币种和舍入发生的时点。

#### 深挖追问

1. **只比较金额大小用什么？**（补充练习）

   通常用 `compareTo`，因为它只看数值大小、不看 `scale`。至于要不要保留不同 `scale` 带来的业务差异，得另外定义。

2. **BigDecimal 是否永远不会丢精度？**（补充练习）

   不是。`MathContext`、`setScale` 和除法的舍入都会按规则改变精度。区别只在于这种变化是显式、可控的。

### JAVA-007：Python 和 Java 做项目有什么主要区别？

- Python 和 Java 写项目有什么主要区别？
- Python 是静态还是动态语言？静／动态的区别、类型转换上的区别？

#### 面试回答

- Python：靠动态类型和简洁表达，原型和迭代速度快。

#### 技术细节

**类型系统的差别**

- Python 的类型标注通常靠检查工具起作用，不会自动变成运行时的强制类型校验。

**并发模型：Python 侧**

- CPython 3.13 的默认构建仍然有 GIL（全局解释器锁），所以 CPU 密集的纯 Python 代码用多线程受限。
- 3.13 另外提供了一个非默认的 free-threaded（去 GIL）构建，但这不能泛化成“所有 Python 都这样”。
- 真要并行：I/O 型并发可以用线程或异步；CPU 型工作可以用进程，或者用会释放 GIL 的原生库。

**并发模型：Java 侧**

- 平台线程可以多核并行，但共享状态和资源同样要控制。

1. **如何选型？**（补充练习）

### JAVA-008：接口和抽象类有什么共同点和区别？

**常见问法**

- 接口和抽象类的共同点和区别？
- 什么时候用抽象类，什么时候用接口？

#### 面试回答

共同点有五条：

- 两者都是抽象类型，都不能被直接实例化（抽象类不能 new，接口也不能 new，但都能当引用类型）。
- 都可以声明抽象方法，强制实现方补齐。
- 都支持多态。
- 都可以写泛型。
- 都可以写 `throws` 声明。

区别主要四条：

- 关系语义：抽象类表达 is-a，是“半成品骨架”；接口表达 can-do，是能力契约。
- 状态：抽象类可以有实例字段和构造器，供子类用 `super(...)` 初始化继承来的状态；接口里的字段只能是 `public static final` 常量，没有实例状态，也没有构造器。
- 继承数量：类只能单继承抽象类，接口可以多实现。
- 成员可见性：抽象类的方法可以是 private／包级／protected／public；接口的方法只能 public（default 也需 public，private 方法仅限接口内部复用）。

选型口径：多个实现共享字段和流程骨架（模板方法）就用抽象类；只约定能力、需要被不同体系混用、或者要做解耦和可替换实现（依赖注入面向接口）就用接口。Java 8 的 default 方法和 Java 17 的 sealed 让两者边界变模糊了，但“能否携带实例状态、能否多继承”仍是硬区别。

#### 技术细节

**接口能力按版本演进（以 Java 17 为基准）**

- Java 8 起：允许 `default` 实例方法和 `static` 方法。
- Java 9 起：允许 `private` 实例方法与静态方法，用于接口内部复用。
- 接口可以含 `static final` 字段，但**不能**声明实例字段和构造器，也不能写初始化块。

**一个常见误区**

- “抽象类必须有至少一个抽象方法才被禁止实例化”？不成立。
- 抽象类即使一个抽象方法都没有，也不能实例化——`abstract` 修饰本身就是那个约束。

**default 方法的解析规则（要能答出来）**

- 类继承来的实现优先于接口的默认实现，也就是“类胜出”。
- 两个接口提供同名 default 时，实现类**必须**显式重写，否则编译错误。
- 重写时可以用 `接口名.super.方法()` 指定调用某一个父接口的默认实现。

**sealed 这一层怎么配合**

- sealed 接口／类（Java 17）可以用 `permits` 限定实现的集合。
- 配合 `record` 与 switch 模式匹配，就能表达代数数据类型：接口负责“有哪些变体”，抽象类负责“共享哪些状态和算法”，sealed 负责“变体封闭”。

#### 深挖追问

1. **接口里可以有静态变量吗？**（面经实际出现；[[面经/美团/一面/0001#Q20：接口和抽象类的共同点和区别？接口里能有静态方法、静态变量吗？方法能有默认实现吗？|MJ031 · 美团 · 一面 · Q20]]）

   可以有字段，但语义受限：接口字段的修饰符隐含 `public static final`。

   - 写 `static int X = 1`，或者干脆不写修饰符，结果都是常量。
   - 不能声明非 final 的静态可变变量，也没有实例字段。
   - 想放共享常量，用接口是可以的；但工程上更推荐枚举或专门的常量类，避免被实现类“继承”进命名空间。

2. **接口的方法可以有默认实现吗？**（面经实际出现；[[面经/美团/一面/0001#Q20：接口和抽象类的共同点和区别？接口里能有静态方法、静态变量吗？方法能有默认实现吗？|MJ031 · 美团 · 一面 · Q20]]）

   Java 8 起可以，就是 `default` 方法：实现类不重写就直接继承它。引入动机是库演进——要给 `Collection` 加 `stream()`，又不能破坏既有实现。两个接口给了冲突的默认实现时，实现类必须自己重写解决。

3. **抽象类一定要写 abstract 类吗，能全是具体方法？**（补充练习）

   可以，抽象类不必含抽象方法。只要类声明成 `abstract` 就不能实例化。常见用法是只对外提供受保护的构造器与静态工厂（比如枚举式基类，以及 `Random` 之外的一些 JDK 类）。

4. **接口怎么表达需要状态的能力？**（补充练习）

   用 default 方法＋抽象访问器：接口声明 `getX()` 这类抽象方法，向实现类“借”状态，default 逻辑建立在访问器之上（`Collection.stream()` 就是这种写法）。这样既不承诺字段布局，又能共享算法。

### JAVA-009：Java 面向对象有哪些特性，现代 Java 新增了哪些能力？

**常见问法**

- Java 是面向对象编程，那它现在的特性是什么？
- Java 的面向对象有哪些特性？
- 最近几个 Java 版本新增了什么语言特性？

#### 面试回答

面向对象层面是封装、继承、多态、抽象四件事：

- 封装：靠访问控制与不变量收口。
- 继承：用 `extends`／`implements` 复用类型与实现。
- 多态：编译期看方法重载，运行期由方法表分派决定。
- 抽象：靠接口和抽象类隔离变化。
- 配套能力：泛型（编译期类型检查、运行期类型擦除）、注解与反射、内部类。

“现在的 Java 新增了什么”才是这题的重点，按版本报：

- Java 8：Lambda、Stream、Optional，接口 default 方法。
- Java 10：`var`。
- Java 15/16：定型的 `record`（不可变数据载体）与文本块；Java 16 的 `instanceof` 模式匹配。
- Java 17：`sealed` 密封类型。
- Java 21：switch 模式匹配与 record 解构定型、虚拟线程、Sequenced Collection。
- Java 22/23：FFM API 定型、未命名变量与模式。
- Java 24：Stream Gatherers 定型。
- Java 25（LTS）：把 Scoped Values、紧凑源文件、模块化 import、灵活构造器体转正；基本类型模式匹配与结构化并发仍在预览。

一句话收口：Java 仍以面向对象为主，但已经融合函数式与值类型风格——`record`＋`sealed`＋模式匹配组合出代数数据类型的写法，虚拟线程改变了阻塞式并发的成本结构。仍在预览的能力（截至 JDK 25）有三个：基本类型模式匹配、结构化并发、稳定值；值对象／值类这条线尚未定型。

#### 技术细节

按“版本 → 能力 → 为什么有用”组织更利于口述，注意区分定型与预览：

| 版本 | 代表能力 | 说明 |
| --- | --- | --- |
| 8 | Lambda／Stream／Optional、接口 default、`java.time` | 函数式风格进入语言；接口可携带实现 |
| 10/11 | `var`、局部变量类型推断、HTTP Client | 仅局部变量，字段仍要显式类型 |
| 15/16 | `record`、文本块、`instanceof` 模式匹配定型 | record 自带规范构造器、equals/hashCode/toString |
| 17 | `sealed` 密封类与接口 | 与 record 配合枚举全部子类型 |
| 21 | switch 模式匹配与 record 解构定型、虚拟线程、Sequenced Collection | 虚拟线程让“一请求一线程”的阻塞写法可扩展 |
| 22/23 | FFM API 定型（22）、未命名变量与模式定型（23） | 非托管内存访问无需 JNI；`_` 占位 |
| 24 | Stream Gatherers 定型、紧凑对象头等 | 自定义中间流操作 |
| 25（LTS） | Scoped Values、紧凑源文件、模块化 import 声明、灵活构造器体定型；结构化并发仍是预览（第五轮） | 预览特性不要说成已稳定 |

**三个易错点**

- 泛型是编译期机制，运行期擦除：所以不能 `new T()`、不能 `T.class`，协变要用通配符 `? extends`。
- 多态的“运行期分派”只对实例方法生效：字段和静态方法都按编译期类型解析；重写（override）和重载（overload）别混。
- 截至 JDK 25，结构化并发与“原始类型参与模式匹配”仍是预览；值对象（Value Objects，JEP 401）未进入 JDK 25，被重新安排到后续版本做预览。讲这几项时必须加“预览”限定，并按面试时实际使用的 JDK 版本说明。

**可以往外延伸的工程面特性**

- 模块化（Java 9 JPMS）。
- GraalVM 原生镜像与 AOT（Java 24/25 的 AOT 能力演进）。
- 分代 ZGC／Shenandoah 等 GC 演进。
- 如果面试官真正想问的是“Java 现在还能做什么”，就用这一层收束。

#### 深挖追问

1. **为什么说 Java 不是纯面向对象语言？**（补充练习）

   因为语言里有基本类型和静态成员这两类不依附于对象的成员，再加上 Lambda、Stream 与函数式接口。所以 Java 实际上是面向对象为主、融合函数式与值语义的多范式语言。

2. **`record` 和 Lombok 的 `@Data`、普通 POJO 怎么选？**（补充练习）

   `record` 是语言级的不可变数据载体：字段 `final`、访问器名就是字段名、自动带等值语义，适合表达值和 DTO。两个缺点：浅不可变（可变字段的内容照样能变），而且不能继承。Lombok 是靠注解处理器生成样板代码，能保留可变 POJO 和继承关系，代价是依赖构建插件、调试时源码和生成物不同步。

3. **虚拟线程会取代线程池吗？**（补充练习）

   不取代，但改变了用法。

   - 虚拟线程适合“大量阻塞任务”，不再需要靠池复用线程来控制成本。
   - 要限制下游并发时，仍然需要 `Semaphore` 或者有界队列。
   - 且不能用它包裹 `synchronized` 长临界区之外的阻塞（JDK 24 起 `synchronized` 已不再钉住载体线程，需按版本说明）。

### JAVA-010：单例模式有哪些写法，懒汉式如何保证线程安全？

**常见问法**

- 单例模式了解吗，具体有什么应用？
- 手撕：实现一个懒加载的单例，多线程同时创建会不会重复创建？
- 手撕：写一个线程安全的单例模式。
- 饿汉式和懒汉式单例的区别？饿汉式为什么是线程安全的？懒汉式为什么要双重检查？

#### 面试回答

单例保证“一个类只有一个实例，并提供全局访问点”。常见写法按“线程安全怎么来”排：

1. **饿汉式**——`static` 字段里直接 `new`，类加载即创建，天然线程安全，但没有懒加载、不用也占内存。
2. **懒汉式（无锁）**——`getInstance` 判空再创建，延迟加载但多线程不安全（两个线程都看到 `null` 会各建一个）。
3. **双重检查锁（DCL）**——`volatile` 字段＋外层判空＋`synchronized`＋内层再判空，兼顾懒加载、线程安全与性能，手撕常考。
4. **静态内部类（Holder）**——外部类加载时不初始化，第一次 `getInstance` 触发内部类加载，靠 JVM 类初始化保证线程安全＋懒加载，写法简洁、推荐。
5. **枚举**——`enum` 单例，天然防反射与反序列化破坏，《Effective Java》推荐。

**应用**：Spring 容器 Bean 默认作用域即单例；线程池、`Runtime`、`Logger`、配置对象、连接池、本地缓存等“全局唯一且共享”的对象。

**两个边界**：

- 单例是共享可变状态，多线程访问要么做成无状态，要么自己保证线程安全。
- 单例过多会隐藏依赖、加大测试难度。

#### 技术细节

**DCL：两个判空各有各的用途**

- 外层判空：避免每次调用都进同步块，这是性能考虑。
- 内层判空：保证真正持锁之后，仍然只有一个线程去创建。

**DCL：`volatile` 为什么不能省**

- `new Singleton()` 可以拆成三步：“分配内存 → 初始化 → 把引用赋给变量”。
- 编译器／CPU 可能把“初始化”和“赋引用”这两步重排序。
- 一旦重排，别的线程在外层判空时看到引用非 null，拿到的却是没初始化完的半成品对象。
- `volatile` 的禁止重排序＋可见性语义正好堵住这个窗口。少了它，DCL 在理论上是坏的（《Effective Java》与 JDK 文档都以此为戒）。

**Holder：无锁懒加载的首选**

- 把实例放进静态内部类的 `static` 字段。
- 外部类初始化时不触及它，第一次 `getInstance` 才去加载内部类。
- `<clinit>`（类初始化）由 JVM 加锁，保证只执行一次。
- 结果：不用写 `synchronized`，就同时拿到懒加载和线程安全。

#### 深挖追问

1. **多个线程同时进入懒汉式 `getInstance` 会不会创建出多个实例？**（面经实际出现）

   只判空不加锁就会。两个线程可能同时通过 `if (instance == null)`，各自 `new` 一个，最后返回不同对象。用 DCL（加锁＋二次判空），或者 Holder／枚举（靠类初始化），都能避免。

   候选人现场答“借 Redis 锁的思路，先到的持锁、后到的放弃”：方向（要互斥）是对的，但表述偏分布式，没落到语言内的 `synchronized` 双检锁。
   来源：[[面经/字节/一面/0008#Q09：手撕：实现一个懒加载的单例（追问：多线程同时创建会重复创建吗）|MJ033 · 字节 · 一面 · Q09]]

2. **`readResolve` 是干什么的？**（补充练习）

   用来在反序列化后把单例找回来。因为序列化会绕过构造函数生成新对象，单例就被破坏了；实现 `private Object readResolve()` 返回既有实例，就能在反序列化时恢复单例。枚举天然免疫这一点，这也是推荐枚举的原因之一。

3. **反射能破坏单例吗，怎么防？**（补充练习）

   能，反射可以调用私有构造再造一个实例。防护分两档：

   - 枚举：反射调用枚举构造会直接抛异常，天然防护。
   - 普通单例：可以在构造里判断“已存在实例就抛异常”来缓解，但最省心的还是用枚举。

4. **饿汉式单例是线程安全的吗？代价是什么？**（面经实际出现；[[面经/虾皮/一面/0002#Q07：饿汉式单例是线程安全的吗？|MJ048 · 虾皮 · 一面 · Q07]]）

   线程安全：实例在静态字段初始化时创建，发生在类初始化阶段——JVM 对 `<clinit>` 加初始化锁且只执行一次，多线程拿到的必然是同一个引用，不需要自己同步。

   代价是没有懒加载：类一加载就占内存；对象创建昂贵或可能永远用不上时浪费。要懒加载又要安全，选静态内部类 Holder 或枚举。

### JAVA-011：常用的 JDK 版本有哪些，版本之间主要差在哪？

**常见问法**

- 平时使用的 JDK 版本有哪些？不同版本有哪些区别？
- 你一般使用的 JDK 版本是多少？谈谈 Java 的新特性。

#### 面试回答

先报自己真用过的版本，再讲主线差异，别逐版本背清单。常提的是几个 LTS：

- **JDK 8**：分水岭，Lambda／Stream／`Optional`、新日期时间 API、`HashMap` 红黑树化；存量系统占比最大，很多框架仍以 8 为基线。
- **JDK 11**：8 之后首个 LTS，模块化（JPMS，9 引入）落地、标准 `HttpClient`、`var` 局部变量推断、G1 成为默认收集器并增强、字符串改进。
- **JDK 17**：主流新基线，`record`、`sealed` 类、`instanceof` 模式匹配、Switch 表达式增强；**Spring Boot 3 ／ Spring 6 最低要求 17**。
- **JDK 21**：LTS，**虚拟线程（Project Loom）**、分代 ZGC、SequencedCollection、switch 模式匹配与记录模式。
- **JDK 25**（2025-09 GA，特性版本非 LTS）：Scoped Values 定稿（JEP 505）、紧凑对象头（JEP 519，默认关闭、需 `-XX:+UseCompactObjectHeaders`）、PEM 编解码 API（JEP 470）、移除 32 位 x86 端口（JEP 503）；结构化并发仍是第五次预览（JEP 613）、Module Import Declarations 预览（JEP 512）——报状态要报准，别说“25 上了结构化并发”。

#### 技术细节

**先把变化分成两类**

- 平台／工具链演进：泛型、注解、模块化、垃圾回收器。
- 语言与库演进：Stream、var、record、sealed、模式匹配、虚拟线程 API。

**LTS 与非 LTS 怎么说**

- 非 LTS 版本（9、10、12…16、18…20）通常不会被长期采用，面试不必逐个细讲。
- 能说出“每半年发一版、每几年出一个 LTS（8／11／17／21）”就够了。

- 还要看依赖库兼容性：老公司的中间件可能不支持 11+ 的模块化，或者不支持被移除的 `javax`→`jakarta` 命名空间。
- Boot 3 换到 `jakarta` 就是典型的迁移成本。

#### 深挖追问

1. **JDK 和 JRE、JVM 有什么区别？**（补充练习）

   三层从小到大：

   - JVM：只负责执行字节码。
   - JRE：运行所需的类库＋JVM。
   - JDK：在 JRE 之上再加编译器 `javac`、调试打包等开发工具。

2. **JDK 25 有什么新特性？**（面经实际出现；[[面经/钉钉/一面/0001#Q11：JDK 25 有哪些新特性？|MJ072 · 钉钉 · 一面 · Q11]]）

   三条主线，能分清“定稿／预览／移除”就算答到点：

   - Loom 系列继续收口：Scoped Values 定稿（虚拟线程间共享不可变上下文的推荐方式）；结构化并发第五次预览（JEP 613）仍在打磨 try-with-resources 式的 `StructuredTaskScope`。

3. **为什么 Spring Boot 3 要求 JDK 17 起步？**（补充练习）

   - 基线直接抬到了 17 这个 LTS。

   想留在 JDK 8，就只能继续沿用 Boot 2。

### JAVA-012：Object 类有哪些方法？equals 和 hashCode 为什么要一起重写？

**常见问法**

- 介绍一下 Java 的 Object 对象有哪些方法？
- Object 的 equals 方法和 hashCode 方法要一起重写，原因是什么呢？

#### 面试回答

Object 有 9 类共 11 个公开方法，按用途分组报：

- 相等与哈希：equals、hashCode。
- 运行时信息与复制：getClass、clone。
- 等待与唤醒：wait（三个重载）、notify、notifyAll。
- 其他：toString、finalize（Java 9 起废弃，不当考点）。

一起重写的原因，先给契约再讲后果：

- 契约：“equals 相等的对象 hashCode 必须相等”；反过来不要求。
- 只重写 equals：内容相等的对象哈希值不同，落进 HashMap／HashSet 的不同桶。
- 后果三连：get 取不到、去重去不掉、remove 删不掉。
- 根因：哈希容器查找是两步——先按 hashCode 定位桶，再用 equals 在桶内确认；第一步就分家，第二步永远轮不到。

#### 技术细节

**各方法的默认行为**

- equals：等价于 `==`，比引用。
- hashCode：返回身份哈希（identity hash code），首次计算后缓存在对象头里。
- toString：`类全名@哈希的十六进制`。
- clone：protected 的浅拷贝，类须实现 Cloneable，否则抛 CloneNotSupportedException。
- finalize：至多执行一次、不保证及时，官方已不推荐，资源清理用 try-with-resources。

**写 equals 的完整清单**

- 自反短路（`this == other`）、判 null、比类型（getClass 或 instanceof，继承场景注意对称性）、逐字段比较、对象字段用 `Objects.equals`。
- hashCode 用参与 equals 的同一批字段计算（`Objects.hash(...)` 或 31 倍数法）；不含某字段就要两边都不含。
- record（Java 16+）自动提供按字段的 equals／hashCode／toString，两者天然一致。

**为什么冲突是安全的**

- hashCode 相等而 equals 不等只是同桶挂链，正确性不受影响，只损失性能。
- 所以“只重写 hashCode 不重写 equals”不会找不中，但会让不同对象挤进同桶，同样不建议。

**一个容易踩的运行时坑**

- 可变字段参与了 hashCode，对象作为 key 存入后又修改该字段：定位桶按旧哈希、比较按新内容，key 从此找不中。哈希表的 key 应当不可变。

#### 深挖追问

1. **不重写 hashCode、只靠 equals，HashMap 就完全不能用吗？**（补充练习）

   能用但语义错：每次 put 内容相同的新对象都会因哈希不同再开一个桶位，Map 变成“允许逻辑重复”，且旧条目 get／remove 不到。

2. **`==` 比较两个内容相同的 String 为什么有时为 true？**（补充练习）

   字面量会被驻留（intern）进字符串池，引用恰好相同；`new String` 出来的就不同。内容比较一律 equals，这也是“别拿 String 当锁”的原因（见 JUC-004）。

### JAVA-013：Java 的异常分为哪几种？受检与非受检异常在使用上有什么不同？

**常见问法**

- Java 的异常分为哪几种？
- 受检异常和非受检异常在使用上有何不同？
- Exception 和 Error 有什么区别？
- Java 里面一般会碰到异常，先讲讲你理解的 Java 里面的异常，该怎么处理？
- 比如调一个 update 产生超时了的异常，这属于受检异常还是非受检异常？有哪些异常属于受检异常？
- 出现异常怎么处理？什么时候向上传递比较好，什么时候自己处理比较好？异常不处理的后果是什么？

#### 面试回答

顶层 Throwable，两大支、小分支三类：

- Error：JVM 层面的故障，OutOfMemoryError、StackOverflowError；应用不该捕获，也恢复不了。
- 受检异常（checked）：Exception 下除 RuntimeException 之外的部分，IOException、SQLException 为代表；编译器强制 catch 或 throws。
- 非受检异常（unchecked）：RuntimeException 及其子类，空指针、越界、ClassCastException；编译器不强制。

使用上的不同，一句话：受检异常是“必须当场表态的外部故障”，非受检是“该修代码的编程错误”。

- 受检：调用处选择重试、换数据源还是继续上抛，逻辑里绕不开。
- 非受检：靠前置校验避免、靠全局异常处理器统一兜底，不该到处 catch 吞掉。

#### 技术细节

**语法层的具体差别**

- 方法签名 `throws IOException` 是编译期契约：调用方不处理就编译不过。
- RuntimeException 可以出现在任何一行而不出现在签名里，这就是“非受检”的含义。
- `throw new Error()` 同样不受编译检查（Error 也不算受检）。

**工程上为什么业务异常常做成 Runtime**

- Spring `@Transactional` 默认只对 RuntimeException 和 Error 回滚；抛受检异常要写 `rollbackFor`，容易漏。
- 链路中间层不想为某个业务失败改一遍方法签名。
- 代价：编译器不再提醒调用方处理，得靠约定和文档补位。

**捕获与抛出的几个易错点**

- finally 里 return 会吞掉 try 的返回值和异常；finally 里抛异常会替换原始异常。
- try-with-resources（7+）自动关资源，并且把关闭异常作为 suppressed 挂在主异常上，不丢信息。
- 包装异常务必传 cause（`new BizException(msg, e)`），否则原始堆栈断了。
- 多 catch `catch (A | B e)`（7+）合并同处理分支；注意分支间类型不能有包含关系。

**处理还是上抛：按“决策能力”分层**

- 判据一句话：谁有能力做出正确的恢复动作，谁才处理；其余层翻译后上抛。
- 恢复动作其实只有四类：重试、换源（备库／备用接口）、降级（返回兜底）、补偿（记下来异步冲账）。这一层四类都做不了，就不该在这层 catch。
- 中层最差的姿势是 catch 住只打一行日志继续走——异常被吞，上层以为成功。要吞就必须写明“为什么可以吞、吞了什么影响”。
- 出口必须收敛：应用边界用统一异常处理（Web 场景 `@ControllerAdvice` 这类全局 handler）翻译成响应码＋脱敏日志，堆栈不向用户暴露，事务回滚也在这层决策。

#### 深挖追问

1. **栈溢出是异常还是错误？为什么不该 catch 它？**（补充练习）

   是 Error（StackOverflowError）。线程栈空间耗尽，catch 住也没有可靠的恢复路径；正确动作是修递归深度或调 `-Xss`，不是兜异常。

2. **受检异常在运行时还存在吗？**（补充练习）

   “受检”只是编译期规则；运行期 JVM 不区分。所以通用容器能塞进任何异常——但这是绕过检查的技巧，不要当实践。

3. **调一个 update 出现超时异常，算受检还是非受检？**（面经实际出现；[[面经/拼多多/一面/0002#Q11：Java 异常怎么处理？update 超时异常属于受检还是非受检？有哪些受检异常？什么时候向上传递、什么时候自己处理？不处理的后果？|MJ044 · 拼多多 · 一面 · Q11]]）

   看你在哪层 API 边界上接它，两头都要说：

   - 底层是受检：`SocketTimeoutException` 是 IOException 的子类；JDBC 的 `SQLException` 也受检。
   - 业务层通常已变非受检：Spring 把持久层异常翻译成 `DataAccessException` 家族（RuntimeException），调用处不被编译器强制处理。
   - 这题考的是“受检性由声明的 API 决定、同一故障在不同层可以两种形态出现”，直接猜一边都会翻车。
   - 顺带报受检清单：IOException 家族、SQLException、ClassNotFoundException、InterruptedException。

4. **异常一直没人处理，后果是什么？**（面经实际出现；[[面经/拼多多/一面/0002#Q11：Java 异常怎么处理？update 超时异常属于受检还是非受检？有哪些受检异常？什么时候向上传递、什么时候自己处理？不处理的后果？|MJ044 · 拼多多 · 一面 · Q11]]）

   异常沿调用栈上抛，一路没人接，当前线程终结：

   - 默认行为是走线程的未捕获异常处理器，把堆栈打到 stderr，线程死亡；线程池里表现为 worker 挂掉补新。
   - 栈上各帧的 finally／try-with-resources 仍会执行，但异常点之后的业务收尾（状态更新、计数、释放登记）被跳过——脏状态才是最大后果。
   - Web／容器有 500 兜底不让进程崩，但事务半执行、消息没发这类不一致没人替你收拾，所以“出口收敛异常”是硬要求。

### JAVA-014：静态内部类和非静态内部类有什么区别？

**常见问法**

- 静态内部类和非静态内部类的调用区别？

#### 面试回答

一句话：区别在“持不持有外部类实例的引用”，调用方式只是它的表象。

- 非静态内部类：编译期隐式持有外部实例引用（`Outer.this`），必须借外部实例创建——`outer.new Inner()`；能直接读写外部实例字段；自身不能声明静态成员（编译期常量除外）。
- 静态内部类：不持有外部引用，本质是“借用外部类命名空间的普通类”——`new Outer.StaticInner()` 直接创建；只能访问外部的静态成员。
- 调用侧两条后果：非静态内部类实例会把外部实例一起钉在内存里（回调、缓存场景易泄漏）；泛型／注解等结构位置（如嵌套的 Builder、DTO）一般应写成 static。

#### 技术细节

**构造差异的根因**

- 非静态内部类的构造器会被编译器加上外部实例参数，字节码里存为 `this$0` 字段——所以没有外部实例就构造不出来。
- 每个非静态内部类实例只绑定“创建它的那一个”外部实例；`o1.new Inner()` 与 `o2.new Inner()` 是两个不同归属的对象。

**成员合法性差别**

- 非静态内部类里静态字段、静态方法都非法（Java 16 起局部接口放宽了部分限制，成员类口径不变）；静态内部类什么都可以有。
- 内部类（非静态）还不能和外部类同名。

**为什么默认推荐 static**

- 不持外部引用 ⇒ 没有隐式生命周期耦合；Effective Java 的建议：只要不需要访问外部实例，成员类一律声明为静态。
- 典型事故：监听器／Handler 写成非静态内部类并被长生命周期对象持有，整个外部 Activity／Service 释放不掉（Android 场景最常见，Java 服务端等价于把大对象挂在回调链上）。

**别混淆的邻居概念**

- 局部类（方法内定义）与匿名内部类都可以捕获外部变量（要求 effectively final），它们是非静态语境；lambda 不产生新的 `this` 作用域，捕获的是词法变量——面试问到“lambda 和匿名类区别”时这是主线之一。

#### 深挖追问

1. **非静态内部类访问外部私有字段，字节码层面是怎么做到的？**（补充练习）

   javac 生成包私有的 synthetic 访问桥方法（历史上是 `access$100` 这类），内部类经桥读写；访问控制仍在源码层生效，这是“编译期协作”而非反射。

2. **静态内部类单例（Holder 模式）为什么线程安全？**（补充练习）

   借用类初始化保证：`private static class Holder { static final INSTANCE = new ...; }`，首次触碰 Holder 才触发其 `<clinit>`，JVM 保证初始化只执行一次且有可见性——延迟加载＋无锁，见 JAVA-010。

### JAVA-015：常用的设计模式有哪些，如何结合项目来讲？

**常见问法**

- 谈谈编程常用的设计模式有哪些（可以列举一些，并结合项目中用到的一起谈谈）。

#### 面试回答

不背 23 个，按“它替你消化了哪种变化”报三大类，再落项目：

- 创建型（管 new）：单例——全局唯一实例；工厂方法／抽象工厂——把“造哪个具体类”的决定收口；建造者——多可选参数的分步构造。
- 结构型（管拼装）：代理——不改被代理类加横切能力（Spring AOP 即样板）；适配器——接口转换接上新依赖；装饰器——包一层加功能（IO 流家族）。
- 行为型（管协作）：策略——一套接口多算法可替换（干掉 if-else）；模板方法——骨架固定、步骤可变；观察者——事件发布订阅解耦；责任链——一串处理器依次放行（过滤器链）。
- 项目讲法公式：变化点是什么 → 选了哪个模式 → 结构怎么落地 → 换朴素写法会痛在哪。【按真实项目填，例：多种计价规则用策略＋工厂注册；缓存预热钩子用模板方法；订单状态通知用观察者解耦】
- 加分边界：模式是词汇不是目标——说不出“应对什么变化”的模式就是过度设计。

#### 技术细节

**框架里的现成例子（背熟十个比背二十三个名字有用）**

- 代理：Spring AOP（JDK／CGLIB）；装饰器：`java.io` 的 `BufferedInputStream(new FileInputStream(..))`——同结构套娃加能力。
- 模板方法：`AbstractList.get` 衍生的遍历骨架、`JdbcTemplate` 的资源管理流程；观察者：事件总线、RxJava 的 Subscriber。
- 责任链：Servlet Filter 链、Netty `ChannelPipeline`；工厂：`Executors`（虽被规约劝退直接用）、`ConnectionFactory`。
- 单例：Spring 容器 Bean 默认 scope 就是受管单例——“你的对象生命周期交给了他”，这层说出层次最好。

**策略 vs 状态机 vs if-else 的选型口径**

- 分支少、稳定：if-else 完全合法，别硬上模式。
- 分支多且会增删、各分支逻辑重：策略＋注册表（Map<类型,策略> 或枚举驱动）。
- 分支间有迁移关系：那已经不是策略，是状态机。

**面试常见戳穿问**

- “你这项目用策略，一共几个策略？多久变一次？”——变化频率撑不起抽象，就坦率说“其实两个分支，写成了配置”，比硬撑强。

### JAVA-016：API 和 SPI 有什么区别，Java 的 SPI 机制怎么工作？

**常见问法**

- API 和 SPI 的区别？

#### 面试回答

一句话：看“接口与实现谁是主导、控制权朝哪个方向”。

- API：服务方定义接口并实现，调用方按接口使用——控制权在提供方内部，实现可以随便改，接口稳定就行。
- SPI（Service Provider Interface）：框架／标准方只定义接口，实现由第三方提供、运行期按约定装载——把“选哪个实现”的决策权外置。
- 记法：API 是“我给你用”，SPI 是“我定规矩、你来接”。典型：`JDBC Driver`（接口在 JDK、实现在厂商 jar）、SLF4J 与日志实现的绑定、Dubbo 扩展点。

#### 技术细节

**JDK SPI 的机制（ServiceLoader）**

- 约定：classpath 下 `META-INF/services/接口全限定名` 文件里写实现类全名，一行一个。
- 加载：`ServiceLoader.load(Itf.class)` 返回可迭代对象——懒加载，遍历时才反射实例化（无参构造），并用迭代器缓存已加载项。
- 边界：一次 load 拿到的是“全部实现”，没有按 key 选择、不会缓存单例、加载即实例化整个列表代价高——这些正是 Spring 在其上补的洞。

**Spring Boot 的“改良 SPI”**

- `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`／旧版 `spring.factories`：同样是“接口方定清单、实现方来登记”，但配合条件注解按需装配（见 SPRING-001），且以 Bean 形式进容器享受生命周期。
- Dubbo 的 `META-INF/dubbo/接口名`（key=value 形式）补上了按名选择——被问“JDK SPI 太糙怎么办”时给这两个演进方向。

**类加载器这层的暗坑**

- `ServiceLoader` 默认用线程上下文类加载器加载实现——JDBC 这类“父加载器的 API 要加载子路径实现”的场景靠它打破双亲委派方向（背景见 JVM-007）。

**别混淆**

- SPI≠RPI 之类缩写想当然；和 Web service 的“接口”（WS／REST）也无涉——本题语境是 Java 扩展点机制。

#### 深挖追问

1. **SLF4J 找日志实现用的就是这套吗？**（补充练习）

   SLF4J 1.x 的 binding 机制思路同源（按 classpath 探测实现，找不到退化为 NOP）；2.x 改用 `ServiceLoader` 加载 `SLF4JProvider`。多个实现同时在 classpath 会告警并选一个——“日志绑定了哪个实现”排查就从这里来。

2. **SPI 的“控制反转”和设计原则什么关系？**（补充练习）

   就是依赖倒置的机制化：高层（框架）只依赖抽象，实现细节由低层模块通过配置文件反向注入；微内核＋插件架构（IDEA 插件、JDK Charset）都靠这个契约运转。

### JAVA-017：值传递和引用传递有什么区别？Java 属于哪一种？

**常见问法**

- 编程中的值传递和引用传递有什么区别？Java 属于哪一种？

#### 面试回答

- 判据一条：在被调方法里给形参重新赋值，调用方的实参跟不跟着变。跟着变才叫引用传递；值传递传的是副本，改副本与实参无关。
- 结论先给：Java 只有值传递；对象参数传的是“引用的副本”。
  - 方法内 `p = new Node()` 重指向 → 外面看不到（改的是副本的绑定）。
  - 方法内 `p.value = 1` 解引用改对象 → 外面看得到（副本指向同一堆对象）。
- 两个经典佐证：交换两个 int 的 swap 函数永远交换失败；`StringBuilder` 参数里 `sb = new StringBuilder()` 不影响外面，`sb.append(..)` 会。
- 易错话术：“Java 对象是引用传递”混了“把引用当值传”和“引用传递”——前者传副本、后者能改绑定，语义完全不同。

#### 技术细节

**术语对照（JLS 口径）**

- 方法声明的参数叫形参；调用时求值传入的是实参。JLS 明确：Java 程序语言只用值调用（call by value）——对象类型的“值”恰好是引用，所以传的还是值。
- C++ 的 `void f(T& x)` 是真引用传递：形参是实参的别名，赋值直通；C# 有 `ref／out` 关键字显式标记；Python 是“对象引用按值传”（call by object reference 的说法），和 Java 机制同类但名字易误导。

**为什么设计成值传递**

- 调用方对变量绑定有绝对控制：任何方法都不能“顺手”把你的变量指向别处，副作用只可能发生在显式解引用处——可读性与封装性的取舍。

**和深浅拷贝的接续点**

- “传引用副本”意味着方法内外共享同一对象：想隔离就得自己深拷贝（见 JAVA-003）；API 返回内部集合前拷贝一份是同一道理的防御性写法。

#### 深挖追问

1. **`final` 参数能表示引用传递吗？**（补充练习）

   不能。`final` 只是禁止改绑定（不能重新赋值形参），也不禁止解引用改对象——它管的是副本本身，不改变传递语义。

2. **native 方法或有例外吗？**（补充练习）

   没有。JNI 层要显式拿句柄、显式回写（如 `SetObjectArrayElement`），“能改外面”也是显式协议的结果，不是语言参数传递语义变了。

### JAVA-018：解释型语言和编译型语言有什么区别？Java 算哪种？

**常见问法**

- 解释型语言和编译型语言的区别？每个分别举两个知道的例子。

#### 面试回答

- 判据：源码翻译成可执行形态发生在运行前还是运行中。
- 编译型：提前整体翻译成机器码／本地码，运行快、部署要按平台编译——例子 C／C++、Go（Rust 亦可）。
- 解释型：运行期由解释器逐句翻译执行，跨平台靠解释器、启动快，单条开销大——例子 Python、JavaScript。
- Java 的标准答案是“两段式混合”：javac 编译成平台无关字节码（编译发生在运行前，但产物不是本地码）；运行期 JVM 解释执行字节码＋热点代码 JIT 即时编译成本地码——它是“编译到中间表示＋解释与即时编译混合”，归纯解释或纯编译都错。
- 例子句加分：正因混合才有预热现象（刚启动慢、跑热变快）与 AOT（GraalVM native-image）的存在意义。

#### 技术细节

**分界线本来就不干脆**

- 现代引擎几乎全是混合：CPython 也先编成 .pyc 字节码再解释；JS 引擎有 tiered JIT；C# 介于其间（IL＋JIT／AOT 双模式）。
- 所以面试价值在“能说出各家的执行形态”，不在背分类表。

**性能差异的来源**

- 执行形态只决定大致方向：JIT 热了以后可以逼近甚至超过静态编译（运行时信息做激进特化，见 JVM 专题的逃逸分析／去优化），代价是预热时间和峰值抖动；静态编译胜在启动与可预测性。

**与 Java 跨平台的关系**

- “一次编译到处运行”成立的前提是每个平台有自己的 JVM 实现＋字节码这个中间层（JVM-004）；换芯片架构要换的是 JVM 与本地依赖，字节码本身不用重编——这正是中间表示的价值。

#### 深挖追问

1. **那 Java 到底算编译语言还是解释语言？**（面经实际出现；见来源——本题后半问）

   规范上不定义：JVM 规范只约定字节码语义，解释还是编译执行是实现自由（JVM-004 同口径）。答题推荐句式：“javac 编译＋运行期解释与 JIT 混合”，并说明这个混合带来的预热行为。

2. **AOT 和 JIT 的取舍？**（补充练习）

   AOT 启动快、峰值稳，丢掉了运行时画像与去优化能力，且失去跨发行版通用性；Server 常驻大流量吃 JIT 红利，短生命周期／CLI 工具适合 AOT——GraalVM native-image 就是为后者补的。

### JAVA-019：方法重载怎么判定，只有返回值不同算重载吗？

**常见问法**

- 两个方法名称和参数列表相同、返回值不同，算重载吗？
- 一个类里出现两个方法，名字和参数列表一样、只有返回值不同，会怎样？

#### 面试回答

不算重载，而且编译不过。

- 重载（overload）= 方法名相同 + 参数列表不同（个数、类型或顺序不同）。返回值类型不是判定依据。
- 名字和参数列表都相同、只有返回值不同，两者方法签名一致，属于重复方法，编译期直接报错（`duplicate method`），轮不到运行期。
- 根因一句话：调用点不写“我要哪个返回值”，编译器无法只凭返回值区分目标方法，所以 Java 干脆不允许返回值参与签名。

#### 技术细节

**什么算“方法签名”**

- 按 JLS，方法签名 = 方法名 + 形参类型列表。
- 返回值类型、访问修饰符、`throws` 列表、是否 `static` 都不属于签名。
- 所以“签名相同”就判定为重复定义；这正是本题两个方法编译报错的原因。

**别和“重写”搞混**

- 重写（override）要求签名相同（方法名 + 参数列表一致），发生在父子类之间。
- 重写允许返回值协变（JDK 5 起，子类可返回更具体的子类型），也允许收窄受检异常。
- 区别记法：协变返回值是“重写里返回值能变”的例外，它不是重载；重载只在同类或同名方法间靠参数列表区分。

**装箱／泛型带来的重载坑（了解即可）**

- `f(int)` 与 `f(Integer)` 是合法重载，传 `1` 会优先匹配 `int`（不做装箱）。
- 泛型擦除后可能让“看着不同”的形参类型变相同，导致编译报冲突——例如 `m(List<String>)` 与 `m(List<Integer>)` 擦除后签名一致，不能共存。
- 传 `null` 调用多重载时，编译器选“最具体”的参数类型；无法判定唯一最具体就报歧义错误。

#### 深挖追问

1. **为什么 Java 不允许只靠返回值重载？**（补充练习）

   因为调用表达式（如 `obj.m()` 或把它当参数传入）本身不带“期望返回值”的信息，编译器在重载决议时拿不到区分依据，会引入歧义。为此规范把返回值排除在签名之外。

2. **`int` 和 `Integer` 参数算重载吗？调用时选哪个？**（补充练习）

   算，是合法重载。传字面量 `int` 时优先匹配 `int`（不装箱）；传 `Integer` 对象时匹配 `Integer`；实在没有精确匹配才按装箱／拆箱与拓宽规则处理。

3. **泛型不同算重载吗？**（面经实际出现的相关延伸；[[面经/科大讯飞/二面/0001#Q07：方法名和参数列表相同、只有返回值不同，算重载吗？会怎样？|MJ051 · 科大讯飞 · 二面 · Q07]]）

   看擦除后的签名。擦除后形参类型相同就不能共存（编译报冲突），与“只有返回值不同”是同一类判定：以擦除后的方法签名为准。

### JAVA-020：二进制序列化和 JSON 序列化有什么差异？各自适配什么场景？

**常见问法**

- [[面经/收钱吧/一面/0001#Q08：序列化的作用、二进制与 JSON 序列化的差异、发生在网络的哪一层|MJ068 · 收钱吧 · 一面 · Q08]]
- 存储用户信息涉及序列化和反序列化，这有什么作用？
- 序列化和反序列化是在计算机网络的哪一层做的？

#### 面试回答

结论：JSON 可读、自描述、跨语言通吃，代价是体积与解析开销；二进制紧凑、快，代价是要靠 schema／约定对齐版本——按“给谁看、多频繁传”选。

- JSON：文本格式，人眼可读、浏览器原生支持、加字段天然兼容；但字段名重复传输使体积大，浮点精度与超大整数（JS Number 只有双精度）会失真，日期只能靠字符串约定。
- 二进制家族：Protobuf（要 .proto schema，按字段编号编码，跨语言且体积常小 2～10 倍）、Hessian／Kryo／Java 原生（带类描述或依赖类路径）、MessagePack 等；解析快，但不可读，版本要靠编号规则／optional 语义维护。
- 发生在哪一层：编解码都发生在应用层（应用进程内）；TCP 只负责把产出的字节流按段传输，它不感知你用了什么编码。
- 场景分工一句话：对外 HTTP 接口→JSON；内部高频 RPC／消息体→Protobuf 等二进制；写缓存要兼顾可查→JSON（Jackson）或按体积选二进制；落日志审计→人要能读的就 JSON。

#### 技术细节

**Java 原生序列化是“二进制”但不建议新用**

- `Serializable` 流携带类描述符，跨语言差、有反序列化攻击面（不可信输入可构造恶意对象链），且字段变更兼容只靠 `serialVersionUID` 很脆弱。
- 本库对它的机制口径（transient、句柄去重、readResolve）见 [[#JAVA-002：什么是序列化与反序列化，能否用于深拷贝？|JAVA-002]]；“二进制”≠“Java 原生序列化”，别混着答。

**Protobuf 的兼容性纪律**

- 字段用编号标识：新增字段用新编号、旧字段永远不删不重用，消费端把未知字段跳过或保留——这是“可演进”的全部基础。
- `optional`（proto3 默认）区分“未设置”与“零值”要靠显式 presence；数值 int64 转 JSON 时按字符串输出防前端丢精度，这些是接口层最常踩的坑。

**Redis／Spring Session 里选哪种**

- RedisTemplate 的 value 序列化器可选：JDK 序列化体积大且不可读；`GenericJackson2JsonRedisSerializer` 带 `@class` 类型信息可还原具体类型；纯 `Jackson2JsonRedisSerializer` 定死类型更省。
- Session 这类“高频读写的小对象”优先 JSON：体积可控、排障时 redis-cli 直接能看；对体积极敏感再考虑二进制。

**性能差异来自哪里**

- JSON 慢在词法解析与反射绑定、大在小数点与转义处理；二进制快在按字段编号直接读写定长／varint 数值。
- 报数字要克制：差异与字段结构强相关，说“通常小数倍、解析快数倍”比背一个固定倍数稳。

#### 深挖追问

1. **序列化后的数据一定要同语言反序列化吗？**（补充练习）

   JSON／Protobuf（共享 .proto）／MessagePack 都跨语言；Java 原生序列化基本只有 Java 能消费，这也是它不适合做服务间格式的原因之一。

2. **“发生在网络哪一层”为什么容易答错？**（面经实际出现；[[面经/收钱吧/一面/0001#Q08：序列化的作用、二进制与 JSON 序列化的差异、发生在网络的哪一层|MJ068 · 收钱吧 · 一面 · Q08]]）

   因为题目把“传输”和“编码”放在一起问。准确口径：序列化是应用进程内的编码（应用层之下的表示问题），产出字节后才进入 4 层栈；TCP 分段、IP 路由都不理解对象结构。答“传输层”就是把 HTTP body 和 TCP segment 混了（分层映射见 NET-013 口径）。
