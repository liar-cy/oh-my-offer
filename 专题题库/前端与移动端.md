## 一、前端组件模型

### FE-001：React 函数组件和类组件有什么区别？

**常见问法**

- 函数式组件和类组件的区别是什么？
- 为什么现在都用函数组件＋Hooks？

#### 面试回答

写法上：类组件继承 `React.Component`，有 `this`、`constructor` 和 `render()`，状态放在 `this.state` 并用 `setState` 合并更新，生命周期是 `componentDidMount`／`componentDidUpdate`／`componentWillUnmount` 这些按“阶段”命名钩子；函数式组件就是接收 props 返回 JSX 的函数，Hooks（React 16.8 起）让它有了 `useState` 管状态、`useEffect` 管副作用，`useEffect` 把“挂载/更新/卸载”三段改成“订阅＋返回清理函数”的按数据组织形式。
本质差别有三条：① **闭包语义**——函数组件每次渲染是一个新的执行作用域，state 和事件处理函数捕获的是那一次渲染的值，所以异步回调里读到旧值、`useEffect` 依赖数组漏写导致读到陈旧状态，是函数组件特有的坑；类组件的 `this.state` 始终指向最新值。② **复用方式**——类组件靠继承和高阶组件复用逻辑，函数组件靠自定义 Hook 复用状态逻辑，能拆得更细也不占用继承位。③ **样板与心智**——函数组件没有 `this` 指向问题、不需要 bind，props 默认浅比较容易配合 `memo` 优化；类组件仍有不可替代的一项：**Error Boundary 目前只能用类组件实现**（React 官方文档明确没有等价的函数写法，实践上常用 `react-error-boundary` 包一层）。
结论：新代码统一函数组件＋Hooks，类组件主要出现在旧工程维护中；React 18 并发渲染（`useTransition`、`useDeferredValue`、自动批处理）也是围绕 Hooks 提供的。

#### 技术细节

对照表（以 React 18／19 为准）：

| 维度 | 类组件 | 函数组件＋Hooks |
| --- | --- | --- |
| 状态 | `this.state`＋`setState`（可传回调） | `useState`／`useReducer`（ updater 函数） |
| 生命周期 | 按阶段的多个钩子 | 一个 `useEffect`＋清理函数，按数据依赖触发 |
| 派生值 | `render` 里算或 `getDerivedStateFromProps` | 直接计算，或 `useMemo` 缓存 |
| 引用/实例值 | 实例字段 | `useRef`（不触发渲染） |
| 性能优化 | `shouldComponentUpdate`／`PureComponent` | `React.memo`＋`useCallback`／`useMemo` |
| 逻辑复用 | HOC、继承 | 自定义 Hook |
| 错误边界 | `componentDidCatch`／`getDerivedStateFromError` | 无等价钩子，需类组件或第三方封装 |
| 编译优化 | 手工 memo | React Compiler（Beta 起）可自动记忆化 |

三个高频陷阱：① `useEffect` 空依赖数组 `[]` 只跑一次，但它内部的 state 会被永久冻结在首帧——要么补依赖，要么用函数式 `setState(prev => ...)`；② `useEffect` 严格模式（React 18 起开发环境会挂载两次）下暴露出的“没有清理函数”问题（重复订阅、重复请求）不是 bug 触发，而是本来就该写 cleanup；③ 依赖数组放对象/数组字面量会导致每次渲染都判定变化而反复执行，要用 `useMemo` 稳定引用，或者依赖拆成原始值。
另外要说清一点：`useState` 的 setter 是幂等的稳定引用，多次调用会批处理（React 18 起所有位置的 setState 自动批处理），这与旧版只在事件处理器里批处理不同——讲“为什么连续两次 setState 只渲染一次”时按版本说。

#### 深挖追问

1. **函数组件每次渲染都会重新执行，性能不会差吗？**（补充练习）

   重新执行的是函数体，不是重新创建 DOM——React 拿新返回的 JSX 做协调（reconciliation），只有差异节点才更新。真正的开销在“无关子树被连带重渲染”，解法是状态尽量下沉、`React.memo` 配合稳定 props、以及把 children 作为 props 传入以天然跳过（组件提升）。

2. **Hooks 为什么不能写在条件或循环里？**（面经延伸，属补充练习）

   Hooks 靠调用顺序在 fiber 上对应槽位保存状态，条件分支会打乱顺序，因此必须在顶层无条件调用；ESLint 的 `react-hooks/rules-of-hooks` 就是静态检查这条约束。

3. **自定义 Hook 和普通的工具函数有什么区别？**（补充练习）

   区别在于是否调用其他 Hook：自定义 Hook 内部用了 `useState`/`useEffect` 等，因此带着“每个调用点独立的状态实例”这一语义（同一组件里调用两次就是两份独立状态）；纯工具函数只是逻辑复用，没有状态身份。

## 二、移动端平台基础

### FE-002：安卓和 iOS 的基础概念有哪些？

**常见问法**

- 简历项目涵盖安卓、iOS，讲讲对这方面基础的了解。

#### 面试回答

按“组件模型—生命周期—线程—内存—布局”五个维度各挑要点讲，比堆名词更能体现理解。
安卓：应用由四大组件构成——Activity（界面与栈管理）、Service（后台任务，前台服务需通知并受后台限制约束）、BroadcastReceiver（系统/应用广播）、ContentProvider（跨应用数据共享），都要在 AndroidManifest 声明；主线程（UI 线程）禁止耗时操作，跨线程更新 UI 的经典链路是 Handler 投递 Message 到 MessageQueue，由 Looper 在主线程循环取出分发（每个线程最多一个 Looper）；开发以 Kotlin 为主，Jetpack 提供 ViewModel／LiveData／Room／Navigation，Gradle 构建；内存问题常见于 Activity 泄漏（静态引用、未取消的监听与 Handler 延时消息）。
iOS：以 UIViewController 为界面单元，生命周期是 viewDidLoad → viewWillAppear → viewDidAppear → viewWillDisappear → viewDidDisappear，视图用 UIKit 命令式布局或 SwiftUI 声明式描述；线程模型靠 GCD（serial/concurrent queue、`async` 派发）与 NSOperationQueue（可取消、有依赖），UI 必须在主线程；RunLoop 决定线程何时休眠唤醒，也用于卡顿监控与自动释放池；内存用 ARC 引用计数管理，循环引用靠 weak/unowned 打破，autoreleasepool 控制临时对象；Swift 的 async/await 与结构化并发已是主流写法。
最后可补一句跨端认知：React Native 是 JS 描述界面、通过桥/新架构映射到原生控件；Flutter 自带 Skia/Impeller 引擎全自绘；uni-app／小程序是 WebView 或自定义渲染＋原生层混合。

#### 技术细节

几个真正会被追问的点及口径：

| 主题 | 安卓 | iOS |
| --- | --- | --- |
| 语言 | Kotlin（Java 兼容）、NDK 用 C/C++ | Swift、Objective-C 混编 |
| 主线程机制 | Looper／MessageQueue／Handler | RunLoop／GCD 主队列 |
| 内存回收 | GC（分代并发，对象引用判定） | ARC 编译期插入引用计数＋autoreleasepool |
| 循环引用 | 同样存在（静态持有 Context） | retain cycle，用 weak／`[weak self]` |
| 屏幕适配 | dp/sp＋约束布局，按密度分桶资源 | pt＋Auto Layout／SwiftUI，@2x/@3x 资源 |
| 后台能力 | 严格限制（Doze、后台启动限制、前台服务） | 后台模式＋APNs 推送，普遍禁止常驻后台 |
| 发布 | Google Play／国内商店分发，包名＋签名 | App Store，Bundle ID＋证书描述文件 |

关键差异要说准：**安卓的内存回收是追踪式 GC，能自动处理循环引用；iOS 的 ARC 是引用计数，循环引用必须开发者打破**——这是两端最容易混的点。另外 Handler 泄漏的本质是延时消息持有 Activity 引用导致其无法被 GC，因此要用静态 Handler＋WeakReference 或在 onDestroy 移除消息；iOS 的 Table/CollectionView 靠 cell 复用池避免频繁创建视图，与安卓 RecyclerView 的回收机制同构，可作为“两端共通”的例子来讲。
网络与全栈衔接：移动端一般 HTTP/2 或 QUIC，长连接与流式回包用 SSE／WebSocket，弱网重试要做幂等与请求去重；证书固定（pinning）是移动端的常见安全加固，这些可与 [[专题题库/计算机网络#NET-002：HTTP 和 HTTPS 有什么区别，证书如何验证？|NET-002：HTTP 和 HTTPS 有什么区别，证书如何验证？]] 串讲。

#### 深挖追问

1. **为什么安卓不能在主线程做网络请求？**（补充练习）

   主线程就是 UI 线程，被阻塞就无法响应触摸和刷新，用户感知为 ANR（应用无响应，系统会弹框并记录 trace）；自 Android 3.0（API 11）起，主线程发起网络会抛 `NetworkOnMainThreadException`（StrictMode 策略）。正确做法是把 IO 放到协程调度器或线程池，结果切回主线程更新 UI。

2. **Kotlin 协程和线程池比有什么优势？**（补充练习）

   挂起而非阻塞：一个 `suspend` 函数在等待网络时不占用底层线程，少量线程能承载海量等待任务；结构化并发（`coroutineScope`）保证父子任务生命周期绑定，取消可传播。它不改变“CPU 密集仍需多核并行”的事实。

3. **iOS 的 weak 引用为什么不会悬垂？**（补充练习）

   `weak` 变量登记在运行时的弱引用表中，对象释放时会被自动置 nil，读它是安全的（区别于 `unowned`——不置 nil，访问已释放对象会崩溃，语义相当于 Swift 侧的“保证不悬垂但需自己正确”）。

4. **RN 的“桥”为什么被认为是性能瓶颈？**（补充练习）

   旧架构里 JS 与原生通过异步序列化 JSON 消息通信，批量 UI 更新与手势滚动这种高频小消息会造成丢帧与启动延迟；新架构用 JSI 让 JS 直接持有原生对象引用、配合 Fabric 渲染器和 TurboModules 按需加载，去掉序列化的中间层。Flutter 则不存在这个问题——它自绘、只把平台调用作为出口。
