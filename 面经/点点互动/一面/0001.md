## Q02：游戏定时器为什么选最小堆而不是有序数组，两者区别是什么？

笔试场景：游戏服要实现「每 30 秒刷一波小怪、每 5 分钟刷 BOSS，且支持取消 BOSS 刷新」的定时器，候选人选了最小堆而非有序数组。

### 面试回答

结论：定时器堆里高频发生的是「插入新任务」和「取最近的到期时间」，最小堆这两件事都是 O(log n)／O(1)，有序数组每次插入要 O(n) 搬移，所以选最小堆。

- 相同点：两者都能拿到「最早到期」的任务——最小堆看堆顶，有序数组看队头。
- 区别在维护成本：数组要保持全局有序，插入定位二分 O(log n)、搬移 O(n)；堆只维护局部偏序，插入和删除堆顶都是 O(log n)。
- 定时器的工作流刚好用不满数组的全局有序：一秒内可能刷几十个小怪任务（频繁插入），到期只处理堆顶一个。
- 补一句边界：如果任务集很小、几乎不变（比如就两条固定刷怪规则），有序数组甚至硬编码更简单；堆的优势在任务数量大、增删频繁时才体现。

## Q03：基于给定的定时器结构体，如何实现取消定时器？

结构体字段：ID、任务类型、时间间隔、触发时间、回调函数、是否已取消标志、是否循环标志。

### 面试回答

结论：正因为结构体里带了「是否已取消」标志，用最自然的惰性删除——置标志，到期时跳过。

- 取消：按 ID 从映射表找到任务，把取消标志置为 true，不从堆里删。
- 到期检查：堆顶弹出时先看标志，已取消就直接丢弃、继续看下一个堆顶。
- 优点：取消 O(1)，不用碰堆结构；缺点：已取消的任务会暂留堆里，占一点内存。
- 另一条路：维护「ID → 堆下标」的位置映射，取消时按下标删除再调整堆，也是 O(log n)；适合取消非常频繁、内存敏感的场景。
- 选型理由现场讲：游戏里取消定时器的频率远低于创建，惰性删除实现最简单、还天然避免并发修改堆的问题。

## Q04：任务类型、是否循环、时间间隔三个字段是否重复？如何裁剪，只留一个留哪个？

### 面试回答

结论：三个字段有冗余——是否循环和时间间隔都在表达「执行一次还是反复」；只留一个的话留时间间隔，用取值编码语义。

- 冗余在哪：间隔为 0 或不设间隔，语义上就是一次性任务；有正间隔，语义上就是循环任务，「是否循环」成了它的重复描述。任务类型若只区分「一次性／循环」，和这两者也重叠。
- 怎么裁剪：保留触发时间和间隔这两个正交字段，类型和循环标志都能推导；类型信息本来就在回调函数里，不需要单独字段。
- 只留一个为什么选间隔：它是唯一的纯数据字段，能承载区分——间隔置 0 表示触发一次后删除；大于 0 表示每次回调后按「上次触发时间＋间隔」重排。
- 现场补一句取舍：真实工程里更常留「是否循环」标志、语义显式可读；这题考的是字段正交性，答案自洽、能讲清推导关系就行。

## Q05：触发时间和时间间隔能否组合使用？一次性任务间隔设什么，循环任务如何继续循环？

### 面试回答

结论：能组合，而且是标准用法——触发时间管「下一次什么时候执行」，间隔管「执行完之后隔多久再来一次」。

- 一次性任务：间隔设 0，表示触发后不重排、直接出队。
- 循环任务：每次回调执行完，用「上次触发时间＋间隔」算出新的触发时间，重新插入堆。
- 一个坑值得主动讲：用「上次触发时间＋间隔」能保持节奏不漂移；用「当前时间＋间隔」会把执行耗时累积进间隔，长期会越跑越晚。
- 取消标志在重排前检查：已取消就不再入堆。

## Q06：最小堆插入一个元素和删除堆顶元素的过程是什么？

### 面试回答

结论：两个操作都靠「先放末尾／先换堆顶，再沿路径下沉上浮」维持完全二叉树＋父不大于子的性质，复杂度都是 O(log n)。

- 插入：新元素放到数组末尾（保持完全二叉树），和父节点比较，比父小就交换上移（sift-up），直到不比父小或到根。
- 删除堆顶：把末尾元素移到堆顶、删掉末尾，然后和两个孩子中较小的比较，比孩子大就交换下沉（sift-down），直到不比孩子大或到叶。
- 数组下标关系：节点 i 的父是 (i-1)/2，孩子是 2i+1 和 2i+2，所以不需要指针。
- 补充：堆只保证「父不大于子」的全局偏序，不保证兄弟间有序，所以它不能替代有序数组做范围遍历。

## Q08：WebSocket 和 Socket 分别属于哪一层的协议，两者是什么关系、有什么区别？

### 面试回答

结论：Socket 不是应用层协议，它是操作系统暴露的传输层编程接口；WebSocket 是应用层协议，跑在 TCP 上，通过 Socket API 使用——「包含」关系不成立，是「基于」关系。

- 分层位置：TCP/IP 四层里，Socket 接口服务于传输层（TCP／UDP），WebSocket 和 HTTP 一样在最上面的应用层。
- 本质区别：Socket 是抽象（一套 API：socket／connect／send／recv），WebSocket 是协议（定义了握手、帧格式、掩码、关闭流程）。
- 关系：客户端建立 WebSocket 连接，底层仍是先经 Socket API 建一条 TCP 连接，再在这条连接上完成 HTTP Upgrade 握手。
- 补一句：拿 Socket 也能自己实现一个 WebSocket 服务端，只是要自己写帧解析——正好说明两者不在一层。

## Q09：为什么 HTTP 只能请求-响应，WebSocket 能主动推送数据？

### 面试回答

结论：这是协议语义的差异，不是 TCP 的限制——HTTP 的事务模型是「客户端发起、服务端应答、事务即结束」，WebSocket 握手后双方持有同一条连接，协议本身定义了双向消息帧。

- HTTP 的响应必须挂在请求上：服务端没有「无请求可回的主动消息」这一层语义，所谓推送都靠变通（轮询、长轮询）伪装。
- 底层 TCP 本来就是全双工的，HTTP 只是在上层把它约束成了一问一答。
- WebSocket 升级握手完成后不再走 HTTP 语义，双方都可以随时发帧（文本／二进制／ping／pong），一个请求-响应的绑定关系不存在了。
- 补一句边界：WebSocket 能推送也不代表消息可靠，丢消息、重连补偿仍要应用层做。

## Q10：在网页输入域名到页面显示，整个 HTTP 请求过程是怎样的？

### 面试回答

结论：先解析 URL 查缓存，真要联网就「DNS 拿 IP → 建连接 → 发请求 → 收响应 → 浏览器渲染」。

- DNS 解析：浏览器／系统缓存没命中才递归查询，拿到域名对应的 IP。
- 建连接：TCP 三次握手，HTTPS 再叠加 TLS 握手协商对称密钥；连接可能直接复用已有的。
- 发请求：浏览器构造 HTTP 请求报文，服务端路由到应用处理。
- 收响应：状态码＋响应体（HTML），命中协商缓存则回 304 用本地副本。
- 渲染：解析 HTML 建 DOM、解析 CSS，执行脚本，布局绘制合成；子资源再各自走上面的链路。
- 这题按「请求过程」答，渲染可以压缩成一句带过。

## Q11：HTTP 连接什么时候断开？什么是短连接？Keep-Alive 字段的作用是什么？

### 面试回答

结论：连接由任何一方主动关闭或空闲超时断开；短连接是「一次请求-响应就关一条 TCP」，Keep-Alive 就是让这条 TCP 复用多次请求的机制。

- 什么时候断：服务端发 `Connection: close`、空闲超过 keep-alive 超时、进程退出或网络中断。
- 短连接：HTTP/1.0 默认每个请求新建并关闭一条 TCP 连接，握手和挥手开销大。
- Keep-Alive：HTTP/1.1 默认持久连接，一条 TCP 上连续处理多个请求；`Keep-Alive: timeout=5, max=1000` 这类字段只是给双方的超时和次数提示。
- 一个常见误区：Keep-Alive 是 HTTP 层的字段，和 TCP 层的 SO_KEEPALIVE 探活是两回事。

## Q12：TCP 的三次握手

### 面试回答

结论：三次握手让双方各自确认对方的发送和接收能力，并完成初始序号同步。

- 客户端发 SYN，seq=x。
- 服务端回 SYN+ACK，seq=y、ack=x+1。
- 客户端回 ACK，ack=y+1，双方进入 ESTABLISHED。
- 为什么不能两次：服务端无法确认客户端收到了自己的初始序号，一个延迟到达的旧 SYN 还可能凭空建立废连接。
- 补一句：SYN 各占一个序号；第三次 ACK 可以携带数据，TFO 这类机制才允许更早带。

## Q13：TCP 序列号怎么生成？发 10 字节后 ACK 是多少，乱序到达如何靠序列号拼接？

### 面试回答

结论：初始序号 ISN 由计时器加随机化算出、防止旧连接的包混进来；后续按字节递增。ACK 计算要先分清 SYN 占不占序号。

- ISN 生成：RFC 6528 的做法是「每 4 微秒递增的计数器＋按四元组混入的随机偏移」，不是固定值也不是随便取——防的是历史报文和序号猜测攻击。
- 先说前提：题干「初始序列号 x」通常指握手完成后的数据序号（SYN 已消耗 x）。这 10 字节占 x～x+9，服务端回 ack=x+10。
- 若把 x 算成 SYN 本身（首包 seq=x 且带 10 字节数据），则数据实际从 x+1 开始，ack=x+11。
- 现场把两种口径都讲出来，比背一个数更稳。
- 乱序拼接：每个字节有全局序号，段按 seq 排序；后到的「前面的包」补上缺口后，按连续边界把已按序部分向上交付，缺口用 SACK 报告、重复 ACK 触发重传。
- 重复的段靠序号落在已确认区间内识别，直接丢弃。

## Q14：TCP 滑动窗口的作用和原理是什么？

### 面试回答

结论：滑动窗口让 TCP 从「停等」变成流水线传输——不等逐个 ACK，允许一段未确认数据在途，兼顾吞吐和流量控制。

- 窗口是什么：发送方可用的一段序号区间，下界是已确认边界（累计 ACK），上界受对端通告的接收窗口 rwnd 和本方拥塞窗口 cwnd 共同限制。
- 怎么「滑」：收到新 ACK，下界前移；窗口右边界随之扩大，可以继续发。
- 接收侧作用：rwnd 反映缓冲区剩余空间，发得比对方能收的快就会被窗口压住——这是流量控制。
- 零窗口与探测：窗口缩到 0 时发送方停发，靠定时窗口探测包避免死锁。
- 一句区分：滑动窗口管「批量在途」，拥塞控制管「网络扛不扛得住」，两者共同决定发送速率。

## Q15：Redis 和 MySQL 的区别是什么？

### 面试回答

结论：MySQL 是磁盘上的关系型数据库，管持久和一致；Redis 是内存 KV 存储，管快和简单结构，典型用法是「MySQL 为主存、Redis 做缓存层」。

- 存储介质：MySQL 数据在磁盘（Buffer Pool 做缓存），Redis 以内存为主、落盘只用于恢复。
- 模型：MySQL 支持关系模型、SQL、事务（ACID）；Redis 是键值／结构化的命令式访问，事务只是命令打包、没有回滚。
- 性能：MySQL 万级 QPS 量级要靠索引优化；Redis 单实例十万级，微秒到毫秒延迟。
- 可靠性：Redis 的 RDB／AOF 恢复能力弱于 MySQL 的行级事务与 binlog 回滚，所以不当主存。
- 组合用法：热点读走 Redis 挡流量，回源和最终一致靠 MySQL；两者一致性问题另有一整套方案。

## Q16：Redis 的 Set 和 ZSet 有什么区别？跳表插入一个元素的过程是什么？

### 面试回答

结论：Set 只管「在不在集合里」，无序；ZSet 给每个成员挂一个分数，按分数有序，支持排名和范围查询。

- Set：底层 intset／listpack／哈希表，成员唯一，O(1) 判存在；适合去重、交并差。
- ZSet：底层 listpack 或「跳表＋哈希表」，跳表管按分数排序和区间，哈希表管成员到分数的 O(1) 定位；适合排行榜、延时队列。
- 跳表插入：先随机抛硬币定新节点的层数 k，再从高到低逐层找插入位置——每层从头指针向后比，比当前层目标大就下沉一层。
- 找到位置后把新节点的各层前驱记进 update 数组，逐层改指针完成插入，更新跨度（span）用于算排名。
- 平均 O(log n)，实现比平衡树简单，范围查询天然顺着链表走。

## Q17：Redis 的网络层和业务层是否共用同一个线程？IO 多路复用的原理是什么？

### 面试回答

结论：命令执行始终在主线程；6.0 起网络读写可以开多个 I/O 线程，但解析后的命令仍然串行进主线程执行。

- 为什么这样设计：命令单线程执行免掉了锁和竞态，也保证了单命令原子性。
- 消息流程：客户端请求就绪 → epoll_wait 返回可读事件 → （多线程时）I/O 线程并发读并解析协议 → 主线程按序执行命令 → 写回响应。
- IO 多路复用原理：用 epoll 一个线程监听几万个连接，靠红黑树管理注册、就绪链表取回就绪事件，避免 select 逐个轮询和全量拷贝 fd 集合。
- 对比一句话：没有多路复用就得「一个连接一个线程」或轮流探测，前者线程爆炸，后者空转。
- 补一句别说过头：Redis 并非只有一个线程——bgsave 是子进程，lazyfree、AOF fsync 等都有额外线程。

## Q18：多线程同步有哪些方式？进程和线程的区别、分别由谁调度？

### 面试回答

结论：同步方式按「互斥」和「协作通知」两类记；进程和线程的区别落在资源归属和执行粒度上，调度都由操作系统做，但逻辑控制流归开发者代码。

- 多线程同步：互斥锁／递归锁、条件变量（配合锁做等待-唤醒）、信号量（计数控制并发度）、读写锁（读多写少）、自旋锁（短临界区省切换）、原子操作（无锁计数）。
- 进程和线程：进程是资源分配单位（独立地址空间），线程是 CPU 调度单位，同进程线程共享堆、各带栈。
- 谁调度：Linux 上调度的基本单位是内核线程，由操作系统调度器决定哪个线程何时在哪个核上跑；协程才是用户态自己调度。
- 线程执行逻辑由谁控制：调度和时序由 OS；逻辑上「谁先谁后、怎么协作」由开发者用同步原语和队列编排——OS 不保证线程间顺序。
- 隔离与切换代价：进程切换要换页表刷 TLB，线程切换不换地址空间，所以更轻。

## Q19：进程间同步有哪些方式？

### 面试回答

结论：进程间同步靠内核提供（或自己用通信原语搭）的具名对象，经典四样：信号量、共享内存＋锁、管道、信号。

- System V 信号量：跨进程计数与互斥，P／V 操作；也能做执行顺序协调。
- 共享内存＋互斥锁／信号量：共享内存本身只解决「看得见」，先后次序必须另配同步。
- 管道／Socket：传数据顺便形成「写入-读出」的时序同步。
- 信号：异步通知，只能传简单事件，携带信息极少。
- 一句串起两题：线程同步的原语（锁、条件变量）大多不跨进程，跨进程要换成有内核标识的对象。

## Q20：MySQL 索引的底层实现是什么？B+ 树如何找到叶子节点，和 B 树有什么区别？

### 面试回答

结论：InnoDB 索引用 B+ 树，非叶节点只存「键值＋子页指针」做导航，数据全在叶子层；从根往下，每个非叶节点内二分找到「键 ≤ 搜索值」的最大项，沿其指针下到子页，直到叶子。

- 为什么找得到：同一节点内键有序，每个子树有明确的键区间，比较结果唯一确定走哪条指针。
- 扇出为什么大：一页 16KB 扣除键和指针后能放上千个导航项，两三棵高就能存千万级行——树矮就是磁盘 IO 次数少。
- 对 B 树的区别：B 树非叶节点也存数据，单页放的导航项少、扇出小、树更高；B+ 树叶子层用双向链表串起来，范围查询找到起点顺着链表扫即可。
- 补充：B 树的键查中可能提前命中内部节点，B+ 树任何查询都走到叶子——用这点反驳「B+ 树处处优于 B 树」。
- 对比哈希：哈希只擅长等值，无法有序遍历。
