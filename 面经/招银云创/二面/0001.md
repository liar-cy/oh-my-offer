## Q02：讲下项目与工作内容，都是你自己做的吗，用的什么框架、为什么？

### 面试回答

- 项目是【做什么、为谁】，我负责【模块 A、B】。

## Q03：项目的底层模型用的什么，模型路由怎么做的？

### 面试回答

按【真实实现】讲，没做过的别编：

- 底层模型：接的是【真实模型，如 DeepSeek／通义千问／GPT 类，或自建／蒸馏模型】，说清通过什么方式调用（API／私有化部署）。
- 模型路由：把不同请求按规则分发到不同模型——常见维度有任务类型（抽取／生成／代码）、成本预算、上下文长度、时延要求、可用性降级。
- 典型做法：
  - 按意图或规则命中一个主模型。
  - 主模型失败或超时降级到备用。
  - 简单任务路由到便宜的小模型、复杂任务到大模型，控制整体成本。

如果项目其实没做路由、只固定用一个模型，就如实说“当前是单一模型＋失败重试，路由是我认为下一步该加的”，比虚构一个路由方案稳。

## Q04：了解设计模式吗，消除大量 if-else 分支用什么？

### 面试回答

“消除大量 if-else”是行为模式的典型场景，给方案不只给名字：

- 策略模式：把每个分支抽成一个策略实现，放进一个 Map（key=类型／枚举），运行时按 key 取策略执行——新增分支只加实现，不改调用方（开闭原则）。
- 责任链：分支是“按顺序判断谁处理”时用，一串处理器各自决定是否拦截。
- 配合工厂或配置表做策略的注册与选择；条件本身很复杂时可上规则引擎。
- 讲清代价：Map 注册要用 Spring 注入所有实现即可；别为三两个简单分支硬套模式。

结合项目说“我把【哪段 if-else】改成了【策略＋工厂】，解决了【扩展时要改一堆代码】的问题”最有说服力。

## Q05：怎么理解注解？

### 面试回答

- 本质：注解是给代码打的“结构化元数据标签”，本身不改变程序行为，要靠读取方来解释和执行。
- 读取时机：`SOURCE`（仅源码，如 `@Override`）、`CLASS`（编译期，默认，如注解处理器 APT）、`RUNTIME`（运行期可反射读取，如 Spring 的大量注解）。
- 谁来处理：编译期注解处理器生成代码（如 Lombok），运行期反射／字节码代理读取并织入行为（如 `@Autowired`、`@Transactional`）。
- 元注解：`@Target`（能标在哪）、`@Retention`（保留到哪）、`@Documented`、`@Inherited`。
- Spring 里注解多靠“扫描＋反射＋代理／BeanPostProcessor”落地，如 `@Autowired` 由依赖注入处理、`@Transactional` 由 AOP 代理生效。

一句收口：注解＝标记，价值在“被谁、在什么阶段读取并做什么”。

## Q06：线上系统频繁出现数据库连接失败，排查思路和可能原因？

### 面试回答

先定位“连不上”还是“连上但拿不到连接”，再分层排：

- 看报错：`Communications link failure`、`Connection refused`、`Too many connections`、连接超时——不同错指向不同层。
- 连接池侧：池是否被打满（活跃连接＝最大连接、获取等待超时），常见于慢 SQL 占着连接不放、或并发突增；调 `maxActive`、看是否连接泄漏（借了没还）。
- 数据库侧：`max_connections` 是否到顶、DB 是否重启／主从切换、`wait_timeout` 把空闲连接服务端断开而客户端还在用（需连接池保活／`testOnBorrow`／validationQuery）。
- 网络侧：防火墙／安全组、DNS、连接数被 LB 限、跨网抖动。
- 认证与容量：密码／账号过期、实例磁盘／连接数／CPU 打满导致拒绝新连接。

排查动作：先看应用日志异常类型→查连接池指标→`SHOW PROCESSLIST` 看 DB 端连接与慢查询→查监控（CPU／内存／连接数曲线）定位时间点。落点是“从池、库、网络三层缩小范围”，并给出对应的兜底（连接池重试与熔断、慢 SQL 治理）。

## Q07：数据库内存占用高，可能的原因是什么？

### 面试回答

先分清是“数据库进程本身吃内存”还是“应用侧内存高”，这里按数据库（MySQL）答：

- 缓冲池（InnoDB Buffer Pool）配置过大：`innodb_buffer_pool_size` 本就是内存大户，正常，但要给系统和连接留余量。
- 连接数多＋每连接会话缓冲区：大量连接 ×（`sort_buffer_size`、`join_buffer_size`、`read_buffer_size` 等）叠加，连接暴涨会顶高内存。
- 大查询／慢 SQL：一次排序、分组、临时表、`SELECT *` 捞大结果集，或没有 LIMIT 的大范围扫描，会短时占大量内存。
- 内存型临时表转磁盘、或临时表过多。
- 配置与版本、内存碎片，或确实存在内存泄漏／被 OOM。

排查：看内存曲线是否随慢查询或连接数上升；`SHOW PROCESSLIST` 找重查询，核对会话级 buffer 参数×最大连接是否超出物理内存。处置：给缓冲池设合理比例（常见物理内存 50～70%）、限制单查询资源、加索引减少排序、控制连接数。

## Q08：谈谈你的优点和缺点。

### 面试回答

- 优点：挑 1 个与岗位相关、能用具体事例背书的（如“遇到问题会钻到底”配一个真实排查／自学的例子），别只贴形容词。
