## Q01：拷打实习（约 20 分钟）。

实习单位、岗位与内容均未记录，以下为可填写框架。20 分钟说明实习经历是本轮主线，后面 LRU 与其并发化追问很可能从你介绍的内容里取。

### 面试回答

二十分钟不是复述简历，按四段组织：

- 业务背景与我的边界（3 分钟）。
- 系统链路与关键设计（6 分钟）：讲清这条链路从输入到输出怎么走、我负责哪一段、上下游是谁。
- 一个技术决策深挖（8 分钟）。
- 结果与复盘（3 分钟）。

难点只选一个能撑三层追问的，候选是：并发与一致性、性能与容量、效果与评测、线上故障排查。选中后按这条线讲完：为什么难 → 试过哪条路、为什么放弃 → 最终方案与关键实现 → 怎么验证 → 留下什么代价。结尾主动留一个可追问的细节。

这个部门以 C++ 为主、看重系统性思维，所以重点不在“用了哪个框架”，而在“约束是什么、你为什么这样权衡、失效会怎样”。每给一个方案，就顺手说它的适用条件与代价。

数字只用真实测过的，没测过的说“未做量化”。

## Q03：手撕 LRU。

原题未约定语言与接口（本库素材按 Java 给参考实现，实际现场语言未记录）。要求通常是 `get(key)` 与 `put(key, value)` 均为 O(1)、超容量淘汰最久未使用。

### 面试回答

数据结构用“哈希表＋双向链表”：哈希表负责定位节点，双向链表负责维护最近使用的顺序。两个操作都要做到 O(1)。

各操作的口径：

- `get`：命中后把节点移到头部。
- `put`：新键插到头部；更新已有键也要刷新顺序。
- 超过容量：删除链表尾部节点，同步删掉哈希表里的条目。

两个实现细节：

- 用头尾哨兵节点，省掉空链和单节点的分支判断。
- 核心不变量是“哈希表里每个节点在链表中恰好出现一次”。

口述时先说清三条约定，再写代码：

- 未命中返回什么。
- 容量为 0 或负数怎么办。
- 更新已有 key 不能占新容量。

写完用容量 2 走一遍 `put(1,1)、put(2,2)、get(1)、put(3,3)`，确认淘汰的是 key=2。

容易漏的一处：移动节点时忘了摘链。

## Q04：把 LRU 改造成线程安全该怎么做；读多写少的并发场景下怎么优化线程安全方案？

原题 4—5 是同一话题的递进追问（先问线程安全改造，再问读多写少场景优化），合并为一题。

### 面试回答

先说结论：只把 `HashMap` 换成 `ConcurrentHashMap` 不够。

- 原因：LRU 的每次访问要同时改哈希表和链表，这是一组必须原子的复合操作。
- 分开保护会读到中间态，比如“map 有节点但链表没摘完”。

基线做法是用一把锁（`synchronized` 或 `ReentrantLock`），把 get／put／淘汰整体串行化。正确性最容易证明，代价是所有访问争同一把锁。

再答第二问的关键陷阱：LRU 的“读”并不只读。

- `get` 会把节点移到队首，本质是写操作，所以读写锁在这里收益有限。
- 读锁保护不了改链表的操作；硬用 `ReadWriteLock`，反而容易写出“多个线程同时在读锁下移动节点”的损坏。

真要优化，按代价从低到高给三条路：

- 放弃严格 LRU，换近似算法：读事件先记到每线程的缓冲／环形队列里，再批量回放到访问顺序结构上，把“读要改结构”变成“攒着改”。Caffeine 就是这个思路：读写分离＋批量处理读事件＋W-TinyLFU 代替严格 LRU。
- 分段（striping）：按 key 哈希把缓存切成若干独立小 LRU，各自一把锁，锁竞争按段数下降。代价是容量与淘汰变成“每段近似”，不再是全局精确。
- 读路径做无锁快照：适合读多写少但顺序要求弱的场景。节点位置只周期性重排，或者用不可变视图＋写线程独占重排。

收尾要说验证方式：

- 并发压测看吞吐与锁等待。
- 确认不出现链表断裂，靠不变量断言或双向链表自检。
- 明确一句“换成哪种近似算法，就换掉了 LRU 的精确语义”。面试官想听的正是你知道收益和代价同时出现。
