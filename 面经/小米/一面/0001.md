## Q04：WebSocket 在 Spring 框架中涉及哪些类或注解；客户端与服务端通信需要在业务侧写代码做消息确认吗？

### 面试回答

结论：Spring 有两条线——原生 WebSocket（`@EnableWebSocket`＋`WebSocketHandler`）和 STOMP 消息代理（`@MessageMapping`／`@SendTo`）；传输层可靠不等于业务可靠，消息确认要不要做取决于“丢了会怎样”。

Spring 侧的类与注解：

- 原生线：`@EnableWebSocket` 开启；实现 `WebSocketHandler`（常继承 `TextWebSocketHandler`／`BinaryWebSocketHandler`）写收发逻辑；`HandshakeInterceptor` 在握手阶段做鉴权；用 `WebSocketConfigurer#registerWebSocketHandlers` 注册路径和跨域。
- STOMP 线：`@EnableWebSocketMessageBroker` 开启；`configureMessageBroker` 配前缀；`@Controller`＋`@MessageMapping` 收消息，`@SendTo`／`SimpMessagingTemplate` 推送；浏览器端常用 SockJS 兜底。
- 会话管理：`WebSocketSession` 自己维护 userId → session 映射（单机内存 Map 或共享存储）。

消息确认怎么判断：

- 协议层：TCP 已保证字节可靠；WebSocket 自身有 ping／pong 探活和 close 帧，但没有“应用层每条消息 ACK”的语义。
- 所以要区分两种“丢”：连接活着但业务处理失败——协议不知道，必须业务侧回执；断线重连期间的消息——TCP 缓冲有限，掉线太久就真丢。
- 结论口径：即时通知类（在线状态、弹幕）可以不做确认；涉钱、涉指令的要做——服务端回 ACK、客户端超时重发、双方按消息 ID 幂等去重。
- 补一层兜底：重连后按最后已确认的序号拉取补发，比逐条确认更常用。

## Q06：项目中 ES 的叶子查询是如何实现的？

### 面试回答

结论：叶子查询就是 match／term／range 这类最小单元查询，底层是查 term 字典拿 postings 再求交并；bool 这类复合查询只负责组合子查询结果，不做检索。

- 叶子查询（leaf）：`term` 精确、`match` 先分词再逐词查、`range` 走 BKD 树；输出是命中文档集合＋打分。
- 复合查询（compound）：`bool` 的 must／should／must_not／filter 对各子查询的文档集合做交集、并集、差集；filter 不算分、可走位图缓存。
- 底层支撑：倒排索引（term→有序 doc ID 列表）、FST 词典、跳表加速归并——多条件求交就是双指针走 postings。
- 项目里怎么用的按【真实查询】说：例如【bool 里 filter 状态＋must 分词匹配标题】。

## Q07：MySQL 中有哪些存储引擎？InnoDB 和 MyISAM 的区别？

### 面试回答

结论：常见引擎有 InnoDB（8.0 起默认）、MyISAM、Memory、Archive、CSV、Blackhole 等；区别集中在事务、锁粒度、索引组织三块。

- 引擎列表：`SHOW ENGINES` 可查；生产基本只用 InnoDB，Memory 偶尔做临时表场景，Archive 做归档。
- 事务与恢复：InnoDB 支持事务、MVCC、崩溃恢复；MyISAM 都没有。
- 锁粒度：InnoDB 行级锁为主；MyISAM 只有表级锁，读锁写锁互斥。
- 存储组织：InnoDB 聚簇索引存行、二级索引叶子存主键（回表）；MyISAM 索引与数据分离、索引直接存行地址。
- 其他差异：MyISAM 有精确行数与 .MYD／.MYI 文件形态，InnoDB 全文索引与自增能力也不弱——别说“读一定谁更快”，按场景说。

## Q08：为什么 InnoDB 选择 B+ 树作为索引？

### 面试回答

结论：为“磁盘 IO＋范围查询”这对组合最优——树矮、非叶子只放键所以每页扇出大，叶子层双向链表让范围扫描顺。

- 对比哈希：等值 O(1) 但范围查询与排序无能为力，且冲突退化。
- 对比二叉树／BST：树高随数据量线性恶化，磁盘读次数＝树高。
- 对比 B 树：B 树非叶子也存数据，单页能放的键更少、树更高；区间扫描要中序回跳。
- B+ 树量化口径：16KB 页、主键 bigint，非叶子约放 1000 个“键＋页号”，三层约可支撑两千万级行——三层内两次额外 IO 就到叶子。
- 叶子双向链表：`between`／`order by`／翻页顺着链表扫，配合最左前缀。

## Q09：数据库的第三范式是什么？数据库设计为什么要遵循三范式？

### 面试回答

结论：3NF 是“非主属性不能传递依赖于主键”；遵循它是为了消除冗余、保证增删改一致性，但报表与高并发读常做反范式。

- 递进记：1NF 字段不可再分；2NF 非主字段完全依赖主键（针对联合主键的部分依赖）；3NF 非主字段之间不能有依赖（如 订单里的 商品编号→商品名）。
- 为什么遵循：一处事实一份拷贝；冗余字段会有更新异常——改一处漏一处，删除会连带丢信息。
- 什么时候不遵循：读多写少、统计聚合、跨表 join 代价高时冗余快照字段（订单存下单时价格）。
- 补一句立场：范式是起点不是教条，先按 3NF 设计，再按查询模式有意识地反范式。

## Q10：Spring 处理一个请求会经过哪些模块？

### 面试回答

结论：以 Spring MVC 为例，主干是“过滤器 → DispatcherServlet → HandlerMapping 找到处理器 → HandlerAdapter 反射调用 Controller → 返回值交给消息转换器／视图解析器渲染”，拦截器与异常处理器横切在前后。

按顺序报模块：

- Servlet Filter 链（跨域、鉴权）先进入。
- `DispatcherServlet.doDispatch`：总调度入口。
- `HandlerMapping`：按 URL 找到 Handler，返回执行链（含拦截器）。
- `HandlerAdapter`：适配调用 Controller 方法；参数经 `HandlerMethodArgumentResolver` 解析（`@RequestBody` 走 `HttpMessageConverter` 反序列化）。
- 拦截器 `preHandle`／`postHandle`／`afterCompletion` 包在调用前后。
- 返回值：`@ResponseBody` 经 `HttpMessageConverter`（如 Jackson）序列化直接写响应；否则 `ViewResolver` 解析视图渲染。
- 异常沿 `HandlerExceptionResolver`（含 `@ControllerAdvice`）兜底。

## Q11：Spring 中的类在启动之后会执行哪些方法、用到哪些注解？

### 面试回答

结论：单例 Bean 按“实例化 → 属性填充 → Aware 回调 → 初始化（@PostConstruct → afterPropertiesSet → init-method）→ AOP 代理 → 就绪”走，销毁时反向回收。

- 实例化：调构造方法（构造器注入在此完成）。
- 属性填充：`@Autowired`／`@Value` 注入发生在这一步之后于构造方法。
- Aware：`BeanNameAware`、`ApplicationContextAware` 等回调。
- 初始化：`@PostConstruct` 最先，其次 `InitializingBean#afterPropertiesSet`，最后自定义 init 方法。
- 代理：`BeanPostProcessor` 后置处理生成 AOP 代理。
- 启动后才跑的：`SmartInitializingSingleton`、`ApplicationRunner`／`CommandLineRunner`、`@EventListener(ApplicationReadyEvent)`。
- 销毁：`@PreDestroy` → `DisposableBean#destroy` → destroy-method。

## Q12：静态代码块和构造方法哪个先执行？

### 面试回答

结论：静态代码块先执行，而且整个生命周期只执行一次；构造方法每次 `new` 都执行。

- 静态块属于类初始化阶段——类首次主动使用时执行一次，此时往往还没有任何实例。
- 对象创建顺序：父静态 → 子静态（各一次）→ 实例字段与实例初始化块（按书写顺序）→ 构造方法。
- 易错点：静态块访问的静态字段若在其后声明，拿到的是默认值；`main` 所在类的静态块先于 `main` 执行。

## Q13：构造方法和 @Autowired 哪个先执行？

### 面试回答

结论：构造方法先执行——先有对象实例，才谈得上往字段里注入依赖。

- 生命周期位置：实例化（调构造）在前，属性填充（`@Autowired` 由 `AutowiredAnnotationBeanPostProcessor` 完成）在后。
- 推论：构造方法里读 `@Autowired` 字段是 null；依赖别的 Bean 的初始化逻辑放 `@PostConstruct` 或更晚。
- 例外口径：构造器注入是“先解析好参数再调构造”，看起来“同时发生”，但字段注入仍是构造之后。

## Q14：@PostConstruct 注解和实现 InitializingBean 重写 init 方法，哪个先执行？

### 面试回答

结论：`@PostConstruct` 先执行。顺序固定为 `@PostConstruct` → `afterPropertiesSet` → 自定义 init-method。

- 机制：`@PostConstruct` 由 `InitDestroyAnnotationBeanPostProcessor` 在初始化前置阶段触发；`InitializingBean#afterPropertiesSet` 是接口回调，紧随其后；`init-method` 由 BeanDefinition 指定，排最后。
- 销毁侧对应：`@PreDestroy` → `destroy()` → destroy-method。
- 选型：业务统一用 `@PostConstruct`；需要被配置／XML 覆盖时才用 init-method；`afterPropertiesSet` 侵入接口不推荐。

## Q15：HashMap 和 ConcurrentHashMap 有什么区别？

### 面试回答

结论：一个是非线程安全的通用映射，一个是线程安全版；JDK 8 后 CHM 用“CAS＋桶头 synchronized”做细粒度锁，而不是整表锁。

- 线程安全：HashMap 并发 put 会丢数据、扩容期读可能拿到坏链；CHM 支持并发读写。
- 实现：JDK 8 两者都是数组＋链表＋红黑树；CHM 每个桶单独加锁，size 用基表＋计数分片（CounterCell）累加。
- 空值：HashMap 允许一个 null 键；CHM 键值都不许 null——并发下无法区分“没有”与“值为 null”。
- 迭代器：都是弱一致遍历，CHM 不抛 `ConcurrentModificationException`。
- 用法边界：只读或单线程用 HashMap；共享可变映射用 CHM；computeIfAbsent 里别再嵌套操作同一个 map。

## Q16：什么是一致性哈希？和普通哈希有什么区别？

### 面试回答

结论：一致性哈希把节点和数据都映射到 0～2³² 的环上，数据顺时针找最近节点；节点增减只影响相邻一段，普通取模哈希则近乎全体迁移。

- 普通哈希 `hash(key) % N`：N 一变，几乎所有 key 的归属都变——分表扩容、缓存集群迁移都遭殃。
- 一致性哈希：加一台节点只在环上插入一点，只截走它逆时针到上一个节点之间的 key；典型迁移量约 1/N²。
- 数据倾斜问题：节点少时环上分布不均，用虚拟节点（每物理节点上百个虚拟点）打散。
- 落地场景：缓存分片、一致性哈希负载均衡、哈希分表扩容方案设计。

## Q18：线程的创建方式有哪些？实现 Runnable 和 Callable 创建线程有什么区别，哪种能拿到执行结果？

### 面试回答

结论：定义任务的角度有 Runnable、Callable、继承 Thread，交给线程池或直接 start；JDK 21 起还有虚拟线程。能拿到结果的是 Callable。

- 常见四种说法：继承 `Thread`、实现 `Runnable`、实现 `Callable` 配 `FutureTask`、线程池提交任务；底层造线程都靠 `Thread`（线程池也是 `ThreadFactory` 在造）。
- Runnable vs Callable：`run()` 无返回值、不能抛检查异常；`call()` 有返回值、可抛检查异常。
- 取结果：`ExecutorService.submit(callable)` 返回 `Future`，`get()` 阻塞拿结果或超时；`CompletableFuture` 可回调编排。
- Runnable 也想有结果：改用 Callable，或任务内部写回调／共享 `CompletableFuture`。

## Q19：线程池一般通过什么方式创建？有哪些核心参数？工作流程是什么？核心线程是一开始就创建还是任务来了才创建？

### 面试回答

结论：显式 `new ThreadPoolExecutor(...)` 七参数创建；流程是“核心 → 队列 → 扩到最大 → 拒绝”；核心线程默认也是任务来了才逐个创建，可 `prestartCoreThread` 预建。

- 创建方式：正解显式构造七参数；`Executors` 快捷工厂有隐患（无界队列 OOM、线程数不设上限），阿里手册禁用；Spring 的 `ThreadPoolTaskExecutor` 是带生命周期的包装。
- 七参数：corePoolSize、maximumPoolSize、keepAliveTime、unit、workQueue、threadFactory、handler。
- 流程：先建到核心数 → 满了入队 → 队列满再扩到 max → 还接不下走拒绝策略。
- 核心线程时机：默认懒建，`execute` 里有任务才 `addWorker`；`prestartCoreThread(s)` 可预创建，`allowCoreThreadTimeOut(true)` 则核心线程空闲也能回收。

## Q20：A 服务调用执行时间较长的 B 服务，B 执行完要把结果返回 A，请设计交互方案（三种）

### 面试回答

结论：三种主流方案是轮询、回调、消息队列；共同前提是“异步化＋结果落存储＋接口幂等”，区别在谁主动取结果。

- 方案一 轮询：A 提交任务立即拿 taskId，之后按间隔调 B 的查询接口直到完成。实现最简单；代价是有窗口延迟与无效查询，要退避加超时告警。
- 方案二 回调：A 提交时带上回调地址，B 完成后反向调 A。实时性好；代价是 A 要暴露接口、处理回调失败重试与乱序，鉴权要防伪造。
- 方案三 MQ：B 完成后把结果发到消息队列，A 订阅消费。彻底解耦、可重播削峰；代价是多一套中间件与最终一致窗口。
- 三者都要配：任务状态表（INIT／RUNNING／SUCCESS／FAILED）、结果幂等（按 taskId 去重）、超时兜底（对账任务重推或置失败）。
- 加分句：短任务同步等待加超时即可，不必上异步；长任务才值得这套复杂度。

## Q21：两个各自不重复、彼此有重复且装不进内存的大集合，如何从数据结构和算法角度找出重复元素？

### 面试回答

结论：三条路——分片哈希后逐块内存求交、外排序后双指针归并、位图或布隆过滤器预筛；选哪条看值域与是否允许误判。

- 哈希分片（通用首选）：两集合按同一 `hash(x) % N` 切成 N 对小文件，相同元素必落同号分片；逐对把小分片读进内存求交集，分片仍过大再递归细分。
- 外排序＋双指针：各自外部排序成有序文件后归并求交，两路顺序扫、内存只需常数级；缺点是全量排序贵。
- 位图：值域已知且不大（如 int 内）最省——A 建 bitset，扫 B 查位；4 亿个 int 才 50MB。值域稀疏巨大时退化。
- 布隆过滤器：A 建 BF 再扫 B——判“在”可能误判，判“不在”必真不在；适合只要快速缩小候选、后续再精确核验的口径，答题要说清误判率。
- 追问口径：单机磁盘不够就按数据分片分布式并行处理，思路同哈希分片。

## Q22：生产环境中一个接口请求响应时间比较慢，如何排查？

### 面试回答

结论：先定界再定层——用监控把“慢”拆到链路的某一段，再从应用逐层往下找证据，不凭感觉改代码。

- 定界：网关／APM 看该接口 RT 分位（P99 慢还是普遍慢）、时间分布（一直慢还是突发）、是否伴随错误率上升；突发慢先问“最近有没有上线或改配置”。
- 应用内：Arthas `trace` 打方法级耗时，看是自身代码慢还是卡在依赖调用；线程池满／队列积压会让“没干活先排队”。
- 依赖层：慢 SQL（`SHOW PROCESSLIST`＋EXPLAIN）、缓存命中率下跌与热 key、下游服务 RT、连接池等待。
- 系统层：CPU／IO／负载（`top`、`vmstat`、`iostat`）、GC（`jstat -gcutil`，FGC 频繁会拉高 RT 长尾）。
- 收尾习惯：定位后给“止血（限流／回滚／扩容）→ 根因 → 防复发”三段，而不是只报一个原因。

## Q23：手撕：(1) LeetCode 20 有效的括号；(2) 手写单例模式

### 面试回答

(1) 有效的括号——栈匹配，O(n) 时间 O(n) 空间：

- 遇左括号入栈；遇右括号则弹栈比对是否配对，不配或栈空即 false；结束时栈为空才 true。
- 边界：首字符是右括号、末尾剩左括号；用“弹栈前判空”统一处理，别写三个 if 特判。

```java
public boolean isValid(String s) {
    Deque<Character> stack = new ArrayDeque<>();
    for (char c : s.toCharArray()) {
        if (c == '(') stack.push(')');
        else if (c == '[') stack.push(']');
        else if (c == '{') stack.push('}');
        else if (stack.isEmpty() || stack.pop() != c) return false;
    }
    return stack.isEmpty();
}
```

(2) 单例模式——推荐背两种：

- 饿汉式：`private` 构造器＋`static final` 字段，类加载即创建，线程安全、实现最简。
- 懒汉双重检查锁：`volatile` 字段＋两次判空加锁——第一次省锁开销，第二次防重复创建，`volatile` 防“引用先于初始化发布”。
- 加分项：静态内部类（Holder）实现延迟加载且无锁；枚举写法天然防反射与反序列化破坏。
