## Q01：手撕：LeetCode 15 三数之和

### 面试回答

结论：排序＋固定一个数＋双指针，O(n²)；这题的得分点几乎全在“去重”。

- 先升序排序；外层 i 固定 `nums[i]`，在 (i, n) 区间左右指针对撞找和为 `-nums[i]` 的两数。
- 三处去重：i 与前一个值相同就跳过；找到解后 left／right 各自跳过重复值。
- 两个剪枝：`nums[i] > 0` 直接 break；对当前 i，`nums[i]+nums[i+1]+nums[i+2] > target` 可 break、`nums[i]+nums[n-2]+nums[n-1] < target` 可 continue。
- 空间 O(1)（不计输出）；结果要“不重复的三元组”，这是题意核心。

## Q04：项目中用到 Seata 的哪种分布式事务模式？底层原理是怎样的？

### 面试回答

结论：模式按【项目实际，常答 AT】选；AT 的底层是“一阶段本地提交＋undo／redo 日志＋全局锁，二阶段只做全局提交或按 undo 回滚”。

AT 原理四步（以扣库存为例）：

- 一阶段：拦截 SQL，记录数据快照 beforeImage（改前）与 afterImage（改后）成 undo log，与业务 SQL 在同一本地事务里提交——本地先释放行锁。
- TC（Seata Server）协调：RM 向 TC 登记分支，事务提交前申请该行主键的全局锁，防其他全局事务并发改同一行。
- 二阶段成功：全局提交只需异步删 undo log，几乎无阻塞。
- 二阶段失败：TC 令各分支用 undo log 反向补偿还原 beforeImage——是补偿，不是回滚未提交事务。

- 对比口径：TCC 要写 Try／Confirm／Cancel 三段业务侵入代码，性能与隔离更强但成本高；XA 是强一致、资源锁全程持有吞吐低。
- 适用前提：AT 要求数据库支持本地事务与行唯一主键，且它保证最终一致，读方可能读到中间态（要隔离需 `@GlobalLock`／SELECT FOR UPDATE 语义）。

## Q05：项目限流把什么作为限流的资源？代码中一个接口的限流是怎么实现的？

### 面试回答

结论：资源是“被保护入口”的抽象——HTTP 接口、服务方法、消息消费都可做资源，粒度按业务隔离需求定；单接口实现用 `@SentinelResource` 或 API 埋点。

限流资源怎么定：

- 默认资源名：Web 入口是 URL 路径（如 `/api/order/{id}` 归一为路由模板，防路径参数把资源打爆）。
- 方法级：`@SentinelResource("createOrder")` 显式命名，业务含义清楚。
- 更细粒度：热点参数限流把“某个参数值”（商品 ID、用户 ID）单独当资源，防单品被打穿。
- 口径：资源划分看“想按什么维度隔离与限额”，全局统一阈值就设入口资源。

代码实现骨架：

- 声明式：`@SentinelResource(value=..., blockHandler=..., fallback=...)`；blockHandler 处理 `BlockException`（被限／熔断），fallback 处理业务异常，两者职责不同要分清。
- 编程式：`try (Entry e = SphU.entry("createOrder")) { ... } catch (BlockException ex) { ... }`，必须 `exit` 释放统计。
- 配规则：`FlowRule`（QPS／线程数、快速失败／Warm Up／排队）＋`DegradeRule`；生产把规则托管 Nacos 数据源热更新。

## Q06：服务上有成百上千个接口都要限流熔断，如何基于 Sentinel 实现？

### 面试回答

结论：不逐个手写埋点——用“框架适配自动生成资源＋规则集中持久化下发＋统一兜底处理器”三件事把接入成本降到零，人工只维护规则。

- 自动生成资源：引入 `sentinel-spring-webmvc-adapter`（或 Spring Cloud Alibaba 的 Gateway／Feign 适配），一个全局过滤器就把所有 HTTP 接口注册为资源；Feign 出口调用同理自动埋点。
- 规则集中管理：数据源托管 Nacos／ZooKeeper，全量规则在一个配置里版本化维护；控制台改规则即时推送，重启不丢。
- 批量配默认规则：给“未单独配规则的接口”设全局兜底（系统保护规则按 Load／入口 QPS 整机限流），避免逐个拍阈值——上线先兜底，再按观测数据细化热点接口。
- 统一兜底：全局 `BlockExceptionHandler` 返回标准错误码与 Retry-After；熔断降级按接口重要性分级——核心接口配精细规则，长尾接口只走默认。
- 运维闭环：Dashboard 看簇点链路找真实热点，只对 Top 接口精调；阈值配置进代码仓库走评审。

## Q07：自定义一个组件集成到 SpringBoot 中，要做哪些操作？

### 面试回答

结论：做一个自定义 Starter——“autoconfigure 模块写装配逻辑＋starter 模块只聚依赖”，再经 `AutoConfiguration.imports` 注册，使用者加一个依赖加一段配置就能用。

四步操作：

- 建两个模块：`xxx-spring-boot-autoconfigure`（自动配置类＋属性类）与 `xxx-spring-boot-starter`（只引 autoconfigure 及必要依赖，不含代码）。
- 写装配：`@AutoConfiguration`（或 `@Configuration`）＋`@Bean` 工厂方法；用 `@ConditionalOnClass`／`@ConditionalOnMissingBean` 等控制“用户没配我兜底、用户配了我让路”；配置项用 `@EnableConfigurationProperties` 绑定 `xxx.*` 前缀。
- 注册：在 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` 写入配置类全限定名（Spring Boot 2.7 前是 `spring.factories` 的 `EnableAutoConfiguration` key）。
- 可选完善：元数据 `spring-configuration-metadata.json` 给 IDE 提示；写 `@ConfigurationProperties` 校验与 README。
- 原理一句话：这是自动装配“扫描 imports → 条件过滤 → 按序加载”链条的入场券（见 SPRING-001）。

## Q08：用过 Java 的哪些 JUC 工具？

### 面试回答

结论：按用途分组报，每组带一个使用场景，比罗列类名有说服力。

- 同步器：`CountDownLatch`（等 N 个依赖就绪）、`CyclicBarrier`（多阶段汇合）、`Semaphore`（限并发额度，如保护下游）。

- 工具类：`ThreadLocal`（上下文传递，注意线程池复用要清理）、`ThreadFactory`／自定义线程池。

## Q09：volatile 保证变量可见性的原理？用 synchronized 加锁能否保证可见性？

### 面试回答

结论：volatile 靠“写即刷回＋其他核副本失效”（缓存一致性协议）和编译屏障实现可见性；synchronized 同样保证可见性——解锁前刷出、加锁后重新读，且它还保证互斥。

volatile 的可见性原理：

- 写 volatile：JMM 层 happens-before 后续对同一变量的读；实现层在写后插 StoreLoad 屏障（x86 上带锁指令／`mfence` 类），同时 MESI 协议让其他 CPU 缓存行失效，下次读被迫从内存／持有者取。
- 局限：只保证单次读写可见与不重排，`i++` 这类复合操作仍不安全。

synchronized 能否保证：

- 能。规范规定：monitor 解锁 happens-before 后续对同一 monitor 的加锁；解锁前工作内存的修改必须刷新到主内存，加锁后从主内存重新读——临界区内的读写对外可见。
- 实现上锁块内代码也不允许越过加解锁重排序。
- 分工：要“改一处、多处看到”用 volatile 发布状态即可；任何涉及读改写或不变量的场景必须 synchronized／Lock，可见性附赠。

## Q10：线程 a、b 各有任务 A、B，b 要等 a 完成 A 后才能执行 B，有哪些实现方式，越多越好

### 面试回答

结论：本质是“等待前驱完成”的事件依赖，最直接是 `join`；能报出一串等价手段才是这题要的深度——按“语言原语 → 同步器 → 异步框架 → 队列”四层说。

- 原语层：`b.join()` 式等待——`aThread.join()` 后再跑 B；或 `LockSupport.park`／`unpark` 手工放行；`wait`／`notify`＋完成标志位（要 `while` 复查）。
- 同步器层：`CountDownLatch(1)`——A 完成 `countDown`，B 开头 `await`；`Semaphore(0)`——A 完成 `release`，B `acquire`；`CyclicBarrier` 单汇合点等价 latch。
- 异步框架层：`CompletableFuture.runAsync(A).thenRunAsync(B, poolB)` 声明依赖；线程池里 B 任务 `futureA.get()`。
- 队列层：把 A、B 丢进单线程线程池按提交顺序串行；或 B 作为 A 的完成回调入队。
- 反例要点：`sleep` 固定时长猜依赖、公平队列只决定“谁先拿锁”都表达不了“完成依赖”；`start()` 先后不代表执行顺序。

## Q11：一般业务中通过什么创建线程池、有哪些核心参数？如何设计可动态调整参数的线程池？如何观测线程池参数变化？

### 面试回答

结论：创建仍是显式 `new ThreadPoolExecutor` 七参数；动态调整不难——`setCorePoolSize` 等 setter 本来就支持热改，难的是“先观测再调”：暴露指标、看水位、配置中心下发、灰度验证效果。

- 创建与参数：显式构造；corePoolSize、maximumPoolSize、keepAliveTime、unit、workQueue、threadFactory、handler；流程“核心 → 队列 → 最大 → 拒绝”。
- 动态调整机制：`ThreadPoolExecutor` 公开 `setCorePoolSize`／`setMaximumPoolSize`／`setKeepAliveTime`／`setRejectedExecutionHandler`，改的是运行中的字段，下次取任务即生效；改队列容量 JDK 队列不支持——换自定义 `ResizableCapacityLinkedBlockingQueue`。
- 配置中心方案（面试中已提出）：启动读参数＋监听器收到变更回调里调 setter，能“无感切换”；但它只解决“改得动”，不解决“改成多少”——仍需人看数据决策。
- 观测设计：给每个池起业务名并注册到管理器，用 Micrometer 周期性打点。
- 打点内容：activeCount、poolSize、队列积压量、completedTaskCount、拒绝次数，再分排队时长与执行时长两类统计（可包一层 TaskDecorator 计时）。
- 决策闭环：Grafana 面板看水位 → 告警阈值（队列持续积压／接近 max／出现拒绝）→ 改配置中心 → 面板验证效果；再进一步才是自适应调参（按 Little 定律或负载反馈自动算，生产上先小流量灰度）。
- 顺序立场（面试官引导点）：先观测定位瓶颈是“线程不够、队列太长还是任务本身变慢”，再谈调参；盲目热改可能把下游压垮。

## Q12：Redis 的哈希数据结构有哪些实现方式？出现大 Key 问题如何解决？

### 面试回答

结论：hash 有两种内部编码——小 hash 用 listpack 省内存、大 hash 用 hashtable 保速度，超阈值单向转换；哈希大 Key 的治理是“拆字段／拆 key＋禁止全量命令＋渐进删除”。

实现方式：

- listpack（6.2 前为 ziplist 压缩列表）：一段连续内存顺序存 field-value，无逐元素指针，紧凑；查找 O(n)，ziplist 时代还有连锁更新隐患。
- hashtable：链地址法真哈希表，读写平均 O(1)，适合大 hash；每 entry 有指针与字典开销。
- 切换条件：元素数或单值长度超过 `hash-max-listpack-entries`／`hash-max-listpack-value`（默认 128／64，以部署配置为准）转 hashtable，且不可逆。

大 Key 治理：

- 先定义：哈希大 Key 是“单 key 下 field 数量巨大或 value 巨大”——内存集中、`HGETALL` 一次拉爆带宽、单线程命令长尾、集群下该分片流量不均。
- 拆：按业务维度把 field 分桶成多个 key（`user:{id}:profile:0..N`），或大 value 外置对象存储只存引用。
- 读：禁 `HGETALL`，改 `HMGET` 按需取、`HSCAN` 增量遍历；写：分批 pipeline。
- 删：`UNLINK` 异步回收，别 `DEL` 阻塞。
- 发现与防复发：`redis-cli --bigkeys`／`MEMORY USAGE`／RDB 分析定期巡检；建 key 规范限制单 key field 数上限。

## Q13：对 Redis Cluster 了解吗？为什么需要把主从模式升级为集群模式？

### 面试回答

结论：主从解决的是“冗余与读扩展”，容量与写仍是单点；Cluster 用 16384 个哈希槽把数据分片到多个主节点，写也能水平扩展，且每个分片自带自动故障切换。

为什么升级：

- 容量上限：单机内存装不下全量数据——复制是整库拷贝，加从库不减单节点数据量。
- 写单点：所有写压在一个主上，QPS 有天花板；主从故障切换要人工。
- 升级后：数据按 `CRC16(key) mod 16384` 分槽到各主，读写都水平扩展；每分片一主多从、主挂自动升从——把哨兵的能力内建进每个分片。

Cluster 要点与代价：

- 客户端收 `MOVED`／`ASK` 重定向并更新槽映射，要能处理。
- 跨槽多 key 操作（MGET、事务、Lua）受限，需要 hash tag `{}` 强制同槽；热 key 仍在单分片，拆不开。
- 口径：数据量小只要高可用 → 哨兵即可，别为用 Cluster 而用 Cluster。

## Q14：怎么看待产品设计与服务过程中把用户放在第一位？

### 面试回答

结论：技术岗答这题要落到“可执行的取舍标准”，不喊口号——用户第一不是无底线满足，而是决策权重里用户利益排最前，同时不牺牲长期信任。

- 设计层：少弹一次窗、快 200ms、出错时给可理解的状态——这些是研发能直接做的事。
- 数据与信任：不因短期指标滥用用户数据／诱导点击；用户第一的前提是尊重与透明。
- 工程实践：故障时先恢复用户可用（止血优先于追责）；需求冲突时以“用户可感知的影响面”做优先级依据。
- 结合经历举例：【实习中一次以体验为准的取舍：如坚持做加载兜底／推动修复某体验问题】。
- 边界句（加分）：用户第一不等于没有商业约束，而是约束存在时排序清楚、手段透明。

## Q15：如果要做观测，谁来观测？怎么观测？整个设计的流程是怎样的？

### 面试回答

结论：观测主体是“平台自动采＋人配阈值看趋势”，不是人盯数字；闭环设计是采集 → 聚合展示 → 告警 → 定位 → 变更验证五步，Q11 的线程池观测就是其中一环。

- 谁来观测：应用自身埋点（Micrometer 暴露 metrics）→ 采集器（Prometheus 拉取）→ 存储与展示（Grafana）→ 告警（Alertmanager／内部平台）；值班的人看告警与面板，容量治理的人看长期趋势。
- 怎么观测线程池：核心水位 gauge（active／poolSize／queueSize）、速率 counter（提交数／完成数／拒绝数）、延迟分布（排队时长、执行耗时直方图）；每个池打“业务名＋实例”标签。
- 流程设计：先定“要回答的问题”（池够不够、任务慢没慢）→ 选对应指标 → 设采集周期与聚合 → 定告警阈值（拒绝出现即告警、队列持续高位预警）→ 变更（调参）后面板对比验证。
- 分层视角：单机线程池指标之上还要服务级（RT／错误率）与依赖级（DB／下游）指标，三者对照才能归因——这正是 Q14 里“先观测再改”的落地。
