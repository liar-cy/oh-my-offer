## Q01：实习拷打（约 8 分钟）

## Q03：图数据库和知识图谱是什么关系？

### 面试回答

结论：图数据库是“存储与查询引擎”，知识图谱是“用图组织起来的知识内容”——前者是数据库软件，后者是数据与语义模型，一个是容器一个是货。

- 知识图谱三要素：实体（节点）、关系（边）、属性／本体（类型与约束，如 schema 层）；重点是语义建模，不是存储技术。
- 图数据库是可选落地之一：Neo4j／NebulaGraph／JanusGraph 能存图谱并提供图查询；但图谱也常存在三元组库（RDF＋SPARQL）甚至关系表里。
- 反过来不成立：图数据库里存的图不一定是“知识”图谱——社交网络、依赖图只是数据集，没有本体层的都只叫图数据。
- 一句对照：做图谱的工作量七成在抽取与治理（本体设计、实体对齐、冲突消解），三成才在选数据库。

## Q04：图数据库和关系型数据库有什么区别？

### 面试回答

结论：差别核心是“遍历靠指针还是靠 JOIN”——关系型靠表连接算出来，图数据库把关系当一等公民，邻接就是物理指针。

- 数据模型：表＋行＋外键 vs 点＋边＋属性（边带类型和方向）。
- 多跳查询：关系型每多一跳一次 JOIN，深遍历成本指数上升；图数据库邻接遍历每步近似 O(度数)，多跳稳定。
- Schema：关系型强 schema、改结构有成本；图库通常宽松（标签／边类型），改模更灵活。
- 事务与生态：关系型的 ACID、工具链、统计查询（聚合／窗口）成熟得多；图查询语言不统一（Cypher／Gremlin／GQL），全局分析要靠图计算引擎补充。
- 收口：不是替代关系——主流架构是业务数据在 MySQL，图数据库承载关系密集查询，两边同步或用多模方案。

## Q05：什么场景适合用图数据库？

### 面试回答

结论：判据一句话——查询以“关系的路径”为中心就用图，以“实体的属性过滤聚合”为中心就用关系／文档库。

- 适合：多跳关系查询（好友的好友、3 度人脉）、路径与连通性（风控关联、扩散）、层级与依赖（组织架构、血缘、IT 依赖图）、循环引用建模（关系型要中间表还要递归 JOIN）。
- 不适合：大规模报表聚合、事务型明细记账、简单 KV 读写——图库不占优，还多养一套组件。
- 隐性成本要主动说：数据要二次建模与同步、查询语言团队要学、全局算法（PageRank 类）往往还得离库跑图计算。
- 选型时给规模：点边量级、跳数深度、QPS——百万点、2～3 跳的在线查询，很多图库都能做；亿级点＋实时写就要提前设计分片（GRAPH-003）。

## Q06：推荐系统用图数据库存储，如何支持推荐算法？

### 面试回答

结论：图提供“结构化的关系信号”，算法分两层用——在线用图做召回与解释，离线用图上特征／嵌入做排序；图库本身不算相似度。

- 召回层：User-Item 二部图上跑相似推荐——共同邻点计数、随机游走（Node2Vec 类）出嵌入，或直接多跳扩列（好友买过、同类目高评分）生成候选。
- 排序层：把图结构落成特征（一度邻域统计、路径命中、节点中心性），连同行为特征喂给模型；嵌入向量预计算落特征库，在线只做近邻检索。
- 可解释与冷启动：推荐理由给“因为你也关注了 X”路径直出；新用户／新物品靠边属性（类目、品牌）挂进图缓解冷启动。
- 工程边界：图库承接的是候选生成与关系查询，重计算（嵌入训练、全图统计）走离线图计算引擎；在线延迟要缓存兜住，热边要打散（REDIS-010 同思路）。

## Q07：图数据库是否支持 BFS、DFS 和两点间最短路？

### 面试回答

结论：变长路径遍历（本质就是 BFS／DFS）与最短路／最短跳数，主流图库都原生支持；但“任意算法自己写”不行，那要走 UDF 或图计算引擎。

- BFS／DFS：`*1..3` 变长路径（Cypher）、`repeat/until` steps（Gremlin）就是广度遍历；深度限制与去环由引擎保证，不用手写 visited。
- 最短路：Neo4j 的 `shortestPath()`（跳数最少，BFS 类）与 `allShortestPaths()`；带权最短路由图算法库／GDS 提供 Dijkstra、A*；NebulaGraph 有 `FIND SHORTEST PATH`／`GO ... OVER` 类算子，各产品能力差别大，报自己用过的。
- 全局算法：PageRank、连通分量、社区发现多在图计算层（GraphX／PLC／GDS 批量模式），不属于在线事务查询——这是图库与图计算引擎的分工线。
- 复杂度自觉说：多跳查询代价≈各跳邻居数乘积，热点会爆——限跳数、限边类型、按属性剪枝是调优三板斧。

## Q08：迪杰斯特拉算法的过程

### 面试回答

结论：维护一个“源点到各点当前最短距离”数组，每轮从未确定集合里取距离最小的点确定下来，再用它松弛邻居；要求边权非负。

- 初始化：`dist[source]=0`，其余无穷大；小顶堆按距离取点。
- 松弛：对新确定点 v 的每条出边 `(v,u,w)`，若 `dist[v]+w < dist[u]` 就更新并把 u 入堆。
- 终止：堆空或目标点被确定；结束后 `dist[]` 即单源最短距离，配 `prev[]` 回溯路径。
- 复杂度：二叉堆实现 O((V+E)logV)；边权为负就要换 Bellman-Ford／SPFA，Dijkstra 不适用。
- 手写时的坑：visited 与堆中旧条目并存时跳过过期项；先口述一遍再写码。

## Q09：知道 A* 算法吗？它优化了迪杰斯特拉的什么问题？

### 面试回答

结论：A* = Dijkstra ＋ 启发式估计——把“离起点多远”换成“离起点多远＋估计离终点还有多远”，让搜索朝目标收敛，少做无谓的均匀扩散。

- 被优化的点：Dijkstra 以同心圆式向外扩张，会把大量与终点无关方向的节点确定下来；A* 用启发函数 h(n) 给节点排序，优先探离目标更近的一侧。
- 关键性质：h 可采纳（不高估真实代价）时，A* 找到的仍是最优路径；h=0 就退化回 Dijkstra，h 越大越贪心、可能不最优。
- 典型 h：地图场景用欧氏／曼哈顿距离到终点的直线估计；路径规划、游戏寻路是主战场。
- 一句局限：启发式依赖“到目标的距离能估计”——没有明确终点或距离无物理含义的图（社交网络），A* 用不上，仍归 Dijkstra／BFS。

## Q10：自己开发用什么 JDK 版本？了解哪些版本的新特性？

### 面试回答

结论：如实报在用版本（按【真实环境】填），并给该版本一两个真用过的特性；再按 LTS 主线报演进，别报背过的清单。

- 8 的坎：没有 `var`、接口默认方法、模块系统；日期时间 API 缺失——从 8 迁移最常提的痛点。
- 11（LTS）：`var` 局部变量推断、HTTP Client、GC 改进（ZGC／Shenandoah 实验版在 11／15 落地）、String 字节码优化。
- 17（LTS）：sealed 密封类、record、instanceof 模式匹配、Switch 表达式增强——Boot 3.x 基线就是 17。
- 21（LTS）：虚拟线程（Loom 正式）、模式匹配的 switch、record patterns、分代 ZGC——现在新项目的首选落点。
- 报法：“我们用【17】，主要用到【record／sealed／文本块】；21 的虚拟线程我在【实验／压测】里试过”——有使用痕迹比列年份可信。

## Q11：JDK 25 有哪些新特性？

### 面试回答

结论：JDK 25 是 2025 年 9 月发布的特性版本（非 LTS），主线是 Project Loom 系列落地＋性能与工具；没跟进就如实说“了解到 21”。

- 正式定稿：Scoped Values（作用域值 JEP 505，虚拟线程间传不可变上下文的推荐方式）、紧凑对象头（JEP 519，默认关闭、`-XX:+UseCompactObjectHeaders` 开启，堆内对象头省内存）；另有 PEM 编解码 API、面向 AI 加速的向量 API 第六次 incubator。
- 仍是预览（报准确状态是加分点）：Structured Concurrency 结构化并发第五次预览（JEP 613）、Module Import Declarations（JEP 512）、Primitive Types in Patterns（第三次预览）、Stable Values（JEP 506）；GraalVM 提前编译（JEP 514）转正但带实验注释，属“可用但不默认”。
- 删除与清理：32 位 x86 端口移除（JEP 503）、AOT 内存映射清理；SecurityManager 在 24 已禁用。
- 收口一句：LTS 选择看 21（当前主流）与下一个 LTS，25 更像“看方向”的版本——Loom 三件套（虚拟线程、结构化并发、Scoped Values）是明确主线。

## Q13：GraphRAG 底层怎么构建实体和实体之间的关系？

### 面试回答

结论：拿 LLM 当“抽取器”——分块后让模型按 schema 抽出实体与关系三元组，再做实体对齐合并、层级社区归纳；抽取不难，难在对齐与质量评估。

- 抽取：每个文本块带实体类型清单（人／组织／产品…）与关系约束提示，要求结构化输出（实体名、类型、描述；头尾实体＋关系＋证据片段）；同一块跑多轮降低遗漏（gleaning 续抽）。
- 对齐合并：同名异体与异名同体是主敌——别名表、向量相似候选再用 LLM 判定同一性，合并实体描述与出处；产物是可溯源的三元组＋原文引用。
- 层级归纳：在实体图上做社区检测（Leiden 类），自底向上让 LLM 为每层社区写摘要——这是“全局问题（summarization query）”能答的原因。
- 索引与评测：实体名／描述入向量与全文索引，检索时图遍历扩上下文；评测必须分两层——抽取质量（抽样人工标注准确率）与端到端答案质量，只有后者会掩盖“实体抽错”。
