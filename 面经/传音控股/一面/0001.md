## Q02：canal 和 Kafka 怎么结合使用的，解决了什么问题？

### 面试回答

一句话：canal 负责把 binlog 变成消息，Kafka 负责把它广播给多个下游。

常见链路是这样：

- canal server 伪装成 replica（从库）解析 binlog。
- 解析结果投递到 Kafka topic。
- 各下游——缓存失效、ES 同步、数仓、审计——以独立 consumer group 消费。

解决的问题有三类：

- 解耦与一对多广播：变更采集端不认识任何具体下游，加消费方不用改 canal。
- 削峰与重放：突发大批量变更先进 Kafka 缓冲，消费方按自己节奏拉取；位点可重置，能重放历史。
- 隔离故障：下游挂掉不影响采集，恢复后继续消费。

两条约束要主动补上：

- 顺序性：同一行／同一 key 要落到同一分区才能保序，跨分区不保证全局序。
- 重复：Kafka 这一层还引入“至少一次”的重复消费问题，所以消费端要幂等。

项目实际拓扑按【真实配置】说。

## Q03：500ms 同步延迟怎么测试的？

### 面试回答

开口先把口径说清——“从哪到哪”不定清楚，数字就没有意义。

- 端到端延迟：数据在主库提交，到目标存储（缓存／ES）可查，这中间的时间差。

测法有两种。第一种，事件内带时间戳：

- canal 事件里取 binlog 提交时间，或者自定义注入一个标记字段。
- 消费落库后算 now − 事件时间。
- 按窗口聚合，出 P50／P99。

第二种，探针法：

- 定时向源表写一条带标记的探测行。
- 轮询目标端，查到它就开始计时。
- 这样测的是完整链路。

要避开的坑有三条：

- 把监控采集／心跳间隔当成端到端延迟。
- 只报平均值，不报分位数。
- 压测环境和生产的批量参数不一致，导致数字不可比。

## Q04：了不了解 harness？Agent 编排呢？

### 面试回答

先分别给定义，再说两者的层次关系。

harness（运行外壳）指模型外面那层运行代码，管四件事：

- 上下文组装：指令、历史、检索结果、工具定义的编排与预算控制。
- 工具执行与结果回灌。
- 循环控制与停止条件。
- 状态持久化与恢复。

同一个模型配不同 harness，能力差别很大。Claude Code、Codex 这类产品的差异，很大程度在 harness 而非模型本身。

Agent 编排是 harness 里再高一层的问题：多步骤／多 Agent 之间谁先谁后怎么定。

- 常见三条路线：固定 workflow、模型自主的 ReAct 循环、或者“先规划后执行”的混合。
- 除此之外还要配状态存储、失败恢复、人工接管点和评测。

用过哪些开源实现如实说【真实经历】；没跑过就说读过源码／文档到什么程度，不虚报。

## Q05：Spring AI 和 MCP 框架，哪块是自带的，哪些是自己开发的？

### 面试回答

分两栏报：框架自带的是什么，我自己写的是什么。最后一句收边界。

Spring AI 自带的（以 1.x 参考文档为口径，按【实际所用版本】说）：

- ChatClient／ChatModel 统一模型抽象，以及各厂商接入。
- prompt 模板与结构化输出。
- tool／function calling 的注解注册与调用循环：@Tool 声明、参数 schema 生成、结果回灌。
- advisors 拦截链。
- RAG 组件：DocumentReader、分割器、向量库、检索 advisor。
- MCP client／server boot starter：把 Spring bean 暴露为 MCP server，或者把 MCP server 的工具聚合进 ChatClient。

自己开发的：

- 业务 prompt 与流程设计。
- 工具背后的真实实现与参数校验。
- 跨调用的编排与状态管理。
- 记忆／上下文的持久化策略。
- 评测集与可观测埋点。
- 鉴权与多租户。

一句话边界：框架给的是“管道和胶水”，判断逻辑与业务正确性是自己的。

## Q07：说明 AI 项目里一个模块的流程，出现异常怎么解决、怎么识别错误？

### 面试回答

按【真实模块】套这个结构：流程按“输入→处理→输出”逐步说，重点放在异常的分层识别与处理。

识别手段有三条：

- 全链路 traceId，把模型调用、工具调用与落库串起来。
- 每步记录输入输出摘要与耗时。
- 输出侧做结构化校验：schema、必填字段、引用是否真实存在。校验不过就判成“模型输出错误”，而不是运行时异常。

错误分四类：

- 输入异常：参数缺失、超长。
- 模型异常：格式漂移、幻觉、拒答。
- 工具异常：超时、报错。
- 系统异常：依赖不可用。

处理按类别走：

- 分类重试与降级：换提示、换小模型、回退规则。
- 超阈值就熔断。
- 留人工接管的出口。
- bad case 沉淀进回归集，防止同类问题复发。

## Q08：AI 时代程序员有什么用，未来的发展观念？

### 面试回答

观点句：AI 大幅压缩的是“把想法写成代码”这一环，但程序员的价值不在打字本身。

下面这四件事，AI 目前只能辅助、不能负责：

- 定义问题与拆需求。
- 在约束下做方案取舍。
- 对正确性与工程后果负责：测试、灰度、回滚、成本。
- 故障时定位和兜底。

发展观念，说的是我往哪走：

- 把自己从“coder”往“能验证 AI 产出的人”移动。用 AI 提效，但要能 review 出幻觉与坏设计。
- 深耕一类系统问题（性能、稳定性、架构）与一个领域知识。这两样恰好是 AI 的短板。

结合自身【真实实践：日常怎么用 AI、边界在哪】说，不喊口号。

## Q11：手撕快速排序。

### 面试回答

做法：选一个 pivot（基准值），把数组分成“< pivot ／ = pivot ／ > pivot”两侧，再递归排序。

- 复杂度：平均 O(n log n)；原地两指针版本的空间是 O(log n) 递归栈。
- 最坏 O(n²)：出现在有序输入＋固定选首元素做 pivot 的时候。
- 所以现场写之前先说明一句，然后随机化 pivot 或用三数取中。

代码骨架（Lomuto 分区）：

```java
void quickSort(int[] a, int l, int r) {
    if (l >= r) return;
    int pivot = a[l + (int) (Math.random() * (r - l + 1))];
    int i = l, j = r;
    while (i <= j) {
        while (a[i] < pivot) i++;
        while (a[j] > pivot) j--;
        if (i <= j) { int t = a[i]; a[i] = a[j]; a[j] = t; i++; j--; }
    }
    quickSort(a, l, j);      // 先递归较短侧可控制栈深
    quickSort(a, i, r);
}
```

三个易错点：

- 等值元素两侧都要停下来，否则死循环。
- `i <= j` 的交叉终止条件。
- 全等数组的性能。

详见专题卡的双指针与三路分区两个版本。
