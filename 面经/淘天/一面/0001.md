## Q01：讲一下你在项目中遇到的问题。

### 面试回答

按“现象→定位→根因→方案→验证”讲一个真实问题：

- 现象：【什么功能在什么条件下出错/变慢】。
- 怎么定位：日志、监控、复现步骤，缩小到哪个环节。
- 根因：真正的原因，不是表面症状。
- 方案与取舍：为什么选这个方案、放弃了什么。
- 结果验证：用什么指标／用例确认解决。

挑一个能体现排查思路和技术深度的，比“调了个 bug 好了”更有说服力。

## Q02：MySQL 查询做过哪些索引优化，用过 EXPLAIN 吗？

### 面试回答

先说真做过的优化，再说 EXPLAIN 怎么读：

- 常见索引优化：给高频 WHERE／JOIN／ORDER BY 列建（联合）索引并按最左前缀排列；把 `SELECT *` 收窄成覆盖索引能命中的列；用联合索引消除 filesort／临时表；大分页改成“上次最大 id 续查”。
- 避免索引失效：WHERE 里别对列做函数／运算、别隐式类型转换、少用前置通配 `LIKE '%x'`。
- EXPLAIN：用来看优化器实际选的执行计划——`type`（访问类型，从 all 到 const 逐级变好）、`key`（真正用的索引）、`rows`（预估扫描行）、`Extra`（`Using index` 覆盖索引、`Using filesort`／`Using temporary` 是危险信号）。

落点：优化的闭环是“EXPLAIN 看现状 → 加/改索引 → 再 EXPLAIN 验证 type 变好、rows 变小”。

## Q03：MySQL 模糊查询里前缀能走索引、后置通配不行的底层原因是什么？

### 面试回答

根因是 B+ 树索引按列值有序排列，只能利用“前缀确定”的有序性。

- `LIKE 'abc%'`（前缀固定）：能以 “abc” 作为起点定位，转成一个连续的范围扫描（`>= 'abc' AND < 'abd'`），走索引。
- `LIKE '%abc'` 或 `'%abc%'`（开头就是通配）：满足条件的值在索引里不连续、散落各处，没法用有序性定位，只能全表／全索引扫。
- 一句话：索引能加速的是“确定前缀的范围”，开头不确定就无法界定起点。

这正是“最左前缀匹配”的一个具体体现——匹配要从左端确定开始。

## Q04：MySQL 索引为什么用 B+ 树？

### 面试回答

对比几种结构，看 B+ 树在“磁盘 + 范围查询”场景为什么最优：

- 二叉树／BST：可能退化成链表，高。平衡树（AVL／红黑）仍是每个节点少量 key，树高、磁盘 IO 次数多。
- B 树：非叶节点也存数据，单页能放的 key 更少、树更“胖矮”程度不如 B+，且范围查询要中序回溯。
- 哈希：等值 O(1) 快，但不支持范围查询和排序，且有冲突。
- B+ 树：非叶只存 key＋指针（扇出大→树矮→IO 少）、数据全在叶子且叶子用双向链表串起来（范围查询、排序顺着链表扫）。

结论：B+ 树矮（通常 3 层放两千万级）、IO 少、天然支持范围与有序扫描，契合 InnoDB 磁盘存储＋大量范围查询的需求。

## Q05：简述在浏览器输入 URL 到页面展示的完整过程。

### 面试回答

按链路分段讲，别只堆名词：

- URL 解析与预处理：拆协议／host／path，安全检查、是否走缓存。
- DNS 解析：域名 → IP（浏览器缓存→本地 hosts→本地 DNS→递归／迭代查询）。
- 建立 TCP 连接：三次握手，HTTPS 再多一步 TLS 握手协商会话密钥。
- 发 HTTP 请求：报文（方法、头部）；服务端处理并返回响应。
- 浏览器解析渲染：解析 HTML 建 DOM、CSS 建 CSSOM，合成渲染树、布局、绘制。
- 断开或复用连接（keep-alive）。

一句加分：能点出“DNS 用 UDP、HTTP 走 TCP、HTTPS 在 TCP 上加 TLS”，说明你真的懂每层是谁。

## Q06：项目中用 Redis 了吗，用来解决什么场景问题？

### 面试回答

按【真实用法】答，落到“解决什么问题”而非只报功能：

- 缓存热点数据：减轻 DB 压力（如商品详情、用户会话）。
- 分布式会话／登录态：多实例共享。
- 计数器／排行榜：点赞、UV、TopN 用 String／ZSet。
- 分布式锁：防重复提交、扣库存（注意锁的正确性与续期）。
- 限流、去重（布隆过滤器）、简单消息（List／PubSub）。

说清“为什么这里用 Redis 而不是 DB／本地缓存”：延迟敏感、数据结构合适、需要跨实例共享或原子操作。

## Q07：Redis 持久化策略有哪些，各自优缺点，生产环境一般怎么做？

### 面试回答

两种＋一种组合：

- RDB：定时全量内存快照。优点是文件紧凑、恢复快、对性能影响小；缺点是两次快照之间宕机会丢数据，fork 大实例有瞬时卡顿。
- AOF：把写命令追加日志、重放恢复。`appendfsync` 可选 always／everysec／no；everysec 兼顾性能与安全（最多丢 1 秒），但文件大、恢复比 RDB 慢。
- 生产常开混合持久化（Redis 4.0+ `aof-use-rdb-preamble`）：AOF 重写时先写一段 RDB 全量、再增量写命令，兼得恢复快与丢数据少。
- 纯缓存、丢了能回源重建的场景，可以只保留必要持久化甚至关闭。

## Q08：AI coding：讲讲你的思路、技术选型原因，以及 AI 起到什么作用？

### 面试回答

本场让现场做 AI coding（素材未记录具体题目），考的是“你怎么和 AI 协作把活干对”，通用讲法：

- 思路：先自己把需求拆清楚（输入输出、约束、边界），再让 AI 生成，不直接采纳——先想方案再问 AI。
- 技术选型：说清为什么用【某语言／框架／数据结构】，依据是场景约束（性能、生态、团队熟悉度），而不是“AI 推荐了这个”。
- AI 的作用定位：把 AI 当“加速器＋第二意见”——生成骨架、补样板、查漏、解释报错；架构决策、正确性判断、边界与测试由人把关。
- 验证：跑用例、看复杂度、审查 AI 代码的安全与边界问题，能改能解释。

要点是让面试官看到“你主导、AI 提效”，而不是“你依赖 AI、说不清为什么”。
