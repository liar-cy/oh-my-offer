## Q04：项目中用 Redis 做了什么？用的什么数据结构？

### 面试回答

## Q05：Redis 的 ZSet 底层实现

### 面试回答

结论：listpack（小数据）＋ skiplist 跳表（大数据）双编码，按元素数与成员长度阈值切换。

- 跳表结构：`dict（成员→分数，O(1) 查分）＋ 按分数排序的跳跃链表`；查询按层向下逼近，期望 O(log N)。
- 为什么用跳表不用红黑树：范围查询天然顺（找到起点沿下层走）、实现简单、可持久化可调试；红黑树的区间遍历要中序。
- 阈值口径：`zset-max-listpack-entries`（默认 128）、`zset-max-listpack-value`（默认 64 字节），超限转 skiplist。
- 3.2 后旧压缩列表 zipList 已换 listpack（解决连锁更新），别说成 zipList。

## Q06：Redis 是单线程还是多线程？

### 面试回答

结论：命令执行永远单线程；6.0 起网络 IO 可以多线程读写与解析。

- 6.0 前：读写、解析、执行都在主线程事件循环。
- 6.0 后：`io-threads`（默认 1 即关闭）只并行做 socket 读写与协议解析，命令仍按到达序回到主线程串行执行——单命令原子性不变。
- 另有常驻后台线程：bgsave 的 fork 子进程、AOF fsync、lazyfree 异步释放——“单线程”指的是命令执行。
- 为什么这么设计：瓶颈在内存与网络而非 CPU；单线程免锁、避免上下文切换，慢命令（KEYS、大 key）会阻塞所有人，所以有 slowlog 与大 key 治理。

## Q07：线程池中多个线程同时对同一个 Redis 做 put，可以吗？

### 面试回答

结论：可以——多线程各自经连接（池）发命令，服务端主线程按到达顺序串行执行，命令级不冲突；但“写同一个 key”时最后一条赢。

- 传输层并发没问题：连接池（JedisPool／Lettuce 单例线程安全连接）就是为多线程设计的；一个 Jedis 实例多线程共享不是线程安全的，要用池。
- 语义层才是坑：多线程对同一 key 做 `GET＋SET` 判重／累加，读改写之间会被穿插——要用 `SETNX`／`INCR`／Lua／事务把判断和写入合成一个原子操作。
- 多线程发命令的执行顺序＝到达顺序，不是发起顺序；业务依赖先后就得自己带版本号（如 `ZADD GT`、外部版本）。
- 若“put”指 `HSET` 多字段：不同线程写同 key 不同 field 互不覆盖，Redis 哈希表按 field 粒度更新。

## Q08：Redis 除了做缓存还能做什么？

### 面试回答

结论：把它当“带持久化的共享内存数据结构服务”，缓存只是最常用一面。

- 分布式锁：`SET NX PX`＋Lua 解锁（Redisson 看门狗）。
- 计数器与限流：`INCR`＋固定／滑动窗口、令牌桶（见 REDIS-004 的 Lua 实现）。
- 排行榜与延迟任务：ZSet 按分数区间取。
- 会话与登录态：Spring Session／Token 存储，多实例共享。
- 消息与广播：Pub/Sub、Stream 消费组（轻量队列，可靠性弱于专业 MQ）。
- 去重与存在性判断：Set、Bitmap、布隆过滤器。
- 报每个用途带一句边界：内存成本、持久化保证、单命令原子范围——只当缓存不需要，上生产就要选保证。

## Q09：Redis 做分布式锁用什么命令？PX 和 EX 的区别？

### 面试回答

结论：一条 `SET lockKey uniqueToken NX PX 30000`——NX 保互斥、PX／EX 保自动过期，必须一条命令原子完成。

- NX：不存在才写，等价于抢锁；分两步（先 SETNX 再 EXPIRE）中间崩掉就是永久锁。
- PX 与 EX 只差单位：PX 毫秒、EX 秒；语义都是“设置绝对过期时刻”，短锁与限流要毫秒精度就用 PX。
- value 必须是本次加锁唯一 token（线程 ID＋随机数）：解锁时比对，防误删别人的锁。
- 解锁要“比较＋删除”原子：Lua 脚本；Redis 8.4 起有条件删除命令可用。

## Q10：分布式锁过期了会怎样？如何避免锁过期带来的问题？

### 面试回答

结论：锁到期即自动释放，旧持有者浑然不觉继续执行，就出现两个“持有者”同时干活——互斥被破坏。

- 危害分级：重复扣款／超卖看下游有没有兜底（条件更新、唯一约束）；纯加速型操作丢了无所谓。
- 缓解一：TTL 覆盖 P99 执行时间并留余量；时长不可预测时看门狗续期（校验 token 再延长，限制续期次数并记录失败）。
- 缓解二：续期挡不住长 GC 暂停／进程假死——关键资源要带 fencing token（单调递增，资源侧拒绝旧号）或数据库条件更新兜底。
- 设计观：Redis 锁是“租约”，不是“所有权证明”；正确性押在锁上之前，先问业务幂等做没做。

关联专题：[[专题题库/Redis#REDIS-006：Redis 分布式锁如何正确加锁、解锁和续期？|REDIS-006：过期、续期与 fencing]]

## Q11：Redis 集群存储锁实例，节点挂掉时如何避免锁丢失？

### 面试回答

结论：锁的丢失来自主从异步复制——主节点写完锁还没同步就挂，从节点升主没有这把锁，第二个人又能加上。

- 方案一 Redlock：向 N 个完全独立的主节点多数派加锁成功才算持锁，挂一个还有多数；但时钟漂移、重启复活都有争议，Martin Kleppmann 明确质疑其安全性，不能当严格保证。
- 方案二（推荐口径）：锁只是“性能屏障”，正确性交给资源侧——fencing token／数据库版本号／唯一约束，保证“即使并发也不会错”，锁挂掉只是变慢不是变错。
- 方案三：要强互斥换 CP 协调服务（ZooKeeper 临时顺序节点、etcd Lease＋Revision），会话断开锁自动释放，代价是吞吐与运维。
- Cluster 模式注意：锁 key 与业务 key 同槽（hash tag）才能保证同节点事务；failover 期间锁语义本来就不可靠，要监控切换事件。

## Q12：项目 2 的图片检索部分怎么实现？

### 面试回答

- 设计四步：抓高频 SQL → 等值列在前、范围／排序在后 → 选择性高优先、写入成本权衡 → EXPLAIN 验证（type、key、Extra）。
- 失效一：不满足最左前缀——条件里缺前导列，后面列用不上。
- 失效二：对索引列做函数／运算／隐式类型转换（varchar 列传数字），或字符集／排序规则不一致的连接。
- 失效三：大范围 `LIKE '%xx'`、`NOT IN`／`!=`、`OR` 一侧无索引、优化器按统计信息判定走索引更贵（回表放大）。
- 加分点：区分“真失效”与“优化器主动不走”——后者是成本决策，用 `FORCE INDEX` 验证再下结论。

## Q16：什么是 CDN？为什么方案里要用 CDN？

### 面试回答

结论：CDN 是离用户更近的边缘缓存集群，把静态内容从源站卸载到边缘；秒杀方案用它是因为“开场 99% 的流量只是在看页面，不是在下单”。

- 原理：DNS 调度（CNAME＋智能解析）把用户指到就近边缘节点；节点缓存命中直接返回，未命中回源并可做请求合并防击穿。

- 边界要讲：CDN 缓存个性化内容会串用户（登录态、价格），个性化片段走边缘脚本／异步接口；它挡不住“直连下单接口”的刷量，防刷在网关层（SYS-033）。

## Q17：有哪些限流算法？秒杀场景适合哪种？

### 面试回答

结论：四种经典算法各解一个问题；秒杀是“入口要平滑、库存要精确”，排队类＋分布式计数组合用。

- 固定窗口：实现最简，窗口边界有 2 倍突刺——单独用不够。
- 滑动窗口：抹平边界突刺，适合“每秒配额”类通用限流（Sentinel 内部就是滑动窗口统计）。
- 漏桶：恒定速率流出，强行平滑——适合保护脆弱下游、把脉冲拉直；秒杀入口可用它排队削峰。
- 令牌桶：允许一定突发（攒桶），更贴合真实用户流量——适合接口常规限流。
- 秒杀口径：入口用漏桶／排队把洪峰整形，库存判定不用限流算法而用原子扣减（`DECR`／Lua 判断）——限流是“拒绝超额请求”，扣减是“先到先得”，别混。分布式全局配额落 Redis（REDIS-004 的 Lua 实现）。

## Q21：如何在 Spring 中实现一个简单的事务？

## Q22：Test 类里 a 调用加了 @Transactional 的 b，事务生效吗？a 也加上呢？

### 面试回答

## Q24：为什么 ES 能支持叶子查询和复合查询？

### 面试回答

结论：因为查询被建模成一棵“可组合的算子树”——叶子对应一种数据结构的检索，复合节点（bool）对子查询结果做集合运算与打分组合。

- 叶子查询：`term／terms`（倒排词典→postings）、`match`（先分词再查倒排）、`range`（数值／日期走 BKD 树＋doc_values）、`exists`、`geo`、`knn`（向量索引进来后向量检索也成为叶子）。
- 复合查询：`bool` 的 must／should／must_not／filter 就是交、并、差与“不参与打分”的开关；`function_score`、`dis_max` 在结果分上再加工。
- 实现支撑：每个查询对象统一实现“重写→供给匹配迭代器”，上层组合下层迭代器（位图／跳表游标），filter 上下文还能吃节点级缓存——这是它能任意嵌套的工程原因。
- 一句对照：MySQL 的 where 组合靠优化器现场找路；ES 是倒排＋列存天然把“任意条件组合”变成集合运算，代价是不做 join。

## Q25：ES 数据分布在不同分片上，范围查询的内部实现逻辑？

### 面试回答

结论：scatter-and-gather——协调节点把同一个 range 查询广播到所有相关分片，各分片本地走 BKD 树求 doc IDs，汇总排序后取全局 top-N；分片存的是区间还是点，不影响正确性，只影响放大。

- 本地执行：range 不是逐行比较；数值／日期字段以 doc_values 列存＋BKD 树（类平衡 KD 结构）索引，按区间圈出匹配文档集，命中后回段内取所需。
- 全局合并：带排序时分片各返回 top-(from+size)，协调节点归并——所以 `from+size` 深分页放大 N 倍，翻页用 `search_after`。

- 减少放大：路由让时间序列／租户数据落有限分片（查询时按分片裁剪），比“靠更大集群硬扛”有效。

### 面试回答

结论：四条主流路——数据库号段、雪花类本地生成、Redis 计数、多库步长自增；选型看“趋势递增要不要、能不能依赖存储、位数要不要短”。

- 号段模式（Leaf-segment 类）：DB 一次发一段（`max_id+step` 原子更新），内存双 buffer 预取；DB 压力骤降，短时不可用还能撑。
- 雪花算法：64 位本地生成，不依赖存储、趋势递增；要解决机器号分配与时钟回拨（Q27 展开）。
- Redis INCR：实现简单、性能高；持久化与可用性要评估，Redis 挂了发号即断。
- 多库不同步长自增：改造小，但空洞与运维心智差； UUID／雪花转 Base62：短且无序，适合非主键场景。
- 收口口径：全局唯一是底线，全局有序是奢侈品——业务要“可排序”时确认需要的是趋势递增还是严格连续。

## Q27：谈谈雪花算法的底层实现

### 面试回答

结论：64 位＝1 符号位＋41 毫秒时间差＋10 机器号＋12 序列号，同一毫秒序列自增、溢出等下一毫秒。

- 各段容量算清：41 位约 69 年（自定义起点起算）、10 位 1024 节点（可拆 5＋5 机房＋机器）、12 位每毫秒 4096 个——单机理论上限约 409.6 万／秒。
- 时钟回拨：小回拨等待追平或把回拨量累加进时间位；大回拨报警停发号——“继续发”就可能重号，这里必须给策略不给侥幸。
- 机器号分配：容器 IP 会变，靠 ZK／etcd 顺序节点或配置中心显式登记，别用 IP／MAC 派生。
- 性质边界：趋势递增而非全局有序——跨机器同一毫秒的号交错，落库分片路由按 ID 高位（时间）能均摊，按低位会倾斜；这也是它与“号段模式”的本质差异。

## Q28：如何排查 CPU 使用率高的问题？Java 的 GC 日志长什么样？

### 面试回答

结论：定位链“机器→进程→线程→代码”，GC 日志按“每次回收一段：时间戳＋回收器风格＋代前后容量＋停顿”读。

- 排查四步：`top` 找进程 → `top -Hp <pid>` 找线程 → `printf '%x' tid` 转 16 进制 → `jstack <pid>` 搜 `nid=0x…` 看栈；分不清在算还是在洗，先看 `%CPU` 最高线程属于业务栈还是 GC 线程（VM Thread／G1 Concurrent GC）。
- GC 线程烧 CPU 的特征：FGC 频繁（`jstat -gcutil` 看 FGC 计数增速）＋日志里回收后老年代降幅小——多半是泄漏或晋升过快，接 heap dump 分析。
- G1 日志示例一行：`[GC pause (G1 Evacuation Pause) (young), 0.021 secs]` 前后带 `[Eden: 512.0M(1024.0M)->0.0B(992.0M) Survivors: 32M->64M Heap: 800M(2G)->310M(2G)]`——“回收了多少、堆还剩多少、停了多久”三件事。
- 常态准备：`-Xlog:gc*:file=gc.log:time,uptime,level,tags`（JDK 9＋ 统一日志），没有日志的现场等于没证据。

## Q29：了解 RAG、Agent、MCP 吗？

### 面试回答

结论：三个词各一句定义＋一个自己动手的证据，没做过就说了解到哪层，别背名词。

- RAG：检索增强的生成——文档切块向量化入库，提问召回 Top-K 拼进 Prompt，模型基于证据回答；关键指标是召回质量（RAG-001 的链路）。
- Agent：模型在循环里做“规划→调工具→观察→再决策”，直到任务完成；工程难点在循环控制与上下文管理（AGENT-009）。
- MCP：给“模型连工具”定的一套开放协议——宿主／Client／Server 分层，工具与资源标准化暴露，一次接入多处复用（AGENT-007 的链路职责）。
- 后端岗的落点可以主动说：这三样的服务端形态就是“向量检索＋任务队列＋网关鉴权”，与我的检索／高并发实践相接。
