## Q03：线程池五连问：提交流程、拒绝策略、队列消费策略、无界队列还要非核心线程吗、无界队列的问题与使用场景。

### 面试回答

提交流程（四步）：

- 线程数没到核心数：直接建核心线程执行。
- 到核心数了：任务进工作队列。
- 队列满了：建非核心线程，直到最大数。
- 还满：走拒绝策略。

拒绝策略四种加一种自定义：

- AbortPolicy（默认）：抛 `RejectedExecutionException`。
- CallerRunsPolicy：提交线程自己跑这个任务，天然形成背压。
- DiscardPolicy：静默丢弃。
- DiscardOldestPolicy：丢队头最老的任务再重试入队。
- 生产上常见自定义：记录日志＋告警＋按业务降级或落库重投。

队列消费策略：

- worker 在 `runWorker` 循环里从队列取任务，默认 `takeLast`/`poll` 阻塞等待，取到就执行——队列是 FIFO，先到先服务。
- 想“高优先级先消费”得换 `PriorityBlockingQueue`，普通队列不保证。

无界队列还要非核心线程吗：

- 基本用不上。入队几乎永远成功，第三步“扩非核心线程”触发不了，`maximumPoolSize` 形同虚设。
- 所以非核心线程只有配“有界队列”才有意义。

无界队列的问题与场景：

- 问题：任务积压吃内存可能 OOM；线程数扩不上去；拒绝策略永不触发，系统失去过载信号。
- 场景：任务量可控的后台低峰处理、或明确要“固定并发＋全部接收”的场合（`newFixedThreadPool` 就是这个形态）；对外流量入口不建议用，优先有界队列＋明确拒绝行为。

## Q04：谈谈 Java 里面的锁消除和锁升级。

### 面试回答

结论：都是减锁开销的优化，但发生在两个层面——锁升级是运行期按竞争程度换锁的实现形态，锁消除是 JIT 编译期把根本不必要的锁直接删掉。

锁升级（对象头 mark word 的状态推进）：

- 无锁 → 偏向锁 → 轻量级锁 → 重量级锁，只升不降。
- 偏向锁：只有一个线程访问，对象头记线程 ID，重入零开销（JDK 15 起默认禁用，JDK 18 移除）。
- 轻量级锁：有交替竞争，线程在栈里建锁记录 CAS 替换 mark word，抢不到先自旋。
- 重量级锁：自旋失败或竞争激烈，膨胀为 monitor，挂起进内核队列，靠 OS 互斥原语。

锁消除：

- JIT（C2）对锁对象做逃逸分析：整个加锁作用域内对象不逃逸出线程，别的线程不可能看到，锁就是多余的——直接删。
- 典型例子：方法内 `new StringBuffer().append(a).append(b)`，StringBuffer 的 synchronized 方法在局部对象上被消除。
- 前提：逃逸分析开启（`-XX:+DoEscapeAnalysis`，默认开）＋锁消除开启（`-XX:+EliminateLocks`，默认开）；只发生在被 JIT 编译的热点代码上，解释执行没有这层。

一句收口：升级解决“竞争少时别惊动内核”，消除解决“压根没竞争时别留指令”。

## Q05：synchronized 可重入吗？能保证可见性吗？

### 面试回答

两个都能。

- 可重入：同一线程重复进入同一把锁不会自锁死——monitor 记录持有线程和重入计数，进入加一、退出减一，归零才真正释放。嵌套的同步方法／递归同步块都靠这个。
- 可见性：能。synchronized 的语义包含“退出临界区前把共享变量刷新回主内存，进入时重新读取”；用 happens-before 说就是“同一把锁的 unlock happens-before 后续的 lock”。

补两句边界，防止说过头：

- 可见性只对“所有路径都经过同一把锁的读写”成立；有人不拿锁裸读，就谈不上可见。
- volatile 和 synchronized 都能保证可见性，但 volatile 不保证原子性，两者用途不同。

## Q06：某个服务 CPU 利用率到 100% 了，如何排查？

### 面试回答

结论：先分清是“业务线程烧的”还是“GC 烧的”，再定位到具体代码行。

- 第一步 `top` 找到高 CPU 进程，`top -H -p <pid>` 看是哪些线程高。
- 记下线程 TID，`printf '%x' <tid>` 转十六进制，`jstack <pid>` 在快照里搜 `nid=0x...`，直接看到线程栈。
- 分支判断：
  - 栈停在业务代码：找死循环、正则回溯、低效序列化、大排序这类热点。
  - 多个 GC 线程满负荷：是 GC 问题，`jstat -gcutil <pid> 1000` 看 FGC 频率与耗时，再查内存侧（对象泄漏或堆配置过小）。
- 更省事的工具路径：Arthas `thread -n 3` 直接列最忙线程，或 async-profiler 出火焰图看热点占比。
- 收口给修复动作：定位到【代码/参数】后【真实修复】，并说明如何验证 CPU 回落。

## Q07：OOM 了怎么排查？自己用过 jmap 这类工具排查过错误吗？

### 面试回答

结论：先看异常类型定方向，再拿 dump 找持有者，别对着字段表心算。

- 第一步读报错分类：
  - `Java heap space`：堆装不下，最常见。
  - `GC overhead limit exceeded`：绝大部分时间在 GC 回收不出东西。
  - `Metaspace`：类元数据涨，常见动态类生成（代理、Groovy 脚本）。
  - `unable to create new native thread`：线程数或 OS 资源到顶，不是堆问题。
- 取现场：启动参数加 `-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=...` 自动落盘；事后可用 `jmap -dump:live,format=b,file=heap.hprof <pid>` 手动抓。
- 分析：MAT 看支配树和 GC Roots 引用链，回答“谁还引用着这些对象”；`jmap -histo` 可先粗看 top 对象类型。
- 高频根因清单：无上限本地缓存、ThreadLocal 没 remove、一次性大结果集查询、集合只增不减、堆外内存误判成堆内。
- 有没有亲手用过（个人事实）：按真实经历答【哪次问题、什么工具、找到什么、怎么修】；没用过就说没用过，能完整讲清上面这条路径同样加分，别编事故。

## Q08：MySQL 有哪几种事务隔离级别（从低到高）？什么是幻读？MySQL 怎么解决幻读？

### 面试回答

从低到高四级：

- READ UNCOMMITTED（读未提交）：能读到别人没提交的数据，脏读。
- READ COMMITTED（读已提交）：解决脏读，同事务两次读结果可能不同（不可重复读）。
- REPEATABLE READ（可重复读，MySQL 默认）：解决不可重复读，幻读在这层要专门处理。
- SERIALIZABLE（串行化）：都读成加锁读，没有并发可言。

幻读的定义：

- 同一事务内两次范围查询，第二次多出（或少了）别人新插入后提交的行——针对“不存在于结果集的行”，和不可重复读（已有行的值变了）不是一回事。

MySQL（InnoDB，RR 层）的解法是两条路各管一类读：

- 快照读：普通 SELECT 走 MVCC，读一致性视图，全程看不到别人新提交的行——两次读自然一样。
- 当前读：SELECT FOR UPDATE／UPDATE／DELETE 走 next-key lock（记录锁＋间隙锁），把范围内的间隙也锁住，别人插不进来。

补一句严谨口径：RR 下“先快照读、再当前读”混用时仍可能看到幻影行，所以“MySQL 彻底解决幻读”说过头了；要绝对没有，得串行化或全部走加锁读。

## Q09：谈谈 Kafka；为什么项目选型用 RabbitMQ；RabbitMQ 的数据持久化怎么做的？

### 面试回答

谈谈 Kafka（按定位—机制—代价三层）：

- 定位：分布式日志系统——分区是追加写的日志，消费按 offset 拉取，天然适合重放与多消费组。
- 高吞吐靠四件事：顺序写磁盘、页缓存（不靠 JVM 堆缓存）、零拷贝 sendfile、分区并行＋批量压缩。
- 语义：分区内有序、跨分区无序；副本 ISR＋`acks` 控制可靠性；消费者组 Rebalance 分配分区。
- 适用：日志采集、埋点、流处理骨干；不适合复杂路由和低延迟小流量的任务队列。

为什么项目用 RabbitMQ（个人选型，按真实理由填）：

- 【参考口径】业务消息量级不大但路由复杂——exchange（direct／topic 等）做灵活分发是 RabbitMQ 的强项。
- 需要延迟队列、消费确认这类任务队列语义；团队已有运维经验。
- Kafka 的优势在吞吐与回放，本项目没有这个瓶颈；选型按场景不按流行度。

RabbitMQ 持久化分三层：

- 元数据：声明 exchange／queue 时 `durable=true`，重启后队列还在。
- 消息：发送时 `delivery_mode=2`（persistent），消息落磁盘存储；非持久化消息重启即丢。
- 边界要主动说：持久化是异步刷盘，“发送返回成功／confirm”不等于已落盘，单节点崩溃仍有丢消息窗口；要高可靠上 quorum queue（Raft 多副本）＋publisher confirm＋消费者手动 ack。

## Q10：线程和进程的区别？

### 面试回答

一句话：进程是资源隔离的单位，线程是 CPU 调度的单位；线程共享进程资源，自己只带一份执行上下文。

- 地址空间：进程间相互隔离；同进程线程共享堆和全局段，各自独立栈与寄存器上下文。
- 切换成本：进程切换要换页表、刷 TLB，明显贵于线程切换。
- 通信：进程要走 IPC（管道、共享内存、Socket 等）；线程直接读写共享变量，代价是要自己解决同步。
- 崩溃影响：一个进程挂了不影响别的进程；一个线程写崩共享内存，整个进程一起倒。
- 补一层协程：用户态调度的更轻执行单元，切换不经过内核，适合海量 IO 并发。

## Q11：线程的安全怎么保证？

### 面试回答

结论：要么不共享，要么控制共享访问；按优先级从“消灭问题”到“解决竞争”排。

- 不共享：线程封闭（每线程一份，如局部变量、`ThreadLocal`）、消息传递代替共享状态。
- 不可变：final 字段＋正确发布的对象不需要锁，字符串和各类 unmodifiable 集合都是这个思路。
- 原子操作：单个变量的更新用 `AtomicInteger`／`LongAdder` 这类 CAS 原子类。
- 加锁：`synchronized`／`ReentrantLock` 保护复合动作（读-改-写、检查-执行）。
- 并发容器：`ConcurrentHashMap`、阻塞队列这些把细粒度锁做好了，优先复用不手写。
- 两条底线：所有访问共享状态的路径都要有同样的保护（漏一条就破功）；避免死锁靠统一加锁顺序和缩小锁范围，不靠运气。

## Q12：进程间通信的方式有哪些？数据是怎么从一个进程传到另一个进程的？

### 面试回答

六种常用方式：管道、命名管道、消息队列、共享内存、信号、Socket；选择按数据量、要不要消息边界、是否跨主机权衡。

数据传输的本质流程——两个进程地址空间互相不可见，数据只有两条路：经内核中转，或映射同一份物理内存。

- 管道／Socket：写方系统调用把数据从用户态拷贝进内核缓冲区，读方再从内核缓冲区拷到自己的用户态——两次拷贝，内核是中间人。
- 消息队列：同管道思路，只是内核按“消息”为单位维护链表，保留边界。
- 共享内存：`mmap` 把同一块物理页框映射进两个进程的虚拟地址空间，之后读写直达同一内存、零拷贝——最快，但要自己做同步（信号量／锁）。
- 信号：不传数据，只传“事件发生了”这个通知，内核里挂起处理函数。
- 跨机场景：走网络 Socket，数据经内核协议栈封装发出，对端协议栈重组再投递给进程。

一句收口：除了共享内存，其它方式都是“拷贝进内核、再拷贝出来”；共享内存省掉拷贝，换来同步要自己负责。

## Q13：Redis 常用的数据结构有哪些？

### 面试回答

基础五种加三种派生，每种带一个真实场景：

- String：缓存对象 JSON、计数器、`SET NX` 分布式锁。
- Hash：对象字段级读写（用户资料、商品库存明细）。
- List：最新动态列表、简单任务队列。
- Set：共同好友、抽奖去重、交并差运算。
- ZSet：排行榜、延时队列（score 存执行时间）。
- 派生：bitmap（签到／活跃标记）、HyperLogLog（海量基数统计）、GEO（附近的人，底层就是 ZSet）。
- Stream：轻量消息队列，支持消费组。

## Q14：ZSet 的具体实现？数据量大时为什么用跳表不用压缩列表？查元素个数和分数的命令与复杂度？

### 面试回答

实现是“按规模换结构”：

- 元素少且短：listpack（单元素带 score，内存紧凑）。
- 超过阈值（`zset-max-listpack-entries`／`-value`）：换成跳表＋哈希表双结构——跳表按分数维护有序，哈希表存 member→score。

为什么大了不能继续用压缩列表：

- listpack 按分数查找／插入都要线性扫描，O(n)；数据量大时排名、区间查询全变慢。
- 跳表查找、插入平均 O(log n)，范围查询沿第 0 层链表顺序走，天然支持 `ZRANGEBYSCORE` 这类操作。
- 双结构互补：没有哈希表，`ZSCORE` 也得扫跳表；Redis 用一点内存换 O(1) 按成员查分数。

两条命令：

- 查元素个数：`ZCARD key`，O(1)——结构里维护了长度计数。
- 查某元素的分数：`ZSCORE key member`，O(1)——走的是哈希表。
- 别和 `ZRANK`（取排名）混：排名要沿跳表累加跨度，平均 O(log n)。

## Q15：手撕：有序含重复数组中找某元素出现的次数（二分找左右边界）。

### 面试回答

题意：数组有序且含重复，如 `nums = [1,2,2,3,3,3,4,4,4,4]`，给 target 返回它出现的次数；利用有序条件做二分。

思路与结论：

- 出现次数＝右边界－左边界：分别二分找“第一个 ≥ target 的下标”和“第一个 > target 的下标”。
- 两个查找共用一个模板，只差判定条件里是 `>=` 还是 `>`。
- 复杂度 O(log n)；边界不存在时两下标相等，返回 0，天然覆盖“元素不在数组里”。

```java
int countOccurrences(int[] nums, int target) {
    return lowerBound(nums, target + 1) - lowerBound(nums, target);
}
// 第一个 >= t 的下标；全都小于 t 时返回 nums.length
int lowerBound(int[] nums, int t) {
    int left = 0, right = nums.length;            // 半开区间 [left, right)
    while (left < right) {
        int mid = left + ((right - left) >> 1);
        if (nums[mid] < t) left = mid + 1;
        else right = mid;
    }
    return left;
}
```

- 例：target＝3，`lowerBound(3)=3`、`lowerBound(4)=6`，返回 3。
- 口述时主动说：线性扫描是 O(n)，有序条件就是为了让两次二分替代它。
