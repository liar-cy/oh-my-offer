## Q02：操作系统的线程和 Java 线程是什么关系？

### 面试回答

结论：HotSpot 里 Java 线程是内核线程的一层包装——1:1 映射，JVM 自己不搞用户态线程调度。

- 创建 `Thread.start()` 最终走到 `pthread_create`（Linux），每个 Java 线程背后就是一个内核线程（LWP），由 OS 调度上核。
- 所以 Java 线程是“贵的”：每条要内核栈＋JVM 栈（`-Xss` 默认约 1MB 虚拟预留），线程数上限受 OS 与内存约束——这也是线程池存在的前提。
- `Thread.State`（NEW／RUNNABLE／BLOCKED／WAITING…）是 JVM 自己定义的抽象，和内核调度状态不是一一对应；比如 BLOCKED／WAITING 在内核里都是“阻塞等待”，RUNNABLE 可能正在跑也可能在就绪队列。
- 变化点：JDK 21 的虚拟线程（Loom）改成 M:N——大量虚拟线程挂载在少量载体线程（内核线程）上，阻塞 IO 时卸载不占内核线程；这是 Java 第一次在语言层引入“类协程”的用户态调度。

## Q03：谈谈协程。

### 面试回答

一句话：协程是用户态调度的轻量执行单元——切换由运行时或库完成，不惊动内核。

- 为什么轻：不需要内核栈，上下文只保存自己的寄存器与少量状态，切换是函数级开销；单线程可以挂成千上万条。
- 两种形态：有栈协程（Go goroutine，GMP 调度，阻塞点自动让出）与无栈协程（Kotlin／Rust 的 suspend 状态机，挂起点显式）。
- Java 的对应物就是虚拟线程：阻塞 IO 时 unmount 载体线程，await 语义由 JDK 内部改造现有阻塞 API 实现（JUC-017 有对照）。
- 代价要主动说：
  - 协程里发生真正的 CPU 密集或不可让出的系统调用，会卡住整个调度循环和载体线程。
  - 单线程内“天然无竞争”只对调度成立——共享数据仍然要同步，别顺手去掉锁。
  - 吃不吃多核看实现：Go 的调度器会分发到多核；只绑单线程的 event loop 不吃。
- 适用场景：海量并发 IO（网关、爬虫、RPC 聚合）；QPS 不高或 CPU 密集场景收益有限。

## Q04：WebSocket 网络层面是怎么做到的？Netty 和 Socket、WebSocket 是什么关系？

### 面试回答

WebSocket 在网络层做的事（按建连—帧—保活三步）：

- 建连：先走一次 HTTP Upgrade 握手——客户端发 `Upgrade: websocket` 和 `Sec-WebSocket-Key`，服务端回 101 Switching Protocols 加 `Sec-WebSocket-Accept`（key 拼固定 GUID 后 SHA-1）。握手完，底层还是那条 TCP 长连接。
- 通信用帧不用报文：帧头带 opcode（文本／二进制／ping／pong／close）、FIN 分片位、长度；客户端→服务端的帧强制掩码（防代理缓存投毒），双向全双工，没有 HTTP“一问一答”的方向限制。
- 保活靠 ping／pong 控制帧；断线由应用层重连策略兜底。

三者的关系是三个层，不是三个竞品：

- Socket：内核提供的网络 API 抽象（TCP 端点），Java 里有 BIO 的 `ServerSocket` 和 NIO 的 `SocketChannel` 两种形态。
- WebSocket：跑在 TCP 之上的应用层协议，解决“HTTP 不适合服务端主动推送”的问题。
- Netty：用户态的事件驱动网络框架，封装 NIO 多路复用（epoll）与线程模型，并自带 WebSocket 协议编解码（`HttpServerCodec` 处理握手升级＋`WebSocketServerProtocolHandler` 处理帧）——用它不用手写协议解析。
- 一句收口：协议是 WebSocket，传输是 TCP，内核接口是 socket API，Netty 是把这些包起来的框架。

有没有用过 Netty（个人事实）：按真实经历答【用在哪、做了什么 handler】；只写过原生 NIO 就如实说，能讲清 pipeline 与多路复用模型即可。

## Q05：什么是分布式事务？有哪些范式？

### 面试回答

定义：一个业务操作跨多个独立的数据资源（多库、多服务、多中间件），要保证“要么都成、要么都败”——单机 ACID 的事务管理器管不到跨进程边界，只能靠协议和补偿逼近。

常见范式按一致性强度排：

- XA／2PC（两阶段提交）：协调者先 prepare 再 commit，强一致；代价是同步阻塞、协调者单点、prepare 后参与者攥锁等待。3PC 加超时缓解但不根治。
- TCC：业务层拆 Try（预留资源）－Confirm（提交）－Cancel（释放），隔离性好但侵入最大；Cancel 要防悬挂、防空回滚。
- Saga：正向操作链＋逆向补偿链，适合长流程（机票、订单）；补偿不是回滚，业务要预先设计成可反向。
- 事务消息／本地消息表：主事务和“发消息”绑在一个本地事务里，靠消息投递把最终一致推下去——放弃强一致换吞吐与解耦。
- Seata AT：自动化版的“2PC＋反向 SQL 补偿”，全局锁做隔离，业务无侵入但要有回滚日志表。

选型收口：

- 金融扣款这类要强隔离选 TCC／XA。
- 多数互联网场景用最终一致（事务消息／Saga）＋对账兜底。
- 先问“能不能不跨”，拆表、合并服务也是解法。

## Q06：常见的限流算法有哪些？滑动窗口相对固定窗口为什么要滑动、解决什么问题？

### 面试回答

四种常见算法：

- 固定窗口计数：一个 key 一个 TTL 的计数器，实现最简单。
- 滑动窗口：把窗口切成多个小格滚动统计（Redis 用 ZSet 存请求时间戳，Sentinel 用槽位链表）。
- 令牌桶：按速率往桶里放令牌，请求取令牌，桶里有存货。
- 漏桶：请求先排队，以固定速率漏出处理。

滑动窗口为什么要滑动——解决固定窗口的“边界突刺”：

- 固定窗口的计数在边界瞬间清零：限流 100／分钟，前一分钟最后 1 秒来 100、新一分钟开头又放 100，两秒内实际放过 200——瞬时流量是配额的两倍。
- 滑动窗口统计的是“最近 N 秒”这个滚动区间，窗口不会同时清零两个相邻区间，突刺被打散；粒度越细越接近真实速率。

令牌桶与漏桶的分工顺带说清：

- 令牌桶允许一定突发（桶里有存货就能一次多取），适合互联网流量；漏桶出口恒定速率，适合保护下游脆弱系统（如落库、三方接口）。

## Q07：谈谈 synchronized：含义、使用场景、特点；它和 CAS 有什么区别？

### 面试回答

含义：基于对象监视器（monitor）的内置互斥锁，每个对象都能当锁——实例方法锁 this、静态方法锁 Class、括号里显式给对象。

使用场景：

- 对共享可变状态的“读-改-写”“检查-再执行”这类复合动作：计数、缓存 put-if-absent、单例懒初始化。
- 需要等待通知时用 wait／notify 配合（生产者消费者）。

特点：

- 可重入（monitor 记持有者与计数）、自动加解锁（异常也释放）。
- 非公平、不可中断、无超时——这是和 `ReentrantLock` 的主要差距。
- 有锁升级路径：偏向→轻量级→重量级，低竞争时开销不大（JUC-024）。
- 语义上同时给互斥和可见性（unlock happens-before 后一次 lock）。

和 CAS 的区别：

- 思路相反：synchronized 悲观——先拿锁再操作，抢不到挂起等待；CAS 乐观——不拿锁直接比较交换，失败就重试。
- 成本形态不同：synchronized 重量级路径有内核上下文切换；CAS 无锁无切换，但高竞争下空转重试烧 CPU。
- CAS 有 ABA 问题（要版本化的 `AtomicStampedReference`）；synchronized 没有这个概念，因为临界区内根本不让别人改。
- 适用面：单变量低竞争用原子类／`LongAdder`；复合不变量、多变量一致性用锁。两者不互相替代，`LongAdder` 内部就是 CAS 加分段 Cell。

## Q09：手撕：合并两个有序链表为升序链表，分别写递归和非递归实现。

### 面试回答

思路都是“双指针比较头节点，小的接进结果”，差别只在控制方式：

- 非递归：哨兵头 `dummy` 起一条 tail 指针，两两比较、尾插、前进；最后接上剩余段。O(m+n) 时间、O(1) 空间——生产写法。
- 递归：比较两个头，胜者的 next 指向“剩余部分的合并结果”；递归深度 m+n，空间 O(m+n)——代码最短但长链表有栈溢出风险。

```java
// 非递归
public ListNode mergeTwoLists(ListNode l1, ListNode l2) {
    ListNode dummy = new ListNode(0), tail = dummy;
    while (l1 != null && l2 != null) {
        if (l1.val <= l2.val) { tail.next = l1; l1 = l1.next; }
        else                  { tail.next = l2; l2 = l2.next; }
        tail = tail.next;
    }
    tail.next = (l1 != null) ? l1 : l2;   // 剩余段直接挂上
    return dummy.next;
}
// 递归
public ListNode mergeTwoListsR(ListNode l1, ListNode l2) {
    if (l1 == null) return l2;
    if (l2 == null) return l1;
    if (l1.val <= l2.val) { l1.next = mergeTwoListsR(l1.next, l2); return l1; }
    else                  { l2.next = mergeTwoListsR(l1, l2.next); return l2; }
}
```

- 口述要点：
  - 复用原节点不新建（题目一般允许原地改 next）。
  - 相等时取 l1 保持稳定。
  - 边界是任一链表为空。
