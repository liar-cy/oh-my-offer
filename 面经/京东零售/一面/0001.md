## Q04：平时使用的 JDK 版本有哪些，不同版本有哪些区别？

先如实报自己实际用过的版本（如 8、11、17、21），并说明它们都是 LTS（长期支持版本）。

- JDK 8：大量存量系统在用，带来 lambda／Stream／新日期 API。
- JDK 11：首个长期支持的新版本，有 HTTP Client、`var`、GC 更新。
- JDK 17：record、sealed、instanceof 模式匹配；Spring Boot 3 的最低要求。
- JDK 21：虚拟线程、分代 ZGC。

答“区别”时挑两三条主线讲就行：语言与 API、GC 默认与能力、模块化与运行时。不用逐版本背清单。

底线是能说清这两句：为什么新项目选 17／21，老系统为什么还留 8。

## Q05：讲一下你已知的所有 GC 算法，不同 JDK 版本中 GC 的迭代方向是什么？

**先报算法**：

- 标记—清除：会有碎片。
- 复制：无碎片，但费空间。
- 标记—整理：无碎片，但移动成本高。
- 分代收集：基于弱分代假说，年轻代用复制、老年代用标记整理。

**迭代方向**一句话：从“吞吐优先、全堆停顿”走向“并发、低停顿、可预测”。

- Serial／Parallel：STW（Stop The World，回收时应用线程全停），换吞吐量。
- CMS：并发清除，停顿低，但有碎片、还可能并发失败。
- G1：堆 Region 化，停顿可以设目标、可预测。
- ZGC／Shenandoah：着色指针／读屏障，停顿跟堆大小几乎无关，能到亚毫秒级。JDK 21 起 ZGC 分代化。

答完点明一句：JDK 9 起默认是 G1，CMS 已在 JDK 14 移除。

## Q06：不同版本的 GC 有什么主要特点（CMS、G1、ZGC）？

**CMS**：并发标记清除，目标是低停顿。

- 走四个阶段：初始标记／并发标记／重新标记／并发清除。
- 缺点：碎片、浮动垃圾；并发失败会退化成 Full GC。
- 版本状态：JDK 9 废弃、14 移除。

**G1**：堆分 Region，逻辑上分代，停顿可预测。

- 停顿目标用 `MaxGCPauseMillis` 设；Mixed GC 优先回收价值最大的 Region。
- 无碎片，代价是复制和写屏障的开销。
- 版本状态：JDK 9+ 默认。

**ZGC**：着色指针＋读屏障，几乎所有阶段都并发。

- 停顿 <1ms、不随堆增长，适合超大堆低延迟。
- 代价是吞吐略低、有元数据开销。
- 版本状态：JDK 21 有分代 ZGC。

收尾给选型三句：要吞吐做批处理用 Parallel；中大型堆要控停顿用 G1；超大堆要亚毫秒用 ZGC。

## Q07：Java 中有哪些锁机制？

按维度分类讲，比干背名字清楚。

- 按乐观／悲观：乐观是 CAS＋版本号，悲观是 `synchronized`、`Lock`。
- 按是否阻塞：自旋锁 vs 重量级锁。
- 按可重入：`synchronized`、`ReentrantLock` 可重入。
- 按公平性：公平锁／非公平锁。
- 按读写：`ReentrantReadWriteLock`、`StampedLock`。
- 按协作工具：`Semaphore`、`CountDownLatch`。
- 按锁粒度与实现层面：偏向／轻量／重量，看的是对象头 Mark Word。
- 跨进程／分布式：还有 Redis 锁、ZooKeeper 锁。

再点明 `synchronized` 与 `Lock` 的取舍，落到 JUC-014 的“实现线程安全手段”。

## Q08：ReentrantLock 内部靠什么核心结构来保护共享资源？

核心是 **AQS（`AbstractQueuedSynchronizer`，队列同步器）**。它就是三样东西拼起来的：

- 一个 `volatile int state`：同步状态，重入计数或者读写许可都编码在这里面。
- 一个 CLH 双向 FIFO 等待队列：抢不到锁的线程排在这儿。
- CAS：改 `state` 用的原子操作。

加锁解锁的流程：

- 获取锁：用 CAS 改 `state`。成功了记下持有者线程，重入就是 `state++`。
- 获取失败：把自己封装成节点入队，然后 `park` 阻塞。
- 释放：改 `state`，再 `unpark` 队首的后继节点。

公平和非公平只差一步：公平锁获取时先判队列前面有没有前驱（`hasQueuedPredecessors`），非公平锁直接先抢一次。

`Condition` 的条件队列也是挂在 AQS 上的。

## Q09：怎么创建一个新线程，它的主要成本（资源消耗）有哪些？

创建方式有三种：继承 `Thread`、实现 `Runnable`／`Callable`、往线程池提交（生产首选）。底层都一样，是构造 `Thread` 再 `start()`。

主要成本四块：

- **线程栈**：每条线程一个，默认约 1MB，`-Xss` 可调，占的是虚拟内存；还有 JVM／OS 的 Thread 控制块。
- **系统调用**：要创建内核调度实体，涉及一次用户态／内核态切换。
- **调度与上下文切换**：寄存器、程序计数器、栈指针要保存恢复，还会冲击 CPU 缓存和 TLB（页表缓存）。
- **线程过多**：内存竞争，GC roots 扫描也变慢。

这正是“要用线程池复用、限制线程数”的原因。大量阻塞型任务可以考虑 JDK 21 的虚拟线程，少占一些载体线程。

## Q10：如何使用 Spring 控制事务？

两种方式：

- **声明式**：`@Transactional`。默认遇到 `RuntimeException`／`Error` 回滚，受检异常不回滚；可以用 `rollbackFor=Exception.class`、`propagation`、`isolation`、`timeout`、`readOnly` 调整。
- **编程式**：`TransactionTemplate`／`PlatformTransactionManager`，手动控制边界。

原理靠 AOP 代理，而 Spring 事务默认是线程绑定的。

`@Transactional` 失效的几种场景要能报出来：

- 方法自调用，没走代理。
- 方法不是 public。
- 异常被 catch 吞掉。
- 传播行为设置不当。
- 换到别的线程执行（见 Q11）。

## Q11：@Transactional 主方法里把其中一个 service 调用放到新线程执行，A、B 两张表还在同一事务吗？

**不在。** 关键在于事务跟线程绑定：

- Spring 的事务上下文绑在当前线程的 `ThreadLocal`（`TransactionSynchronizationManager`）上，连接也是从线程绑定的连接里取。
- 主方法 `method()` 开事务，`serviceB.updateB()` 用的就是这个事务连接。
- 把 `serviceA.updateA()` 丢进新线程之后，新线程的 `ThreadLocal` 是空的，拿不到原事务那个连接。
- 于是 `updateA` 要么以自动提交独立执行，要么自己开一个事务，**不会**随主事务一起回滚。
- 结果是原子性被破坏：主方法抛异常时，A 表不会回滚。

正确处理分几种情况：

- 确实需要并行：把它设计成**独立事务 + 补偿／对账**，接受最终一致。
- 或者在新线程内用编程式事务显式管理，并处理好失败。
- 不要假设有跨线程传播这回事。
- 要的是“异步但同事务”的语义，就在事务提交后再触发：`TransactionSynchronization.afterCommit`。

## Q12：如何保证缓存（Redis）与底层数据库之间的数据一致性？

先把预期摆正：没有绝对的强一致，做的是“尽量缩小不一致窗口＋最终一致”。

主流方案是 **Cache-Aside**：

- 读：先查缓存，未命中就回源并回填。
- 写：先更新并提交数据库，再删除缓存——注意是删除，不是更新缓存。
- 删失败：用重试、消息，或者 CDC（canal 订阅 binlog）兜底。

还有一个竞态：并发读写可能把旧值回填进缓存。四种缓解手段——key 版本号、短 TTL、延迟双删、条件写。

要点是承认一句：不管先更库还是先删缓存，都有窗口。靠 TTL 自然过期加对账去收敛，而不是追求零不一致。

## Q13：MySQL 是如何实现事务隔离性的？

InnoDB 用两件套：**锁 + MVCC**（多版本并发控制）。四种隔离级别——读未提交／读已提交／可重复读／串行化——就是靠它们组合实现的。

两者分工：

- 快照读：读已提交及以上用 MVCC，做到无锁、读到一致性视图。
- 当前读：`SELECT ... FOR UPDATE` 和更新语句，用行锁／间隙锁防幻读。

RR（可重复读）级别具体这么落地：

- 靠 MVCC，让事务内多次读都拿到同一份快照。
- 幻读再配合间隙锁来防。

最后补一句对应关系：脏读、不可重复读、幻读，分别对应不同级别要解决的问题。

## Q14：MVCC 是怎么实现的？

靠三样东西：**隐藏字段 + undo 版本链 + ReadView**。

- 隐藏字段：每行有 `trx_id`（最后修改它的事务号）和 `roll_pointer`（指向 undo log 里的上一版本）。
- 版本链：这些上一版本被 `roll_pointer` 一路串起来。
- ReadView：事务做快照读时生成，里面记着活跃事务列表、最小和最大事务号等。读的时候沿版本链从新到旧，找第一个对它“可见”的版本。

两个级别的差别就在 ReadView 建几次：

- 读已提交：每次查询都新建一个，所以能看到期间已提交的改动。
- 可重复读：只在事务第一次快照读时建一次并复用，所以前后读到的一样。

补一句边界：RR 下快照读能避开幻读，但当前读还是得靠间隙锁。

## Q15：不同进程之间有哪些数据传递方式？

先报方式：

- 管道：分匿名和命名两种。
- **消息队列**：System V 或者 POSIX mq。
- **共享内存**：最快，但要配信号量做同步。
- **信号**：异步通知，携带的信息很少。
- **Socket**：可以跨机器。本机用 Unix domain socket，走网络用 TCP／UDP。
- **文件**：间接共享。

选型看两点：数据量级、要不要跨机器。

- 本机传大块数据：共享内存；要通知就配信号量。
- 跨机器：Socket。
- 简单的父子进程：管道。

## Q16：I/O 的“零拷贝”技术指什么？

先看老路径：“读文件再发网络”要 4 次拷贝、2 次上下文切换：磁盘→内核页缓存→用户缓冲→socket 缓冲→网卡。

**零拷贝**要省的，就是用户态和内核态之间那几次冗余拷贝。三个手段：

- **`sendfile`**：数据在内核里直接从页缓存送到网卡，走 DMA 拷贝，CPU 不参与搬运。网卡支持 scatter-gather（分散／聚集式收集）时，还能省掉往 socket 缓冲拷贝那一次。
- **`mmap`+`write`**：把文件映射到用户空间，避免一次 read 拷贝。
- 还有 `splice`／`tee`。

典型应用：Kafka、Nginx、Netty 的 `FileRegion`。

收益两条：拷贝次数和上下文切换少了，CPU 与内存带宽的压力也降下来了。

## Q17：手撕：硬币找零（LeetCode 322 零钱兑换）

题目是求凑出金额 `amount` 所需的**最少硬币数**，凑不出来返回 -1。

做法是完全背包型的动态规划：

- 状态定义：`dp[j]` 表示凑出金额 j 的最少硬币数。
- 初始化：`dp[0]=0`，其余全设成 `amount+1`——这是不可达的哨兵，取一个比最大可能值更大的数就行。

```java
int coinChange(int[] coins, int amount) {
    int[] dp = new int[amount + 1];
    Arrays.fill(dp, amount + 1);
    dp[0] = 0;
    for (int j = 1; j <= amount; j++)
        for (int c : coins)
            if (c <= j) dp[j] = Math.min(dp[j], dp[j - c] + 1);
    return dp[amount] > amount ? -1 : dp[amount];
}
```

讲完代码要补的几个点：

- 循环顺序：外层遍历金额、内层遍历硬币。反过来也行，求最少数量时两种都可以。
- 转移方程：`dp[j]=min(dp[j], dp[j-c]+1)`。
- 判无解：最后 `dp[amount]>amount`，说明它压根没被更新过，返回 -1。
- 复杂度：时间 O(amount·coins)，空间 O(amount)。
- 为什么不用贪心：贪心不通用，面值不是规范体系时会算错，所以这题要用 DP。
