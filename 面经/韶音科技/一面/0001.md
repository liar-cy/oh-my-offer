## Q01：Agent 项目功能说明，中心调度 Agent 起什么作用？

### 面试回答

先一句话讲清产品做什么，再讲中心调度的职责：

- 项目功能：【一句话：面向谁的什么任务，端到端交付什么】。
- 中心调度 Agent 的作用：它是“总控”，负责意图理解与任务拆解、决定路由到哪个子 Agent／Skill、汇聚各步骤结果、控制循环与终止、异常时兜底或转人工。
- 好处：把“规划决策”收敛到一处，子模块只做各自专长、可独立演进；调度层统一管上下文和预算。

中心调度是多 Agent 架构里的 orchestrator 角色，本质是用一个决策中枢换取分工清晰与可控。

## Q02：Agent 有没有无法完成需求的情况？有没有做系统评测？

### 面试回答

- 无法完成的情况要如实说，典型四类：能力边界外（没接对应工具／知识）、多步任务陷入循环或无进展、依赖的外部数据缺失或不准、需要人工判断的高风险动作。
- 系统评测：要分能力评测和安全／鲁棒评测两层，用一套和调优数据隔离的评测集，看端到端任务成功率、各步通过率、失败归因分布、无进展率、越权率。
- 关键是“怎么发现它不行”：靠评测集 + 线上 badcase 归档，而不是凭感觉。

诚实承认边界＋给出你怎么量化这些边界，比吹“都能做”更可信。

## Q03：用一个实际例子讲完整的执行流程和每一步逻辑。

### 面试回答

挑一个真实 query，端到端走完并说每步的输入输出：

- 入口：用户 query → 意图识别／路由。
- 规划：中心调度拆出子任务、决定调用哪个 Skill／工具。
- 执行：调工具→拿到结果（观察）→回填上下文→决定下一步或收敛。
- 生成：汇总证据产出答案，带引用／状态。
- 终止：满足完成校验或达预算上限，触发兜底。

讲的时候点出“哪一步最容易出错、你怎么兜底”，比平铺直叙更能体现你真跑通过。项目实例按【真实例子】讲。

## Q04：项目底层模型怎么选的，选型考量是什么？

### 面试回答

选型按场景约束权衡，别只报模型名：

- 候选：【真实模型，如 DeepSeek／通义／GPT 类，或本地部署】。
- 考量维度：任务类型（抽取／生成／代码／推理）、中文与领域效果、上下文长度、时延、成本、是否要私有化／数据合规、函数调用与结构化输出能力。
- 做法：常见是“分层选型”——简单高频用小／快／便宜模型，复杂推理上强模型；再按评测集在效果与成本间定夺。

结论落到“我用评测数据选了它”，而不是“因为它最火”。

## Q05：项目做过模型微调／后训练吗？Prompt 怎么迭代优化、怎么验证效果？

### 面试回答

按【真实做过】分层答，没做过就说只调 Prompt：

- 微调：如果做了，说数据怎么构造、方法（如 LoRA）、和基线对比的效果；没做就明确“只做 Prompt 工程，未微调”，别混。
- Prompt 迭代：先固定一份评测集，改一版跑一次，按 badcase 归因针对性调整（澄清指令、加 few-shot 示例、拆步骤、加约束／输出格式），而不是凭手感改词。
- 验证效果：同一评测集上做 A/B 或前后对比，看关键指标（成功率／准确率／格式合规率）是否稳定提升，警惕在调优集上过拟合。

一句收口：优化要“改动—评测—归因”闭环，能报出数字口径。

## Q07：详细介绍整体架构、各模块和工作流程。

### 面试回答

用“分层”讲，别报流水账：

- 接入层：对话／API 入口，参数与权限校验。

## Q08：遇到现有 Skill 无法解决的问题，Agent 怎么处理？

### 面试回答

要有“无解兜底”，而不是硬套一个不对的 Skill：

- 先判定确无匹配：意图路由或 Skill 选择置信度低、或没有覆盖该场景的工具／知识。
- 兜底顺序：① 组合已有能力看能否近似解决；② 检索知识库尝试直接回答；③ 明确“当前不支持”，给出原因或替代建议；④ 需要时转人工或记录为待补能力。
- 别让它“幻觉式”地调一个不相干的 Skill 硬做——相似 Skill 误选本身就是这类坑（见 AGENT-015）。
- 沉淀：把“无法解决”的样本归档，反过来驱动补 Skill／补知识。

## Q09：大模型生成的内容如何与后续工具代码对接，怎么约束输出规范？

### 面试回答

核心一句：模型输出只当“意图／草稿”，落地靠代码层校验与结构化解析。

- 约束格式：让模型按固定 schema 输出（函数调用 JSON、字段化的结果结构），用受限解码／强制 JSON；字段带类型和必填约束。
- 代码层对接：解析输出→做 schema 与取值校验（类型、枚举、范围、越权）→映射到工具入参→执行；参数出错就回传错误让模型重填（见 Q08／AGENT-010）。
- 输出规范：给模板／few-shot 示例定样式，字段化而非自由文本，下游按字段取值，不做正则硬猜自然语言。
- 边界：模型只“提出”，执行、鉴权、幂等都在宿主侧。

## Q10：RAG 检索明明文档里有目标内容却召回失败，怎么一步步排查定位？

### 面试回答

按“数据在不在→切没切对→表征对不对→检得到吗→排得上吗”逐层排：

- 先确认内容真的已入库且生效：摄入链路有没有落、版本／权限／生效状态是否把它挡在外面。
- 看切块：目标是否被切断在两个 chunk、块太大稀释语义、表格／图是否被拆坏（见 RAG-010）。
- 看表征：embedding 模型是否匹配语言／领域，查询和文档用同一套编码；有没有用错模型或旧向量没重建。
- 看检索：query 与文档措辞的语义鸿沟（该上混合召回／查询改写）；相似度阈值是否太高、top-k 是否太小；metadata 过滤是否误把目标滤掉。
- 看排序：可能“检到了但排在 k 之外”，需要重排（见 RAG-009）。
- 定位手段：把“没检到”和“检到但排后面”分开统计，用同一评测集复现该 case，再对症修。

## Q11：三个模块分阶段开发，每个模块怎么做验证与效果评估，Bad case 怎么优化？

### 面试回答

讲“分模块各自可验收 + 端到端再合”：

- 每模块单独定验收标准：明确输入输出契约和指标（如检索模块看 Hit@k／Recall@k，生成模块看忠实度／格式合规率）。
- 先小评测集跑通单模块，再串起来测端到端成功率，避免问题混在一起说不清。
- Bad case 优化闭环：归档坏例→归因（数据／检索／生成／哪一步）→针对性改（补数据、调召回、改 Prompt）→回到评测集验证是否真的提升、有没有引入回归。
- 纪律：评测集与调优数据隔离，防过拟合；改一次测一次，不凭感觉。

## Q12：这个 Agent 是否已经落地使用？

### 面试回答

如实说现状，别把 demo 说成生产：

- 落地程度：【已上线给真实用户／内部试用／仍在 demo 或评测阶段】，说清用户规模和场景。
- 有落地就给可核实的信号：接入渠道、调用量、线上评测或反馈、稳定性。
- 没落地也如实讲：当前到哪个阶段、上线前还差什么（评测达标、成本、安全合规、审核链路）。

诚实分层比夸大更稳——面试官一追问线上数据就能验证。
