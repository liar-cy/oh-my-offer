## Q02：Java 面向对象的特性、在框架层面的应用；Spring 里哪些地方用到了这些特性？

### 面试回答

结论：特性是封装、继承、多态、抽象四件事；框架层的应用要逐个配真实例子讲，Spring 是最好素材库。

特性与含义（各一句）：

- 封装：访问控制＋不变量收口，对外只暴露必要方法。
- 继承：`extends`／`implements` 复用类型与实现，单继承多实现。
- 多态：同一调用不同行为；编译期重载、运行期按实际类型分派。
- 抽象：接口／抽象类隔离变化，面向接口编程。

Spring 里的落点：

- 封装：容器把对象创建与依赖装配封装起来（BeanDefinition／工厂），配置细节收在 `@Value`／`@ConfigurationProperties` 后面。
- 抽象：核心全是接口——`BeanFactory`、`ApplicationContext`、`BeanPostProcessor`、`HandlerAdapter`；实现可换（`XmlApplicationContext` vs `AnnotationConfigApplicationContext`）。
- 继承：模板方法大量使用——`AbstractApplicationContext#refresh` 定骨架、`JdbcTemplate`／`RestTemplate` 把“获取资源—执行—释放”固化，子类只填差异。
- 多态：`@Autowired` 注入接口可换实现；`HandlerMethodArgumentResolver`、`HttpMessageConverter` 按类型匹配多个实现逐个尝试。
- 配套：AOP 本身是“代理实现的多态”——调用方面向接口，运行期拿到的是增强后的代理对象。

## Q03：子类想访问父类的私有成员，有哪些方式？哪种方案更好？

### 面试回答

结论：能操作的有四种——父类开 getter／setter、把字段改 protected、反射强闯、内部类同顶层类特例；业务里首选 getter／setter，它保住了封装的收口位置。

- 方式一 父类提供访问方法：加 `protected` 或 `public` 的 getter／setter——字段仍 private，控制权在父类（可以只开读、可以校验后开写）。
- 方式二 字段放宽为 `protected`：子类直接访问；省方法但把“实现细节”固化进契约，父类改字段名就是破坏性变更。
- 方式三 反射：`Field.setAccessible(true)` 强改——能绕过编译检查；性能差、破坏封装、JDK 9 模块化后还可能被访问规则挡住。
- 方式四 结构特例：把子类写成父类的成员内部类（同一顶层类内 private 互通），属于语法巧合不是设计手段，别当方案推荐。
- 判断句：业务实现选方式一——“要不要暴露、暴露给谁、要不要校验”都由父类集中决定；框架级通用代码（序列化、ORM 字段映射）才会用方式三，并且会明确标注代价。
- 加分补一句：如果父类是你的代码且多个子类都要碰这个字段，说明“该字段对应的行为”也许应该下沉到父类方法里，而不是大家都在挪数据。

## Q04：谈谈你对 IOC 和 AOP 的理解

### 面试回答

结论：IoC 管“对象从哪来、怎么组装”，AOP 管“横切逻辑放到哪”——一个解对象图的耦，一个解业务代码被非业务逻辑污染。

- IoC：对象创建与依赖装配的控制权从业务代码移到容器，声明依赖即可，DI 是其落地手段；收益是可替换、可测试（注入 Mock）、生命周期统一。
- AOP：把事务、日志、鉴权这类“多处重复且与主流程无关”的逻辑抽成切面，运行期靠代理织入到方法调用的前后。
- 两者关联：AOP 建立在容器之上——Bean 初始化后由 `BeanPostProcessor` 返回代理对象，注入给别人的已经是增强版。
- 常见坑各报一个：IoC 侧是循环依赖（构造器注入无解，需改依赖方向）；AOP 侧是自调用不走代理（事务／切面失效）。
- 一句话收束：IoC 是“谁来 new”，AOP 是“谁来包一层”。

## Q05：AOP 有哪些注解？

### 面试回答

结论：AspectJ 注解族一个切面类加五个通知注解，Spring 侧还有 `@EnableAspectJAutoProxy` 与框架自带的“已组装切面”注解。

- 声明切面：`@Aspect`＋组件注解（`@Component`）进容器。
- 切点：`@Pointcut("execution(...)")` 定义可复用的切入点表达式。
- 通知五件套：`@Before`、`@AfterReturning`（`returning` 属性可接住返回值）、`@AfterThrowing`、`@After`、`@Around`（最强，环绕并决定目标方法是否执行，记耗时／重试都用它）。
- Spring 开关：`@EnableAspectJAutoProxy`（Boot 自动配好，proxyTargetClass 控制 CGLIB／JDK）。
- 框架自带切面注解：`@Transactional`、`@Cacheable`、`@Async`、`@SentinelResource`——本质都是“别人写好的切面”，同样吃“自调用失效”规则。

## Q06：HTTP/1.1 和 HTTP/2.0 有什么区别？HTTP/2.0 有哪些优势？

### 面试回答

结论：1.1 是文本协议、一条连接顺序处理请求（靠长连接复用但仍要排队）；2.0 改成二进制分帧，在一条 TCP 上多路并发，外加头部压缩与服务端推送。

- 传输格式：1.1 文本报文；2.0 二进制分帧层——帧→消息→流三级抽象。
- 多路复用：1.1 的 keep-alive 上请求仍按序应答，有应用层队头阻塞；2.0 每个 stream 独立收发，互不阻塞。
- 头部开销：1.1 每次重复 Cookie／UA 全量头；2.0 HPACK 动态表＋索引编码，重复头几乎为零。
- 服务端推送：2.0 可提前推资源（实践中因滥用基本被弃用，诚实提一句是加分）。
- 优先级与安全：stream 可带权重；浏览器实际只在 TLS 上用 h2。
- 遗留短板（高频追问）：多路复用救不了 TCP 层队头阻塞——丢一个包全部 stream 等重传，这是 HTTP/3 换 QUIC（UDP）的动因。

## Q07：谈谈 TCP 的三次握手和四次挥手

### 面试回答

结论：三次握手为“双方都确认收发能力＋同步初始序号”，两次不够是因为被动方无法向发起方证明自己能发；四次挥手因为全双工的两个方向要各自关。

- 握手：SYN(seq=x)→SYN+ACK(seq=y, ack=x+1)→ACK(ack=y+1)；每次 SYN 消耗一个序号，纯 ACK 不消耗。
- 为什么三次：两次时，历史迟到的 SYN 会让服务端凭空建半开连接；且服务端的初始序号没法被确认。
- 半连接防护：SYN cookie（追问高频）。
- 挥手：FIN→ACK→FIN→ACK；主动方最后进 TIME_WAIT，等 2MSL。
- 为什么四次：对方收到我的 FIN 后可能还有数据要发，ACK 与它的 FIN 分开发。
- 为什么不能等 CLOSE 直接关：迟到的 FIN／ACK 会扰乱下一个连接；TIME_WAIT 也保证最后一个 ACK 可达。
- 实战关联：短连接压垮服务端就是 TIME_WAIT 堆积——上长连接／连接池（与 HTTP keep-alive 呼应）。

## Q08：Redis 有哪些常用数据结构？分别应用于哪些场景？

### 面试回答

结论：五种基本型按“值的形状”记——String 单值、Hash 字段表、List 序列、Set 去重集、ZSet 带分数排序集，再各配一个场景。

- String：缓存对象序列化值、计数器（INCR 原子）、分布式锁（SET NX PX）、限流基元。
- Hash：存对象多字段（用户信息），可单字段读写、避免整对象重写。
- List：简单队列、消息列表（LPUSH＋RPOP／BRPOP），朋友圈时间线型“最近 N 条”。
- Set：交并差运算（共同好友、抽奖去重），SISMEMBER 做存在性判断。
- ZSet：排行榜（score 排序）、延迟队列（score 存到期时间戳）、带权重的去重队列。
- 进阶可提一句：bitmap（签到／活跃统计）、HyperLogLog（基数估算 UV）、GEO（附近的人）、Stream（简易消息流）。
- 加分口径：场景外各带一个坑——大 key 的集合类要 `SCAN` 分批、ZSet 元素过多跳表内存开销等（危害见 REDIS-009）。

## Q09：什么是缓存雪崩、缓存击穿、缓存穿透？对应的解决方案？

### 面试回答

结论：三者都是“请求没被缓存挡住、打到了数据库”，区别在原因——穿透查不到数据、击穿是单个热 key 过期、雪崩是大批 key 同时失效或缓存整体挂掉。

- 穿透（查不存在的数据，缓存里永远没有）：
  - 缓存空值／空对象（短 TTL）。
  - 布隆过滤器前置拦截“必定不存在”的 key。
  - 参数校验挡非法 ID。
- 击穿（热 key 到期瞬间并发全漏下去）：
  - 互斥重建（只放一个线程回源，其余等待或返回旧值）。
  - 逻辑过期不真删。
  - 热 key 提前刷新或多级缓存（本地挡一层）。
- 雪崩（大面积同时失效／Redis 宕机）：
  - TTL 加随机抖动错开过期。
  - 缓存高可用（哨兵／Cluster）。
  - 数据库侧限流＋熔断兜底，必要时返回降级页／本地缓存旧值。
- 记忆锚点：穿透“无此数据”、击穿“一点塌陷”、雪崩“全面塌陷”。
- 补一句布隆边界：BF 判“不存在”可信、“存在”有误判，不能做到 100% 拦截，删除也做不了（要支持删除用计数布隆，口径见 REDIS-002）。

## Q10：做题：原地重排链表，交换实际节点（1,2,3,4→1,4,2,3；1,2,3,4,5→1,5,2,4,3）

### 面试回答

结论：这就是 LeetCode 143 重排链表——快慢指针找中点、后半段原地反转、前后两段交错拼接，全程只动指针不改值，时间 O(n)、空间 O(1)。

- 规律先说清：输出顺序＝第 1 个、最后 1 个、第 2 个、倒数第 2 个……正是 L0→Ln→L1→Ln−1。
- 反例自证：题目强调“不能只改节点内部的值”——把值抄来抄去在链表节点携带外部引用（对象、位置）时是错的，必须搬节点。

```java
public void reorderList(ListNode head) {
    if (head == null || head.next == null) return;
    // 1) 快慢指针找中点（偶数取前中点，保证前半不短于后半）
    ListNode slow = head, fast = head;
    while (fast.next != null && fast.next.next != null) {
        slow = slow.next;
        fast = fast.next.next;
    }
    // 2) 反转后半段
    ListNode second = reverseList(slow.next);
    slow.next = null;
    // 3) 交错合并：前半一个、后半一个
    ListNode p = head;
    while (p != null && second != null) {
        ListNode n1 = p.next, n2 = second.next;
        p.next = second; second.next = n1;
        p = n1; second = n2;
    }
}

private ListNode reverseList(ListNode head) {
    ListNode prev = null, cur = head;
    while (cur != null) {
        ListNode nxt = cur.next;
        cur.next = prev; prev = cur; cur = nxt;
    }
    return prev;
}
```

- 边界自查：n=1／n=2 直接返回或等价成立；奇数长度最后一个节点落在前半末尾，`second` 先到 null，循环自然收口。
- 白板顺序口述“中点→反转→合并”再动笔，每步画 4 节点小例走一遍指针。

## Q11：MySQL 的存储引擎以及对应的索引结构

### 面试回答

结论：常用引擎是 InnoDB（默认）、MyISAM、Memory，冷门的 Archive／CSV／Blackhole 知道即可。索引结构主线是“B+ 树家族＋特殊成员”——InnoDB 聚簇＋二级 B+ 树、MyISAM 索引与数据分离、Memory 支持 HASH。

- InnoDB：B+ 树聚簇索引（主键）＋非主键二级索引（叶子存主键、查询回表）；另有自适应哈希索引（AHI）加速热点等值——内部优化，不是用户可指定的索引类型。
- MyISAM：索引与数据分离（非聚簇），.MYI 里也是 B+ 树、叶子存行地址；支持全文索引（早期形态）。
- Memory：哈希索引是其特色（等值 O(1)、不支持范围与排序），也建 B+ 树；数据在内存，重启即失。
- 机制一句：B+ 树适合磁盘——矮（三层两千万行）、叶子双向链表适合范围扫描；哈希快但没有区间与有序能力。
- 易错点：别说“InnoDB 有哈希索引供使用”（AHI 是引擎自动维护）；别把全文索引说成 MyISAM 专属（InnoDB 5.6 起也支持）。

## Q12：MySQL 的事务隔离级别

### 面试回答

结论：四个级别——读未提交、读已提交、可重复读（InnoDB 默认）、串行化，逐级消灭脏读、不可重复读、幻读。

- 脏读：读到别人未提交的数据。
- 不可重复读：重读时旧行的值被改过。
- 幻读：同一条件重读结果集行数变了（别人插／删了整行）。
- RU 几乎不用。
- RC 一条语句一个快照（Oracle 默认、互联网常用）。
- RR 事务内一致性读复用首次快照。
- InnoDB RR 防幻读两条路：快照读靠 MVCC 版本链；当前读靠 next-key lock（记录锁＋间隙锁）挡区间插入。
- 别说满：RR 下快照读与当前读交错的边角场景仍可能看到“幻影”，MVCC 与锁各管一条路径。
- 收尾实操句：选级别看“能否接受哪种异常＋并发代价”，一般默认 RR，高并发写冲突大的业务常降到 RC＋行模式 binlog，锁范围更小。
