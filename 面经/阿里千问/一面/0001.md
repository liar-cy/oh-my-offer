## Q01：你理解的 Agent 是什么？什么场景用 Agent、什么场景用固定 workflow？

### 面试回答

Agent 是“模型自己决定下一步做什么”的系统：给定目标，它在循环里自主规划、调用工具、读取结果、再决定下一步，直到达成目标或触发终止。

适合 Agent 的场景：

- 步骤无法提前穷举、要按中间结果动态决策（开放式问答、复杂检索、编码）。
- 任务有不确定性、需要自我纠错和重试。

适合固定 workflow 的场景：

- 流程稳定、可枚举、有明确分支——固定编排更快、更可控、更便宜、更好测。
- 一句话：能用 workflow 就别上 Agent；Agent 的自主性是用可靠性成本和延迟换来的，只在“路径真的不可预知”时才值。

## Q02：Agent 动态调用工具，如何解决模型幻觉？哪些做固定流程、哪些交给模型决策？

### 面试回答

幻觉的根子是自回归只优化“下一个 token 的概率”，目标里没有“真”，所以只能压低、不能归零。

治理分三层：

- 供给证据：先检索／查库拿到事实，再让模型“只依据给定证据作答并逐条引用”。
- 约束输出：结构化 schema、受限解码，工具参数要后端校验，缺参就追问而不是硬编。
- 事后校验＋兜底：后端核对结论是否被证据支持，低置信就拒答或转人工。

固定 vs 决策的分工原则：

- 交给固定流程：输入校验、权限与鉴权、参数合法性检查、结果格式校验、计费与预算控制、终止判定。
- 交给模型：意图理解、拆解与规划、选哪个工具、把观察转成下一步。
- 越靠近“事实、钱、写操作”的环节越要固定；越“理解与生成”的越可交给模型。

## Q03：Agent 循环怎么控制？有哪些终止条件（最大次数／目标校验／重复检测／人工介入）？

### 面试回答

不能只靠“模型说完成就完成”，要有显式的循环护栏：

- 最大循环次数／步数预算：硬上限，防无限循环烧钱。
- 目标完成校验：不只看模型自述，要有可判定的完成条件（产出通过校验、答案有证据、任务状态置位）。
- 重复调用检测：同一工具＋同一参数反复出现即判“原地打转”，触发提示或终止。
- 费用／时延预算：token 或墙钟时间超限就收口。
- 人工介入（HITL）：高风险动作或低置信时暂停，转人工确认后再继续。
- 兜底策略：达到上限仍未完成时，明确返回“部分完成／失败原因”，而不是硬编一个答案。

## Q04：LangChain 和 LangGraph 的区别？LangGraph 为什么适合循环和图流转？

### 面试回答

- LangChain：组件＋链式编排（LCEL）为主，本质偏“有向无环的一次性流水线”，擅长串模型、Prompt、工具、检索。
- LangGraph：把流程建成“带状态的图”——节点是步骤、边是流转（可含条件边和回边）、共享一个 state 对象。

LangGraph 为什么适合循环：

- 支持回边（cycle），能表达 ReAct 那种“思考→行动→观察→再思考”的往复，链式 DAG 做不了带回路的流程。
- 显式状态：每个节点读写同一个 state，循环里进度可累积、可判断是否继续。
- 内置 checkpoint／持久化，能暂停恢复、可加人工确认节点（interrupt），天然适配 HITL。
- 条件路由：按 state 决定下一个走哪个节点，比在链里塞 if 更清晰。

## Q05：完整的工具调用链路是怎样的？模型生成工具调用 JSON 之后代码层做什么？

### 面试回答

模型只“提出调用”，真正执行和鉴权都在宿主代码侧。链路：

- 把可用工具的 schema（名称、描述、参数）注入上下文 → 模型决定调用并输出结构化的“工具名＋参数 JSON”。
- 代码层拿到这个 JSON 后依次做：解析→参数 schema 校验（类型、必填、取值范围、越权）→按工具类型校验权限与危险操作→用调用 ID 关联请求→真正执行工具（本地函数或经 MCP Client 发 `tools/call`）→拿到结果。
- 结果处理：截断／结构化后作为“观察（observation）”回填进对话，再交回模型决定下一步。

强调一句：执行成功与否要校验，别把模型的调用意图当成事实直接跑。

## Q06：模型生成的工具参数出错怎么处理？

### 面试回答

参数出错是常态，要在“执行前”拦住，而不是报错给运行时：

- Schema 校验：类型／必填／枚举／范围不过 → 不执行。
- 分级处理：
  - 可自动纠正的（缺省值、明显格式问题）按规则补齐。
  - 缺关键信息就回一轮“追问”，把错误信息带回去让模型重填。
  - 实在不行才降级到默认值或人工。
- 把错误结构化回传给模型：告诉它“哪个字段、为什么不行”，通常重试一次就能修正。
- 边界：校验永远在宿主侧，模型输出不可信；危险操作即使参数合法也要二次确认。

## Q07：Agent 的边缘场景怎么考虑？

### 面试回答

按“输入侧、决策侧、执行侧、资源侧”扫一遍边界：

- 输入侧：歧义、缺参、超长上下文、prompt 注入（用户内容里藏指令）、多语言。
- 决策侧：幻觉调用不存在的工具、参数胡编、陷入重复动作、目标永远不达成、越权想做危险操作。
- 执行侧：工具超时／报错／返回脏数据、结果过大撑爆上下文、并发写冲突。
- 资源侧：token／费用／时延失控、限流。
- 通用对策：工具与参数白名单＋校验、无进展检测、预算上限、危险动作强制人工确认、异常与失败语义明确返回。

## Q08：工具调用错误怎么处理，重试策略怎么设计？

### 面试回答

先分错误类型，再决定要不要重试：

- 可重试（瞬时类）：网络抖动、超时、429／5xx——用指数退避＋随机抖动，设最大次数，超过就降级或失败。
- 不可重试（确定性类）：参数错、鉴权失败、权限不足——重试没意义，回去改参数或转人工。
- 幂等性是关键前提：非幂等工具（如下单、扣款）重试前先带幂等键，避免重复副作用。
- 兜底：失败要记录、可观测（哪一步、什么错），必要时切换备用工具或整体降级，别让 Agent 拿一个错误结果继续往下推。

## Q09：什么是 Skill？粒度怎么划分？怎么评价写得好坏、怎么评测效果？

### 面试回答

- 是什么：Skill 是把“某类任务的做法＋所需工具＋约束”打包成的可复用能力单元，让 Agent 按声明去选和调用。
- 粒度划分：以“一个可独立验收的任务”为界——太粗难复用易误选，太细调用链太长难维护；按用户意图边界切，一个 Skill 内工具协同、职责单一。
- 写得好坏的标准：描述准确可区分（减少相似 Skill 误选）、输入输出契约清晰、内部步骤确定可测、失败语义明确、不越权。
- 评测：建带标准动作／答案的评测集，测“选没选对该 Skill、执行结果对不对、失败率、被误选率”，再看线上反馈与 badcase 归因。

## Q10：什么是 Agent Harness，解决什么问题？

### 面试回答

Agent Harness 是包在模型外面那一层“运行框架／脚手架”——把不可靠、会出错、按量计费的模型，约束成一个能干活的系统。

它负责模型的“身体”，解决的是：

- 上下文管理：组装 system prompt、工具定义、历史与检索结果，控窗口和缓存。
- 循环编排：驱动“模型→工具→观察→再模型”的回合，管终止与预算。
- 工具执行与鉴权：解析、校验、执行、回填结果。
- 状态与记忆、观测与恢复、成本与延迟控制。

同一模型换个 Harness，实际表现可能差很多——工程能力大多体现在这层。

## Q11：Python 是静态还是动态语言？静动态的区别？类型转换方面呢？

### 面试回答

Python 是动态强类型语言。

- 静态 vs 动态：看类型检查发生在编译期还是运行期。静态（Java、C）编译时就确定并校验类型，写错类型编译不过；动态（Python、JS）变量运行时才绑定到带类型的对象，同一变量先后可指不同类型，错误要到运行时才暴露。
- “强／弱类型”是另一维度：讲会不会自动跨类型运算。Python 是动态但强类型（`"3"+5` 会报错，不像 JS 隐式拼接）。
- 类型转换：Python 是显式转换（`int("3")`、`str(5)`），不做隐式窄化；弱类型语言会暗地里自动转。Python 有类型注解（type hints），但默认只提示、不在运行时强制，需 mypy／pydantic 这类工具才生效。

补一句 Java 对照：Java 编译期静态类型、需要显式 cast、有自动装箱这类受控的隐式转换。
