## Q04：项目中 MD5＋盐主要解决什么问题？

### 面试回答

结论：解决“密码库泄露后批量还原明文”的问题，核心是挡彩虹表，不是挡爆破。

- 不加盐：所有人同密码同哈希，攻击者拿预计算表一查即中。
- 加盐（每人随机、随哈希一起存）：同密码产生不同哈希，彩虹表失效，攻击只能逐用户爆破。
- 要如实承认局限：MD5 太快，拿到库后 GPU 离线爆破成本仍然低；现代口径换慢哈希 BCrypt／Argon2id。
- 校验流程一句带过：取盐重算 `hash(输入＋盐)`，与存储哈希等时比较。

关联专题：[[专题题库/Web安全#WEBSEC-002：密码如何安全存储，常见方案有哪些问题？|WEBSEC-002：密码哈希存储与 MD5＋盐的局限]]

## Q05：当前的密码存储方式，拿到数据库权限能否破解出用户密码？

### 面试回答

结论：不能“还原”，但可以“爆破”——哈希单向，库盗了拿不回明文；能不能破取决于口令强度和哈希速度。

- 能做到的：拿到盐＋哈希后离线跑字典／GPU 穷举，MD5＋盐这类快哈希挡不住弱口令。
- 挡不住的三类：用户本来就用了常见弱口令（字典命中）、口令可猜测（手机号拼接）、彩虹表虽废但字典仍有效。
- 把成本抬上去的手段：慢哈希（BCrypt cost／Argon2id 内存硬）、登录限流与失败锁定、强度校验与泄露口令库检测、pepper／KMS。
- 收尾口径：我们项目【真实方案】；如果还是 MD5＋盐，说出迁移路径（DelegatingPasswordEncoder 按前缀渐进升级）比辩解加分。

### 面试回答

## Q07：Spring Session 中存储的是什么数据？

### 面试回答

结论：存的是服务端会话状态——Session 元数据＋属性集合，客户端 Cookie 里只有会话 ID。

- 元数据：session id、创建时间、最后访问时间、maxInactiveInterval（空闲超时）、principal name（登录用户标识）。
- 属性：`setAttribute` 进去的业务对象，典型是登录态用户信息、【购物车／向导步骤】这类跨请求状态。
- 用 Redis 做存储时对象要序列化，所以属性必须可序列化、体积要控制——Session 是热点小对象，不是存储池。
- 客户端定位：默认 `SESSION` Cookie 带 id，`SessionRepositoryFilter` 拦截请求换回 Session 对象；共享存储后任意实例都能处理同一会话。

## Q08：序列化的作用、二进制与 JSON 序列化的差异、发生在网络的哪一层

### 面试回答

三问一条线：

- 作用：把内存对象编码成可存储、可传输的字节形式；反序列化还原。跨进程传输、写缓存、落日志都靠它，顺带还能当深拷贝手段。
- 二进制 vs JSON：二进制（Java 原生／Protobuf／Hessian）体积小、解析快，但不可读、要靠 schema／约定对齐版本；JSON 可读、跨语言、调试友好，但体积大、数字精度与日期格式有坑。
- 场景分工：对外 HTTP 接口给前端 → JSON；内部 RPC／高频缓存 → Protobuf／Hessian 这类二进制；落库审计要人看 → JSON。
- 发生在哪一层：序列化是应用层（更准确说是应用进程内的事）；它产出的字节流才交给 TCP 按段传输。TCP 不关心你用什么编码，别说成“传输层做序列化”。

## Q09：项目中分段锁＋编程式事务是如何实现的？

### 面试回答

结论：按“库存分桶”场景讲——把一个热点行拆成 N 个小库存桶，请求按 key 路由到桶，桶级加锁只锁自己的桶；事务用 TransactionTemplate 编程式控制，边界压到一次 DB 更新以内。

- 分段锁：`ConcurrentHashMap` 思路的业务版——把 `stock` 一行拆成 `stock_bucket_0..N`，扣减先选有余量的桶；锁粒度从“全局一行”降到“一桶”，争用立刻下降。
- 编程式事务：`transactionTemplate.execute(...)` 包住“扣桶库存＋写流水”，替代大 `@Transactional`——事务里不再有 RPC／发 MQ／缓存更新，锁持有时间可测。
- 两者配合的要点：事务只覆盖单桶的 DB 写；跨桶汇总、发通知放事务外，失败靠补偿。
- 若原题其实问 ConcurrentHashMap 的“分段锁”：JDK 7 是 Segment 锁、JDK 8 起已是 CAS＋桶头节点 synchronized，别说回分段锁。

## Q10：ConcurrentHashMap 在项目中如何使用？key 和 value 存什么？

### 面试回答

结论：报一个真实用途＋key／value 的具体内容，别停在“线程安全的 Map”。

- 常见形态一：本地缓存／计数聚合——key【商品 ID／接口名】，value【缓存对象／AtomicLong 计数】，配合定期落 Redis 或 DB。
- 常见形态二：任务状态表——key【任务 ID】，value【Future／状态对象】，多线程提交与收割共用一份。
- 用法红线：`get` 后再 `put` 仍会丢更新，判空写入用 `computeIfAbsent`／`putIfAbsent`。
- value 指向的对象本身不因此线程安全——往里放 ArrayList 照样要防并发修改。

## Q12：Sentinel 有哪些限流方式？区别和使用场景？

### 面试回答

结论：Sentinel 限流按“统计口径 × 流控效果 × 流控模式”三个维度组合，不是并列的几种算法。

- 统计口径：QPS 限流（默认）与并发线程数限流；线程数适合慢依赖保护，QPS 适合入口流量控制。
- 流控效果三选一：快速失败（默认，普通接口）、Warm Up 预热（冷启动，缓存／连接未就绪场景）、排队等待（漏桶整形，适合脉冲流量、下游可缓冲的秒杀削峰）。
- 流控模式：直接（拦本资源）、关联（保护下游：下游饱和限上游）、链路（只限入口调用路径）。
- 与 Redis 限流的区别：Sentinel 单机默认独立计数，集群限流要接 token server；网关／分布式场景才需要全局配额（对照 REDIS-004 的窗口／令牌桶实现）。

## Q13：Sentinel 底层的实现原理

### 面试回答

结论：一条“滑动窗口统计 → 责任链槽位 → 规则判定”的流水线。

- 统计：LeapArray 滑动窗口把 1 秒切成若干 sample 桶（`windowIntervalMs`／`sampleCount` 可配），QPS、RT、异常数都从桶里聚合，解决固定窗口的突刺问题。
- 责任链：资源调用穿过 NodeSelectorSlot（调用树）→ ClusterBuilderSlot（按资源聚合）→ StatisticSlot（统计）→ 流控／系统规则槽位，链由 `SlotChain` 装配。
- 判定：DefaultController 拿当前窗口值与阈值比较（直接拒绝／预热／排队三种效果在 `controlBehavior` 里分支）；熔断降级按慢调用比例、异常比例、异常数三种策略，进入半开探测恢复。
- 数据出口：指标留在客户端内存，Dashboard 通过 HTTP API（默认命令端口 8719）拉取；客户端定时心跳向 Dashboard 注册。

## Q14：购物车多商品参加满减与满折活动，如何展示最优价格？

### 面试回答

结论：这是“凑单最优化”问题，没有免费午餐——按商品数规模选“枚举组合／贪心近似／动态规划精确”三档，线上口径是预计算＋缓存。

- 先立模型：购物车 N 个商品、每个可选参与满减档或折扣活动，求“用户实付最低”；本质是带约束的组合优化。
- 小 N（≤10）：直接枚举活动组合逐个试算取最优，简单可靠。

## Q15：Nacos 服务注册、服务发现的原理

### 面试回答

结论：注册是“实例上报＋服务端健康维护”，发现是“订阅＋变更推送”，一致性按实例类型分 AP／CP。

- 注册：临时实例启动后调注册接口上报元数据，之后每 5 秒左右发一次心跳（beat）；15 秒无心跳标不健康，30 秒无心跳剔除。
- 发现：消费方按服务名订阅，本地缓存实例列表，服务端变更时推送（UDP／长轮询类机制），调用方负载均衡选实例。
- 一致性：临时实例走 AP 的 Distro 协议（各节点各自可写、异步复制，短暂读到旧列表可接受）；持久实例服务端主动探活（TCP／HTTP 探测），元数据走 CP 的 JRaft／Raft 系协议。
- 对比一句话：Eureka 同为 AP；ZooKeeper 是 CP——网络分区时 ZK 宁可不可写也不给旧列表，Nacos 让注册发现优先可读。

## Q16：线程池有哪些核心参数？每个参数的作用？

### 面试回答

## Q17：ThreadLocal 主要做什么？跨线程传递 ThreadLocal 有哪些方法？

### 面试回答

结论：给每个线程一份独立变量副本，放线程内上下文（用户身份、traceId、数据库连接、格式化器）；跨线程传递靠三条路——继承、显式搬运、包装器。

- 隔离语义：值存在每个 Thread 的 ThreadLocalMap 里，槽位隔离但对象本身不线程安全。
- `InheritableThreadLocal`：创建子线程时复制父线程的值——只覆盖“new Thread”场景，线程池复用线程时拿不到提交时上下文。
- 线程池正确做法：提交任务前手动捕获上下文、任务内回放；或直接用 TransmittableThreadLocal（阿里 TTL，配合 `TtlExecutors`／`TtlRunnable` 包装，提交时快照、执行时回放）。
- 收尾一句纪律：用完 `finally` 里 `remove()`，池化线程不删就是下一个请求的脏上下文。

## Q18：volatile 有什么作用？原理是什么？

### 面试回答

结论：管两件事——共享变量的可见性和相应的有序性；不管原子复合操作。

- 语义一句话：对某 volatile 变量的写 happens-before 后续对它的读；适合发布状态标志、发布不可变快照引用。
- 原理：写时经缓存一致性协议让其他核的副本失效，同时编译器插内存屏障（写前 StoreStore、写后 LoadStore／StoreLoad 等）禁止重排序；x86 上前三类基本免费，StoreLoad 用 `mfence`／lock 前缀指令补。
- 边界背清：`volatile int a; a++` 依然线程安全不了——读—改—写三步可以被交错，更新丢失；要原子用 AtomicInteger（CAS）或加锁。
- 修饰引用只保证“引用本身”可见，指向对象内部的修改不因此安全。

## Q19：TCP 和 UDP 的区别，以及各自的使用场景

### 面试回答

结论：TCP 面向连接、可靠、字节流；UDP 无连接、不保证到达、按报文收发——要“不丢不乱”选 TCP，要“低延迟可容忍丢”选 UDP。

- 连接：TCP 三次握手建连再传；UDP 拿到地址就发，没有连接状态。
- 可靠性：TCP 靠序号、确认、超时重传、流量与拥塞控制兜住；UDP 全部交给应用层自己定。
- 形态与开销：TCP 头 20 字节起、有队头阻塞；UDP 头仅 8 字节、无重传缓冲，延迟更平。
- 场景：HTTP／文件／支付用 TCP；DNS、直播、语音、游戏状态同步、QUIC（UDP 上重建可靠语义）用 UDP。

## Q20：TCP 挥手为什么要四次？两次和三次分别会有什么问题？

### 面试回答

结论：因为关闭是两方向独立的——“我发完了”（FIN）和“我收到了你的结束”（ACK）语义不同，压不成三次是设计使然。

- 序列：A 发 FIN → B 回 ACK →（B 可能还有数据要发）→ B 发 FIN → A 回 ACK，进入 TIME_WAIT。
- 两次的问题：若 B 把 ACK 和 FIN 合并立即关，B 的半发送通道被提前掐断，后发数据丢失，A 也无从确认。
- 三次的问题：只有当 B 的 ACK 与 FIN 恰好同时具备时才合并；不能假设总是如此。
- 被动方的 CLOSE_WAIT 堆积说明应用没调 close；主动方 2MSL 的 TIME_WAIT 保证最后 ACK 可重传并隔离旧报文。

## Q21：HTTP/1.0、HTTP/1.1、HTTP/2.0 版本的差异

### 面试回答

结论：演进主线是“复用连接 → 消应用层队头阻塞 → 多路复用与头部压缩”。

- 1.0：默认每请求一条连接；1.1：持久连接（keep-alive）＋管道化＋分块传输＋更丰富的缓存控制（`Cache-Control` 等）。
- 1.1 的天花板：管道化响应乱序即堵、浏览器靠开 6 条并发连接硬扛，仍有 TCP 层队头阻塞。
- 2.0：二进制分帧＋同一连接多路复用（流粒度交错）、HPACK 头部压缩、服务端推送；解决应用层队头阻塞，但 TCP 丢包仍会卡住所有流。
- 顺一句 3.0 加分：QUIC over UDP，传输层重建可靠与多流独立，消掉 TCP 层队头阻塞并加速握手。

## Q22：浏览器键入 URL 按下回车后的执行链路

### 面试回答

结论：按“URL 解析 → DNS → 建连（TCP＋TLS）→ HTTP 请求 → 服务端处理 → 响应 → 渲染”七段讲，每段准备一个追问点。

- URL 解析与缓存检查：先查浏览器缓存／Service Worker，未命中才走网络。

- 渲染：解析 HTML 建 DOM、CSS 建 CSSOM，布局绘制；期间继续拉子资源。
- 收口：这题考的是链路完整度，不是背诵深度——挑【DNS 迭代递归／TLS 验证／TIME_WAIT】一个点主动讲深。
