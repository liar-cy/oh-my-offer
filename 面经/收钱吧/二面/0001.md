## Q04：如何设计 WebSocket 实现多人同时编辑？

### 面试回答

结论：WebSocket 只做通道，协作正确性靠“服务端定序＋操作变换”——核心是选 OT 还是 CRDT，不是连接本身。

- 连接层：每人一条 WS 双向通道，服务端维护房间（文档 ID → 连接集合），广播增量操作而非全文档。
- 定序层：所有写操作经过服务端串行定序（单文档单写队列＋单调版本号），再广播给其他人。
- 合并层：并发编辑两个主流——OT（中心服务器变换操作偏移量，需权威服务端）或 CRDT（操作可交换收敛，去中心但元数据膨胀）；表格类也可按单元格粒度做 last-write-wins 降复杂度。
- 可靠性：断线重连后按“已应用版本”补拉增量或快照重建；心跳保活与鉴权刷新都得自己设计。

## Q05：WebSocket 的底层原理与连接建立过程

### 面试回答

结论：起点是 HTTP、终点是独立的全双工帧协议—— Upgrade 握手后脱离 HTTP 语义。

- 握手：客户端发 `Upgrade: websocket`＋`Connection: Upgrade`＋随机 `Sec-WebSocket-Key`；服务端接受后回 101 Switching Protocols＋`Sec-WebSocket-Accept`（key 拼固定 GUID 做 SHA-1），此后这条 TCP 连接改跑 WS 帧。
- 帧结构：opcode 区分文本／二进制／ping／pong／close 帧，客户端→服务端帧必须掩码（防代理缓存与注入），服务端下行不掩码；分片帧支持大消息。
- 保活与关闭：ping／pong 心跳探测半开连接；关闭走 close 帧四次语义（发起→回→关），否则中间层闲置超时先掐。
- 与 Socket 的关系：WebSocket 是应用层消息协议，跑在 TCP 之上；Socket 是 OS 传输层 API 抽象，两者不同层，别混。

## Q06：如何保证多人扩图操作的顺序性？

### 面试回答

结论：把“顺序”定义清楚再给机制——要的是“服务端执行顺序=全局事实顺序”，做法是单写队列定序＋单调版本号，客户端按版本应用。

- 每个文档／画布一个串行写通道：服务端把并发操作排队，赋单调递增版本号后落库并广播。
- 接收端规则：`v ≤ 已应用版本` 丢弃（重复或过期）、`v == 已应用+1` 顺序应用、出现缺口回源补拉（见 SYS-030 的版本号回放）。
- 冲突语义：位置相关的操作（如画布元素偏移）在定序后做 OT 变换，或改用可交换的 CRDT 让顺序不敏感。
- 若是消息队列形态：按业务键（文档 ID）路由到同一分区／队列保序，不同文档并行不互等。

## Q07：基于事件驱动的广播，如何保证 C 收到的顺序是“先 A 后 B”？

### 面试回答

结论：事件广播天然不保序，想要“先 A 后 B”只有两条正路——发送前集中定序，或接收后按序重放；靠“发消息快一点”解决不了。

- 根因：A、B 两条链路各自异步，MQ 多分区／多消费者并发处理，到达顺序与发生顺序无关。
- 定序方案：同一实体的事件带单调序号（版本号／序列号），广播前由单点（按实体分区的串行消费者）定序；C 端缓存乱序事件，缺号就先拉补偿或等待，不能先应用后改。
- 兜底方案：接受到达乱序、保证收敛——事件可交换（CRDT）或幂等＋最终状态对账，按“最终一致”承诺而不是“顺序一致”。
- 别说“用 RabbitMQ 就能保序”：队列只保证单队列投递顺序，并发消费就会打乱（二面 Q11 同一考点）。

## Q09：什么是倒排索引，怎么理解？

### 面试回答

结论：正排是“文档 → 词”，倒排是“词 → 文档列表”——把“查哪些文档包含这个词”从扫全表变成查字典。

- 结构：词典（term 有序）＋ postings 倒排列表（doc ID 列表，带词频／位置），列表间求交集用跳表加速多条件查询。
- 写入代价：文档更新要重建其涉及 term 的 posting，所以近实时（refresh）而非实时。
- 为什么快：term 有序可二分＋前缀检索；posting 可压缩（delta 编码）省 IO。
- 类比一句：像书末尾的“术语→页码”索引，按页找词是正排，按词找页是倒排。

## Q10：项目中用 RabbitMQ 给 ES 和 MySQL 做数据同步怎么实现？有无更好办法？

### 面试回答

结论：业务双写发 MQ 可行但侵入大；更好的默认选项是 Canal 订阅 binlog——不依赖每个写入口都记得发消息。

- 现实现：更新 MySQL 的同一事务里写本地消息表，事务提交后投递 MQ，消费端写 ES（删除／更新按 doc id 幂等）。
- 双写的死穴：漏一个写入口就永久不一致；库写成功、消息失败的窗口要补偿任务兜底。
- 替代方案：Canal 伪装从库读 binlog → 投 MQ → 消费写 ES，业务零改动、不漏变更（见 SYS-044 的选型与量化对比）。
- 无论哪条链路都配：全量重建工具＋定时对账，不一致能修复才算闭环。

## Q11：增删改各建一个队列让 ES 消费，如何保证消费顺序与执行顺序一致？

### 面试回答

结论：保证不了——按操作类型拆队列从根上就错了，同一条数据的变更必须进同一个有序通道。

- 错因：增、删、改三条队列各自独立消费，MySQL 里“先增后删”到 ES 可能“先删后增”，最终多出一条幽灵文档。
- 正确做法：按实体主键（doc id）做队列选择器，同一实体的所有变更路由到同一队列、单消费者串行消费；不同实体并行，吞吐不受损。
- 版本兜底：消息带单调版本号／binlog 位点，消费端拒绝旧版本覆盖新版本（external version）。
- 收尾一句：MQ 只能提供“单队列单消费者”的偏序保序；跨实体本来就不需要顺序，别为全局顺序牺牲并发。

## Q13：RabbitMQ 有哪些交换机？

### 面试回答

结论：四种类型＋一个默认——direct、topic、fanout、headers，外加开箱即用的 default（无名 direct）。

- direct：routing key 精确匹配，适合按业务类型点对点路由。
- topic：通配符匹配（`*` 一段、`#` 多段），最常用，适合按层级 key 分发。
- fanout：忽略 key 广播到所有绑定队列，适合失效通知、配置刷新这类一对多。
- headers：按消息头属性匹配，性能差、用得少；RabbitMQ 还有基于 fanout 机制的 consistent hash 与 DLX（死信交换机）等特殊用法。
- 项目落点：我们路由用【topic】、失效广播用【fanout／Redis pub-sub】——报一个真实用例比报全清单强。

## Q14：项目中用 Seata 解决分布式事务，采用的是哪种事务模式？它如何保证原子性和一致性？

### 面试回答

结论：按项目真实模式答，最常见是 AT——自动两阶段＋undo log 补偿，业务无侵入。

- 三个角色：TC 事务协调者（独立 server 管全局事务），TM 事务管理者（`@GlobalTransactional` 发起方），RM 资源管理者（每个分支数据源代理）。
- 一阶段：拦截 SQL 记录前镜像／后镜像，与业务写同一本地事务提交 undo_log，拿到全局锁后直接提交本地事务、释放行锁——这是 AT 性能好的关键。
- 二阶段：全局提交只异步清 undo_log（近似“已提交，等回收”）；全局回滚用前镜像反向补偿，回滚前先做脏写校验（后镜像对不上就人工介入）。
- 如实说代价：全局锁在热点行上会退化成瓶颈；默认隔离下全局视角有脏读，要强读已提交得 `select for update` 走代理。

## Q15：用 Sentinel 限流后，如何观测资源是否被限流或熔断？

### 面试回答

结论：三个观察面——Dashboard 实时指标、被拒异常与日志、自己的 Metrics 出口。

- Dashboard：簇点链路看每个资源的通过 QPS、拒绝 QPS、平均 RT、异常数；实时监控曲线看秒级抖动；限流与熔断各有独立的通过／拒绝计数。

## Q16：限流熔断产生的数据如何传给 Dashboard？为什么控制台能看到统计值？

### 面试回答

结论：Dashboard 主动拉、客户端不推指标——客户端把统计留在内存滚动窗口里，Dashboard 通过 HTTP API 定时取。

- 注册：客户端启动后向 Dashboard 发心跳（transport 配置，默认命令端口 8719），Dashboard 因此“看得见”应用。
- 拉取：控制台页面轮询客户端 `/metric.json` 等 API，取最近 1 分钟（10 秒粒度）与历史聚合的窗口统计——所以看到的是滑动窗口聚合值，不是逐条流水。
- 数据从哪来：StatisticSlot 在调用链上实时写 LeapArray 滑动窗口桶（pass／exception／block／RT），拉取时按桶聚合。
- 延伸点：控制台规则改动会下发到客户端（也走该 HTTP 通道）；生产要做持久化监控得自建 Prometheus 方案，Dashboard 默认无存储。

## Q17：Java 有哪些默认的内置类加载器？

### 面试回答

结论：按口径报三或四个——JDK 9 起是启动、平台、应用三个内置加载器。

- Bootstrap（启动类加载器）：C++ 实现，加载 `java.base` 等核心模块，Java 里表现为 null。
- Platform（平台类加载器，JDK 9 新增）：加载 `java.sql`、`java.xml` 等平台模块（JDK 8 及以前的 Ext 扩展加载器已被取代）。
- Application（系统类加载器）：加载 classpath／模块路径上的应用类，`main` 从这里开始。
- 再补一层：要加载第三方隔离类还有自定义加载器／线程上下文加载器（Tomcat、SPI、热部署都靠它），一句带出下一问。

## Q18：为什么 Java 要引入双亲委派模型？哪些场景会打破它？

### 面试回答

结论：两个理由——核心类安全（应用伪造 `java.lang.String` 也轮不到被加载）＋类身份唯一（同 ClassLoader 树内一个类只加载一次，类型系统才成立）。

- 机制回顾：每层加载器先委托父级尝试，父级加载不了才自己加载；委派范围由父级的搜索路径决定。
- 打破场景一 SPI：DriverManager 等核心代码要加载 classpath 上的第三方实现——父加载器“求助”线程上下文类加载器反向委派。
- 打破场景二 模块化／热部署：OSGi 网状委派、Tomcat 每 webapp 独立加载器（优先自己加载）、Agent 字节码增强都要自定义策略。
- 说“打破”前先给定义：这些是有意的层级反转／隔离设计，不是模型缺陷；症状是同名类 ClassCastException、instanceof 为 false。
