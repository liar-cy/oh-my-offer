## Q01：专业是电子信息工程，Java 是怎么学的？

### 面试回答

结论先行：Java 是自学成才，路径是“语法基础→后端栈→项目实战→查漏补缺”，每一步都拿得出证据。

- 语言基础：通过【书／课程名】自学语法与面向对象，同步补数据结构、多线程等基础。
- 后端栈：学 Spring／Spring Boot、MyBatis、MySQL、Redis，目标是能独立搭出一个 CRUD 服务。
- 项目实战：做【项目名】把学的东西串成一条完整链路；项目暴露的缺口再回到文档和源码去补。
- 学习方法：面对陌生技术先看它解决什么问题，再跑最小示例，最后读关键源码路径；这条路径换任何语言都适用。
- 跨专业动机一句话带过：电子信息课程偏【硬件／信号】，实践后确认对软件开发兴趣更大、反馈更快，于是把自学重心放到 Java 后端。

别说“看了几个视频”。要用能跑的项目和读过的源码证明学习闭环成立。

## Q03：由 Skill 演进到 LangGraph 编排的工作流，其中的技术挑战

必要上下文：原文写“由 skill 演进到 LangGraph 编排的工作流”。Skill 与 Workflow 不是进化两端，而是同一任务的两种承载；本题按“把流程做成图编排”这一口径讲工程挑战。

### 面试回答

结论：难点不在换框架，而在把“提示里隐含的流程”显式化成可编排、可恢复、可观测的工程。

- 原形态与动机：【原来的 Skill 是一段提示／脚本／工具链，为什么改用 LangGraph——多半是流程变长、出现循环、分支或人工确认】按项目填。
- 状态管理：共享 State 承载中间产物，要设计 schema 与字段累积策略，别让消息无限膨胀。
- 流程控制显式化：分支、循环、条件路由、终止条件改成节点和边，不再靠硬编码 if-else；循环要设上限。
- 中断与恢复：checkpoint 落执行进度，可暂停可续跑；有副作用的节点要配幂等，恢复不等于外部调用天然只执行一次。
- 人机协同与汇合：人工审批节点、并行分支的汇合与超时，都要在图里显式建模。
- 可观测与评测：每个节点看得到输入／输出／耗时；用同一任务集对比改造前后的成功率、时延和维护成本。
- 边界：若只是“一次检索＋一次生成”、分支也少而稳定，函数组合更好维护，不必为上图而上图。

## Q04：知识库为什么按文档、章节、页面三级组织？

必要上下文：原文“为什么选用文档，结构，页面这三级”，其中“结构”按“章节／结构单元”理解，需按原题确认。本题答分级切块与分级检索的设计理由。

### 面试回答

结论：三级是一套由粗到细的索引层级，用“细单位精准召回、粗单位补全上下文”这对矛盾来组织检索。

- 单一块大小满足不了两头：块太小切断语义，块太大稀释相关性、还占满上下文窗口。
- 层级对齐文档天然结构：
  - 页面／段落是最小检索单位，命中更准。
  - 章节承载子话题与段落级语义，给命中片段补上下文。
  - 文档承载全局背景与元数据（标题／来源／时间／权限），用于过滤、去重和溯源。
- 支持分级检索：先用文档／章节的摘要缩小范围，再下钻到页面级细节，对“全局型、总结型”问题命中更好，也更省 token。
- 落地形态：父子块（命中子块回取父块）和分层摘要最常用。
- 代价要讲：三级等于三套索引，更新一致性更难（删文档要三级一起清）；短文档没必要硬上三级。

## Q05：关键词检索和向量检索各自擅长什么？

### 面试回答

结论：关键词检索擅长词面精确匹配，向量检索擅长语义泛化，两者互补，生产上常用混合召回。

- 关键词（倒排＋BM25）擅长的：
  - 专有名词、型号、单号、代码、稀有词、精确短语。
  - 靠词面命中，IDF 权重给稀有词，命中准。
  - 短板：同义改写、换个说法就问不到。
- 向量（embedding）擅长的：
  - 同义改写、口语问法匹配书面文档、跨语言。
  - 靠语义相似，能召回字面不同但意思近的片段。
  - 短板：精确稀有词、编号与数字易被淹没，可解释性弱。
- 怎么配合：两路各自召回再做分数融合（RRF／加权），再重排；关键词补精确、向量补泛化。

## Q06：过滤了 43.5% 的无效图片，这个数字怎么验证？有没有自动核对方法？

必要上下文：“无效图片”的定义与 43.5% 的统计范围属项目事实，用【】填；下面是通用的口径与自动核对设计，不表示原项目已实现。

### 面试回答

结论：先报口径再报数，验证靠“分层抽样＋人工标注算误杀率”，自动化靠“金标集回归＋规则与模型双路比对”。

- 数字口径（先说清才能被追问不倒）：
  - 43.5% = 被过滤图片数 ÷ 过滤前图片总数，样本量与时间范围是【____】。
  - “无效”的定义是【纯装饰／无正文／重复图／OCR 置信度过低等，按实际口径】。
- 怎么验证：
  - 分层抽样人工标注，算过滤的查准率（误杀多少有效图）和查全率（漏了多少无效图）。
  - 报数时同时给指标名、样本量和分母，不只丢一个 43.5%。
- 自动核对方法：
  - 金标集回归：固定一份人工标注样本，管线每次改动自动跑查准／查全，防止误杀悄悄升高。
  - 规则与模型双路：两条各自判定，比对不一致的样本送人工复核。
  - 上线抽检：每批随机抽样人工核验，把误杀率做成持续监控指标。
  - 前后对照：比较清洗前后的检索表现和答案质量，证明过滤确实有正收益。
- 诚实边界：如果只统计了数量、没做误杀率评估，就直说没做，别编指标。

## Q07：Trading Agent 的 12 类节点怎么理解？外部工具调用指什么？工具调用超时怎么办？

必要上下文：12 类节点的具体清单、工具列表与超时处理属项目事实，用【】填。

### 面试回答

- 12 类节点怎么理解：
  - 先讲划分原则：一个节点只做一件事（数据获取、信号计算、风控、下单、执行、复盘等），“12 类”是职责枚举，不是话术。
  - 分组讲更稳：【按 感知／决策／执行／风控／汇总 分组，说清每组节点】，别硬背十二个名字。
  - 记不全就说“大约十二类职责，按……归类”，不编名称。
- 外部工具调用指什么：
  - 图内节点调用的模型之外能力：【行情接口、下单 API、数据库、大模型推理、消息推送等】。
  - 链路要切开：模型只产出“调用意图（函数名＋参数）”，执行层负责参数校验、鉴权、执行、结果检查，再把结构化成功／错误回传模型。
  - 别背错：模型生成了一个调用，不等于它已经执行了；副作用发生在执行层。
- 工具调用超时怎么办（金融交易场景更要小心）：
  - 超时不等于没生效，写操作（下单）尤其不能直接当失败重发。
  - 先查状态：用订单号／请求 ID 回查“到底执行了没”，再决定重试、补偿还是标记失败。
  - 幂等＋退避：写操作带幂等键，同一键不重复生效；查询类用退避重试、超时上限、熔断降级。
  - 错误向上传：把超时作为结构化错误反馈给上层节点／模型重新决策，不静默吞掉。

## Q08：怎么保证信息可靠传输？为什么记录消息和发送消息要记在一个事务里？

### 面试回答

结论：用事务性 outbox（发件箱／本地消息表）——在同一本地事务里写业务数据＋“要发的消息”，再由异步投递器重复发送直到确认；可靠传输靠“本地原子写入＋最终投递＋消费幂等”，不是跨系统的瞬时强一致。

- 为什么要记在同一个事务里：
  - 要防的是两种“半成功”：业务写成功但消息没发（丢消息），或消息发了但业务回滚（脏消息）。
  - 本地事务能保证“业务数据＋outbox 记录”原子落库；但 MQ 发送参与不了本地事务，数据库和 broker 组不成一次原子提交。
  - 所以把原子动作做小：事务里只做“可靠记录”，发送交给事务外的投递器保证最终送达。
- 投递怎么可靠：
  - 投递器扫未发送记录→发送→等 publisher confirm→标记已发；确认丢失或崩溃就重发，因而必然会产生重复。
  - 消息要带稳定业务 ID，消费端幂等是这套方案的硬前提。
- 项目实现【按实际填：RocketMQ 事务消息／自研 outbox／Seata 等】。

## Q09：出现重复消费怎么解决？中间过程已受影响怎么办？除了回滚还有正向方法吗？

### 面试回答

结论：MQ 是 at-least-once，重复无法根除，解法是消费端幂等；“中间过程已有副作用”的关键是让每一步幂等并记录进度，靠正向推进而不是回滚。

- 重复从哪来：手动 ack 下，处理完但 ack 没送达就掉线，消息会重投——这是“至少一次”的设计结果，不是 bug。
- 常规幂等三档（按可靠性排）：
  - 数据库唯一约束：业务键唯一索引，插入冲突即视为已处理。
  - 状态机条件更新：`UPDATE ... WHERE status=前态`，影响行数 0 说明处理过。
  - 消费记录表：`（消费者, 业务键）` 唯一索引，与业务写入同一事务。
- 中间过程已部分生效（半成功）怎么办：
  - 不要只在入口判一次重，要按“步骤＋幂等键”记进度；重投时跳过已完成步骤，继续往下走。
  - 把副作用改成幂等形态：下单／扣减带幂等键，同一键不重复生效。
- 除了回滚的正向方法：
  - 幂等本身就是正向：重复执行是 no-op，根本不用回滚。
  - 补偿推进到目标终态：不回滚反向操作，而是用新操作把状态“补齐到正确结果”。
  - 对账任务：定期核对最终态，发现漏处理／多处理就正向修正。
  - 要避的坑：只用 Redis setnx 判重、又不和业务同事务——标记打了但业务回滚，会把“重复消费”变成“丢消息”，更糟。

## Q10：MySQL 主从复制的原理；主从是强一致吗、延迟原因；怎么提升从库复制速度

### 面试回答

原理一句话：三个线程接力，把主库的 binlog 搬到从库重放。

- 主库事务提交时写 binlog。
- 主库 dump 线程按位点（File＋Position）或 GTID，把事件推给从库。
- 从库 IO 线程接收事件，追加到 relay log（中继日志）。
- 从库 SQL 线程读 relay log 重放事件，更新复制进度。

是不是一致（回答“强一致吗”）：

- 默认不是。异步复制主库提交不等从库，可能读到旧数据，属最终一致。
- 半同步：至少一个从库确认收到并落 relay log 主库才返回，缩小丢失窗口，但仍不是强一致，超时还会降级成异步。
- 同步／组复制（单主）能更接近强一致，代价是吞吐下降；结论是按 RPO（恢复点目标）选架构。

主从延迟的原因：

- 从库重放并发不足，单线程重放是经典瓶颈。
- 主库大事务、批量 DDL，从库要串着回放一大段。
- 从库自身读压力大、磁盘或网络慢。

怎么提升从库复制速度：

- 开并行复制：`replica_parallel_workers` 大于 0；把 `binlog_transaction_dependency_tracking` 设为 `WRITESET`，让更多无冲突事务能并行回放。
- 减小主库大事务、拆成批，错峰避免重写入。
- 降低从库回放开销：放宽从库刷盘（如 `innodb_flush_log_at_trx_commit` 调低）、加大缓冲与 IO 能力。
- 架构层面：按库／表拆多个从库分担读，或级联中间从库。

版本注意：8.0.26+ 用 `replica_*` 命名（旧版是 `slave_*`），`WRITESET` 依赖 `binlog_format=ROW`。

### 面试回答

结论：三段式——快慢指针找中点、反转后半段、前后交错合并；O(n) 时间、O(1) 空间，只动指针不改节点值。

- 找中点：快指针每次两步、慢指针一步，偶数长度取偏前的中点，保证前半不短于后半。
- 反转 `slow.next` 起的后半段（三指针迭代），在 `slow` 处切断。
- 双头交错接链：`p.next = q; q.next = p 的下一个`；后半先耗尽时自然收口。
- 易错点：偶数长度若用后中点，合并阶段会接错；先口述验证 n=1、n=2 再动笔。
