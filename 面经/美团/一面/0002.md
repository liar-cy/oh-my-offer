## Q02：介绍一下营销项目，遇到什么问题、怎么实现的（抽奖业务、规则树、责任链），为什么要这样设计？

### 面试回答

介绍顺序：业务目标 → 核心链路 → 遇到的真问题 → 设计与取舍。可用框架：项目是【营销抽奖】活动，用户满足条件后抽奖，返回奖品并落发奖记录。核心链路是「资格校验 → 规则判定 → 概率抽取 → 库存扣减 → 异步发奖」。

遇到的主要问题是**规则膨胀**：最初把“是否新用户、是否已参与、限领几次、黑名单、活动时间、渠道限制”写成一串 if-else，每加一条规则都要改同一个方法，测试回归面越来越大，规则还有先后依赖（黑名单必须先于概率抽取）。解法是两层拆分：① **责任链**做资格与约束校验，每个校验器一个规则、可配置顺序、命中即短路并返回明确拒绝原因（便于运营定位“为什么没抽中”）；② **规则树**描述奖品的中奖条件（与／或／非组合的表达式，配置化存库或存配置中心），执行时把用户上下文喂给树求值，加规则只改配置和新增节点，不改主干代码。概率抽取用加权随机，奖品的库存与发放走后面的扣减与发奖链路。

为什么这样设计（这是本题真正的考点）：责任链解决的是**线性顺序与短路**——规则有优先级、命中就终止，链式结构让每条规则独立可测、可插拔；规则树解决的是**组合表达式**——条件之间是布尔嵌套，链表达不了“（A 且 B）或 C”。两者不重复：链管“能不能参与”，树管“能中哪一档”。代价也要说：责任链要处理上下文对象膨胀与顺序配置错误（顺序错就是逻辑错），规则树要处理配置校验与解释执行的性能（表达式编译缓存、避免每次反射取值），并且规则一旦外置，运营误配的风险就上来了，所以配了灰度与生效时间校验。如果面试官问“为什么不上规则引擎（Drools／Aviator）”，答：项目规则量级不大，自研树＋表达式求值已够，引入引擎的学习与运维成本不划算；规则复杂到需要热更新与决策表时再换。

## Q03：库存扣减是怎么实现的？

### 面试回答

分两种口径说，先问自己项目实际是哪种再答。低并发下数据库条件更新就够：`update prize_stock set stock = stock - 1 where prize_id = ? and stock > 0`，靠 `stock > 0` 这个条件让 InnoDB 的行锁保证不超卖，影响行数为 0 就是没库存；关键是**不能先查再改**（check-then-act 在并发下会超卖），也不要在扣库存的同一事务里做 RPC 或发 MQ，那会把行锁持有时间拉长。高并发场景把扣减前移到 Redis：库存预热进 Redis，用 Lua 脚本把“判断余量＋扣减”做成一个原子操作，扣成功后异步落库（消息或定时对账），DB 侧仍保留 `stock > 0` 条件做兜底；Redis 不可用时降级为直接走 DB 并限流，或者只读不写，避免超卖。项目实际实现：【预热方式／Lua 或 DB／异步落库路径／压测数字】要能对上，被追问“为什么不用分布式锁”时答：锁是把并发串行化，扣减本身只是单变量原子更新，条件更新或 Lua 更轻且不引入锁续期与死锁问题。

## Q04：MySQL 和 Redis 数据一致性怎么保证？出现短暂不一致怎么考虑？

（原题 3 与原题 12 是同一考点，两次提问合并为本组问答。）

### 面试回答

先给口径：缓存与库的一致性目标是**有界陈旧**，不是零窗口——先问业务能容忍多久的旧值，再选方案。项目实现（按实际填）：以 MySQL 为事实源，写路径是**本地事务提交成功后删除缓存**（cache-aside），删除失败进重试表或由 binlog 订阅（canal）驱动补偿删除；读路径未命中回源并回填，TTL 设上限兜底。为什么是删缓存而不是更新缓存：更新要重复算一遍且并发写会互相覆盖，删除让下一次读去重建更简单。

被追问“出现短暂不一致怎么考虑”时分三层：① 承认窗口存在——先删后写会有并发读回填旧值，先写后删窗口更短但仍不为零；② 给业务影响分级——奖品余量、库存这类“少卖可以、超卖不行”的字段不能只信缓存，判断以 DB 条件更新为准，缓存只用于展示与限流，所以短暂旧值不会造成资损；③ 给收敛手段——关键读走主库或直接读 DB、缓存带版本号或延迟二次删除、TTL 设成可容忍的最大陈旧时间、加对账任务定期比对缓存与库并修正。若被问“有没有更强一致的方案”，可提读写同一分片时用 Redis 事务／Lua 把缓存与计数写原子化，但跨 MySQL 与 Redis 无法做到分布式强一致（除非引入 XA／TCC 并承担代价），业务上一般用最终一致＋幂等＋对账。

## Q05：Redis 使用过程中遇到过缓存穿透吗？出现不一致的情况吗？

### 面试回答

穿透的定义先说准：查的是**根本不存在**的 key，缓存永远命中不了，每次都打到 DB。项目里是否遇到要按实际答（原文备注“本地部署，没”）：本地部署、流量可控时不会自然出现，但**用不存在的 ID 压测就能复现**——比如拿随机大 ID 打接口，DB QPS 直接抬起来。当时的处理：① 空值缓存（查不到也写一个短 TTL 的空标记，TTL 要明显小于正常数据）；② 参数校验挡掉明显非法 ID；③ 需要时用布隆过滤器前置拦截，并说清它的局限——有假阳性、删除困难、新增数据要同步更新，且它挡不住“每次都查不同不存在的 key”的极端构造（布隆会误放）。顺带区分击穿（热点 key 过期瞬间大量回源，用互斥重建或逻辑过期）与雪崩（大批 key 同时过期或 Redis 整体不可用，用 TTL 抖动、多级缓存与限流降级）。

不一致的情况：本地部署没有真实并发写，所以未观察到；但要主动说出**什么条件下会出现**——写库与删缓存之间进程崩溃、删缓存失败未重试、并发读在删之前回填旧值、主从延迟导致从库回源读到旧数据。这些在压测或线上才会暴露，回答时说明“我按窗口分析过，风险点在哪、怎么补偿”，比只答“没遇到”可信。

## Q06：RabbitMQ 发奖，怎么确保奖品会被发放（发奖可靠性）？

### 面试回答

按“三段不丢＋一段不重”讲。① **生产端不丢**：抽奖资格与扣库存先在一个本地事务里落库（含发奖状态“待发放”），事务提交后再发消息；开启 publisher confirm 拿到 broker 接收确认，确认失败或超时的记录由补偿任务重投；更稳的做法是事务型 outbox——把待发消息与业务变更写在同一事务，由投递器扫表发送，避免“库提交了但消息没发出去”。② **Broker 不丢**：queue 与 message 都持久化，生产端确认落盘；重要队列配镜像／仲裁队列避免单点。③ **消费端不丢**：手动 ack，消费者在**一个事务内**完成幂等判定、写发奖记录、更新状态，事务提交后再 ack；处理失败 nack 且带重试上限，超限进死信队列并告警，人工或定时补偿兜底。④ **不重复发**：消息带稳定业务唯一键（活动＋用户＋批次），消费端用唯一约束或条件状态更新去重——不能靠“先查不存在再插入”，也不能只在单机内存记 ID，因为消息可能被另一台机器重投。最后加**对账**：定期比对“应发”和“实发”，差异自动补发或人工处理，这是“确保一定发放”的最后一环；同时说明幂等让重投安全，所以宁可至少一次＋幂等，也不追求精确一次。

## Q07：Agent 项目介绍一下，你是怎么设计这个项目的，Agent 的定位是什么？

### 面试回答

三层回答：定位 → 设计 → 为什么不选另一种。定位：这个 Agent 解决的是【多步骤、需要查资料并调工具的任务】，比如【日志检索问答／运维排查助手】——用户给自然语言目标，系统要理解意图、检索上下文、调用工具、把结果整理成结论。它是【辅助人做判断／直接执行动作】的定位，所以【高风险动作留人工确认】。

## Q08：记忆是怎么实现的，补充的上下文介绍一下（RAG）

### 面试回答

分两类说，别混成一个词。**会话内记忆**：短期上下文就是当前对话历史＋本轮中间结果，实现上是按 token 预算裁剪——保留系统指令、最近若干轮、被引用的关键中间结论，超预算时对早期内容做摘要压缩或丢弃，必要时把整段历史做结构化笔记（把已确认事实单独存，避免摘要丢关键约束）。**跨会话记忆**：把用户偏好、项目事实、历史结论写进外部存储（向量库＋键值／关系表），检索时按相关性召回并注入，更新时要处理冲突事实——新事实带时间与来源，命中同一实体时按“更新覆盖旧值但保留历史版本”的方式写，不能简单追加导致模型同时看到矛盾内容。

**二、MySQL 与 JVM（原题 10—14 → Q11—Q14）**

## Q11：MySQL 索引的数据结构是 B+ 树，能介绍一下 B+ 树吗？

### 面试回答

B+ 树是多路平衡搜索树：所有分支节点只存键和子页指针，**数据全在叶子层**，叶子节点之间用双向链表串起来。相比 B 树（非叶节点也存数据），同样页大小下分支节点能放更多键，扇出更大、树更矮——三层就能撑千万级行，一次主键查找最多三次页访问，且根与上层通常常驻缓冲池。相比哈希表，哈希只支持等值、不支持范围与排序，B+ 树能天然支持范围扫描、order by 和最左前缀匹配。叶子链表让范围查询顺序扫即可，不必回树。

再补两层细节：InnoDB 的**聚簇索引**叶子存整行，二级索引叶子存索引列＋主键值，所以走二级索引查非索引列要“回表”，覆盖索引可以避免；主键用自增 bigint 是为了顺序写入减少页分裂，UUID 太宽会同时放大每棵二级索引。MyISAM 是索引与数据分离（叶子存地址），没有聚簇概念。被追问“为什么不是红黑树／B 树／跳表”时，落点都是同一个：磁盘按页读，目标是**降低树高、提高顺序扫描局部性**，红黑树太高、B 树扇出小、跳表不便于磁盘页组织。

## Q12：一行数据 1KB、主键 bigint、树高约 3 层，大概多少数据量，怎么思考？

### 面试回答

这是估算题，面试官明确说“没关系，说思路”，所以要把假设摆出来再算。以 InnoDB 默认 16KB 页为例：非叶节点每项是「键＋页指针」，bigint 主键 8 字节＋页指针约 6 字节≈14 字节，一页可放约 1100～1200 个分叉（扣掉页头页尾与填充）；叶子页存整行，行 1KB 时每页约 16 行。于是三层容量≈1200 × 1200 × 16 ≈ 2300 万行，也就是常说的“三层 B+ 树撑两千万行”。

再补敏感性分析才算讲透：行越小容量越大（100B 行每页约 160 行，同三层可到两亿级）；主键越宽扇出越小（换成 varchar 长主键，每页分叉数直接掉）；二级索引树更“矮胖”，因为叶子只存索引列＋主键，同样三层能放远多于聚簇索引的键值。还要说清估算依赖 `innodb_page_size`、平均行宽、填充率和隐藏列（事务 ID、回滚指针、NULL 位图、变长头），所以报数前先问条件、给区间而不是给一个死数字。最后一句可延伸：树高决定 I/O 次数，这也是数据量上亿、树升到四层后查询明显变慢的机制解释。

## Q14：JVM 内存结构介绍一下

### 面试回答

按“哪些线程共享、哪些私有”来讲最清楚。**线程私有**：虚拟机栈（每个方法调用创建一个栈帧，存局部变量表、操作数栈、动态链接、方法返回地址）、本地方法栈、程序计数器（当前字节码行号，唯一不会 OOM 的区域）。**共享**：堆（对象实例与数组，GC 主战场，分新生代与老年代，或 G1 下的 Region）、方法区／元空间（类元信息、运行时常量池、静态字段；JDK 8 起用本地内存的 Metaspace 取代永久代，所以字符串常量池和静态变量实际随类加载器放在堆侧）。

再补三处易错点：① 运行时常量池属于方法区，但**字符串常量池在 JDK 7 起位于堆**；② 直接内存（NIO 的 ByteBuffer、Netty 池外内存）不属于 JVM 规范里的运行时数据区，但会真实占用物理内存，容器里最容易造成“堆没满却被 OOMKilled”；③ 别把“JVM 内存结构”和“Java 内存模型 JMM（工作内存、volatile、happens-before）”混为一谈，两者只是名字像——被问“内存模型”时先确认对方指哪一个。对象层面还能延伸：对象头（mark word、类指针、数组长度）、指针压缩、压缩类指针、32 字节对齐，以及逃逸分析后可能栈上分配标量替换。

## Q17：两类误判怎么思考，该怎么处理？

### 面试回答

两类误判就是假阳性（把好判成坏，误杀）和假阴性（把坏判成好，漏放）。思考方式：先问**代价不对称**在哪一侧——内容审核里误删伤害用户表达且引发申诉，漏放伤害平台与合规，通常漏放代价更高；推荐或风控里误杀损失一次转化、漏放损失资损，方向可能反过来。所以不能用一个准确率数字统一优化，要按类目分别看精确率与召回率，再用业务能接受的阈值定折中点（ROC／PR 曲线选点，而不是拍脑袋调置信度线）。

处理分三层：① **阈值与分档**——高风险类目压低召回门槛（宁可送人工），低风险类目允许自动放行；中间置信区间不做不可逆动作；② **兜底与可逆**——误判要能撤销（保留快照、一键恢复、申诉入口），并把申诉结果作为高价值样本回流；③ **归因与迭代**——分别统计两类误判的成因（样本缺失、类目定义歧义、上下文不足、检索没召回证据、阈值漂移），假阳性多就补“正常但有歧义”的负例，假阴性多就补新变体样本；同时盯指标趋势，防止只优化一类导致另一类恶化。最后强调：模型给的是建议，两类误判的**权衡标准由业务定**，不能把阈值当成纯技术问题。

## Q22：JVM 垃圾回收：怎么判断垃圾、回收算法优劣、分代，CMS 和 G1 的特点、执行步骤与使用场景

### 面试回答

**判活**：Java 堆用可达性分析，从 GC Roots（活动线程栈引用、静态字段、JNI 引用等）向下遍历，不可达即可回收；引用计数难处理循环引用，不是 Java 的主要判活手段。**算法与优劣**：标记—清除不用搬对象但留碎片，可能触发提前 GC；复制算法无碎片、成本与存活量成正比，适合存活率低的新生代，但要浪费一块空间；标记—整理无碎片且不留空块，代价是移动对象要更新引用、暂停更长，适合老年代。**分代**基于“多数对象朝生夕死”的弱分代假说，新生代用复制（Eden＋两块 Survivor，Minor GC 只扫年轻区域所以快），老年代用标记整理；跨代引用靠记忆集记录，避免全堆扫描。

**CMS**（并发标记清除，面向低停顿）：四个阶段——初始标记（短暂 STW，只标 Roots 直连）、并发标记（与用户线程同时走引用图）、重新标记（短暂 STW，修正并发期间变动的引用，用增量更新／SATB 思路）、并发清除（与用户线程并发回收，不移动对象）。特点与代价：并发度高、暂停短；但有**浮动垃圾**（本轮标记后新产生的垃圾只能下轮处理）、**碎片**问题（不整理，长期可能 Full GC 兜底）、并发阶段抢占 CPU 且要预留堆空间（Concurrent Mode Failure 会退化）。JDK 9 起被标记废弃、JDK 14 移除，面试时要说明现在默认是 G1。**G1**：把堆分成大小相同的 Region，逻辑上仍有年轻／老年代，用记忆集控制跨区扫描；流程是 Young GC → 并发标记周期（初始标记借用 Young 暂停、并发标记、最终重标记、清理）→ 混合回收（Mixed GC 挑垃圾多的 Region 一起回收），并可在暂停目标内优先回收价值最高的 Region（“Garbage First”名字由来）。它把停顿做成**可调目标**（`MaxGCPauseMillis`），适合大堆；代价是有复制开销、写屏障成本，以及 humongous 对象处理不当会影响空间。

**选型**：要低延迟且堆大 → G1（JDK 9+ 默认）；追求极短暂停、大堆且能接受吞吐略降 → ZGC／Shenandoah（分代 ZGC 在 JDK 21+）；小堆、吞吐优先的批处理 → Parallel GC。CMS 只出现在旧版本 JDK 的题面上，答完要主动说它已被移除，避免被认为知识停在 JDK 8。

## Q23：MySQL 事务特性逐个展开：原子性、隔离性、持久性、隔离机制、MVCC、间隙锁

### 面试回答

**原子性**：事务里的操作要么全做要么全不做，靠 undo log 实现——修改前把旧值写进 undo，回滚时按 undo 逆向恢复；undo 本身也是先写后改，所以崩溃恢复同样能回滚未提交事务。**持久性**：提交后数据不丢，靠 redo log（WAL：先写 redo 再改内存页，崩溃后按 redo 重放已提交事务）＋刷盘策略 `innodb_flush_log_at_trx_commit`（=1 每次提交刷盘最安全，=2 交给 OS，=0 最多丢一秒）；binlog 与 redo 用两阶段提交保证“逻辑日志”与“物理恢复”一致。**隔离性**：由锁＋MVCC 共同实现，隔离级别（RU／RC／RR／串行化）决定读写之间互相看到什么。**一致性**（ACID 的 C）是目标而非机制：约束、外键、唯一索引加上业务不变量共同保证，不能靠“原子隔离持久”自动获得。

**隔离机制**：RC 下每次一致性读都新建快照，能看到别人已提交的新值；RR 复用事务内**第一次**一致性读建立的 read view，所以重读同一记录结果不变。MVCC 的实现是行里的隐藏列（事务 ID、回滚指针）＋ undo 版本链＋read view：快照读按可见性规则沿版本链找到该事务能看见的版本，因此读写不互相阻塞；当前读（`SELECT ... FOR UPDATE`、`LOCK IN SHARE MODE`、`UPDATE`、`DELETE`）读最新版本并加锁。**间隙锁**是 RR 下防幻读的关键：范围锁定读会锁住记录之间的间隙（next-key lock＝记录锁＋间隙锁），阻止别的事务在间隙内插入；但要注意两点——快照读不加锁，所以 RR 并不能阻止“别的事务插入并提交”，只是自己看不到；而一旦该事务做当前读或写入，就可能看到新行，出现所谓幻读，需要 next-key lock 覆盖。锁的粒度还依赖索引：条件没走索引时行锁会退化成扫描到的大量记录甚至近似表锁，间隙范围也随之放大——这是很多“莫名死锁／锁等待”的根因。

## Q24：Redis 数据持久化，两种方式各自介绍

### 面试回答

**RDB**：某一时刻的内存快照，`SAVE`（阻塞主线程，不推荐）或 `BGSAVE`（fork 子进程写临时文件后替换），触发条件写在 `redis.conf` 的 `save` 规则里（如 900 秒内至少 1 次写）。优点是文件紧凑、恢复快、适合备份与主从全量同步；缺点是两次快照之间的数据会丢，且大实例 fork 时可能有内存与延迟抖动（写时复制）。

**AOF**：把写命令追加到缓冲区，按策略刷盘（`appendfsync always`／`everysec`（默认，最多丢一秒）／`no`），重启时重放命令恢复。优点是丢数据少、文件是追加写不易坏；缺点是体积大、恢复慢，所以有 **AOF 重写**（`AUTO_AOF_REWRITE`，由子进程按当前数据生成最小命令集，配合增量 AOF buffer 保证重写期间的写不丢）。Redis 7.0 起是多文件 AOF 布局（基础文件＋增量文件＋清单 manifest）。

**混用与取舍**：生产常见两者都开，重启时**优先用 AOF**（数据更全）。只配 RDB 的场合是“缓存可重建”的场景；AOF 也挡不住所有丢失（everysec 有一秒窗口），也不等于备份——要防误删与磁盘故障仍需异地备份。延伸：主从复制本身不是持久化，`appendonly no` 且不开 RDB 的实例重启即空；关闭持久化能提升写入吞吐，但必须接受数据全丢的风险，这题答完最好主动补一句“我的项目里 Redis 用作【缓存／库存预占／分布式锁】，所以【要不要持久化】的结论是【什么】”。

## Q25：慢查询怎么定位，SQL 如何优化？

### 面试回答

**定位链路**：先开慢查询日志（`long_query_time`）或用 performance_schema／sys 库抓 top SQL，再用 `EXPLAIN`（必要时 `EXPLAIN ANALYZE` 看真实执行）判断访问类型 `type`、使用的索引 `key`、`rows` 估算、`Extra`（`Using filesort`／`Using temporary`／`Using index`／`Using index condition`）；同时看锁等待（`SHOW ENGINE INNODB STATUS`、`data_locks`／`data_lock_waits`）和是否被大事务、连接数、缓冲池命中率拖累。定位顺序是“先确认它真的慢在数据库、慢在哪一步”，不要一上来就改索引。

**优化手段**按层次给：① SQL 写法——只取需要的列、避免 `SELECT *` 与回表、把不可 sarg 的写法改掉（列上做函数／运算、隐式类型转换、`LIKE '%x'`、`OR` 连接非索引列都会导致索引失效）；② 索引设计——按最左前缀建联合索引，把等值条件放前、范围条件放后，排序与分组字段纳入索引避免 filesort，能用覆盖索引就覆盖，必要时用前缀索引省空间；③ 结构与分布——大分页改游标／延迟关联，避免一次取百万行，区分度低的列不单独建索引，写入热点表考虑拆分或分区；④ 事务与锁——缩短事务、按固定顺序加锁避免死锁，减少在事务里做外部调用；⑤ 架构层——读写分离、缓存热点、归档历史数据；⑥ 配置与资源——连接池参数、缓冲池大小、临时表与排序缓冲区。收尾必须回到验证：改完用同一 SQL 与同一数据量对比 `EXPLAIN` 与实际耗时（`EXPLAIN ANALYZE` 会真执行，线上慎用），并说明为什么变快（扫描行数下降／避免回表／消除 filesort），而不是“加了索引就快了”。

## Q26：MySQL 主从，读取可能数据不一致，你觉得怎么解决？

### 面试回答

先定性：这不是脏读，是**复制延迟导致的旧数据**——从库还没重放主库已提交的事务。解决按“读己之写的重要性分级”，全量读主库等于放弃读写分离。手段：① **强制走主库**——写后立读的关键接口（下单后查订单、支付后查状态）用注解／Hint 或在同一事务内自动路由主库；② **会话粘性**——用户写入后的一小段时间内其读请求都走主库，或把刚写入的实体 ID＋版本记到缓存里带过去；③ **等待复制位点**——拿到主库 GTID 后用 `WAIT_FOR_EXECUTED_GTID_SET` 等在目标从库追上再读，代价是延迟；④ **半同步复制**降低丢失风险（但它保证的是送达，不保证从库已回放完）；⑤ **业务层兜底**——从库查空不立即判“不存在”，回主库复核一次；前端提交成功页先展示已知数据；⑥ **监控与对账**——盯 `Seconds_Behind_Source`、用 pt-table-checksum 类工具定期核对，延迟超阈值时自动把读切回主库或降级；同时排查延迟成因（大事务、从库单线程回放、从库负载、网络），开并行复制能缓解。最后补一句架构判断：能容忍最终一致的报表／列表走从库，不能容忍的库存／余额走主库或用 Redis 原子扣减，读写分离的边界要按数据重要性划。
