## Q02：对 MCP 的理解；MCP 客户端调用服务器工具的整体交互流程。

原题 2—3 同话题，按提问顺序合并。

### 面试回答

MCP 是 Anthropic 发起的开放协议，用 JSON-RPC 给“模型上下文供给”定一套标准接口。

角色关系：

- Host（IDE／Agent 应用）内建 Client，Client 连 Server。
- Server 对外暴露三类能力：tools、resources、prompts。
- 它常被类比成 AI 世界的 USB-C——把 M×N 的私有适配收敛为 M＋N。

和 Function Calling 不冲突，两者管的层不同：

- Function Calling 是模型层的能力：选哪个工具、传什么参数。
- MCP 是应用层的协议：工具怎么被发现、被调用、被鉴权。它解决的是工具与数据接入的碎片化问题。

交互流程六步：

- Client 发 initialize，双向协商协议版本与能力。
- notifications/initialized 表示就绪。
- tools/list 拉取工具定义，转成模型可见的工具描述。
- 模型推理产出调用意图（工具名＋参数），运行时做参数与权限校验。
- Client 发 tools/call，Server 路由到实现执行，返回 content 或 isError。
- 宿主把结果回填到消息流，继续推理。

再补两点显示理解深度：

- 初始化与发现的结果可以复用，不必每次调用都重做。
- 写操作超时时，要靠幂等与状态查询来判断结果，别盲目重试。

## Q03：讲一下 Spring AI Alibaba Graph 的底层原理。

### 面试回答

它是阿里在 Spring AI 之上做的工作流／多 Agent 编排引擎，设计借鉴 LangGraph——把应用建模成状态图，而不是一条链。

核心四件：

- StateGraph 声明图结构：Node 封装一段逻辑（LLM 调用、工具、纯函数），Edge 与条件边决定路由。
- OverAllState 是全局状态：节点不传消息，而是返回“状态增量”，按每个 key 的合并策略（Replace／Append）写回。这决定了并行分支的写冲突语义。
- compile() 把声明式图转成可执行结构，并做图校验：可达性、路由完整性。
- 执行是“超步”模型：每个超步跑完当前激活的节点集合、合并状态、再算下一批，天然支持并行分支与循环。

配套的两件事：

- Checkpoint 按 threadId 持久化状态，用来实现中断恢复与 human-in-the-loop（人在环路里确认）。
- 输出侧用 Reactor Flux 做流式。

和直接用 ChatClient 做链式编排的区别：

- 链是一趟单向流水线。
- 图能表达分支、循环、状态回溯与暂停续跑——复杂 Agent 拓扑的控制流，从代码里的 if-else 外化成了数据。

答题落点：我在项目里用它做过【真实场景，按实际填写】，节点划分与状态 key 设计是主要工程量。版本口径 1.x，细节以官方文档为准。

## Q05：为什么要有线程池？怎么创建线程池，拒绝策略有哪些？

原题 6—8 同属线程池话题，按提问顺序合并。

### 面试回答

**为什么要有线程池**：

- 线程的创建销毁是系统调用级成本；无节制地创建还会打爆内存与调度。
- 线程池做三件事：
  - 复用线程摊薄创建成本。
  - 限制在途并发，保护 CPU／内存／下游。
  - 统一管理生命周期与监控。

**怎么创建**：

- 正确姿势是显式用七参构造：`new ThreadPoolExecutor(核心数, 最大数, 空闲存活时间, 单位, 工作队列, 线程工厂, 拒绝策略)`。
- Executors 工厂方法只是包装，而且带官方明示的隐患。
- newFixedThreadPool 与 newSingleThreadExecutor 用无界 LinkedBlockingQueue，任务积压能导致 OOM。
- newCachedThreadPool 与 newScheduledThreadPool 允许 Integer.MAX_VALUE 个线程，会线程爆炸。
- 生产按《阿里巴巴 Java 开发手册》的口径禁用快捷工厂；Spring 场景常用 ThreadPoolTaskExecutor 再接生命周期管理。

**拒绝策略四种**：

- AbortPolicy：默认，抛 TaskRejectedException。
- CallerRunsPolicy：让提交线程自己跑，形成天然背压，但会拖慢提交方。
- DiscardPolicy：静默丢新任务。
- DiscardOldestPolicy：弹掉队首最老的任务再重试。

丢任务都要求业务可容忍。生产实践是自定义 RejectedExecutionHandler：记日志、报警、降级入队或持久化补偿，而不是选一个内置策略就完事。

## Q06：多线程怎么保证线程安全？

### 面试回答

按成本从低到高给一个梯度。

- 根本不共享：栈封闭、每线程各一份、不可变对象（final 正确发布、record）。
- 共享但不写：只读的派生数据；或者 volatile／Atomic／LongAdder 这类单变量无锁更新。注意它们只保证单个操作原子，i++ 这种复合动作不行。
- 显式互斥：synchronized 或 ReentrantLock 圈住临界区，配 wait／notify 表达条件。
- 直接交给并发组件：ConcurrentHashMap 的 computeIfAbsent、BlockingQueue。把 check-then-act 这类竞态收进原子方法里，别自己拼。
- 架构层面消灭共享：单写者＋消息传递（Disruptor／队列）、分片降低争用。

收尾立一个判断标准：先问“这份数据真的需要跨线程可变共享吗”。能降级成前两种就不用锁；同时对死锁四条件与锁顺序保持警觉。

## Q07：synchronized 和 ReentrantLock 的区别。

### 面试回答

两个都是可重入的独占锁，差别在使用契约与能力面。

synchronized：

- JVM 内建，monitor 语义；获取和释放由字节码与管理器自动完成，不会忘记解锁。
- 支持锁升级优化（轻量级／重量级）；偏向锁 JDK 15 起废弃。

ReentrantLock：

- API 层实现，必须在 finally 里 unlock。
- 换来的是 synchronized 给不了的能力：可中断获取 lockInterruptibly、超时 tryLock、公平锁选项、多个 Condition 精确唤醒（比如读写分离队列），以及和 AQS 生态的可组合性。

选择口径：

- 没有特殊需求就用 synchronized，代码更安全也更可读。
- 需要超时／中断／公平／多条件等待，才上 ReentrantLock。

一个版本相关的坑：JDK 21 的虚拟线程场景下，synchronized 的长临界区曾会钉住载体线程（JDK 24 的 JEP 491 有所缓解）。所以在高并发 IO 服务里，阻塞式锁更推荐换成 Lock 或无锁结构。

## Q08：ReentrantLock 底层原理；AQS 怎么实现、如何保证 state 的原子性？

原题 11—12 递进话题，合并作答。

### 面试回答

**锁状态怎么存**：ReentrantLock 内部是一个 AQS 子类 Sync，锁状态就是 AQS 的 `state`（int）。

- 0 表示无人持锁。
- 加锁是 CAS 把 state 从 0 置 1，成功后记下 owner。
- 重入是同线程再 CAS 自增。
- 释放时递减，减到 0 才真正放开。

**公平与非公平**：只差获取时的一步。

- 公平版先调 `hasQueuedPredecessors()` 查队列。
- 非公平版直接插队 CAS。
- 所以非公平吞吐更高，但可能饥饿。

**拿不到锁的线程怎么处理**：

- 被包成 Node（存线程、waitStatus），CAS 入 CLH 变体的 FIFO 双向队列。
- 前驱是 head 且重试成功才出闸，否则 park 挂起。
- 释放时 unparkSuccessor 从 tail 向前找有效后继并唤醒。
- Condition 队列独立存放 await 节点，signal 时整体转移到同步队列参与竞争。

**state 的原子性怎么保证**：

- state 用 volatile 修饰，保证可见性与禁止重排。
- 但 volatile 管不了“读—改—写”这个复合动作，所以所有修改统一走 compareAndSetState。
- 它经 Unsafe／VarHandle 落到 CPU 原子指令（x86 的 lock cmpxchg）：要么整个成功，要么保持不变，失败就重读重试。
- “volatile 读＋CAS 写”这个组合就是无锁原语的标准形态，锁自身不再依赖上层的锁。

## Q09：垃圾回收算法有哪些？

### 面试回答

基础三件套：

- 标记—清除：快，但会碎片化。
- 标记—整理：无碎片，但移动成本高。
- 复制：年轻代专用，存活少时很高效；代价是空间减半。实践上按弱分代假设定 Eden:S0:S1＝8:1:1，把浪费压到两成。

在这之上是分代收集：

- Minor GC 用复制算法处理新生代。
- Full GC 用标记—整理处理老年代。

收集器演进要连着报：

- Serial／ParNew。
- CMS：并发标记清除，低停顿，但碎片化且对 CPU 敏感；JDK 14 移除。
- G1：堆划 Region、可预测停顿模型、混合回收；JDK 9 起默认。
- ZGC／Shenandoah：靠着色指针／转发指针做到停顿与堆大小基本无关；ZGC 在 JDK 15 转正、21 起分代。

两个加分点：

- 算法与收集器是两层概念，别把“标记整理”和 G1 并列着背。
- 判断对象存活用可达性分析（GC Roots）；引用强度的四级决定回收时机。

## Q10：对象在 JVM 中的生命周期；新生代 S0/S1 的作用与晋升老年代的时机。

原素材在 15 题保留候选人自评“这个没怎么答好、没说完整”，故此处给完整版供复盘。

### 面试回答

生命周期一条线：

- new 之后在 Eden 诞生，分配走 TLAB（线程私有的分配缓冲区）。
- Minor GC 来临时，可达对象被复制到 Survivor，年龄＋1。
- 反复存活到 MaxTenuringThreshold（默认 15）就晋升老年代。
- 之后在老年代回收（Full GC／mixed GC）时若不可达就被清除，对象终结。

中间穿插三类捷径：

- 大对象直接进老年代：按 `-XX:PretenureSizeThreshold`（Serial／ParNew 口径，G1 是用 Region 直接放）或者动态判定，防止 Survivor 颠簸。
- 动态年龄判定：Survivor 内同龄对象总和超过其一半时，年长对象提前晋升。
- 逃逸分析开启时，不逃逸的对象根本不上堆：标量替换把它拆成栈上局部变量，锁也可能被消除。

S0／S1 的作用：

- 复制算法要求“从一块活区倒进一块空区”，所以两个 Survivor 互为 from／to 角色。
- 每轮 Minor GC 后两者交换，活对象始终集中在一个区。
- 这就是不产生碎片、成本只与存活对象数成正比的来源。
- 如果只有一个区，就得整堆扫描整理，代价高得多。

没答全的点通常漏在“什么时候去老年代”。四条，缺一条就不完整：

- 年龄满阈值晋升。
- 动态年龄判定。
- 大对象直达。
- Minor GC 时 Survivor 放不下，靠分配担保进老年代。

## Q11：Kafka 特性、与 RabbitMQ 的区别、高吞吐量的原因。

原素材在 17 题保留候选人自评“答的很一般”，此处给完整版供复盘。

### 面试回答

**特性**：Kafka 本质是分布式提交日志。

- topic 分区、分区内有序追加、消费者按 offset 拉取。
- 消息是“可重放的流”，不是“消费即消失的队列”。
- 外面再配合消费者组、副本 ISR、Connector／Streams 生态。

**与 RabbitMQ 的区别**，从模型讲起：

- Rabbit 是 broker 路由模型：exchange 按规则分发到 queue，push 为主，消息取出即删。它擅长复杂路由、低延迟（微秒级）、per-message 可靠语义。
- Kafka 是日志模型：pull＋offset，分区决定并行与顺序。它擅长吞吐（百万级 TPS）、消息回溯、流处理；顺序只保证到分区粒度。

**选型**：订单通知这类业务消息用 Rabbit；日志采集、行为流、大数据管道用 Kafka。

**高吞吐四个支柱**：

- 顺序写磁盘＋页缓存：追加写把随机 IO 变成顺序，OS page cache 让热数据根本不过用户态。
- 零拷贝 sendfile：消费时数据从页缓存直达网卡，省掉四次拷贝、三次切换。
- 分区并行：生产和消费都能按分区水平扩展，并行度随分区数线性涨。
- 批量＋压缩：producer 攒批、broker 按批存储、消费者按批拉；压缩批原样传输，摊薄协议与网络开销。

## Q12：大模型产生幻觉的原因及解决方案。

### 面试回答

从生成机制讲起，幻觉就不是玄学。

原因：

- 模型学的是 token 的条件概率分布，训练目标是“像下一个词”，不是“真”。
- 知识以参数化记忆存在，长尾事实稀疏或过期，就会编。
- 解码带随机采样，错误的 token 会沿自回归滚雪球，也就是暴露偏差。
- 训练数据本身就有错误与冲突。
- 上下文里的矛盾信息，或者超长窗口里的注意力稀释，也会诱发。

解决方案分层给：

- 知识侧：用 RAG 接地，外部证据可更新、可引用。
- 推理侧：
  - 用 CoT 拆步。
  - 把计算交给确定性工具（SQL／计算器／检索）。
  - 把温度调低。
- 生成侧：提示词里显式允许拒答，并要求带引用。
- 验证侧：自一致性多采样比对、引用支持度校验、独立模型或规则审查；关键链路留 human-in-the-loop。
- 训练侧：SFT 提升数据质量，DPO／RLHF 把“不确定时坦白”对齐进模型。

收口要诚实：

- 只能压缩幻觉率和影响面，不能归零。
- 按场景定预算：财务数字类要有校验兜底，创意类可以宽松。

## Q13：RAG 的具体实现过程。

### 面试回答

离线和在线两段讲。

离线入库：

- 链路是：文档采集 → 解析清洗 → 分块 → embedding 向量化 → 与关键词索引双写进向量库。
- 解析清洗做三件事：格式归一、去噪、保留结构与来源元数据。
- 分块按语义或标题层级切，控制粒度并保留上下文重叠；块大小按下游模型窗口和召回精度做实验来定。
- 更新策略是增量重算，加版本失效。

在线查询：

- 问题理解：改写、补全指代；复杂时路由到不同的库。
- 混合召回：向量 top-k 加 BM25（一种关键词检索的排序算法）。权限过滤必须在召回层就生效。
- 重排：用 cross-encoder 精排，压掉噪声。
- 上下文组装：去重、按预算截断；指令里约束“仅依据资料回答、缺证据明确拒答”。
- 生成时带引用，出口再校验引用是否真的支持结论。

最后一块是评测闭环：

- 建评测集，跑召回命中与答案忠实度。
- 坏例回流，用来优化切块与索引。
- 立场是：没有评测的 RAG 只是玄学拼接。

项目细节（模型选型、指标数字）按【真实实现】口径替换。

## Q14：预训练和微调的区别。

### 面试回答

一句话：预训练决定能力上限，微调决定它怎么表现。

预训练：

- 在海量无标注语料上做自监督，目标就是下一 token 预测。
- 把语言与世界知识压进参数，产出 base 模型。
- 这是算力大头：千卡月级，一次性投入决定能力上限。

微调：

- 拿小规模任务数据继续训练。
- SFT 用“指令—回答”对，让模型学会听指令与输出格式。
- 偏好阶段用 RLHF／DPO 对齐人类偏好。
- 工程上常用 LoRA／QLoRA，只训旁支参数，把成本降到单机可跑。
- 产出 instruct／chat 模型：改变的是行为方式与领域风格，不会创造预训练没有的底层能力。

对比维度一起报：

- 数据：规模与标注程度差别很大。
- 目标函数不同。
- 算力与频率：预训练一次，微调可以反复且成本较低。
- 风险：微调过量会灾难性遗忘通用能力，混入通用数据或用 PEFT 能缓解。

落点接实践：

- 知识时效问题不该用微调解决——会过期、会幻觉，该走 RAG。
- 微调用于固定格式、风格、领域行为，见 LLM-008。

## Q16：手撕 LeetCode 415（字符串相加）。

按 LeetCode 415 标准题解作答：给定两个非负整数字符串，模拟竖式加法返回结果字符串，不得直接使用内置大整数库。

### 面试回答

双指针从两个串的末尾对齐扫描。

- 每轮取 `num1[i]`、`num2[j]`（越界记 0）与进位求和。
- `sum%10` 追加到结果，`sum/10` 作为下一轮进位。
- 一方耗尽后继续走另一方；最后进位若还有余，再补一位。
- 因为是逆序拼接，结束时整体反转。

复杂度：时间 O(max(m,n))，空间 O(max(m,n)) 用来存结果。Java 用 StringBuilder 从尾追加，再 `reverse()`。

三个坑点：

- 全零边界：`"0"+"0"` 要得到 `"0"`。循环条件得允许“两指针耗尽但进位为 1”时多跑一轮，或者在循环后补位。
- char 转数值是 `c-'0'`，别直接把 char 相加。
- 题目约定无前导零，所以不必自己裁剪。

写完用 `["999","1"]→"1000"` 走一遍验证。
