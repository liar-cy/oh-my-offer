### 面试回答

面试官这两问其实是在校验“你讲的东西是否自洽”，所以顺序上先答目标与场景、再答挑战与解法更稳：这个系统为谁解决【具体问题】，触发场景是【谁在什么时候怎么用、频率与量级多少】，成功标准是【指标】；在这个前提下，核心挑战有【N】个，我挑最硬的讲清“为什么难（并发规模／数据质量／效果不可控／资源限制）→我怎么定位（证据、实验、日志）→比较过哪些方案与为什么放弃→最终方案与代价→怎么验证（评测集或上线指标）”。AI 项目要特别注意把“效果类挑战”说成可测的：不要说“提升了准确率”，要说“在某评测集【N】条上某指标从 X 到 Y，基线是什么、怎么标注的”。同时如实划边界：本人负责【模块】，团队其他人负责【模块】；没做完的就说没做完、下一版打算怎么改，别把规划讲成已上线。

## Q04：RAG 引擎具体是做什么的？

### 面试回答

一句话说清职责边界：它把“散落的资料”变成“可回答、可引用的问题答案”。输入是用户自然语言问题，输出是带来源引用的回答或明确的“证据不足”。内部做三件事：把知识整理入库（解析、清洗、切块、建索引）、把问题变成检索（改写、路由、混合召回、过滤、重排、上下文组装）、把证据变成可控生成（约束模型只依据证据作答、要求引用、必要时拒答）。价值不是“能聊天”，而是让答案可追溯、知识可更新、领域不靠模型参数硬记——这也是它相对直接问大模型和相对微调的区别所在。最后如实补一句本项目的范围裁剪：哪些环节做了、哪些用了框架默认、哪些还没做（比如权限过滤、增量更新），不要把所有模块都说成自己实现的。

## Q06：具体使用了哪些知识、如何评估这些知识的质量；有没有自建知识库做对比实验来评估效果？

原题 7—8 同属“知识内容与质量评估”话题：一个是自建对比实验与效果评估，一个是所用知识的构成与质量判断，合并为一题。知识清单与实验结论属个人事实，未记录，给可填写框架。

### 面试回答

先答知识构成：入库的是【类型清单，如规范文档、操作手册、FAQ、代码注释、表格数据】，各自占比与切块方式不同（表格结构化保存、FAQ 按问答对成块、长文按标题路径切）。再答质量怎么评估，分两层：内容层看“来源是否权威、是否最新、是否互相冲突、是否可回溯到原文”，做法是给知识打来源与时效标签、重复与冲突检测、抽样人工核对；效果层看“这类知识在检索里到底有没有用”，用分层评测集按类型统计命中率、引用支持率与无结果率，检不到就归因到“没入库／解析丢失／切块破坏语义／问法与文档措辞有鸿沟”。关于自建对比实验，按真实情况答：常见做法是固定同一批测试问题与语料版本，做有／无某模块的消融（关掉重排、换切块粒度、去掉改写、换 embedding 模型），逐项比较指标增量，而不是只报一个“效果不错”；有对照组和样本量才叫实验，只跑通 demo 不叫。若确实没做过对照实验，就直说“只做了单链路验证与 badcase 分析，缺对照组是这版的不足”，比编数字安全。

## Q07：RAG 里面的向量化是怎么做的？

模型名称、维度与实现属个人事实，未记录，按【真实方案】填写。

### 面试回答

四步说清：① 选模型——按业务语言（中英文／代码／专业术语）、向量维度、单条 token 上限、调用成本与是否需要私有化部署来选，开源可本地部署（如 BGE／GTE／m3e 一类）或用商用 API，最终以自己评测集上的召回效果定，而不是照搬榜单；② 决定向量化什么——把“标题路径＋正文切片”这类有语义检索价值的单元编码，精确标识（编号、订单号）、权限、版本、时间戳留作结构化 metadata 做过滤，不塞进向量；③ 入库工程化——批量编码控吞吐与重试、按模型输入上限切窗、向量归一化后用内积即余弦相似度、写入前先算 embedding 与文档 ID／原文位置的映射并绑定模型版本；④ 检索与更新——查询用同一模型同一空间编码，ANN 索引（HNSW 一类）在召回率与延迟间调参，内容或模型变更时重建或失效旧向量，换 embedding 模型基本等于全库重建。被追问“为什么不能一半用模型 A 一半用模型 B”：不同模型向量空间不可比，混用等于随机检索。

## Q08：如何评测这个 RAG 引擎的具体效果？

### 面试回答

先立口径：评测要分层，不然“效果不好”说不清是谁的锅。检索层用 Hit@k／Recall@k 看该被检到的证据有没有进候选，用 NDCG 看排序；生成层看答案是否被证据支持（引用正确率／忠实度）、该拒答时有没有拒答、任务是否真正完成；端到端再补延迟、单次成本与线上无结果率、用户采纳。评测集怎么来：从真实问题按业务类型、难度、语言、时效性分层采样，并专门放无答案、材料过时、事实冲突这三类困难样本；标注要写清“哪些片段能支持答案”，同一模板或近重复问题不能同时出现在调优用的验证集和最终测试集里，否则是数据泄漏。报告要带样本量与基线，例如“【N】条查询上 Hit@5 从 X 到 Y，基线是纯向量召回”，不能报人工观感。自动指标（含 LLM 当评委）适合跑回归，但必须抽样人工复核，因为评委模型自己也会错；线上反馈存在位置偏差，不能直接当标准答案。改动的比较用同一份冻结语料与测试集逐项消融，一次只动一个变量。

## Q09：系统生成一次回答大概需要多长时间？知识检索为什么花这么久，各步骤耗时怎么预估？

原题 11—12 同属端到端耗时归因：先问总时长，再追问检索为什么慢、分步预估，合并为一题。项目真实数字未记录，以下为拆解方法与可填写量级。

### 面试回答

先给分步瀑布再给总数，比只报一个平均数可信。典型链路的耗时结构大致是：问题改写／意图判断若走一次模型调用，几十毫秒到秒级（小模型或规则可压到几十毫秒）；查询向量化几毫秒到几十毫秒；ANN 召回本身通常几毫秒到几十毫秒，但多路召回若串行就会叠加，关键词检索与元数据过滤也在这里；重排用 cross-encoder 时对每个候选都要过一遍模型，候选数线性放大耗时，几十到几百毫秒；上下文组装是本地拼接，可忽略；生成阶段占大头，取决于输出长度与是否流式，首 token 延迟＋逐 token 输出，常占总耗时七成以上。所以“检索为什么慢”的常见真因不是向量算得慢，而是：串行调了多次模型（改写、路由、判断各一次）、多路召回串行、重排候选过多、外部检索服务冷启或网络往返、权限过滤导致回表查询、以及被大结果集与序列化拖住。归因做法是按步骤打点记录 P50／P95 与 token 数，画瀑布找最长那段；优化按收益排：并行化独立步骤、砍掉非必要的模型调用、限制重排候选数、把可复用的查询结果与向量缓存起来、生成侧用流式先出正文再补引用、必要时给简单问题走轻量链路。真实数字必须按【本项目实测】口径答，并说明是端到端还是仅检索、P50 还是 P95。

## Q10：实验室项目微调的训练集是怎么构造的？微调后的效果怎么样、怎么评测？

原题 13—14 同属“微调数据与评测”话题，合并为一题。训练集规模、基座模型、真实指标均未记录，以下为可填写框架与方法。

### 面试回答

数据怎么构造，按“来源—加工—质控—配比”讲：来源是【人工标注／规则模板生成／强模型蒸馏出草稿再人审／线上日志与文档改写】；加工是统一成指令格式（单轮指令或带历史的对话格式），每条含输入、期望输出与必要的约束；质控看去重、长度与格式合法、标注一致性抽检，并把与评测集相似的数据剔除避免污染；配比按难例与边界样本上采样，而不是无脑堆量。数据量级要如实——几千到几万条指令微调是小模型常见量级，说“几十万条”而讲不清来源会立刻被追问。效果怎么评测：在从未参与训练的保留集上比基座模型和微调模型，用与任务对齐的指标（分类看准确率／F1，生成看规则可判定结果或人工盲评），同时跑通用能力回归看有没有把原来会的训坏（灾难性遗忘），并给 badcase 分析。方法上要点出对照：同一评测集下比较“只调检索、只调权重、两者都调”的差别，才能说明微调带来的增量；有条件就补线上灰度。若结论是“微调没有明显收益，最后靠 RAG 解决”，如实说出来反而显得判断可靠——这是常见且合理的答案。

### 面试回答

## Q14：让你实现一个类似 Copilot 的代码生成工具，大致思路是怎样的？如何让它达到较高的准确度？

原题未记录候选人回答，以下为通用设计答法框架；“Copilot”按 IDE 内代码生成／补全类产品理解，不据此声称复刻某产品内部实现。

### 面试回答

先区分形态，因为三者架构完全不同：行内补全（光标处续写，要求百毫秒级）、对话式生成（给一段需求产出函数或文件，容忍秒级）、Agent 式改造（多步读改跑验证，容忍分钟级）。若做行内补全，关键设计是上下文构造与延迟：拿光标前后代码＋当前文件＋同仓库相关文件片段＋最近编辑历史（去敏感信息），按优先级裁剪到预算内，可用 fill-in-the-middle 方式把前后文都喂给模型；候选结果做缓存与前缀复用，走流式输出，超时或有更急输入时取消上一次请求。若做对话／Agent 生成，就是搭一个 Coding Agent 闭环：需求→上下文构建（相关文件、接口签名、项目规范）→按 diff 或整文件协议生成→可执行验证（编译、lint、单测、沙箱运行）→失败信息回传迭代→人工 review 兜底。准确度怎么提，核心不是堆更大模型，而是四件事：① 上下文质量（检索对的相关代码与项目约定，比塞满窗口重要）；② 输出协议与范围约束（只改该改的，禁止顺手重构）；③ 可执行验证——能跑测试绝不靠肉眼，不通过不交付，用编译与测试结果反推修复；④ 反馈闭环与评测——离线用带标准答案的任务集，线上以采纳率、留存率、修改后是否通过构建为准；把被拒与回滚样本回流成训练与提示改进的数据，同时盯幻觉 API（调用了不存在的库函数）这类高频错误。最后如实说明：模型侧的微调与数据要专门团队做，我能负责的是工程侧的上下文、验证与评测闭环。
