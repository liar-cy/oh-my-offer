## Q02：讲一下秒杀活动的实现。

原素材未记录候选人对项目的具体实现口径（QPS、库存量、技术选型的真实数字），以下按通用高并发秒杀链路作答，个人项目细节按【真实实现】替换。

### 面试回答

先立前提：秒杀的特征是瞬时读流量极高、写流量集中在少量库存。所以目标是“不超卖、不崩、体验可接受”，而不是所有请求都成功。

链路上分六段：

- 活动前置：商品与库存、限购规则提前预热进 Redis；活动页静态化并上 CDN。
- 入口准入：网关按用户／设备／接口多维限流，配合防刷与资格校验——是否登录、是否符合领取条件、是否已购。绝大多数无效流量要挡在写路径之前。
- 库存预占：用 Redis＋Lua 把“判库存、扣减、记名”做成一个原子操作，避免分布式锁串行化。库存不足直接快速失败。
- 异步落单：预占成功只表示受理。发队列由消费者写数据库，用户拿请求 ID 轮询或推送查结果，把尖峰写流量摊平到消费能力上。
- 终态一致：MySQL 侧用带条件的更新（`库存 >= 数量`、唯一约束防重复）兜住最终正确性；定时对账修复预占与落库的差异。
- 回补与关闭：支付超时或取消要释放库存回池；售罄后置活动开关，入口直接返回已结束，不再打下游。

收尾补一句风险：Redis 不可用时，宁可用本地缓存＋少量库存直扣兜底，也不能放开导致超卖。具体降级口径见系统设计的秒杀专题。

## Q03：前端防刷能解决哪些问题、有哪些局限；用户不走浏览器直接模拟或调用后端接口刷单怎么防？

原题 3—4 同属“防刷”话题：前端层能挡什么、绕过前端直连接口怎么防，合并为一题。

### 面试回答

先说清定位：前端防刷不是安全边界，只是体验与成本的优化。

它能解决三类问题：

- 非恶意的重复点击：按钮置灰、节流、结果页防重。
- 初级脚本与手动连点：验证码、答题、滑块，把操作成本抬上去。
- 把无效流量挡在服务端之外：页面缓存，按钮态按服务端时间控制，未开始就不发请求。

局限在于前端的一切逻辑都能被绕过：JS 可逆向、参数可自造、验证码可打码或走协议破解，无头浏览器和改 UA／设备指纹的成本也很低。所以它的真实作用是抬高刷单成本、过滤低质量流量，而不是阻止有组织的刷单。

至于直接模拟或调用后端接口的刷单，思路是一句话：让合法请求带着合法上下文来，服务端不信任任何自称。

- 接口不裸露：下单前先取一次性准入令牌，凭证和服务端会话／活动绑定，用过即废。把“抢”和“买”拆成两步，脚本拿不到有效凭证就只能空转。
- 请求加签：参数＋时间戳＋nonce（一次性随机串）做签名，服务端校验，再做时间窗和 nonce 去重，防重放和参数篡改。
- 服务端硬校验限购：按用户、账号、设备、SKU、时间窗计算已购量，绝不依赖前端展示。
- 风控识别：按行为序列（点击节奏、页面停留、无浏览直接下单）、设备与网络信誉、账号画像、团伙关联（同收货信息／同支付账户）打分。高风险走验证、排队或直接拒绝。
- 事后处置：异步处罚加名单沉淀，配合订单侧的人工审核与回收。

收尾强调：所有防刷都是概率与成本的博弈，关键是把“绕过前端”的边际收益打下来。一次性令牌、限购校验和风控这三层必须在服务端。

## Q04：局域网下（同一 IP）大量用户同时抢购，IP 限流策略怎么设计？

### 面试回答

核心判断是 IP 不等于用户。校园网、企业出口、机房代理池背后，同一个 IP 可能是几百个真实用户，也可能是几十个伪造来源的脚本。所以 IP 只能当“异常维度”，不能作为唯一的限流键。

设计上分四步：

- 主限流维度用身份：登录用户 UID、设备指纹、账号信誉，一人一配额，正常用户互不影响。
- IP／CIDR 维度做兜底阈值：按该 IP 历史正常并发基线放大若干倍设阈；同 C 段归并聚合，避免只按单 IP 精确匹配被换 IP 绕过。
- 分级处置而不是一刀切：超过 IP 配额不直接拒绝服务，而是把该来源的增量请求降级为“排队／出验证／限缩库存可见性”，可疑比例越高越严。白名单（已知校园网、企业出口）单独登记，走宽松策略。
- 度量误伤：把“被限流后申诉量”“同 IP 真实用户成功率”作为指标盯着，阈值随流量曲线动态调整，而不是一开始拍一个常数。

实现上用 Redis 集中计数，保证多实例一致：滑动窗口或令牌桶，按维度组合成 key（IP＋活动、UID＋活动）。限流判定放在网关或统一切面。本地缓存做兜底，以防 Redis 抖动时退化为“宽松放行＋核心链路保护”。

同一活动的热点 key 处理另见热 Key 专题。

## Q05：高并发场景下热 Key 问题会对系统产生什么影响，怎么解决？

### 面试回答

先界定：热 Key 是某个 key 的访问量远超其它 key，典型场景是秒杀商品详情、爆款内容、活动配置。

危害不在于数据大，而在于访问集中：

- Redis 处理命令是单线程，Cluster 又按 slot（哈希槽）分片，一个热 key 只会落在一个分片上。
- 结果是把该分片的 CPU／网卡／连接打满：集群整体 QPS 不高，但这个节点延迟飙升、其它 key 被拖慢。
- 它常伴随失效重建风暴：过期的瞬间大量请求穿透到数据库，形成级联雪崩。
- 写热 key 同理：单 key 或单行的写被串行化，并放大锁竞争。

解决按“探测＋分摊＋下沉”三层：

- 探测：靠监控统计——客户端埋点、`redis-cli --hotkeys`／`--bigkeys` 采样、云上热 key 分析。先确认是真的读热还是写热。
- 分摊，三条路一起用：
  - 本地多级缓存：把热数据放进应用进程内的 Caffeine，用短 TTL＋异步刷新容忍短暂陈旧。这是最有效的一招。
  - key 拆分打散：把库存或详情拆成 `key#0..N`，让请求散到不同分片，读取时随机后缀。
  - 只读副本与多副本 key 分摊读。
- 下沉与兜底：
  - 逻辑过期／互斥重建，防击穿。
  - 请求合并（singleflight，同一时刻只放行一次回源）。
  - 预热，避免冷启即峰值。
  - 写热用攒批或异步队列合并写。

最后给边界：本地缓存换来的是一致性窗口，多级缓存就要配套失效广播（见 SYS-009），不能只说“加个本地缓存”。

## Q06：除了下单环节，整个秒杀链路还有哪些环节可能存在性能瓶颈或挑战？

### 面试回答

按请求走过的顺序盘一遍，比只讲“下单”更能显示容量意识。

- 客户端与静态层：活动页资源、图片、JS 未上 CDN 时，回源带宽先打满；解析与渲染慢，会导致用户在开抢瞬间集中重试。
- 接入层：网关连接数与 TLS 握手——新建连接风暴、有没有开会话复用；限流组件本身可能成为串行点。
- 鉴权层：token 校验／会话查询是每次请求都要打的同步依赖。Redis 会话或权限服务被打爆，会放大成全站故障。
- 资格校验层：查会员等级、优惠券、黑名单往往是跨服务的同步 RPC，一个慢下游就能拖住线程池。
- 库存层：Redis 单 key 串行与 Lua 排队、集群单分片热点；数据库侧是热点行锁等待。
- 订单与存储层：
  - 主键生成（号段／雪花时钟回拨）。
  - 分库分表路由有没有让写集中在一个分片。
  - 单库写能力上限。
  - 从库延迟造成“已下单但查不到”。
- 消息层：
  - 生产端网络与刷盘配置。
  - Broker 分区数决定消费并行度上限。
  - 消费者数量与批大小。
  - 积压后最老消息的年龄。
- 下游依赖：积分、券、风控、推送等被秒杀流量放大，需要能降级或异步化。
- 外部回调：支付回调乱序与重试，要求状态机幂等。
- 任务与运维层：对账回补、库存释放、活动开关的时效。

定位方法统一：逐层压测，找出最小容量环节，算出各层水位（不能只看网关 QPS）；再配套超时与熔断、可观测指标和活动开关兜底。

## Q07：秒杀正式开始前，如何应对用户不断刷新页面等行为带来的流量冲击？

### 面试回答

开抢前的流量特征是“读多写零且高度重复”：几十万人反复刷新同一份活动详情。处理思路是让这些请求根本不落到业务链路。

- 页面与数据静态化：活动详情、商品图、规则文案生成静态文件，走 CDN 与浏览器缓存，用户刷新命中边缘节点。动态接口只保留“是否开始、是否售罄、我的状态”三个极小查询。
- 时间口径统一到服务端：按钮态由服务端下发时间判定，未开始直接返回统一结果且不回源，避免各客户端时钟不齐造成的“提前打接口”。
- 请求整形：
  - 把固定间隔轮询改成带随机抖动的退避。
  - 前端做节流与合并刷新。
  - 服务端对同一时刻的并发相同查询做请求合并（singleflight／只回源一次）。
- 缓存预热与扩容：
  - 活动前把热点数据预热进 Redis 和应用本地缓存。
  - 连接池、线程池、JIT 与下游凭据缓存都提前暖机。
  - 按压测水位扩容并压测定级。
- 兜底与降级：准备静态兜底页与默认文案，详情查询失败时返回缓存旧值，而不是报错打穿数据库。
- 入口限流按维度分开：刷新类只读接口的配额，和下单类写接口的配额分离统计，防止刷页面把写路径的额度挤占。
- 异常流量治理：高频刷新的 IP／设备走风控评分，超阈值降速或出验证；但真实用户刷新只记指标、不断服务。

一句话收口：开抢前的冲击本质是“把重复读全部往上层收敛”，开抢后的冲击才需要限流与削峰来兜。

## Q08：为什么决定做这个 Agent 项目？

项目动机、需求来源与本人职责未记录，以下为可填写框架，不代为虚构立项理由。

### 面试回答

## Q09：怎么用 Graph 框架来设计和控制任务流程的？

原素材未记录用的是哪个 Graph 框架（LangGraph 或 Spring AI Alibaba Graph）与图的真实拓扑，以下按通用 Graph 建模作答，实现细节按【真实项目】替换。

### 面试回答

我的建模方法是：先划节点、再定状态、最后加控制。

节点粒度按“可独立重试、可观测、状态可合并”来切：

- 一个节点只做一件事：一次模型调用、一次工具执行、或一次纯函数转换。
- 副作用（写库、发消息）单独成节点，这样失败重放不会重复扣款。

边分两类：

- 固定边，表达确定的流转。
- 条件边，把路由判断做成显式的分支函数，而不是把 if-else 埋在提示词里。这样流程图本身就是可读的编排逻辑。

状态是第三等公民：

- 定义共享 State，并给每个 key 指定合并策略——覆盖／追加／归并。
- 并行分支的写入靠 reducer（合并函数）合起来，而不是隐式互相覆盖。

控制手段主要四件：

- 编译期校验图的连通性与合法性，避免上线才发现死分支。
- 超步（super-step，一轮全局推进）推进，加最大迭代数防循环爆炸。
- 检查点按会话线程落快照，支持断点恢复与回溯。
- interrupt／人在环：把需要审批的节点挂起，等外部输入再续跑。

输出侧用流式（事件流）把节点进度透出去，改善体感。

对比裸写链式 Prompt 的收益，就是把路由、重试、状态与恢复显式化。代价是编排复杂度上移，简单两三步任务不值得上图。所以我先问自己一句：这个流程有没有循环、分支和需要人工确认的点。

## Q10：RAG 知识引擎包含了哪些核心功能？

“知识引擎”是本人项目里的叫法，具体范围按【真实实现】裁剪，未做的模块要明说没做。

### 面试回答

我把它分成离线、在线、支撑三块讲。

离线是知识生产：

- 多源接入：文档、网页、表格、代码、FAQ、图片。
- 解析与去噪：版式还原、表格结构化、OCR。
- 切块，并保留标题路径／文档 ID／版本／权限等元数据。
- 去重与冲突检测。
- 向量化与关键词双索引。
- 增量更新：文档变更要同步清理旧块与失效向量。

在线是查询服务：

- 问题理解与改写：消解指代、补全条件。
- 按意图和知识类型做路由。
- 混合召回：向量＋关键词＋元数据过滤。
- 重排与去冗余。
- 上下文组装与 token 预算控制。
- 带引用的生成；证据不足时拒答或澄清。

支撑面容易被忽略，但面试值得说：

- 分层评测：召回命中、证据充分、答案是否被证据支持，分开算。
- 可观测：每步耗时、成本、无结果率。
- badcase 回流成回归集。
- 知识治理：版本、时效、权限、来源可信度分级。

被问“最难的是什么”时，答“证据质量与可评估性”比答“换了个向量模型”更有说服力。

## Q11：知识库内容庞杂、包含多种类型时，如何智能判断并优先提供最相关的知识？

### 面试回答

思路一句话：入库时就把知识分好类，查询时做路由，融合时给优先级。而不是把所有片段丢进一个向量库拼分数。

- 入库侧打标：给每条知识登记类型（制度文档／操作指引／FAQ／表格／代码／图表）、来源权威度、时效与生效状态、权限域。
- 这些是结构化 metadata，不塞进 embedding。
- 查询侧识别：
  - 先用规则＋小模型或 LLM 做意图分类，判断这个问题该问哪类知识、要不要走结构化查询。
  - 数值、清单类问题走 SQL／表格检索，而不是向量。
  - 再据此选库、选索引、下推元数据过滤条件。
  - 判不准时多路并行召回，而不是押一条。
- 融合与优先级：各路结果统一重排，排序分数不只看语义相关，还叠加来源权威度、时效、是否命中用户上下文与权限。
- 配额：给每类结果设 top-k 名额分配，避免海量 FAQ 挤掉少量高质量规范文档。
- 冲突仲裁：同一事实多来源冲突时，按“新版覆盖旧版、权威源优先”处理，并把冲突显式提示。
- 闭环：按知识类型分层建评测集，看每类的命中率与引用支持率。路由判错本身就是一种需要归因的失败类型。

要主动补一句边界：类型判断错会让“本该检到的”直接漏检。所以宁可保守地多召回再重排，也别在路由层做硬闸。

## Q12：讲一下 MCP 的实际开发或集成经验。

原素材未记录候选人做过哪些 MCP Server／Client，以下为可复用的落地口径框架，具体项目按【真实实现】填写；不虚构做过的事。

### 面试回答

讲经验要落到“我怎么把一个已有服务，变成可被模型调用的工具”。我的路径是这样：

- 先切边界：把内部 HTTP 服务或 Spring Bean 的能力，按业务动作粒度整理成工具清单。
- 每个工具写清 name、description 和 inputSchema（JSON Schema，入参结构声明）。描述是给模型看的，要写“什么时候该用它、参数含义与取值范围”，而不是复制接口注释。
- 选传输形态：本机或桌面客户端接就用 stdio；多个应用共用或跨网络就用远程 Streamable HTTP。后者要考虑会话（Mcp-Session-Id）、多实例路由与长连接。
- 用官方 SDK／Spring AI 的 MCP starter 少造轮子：框架负责协议握手与能力协商（initialize、tools／resources／prompts 的发现）。
- 我负责参数校验、权限、幂等和错误语义：协议层错误与工具执行失败（结果里的 isError）要分开表达；超时的写操作不能假定没生效。
- 调试与联调：用 MCP Inspector 看请求报文、验证 schema 是否被宿主正确翻译成工具描述、检查工具数变化是否触发 list_changed 通知。
- 鉴权与治理：内网可先静态密钥或网关透传身份，但每次调用必须能回答“代表哪个用户、能不能碰这条数据”。服务端做资源归属校验，而不是把高权限凭据透传下去。
- 上线后关心三件事：工具被误选怎么办、描述变更后模型行为是否回归、以及调用量与失败率。

没做过的模块（动态注册、OAuth 2.1 全流程）就直说“了解规范但项目里未落地”。

## Q13：MCP 与传统 Function Calling 在工具调用层面主要有什么区别和优势？

### 面试回答

两者不在同一层，先说层、再说优势。

- Function Calling 是模型 API 的能力：宿主把工具描述注入，模型输出“函数名＋参数”的结构化意图。参数校验、执行、结果回填全在应用侧，模型只表达“我要用哪个工具”。
- MCP 是应用与外部工具／数据服务之间的接入协议，基于 JSON-RPC 标准化的发现、调用与错误语义。它把“工具怎么被描述、怎么被调用、怎么鉴权”从各家私有胶水变成公共约定。

优势有四点：

- 跨宿主复用：同一个 Server 可被不同客户端、不同模型接入，不必为每个应用重写一遍适配。
- 职责边界清晰：执行权、幂等、权限校验收敛在 Server 端，凭据不必暴露进模型上下文。
- 能力不止函数：除 tools 外还有 resources（可读数据源）与 prompts（模板），并能用 list_changed 动态更新工具清单，宿主按需翻译为模型的工具描述。
- 进程与语言解耦：工具服务可独立部署、扩缩与治理。

代价也要讲：

- 多一层协议与进程开销，链路排查要看协议报文。
- 工具多了，依然受宿主上下文预算与模型选错工具的限制。
- MCP 不解决“模型是否会用对”的问题。

最后收口：Function Calling 解决“模型如何表达调用”，MCP 解决“应用如何标准化接工具”。实践中是组合关系——模型出意图，宿主经 MCP 转成对 Server 的请求。
