## Q02：Java 的 List 有哪些实现？分别适合哪些应用场景？

### 面试回答

结论：常用的是 ArrayList、LinkedList，再加线程安全的 CopyOnWriteArrayList 和历史遗留的 Vector；按「随机访问多还是头尾插删多、要不要并发」选型。

- ArrayList：动态数组，按下标访问 O(1)，尾部追加摊还 O(1)；中间插删要搬元素 O(n)。绝大多数场景的默认选择。
- LinkedList：双向链表，持有迭代器时头尾插删和 remove 当前节点 O(1)；按下标访问要遍历。当作双端队列用不如 ArrayDeque。
- CopyOnWriteArrayList：写时复制整个数组，读完全无锁；适合读极多写极少的列表（监听器、白名单）。
- Vector／Hashtable 这类旧同步容器如实带过：方法级粗粒度锁，并发场景已被 j.u.c 容器取代。

## Q03：谈谈 HashMap 的底层数据结构

### 面试回答

结论：JDK 8 是「数组＋链表＋红黑树」，桶数组是主体，冲突挂在桶上，链太长才树化。

- 定位：key 的 hashCode 高 16 位异或低 16 位扰动后，用 `(n-1) & hash` 取桶下标；容量恒为 2 的幂。
- 同桶冲突挂单链表；链表长度到 8 且表容量到 64 才转红黑树，缩回 6 变回链表。
- 元素数超过容量×负载因子（默认 0.75）触发扩容翻倍。
- 允许一个 null key（固定在下标 0 桶）；迭代无序；非线程安全。

## Q04：什么是哈希冲突？有哪些解决哈希冲突的方案？

### 面试回答

结论：不同 key 算出同一个桶下标就是冲突——哈希表是压缩映射，桶数有限，冲突不可避免，只能处理。

- 链地址法：同桶挂链表，JDK HashMap 采用；删除干净、容忍高装载因子，代价是指针跳转缓存不友好。
- 开放寻址：冲突就在数组里往后探空槽（线性探测、二次探测、双重哈希）；内存紧凑局部性好，但要压装载因子、删除留墓碑。
- 再补一句工程手段：扰动函数、扩容摊薄冲突，从源头降低冲突概率。

## Q05：为什么 HashMap 要把链表转为红黑树？红黑树相比其它树结构的优势是什么？

### 面试回答

结论：树化是给「冲突堆成链」兜底，把最坏查找从 O(n) 压到 O(log n)；选红黑树是查 AVL 的写放大、B 树的单行查找、普通 BST 的退化风险之后的平衡选择。

- 触发条件：链长到 8 且表容量≥64 才树化——正常哈希下链到 8 概率极低，是防哈希质量差的保险。
- 相比 AVL：红黑树旋转次数更少，插删代价低；HashMap 键分布会变、读写混多，不只读。
- 相比普通 BST：红黑树保证最长路径不超最短两倍，不会被插入顺序退化成链。
- 相比 B+ 树：B+ 树为磁盘块设计，内存单行场景没优势还更复杂。

## Q06：HashMap 在多线程环境下存在哪些问题？

### 面试回答

结论：丢更新、读到旧值、size 不准这些一个不少；JDK 7 还会在并发扩容时把链表接成环导致 get 死循环。

- 两个线程同时 put 同一个空桶：都判断为空，后写的把先写的覆盖掉——没有任何锁保护。
- 可见性无保证：一个线程写完，另一个可能还读到旧表旧值。
- JDK 7 头插法在并发扩容下可能成环，get 死循环 CPU 打满；JDK 8 尾插＋拆链不再成环，但只是去掉最恶性的一种。
- 出路：并发场景换 ConcurrentHashMap，或把全部读写收敛到同一把锁；给写加锁读绕过不是正确协议。

## Q07：ConcurrentHashMap 的锁是怎么加的？

### 面试回答

结论：JDK 8 起不再是分段锁——桶为空直接 CAS 放入，不加锁；桶已有节点，只对这条链／树的头节点 synchronized，锁粒度是一个桶。

- 扩容迁移中的桶有 ForwardingNode 占位，写线程先协助迁移完再重试。
- get 一般不加锁，靠 table 元素自身的可见性读到已发布节点。
- 别再用 JDK 7 的 Segment 分段锁口径描述它，那是老实现。
- 补一句边界：单次调用线程安全，「先 get 再 put」的多步逻辑仍要换 putIfAbsent／compute 系列。

## Q08：谈谈 synchronized 的原理

### 面试回答

结论：synchronized 是语言级的监视器锁，锁状态记在对象头 Mark Word 里，字节码层是 monitorenter／monitorexit 或方法的 ACC_SYNCHRONIZED 标志。

- 同步代码块编译成 `monitorenter`／`monitorexit`（异常表保证必退出）；同步方法靠 `ACC_SYNCHRONIZED` 标志。
- 运行时每个对象关联一个 monitor：持有计数支持重入，等待队列实现阻塞，退出时释放并建立可见性。
- 锁的是对象引用（this／Class／指定对象），不是代码——锁对象身份不同就不互斥。
- 口径声明：以上是 HotSpot 的实现细节，JVMS 只规定语义，答题注明版本。

## Q09：谈谈 synchronized 的锁升级机制

### 面试回答

结论：锁升级是 HotSpot 按竞争激烈程度让 Mark Word 在「无锁 →（偏向）→ 轻量级 → 重量级」单向演进，核心动机是低竞争时别惊动操作系统。

- 轻量级锁：CAS 把 Mark Word 拷进线程栈的锁记录，抢不到就自旋重试——适合极短临界区。
- 自旋失败／竞争加剧就膨胀成重量级锁：依赖 OS mutex 的 monitor，抢不到直接挂起阻塞。
- 偏向锁当年为「始终单线程重入」设计，撤销要走 safepoint、收益不匹配，JDK 15 起废弃（JEP 374）。
- 只升不降：膨胀成重量级后一般不回退（仅在 monitor 整体无竞争的罕见条件下回收），别说成「竞争消失自动降级」。

## Q10：谈谈对 Redis 的理解

### 面试回答

结论：按「是什么→为什么快→能干什么→要注意什么」四层讲，每层一两句就够。

- 是什么：基于内存的键值数据结构服务，常做缓存、计数、分布式协调，也支持持久化。
- 为什么快：数据在内存、单线程命令执行免锁竞争、IO 多路复用撑并发、高效内部编码。
- 能干什么：五种基本类型加 Bitmap／HyperLogLog／GEO／Stream，落点是缓存、排行榜、签到、限流、分布式锁这些真实场景。
- 注意点：容量有界要配淘汰策略；缓存与库的一致性、穿透／击穿／雪崩、big key 与热 key 是使用中真正要设计的。

## Q11：Redis 两种持久化方式的区别及各自优缺点

### 面试回答

结论：RDB 是某时刻全量快照，AOF 是写命令追加日志——恢复速度与数据安全不可兼得，生产上常两者同开。

- RDB：fork 子进程二进制落盘，文件小恢复快；缺点是两次快照之间的数据会丢，fork 大堆有瞬时开销。
- AOF：默认 everysec 刷盘，最多约丢一秒；文件大恢复慢，靠重写压缩；比 RDB 更保数据。
- 组合口径：先用 RDB 做底座快速恢复，再用 AOF 补齐最近增量。
- 提醒：持久化解决的是重启丢数据，不解决高可用——那要看主从／哨兵／Cluster。

## Q12：什么是缓存穿透？如何解决？

### 面试回答

结论：穿透是请求根本不存在的数据——缓存永远不命中，每次都打到数据库，恶意伪造不存在的 ID 可以打垮 DB。

- 参数校验：非法 ID 在入口直接拒掉。
- 空值缓存：查库为空也缓存一个短 TTL 的空标记。
- 布隆过滤器：请求先过过滤器，判不存在直接返回；但有假阳性，不能算「完全解决」。
- 兜底：对回源路径限流，别让穿透流量裸奔到数据库。

## Q13：如何利用 Redis 设计分布式锁？需要注意哪些地方？

### 面试回答

结论：`SET key value NX EX ttl` 一条命令拿锁——NX 保互斥、EX 防死锁、value 放唯一标识；难点全在「不误删、不漏续、不锁错」。

- 解锁用 Lua：先比对 value 是自己的持有标识再删，否则 TTL 过期后会把别人的锁删掉。
- 看门狗续期：业务没干完锁先过期是常态，Redisson 自动续期解决这一类问题。
- 主从切换会丢锁：Redis 锁是「高效优先」不是「绝对正确」，强正确场景考虑 ZooKeeper 或数据库约束兜底。
- 锁只保护单入口：所有改这份数据的路径都要走同一把锁，且别拿 Redis 锁当分布式事务用。

## Q14：谈谈对 Spring IOC 的理解

### 面试回答

结论：IoC 是把对象的创建和依赖装配从代码里拿出来交给容器，DI 是它的落地方式——类只声明「我需要什么」，不再自己 new。

- 容器流程：读配置形成 BeanDefinition，实例化、注入依赖、初始化与后处理，按作用域管理到销毁。
- 好处一句话：解耦、可替换（面向接口＋注入）、可统一织入代理（AOP 靠的就是容器的后处理）。
- ApplicationContext 在 BeanFactory 之上补了事件、国际化等企业能力，日常用它。
- 边界：单例不自动线程安全；构造器注入的循环依赖容器也解不开。

## Q15：IOC 在做项目的过程中有哪些应用场景？

### 面试回答

结论：项目里的落点就是「换实现不改调用方、横切逻辑统一织入、对象交给容器管生命周期」这三类。

- 面向接口多实现：Service 依赖接口，【支付渠道／存储／消息发送】的实现用配置或 `@Primary`／Qualifier 切换，测试时注入 Mock。
- 横切能力织入：事务、日志、限流靠注解＋代理统一做，不用每个方法手写（AOP 建立在容器后处理之上）。
- 统一管理生命周期与配置：连接池、线程池这类重资源做成 Bean 由容器创建销毁；`@Value`／配置类把环境差异注入出去。
- 事件解耦：`ApplicationEventPublisher` 发布事件，让协作方不直接依赖彼此。

## Q16：什么是循环依赖？Spring 是如何解决循环依赖的？

### 面试回答

结论：A 依赖 B、B 又依赖 A 就是循环依赖；Spring 用三级缓存对「单例＋属性注入」的环提前暴露早期引用来解开，但别把它当万能药。

- 能解的：单例作用域、setter／字段注入的环——A 先实例化，属性没填完就能被 B 拿到早期引用。
- 解不开的：构造器注入的环（对象还没造出来）、原型作用域的环、部分代理复杂情形。
- 第三层缓存放的是 ObjectFactory，作用是让后处理器按需产出代理，协调早期引用和最终代理一致。
- 正确姿势排序：首选拆职责消环，其次 `@Lazy`／`ObjectProvider` 延后解析；Boot 2.6 起默认禁用循环引用，打开开关不等于修好设计问题。

关联专题：[[专题题库/Spring#SPRING-006：Spring 如何处理循环依赖，如何解决？|SPRING-006：Spring 如何处理循环依赖，如何解决？]]
