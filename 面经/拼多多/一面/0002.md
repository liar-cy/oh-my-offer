## Q05：项目里为什么用 synchronized 加锁？锁的机制保护什么？为什么选 synchronized 而不是其它锁？

### 面试回答

为什么加锁——一句话：有共享可变状态，且访问是复合操作，不锁就会互相踩。

- 场景：【项目里多线程并发访问 XX（共享变量／连接／文件），按实际填】。
- 不加锁的后果：读—改—写被交错，出现更新丢失、脏读，数据不一致。
- 锁机制的本质：同一时刻只允许一个线程进入临界区（互斥），并且解锁前的写入对下一个加锁者可见（可见性）——它防的就是“并发交错”和“看不见别人的修改”两件事。

为什么选 synchronized 而不是别的锁：

- 需求只是简单互斥，synchronized 是语言级关键字：自动加解锁，不会忘 unlock，退出作用域必然释放。
- ReentrantLock 的增值能力——可中断、超时 tryLock、公平策略、多 Condition——这个场景都用不上；用不上就不付那份复杂度。
- 一句话收尾：按语义选型，不按“谁高级”。

## Q06：Java 里除了 synchronized 还了解哪些锁？公平锁、非公平锁、轻量级锁、自旋锁各是什么，synchronized 属于哪种？

### 面试回答

先声明“按维度答，不按名字背”，再给每类一句话：

- 乐观 vs 悲观：CAS／版本号失败再重试 vs 先加锁再操作；synchronized 是悲观锁。
- 阻塞 vs 自旋：拿不到挂起 vs 忙等重试；synchronized 是“先自旋后阻塞”的混合。
- 可重入 vs 不可重入：synchronized 可重入，同线程再次进入不死锁。
- 公平 vs 非公平：synchronized 没有公平选项（队列近似非公平）；ReentrantLock 可选。
- 独占 vs 共享：读写锁读读并行；synchronized 是独占。
- 偏向／轻量／重量（锁状态，HotSpot 实现层）：synchronized 会经历“无锁 → 轻量级 → 重量级”的升级（偏向锁 JDK 15 起废弃）。

收尾给归属：synchronized ＝悲观、可重入、独占、会做锁升级的监视器锁。维度是横切的，一把锁同时落在多个维度里。

## Q07：轻量级锁自旋获取会消耗 CPU 吗？有什么问题？自旋适合什么场景、什么时候无效？

### 面试回答

会消耗，而且问题可以说透：

- 自旋就是忙等：拿不到锁就循环重试，这段时间 CPU 不闲下来。
- 核心矛盾：短等待时自旋省掉了挂起—上下文切换—唤醒的开销；等待一长，它就变成纯粹烧 CPU，还抢占了本来可以干活的核。
- 所以 HotSpot 用自适应自旋：旋转让 JVM 根据“上一轮在这把锁上是否成功、等了多久”动态调整，不会无限空转；升级竞争后干脆膨胀成重量级锁去挂起。

适用判断给两条标准：

- 有效：临界区短、持锁时间确定地小、核数富余——等一会儿就轮到我。
- 无效：临界区长或不可预期（里面有 IO、锁内查询）、线程数明显多于核数、高竞争——此时挂起比忙等礼貌，纯烧 CPU。
- 推广到 CAS 同理：低竞争漂亮，高竞争空转，所以高竞争要么换锁、要么分段降冲突。

## Q08：谈谈 ReentrantLock 的公平锁和非公平锁。

### 面试回答

- 公平锁：新来的线程先看同步队列里有没有人排队，有就排到队尾——先来先到，代价是每次都要唤醒排队，吞吐低。
- 非公平锁（默认）：进来先 CAS 抢一次，抢不到再排队——允许插队，吞吐高，队首可能饿。
- 为什么非公平更快：唤醒一个挂起线程有延迟，插队的线程正好利用这段空窗，减少整体等待与切换。
- 用法边界：`new ReentrantLock(true)` 开公平；业务里绝大多数用默认非公平，除非明确接受不了饥饿（如排队公平性有业务含义）。

## Q09：手撕：单链表从尾部开始每两个节点位置翻转，O(n)／O(1)（示例 1,2,3,4 → 2,1,4,3）。

### 面试回答

先看示例：`1,2,3,4 → 2,1,4,3`，效果就是相邻两两交换（LeetCode 24 Swap Pairs）；“从尾部开始”不改变结果——成对交换互不重叠，从哪端处理输出一样。答题前把这句口径说出来。

- 迭代解法：建哑结点 dummy 指向头，维护 pre 指针；每轮摘 (pre.next, pre.next.next) 一对交换接回，pre 前移两步。
- 时间 O(n)、指针变量常数个，空间 O(1)，满足约束。
- 口径确认（答题时主动问面试官）：允许只交换节点值吗？允许的话实现更短，但工程上值可能很大／被共享，稳妥答法是改指针。

```java
ListNode swapPairs(ListNode head) {
    ListNode dummy = new ListNode(0, head), pre = dummy;
    while (pre.next != null && pre.next.next != null) {
        ListNode first = pre.next, second = pre.next.next;
        pre.next = second;
        first.next = second.next;
        second.next = first;
        pre = first;
    }
    return dummy.next;
}
```

- 边界：空链表、单节点原样返回；奇数长度最后一节点不动（1,2,3 → 2,1,3）。
- 追问预案：若原题实为“从尾部计数配对”（长度奇偶不同起点），先反转再两两交换再反转回去，同样 O(n)／O(1)。

## Q10：静态内部类和非静态内部类的调用区别？

### 面试回答

一句话：区别在“要不要外部实例”。

- 非静态内部类：
  - 持有外部类实例的隐式引用（Outer.this），必须通过外部实例创建——`new Outer().new Inner()`。
  - 能直接访问外部实例字段。
  - 自己不能声明静态成员（除非编译期常量）。
- 静态内部类：不持有外部引用，就是个挂在外部类命名空间下的普通类——`new Outer.StaticInner()` 直接创建；只能访问外部类静态成员。
- 调用侧后果：非静态内部类实例的生命周期被外部实例牵着，回调／缓存场景容易把外部大对象一起钉住造成泄漏；静态内部类没这个问题。
- 实践默认值：优先写成静态内部类（本项目里若内部类只服务数据结构／Builder，应 static）；需要访问外部实例状态或做模板方法骨架时才用非静态。

## Q11：Java 异常怎么处理？update 超时异常属于受检还是非受检？有哪些受检异常？什么时候向上传递、什么时候自己处理？不处理的后果？

### 面试回答

先给观念（原问题 14）：

- 异常体系：Throwable 下 Error（OOM／栈溢出，不该接）和 Exception；Exception 分受检（编译器强制处理）与非受检（RuntimeException 系）。
- 处理思路：在“有能力做出正确决策”的那一层处理，其余层次翻译后上抛。

超时算哪类（原问题 15，答“看入口”）：

- 底层 IO 超时本身是受检：`SocketTimeoutException` 是 IOException 的子类。
- 但经 JDBC／Spring 包装后通常变非受检：SQLException 受检，Spring 翻译成 `DataAccessException` 系（Runtime）。
- 所以“调一个 update 超时”在你的业务代码里大多以非受检形态出现——这题考的是你知不知道“受检性看 API 层”，不是背类名。

常见受检异常点名（原问题 16）：

- IOException 家族（FileNotFound、SocketTimeout）。
- SQLException。
- ClassNotFoundException。
- InterruptedException。
- 以及自定义 checked。

传递还是自己处理（原问题 18）：

- 自己处理：这一层有明确补救动作——重试、换源、降级、补偿，处理完流程能继续。
- 向上传递：不知道怎么办、或恢复需要更高层的上下文（事务回滚、给用户报错）；不要在中层 catch 掉只打一行日志就吞了。
- 边界：对外接口出口必须收敛（全局异常处理转统一响应码），不能让堆栈穿透给用户。

不处理的后果（原问题 19）：

- 异常沿调用栈上抛，任何一层都没接住时终结当前线程：默认处理器打印堆栈到 stderr，线程死亡。
- 连带风险：主线程不受影响但业务线程池 worker 死一个补一个；`finally`／try-with-resources 仍会执行，但被跳过的收尾逻辑（状态更新、计数）可能永久残缺。
- Web／服务容器通常有兜底 handler，对用户表现为 5xx；但事务半提交、资源没还这类脏状态没人替你收拾——这就是“出口必须自己收敛异常”的原因。

## Q12：谈谈 SpringBoot 有哪些关键特性。

### 面试回答

按“解决什么问题”报四个主特性，加一个加分项：

- 自动装配：starter 聚合依赖＋条件化配置（`@EnableAutoConfiguration`），依赖进来配置就生效，告别 XML 大海捞针（原理见 SPRING-001）。
- 起步依赖与版本仲裁：`spring-boot-starter-parent` 统一管理依赖版本，避免“两个库各带一个 Jackson 版本”的冲突地狱。
- 内嵌容器：Tomcat／Jetty／Undertow 打进 jar，`java -jar` 直接跑，不需要外置 war 部署。
- 约定优于配置：默认值覆盖 80% 场景，`application.yml` 只写例外；配 Actuator 提供健康检查／指标端点，方便运维接入。
- 加分收尾：这些特性合起来解决的是“Spring 配置成本高、部署重”的老问题，让微服务从脚手架到上线的路径标准化。

## Q13：谈谈对 Java GC 的理解；什么样的对象可以作为 GC Roots？

### 面试回答

理解 GC 分四层说，别背散点：

- 判活：从 GC Roots 做可达性分析，不可达即可回收。
- Roots 具体是谁：活动线程的栈上局部变量／参数、静态变量、JNI 引用、活跃监视器、（分代收集时）老年代指向年轻代的记忆集引用；跨代引用靠卡表记录进 Roots 集合。
- 回收算法：标记清除（碎片）、复制（浪费空间换规整）、标记整理（不搬死对象压实）；新生代复制、老年代整理是基本盘。
- 工程取舍：分代假设＋选收集器就是选“停顿 vs 吞吐 vs 内存开销”的组合，G1／ZGC 演进主线见 JVM-010。

一句收尾：GC 管理的是堆上对象生命周期，不是“帮你防内存泄漏”——可达但不该活的它管不了（见 JVM-005）。

## Q14：为什么 JVM 要分代？从写代码角度怎么管理对象才对 GC 友好？

### 面试回答

为什么分代：

- 依据是弱分代假说——绝大多数对象朝生夕死，熬过几轮 GC 的会长久存活。
- 假设成立后策略就能分化：新生代小而勤快（Minor GC 用复制算法，成本只和存活对象数挂钩、天然无碎片），老年代大而从容（整理式回收）。
- 不分代的话，每次回收都要扫全堆：要么停顿无法接受，要么永远等不到一次“便宜”的局部回收。

对 GC 友好的写法，按“让它少干活”组织：

- 少造长寿垃圾：无界集合、static 缓存不逐出是老年代持续增长的头号来源。
- 让短命对象别晋升：方法内小对象放心 new；大批量中转数据用完即弃、别挂到长生命周期字段上。
- 缓存加边界：容量上限＋逐出策略（Caffeine 这类），而不是全量堆内存。
- 别囤大对象：大数组／大 List 直达老年代，回收贵还造成碎片；分批、流式处理。
- 热点分配复用：StringBuilder 代替字符串拼接、池化昂贵资源（线程、连接）——但池是有上限的复用，不是囤积。
