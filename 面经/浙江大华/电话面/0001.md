## Q02：谈谈图数据库和关系型数据库的差异

### 面试回答

结论：差异的核心是“关系是一等公民还是外键拼接”——图数据库把边存成可遍历的一级结构，多跳关系查询 O(邻接)；关系型靠 join，多跳代价指数级。

- 数据模型：图＝点＋边＋属性，天然表达网络；关系型＝二维表，关系靠外键与 join 还原。
- 查询模式：图库擅长“以某点为中心向外扩 N 跳”（好友的好友、风控关联、最短路径）；关系型擅长集合运算（过滤、聚合、事务写入）。
- 性能机理：图库“免索引邻接”——遍历沿指针走，不吃全表扫描；关系型多跳 join 中间结果膨胀。
- 生态与约束：关系型有 SQL、事务与工具成熟度优势；图库（Neo4j 等）生态小、写入吞吐与复杂聚合通常弱一些。
- 选型一句话：查询里频繁出现“关系的关系”上图，报表与强事务用关系型，很多系统是两者搭配。

## Q04：哪些集合是线程安全的？

### 面试回答

结论：按“历史遗留／并发优化／只读不可变”三类报。

- Vector、Hashtable 是旧的全表锁。
- ConcurrentHashMap、CopyOnWriteArrayList、阻塞队列是细粒度的现代方案。
- 不可变集合天然安全。

- 遗留类：`Vector`、`Hashtable`、`Stack`——方法级 `synchronized` 锁整张表，性能差，新代码不用。
- 并发优化类：`ConcurrentHashMap`（CAS＋桶头 synchronized）、`CopyOnWriteArrayList`（写时复制，读多写少）、`BlockingQueue` 家族（`ArrayBlockingQueue`／`LinkedBlockingQueue` 等，生产者消费者标配）。
- 工具类：`Collections.synchronizedList/Map`——包装成单锁同步，遍历仍需手动加锁，只算“凑合安全”。
- 不可变类：`List.of()`／`Map.of()`（JDK 9＋）与 `Collections.unmodifiableList` 包装的只读视图——发布后无人改，天然线程安全。
- 收尾一句：选哪个看读写比与是否需要协作语义（阻塞、await），不是“线程安全”四个字就完事。

## Q05：ArrayList 和 LinkedList 的区别

### 面试回答

结论：底层结构不同带来操作代价互换——ArrayList 动态数组，随机访问 O(1)、中间插删要搬元素；LinkedList 双向链表，已知节点处插删 O(1)、按下标访问 O(n)。

- 内存：ArrayList 连续数组＋预留扩容（1.5 倍）；LinkedList 每节点两个指针加对象头，散点分配。
- 遍历：ArrayList 缓存友好；LinkedList 指针跳转局部性差。
- API 假象：`list.get(i)` 在 LinkedList 上是 O(n)——“循环里 get(i) 遍历 LinkedList”是典型性能坑。
- 实战口径：绝大多数场景用 ArrayList；真正两头频繁增删的队列场景，优先 `ArrayDeque` 而不是 LinkedList。
- 线程安全：两者都不安全，并发考虑回到 Q04。

## Q06：HashMap 的原理

### 面试回答

结论：数组＋链表＋红黑树——key 的哈希扰动后取模定位桶，冲突挂链，链长到 8 且表不小于 64 才树化；负载因子 0.75 触发 2 倍扩容。

- put 流程：`hash = (h ^ h>>>16)` 扰动 → 空表先初始化 16 → `(n-1) & hash` 定桶 → 空桶直接放；同桶 key 相等（hash 同且 equals 真）覆盖，否则尾插（JDK 8 起）。
- 扩容：阈值＝容量×0.75；新表 2 倍，元素新位置“要么原地、要么原地＋旧容量”，靠 hash 新增的那一位判断，不重算 hash。
- 树化／退化：链≥8 且容量≥64 树化；树≤6 退化回链——红黑树保证查找 O(log n) 且不会像 AVL 那样频繁重排。
- 边界：
  - 允许一个 null key（恒落 0 号桶）。
  - 非线程安全，并发 put 会丢数据。
  - 迭代器 fail-fast。
- 追问“为什么容量是 2 的幂”：让 `(n-1) & hash` 等价取模且分布均匀，扩容位移判断才成立。

## Q07：两个对象的 hashCode 值相等，意味着什么？它们一定相等吗？

### 面试回答

结论：只意味着它们会落进哈希表的同一类桶位置，不一定相等——hashCode 是 int 而对象空间无限，碰撞不可避免；equals 相等才要求 hashCode 必须相等。

- 规定方向：`equals` 为真 ⇒ `hashCode` 必须相等；反向不成立。
- 为什么这样约定：HashMap 先用 hash 定位桶，桶内再用 equals 区分——equals 同而 hash 不同会导致“存进去取不出来”。
- hashCode 相等的含义：可能是同一对象、可能是 hash 碰撞的不同 key、也可能是 equals 未重写的值对象（Object 默认按身份算，则相等即同一实例）。
- 实践：重写 equals 必须一起重写 hashCode，且只用 equals 用到的字段；否则 HashMap／HashSet 行为错乱。

## Q08：有哪些线程池的创建方法？

### 面试回答

结论：正解是显式 `new ThreadPoolExecutor(...)` 传满七参数；`Executors` 快捷工厂有 OOM／线程爆炸隐患被规范禁用，Spring 的 `ThreadPoolTaskExecutor` 是带生命周期的包装。

- 显式构造：corePoolSize、maximumPoolSize、keepAliveTime、unit、workQueue、threadFactory、handler 七项自己定——参数可控、队列有界。
- `Executors` 的坑：`newFixedThreadPool`／`newSingleThreadExecutor` 挂无界队列堆积 OOM；`newCachedThreadPool`／`newScheduledThreadPool` 线程数上限是 int 最大值。
- Spring 包装：`ThreadPoolTaskExecutor` 本质仍是内部构造 ThreadPoolExecutor，多了 Bean 生命周期管理与优雅关闭。
- 实践加分：`threadFactory` 给线程起业务名，方便 jstack 定位；自定义拒绝策略做日志＋报警＋降级入队。

## Q09：ThreadLocal 的使用场景

### 面试回答

结论：ThreadLocal 是“线程内的全局变量”——用空间换隔离，典型场景是上下文传递和无状态化共享；代价是线程池复用必须 remove，否则脏数据加内存泄漏。

- 常见场景：
  - 用户登录态／traceId 上下文。
  - `SimpleDateFormat` 等非线程安全工具实例每线程一份。
  - JDBC Connection、事务上下文（Spring `TransactionSynchronizationManager` 底层就是它）。
- 原理一句话：每个 Thread 持有 `ThreadLocalMap`，key 是 ThreadLocal 的弱引用、value 强引用——不 remove 时 value 可能滞留。
- 线程池坑：线程不销毁，下一次请求复用同一线程会读到上次的值——用完 finally 里 `remove()`。
- 边界：它解决“同线程内到处传参”，不解决线程间共享；异步跨线程要用 `InheritableThreadLocal`／阿里 TransmittableThreadLocal 或显式传参。

## Q10：MySQL 的事务隔离级别有哪些？什么是幻读？

### 面试回答

结论：四级别——读未提交、读已提交、可重复读（InnoDB 默认）、串行化，各自逐级消灭脏读、不可重复读、幻读；幻读是“同一条件两次查询，结果集多出／少了行”，由别人插入或删除整行造成。

- 脏读：读到未提交数据。
- 不可重复读：重读时已提交更新改了旧行值。
- 幻读：重读时新增／消失行。
- 区别记法：不可重复读针对“改”、幻读针对“增删”，都属并发读异常。
- InnoDB 的 RR 处理幻读两条路：快照读靠 MVCC 复用首次一致性读版本；当前读靠 next-key lock（记录锁＋间隙锁）挡住区间内插入。
- 别说满：RR 下“先快照读、再当前读”的交错仍可能出现类幻读现象，答题点一句“MVCC 与锁各管一条路径”更稳。
- 实际取舍：不少团队用 RC＋行模式 binlog 放弃间隙锁，把幻读防线移到业务条件更新。

## Q11：谈谈 MySQL 的索引；索引失效的场景有哪些？

### 面试回答

结论：索引按“数据结构（B+ 树）—逻辑（主键／二级、覆盖、前缀）—物理（聚簇与非聚簇）”三个维度谈；失效场景本质都是“查询条件破坏了对 B+ 树的有序利用”。

- 索引体系：
  - 主键索引叶子存整行（聚簇）。
  - 二级索引叶子存主键，查询回表。
  - 覆盖索引免回表。
  - 前缀索引省空间换区分度。
  - 联合索引按列序建树。
- 失效场景（条件侧）：
  - 对索引列用函数或运算（`WHERE YEAR(t)=2024`）。
  - 隐式类型转换（字符串列传数字、join 两侧字符集不一致）。
  - 前导通配 `LIKE '%xx'`。
- 失效场景（结构侧）：
  - 范围条件后的联合索引列不再用于过滤（最左前缀）。
  - `OR` 连接非索引列。
  - `!=`／`NOT IN` 让优化器放弃索引。
- 优化器主动放弃：统计信息过期、小表、回表成本高于扫表——“建了索引不走”不一定是语法问题。
- 排查抓手：`EXPLAIN` 看 type、key、rows、Extra（filesort／temporary 一并报警）。

## Q12：什么是乐观锁、什么是悲观锁？

### 面试回答

结论：悲观锁假设“一定会撞”，先锁再改（`SELECT ... FOR UPDATE` 行锁、synchronized）；乐观锁假设“多半不撞”，改完提交时校验（版本号／条件更新），冲突就重试或报失败。

- 悲观锁：数据库层靠 InnoDB 行锁，持锁期间他人阻塞等待——并发低、冲突高时划算；缺点是吞吐受限、有死锁风险。
- 乐观锁：实现是 `UPDATE ... SET stock=stock-1 WHERE id=? AND version=?`，影响行数为 0 即冲突；本质是把校验压进一条原子条件更新。
- 省 version 的写法：扣减类可写 `WHERE id=? AND stock>=?`，校验与更新合一。
- 选型口径：读多写少用乐观（冲突重试成本低），写冲突密集用悲观（反复重试比排队更贵）；两者都是“单行”策略，跨行跨服务要靠分布式事务。

## Q13：Redis 有哪几种持久化方式？

### 面试回答

结论：RDB 存某时刻全量快照（fork 子进程二进制落盘），AOF 存写命令日志（追加＋重写），生产常两者同开——RDB 管快速恢复与备份，AOF 管少丢数据。

- RDB：`SAVE`（阻塞主线程）／`BGSAVE`（fork 子进程，靠写时复制）；恢复快、文件紧凑，代价是崩溃会丢掉上次快照之后的数据。
- AOF：`appendfsync always／everysec（默认）／no` 决定丢数据窗口；`MATCH／REWRITE` 重写把日志压成等价最小集。
- 混合持久化（4.x 起默认开）：AOF 重写时前半段存 RDB 二进制、增量接 AOF 文本——恢复速度与丢数据窗口两头兼顾。
- 一句话边界：持久化解决“重启恢复”，不解决高可用——主从、哨兵是另一层（REDIS-011）。

## Q14：为什么 Redis 是单线程还能保证高并发？

### 面试回答

结论：Redis 的瓶颈在内存与网络 IO 而非 CPU，单线程把命令执行做成无锁串行，靠 IO 多路复用（epoll）一个线程管几万连接——省掉锁与上下文切换的开销，快得超出预期。

- 纯内存操作：单条命令微秒级，CPU 不是短板。
- IO 多路复用：`epoll` 监听海量连接，就绪的才读；读写解析单线程排队执行，命令天然原子。
- 无锁设计：并发代价全免——不需要锁竞争、线程切换，也不需要多核。
- 诚实补一句：“单线程”指命令执行主线程；RDB 的 BGSAVE fork、AOF 重写、 lazy free（UNLINK／淘汰大 key）删除、4.0 起的部分 IO 线程都不在主线程。
- 高并发上限：单命令耗时是公敌——大 key、`KEYS *`、慢脚本会卡住整个实例（危害口径见 REDIS-009）。

## Q15：RabbitMQ 的使用场景

### 面试回答

结论：MQ 三大经典用途——解耦、异步、削峰；RabbitMQ 的加分项是路由灵活（direct／topic／headers 交换机）、延迟插件、低延迟，适合业务消息与中小吞吐（百万级以下日量轻松）。

- 解耦：下单后通知积分／短信／物流，新增订阅方不改主流程。
- 异步：非关键路径（发券、推消息）扔队列，接口 RT 只留核心逻辑。
- 削峰：秒杀流量进队列，消费者按下游容量匀速拉取（配积压处理，见 SYS-005）。
- RabbitMQ 特性题眼：
  - 交换机模型＋绑定键做精细路由。
  - 死信队列／延迟插件做延时任务。
  - 事务与 confirm 机制管投递可靠。
- 边界句：日志流与超大吞吐、回放需求选 Kafka；按【项目实际】说选 RabbitMQ 的真实理由。

## Q16：有哪些 GC 算法？

### 面试回答

结论：按“怎么判断垃圾”和“怎么回收内存”两组记——判定用可达性分析（GC Roots）；回收有标记清除、复制、标记整理、分代收集四种，各治一种代价。

- 判定：可达性分析；引用链可达即存活（强软弱虚四种引用影响回收时机）。
- 标记—清除：快但产生碎片，CMS 采用。
- 复制：无碎片但浪费一半空间，适合存活率低的年轻代（Serial／ParNew／G1 的 Eden→Survivor）。
- 标记—整理：无碎片不浪费但移动成本高，老年代用（Serial Old、Parallel Scavenge 配套）。
- 分代收集不是第五种算法，而是“按代选法”的组合策略：新生代存活低用复制，老年代存活高用标记整理。
- 加分：G1 用 Region＋回收价值排序、ZGC 用染色指针把停顿压到亚毫秒——演进主线见 JVM-010。
