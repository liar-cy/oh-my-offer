## Q05：谈谈 Spring 的实现原理；Spring 是怎么根据 XML 或注解创建出对象的？

### 面试回答

结论：Spring 的两大支柱是 IoC 容器（管对象生命周期与依赖）与 AOP（横切逻辑代理化）。创建对象的统一路径是“配置解析成 BeanDefinition → 反射实例化 → 注入依赖 → 初始化回调”，XML 和注解只是两种定义来源。

- IoC：把 new 的控制权交给容器，依赖靠 DI 装配——解耦的是对象图的组装过程。
- XML 路径：`XmlBeanDefinitionReader` 解析 `<bean>` 标签，把 class、构造参数、属性、init-method 记成 `BeanDefinition`。
- 注解路径：组件扫描（`@Component` 系）或 `@Bean` 方法，同样落到 `BeanDefinition` 注册表；`@Autowired` 由 `AutowiredAnnotationBeanPostProcessor` 在属性填充阶段反射注入。
- 汇合点：两条路生成的定义进入同一套 `AbstractApplicationContext#refresh` → `getBean` 创建流水线——所以 XML 与注解行为一致，可混用。
- 一句话收束：Spring 不魔法，本质是“配置元数据＋反射＋模板方法”把对象创建标准化。

## Q06：谈谈 AOP 的原理以及应用场景

### 面试回答

结论：AOP 把横切逻辑（事务、日志、鉴权、限流）从业务方法里抽出来，运行时靠代理织入——Spring AOP 是容器内代理：接口默认 JDK 动态代理，无接口用 CGLIB 子类字节码。

- 概念对应：
  - 切面＝横切类。
  - 连接点＝方法执行。
  - 切入点＝表达式圈定哪些方法。
  - 通知＝前置／后置／环绕。
  - 织入＝生成代理的时机（Spring 是运行期）。
- 实现一句话：注入的是代理对象，调用先过拦截器链（`TransactionInterceptor` 等）再反射目标方法。
- 应用场景：声明式事务 `@Transactional`、统一日志与耗时、权限校验、重试／限流注解、缓存 `@Cacheable`。
- 与 AspectJ 的区别：AspectJ 编译期／类加载期织入，能拦字段和构造器；Spring AOP 只拦容器管理的 Bean 的方法调用。
- 自调用失效是高频追问：this 调用不经过代理，通知丢失——拆方法、注入自身代理或 `AopContext` 都算修法。

## Q07：除了用 AOP 实现日志输出，还有什么方式记录日志并减少对业务代码的侵入？

### 面试回答

结论：按侵入程度给梯度——MVC 拦截器／Servlet Filter 管入口日志，日志框架自身能力（MDC＋pattern）管上下文，Java Agent 字节码增强管方法级；“完全不侵入”是 APM 探针路线。

- 拦截器／Filter：Spring MVC 的 `HandlerInterceptor`（能拿到 HandlerMethod）或 Filter，统一记请求 URL、参数、耗时、traceId——覆盖“进出系统的日志”，进不到方法内部。
- 日志框架侧：logback／log4j2 的 pattern 自动带类名行号与 MDC 上下文，业务代码只管打日志不拼格式；traceId 用 Filter 放 MDC、异步线程用装饰器传递。
- Java Agent 字节码增强：`-javaagent` 挂载探针（SkyWalking／Pinpoint，或自写 ByteBuddy transformer），方法进出埋点全在增强里，业务零代码——这就是 AOP 之外的“零侵入”答案。
- 其他手段：`@Slf4j` 等注解只减样板不减调用；Spring 事件／装饰器模式把“记录动作”移出主流程但仍要显式发事件，侵入介于两者之间。
- 收尾选型：
  - Web 层日志用拦截器足够。
  - 要链路级方法日志上 APM 探针。
  - 别为了记日志在业务里手写时间戳。

## Q08：Java 程序对 CPU 使用率 100% 时，如何排查？

### 面试回答

结论：三步收敛——先用系统工具定位进程和线程，再把线程号转 16 进制进 jstack 找代码栈，最后按“死循环／GC 风暴／热点计算”分类处理。

- 系统层：`top` 找到高 CPU 进程；`top -Hp <pid>` 列出线程级占用，拿到线程 TID。
- 转栈：`printf '%x' <tid>` 转 16 进制，`jstack <pid>` 里搜 `nid=0x...` 定位栈帧；或直接 Arthas `thread -n 3` 一步给出最忙线程栈。
- 分两路判断：栈顶是业务方法→死循环、正则回溯、频繁序列化等代码问题；栈顶是 GC 线程→先 `jstat -gcutil <pid> 1000` 看 FGC 频率，转内存排查（对象分配过快／泄漏）。
- 应急与根治分开：先摘流量／重启止血留现场（dump），再修代码，别在没抓栈前直接重启丢证据。

## Q09：有过什么样的数据库优化经验？

### 面试回答

结论：按“分层清单”答最稳——SQL 与索引层、表结构与库设计层、配置与架构层，每层挑一个自己做过的真实案例；没做过的层明确说了解但未实践。

## Q10：如何排查 MySQL 的死锁问题？

### 面试回答

结论：先拿证据再谈原因——`SHOW ENGINE INNODB STATUS` 的 LATEST DETECTED DEADLOCK 段看两个事务各持什么锁、等各什么锁；持续监控开 `innodb_print_all_deadlocks` 落错误日志，事后按“锁等待图＋SQL 顺序”复盘。

- 定位现场：InnoDB 有死锁检测，默认自动回滚代价小的牺牲者（报错 1213）——业务侧表现为偶发更新失败。
- 读日志：状态输出里两个事务的行分别给出持有锁与等待锁（记录锁／间隙锁／插入意向锁），对照 SQL 能还原环路。
- 在线观测：`performance_schema.data_locks`／`data_lock_waits`（8.0）看实时锁与等待链，未死锁的长等待也能抓。
- 常见环路：
  - 多行更新顺序不一致。
  - 两事务先各持不相邻 gap 锁再互插对方间隙。
  - `UPDATE` 无索引命中锁表级范围。
- 修复方向：固定加锁顺序、让更新走索引缩小锁范围、短事务、失败重试兜底——而不是加大超时。

## Q11：在 Java 程序中如何实现对数据库的行级锁？

### 面试回答

结论：行级锁不由 Java 直接提供，而是让 InnoDB 替你锁——悲观路线是事务内 `SELECT ... FOR UPDATE`（锁定读），乐观路线是版本号的原子条件更新；Java 侧职责是管好事务边界与失败处理。

- 悲观写法：`@Transactional` 方法里先 `SELECT id FROM t WHERE ... FOR UPDATE`（走索引才锁行），校验后 UPDATE，提交释放；MyBatis 直接在 mapper SQL 写 `FOR UPDATE`。
- 关键坑：`FOR UPDATE` 的查询不在事务里（autocommit）锁立刻释放，等于没锁；条件不走索引会锁大范围甚至锁表。
- 乐观写法：`UPDATE t SET stock=stock-1, version=version+1 WHERE id=? AND version=?`，`jdbcTemplate.update` 返回值 0 即冲突——重读重试（限次）或向上抛业务异常。
- 选型：冲突密集选悲观（排队可控），冲突稀疏选乐观（无阻塞）；跨服务场景再上分布式锁或 Seata，行级锁只管单库单表。

## Q12：项目中的 RabbitMQ 主要用来做什么工作？

### 面试回答

结论：报项目真实用途，一般落三选一：解耦下游通知、异步非关键路径、削峰；每项补“消息流向（谁生产→哪个交换机→谁消费）＋失败处理”。

- 【下单后异步：积分／通知】——消息流向：
  - 生产者：订单服务。
  - topic 交换机按 `order.*` 路由。
  - 消费者按业务分队列。
- 【延时关单】——TTL＋死信队列或延迟插件，30 分钟未支付自动取消（未支付回补库存放消费逻辑里）。
- 【秒杀缓冲】——请求先入队，消费端按下游容量匀速落库；积压处理预案见 SYS-005。
- 可靠性口径一起给：生产端 confirm、消费端手动 ack、按消息 ID 幂等去重、死信兜底人工。
- 没实际用过就直说“项目规模小，MQ 用在【真实场景】或了解但未落地”，别把商城模板当经历。
