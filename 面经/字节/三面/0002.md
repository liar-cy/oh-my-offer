## Q03：谈谈 Redis ZSet 的底层实现

### 面试回答

结论：小集合用 listpack 紧凑存储；规模上去后切到「跳表＋哈希表」双结构——跳表管按分数排序与区间查询，哈希表管成员到分数的 O(1) 定位。

- 跳表：多层有序链表，平均 O(log n) 查找；节点存 backward 指针支持反向遍历。
- 字典：成员→分数，ZSCORE 不碰跳表。
- 阈值（score 数量与元素大小）可配，默认量级下小 ZSet 根本不走跳表——说结构要带规模条件。
- 与 Set 的区别一句话：ZSet＝Set＋按分数排序，多花一份双结构内存。

## Q04：ZSet 插入元素的时间复杂度、完整插入过程与跳表的具体操作

### 面试回答

结论：插入平均 O(log n)；完整链路是“查字典判新增还是改分 → 跳表找位 → 逐层接链”，改分要“先删后插”。

- 字典里没有该成员：新增；已有：分数没变直接结束，变了从跳表旧位置删除再按新分数重插（跳表不支持原地改键）。
- 跳表插层：随机定层数——每层 1/4 概率晋升、上限 32 层，期望层数恒定。
- 找位置：从表头最高层下滑，当前层下一个节点分数更小（同分比成员字典序）就右移，不能再走就下沉，直到第 0 层。
- 接链：沿途每层记录前驱（update 数组）与排名（rank 数组），逐层改指针、更新跨度与排名——一次插入 O(log n) 期望。

## Q05：Redis 有哪些使用多线程的场景？

### 面试回答

结论：“命令执行单线程”不等于“Redis 单线程”——网络 IO 线程、后台 BIO 线程、BigKey 删除异步线程都是多线程在用。

- IO 多线程（6.0＋io-threads）：只并行做读写 socket 与协议解析，命令仍回主线程串行执行——所以快不在这里，在把内核态拷贝摊开了。
- BIO 后台线程：AOF fsync、惰性 UNLINK／FLUSHALL ASYNC 的大内存释放、部分过期清理。
- 集群与复制：节点各自独立主线程，横向并行是集群形态提供的。
- 口径补一句：未开启 io-threads 时默认仍是单线程事件循环（细节见 REDIS-012）。

## Q06：持久化的 save 和 bgsave 有什么区别？为什么 bgsave 要 fork 子进程？

### 面试回答

结论：SAVE 主线程原地做快照，全程阻塞客户端；BGSAVE fork 子进程写临时 RDB，主线程继续服务——生产只用 BGSAVE。

- SAVE：同步、阻塞时长＝全量写盘时间，线上等于主动制造故障窗口。
- BGSAVE：子进程按 fork 瞬间的内存视图生成快照；新改动不进这份快照，靠 AOF 或下次快照补。
- 为什么 fork（追问落点）：要“不冻结主线程也能拿到一致视图”，COW 让子进程以页粒度共享父内存——只有被改的页才复制，主线程照常写。
- 主动补代价：大堆 fork 本身有页表复制停顿；子进程期间内存峰值可近两倍（COW 复制）。

## Q07：谈谈 fork 的原理

### 面试回答

结论：fork 创建子进程，不复制物理内存——父子共享页表指向的页，写时复制（COW）把实际复制推迟到“有人写那一页”时。

- 系统调用层：子进程得到父进程地址空间的副本（页表克隆），物理页帧加引用计数共享。
- 写触发复制：任一方写页 → 缺页异常 → 内核给写方新建页帧（copy-on-write），另一方可回收旧页。
- 所以 fork 成本≈页表复制＋少量元数据，和内存大小弱相关、和页数量强相关——这就是 Redis BGSAVE 敢用它的原因。
- 延伸一句 Linux 的 clone／vfork 与多线程（CLONE_VM 不复制页表）能显示深度，但没把握别展开。

## Q08：Redis 的 LRU 底层实现；让你实现一个简易 LRU 怎么做？

### 面试回答

结论：两层答——Redis 的淘汰是近似 LRU（随机采样比空闲时钟），不维护全局链表；自己实现标准 LRU 则是哈希表＋双向链表 O(1)。

- Redis 侧：
  - 每个 key 记最后访问时间（空闲时钟 lru 字段）。
  - `maxmemory-policy` 到 allkeys-lru 时随机采 N 个 key（`maxmemory-samples`，默认量级小）淘汰其中最久未用的。
  - LFU 策略则换成分数计数。
- 为什么近似：全局精确 LRU 每次访问都要移动链表节点，写放大与内存代价在百万 key 级别不值；采样 5～10 个已贴近理论值。
- 手写简易版：`LinkedHashMap(cap, 0.75f, accessOrder=true)` 加 removeEldestEntry 是偷懒正解；手撕口径＝HashMap 存 key→节点，双向链表头最新、尾最旧，get／put 都 moveToHead，超容量删 tail。
- 并发版追问（本面没问但常接）：见线程安全 LRU 专题。

## Q09：谈谈 ConcurrentHashMap 的底层实现

### 面试回答

结论：JDK 8 结构仍是桶数组，但并发控制换成「空桶 CAS ＋ 非空桶对头节点 synchronized」，粒度到一个桶；扩容有转发节点与协助迁移。

- put 路径：
  - table 未初始化先初始化。
  - 桶空→CAS 放新节点。
  - 桶非空→锁头节点挂链或进树。
  - 扩容中→先 helpTransfer。
- size 用 baseCount＋CounterCell 分散计数；get 全程无锁，靠 volatile 读已发布节点。
- 树化的桶也支持并发操作；旧“分段锁 Segment”说法只属于 JDK 7。
- 边界一句：单次调用线程安全≠“先 get 再 put”复合逻辑原子，那要 compute／merge 系列。

## Q10：设计微信群发红包、抢红包系统（追问：为什么用 MQ 承担什么工作；拼手速的抢到逻辑；扣减成功后续失败如何回滚；春晚全国人民规模）

### 面试回答

结论：主线是“发时预拆分、抢时原子弹份额、事后全异步”——群主发出瞬间把总金额切成 N 个随机份额入池，抢到＝对池子做一次原子 pop，落库通知走 MQ；追问四问都挂在这条主线的位置上。

- 发红包：金额按二分成法拆成 N 份（每份∈[0.01, 剩余均值×2]， cent 级整数），份额集合批量进 Redis（List／Hash），红包元数据（总额、份数、状态）落 DB；请求号做幂等。
- 抢（追问 2）：风控与限流后一段 Lua 原子弹出份额——池空即“已抢完”；“拼手速”不靠锁竞争，靠存储原子性，天然无重复分配。
- MQ（追问 1）：抢到只算“预占”，核销落领取流水、推送、账务对账全走消息异步——缩短主链路、削峰、解耦；MQ 承担“事后”，不承担“扣减”。
- 回滚（追问 3）：
  - 份额带状态（弹起未核销／已核销）。
  - 后续失败靠消息重试，超阈值进死信人工。
  - 超时未核销的份额定时回推入池，对账任务兜平——放弃“绝对不回滚”改说“最终一致＋窗口可控”。
- 春晚规模（追问 4）：
  - 单红包热点→按活动分片＋本地预分配份额段（应用节点整段领取后本地弹）。
  - 入口静态化＋CDN。
  - 多级缓存挡查询。
  - “显示金额延后到账”降级。
  - 容量按峰值 QPS 预算压测演练。

## Q11：手撕：整型数组第 K 大的数（要求基于快排实现）

### 面试回答

结论：基于快排的“快速选择”——一次 partition 后 pivot 落点就是它的最终名次，只递归目标侧那一半；期望 O(n)、原地 O(1)，对比全排序 O(n log n) 省下无用的一半工作。

- 第 K 大＝下标 `n-k`（升序视角）；每轮 `partition` 后比较 pivot 位置与目标下标，缩小区间一侧。
- 随机化 pivot（或三数取中）防有序退化，最坏 O(n²) 只在没随机时出现。
- 重复元素多要三路划分（Bentley–McIlroy），否则等于全排序；这是常见追问。
- 口述对比：堆法 O(n log k) 适合流式／海量（本库 ALG-034 场景），快选适合一次性内存内——面试官点名快排，就写快选并说出这个边界。
