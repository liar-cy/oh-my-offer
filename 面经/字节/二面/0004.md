## Q02：RAG 中都有哪些分块的方法？

### 面试回答

结论：从粗到语义排一排，按数据形态选，不是越先进越好。

- 固定长度切分＋重叠窗口：最简单，会切断语义。
- 按分隔符切：段落／标题／句子边界。
- 递归字符切分：分隔符按优先级逐级降级，超长再细分。
- 结构感知切分：按 Markdown 标题层级、表格与代码整体保留。
- 语义切分：用相似度找断点。
- 父子块／滑动窗口：小块召回、大块补上下文。
- 分级切块：文档／章节／页面多级索引（见 RAG-026）。

## Q03：切块之后做什么？了解哪些 embedding 模型，为什么用 BGE-M3，有做过比较吗？BGE-M3 是多少维、算高维还是低维？

### 面试回答

切块之后是一条入库流水线，不止“转向量”一步：

- 清洗规范化（编码、空白、HTML 标签）→ embedding 编码 → 建索引。
- 索引至少两套：向量索引（ANN）＋关键词倒排；再加 metadata 过滤字段。
- 可选增强：给块生成摘要、父子块映射、稀疏权重。

模型选型参考口径（项目实际情况【按真实经历填】）：

- 常见开源：BGE 系列（bge-large-zh／BGE-M3）、m3e、GTE、E5；商用有各家 embedding API。
- 为什么常用 BGE-M3：支持 100 多种语言、最长 8192 token 输入、一个模型同时给稠密、稀疏、多向量三种表示，适合混合召回；中文效果好且可私有化部署。
- 维度：稠密向量输出 1024 维（口径以模型卡为准）。
- 高维还是低维：1024 在主流 embedding（768～3072）里属中间档，没有绝对的高／低之分；维度越高存储与计算越贵，效果不必然更好。
- 做过比较吗：有比较才能说“选择”，用同一评测集比 Recall@k／Hit@k（口径见 RAG-008）；【项目是否真做过、结果如何按事实说，没做就明说】。

## Q04：除了做成向量还有什么额外处理？关键词检索用的什么方法？BM25 是高维还是低维？关键词和向量检索有什么区别？

### 面试回答

- 向量之外的额外处理：
  - 关键词路线：分词＋倒排索引，BM25 打分。
  - metadata 过滤：权限、来源、时间、版本。
  - 父子块与摘要索引、检索后重排。
  - 混合表示：BGE-M3 这类模型还能直接输出稀疏权重（词级权重），和 BM25 同类思路、不依赖分词器词表。
- 关键词检索方法：中文先分词（IK／jieba 等）进倒排，查询词定位候选文档，BM25 按词频饱和、IDF、长度归一打分。
- BM25 是高维还是低维：是“稀疏高维”。
  - 表示空间是整个词表，维度可达数万到百万级，比 1024 维的稠密向量“高”得多。
  - 但每条文本只在它包含的少数词上有非零值，所以是稀疏表示，不产生定长实数向量，也不做相似度距离计算。
  - 一句话：向量检索是“低维稠密”，BM25 是“高维稀疏”。
- 两者区别：关键词吃词面精确（术语、编号、稀有词），向量吃语义泛化（同义改写、跨表述），互补所以混合召回。

## Q05：检索方式是什么？HNSW 和 DiskANN／IVF 知道吗，存储形式是什么？

必要上下文：原文写“HNSW和HNSW”，疑似转写重复，按“HNSW 与 IVF／DiskANN 等 ANN 索引对比”一并作答，需按原题确认第二个指谁。

### 面试回答

检索方式一句话：查询向量化后在 ANN 索引里取 top-k，叠加 metadata 过滤，与关键词路结果做分数融合，再重排进提示。

- HNSW：多层可导航小世界图，上层粗定位、逐层下探。索引常驻内存，召回高、延迟低；构建慢、内存占用大，写入要维护图。
- DiskANN：面向单机十亿级、索引放 SSD 的路线。图结构（Vamana 图）＋全量向量存盘，内存里只放压缩向量（PQ）做粗筛；比 HNSW 省内存，代价是盘 IO 带来更高延迟。
- IVF（若原问是这个）：先聚类分桶，查询只扫最近的若干桶（nprobes 调召回）；建索引快、省内存，数据分布漂移后要重训。
- 存储形式：向量本体＋ID＋metadata 为一条记录；索引结构单独存——HNSW 存每个节点的各层邻居表，IVF 存聚类中心与桶内清单，DiskANN 存图节点与磁盘布局（向量数据与图邻接放一起）。原始文本与倒排另存，命中后回查原文。

## Q06：用的是框架还是自己实现的？有没有做多路召回？

### 面试回答

- 框架还是自研：属项目事实【按真实情况答】。

  - 自研就说清为什么：可控性与精简链路；被追问“重复造轮子值不值”要给取舍理由。
- 多路召回：有／没有都要能讲一层设计。

  - 效果要用同一评测集验证混合比单路提升多少（口径见 RAG-008）。

## Q07：怎么保证 LLM Wiki 的生成质量？有没有对生成的内容做评测？

### 面试回答

结论：质量靠“生成约束＋可回溯＋人审”，评测分条目层和端到端层，只说“生成完人工看了看”会被追死。

- 生成质量保证：
  - schema 约束：条目字段（标题、定义、步骤、来源）固定，要求模型带证据句输出。
  - 引用可回溯：每条内容映射回原文位置，改写失真能追责、能回滚。
  - 冲突检测与合并：与已有条目比对，冲突走版本链而不是直接覆盖。
  - 抽样人审＋入库门槛：低置信或不合规打回。
- 评测两层：
  - 条目层：忠实度（是否被源文支持）、引用支持率、重复率与冲突率。
  - 端到端：固定问答评测集比较“有 Wiki 层／无 Wiki 层”的答案质量与延迟，改动跑回归。
- 项目实际做到哪层【按事实填写】；没做过对照就明说，别把设想说成已实现。

## Q08：手撕：判断树 B 是不是树 A 的子树

必要上下文：原文只写“判断 b 树是不是 a 的子树”，未记录树的类型（二叉树还是多叉树）、语言与约束。按最常见的“二叉树子树包含”（LeetCode 572 口径：结构完全相同）作答；若指 B 树（B-Tree）或要求“拓扑子图”式宽松匹配，需按原题重做。

### 面试回答

结论：两处递归——在 A 的每个节点试一次“完全相同”，任一处成功即是子树；最坏 O(m×n)。

- `same(p, q)`：
  - 两棵树都空为真。
  - 一空一非空为假。
  - 值相等且左右子树都 same 为真。
- `isSubtree(a, b)`：b 为空按约定处理（通常空树不算子树要说明）；否则 `same(a, b) 或 isSubtree(a.left, b) 或 isSubtree(a.right, b)`。
- 多叉树同理：same 里遍历孩子列表逐一对应。
- 优化说法：可用“前序＋空占位符”序列化后做字符串包含，但要强调必须带空标记，否则结构会歧义（[1,2] 和 [1,null,2] 序列相同）；朴素双递归一般已够，序列化匹配要注意假阳性来源。

## Q09：手撕：手写一个 Agent loop 的过程

必要上下文：未记录语言与约束，按伪代码作答；核心是“循环—决策—执行—回写—退出”五件事。

### 面试回答

结论：一个带预算和出口的 while 循环——模型每轮要么给工具调用、要么给最终答案；执行层跑工具并把观察写回消息历史。

```text
messages = [system_prompt, user_task]
for step in 1..max_steps:
    resp = llm.call(messages, tools)          # 模型决策
    if resp.is_final:
        if verify(resp.answer): return resp.answer   # 目标验证后结束
        else: messages.append(校验失败原因); continue
    for call in resp.tool_calls:
        check_args_and_permission(call)        # 参数与权限校验
        result = execute(call)                 # 执行层真正调用
        record(call, result)                   # 留痕：ID／耗时／状态
        messages.append(assistant_turn, observation(result))  # 写回
    if no_progress(repeated_calls) or budget_exceeded(时间/费用):
        return fail_or_escalate_to_human       # 失败出口
return fail_timeout                             # 预算耗尽不等于成功
```

- 口述要点：
  - 模型“生成调用”不等于“已执行”。
  - 退出条件要同时看 final 动作与目标验证。
  - 重复无进展与三类预算（步数、耗时、费用）防失控。
