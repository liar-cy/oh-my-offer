## Q03：TCP 三次握手中第三次握手的 ACK 丢失，协议如何恢复？若客户端随后立即发数据且早于重传的 ACK 到达服务端，服务端能否正确处理，怎么优化？

原题 3—4 是同一场景的递进追问，合并为一题。

### 面试回答

先摆状态机：第三次 ACK 丢失时，客户端已经处于 ESTABLISHED（它发完 ACK 就认为连接建立完成，可以直接发数据），而服务端仍停在 SYN_RECEIVED，它已经分配了连接控制块（TCB）并把监听队列里的半连接转成了已建立的等待确认状态。恢复靠服务端的重复握手超时重传：服务端会重发第二个报文（SYN＋ACK），采用指数退避并有重试上限（Linux 上由握手重试次数参数控制，默认量级为几次），次数耗尽就丢弃该 TCB、释放资源，客户端此后会收到 RST 而不是响应。所以“恢复”有两种结局：ACK 在重传窗口内到达则正常进入 ESTABLISHED；始终不到则服务端超时清理，客户端要等到自己发数据收到 RST 才发现连接已失效并需要重建。

第二问的答案是“可以正确处理，靠序号机制”。关键点是 SYN 占一个序号：客户端发的第一个数据字节序号正好等于服务端期望的下一个序号（ISN＋1），这条数据报文同时带有对 SYN＋ACK 的确认，服务端在 SYN_RECEIVED 状态下收到合法 ACK 就直接迁入 ESTABLISHED——也就是说数据报文本身把第三次握手补完成了，不需要再等那个丢失的 ACK。收到数据后按正常流程处理：序号匹配就交付并回 ACK，之后的数据按序滑窗接收。风险在乱序与重复：如果客户端的 SYN 重传晚于这条数据到达（少见但可能），服务端会因当前 TCB 存在而按已有状态处理，通常回挑战确认（challenge ACK）由攻击面防护机制约束，不会因一个旧 SYN 就把连接状态倒回半连接；同理，旧连接的报文要靠序号窗口判定被丢弃，这也是 TIME_WAIT 存在的理由之一。

优化方向要说得出可落地的几项：客户端侧——连接池复用避免频繁握手、首包携带数据（TFO，TCP Fast Open）让 SYN 带上请求体省一个 RTT；服务端侧——调低 SYN 重传次数与半连接超时以便更快回收、用 SYN Cookie 抵御 SYN 洪泛（不分配 TCB，靠哈希验证）、限制单客户端连接数与空闲超时；应用侧——请求超时与幂等重试（因为连接是否存活无法从错误码可靠区分）、把首个请求做成小探测而不是把大 body 交给一条可能已失效的连接。

## Q04：假设一台服务器所有资源无限，理论上能同时建立多少个 TCP 连接？

### 面试回答

先把“资源无限”这条前提拆掉——这题考的是能不能识别真实约束，而不是给一个天文数字。连接身份是四元组（源 IP、源端口、目的 IP、目的端口），所以理论上限来自四元组的组合数：单 IP、单目的端时，受本地端口数限制（IPv4 的 16 位端口，去留用途后是 6 万多量级），要突破就得加源 IP 或目的 IP／端口，此时上限是二者乘积；IPv4 地址空间整体是 2 的 32 次方，两端相乘看似天文数字，但这些都不是工程约束。

工程上真正卡住连接数的是：文件描述符上限（进程级 `ulimit -n` 与系统级 `fs.file-max`，每个连接占一个 fd）、内存（每条连接的发送／接收缓冲与 TCB 元数据，按 `tcp_rmem`／`tcp_wmem` 配置，百万连接即使每连接几 KB 也要几十 GB）、端口耗尽（仅发生在作为客户端主动出连接时，服务端接受连接不占本地端口）、连接跟踪表与中间设备会话表、以及 epoll 等事件机制自身的容量与调度成本。所以正确答法是：如果“资源无限”指 fd、内存、内核表都不限，那上限由四元组空间决定；但这个假设没有意义，真实系统里先到的是内存与 fd，所以要做的是每连接内存瘦身（默认缓冲收敛、开启 `tcp_mem` 调控）、用边缘触发 epoll 与合理的中断绑核、必要时上 eBPF／DPDK 或把长连接网关独立出来，并且用连接数与内存指标设准入而非事后 OOM。加分的一句：现代大流量服务真正的问题不是“能不能建这么多连接”，而是“这么多连接同时可读写时的唤醒与调度成本”，这也是 C10K→C100K 的核心矛盾。

## Q05：给定订单表、订单明细表、商品表，编写 SQL 统计每个商家销售额超过 10 万的商品。

原题 5—7 与 Q06、Q07 是同一段表结构上的连续追问，但考察点不同（聚合过滤／范式判断／组内 Top1），故分开成题；原素材未给出真实表结构，以下按常见命名假设，需按实际字段修正。

### 面试回答

先澄清口径再写：销售额按什么算（明细里的成交额字段还是“单价×数量”）、是否要排除已取消或已退款的订单、时间范围、是否只算支付成功、商家与商品的归属关系从订单还是商品表取（同一商品可能被多商家卖）。表结构按 `orders(id, merchant_id, status, created_at)`、`order_items(order_id, product_id, price, quantity)`、`products(id, name)` 假设。

写法是“多表连接 → 按商家＋商品分组 → 聚合后过滤”：

```sql
SELECT oi.product_id,
       p.name,
       o.merchant_id,
       SUM(oi.price * oi.quantity) AS sales
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
JOIN products p     ON p.id = oi.product_id
WHERE o.status = 'PAID'
GROUP BY o.merchant_id, oi.product_id, p.name
HAVING SUM(oi.price * oi.quantity) > 100000;
```

要点说三条：过滤条件是“聚合后的值”，必须写在 HAVING 而不是 WHERE（WHERE 里 `SUM(...)` 非法，且语义是先删行再分组）；分组键必须包含商家与商品，否则会把不同商家同款商品的销售额合并；SELECT 里未聚合的列都要出现在 GROUP BY 中（`ONLY_FULL_GROUP_BY` 模式下否则报错），商品的 name 可用 `MAX(name)` 或进分组键。若题目其实是“每个商家总销售额超过 10 万，列出这些商家的商品”，那是两步——先按商家分组筛出商家集合，再列商品，用子查询或窗口函数区分开。这个歧义要主动指出，是这道题的加分处。

## Q06：上述表结构是否符合 3NF？

原素材未给出真实表结构，以下给判断方法与常见违反形态，需按实际字段收敛结论。

### 面试回答

先把定义说准再判。1NF 要求属性不可分（不要在一个字段里存逗号分隔的商品 ID）；2NF 要求非主属性完全依赖候选键（联合主键下不能只依赖其中一部分，比如以 `(order_id, product_id)` 为主键的明细表里放 `product_name`，它只依赖 `product_id`）；3NF 要求非主属性不传递依赖候选键——A→B→C 时 C 不能留在依赖 A 的表里。判据一句话：每个非主属性都“直接、完全”依赖主键，且彼此无关，也就是那句经典表述“the key, the whole key, and nothing but the key”。

按前面那三张表判：把 `orders(merchant_id, created_at, status)`、`order_items(price, quantity)`、`products(name)` 拆开看，商家名、商品名不落在订单表里，价格与数量属于“这一单这一件”的事实而不是商品快照的当前价，所以这个结构基本符合 3NF——但要指出两个易踩的违规：订单表里若冗余存了 `merchant_name`，那是商家表对主键的传递依赖（订单→商家→商家名），违反 3NF；订单表里若存 `total_amount` 而它可由明细求和推出，属于非主属性依赖其他非主属性／派生字段，同样违反 3NF（不过这个冗余在工程上很常见，理由见下一句）。

所以要把话说完整：3NF 的收益是消除更新异常（改商家名不用回写历史订单）、减少冗余；代价是查询要多表 JOIN、聚合类读放大。真实业务里会刻意反范式：订单快照保存成交时的单价与商品名（因为价格会变，历史订单必须能还原当时口径）、用派生列或汇总表换查询性能、宽表给分析类查询。答题的收口应该是“我先保证写入语义正确（3NF 能表达清楚依赖关系），再按读侧证据决定是否冗余，冗余了就要有一致性维护手段（同事务更新或异步对账）”，而不是死守范式。

## Q07：编写 SQL：查询每个商家销售额最高的商品。

### 面试回答

这是典型的“组内 Top1”，比上一题多一层：先算出（商家，商品）的销售额，再在每个商家内取最大那条。用窗口函数最清晰：

```sql
WITH sales AS (
  SELECT o.merchant_id, oi.product_id, SUM(oi.price * oi.quantity) AS sales
  FROM orders o
  JOIN order_items oi ON oi.order_id = o.id
  WHERE o.status = 'PAID'
  GROUP BY o.merchant_id, oi.product_id
), ranked AS (
  SELECT merchant_id, product_id, sales,
         RANK() OVER (PARTITION BY merchant_id ORDER BY sales DESC) AS rk
  FROM sales
)
SELECT merchant_id, product_id, sales
FROM ranked
WHERE rk = 1;
```

三个细节要主动交代：① 并列第一怎么办——`RANK()` 会把并列的都返回，要“每商家只留一行”就得用 `ROW_NUMBER()`，并加一个确定性次级排序键（如 `product_id`）避免结果不稳定；② 不能直接 `GROUP BY merchant_id` 后用 `MAX(sales)`，那样商品列会落到不确定的行上；③ 老版本 MySQL（5.7 无窗口函数）用“先按商家取最大销售额，再回连原结果集”的写法：派生表 `GROUP BY merchant_id` 求 `MAX(sales)`，然后与聚合结果按 `merchant_id 且 sales` 连接，此时并列会都出来，要唯一就得再定规则。

延伸一句会加分：数据量大时这个查询要先有支撑索引（订单表按 `merchant_id, status` 建复合索引，明细表按 `order_id` 建索引），并考虑用汇总表（按天／商家／商品预聚合）避免每次全量算——这类“组内 TopN”在线上有必要物化。

## Q08：手撕：100 个文件、每个文件含几亿个数字，找出全局最大的 1000 个数字（4 核 CPU，内存无限或有限如 32G）。

原素材记录候选人“只写了无限的伪代码，之后被要求修改代码优化性能”，如实保留；以下给两种内存口径的完整答法。

### 面试回答

先做量级判断再动手：100 文件 × 几亿个数＝千亿级数字，即使内存无限也不能把全部数字装进内存（千亿个 int 就是数百 GB），所以这题的正确解法本质是“流式处理＋固定大小结构＋并行读文件”。

内存充裕或不需要极限时，最优结构是大小为 1000 的最小堆（或排序容器）：顺序读每个文件的数字流，对每个数 x，若堆未满或 `x > 堆顶最小值` 就弹出堆顶并压入 x；否则丢弃。每文件一个局部 Top1000，最后把 100 个局部结果做 k 路归并（或直接继续喂同一个全局堆）得到全局 Top1000。时间 O(N log K)（N 为总数字量、K=1000 时 logK≈10），空间 O(K) 与内存是否 32G 无关——这才是关键结论：算法本身内存友好，不需要按内存大小改造。

并行与性能优化（面试官要的“修改代码”方向）：4 核 CPU 说明瓶颈在 IO 与文本解析而不是比较。做法是生产者—消费者：4 个（或 2×核数）worker 各领若干文件，按行流式读取（固定字节缓冲、避免一次 `readlines()` 载入整文件），把解析成本降下来——用现成的整型解析（避免正则与字符串切分开销），每个 worker 维护自己的局部 Top1000 堆（不要共享堆，锁竞争会吃掉并行收益），最后合并 100 个小堆。文件读取用 `seek` 分段并行也可以，但要处理边界（按行读时跳过半行），收益不如“按文件分片”直观。内存受限时（32G）以上做法本来就成立；如果被追问“要排序全部数字”才需要外部排序：分块内排＋多路归并（与 [[专题题库/算法与数据结构#ALG-026：取值范围远小于数据量时如何给海量数据排序？|ALG-026：海量数据排序]] 同源）。

要主动补的三点：① 数据有重复时 Top1000 是否要去重（去重就要用集合或位图，内存另算）；② 数字范围若已知且不大，可用计数／分桶法（按值域分桶统计数量，从大到小累加到 1000，比堆更省 log 因子）；③ 验证方式——构造小样例（已知答案的 3 文件×10 数）覆盖“全部小于堆内值”“并列边界值”“空文件”三类，并给出实测吞吐而不是只说“应该更快”。
