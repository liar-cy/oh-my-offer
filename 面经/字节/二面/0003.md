## Q03：微服务项目中的服务发现怎么做的？Nacos 靠什么保证注册与可用性？数据怎么存、有持久化吗？

### 面试回答

结论：项目里是“SDK 订阅＋本地缓存实例表”的客户端发现（按【真实：Nacos／Eureka／K8s Service】答）；Nacos 的可用性靠“AP 的 Distro＋心跳健康检查＋客户端快照”，存储分两类——临时实例在内存、持久化走外部存储。

- 服务发现（原题）：启动注册服务名＋IP＋端口，消费方按服务名拉实例列表，本地缓存＋变更推送；调用端自己做负载均衡。
- 注册与可用性（追问 1）：临时实例 5 秒心跳，约 15 秒标不健康、30 秒剔除；Distro 让每个节点都能独立应答读请求，集群分区也不拒绝服务发现。
- 存储与持久化（追问 2）：临时实例数据在主存内存、节点间异步复制，本身不逐条落库（丢了靠实例重启重注册）；持久实例与配置中心数据落在 Nacos 的存储层（内嵌 derby 或外接 MySQL），Raft 类协议保一致。
- 客户端还有一份本地快照文件：Nacos 集群整体短时不可用时，已有调用仍可凭快照继续——这是“可用性”的最后一公里。

## Q04：项目中的限流操作是怎么做的？底层基于什么限流算法？

### 面试回答

结论：按【项目真实】答“在哪限、限什么维度、用什么组件”，再报底层算法；常见形态是网关全局限流＋服务内 Sentinel／Guava RateLimiter 二级。

- 维度：接口 QPS／用户／租户／出口 IP——维度组合比算法更体现思考。
- 单机算法：Guava `RateLimiter` 是令牌桶（平滑放速）；分布式要计数共享存储（Redis＋Lua）或中心组件（Sentinel 滑动窗口统计）。
- 落地细节：限流后的动作要说清——快速失败返回 429／排队等待／降级兜底，不同业务选择不同。
- 被追“为什么不是漏桶”：接口流量允许突发（真实用户就是忽来忽去），令牌桶放突发更贴合；要恒定速率喂下游（如刷数任务）才换漏桶。

## Q05：对比令牌桶、漏桶、滑动窗口的优劣势与适用场景

### 面试回答

结论：三者管的对象不同——滑动窗口管“数没数对”（统计口径），令牌桶／漏桶管“放不放行”（执行策略）；常被并列问，比较时要先分层。

- 固定窗口计数最简单，但临界突刺能放过两倍量；滑动窗口把时间切片滚动统计，判定更贴真实速率。
- 令牌桶：按速率产令牌、桶有容量——允许有限突发，平滑提速；实现要处理“一次性取多个令牌”。
- 漏桶：请求先进桶、以固定速率流出——强制恒定速率、削突发最狠，但没有容量弹性、排队久了调用方超时。
- 场景：
  - 对外 API 网关常用令牌桶（容忍真实突发）。
  - 保护下游脆弱资源（刷库、第三方低配额）用漏桶。
  - 只做“每分钟 N 次”配额统计用（滑动）窗口计数。

## Q06：项目中的熔断是怎么实现的？熔断器具体怎么实现？

### 面试回答

结论：项目里用现成组件（【真实：Sentinel／Hystrix 类实现／Resilience4j】，或自研拦截器）对下游调用加保护；熔断器本质是一台三态状态机。

- 三态：
  - closed 正常放行并统计。
  - 失败率／慢调用比例超阈值（且样本数达最小调用量）→ open，直接走降级不再打下游。
  - 冷却后 half-open 放少量探针，成功回 closed、失败回 open。
- 统计窗口：滑动窗口记录最近调用结果，避免历史样本干扰；阈值要与下游 SLO 对齐。
- 降级动作要明确：返回缓存旧值／默认值／快速失败，熔断只是决策，降级才是给用户的东西。
- 自研怎么落（追问落点）：调用切面里包一层“try 调下游＋结果上报状态机”，状态机内存态＋定时快照；但先说结论——生产用成熟组件，自研只在面试讲原理。

## Q07：手撕：最大的以 1 为边界的正方形（LC1139）

### 面试回答

结论：DP 预处理＋枚举。先双向扫出 `right[i][j]`／`down[i][j]`：从 (i,j) 向右、向下连续 1 的个数；再枚举左上角与边长 s，四条边都由这两个数组 O(1) 判定，最大 s 即答案。

- 预处理：逆序扫，`grid[i][j]==1` 时 `right=right[i][j+1]+1`、`down=down[i+1][j]+1`。
- 判定边长 s 的方框：`right[i][j]≥s && right[i][j+s-1]≥s && down[i][j]≥s && down[i+s-1][j]≥s`。
- 复杂度：预处理 O(mn)；枚举 O(mn·min(m,n))，现场可先给全枚举版，再补“从大到小剪枝”（当前 s 不大于已找到答案就停）。
- 易错：边界是 1、内部不要求；`s=1` 需四条边退化到同一个点。

## Q08：二维数组按行遍历和按列遍历性能有什么差异？除内存外还有什么原因？

### 面试回答

结论：按行遍历显著快于按列——Java／C 的二维数组按行连续存放，按行走命中缓存行，按列每次跳一整行，cache miss 数量级上升。

- 行主序：`int[][]` 每行是连续块，顺序访问一次预取一整条缓存行（64B＝16 个 int），后续访问近乎免费。
- 按列：同列相邻元素相隔一行，几乎每个元素一次 miss，还伴随 TLB 压力。
- 除“内存大”外的其它原因（追问）：缓存行／硬件预取器吃顺序访问、TLB 条目复用、分支预测对规律访存的加成——瓶颈是访存局部性，不是指令数。
- 工程补一句：真要列操作就转置后按行扫（或分块遍历），把 miss 摊薄——N 维数值计算的标准手法。

## Q09：浏览器输入 douyin.com 按下回车，整个调用链路是怎样的？

### 面试回答

结论：DNS 解析 → 建连（TCP 握手＋TLS）→ 发请求 → 服务端链路（CDN／网关／后端）→ 响应渲染；字节场景要把“服务端侧”讲厚一点才像后端候选人。

- DNS：浏览器／系统缓存→本地 resolver→递归查询权威 NS，A／AAAA 记录；命中 CDN 时按调度策略返回就近 IP。
- 传输：TCP 三次握手（HTTPS 再加 TLS 握手拿会话密钥），HTTP/2 在其上多路复用。
- 请求：携带 Cookie／token；网关鉴权限流后按服务发现路由到后端，查缓存／DB 组装返回。
- 响应：
  - 302 跳登录或 200 回 HTML／JSON。
  - 浏览器边下边渲，静态资源走 CDN。
  - 后续数据请求转 XHR／长连接（本面的 WebSocket 可能在这被追）。

## Q10：TCP 为什么需要三次握手而不是两次？

### 面试回答

结论：两次握手的根本缺陷是“服务端单方面认为连接可建”，历史遗留 SYN 能让服务端建立无效连接；第三次 ACK 同时补上双向序号同步与旧包确认。

- 序号同步：客户端 SEQ 在服务端 SYN-ACK 中已回认，但服务端的 ISN 必须由客户端第三次确认——否则客户端不知道服务端序号起点。
- 旧 SYN 灾难：网络滞留的旧 SYN 两次握手中会直接建连并挂死资源；有第三次，客户端对陌生 SYN-ACK 回 RST，旧连接建不成。
- 顺带防资源滥用：两次握手的 SYN Flood 伤害更大，三次确认至少抬高成本。
- 加分点：第三次握手可携带数据；“两次也能可靠”说法被 RFC 明确否定，口径守住。

## Q11：Redis 的高可用是通过哪些方面保证的？

### 面试回答

结论：分层答——单机层靠持久化不丢数据，副本层靠主从＋哨兵／Cluster 故障转移，架构层靠限流降级兜底；高可用是“故障快发现、角色快接管、期间少丢数”的组合拳。

- 部署形态：
  - 主从复制是基础。
  - 哨兵自动选新主并改写客户端指向。
  - Cluster 再加分片级多副本与槽迁移（按【项目真实】选一层展开）。
- 复制的软肋要主动说：异步复制有丢数据窗口，主宕最后写入可能未同步；需要更强再谈 Redlock 的争议或换 CP 协调服务。
- 故障转移指标：发现时间（down-after-milliseconds）、选举与切流耗时、脑裂防护（`min-replicas-to-write`）。
- 应用侧兜底：Redis 不可用时本地缓存＋限流降级，别让“依赖高可用”变成“单点依赖”。

## Q12：优化一条 SQL 语句应该怎么做？

### 面试回答

结论：固定动线——EXPLAIN 定位现状 → 索引与写法改写 → 结构与架构层兜底；先量出瓶颈再动手，不背“优化口诀”。

- 看执行计划：type（ALL→ref／range 是首要目标）、key、rows、Extra（Using filesort／temporary 都要处理）。
- 索引手段：按最左前缀建联合索引、把过滤＋排序列收进覆盖索引、前缀索引换选择性；函数包列／隐式类型转换会让索引失效。
- 写法手段：`SELECT *` 改按需取列、大分页改游标条件、join 小表驱动、批量代替循环单条。
- 数据量层面：冷热分表、归档、读写分离；慢 SQL 常态化靠 `slow_query_log` 抓取——说出“我先开慢日志抓样本”比报参数更显工程成熟。
