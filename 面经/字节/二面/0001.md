## Q02：你的 Agent 是什么架构，具体怎么设计的？

### 面试回答

我是【真实项目】，按通用架构讲法，系统分成六块：

- 入口与会话层：收请求、管会话状态。
- 任务状态存储：步骤、中间结果、预算都落库。
- 上下文构建：决定这一轮喂给模型什么。
- 模型决策循环：ReAct 式，根据任务和已有观察选下一步动作。ReAct 就是“想一步—做一步—看结果”交替推进。
- 工具执行层：参数校验、鉴权、结果检查。
- 结果验证与报告：确认产出可用再回给用户。

讲每一块时都说清三件事：输入输出是什么、失败从哪里出口、预算怎么控。本人职责和团队成果分开说。

别把通用架构说成已经实现——没做的部分直接讲“计划中”。

## Q03：Think、Plan、Action、Observation 四个阶段分别保存什么状态，怎么影响下一轮？

### 面试回答

四个阶段各存一份状态，作用是让下一轮“接得上”：

- Think：本轮的推理结论、动作理由摘要。不依赖模型的隐藏思维链，我们自己存的就是它说出来的那句理由。
- Plan：步骤清单，外加每一步的状态——待办、完成、失败。
- Action：结构化的工具请求，含调用 ID、工具名与参数。
- Observation：工具返回结果或错误，再加时间戳。

下一轮的上下文由四样东西组装：目标＋计划进度＋最近观察＋未解决问题。这样带来三个效果：

- 观察会驱动模型修正计划。
- 调用 ID 把请求和结果配成对。
- 已完成的步骤不会被重复执行。

再补一句工程价值：这些状态落库之后，中断可以恢复，排障能回放。

## Q04：Agent 怎么决定继续检索，还是已经可以停止并给出答案？

### 面试回答

不由模型“感觉够了”就停，判定分两层。

模型侧：它输出结构化的动作，要么是给最终答案的 final，要么是继续检索的动作。

运行时侧：拿到 final 再验证目标是否真的满足——

- 必要证据齐了没有。
- 引用能不能核对上。
- 置信度是否过了阈值。

不足时不结束，把“还缺什么”写回任务状态，由它驱动下一轮。

另外有硬预算兜底：步数、耗时、费用任一超限，就进入失败或人工处理状态。预算耗尽不能当成功输出。

## Q05：这套 Agent 的评测条件怎么设计？

### 面试回答

按【真实评测】填写。通用做法是下面这套：

- 任务集分层采样：覆盖简单／多跳／缺参／工具失败这几类场景。
- 把变量钉死：模型版本、工具集、预算都固定，才有可比性。
- 指标看四类，分别是任务成功率、步骤效率、过程正确性、失败类型分布。
- 步骤效率的口径是调用次数、P95 延迟、成本。
- 过程正确性的口径是工具选择与参数准确率、引用支持率。
- 多次重复跑：控制随机性，不看单次结果。
- 留出测试集：不参与调优，改动逐项归因。

## Q06：多轮检索怎么避免重复查询、循环调用和上下文无限增长，除最大循环次数外还有什么办法抑制循环？

### 面试回答

三个问题分开治。

重复查询：把（工具名＋规范化参数）当键做去重缓存，同参数直接返回已记录的结果。

循环抑制，除最大次数外还有四条：

- 无进展检测：连续 N 轮状态或证据集合没有变化，就直接退出。
- 预算限制：给单个工具设调用与重试预算。
- 结果收敛判据：新证据的增量低于阈值就停。
- 结构化错误反馈：让模型换策略，而不是原样再试一次。

上下文增长：

- 每轮只注入计划进度与最近观察。
- 旧内容做结构化摘要，同时保留回查 ID，需要时能捞回原文。
- 工具输出分页截断。
- 按 token 预算强制裁剪。

## Q07：负向 Prompt 和“不要重复调用工具”这类简单声明有什么区别，怎么验证它是否有效？

### 面试回答

两者本质一样，都是文字约束，区别只在泛化与具体：

- 负向 Prompt：列一批禁止行为。
- 简单声明：只针对单一动作，比如“不要重复调用工具”。

共同弱点有两条：一是模型可能根本不遵守，二是约束越堆越长会互相干扰。

所以可靠做法是分层：能确定的规则下沉到运行时，由执行层做参数去重、预算熔断、结构化报错；Prompt 只负责让模型理解什么时候该怎么做。

验证有效性要看数据，不看个例：在含易重复行为的评测集上统计重复调用率、无进展轮数与成功率，做“加这条约束”和“不加”的对照。拿个别成功案例证明是站不住的。

## Q08：放到业务中，面对简单、中等、困难问题，怎么设计整体流程控制延迟？

### 面试回答

核心是分级路由：入口用规则加小模型或轻量分类先判断难度，再按难度走三条路。

- 简单问题：走缓存或单次检索直接回答，秒级以内。
- 中等问题：走固定工作流——预定义步骤、并行取数、一次生成。
- 困难问题：才进带预算的 Agent 循环，并且先返回受理状态、流式输出中间进展。

延迟怎么控住：各层都设延迟与费用预算，超预算自动降级到下一层的确定性路径。

最后补一句运维：命中率、各层占比、端到端分位延迟都要持续监控。

## Q09：多 Agent 协同怎么设计，哪些功能放主 Agent、哪些放 Sub Agent，是否需要 Sub Agent？

### 面试回答

原则先说：能一个 Agent 稳定完成，就先用一个。

判断要不要拆，看子任务是否满足：有独立专长、有独立权限边界，或者需要独立上下文（比如一长串检索过程），而且可以并行。

拆完怎么分工：

- 主 Agent 保留：目标理解、规划、路由、状态汇总，以及对用户的最终输出。
- Sub Agent 承担：边界清晰的专项，比如检索、代码执行、审核。
- 交接方式：只传结构化结果和证据引用，不把全部对话广播出去。

要不要拆不能靠感觉：用同一任务集和单 Agent 基线对比成功率、延迟、成本、人工接管率。协调开销大于收益，就不拆。

## Q11：能介绍一下 Java 的 GC 机制吗？

### 面试回答

GC 分三步走。

第一步，先判断谁是垃圾：从 GC Roots（一组确定还活着的起点对象）出发做可达性分析，走不到的对象算不可达。

第二步，按区域选回收算法：标记清除、复制、标记整理。

第三步，按代组织频率：分代收集用对象寿命决定回收节奏。G1、ZGC 这些是具体收集器，是上面这些算法的实现组合，不要和算法混着称呼。

三个易错点：

- 回收只管 JVM 管理的堆内存。
- 并行（多条 GC 线程一起干活）和并发（和用户线程同时跑）要分清。
- 选型看三点：暂停时间、吞吐、堆规模。

口径按 Java SE 21／JDK 21 说，项目的收集器与参数按【实际配置】补充。

## Q12：既然有 GC，为什么还会出现内存泄漏？

### 面试回答

一句话：GC 只回收不可达的对象，所以“可达但没用”它管不了。对象还被一条合法的引用链持有着，业务上却已经不需要，这就是泄漏。

典型来源记六条：

- 只增不删的集合与缓存。
- 注册了但没注销的监听器回调。
- 没关闭的资源。
- 非静态内部类隐式持有外部实例。
- 线程池里 ThreadLocal 用完没 remove。
- static 集合长期累积。

再说两个边界：堆外直接内存和线程栈都不归堆 GC 管，所以容器 OOM 时 Xmx（最大堆大小）不是进程的上限。

诊断口径：看 Full GC 之后老年代占用是不是还在持续抬升；是的话用堆转储加支配树，定位到具体那条持有链。

## Q13：能介绍一下 SSE 是什么吗？

### 面试回答

SSE（Server-Sent Events，服务端推送事件）是基于 HTTP 响应流的服务端单向推送。

- 响应类型是 `text/event-stream`。
- 事件带 `data`、`event`、`id`、`retry` 这几个字段。
- 浏览器侧 `EventSource` 原生支持断线重连，靠 `Last-Event-ID` 续传。

适合下行的单向场景：服务端通知、进度推送、LLM 的 token 流。需要双向高频通信时改用 WebSocket。

两个边界记一下。上行仍然走普通 HTTP。二进制数据要么先编码，要么换通道。

## Q14：算法：二叉树的直径。

### 面试回答

后序遍历，自底向上顺手把答案算出来。

- 对每个节点：经过它的最长路径边数＝左子树高度＋右子树高度，用一个全局变量取最大。
- 往父节点返回的是高度：1＋max(左, 右)。

时间 O(n)，空间 O(h)。原文记“直接秒”，未记录具体作答过程。
