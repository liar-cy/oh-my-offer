## Q02：Java 的 AOP 是什么？作用是什么？主要解决什么问题？好处是什么？

### 面试回答

结论：AOP 是面向切面编程——把散在各业务方法里的横切逻辑（事务、日志、鉴权、限流）抽出来，由代理在调用前后统一织入。

- 实现：Spring AOP 在目标对象外包一层代理，JDK 动态代理（接口）或 CGLIB（子类）；调用必须经过代理对象才生效。
- 解决的问题：不抽的话每个方法都要手写“开事务→try-catch→记日志→提交”，重复且容易漏改。
- 好处：业务代码只留业务、横切逻辑集中一处可配置；新增审计只需加切面。
- 主动补边界：同类内 `this` 自调用绕过代理会失效；AOP 是运行期代理，不是 AspectJ 的编译期织入。

## Q03：WebSocket 是怎样的协议？建立连接的过程用的什么协议？

### 面试回答

结论：WebSocket 是 HTML5 定义的全双工应用层协议（ws／wss），一次握手后在同一条 TCP 连接上长期保持双向通信；握手借用 HTTP 协议升级完成。

- 建立过程：客户端发普通 HTTP 请求，带 `Upgrade: websocket`、`Connection: Upgrade` 和随机 `Sec-WebSocket-Key`；服务端回 101 Switching Protocols 确认升级，之后同一 socket 上改走 WebSocket 帧格式。
- 对比 HTTP：HTTP 请求响应式、服务端推送要靠轮询或 SSE；WebSocket 建立开销摊薄后几乎为零，适合聊天、协作编辑、实时推送。
- 保活：ping／pong 控制帧探测连接；断线要自己做重连与消息补偿。
- 握手后不再是 HTTP：本质仍是 TCP，HTTP 只是握手的“壳”——这是追问的标准答点。

## Q05：HTTP 的请求信息里有哪些内容？请求行里具体有什么？

### 面试回答

结论：请求报文四部分——请求行、请求头、空行、请求体（可选）；请求行三样：方法、请求目标（URI）、HTTP 版本，空格分隔。

- 例：`POST /user/login HTTP/1.1`——方法 POST、目标路径、版本 1.1。
- 请求头：通用／请求／实体头（Host、Content-Type、Content-Length、Cookie 等），每行“名字: 值”。
- 空行：分隔头部与正文的强制边界，漏了它正文会被当头部解析。
- 请求体：GET／HEAD 通常没有；POST 携带表单或 JSON。

## Q06：HTTP 请求过程中的传参方式是怎样的？

### 面试回答

结论：参数能走四个位置——URL 查询串（?k=v&k2=v2）、URL 路径段（RESTful /user/{id}）、请求头、请求体（form／JSON／文件）。

- GET 常用查询串：受 URL 长度限制、会进日志与缓存，敏感信息别放。
- POST 请求体：表单 `application/x-www-form-urlencoded` 或 `application/json`，容量基本不受 URL 限制。
- 中文与特殊字符要 URL 编码（百分号转义）；查询串格式与数组序列化风格（重复 key／逗号分隔）需前后端约定。
- 被追“GET 一定不带 body 吗”：协议允许部分服务端收到 body，但语义与兼容都不保证——按规范答题别依赖它。

## Q08：缓存的 key、value 怎么设计？和数据库中数据的对应关系是怎样的？

### 面试回答

结论：key 用“业务:实体:标识”的冒号分层命名（如 `item:detail:1024`），value 存序列化后的整行对象或按字段拆 Hash；对应关系一般是“一行业务记录 ↔ 一个缓存 key”。

- key 设计三原则：可读可检索（前缀＋通配排查）、带上版本号或租户前缀防串数据、长度别夸张（key 本身占内存）。
- value 粒度：整对象缓存读写一次完成但更新要整体覆盖；Hash 分字段可局部更新，代价是序列化边界模糊——按【项目真实选择】答。
- 与 DB 映射：缓存是 DB 行的只读派生副本，DB 是唯一真相源；更新走“先写库、再失效缓存”，映射断裂靠过期时间兜底。
- 一对一之外还有聚合型：排行榜 ZSet、计数 String 这类 value 不对应单行，是计算结果——被追问要能区分。

## Q09：谈谈项目中多级缓存的设计逻辑，为什么要用多级缓存，缓存的更新逻辑是怎样的

### 面试回答

结论：多级缓存＝本地缓存（Caffeine）挡热点＋Redis 挡全量＋DB 兜底；目的是把大部分请求在进程内终结，压住 Redis 的网络往返与热 key 压力。

- 为什么：本地缓存纳秒级、无网络开销；Redis 容量与带宽有限，热点 key 集中打会打爆单分片。
- 一致性代价：本地缓存多实例各一份，更新有毫秒～秒级不一致窗口，靠短 TTL＋广播失效收敛。
- 更新逻辑（按【项目真实】答，通用口径）：写请求先更新 DB 再删 Redis，并通过发布订阅／MQ 通知各实例失效本地缓存；读路径先本地后 Redis 回源。
- 主动补一句降级：Redis 故障时本地缓存＋限流兜底，别让全部流量裸奔到 DB。

## Q10：什么是缓存雪崩、缓存击穿、缓存穿透，三者的解决方案

### 面试回答

结论：三者都表现为“请求绕过缓存打到 DB”，区别在原因：

- 雪崩是大批 key 同时过期或缓存宕机。
- 击穿是单个热点 key 过期瞬间并发回源。
- 穿透是查根本不存在的数据。

解决方案：

- 雪崩：TTL 加随机打散、缓存高可用（哨兵／集群）、限流熔断兜底。
- 击穿：互斥重建（拿不到锁的等旧值）、热点 key 逻辑过期＋异步刷新、提前续期。
- 穿透：参数校验、空值短 TTL 缓存、布隆过滤器前置（有假阳性，不算完全解决）。
- 收口报组合拳：三层防线（缓存层高可用、回源层限流互斥、业务层降级）比单点方案更稳。

## Q11：为什么 Redis 的性能比 MySQL 高这么多？是基于什么设计的？

### 面试回答

结论：不是“实现更好”，是设计目标不同——Redis 按“纯内存、简单结构、单线程事件循环”设计；MySQL 要支撑磁盘持久存储与通用 SQL 计算。

- 内存 vs 磁盘：Redis 读写纳秒～百纳秒级；MySQL 即使缓冲池命中也要走页管理、事务与索引通用逻辑。
- 数据模型：Redis 只做键到结构的操作，无 SQL 解析、优化器、通用 join；MySQL 的复杂度就是成本。
- 并发模型：Redis 命令单线程执行，无锁无上下文切换，靠 IO 多路复用撑连接；InnoDB 多线程要处理行锁、MVCC、缓冲池闩锁。
- 别说过头：Redis 快不以持久化为代价的口径要如实——它仍有 RDB／AOF，只是路径设计成异步；大数据量、复杂查询场景 MySQL 不可替代。

## Q13：MQ 中的消息被消费者接收之后，如何保证消息一定被完整处理？

### 面试回答

结论：原则一句——处理完成之前不确认；“接收”不等于“处理完”，可靠性靠手动 ack＋失败重试＋兜底记录。

- 消费端先落库／执行事务，成功后再 ack；抛异常不 ack，让消息重投。
- 重试要有上限：多次失败进死信队列（DLQ），配告警人工处理，避免毒消息无限重试堵队列。
- 重投意味着至少一次投递：消费必须幂等（这题与 Q15 是一对）。
- 极端情况补一句：ack 与业务提交的先后要按“先提交后 ack”来，否则可能消息丢了业务还没做——中间窗口用对账兜底。

## Q14：项目中对于消费者而言，消费逻辑的代码是怎么实现的？

### 面试回答

结论：消费代码＝幂等检查＋业务事务＋异常分级处理＋手动 ack 四段固定结构（按【项目真实框架／MQ 组件】填细节）。

- 骨架：监听回调里先按消息 ID／业务唯一键查“处理过没有”（幂等表或唯一约束），重复直接 ack 跳过。
- 业务处理放事务里；可重试异常抛出交给 MQ 重投，不可重试（数据非法）记录后转死信，不空转。
- 并发控制：消费者并发数与 DB 连接池匹配，慢操作（外部调用）不要占着消费线程。
- 监控埋点：消费延迟（lag）、失败率、死信数量——“我看过这些指标”最能证明真做过。

## Q15：使用 MQ 过程中的幂等性是怎么保证的？

### 面试回答

结论：MQ 只能保证“至少一次”，去重责任在消费端——按业务唯一键判重，重复消息直接短路。

- 常规手段：处理前查幂等表／Redis SETNX（键＝业务单号）；或数据库唯一索引兜底，插入冲突即视为重复。
- 状态机幂等：如“订单只有 待支付→已支付 一次迁移”，非法状态更新影响行数为 0，天然幂等。
- 判重与业务动作要同事务落库，否则“记录了已处理但业务没做”更糟。
- 主动区分：消息去重（幂等）解决“消费两次”，投递去重（exactly-once 语义）依赖事务消息——两层别混。

## Q16：除了项目中使用的场景，MQ 还有哪些使用场景？

### 面试回答

结论：通用三大件——异步（非核心链路后置提速主流程）、解耦（生产消费各自演进）、削峰（尖峰缓冲按节奏消费）；再加两个常见形态：事件驱动／最终一致、流量隔离的任务分发。

- 异步：注册后发邮件短信、下单后同步积分；主流程只做必须同步的事。
- 解耦：一条订单事件消息，积分、风控、数据组各自订阅，新增下游不改上游。
- 削峰：秒杀请求先入队，消费端按 DB 容量拉取。
- 场景之外补边界：MQ 引入延迟与一致性成本（最终一致），能同步调用解决的小事不必上 MQ。

## Q17：手撕：反转单链表中位置 left 到 right 的节点（LC92）

### 面试回答

结论：LC92 reversalBetween——建虚拟头结点 `dummy`，先走到 left 的前驱 `prev`，然后对 [left, right] 段做“头插法”：反复把 `cur.next` 摘下来插到 `prev.next` 位置，共 right−left 次。

- 为什么用 dummy：left=1 时前驱不存在，dummy 统一处理边界。
- 关键不变量：段内未处理部分保持原序、已处理部分整体挂在 prev 前部；每轮只动一个节点，O(n) 时间、O(1) 空间。
- 对比写法：也可以“截断→整段反转→接回”，要多记几个指针，现场容易断链——先讲清选择再动手。
- 自查用例：left==right（原样返回）、反转全链表、跑完 `dummy.next` 是否仍是正确头。
