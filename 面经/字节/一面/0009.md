## Q04：大模型微调的训练数据集是如何构建的、数据量多大；构建过程中遇到哪些挑战、花了多长时间？

### 面试回答

数据怎么来（按真实情况选）：人工标注、规则与模板批量生成、强模型蒸馏出草稿再人审、线上真实日志与文档改写。加工与质控是关键得分点：统一成指令格式（输入＋期望输出＋必要约束），去重与近重复合并、长度与截断检查、按类别看分布是否被某类淹没、双人抽检算标注一致率、难例与边界样本单独上采样，并剔除与评测集同源的样本避免污染。数据量要报得具体——几千到几万条指令是小规模微调的常见量级，说不清来源的“几十万条”会立刻被追问。

被问“遇到哪些挑战、花多长时间”时讲真实的三个难点更有说服力：① 标注一致性——不同人对“正确答案”理解不同，靠写标注规范＋仲裁样本收敛；② 分布偏斜——简单样本占多数导致难例学不到，靠分层采样与难例上采样；③ 教师模型错误继承——蒸馏结果看着流畅但含事实错误，需要抽样人工核对并留 badcase 集。耗时按“数据准备占大头”这个常识答：构建与清洗往往比训练本身更花时间，训练一轮多久、迭代几轮、最后为什么停（指标不再提升或时间预算）都要说得出。若结论是微调收益不明显、最终靠 RAG 解决，如实讲反而显得判断可靠。

## Q06：讲讲 Golang 中 Channel 的概念与作用，它是否并发安全；Channel 和 Mutex 在并发控制上有什么区别、各自适用什么场景？

原题 7—8 同属 Go 并发原语话题（channel 本体与是否并发安全、与 mutex 的取舍），合并为一题。

### 面试回答

channel 是运行时提供的、带类型与容量的 goroutine 间通信队列，底层是 `hchan` 结构：一块环形缓冲（`buf`，配合 `qcount`／`sendx`／`recvx` 读写指针）加两个等待队列（`sendq`／`recvq`，阻塞的发送方与接收方挂在这里）和一把保护自身的互斥锁。语义上分三类：无缓冲 channel 是同步握手，发送必须等到有人接，等于一次“交接所有权”；有缓冲 channel 缓冲未满即返回，起解耦与削峰作用；`select` 多路复用配 `default` 可以做非阻塞收发与超时。

“是否并发安全”要分两层答：channel 自身是安全的——多个 goroutine 同时向同一 channel 收发由运行时加锁保护，不会破坏内部结构；但“用 channel 写的程序没有竞态”不成立，因为竞态可能发生在 channel 之外的共享变量上，而且它有明确的错误用法会 panic 或死锁：向已关闭的 channel 发送会 panic，从已关闭的 channel 接收返回零值加 false（所以靠 `v, ok` 判断关闭而不是靠值），向 nil channel 收发会永久阻塞，多发送方时关闭权要唯一约定（否则谁都可能提前 close），重复 close 同样 panic。

与 Mutex 的区别不是“谁更安全”，而是抽象层次不同：mutex 保护共享状态，所有访问者竞争同一把锁来读写同一份数据，适合保护缓存、计数、复合数据结构、必须原子的读—改—写；channel 传递数据的所有权与事件，适合流水线分段、任务分发、限流（带缓冲 channel 当令牌桶）、取消与超时广播。取舍判据可以说成：共享可变状态、且要原地读写→用锁；把数据交给下一个处理者、或表达“发生了某件事”→用 channel。反过来也要能说出反例：用 channel 做全局计数器会平白引入一个串行化的 goroutine，用 mutex 保护一个只写一次的 map 反而比 channel 简单——Go 社区那句 “不要通过共享内存来通信，而要通过通信来共享内存” 是指导而非教条，实际项目里 `sync.Mutex`／`RWMutex` 用得比 channel 更多，一旦为了 channel 而 channel，代码可读性和性能都会变差。

关联专题：[[专题题库/Go#GO-002：Go 的 channel 是什么、并发安全吗，和 Mutex 怎么取舍？|GO-002：Go 的 channel 是什么、并发安全吗，和 Mutex 怎么取舍？]]

## Q07：讲一下 GMP 模型；P 的本地队列为空或不为空时，它会怎么调度 G？

原题 9—10 同属 GMP 调度话题（模型定义与调度路径），合并为一题。

### 面试回答

G 是协程（自带更小栈，可增长），M 是内核线程（真正执行代码的实体），P 是调度上下文（持有本地可运行队列和一个内存分配缓冲，数量由 `GOMAXPROCS` 决定，通常等于可用的逻辑核数）。M 必须绑定一个 P 才能执行 Go 代码，这层设计把“线程数”和“并行度”分开：并行度由 P 控制，阻塞在系统调用上的 M 可以多出来而不影响调度公平。

调度取 G 的顺序是关键：M 拿到 P 后，先看 P 的本地队列——不为空就直接取头部的 G 执行（本地队列无锁访问，这是 Go 并发开销低的主要原因之一，`runnext` 会被优先安排以减少调度延迟）；本地队列为空时，先去全局队列取一批（一次取若干个，避免频繁加锁）；还没有就做网络轮询 `netpoll`，把已经就绪的 G 拿到本地；仍没有，就随机挑其他 P 做工作窃取，通常偷走其本地队列的一半（而不是一个一个偷，减少再次偷取的开销）。窃取也失败，M 就进入自旋状态等待有 G 可用——自旋 M 的数量有限制，防止空转烧 CPU，没有则让 M 睡到调度器等待队列里，等有新 G 入队时被唤醒。两个防饿死与防阻塞的机制必须提：一是每 61 次调度会强制检查一次全局队列，避免本地队列源源不断导致全局队列的 G 长期得不到执行；二是 `sysmon` 这个不绑定 P 的监控线程，周期约 10ms，负责抢占运行过久的 G（配合栈检查点实现协作式抢占）、接手长时间阻塞在系统调用上的 P 并把它交给别的 M。此外要能说清“为什么阻塞系统调用不影响别人”：M 阻塞时 P 与 M 解绑（hand off）转给其他 M 继续跑队列里的 G，系统调用返回后再重新找 P，找不到就排队。

## Q08：Redis 支持哪些数据结构？

### 面试回答

按“类型＋典型场景＋底层编码”三层答才有区分度。五种基本类型：String（计数、缓存对象、分布式锁的持有标记；编码为 int／raw／embstr）、Hash（对象字段级更新与读取，如商品详情字段；ziplist／listpack 或 hashtable）、List（最新动态列表、简单队列；quicklist 即双向链表＋listpack 节点）、Set（去重与交并差，如共同好友、抽奖去重；intset 或 hashtable）、ZSet（排行榜、延迟队列、带权重的 TopN；listpack 或 skiplist＋hash 双结构）。再补三种高级类型：Sorted Set 之外还有 Bitmap（本质是 String 的位操作，签到与活跃标记）、HyperLogLog（基数统计，UV 这类可容忍约 0.81% 标准误差的场景）、Stream（追加日志型结构，带消费者组与 ID，能做轻量消息队列）；Geo 是 ZSet 上的封装。若被问选型，用一两个例子说明“为什么用 ZSet 而不是 List 做排行榜”，并如实说清项目里实际用了哪些。

## Q09：为什么 Redis 的速度这么快？

### 面试回答

四层原因，按主次给：① 纯内存操作，读写不落到磁盘，这是最根本的一条；② 命令执行走单线程模型，省掉了锁竞争与线程上下文切换，同时天然保证单条命令的原子性（Redis 6.0 之后网络 I/O 可以多线程，但命令执行仍然串行，答题要说清这条边界，别把“多线程 IO”说成“命令并行执行”）；③ 基于 epoll 的事件驱动 I/O 多路复用，单个线程照看大量连接，配合事件循环与命令队列，避免为每个连接开线程的开销；④ 数据结构是为场景特化的——SDS 便于长度与拼接、ziplist／listpack 紧凑省内存并提高缓存命中、跳表实现 ZSet 的有序与范围查询、intset／hashtable／embstr 按元素规模切换编码；再加上协议本身简单（RESP 解析开销小）与 pipeline 批量发送能显著摊薄往返成本。

收尾要主动补一句限制，避免被反问：快是有前提的——单线程意味着一个慢命令（`KEYS`、大集合的 `SORT`、`DEL` 大 key）会阻塞所有人，所以生产上要禁用危险命令或用 `SCAN`／`UNLINK`；大数据量或热 key 会让单分片成为瓶颈，这时要靠 Cluster 分片、本地缓存与拆 key 解决（热 key 的处理另见专题）。

## Q11：实时搜索通常使用什么网络协议（如 WebSocket）？了解或用过吗，讲一下。

### 面试回答

先给结论：输入联想不需要长连接。它是“每次按键触发的一次短查询”，最合适的形态是 HTTPS 短请求＋客户端防抖＋请求取消或序列号丢弃旧响应；真正的难点不是协议而是并发量与乱序（用户继续输入时上一个慢请求返回了旧结果，必须按序号丢弃）。需要服务端持续推送的场景才上长连接：搜索结果的实时刷新、协同编辑、消息与日志流。

三种实时方案怎么选：短轮询最简单但空转；长轮询省一点带宽但连接占用与延迟仍受往返影响；SSE 是基于 HTTP 的单向服务端流，自带 UTF-8 文本、事件 ID 与 `Last-Event-ID` 断线续传、心跳注释行，实现成本低、走普通网关，适合“服务器推结果给浏览器”这类单向场景，也是大模型流式输出的常用载体；WebSocket 是 TCP 之上的全双工协议，握手后独立于 HTTP，可发二进制、消息往返都便宜，适合双向高频交互（协同、在线对战、实时行情），代价是网关与实例侧要维护连接状态、要做心跳与重连（指数退避加抖动、重连后重新鉴权并按序号补拉）、连接数上限与扩缩容更麻烦。实际项目里更常见的是“请求走 HTTP／RPC，返回用 SSE 流式”，除非确实需要双向通道才上 WebSocket。是否用过按真实经历说，没做过就说“理解机制但项目未落地”，不要编。

## Q12：请详细说明微信扫码登录的完整流程和背后的原理。

### 面试回答

关键前提：PC 是未登录的，手机 App 上已经有登录态，扫码本质是“让已登录端替未登录端完成一次身份授权”，所以核心是一条“票据（ticket）”的状态机在两端之间流转，而不是把凭据传来传去。

完整流程分六步：① PC 打开登录页，向后端申请二维码，后端生成随机且一次性、短有效期（如 60～120 秒）的 ticket，状态置为“待扫码”，存进 Redis 并设过期，把 ticket 拼进一个指向 H5 确认页的 URL 生成二维码返回给 PC 展示；② PC 开始查状态——轮询同一 ticket 最简（间隔 1～2 秒，配合过期时间），也可用 SSE／WebSocket 让服务端推送；③ 用户用手机 App 扫码，App 带自己的登录态请求服务端，服务端校验域名与参数合法后把该 ticket 状态改为“已扫码待确认”，PC 立刻显示“已扫码请在手机上确认”；④ 用户在手机上点确认，服务端把 ticket 置为“已确认”并把用户身份与该 ticket 绑定；⑤ PC 感知到已确认，凭 ticket 换一次性 code／token，服务端校验后立即消费该 ticket（防止重放），给 PC 签发 PC 侧登录态（Set-Cookie 或下发 JWT）并跳转；⑥ 二维码过期或取消时状态终止、PC 提示刷新重新申请。

背后的原理要点：身份只从已认证的一端流向未认证的一端，ticket 是双方共享的、与用户身份解耦的中间凭证，它必须随机不可猜、一次性消费、有效期短；确认动作只能由已登录的移动端发起，服务端据此授权；`state` 之类的参数与固定回调域名用来防 CSRF 与钓鱼跳转；登录态本身走 HttpOnly／Secure（Cookie 场景）或 JWT 的短有效期加撤销机制；二维码内容不要携带任何用户凭据，全部走服务端状态。能被追问到的一层是“为什么不用手机直接把账号密码传给 PC”——那会把凭据暴露在跨端通道里且无法控制授权范围，票据模型让授权可过期、可撤销、可审计。

## Q13：微服务架构中服务发现和负载均衡如何实现；注册中心（Nacos、Consul）如何工作，实例如何注册与保活（心跳机制）？

原题 17—18 同属服务发现与注册中心话题，合并为一题。

### 面试回答

服务发现解决“调用方怎么知道对方的地址”，链路是：实例启动时向注册中心注册（服务名、地址、端口、元数据、权重、版本），运行期持续续约，下线时主动注销或被探活摘除；调用方拿到某服务的一份实例列表，交给负载均衡器按策略选一个，再发起调用。

负载均衡分两个位置：客户端负载均衡（调用方进程内选实例，如 Ribbon／Spring Cloud LoadBalancer、Dubbo 的 Cluster 层）省一次网络跳、能拿到调用方视角的信息，但每种语言都要有实现；服务端负载均衡（DNS、LVS／Nginx 等反向代理、Service Mesh sidecar）把选择逻辑集中到代理层，业务无侵入、治理统一，但多一跳。策略上说得出这几种就够：轮询、随机与加权（权重常按机器规格或实例负载设）、最小活跃数（Dubbo 默认之一，对慢机器更友好）、一致性哈希（同参数稳定路由，便于本地缓存与有状态分片）。

注册中心的工作机制要按“实例类型”讲，这是最容易被追问的地方。临时实例（如 Nacos 的 ephemeral 实例、Eureka）：客户端主动发心跳续约（Nacos 默认 5 秒一次），服务端按阈值判定——约 15 秒没收到标为不健康、30 秒没收到直接摘除；这类系统按 AP 设计，网络分区时优先保证仍能拿到旧列表，代价是可能推到已经挂掉的实例。持久实例（如 Consul 的默认健康检查、Nacos 非临时实例）：由服务端主动去探活（TCP／HTTP 检查），检查失败只标不健康、不自动删实例。ZooKeeper 与 etcd 则是第三种形态：靠会话与临时节点，客户端 session 过期节点即消失，属于 CP，可用性与分区时的表现不如 AP 方案，所以注册场景要谨慎选。

实例列表的变更怎么让调用方感知：拉模型（客户端定时全量或增量拉，Eureka 约 30 秒，实现简单但有窗口延迟）、推模型（服务端长连接或事件通知，Nacos 用 UDP 推送加客户端拉取兜底、ZooKeeper／etcd 靠 watch、Consul 用 blocking query 挂起等变更）。最后要能讲三个真实工程坑：注册中心抖动或自我保护机制（阈值保护）触发时会把不健康实例留着，需要调用侧自己有失败重试与熔断兜底；实例下线要“先摘流量再停进程”，否则调用方还在用旧列表；调用方本地缓存快照能在注册中心不可用时继续调用，但地址变更要能重建连接池——这些才是“生产经验”的信号。项目里用哪个组件、怎么配的，按【真实实现】说。

## Q14：讲一下 Agent 中的“长短期记忆”；什么样的信息放长期记忆、什么放短期记忆？

原题 19—20 同属 Agent 记忆话题（概念与划分判据），合并为一题。

### 面试回答

短期记忆是“这次会话里的工作记忆”：对话历史、当前任务状态、已调用工具及其中间结果、计划与待办。它受上下文窗口预算约束、生命周期与会话同生死，追求“够当前这一步用”，价值随时间衰减。长期记忆是“跨会话还要成立的东西”：用户画像与稳定偏好（称呼、语言、常用环境、禁忌）、领域事实与业务口径、可复用的经验与流程（哪类任务该用哪个工具、上次踩过的坑）。它存在会话之外，写进外部存储，要能被检索、能更新、能冲突消解。

划分判据我给三条，比“按时间长短分”更可操作：① 生命周期——这句话在下次会话还有用吗？“用户叫某某、偏好中文回复、常用某个项目路径”是长期，“这次查询的中间结果”是短期；② 是否需要按内容检索——需要模糊召回的进长期（向量库或键值＋标签），只按会话取最新几条的留在短期；③ 是否属于原始对话——原始逐轮对话既不整段塞长期也不当事实用，它是证据，落库归档即可，长期记忆里存的是从中抽取出的结论，并带上来源与时间戳，方便后续更新或撤销。

被继续追问“怎么写入”时给工程细节：短期靠消息列表＋状态对象（放在 Redis 一类带 TTL 的存储里，重启可恢复），长期用抽取器（对话结束或每 N 轮把值得沉淀的事实结构化写入，向量库做召回、关系表存权威值），写入要判定冲突（新事实与旧事实是取代、补充还是矛盾，时间新者胜但冲突要显式提示而不是静默覆盖），并支持用户可见可删。落地程度按【真实项目】说，没做冲突消解就直说没做。

## Q15：对话轮数很多、上下文窗口不足时有哪些处理策略（截断、压缩等）；记忆压缩通常有哪些方法？

原题 21—22 同属上下文预算与压缩话题，合并为一题。

### 面试回答

处理策略按代价从低到高给四档：① 截断——丢最早的消息或最不相干的部分，实现简单，但会丢约束与未闭环的工具结果，只能当兜底；② 摘要压缩——把较早的历史折叠成摘要，只保留近期原文；③ 外置检索——把完整历史写到会话外的存储（向量库／数据库），窗口里只放按需召回的相关片段，等于对历史做 RAG，好处是可回读原文，代价是召回不准就丢关键信息；④ 结构化状态——把任务目标、约束、已确认事实、待办抽成字段常驻提示，不依赖对话原文，这是最省 token 也最容易做对的一档。实际系统通常是四者组合，而不是只做摘要。

压缩方法的具体做法：滚动摘要（新摘要＝f(旧摘要, 最近若干轮)，注意每次压缩都不可逆且有信息损失）、层级摘要（分段摘要＋顶层索引，需要细节时按引用回读该段而不是把所有内容糊成一段）、工具输出归一（把长篇输出压成结论＋可回读的引用 ID，分页与裁剪优先作用于工具结果而不是用户原话）、去重与同义合并（同一事实被反复表述时只留最新一条并保留来源）、关键信息保护清单（系统提示、任务目标、约束与偏好、进行中的工具状态、未完成的待办永不参与压缩）。触发要用水位而不是固定条数——例如到窗口的 80% 先折叠最早的段、90% 再降一级预算，并预留生成与工具结果的空间。

必须补一句自证：压缩后要验证。递归摘要会漂移（越压越偏、把不确定当结论），所以要有“摘要—原文一致性”的抽样核对与回读机制，以及关键事实丢失的回归用例；只做压缩不做校验，等于把幻觉写进记忆。项目里做到哪一档按【真实实现】说。

## Q16：了解过 Agent 的设计范式吗？有哪些？

### 面试回答

按“控制权交给谁”给一条谱系，比罗列名词更清楚：① 单次调用加结构化输出——一次请求让模型按 schema 返回结果，没有循环，能解决大多数分类、抽取、改写；② 固定工作流——流程与分支由代码编排（DAG／状态图），模型只负责其中的节点，确定性与可测性最好；③ ReAct 循环——模型交替“思考—选工具—观察”，由运行时驱动多步，适合不确定步数的任务；④ Plan-and-Execute——先出计划再执行、必要时重规划，适合长任务且便于展示进度；⑤ 反思／评审增强——再加一个评审者或自检步骤迭代改进输出，代价是成本翻倍；⑥ 多 Agent——按角色或子任务拆分上下文，解决单窗口装不下与权限隔离问题，也带来协调与失败传播成本。

选型判据给四条并表明自己会“降级”：任务是否需要多步与外部信息（不需要就别上 Agent）、流程能否预先写死（能就用工作流，模型只做节点）、错误代价与可验证性（无验收标准时不要放循环）、延迟与成本预算。收尾一句自己的判断：所谓范式不是进化阶梯，成熟系统常是“工作流为主干、局部用 ReAct、关键节点加评审”，把不确定性关在尽量小的盒子里。项目里用哪种、为什么，按【真实实现】答。

## Q17：你设计的 Agent 是怎么实现 ReAct 模式的？详细讲讲。

### 面试回答

按运行时的六个环节讲自己的实现：① 提示与状态——系统提示里给任务目标、工具清单（名称、参数 schema、何时该用）、输出格式约束（严格 JSON），状态对象保存消息历史、已执行动作与观察结果、剩余步数与预算；② 一步循环——模型产出“思考＋动作＋动作入参”，解析层把动作路由到具体工具，执行前按 schema 校验参数并对写操作做权限与幂等确认；③ 观察回填——工具结果归一后写回（长输出截断或只留结论加引用 ID），错误也作为观察喂回去而不是抛异常终止，让模型有机会改道；④ 终止判定——模型显式给出 final answer、或达到最大步数／超时／成本上限时强制收尾，两种情况返回内容不同（前者是答案，后者是“未解决＋已收集证据”）；⑤ 循环抑制——记录动作签名，同一动作与参数重复出现即注入提示打断，连续失败若干次就降级为直接检索或向人确认；⑥ 可观测与评测——每步留痕便于回放，用固定任务集跑成功率、平均步数、成本与失败类型分布，改动只按指标决定。

要主动说清它解决的问题与代价：ReAct 的价值在于步数不定时能自主取信息，代价是错误会沿链路传播、成本和延迟不可预测、以及“看起来在推理其实没进展”——所以我的实现里最重要的不是循环本身，而是预算、终止判定和循环抑制。如果项目其实用的是固定工作流，就如实说清边界（哪些节点是模型决策、哪些是代码分支），别把编排包装成 ReAct。

## Q18：手撕：实现一个并发任务处理器——100 个任务 ID，最大并发数为 3，模拟并发调用外部接口（如打印 ID）。

原素材未记录现场使用的语言与完成情况，下面给 Java 与 Go 两种口径的实现与要点。

### 面试回答

这题考的是“限制同时在飞的任务数”，本质是信号量或固定大小工作池，两种写法都要会说。Java：最省事的是固定线程池——`ExecutorService pool = Executors.newFixedThreadPool(3)`，提交 100 个任务后 `shutdown()` ＋ `awaitTermination()`；更贴近“并发数”原意的是 `Semaphore(3)`：每个任务 `acquire()`、`finally` 里 `release()`，配并发容器或 `CountDownLatch` 等全部完成（Java 21 起可以直接虚拟线程 ＋ Semaphore，线程数不再是约束，靠许可控制并发）。Go：`golang.org/x/sync/errgroup` 的 `g.SetLimit(3)` 然后循环 `g.Go(func(){...})` 再 `g.Wait()`；或自己写一个容量为 3 的带缓冲 channel 当令牌池，起 goroutine 前 `tokens <- struct{}{}`、完成时 `<-tokens`。

写完要主动补三点，这才是这题的深水区：① 失败与取消——外部接口报错是重试还是继续（要设重试上限与退避），一个任务失败是否取消其余（Go 用 `context.WithCancel`／`gctx`，Java 用 `Future.cancel` 或中断），必须保证已获取的许可与 goroutine／线程一定释放，否则并发数会“漏”；② 有序与可观测——结果要不要保持原顺序（按索引写回数组而不是加锁追加）、进度与耗时统计；③ 并发数不等于 QPS——限制同时在飞的请求数是最常用的自我保护，真要限制速率还得配令牌桶或漏桶，两者一起用。最后提一句验证方法：让模拟调用睡眠固定时间，观察同时在执行的数量峰值是否恰为 3、总耗时是否符合“100/3 × 单次耗时”的量级。
