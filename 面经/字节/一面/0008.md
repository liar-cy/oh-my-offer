## Q02：项目里分了哪些服务，怎么做到远程调用的？

这题考“你能否把自己的项目讲成一个分布式系统”，答案要落到真实项目事实上（缺失处填写，不虚构）。可复用口径：

- **服务划分依据**：按业务域／单一职责拆（如 用户、订单、内容、网关…）。
  - 拆的理由是变更频率、团队边界或扩缩容粒度不同，不是为了微服务而微服务。
  - 要能说清“为什么这几个不合并”。
- **远程调用方式**：服务间用 ______（如 Dubbo／gRPC／OpenFeign over HTTP）。要能展开四点：
  - 寻址：直连，还是走注册中心（ZooKeeper／Nacos）做服务发现。
  - 序列化：JSON 还是二进制（protobuf／Hessian）。
  - 调用语义：同步阻塞／异步，超时与重试参数。
  - 一次调用经过哪些组件：客户端负载均衡 → 网络 → 服务端线程池。
- **踩过的坑**：超时链路、重试放大、幂等、部分失败——顺势引出后面的场景题。

框架背后对应的通用知识见 SYS-029（服务拆分、注册发现、远程调用与容错）。面试时“先讲自己项目怎么做的，再补一句通用权衡”最稳。

## Q03：场景题：用 RPC 把 A 实例上的文件信息同步到 B 实例（例如表格），怎么设计？

这是压力面里的开放设计题，考“跨实例状态同步”的通用思路。先澄清题意（表格是结构化协同编辑，还是文件元信息复制），再按口径给方案：

- **先问：谁是事实源。** 推荐把权威数据放在共享存储（数据库／对象存储），A、B 实例只是无状态计算节点。这样“同步”退化为“都从权威源读最新”，最不容易出错。面试官说“必须在实例间同步”时，再走下面的直接同步模型。
- **同步什么：增量而非全量。** 表格类结构化数据不传整份文件，传“操作／版本”。
  - 给每条变更记录一个单调递增的版本号或操作日志（op log）。
  - B 拉取／接收增量并回放。
- **怎么传：推拉结合。**
  - 低频：B 定时拉，简单、可合批。
  - 实时性高：A 经消息总线（MQ／pub-sub）或直接 RPC 推给 B。
  - 大文件：走对象存储传引用，只同步元数据。
- **冲突与一致：** 并发编辑要明确模型——last-write-wins 按时间戳、按操作合并（协同表格用 OT／CRDT）、或加行级锁。跨实例是最终一致：先保证收敛，再谈延迟。
- **可靠性：**
  - 每次同步携带幂等标识与版本，网络抖动重试不能重复应用（见 Q04）。
  - B 侧对乱序、重复、丢失消息，用版本号做去重与断点续传。
  - 同步失败要有对账／重放兜底。

答题骨架：**权威源 → 增量（版本／oplog）→ 传输（推拉／MQ）→ 冲突解决（LWW／OT／CRDT）→ 幂等与对账**。

## Q04：怎么保证同步操作只执行一次（幂等性）？

幂等的本质是“同一操作执行一次和执行多次，对目标状态的效果相同”，同步／重试场景必备：

- **去重标识**：给每次同步操作一个全局唯一 ID（业务键或雪花／UUID）＋单调版本号，接收方按 ID／版本判重。
- **判重落地**，三种做法：
  - 已处理集合：用 Redis SETNX／数据库唯一索引记录已处理的 ID，重复的直接返回上次结果。
  - 版本比较：只接受版本号大于本地已应用版本的操作，乱序、重复、过期都被自然过滤（表格／文档同步最常用）。
  - 状态机：只有处于某状态的请求，才允许触发一次转移。
- **原子性**：判重＋执行要在同一原子步骤内（Redis Lua／数据库事务）。否则“检查—执行”之间有竞态，仍会重复。
- **天然幂等 vs 设计幂等**：读、`set x=5`、`INCRBY`（用唯一 ID 记录增量）幂等；`INSERT` 追加、`amount+=x` 非幂等，需靠幂等键或条件更新改造。
- **代价**：幂等存储要设过期窗口（窗口外不保证）。还要说清“幂等只是允许安全重试”，最终仍需对账才能发现丢失。

候选人当时答“用 Redis 分布式锁保证只执行一次”——锁只能把并发写串行化，解决不了“重试导致的重复执行”（持锁执行成功后崩溃，重试仍会再执行一次）。正确方向是幂等键／版本号判重＋条件写，见 SYS-013。

关联专题：[[专题题库/系统设计#SYS-013：接口幂等性如何设计，重复提交订单怎么处理？|SYS-013：接口幂等性如何设计？]]、[[专题题库/Redis#REDIS-006：Redis 分布式锁如何正确加锁、解锁和续期？|REDIS-006：Redis 分布式锁如何正确加锁、解锁和续期？]]

## Q05：让你设计一个分布式服务系统，大概会怎么设计？

开放题考“分层框架 + 逐层能展开”，不要一上来堆组件名。骨架：

1. **先问需求与约束**：QPS／数据量、读写比、一致性要求、延迟目标、可用性预算——设计随这些取值而变。
2. **服务拆分**：按业务域／单一职责拆，边界看变更频率、团队与扩缩容粒度（能合并就别过度拆）。
3. **通信**：同步调用（RPC／HTTP）走关键链路，异步解耦与削峰走 MQ。
4. **注册发现与配置**：服务实例注册到注册中心（Nacos/ZK），客户端／网关做负载均衡与故障摘除；配置中心统一下发。
5. **接入层**：网关做路由、鉴权、限流。
6. **数据层**：缓存（多级／一致性策略）、分库分表、主从与读写分离，冷热分离。
7. **一致性与容错**：跨网络调用一律带超时，配重试退避＋上限、熔断、降级；数据用最终一致 + 幂等 + 对账。
8. **可观测与运维**：指标／日志／链路追踪 + 告警，灰度发布、压测容量、故障演练。
9. **高可用**：去单点、多副本、多可用区部署。

一句话收尾：先保证“单链路正确”，再用冗余、隔离和可观测把故障影响控制在预算内——这与 SYS-027 可靠系统设计同源。

## Q06：有 A、B、C 三个线程，如何保证它们的执行顺序？

要求“A→B→C 依次执行完”，最直接的现场答案是 **`join`**：

```java
Thread a = new Thread(taskA);
Thread b = new Thread(taskB);
Thread c = new Thread(taskC);
a.start(); a.join();   // 等 A 结束
b.start(); b.join();   // 等 B 结束
c.start(); c.join();   // 等 C 结束
```

或在 B 的任务里 `a.join()`、C 的任务里 `b.join()`，让线程互相等待前驱。

等价手段还有四种：

- 单线程线程池按序 `submit`（`Executors.newSingleThreadExecutor()`），天然串行。
- `CountDownLatch`：B 等 A 的 latch 归零再跑。
- 有依赖关系时，用 `CompletableFuture.thenRunAsync` 串起来。
- 显式锁／`Condition` 按标志位放行——这是最重的手段。

候选人最初答“把 A/B/C 放进公平等待队列，一个个取”——那描述的是“公平调度的排队”，并不能表达“必须 A 完成再 B”的依赖，面试官不认可；回到 `join`／串行线程池／latch 这类“等待前驱完成”的机制才是本题要的答案。

## Q07：介绍一下 Java 里的 CMS 和 G1 这两个 GC

**CMS（并发标记清除）** 目标是低停顿，四个步骤：

- 初始标记：短暂 STW（全局停顿），只标 GC Roots 的直接引用。
- 并发标记：与用户线程同时遍历引用图。
- 重新标记：再次短暂 STW，修正并发期间的引用变化。
- 并发清除：并发回收、不移动对象。

代价有五条：与用户线程抢 CPU、要预留堆空间、有**浮动垃圾**、不整理导致**碎片**、分配失败会 Concurrent Mode Failure 退化成单线程 Full GC。它在 JDK 9 被废弃（JEP 291）、JDK 14 移除，答完主动补一句“现在默认是 G1”。

**G1** 把堆切成等大 Region，年轻／老年代只是逻辑分组。流程是 Young GC →（占用达阈值）并发标记周期 → Mixed GC：回收年轻代加一批垃圾最多的老年代 Region，“Garbage First”就是这么得名。

- 用记忆集控制跨区扫描，用 SATB 保证并发标记的正确性。
- 停顿做成可调目标：`-XX:MaxGCPauseMillis`，默认约 200ms，这是调度目标而非硬上限。
- 适合大堆、延迟敏感的服务，是 JDK 9 起的默认收集器。
- 代价：复制与写屏障开销、humongous 大对象处理。

**选型**三条：

- 小堆、吞吐优先 → Parallel。
- 中大型堆控停顿 → G1。
- 亚毫秒暂停的超大堆 → ZGC（JDK 21 起分代 ZGC）。

一句话区别：CMS 并发清除不整理（有碎片），G1 并发标记＋暂停内复制整理（无碎片、停顿可预测）。

## Q08：单例模式了解吗，具体有什么应用？

单例保证“一个类只有一个实例，并提供全局访问点”。写法谱系：

- **饿汉式**：`static` 字段里直接 `new`，类加载即创建，天然线程安全，代价是不用也占内存、无懒加载。
- **懒汉式（无锁）**：`getInstance` 里判空再创建，延迟加载但**多线程不安全**（见 Q09）。
- **双重检查锁（DCL）**：`volatile` 实例字段 ＋ 两次判空 ＋ `synchronized`，兼顾懒加载与线程安全（手撕常考）。
- **静态内部类**：靠类初始化实现懒加载＋线程安全，写法简洁，推荐。
- **枚举**：`enum` 单例，天然防反射攻击与反序列化破坏，《Effective Java》推荐。

**应用**：

- Spring 容器的 Bean，默认作用域就是单例。
- 线程池、`Runtime`、日志 `Logger`、配置对象、连接池、缓存——这类“全局唯一且共享”的对象。

答题时补一句边界，显得想得全：

- 单例是共享可变状态，多线程访问要么做成无状态，要么自己保证线程安全。
- 单例过多会隐藏依赖关系，也增加测试难度。

## Q09：手撕：实现一个懒加载的单例（追问：多线程同时创建会重复创建吗）

**候选人当时的思路**（原样保留）：把实例设为 `static volatile`，`getInstance` 先检查实例是否存在再创建。面试官追问“多个线程同时创建不就重复创建了吗”，候选人答“借用 Redis 锁的理念，先到的线程持锁表示准备创建，后到的看到有锁就放弃”。方向对（意识到要互斥），但表述偏分布式锁，现场没写出正确的双检锁代码。

**规范实现——双重检查锁（DCL）**：

```java
public class Singleton {
    // volatile 缺一不可：禁止“分配内存-初始化-赋引用”重排序，保证其他线程看到引用时对象已初始化
    private static volatile Singleton instance;
    private Singleton() {}
    public static Singleton getInstance() {
        if (instance == null) {                    // 第一次检查：无锁快速路径
            synchronized (Singleton.class) {
                if (instance == null) {            // 第二次检查：持锁后再判，防重复创建
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}
```

针对追问“多线程同时创建会不会重复”：会。

- 只判空不加锁时，两个线程都看到 `null`、各自 `new`，就产生两个实例。
- 解决就是**加锁＋双重检查**：外层判空避免每次都进同步块（性能），内层判空保证真正持锁后只有一个线程创建。
- `volatile` 管的是另一件事：`new` 的指令重排序会让别的线程拿到“引用非空但未初始化完”的半成品对象——少了 `volatile`，DCL 在理论上是坏的。

比 DCL 更省心的答案：静态内部类或枚举（类加载机制天然保证线程安全＋懒加载）。面试时可以主动提一句：“生产我更倾向枚举／Holder，但既然要求手撕 DCL，就写双检锁。”

## Q10：手撕：实现 LRU

LRU（最近最少使用）要求 `get`／`put` 均为 O(1)。标准解是 **哈希表 ＋ 双向链表**：

- 哈希表：按 key O(1) 定位节点。
- 双向链表：维护“最近使用”的顺序，越靠近头部越新。

```java
class LRUCache {
    class Node { int k, v; Node prev, next; Node(int k,int v){this.k=k;this.v=v;} }
    final Map<Integer, Node> map = new HashMap<>();
    final Node head = new Node(0,0), tail = new Node(0,0); // 哨兵
    final int cap;
    LRUCache(int capacity){ cap=capacity; head.next=tail; tail.prev=head; }
    int get(int key){
        Node n = map.get(key);
        if (n == null) return -1;
        moveToHead(n);            // 命中即“最近使用”
        return n.v;
    }
    void put(int key, int value){
        Node n = map.get(key);
        if (n != null){ n.v = value; moveToHead(n); return; }
        n = new Node(key, value); map.put(key, n); addToHead(n);
        if (map.size() > cap){                 // 容量满：淘汰尾部（最久未用）
            Node lru = tail.prev;
            remove(lru); map.remove(lru.k);
        }
    }
    void remove(Node n){ n.prev.next = n.next; n.next.prev = n.prev; }
    void addToHead(Node n){ n.next = head.next; n.prev = head; head.next.prev = n; head.next = n; }
    void moveToHead(Node n){ remove(n); addToHead(n); }
}
```

要点／易错四条：

- 用哨兵 `head`／`tail`，省去大量边界判断。
- `get` 也要把节点移到头部，它也算“使用”。
- 淘汰时先 `remove` 链表节点，再 `map.remove(node.key)`——所以节点里必须回存 key。
- 手写双向链表容易在指针摘挂上出错，这正是候选人“写过 Hot100 但现场写崩”的地方。

偷懒写法可以提，但要能解释：Java 里用 `LinkedHashMap(cap, 0.75f, true)` 重写 `removeEldestEntry` 一行搞定，面试时要说明它内部就是哈希＋链表。
