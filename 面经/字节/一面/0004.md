## Q01：Redisson 解决了什么问题，底层是怎么实现的？

### 面试回答

它解决的是手写 Redis 分布式锁难写对的问题：加锁解锁的原子性、误删他人锁、过期续期、可重入和等锁自旋，自己处理很容易留下竞态 bug。Redisson 把锁、读写锁、信号量、限流器等分布式原语封装成 Java 对象，这些边界都给了经过设计的实现。

底层核心是三件事：

- 所有状态变更用 Lua 脚本在 Redis 内原子执行。
- 可重入锁把“客户端＋线程”标识作为 Hash 的 field、重入次数作为 value。
- 看门狗对未指定 lease（锁的过期时间）的锁自动续期；等锁的客户端订阅解锁通知，而不是纯轮询。

最后一句拔高：它解决的是“用 Redis 做分布式协调”的通用问题，锁只是其中最常用的一部分。

## Q02：模型选用、鉴权、上下文处理、偏好提取、记忆系统与主流 Agent 实现方案如何设计？

### 面试回答

这是一组 Agent 项目设计的老生常谈，逐项给口述要点：

- 模型选用：按真实任务集比较工具调用正确率、推理质量、时延和成本；强模型做规划与难任务，小模型或规则做稳定路由。
- 鉴权：用户身份与工具权限都在服务端校验；模型生成的参数不可信；密钥不进 Prompt、模型上下文和日志。
- 上下文处理：指令、历史、检索证据、工具结果和任务状态分区组织，按需加载；超预算时做结构化摘要并保留回查入口。
- 偏好提取：从对话抽取候选事实，去重与冲突校验后，带来源和生效期落库，允许用户纠正；不把一次性表达当长期偏好。
- 记忆系统：区分会话短期状态和跨会话长期事实；短期放 Redis，长期放持久化存储加检索索引。
- 主流实现方案：按层比较——模型 API 加原生工具调用、编排框架（LangGraph 等）、Agent 产品（Claude Code、Codex 类）与接入协议（MCP、A2A），不要跨层次排名。

项目真实选型与实现细节需按【实际方案】填写。

## Q03：记忆系统为什么用 Redis，有什么好处？

### 面试回答

先说负载特征：记忆读写是伴随每轮对话的高频低延迟操作——会话开始要快速召回，结束要写入候选事实。Redis 的好处对得上这个特征：

- 内存服务，QPS 高、延迟稳定。
- 数据类型能直接映射记忆形态：Hash／String 存当前事实与偏好，ZSet 按时间或权重排序召回，TTL 做过期，多实例共享一个存储。
- RDB／AOF 持久化和主从能提供基本可靠性。

但要把边界讲清：Redis 不适合复杂条件查询、版本历史和语义检索。生产级记忆一般用它做热层——长期事实在数据库主存，向量或全文索引负责召回，再按需加载进 Redis 和上下文。

## Q04：服务器宕机了怎么办、怎么恢复，Agent 宕机了怎么办？

### 面试回答

宕机分三类：进程崩溃、机器失联和依赖故障。恢复思路一致：服务无状态、状态外置。

- 检测靠多层探活：平台存活探针自动重启；健康检查挂负载均衡摘除实例；业务超时与心跳告警发现“活着但不响应”。
- 恢复靠：实例自动重建、主从或副本切换、在途请求按幂等键重试；重建后预热流量，防止缓存被打穿。

Agent 服务还多一层“任务级”恢复：

- 任务状态、计划、工具调用结果和检查点持久化在外部存储；重启后按 taskId 从已验证的检查点继续，而不是从头重跑。
- 已发出但结果未知的副作用工具调用，先查目标系统实际状态再决定重试。
- 长任务失败要有超时、取消和人工接管出口。

## Q05：MCP 实现的关键是什么，怎么做鉴权？

### 面试回答

实现关键是忠实落实协议语义：

- `initialize` 完成版本与能力协商。
- tools／resources／prompts 做发现和声明式 schema。
- 调用时服务端先校验参数再执行；协议层错误与工具执行失败（isError）分开表达。
- 本地 stdio、远程 Streamable HTTP，按部署形态选择。

最重要的设计原则：真正的执行权、幂等和权限校验都放在 Server 端；协议只标准化交互，不替业务保证安全。

鉴权按传输区分：

- 远程 MCP：官方规范按 OAuth 2.1 做——MCP Server 是资源服务器，由授权服务器签发令牌；强制 PKCE，用 resource indicator 绑定令牌受众，支持动态客户端注册。
- stdio 本地服务：不走该流程，凭据一般由环境变量或系统钥匙串注入。

无论哪种，服务端都要验证调用者代表的最终用户身份和资源归属，防止把服务端自身凭据透传给下游造成混淆代理；密钥不进工具参数和提示词。

## Q06：记忆怎么按需读取？

### 面试回答

原则：不把全部记忆塞进上下文。召回分三步：

- 强过滤：先按用户身份、记忆类型和有效性强过滤，控制权限和过期数据。
- 检索：在子集内用关键词加语义相关性检索并重排，取 topK。
- 注入：按 token 预算注入，带来源标识便于引用和回查。

两类数据区别对待：高频当前值走缓存直接读；长尾档案只注入摘要和回查句柄，详情让 Agent 用工具再取。记忆更新后要重建检索索引，避免旧事实继续召回。

本质和上下文工程一致：上下文是稀缺预算，记忆是外部持久数据，只有被过滤和相关性选中才进窗口。

## Q07：MCP、Function Calling 和 A2A 有什么区别？

### 面试回答

结论：三者不在同一层，可以在一个系统里组合使用。

- Function Calling：模型 API 能力。宿主注入工具描述，模型输出结构化的“函数名＋参数”，表达调用意图，执行由调用方完成——解决“模型如何表达要用工具”。
- MCP：AI 应用与外部工具、数据资源之间的接入协议，基于 JSON-RPC 定义发现与调用，让工具服务跨宿主复用——解决“应用如何接工具”。
- A2A：Agent 与 Agent 之间的对等协作协议：通过 Agent Card 声明能力，围绕任务生命周期交换消息和产物，支持不透明协作——解决“智能体之间怎么互操作”。

典型链路串一遍：模型 function calling 提出调用 → 宿主经 MCP 转成对工具 Server 的请求 → 跨 Agent 的子任务用 A2A 委派。

## Q08：系统提示词怎么设计？

### 面试回答

分层写，五块内容：

- 角色与目标。
- 能力边界和工具使用规则：何时调用、缺参先澄清、失败如何处理。
- 安全与授权约束。
- 输出格式契约。
- 稳定的背景知识。

原则是“少而稳”：权限和参数校验放在执行层，而不是靠措辞；长变化内容用外部状态或 Skill 按需加载，不把所有知识硬编进提示词。

最后要工程化：系统提示词版本化，用覆盖正常、歧义、工具失败和越权场景的评测集验证改动，避免越写越长。

## Q09：Skill 是怎么调用的，写在提示词里就能用吗？

### 面试回答

结论：不是写进提示词就能用。以 Agent Skills 机制为例，核心是“渐进式披露”：

- 宿主启动时，只把每个 Skill 的 name 和 description 元数据放进上下文。
- 任务与描述匹配触发后，才读取 SKILL.md 正文，再按需加载参考文件、执行脚本。
- 效果：平时不占预算，用时完整展开。

对比一下：把一段文字复制进系统提示词，只是给了常驻指令——没有按需加载，没有资源文件与脚本执行链路，也不获得任何工具权限。Skill 需要被宿主发现和管理，权限仍由运行时和工具层控制。

## Q10：single-agent 和 multi-agent 的优缺点？

### 面试回答

两边优缺点对着说：

- 单 Agent：调用链短、上下文集中、成本和排障都更低，适合边界不清或强耦合任务；缺点是工具和指令堆多时上下文拥挤、权限难收敛、单点角色过载。
- 多 Agent：可按专长和权限边界拆分、子任务并行、各自维护独立上下文；代价是协调、交接信息损失、重复推理、状态冲突和恢复复杂度。

结论不是站队：能用一个 Agent 稳定完成就用一个。拆不拆，要在同一任务集上对比成功率、人工接管率、延迟和成本，收益超过协调开销才值得。

## Q11：MySQL 索引底层是怎么实现的？

### 面试回答

InnoDB 的常规索引是 B+ 树，抓三个结构特点：

- 非叶子节点只存导航键值：扇出大、树高低。
- 叶子节点存键加载荷，并用双向链表连接：等值和范围查询都走同一棵树。
- 主键索引（聚簇）叶子存整行；二级索引叶子存索引列加主键值，查询缺列时按主键回表。

配套机制：页是磁盘读写单位，索引节点就是一个页，配合缓冲池缓存热点页。

为什么不选别的：不用 B 树，是因内部节点带数据会降低扇出；不用纯哈希，是因无法有序遍历和范围扫描。

## Q12：最左前缀匹配法则是什么，什么时候会失效？

### 面试回答

一句话：联合索引按列定义顺序构造 B+ 树键序，查询要从最左列开始连续匹配，才能利用有序性定位。

- 条件 a、a＋b、a＋b＋c 可用；只给 b 或 c 定位不了。
- 等值前缀之后遇到范围条件，范围列后面的列不能再用于定位。

常见“失效”场景：跳过前导列、范围切断、对索引列使用函数或表达式、隐式类型转换、LIKE 以百分号开头、OR 中混入无索引列。

注意表述别说过头：失效通常是“无法用它定位”；优化器仍可能把它当覆盖索引做索引内过滤，或走 Skip Scan 等特例。最终用不用、用到哪一列，由执行计划说了算。

## Q13：给出一段 SQL，可以在什么位置建立索引？

> 面试官给出了具体 SQL，原文未记录语句内容，本题按通用方法论整理，不代表原 SQL 的真实最优解。

### 面试回答

先要回查询模式，再给方案。方法论分四步：

- 找列：WHERE 等值列、范围列、连接列、ORDER BY 与 SELECT 返回列。
- 定序：等值列放联合索引前部；范围列之后，排序列通常用不上索引顺序。列序还要同时考虑其他高频查询对左前缀的复用和选择性，不是“区分度高永远在前”。

- 验证：候选方案在代表性数据上用 EXPLAIN ANALYZE 对比扫描行数、是否 filesort 和写入成本，而不是背套路。

## Q14：大分页查询怎么优化？

### 面试回答

先讲问题：`LIMIT n OFFSET m` 在大偏移时要把前 m 行扫出来再丢弃，走二级索引还有大量回表，延迟随页深线性恶化。

优化按场景选：

- 首选 seek 法（书签式分页）：不传页码，带上上一页最后一行的排序键值，`WHERE (排序列, id) > (上次的值) ORDER BY ... LIMIT n`，直接走索引定位；代价是不支持跳页。
- 必须保留跳页语义时用延迟关联：先用覆盖索引的子查询分页取主键，再回表取整行，减少扫描和回表成本。
- 深翻导出：改流式批次或离线索引（ES）。
- 业务侧兜底：限制最大页数、去掉精确总数，也是常用手段。

## Q15：缓存击穿、缓存穿透、缓存雪崩是什么，怎么解决？

### 面试回答

一句话记忆：三者分别对应“数据不存在”“单点失效”“大面积失效”，解法不可互换。

- 穿透：请求本来不存在的数据，缓存永远不命中、反复打数据库。解法：参数校验、空值缓存、布隆过滤器和限流；注意布隆有假阳性，不能称完全解决。
- 击穿：单个热点 key 过期瞬间，大量并发同时回源。解法：互斥重建、请求合并、逻辑过期或提前刷新；业务允许时可返回旧值异步更新。
- 雪崩：大批 key 集中过期，或缓存服务整体不可用。解法：打散 TTL、提升缓存可用性，并用限流、熔断降级和回源并发上限保护数据库。

## Q16：SSE 和 WebSocket 之间的区别是什么？

### 面试回答

两者定位不同：

- SSE：HTTP 响应流加 text/event-stream，浏览器用 EventSource 持续接收服务端推送；方向以服务端到客户端为主，上行走普通请求。事件可带 id 和 retry，浏览器原生重连。
- WebSocket：握手升级后是双向通道，支持文本和二进制消息；但重连、消息确认、鉴权刷新和背压都要应用自己设计。

选型：流式推送进度、通知、LLM token 输出用 SSE 更简单——复用 HTTP 基建、自带重连；聊天、协同编辑、游戏和高频双向控制用 WebSocket。

一句话收束：选型的差异，就在这几件事由谁负责。

## Q17：SSE 中间断开了怎么办？

### 面试回答

基础机制：浏览器 EventSource 会自动重连，间隔可由服务端 retry 字段控制；重连时带 Last-Event-ID 请求头。所以服务端事件要发递增或有意义的 id。之后分两类恢复：

- 能重放的场景：按 id 续推漏掉的事件。
- 不能重放的内容另设恢复：LLM 流式生成断线后，通常按消息 ID 重新拉取已生成部分再接续生成，或整段重来，而不是假装续传 token；客户端按事件 id 去重保证幂等。

还要配两个细节：心跳注释行防代理空闲断连；服务端产出比消费快时，要处理背压与断开策略。

## Q18：并发和并行是什么、有什么区别，IO 密集型适合并发还是并行？

### 面试回答

概念分开：

- 并发：同一时间窗口内多个任务都在推进——单核上靠时间片交替，任一时刻其实只有一个在跑。
- 并行：多个任务在多个核上同一时刻物理执行。
- 关系一句话：并发是程序结构，并行是执行状态。

IO 密集型适合哪种：它的耗时大头在等待设备与网络，不占 CPU，所以适合用高并发组织——异步 I/O、事件循环或协程能用少量线程承载大量等待中的连接；盲目开很多并行线程只会增加切换开销。CPU 密集型要提吞吐必须靠多核并行，单靠并发结构不会变快。

准确说法：IO 密集靠并发获得边际收益，CPU 密集靠并行扩吞吐，真实服务两者往往兼有。

## Q19：介绍一下 TCP 的拥塞控制和流量控制。

### 面试回答

先分清两个目标：流量控制防压垮接收方，拥塞控制防压垮网络本身。

- 流量控制：接收方用 ACK 通告接收窗口 rwnd，发送方未确认在途数据不超过它；窗口为 0 时，发送方周期性地发零窗口探测，接收方有空位后发窗口更新。
- 拥塞控制：发送方维护拥塞窗口 cwnd，估计网络可承载的在途上限；实际可发字节受 min(rwnd, cwnd) 约束。

经典拥塞算法四段：

- 慢启动：从小窗口指数增长到阈值 ssthresh。
- 拥塞避免：改为加性增长（AIMD，加性增、乘性减）。
- 收到三个重复 ACK：快速重传并快速恢复。
- RTO 超时：大幅收缩，重进慢启动。

两者的区别一句话：rwnd 由接收端缓冲决定、反映端侧容量；cwnd 是发送端对网络状态的自适应估计，丢包是其主要收缩信号。

可补的实现差异：现代 Linux 默认 CUBIC，BBR 改用带宽与 RTT 建模。
