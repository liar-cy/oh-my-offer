## Q01：LangGraph 的特征是什么，为什么用图结构编排，if-else 不行吗？

### 面试回答

LangGraph 的特征：state 共享状态＋node 步骤＋edge 转移（含条件边与循环），配 checkpoint 中断恢复、并行分支与人工介入点。if-else 当然“能写”——线性流程、少量分支时嵌套判断最直接；图结构解决的是流程复杂后的工程问题：转移关系从散落在代码里的分支变成可枚举、可可视化、可单测的拓扑；循环/重规划、跨节点并行、断点恢复、状态回放这些用裸 if-else 实现会迅速失控。结论按复杂度给：分支少且稳定就 if-else，出现循环、恢复、多分支汇合再上图框架，别为架构而架构。

## Q02：除了 LangGraph，还了解哪些 Agent 架构？

### 面试回答

按控制方式给谱系：单次调用＋结构化输出、固定工作流（代码/DAG）、ReAct 式推理行动交替、Plan-and-Execute（先规划再执行、可重规划）、反思/评审增强、多 Agent 分工（supervisor、流水线、群聊/辩论）。框架层面了解 LangChain/LangGraph、AutoGen（后继 Microsoft Agent Framework）、CrewAI、OpenManus 等；只了解未用过就如实分层，不跨层次排名。

## Q04：自己设计一个 Agent，会选择 LangGraph 还是手搓？

### 面试回答

按需求给结论：任务简单、循环逻辑清晰、要完全吃透每一步（学习/面试场景或极小 MVP）→ 手搓，行为可控、排障不隔层；需要复杂分支汇合、循环重规划、中断恢复、团队协作与长期维护 → 用 LangGraph 这类显式状态图，别自己重造 checkpoint 与调度。两者不互斥：先手搓理解原理，产品化时再评估引入框架替换哪些部件；决定权在任务形态与团队维护成本，不在框架热度。

## Q05：Harness 分为哪些模块，除了 runtime 还有什么，比如评测？

### 面试回答

Harness 是模型之外的工程承载层，模块大致六块：① 运行时/循环——上下文组装、动作解析、工具执行、状态与预算控制；② 上下文管理——历史压缩、按需加载、检索注入；③ 工具与权限——schema 校验、鉴权、沙箱、结果校验；④ 状态与记忆——会话持久化、检查点恢复、长期记忆存取；⑤ 评测——任务集、指标、回归与线上反馈闭环；⑥ 可观测与治理——轨迹、成本、延迟、告警。评测和可观测常被忽略但决定迭代速度：没有评测的 harness 改动全凭感觉。

## Q06：调用 LLM 的时候会涉及到哪些互联网协议？

### 面试回答

按栈拆开：寻址靠 DNS；传输是 TCP（HTTP/1.1、2 over TCP；HTTP/3 走 QUIC/UDP）；安全层 TLS（证书认证＋对称加密通道）；应用层最常见 HTTPS＋REST/SSE 流式返回，内部服务间可能用 gRPC（HTTP/2）；长连接双向场景有 WebSocket；企业出口还有 CONNECT 代理与 VPN。再往外是 CDN、负载均衡与网关层。答题时按“解析→可靠传输→加密→应用协议→流式语义”串一遍，并能对每层展开（SSE 事件格式、TLS 握手、QUIC 为何换 UDP）。

## Q07：HTTP 和 HTTPS 有什么区别，非对称加密算法知道哪些，加代理抓包有什么影响？

### 面试回答

区别：80→443；明文→加密（握手期用非对称/密钥封装协商对称密钥，传输用对称加密）；无身份验证→证书链校验服务器身份；完整性由 TLS 保证。非对称算法：RSA（密钥交换/签名）、ECC 与 ECDSA（更高效，主流证书常用）、Ed25519、国密 SM2。抓包代理（mitmproxy/Fiddler/公司网关）本质是中间人：代理与客户端扮“服务器”、与真服务器扮“客户端”，两段 TLS 终止于代理，需要客户端信任其根证书，否则证书校验失败；因此生产 App 常做证书固定（pinning）防中间人，调试时抓不到包多半是这个原因，而不是“HTTPS 不能抓”。

## Q08：Redis 除了缓存还有什么作用？

### 面试回答

按数据结构讲用途：分布式锁（SET NX＋Lua 解锁，Redisson）；计数器/限流（INCR＋过期，滑动窗口）；排行榜与延迟队列（ZSet）；消息与任务队列（List、Stream 消费组）；去重与签到（Set、Bitmap）；UV 基数统计（HyperLogLog）；会话与幂等 token（TTL 键）；发布订阅做轻量事件通知。共同优势是单线程命令原子性、内存级延迟与过期机制；边界是持久化与容量，不适合作为唯一事实存储。

## Q09：抢到锁的服务线程挂了，一直不释放要怎么办？

### 面试回答

靠“锁是租约不是承诺”来设计：加锁必须带 TTL，持锁进程崩溃后无人续期，到期自动释放，其他实例接管——所以关键是 TTL 要大于业务正常耗时并留余量，同时防两件事：① 业务没做完锁先到期（看门狗续期）；② 过期后旧持有者复活继续写（fencing token／版本号让资源侧拒绝旧持有者）。若当初用了不带过期的裸 SETNX，就会死锁，只能人工清理——这正是 SET NX EX 必须原子带过期、解锁必须校验持有者的原因。强正确性场景再用数据库条件写兜底。

关联专题：[[专题题库/Redis#REDIS-006：Redis 分布式锁如何正确加锁、解锁和续期？|REDIS-006：Redis 分布式锁如何正确加锁、解锁和续期？]]

## Q10：用 Redis 设计一个功能统计次数。

### 面试回答

按需求分档：精确 PV/计数——`INCRBY` 原子加＋按维度拼 key（日期/租户/功能），落库归档后清 TTL；精确 UV（去重计数）——Set/SADD，内存随用户数线性涨，量大要评估；近似 UV——HyperLogLog，固定约 12KB、标准误差约 0.81%，适合“量级监控够用”的大基数场景；连续状态（签到）——Bitmap 位运算；多维分析——计数进 Redis 做实时层，明细异步进数仓。答题先问“精确还是近似、维度多少、保留多久”，再选结构，这本身就是考点。

## Q11：手撕：两个有序数组，找到其中第 k 大的元素。

### 面试回答

两种口径都要会说：两个有序数组合并视角下第 k 小（“第 k 大”先与面试官确认换算成 k' = m+n−k+1 再处理）。最优解二分：在较短数组上切分，使两数组“左半部分”共含 k 个元素且满足交叉大小关系，O(log(min(m,n)))；朴素解双指针模拟归并走 k 步，O(k) 更好写。手撕时先给双指针保证正确，再升级到切分二分，边界用 ±∞ 哨兵处理空左半。

## Q12：trading 的多个 Agent 之间结论有冲突时怎么办？

### 面试回答

冲突是多 Agent 的常态，要有显式仲裁机制而不是取平均：① 证据优先——要求每个结论附带可核对的证据与置信度，比“谁嗓门大”，证据缺失方降级；② 角色设计——引入 verifier/裁判 Agent 或规则断言复核分歧点，或按领域权威划分（各子域 Agent 在自己权限域内结论优先）；③ 决策融合——投票、加权（历史准确率作权重）或辩论后重投票；④ 兜底——分歧超阈值转人工或输出“不确定＋各方论据”，尤其交易类高风险场景宁可不决策。评测上把“冲突率、仲裁正确率”纳入指标，冲突样本回流做回归。

## Q13：多 Agent 都有哪些实现方式？

### 面试回答

按协作拓扑分：supervisor/中心调度（主 Agent 路由、子 Agent 执行，最常见可控）；流水线（固定顺序交接）；群聊/黑板（共享会话或共享存储上多方发言，灵活但难控）；层级式（调度器的调度器）；辩论/投票式（同题多解再仲裁）；事件驱动（消息队列异步协作，跨机扩展形态）。实现层要点一致：消息带任务 ID 与角色、交接传结构化结果和证据引用、共享状态放受控存储、并发认领用租约，并处理部分成功与重复执行。选型回到“是否真有独立专长/权限/上下文边界”，能单 Agent 就单 Agent。

## Q14：随着模型能力变强，最终是单 Agent 好还是多 Agent 好（奥卡姆剃刀、第一性原理）？

### 面试回答

用第一性原理拆：多 Agent 的存在理由只有三个——独立权限/安全边界、独立上下文（超窗或互相污染）、可并行的异构专长；模型变强削弱的是“能力分工”需求（一个模型就能干），但不消除边界、上下文与并行这三个物理约束。奥卡姆剃刀落在验证上：默认单 Agent，只有评测证明拆分的综合收益（成功率、延迟、成本、安全）大于协调开销才拆——历史上“工作流→Agent→多 Agent”的每次加复杂度都曾被证明过度。所以答案不是“谁最终赢”，而是复杂度必须持续用实验赎回；模型越强，默认解越偏向单 Agent＋好工具。
