## Q01：LangGraph 的特征是什么，为什么用图结构编排，if-else 不行吗？

### 面试回答

LangGraph 的特征是三个组件加一组能力。

- 三个组件：state 做共享状态、node 是一个步骤、edge 是转移，包含条件边与循环。
- 一组能力：checkpoint 中断恢复、并行分支、人工介入点。

if-else 当然“能写”——流程线性、分支少的时候，嵌套判断最直接。图结构解决的是流程变复杂之后的工程问题：

- 转移关系从散落在代码里的分支，变成可枚举、可可视化、可单测的拓扑。
- 循环／重规划、跨节点并行、断点恢复、状态回放这几件事，用裸 if-else 写会迅速失控。

结论按复杂度给：分支少且稳定就 if-else，出现循环、恢复、多分支汇合再上图框架。别为架构而架构。

## Q02：除了 LangGraph，还了解哪些 Agent 架构？

### 面试回答

按控制方式给一条谱系：

- 单次调用＋结构化输出。
- 固定工作流：代码或 DAG（有向无环图）编排。
- ReAct：推理与行动交替。
- Plan-and-Execute：先规划再执行，可重规划。
- 反思／评审增强。
- 多 Agent 分工：supervisor（中心调度）、流水线、群聊／辩论。

框架层面了解 LangChain／LangGraph、AutoGen（后继是 Microsoft Agent Framework）、CrewAI、OpenManus 等。

## Q03：pi agent 了解吗，为什么不用 LangGraph 编排？（指代待确认）

### 面试回答

“pi agent”的确切指代未确认（可能是某内部／开源的 Agent 产品名），不猜测编造。

能给的通用口径是：不少生产 Agent 产品确实不用图编排框架，而是“模型 API＋自研循环”。

- 循环逻辑本身不复杂时，手写的上下文组装、工具分发、状态管理更可控、依赖更轻、调试路径更短。
- LangGraph 的价值在显式状态图、checkpoint 恢复与复杂拓扑；任务形态用不上这些，不用它是合理取舍（同 Q04 的手搓 vs 框架）。

## Q04：自己设计一个 Agent，会选择 LangGraph 还是手搓？

### 面试回答

按需求给结论，两条路线：

- 手搓：任务简单、循环逻辑清晰、要完全吃透每一步——学习／面试场景或极小 MVP。好处是行为可控、排障不隔层。
- 用 LangGraph 这类显式状态图：需要复杂分支汇合、循环重规划、中断恢复、团队协作和长期维护。别自己重造 checkpoint 与调度。

两者不互斥，可以走这个顺序：先手搓理解原理，产品化时再评估引入框架、替换哪些部件。

一句收尾：决定权在任务形态与团队维护成本，不在框架热度。

## Q05：Harness 分为哪些模块，除了 runtime 还有什么，比如评测？

### 面试回答

Harness 是模型之外的工程承载层，模块大致六块：

- 运行时／循环：上下文组装、动作解析、工具执行、状态与预算控制。
- 上下文管理：历史压缩、按需加载、检索注入。
- 工具与权限：schema 校验、鉴权、沙箱、结果校验。
- 状态与记忆：会话持久化、检查点恢复、长期记忆存取。
- 评测：任务集、指标、回归，加线上反馈闭环。
- 可观测与治理：轨迹、成本、延迟、告警。

最后两块最容易被忽略，但它决定迭代速度：没有评测的 harness，改动全凭感觉。

## Q06：调用 LLM 的时候会涉及到哪些互联网协议？

### 面试回答

按协议栈一层层拆：

- 寻址：DNS 把域名换成 IP。
- 传输：TCP 承载 HTTP/1.1、HTTP/2；HTTP/3 走 QUIC／UDP。
- 安全层：TLS，做证书认证＋对称加密通道。
- 应用层：最常见 HTTPS＋REST／SSE 流式返回；内部服务之间可能用 gRPC（HTTP/2）。
- 长连接双向场景：WebSocket。
- 企业出口：CONNECT 代理与 VPN。

再往外还有 CDN、负载均衡与网关层。

说法上按“解析→可靠传输→加密→应用协议→流式语义”串一遍，并且每层都能展开一句：SSE 的事件格式、TLS 握手过程、QUIC 为什么要换成 UDP。

## Q07：HTTP 和 HTTPS 有什么区别，非对称加密算法知道哪些，加代理抓包有什么影响？

### 面试回答

区别说四条：

- 端口 80→443。
- 明文→加密。
- 无身份验证→证书链校验服务器身份。
- 完整性由 TLS 保证。

- 加密的分工：握手期用非对称／密钥封装协商出对称密钥，传输过程用对称加密。

非对称算法知道这几个：

- RSA：密钥交换／签名。
- ECC 与 ECDSA：更高效，主流证书常用。
- Ed25519。
- 国密 SM2。

第三问抓包代理（mitmproxy／Fiddler／公司网关），本质是中间人：

- 代理对客户端扮“服务器”、对真服务器扮“客户端”，两段 TLS 都终止在代理上。
- 前提是客户端信任了它的根证书，否则证书校验直接失败。
- 所以生产 App 常做证书固定（pinning）来防中间人。

结论：调试时抓不到包，多半是 pinning 拦的，而不是“HTTPS 不能抓”。

## Q08：Redis 除了缓存还有什么作用？

### 面试回答

别只说缓存，按数据结构讲用途最有层次：

- 分布式锁：SET NX 加锁＋Lua 脚本解锁，或者用 Redisson。
- 计数器／限流：INCR＋过期，能做滑动窗口。
- 排行榜、延迟队列：ZSet。
- 消息与任务队列：List、Stream 的消费组。
- 去重、签到：Set、Bitmap。
- UV 基数统计：HyperLogLog。
- 会话、幂等 token：带 TTL 的键。
- 发布订阅：轻量事件通知。

这些用法吃的是同一批红利：单线程命令的原子性、内存级延迟、过期机制。

边界也要说：持久化与容量是短板，Redis 不适合作为唯一的事实存储。

## Q09：抢到锁的服务线程挂了，一直不释放要怎么办？

### 面试回答

设计原则是“锁是租约，不是承诺”。

- 加锁必须带 TTL：持锁进程崩溃后没人续期，到期自动释放，其他实例接管。
- 所以关键是 TTL 要大于业务正常耗时，并且留余量。

余量之外还要防两件事：

- 业务没做完、锁先到期：用看门狗续期。
- 锁过期后旧持有者复活继续写：用 fencing token／版本号，让资源侧拒绝旧持有者。

反面情况说清楚：如果当初用的是不带过期的裸 SETNX，就会真死锁，只能人工清理——这正是 SET NX EX 必须原子地带上过期、解锁必须校验持有者的原因。

强正确性场景，再用数据库的条件写兜底。

## Q10：用 Redis 设计一个功能统计次数。

### 面试回答

按需求分档选结构：

- 精确 PV／计数：`INCRBY` 原子加，key 按维度拼（日期／租户／功能），落库归档后再清 TTL。
- 精确 UV（去重计数）：Set 的 SADD；内存随用户数线性涨，量大要先评估。
- 近似 UV：HyperLogLog，固定约 12KB、标准误差约 0.81%，适合“量级监控够用”的大基数场景。
- 连续状态（签到）：Bitmap 位运算。
- 多维分析：计数进 Redis 做实时层，明细异步进数仓。

开口先问三件事：要精确还是近似、维度有多少、保留多久，然后再选结构——这本身就是考点。

## Q11：手撕：两个有序数组，找到其中第 k 大的元素。

### 面试回答

两种口径都要会说：常见口径是两个有序数组合并视角下的第 k 小；如果题面真是“第 k 大”，先与面试官确认换算成 k' = m+n−k+1 再处理。

两个解法：

- 最优解是二分：在较短数组上切分，让两个数组的“左半部分”共含 k 个元素，且满足交叉大小关系，O(log(min(m,n)))。
- 朴素解是双指针：模拟归并走 k 步，O(k)，更好写。

手撕节奏：先给双指针保证正确，再升级到切分二分；边界用 ±∞ 哨兵处理空左半。

## Q12：trading 的多个 Agent 之间结论有冲突时怎么办？

### 面试回答

冲突是多 Agent 的常态，要有显式的仲裁机制，而不是取平均。四条做法按层给：

- 证据优先：要求每个结论都附带可核对的证据与置信度，比的是证据不是“谁嗓门大”；证据缺失的一方降级。
- 角色设计：引入 verifier／裁判 Agent，或用规则断言复核分歧点；也可以按领域权威划分，各子域 Agent 在自己权限域内结论优先。
- 决策融合：投票、加权（用历史准确率当权重），或者辩论后重新投一次。
- 兜底：分歧超过阈值就转人工，或者输出“不确定＋各方论据”。交易这类高风险场景，宁可不决策。

评测上把“冲突率、仲裁正确率”纳入指标，冲突样本回流做回归。

## Q13：多 Agent 都有哪些实现方式？

### 面试回答

按协作拓扑分六种：

- supervisor／中心调度：主 Agent 路由、子 Agent 执行，最常见也可控。
- 流水线：固定顺序交接。
- 群聊／黑板：在共享会话或共享存储上多方发言，灵活但难控。
- 层级式：调度器之上还有调度器。
- 辩论／投票：同一题多解，再仲裁。
- 事件驱动：走消息队列异步协作，是跨机扩展的形态。

实现层的要点各家都一样：

- 消息带上任务 ID 与角色。
- 交接传结构化结果和证据引用。
- 共享状态放在受控存储里。
- 并发认领用租约。
- 要处理部分成功与重复执行。

选型还是回到那一句：是不是真有独立的专长／权限／上下文边界，能单 Agent 就单 Agent。

## Q14：随着模型能力变强，最终是单 Agent 好还是多 Agent 好（奥卡姆剃刀、第一性原理）？

### 面试回答

用第一性原理拆：多 Agent 的存在理由只有三个——独立的权限／安全边界、独立的上下文（超窗或互相污染）、可并行的异构专长。

- 模型变强削弱的是“能力分工”这一条：一个模型就能干。
- 但边界、上下文、并行这三个物理约束不会被消除。

奥卡姆剃刀落在验证上：

- 默认单 Agent。
- 只有评测证明拆分的综合收益——成功率、延迟、成本、安全——大于协调开销，才拆。
- 历史上“工作流→Agent→多 Agent”的每次加复杂度，都曾被证明过度。

所以答案不是“谁最终赢”，而是复杂度必须持续用实验赎回。模型越强，默认解越偏向单 Agent＋好工具。
