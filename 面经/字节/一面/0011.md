## Q03：把项目 1 升级为分布式系统如何设计改造，怎么保证数据不丢、不重、有容错能力？

### 面试回答

结论：先把自己拆开——无状态层直接横向扩，有状态的部分才是难点，改造顺序是「拆状态 → 定分片 → 加副本 → 管写入语义 → 做故障恢复」。

- 拆状态：单机版最容易漏的是「嘴上说无状态、其实本地盘和内存队列里存着东西」，先把这些外置或可重建。
- 定分片：按 key 哈希一致性分片或按区间分片，保证同一实体的变更落同一节点，才有局部顺序可言。
- 不丢：写入先落持久化日志（WAL／redo）或副本确认再回成功；确认点之后才算提交，崩溃从日志恢复。
- 不重：给每条消息或任务一个唯一 ID＋幂等键，重放时按 ID 判重；需要「恰好一次」就用去重＋幂等，而不是分布式事务。
- 容错：副本数与写可读策略、心跳与故障检测、自动切主与再平衡、限流降级兜底，再配超时与指数退避重试。
- 一句收口：分布式不靠「不出错」，靠「出错后能收敛」，所以对账与补偿任务必须存在。

## Q04：项目 1 中图数据在内存和磁盘里的数据结构是怎么设计的？

### 面试回答

结论：内存和磁盘按「读写形态」分开设计——内存要可变、支持增量更新；磁盘要紧凑、支持顺序扫和整块加载。

- 内存态：邻接表形态，每个顶点一个边列表；写入频繁时用「追加＋版本」或分段结构（类似 C4／copy-on-write）避免并发修改一把大锁。
- 磁盘态：批量分析与读取走紧凑结构，如 CSR（offsets 数组＋neighbors 数组），一次顺序读入即可遍历；更新用增量文件（delta）叠加，定期 compaction 合并回基线。
- 属性与拓扑分开存：拓扑追求紧凑可扫描，属性是变长的，单独成链或存 KV，避免破坏定长记录。
- 项目事实要按真实实现填：【我的实现是 ______，内存用 ______，磁盘用 ______，为什么这么选】。
- 一句取舍：紧凑结构换的是扫描效率与内存占用，代价是更新昂贵——所以图引擎普遍「读写分离」存储。

## Q05：项目中自己做了哪些工作，自研淘汰策略相比 LRU／LFU 优势在哪？

### 面试回答

结论：先说清自己负责的模块边界，再讲策略解决的是 LRU 和 LFU 各自的哪个失效场景。

- 我的部分：【实现了淘汰策略／评估框架／某层的接入】，团队其他人负责〔______〕。
- LRU 的问题：只看最近性，一次全量扫描（批处理、爬虫）就能把真正的热点挤出缓存。
- LFU 的问题：看累计频次，老热点赖着不走、新条目进不来，还要处理频次衰减与计数开销。
- 我的策略解决点（按真实实现填）：【用频率估计做准入、用分代或时间窗口做老化，让扫描流量不污染主缓存，让温数据有机会晋升】。
- 一句诚实边界：优势要在同一 trace 上比出来的，不是「理论上更优」——具体数字与对比见 [[专题题库/Caffeine#CAFFEINE-002：缓存淘汰策略 LRU、LFU、W-TinyLFU 有什么区别，自研策略怎么比较？|CAFFEINE-002：淘汰策略对比与评估]]。

## Q06：淘汰策略的设计依据是什么，有没有其他可比较的模型？

### 面试回答

结论：依据来自「负载特征」而不是直觉——先看访问分布，再选结构；可比较模型从 LRU、LFU 到 TinyLFU／SIEVE、ARC、LIRS 这一族。

- 设计依据：【用真实或模拟的访问日志统计复用距离与热度分布，确认是长尾偶发访问多、还是稳定热点多】，这决定了要不要做频率准入。
- 经典可对照模型：LRU（复用距离的近似）、LFU（频次）、SLRU／2Q（冷热分代）、ARC 与 LIRS（同时照顾 recency 与 frequency、对扫描更稳）、TinyLFU／W-TinyLFU（小窗口＋频率准入＋老化衰减）、SIEVE（近期论文，用指针快速清理低价值条目）。
- 评估口径要能说：命中率优先按「字节命中率」报（大小不一的对象按条数会失真），再看尾延迟、内存开销、CPU 开销。
- 一句加分：说明为什么没选某个主流方案（例如「ARC 实现复杂、我们要的是可解释的准入阈值」），比只夸自己的方案更可信。

## Q07：温数据被驱逐和重新加载会不会引起系统波动，怎么解决？

### 面试回答

结论：会，这是典型的缓存颠簸（thrash）——一批刚好卡在淘汰边界的温数据反复被驱逐再回源，产生周期性延迟尖刺和回源流量尖峰。

- 表现：P99 周期性抖动、回源 QPS 抖动放大、磁盘或网络带宽被加载占满。
- 控制手段：加准入（新条目先进小窗口，被访问到一定次数才进主缓存）、给淘汰加滞回（水位高低两条线，不一刀切）、限流加载（后台预热控制速率，别让加载挤占前台）。
- 结构性办法：冷热分层——把温数据放到便宜的 SSD 层而不是每次回源；分片淘汰避免同时驱逐一批相关 key。
- 兜底：回源请求合并（singleflight）＋熔断，同一 key 并发只放一个请求下去。
- 项目事实按真实填：【我们当时出现的波动是 ______，最后用 ______ 压住】。

## Q08：数据迁移引擎怎么设计的？异步迁移任务挂掉后如何保证不丢数据、顺序不乱？

### 面试回答

结论：迁移引擎按「全量快照 → 增量追平 → 双写对账 → 切流 → 下线」五步走；可靠性靠位点＋幂等＋按 key 分区保序。

- 拆分：按主键区间或分片把数据切成可独立完成的单元，每个单元有状态机（待迁移／迁移中／校验完成）。
- 不丢：每条任务的位点（读到哪、写到哪）先落日志再提交；进程重启从最后确认位点续传，未完成单元整体重跑。
- 不重：目标端写入用「按主键 upsert」或带去重键的幂等写，重放同一条不会产生两份。
- 不乱序：同一 key 的变更必须落同一分区、由单线程或串行队列应用；跨 key 不承诺全局顺序，业务若依赖就要显式串行化。
- 一致性校验：迁移完比对行数与抽样字段（对账任务），差异走补偿；切换期间保留回滚窗口，可回切。
- 一句边界：异步迁移必然有「两边都在写」的窗口，所以要明确这段时间以哪边为准（单一写入口或双写）。

## Q09：设计一个短链系统，点击短链跳转长链，支持几十万 QPS 且高可用稳定，怎么设计？

### 面试回答

结论：读多写少的 KV 查询系统——核心是「发号＋编码＋多级缓存＋无状态横向扩」，高可用靠副本、限流和兜底。

- 链路：用户点短链 → DNS／CDN 或四层入口 → 无状态跳转服务（查映射）→ 返回 302／301 到长链。
- 写路径：创建短链时生成 ID、编码成短码、落库并预热缓存；读路径只查缓存和 KV，不在跳转时算 anything。
- 几十万 QPS 的读：映射关系进本地缓存（命中即返回，不打 Redis）→ Redis 分片扛全量热点 → KV／MySQL 分片做真相源；按读多写少把成本都放在读侧优化。
- 高可用：
  - 无状态服务多实例＋多机房，缓存与存储多副本。
  - 入口限流与熔断。
  - Redis 挂了走本地兜底缓存或直接读 DB 并限并发。
- 稳定性细节：短码长度与字符集固定、避免暴露总量；跳转要能统计（这题方向是度量，所以用不缓存的 302，别用会被浏览器长期缓存的 301）。
- 一句反问式收口：先确认读写比例与是否需要点击统计，这两个决定 301／302 和缓存策略。

## Q10：用数据库自增 ID 做短链发号，数据库能扛住压力吗？

### 面试回答

结论：读没问题，写要看量级——单库单行自增会串行化，短链创建 TPS 上千就要改造成号段或独立发号服务。

- 为什么有瓶颈：自增需要行锁保证连续，所有请求争同一行；单库写入还要受磁盘刷盘与主从复制限制。
- 号段模式：一次从库里取一批（例如 1000 个）在内存里发，用完再取下一批，把数据库压力降千倍量级；取号段这一步仍然串行但频率极低。
- 双 buffer 预取：当前号段用到阈值（如 10%）就异步加载下一段，避免用完瞬间的取号毛刺。
- 其他方案：多库不同起始步长（扩容简单但有空洞与运维负担）、雪花算法（去中心、无 DB 依赖，但要处理时钟回拨与 worker id 分配）、Redis INCR（快但引入 Redis 依赖与持久化风险）。
- 一句结论：短链场景我会选号段服务或 Redis 发号，而不是让业务写库直接依赖自增。

## Q11：ID 映射成短链字符串怎么做，哈希冲突怎么处理，雪花算法的 64 位整数怎么编码，进制转换怎么设计？

### 面试回答

结论：不映射、直接编码——ID 到短码用进制转换（Base62）就是可逆、无冲突的映射；哈希方案才会遇到冲突。

- 为什么先转码不暴露 ID：自增 ID 直接暴露会被猜出下一个短码、也被看出业务量；Base62（0-9a-zA-Z）把它压成最长 11 个字符的短串。
- 冲突：哈希（如 MurmurHash 取低位）会撞——处理办法是「加盐重试／二次探测／落库唯一索引冲突时递增扰动再算」，代价是需要回查重试，工程上通常能不用哈希就不用。
- 雪花 64 位转字符串：十进制最长 19 位，太长；常见做法是整包 Base62 压到最长 11 位，或把「时间差／机器号／序列」三段分别 Base32 再拼接（长度固定、可解码回字段）。
- 进制转换设计：正向「除基取余、低位在前」，反向「按位乘基累加」；要定好字符表顺序当「数字位值」，并约定是否需要定长（定长要在最前面补齐首个字符）。
- 一句可验证的点：62^10 ≈ 8.4×10^17、62^11 ≈ 5.2×10^19，int64 上限约 9.2×10^18，所以最长 11 个字符（实测 `Long.MAX_VALUE` → 11 位）——别答成「6～8 位够用」。

## Q12：新短链是热点且 Redis 没缓存，请求全打到数据库，这种场景怎么解决？

### 面试回答

结论：这既不是缓存穿透也不是过期击穿——数据真实存在，但 key 从没进过缓存；解法是「写路径预热＋读路径请求合并」。

- 写时预热：创建短链成功后立刻把映射写进 Redis 和各实例本地缓存，热点来自投放／转发时已经就位。
- 读时合并：同一个短码的并发回源用 singleflight 收敛成一个请求，其余等待共享结果，避免数据库被同 key 打穿。
- 兜底限流：DB 前置连接池与并发上限，超限走降级（返回兜底页或排队），并给缓存重建加锁与超时。
- 结构性缓解：本地缓存扛大头（几十万 QPS 中绝大多数不需要出网），分片与多副本 key 摊读；对突发投放做入口限速与预热任务。
- 一句区分：若查的是「根本不存在的短码」，那才是穿透，要靠布隆过滤器或空值缓存。

## Q13：手撕：实现一个基于线性探测的哈希表，主要实现 put 和 get

### 面试回答

结论：数组＋开放寻址——槽位空着就放，被占就往后一格一格找；删除要留墓碑，装载因子超阈值就扩容重哈希。

- put：算槽位 → 沿探测序列找，遇到空槽则插入新键，遇到同 key 则覆盖值，遇到墓碑继续走（但记住第一个墓碑位，找不到同 key 时优先复用）。
- get：同样沿探测序列走，遇到空槽说明不存在（墓碑不能终止查找），遇到同 key 返回。
- 删除：写墓碑标记；墓碑会让探测链变长，所以扩容或到达阈值时要顺手清掉。
- 复杂度：平均 O(1)；簇集（primary clustering）会让最坏退化，靠低装载因子（如 0.6～0.7）和好的扰动函数控制。
- 写之前先说清接口和边界：键为 null 怎么处理、扩容时机、是否要求泛型——一次性写对再补测试用例。
