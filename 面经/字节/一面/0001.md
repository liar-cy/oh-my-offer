## Q02：讲解第二个项目从用户输入到最终输出的完整链路。

### 面试回答

一句话：请求从入口进来，经过路由、Agent 执行、生成校验，再流式返回。分五段讲：

- 入口：先进入【API／会话层】，完成鉴权、会话识别和 requestId 生成。
- 路由：【意图识别／路由模块】决定直接回答、走 RAG（检索增强生成），还是进入 Agent。
- 组装上下文：Agent 内，上下文模块组装系统指令、会话历史、用户状态和检索证据，模型基于这些信息选择工具。
- 执行工具：执行层校验参数和权限，执行后把结果回填给模型，继续下一轮决策。
- 结束返回：达到结束条件后，【生成／校验模块】产生最终结果，通过【SSE 或项目真实通道】返回。

面试时再补充每个模块的真实技术选型和本人负责的部分。

## Q03：ReAct 在项目中如何体现，循环如何防止失控并正常结束？

### 面试回答

ReAct 体现为一个循环：“模型根据当前任务和观察选择动作—执行工具—把结果作为新观察—再次决策”，而不是只调用一次模型。结束和防失控分两头说：

- 正常结束：由模型返回结构化 final 动作，运行时再验证目标已满足、必要证据齐全，然后退出。
- 防无限循环：
  - 同时设最大步数、总耗时和费用预算。
  - 识别连续重复动作或状态无进展。
  - 限制同一错误的重试次数。
- 留出口：提供取消、失败和人工接管三条出口。

最后一条原则：达到预算不应伪装为成功，而应返回可诊断的终止原因。

## Q04：为什么使用多个 Agent，一个 Agent 能否解决？

### 面试回答

结论：一个 Agent 能完成时，不要拆多 Agent。单 Agent 调用链更短，上下文、调试和成本都更好控制。

多 Agent 适合三类情况：

- 子任务能明显并行。
- 不同角色需要不同工具、权限或上下文。
- 某个子任务需要专门的模型或策略。

拆分的代价也要说：会多出交接信息丢失、重复调用、状态同步和失败恢复的复杂度。

所以要用同一批任务和单 Agent 基线对比成功率、延迟、费用和人工接管率，有明确收益再拆。

## Q05：MCP 在项目中起什么作用，是否必需，工具还有哪些接入方式？

### 面试回答

MCP（Model Context Protocol，AI 应用接外部工具和资源的开放协议）在项目里干一件事：标准化宿主与外部工具、资源之间的发现和调用。链路是：

- 模型提出工具调用后，宿主校验权限和参数。
- 由 MCP Client 调用 Server 暴露的能力。
- 结构化结果交回运行循环继续推理。

但它不是必需的：工具少、只供单个服务内部使用时，直接函数调用、框架原生 function calling 加内部适配器或 HTTP／RPC SDK 可能更简单；需要跨宿主复用、统一发现和隔离部署时，MCP 才更有价值。

最后一句防守：必须按真实实现说明工具究竟是否通过 MCP 暴露，不能把模型的 function call 格式和 MCP 协议混为一谈。

## Q06：检索成功率提升至 85％ 的数据口径如何定义？

### 面试回答

先说清“成功”是哪一层指标——不能把最终回答看似合理直接叫检索成功。

- 怎么量：若指检索，应在预先标注相关文档或片段的查询集上统计 Hit@k 或 Recall@k。例如 100 条查询中 85 条的 top-k 至少包含一个标注相关片段，才可称 85% 的 Hit@k。
- 数据怎么分：按真实业务分层，去除训练或人工调参造成的泄漏；开发／验证集用于选切块、模型、top-k 和阈值，最终保留的测试集只用于报告。
- 报告什么：样本量、k、基线、置信区间或波动、难例和无答案样本。
- 分层口径：检索命中、重排、答案正确率是三件事，分开报。

## Q08：SSE 和 WebSocket 有什么区别，如何选择？

### 面试回答

一句话：SSE 是架在 HTTP 上的服务端单向流，WebSocket 是真正的全双工通道。

- SSE（Server-Sent Events，服务器发送事件）：
  - 基于 HTTP 响应流，浏览器 `EventSource` 接收 `text/event-stream`。
  - 核心方向是服务端到客户端，协议简单，支持事件 ID 和自动重连语义。
  - 客户端上行通常另发 HTTP 请求。
- WebSocket：握手升级后双方都可主动发消息，支持文本和二进制帧；代价是连接状态、心跳、重连、背压（消费不过来时要控制生产速度）和网关适配都更复杂。

选型：LLM token 流、通知和进度推送通常优先 SSE；聊天、协同编辑、游戏或高频双向控制更适合 WebSocket。最终还要看鉴权、代理超时、连接规模和客户端能力。

## Q09：5000 QPS 如何测得，怎样证明多级缓存架构有效？

### 面试回答

结论：5000 QPS（每秒请求数）不能只报一个数，必须绑定测试环境、请求模型、并发、持续时间、成功率和延迟水位来说，并讲清这是达到、稳定还是峰值吞吐。

证明多级缓存有效，靠两类实验：

- 场景区分：压测要分开全命中本地缓存、命中 Redis、回源数据库和冷热混合，并按真实流量比例报告各层命中率；否则全命中缓存只能证明一条最短路径。
- 对照实验：逐层关闭 L1／L2 缓存，比较吞吐、P95／P99、回源量与资源消耗，才能体现多级架构的价值。

观测面要覆盖：客户端吞吐与错误、应用 CPU／GC／线程池、缓存命中和延迟、Redis、数据库连接／慢查询，以及网络和负载均衡指标。

## Q10：本地缓存及多机器之间如何保证数据一致性？

### 面试回答

先定义一致性要求；本地缓存通常以最终一致为目标。

- 写路径：以数据库为准，提交后删除或更新 Redis，并通过消息／变更日志广播失效到各实例的本地缓存。
- 本地兜底：本地项再设较短 TTL 和版本号。
- 消息不可靠：可能延迟或丢失，所以消费者要幂等，提供重试、对账和监控；读时可比较版本，或在关键写后绕过缓存。
- 一个否定：不同机器不能靠各自 TTL 保证同一时刻一致。

若业务要求强一致，关键读写应绕过本地缓存，或使用能参与一致性协议的数据源，接受更高延迟。

## Q11：Redis 故障后本地缓存能支撑多久，系统如何降级？

### 面试回答

能撑多久没有固定秒数，取决于五个因素：TTL、已预热覆盖率、内存容量、数据可陈旧窗口和流量结构。

降级按请求类型分档：

- Redis 故障时先熔断，避免请求堆积。
- 允许短暂旧数据的读：在明确陈旧上限内用本地缓存；未命中则按数据库容量限流回源，并做请求合并。
- 关键写和强一致读：失败、排队，或切换到经验证的备用路径。
- 恢复 Redis 时：限速回填，避免雪崩。

功夫在平时：要预演 Redis 故障，观察本地命中率、回源 QPS、旧数据年龄、错误率和恢复时间。

## Q13：RabbitMQ 用于什么业务，消费端如何实现跨机器幂等？

### 面试回答

业务场景必须按项目真实填写，例如【订单后异步通知／索引更新／耗时任务】，并说明为何需要解耦、削峰或异步。跨机器幂等抓三点：

- 生产者：为每个业务动作生成稳定的 messageId／业务幂等键，随消息持久化。
- 消费者：在自己的数据库事务里，用唯一约束插入消费记录或条件更新业务状态，只有业务提交成功后才 ack（伪代码见下）。
- 存哪：幂等 ID 不能只放单机内存，应放所有消费者共享且持久化的数据库或其他满足一致性要求的存储，这样另一台机器重投时也能识别。

```text
begin transaction
if insert consumed(message_id) on conflict do nothing == 0:
    commit; ack; return
apply business change with unique/conditional constraint
commit
ack
```

实际实现还要处理业务失败回滚、处理中状态、毒消息和幂等记录保留期。

## Q14：如何发现并恢复 MQ 消息积压？

### 面试回答

发现：通过队列 ready 数、unacked（已投递未确认）数、最老消息年龄、生产／消费速率、重投与失败率来告警，不能只看队列长度。

恢复分三步：

- 先定位根因：是生产突增、消费者变慢或异常、下游限流、热点消息还是反复重试；先修根因并限制入口。
- 再提容量：在下游有容量时增加消费者或分片、批量处理并调优 prefetch。
- 估清空时间：若进入速率 λ 小于稳定处理速率 μ，理想清空时间约为积压量除以 μ−λ。

三条红线：

- 扩容不能破坏顺序或幂等。
- 不能直接删除尚未完成业务结算的消息。
- 毒消息应有限重试并进入可追踪的隔离流程。

## Q15：业务要求写数据和发消息都成功时，如何保证一致性？

### 面试回答

先给结论：数据库和 RabbitMQ 之间，不能靠普通本地事务直接做到原子提交。常用方案是事务 outbox（把“待发消息”和业务数据写进同一事务的本地消息表）：

- 在同一个数据库事务中，写业务数据和待发送消息表。
- 提交后由独立投递器读取 outbox 并发送，收到 publisher confirm（broker 送达确认）后标记已发送。
- 发送确认丢失会导致重发，所以消息要携带稳定 ID，消费者必须幂等。

若业务语义要求用户请求返回时消息已被 broker 确认：可在提交后同步等待投递结果。但失败时数据库已提交，仍需通过状态机、重试或补偿说明“处理中”，不能宣称瞬时强原子。

也可评估特定平台的事务消息，但仍要核对故障窗口和消费幂等。

## Q16：多条件过滤并按 score 排序的 SQL 如何设计联合索引？

原 SQL：`WHERE language = '粤语' AND time > 1990 AND style = '慢歌' ORDER BY score DESC`。

### 面试回答

以 MySQL 8.4 InnoDB 为前提，候选索引对比 `(language, style, time)` 与 `(language, style, score DESC, time)` 两种：

- 列序原则：两个等值列通常放在范围列之前。`language` 和 `style` 谁先不能只凭名字判断，要结合选择性、字段分布以及其他查询能否复用左前缀；单条同时等值命中两列时，二者内部顺序往往不如整体访问路径重要。
- `time` 放在 score 前：能按年份范围定位，但通常不能继续依赖后续 score 的索引顺序免排序。
- score 放在 time 前：可按等值前缀顺序扫描并过滤 time，适合 `LIMIT` 较小且高分记录很快满足条件的场景。
- score 是否加入：看扫描量、排序成本、返回列和写放大，用代表性数据的 `EXPLAIN ANALYZE` 验证，不能机械给唯一答案。

## Q17：Redis 分布式锁如何实现，过期与解锁有哪些风险？

### 面试回答

单 Redis 实例的基本做法：`SET lockKey uniqueToken NX PX ttl`，把加锁与过期设为一个原子命令。风险分解锁和过期两组：

- 解锁：释放时必须只删除 token 仍属于自己的锁。否则客户端 A 超时后 B 已重新获得锁，A 再执行普通 `DEL` 会误删 B 的锁。Redis 8.4 之前通常用 Lua 把比较 token 和删除合成一次原子执行；8.4 起官方文档还给出条件删除命令。
- 过期：业务超过 TTL 时，可由看门狗在确认 token 匹配后有限续期；但进程长暂停或续期失败仍可能失锁。

兜底：关键写入还应使用 fencing token（随请求携带的校验编号）或资源侧版本检查，不能假设进程活着锁就一定有效。

## Q18：HashMap 如何扩容并迁移旧数据？

### 面试回答

以 OpenJDK 8 为例，扩容发生在两个时刻：首次插入时初始化表；元素数超过阈值时，通常把容量扩为原来的两倍。

迁移的细节：

- 不必重新计算每个 key 的 `hashCode`：因为容量是二次幂，节点根据 `hash & oldCap` 为 0 或非 0，分别留在原索引或移动到“原索引＋oldCap”。
- 链表拆成 low／high 两组并保持组内顺序；树桶也会拆分，并按大小决定是否退化。

并发边界：普通 HashMap 扩容不是线程安全操作，并发读写应使用 ConcurrentHashMap 或外部同步。

## Q19：ConcurrentHashMap 的实现原理是什么？

### 面试回答

以 OpenJDK 8 为例：它不再用 JDK 7 的固定 Segment（分段）作为核心描述，而是基于桶数组、CAS（比较并交换）、桶级 `synchronized` 和可见性规则协调更新。

- 写空桶：用 CAS 放入首节点。
- 写冲突桶：`synchronized` 锁住该桶后，按链表或红黑树更新。
- 扩容：达到条件时扩容，线程通过转发节点识别迁移状态，并可协助 transfer。
- 读：通常不加锁，利用 volatile／可见性设计读取当前节点；迭代器是弱一致，不是全表瞬时快照。

易错点：单次操作线程安全，不代表 `get` 后 `put` 的组合原子，应使用 `putIfAbsent`、`compute` 等合适原子方法。

## Q20：代码题——验证二叉搜索树。

### 面试回答

思路：递归时携带每个节点允许的开区间。

- 根节点范围为负无穷到正无穷；进入左子树时上界变为当前节点值，进入右子树时下界变为当前节点值。
- 边界用 `long`：避免节点恰为 `Integer.MIN_VALUE` 或 `Integer.MAX_VALUE` 时溢出。
- 标准定义下不允许重复值，所以比较使用严格不等式。

复杂度：时间 O(n)，递归栈 O(h)。

```java
boolean isValidBST(TreeNode root) {
    return valid(root, Long.MIN_VALUE, Long.MAX_VALUE);
}

boolean valid(TreeNode node, long low, long high) {
    if (node == null) return true;
    if (node.val <= low || node.val >= high) return false;
    return valid(node.left, low, node.val)
        && valid(node.right, node.val, high);
}
```
