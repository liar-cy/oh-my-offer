### 面试回答

一到两分钟，按“基本情况→实习主线与岗位业务的对应关系→后端语言与工程能力→一句求职意向”组织。

### 面试回答

- 架构与数据流：6 分钟。
- 关键技术决策逐个深挖：12 分钟。

## Q03：为什么选择 Graph 作为多智能体架构？当时有没有考虑其他方案（如 AutoGPT 等）？

### 面试回答

按“任务形状决定架构”来讲，而不是说某个框架更流行。

- 我的流程有分支、有回环，还需要在中间节点暂停等人工确认，所以要把拓扑显式建模。
- Graph 把节点、条件边和共享状态变成一等公民：能编译校验、能导出可视化，每一步有状态快照，可以做中断恢复与并行汇合。
- 反过来，如果只是“一次检索一次生成”或者固定顺序的流水线，用链式调用甚至一次 Prompt 就够，上 Graph 是纯增加复杂度。

关于替代方案，要如实给出比较维度而不是名词：

- AutoGPT 一类：属于“给一个目标、模型自己无限拆解执行”的自主代理形态。开放度最高，但在业务链路里不可控——步数与成本不可预测、中间结果难验收、失败会沿链路放大。而且我们的流程本身是明确的，不需要让模型决定要不要做某一步。
- LangChain 顺序链：没有回环与状态仲裁能力。
- 状态机／自研 while 循环：能做，但路由、检查点、并发合并都要自己实现，等于重造轮子。
- 工作流引擎加模型节点：确定性最好，适合强合规流程；缺点是交互与动态规划能力弱。

结论要收在自己的判断上：我选 Graph，是因为它恰好覆盖“分支＋循环＋人工确认＋可恢复”这四项，而这几项正是业务要求的；如果流程是固定顺序，我会退回工作流。

能顺带说一句“如果重做，我会先用最朴素的链跑通，再决定是否上图”，这比声称一开始就选对更可信。

## Q04：Graph 中的“自动化状态管理”具体管理哪些状态？这些状态是如何持久化的？

原题 4—5 同属 Graph 状态管理与持久化话题，合并为一题。项目的真实状态定义与存储选型未记录，以下按通用 Graph 建模作答，实现细节按【真实项目】填写。

### 面试回答

被框架托管的状态有四类：

- 业务共享状态（State）：节点之间真正要传递的东西。
  - 原始输入与改写后的查询。
  - 各节点的中间产物：检索结果、抽取的结构化字段、工具返回值。
  - 累计的计数与统计：步数、重试次数、token 用量。
  - 控制位：下一步走哪个分支、是否需要人工确认、是否已判定完成。
- 消息与会话历史：参与对话的节点会带消息列表，通常按“追加”合并。
- 执行上下文：当前线程／会话标识、超步序号、待执行的激活节点集合。这类由运行时维护，业务代码不该自己记。
- 边界资源：LLM 客户端、工具连接、数据库句柄。这些不是状态，是依赖，不该塞进 State——会被序列化进检查点，导致恢复时拿到失效连接。

持久化机制是检查点：

- 图执行以超步推进，每个超步结束后，运行时把该线程的 State 快照写进 CheckpointSaver。
- 键是 threadId（会话隔离）；恢复时按 threadId 取最近的快照继续跑。
- 所以持久化的粒度是“每一步的状态版本”，而不是整个流程的最终结果。
- 这也解释了为什么能做人审批：interrupt 后进程可以退出，几小时后 resume 从快照继续；同理还能做状态回溯。

存储选型按需求分层：

- 本地开发用内存实现。
- 要跨进程恢复、多实例部署，就用数据库或 Redis 存快照。
- 序列化格式要能表达自定义类型，别把大对象塞进 State。

三个必须注意的点：

- 合并策略：State 的每个 key 都要注册合并策略（覆盖／追加／归并）。并行分支写同一 key 时，Replace 会互相覆盖、顺序不确定；要么各自用独立 key 下游汇聚，要么用 Append。
- 节点幂等：从检查点重放可能重复执行有副作用的节点。写库、发消息要么做去重键，要么挪到独立节点。
- 快照膨胀：快照会随对话增长变大。长任务要定期把大字段外置到对象存储或表里，State 只放引用。

## Q05：RAG 引擎中的“混合检索策略”是怎么实现的，检索结果如何合并或重排？

### 面试回答

“混合”要具体到哪几路、为什么互补：

- 至少两路：向量召回（语义相近但措辞不同）＋关键词／全文召回（BM25 或精确短语，专治术语、编号、代码标识符这类向量容易糊过去的硬匹配）。
- 再按查询形态决定是否叠第三路：带时间／租户／文档类型约束的元数据过滤查询；数值与清单类问题走结构化查询。
- 各路独立召回 TopN，N 比最终 k 大，通常 2～5 倍。
- 必须带权限过滤下推，不能召回后再遮。

合并与重排分三步：

- 归一化：向量的相似度分数与 BM25 分数不同尺度，不能直接相加。工程上要么各自做 min-max／排名归一，要么干脆用排名融合法 RRF（倒数排名融合，`score = Σ 1/(k + rank)`）——实现简单、对分数尺度不敏感，是默认起手。
- 去重：同一片段被多路命中，要按文档 ID＋跨度或内容哈希合并。重复块同时挤占名额，是效果下降的常见原因。
- 重排：融合后的 TopN 交给 cross-encoder 之类重排模型做精排——query 与候选成对打分，比双塔向量准但成本高，所以只用于最后几十条。再叠加来源权威度、时效与权限等业务偏置，并按类型设配额，最后取 TopK 进上下文组装。

被问“效果提升了多少”，要能给出同一评测集上纯向量、纯关键词、融合、融合＋重排的逐项对比数字（消融），并按延迟与成本说明为什么候选规模设成现在这样。没实现重排就直说没实现，不要含糊。

## Q06：Embedding 模型选的哪个，选择依据是什么？

模型名称与真实评测数字属个人事实，未记录，按【真实选型】填写。

### 面试回答

选型依据讲五条，模型名只是结论：

- 语种与领域：中文还是中英混合、有没有专业术语与代码；必要时用领域微调过的版本。
- 维度与上下文上限：维度影响存储与计算量，单条 token 上限决定切块的最大长度。
- 效果要在自己的数据上量：用自建评测集比 Recall@k／Hit@k，不看公开榜单名次——榜单域与业务域常常不匹配。
- 部署与成本：能否私有化、吞吐与延迟能否满足在线要求、按量计费的价格。
- 兼容性与工程约束：是否要求查询端与文档端同一模型同一版本；换模型等于全库重建。

答题时给一句可核对的过程最有说服力。比如：“在【N】条标注查询上比了候选 A、B，A 的 Recall@5 高 3 个点，但维度更大、索引内存翻倍，我们当时以在线延迟为硬约束选了 B。”这样即使选得不完美，也显示出是决策而不是抄来的。

同时主动说边界：模型版本会换，换模型要全库重算并重新评测，向量与 embedding 版本必须绑定存储。

## Q07：切片大小是多少？不同文档类型有不同的切片方法吗？

真实切块参数属项目事实，未记录，以下给方法与可填写口径。

### 面试回答

先给原则再给数字：chunk 大小没有普适值，它由“检索粒度”和“生成预算”两头夹出来。

- 块太大：定位不准，无关内容还占预算。
- 块太小：丢上下文。

我的做法是：

- 以语义边界优先切：按标题层级、段落、列表项、代码函数。
- 设目标区间：例如 300～800 token 量级，按【真实值】填。
- 相邻块留少量重叠：几十到百来 token。
- 每个块前缀拼上文档标题路径与摘要，让孤立片段自带语境。
- 所有参数都用标注片段的召回指标和答案完整性去调，不凭感觉。

不同文档类型确实要分开处理，这是这题的得分点：

- 长文与技术文档：按标题结构递归切。
- 表格：不能拉平成文本流，要按表为单位，或“表头＋行组”成块并保留表头绑定；否则检索命中一堆没署名的数字。
- FAQ／问答对：天然一条一块，问句本身就是检索键。
- 代码：按函数或类切，保留文件路径与签名。
- PPT／PDF 版式文档：先去噪（页眉页脚水印、目录页），再按版式分块；插图走 OCR／图注，并与正文位置绑定。
- 合同、制度类：条款编号要独立成块，否则“第 X 条”检不到。

最后补一句自我批判：切块策略要能被评测验证——按类型分头建评测集，看每类的命中率，才知道是不是某类的切法在拖后腿。

## Q08：PGVector 选了哪种向量索引（HNSW），为什么？

### 面试回答

pgvector 主要两类索引：

- IVFFlat：要训练 centroids、按列表聚类。建索引快、内存小；但查询要设 `probes`（扫多少个簇）在召回与延迟间取舍，且数据分布漂移后要重建。
- HNSW：多层次可导航小世界图，查询从上层粗定位逐层下降，召回率—延迟曲线明显更好。`m`（每点邻居数）与 `ef_construction`／`ef_search` 三个参数分别控制图质量与查询深度；代价是构建更慢更耗内存、写入时要维护图。

我选 HNSW 的理由：查询延迟要求高且要稳定召回，数据量在建索引可接受范围内，写入是批量导入而不是高频更新——所以把成本从查询侧挪到构建侧。

要主动补三点边界，否则会被判“只会照抄推荐”：

- 建索引成本：HNSW 在大表上耗时和内存都可观，导入数据要先灌完再建索引，别边大批写边建。
- 与过滤的组合：ANN 加元数据过滤时可能返回不足 k 条。新版 pgvector 提供迭代索引扫描缓解，但仍有扫描上限；权限过滤严格时，要在 SQL 侧核对结果数量并允许降级为精确扫描。
- 规模下限：小数据量（几万条以下），HNSW 相对全表精确扫描未必有明显收益，那时不建索引或用 IVFFlat 更省事。选型必须与数据规模绑定。

另外要点一句：换 embedding 模型等于全库重建索引与向量，索引参数也要在新向量上重测召回。

## Q10：Java 和 Go 最大的不同是什么？Go 的并发模型（GMP）与 Java 的多线程模型有何区别？

原题 11—12 同属“Java 与 Go 的语言差异”，合并为一题。原素材写作“GPM”，按 Go 的 GMP 调度模型理解。

### 面试回答

“最大的不同”我给一条主线，再加几条支撑：

- 主线：Go 是一门为“在容器里跑大量并发 IO 服务”而设计的现代语言，Java 是长在成熟 JVM 生态上的企业级平台。

落到日常写代码，差别有五点：

- 并发原语：Go 用 goroutine＋channel 作为语言级能力；Java 靠线程＋共享内存＋锁与 JUC 工具类。
- 错误处理：Go 用显式 error 返回值，没有异常控制流，`panic` 不是错误处理手段；Java 是受检／非受检异常。
- 内存与运行形态：Go 编译成静态二进制，协程栈从几 KB 起按需增长，GC 偏向低延迟；Java 要 JVM，栈大小由参数决定，GC 调优空间大但要管堆内外内存。
- 类型系统：Go 是结构化类型（隐式实现接口），泛型晚到且约束基于接口；Java 是名义类型＋泛型擦除，注解与反射生态厚重。
- 工程约定：Go 以工具链与格式统一、包级组合为主；Java 以框架与依赖注入为主。

结论收在“我按场景选语言”，不要变成语言优劣之争。

并发模型的差别才是这题的技术核心：

- Go 侧是 GMP：G 是协程，M 是内核线程，P 是执行 Go 代码所需的调度上下文（数量由 `GOMAXPROCS` 决定），M 必须绑 P 才跑业务代码。
- G 阻塞在 channel 或网络 IO 时，由运行时装起并让 M 去跑别的 G；阻塞在系统调用时，P 与 M 解绑交给其他 M。所以“一请求一协程”成本极低，调度在用户态完成。
- Java 侧（传统模型）是 1:1 映射到内核线程：线程创建与切换要进内核，栈默认 MB 级，几百到几千线程就出现明显的调度与内存开销。于是要靠线程池＋有界队列＋拒绝策略复用线程，并发语义靠 `synchronized`／JUC 锁与原子类保护共享内存。
- 关键区别不在“协程比线程轻”，而在通信范式：Go 鼓励把数据交给某个 goroutine 独占、通过 channel 传递所有权与事件；Java 习惯共享对象加锁。

最后补公平性细节会加分：Go 调度有本地队列、全局队列、工作窃取，每 61 次调度检查全局队列防饿死，还有 sysmon 做抢占（原素材未记录候选人答到哪层）。

## Q11：主要使用的 Go 是哪个版本？Go 的泛型有了解吗，和 Java 的泛型相比有什么区别？

原题 13—14 同属 Go 语言版本与泛型，合并为一题。真实使用版本属个人事实，未记录。

### 面试回答

版本如实答（例如 Go 1.21／1.22 一类，按【实际使用】填），并且要能说出你所用版本带来的差异，否则报了版本号会被追问：

- Go 1.18：引入泛型（类型参数与约束）。
- Go 1.21 起：泛型配合 `min`／`max` 内建函数和 slices／maps 标准库包才真正好用。
- Go 1.22：改了 for 循环变量“每次迭代新变量”的语义，这个坑直接影响闭包与 goroutine 捕获。
- 1.22 之后调度器改进与 runtime 相关变化要谨慎说，以官方发布说明为准。

泛型的价值用一句话点明：它替代了“复制粘贴一份 int 版、一份 string 版”，或者用 `interface{}`＋类型断言、两头损失表达与性能的写法。

与 Java 泛型的区别给四条：

- 类型系统基础：Java 泛型是名义类型（必须显式 `implements` 声明），约束写 `extends Comparable<T>`；Go 是结构化类型，满足方法集即隐式实现接口。Go 的泛型约束（type parameter bound）也是接口，但只能是方法集加类型联合，不能像 Java 那样写“继承自某个类”。
- 运行时表示：Java 泛型在字节码层面被类型擦除，`List<String>` 与 `List<Integer>` 运行时是同一个类，所以不能 `new T()`、不能对类型参数做 `instanceof`、原始类型要装箱。Go 泛型是受限单态化（GC 字典共享，同一字典可复用代码），对基本类型无需装箱。
- 通配符与型变：Java 有 `? extends T`／`? super T` 的 PECS 型变规则；Go 没有通配符，泛型类型不做型变（`List[int]` 不是 `List[int64]` 的子类型）。
- 生态影响：Java 泛型晚于集合框架出现，留下裸类型、通配符、`Comparable<? super T>` 这类表达负担；Go 的泛型新且保守，刻意不支持“特化生成不同机器码”的高级特性。

收尾给判断：Go 泛型的克制是优点——用少量特性覆盖容器与算法复用。Java 泛型的复杂度，来自既要兼容二十年前未参数化的代码，又要在类型推断与型变上表达完整。

## Q12：Go 的数组、slice 与 map 的底层数据结构与区别。

### 面试回答

数组是值类型，长度是类型的一部分：

- `[3]int` 与 `[4]int` 是不同类型，赋值和传参都整体复制。
- 因此实际项目里几乎不直接用数组传数据，它更多是作为“slice 的底层存储”存在。

slice 是描述符（指针、长度 len、容量 cap），指向底层数组的一段视图：

- 赋值与传参只复制描述符，多个 slice 可以共享同一段底层数组——这正是它的用法与陷阱。
- `append` 超过容量就分配新数组并拷贝，此时旧 slice 看不到新写入。
- 未扩容时，两个 slice 会互相影响，也就是“别名”问题。
- 要安全地传给别的函数保存，就 `copy` 或用 `s[:n:n]` 限制容量。
- 切片再切片可能共享底层内存、被切掉的前段无法释放，是内存驻留的常见来源。

map 是哈希表：运行时 `hmap` 结构，桶数组（每桶 8 个键值槽）＋溢出桶，按 key 的哈希低 bits 选桶、高 bits 存签名，另带增量扩容状态（doubling／same-size 迁移）与写保护标志。

要点按“能不能用”来讲最抗追问：

- 不是并发安全的：Go 1.6 之后检测到数据竞争 `concurrent map writes` 会直接 fatal。共享写要加 `sync.Mutex`／`sync.RWMutex`；读多写少可用 `sync.Map`；分片场景常用分段锁自建。
- 遍历顺序是刻意打乱的（随机起始桶），不能依赖。
- 键必须是可比较类型，切片、map、函数不能作键。
- 删除键不会立即缩容；返回零值无法区分“不存在”和“值为零”，要靠 `v, ok := m[k]`。
- 扩容 rehash 期间可能读到中间态，但同一 goroutine 内不会出现读到半新半旧值的语义错误。

一句话对比三者：数组定长值拷贝、slice 是可变长视图、map 是哈希映射。

- 性能上 slice 顺序访问最友好（连续内存、缓存命中）；map 有一次哈希与指针追逐的开销，还会产生更多垃圾。
- Java 侧对照就是“数组 vs ArrayList vs HashMap”。但 Go 没有泛型集合包装层的概念：slice 直接承载数组语义、map 是语言内建而非库，这个差别常被拿来追问。

## Q13：数组和链表的区别是什么？

### 面试回答

内存布局：数组连续存储，链表由节点加指针链接。由此推出四项差异：

- 随机访问：数组 O(1)，链表 O(n)。
- 头部或中间插入删除：链表只需改指针 O(1)（前提是已定位到节点），数组要搬移元素 O(n)。
- 缓存友好性：数组明显更好（顺序预取、无指针追逐）；链表每跳一个节点可能一次缓存缺失。
- 内存开销：数组只需按元素大小预留（动态数组扩容时可能浪费或有再分配成本）；链表每节点要额外存指针并对齐填充。

场景按“读写形状”答：

- 读多、需要按下标或做范围扫描／向量化处理 → 数组及衍生结构（切片、`ArrayList`）。
- 频繁在任意位置插删、元素数量动态且大小不稳定 → 链表（`LinkedList`）。
- 但要老实说出工程实际：即使频繁中间插入，CPU 缓存局部性的影响常常压过指针操作的优势。所以真实系统更常用数组派生结构（分块表、rope、环形数组 deque），纯链表演化成分块或索引结构。

再补一层与哈希的联动：Go 的 map 桶内是数组；HashMap 的桶是链表到红黑树（Java 8）／无链表（Go 用溢出桶）。被问到“那哈希冲突到底用数组还是链表”时，能区分这两家实现是很好的加分点。

## Q14：TCP 和 UDP 的区别与各自的应用场景。

### 面试回答

从连接、可靠性、顺序、边界、拥塞与头部开销六层对比：

- TCP：面向连接、需要三次握手；字节流、无消息边界；可靠（确认＋重传＋超时）；按序交付；有流量控制与拥塞控制；头部 20 字节起，还有选项开销。
- UDP：无连接；数据报有明确边界，一个 send 对应一个接收；不保证到达、不保证顺序；无拥塞控制；头部仅 8 字节。单包受 MTU 限制，不能像 TCP 那样自由流式发送。

场景要给判断理由，不是背列表：

- 要“内容完整正确”且能容忍重传延迟 → TCP：HTTP／文件传输／数据库与 RPC 长连接。
- 要“低延迟且能容忍丢” → UDP：实时音视频、游戏状态同步、DNS 查询。
- 一对多广播／组播只能 UDP，因为 TCP 是点对点。
- 应用层自带可靠语义时，UDP 反而更合适：比如 QUIC／HTTP3 在 UDP 上做用户态可靠与拥塞控制，绕开 TCP 队头阻塞，还能迁移连接。

补两个易错点：

- UDP 不保证分片一定安全，分片丢失整包作废。生产上常把报文大小控制到不超过 MTU，自己定义分片与序号。
- TCP 的“可靠”只保证字节到达与顺序，不保证业务幂等，重复请求仍要在应用层处理。

## Q15：什么是 SQL 注入？有哪些防范措施？

### 面试回答

定义要说到机制：SQL 注入是攻击者把数据伪装成语句结构提交。拼接 SQL 时，用户输入里的引号、注释符、布尔或 `UNION`、堆叠语句改变了原本的语义，导致越权读、数据篡改甚至命令执行。

- 根因只有一句：把不可信输入当作代码来解释。
- 典型形态：`or '1'='1'` 绕过登录；拖库的 `UNION SELECT`；`' --` 注释掉后续条件；报错回显泄露结构；二阶注入——存进库后，下次取出时被拼接执行。

防范措施按有效性排序：

- 参数化查询／预编译是首选：让值始终以绑定参数传递，不进入语句文本。MyBatis 里 `#{}` 与 `${}` 的差别就是这条，后者是字符串替换、会引入注入。
- 输入校验与白名单：列名、表名、排序方向、分页参数这类不能参数化的地方，只能靠白名单映射，不能靠转义。
- 最小权限：业务账号不给 DDL／系统表权限，Web 应用不用 root，只读场景给只读账号。
- 减少可利用面：关闭详细错误回显（只回错误码与 traceId）；生产上不拼接 SQL；ORM 的原生查询接口谨慎使用。
- 纵深防御：WAF 与 SQL 审计能拦能查，但存在被绕过的风险，不能替代前四条；二次确认与敏感接口限流用来降低损失。

还要补一句“参数化不等于万事大吉”：标识符（表名、列名）、`LIKE` 通配符、`ORDER BY` 的位置参数这些仍需单独处理，二阶注入也要靠“取值处同样不拼接”来防。

## Q16：HTTP 请求中 GET 和 POST 方法的区别是什么？

### 面试回答

按语义层、实现层、副作用层分开答，比背“GET 传参在 URL、POST 在 body”更抗追问。

- 语义上：GET 是读取，应当安全（不改服务器状态）且幂等，因此可以被缓存、被收藏、被浏览器预取，可以出现在日志与 Referer 里；POST 是提交处理，不安全也不幂等，默认不缓存。
- 实现上：两者都是“带 body 与否都行”——GET 请求也可以携带 body，但服务端与客户端库的支持不一致，别依赖。URL 长度限制来自浏览器与服务器对请求行的上限，而不是协议规定。参数位置选 GET 是为了可分享，选 POST 是为了不暴露与更大载荷。

幂等性是重点：

- 幂等指同一请求重复执行，对服务器状态的影响相同。GET／PUT／DELETE 通常幂等，POST 不幂等。
- 所以重试 POST 可能重复下单，要靠幂等键去重（见接口幂等设计）。

缓存与预取的实际风险要讲出来：

- 浏览器 prefetch、安全扫描器都可能自动重发 GET；把“删除”“支付”做成 GET 参数接口，就可能被误触发。
- 这才是把读取之外的操作塞进 POST 或更明确方法的真正理由。

再补几条现代口径：

- HTTP 语义与幂等性由方法定义决定：GET／HEAD 安全，PUT／DELETE 幂等，POST 不幂等，PATCH 不保证。
- POST 请求若被非幂等重定向（301／302／303），会被改方法重发；浏览器对 307／308 才保持方法与 body。
- 跨域时，含自定义头或非常规 Content-Type 的 POST 会先触发 CORS 预检（OPTIONS），这也是两者在实践中的常见差异。

## Q17：讲一下 DNS 的工作原理；常见的 DNS 记录类型有哪些，你用得比较多的是哪一种？

原题 20—21 同属 DNS 话题，合并为一题。

### 面试回答

先给查询链路：

- 应用调 `getaddrinfo` 之类接口；本地解析器先查进程与系统缓存、`hosts` 文件。
- 再向递归解析器（通常由运营商或公共 DNS 提供）发递归查询。
- 递归解析器自己不行的时候，从根服务器开始迭代：问根得到 TLD（如 .com）的权威地址，问 TLD 得到该域权威服务器的地址，问权威拿到最终记录，逐层把结果按 TTL 缓存。

要强调分工：对客户端而言只有递归（解析器替你把活干完），对上游而言多是迭代（一层层委派给你）。这个区别是常见追问点。

解析结果不止“域名变 IP”：

- 可能有 CNAME 链要续查；可能返回多个 A／AAAA 记录做轮询。
- 可能命中否定缓存（NXDOMAIN）。
- 也可能因为 CDN／GSLB，返回离你最近的节点地址，而不是源站 IP。

传输层：默认 UDP 53；响应过大（超过 EDNS 缓冲区）、做区域传输或 DNSSEC 查询时走 TCP；加密场景还有 DoT／DoH。

记录类型按“我用过哪条”答最有说服力：

- A：域名→IPv4；AAAA：→IPv6。
- CNAME：规范别名，指向另一个域名，不能与同名的其他记录共存，常用在 CDN／服务别名。
- MX：邮件交换，带优先级。
- TXT：任意文本，SPF／DKIM、域名归属验证与 `_dmarc` 都放这里。
- NS：该域由哪些权威服务器负责。
- PTR：反解，IP→域名，邮件校验常用。
- SRV：服务定位，协议加端口加权重，IM／语音一类在用。
- CAA：授权哪些 CA 可为本域签发证书。

最常用的是 A／AAAA 与 CNAME（业务域名指到负载均衡或 CDN 域名）；部署邮件或校验域名归属时会用到 TXT／MX；配证书时踩过 CAA。

再加一个工程视角：切流量时 DNS 不可靠。TTL 决定了切换窗口，客户端缓存又不受控，所以真要秒级摘流量，必须靠网关或负载均衡侧的手段，而不是改解析记录——这类结论最能显示实践经历。

## Q18：手撕 LeetCode 3：无重复字符的最长子串；追问时间复杂度。

原素材未记录现场语言与完成情况，以下按通用滑动窗口作答。

### 面试回答

基本写法是滑动窗口，维护“以 right 结尾、无重复字符的最长窗口”：

- 用哈希集合，或长度为 128／256 的计数数组，记录窗口内的字符。
- `right` 右移加入新字符；若该字符已在窗口内，就不断从 `left` 移出字符，直到冲突消除。
- 然后更新答案 `max(right - left + 1)`。
- 关键在于窗口始终合法，所以每次只需在收缩后取长度，不必枚举所有子串。

更省一步的写法，是把“字符到最近下标”的映射存下来：

- 当 `right` 处字符的上次出现位置 `prev >= left` 时，直接把 `left` 跳到 `prev + 1`；不能回退，所以取 `max(left, prev + 1)`，省掉逐格收缩。
- 两种写法都是 O(n) 时间、O(min(n, 字符集大小)) 空间。

追问复杂度要答得出理由：

- 每个字符至多被 `right` 处理一次、被 `left` 移出一次，所以是双指针线性扫描而不是 O(n²)。
- 收缩循环不会叠加成平方，这是典型的摊还论证。
- 空间是字符集规模决定的常数级。

写完必须自测边界：

- 空串返回 0。
- 全部相同字符 `"aaaa"` 返回 1。
- `"pwwkew"` 返回 3，答案是 `"wke"`；要能说清为什么不是 `"pwke"`——那是子序列不是子串。
- `"dvdf"` 用来验证 left 跳跃不回退的正确性。

若题意改成“最长无重复子序列”，那就是另一道题（答案等于不同字符个数）。这类语义澄清先问清再动手。
