## Q01：你觉得 RAG 中最难的是什么？

### 面试回答

同一问题在本场出现两次（原题 1 与 20）。

最难的不是接模型，而是“证据链质量”。难点分三层：

- 语料侧：文档解析与切块决定了召回的上限，垃圾进就是垃圾出。
- 匹配侧：用户问法和文档措辞之间有语义鸿沟，再加上多跳与跨文档的问题，单一向量检索不够用。
- 验证侧：怎么证明“检索到了正确证据、答案忠实于证据”。这需要标注评测集和分层指标，否则优化全靠感觉。

讲的时候挑一个自己踩过的坑展开，比罗列名词有说服力。例如：切块把语义切断了，就用父子块补全。

## Q02：你是怎么解决幻觉问题的？

### 面试回答

原题 2 与 26 同题合并。分检索和生成两段来治理，再加一层兜底。

检索段，保证证据相关且及时：

- 混合召回＋重排、权限过滤、时效校验。
- 召回不到就明确说“库内无答案”，不硬凑。

生成段：

- Prompt 约束“只依据给定证据作答并逐条引用”。
- 输出格式带引用字段。
- 后端再校验一遍：引用是否真的支持结论。

兜底段：低置信就拒答或转人工。

评测要分别测两类错——“没检到”和“有证据却编造”，所以评测集里要放无答案样本和冲突样本。别把流畅当正确。

## Q03：微调和 RAG 的区别与优劣势是什么？

### 面试回答

原题 3 与 27 同题合并。一句话：RAG 改“模型能看到什么”，微调改“模型本身会什么”。

RAG（检索增强生成，回答前先把外部资料捞进上下文）：

- 优势：知识外置、可实时更新、可溯源、成本低，适合事实问答与私有知识。
- 劣势：受上下文预算和检索质量制约，而且不改变模型的风格与能力边界。

微调（用领域数据继续训练模型）：

- 优势：把风格、格式、行业术语和任务行为内化进权重，推理时不占上下文。
- 劣势：知识固化进权重，更新要重训、难以溯源，数据与算力成本高，还可能灾难性遗忘（学了新的忘了旧的）。

选型：事实类问题优先 RAG，输出格式／领域表达不稳优先微调。两者常组合——微调打底行为，RAG 供事实。

## Q04：大模型是怎么训练出来的？

### 面试回答

三阶段，每阶段解决一个不同问题：

- 预训练：在海量文本上做自回归的下一 token 预测（因果语言建模，只能看左边）。这一步学出语言能力和世界知识，也是算力的主要消耗。
- 后训练：先做监督微调（SFT），用“指令—回答”对教会它听指令、按格式回答；再做偏好对齐（RLHF／DPO 等），用按人类偏好排序的数据优化回答风格与安全性。
- 推理侧增强：可选的推理训练（RL 类），再加蒸馏、量化来降低部署成本。

口述时强调每个阶段解决什么问题，别只堆名词。

## Q05：Transformer 的架构，Encoder 和 Decoder 是什么？

### 面试回答

核心是自注意力机制：每个 token 用自己的 Q／K／V（查询、键、值三组向量）对序列里所有位置加权聚合。它替代了循环结构，所以能并行，也能建模长距离依赖。

Encoder 和 Decoder 的区别在“能看见什么”：

- Encoder：堆叠“自注意力＋前馈网络”，双向看全文，适合理解类任务（BERT 系）。
- Decoder：在前面基础上加带因果掩码的自注意力（只看左侧已生成的内容），再加可选的交叉注意力（读取 Encoder 的输出），适合自回归生成（GPT 系）。

补一句现状：当前主流大模型多是纯 Decoder 架构。

配套要素还有三样：位置编码、残差＋归一化、多头注意力。

## Q06：Function Call 是怎么训练的？

### 面试回答

模型会输出工具调用，不是靠 Prompt 硬凑出来的（也能凑，但可靠性差），而是训练出来的。

训练侧：

- 构造大量“对话上下文＋可用工具 schema → 正确的调用决策与参数 JSON”样本，拿这些做 SFT（有监督微调）。
- 样本要覆盖三类行为：该调用时调用、不该调用时直接回答、缺参时追问。
- 再用偏好数据对齐，优化调用格式与选择质量。

运行时侧由推理框架配合：把工具定义注入上下文、用受限解码／文法约束输出保证 JSON 合法、解析之后才真正执行。

一句边界要说清：模型只“提出调用”，执行和鉴权都在宿主侧。

## Q07：微调的方案有哪些，自己做过没有？

### 面试回答

方案是一个谱系：

- 全参数微调：效果上限最高，但成本也高，还容易遗忘旧能力。
- 参数高效微调里的 LoRA 最常用：冻结原权重，只训练一条低秩旁路（额外的一小套参数）。
- QLoRA 是 4bit 量化基座＋LoRA，单卡能跑。
- 参数高效微调还有 Adapter／Prefix／Prompt Tuning 等方案。
- 数据侧：要构造指令集、控制质量并做去污染。
- 训完必须评：在保留的评测集上和基线对比。

做没做过要如实：做过就讲【数据规模、基座、方法、评测结果】；没做过就说“跑过教程级实践／仅了解”，不要虚构。

## Q08：大模型分词器是什么？

### 面试回答

分词器的作用是把文本切成模型词表里的 token，也就是子词（BPE／WordPiece／SentencePiece 这类算法）。词表是个折中：常见词整存，生僻词拆成子词。

为什么它重要：

- 它定了上下文长度的计量单位——token 数不等于字数。
- 计费、截断都按 token 走。
- 它还影响多语言以及数字／代码的处理质量。不同模型的分词器不一样，同一句话的 token 数可能差很多。

一个易错点：分词是模型输入的第一步，和后面查 embedding 表是两件事，别混着说。

## Q09：Embedding 是什么，你们用的哪个模型？

### 面试回答

Embedding（向量表示）是训练好的模型把文本映射成一个固定维度的实数向量。语义相近的文本，向量距离就近。

用途：检索召回、聚类、去重这几类。

两个要说清的点：

- 维度和各维含义由训练决定，不是人工定义的。
- 换模型要重建全库向量，查询侧和文档侧必须用同一套兼容体系编码。

用的哪个模型按【项目实际】如实回答——商用 API 的向量服务，或者开源句向量模型。同时说清选型依据：业务评测上的召回、维度、语言支持、成本。

## Q10：介绍一下 LangChain。

### 面试回答

LangChain 是 LLM 应用的组件框架，提供四类东西：

- 统一的模型接入抽象。
- 链式编排（LCEL，它的表达式编排方式）。
- 工具与检索组件。
- Agent 能力。

配套的 LangGraph 负责有状态的图编排。

评价要客观：它确实降低起步成本，但抽象层多、版本演进快，排障时可能得去翻源码。

用得多深按【真实使用程度】分层说：哪些模块亲自用过，哪些只看过文档。

## Q11：介绍一下 AutoGen。

### 面试回答

AutoGen 是微软开源的多 Agent 会话框架，核心抽象就是“多个可对话的 Agent 协作”。

- 典型角色：AssistantAgent／UserProxyAgent。
- 支持群聊式协作，也支持在代理环境里执行代码。
- 适合研究多 Agent 分工与自动执行。

要按 2026 年的现状补一句：微软已经推出 Microsoft Agent Framework，作为 AutoGen 与 Semantic Kernel 的统一后继，官方提供迁移指引。AutoGen 仓库还在，但新的生产选型应该先看后继框架。

只了解没用过，就如实说明。

## Q12：有没有用过大模型的网关框架（LiteLLM）？

### 面试回答

LLM 网关是放在应用和多家模型 API 之间的统一接入层。一套 OpenAI 兼容接口就能路由 100+ 模型，LiteLLM 就是这类的开源方案。

它集中管这几件事：

- 密钥托管、预算与限流。
- 失败自动 fallback／重试。
- 缓存与调用观测：成本、延迟按 key／模型统计。

价值是把“供应商差异与治理”从业务代码里拿出来。代价是多一跳，也多一个要运维的组件——单体小项目直连 SDK 也可以。

用过讲【部署与配置】，没用过如实说明。

## Q13：为什么手搓 Agent，而不是用框架？

### 面试回答

按真实动机讲。通用的三条理由是：

- 控制与理解：循环、上下文组装、工具执行都是自己写的，行为可预测，排障也不用隔着一层抽象。
- 依赖最小：不被框架的版本演进绑架。
- 教学与面试场景：能讲清每一步发生了什么。

代价也要认：持久化、恢复、并发、观测这些框架已经解决的问题，得自己实现一遍；团队之间也不好复用。

所以合理结论是分场景：要理解原理、或者需求极简时手写；要做复杂状态编排、要团队协作时评估框架（LangGraph 类）。两者不互斥。

## Q14：MCP 是什么，和 Function Call 有什么区别，有没有实践过？

### 面试回答

先给结论：两者层次不同。

- Function Call 是模型能力：模型按注入的工具 schema（接口描述），输出结构化的调用意图。
- MCP 是协议：标准化宿主应用与外部工具／资源服务之间的发现和调用，角色是 host—client—server。

实践链路按顺序说：模型提出调用 → 宿主运行时校验授权 → MCP Client 发 `tools/call` → Server 执行并返回。

有没有实践过按【真实做过】讲：接过什么 Server、工具清单有哪些、参数和结果怎么处理。

## Q15：A2A 了解吗？

### 面试回答

A2A（Agent2Agent）是 Agent 之间的互操作协议，由 Google 在 2025 年发起、后来捐赠给 Linux Foundation。

三个机制点：

- Agent Card：Agent 用它声明自己有什么能力。
- 协作方式：走任务生命周期（Task）加消息交换。
- 传输层：JSON-RPC／HTTP＋SSE。

与 MCP 的分工一句话记住：MCP 面向“Agent 调工具”，A2A 面向“Agent 对 Agent”。

## Q16：ReAct 是啥，怎么实现的？

### 面试回答

ReAct 就是推理（Reason）与行动（Act）交替，按顺序循环：

1. 模型先想一步，输出结构化的动作（工具＋参数）。
2. 执行器校验并执行。
3. 把观察结果回传。
4. 如此循环，直到输出 final 答案。

实现要点五条：

- 动作协议要结构化，不能靠自然语言猜。
- 参数与权限在运行时校验。
- 用调用 ID 把请求和结果配成对。
- 设步数与费用预算。
- 加无进展检测兜底，防止原地打转。

来源说一句：这个范式出自 2022 年的论文，各家生产实现都有变体。

## Q17：CoT 是啥，为啥效果好，有啥缺点？

### 面试回答

CoT（思维链）是让模型显式生成中间推理步骤，再给结论的提示方式。常见形态有三种：“一步步想”、few-shot 推理示例、零样本触发句。

为什么有效：一步做不完的多约束问题，被拆成多个短步骤，每一步都以上一步的产出为条件再生成。相当于用自回归的串行计算换深度，单次映射的难度就降下来了。

缺点要记全：

- token 与延迟成本显著增加。
- 中间步骤错了会连锁带偏后面。
- 推理链写得流畅，也可能是事后合理化，并不忠实于模型真实的计算过程。
- 对简单任务反而降效。
- 隐藏思维链的场景下，拿不到中间过程。

## Q18：Prompt Caching 是什么？

### 面试回答

Prompt Caching（提示词缓存）是对请求前缀复用上一次算出来的 KV／注意力状态，也就是键值缓存。前缀指系统提示、工具定义、长文档这些稳定部分。命中之后，这部分按更低价格计费，首 token 延迟也下降。

三个要点：

- 匹配是按前缀来的，所以要把稳定内容放前面、易变内容追加在后面。
- 各家的实现粒度、TTL（缓存存活时间）、最小可缓存长度、计费折扣都不一样，按所用厂商文档核对。
- 边界要说清：它只优化计算和成本，不减少上下文占用量，也不改变模型行为。

## Q19：温度／top-p／top-k 分别是什么，各场景最佳设置？

### 面试回答

三者都作用在采样阶段，改的是 logits（每个候选 token 的原始打分）：

- 温度：把 logits 除以 T，改变分布的陡峭度。T→0 趋近贪心，越大越随机。
- top-k：只在概率最高的 k 个 token 里采样。
- top-p：也叫核采样，取累计概率达到 p 的最小集合。

关于“最佳设置”，先说结论：没有普适值，只有方向。

- 事实问答／抽取／代码用低温（0~0.3）求稳定，创意写作往上调。
- 结构化输出与函数调用，配低温＋受限解码。

补一句方法：要在同一个 seed 下做参数的可复现比较，别宣称某个固定值最优。

## Q20：文档切割策略有哪些，怎么规避语义被切割掉？

### 面试回答

- 固定长度＋重叠。
- 按分隔符：段落、标题层级。
- 结构感知：Markdown 标题、代码块、表格整体保留。

## Q21：多路召回是什么？

### 面试回答

多路召回就是：同一个查询用多条互补路径并行召回，再融合去重。常见几条路：

- 关键词检索：BM25，一种经典的词项匹配打分，擅长精确术语和编号。
- 向量检索：擅长语义改写后的表达。
- 多查询扩展：换几种问法。
- 结构化过滤：按元数据、时间筛。
- 图关联扩展：沿关系往外扩。
- 不同粒度的块：子块用来定位，父块用来补全。

为什么要这么做：单一检索器各有盲区，多路是为了提覆盖率；融合之后再统一重排控制精度。

最后强调一点：各路权重和 top-k 是在评测集上调出来的，不是玄学默认值。

## Q25：怎么量化回答效果，例如检索的效果、回答的效果？

## Q35：你最大的难题是什么，怎么提高效果、怎么降低延迟？

回答框架（按【真实经历】填）。挑题原则：选一个能同时贯穿“效果”和“延迟”两条线的难题，例如“检索质量不稳且时延高”。

效果侧怎么提：

- 错误分层归因：分清是召回没中、上下文断了，还是生成跑偏。
- 再逐项做消融和评测回归。

延迟侧怎么降：

- 分级路由，简单问题不走 Agent。
- 多路召回把串行改成并行。
- Prompt Caching 与模型降级组合使用。

讲述的骨架是“先量化现状，再按瓶颈投入，改完再量化”，不要堆名词。

## Q36：端到端延迟如何优化的？

### 面试回答

方法是先测再改：先分段测量，找出大头在哪，再按段优化。分段包括路由、检索、各次模型调用、工具、生成。

按段能做的六件事：

- 减少调用次数：分级路由，能一次做对的就不要进循环。
- 并行化没有依赖的步骤。
- 流式输出，降低体感延迟。
- 压上下文：Prompt Caching，加上压缩历史、裁剪工具输出。
- 稳定的子任务交给小模型。
- 检索侧给热点做缓存。

验收口径两条：用 P95 而不是平均值；同时盯成功率和成本，防止“快但错”。

## Q37：Agent 服务高可用、稳健性是怎么保证的？

### 面试回答

分两层做，再加一层验证。

服务层：

- 多实例无状态部署，配健康检查摘流。
- 模型供应商走双通道，或者用网关 fallback。
- 按租户和下游设并发与速率限制，防止故障放大。

任务层：

- 状态与检查点（checkpoint）外置持久化；宕机后按任务 ID，从已验证的检查点恢复。
- 工具调用要有超时，重试要带幂等键。
- 结果未知的写操作，先查实际状态再决定。
- 预算耗尽和不可恢复错误，进入失败或人工接管状态。

验证只认一种做法：故障注入演练，覆盖模型超时、工具半成功、实例宕机。纸面上的高可用不可信。
