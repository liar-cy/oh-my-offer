## Q03：缓存和 DB 用什么一致性策略？是强一致的吗？策略能否用到分布式场景？需要考虑哪些问题？

### 面试回答

结论：报项目真实策略（常规是 Cache Aside：先更新 DB、再删缓存，配 TTL 兜底），并主动定性——它做的是最终一致不是强一致；策略本身能推广到分布式，但要额外解决“本地缓存跨实例失效”和“失效乱序”两个新问题。

- 单机口径：
  - 更新走“DB 提交成功→删缓存”。
  - 不直接改缓存（并发改会写花）。
  - 删除失败进重试队列／靠 TTL 自然过期兜底。
- 为什么不是强一致：删除与更新之间总有窗口，并发读可能把旧值重新加载；要读到严格最新只能加锁牺牲吞吐或直接读 DB——按业务选，多数场景接受毫秒级窗口。
- 分布式化要考虑的四件事：
  1. 本地缓存不再共享：每个实例各有一份，失效必须广播（Redis pub/sub、MQ 广播、版本号比对），否则各实例各自为政。
  2. 失效消息乱序：给数据带版本号／更新时间，应用侧“只接受更新的版本”，防止旧失效后到把新值顶掉。
  3. 集中层与本地层的一致性：Redis 更新成功后本地层才失效；本地层只留短 TTL 降低不一致暴露面。
  4. 热点与击穿：分布式下同一热 key 在多实例同时 miss，回源要加互斥（singleflight／分布式锁）。

## Q05：项目中用到 ES，谈谈 ES 和 Lucene 的关系

### 面试回答

结论：Lucene 是 Java 搜索库——倒排索引、段、打分、查询执行都在它这一层；ES 是围绕 Lucene 建的分布式系统——把“一个库”变成“ REST API＋分片副本＋集群管理”的搜索引擎。

- Lucene 给什么：倒排索引结构与读写（段不可变、FSST 词典、postings、跳表）、BM25 打分、近实时刷新、BKD／doc values 等列存结构。
- ES 加什么：HTTP／JVM 层文档模型与 mapping、索引／分片／副本与路由、跨节点 scatter-and-gather 归并、集群治理（发现、再平衡）、聚合框架、插件生态。
- 关系一句话：ES 的一次查询，最终在每个分片上落成一次 Lucene 的本地检索；说“ES 快”时结构层面的功劳在 Lucene，规模层面的在分布式。
- 顺带定位竞品口径：OpenSearch 同源分支；Solr 也是包 Lucene 的独立生态——一句话展示知道谱系即可。

## Q06：ES 怎么实现高效检索？数据查询是在内存还是磁盘？

### 面试回答

结论：高效=结构＋裁剪＋缓存三层叠加——倒排索引让“找词”变查字典，FST／跳表／BKD 把磁盘读次数压到常数级，filter 位图缓存与 OS 页缓存把热数据实际变成内存操作。

- 结构层：
  - term 字典（FST 常驻内存）→ postings（doc ID 升序、delta 压缩、跳表跨块）。
  - 多条件求交并就是有序序列归并。
  - 数值范围走 BKD 树。
  - 打分 BM25 词频预计算。
- 执行层：先 filter 后 must（filter 不打分、可缓存位图）；协调节点按分片广播、各分片只回局部 top-N 再归并——不是把命中的都捞回来。
- 内存还是磁盘（分层答）：
  - 词典索引等小体积元数据常驻 JVM 堆／内存结构；段文件真身在磁盘，但 Lucene 通过 mmap／顺序读让 OS page cache 充当热数据缓存——“磁盘是事实源，内存是热点副本”。
  - fielddata／聚合用 doc values 从磁盘随机读（OS 缓存托底），大字段进 JVM 堆会 OOM，所以要控制基数与请求量。
- 加分句：所以 ES 容量规划看“热数据能否留在 page cache”，堆只放元数据，节点内存一半给 Lucene 文件缓存。

## Q07：MySQL 有深分页，ES 会有吗？limit 100,100 实际检索多少行？MySQL 深分页处理手段？Google／百度这类大型产品怎么处理深分页？

### 面试回答

结论：都会有，但放大机制不同——MySQL 是“扫出来再扔掉”，ES 是“每个分片都要取 from+size 条给协调节点归并”。产品级答案：搜索引擎根本不让你翻到第 50 页。

- MySQL 计数题：`LIMIT 100,100` 丢弃前 100 取 100，引擎侧实际处理 200 行；若二级索引非覆盖，这 200 行都要回表——offset 大成本线性涨。
- MySQL 手段：游标化（`WHERE id > last_max LIMIT 100`，只能顺序翻）、延迟关联（先在覆盖索引上取主键分页再回表）、按业务限定最大页深、大数据量导出直接分批不走分页。
- ES 侧：
  - `from+size` 成本≈分片数×(from+size) 的候选排序与网络传输。
  - 默认 `max_result_window=10000` 直接封顶。
  - 深翻改 `search_after`（上一页排序值当游标），全量导出走 scroll／PIT。
- 大型产品的做法（这题想听的）：
  - 不让翻深：Google 搜索稳定在第 10 页附近截断、bing 类限约前 1000 条——深层页流量极低还容易被爬虫白嫖，产品上直接取消。
  - feed 流全改游标：时间线用 cursor／min-time 无限下拉，“第几页”这个概念在 C 端信息流里基本消失。
  - 后台与导出场景才允许“遍历”，实现是游标分批＋异步任务，绝不给在线接口开大 offset。
- 一句话收束：深分页的终解不是把翻页做快，而是取消翻页——面试里先讲技术缓解、再升到产品策略最加分。

## Q10：如何理解“大模型”这三个字？聊天的记忆功能是大模型提供的吗？大模型有状态吗？

### 面试回答

结论：“大”在参数规模与训练数据、更在“通用能力涌现”——它本质是一个无状态的下一 token 预测函数；对话记忆不是模型能力，是应用层每次把历史重新塞进上下文窗口造出来的效果。

- 三个字的拆解：大参数（十亿级起）＋大数据（互联网规模语料）＋大算力预训练，换来少样本甚至零样本的通用任务能力；能力来自训练三阶段（预训练学语言与知识、后训练学指令与对齐，见 LLM-012）。
- 有没有状态：推理是一次前向计算，输入 prompt 输出续写，调用之间没有任何残留——服务端不会“记得”你上一句；模型侧的 KV Cache 只为同一次生成加速，跨轮会话不靠它。
- 记忆从哪来：应用层把历史消息（或摘要、检索片段）重新拼进上下文再发给模型——所谓记忆＝上下文工程，窗口有限所以要截断／摘要／向量检索外存（这正是 Harness 层的事）。
- 加分句：所以“窗口多大”决定模型“当场能看多少”，“记忆系统做得好坏”决定“跨会话能记住什么”——一个是能力上限，一个是工程问题。

## Q11：大模型如何驱动任务执行（订机票、打开网页）？为什么它能订机票？

### 面试回答

结论：模型自己不能订机票——它只会输出文本；是 Function Calling 把“可执行工具”的 schema 放进上下文，模型输出一个结构化的调用意图，宿主程序校验后真正执行，再把结果喂回去继续决策。

- 关键认知：模型输出的是“意图 JSON”，不是动作。执行权、鉴权、事务全在应用层。
- 闭环四步：注册工具（航班查询／支付／日历）→ 模型判断需要工具、输出 `tool_name + arguments` → 宿主校验 schema＋权限后执行 → 结果回填上下文，模型决定下一步或收尾。
- 能力哪来的：后训练阶段用工具调用数据微调，模型学会了“什么时候该调、参数怎么填”（见 LLM-009）；MCP 只是把“接哪些工具”标准化成协议，不改变执行边界。
- 打开网页同理：browser-use 这类工具把“打开／点击”暴露成带 schema 的动作，模型出指令、宿主跑浏览器截图回传。
- 风险句（加分）：所以参数校验、二次确认、幂等和资金风控是宿主的责任——模型幻觉出的参数不能直接执行。

## Q12：100 万包裹柜、一天 1 亿次存取（存取出时间存数组里，当天存当天取），找出包裹滞留数最多的时间段及长度；时空复杂度？

### 面试回答

结论：这是“区间重叠峰值”问题——每个包裹的在柜时段是一条 [存入, 取出) 区间，问题＝找事件线上重叠数最大的时间段。扫描线：所有端点排序，存入＋1 取出−1，前缀和最大值即峰值，并记录达到峰值的区间。

- 建模：一条记录 (存入 t1, 取出 t2) → 拆成事件 (t1, +1)、(t2, −1)；同一时刻先处理 −1 再＋1（或按题面约定），语义统一即可。
- 求峰值：事件按时间排序后累加 current，记录 max 及对应的起止事件时刻——最大滞留数与它持续的时间段一起拿到。
- 数据量：2 亿个事件排序属外部排序场景——先按时间分桶／分片（每桶装得下再内存排），多路归并扫描；分桶也天然并行化。
- 复杂度：设事件数 E（本题 E=2×1e8），时间 O(E log E)、空间 O(E)；时间已离散到“一天内的秒／分钟”时可换差分计数数组，O(E＋T)（T 为时间刻度数）。
- 追问预案：要“最长时间段”指峰值持续的总区间（合并相邻峰值段）；若还要定位哪些柜机，则按柜机分组各跑一遍扫描线（同 SYS-060 拆桶思想）。
