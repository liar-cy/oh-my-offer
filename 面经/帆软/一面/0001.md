## Q01：选一个案例，详细讲讲 Agent 工作的完整过程。

### 面试回答

挑一个能讲透的真实案例，按“一次完整执行”从头走一遍。我分成八步：

- 用户提出【任务】。
- 加载会话和任务状态，把上下文拼出来：指令、历史、必要证据。
- 模型输出一个结构化动作，比如调用查询工具。
- 运行时校验参数和权限。
- 工具执行，把观察结果回传。
- 模型继续决策：补查，或者直接产出。
- 结果验证：格式、事实、业务断言。
- 输出，同时记录整条轨迹。

讲每一步都带上三样东西：输入输出是什么、失败了走哪个出口（重试／澄清／转人工）、预算是多少（步数、耗时、费用）。

案例细节按【真实项目】填写，没实现的环节明说是设计而不是现状。

## Q02：如何评估 Agent 任务执行准确率？

### 面试回答

先给“正确”下一个可验证的定义，再谈指标。

- 定义：每个样本预先声明成功条件——结果可以由代码、数据库状态或业务断言来判定。
- 主指标：端到端任务成功率。同一批样本多次运行，还要看它的波动。
- 过程指标用来定位问题出在哪一层：意图／路由准确率、工具选择与参数正确率、结果校验通过率、约束违反率。

评测集怎么建：

- 覆盖正常样本、缺参样本、歧义样本和工具失败样本。
- 留出一部分测试集，不参与调优。
- 主观输出用明确的 rubric（评分细则）做人工评审，或者用经校准的模型来评。

最后守住一句：报出来的数字必须带样本量和口径。

## Q03：千万级数据库做等值过滤、范围查询慢，怎么排查优化？

### 面试回答

思路是先定位、再按证据优化，不要上来就动结构。

排查两步：

- 慢查询日志：确认到底是哪条语句、耗时怎么分布。
- EXPLAIN：看 type／rows／key／Extra 这几列。

两类慢分别看什么：

- 等值过滤慢：常见于没有可用索引（type=ALL，全表扫），或者是隐式转换、函数包住列，导致索引失效。
- 范围查询慢：看是不是走了索引但扫描区间过大、回表行数多、排序还额外用了临时表。

优化按证据来：

- 为高频等值列＋范围列建联合索引，等值在前、范围在后。
- 能做覆盖查询就做，避免大回表。
- 限制返回的列和行数。
- 数据层做冷热分离归档，必要时分区或分片。
- 同时排除三类干扰：锁等待、连接池排队、统计信息过期导致的计划劣化。

千万级的结论：先把索引和查询改写做扎实，分库分表是单节点确实撑不住之后的选项。

## Q04：包含等值查询，索引如何设计？

### 面试回答

一句话：联合索引的列序是“等值在前、范围在后”。

- 为什么：范围列之后的索引列没法再用来定位，最左前缀在范围这一步就“断”了。
- 等值列之间的顺序：按选择性和使用频率排。
- 高频组合可以做成覆盖索引，把 select 的列一起带上。
- 还要考虑 ORDER BY 能不能复用索引顺序，省掉 filesort。

设计完必须验证：

- 用代表性 SQL 跑 EXPLAIN，看 key、key_len 和 Extra。
- 用真实数据分布确认选择性。

别凭感觉堆索引：每个索引都有写入成本和空间成本。

## Q05：列举索引失效的常见场景。

### 面试回答

常见场景列七条：

- 对索引列用了函数或表达式，比如 `WHERE DATE(t)=...`。
- 隐式类型转换：字符串列传了数字，或者关联两边字符集／排序规则不一致。
- LIKE 以 % 开头。
- 联合索引没命中最左前缀：跳过前导列，或者范围列之后的条件不再用来定位。
- OR 连接了非索引列。
- 优化器基于统计信息判断全表扫更便宜，主动弃用索引：选择性低、需要回表的行数大。
- `!=`、`NOT IN`、`IS NOT NULL` 在特定数据分布下难走索引。

注意口径：多数场景是“优化器选择不走”，不是“结构上绝对不能走”。判断以 EXPLAIN 为准。

## Q06：联合索引场景下，单独给字段建索引和建联合索引有什么区别？

### 面试回答

两种建法的差别在服务谁。

- 单列索引：各自独立，任意一个单条件都能用。组合查询最多靠 index_merge（把多个索引的结果做合并排序／交集），效率不稳定，而且回表多次。
- 联合索引：按列序服务“前缀组合”，一条索引同时支持 (a)、(a,b)、(a,b,c) 的左前缀查询和覆盖。多条件定位一次完成，通常更快、更省回表。

联合索引的代价要说清：

- 只服务以首列开头、或者能构成前缀的查询，单独的 b、c 条件用不上。
- 列序设计错了，灵活性就没了。
- 写放大和空间要按组合来评估。

结论：高频一起出现的条件做联合索引，等值在前、范围在后；只有独立查询的场景才建单列。索引不是越多越好，用 EXPLAIN 和冗余索引检查工具收敛。

## Q07：PDF 解析、模型调用、网络 IO 分别适合进程／线程／协程哪种？三者区别与开销对比？

### 面试回答

先分负载类型，再决定用哪种执行单元。

- PDF 解析：CPU 密集。要真正并行就得有多个执行线程或进程——Java 用线程池、按核数限制并发，就能吃满多核；Python 受 GIL（全局解释器锁）约束，要上多进程。
- 模型调用、网络 IO：IO 密集，等待占比高。用协程或异步 IO，靠少量线程承载大量在等待的任务最合适；Java 没有原生协程，可以用虚拟线程或线程池来承载异步。
- 一条红线：不能在单线程事件循环里直接跑阻塞调用。

三者的区别和开销对比：

- 进程：独立地址空间，隔离最强，切换和通信成本最高。
- 线程：共享堆，切换较轻，代价是有数据竞争。
- 协程：用户态调度，切换最轻，单线程内没有竞争；但一个协程阻塞会拖累整个循环，而且吃不到多核。

## Q08：TCP 如何保证可靠传输？

### 面试回答

TCP 的可靠不是一条机制，是一组机制叠出来的：

- 序列号＋确认应答：给每个字节编号，按序确认、顺手去重。
- 重传：超时重传补回丢失的段；快速重传靠 3 个重复 ACK 提前触发。
- 滑动窗口与流量控制：让发送速度不超过对端的接收能力。
- 拥塞控制：慢启动、拥塞避免、快重传快恢复、乘性降，避免把网络压垮。
- 校验和：发现损坏就丢弃。

局限也要说清楚：这里的“可靠”只指字节有序送达。它不保证应用层的请求成功语义，也不防重复提交。超时断连之后，还得业务自己用心跳和幂等兜底。

## Q09：WebSocket 断开重连如何设计？

### 面试回答

分四件事：怎么发现断了、怎么重连、怎么恢复、怎么防重。

- 检测：靠应用层心跳，ping／pong 加超时判定。别漏了一句——TCP 本身不会告诉你“对端假死”。
- 重连：指数退避再叠加随机抖动，防止一堆客户端同时回来惊群；设最大间隔和重试上限。页面可见性恢复、网络恢复这类事件可以触发立即重连。
- 恢复：重连后先重新鉴权，token 可能已经过期；带上最后收到的消息序号或会话 ID，向服务端补拉断连期间的增量；待发消息在客户端队列暂存，队列必须有界，超限的丢弃策略要写明确。
- 幂等：重连和补发可能产生重复消息，收发两端都按序列号去重。

收尾一句：传输层重连成功不等于业务会话还在，会话恢复协议要应用自己设计。

## Q10：接口超时如何处理？

### 面试回答

第一原则：每个外部调用都显式设连接超时和读超时，绝不无限等待。

超时之后先分清语义——是结果未知，不是失败：

- 幂等的 GET：可以退避重试。
- 非幂等的写操作：先凭请求号去查实际状态，确认没执行过才重试。

配套的四层兜底：

- 重试设次数上限，配指数退避，防重试风暴。
- 连续超时或失败率达到阈值，走熔断降级：快速失败、返回兜底，或者转异步受理。
- 长耗时操作改成“受理＋状态查询”，从设计上消灭长同步等待。
- 超时时长按压测的 P99 加余量来定，并且逐层核对：调用方的超时要大于被调方内部预算之和，否则就是“我超时了你还在跑”，白耗资源。

## Q11：服务端同时收到大量请求怎么处理，如何保证请求幂等性？

### 面试回答

两问分开答。

第一问，大量请求分层泄压：

- 入口限流：按接口／用户／租户设配额，超限就快速拒绝或排队。
- 服务做成无状态，水平扩容。
- 热点读走缓存。
- 写洪峰用 MQ 削峰，改成异步。
- 慢依赖做隔离和降级。

目标是系统“有损服务”，而不是被整体拖死。

第二问，幂等性按写操作来设计：

- 客户端携带稳定的请求号或业务唯一键。
- 服务端做持久化去重——唯一索引或 token 核销，重复请求返回首次结果。
- 状态机只允许从前置状态往下流转，乱序和重复都能判定。
- 去重记录要和业务写入在同一个事务里，或者放共享存储，多实例部署下才有效。

一句别背错：前端按钮置灰和本地缓存不是正确性保证。

## Q12：Java 对象内存大小怎么估算，基本数据类型占用多少字节？

### 面试回答

先摆布局，再按类型加字段。

- 对象头：Mark Word 8 字节＋压缩类指针 4 字节，未压缩时是 8。
- 实例字段：按类型算宽度。
- 对齐填充：HotSpot 按 8 字节对齐。

基本类型占用，成对记：

- boolean／byte：1
- char／short：2
- int／float：4
- long／double：8
- 引用：开启压缩指针时 4 字节（默认开启，堆小于 32G 时生效）。

现场举个例子：一个 int 加一个引用，12＋4＋4＝20，补齐就是 24 字节。

三条注意事项：

- 基本类型数组每个元素按上面的宽度存，boolean 数组每元素占 1 字节。
- JVMS（Java 虚拟机规范）不规定裸类型的大小，上面是 HotSpot 的实现口径。
- 要准数用 JOL 工具实测；另外区分 shallow size（只算对象自己）和 retained size（算上它引用到的对象）。

## Q13：介绍一下 JVM 内存模型。

### 面试回答

开口先确认口径，因为这个词有两种含义。

如果问的是运行时内存区域，分线程私有和共享两类报：

- 线程私有：程序计数器、虚拟机栈、本地方法栈。
- 共享：堆——对象分配和 GC 的主战场；方法区——HotSpot 用元空间实现，运行时常量池归属在其中。
- 再补一句边界：直接内存不受堆 GC 管辖，所以 Xmx 不是进程的总上限。

如果问的是 JMM（Java 内存模型）：

- 它是描述多线程访问共享变量的抽象模型，讲主内存和工作内存。
- 规则是 volatile 与锁提供的 happens-before。
- 解决的是可见性和有序性。

两种不能互相顶替：拿堆栈分区去答 JMM 就是答非所问。

## Q15：N 类请求峰值占用已知、同类结果可复用、内存有限，如何兼顾并发、延迟与稳定性？

### 面试回答

这是容量规划＋缓存准入问题。答题框架是“先量化、再隔离、后优化”。

- 静态预算：用已知的每类峰值占用，给每类请求设内存配额，总和留安全水位——低于容器限额，预留栈、元空间和临时对象。目的就是杜绝单类吃满整机。
- 缓存：同类结果可复用，就按类建缓存，key 里带上依赖资源的版本。设容量上限，用 LRU／TTL 逐出。
  - 命中直接返回；未命中限制并发回源（singleflight，同一个 key 只放一个请求去回源，防击穿）。
- 并发与延迟：高命中率的类优先驻留；计算型任务的并行度按 CPU 和内存双重限制。
- 稳定性：超出配额就排队，或者降级到慢路径，而不是走到 OOM。监控命中率、内存水位和 P95 延迟，据此动态调配额。

开放题就按这个框架答。

## Q16：如何设计任务队列处理多类请求，保证公平性、防止一类请求占满资源？

### 面试回答

核心是隔离＋加权调度，四件事：

- 隔离：每类请求有独立的子队列和并发配额（bulkhead，舱壁隔离），杜绝一类积压把别人饿死。
- 调度：用加权公平，思路参考 WFQ（加权公平队列）或 deficit round-robin（亏空轮转）。按业务优先级和配额轮转取任务，低优先级也保底一点带宽，同样是为了防饿死。
- 线程池：worker 池按各类任务的资源画像分组，CPU 型和 IO 型分开。
- 准入：队列有界加准入控制，满了就快速拒绝或降级；监控各类的排队时长和完成率，据此动态调权重。

再加一层：如果某一类任务可以合并或批处理，就做聚合，把它的资源占用直接降下来。

## Q17：缓存如何设计，需要考虑什么？

### 面试回答

我按问题清单逐项过：

- 缓存什么：选型由命中率驱动，看热点程度、计算成本、时效性。
- key 和粒度：key 里含版本／租户，不要把大对象整个存进去。
- 读写模式：以 cache-aside 为主，顺序是先提交 DB 再删缓存。
- 一致性和陈旧上限：先问业务能忍多久旧数据，再定失效的驱动方式，并用 TTL 兜底。
- 容量与逐出：设上限，用 LRU 一类策略，按内存预算来。
- 异常场景：穿透用空值缓存或布隆过滤器；击穿用互斥或逻辑过期；雪崩把 TTL 打散，再加高可用。
- 冷启动：预热，同时保护回源——限制并发、加熔断。
- 观测和治理：命中率、逐出率、P99、大 key；权限、脱敏、失效补偿、监控告警。

现场结合【项目实际】挑重点展开，不要背清单。

## Q18：n 个请求分两批到达，完整请求耗时 1 分钟，30 秒时依赖资源变更，多长时间完成？

### 面试回答

开放题，先澄清三个条件，再分情形给数：

- 两批各自的到达时刻。
- 并行度是否充足。
- “依赖资源变更”会不会让变更前算出的结果作废。

典型情形（n 个请求 t=0 全部到达、并行足够、变更使旧结果失效）：

- 第一批 60s 算完，但结果作废，重算再 60s → 120s。
- 第二批 30s 到达、90s 完成。
- 全部完成是 120s。

换一种口径：如果变更只影响“尚未开始或尚未读取依赖”的请求，第一批不受影响 → 90s。

再给优化方向，这部分才体现工程思维：

- 请求开始时快照依赖的版本，结束时比对——没跨越变更的结果保留，避免全量重算。
- 或者依赖变更时只失效受影响的那部分，做增量重算。

答完主动给一张口径表：不同假设对应不同答案，先和提问者对齐条件。
