## Q03：千万级数据库做等值过滤、范围查询慢，怎么排查优化？

### 面试回答

排查：慢查询日志确认语句与耗时分布→EXPLAIN 看 type/rows/key/Extra——等值过滤慢常见于无可用索引（type=ALL 全表扫）、隐式转换或函数包列导致索引失效；范围查询慢看是否走了索引但扫描区间过大、回表行数多、排序临时表。优化按证据：为高频等值列＋范围列建联合索引（等值在前、范围在后）；覆盖查询避免大回表；限制返回列与行数；数据层做冷热分离归档、必要时分区或分片；同时排除锁等待、连接池排队与统计信息过期导致的计划劣化。千万级先把索引与查询改写做扎实，分库分表是单节点确实撑不住后的选项。

## Q04：包含等值查询，索引如何设计？

### 面试回答

联合索引列序：等值条件列放前、范围条件列放最后——范围列之后的索引列无法再用于定位（最左前缀在范围处“断开”）；等值列之间按选择性/使用频率排，高频组合可做成覆盖索引把 select 列带上；同时考虑 ORDER BY 能否复用索引序避免 filesort。设计后用代表性 SQL 的 EXPLAIN 验证 key、key_len 与 Extra，并用真实数据分布确认选择性，不凭感觉堆索引——每个索引都有写入与空间成本。

## Q05：列举索引失效的常见场景。

### 面试回答

常见：对索引列使用函数或表达式（`WHERE DATE(t)=...`）；隐式类型转换（字符串列传数字，或字符集/排序规则不一致的关联）；LIKE 以 % 开头；联合索引未命中最左前缀（跳过前导列、范围列之后的条件不再定位）；OR 连接非索引列；优化器基于统计信息判断全表更便宜而弃用索引（低选择性、需回表行数大）；`!=`、`NOT IN`、`IS NOT NULL` 在特定分布下难走索引。注意口径：多数场景是“优化器选择不走”而非“结构上绝对不能走”，以 EXPLAIN 为准。

## Q06：联合索引场景下，单独给字段建索引和建联合索引有什么区别？

### 面试回答

单列索引各自独立：任意单条件都能用，组合查询最多靠 index_merge（合并排序/交集），效率不稳定且回表多次；联合索引按列序服务“前缀组合”：一条索引同时支持 (a)、(a,b)、(a,b,c) 的左前缀查询与覆盖，多条件定位一次完成，通常更快更省回表。代价：联合索引只服务以首列开头（或能构成前缀）的查询，单独的 b、c 条件用不上；列序设计错了灵活性尽失；写放大与空间要按组合评估。结论：高频一起出现的条件做联合索引（等值前范围后），只有独立查询场景才单列；不是“越多越好”，用 EXPLAIN 与冗余索引检查工具收敛。

## Q07：PDF 解析、模型调用、网络 IO 分别适合进程／线程／协程哪种？三者区别与开销对比？

### 面试回答

先分负载类型：PDF 解析是 CPU 密集——要真正并行需多个执行线程/进程（Java 线程池按核数限制并发即可吃满多核；Python 受 GIL 约束用多进程）；模型调用与网络 IO 是 IO 密集——等待占比高，用协程或异步 IO 以少量线程承载大量等待任务最合适（Java 无原生协程可用虚拟线程/线程池承载异步），关键是不能在单线程事件循环里直接跑阻塞调用。区别与开销：进程有独立地址空间，隔离强、切换与通信成本最高；线程共享堆、切换较轻但有数据竞争；协程由用户态调度，切换最轻、单线程内无竞争，但一个协程阻塞会拖累整个循环且不吃多核。

## Q08：TCP 如何保证可靠传输？

### 面试回答

机制组合：序列号＋确认应答给每个字节编号、按序去重；超时重传与快速重传（3 个重复 ACK）补回丢失段；滑动窗口与流量控制让发送不超过对端接收能力；拥塞控制（慢启动、拥塞避免、快重传快恢复、乘性降）避免压垮网络；校验和发现损坏丢弃。局限也要说：可靠指“字节有序送达”，不保证应用请求成功语义、不防重复提交，超时断连后业务要靠心跳与幂等兜底。

## Q09：WebSocket 断开重连如何设计？

### 面试回答

检测：应用层心跳（ping/pong＋超时判定，TCP 本身不告诉你“对端假死”）；重连：指数退避叠加随机抖动防惊群，设最大间隔与重试上限，页面可见性/网络恢复事件可触发立即重连；恢复：重连后重新鉴权（token 可能已过期）、携带最后收到的消息序号或会话 ID 向服务端补拉断连期间的增量、客户端队列暂存待发消息（有界，超限丢弃策略明确）；幂等：重连与补发可能产生重复消息，收发两端按序列号去重。传输层重连成功不等于业务会话还在，会话恢复协议要应用自己设计。

## Q10：接口超时如何处理？

### 面试回答

第一原则：每个外部调用显式设连接与读超时，绝不无限等待。超时后先分清语义——结果未知而非失败：幂等 GET 可退避重试；非幂等写操作先凭请求号查询实际状态，确认未执行才重试。配套：重试设次数上限＋指数退避防风暴；连续超时/失败率达阈值走熔断降级（快速失败、返回兜底或转异步受理）；长耗时操作改“受理＋状态查询”从设计上消灭长同步等待；超时时长按压测 P99 加余量设定，并逐层核对（调用方超时要大于被调方内部预算之和，避免“我超时了你还在跑”的资源浪费）。

## Q11：服务端同时收到大量请求怎么处理，如何保证请求幂等性？

### 面试回答

大量请求分层泄压：入口限流（按接口/用户/租户配额，超限快速拒绝或排队）→ 无状态水平扩容 → 热点读走缓存 → 写洪峰用 MQ 削峰异步化 → 慢依赖隔离与降级，保证系统“有损服务”而不是整体拖死。幂等性按写操作设计：客户端携带稳定请求号或业务唯一键，服务端持久化去重（唯一索引／token 核销），重复请求返回首次结果；状态机只允许前置状态流转，乱序重复可判定；去重记录与业务写入同事务或共享存储，多实例下才有效——前端按钮置灰与本地缓存不是正确性保证。

## Q12：Java 对象内存大小怎么估算，基本数据类型占用多少字节？

### 面试回答

估算布局：对象头（Mark Word 8 字节＋压缩类指针 4 字节，未压缩 8）＋实例字段＋对齐填充（HotSpot 按 8 字节对齐）。字段按类型计：boolean/byte 1、char/short 2、int/float 4、long/double 8 字节；引用在开启压缩指针（默认、堆 <32G）时 4 字节。例：含一个 int 一个引用的对象 ≈ 12＋4＋4＝20 → 补齐 24 字节。注意：基本类型数组每元素按上述宽度存（boolean 数组每元素占 1 字节）；JVMS 不规定裸类型大小，这是 HotSpot 实现口径；估算用 JOL 工具实测，并区分 shallow size 与含引用对象的 retained size。

## Q13：介绍一下 JVM 内存模型。

### 面试回答

## Q15：N 类请求峰值占用已知、同类结果可复用、内存有限，如何兼顾并发、延迟与稳定性？

### 面试回答

这是容量规划＋缓存准入问题：① 用已知的每类峰值占用做静态预算——给每类请求设内存配额，总和留安全水位（低于容器限额，预留栈、元空间与临时对象），杜绝单类吃满整机；② 同类结果可复用 → 按类建缓存（key 含依赖资源版本），设容量上限＋LRU/TTL 逐出，命中直接返回、未命中限并发回源（singleflight 防击穿）；③ 并发与延迟：高命中率类优先驻留，计算型任务并行度按 CPU 与内存双限；④ 稳定性：超配额排队或降级到慢路径而不是 OOM，监控命中率、内存水位与 P95 延迟，动态调配额。开放题按“先量化、再隔离、后优化”的框架答。

## Q16：如何设计任务队列处理多类请求，保证公平性、防止一类请求占满资源？

### 面试回答

核心是隔离＋加权调度：每类请求独立子队列与并发配额（bulkhead），杜绝单类积压饿死他人；调度用加权公平（WFQ/ deficit round-robin 思路）按业务优先级与配额轮转取任务，低优先级保底少量带宽防饿死；worker 池按各类任务的资源画像分组（CPU 型与 IO 型分开）；队列有界＋准入控制（满了快速拒绝或降级），监控各类排队时长与完成率并可动态调权重。若一类任务可合并或批处理，再加一层聚合减少占用。

## Q17：缓存如何设计，需要考虑什么？

### 面试回答

按问题清单逐项过：缓存什么（命中率驱动的选型依据：热点、计算成本、时效性）；key 与粒度（含版本/租户，避免大对象整存）；读写模式（cache-aside 为主，先提交 DB 再删缓存）；一致性与陈旧上限（失效驱动方式、TTL 兜底，业务能忍多久旧数据）；容量与逐出（上限、LRU 类策略、内存预算）；异常场景（穿透空值/布隆、击穿互斥或逻辑过期、雪崩 TTL 打散＋高可用）；冷启动预热与回源保护（限并发、熔断）；观测（命中率、逐出率、P99、大 key）与治理（权限、脱敏、失效补偿、监控告警）。结合【项目实际】挑重点展开，不背清单。

## Q18：n 个请求分两批到达，完整请求耗时 1 分钟，30 秒时依赖资源变更，多长时间完成？

### 面试回答

开放题，先澄清再分情形：两批各自的到达时刻、并行度是否充足、“依赖资源变更”是否使变更前算出的结果作废。典型情形（n 个请求 t=0 全部到达、并行足够、变更使旧结果失效）：第一批 60s 算完但结果作废，重算再 60s → 120s；第二批 30s 到达、90s 完成 → 全部完成 120s。若变更只影响“尚未开始/尚未读取依赖”的请求，第一批不受影响 → 90s。优化方向（体现工程思维）：请求开始时快照依赖版本，结束时比对——未跨越变更的保留结果，避免全量重算；或依赖变更时只失效受影响部分做增量重算。答完主动给口径表：不同假设对应不同答案，先和提问者对齐条件。
