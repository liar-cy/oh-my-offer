### 面试回答

实习介绍：我在【公司／团队】负责【模块】，用【Gin／go-zero／kratos 等，按实际】搭建服务，链路是【接口→业务→存储／缓存】。

- 并发模型：goroutine 加 channel，让“每个请求一个轻量执行单元、用消息传递共享状态”写起来很自然。网关、爬虫这类 IO 密集场景，几行代码就能安全并发。
- 部署与资源：编译产物是单个静态二进制，不依赖运行时；镜像小、内存占用低，适合容器化弹性伸缩。
- 工程效率：标准库覆盖 HTTP、JSON 等常用能力，编译快，格式与错误处理的规范也统一，团队协作的心智负担小。

说完优势要主动交代边界：泛型与生态成熟度弱于 Java，复杂业务分层不如 Spring 体系完备。

## Q03：如果改用 Java 开发同样的需求，架构上要注意什么、用什么技术达到类似效果？

### 面试回答

我会从三个层面对齐：并发模型、分层与生态、部署运维。

- 并发：Java 传统做法是线程池复用平台线程，配合 BlockingQueue 做生产者消费者，来近似 channel。
  - JDK 21 起可以直接用虚拟线程，把“一请求一线程”的写法找补回来——IO 阻塞由运行时挂起，而不是占着 OS 线程。这是与 goroutine 最接近的方案。
- 架构：Spring Boot 承担依赖注入、事务与横切能力，分层仍是 controller-service-mapper／repository。
  - 要注意一个习惯差异：Go 里习惯的显式组合，在 Java 里会改成面向接口＋组件扫描。
  - 共享可变状态也比 Go 更容易踩并发坑，要靠不可变对象、ThreadLocal 隔离或锁来收敛。
- 部署：三点差异。
  - 产物是 jar 加 JVM，要管理堆内外内存与容器 limit 的匹配。
  - 启动有 JIT 预热，冷启动与弹性伸缩要考虑。
  - 换来的是 JFR、Arthas 这类更成熟的运行时观测手段。

## Q04：Go 的协程在 Java 里有类似的方案吗？

### 面试回答

有，最接近的是 JDK 21 正式引入的虚拟线程（Loom，JEP 444）。

- 机制：每个虚拟线程由 JVM 调度，栈按需增长；阻塞 IO 时自动从载体线程卸载。
- 效果：用同步写法就能跑出接近 goroutine 的高并发吞吐。
- 用法：`Thread.ofVirtual()` 或 `newVirtualThreadPerTaskExecutor` 即可创建。

21 之前的替代方案：

- 响应式框架（WebFlux／Reactor）或 CompletableFuture 异步链：能扛并发，但代码风格倒置。
- 编译期方案：Quasar、Kotlin 协程这一类。

差异点也要说清：它不是 goroutine 的完全等价物。

- 虚拟线程不改变“阻塞即挂起”的 IO 语义，但对 synchronized 的长临界区曾经会钉住载体线程，JDK 24 JEP 491 之后已缓解。
- 它没有 channel 那样的语言级通信原语，协作要靠 BlockingQueue 或 StructuredTaskScope（仍在孵化）。

## Q05：Java 里锁的作用是什么，什么样的业务需要用锁？

### 面试回答

先说本质：锁是把“同一时刻不允许多个线程交错执行”这个约定，交给操作系统或运行时来强制。

- 保护对象：共享可变状态下的临界区。
- 保证什么：复合操作的原子性与可见性。
- 典型动作：“读—改—写”“检查再执行”——单条指令都原子，组合起来不原子。

需要锁的业务有共性：多个线程写同一份数据，而且结果必须正确。

- 库存超卖、限流计数。
- 单例与缓存重建。
- 订单状态机流转、堆内缓存的复合更新。
- 换成分布式场景，就升级为数据库条件更新或 Redis／zk 分布式锁。

反过来，这些情况就不需要锁：无共享（栈封闭、每线程一份）、不可变对象、单写者模型。能用这些手段就不用锁，因为锁带来吞吐损耗和死锁风险。

## Q06：讲一下 CAS 操作，CAS 和锁有什么关系？

### 面试回答

CAS 就是“比较并交换”：给定内存地址、期望旧值和新值，只有当前值恰好等于期望值才原子地写入，否则失败返回，由调用方重读重试。它由 CPU 指令支撑，比如 x86 的 lock cmpxchg。

和锁的关系，分两面说：

- CAS 本身不是锁。它是无锁并发的基础原语，不挂起线程，靠乐观重试。
- 但它是实现锁的零件，这几处底层都是 CAS 循环：
  - Atomic 类、AQS 抢 state。
  - synchronized 轻量级锁把对象头 Mark Word 替换成锁记录。
  - ConcurrentHashMap 的桶插入。

适用边界也要讲三条：

- CAS 只保证单个字原子更新，多字段的不变量还得靠锁。
- 高竞争下重试空转，烧 CPU。
- 有 ABA 问题，需要版本号配合，比如 AtomicStampedReference。

## Q08：LeetCode 31 下一个排列：讲思路与时间复杂度，未手撕。

面试官只要求口述思路与复杂度，未让现场写代码。题意按 LeetCode 31 标准定义：把排列重排成字典序中下一个更大的排列，若无则变成最小排列。

### 面试回答

开口先讲为什么这么改：要字典序恰好大一级，就得把靠右的一位抬起来，再让尾部尽量小。三步：

- 从右往左找第一个升序相邻对 a[i] < a[i+1]。i 右侧就是最长的降序后缀，在该前缀下已经是最大排列。找不到 i 说明整体降序，直接翻转整个数组就得到最小排列。
- 找到 i 后，在这个降序后缀里从右往左找第一个大于 a[i] 的数，两者交换。也可以二分——后缀是降序的，所以它就是后缀中“比 a[i] 大的最小值”。
- 再把 i 之后的后缀反转成升序，让尾部尽可能小。这样得到的就是字典序恰好大一级的排列。

复杂度和论据：

- 时间 O(n)，最多两遍线性扫描加一次反转；原地，额外空间 O(1)。
- 关键不变量：交换之后后缀仍保持降序，这是反转能拿到最小尾部的依据。

口述时拿【1,5,8,4,7,6,5,3,1】这类例子走一遍流程即可。
