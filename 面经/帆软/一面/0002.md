## Q01：LLM Wiki 相比 RAG 有什么区别，LLM Wiki 是怎么做的？

### 面试回答

（原第 1、4 题同题合并；“LLM Wiki”按“LLM 生成维护的结构化知识条目层”口径作答，指代需确认。）核心区别在“整理知识”发生在什么时候：RAG 在查询时——相似度检索原始片段、打包进上下文再生成，语料本身不被消化；LLM Wiki 在入库时——由模型把原始资料改写成规范条目（摘要、定义、步骤、FAQ），维护条目间链接与更新合并，查询时更像“找条目读条目”，可用关键词/链接导航而未必依赖向量相似度。它把“检索质量问题”前移成“条目质量问题”：答案更凝练、跨文档信息可预先融合；代价是生成式条目可能引入改写偏差，必须保留原文引用可回溯，更新管线也要版本化。两者常组合：Wiki 层做主干知识，RAG 兜原文长尾。

## Q02：RAG＋语义＋关键词＋GraphRAG 相比 LLM Wiki 有什么区别？

### 面试回答

这两条路线不在同一维度竞争：左边是“查询时把召回做强”——混合召回补语义/精确词盲区，GraphRAG 预构建实体关系以支持多跳；LLM Wiki 是“入库时把知识整理好”——生成规范条目、层级组织、互链导航。共同点：都提前做了某种“编译”（GraphRAG 预抽图、Wiki 预写条目），都在为“原始片段不够好”买单。选择看知识形态：事实密集、关系复杂、多跳问题→GraphRAG；文档型知识、问答与操作指引→Wiki 化条目＋检索兜底；两者都增加入库成本与“编译期出错”的新风险，小规模语料先用普通 RAG 验证，别默认全都要。

## Q03：LLM Wiki 的存储形式是什么？

### 面试回答

按“条目”组织而不是按原文 chunk：每个条目一行/一文档，字段通常含标题、正文（模型改写的规范表述）、来源引用（原文件＋位置，可回溯）、版本与更新时间、条目间链接（父主题/相关条目）、生效状态；检索友好形态是“条目正文再切块入向量库＋结构化字段入关系库”，或叠加图谱/链接索引支持导航。与 RAG 库的关键差别：存储单元是“被整理过的知识对象”而非“原文片段”，因此必须有来源映射与版本链，防止改写失真无法追责。项目实际表结构按【真实实现】填写。

## Q04：检索的时候有没有遇到什么问题，怎么调试的？

### 面试回答

按【真实经历】答，通用调试路径：问题先分类——“没检到”（召回失败）、“检到了但不对”（排序/冗余/权限）、“检对了答错”（生成不忠实）。手段：拿原始 query 人工复现→看该 query 的 top-k 明细与分数→对照标注片段算 Hit@k/Recall@k→定位是切块、embedding 域不匹配、过滤条件还是重排问题；bad case 沉淀成回归集，改动逐项消融验证。常见坑：查询与文档措辞鸿沟（靠改写/多路召回）、元数据过滤误杀、近重复块挤占 top-k（去冗余）。

## Q05：对文档的解析做了哪些优化？

### 面试回答

解析质量决定召回上限，常见优化：版式还原（标题层级、分栏阅读顺序恢复）；表格结构化保存而不是拉平成文本；图片走 OCR/图注提取并与正文位置绑定；页眉页脚、水印、重复模板元素去噪（按版式位置判定，不“重复就删”）；扫描页判定与低置信标注；按文档类型（PDF/PPT/Markdown/Word）分管线；解析结果保留原文坐标与版本供回溯。每项改动用“清洗前后有效信息保留率＋检索指标”对照验证。项目实际做到哪些按【真实实现】说。

## Q06：用户反馈知识库效果不好，怎么确定是问法不对还是索引建得不好？

### 面试回答

做归因实验而不是猜：① 收集该用户原始 query 与会话上下文复现；② 索引侧检验——用“标准问法”（人工把意图写成文档措辞）查同一知识，若标准问法能检到而用户问法检不到，问题在查询侧（问法/改写/召回覆盖）；若标准问法也检不到，问题在索引侧（没入库、解析丢失、切块破坏语义、embedding 域不匹配）；③ 按意图聚类统计失败分布，看是长尾问法普遍差还是特定文档差；④ 两侧各自修：查询侧上改写/多路召回，索引侧补数据、修解析切块，全部改动进回归集对比。

## Q07：用户的问题重写应该怎么设计？

### 面试回答

目的：弥合用户说法与知识库表述的差距，同时不偏离原意图。设计要素：多轮对话先做指代消解与省略补全，生成独立检索问题；口语规范化与错别字纠正；同义词/缩写扩展或多查询并行；复杂问题拆子查询；结构化抽取过滤条件（时间、对象、编号走精确查询不进向量）。约束：改写规则逐条在评测集验证增益，保留原 query 与改写后 query 同时召回再融合，防止改写漂移比不改更糟；高歧义时澄清而不是硬改写。

## Q08：Redis 为什么快，有哪些数据结构，String 用的什么结构？

### 面试回答

快在四层：纯内存操作；命令在单线程模型内顺序执行，无锁竞争、无多线程上下文切换（网络 IO 由 epoll 事件驱动多路复用，6.0 后读写与响应可多线程、执行仍单线程）；数据结构针对场景高度优化（listpack、跳表＋字典、intset、quicklist 等编码按规模自动切换）；协议简单＋pipeline 摊薄往返。类型：String、Hash、List、Set、ZSet 及 Bitmap/HLL/GEO/Stream。String 内部是 SDS（预分配＋记录长度，O(1) 取长、避免溢出），值≤20 字节且纯数字用 int 编码，短文本 embstr（一次分配连续内存），长文本 raw（分离分配可修改）。

## Q09：AQS 的数据结构是什么，锁竞争怎么处理，入队出队的并发安全怎么保证？

### 面试回答

AQS 核心＝一个 `state`（volatile int，锁/信号量的语义由子类解释）＋一条 CLH 变体的 FIFO 双向等待队列。获取流程：子类 tryAcquire 用 CAS 改 state 抢锁；失败则把线程包装成 Node（存线程、等待状态 waitStatus）CAS 入队尾，然后前驱是 head 且再次 tryAcquire 才出闸，否则按条件 park 挂起。竞争处理是“自旋一次＋挂起等待”的混合：避免纯自旋烧 CPU，也避免每次都要唤醒。入队安全靠 CAS 设置 tail＋CAS 设置前驱（两次原子步骤拼出安全入队，中间被观察到不一致时用 waitStatus 修正）；出队靠 setHead＋unparkSuccessor，唤醒时从尾部向前找有效后继以容忍并发断链；释放由 tryRelease 决定 unpark 队首。ReentrantLock 的公平/非公平只差在获取时是否先检查队列。

## Q10：表到千万级查询很慢是什么原因，回表是什么？

### 面试回答

千万级变慢的典型原因：无可用索引走了全表扫；有索引但选择性差、扫描行数仍巨大；二级索引命中后大量回表（按主键随机回聚簇索引取整行，I/O 放大）；排序/分组无索引支持产生 filesort/临时表；深分页 offset 扫弃；数据页分裂碎片化、统计信息过期导致计划劣化；锁等待或连接池排队。回表：InnoDB 二级索引叶子只存索引列＋主键值，查询需要其他列时须再按主键查聚簇索引取整行——这一跳就是回表；覆盖索引（所需列都在索引内）可免回表，延迟关联先取本页主键再回表可把回表次数压到页大小。

## Q11：三层高的 B+ 树能存储多少数据？

### 面试回答

这是估算题，先摆假设再算：InnoDB 页 16KB；非叶节点存（索引列＋页指针），按 bigint 主键约 8＋6≈14 字节/项，一页可放约 1170～1200 个分叉；叶子节点存整行，假设行平均 1KB，则一页放约 16 行。三层＝1200×1200×16≈2300 万行——这就是“三层 B+ 树约撑两千万行”的口径。追问必答敏感性：行更小（100B）叶子每页 160 行、同三层可到两亿级；主键越宽分叉越少；估算依赖页大小、行宽、填充率，报数前先问条件，别背常数。

## Q12：Claude Code 的 memory 和上下文是怎么做的？

### 面试回答
