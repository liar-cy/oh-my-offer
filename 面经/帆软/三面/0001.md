## Q01：简历 Agent 项目，整体业务流程是什么？

### 面试回答

讲法是按一条真实请求走完整链路，八个环节依次报出来：

- 用户入口：鉴权、识别是哪个租户。
- 加载会话与任务状态。
- 上下文构建：指令、历史、检索到的证据。
- 模型决策：规划，或者选择工具／Skill。
- 工具执行：参数校验、权限、调下游。
- 观察回传与状态更新。
- 结果验证：格式、事实、业务断言。
- 输出与落库：轨迹、成本、把反馈挂上去。

被追场景题时按层展开：隔离（Q02）、记忆（Q03）、错误（Q09）、成本（Q11）。

## Q02：多租户场景，Agent 如何做租户隔离与权限控制？

### 面试回答

隔离贯穿每一层，不是单点方案。按四个面讲，数据面有两条：

- 数据面：存储按租户划分，可以是库／表／行级，tenant_id 由服务端强制注入。
- 数据面还有一条底线：绝不信任客户端或模型传来的租户参数；检索和记忆查询要先按租户＋权限过滤，再召回。
- 执行面：工具与资源的权限模型是“租户→角色→工具→数据范围”，由服务端独立校验。模型只能表达意图。
- 上下文面：会话、缓存、向量索引、trace 日志都带租户命名空间。语义缓存的键要含租户，防止串数据。
- 资源面：按租户配额限制并发和成本。

遇到强合规的客户要求时，再提供独立部署／独立库的选项。

## Q03：Agent 的会话记忆、短期长期记忆是如何持久化存储的？

### 面试回答

这题按【项目实际】答；通用做法是分短期和长期两层。

短期记忆 ＝ 会话内的状态：

- 存的是消息序列和任务状态，包括计划、工具结果、检查点。
- 持久化到共享存储，比如 Redis 做热层、数据库落事实。
- 会话恢复时按 sessionId 加载。
- 摘要过的历史要保留原文的回查 ID。

长期记忆 ＝ 跨会话的事实：

- 先抽取候选，经过去重和冲突校验。
- 再带上 user_id、属性、来源、生效期、版本，写进数据库做主存。
- 再配上可重建的检索索引（关键词＋向量）。
- 注入上下文前，要按权限和有效性过滤。

两条关键口径：记录时间不等于事实生效时间；变更用“当前值＋历史失效”，不要用覆盖删除。

## Q04：平台访问量变大，如何避免不同用户会话互相干扰？

### 面试回答

思路：干扰都来自共享状态的泄漏路径，就逐条把它堵住。

- 状态隔离：会话／任务用命名空间，配服务端验证的 taskId。异步消息、回调、缓存键、临时文件、工具会话都要绑定任务（见 HARNESS-005）。
- 资源隔离：按用户／租户给并发配额和有界队列，防止单个大会话挤占线程和内存。
- 执行隔离：浏览器实例、文件目录、连接池做会话级隔离，或者复用前清理。
- 故障隔离：用 bulkhead（线程池分组隔离）、超时和熔断，一个会话卡死不外溢。
- 数据隔离：检索、缓存和日志全都带租户过滤。

压测时再用交叉验证的样本，专门测“串会话”这类场景。

## Q05：trace 数据如何存储、检索，千万／亿级日志量怎么优化查询性能？

### 面试回答

按写入、存储、检索三段讲。

写入侧：

- trace 先结构化，用 OTel 那类模型：traceId、spanId、属性。
- 走高吞吐通道：agent 采集 → Kafka → 批量写入。
- 用采样控制量：头部采样保住错误和慢请求，尾部采样按规则来。

存储分层：

- 热数据（近 7 天）进 ES／ClickHouse，支持全文和聚合查询。
- 冷数据落对象存储，用 Parquet 按天分区。
- 查询按时间路由到对应层。

检索优化：

- 查询必带时间范围和租户，这样才能做分区裁剪。
- traceId 精确索引优先。
- 聚合分析走列存。
- 避免全量倒排。

规模再涨就降采样率、缩短热数据期；明细可以重放的场景，另存原始日志。

## Q06：大表数据量大查询变慢，如何优化？

### 面试回答

一句话：分层递进，别一上来就说分表。

- 先定位：看慢查询日志，用 EXPLAIN 判断到底是全表扫、回表放大、排序临时表，还是锁等待。
- 再优化 SQL 和索引：联合索引、覆盖索引，深分页改成 seek。
- 然后做数据治理：归档冷数据，分区表按时间裁剪。
- 最后才谈架构扩展：读写分离分流读，分库分表拆写和容量，热点数据上缓存。

顺序的理由要讲出来：索引和归档先做掉。分表会引入跨片查询、分布式事务和扩容成本，它是容量确实撑不住时的选项，不是默认答案。

## Q07：哈希分表扩容有什么问题，一致性哈希算法原理？

### 面试回答

先说痛点：`hash(key) % N` 只要 N 一变，几乎所有键的归属都会变，等于触发全量数据迁移，在线扩容的代价很大。

一致性哈希的原理：

- 把键和节点都映射到 2^32 的哈希环上。
- 键顺时针找最近的节点。
- 扩容时只迁移新节点和它顺时针相邻的那一段，缩容同理。
- 再用虚拟节点解决分布不均和热点：每个物理节点挂上百个虚拟像。

工程上的三个注意点：

- 数据倾斜不能只看哈希，业务上的热点键要单独处理。
- 迁移期走双写＋校验＋灰度切流。
- 各处的路由版本要保持一致。

替代方案有两条，按系统对可控性的需求选：

- 槽位映射：像 Redis Cluster 的 16384 个 slot，迁移按槽粒度做。
- 倍数扩容：表数翻倍时只需要迁移一半。

## Q08：用户中途修改历史对话，如何增量更新避免全部重跑，缓存复用怎么设计？

### 面试回答

核心一句话：把会话从“一条线性文本”改成“一张带依赖关系的图”。

怎么建这张图：

- 消息按 ID 存储，并记录版本和分支。
- 每个派生物——摘要、检索索引、Agent 中间状态、已生成产物——各自登记“我依赖哪些消息”。

改一条历史消息时做依赖失效：

- 只有受影响的子树重算，未受影响的派生物直接复用。
- 摘要只重算覆盖到该消息的那一段。
- 向量索引只重建变更的 chunk。
- Agent 从对应的检查点续跑，而不是从头。

缓存复用怎么设计：

- 缓存键用输入内容的哈希，并且把版本算进去。
- Prompt 前缀缓存把稳定部分放前面、修改点往后移，这样能命中到分叉点为止。

最后一条保护：重算任务要幂等、可以限流排队，避免一次编辑触发重算风暴。

## Q09：Agent 节点执行报错有哪些处理策略，重试、降级、fallback、错误向上传递怎么处理？

### 面试回答

先给错误分类，再按类别选策略。

- 瞬时错误（超时、限流、网络抖动）：指数退避重试，加次数上限；重试要带幂等键。
- 依赖故障（某个模型通道挂了）：走 fallback，切备用模型或备用工具实现。
- 非关键步骤失败：降级——跳过该步、用简化路径或旧数据，并在结果里标注能力缺失。
- 业务性错误（参数不合法、权限不足）：不重试。把结构化错误回传给模型修正，或者转人工。
- 不可恢复错误：向上传播。任务进失败状态、释放资源、通知用户，绝不静默吞掉。

所有策略共享三条：错误要分类、可枚举；每次处理都留轨迹；预算（重试次数／时间／费用）超限就统一走失败出口。

## Q10：Agent 开发有哪些关键工程实践经验，如何控制上下文长度？

### 面试回答

实践清单挑自己亲自做过的讲，我报五条：

- 工具和输出全部走结构化契约。
- 权限校验放服务端，不靠 Prompt。
- 每步落状态，支持恢复与回放。
- 用评测集＋bad case 回归来驱动改动。
- 预算（步数／时间／成本）和终止条件先行确定。

上下文长度控制，按信息来源分手段：

- 按需加载：Skill 渐进披露、文件分页。
- 检索限数量，重排后只注入 top 几条。
- 工具输出截断，并给出回查 ID。
- 旧历史做结构化摘要；关键状态落到外部存储，用多少取多少。
- 固定开销（系统提示、工具定义）压缩合并。
- 按 token 预算给各分区分配，并预留输出空间。
- 压缩后回读关键状态，验证没有漂移。

## Q11：怎么降低大模型 API 调用成本，有哪些优化手段？

### 面试回答

我按四条线说：少调用、调小模型、少 token、复用。

- 少调用：做分级路由，简单问题不进 Agent 循环；合并可以并行的步骤；控制重试和循环的预算。
- 调小模型：分类、抽取、改写这类稳定子任务用小模型或规则；强模型只留给规划和难任务。
- 少 token：裁剪上下文——检索限量、工具输出截断、做摘要；输出用格式契约限长；设 max_tokens 上限。
- 复用：用 Prompt Caching 命中稳定前缀；缓存检索结果和答案，键里要含租户与版本。这里注意语义缓存有串数据的风险。

再配套成本观测：

- 按租户、按场景统计 token 和调用量。
- 优化前后用同一评测集验证，确认质量没有回退。

## Q12：如何规避 Agent 产生预期外漏洞、坑点，你的开发思路是什么？

### 面试回答

一句话：假设模型会出错，用这个前提来设计系统。

- 契约优先：工具的输入输出用结构化 schema，非法参数在执行前就拒绝。
- 最小权限＋服务端校验：模型只能申请，鉴权和资源归属由服务端判定；写操作带幂等和预览。
- 确定性兜底：能用代码校验的就别交给模型判断，比如格式、数值、状态机。
- 隔离与限制：沙箱执行，设资源和并发限额，敏感信息不进上下文也不进日志。
- 评测与灰度：新能力先过回归集，里面要含对抗样本（注入、越权、边界）；上线走灰度，并保留人工接管。
- 可观测：轨迹全量留痕，异常行为能回放定位。

坑点案例按【真实踩过的】讲。

## Q13：AI 开发和后端开发的异同，你怎么看待二者关系？

### 面试回答

相同点：两边都是工程。需求拆解、架构、可靠性、可观测、协作交付，一样都不能少。

不同点有四条：

- 输出是概率性的，所以多了“质量度量”这类工作：评测集、bad case 回归、置信度与拒答设计。
- 数据和 Prompt 也成了交付物，要版本化。
- 成本和延迟的结构不同：按 token 计费、依赖外部模型，容量规划要算整条调用链。
- 行为不确定，所以要求输入输出契约化，并由服务端校验兜底。

关系怎么看：AI 应用开发是后端工程的延伸。模型调用本质上是一个昂贵、会出错、不稳定的外部依赖，恰恰需要扎实的后端能力把它工程化——隔离、重试、限流、观测。

所以我的判断是：懂后端的人做 AI 应用，短板在评测思维，不在代码。

## Q15：工作中遇到和别人方案意见冲突，你怎么处理？

### 面试回答

回答框架，按真实经历填：

- 先对齐目标与事实。分歧常来自假设不同，把各自的前提摆出来。
- 完整听完对方方案的逻辑，再明确各自的优劣维度：成本、风险、可逆性、对上下游的影响。
- 能实验就用小成本 POC／数据说话；不能实验就请更了解上下文的人做评审。
- 形成决定后完整执行，同时保留异议记录和回滚预案。

收尾一句：对事不对人，别把方案分歧升级成立场之争。
