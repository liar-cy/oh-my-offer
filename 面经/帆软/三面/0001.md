## Q01：简历 Agent 项目，整体业务流程是什么？

### 面试回答

按一条真实请求走完整链路：用户入口（鉴权、租户识别）→ 会话与任务状态加载 → 上下文构建（指令、历史、检索证据）→ 模型决策（规划／选择工具或 Skill）→ 工具执行（参数校验、权限、下游调用）→ 观察回传与状态更新 → 结果验证（格式、事实、业务断言）→ 输出与落库（轨迹、成本、反馈挂钩）。场景题追问时按层展开：隔离（Q02）、记忆（Q03）、错误（Q09）、成本（Q11）。项目真实模块与本人职责按【实际】填写。

## Q02：多租户场景，Agent 如何做租户隔离与权限控制？

### 面试回答

隔离贯穿每一层而不是单点：① 数据面——存储按租户划分（库／表／行级 tenant_id 由服务端强制注入，绝不信任客户端或模型传来的租户参数），检索与记忆查询先按租户＋权限过滤再召回；② 执行面——工具与资源的权限模型是“租户→角色→工具→数据范围”，服务端独立校验，模型只能表达意图；③ 上下文面——会话、缓存、向量索引、trace 日志都带租户命名空间，语义缓存键含租户防串数据；④ 资源面——按租户配额限并发与成本。强合规客户要求时提供独立部署／独立库选项。

## Q03：Agent 的会话记忆、短期长期记忆是如何持久化存储的？

### 面试回答

按【项目实际】答，通用分两层：短期＝会话内状态——消息序列与任务状态（计划、工具结果、检查点）持久化到共享存储（如 Redis 做热层＋数据库落事实），会话恢复时按 sessionId 加载，摘要后的历史保留原文回查 ID；长期＝跨会话事实——抽取候选经去重与冲突校验后带 user_id、属性、来源、生效期、版本入数据库主存，配可重建的检索索引（关键词＋向量），按权限与有效性过滤后注入上下文。关键口径：记录时间≠事实生效时间；变更用“当前值＋历史失效”而不是覆盖删除。

## Q04：平台访问量变大，如何避免不同用户会话互相干扰？

### 面试回答

干扰来自共享状态的泄漏路径，逐条堵住：状态隔离——会话/任务命名空间＋服务端验证的 taskId（异步消息、回调、缓存键、临时文件、工具会话都绑定任务，见 HARNESS-005）；资源隔离——按用户/租户的并发配额与有界队列，防单个大会话挤占线程与内存；执行隔离——浏览器实例、文件目录、连接池会话级隔离或复用前清理；故障隔离——bulkhead 线程池分组、超时与熔断，一个会话卡死不外溢；数据隔离——检索、缓存与日志全带租户过滤。压测时用交叉验证样本专门测“串会话”场景。

## Q05：trace 数据如何存储、检索，千万／亿级日志量怎么优化查询性能？

### 面试回答

写入侧：trace 结构化（OTel 类模型：traceId/spanId/属性），高吞吐通道（agent 采集→Kafka→批量写入），采样控制量（头部采样保错误与慢请求、尾部采样按规则）。存储分层：热数据（近 7 天）进 ES／ClickHouse 支持全文与聚合查询，冷数据落对象存储（Parquet 按天分区），查询按时间路由。检索优化：查询必带时间范围与租户（分区裁剪）、traceId 精确索引优先、聚合分析走列存、避免全量倒排。规模再涨就降采样率、缩短热期，明细可重放场景另存原始日志。

## Q06：大表数据量大查询变慢，如何优化？

### 面试回答

分层递进：先定位（慢查询日志＋EXPLAIN 判断是全表扫、回表放大、排序临时表还是锁等待）→ SQL 与索引优化（联合索引、覆盖、深分页改 seek）→ 数据治理（归档冷数据、分区表按时间裁剪）→ 架构扩展（读写分离分流读、分库分表拆写与容量、热点上缓存）。顺序上先把索引与归档做掉，分表引入跨片查询、分布式事务与扩容成本，是容量确实撑不住时的选项而不是默认答案。

## Q07：哈希分表扩容有什么问题，一致性哈希算法原理？

### 面试回答

`hash(key) % N` 的痛点：N 一变几乎所有键的归属都变，触发全量数据迁移，在线扩容代价大。一致性哈希：把键与节点都映射到 2^32 哈希环上，键顺时针找最近节点；扩容只迁移新节点与其顺时针相邻区间，缩容同理；用虚拟节点（每物理节点上百个虚拟像）解决分布不均与热点。工程注意点：数据倾斜不只看哈希（业务热点键要单独处理）、迁移期双写＋校验＋灰度切流、路由版本一致。替代方案：槽位映射（Redis Cluster 16384 slot，迁移按槽粒度）与倍数扩容（表数翻倍只迁移一半），按系统可控性需求选择。

## Q08：用户中途修改历史对话，如何增量更新避免全部重跑，缓存复用怎么设计？

### 面试回答

核心是把会话从“一条线性文本”改成“带依赖关系的图”：消息按 ID 存储并记录版本/分支，派生物（摘要、检索索引、Agent 中间状态、已生成产物）各自登记“依赖哪些消息”。修改一条历史消息时做依赖失效：只有受影响子树重算——摘要只重算覆盖该消息的段、向量索引只重建变更 chunk、Agent 从对应检查点续跑而不是从头；未受影响的派生物直接复用。缓存键用输入内容哈希（含版本），Prompt 前缀缓存把稳定部分放前、修改点后移，命中到分叉点为止。重算任务幂等、可限流排队，避免一次编辑触发风暴。

## Q09：Agent 节点执行报错有哪些处理策略，重试、降级、fallback、错误向上传递怎么处理？

### 面试回答

先给错误分类，再按类别选策略：瞬时错误（超时、限流、网络抖动）→ 指数退避重试＋次数上限，重试要幂等键；依赖故障（某模型通道挂）→ fallback 切备用模型/工具实现；非关键步骤失败 → 降级（跳过该步、用简化路径或旧数据）并在结果标注能力缺失；业务性错误（参数不合法、权限不足）→ 不重试，结构化错误回传给模型修正或转人工；不可恢复错误 → 向上传播，任务进失败状态、释放资源、通知用户，绝不静默吞掉。所有策略共享：错误要分类可枚举、每次处理留轨迹、预算（重试次数/时间/费用）超限统一进失败出口。

## Q11：怎么降低大模型 API 调用成本，有哪些优化手段？

### 面试回答

按“少调用、调小模型、少 token、复用”四条线：少调用——分级路由（简单问题不进 Agent 循环）、合并可并行步骤、控制重试与循环预算；调小模型——稳定子任务（分类、抽取、改写）用小模型或规则，强模型只留规划与难任务；少 token——上下文裁剪（检索限量、工具输出截断、摘要）、输出格式契约限长、max_tokens 上限；复用——Prompt Caching 命中稳定前缀、检索结果与答案缓存（键含租户与版本，注意语义缓存串数据风险）。配套成本观测：按租户/场景统计 token 与调用量，优化前后用同一评测集验证质量不回退。

## Q12：如何规避 Agent 产生预期外漏洞、坑点，你的开发思路是什么？

### 面试回答

开发思路是“假设模型会出错来设计系统”：① 契约优先——工具输入输出结构化 schema，非法参数在执行前拒绝；② 最小权限＋服务端校验——模型只能申请，鉴权与资源归属在服务端判定，写操作带幂等与预览；③ 确定性兜底——能用代码校验的不交给模型判断（格式、数值、状态机）；④ 隔离与限制——沙箱执行、资源与并发限额、敏感信息不进上下文与日志；⑤ 评测与灰度——新能力先过含对抗样本（注入、越权、边界）的回归集，上线灰度并保留人工接管；⑥ 可观测——轨迹全量留痕，异常行为能回放定位。坑点案例按【真实踩过的】讲。

## Q13：AI 开发和后端开发的异同，你怎么看待二者关系？

### 面试回答

相同：都是工程——需求拆解、架构、可靠性、可观测、协作交付一样不少。不同：① 输出是概率性的，所以多了评测集、bad case 回归、置信度与拒答设计这些“质量度量”工作；② 数据与 Prompt 成为交付物，要版本化；③ 成本与延迟结构不同（按 token 计费、外部模型依赖），容量规划要算调用链；④ 行为不确定性要求契约化输入输出与服务端校验兜底。关系：AI 应用开发是后端工程的延伸——模型调用本质是一个昂贵、会出错、不稳定的外部依赖，恰恰需要扎实的后端能力（隔离、重试、限流、观测）把它工程化；懂后端的人做 AI 应用，短板在评测思维，不是代码。

## Q14：你遇到最难的一个任务是什么？

### 面试回答
