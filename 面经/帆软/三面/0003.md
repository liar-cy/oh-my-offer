## Q02：自研项目的来历：从哪里找的项目？做这些项目有什么作用？

### 面试回答

这题考“项目是不是你真做、真想过”，按来历→作用两层答，全部填真实事实：

- 来历：项目起点是【真实触发点：课设延伸／实习痛点复现／自己要用的小工具／开源社区找的方向】，选型时确认过【能覆盖我想练的技术点】。
- 不是“找来的项目”就低人一等：说清自己在上面做了哪些增量【新功能／重构／性能优化】即可。
- 作用一（能力）：把【并发／缓存／SQL 优化等】从“背过”变成“调过”，每个技术点都能对上一次真实排障。
- 作用二（结果）：【用户量／请求量／比赛或开源 star 等可核实产出】；没有量化结果就如实说“主要收益是完成了端到端闭环”。
- 落点：这些项目是为胜任【后台开发岗位】服务的，不是简历装饰。

避雷：不要把教程项目说成自研——面试官追两层实现细节就能问出来；被问穿比“项目普通”伤害大得多。

## Q04：文件中有大量整数（值域 1 到 1 千万），怎么去重并保证时间和空间复杂度尽可能低？

### 面试回答

结论：值域只有 1 千万，直接上位图——固定 1.25MB 内存，和文件多大无关。

- 量级先报出来：10^7 个取值对应 10^7 个 bit，折合约 1.25MB；换成 HashSet 每个元素要背对象和桶开销，差几个数量级。
- 第一趟流式读文件，每行一个整数 x 就置位：`bits[x>>6] |= 1L << (x&63)`。重复置位无副作用，这一步天然完成去重。
- 第二趟按位下标从小到大扫描，输出为 1 的位对应的数——去重和排序一次完成。
- 复杂度：时间 O(n＋值域)，空间只取决于值域，与 n 无关。
- 文件本身超内存也不影响：读文件是流式的，位图大小不变。

主动补两句边界：

- 要保留“每个数出现几次”，位图不够，升级成计数数组。
- 值域再大到位图放不下：分趟扫描（切 k 段扫 k 遍，用 I/O 换内存）或压缩位图；允许假阳性的近似去重才用布隆过滤器。

关联专题：[[专题题库/算法与数据结构#ALG-027：如何用位图对已知值域的数据去重排序？|ALG-027：如何用位图对已知值域的数据去重排序？]]

## Q05：user 表的电话号码与邮箱各建单列索引，两条件等值查询更可能命中哪个索引？

### 面试回答

结论：不由列名语义决定，优化器按成本在两个索引里各估一遍行数，选预估更便宜的；两个都高度唯一时结果可能倒向任一边，以 EXPLAIN 为准。

能想到的原因分四类：

- 选择性：谁被单独命中后剩余行数少谁占优。手机号基本一人一号；邮箱若存在共用、测试账号或大量 NULL，选择性变差就被放弃。
- 统计信息：行数估计来自持久化统计或 index dive；大批量改数据后统计过期，优化器可能“估错而选错”，`ANALYZE TABLE` 可纠。
- 索引本身的成本：手机号一般 11 位左右，键短、树小、扫描页少；邮箱 varchar 较长，utf8mb4 下全列索引超限常改建前缀索引，前缀区分度更低。
- 写法陷阱（最常见考点）：`phone_number = 13800138000` 写成数字字面量而列是 varchar，隐式类型转换让手机号索引直接失效，只剩 email 索引可走。

再补两条完整口径：

- 也可能两个都用：index merge intersection 取交集，但回表代价常让它不划算，优化器多选单索引＋另一条件回表后过滤。
- 验证手段：EXPLAIN 看 key／rows／Extra，看真实代价对比用 `optimizer_trace`。

## Q06：阅读共享的伪代码：这段代码在做什么？三个输入各输出什么？

面试官共享一段 Python 代码（截图提供），函数名被隐去写作 `xxx(data)`：

```python
def xxx(data):
    data = data.replace(" ", "").replace("\n", "")

    if not ((data.startswith("{")) and data.endswith("}")) and not ((data.startswith("[")) and data.endswith("]")):
        return False

    stack = []
    for char in data:
        if char in "{[":
            stack.append(char)
        elif char in "}":
            if not stack or stack[-1] != "{":
                return False
            stack.pop()
        elif char in "]":
            if not stack or stack[-1] != "[":
                return False
            stack.pop()
    return not stack
```

原题 7 给的三个输入：`input1 = [{1:}]`、`input2 = [{]}`、`input3 = [{[1}]]`。原文未写明输入是字符串还是对象；按“以字符串传入”作答——参数要走逐字符扫描，只能是字符串。

### 面试回答

结论：这是一个宽松的 JSON 风格括号结构校验器——去掉空格换行后，要求字符串整体被 `{}` 或 `[]` 包起来，再用栈检查 `{}／[]` 两类括号配对嵌套，数字、冒号等非括号字符一律忽略。

逐步对应代码：

- 预处理：删空格和换行，格式空白不影响判断。
- 前置检查：首尾必须构成 `{...}` 或 `[...]` 包裹，否则直接 False——比纯括号匹配多了一层“整体成对”要求。
- 扫描：左括号入栈；右括号来时栈顶不是对应左括号就 False（专防 `{[}]` 这类交叉嵌套）。
- 收尾：`return not stack`，栈空才 True；有剩余左括号说明没闭合完。

三个输入的结果：

- `[{1:}]` → True：外层 `[]` 包裹满足；括号序列 `[ { } ]` 逐对弹空。
- `[{]}` → False：首字符 `[`、末字符 `}`，两种包裹都不满足，在前置检查就返回 False；即使进到扫描，`{` 未闭合也会被栈检查拦下。
- `[{[1}]]` → False：`[ { [` 依次入栈；遇到 `}` 时栈顶是 `[`，不配对。

顺带说清它“不算严格 JSON 校验”的地方：`{1:}` 能通过，但 1 不是合法 JSON 键；引号、逗号、内容合法性它都不查，只管括号结构。

## Q08：想把一个问题问好，有研究过提示词应该怎么写吗？

### 面试回答

结论：答“有”，并给一套能复述的方法，不背术语。

- 四要素先想清：背景、目标、约束、输出格式。例：“你是 Java 评审者（角色），看这段并发代码（数据），只找死锁风险（目标），按严重程度列清单（格式）”。
- 给锚点：贴真实报错原文、最小可复现代码、一组示例输入输出，比形容词有效。
- 迭代而非重发：不满意就指出具体哪里偏——“第二点方向对，第三点跑题了，重来”；原样重发只会得到同样的答案。
- 分场景：简单问题一句话问完，不为小事堆模板；把方法论用在复杂任务上。
- 可加一句边界：提示词解决“表达”，解决不了知识缺口和模型幻觉，所以产出仍要自己验证。
