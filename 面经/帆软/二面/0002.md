## Q01：Redis 的 RDB 和 AOF 有什么区别，混合持久化如何工作？

### 面试回答

一句话：RDB 管“恢复快”，AOF 管“丢得少”，混合持久化让两者同时成立。

RDB：

- 本质是某一时刻的全量快照：BGSAVE fork 出子进程，写一个紧凑的二进制文件。
- 恢复时直接载入，所以速度快、文件小。
- 代价是两次快照之间宕机，这段写入就丢了；fork 和写时复制在大实例上还可能造成停顿。

AOF：

- 把写命令追加进日志，恢复靠回放命令。
- 丢多少数据由刷盘策略决定：always 几乎不丢但最慢，everysec 通常丢约一秒，是默认的折中。
- 文件更大，还需要重写压缩。

混合持久化解决两者的矛盾：

- 触发点是 AOF 重写的瞬间：先把当时的全量数据以 RDB 格式写进新的 AOF 文件，作为 base。
- 之后的增量命令继续按命令追加。
- 重启恢复时先载入 base，再回放尾部的增量。
- Redis 7.0 的多部分 AOF（base＋增量＋manifest 清单）把这套机制工程化了。

## Q02：JWT 用户认证的整体过程；改密后如何让旧令牌失效？

原题 3（认证过程）与原题 5（改密失效）同属 JWT 话题，按提问顺序合为一组；原素材未记录项目具体实现，以下为通用参考答案，接入细节需按真实项目修正。

### 面试回答

这题分两半：先讲正常的认证链路，再讲改密之后怎么让旧令牌失效。

登录与校验：

- 用户注册后登录，服务端校验用户名密码；密码存的是 bcrypt 这类哈希。
- 校验通过就签发 JWT，格式是三段式 header.payload.signature。payload 里放 userId、角色、过期时间等声明。
- 签名算法：单体服务用 HS256，拿服务端密钥签；网关＋多服务的场景用 RS256，公私钥分开。
- 客户端保存令牌，之后每个请求都放在 Authorization: Bearer 头里。
- 网关或拦截器验签、校验 exp 这些声明，通过后把 userId 注入请求上下文。
- 好处是不用查会话表，服务天然无状态、容易横向扩展。

追问“改了密码怎么让旧令牌失效”：

- 先说清前提：JWT 自包含，签发即有效，改密本身不会作废已经发出去的令牌，必须额外落一层状态。
- 最常用的组合：access token 只给分钟级的短有效期，改密时撤销全部 refresh token。攻击者能续命靠的就是 refresh。
- 要立即生效：在用户记录里加 token 版本号，或者加 password_changed_at 声明；验签之后再比对版本，改密就把旧版本整体作废。
- 另一种做法：把已签发令牌的 jti（令牌的唯一标识）记进 Redis 白／黑名单，改密时清空该用户的会话。精确，但引入了存储，而且每个请求要多一次查询。
- 按我的真实项目，我会说明用的是哪一种。

底线三条要主动讲：payload 只签名不加密、走 HTTPS 传输、固定校验算法以防 alg 被改成 none 的混淆。

## Q03：ThreadLocal 哪部分数据可能存在内存泄露？

### 面试回答

泄露的不是 ThreadLocal 对象本身，而是 ThreadLocalMap 里的 value。

为什么会泄露：

- 条目 Entry 的 key 是对 ThreadLocal 的弱引用，value 是强引用。
- 外部一旦不再强引用某个 ThreadLocal，key 就被 GC 置成 null。
- 但“线程 → ThreadLocalMap → Entry → value”这条强引用链还在。
- 线程池的线程长期存活，这些 key 为 null 的 value 就一直滞留，形成泄露。
- 所以准确说法是：线程对象持有的 Map 中，键已经失效的那些条目的值。

怎么防：

- 靠显式约定：谁 set 谁在 finally 里 remove。
- 别指望自动清理，Map 的探测式清理只在部分操作里顺带做，不是及时性保证。
- 同时避免把 ThreadLocal 定义成方法内的临时变量，又往里存巨大的 value。

## Q04：什么是缓存雪崩，怎么解决？除随机化 TTL 还有什么补充方案？

### 面试回答

雪崩是大量缓存 key 在同一时刻集中失效，或者 Redis 实例整体不可用，这批请求就同时打到数据库；DB 被压垮后失效面继续扩散，表现是“整块服务突然不可用”。

先把三个概念分清：击穿是单个热点 key 失效，穿透是去查根本不存在的数据，雪崩是一大批一起失效。

核心思路一句话：别让失效同时发生，别让回源同时到达。

第一层，打散 TTL：

- 基础值上加随机偏移，避免批量写入的 key 同生共死。
- 热点 key 可以用“永不过期 ＋ 后台刷新”。

第二层，随机化之外的补充方案，我按三层说：

- 缓存层：保证 Redis 本身高可用——集群、哨兵、副本；必要时用本地缓存（Caffeine）兜底热点。
- 回源层：做限流保护——互斥重建、请求合并、用信号量控制同时回源的并发数，DB 前面加线程池排队。
- 业务层：做降级——返回旧值、静态兜底或熔断，再配合故障演练和缓存预热。

收尾补一句：只答“TTL 加随机”是不完整的，它只解决“集中过期”这一种成因。

## Q05：讲一下布隆过滤器。

### 面试回答

布隆过滤器是“位数组＋k 个独立哈希”的概率结构，用空间换时间，专门回答“这个元素在不在集合里”。

怎么用：

- 插入：把元素哈希到 k 个位置，全部置 1。
- 查询：只要有任意一位是 0，就一定不存在；全是 1，则“可能存在”。

特性边界必须说全：

- 没有假阴性，但有假阳性。
- 误判率随元素数增长，近似 (1-e^(-kn/m))^k。
- 实际做法是按预期量 n 和目标误判率，反推位数组大小 m 和哈希个数 k。
- 经典布隆不支持删除，把某位置 0 会误伤和别人共用的那些位。要删除就用 Counting Bloom（计数布隆）或 Cuckoo Filter。

工程用法：

- 最常用的是放在缓存前面判存在，防穿透。Redis 侧有 RedisBloom／Tair 模块，也可以用 BitSet 自己实现。
- 一条硬性要求：数据新增必须同步进过滤器。漏同步会把真实存在的数据判成不存在——这是“宁可误拒不可误放”的反向坑。
- 它还常做大规模去重（爬虫 URL）和链路粗筛。

关联专题：[[专题题库/Redis#REDIS-002：缓存穿透是什么，布隆过滤器能完全解决吗？|REDIS-002：布隆过滤器能完全解决穿透吗？]]

## Q06：Redis 有哪些常用的淘汰算法？

### 面试回答

先分清两套机制，别混着答：

- 过期删除管“到没到期”：惰性删除＋定期抽样删除。
- 内存淘汰管“maxmemory 满了踢谁”。

淘汰策略是按键范围乘算法组合的：

- 键范围：noeviction 不淘汰、直接报错；allkeys 系作用于全部 key；volatile 系只作用于带 TTL 的 key。
- 算法：LRU、LFU、random、TTL 优先（volatile-ttl）。
- LRU 是近似实现，从抽样的候选池里比较空闲时长。
- LFU 在 8.0 之前就已经存在，按衰减后的计数看访问频次。
- 另有 allkeys-lrm（最近修改优先），是否支持要按版本确认。
- 生产里最常用的就是 allkeys-lru 和 allkeys-lfu。

一个易错点：Redis 的 LRU 不是精确链表，而是 `maxmemory-samples` 抽样近似，样本调大更准、也更耗 CPU。

选型结论：纯缓存场景选 allkeys-*；如果混存了不可丢的状态，必须先做键隔离，别指望 volatile-* 兜底。

## Q07：要自己实现一个 LRU，要怎么实现？

### 面试回答

结构就是哈希表＋双向链表。要同时满足两点：按访问序淘汰最久未用的，而且 get／put 都是 O(1)。

各自负责什么：

- Map 负责 key 到节点的 O(1) 定位。
- 链表维护访问顺序。
- 任意节点命中后，O(1) 摘出来提到头部。
- put 新键时如果容量满了，删除链表尾节点，并同步删掉 Map 里的条目。

要点全在细节：

- get 也算“使用”，要移动节点。
- put 一个已存在的键，要更新值并移动节点。
- 手写时把 moveToHead／removeNode 抽成私有方法；边界（头尾指针、只剩单节点）最容易错。

Java 的捷径：`LinkedHashMap(16, 0.75f, true)` 再覆写 `removeEldestEntry` 可以做出来，但这题考的是手写，别只背 API。

如果追问线程安全：

- 直接加锁会让热点 get 全部串行化。
- 常见做法是分片（如 Caffeine 的思路），或者接受近似 LRU。

## Q08：JVM 内存分哪些区域，直接内存由 JVM 管理吗，哪些区域会 OOM？

### 面试回答

分三块答：区域怎么分、直接内存归谁管、哪些区域会 OOM。

运行时数据区分线程私有和共享两类：

- 线程私有：程序计数器、虚拟机栈、本地方法栈。
- 线程共享：堆和方法区。HotSpot 的方法区用元空间承载，跑在本地内存里。
- 运行时常量池属于方法区。
- 另外，NIO 的 DirectByteBuffer 用的直接内存，不属于 JVMS 规范里的运行时区域。

直接内存“由谁管”，分两层：

- 它不像堆对象那样归 GC 管：分配走 Unsafe／native malloc，就在堆外。
- 但释放挂在 DirectByteBuffer 这个堆上对象的 Cleaner（幻影引用）上，对象被 GC 时顺带释放 native 内存。
- 所以准确说法是：GC 间接触发，由 JVM 记录用量，并用 -XX:MaxDirectMemorySize 限额。
- NIO 满了会先主动 System.gc() 再重试。

哪些区域会 OOM：

- 堆：Java heap space，最常见。
- 虚拟机栈：请求栈深度超过 -Xss 时抛 StackOverflowError；动态扩展的场景可以抛 OOM。
- 方法区／元空间：Metaspace，大量动态类或类加载器泄漏。
- 直接内存：堆外打满或 limit 不足。
- native thread：unable to create new native thread，线程数打到 OS 上限。
- 程序计数器是规范里唯一不发 OOM 的区域。

## Q09：线程池有哪些核心参数，如何设计让高优先级任务先执行？

### 面试回答

ThreadPoolExecutor 有七个参数：corePoolSize、maximumPoolSize、keepAliveTime 与 unit、workQueue、threadFactory、handler。

任务提交流程：

- 线程数先扩到核心数。
- 扩满了就入队。
- 队满再扩到 maximumPoolSize。
- 还不行就走拒绝策略。

要让高优先级任务先执行，改造点就在 workQueue：

- 换成 PriorityBlockingQueue。
- 任务实现 Comparable：优先级为主键、提交序号为次键，保证同级还是 FIFO。
- 入队即按序排列，出队自然先取到高优先级的。

但必须讲三个坑：

- 这个队列是无界的。队列不“满”，maximumPoolSize 就几乎不生效；真要扩线程，得靠显式 addWorker 或者换有界方案。
- 只有还在排队的任务享受优先级。已经在跑的低优先级任务不会被抢占；要做到“运行中也让路”，得上层调度或双池隔离。
- 低优先级任务会饥饿。要有老化提权，或者给低优先级留保底配额。

实践里更稳的做法往往是两级池：高优池固定资源直通，普通池限流排队，按业务分级路由。

## Q10：数据库是怎么保证事务的原子性的？

### 面试回答

一句话：InnoDB 的原子性靠 undo log——它就是事务改数据之前记下的“改动前的旧值”。

怎么起作用：

- 修改数据页之前，先把旧值写成 undo 日志。
- 回滚时按 undo 逆向恢复，把已经做过的修改逐条撤销。
- 崩溃恢复时，对未提交的事务同样用 undo 回滚，效果就等价于“要么全做、要么全没做”。

顺序和配合关系：

- 先写 undo 再改数据页，两者都遵循 WAL。
- 真正决定“恢复后从哪重放”的是 redo：redo 保证已提交的不会丢，undo 保证未提交的可撤。
- 两者配合，才让原子性和持久性同时成立。
- 提交时事务要走到 redo 落盘（prepare），再配合 binlog 的两阶段提交。

补一句边界：undo 不是给 MVCC 之外另造的一套数据。版本链就存在 undo 里，回滚和快照读共用这些历史版本；purge 线程要等到没有任何活跃快照还需要它，才能清理。

## Q11：MySQL 的读已提交怎么避免脏读，RC 和 RR 的核心差异是什么？

### 面试回答

读已提交避免脏读，靠的是 MVCC 的可见性判断：

- 快照读时，沿着行内的回滚指针走版本链。
- 跳过事务还没提交的版本，只取第一个“提交版”里在本事务视角已可见的那个。
- 所以别人没提交的东西永远读不到，而且不需要为此加读锁。
- 一个容易漏的细节：RC 仍然可能读到别的会话刚提交的修改，因为它每条 SELECT 都会新建一份 ReadView。

RC 与 RR 的核心差异就一点：ReadView 的生成时机。

- RC：每条语句各建一份。于是同一事务内两次重读同一行，可能看到新值，也就是不可重复读。
- RR：事务内第一次一致性读时建一份并复用，重读结果稳定。

延伸出来的差异：

- RR 在当前读的路径上额外用间隙锁／next-key lock，去抑制同条件结果的插入幻读；代价是锁冲突与死锁风险更高。
- RC 没有间隙锁，并发更好。很多互联网公司选 RC＋row 格式的 binlog。
- 别配错：按官方口径，RC 与语句格式的 binlog 不安全。

## Q12：一堆数中只有一个出现一次、其余都出现两次，如何快速找出它？

### 面试回答

全体异或一遍，结果就是答案。

为什么成立：

- 异或满足交换律和结合律，而且 x^x=0、x^0=x。
- 配对的两个数互相抵消，剩下的就是落单的那个数。

代价：时间 O(n)、空间 O(1)，不需要哈希表计数。排序后两两比较也能做，但是 O(n log n)，还会改数据。

口述时主动补两点，展示深度：

- 如果变成“其余出现三次、只有一个出现一次”，异或就不够了：要么按位统计次数再对 3 取模，要么用一次遍历的 ones／twos 双掩码状态机。
- 如果问“出现一次的两个数”：先全体异或，得到两数之差的信息；再按结果中某个为 1 的位把数组分成两组，分别异或。

边界说清楚：这套做法的前提是“其余恰好两次”，前提一变方法就得换。

## Q13：对 2 亿个取值在 1 万到 2 万之间的数据排序，怎么实现？

### 面试回答

先判场景：取值范围约 1 万种，远小于 2 亿的数据量。这种比例直接上计数排序。

两步走：

- 开一个长度 10001 的 int／long 数组，流式扫一遍输入，每来一个数就对 count[x-10000] 加一。
- 再按值域从小到大顺序扫计数数组，把每个值重复输出对应的次数。

代价：

- 时间 O(n+k)，这里 k=10001，两趟完成。
- 额外内存只有几千个计数器，几 KB 到几十 KB，远小于 2 亿数据的任何存储形态。
- 它是稳定排序，而且天然去重出“值＋频次”。

对比口径也备好：

- 不用 O(n log n) 的内存排序，是因为 2 亿整条数据放不进内存。
- 如果取值范围也很大，计数就不适用了，退回分块外部排序或者位图。
- 注意位图只能表达“存在与否”；要保留重复次数，还得用计数数组。

给个数字感受：每个数约 4 字节，输入共 800MB；计数器那边忽略不计，瓶颈全在 I/O 顺序读。
