## Q01：Redis 的 RDB 和 AOF 有什么区别，混合持久化如何工作？

### 面试回答

RDB 是某一时刻的全量快照：BGSAVE fork 子进程写紧凑二进制文件，恢复时直接载入，速度快、文件小，代价是两次快照之间的宕机会丢数据，fork 与写时复制在大实例上可能有停顿。AOF 把写命令追加进日志，恢复靠回放，数据丢失窗口由刷盘策略决定（always 几乎不丢但最慢，everysec 通常丢约一秒，是默认折中），文件更大、需要重写压缩。混合持久化解决两者矛盾：AOF 重写的瞬间，先把当时的全量数据以 RDB 格式写入新 AOF 文件作为 base，之后的增量命令继续以命令追加；重启恢复时先载入 base 再回放尾部增量。Redis 7.0 的多部分 AOF（base＋增量＋manifest 清单）把这套机制工程化了。一句话总结：RDB 管“恢复快”，AOF 管“丢得少”，混合让两者同时成立。

## Q02：JWT 用户认证的整体过程；改密后如何让旧令牌失效？

原题 3（认证过程）与原题 5（改密失效）同属 JWT 话题，按提问顺序合为一组；原素材未记录项目具体实现，以下为通用参考答案，接入细节需按真实项目修正。

### 面试回答

注册后登录：服务端校验用户名密码（密码存 bcrypt 类哈希），通过后签发 JWT——三段式 header.payload.signature，payload 放 userId、角色、过期时间等声明，用服务端密钥做 HS256 签名（或网关多服务场景用 RS256 公私钥）。客户端保存令牌，之后每个请求放在 Authorization: Bearer 头；网关／拦截器验签、校验 exp 等声明，通过后把 userId 注入请求上下文，无需查会话表，服务天然无状态、易横向扩展。追问“改了密码怎么让旧令牌失效”：JWT 自包含意味着签发即有效，改密本身不会作废已发出的令牌，要额外落一层状态——最常用组合是 access token 只给分钟级短有效期＋改密时撤销全部 refresh token（攻击者续命靠的是 refresh）；要立即生效则在用户记录加 token 版本号或 password_changed_at 声明，验签后再比对版本，改密即整体作废旧版本；或把已签发令牌的 jti 记入 Redis 白／黑名单，改密时清空该用户会话——精确但引入存储与逐请求一次查询。按真实项目我会说明用的是哪种；同时讲清底线：payload 只签名不加密、HTTPS 传输、固定校验算法防 alg none 混淆。

## Q03：ThreadLocal 哪部分数据可能存在内存泄露？

### 面试回答

泄露的不是 ThreadLocal 对象本身，而是 ThreadLocalMap 里的 value。条目 Entry 的 key 是对 ThreadLocal 的弱引用、value 是强引用：当外部不再强引用某个 ThreadLocal 时，key 被 GC 置 null，但“线程→ThreadLocalMap→Entry→value”的强引用链还在；线程池的线程长期存活，这些 key 为 null 的 value 就一直滞留，形成泄露。所以泄露部分是“线程对象持有的 Map 中键已失效的条目值”。防护是显式约定：谁 set 谁在 finally 里 remove，Map 的探测式清理只在部分操作顺带进行，不是及时性保证；同时避免把 ThreadLocal 定义成方法内临时变量又存巨大 value。

## Q04：什么是缓存雪崩，怎么解决？除随机化 TTL 还有什么补充方案？

### 面试回答

雪崩是大量缓存 key 在同一时刻集中失效，或 Redis 实例整体不可用，导致这批请求同时打到数据库，把 DB 压垮后失效面进一步扩散，表现为“整块服务突然不可用”。和击穿（单个热点 key）、穿透（查不存在的数据）要分清。核心思路是“别让失效同时发生、别让回源同时到达”：一是打散 TTL——基础值加随机偏移，避免批量写入的 key 同生共死，热点 key 可用永不过期加后台刷新；二是随机化之外的补充方案我分三层：缓存层保证 Redis 本身高可用（集群、哨兵、副本，必要时本地缓存 Caffeine 兜底热点）；回源层限流保护——互斥重建、请求合并、信号量控制同时回源并发数，DB 前加线程池排队；业务层降级——返回旧值、静态兜底或熔断，配合故障演练与缓存预热。只答“TTL 加随机”不完整，它只解决“集中过期”这一种成因。

## Q05：讲一下布隆过滤器。

### 面试回答

布隆过滤器是“位数组＋k 个独立哈希”的空间换时间概率结构：插入时把元素哈希到 k 个位置全部置 1；查询时任一位置为 0 则一定不存在，全 1 则“可能存在”。特性边界必须说全：无假阴性、有假阳性，误判率随元素数增长，近似 (1-e^(-kn/m))^k，要按预期量 n 和目标误判率反推位数组 m 与 k。经典布隆不支持删除（置 0 会误伤共享位），删除场景用 Counting Bloom 或 Cuckoo Filter。工程上最常用的是缓存前置判存在防穿透，Redis 侧有 RedisBloom／Tair 模块，也可以用 BitSet 自实现；要注意数据新增必须同步进过滤器，漏同步会把真实数据误判为不存在——这是宁可误拒不可误放的反向坑。它还常做大规模去重（爬虫 URL）和链路粗筛。

## Q06：Redis 有哪些常用的淘汰算法？

### 面试回答

先区分两套机制：过期删除管“到没到期”（惰性＋定期抽样），内存淘汰管“maxmemory 满了踢谁”。淘汰策略按键范围乘算法组合：noeviction 直接报错；allkeys 系作用于全部 key，volatile 系只作用于带 TTL 的 key；算法有 LRU（近似实现，抽样候选池比较空闲时长）、LFU（8.0 前即存在，按衰减计数频次）、random、TTL 优先（volatile-ttl），另有 allkeys-lrm（最近修改优先，需按版本确认支持）。生产最常用的就是 allkeys-lru 与 allkeys-lfu。要强调 Redis 的 LRU 不是精确链表，而是 `maxmemory-samples` 抽样近似，调大样本更准更耗 CPU；纯缓存场景选 allkeys-*，混存不可丢状态时必须先做键隔离，别指望 volatile-* 兜底。

## Q07：要自己实现一个 LRU，要怎么实现？

### 面试回答

LRU 要同时满足“按访问序淘汰最久未用”和 get／put 都 O(1)，结构就是哈希表＋双向链表：Map 负责 key 到节点的 O(1) 定位，链表维护访问序，任意节点命中后 O(1) 摘出提到头；put 新键时若容量满，删除链表尾节点并同步删 Map。要点在细节：get 也算使用要移动节点；put 已存在键要更新值并移动；手写时把 moveToHead／removeNode 抽成私有方法，边界（头尾指针、单节点）最容易错。Java 里可以说明 LinkedHashMap(16, 0.75f, true) 覆写 removeEldestEntry 是捷径，但面试考的是手写，别只背 API。若追问线程安全，加锁会让热点 get 全序列化，常见做法是分片（如 Caffeine 的思路）或接受近似 LRU。

## Q08：JVM 内存分哪些区域，直接内存由 JVM 管理吗，哪些区域会 OOM？

### 面试回答

运行时数据区分线程私有和共享两类：线程私有有程序计数器、虚拟机栈、本地方法栈；共享有堆和方法区（HotSpot 用元空间承载，跑在本地内存），运行时常量池属于方法区；另外 NIO 的 DirectByteBuffer 用的直接内存不属于 JVMS 规范的运行时区域。直接内存“由谁管”我分两层：它不归 GC 管理堆对象那样管，分配走 Unsafe／native malloc，在堆外；但释放挂在 DirectByteBuffer 这个堆上“ Cleaner（幻影引用）上，对象被 GC 时顺带释放 native 内存，所以是“GC 间接触发、由 JVM 记录用量并以 -XX:MaxDirectMemorySize 限额”，NIO 满时先主动 System.gc() 再重试。能 OOM 的区域：堆（Java heap space，最常见）、虚拟机栈（请求栈深度超 -Xss 时 StackOverflowError，动态扩展场景可抛 OOM）、方法区／元空间（Metaspace，大量动态类或类加载器泄漏）、直接内存（堆外打满或 limit 不足）、native thread（unable to create new native thread，线程数打到 OS 上限）；程序计数器是规范里唯一不发 OOM 的区域。

## Q09：线程池有哪些核心参数，如何设计让高优先级任务先执行？

### 面试回答

ThreadPoolExecutor 七个参数：corePoolSize、maximumPoolSize、keepAliveTime 与 unit、workQueue、threadFactory、handler；任务先扩到核心数、再入队、队满扩到最大、再不行走拒绝策略。要让高优先级任务先执行，改造点就在 workQueue：换成 PriorityBlockingQueue，任务实现 Comparable（优先级为主键、提交序号为次键保证同级 FIFO），入队即按序排列，出队自然先取高优先级。但必须讲三个坑：一是该队列无界，队列不“满”maximumPoolSize 就几乎不生效，扩线程要靠显式 addWorker 或换有界方案；二是只有排队中的任务享受优先级，已经在跑的低优先级任务不会被抢占，要“运行中也让路”得上层调度或双池隔离；三是低优先级任务会饥饿，要有老化提权或给低优先级保底配额。实践里更稳的做法往往是两级池：高优池固定资源直通，普通池限流排队，按业务分级路由。

## Q10：数据库是怎么保证事务的原子性的？

### 面试回答

InnoDB 的原子性靠 undo log。事务修改数据前，先把“改动前的旧值”记成 undo 日志——回滚时按 undo 逆向恢复，把已做的修改逐条撤销；崩溃恢复时，对未提交事务同样用 undo 回滚，效果等价于“要么全做、要么全没做”。顺序上是先写 undo 再改数据页，且都遵循 WAL：真正决定“恢复后从哪重放”的是 redo，redo 保证已提交不丢、undo 保证未提交可撤，两者配合才让原子性和持久性同时成立，提交时事务要走到 redo 落盘（prepare，再配合 binlog 两阶段提交）。可以补一句边界：undo 不是给 MVCC 之外另造一套，版本链就存在 undo 里，回滚与快照读共用这些历史版本，purge 线程要等没有任何活跃快照需要才能清理。

## Q11：MySQL 的读已提交怎么避免脏读，RC 和 RR 的核心差异是什么？

### 面试回答

读已提交避免脏读靠 MVCC 的可见性判断：快照读时沿行内回滚指针走版本链，跳过事务未提交的版本，只取第一个“提交版”在本事务视角已可见的版本，所以别人没提交的东西永远读不到——不需要为此加读锁。注意 RC 也仍然可能读到别的会话刚提交的修改，因为它每条 SELECT 都新建 ReadView。RC 与 RR 的核心差异就是 ReadView 的生成时机：RC 每条语句各建一份，于是同一事务两次重读同一行可能看到新值（不可重复读）；RR 事务内第一次一致性读建一份并复用，重读结果稳定。延伸差异：RR 在当前读路径上额外用间隙锁／next-key lock 抑制同条件结果的插入幻读，锁冲突与死锁风险也更高；RC 无间隙锁、并发好，很多互联网公司选 RC＋row 格式 binlog（RC 与语句格式 binlog 不安全，官方口径）。

## Q12：一堆数中只有一个出现一次、其余都出现两次，如何快速找出它？

### 面试回答

全体异或一遍就是答案。异或满足交换律结合律，且 x^x=0、x^0=x，配对的两个数互相抵消，剩下落单的那个数。时间 O(n)、空间 O(1)，不需要哈希表计数；排序后两两比较也能做但 O(n log n) 且改数据。口述时主动补两点展示深度：若“其余出现三次、一个出现一次”，异或不够，要按位统计后对 3 取模，或用一次遍历的 ones／twos 双掩码状态机；若问“出现一次的两个数”，先全体异或得到两数之差的信息，按结果的某个为 1 的位把数组分成两组分别异或。边界上此法假设“其余恰好两次”的前提成立，前提变了方法就换。

## Q13：对 2 亿个取值在 1 万到 2 万之间的数据排序，怎么实现？

### 面试回答

这是取值范围（约 1 万种）远小于数据量（2 亿）的场景，直接计数排序：开一个长度 10001 的 int／long 数组，流式扫一遍输入，每来一个数对 count[x-10000] 加一；再按值域从小到大顺序扫描计数数组，把每个值重复输出对应次数。时间 O(n+k)，k=10001，两趟完成；额外内存只有几千个计数器，几 KB 到几十 KB，远小于 2 亿数据的任何存储形态。要点是它是稳定排序且天然去重出“值＋频次”。对比口径也备好：不能用 O(n log n) 内存排序是因为 2 亿整条数据放不进内存；若取值范围也大就不能计数，退回分块外部排序或位图（位图只能表达“存在与否”，要保留重复次数还是计数数组）。数字感受：每数约 4 字节共 800MB 输入，计数器侧忽略不计，瓶颈全在 I/O 顺序读。
