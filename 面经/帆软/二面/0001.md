## Q02：Agent 的工具调用链路、Skill 开发、CLI 脚本的设计实现细节？

### 面试回答

按【真实实现】逐条讲三块。

- 工具调用链路：模型输出结构化调用（工具名＋参数）→ 运行时做 schema 校验与鉴权 → 执行器调用 → 结果结构化回传。
  - 讲的时候点三处细节：调用 ID 怎么配对、错误怎么分类（格式错／业务错／执行错）、超时怎么处理。
- Skill 开发：SKILL.md 定义触发条件与流程；长资料放 references，确定性操作放 scripts。拆分依据是真实的触发边界。
- CLI 脚本：它是 Skill 里的确定性执行件。要有明确的参数契约（必填、类型、默认值），退出码和结构化输出供 Agent 解析，而且要幂等、失败可诊断。

最后给一句层次划分：Skill 管方法，CLI 和工具管执行，模型只做决策表达。

## Q03：如何收集 Agent 的用户反馈、做观测监控、评测 Skill？

### 面试回答

分三块说，最后一句把它们串起来。

- 反馈收集：显式和隐式都要。显式是点赞／点踩、修正被采纳；隐式是重新表述、中途放弃、人工接管。两类都要落库，并关联到任务轨迹。
- 观测监控：按 taskId 和步骤 ID 记录模型与工具调用、耗时、token 成本、错误类型、状态转换，再聚合成看板：分位数延迟、成功率、工具失败率。
- Skill 评测：给这个 Skill 建任务集，覆盖正常、歧义、越界三类场景。指标分三个：触发正确率（该用才用）、步骤完成率、产物合格率。真实 bad case 持续回流成回归样本。

串起来的要求：三层数据要能互相下钻——告警 → 轨迹 → 具体步骤。

## Q04：从 Workflow 改造为 LangGraph 中心调度 Agent，改造思路是什么？

### 面试回答

我的顺序是先盘资产，再动结构。

盘资产：

- 列出现有 workflow 每个节点的输入输出、依赖、状态与副作用。
- 标出哪些步骤是确定性代码、哪些是模型调用、哪些需要人工确认。

改造思路：把“中心调度”从硬编码流程改为图。

- 共享 state 承载任务上下文。
- 节点封装原来的步骤，边表达条件流转。
- 循环与重规划在图上显式建模。
- 配置 checkpoint，拿到中断恢复能力。
- 确定性节点保留原实现，不重做。

收益要拿数据说话：分支灵活、可恢复、可观测，用同一任务集对比改造前的成功率、时延与维护成本。

最后一句边界：不是所有流程都值得改，强顺序的合规流程保留编排。

## Q05：科研助手上线大量用户使用，如何搭建观测系统保证系统稳定性？

### 面试回答

面向上线的观测＋稳定性体系，我分四块。

- 全链路追踪：请求 → Agent 循环 → 模型／工具调用，逐层带上 traceId，按采样存下轨迹。
- 指标与告警：按场景分桶看端到端成功率与 P95 延迟，再加模型错误率与限流命中、工具失败率、token 成本、队列积压。上面设 SLO，告警分级。
- 质量监控：抽样做人工评审，配自动断言（引用可核对、格式合法）；版本发布前先跑回归评测集。
- 稳定性手段：入口限流与并发配额、模型多通道 fallback、超预算降级到确定性路径、任务状态外置以支持宕机恢复，再用故障演练验证。

一句话要求：观测数据要能回答“哪个环节、哪类任务在变坏”，而不是只有一堆曲线。

## Q06：项目的向量库分层设计说明，向量数据库选型原因？

### 面试回答

分两层说：先讲怎么分层，再讲怎么选型。

分层设计按【项目实际】讲，常见口径：

- 按业务域或权限分集合（collection）。
- 热库与冷库分开：热库是高频小库，冷库做全量归档。
- 两级检索降候选量：粗索引（文档摘要级）先行，命中后再细查 chunk 级。

选型原因要落到比较过程，不能只报名字：

- 比较维度：数据量与增长、过滤条件复杂度、延迟与召回要求、与现有栈的协同（已有 PG 就先测 pgvector）、运维成本与许可。
- 定论方式：在相同数据集与相同查询分布上对比 Recall@k、P95 和成本，再决定。
- 不引用“某某最快”的榜单结论。

## Q07：Docker 做中间件本地化部署，遇到过什么问题？

### 面试回答

按【真实踩坑】答，常见题材列这几类：

- 容器网络互通与端口映射：服务名解析、bridge 模式下宿主机怎么访问。
- 数据持久化：忘挂 volume，重建容器数据就丢了。
- 平台架构不匹配：arm Mac 上跑 x86 镜像的模拟与选择。
- 资源限制：内存配额导致 OOMKill。
- 时区与字符集差异。
- 依赖版本漂移：镜像 tag 不锁定。
- 启动顺序与就绪探测：应用先于 MySQL 就绪就启动失败，要配 healthcheck 加 depends_on 的条件。

讲每个问题时固定一个结构：现象 → 定位 → 解决 → 预防，预防要写进 compose 或文档。

## Q09：Prompt 的 few-shot、bad case 如何迭代优化？

### 面试回答

流程是“先归因，再改”。

- 归因：这条 bad case 是指令不清、示例误导、缺上下文，还是根本就该由代码或检索解决。
- 再改示例：选覆盖边界的最小集合，正反例成对，格式锚点保持稳定。
- 新示例进 Prompt 之前，先在评测集上验证它不引入回归。

四条纪律：

- 每次只动一类变量，便于归因。
- Prompt 版本化。
- few-shot 的顺序与格式固定——抖动本身就是一个变量。
- 留出未参与调优的样本，防止过拟合到示例上。

## Q10：大模型选型策略？

### 面试回答

一句话：以任务集驱动，不评“哪个模型最强”。

- 先列真实负载：规划、抽取、代码、长文摘要。
- 每类分别测：工具调用的参数正确率、答案质量（rubric 盲评）、P95 延迟、单位成本、上下文窗口需求。
- 再做分配：强模型留给规划与难任务；稳定的简单子任务用小模型或规则，把成本降下来。
- 最后核三件非技术指标：合规（数据出境、私有化）、供应商稳定性、切换成本——经网关抽象后，换模型只改配置。

结论的形式给“场景→选择”，不给单一冠军。项目实际型号按【真实配置】答。

## Q11：PDF 中插图如何处理，后续怎么扩展多模态能力？

### 面试回答

插图处理分两层：

- 原图本身：能提取的就抽出图片文件，同时保留页码、位置和所属章节的上下文。
- 图内的信息：按类型分流。文字型图表走 OCR；流程图、示意图用视觉模型生成描述或结构化数据。文本化之后和图的引用一起入索引——检索命中的是文本，展示时回源原图。

一个坑：纯坐标裁剪会切断图文关联，图注与正文要绑定。

扩展多模态的顺序：

- 先建评测集，把含图任务的基线打出来。
- 再选路线：支持图像输入的模型，或者 OCR＋文本模型的混合链路。
- 指标看三项：含图任务成功率、图像信息提取准确率、延迟与成本增量。

别犯的错：把“支持上传”当成“支持理解”。

## Q13：Agent 框架技术选型，需要分析哪些维度？

### 面试回答

维度清单七条：

- 能力匹配：需不需要循环、分支、并行、人工介入、检查点恢复。
- 状态与持久化模型：是否契合业务。
- 工具与生态：模型兼容、MCP 和函数调用的支持。
- 可观测性与调试成本。
- 部署形态与依赖重量：能否私有化、要引入多少组件。
- 版本稳定性与维护活跃度、许可。
- 团队学习成本与逃生通道：也就是被锁定到什么程度。

方法上别照抄清单：拿 2～3 条真实业务任务在各候选框架做原型跑通，比较开发工时与故障可诊断性，而不是看 star 数排名。

## Q14：分布式场景下乐观锁、synchronized 锁的注意点，死锁、锁超时释放怎么处理？

### 面试回答

先给一个关键前提：synchronized／ReentrantLock 只在单 JVM 内有效。多实例部署时，同一把“本地锁”各锁各的，互斥必须上移到分布式锁或数据库约束。

乐观锁：

- 版本号／CAS 在分布式下天然可用，落地形式就是条件更新。
- 注意设重试上限、监控冲突率；高冲突时会退化成活锁。

分布式锁的两类异常要分开处理：

- 死锁预防：统一加锁顺序、锁分层与超时。
- 锁超时释放，先分清是哪一种。业务还没完成但 TTL 先到：靠看门狗续期，再加 fencing token 防旧持有者写坏。进程崩溃：TTL 自然过期由他人接管，前提是业务必须幂等。

收尾一句：锁只是协调手段，正确性最终靠资源侧的条件写与幂等。

## Q15：Redis 实现分布式锁的思路？

### 面试回答

基本写法：`SET key token NX PX ttl`，一条命令同时完成抢占与租期。

四个细节：

- value 必须是本次持锁的唯一标识，uuid＋线程。
- 解锁用 Lua 脚本，原子地“比对持有者再删除”，防止误删别人的锁。
- 可重入用 Hash 记录持有者与次数，Redisson 就是这么做的。
- 续期靠看门狗。

局限也要说：

- 单实例 Redis 锁在故障切换时可能双持有。强正确性场景要 Redlock 类的多节点方案，或者干脆用数据库条件更新兜底。
- 锁粒度按业务键；再配 fencing token，让资源侧能拒绝已过期的持有者。

## Q16：行式存储与列式存储的区别，适用场景？

### 面试回答

区别就一句：存的时候是按行连续还是按列连续。

- 行式：一整行连着存。读写整行实体快，对事务型 OLTP（点查、更新、插入）友好。代表是 MySQL、PostgreSQL。
- 列式：同一列的值连着存。一列类型相同，压缩率高；分析查询只读需要的列、跳过无关列，聚合扫描快。代表是 ClickHouse、Parquet 这类数仓格式。

各自的代价：

- 列式的更新、删除要重写文件或做合并（LSM 类），不适合高频小事务。
- 行式做大范围聚合要扫全行，I/O 被放大。

最后补一句：实际系统常常混着用，行存主库加定时转出的列存分析副本，这是常见架构。

## Q17：Java 应用响应慢、CPU 负载高怎么排查；CPU 低但负载高如何定位？

### 面试回答

两种情况分开讲。

CPU 高＋响应慢，三步定位：

- `top` 定位高 CPU 进程。
- `top -Hp <pid>` 找热点线程。
- 线程 ID 转 16 进制，再用 `jstack <pid>`（或 arthas 的 thread -n）匹配栈顶。

接着区分三类热点：业务死循环、GC 风暴（结合 GC 日志看，频繁 Full GC 会同时表现为 CPU 高与响应慢）、正则或序列化这类计算热点。容器里还要注意配额与宿主机视角的差异。

CPU 低但负载高，先讲清概念：

- 负载里含不可中断等待（D 状态），所以负载高说明任务在排队，不是在计算。
- 手段：`vmstat` 看 r、b 与 wa；`iostat` 查磁盘；`ps` 找 D 状态线程，常见是 NFS、磁盘或锁等待。
- 还有一种：大量线程阻塞在外部调用，运行队列与积压同时存在。

根因一般在 I/O、依赖慢或线程池配置上，而不是 CPU。
