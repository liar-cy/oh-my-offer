## Q02：Agent 的工具调用链路、Skill 开发、CLI 脚本的设计实现细节？

### 面试回答

按【真实实现】逐条讲。工具链路：模型输出结构化调用（工具名＋参数）→运行时 schema 校验与鉴权→执行器调用→结果结构化回传，讲清调用 ID 配对、错误分类（格式错／业务错／执行错）与超时处理。Skill 开发：SKILL.md 定义触发条件与流程，长资料放 references、确定性操作放 scripts，按真实触发边界拆分。CLI 脚本：作为 Skill 里的确定性执行件——参数契约（必填、类型、默认值）、退出码与结构化输出供 Agent 解析、幂等与失败可诊断。三者的层次：Skill 管方法，CLI/工具管执行，模型只做决策表达。

## Q04：从 Workflow 改造为 LangGraph 中心调度 Agent，改造思路是什么？

### 面试回答

## Q05：科研助手上线大量用户使用，如何搭建观测系统保证系统稳定性？

### 面试回答

## Q06：项目的向量库分层设计说明，向量数据库选型原因？

### 面试回答

## Q09：Prompt 的 few-shot、bad case 如何迭代优化？

### 面试回答

## Q14：分布式场景下乐观锁、synchronized 锁的注意点，死锁、锁超时释放怎么处理？

### 面试回答

关键前提：synchronized／ReentrantLock 只在单 JVM 内有效，多实例部署时同一把“本地锁”各锁各的，互斥必须上移到分布式锁或数据库约束。乐观锁（版本号/CAS）在分布式下天然可用（条件更新），注意重试上限与冲突率监控，高冲突时退化为活锁。分布式锁的异常处理：死锁预防靠统一加锁顺序、锁分层与超时；锁超时释放要区分“业务未完成 TTL 先到”（看门狗续期＋fencing token 防旧持有者写坏）与“进程崩溃”（TTL 自然过期由他人接管，业务必须幂等）。锁只是协调手段，正确性最终靠资源侧条件写与幂等。

## Q15：Redis 实现分布式锁的思路？

### 面试回答

`SET key token NX PX ttl` 一条命令完成抢占与租期；value 必须是本次持锁唯一标识（uuid＋线程），解锁用 Lua 原子地“比对持有者再删除”防误删；可重入用 Hash 记录持有者与次数（Redisson）；续期靠看门狗。单实例 Redis 锁在故障切换时可能双持有，强正确性场景要 Redlock 类多节点方案或干脆用数据库条件更新兜底；锁粒度按业务键，配合 fencing token 让资源侧拒绝过期持有者。

## Q16：行式存储与列式存储的区别，适用场景？

### 面试回答

行式按行连续存：读写整行实体快，事务型 OLTP（点查、更新、插入）友好，代表 MySQL/PostgreSQL；列式把同一列值连续存：同列类型相同压缩率高，分析查询只读需要的列、跳过无关列，聚合扫描快，代表 ClickHouse、Parquet 类数仓格式。代价：列式更新/删除要重写文件或合并（LSM 类），不适合高频小事务；行式做大范围聚合要扫全行 I/O 放大。混合系统（行存主库＋定时转列存分析副本）是常见架构。

## Q17：Java 应用响应慢、CPU 负载高怎么排查；CPU 低但负载高如何定位？

### 面试回答

CPU 高＋响应慢：`top` 定位高 CPU 进程→`top -Hp <pid>` 找热点线程→线程 ID 转 16 进制后 `jstack <pid>`（或 arthas thread -n）匹配栈顶，区分业务死循环、GC 风暴（结合 GC 日志，频繁 Full GC 会同时表现为 CPU 高与响应慢）与正则/序列化类热点；容器里注意配额与宿主机视角差异。CPU 低但负载高：负载含不可中断等待（D 状态），说明任务在排队而非计算——`vmstat` 看 r/b 与 wa，`iostat` 查磁盘，`ps` 找 D 状态线程（NFS/磁盘/锁等待），或大量线程阻塞在外部调用导致运行队列与积压并存；根因常在 I/O、依赖慢或线程池配置，而不是 CPU。
