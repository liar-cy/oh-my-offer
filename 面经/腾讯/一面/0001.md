## Q03：密码加密存储后用户忘记了怎么办？为什么选 MD5＋盐？登录时怎么校验密码正确？

### 面试回答

三问一条线（哈希存储、找回=重置、校验流程），先纠正口径再答：

- “加密存储”实为“哈希存储”：单向、系统还原不出明文。所以“忘记密码”不可能“找回”，只能重置——短信／邮箱验明身份 → 一次性有效链接 → 设新密码并更新盐与哈希、使旧登录态失效。
- 为什么当年选 MD5＋盐：盐随机唯一、随哈希记录存储，能防彩虹表、让同密码不同哈希——这是它“对”的部分。
- 但要主动说出不足：MD5 太快，GPU 离线爆破成本低；现代推荐慢哈希 BCrypt／scrypt／Argon2id（OWASP 口径），加“登录限流＋失败锁定”防在线爆破。
- 登录校验流程：取存储记录里的盐 → 用同一算法重算 `hash(输入密码＋盐)` → 与存储哈希比对（等时比较防时序侧信道）；一致才发登录态。

## Q04：项目里 Redis 用来干嘛、怎么缓存？为什么先更新 Redis 再更新 Caffeine？会有一致性问题吗？

### 面试回答

项目缓存架构题，真实实现【按实际填】，通用口径组织成三层：

- Redis 的角色：【热点数据读缓存／会话／计数器等，按实际】；缓存策略说清 cache-aside：读先查缓存、未命中回源并回填，写走下面的更新流程。
- 为什么“先 Redis、后 Caffeine”：Redis 是跨实例共享层，先写它让“全系统视角”尽早变新；本地 Caffeine 只影响本进程，后刷新、甚至不主动刷而是等短 TTL 自然过期，把跨层写序的影响面缩到最小。
- 一致性问题会不会有：会——两层写入不是原子的，中间窗口内本实例读旧本地值或其他实例读旧 Redis 值。所以正确性不能押在写序上，要靠三件套兜底：失效消息广播（各实例按版本消费）、本地短 TTL、版本号拒绝旧值。
- 收口一句：本地缓存天然只能做到“最终一致＋有界陈旧”，先和业务确认可接受窗口再定参数。

## Q05：怎么定义热 Key、判断依据是什么？访问次数在哪里统计、阈值在哪里比较？分布式多机环境怎么处理？

### 面试回答

- 定义：单位时间访问量显著高于其它 key 的键（秒杀详情、爆款内容、全局配置）；判断依据就是访问频次——按 QPS 统计取 Top-N 与阈值比较，也可看流量占比而非绝对次数。
- 统计位置三档：
  - 业务代码／网关埋点（每个 key 一个计数器，放滑动窗口里）。
  - Redis 侧 LFU 策略自带访问计数（`maxmemory-policy` 设成 lfu 后可用 `OBJECT FREQ`／`--hotkeys` 读）。
  - 云托管的热 Key 实时分析。
- 阈值比较放在聚合侧的统计组件，不放请求路径——判定是运维决策，不该给每次访问加判断开销。
- 分布式多机：
  - 本机计数只反映单机视角，请求被负载均衡打散后热点会被“摊薄假象”。
  - 做法是本地增量计数＋定时合并上报，中心侧（或实时计算组件）滑窗聚合出全局 Top-N。
  - 统计成本高就上采样加 heavy hitter 结构（Count-Min Sketch／Space Saving）压内存。
  - Top-N 结果再下发各实例做本地缓存与告警。
- 补一句处置：发现热 Key 后按“分摊（拆 key／多副本）→ 下沉（本地缓存，注意失效广播）→ 防重建风暴（逻辑过期／互斥）”三招跟进。

## Q07：用 COS 对象存储快速上传一批约 1G 数据，怎么做、考虑哪些点？具体怎么分片？二进制数据怎么按关键字哈希分片？

### 面试回答

- 快速上传的主方案就一句：分片上传（multipart upload）＋有限并发＋失败分片重试。1G 按每片 10～100MB 切成几十到一百片，先建上传会话拿 uploadId，各片独立 PUT，全部确认后 Complete 合并。
- 过程要考虑的点：
  - 片大小与并发数的权衡（片太小请求开销大、太大重传代价高）。
  - 每片带摘要（ETag／MD5）做完整性校验。
  - 断点续传——重传前查已完成片号，幂等跳过。
  - 过期会话与临时片清理。
  - 限速与重试退避，防把网络和服务端打爆。
- 怎么分片：按字节偏移定长切（第 i 片＝[i×size, (i+1)×size)），业务层维护 uploadId＋片号＋校验值三元组；不需要任何语义边界，二进制流定长切分就是标准做法。
- “按关键字算哈希分片”要先纠正：
  - 对象存储分片不按“内容里的关键字”路由——二进制没有天然关键字，也不需要。
  - 若真要说哈希：路由键用元数据（对象名、业务 ID）或整片内容的摘要（content hash，MD5／SHA256 直接对字节算，无需提取关键字）。
  - 后者用于去重与完整性校验，不用于“找分片位置”。
  - 这题考的是别把 KV 分库分表的概念错套到文件分片上。

## Q08：假设每次都上传成功，瓶颈在哪？网络问题包括哪些因素？怎么克服硬件和网络问题？

### 面试回答

- 瓶颈先给上限公式：总耗时 ≈ max(数据量÷有效带宽, 磁盘读取时间)——客户端上行带宽几乎总是第一瓶颈，多连接并发只能逼近它，超不过它。
- 其余瓶颈排一遍：
  - 本地磁盘顺序读（一般快于上行，但机械盘混随机读会拖）。
  - 单条 TCP 连接吞吐受带宽时延积限制（窗口×MSS÷RTT），所以要并发多连接。
  - TLS 加解密 CPU。
  - 对象存储侧单请求与合并开销、服务端限流。
- 网络问题的构成：带宽不足、丢包（触发重传与拥塞窗口收缩）、RTT 高（跨境尤其明显）、乱序、运营商／防火墙限速与抖动。
- 克服手段按“绕过、摊薄、恢复”三类：
  - 绕过——就近接入点／传输加速域名、边下边传。
  - 摊薄——多连接分片并发、连接池复用。
  - 恢复——分片级断点续传、超时与指数退避重试、完成后整文件摘要校验，任何一片坏了只补那一片。

## Q09：什么情况下会产生丢包？丢包后 TCP 怎么处理？

### 面试回答

丢包的成因分两类记：

- 网络侧：
  - 拥塞时路由器／交换机缓冲队列溢出被主动丢弃（大头）。
  - 链路误码（无线干扰、线缆质量）导致校验失败被丢。
  - 防火墙／限速器按策略丢弃。
  - 路由或 ARP 异常把包送进黑洞。
- 主机侧：网卡环形缓冲区来不及收（overrun）、内核软中断处理不过来，包在最后一米被丢。
- 丢的是数据还是 ACK 后果不同：丢 ACK 只是让发送方提前重传一份还在正常飞的数据。

TCP 的处理主线是“检测＋重传＋退让”：

- 检测：重复 ACK 触发快速重传（现代实现还有 RACK／SACK 等更精细的丢失判定，别背成“必是三个重复 ACK”）；更严重场景回退到重传超时 RTO。
- 恢复：丢包后拥塞窗口收缩（快恢复／超时后从慢启动再来），用带宽信号反推安全速率；SACK 让重传只补缺失段而不是整窗。
- 应用层还要接住：传输总时长不可控，所以大文件要分片续传＋幂等重试，别让一个丢包拖崩整条业务链路。

## Q10：单核机器同时执行多个程序为什么不卡住？死循环程序会怎样、操作系统自己会怎么处理？

### 面试回答

- 不卡住的原因：并发不是并行——单核靠调度器做时间片轮转，周期性时钟中断把 CPU 强制收回，再上下文切换到下一个 runnable 进程；切换是微秒级，宏观上就像同时运行（切换保存的内容见 OS-009）。
- 用户态死循环的现象：该进程每轮都“用满自己的时间片”，CPU 占用率顶到 100%，整机变卡但没死——其它进程照样按调度获得时间片，只是分到的份额和响应都变差。
- 操作系统自身怎么处理：
  - 不会主动杀它——用户态死循环在内核看来只是个正常的 CPU 密集任务，调度器的公平性（Linux CFS 按虚拟运行时间均衡）就是防线。
  - 出现高优先级任务可随时抢占。
  - 没有“程序跑太久”的异常判定，OOM 也管不到它（占的是 CPU 不是内存）。
- 例外要说全：死循环发生在内核态且不经过调度点，会威胁整机响应——watchdog 机制检测 soft lockup 并打告警，按内核配置可 panic 重启自救；用户态“跑飞”的处置则交给运维手段（nice 降优先级、人工终止），操作系统不替你写正确代码。
