## Q01：手撕（核心代码模式）：力扣 88．合并有序数组

### 面试回答

结论：原地合并一定“从后往前”——nums1 尾部有 m+n 长度的空位，双指针从两个数组的末尾起，把较大者填到写指针，被取的指针前移。

- 为什么不能从头往前：从前往后写会覆盖 nums1 里还没读走的元素；尾部空位才是安全区。
- 终止条件：`p1 < 0` 时 nums2 剩余本就就位，可提前返回；只需把 nums2 剩下的搬过来。
- 核心代码模式只写方法体：不处理输入输出，边界（nums2 为空、m=0）仍要口述自查。
- 复杂度：时间 O(m+n)、空间 O(1)；用额外数组的 O(m+n) 空间解法先提一句再说明为什么不用。

## Q04：synchronized 和 ReentrantLock 的区别

### 面试回答

结论：两者都可重入、都提供互斥与可见性；差别在“语言级自动管理”与“API 级显式控制”。

- 用法：synchronized 修饰代码块／方法，退出自动释放；ReentrantLock 必须 `finally` 里 `unlock()`，忘了就是死锁隐患。
- 多出来的能力：可中断获取（`lockInterruptibly`）、限时尝试（`tryLock`）、公平锁选项、多个 Condition 精准唤醒——需要才选显式锁。
- 实现层面：synchronized 走监视器（对象头 Mark Word，锁状态经偏向／轻量级到重量级，偏向锁在新版本已弱化）；ReentrantLock 基于 AQS，state 加 CLH 队列管理等待。
- 选型一句话：普通互斥用 synchronized 写法清晰；要超时、要公平、要分组唤醒才上 ReentrantLock。

## Q05：JVM 内存区域怎么划分？哪些区域可能发生 OutOfMemoryError？

### 面试回答

结论：线程私有三块＋共享两块，除程序计数器外都可能 OOM。

- 线程私有：程序计数器（规范里唯一不抛 OOM 的区域）、虚拟机栈（超 `-Xss` 一般 StackOverflowError，动态扩展失败才 OOM）、本地方法栈。
- 线程共享：堆（`Java heap space`，对象分配与 GC 主战场，分年轻代／老年代）、方法区（Metaspace，`MetaspaceSize` 打满或类加载器泄漏）。
- 再补一句堆外：直接内存不在规范区域内，但超 `MaxDirectMemorySize` 同样 OOM；native 线程创建失败（`unable to create new native thread`）也算进程层面的内存问题。
- 若被问“JVM 内存模型”，先确认是运行时区域还是 JMM，别混答。

## Q06：用过哪些 GC 回收器？各有什么特点

### 面试回答

结论：按“吞吐优先→停顿优先”的演进线报，用过哪个重点讲哪个。

- Serial／Parallel：单线程／多线程、全程 STW，吞吐优先；Parallel 适合批处理与中小堆。
- CMS：
  - 并发标记清除，第一次把停顿压到几十毫秒。
  - 代价是碎片、浮动垃圾与 Concurrent Mode Failure。
  - JDK 9 废弃、JDK 14 移除。
- G1：Region 化堆＋停顿预测模型（`-XX:MaxGCPauseMillis`）＋Mixed GC，JDK 9 起默认；大堆通用之选。
- ZGC：着色指针＋读屏障，几乎全并发，停顿亚毫秒且不随堆增长；JDK 15 生产可用，JDK 21 加分代。
- 口径：说“用过”就给场景与参数（堆大小、选中原因、调了什么），没用过的如实说只了解原理。

## Q07：Java 中 Exception 和 Error 的区别

### 面试回答

结论：都继承 Throwable；Error 是 JVM 自身 problems（不该捕获也恢复不了），Exception 是程序可处理的异常。

- Error：OutOfMemoryError、StackOverflowError、UnknownError——发生时应重启／扩容／修代码，不该 try-catch 吞掉。
- Exception 再分两支：受检（IOException、SQLException，编译器强制 catch 或 throws）与非受检（RuntimeException 子类：NPE、越界、ClassCastException，不强制）。
- 处理原则：受检异常在调用处当场表态（重试／降级／上抛）；编程错误靠前置校验避免，靠全局异常处理器统一兜底，别到处 catch 吞。
- 自定义异常：继承 Exception 做受检、RuntimeException 做非受检；带上原因链（`new XxxException(msg, cause)`），别丢栈。

## Q08：服务程序明显变慢、运行吃力，诊断思路是什么？

### 面试回答

结论：先分层定位“慢在哪一类资源”，再进进程内找代码——顺序是系统层→进程层→JVM 层→依赖层，忌一上来就 dump。

- 系统层：`uptime` 看负载趋势，`top`／`vmstat 1` 分 CPU（us／sy／wa）、`iostat -x 1` 看磁盘 util 与 await、`free -h`＋`sar` 看内存与换页、`ss -s`／`ping`／`mtr` 看网络。
- 进程层：`top -Hp <pid>` 找高 CPU 线程，线程号转 16 进制后在 `jstack` 里对号入座；GC 嫌疑先 `jstat -gcutil <pid> 1000` 看 FGC 频率与耗时。
- JVM 层：
  - CPU 高看热点线程与火焰图（Arthas `thread -n 3`／async-profiler）。
  - 内存涨看堆直方图（`jmap -histo`）与 MAT。
  - 卡顿看 GC 日志停顿分布。
- 依赖与变更：慢 SQL（`SHOW PROCESSLIST`＋EXPLAIN）、下游 RT 与连接池排队、缓存命中率——同时先问“最近上没上线／改没改配置”，90% 的变慢对应一次变更。
- 收口补一句：先恢复（扩容／回滚／限流）再根因，止损优先级高于找答案。

## Q09：主键等值查询，select * 和 select id 效率一样吗？为什么？

### 面试回答

结论：不一样，但原因常被说错——两者都走聚簇索引主键等值定位，都不存在二级索引回表；差距主要在“取哪些列”带来的成本。

- 定位成本相同：主键等值都沿 B+ 树找到唯一叶子行。
- 差异一：`select *` 要读整行（溢出列还要追 LOB 页），页内解析、结果集序列化与网络传输都变大；`select id` 的行极窄，一次能扫进 buffer pool 更多行。
- 差异二：走二级索引时差距更明显——`select id` 可被覆盖索引免回表，`select *` 必须回表，这才是“回表”话题的正确打开方式。
- 结论收口：列少而窄利于覆盖与批量吞吐；`SELECT *` 还带来“加字段就改变查询行为”的维护风险，所以按列取。

## Q10：MySQL 如何快速复制一张表（结构＋数据）？

### 面试回答

结论：两条语法两条路——`CREATE TABLE ... LIKE` 完整复制结构但无数据；`CREATE TABLE ... SELECT` 复制数据但丢索引／主键／AUTO_INCREMENT。

- 结构＋数据一步到位的正确组合：`CREATE TABLE t2 LIKE t1;` ＋ `INSERT INTO t2 SELECT * FROM t1;`——索引、主键、自增都在。
- 只 `CREATE TABLE t2 AS SELECT * FROM t1`：所有列变成普通列，二级索引与主键丢失，大表下写入还是无日志的快速装载路径——用它做备份要心里有数。
- 跨库同步结构：`SHOW CREATE TABLE` 取 DDL，改表名后执行，再导数据（mysqldump／SELECT INTO OUTFILE 适合大表离线搬）。
- 大表注意：复制期间会长时间占 IO 与锁资源，低峰执行；纯结构复制可加 `WHERE 1=0`。

## Q11：MySQL 什么时候会用到内部临时表？

### 面试回答

结论：计划里出现 `Using temporary` 就是内部临时表——排序／分组无法用索引顺序完成、或要先物化中间结果时产生。

- 典型场景：`GROUP BY` 与 `ORDER BY` 用了不同列集合、分组列无合适索引、`DISTINCT`＋排序、`UNION`（非 ALL）、派生表／CTE 物化、窗口函数按 frame 计算。
- 存取引擎：默认先放内存（TempTable 引擎，受 `temptable_max_ram` 约束，可超进程内存），装不下转 InnoDB 临时表（落本地盘，datadir 下的临时表空间）。
- 怎么确认：EXPLAIN 的 Extra 字段；运行中可看 `Created_tmp_disk_tables` 与 `Created_tmp_tables` 的增量，比例高就是磁盘临时表太多。
- 优化方向：给分组／排序列建合适索引（能覆盖更佳）、减少 `SELECT *`、改写 SQL 让 UNION ALL＋显式去重、控制窗口函数分区列的数据量。

## Q12：主存 100G，对 200G 的表做全表扫描，会吃光内存吗？为什么？

### 面试回答

结论：不会——MySQL 不会把 200G 装进内存，扫描是流式的；内存上限由缓冲池等几块结构性配置决定，不由表大小决定。

- 扫描方式：InnoDB 全表扫描沿聚簇索引逐页读取，server 层按行取回、逐批发给客户端（JDBC 也有 fetchSize；MySQL 客户端默认逐行流式接收），不存在“整表驻留”。
- 缓冲池：`innodb_buffer_pool_size` 固定容量＋LRU（全扫描用热端插入防污染），页进页出有上限，不会按表大小膨胀。
- 会涨的部分有界：连接级缓冲（`read_rnd_buffer_size` 等）、排序／临时表（超阈值落盘成临时文件）、客户端结果集缓存——客户端把 200G 结果全 fetch 进内存才是真风险点，所以要 LIMIT 或流式消费。
- 提醒：扫描期间 buffer pool 被冷数据冲刷、预热缓存失效，性能“抖”不等于内存“光”。

## Q13：mvn compile、package、install 三个命令的区别

### 面试回答

结论：它们是同一条生命线上的三个先后阶段，区别＝“构建到哪一步、产物放哪”。

- 生命周期顺序：`validate → compile → test → package → verify → install → deploy`，执行后面阶段会自动先跑前面阶段。
- compile：只编译主代码到 `target/classes`，不打包。
- package：编译＋跑测试＋打成 jar／war 到 `target/`。
- install：在 package 之后，把产物＋pom 装进本地仓库（`~/.m2/repository`），其他本地项目才能依赖它——多模块联调最常用到的一步。
- 补一句：deploy 才推到远程仓库（私服／Nexus），三者都不改源码、只是构建深度不同。

## Q14：-DskipTests 和 -Dmaven.test.skip=true 的区别

### 面试回答

结论：一个“跳执行”，一个“连编译都跳”——`-DskipTests` 仍编译测试代码只是不运行；`-Dmaven.test.skip=true` 测试代码根本不编译。

- `-DskipTests`：surefire 跳过运行，但 `src/test/java` 会编译——测试代码有编译错误会暴露出来。
- `-Dmaven.test.skip=true`：编译插件跳过测试源码，测试相关完全不参与——更快，但测试代码烂在锅里也不知道。
- 生产口径：CI 上两个都不该长期用；临时构建加速用 `-DskipTests`，它保留测试编译这一层保护。
- 顺手可报的相关参数：`-Dtest=XxxTest#method` 只跑指定用例，比全跳更克制。

## Q15：了解过 K8s 吗？

### 面试回答

结论：如实定档——“用过／了解概念”都行，能按“解决什么问题＋核心对象”讲一层就不虚。

## Q16：项目用的哪种消息队列？为什么选它而不是其它 MQ？

### 面试回答

结论：选型没有“最好”，按“场景匹配度”答——报自己用的那个，再给两个放弃理由。

- 用 RabbitMQ：【业务消息量级不大、要灵活路由（exchange）与低延迟】，Spring AMQP 生态开箱即用；放弃 Kafka 是日志型吞吐用不上、消息消费即走不需回溯。
- 用 Kafka：【埋点／行为流高吞吐、要分区有序与回放】；放弃 RabbitMQ 是路由模型不匹配流式重放。
- 用 RocketMQ：【事务消息、顺序消息、电商级削峰】；注意生态与运维熟悉度。
- 每个答案都补一句可靠性落地（持久化＋手动 ack＋死信／重试），证明不是只会报名字；追问“积压怎么办／会不会重复消费”时接 SYS-005／SYS-048 口径。
