## Q02：Spring 框架常用的注解有哪些？

### 面试回答

报名单没有区分度，按用途分类讲、并且每类带一句机制会更稳。

- 容器与配置：`@SpringBootApplication`（＝`@EnableAutoConfiguration`＋`@Configuration`＋`@ComponentScan`）、`@Configuration`／`@Bean`、`@Component` 及派生的 `@Service`／`@Repository`／`@Controller`、`@Import`、`@Conditional*`、`@PropertySource`。
- 依赖注入：`@Autowired`（按类型，可配 `@Qualifier`）、`@Value`、`@Resource`（按名）。
- Web 层：`@RestController`／`@Controller`、`@RequestMapping` 与派生的 `@GetMapping` 等、`@PathVariable`、`@RequestBody`、`@RequestParam`、`@Valid`。
- 面向切面与事务：`@Aspect`／`@Around` 等、`@Transactional`。注意自调用与传播行为会决定它是否生效。
- 生命周期与顺序：`@PostConstruct`／`@PreDestroy`、`@Lazy`、`@Primary`、`@Order`。
- 其他常配的：`@Cacheable`、`@Async`、`@ConfigurationProperties`；测试侧的 `@SpringBootTest`／`@MockBean`。

收尾给一句自己的判断标准：注解只是声明式外衣，真正要掌握的是它在哪个扩展点被谁处理。比如 `@Autowired` 由 `AutowiredAnnotationBeanPostProcessor` 处理，`@Transactional` 靠代理。不这样记，遇到“为什么我的注解不生效”就答不出。

## Q03：@Autowired 的底层原理；实现时怎么通过反射获取成员变量、用哪个反射方法取 Field、又用哪个方法检查它是否被 @Autowired 标记？

原题 3—6 是同一条实现链的连续追问（原理→怎么拿到成员变量→用哪个反射方法→用哪个方法判断注解），合并为一题。

### 面试回答

先说原理链路，再落到反射的三个具体问题，最后备好“自己实现一个最小版”的答法。

原理：`@Autowired` 由 `AutowiredAnnotationBeanPostProcessor`（一个 `InstantiationAwareBeanPostProcessor`）实现，介入时机是 Bean 实例化之后、属性填充阶段。

- 它的 `postProcessProperties` 拿到该 Bean 的注入元数据，逐个元素解析依赖并写入。
- 解析依赖时把字段包装成 `DependencyDescriptor`，交给 `DefaultListableBeanFactory.doResolveDependency` 按类型查找候选。
- 多候选时依次用 `@Qualifier`、`@Primary`、优先级和字段名回退匹配。
- `required=true` 且找不到，就抛 `NoSuchBeanDefinitionException`。
- 结果再回填到字段上。
- 构造器注入不在这一步，它在实例化阶段由容器选择构造器完成。

落到反射的三个具体问题：

- 怎么拿成员变量：`clazz.getDeclaredFields()` 取本类声明的字段，含私有、不含父类。父类字段要沿继承链向上遍历，Spring 内部用 `ReflectionUtils.doWithFields` 做这个遍历。
- 用哪个反射方法：就是 `Class#getDeclaredFields()`，拿到的是 `java.lang.reflect.Field`。方法注入用 `getDeclaredMethods()`，构造器用 `getDeclaredConstructors()`。
- 怎么判断被注解标记：`field.isAnnotationPresent(Autowired.class)`。Spring 实际用的是 `AnnotationUtils.findAnnotation(field, Autowired.class)`，因为它还要支持元注解（自定义注解里再标 `@Autowired`）与合成注解，而 `isAnnotationPresent` 只看直接标注。

还有两个实现细节：

- 写值前要 `field.setAccessible(true)`（Spring 封装为 `ReflectionUtils.makeAccessible`），否则给私有字段赋值不了；最后一步是 `field.set(bean, value)`。
- 性能上它不会每次反射扫描：首次解析后把字段／方法集合缓存成 `InjectionMetadata`，之后只是遍历缓存做注入。

若被反问“自己实现一个最小版怎么做”：

- 容器启动后遍历 Bean 的 `getDeclaredFields()`，对 `isAnnotationPresent` 命中的字段按名称或类型从 Bean 定义表里取实例，`setAccessible` 后 `set` 进去即可。
- 但要补上循环依赖：字段注入能靠提前暴露对象解决，构造器注入不能。
- 还要补限定符与 `@Primary` 的仲裁，以及代理对象与注解元数据的兼容处理。

## Q04：请讲一下 Spring 中一个 Bean 的生命周期。

### 面试回答

以单例 Bean 为主线，讲六段：

- 元数据与实例化：读 Bean 定义，推断或选定构造器创建实例。构造器注入在这一步完成。
- 属性填充：`BeanPostProcessor` 介入，`@Autowired`／`@Value` 在这里写入。循环依赖也在这一步靠三级缓存提前暴露对象解决。
- Aware 回调：容器把自身资源交给 Bean，`BeanNameAware`、`BeanFactoryAware`、`ApplicationContextAware` 等按顺序回调。
- 初始化前：走 `BeanPostProcessor#postProcessBeforeInitialization`；`@PostConstruct`、`InitializingBean#afterPropertiesSet`、自定义 `init-method` 依次执行。前三者时机不同，`@PostConstruct` 在属性填充后、初始化回调里最先。
- 初始化后：走 `postProcessAfterInitialization`。AOP 代理通常在这里生成并替换原对象——这也是“自调用绕过代理”会失效的原因。
- 使用与销毁：容器关闭时执行 `@PreDestroy`、`DisposableBean#destroy`、`destroy-method`。

再补三点显示深度：

- 原型 Bean：容器只负责创建与装配，不管理销毁。
- 代理替换：同一个 Bean 的代理可能在初始化前后被替换，注入到别处的应是最终对象。这也是三级缓存里 `getEarlyBeanReference` 存在的原因。
- 定位思路：看异常发生在哪一段。实例化失败多在构造与依赖解析阶段；`BeanCurrentlyInCreationException` 是循环依赖；属性为 null 常是走了 `new` 而不是容器创建。

## Q05：谈谈你对 JVM 调优的理解，有哪些常见的调优参数或方法？在启动命令中调整 JVM 参数怎么做？

原题 8—9 同属“JVM 调优与参数落地”，合并为一题。

### 面试回答

先把调优定成“从现象出发、有目标的实验”，而不是背参数清单。

目标只有三类：吞吐、停顿、内存占用。三者互斥，得先明确这次要牺牲什么。

现象分三类，对症下药：

- GC 频繁或停顿长：查堆大小与年轻代比例、收集器与目标停顿（`-XX:MaxGCPauseMillis`）、是否有大对象与过早晋升、是否存在内存泄漏（老年代只涨不降）。
- OOM 与内存账：分清纯堆 OOM、元空间（`MaxMetaspaceSize`，常见于动态类／代理膨胀）、堆外与直接内存（`MaxDirectMemorySize`、Netty）、线程栈累加（`Xss × 线程数`）。容器里还要看 RSS 与 limit 的差值，判断是不是被 OOMKilled。
- 线程与延迟毛刺：看 GC 线程数（`ParallelGCThreads`／`ConcGCThreads`）、safepoint 与业务锁竞争。

方法上固定一个顺序：开 GC 日志与监控 → 复现或取一段现场 → 定位是哪类问题 → 改一个参数 → 对比同一指标。一次只动一个变量。

落地到启动命令，两条规则：

- 所有 JVM 参数必须放在 `-jar` 或主类之前，例如 `java -Xms4g -Xmx4g -XX:MaxMetaspaceSize=512m -Xss512k -XX:+UseG1GC -XX:MaxGCPauseMillis=200 -XX:ParallelGCThreads=8 -Xlog:gc*:file=logs/gc.log:time,uptime:filecount=5,filesize=20m -jar app.jar`。
- JDK 9 之后 GC 日志统一用 `-Xlog`，`-XX:+PrintGCDetails` 那套已废弃。

工程上通常不写死在命令行，而是走环境变量：

- 脚本里的 `JAVA_OPTS`／`JAVA_TOOL_OPTIONS`；后者会被 JVM 自动拾取，容器与部分中间件启动器常用。
- 或者 Dockerfile 的 `ENTRYPOINT ["sh","-c","java $JAVA_OPTS -jar app.jar"]`。
- 容器里更推荐 `-XX:MaxRAMPercentage=70`，按容器内存比例给堆，而不是硬写 `Xmx`，这样换规格时不用再改参数。

改完要验证：

- 用 `jcmd <pid> VM.flags` 看参数是否真的生效。
- 用 `jstat -gcutil` 与 GC 日志看效果。
- 还要清楚多数参数只在启动时读取、运行期不能随意改。能动态调整的只是少数，如 `jcmd GC.heap_hint` 或某些诊断命令，所以调优要留发布或重启窗口。

## Q06：ThreadLocal 是什么、底层原理如何，可能导致什么问题？

原题 10—11 同属 ThreadLocal 话题（定义与底层原理、可能导致的问题），合并为一题。

### 面试回答

一句话：ThreadLocal 提供“每个线程一份变量副本”的线程封闭手段。

先看数据到底存在哪：

- 不存在 ThreadLocal 对象里，而是存在每个 `Thread` 自身的 `threadLocals` 字段中，那是一个 `ThreadLocalMap`。
- key 是指向 ThreadLocal 实例的弱引用 `Entry`，value 是实际值。
- 读写时以 ThreadLocal 的哈希值（内部递增的哈希增量，散列均匀）对表长取模定位下标。
- `ThreadLocalMap` 用开放寻址的线性探测解决冲突，而不是链表；探测时会顺手清理 key 已被回收的过期槽位。
- set 不走同步，因为整张表只属于当前线程。这也是它“快”的原因，同时是它隔离性的来源。
- `get` 慢路径才回退到 `getMap` 重建；父子线程传递靠 `InheritableThreadLocal`，在创建子线程时复制。

会导致的问题有五条：

- 内存泄漏：线程长期存活时，key 被回收后 Entry 的 value 仍被强引用链（Thread→ThreadLocalMap→Entry→value）拖住，只有再碰到该槽位时才被清理。所以要 `finally { remove(); }`。
- 脏数据与串上下文：线程池复用线程，上一个请求没清干净，下一个请求就读到旧值。Web 场景里就是用户身份串号，比泄漏更致命。
- `InheritableThreadLocal` 在池化线程上只在线程创建时复制一次，池复用就不生效。要显式在任务提交时捕获、在执行时回放。
- 值本身的可见性与副本语义误解：子线程拿到的是同一对象引用，改内部状态仍会互相影响。
- 数量与生命周期：大量短命 ThreadLocal 会让表膨胀、探测成本上升。

落到实践：只在“线程封闭”时用，比如连接、会话上下文、格式化工具；跨线程共享状态改用并发容器或显式传参。

## Q07：MySQL 和 Elasticsearch 有什么区别、各自适用什么场景；ES 为什么要用倒排索引，相比顺序扫描好在哪？

原题 12—13 同属“MySQL 与 ES 的分工与 ES 为什么用倒排”这一话题，合并为一题。

### 面试回答

先定关系：两者职责不同，不是替代关系。

- MySQL：事务型主存。行存储、B+ 树索引、强一致与唯一约束，负责写与业务真相。
- ES：文档型检索与分析引擎。倒排索引＋列式的 doc values，负责全文检索、任意字段组合过滤、相关性排序、高亮和聚合统计。代价是没有事务、写入近实时（refresh 后才可搜）、更新要重写段。

选型口径一句话：写和真相放 MySQL，读模型与搜索放 ES。两者用 binlog／CDC 同步，并接受秒级延迟。

再答 ES 为什么必须用倒排：

- 检索语义是“给词找文档”。正排（文档→词）与 B+ 树只擅长精确与前缀匹配。
- 多字段任意组合的搜索如果靠 B+ 树，要么索引数量爆炸，要么退化成 `LIKE '%kw%'` 的顺序扫描。
- 顺序扫描的问题是三重的：无法用索引、代价随数据量线性增长、拿不到分词／词频与位置信息。因此也就无法算 BM25 相关性、做高亮和“匹配度排序”。
- 倒排索引把词项字典映射到 posting list（按 doc id 升序，可双指针求交集、delta 编码压缩），查询代价与结果集规模相关，而不是与全表行数相关。

最后把倒排自己的代价也说全：

- 建索引与段合并吃 IO 与 CPU。
- 近实时而非立即可见。
- 深分页与高基数聚合耗内存。
- 不适合做业务主存储。

## Q08：项目为什么选 PGVector 而不是 ES 做向量数据库，ES 可以吗？

未记录候选人当时给的选型理由与真实数据量，以下给可复用的答法框架，数字与实现按【真实情况】填。

### 面试回答

先承认“ES 可以”：

- ES 支持 `dense_vector` 字段与 kNN 近似检索（HNSW），也能用 `script_score` 精确算分。
- 它还自带 BM25，做“关键词＋向量”的混合检索是它的强项。

再讲选 pgvector 的理由，重点不在性能，在架构成本：

- 元数据与向量同库：文档、权限标签、版本与向量放在一张表里，一次 SQL 就能“过滤＋近邻检索”。行级权限（RLS）和 join 天然可用，不必维护两套存储的同步一致性。
- 事务与幂等：写入与更新在一个事务里完成，向量与原文不会分叉。
- 运维：项目本来就有 Postgres，不额外引入集群、分片与映射链路。
- 量级：【真实规模，如数万到数百万条向量】在 pgvector 的 HNSW／IVFFlat 能力范围内。QPS 与召回指标达标，就没必要为“可能变大”提前上重型组件。

同时给出会换掉的边界，显示知道自己选型有代价：

- 向量规模到千万到亿级、需要多副本分片与高并发写入、要 GPU 或极致低延迟。
- 或者必须与已有的 ES 全文检索集群合并成一个链路。
- 这时 pgvector 会先撑不住，更倾向 Qdrant 一类专用向量库，而不是把 ES 同时当全文与向量两套用。

被追问“pgvector 的坑”就答实测：索引构建耗时与内存、默认参数下召回不足、大表上 HNSW 建立期间写入放大，以及换 embedding 模型要全库重建。

收一句：真实结论要用同批评测集上的召回与延迟数据支撑，而不是“听说它更快”。

## Q09：谈谈对 RAG 的理解，它主要解决了哪些问题？

### 面试回答

先说机制：RAG 是把外部证据检索接到生成前面。

- 离线：整理知识，做解析、切块、索引。
- 在线：检索改写后的问题，召回、过滤重排、组装上下文，再让模型依据证据作答并给引用。

它主要解决四个问题：

- 知识截止与时效：模型参数里的知识会过期，换文档比重训便宜得多。
- 私域与长尾知识：公司内部文档、规范、代码，这些模型没见过。
- 幻觉与可追溯：要求结论有证据、能给出来源；答不出时应明确拒答而不是编。
- 上下文与成本约束：不可能把全部资料塞进窗口，检索把有限预算花在相关片段上，同时可按权限过滤来源。

另外，权限与可审计（哪些用户能看到哪些资料）常被算作第五个价值。

边界要一起说清，否则会被判“只会说好处”：

- RAG 不保证消除幻觉：证据在场时，模型仍可能曲解或引用不支持结论。
- 它不提升多跳推理能力，需要 Agent 式迭代检索（Deep Search）来补。
- 召回质量是上限：索引、切块与数据治理做不好，换更强的生成模型也救不回来。

效果要分层评测：

- 检索层看 Hit@k／Recall@k。
- 生成层看忠实度与引用支持率。
- 端到端再算延迟与成本。
- 别把“答案看起来顺”当作效果。

## Q10：手撕八皇后问题；追问：时间复杂度是多少？

未记录现场写的语言与是否写完；以下给回溯＋布尔数组标记的标准解法与复杂度口径。

### 面试回答

解法是按行递归。

- `dfs(row)` 时枚举每一列 `col`，判断该位置是否被已放置的皇后攻击：列、两条对角线。
- 三条约束各用一个数组标记，就能 O(1) 判定：列用 `col` 本身；同一条“主对角线”上 `row - col` 为常数，偏移 n-1 处理负数；另一条“副对角线”上 `row + col` 为常数。
- 放下子皇后，递归到 `row+1`；回溯时把三个标记清回去；`row == n` 时收集一个解。
- 写完自测：`n=4` 有两个解、`n=8` 有 92 个解。
- 还要注意棋盘表示方式：输出方案时，按题目要求给字符矩阵还是列下标数组。

时间复杂度答 O(n!)：

- 逐行放皇后，第一行最多 n 个选择，第二行受列约束至多 n-1，依次递减，所以上界是 `n!`。再乘每个解的拷贝与判定成本。
- 若不做任何剪枝、按“每格都可放”建模，则是 `O(n^n)`。要说清上界收紧靠的是列与对角线的剪枝。

空间：O(n) 量级的标记数组，加上递归栈深度 n，不计输出；若要存全部解，就是解的数量级。

被继续追问可以再补两点：

- 位运算：把三个标记压成整型掩码，每行用可用位集合 `bits` 逐个取最低位，可显著加速。
- 对称性剪枝：只把第一行皇后放在前半列，解数减半后乘回来。
