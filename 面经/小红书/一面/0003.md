## Q03：Java 的 GC 有 Stop the World，为什么要有 STW 机制？

### 面试回答

结论：GC 要在一个“对象图不断被修改”的系统上做全局判断和搬移，STW 是买一个一致的时间切面——停下来，活对象集合与引用关系就不会在扫描／移动中途变化，判断和搬迁才可能正确。

- 没有 STW 的两个死结：标记时引用边在增删，会出现漏标（对象被错误回收）或错标；复制／整理时对象正被应用线程读写，搬一半的现场无法自洽。
- 各回收器做的就是“把 STW 变小变少”，而不是取消它：
- 标记阶段：并发标记＋SATB／增量更新修正确保不漏标，只在初始标记、最终标记两个短停顿点核对根与修正集。
- 搬移阶段：G1  evacuate 仍在 STW 内做（所以停顿随存活对象规模涨）；ZGC 用着色指针＋读屏障把搬移也做成并发，代价落在屏障指令上。
- 停顿的组成也说清：根扫描（线程栈、JNI 全局引用这些“外部引用源”）没法并发省掉，只能缩短扫描范围——这是所有收集器 STW 不归零的底线之一。
- 一句话收束：STW 是“正确性的买价”，回收器演进的主线就是压缩这笔买价（分代把范围缩小、并发化把阶段搬出去）。

## Q04：谈谈 Serial GC、G1、ZGC；G1 已经不错了，为什么还要 ZGC？

### 面试回答

结论：三者是一条“停顿怎么付”的演进线——Serial 全程停、单线程，适合小堆；G1 分 Region、按停顿目标挑选价值最高的区域回收，停顿可控但搬移仍要停；ZGC 把搬移也并发化，停顿亚毫秒且不随堆大小增长。

- Serial（含 Serial Old）：单线程、全堆 STW；简单省内存，客户端／容器小堆与批处理场景仍有效。
- G1（JDK 9 起默认）：Region 化堆＋Remembered Set；`-XX:MaxGCPauseMillis` 目标驱动，优先回收垃圾最多的 Region；Young GC＋Mixed GC 两形态。
- G1 的停顿下限：它把“选哪些区”变聪明了，但复制存活对象的 evacuate 阶段仍在 STW 里做——大堆／高存活对象时停顿会到百毫秒级，且随堆大小增长。
- ZGC：着色指针（指针里借位存标记状态）＋读屏障，标记、搬移、引用修正全与应用并发；停顿基本恒定亚毫秒、支持 TB 级堆；JDK 15 转正、JDK 21 加分代版补吞吐短板。
- 代价对比：并发化不是免费——屏障与并发线程吃 CPU、吞吐下降、内存占用（转发表／视图），所以吞吐型批处理选 Parallel 族而不是 Z。
- 版本口径：Serial／Parallel→CMS（已移除）→G1（默认）→ZGC 分代，一句话串起演进主线。

## Q05：订机票场景（多外部系统、约半小时才出结果）的分布式事务怎么设计？消息传递失败怎么办？该场景 MQ 怎么选型？

### 面试回答

结论：这类“参与者含外部系统、耗时以分钟计”的流程做不了强一致——2PC／TCC 要求同步锁资源半小时，外部航司与支付宝不可能配合；正确目标是最终一致，手段是订单状态机＋事件驱动＋补偿与对账。

- 为什么排除强一致：外部系统不受控（无法当 TM 参与者）、结果异步返回（支付后半小时才出票）——任何“全程持锁等所有人就绪”的协议在这里都不成立。
- 设计骨架（正向流程）：
1. 建单：本地事务写订单（待占位），发“占座”事件调航司接口。
2. 占座成功→发起支付（调支付宝／微信），订单置“支付中”，同时设超时时间戳。
3. 支付结果靠回调＋轮询双通道拿；出票结果异步回写（可能就是那半小时后）。
- 失败即补偿（逆向动作）：占座失败→关单；支付成功但出票失败→自动退款＋通知；每个环节可重入（按订单号幂等）。
- 消息可能传递失败，分三层兜底：
- 发送失败：本地消息表（outbox，与业务同一事务落库）＋定时任务重投；RocketMQ 事务消息是它的托管版。
- 投递丢失：MQ 持久化＋生产端确认机制（confirm／ACK）。
- 消费失败：手动 ACK＋重试队列＋进死信人工处理；消费按业务键幂等去重。
- 最后一条防线是对账：定时扫中间态订单（支付中／出票中超时），主动向外部系统查终态并修正——消息保证“通常快”，对账保证“一定到”。
- MQ 选型（该场景）：量级不大、可靠性与延迟权衡要求高、需要事务消息／定时消息语义——选 RocketMQ；
- Kafka 吞吐强但业务消息的事务与低延迟推送非其长，日志流场景才优先它。
- 项目已有 RabbitMQ 也可行：confirm＋手动 ack＋死信/延迟插件，配本地消息表补事务语义——答“按现有设施选”比背参数更成熟。

## Q06：做题：新兵报到按身高排序，每次从头调整、一次只允许交换一次（N≤20）

### 面试回答

结论：“每轮从头扫一遍、只允许一次交换”就是选择排序——每轮在未排序区找最小值，与本轮首位置换一次，N 个元素最多 N−1 次交换；N≤20 时 O(n²) 完全够。

- 题意先复述确认：示例输出是最终升序数组；若还要求“输出每轮的交换过程”，加一个每轮打印即可，算法不变。
- 每轮逻辑：从 i=0 开始，扫描 [i, n) 记最小值下标 min，扫完只交换 `a[i]` 与 `a[min]` 一次，然后 i++。
- 为什么不是冒泡：冒泡每轮做多次相邻交换；这里约束“一次只交换一次”，对应的是“找位再换”的选择逻辑。

```java
public void sortSoldiers(int[] a) {
    int n = a.length;
    for (int i = 0; i < n - 1; i++) {
        int min = i;
        for (int j = i + 1; j < n; j++) {
            if (a[j] < a[min]) min = j;      // 只记录，不交换
        }
        if (min != i) {                        // 每轮至多一次交换
            int t = a[i]; a[i] = a[min]; a[min] = t;
        }
    }
}
```

- 复杂度：时间 O(n²)、空间 O(1)；交换次数 ≤ n−1，这正是“交换代价高”时选它的原因。
- 稳定性提醒：简单选择排序不稳定——175a／175b 可能换序；若“同身高保持报到顺序”，改成记录插入位置（每轮至多一次赋值移动）或带序号比较。

## Q07：基于 Redis 如何实现分布式锁？SET 为什么要加 PX 参数？

### 面试回答

结论：三件套——加锁 `SET key token NX PX ttl`（原子地占位＋设租期），解锁用 Lua 比对 token 再删，长任务加看门狗续期；PX 必须和 NX 在一条命令里，否则存在“加锁成功但没设上过期”的窗口。

- 加锁：key 按业务资源命名，value 是唯一 token（线程／请求标识）；NX 保证互斥，PX 给租约。
- 为什么 PX 要一起：先 `SETNX` 再单独 `EXPIRE`，两步之间进程崩溃→锁永不过期，全员死等；`SET key val NX PX 30000` 一条命令原子完成互斥与租约。
- 解锁：Lua 脚本 `if GET==token then DEL`——先查后删必须原子，否则会误删别人的锁（自己的锁超时被别人持有）。
- 续期：看门狗（Redisson watchdog）在锁未释放且线程还活着时周期延长 TTL；租约定多长看“任务最坏耗时＋安全余量”。
- 边界要主动说：Redis 主从异步复制，主节点带锁宕机切换后锁可能丢——极端正确性要求用 Redlock（也有争议）或改走数据库方案；锁不是 100% 正确性保证，业务侧仍需幂等兜底。

## Q08：基于数据库的方式如何实现分布式锁？

### 面试回答

结论：三条实现路线——锁表加行悲观锁（`SELECT ... FOR UPDATE`）、唯一键插入锁（插得进即持锁）、MySQL 咨询锁 `GET_LOCK()`；共同短板是性能与租约管理，适合低频、强持久正确的场景。

- 锁表悲观锁：建一张锁资源表，`SELECT * FROM locks WHERE name='xxx' FOR UPDATE` 拿到行锁即持锁，事务结束释放；跨实例互斥靠“锁记录都在同一个库”这个前提。
- 唯一键锁：`INSERT INTO lock(name, owner) VALUES ('xxx', 'me')`，唯一索引冲突即抢锁失败；释放是 DELETE。不需要单独查一步，天然防重。
- 咨询锁：`GET_LOCK('name', timeout)`／`RELEASE_LOCK()`——服务器维护的命名锁，不锁任何业务表，连接断开自动释放。
- 必须处理的两件事：租约——给锁记录加过期时间字段＋定时清理，否则持锁进程崩溃锁就死了；可重入——按 owner＋计数器自己实现。
- 硬伤：每次抢锁都是真实 DB 写，高并发下锁表成热点；抢锁等待要么轮询要么靠锁超时，延迟不可控。

## Q09：数据库实现和 Redis 实现的区别？应用场景？

### 面试回答

结论：区别在“谁扛得住什么”——Redis 锁快、自带租约、适合高频短期互斥但极端场景可能丢锁；数据库锁慢、持久可靠、几乎不会“悄悄丢”，适合低频强正确。按冲突频率与错误代价选。

- 一致强度：Redis 主从切换存在丢锁窗口（异步复制）；数据库方案只要单点主库存活就不丢（代价是 DB 本身成了瓶颈）。
- 性能：Redis 加解锁毫秒内、可上万 QPS；数据库每次抢锁是一次带锁写的短事务，几百 TPS 级就会成为热点。
- 失效语义：Redis 靠 PX 租约自动过期；数据库悲观锁随事务结束释放、插入锁必须自建过期字段——持锁崩溃后的“僵尸锁”是两边都要答的点。
- 场景口径：
- 高频接口防重复执行、分布式定时任务防多机并发跑、短临界区——Redis 锁。
- 低频后台操作互斥、审批／配置变更串行化、对一致性容忍为零且本就在操作这张表——数据库锁（或直接唯一约束防重）。
- 收尾一句成熟的：锁只降冲突概率，钱货级的正确性最终靠幂等键＋状态机＋对账，不靠任何一把锁。
