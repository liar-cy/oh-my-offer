## Q03：公司或项目会出于什么考虑选择编程语言（C、C++、Java、Python 等）？

一句话：语言选型是工程与组织决策，性能只是因素之一。按四类讲：

- 生态与人才：现成框架／中间件多不多、团队会不会、招人不招人难（Java 后端生态与公司存量系统是最强理由）。
- 运行场景：贴近系统与极致性能／实时性选 C／C++（网关、存储引擎、游戏）。
- 场景再分两档：高并发业务服务选 Java／Go，算法与数据选 Python（开发效率优先，算力在底层 C 扩展里）。
- 工程约束：与已有技术栈、部署设施、监控体系能否复用；跨语言混合也是常态（Python 训练＋C++ 推理、Java 业务＋Go 中间件）。
- 长期成本：可维护性、类型系统对大协作的作用、版本演进与官方支持。

收尾加一句判断：新项目选“团队最熟＋生态够用”的，而不是追性能榜单；语言决定的差异往往小于架构与代码质量决定的差异。

## Q04：介绍一下计算机网络的层级结构

先报口径：常用两套——OSI 七层与 TCP/IP 四层（有的教材称五层），答之前说明用的哪套。

- OSI 从低到高：物理、数据链路、网络、传输、会话、表示、应用。
- TCP/IP 四层：链路层（合并物理＋数据链路）、网际层（IP）、传输层（TCP／UDP）、应用层（会话／表示／应用合并）。
- 分层的意义：每层只依赖下层的接口，各层独立可替换；封装时上层数据是下层的载荷。
- 补一句边界：映射是教学概括，实际协议职责不总能严格一一对应。

## Q05：TCP 和 UDP 属于哪一层？有什么区别？应用场景如何？

**哪一层**：都属于传输层（四层模型）／OSI 第四层，向应用层提供端到端通信。

**区别**（按成对维度说）：

- 连接：TCP 三次连接建立、四次挥手释放；UDP 无连接，发前不握手。
- 可靠性：TCP 靠序号确认、超时重传、流量控制、拥塞控制保证不丢不乱；UDP 尽最大交付，丢包不重传。
- 形态与开销：TCP 面向字节流、有头部（20 字节起）与状态维护成本；UDP 头部仅 8 字节、报文边界保留。
- 时延：UDP 没有重传与握手等待，实时性更好。

**场景**：

- TCP：文件传输、HTTP／API、消息投递这类不能出错的。
- UDP：DNS 查询、音视频直播、游戏状态同步、QUIC（UDP 上自建可靠性）。
- 一句收口：要“准”用 TCP，要“快且能容忍丢”用 UDP；需要两者折中就在 UDP 上自建（QUIC 是现例）。

## Q06：项目中用的什么序列化方式？还了解哪些序列化方式，差异和应用场景？

**先给项目事实**：微服务／RPC 通信按【真实用法】答，常见是 JSON（Jackson／HTTP 接口）或 Java 原生＋Redis 侧 Jackson。

**横向对比按三类讲**：

- 文本通用型：JSON／XML——跨语言、可读、调试友好；体积大、解析慢，适合对外 HTTP 接口与配置。
- 二进制紧凑通用型：Protobuf——IDL 定契约、体积小速度快、跨语言，需预编译 schema，适合内部 RPC、流量敏感链路；Thrift 定位类似但生态较弱。
- 语言绑定型：Java 原生序列化——免配置但与语言强绑定、有反序列化攻击面、类结构变更易失败，生产上建议换 JSON 或 Protobuf（Kryo 同理，快但跨语言差，适合进程内／缓存）。

**选型口径**：

- 对外与可读性优先 → JSON。
- 内部高性能跨服务 → Protobuf。
- 深拷贝／缓存临时态 → 可用 Kryo，但要接受跨语言差。
- Java 原生序列化 → 生产上不建议，风险见上一条。

**易错点**：换序列化方式要处理存量数据兼容（字段编号 vs 字段名、新旧协议并存窗口）。

## Q07：进程和线程的区别

一句话：进程是资源分配的单位，线程是 CPU 调度的单位；线程是进程内的执行流。

- 隔离性：进程有独立虚拟地址空间与文件描述符表，崩溃互不影响；线程共享进程地址空间，一个线程崩可能带崩整个进程。
- 成本：创建／切换进程要换页表、刷 TLB，开销大；线程切换只换寄存器与栈上下文，轻量。
- 通信：进程间要走 IPC（管道、共享内存、Socket 等）；线程直接读写共享内存，但要自己做同步。
- 资源占用：一个进程可含多线程，共享代码段与堆；每线程独享栈与寄存器上下文。

## Q08：谈谈 ThreadLocal（作用、为什么会内存泄漏、存什么类型的数据）

**作用**：给每个线程绑一份变量副本，线程内各处可见、线程间隔离；典型是用户上下文、数据库连接、日期格式化对象这类“隐式传参”。

**为什么会内存泄漏**：结构是“每个 Thread 内含一个 ThreadLocalMap”，key 是 ThreadLocal 的弱引用，value 是强引用。

- 外部 ThreadLocal 变量被回收后，key 变 null，但 value 还被 entry→map→thread 这条强引用链挂着，成了“查不到又释放不掉的尾巴”。
- 线程池线程长期存活时更危险：map 不会随线程销毁自动清，泄漏会累积。
- 防护：用完 `remove()`（放 finally）；线程池场景不要依赖“线程结束自然清理”。

**存什么类型**：

- 适合：每线程独占、生命周期短、有状态的轻量对象——用户身份、traceId、连接、SimpleDateFormat。
- 不适合：大对象缓存（线程数一多就内存放大）。
- 不适合：跨线程共享的数据（语义本来就不对）。
- 要评估：线程数极大的场景——百万级虚拟线程各挂一份副本会失控，可看 Scoped Values。

## Q09：线程池的核心参数；核心线程数和最大线程数怎么设置才友好？

**七个参数**（以 `ThreadPoolExecutor` 为准）：

- `corePoolSize`：常驻线程数；`maximumPoolSize`：队列满后可扩到的上限。
- `workQueue`：任务队列；`keepAliveTime`＋时间单位：非核心线程空闲回收。
- `threadFactory`：命名／守护属性；`handler`：饱和拒绝策略（Abort 抛异常／CallerRuns 回压／Discard／DiscardOldest）。
- 提交流程一句：核心未满建核心 → 入队 → 队满建非核心 → 仍满走拒绝。

**核心／最大怎么设**：先分任务类型再算，不按感觉给数字。

- CPU 密集：线程太多只会抢核加切换开销，取 N核 + 1（约等于核数）起步。
- IO 密集：线程大量时间在等，并发度主要看下游容量。经典估算 `线程数 = N核 × 1/(1-阻塞系数)`；更实用的做法是按下游（DB 连接池、外部接口限额）反推上限。
- 两条纪律：最大线程数配上有界队列和可观测指标（活跃数、队列深度、拒绝数、RT）去压测调参；别把“公式算出的数”直接搬到线上，公式只是起点。

## Q10：MySQL、Redis、本地缓存的使用场景；三者结合一致性有损失，怎么保证？

**分工**：

- MySQL：事实源——持久、强一致、支持事务与复杂查询，容量和延迟换可靠性。
- Redis：共享加速层——跨实例一致视图、数据结构丰富，做热点读、分布式锁、计数器、会话；持久化是兜底不是账本。
- 本地缓存（Caffeine）：进程内层——零网络、纳秒级读，容量受内存限制，各实例各一份。

**三者叠加一致性确实有损失**：先立预期——做的是“有界不一致”，不是强一致。

- 写：DB 事务提交后删／更 Redis；Redis 变更通过失效消息或 CDC 广播各实例，本地层“失效重建”优于“主动更新”。
- 界：本地短 TTL 封顶陈旧窗口，消息带版本号幂等消费，失败重试＋对账收敛。
- 例外：涉及资损的读（库存、余额）绕过缓存直读 DB 或用条件更新。

## Q11：多节点部署，某节点先更新 Redis 再更新本地缓存，其它节点怎么知道要更新本地缓存？

（项目中未实现，现场给方案——答“通知机制＋兜底”两层）

- 首选失效广播：以 Redis 为变更总线，发布带实体 ID＋版本号的失效消息（pub/sub 或 Streams），各节点订阅后删本地对应 key，按“只接受不低于当前版本”消费防乱序。
- 消息总线选项：MQ 广播消费／Redis pub-sub 轻量但消息不持久，可配 CDC（canal 监 binlog）把“更新 Redis＋广播”统一由一条链路完成。
- 拉模式兜底：本地缓存带短 TTL，漏通知最多陈旧一个 TTL；重要数据再加版本号比对或定期反查 Redis 里的 version key。
- 诚实补一句：做不到物理上的“同时失效”，各节点收到消息的时间有先后；强一致读写直接绕过本地层。

## Q12：缓存击穿和缓存雪崩的区别？缓存击穿应当怎么防护？

**区别**（先分清三者成因）：

- 穿透：查根本不存在的数据，缓存永远不命中，请求直达 DB。
- 击穿：单个热点 key 过期瞬间，大量并发同时打到这一行数据。
- 雪崩：大量 key 集中过期或缓存服务整体宕机，回源洪峰打垮 DB。
- 一句记法：击穿是“一个点”，雪崩是“一大片”，穿透是“压根没有”。

**击穿防护**：

- 互斥重建：只放一个请求去回源（`SETNX` 锁／进程内 `synchronized` 合并），其余等待或重试；注意多实例下进程内锁挡不住。
- 请求合并：把并发回源收敛成一次广播结果（singleflight 思路）。
- 逻辑过期：value 里带过期时间，过期后先返回旧值、由抢到重建权的异步刷新——延迟平稳，代价是容忍短暂旧数据。
- 提前刷新：热点 key 由后台任务在到期前续填，前台读永远命中。
- 选型口径：余额库存类不能读旧值，用互斥重建；商品详情类读多可容忍陈旧，用逻辑过期。

## Q13：MySQL 索引的作用；什么场景需要建索引？建立索引要考虑哪些因素？

**作用**：把“全表扫描找行”变成“按有序结构定位”，InnoDB 用 B+ 树——非叶子只存键、叶子双向链表，范围与排序友好；顺带提供唯一约束和覆盖索引免回表。

**什么场景建**：

- 高频 WHERE／JOIN／ORDER BY 的列，且过滤后结果远小于全表（选择性高）。
- 需要唯一业务约束（订单号、手机号）——唯一索引兼做数据约束。
- 不建：小表、更新密集且很少被查的列、选择性极差的列（性别）；前缀重复度低的长文本可用前缀索引。

**考虑因素**：

- 写放大：每个二级索引都要在增删改时同步维护，索引不是越多越好。
- 最左前缀：多条件查询设计联合索引，把等值列放前、区分度高的在前，顺带覆盖排序。
- 回表与覆盖：查询列都在索引里可免回表（covering index）。
- 失效陷阱：函数包列、隐式类型转换、前导模糊 `LIKE '%x'` 会让索引失效。

## Q14：项目中 ES 主要用于什么场景、解决什么问题？

**定位**：ES 是搜索读模型，事实源仍是 MySQL——它解决的是 B+ 树解决不了的查询。

- 分词全文检索：中文／多词匹配、相关性打分排序，`LIKE '%x%'` 走不了索引也做不了打分。
- 多字段任意组合过滤：商品筛选、后台检索这类“条件自由组合”的场景。
- 聚合统计：按维度分组计数、趋势聚合。
- 场景按【真实项目】填：如“帖子／商品搜索＋筛选”，写路径由 binlog 监听（canal）同步进 ES，接受秒级最终一致。

**解决什么问题**一句收口：把“模糊查询全表扫描、扛不住也搜不准”的读流量从 MySQL 挪到为倒排索引设计的引擎上，代价是数据同步链路与秒级延迟。

## Q15：口述：如何快速找出一个数组的一个峰值（比左右两个数都大）？

结论：不要求全局最大时，二分即可，O(log n)。

- 前提确认（口述题先说清）：相邻元素不等的连续数组；边界按“外侧视为 −∞”处理。
- 二分逻辑：看 `mid` 与 `mid+1`——若 `a[mid] < a[mid+1]`，右侧必有峰（一路上坡总会碰到下坡或边界）；否则左侧（含 mid）必有峰。
- 为什么成立：上坡方向走一步总会到达“开始下降”或“到边界”的位置，那即是峰；不需要比较左边，只看一侧相邻即可定方向。
- 兜底：若无“相邻不等”前提，退化为线性扫描 O(n) 一定可解；先求全量再谈优化，说明追求的是“一个峰”而非最大值。

## Q16：1×2×3×…×100 的结果末尾有多少个零？

结论：24 个。

- 末尾一个零 = 一对因子 2×5；100! 里因子 2 远比 5 多，所以数 5 的个数。
- 计数分三层：每 5 个数贡献一个 5 → ⌊100/5⌋=20。
- 25=5² 的倍数自带两个 5，要再补一层 → ⌊100/25⌋=4。
- 125 超过 100，第三层为 0，停止。
- 合计 20+4=24。
- 推广：n! 尾零 = `Σ ⌊n/5^k⌋`（k=1,2,…）。
- 易错：只数 5 的倍数（漏 25、125 的重复贡献）得 20；被提示后要点出“5² 要再算一层”。
