## Q01：项目中的 Redis 是怎么用的，存了哪些数据？

### 面试回答

一句话：按【真实项目】逐项说，每类数据都要对上具体用了哪种 Redis 结构，不能泛泛而谈“用了缓存”。

- 缓存了什么：商品／用户信息这类数据用 String 或 Hash，列表用 ZSet。
- 还拿它做什么：分布式锁、限流计数、去重集合。
- key 怎么设计：前缀:业务:ID 这样的分层命名，再配对应的 TTL。
- 服务端配置：淘汰策略和持久化是怎么配的。
- 为什么这些数据适合放 Redis：热点读多、数据结构正好匹配、访问延迟低。

## Q02：有没有做幂等性设计，比如用户连续点击两个提交订单怎么做？

### 面试回答

有做，用的是一套通用组合拳。核心一句：幂等标识＋持久化去重，不能只靠前端按钮置灰或者内存标记。

- 一次性 token：进入提交页先发一个 token，提交时原子核销。重复提交拿不到 token，直接拒绝。
- 业务唯一键兜底：订单表用业务唯一键（用户＋活动／请求号），重复插入命中唯一约束时，返回已有结果。
- 状态机条件更新：只有“待支付”能往下流转，防住乱序和重复。
- 分布式锁：并发强冲突的场景再加这一层。

## Q04：如何保证 Redis 和 MySQL 的数据一致性？

### 面试回答

常见做法是 cache-aside（旁路缓存，缓存由应用自己读写和维护）。写的顺序是：先提交数据库事务，再删除缓存——注意是删除，不是更新。

剩下要处理的就那几个窗口：

- 删缓存失败：做失败重试；或者订阅 binlog（canal 类工具）来驱动缓存失效。
- 兜底：缓存统一设 TTL，最坏也只陈旧到过期为止。
- 并发回填旧值：用延迟二次删除缩小窗口，再配合 key 版本号。
- 强一致读：不碰缓存，直接走数据库。

项目里按【项目实际做到哪一层】如实说明。没做补偿，就讲清能容忍多久的陈旧、为什么能容忍。

## Q05：如果 MQ 因为网络等原因发送消息延迟，如何优化？

### 面试回答

先定位问题出在哪一层：网络、broker（消息服务器）、还是客户端。再对症下手：

- 连接：改成长连接复用＋连接池，避免每次都重新建连和握手。
- 发送：改成异步＋回调确认，并且设超时；允许批量聚合，把往返次数降下来。
- 超时之后：按幂等键做有限次重试。
- 还满足不了实时性就降级：本地消息表／outbox 先落库，后台持续补发；小流量业务可以直接同步写库，绕过 MQ。

效果怎么验证：看发送延迟的分布和失败率。

## Q06：有用到事务实现吗，MQ 发送消息失败是回滚还是重试？

### 面试回答

结论：本地事务没法原子地覆盖 MQ 发送，所以回滚还是重试，取决于这条消息的业务语义。

- 只是通知类的消息：订单等主流程不该因为它发不出去就整体回滚。业务照常提交，消息落到 outbox／本地消息表，由后台重试补发。
- 消息本身是业务生效的前提：比如扣款指令必须送达，那发送失败就回滚本地事务，或者同步确认成功之后再提交。

处理原则三条：

- 可重试的暂时故障：重试。
- 确定失败的：进失败流程，人工处理。
- 不能自欺：不能假装已回滚、已提交。

## Q07：MQ 中的脏数据怎么处理？

### 面试回答

先确认口径：这里说的“脏数据”可能是过期数据、不该发的消息、格式坏掉的消息，三种的处理不一样。

通用处理是这四条：

- 生产端给消息带版本号／时间戳，消费时比较状态。
- 旧版本或者已取消的：直接丢弃，但要记录下来。
- 格式错误的：进死信队列人工排查，不重试、不污染主流程。
- 消费侧做幂等，防住重复消息。

再加两道保险：上线前用回放测试验证；事后靠对账发现差异再补偿。

一条底线：丢弃要有依据、要留痕，不能静默把消息吞掉。

## Q08：秒杀流程怎么改进的，为什么要改为异步实现？

### 面试回答

先说瓶颈：同步流程里，请求线程要直接等数据库扣减和落库。

- 热点行的锁在排队，吞吐上不去。
- 瞬时流量一来，直接打满连接池。

改进是把一步拆成两步：

- 入口做完校验，就用 Redis 原子预占库存，投 MQ 后立即返回受理结果。
- 消费者按幂等事务落库、发券，把洪峰的写入摊平到数据库可承受的速率。

异步换来的是削峰和吞吐，代价也要说清：用户先看到的是“处理中”。所以要配三样东西——结果查询、消息可靠性、对账兜底。

按【项目实际改造】说明，没做的部分不声称。

## Q09：如果数据库故障导致无法写入，怎么处理？

### 面试回答

分层处理，顺序是发现、切换、降级。

- 快速发现：靠连接超时和写失败率的告警。
- 切高可用：主从切换／MHA 这类方案。
- 切换期间按业务降级：读的一侧走缓存或者从库。
- 写入按重要性三选一：排队缓冲（本地消息表、请求队列），恢复后补偿落库；直接失败，返回稍后重试；可容忍的业务先记临时存储，再走对账。

两条关键约束：缓冲要幂等、要可恢复；还得说清最多丢什么。不能让缓冲无限堆积，反过来把应用拖垮。

## Q10：限流部分怎么实现的，为什么要用 AOP 和注解，有哪些作用？

### 面试回答

实现分三步：

- 注解声明规则：比如 @RateLimit(key, 阈值, 窗口)。
- AOP 切面在方法执行前取出注解参数，调用限流器判断要不要放行。限流器用 Redis＋Lua 做原子计数，或者用令牌桶。
- 超限就抛异常，交给全局异常处理返回友好错误。

为什么用 AOP＋注解：

- 限流是横切关注点，这样能和业务代码解耦。
- 声明式统一接入，新增接口只加注解，不用改业务逻辑。
- 规则集中在一处，可以配置。

代价也要说：受代理机制限制（自调用会失效），规则表达也受注解只能写静态值这个约束。

## Q11：介绍一下常见的锁，乐观锁和悲观锁是什么，分别有哪些优缺点？

### 面试回答

先按维度分类，再重点讲乐观／悲观。

- 乐观／悲观：区别就在于假设冲突多还是少。
- 其他维度：共享／排他、行／页／表粒度、公平／非公平、可重入，以及数据库锁和分布式锁。

乐观锁：不阻塞，靠版本号或者 CAS（compare-and-swap，比较并交换）做校验，冲突时提交失败再重试。

- 优点：读多写少、冲突低的时候吞吐好。
- 缺点：高冲突下重试很浪费，ABA 问题（值被改走又改回，校验会误判通过）还得另外处理。

悲观锁：先加锁再操作，比如 SELECT FOR UPDATE。

- 优点：一致性强，写冲突时行为确定。
- 缺点：持锁要等待，有死锁风险和吞吐损失。

选型口径：按冲突频率和一致性要求来选。

## Q15：MCP、Skills、RAG 了解吗，介绍一下。

### 面试回答

这三个不在同一层，分开说：

- MCP：一个开放协议，把 AI 应用和外部工具／数据连起来。角色分 host—client—server，管的是工具发现和调用。
- Skill：可复用的任务方法包。一个 SKILL.md 写清做法，再配脚本／资料，按需加载。
- RAG（检索增强生成）：先检索外部证据，再让模型依据这些证据生成答案。缓解的是知识过时和幻觉。

组合关系一句话：RAG 提供证据，Skill 组织方法，MCP 接入能力。

## Q17：未来打算直接就业还是读研，为什么不选择读研？

如实回答个人规划。框架是：

## Q18：能实习多久？

### 面试回答

把时间说具体，别只说“能来挺久”。

- 时长：【每周可实习天数 × 可持续月数】。
- 起止：什么时候能到岗，最晚待到什么时候。
- 保障：学业安排（课程、论文）怎么让这段时间落得下来。
- 意向：有转正或者长期的想法可以表达，但不要做无法兑现的承诺。

最后和 Q17 的规划保持一致。
