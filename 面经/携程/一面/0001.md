## Q01：项目中 Redis 怎么用的，数据一致性怎么保证？

### 面试回答

先按【真实用法】列场景：缓存、分布式锁、计数／限流、排行榜等，再挑一致性展开。

缓存一致性的通用答法：

- 定原则：以数据库为事实源。
- 写路径走 cache-aside（旁路缓存：读未命中时回填，写不直接改缓存）：先提交数据库，再删缓存。
- 删缓存失败要有补偿：CDC／binlog 订阅，或者可靠消息重试；再加定期校准，key 带 TTL 兜底。
- 并发回填旧值的竞态，用版本号、短 TTL 或延迟二次删除把窗口缩小。

口径要主动说明白：这套“删除缓存＋补偿＋TTL”是最终一致，不承诺严格同时刻一致。业务能容忍多旧的数，得先定义清楚。

## Q02：canal 同步 500ms 延迟怎么来的，怎么优化？

### 面试回答

先把延迟拆开归因，再谈优化；数字口径按【项目实测】说明。

链路是：业务写库提交 binlog → canal server 伪装成 replica 拉 dump → 解析成行事件 → 投递／落到目标（Redis、ES、MQ）→ 下游消费才生效。

500ms 可能出在这几处：

- 解析吞吐：默认是单线程解析，大事务、宽表的行会放大工作量。
- 投递与消费的攒批间隔：轮询式写入天然要等一个批次。
- 目标端写入排队。
- 大事务或 DDL 阻塞位点推进。
- 也可能只是统计口径：取的是“事务提交时间→可见”的 P99，或者心跳间隔，而不是单个环节的耗时。

优化跟着一一对应：

- 过滤无关的库表列，减少解析量。
- 增大并行度：按主键 hash 分区，做保序的并行 sink。
- 缩短攒批，或者改成事件驱动。
- 拆大事务。
- 分段监控各段耗时（拉取延迟、解析耗时、sink 积压），先治最长的那段。

## Q03：需要缓存的数据特别大怎么办？

### 面试回答

先分清是“单值大”还是“总量大”，两个办法不一样。

单值大（big value）：

- 按字段或分片拆成多个 key。
- 换紧凑的序列化方式（protobuf、kryo），或者压缩之后再存。
- 大内容外置到对象存储／DB，Redis 只缓存一个引用。
- 读取按分片或字段拉，不要一次取整块。

总量大：

- 只缓存热子集，配 TTL 淘汰。
- 叠一层本地缓存做分级。
- 冷数据直接查库，回源要限流。

为什么要管：大 value 会拖住单线程的传输、造成内存不均，还占带宽。

改完怎么验证：用 `--bigkeys`／`MEMORY USAGE` 复查。具体多大、怎么拆，按【项目实际】说。

## Q04：创建订单耗时很长怎么办？

### 面试回答

先用链路追踪把耗时拆开定位，再分类下手：

- 互相独立的校验（风控、优惠、库存、地址）并行化，不要串成一串 RPC。
- 非核心的副作用（通知、积分、埋点、报表）移出同步链路，改 MQ 异步。
- 慢查询和热点数据前置：价格／优惠做预计算或缓存，DB 事务里只留必要的写。
- 拆分事务，缩短持锁时间；小写合并成批量。
- 订单号这类用号段预取。

两条约束：

- 异步化的部分要有幂等和最终一致的补偿，也就是对账／状态机。
- 优化之后用同口径的压测和 trace 对比，验证收益；别只报一句“感觉快了”。

## Q05：下游接口无法降级怎么办？

### 面试回答

先确认“无法降级”是哪一种：真的业务不允许（这一步必须成功），还是没做降级预案。

真不能降级的，方向是把“可用性降级”换成“时间换空间”：

- 调用本身做足超时＋幂等键＋有限重试，别把线程拖死。
- 仍然失败就转入异步补偿：订单受理后写重试队列／死信，加告警；后台恢复之后重放。用户侧的表现是“处理中”，而不是失败。
- 再兜不住，就留一个人工接管的出口。

核心论点是这一句：不能降级的依赖，要设计成“可延迟完成”。前提是操作幂等、状态可查、有对账。

边界：如果连延迟都不允许，那就是强一致的同步依赖。这时只能提高该依赖自身的可用性与容量，并明确故障时的业务止损预案。

举例按【项目真实依赖】来说。

## Q06：MySQL 隔离级别，索引失效的场景？

### 面试回答

隔离级别四档，每档记住它挡不住什么：

- 读未提交：会有脏读。
- 读已提交：会有不可重复读。
- 可重复读：InnoDB 默认级别。MVCC（多版本并发控制）的快照读解决不可重复读；当前读＋next-key 锁在很大程度上防住幻读。
- 串行化：全互斥，吞吐最低。

索引失效（严谨的说法是“不能用于定位”）的常见场景：

- 对索引列套函数或表达式。
- 隐式类型转换，比如字符串列去比数字。
- LIKE 以百分号开头。
- 联合索引跳过前导列，或者被范围条件截断。
- OR 连接了没有索引的列。
- 选择性太差时，优化器主动放弃索引。

最后一条要单独说清：那是优化器按统计信息做的选择，不是语法上的失效。用 EXPLAIN 验证。

## Q07：synchronized 和 ReentrantLock 是干啥的，区别？

### 面试回答

一句话：两者都是解决多线程互斥、并保证可见性的锁。区别在实现层次和能拿到什么。

- synchronized：JVM 内置的监视器锁。加在方法或代码块上，进出自动获取和释放，不存在忘解锁。
- ReentrantLock：JDK API 层的显式锁（基于 AQS，抽象队列同步器）。必须在 finally 里 unlock，换来的是额外能力。

ReentrantLock 多出来的四条能力：

- 可中断获取：lockInterruptibly。
- 限时尝试：tryLock。
- 公平锁选项。
- 多个 Condition 等待队列。

选法：普通互斥用 synchronized 更简洁；需要上面任何一条能力，再上 ReentrantLock。

## Q08：synchronized 能锁住 String 和 Long 对象吗？

### 面试回答

语法上能——synchronized 锁任何引用对象都可以（基本类型不行，long 会先装箱）。但恰恰不该拿它们当锁。

- String：字面量会进常量池，内容相同的字符串全局就是同一把锁。这会把不相干的业务意外串在一起，还可能和第三方库共享同一个对象。
- Long／Integer 等包装类：只有 −128～127 有缓存，超出范围每次装箱都是不同对象。两个线程锁“相同的值”，实际锁的是两个对象，互斥直接失效。而且这些类不可变，值一变，锁对象就换了。

正确做法有两条：

- 用专有的锁对象：`private final Object lock = new Object()`。
- 或者按业务键做分段锁（比如 `Striped`／锁字典），锁对象的生命周期由自己掌控。

## Q09：类加载的过程是什么？

### 面试回答

五个阶段：加载 → 验证 → 准备 → 解析 → 初始化，后三步合称链接。

- 加载：类加载器按“双亲委派”（Bootstrap→App→自定义）拿到字节流，生成方法区的 Class 对象。
- 验证：查格式、元数据、字节码语义和控制流。
- 准备：给静态变量分配内存并置零值。编译期常量这时已经是终值。
- 解析：把符号引用换成直接引用。这一步可以延后到使用时才做，所以支持动态绑定。
- 初始化：执行 `<clinit>`，也就是静态块和静态赋值按书写顺序跑一遍。

初始化的时机值得单独补一句：首次主动使用时才触发，JVM 保证它只执行一次且线程安全。懒加载单例靠的就是这点。

## Q10：怎么计算一个对象的大小？

### 面试回答

按 HotSpot 64 位、默认开启压缩指针来估算：

- 对象头：Mark Word 8 字节＋压缩类指针 4 字节。
- 实例字段按类型宽度排列：int 4、long／double 8、引用 4。
- 最后补齐到 8 的倍数；数组还要另加一个长度字段。

举个例子：一个 int 加一个引用的对象，≈ 12＋4＋4＝20，补到 24 字节。

两个概念要分清：

- shallow size：对象自身的大小。
- retained size：连同它独占引用的整个对象图。
- 排查“谁吃了堆”要看后者。

实测用 JOL 工具或 MAT。还有个前提会变：堆超过 32G 时关闭压缩指针，这时引用变成 8 字节。

## Q11：创建类有几种方法？

### 面试回答

题意有歧义，先确认口径，两种常见理解都准备好。

如果问的是“创建对象”的方式：

- new：绝大多数场景。
- 反射：Class／Constructor.newInstance。
- clone：需要实现 Cloneable，而且会绕过构造器。
- 反序列化：同样绕过构造器，所以 readObject 里要做校验。
- 方法句柄／`MethodHandles`。

如果问的是“生成一个新类”的方式：

- 正常编译，产出 class。
- 运行期动态代理：JDK Proxy 按接口，CGLIB 生成子类。
- 字节码框架：ASM／Javassist／ByteBuddy，它们是 AOP 与探针的基础。
- 运行期源码编译：javax.tools.JavaCompiler，或者 Groovy 脚本。

判断线索：问“实例化对象的途径”多指前一种；但这题接在类加载后面问，也可能指后一种。按面试官的澄清展开。

## Q12：怎么设计一个可靠的系统？

### 面试回答

先给口径：可靠性 = 先明确 SLO（可用性几个 9、故障恢复时间），再让单点故障不放大。

框架分五步：

- 冗余去单点：服务多实例多可用区，依赖做主从／集群；容量留冗余，要能承受 N-1。
- 依赖治理：
  - 所有跨网络的调用都带超时。
  - 重试加退避和上限。
  - 配熔断、限流和降级预案。
  - 做故障隔离，比如线程池／舱壁。
- 状态正确性：幂等键贯穿全链路，用状态机约束流转，失败可重放；关键链路要有对账补偿。
- 可观测：指标／日志／链路追踪加告警，争取先于用户发现问题。
- 演练与预案：压测摸容量，故障演练验证切换，备份能恢复（RPO／RTO）且能回滚。

最后落一句：结合【项目真实链路】挑一条讲透，比背清单可信。

## Q13：项目里怎么用熔断的，熔断时机、恢复时机？

### 面试回答

项目里用【真实组件：Sentinel／Resilience4j 等】对【真实依赖】做熔断。

什么时候打开：

- 按滑动窗口统计，错误率或慢调用比例超过阈值。
- 还要窗口内请求数达到最小样本量才打开——这是为了低流量时不误判。
- 熔断期内请求直接快速失败、走 fallback，不再打到这个故障依赖。

什么时候恢复：

- 超时之后进入半开，放行少量探测请求。
- 成功率／延迟达标就关闭、恢复全量；仍然失败就回到断开并重新计时。
- 恢复初期常配小流量爬坡，防止二次把它打垮。

边界要讲清：熔断解决的是“快速失败、防止线程堆积拖垮自己”，不解决“请求不丢”。所以它常和超时＋重试（要幂等）＋异步补偿组合在一起；重试还得设上限，防止重试风暴。
