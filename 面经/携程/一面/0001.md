## Q01：项目中 Redis 怎么用的，数据一致性怎么保证？

### 面试回答

按【真实用法】先列场景（缓存、分布式锁、计数/限流、排行榜等），再挑一致性展开。缓存一致性通用答法：以数据库为事实源，cache-aside 写路径“先提交数据库、再删缓存”；删缓存失败要有补偿（CDC/binlog 订阅、可靠消息重试）与定期校准，key 带 TTL 兜底；并发回填旧值用版本号、短 TTL 或延迟二次删除缩小窗口。明确说“删除缓存＋补偿＋TTL”是最终一致，不承诺严格同时刻一致，业务能容忍多旧的数要先定义。

## Q02：canal 同步 500ms 延迟怎么来的，怎么优化？

### 面试回答

先把延迟拆开归因再谈优化，数字口径按【项目实测】说明。链路：业务写库提交 binlog → canal server 伪装 replica 拉 dump → 解析成行事件 → 投递/落目标（Redis、ES、MQ）→ 下游消费生效。500ms 可能来自：解析吞吐（默认单线程解析，大事务/宽表行放大）、投递与消费的攒批间隔（轮询式写入天然带一个批次等待）、目标端写入排队、大事务或 DDL 阻塞位点推进，还可能只是统计口径（取“事务提交时间→可见”的 P99 或心跳间隔）而非单环节。优化对应：过滤无关库表列减少解析量、增大并行度（按主键 hash 分区保序并行 sink）、缩短/事件化攒批、拆大事务、监控各段耗时（拉取延迟、解析耗时、sink 积压）先治最长的那段。

## Q03：需要缓存的数据特别大怎么办？

### 面试回答

先分清是“单值大”还是“总量大”。单值大（big value）：按字段/分片拆成多个 key；换紧凑序列化（protobuf、kryo）或压缩后存；大内容外置到对象存储/DB，Redis 只缓存引用；读取按分片或字段拉取而不是一次整块。总量大：只缓存热子集＋TTL 淘汰，叠加本地缓存分级，冷数据直接查库并限流回源。还要讲影响：大 value 拖住单线程传输与内存不均、占带宽，改完用 `--bigkeys`／`MEMORY USAGE` 验证。具体多大、怎么拆按【项目实际】说。

## Q04：创建订单耗时很长怎么办？

## Q05：下游接口无法降级怎么办？

### 面试回答

先确认“无法降级”是真的业务不允许（这步必须成功），还是没做降级预案。真不能降级的，方向是把“可用性降级”换成“时间换空间”：调用本身做足超时＋幂等键＋有限重试，避免线程被拖死；仍失败则转入异步补偿——订单受理后写重试队列/死信＋告警，后台恢复后重放，用户侧表现为“处理中”而非失败；再兜不住就人工接管出口。核心论点：不能降级的依赖要设计成“可延迟完成”，前提是操作幂等、状态可查、有对账；如果连延迟都不允许，那就是强一致同步依赖，只能提高该依赖自身的可用性与容量，并明确故障时的业务止损预案。按【项目真实依赖】举例。

## Q06：MySQL 隔离级别，索引失效的场景？

### 面试回答

隔离级别四档：读未提交（脏读）、读已提交（不可重复读）、可重复读（InnoDB 默认，MVCC 快照读解决不可重复读，当前读＋next-key 锁在很大程度上防幻读）、串行化（全互斥、吞吐最低）。索引失效（严谨说法是“不能用于定位”）常见场景：对索引列套函数或表达式、隐式类型转换（字符串列比数字）、LIKE 以百分号开头、联合索引跳过前导列或被范围条件截断、OR 连接无索引列、选择性太差时优化器主动放弃索引——最后这条是优化器按统计信息的选择，不是语法失效，用 EXPLAIN 验证。

## Q07：synchronized 和 ReentrantLock 是干啥的，区别？

### 面试回答

两者都是解决多线程互斥并保证可见性的锁。synchronized 是 JVM 内置的监视器锁，加在方法或代码块上，进出自动获取释放，不会忘解锁；ReentrantLock 是 JDK API 层的显式锁（基于 AQS），必须 finally 中 unlock，换来的是额外能力：可中断获取（lockInterruptibly）、限时尝试（tryLock）、公平锁选项、多个 Condition 等待队列。选法：普通互斥用 synchronized 更简洁，需要上述任一能力再上 ReentrantLock。

## Q08：synchronized 能锁住 String 和 Long 对象吗？

### 面试回答

语法上能——synchronized 锁任何引用对象（基本类型不行，long 会先装箱），但恰恰不该用它们当锁：String 字面量进常量池，内容相同的字符串全局同一把锁，会把不相干业务意外串在一起，还可能与第三方库共享同一对象；Long/Integer 等包装类只在 −128～127 有缓存，超出范围每次装箱都是不同对象，两个线程锁“相同的值”实际锁了两个对象，互斥直接失效，且这些类不可变，值一变锁对象就换了。正确做法：用专有的 `private final Object lock = new Object()`，或按业务键做分段锁（如 `Striped`／锁字典），锁对象生命周期自己掌控。

## Q09：类加载的过程是什么？

### 面试回答

加载→验证→准备→解析→初始化（后三步合称链接）。加载：类加载器按“双亲委派”（Bootstrap→App→自定义）拿到字节流，生成方法区的 Class 对象；验证：格式、元数据、字节码语义与控制流检查；准备：静态变量分配内存并置零值（编译期常量此时已赋终值）；解析：符号引用换直接引用，可延后到使用时（支持动态绑定）；初始化：执行 `<clinit>`（静态块与静态赋值按书写顺序），首次主动使用时触发，JVM 保证只执行一次且线程安全——懒加载单例靠的就是这点。

## Q10：怎么计算一个对象的大小？

### 面试回答

按 HotSpot 64 位、默认开启压缩指针估算：对象头＝Mark Word 8 字节＋压缩类指针 4 字节，实例字段按类型宽度排列（int 4、long/double 8、引用 4），最后补齐到 8 的倍数；数组另加长度字段。例：一个 int 加一个引用的对象 ≈ 12＋4＋4＝20→补到 24 字节。要区分 shallow size（对象自身）与 retained size（连同独占引用的整个对象图），排查“谁吃了堆”要看后者；实测用 JOL 工具或 MAT，堆超 32G 关闭压缩指针时引用变 8 字节。

## Q11：创建类有几种方法？

### 面试回答

## Q12：怎么设计一个可靠的系统？

### 面试回答

先给口径：可靠性＝明确 SLO（可用性几个 9、故障恢复时间）后，让单点故障不放大。框架五步：① 冗余去单点——服务多实例多可用区、依赖主从/集群，容量冗余可承受 N-1；② 依赖治理——所有跨网络调用带超时，重试加退避与上限，配熔断、限流和降级预案，故障隔离（线程池/舱壁）；③ 状态正确性——幂等键贯穿、状态机约束流转、失败可重放，关键链路有对账补偿；④ 可观测——指标/日志/链路追踪加告警，先于用户发现问题；⑤ 演练与预案——压测摸容量、故障演练验证切换、备份可恢复（RPO/RTO）且能回滚。结合【项目真实链路】挑一条讲透，比背清单可信。

## Q13：项目里怎么用熔断的，熔断时机、恢复时机？

### 面试回答

项目用【真实组件：Sentinel／Resilience4j 等】对【真实依赖】做熔断。触发时机：按滑动窗口统计，错误率或慢调用比例超过阈值、且窗口内请求数达到最小样本量才打开熔断——最小调用量是为了低流量时不误判；熔断期内请求直接快速失败走 fallback，不再打到故障依赖。恢复时机：超时进入半开，放行少量探测请求，成功率/延迟达标就关闭恢复全量，仍失败回到断开并重新计时；恢复初期常配小流量爬坡防止二次打垮。边界要与讲清：熔断解决“快速失败、防止线程堆积拖垮自己”，不解决“请求不丢”，所以常与超时＋重试（幂等）＋异步补偿组合，重试要设上限防止重试风暴。
