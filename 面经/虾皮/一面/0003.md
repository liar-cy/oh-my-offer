## Q01：讲一下项目里 RAG 的整体实现流程。

### 面试回答

按“离线建库 → 在线问答”两段讲：

- 离线：文档解析清洗 → 分块 → 打标（来源／版本／权限）→ embedding → 入向量库＋关键词索引。
- 在线：query 预处理（改写／指代消解）→ 混合召回（向量＋关键词）→ 融合去重 → 重排 → 拼上下文喂模型 → 生成带引用的答案。
- 闭环：用标注评测集测召回与答案质量，badcase 回流迭代。

## Q02：向量检索这里是不是只使用余弦相似度？余弦相似度特点是什么？还有哪些相似度算法？

### 面试回答

不是只用余弦，主流三种，差别在“看方向还是看幅度”：

- 余弦相似度：只看夹角方向、不看长度，对长短文档不敏感，最常用。
- 点积／内积：兼顾方向与幅度；归一化后就等价于余弦。
- 欧氏距离（L2）：看绝对距离，受向量模长影响。

关键：用哪个取决于 embedding 模型的训练目标，且索引端和查询端必须同一度量，否则分数不可比。

## Q03：召回时关键词片段如何检索？BM25 的计算原理是什么？

### 面试回答

关键词检索＝倒排索引＋BM25 打分：

- 倒排索引：term → 含它的文档，查询分词后直接定位候选，擅长精确术语、编号、稀有词。
- BM25 三要素：词频饱和（出现越多分越高但有上限，参数 k1）、IDF（稀有词权重高）、文档长度归一（长文档惩罚，参数 b）。
- 它是 TF-IDF 的改进版，加了饱和与长度归一，是 ES 默认打分。
- 和向量互补：BM25 管词面精确、向量管语义泛化。

## Q04：BM25 检索结果和向量检索结果，两套数据如何做结果融合？

### 面试回答

两路分数不能直接相加（量纲不同），要融合：

- RRF（倒数排名融合）：只按各路排名算 `1/(k+rank)` 相加，不依赖原始分数量纲，简单稳健。
- 或各自归一化（min-max／排名归一）后加权，权重在标注集上调。
- 融合去重后再统一重排控制精度。

## Q05：文档分块策略、递归字符切分执行逻辑、切分仍超长怎么办、还有哪些分块方案？

### 面试回答

- 策略族：固定长度＋重叠、按分隔符（段落／标题）、递归字符切分、结构感知（Markdown／表格整体）、语义切分、父子块／滑动窗口。
- 递归切分：分隔符按优先级 `\n\n→\n→句号→字符` 逐层降，某段仍超长就用下一级继续切。
- 切完仍超长：允许该条单独成块、或强制截断带重叠、表格／代码改用结构保留而非硬切。

## Q06：表格与图片如何处理，PDF 长表格被 chunk 截断怎么办？

### 面试回答

- 表格：不从中间切断，整体成块；太长则按行分块且每块重复表头，或把“表头＋每行”转成自然语言，避免“有数字没列名”的残缺行。
- 图片：文本检索吃不了图，用 OCR 抠字或视觉模型生成图片描述入库、回链原图；需要理解图片再上多模态或 OCR＋文本混合。
- PDF 长表截断的补救就是上面这套：结构保留＋表头随行，而非按固定字符硬切。

## Q07：Agent 是人工触发任务吗？整体工作流程是否固定？

### 面试回答

按【真实设计】答：

- 触发方式：可人工触发（用户提需求），也可定时／事件驱动自动触发。
- 流程是否固定：多数业务是“半固定”——主干流程固定（确定步骤用代码／workflow），只在需要判断的节点交给模型动态决策；纯开放任务才让 Agent 自主规划。
- 一句判据：能用固定 workflow 就别全交给 Agent，固定部分更可控、更省、更好测。

## Q08：Skill 硬编码写死 workflow，效率上有什么差异，各自优缺点？

### 面试回答

硬编码 workflow vs 让模型动态编排的取舍：

- 硬编码：可预测、延迟低、便宜、好测试、可审计；缺点是灵活性差，需求一变就要改代码，长尾场景覆盖不全。
- 动态编排：泛化好、能应变没预设的情况；缺点是不确定、慢、贵、难复现、易跑偏。
- 差异本质是“确定性换灵活性”。合理做法是分层：高频确定的固化成 workflow／Skill，开放长尾交给模型决策（分级设计见 AGENT-024）。

## Q09：项目里上下文压缩是怎么做的？

### 面试回答

多手段组合控窗口：

- 对历史与工具结果做摘要／裁剪，丢无关轮次。
- 长期信息外置到记忆库，按需检索回注而非全塞。
- 结构化与去冗余：工具结果取关键字段而非原文，精简提示模板。
- 稳定前缀用 Prompt Caching 降成本（注意它不减占用，只降开销）。

## Q10：复杂任务场景下，中心调度 Agent 如何路由调用不同的 subAgent？

### 面试回答

中心调度做“理解—拆解—路由—汇聚”：

- 意图识别与任务拆解后，按子任务类型路由到对应 subAgent（各自专精一个领域／工具集）。
- 路由依据：固定规则／分类器，或让模型按各 subAgent 的能力描述（类似 skill 选择）决定。
- 汇聚结果、控制循环与终止、异常兜底。

## Q11：子 Agent 之间任务、上下文、输出结果如何传递给中心调度 Agent？

### 面试回答

靠“契约化消息”，不共享内部黑箱：

- 中心调度下发：子任务目标＋必要输入＋约束（结构化），不带全量上下文。
- 子 Agent 回传：结构化的结果／状态／引用，而不是把它的完整推理链塞回来。
- 传输层可以是进程内调用、函数返回值，或跨机用消息／协议（多 Agent 通信框架）；关键是定义清楚输入输出契约。

## Q12：多层子 Agent 调用会不会造成中心调度 Agent 上下文爆炸，怎么解决？

### 面试回答

会——若把每个子 Agent 的完整过程和长输出都塞回中心上下文，层数一多就爆。对策：

- 各子 Agent 上下文相互隔离，中心只收“结论摘要＋关键引用”，不收全量轨迹。
- 子 Agent 结果先做结构化压缩／摘要再回传。
- 需要时按任务分片／分层记忆，中心维持“轻量控制上下文”，细节外置可按需检索。

## Q14：手撕：编辑距离。

### 面试回答

二维 DP，O(m·n)：`dp[i][j]` 为 word1 前 i 个变 word2 前 j 个的最少操作数；字符相等走 `dp[i-1][j-1]`，不等取「替换／删除／插入」三者最小＋1；边界 `dp[i][0]=i`、`dp[0][j]=j`。可用滚动数组压到 O(n)。
