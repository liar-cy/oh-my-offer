## Q04：怎么保证缓存和数据库之间的数据一致性？

### 面试回答

先立口径：目标是最终一致，不是强一致。缓存和数据库跨两个存储，应用层做不到两阶段原子，只能把不一致的窗口控制住。

主方案是 cache-aside 下“先提交数据库、再删除缓存”。不直接更新缓存，是为了避免并发写交错产生旧值；删除则是让下一次读去重建。

残余风险有两类，各有各的补法：

- 更新库成功、但删缓存失败：用订阅 binlog（canal 这类 CDC）或者 outbox 可靠重试来驱动失效，删失败就进补偿队列。
- 删缓存之后读到旧值再回填的竞态：用延迟双删缩小窗口，用 key 版本号拒绝旧值覆盖，再用短 TTL 兜底。

收尾给一个分层结论：

- TTL 是最后一条防线，不是主机制。
- 业务容忍度决定做多重：商品详情秒级陈旧可以接受，就用轻量方案；账务类根本不该缓存，直接查。

关联专题：[[专题题库/系统设计#SYS-009：多级缓存如何保持一致，并在 Redis 故障时降级？|SYS-009：多级缓存如何保持一致？]]

## Q05：对 CAP 原理的理解；为什么保证 CP 时可用性就会损失？

### 面试回答

先给三个字母的定义，说的是分布式数据系统：

- C 一致性：这里指线性一致。
- A 可用性：每个请求都能收到非错误的响应。
- P 分区容错：网络丢包、延迟之下系统仍然工作。

前提要讲对：网络分区在分布式环境里必然发生，P 不能放弃。所以真正的抉择是——分区出现时，在 C 和 A 里二选一。

为什么选 CP 必然损失 A：

- 分区把集群切成互不通信的两边。
- 如果两边都继续接受读写，分区愈合时同一份数据就有两个分叉版本，强一致被破坏。
- 要守住 C，就只能让其中一边拒绝写入，或者读写都返回错误、等待追平。这部分请求拿不到正常响应，可用性的定义就被打破了。

举两个例子：

- CP 代表：ZooKeeper／etcd，选主期间整体短暂不可写。
- 偏 AP：Cassandra／DNS，分区两侧各自可写，愈合后靠冲突策略收敛。

再补两层，显得读得深：

- CAP 只在“分区时刻”做取舍。正常时期还有一致性 vs 延迟的权衡，这是 PACELC 的口径。
- 实践中大量系统按数据项混合选择：订单余额走 CP 语义，Feed 流走 AP＋最终一致。

## Q07：binlog 监听后数据更新到 ES，ES 的作用是什么、搜索什么内容、流量最高时直接打到 ES 吗？

原题 8—10 是同一条项目链路的连续追问；项目里“搜索什么内容”属个人事实，未记录，给可填写框架。

### 面试回答

这题是三个连续追问，分开答。

ES 的作用——因为 MySQL 的 B+ 树索引解决不了这个场景：

- 需要的是多字段任意组合过滤、分词的全文匹配、高亮与相关性排序、聚合统计。
- 用 LIKE 加全表扫描，在数据量上直接不可用。
- ES 用倒排索引把这些做成毫秒级。代价是它不承担事务，事实源仍然是 MySQL。

为什么走 binlog 同步，而不是业务双写：

- 双写会把同步逻辑侵入每一个写入口，失败补偿也很复杂。
- canal 这类 CDC（变更数据捕获）以 binlog 为单一事实源，业务零改动，代价是接受秒级延迟。
- 搜索场景对“刚发布的内容多快能搜到”的容忍度是明确的，所以这个延迟可以接受。

搜索什么内容，按真实项目填：【商品／文档／帖子等，写清索引结构与更新频率】。

流量最高时不直接裸打 ES，做法有这么几条：

- 入口先挡一层热点查询缓存，结果 key 带上查询参数与版本。
- ES 侧靠集群分片扩容扛量。
- 用限流与熔断保证集群不被打挂。
- 深分页改写成 search_after 游标。
- 做读写分离，写入走独立节点。
- 大促前预热，并按容量压测定水位。

数字与拓扑按【真实实现】的口径答。

## Q08：ES 底层的搜索数据结构了解吗，具体讲倒排索引的算法或数据结构。

### 面试回答

核心是倒排索引。先对比一下方向：正排是“文档 → 词”，倒排反过来。它由 term 字典（词典树）映射到 postings list，也就是一份包含该词的文档 ID 列表，还带上词频和位置。

拿查询“后端 AND 面试”举例，走的是这几步：

- 取两条 postings 求交集。
- 词项在字典里是有序的，postings 内部按 doc ID 升序，所以交集能用双指针归并。
- 长列表再配跳表指针，跨块加速。
- postings 用 delta 编码＋位压缩：相邻 doc ID 差值小，用 FOR／PFZ 这类打包方式。既省空间，也顺带把 doc ID 的有序性钉死。

term 字典这一侧：

- 用 FST（有限状态转换机）把前缀共享的词典压进内存常驻。
- 磁盘上按块做二分加载。

一次完整查询还要提到这几点：

- 分词器在建索引时处理。
- BM25 打分按段算，再合并。
- 段（segment）是不可变的，靠后台 merge。
- 排序和聚合不走倒排，走 doc values 的列存（正排列式）。

最后主动和 MySQL 对比：B+ 树只适合精确匹配与前缀匹配，任意词项组合会让索引爆炸——这正是 Q07 里 ES 存在的理由。

## Q09：手撕：最大子数组乘积（LeetCode 152）。

### 面试回答

开口先说本质区别：和最大子数组和不一样，难点在负数——一个很小的负数乘上下一个负数，可能翻身成最大值。

做法是：

- 同时维护以当前元素结尾的最大积 `mx` 和最小积 `mn`。
- 遍历时三者比较，决定续接还是重开。
- 当前值为负时，先交换 mx 与 mn 再各自乘，这是等价的省分支写法。
- 零自动充当断点：乘完归零，下一步 max(x, 0·x) 就重开了。
- 最后返回历史最大值。

复杂度：时间 O(n)、空间 O(1)。

边界要说全：

- 子数组非空且连续；单元素的负数数组要返回那个最大负数。初始化用 a[0] 而不是 0，这是关键的坑。
- 溢出：按题目约束在 int 范围内不处理，但口述时补一句“若可能溢出就换 long”。

验证方式：写完用 `[-2,3,-4]`（答案 24）和 `[2,-5,-2,-1,3]` 各走一遍。
