## Q04：手撕 SQL：1000 件商品按价格区间 (0,10)、(10,120)、(120,1000) 分别统计数量。

### 面试回答

表 `item_tab(id, name, desc, price)`，一行 CASE 分桶最通用（注意虾皮环境无法执行，靠口述自检）：

```sql
SELECT CASE
         WHEN price > 0   AND price < 10   THEN '(0,10)'
         WHEN price >= 10 AND price < 120  THEN '[10,120)'
         WHEN price >= 120 AND price < 1000 THEN '[120,1000)'
         ELSE 'other'
       END AS price_range,
       COUNT(*) AS cnt
FROM item_tab
GROUP BY price_range;
```

- 口径先说破：题面写的是开区间，端点 10／120 归哪边、`(120,1000)` 之外（≤0、≥1000、NULL）要不要单列——答题时主动声明假设（上按左闭右开＋other 兜底）。
- 要“没有商品的区间也显示 0”：CASE 分桶会丢掉空区间，改法是先造一张区间表再 LEFT JOIN，或一行 SELECT 三个 SUM(CASE WHEN ... THEN 1 ELSE 0 END) 列。
- 环境无法执行：用“三个桶计数之和 = COUNT(*)（含 other 修正）”做口述校验。

## Q05：手撕算法：每次最多走 m 阶台阶，走 n 阶共有多少种走法（动态规划）。

### 面试回答

f(i)＝走到第 i 阶的方法数，转移是前 m 项和：

- `f(0)=1`（在地面，一种“什么都不做”的走法作基准）；`f(i) = Σ f(i-j)`，j 从 1 到 min(i, m)。
- 答案 f(n)。m=2 时就是爬楼梯斐波那契——先代特例验证（n=3，m=2→3 种）再写通式。
- 口径确认（写码前问）：一次至少走 1 阶；顺序不同算不同走法（题面默认“是”）。
- 大数风险：方法数随 n 指数增长，主动问是否需要取模。

先写保底的循环版，O(n·m)：

```java
long climbStairs(int n, int m) {
    long[] f = new long[n + 1];
    f[0] = 1;
    for (int i = 1; i <= n; i++) {
        long sum = 0;
        for (int j = 1; j <= m && j <= i; j++) sum += f[i - j];
        f[i] = sum;
    }
    return f[n];
}
```

再口述升级：每步的求和窗口只滑动一格，维护 `window = f(i-1)+…+f(i-m)`，`f(i)=window`，随后 `window += f(i) − f(i-m)`——整体 O(n)、空间可滚动压到 O(m)。

## Q07：饿汉式单例是线程安全的吗？

### 面试回答

- 是。实例在类初始化阶段（`<clinit>`）创建，JVM 对类初始化加锁并保证只执行一次，多线程拿到的是同一个引用，无需自己同步。
- 代价：类加载即创建，没有懒加载——对象重或可能用不上时浪费。
- 对比一句收口：懒汉式不写 `synchronized` 就不安全，正确写法是双重检查锁（实例字段要 `volatile`）或静态内部类 Holder（兼得懒加载与线程安全）。

## Q08：谈谈对 Spring 中 JDK 动态代理的理解。

### 面试回答

- 是什么：运行期用 `Proxy.newProxyInstance(类加载器, 接口数组, InvocationHandler)` 生成实现同一批接口的代理类；方法调用全部转发到 handler 的 `invoke(proxy, method, args)`。
- Spring 用在哪：AOP 织入的横切逻辑就写在 invoke 链里（拦截器链依次执行后反射调目标方法）；目标有接口时默认走 JDK 代理（Boot 里 `proxyTargetClass=true` 则统一 CGLIB）。
- 边界：JDK 代理只代理接口方法——注入时字段类型必须是接口；final 方法、非接口方法它管不到，这是“自调用失效”“注入实现类报错”这类坑的根源之一。
- 底层一句：`$Proxy0` 源码是生成的，每个方法体就是 `h.invoke(this, 方法句柄, args)`；方法句柄在静态块里一次性反射查好。

## Q09：谈谈 HashMap 的扩容机制。

### 面试回答

四句话（JDK 8）：

- 何时扩：`++size > threshold`（容量×负载因子 0.75）触发；链表树化前若容量不足 64 也先扩容代替树化。
- 扩多少：容量翻倍（保持 2 的幂）。
- 怎么迁：新建数组，节点按 `hash & oldCap` 是 0／1 决定“留原位”还是“移到原位＋oldCap”，链表一次拆成 low／high 两条且保序，不重算 hash。
- 并发口径：扩容本身对普通 HashMap 没有任何并发保护，多线程要换 ConcurrentHashMap。

## Q10：谈谈 CountDownLatch。

### 面试回答

- 解决什么：“等 N 件事都完成”的一次性闩：构造给计数 N，干活方完成时 `countDown()` 减一，等待方 `await()` 阻塞到计数归零被唤醒。
- 三个关键性质：计数一次性（归零后不能复用）；`countDown` 不阻塞（减完就走）；允许多个等待者同时被放行。
- 底层一句：基于 AQS 的共享模式——state 存计数，`tryAcquireShared` 判断是否归零，`tryReleaseShared` 减到零时唤醒队首传播唤醒。
- 场景区分：主线程等 N 个子任务汇合用它；两个线程互相等步点用 CyclicBarrier（可复用）；限并发用 Semaphore（发许可不是记完成）。
- 一个易错：子任务抛异常也要 countDown，放在 finally，否则 await 永久挂起。

关联专题：[[专题题库/Java并发#JUC-022：CountDownLatch 解决什么问题，和 CyclicBarrier、Semaphore 怎么区分？|JUC-022：CountDownLatch 解决什么问题，和 CyclicBarrier、Semaphore 怎么区分？]]

## Q11：谈谈 AQS。

### 面试回答

- 定位：`AbstractQueuedSynchronizer`，JDK 同步器的公共骨架——一个 volatile state ＋ 一条 FIFO 等待队列（CLH 变体）＋ 模板方法。
- 三块核心：state 表达资源量（锁重入次数／许可数／闩计数）；队列管“抢不到的人怎么排队与挂起”（park）；共享／独占两套获取释放协议由子类实现 `tryAcquire／tryRelease／tryAcquireShared／tryReleaseShared`。
- 竞争处理：入队 CAS 自旋，前驱是 head 才再尝试；支持条件队列 `ConditionObject`（await 释放锁入条件队，signal 转同步队）。
- 谁在用它：ReentrantLock（state=重入数）、Semaphore（state=许可数）、CountDownLatch（state=计数）——说出这三个映射关系比背流程更显理解。
- 边界提醒：AQS 管的是线程协作，不解决跨进程；它自身原子性靠 CAS＋volatile（入队出队的并发安全细节见关联专题）。

关联专题：[[专题题库/Java并发#JUC-012：AQS 的数据结构是什么，锁竞争与入队出队的并发安全怎么保证？|JUC-012：AQS 的数据结构是什么，锁竞争与入队出队的并发安全怎么保证？]]

## Q12：MyBatis 的两级缓存是干嘛的？分别存的是什么？

### 面试回答

- 目的都一样：减少重复 SQL 回库；差别在作用范围与生命周期。
- 一级缓存＝SqlSession 级：存“本次会话执行过的语句→结果对象”（update／query 的本地缓存 Map），同会话重复 query 直接返回；会话提交／关闭／手动 `clearCache` 即失效。默认开。
- 二级缓存＝namespace（mapper）级、跨会话共享：存序列化后的结果记录（按 `缓存id＋` 记录槽组织，命中后返回各对象副本），由 `<cache>`／`cacheEnabled` 显式开启。
- 关键口径：二级缓存是“语句执行完才写入”，两个 namespace 关联同一张表时会读到旧值；分布式多实例各存各的、天然不同步——所以生产常见做法是关掉二级缓存，把共享缓存交给 Redis 这层显式做。

## Q13：谈谈 SpringBoot 的启动过程。

### 面试回答

`SpringApplication.run` 按七步讲：

- 准备：推断应用类型（servlet／reactive／none）、加载 `ApplicationContextInitializer` 与 `ApplicationListener`（SPI 式从 `spring.factories`／imports 载入）。
- 环境：`ApplicationEnvironmentPreparedEvent` 触发配置文件与 profile 加载进 Environment。
- 建容器：按类型创建上下文，注册主 Bean 定义（启动类、自动配置入口）。
- 刷新 `refresh()`——重头戏：执行 BeanFactoryPostProcessor（含自动配置评估：导入候选配置＋条件过滤）、注册 BeanPostProcessor、实例化单例 Bean（生命周期走 SPRING-011）。
- 内嵌容器随 Servlet 相关后处理启动并开始监听端口。
- Runner 回调：`ApplicationRunner`／`CommandLineRunner` 在容器就绪后执行。
- 发布 `ApplicationReadyEvent`——监听器里做预热／注册；失败路径发布对应的 Failed 事件后退出。
- 收尾一句：理解“事件贯穿＋refresh 是主干”，再排查启动慢（哪步耗时）就有地图。

## Q14：项目中用到了 ES，谈谈对倒排索引的理解。

### 面试回答

- 一句定义：正排是“文档→词”，倒排反过来——“词 Term→包含它的文档列表（Posting List）”，检索词直接定位候选集。
- 结构三层：Term Dictionary（词项字典，FST 压缩前缀共享，常驻缓存加速查找）→ Posting List（docID、词频、位置，用 FOR／Roaring 位图压缩）→ 段（segment）不可变，写入建新段＋定期 merge。
- 为什么快：查词是词典 O(前缀长度)＋链表交集合并，不用扫全表；不可变段让缓存与压缩都激进可行。
- 代价与配套：段不可变→更新＝删＋插、近实时（refresh 1s 才可见）；相关性打分（BM25）在打分阶段用词频／位置；`keyword` 字段不分词走的是另一套（doc_values 排序聚合）。
- 项目落点【真实填】：我们索引的是【商品／日志／文本】，分词器选【IK／standard】，踩过的坑是【深分页／mapping 爆炸等按实际】。

## Q15：ES 建索引时，分片和副本一般怎么设置？

### 面试回答

- 分片（primary）：建索引后不可改（只能重建或 reindex）；经验锚点——单分片控制在 10～50GB（日志类可到 50，搜索类偏小），按“预估总数据量÷目标分片大小”定数量，同时不超过节点数×每节点合理分片位。
- 副本（replica）：默认 1 够用——每主分片一份拷贝，扛单分片故障＋分摊读；写敏感场景可临时调 0 批量导入，导完再拉回。
- 决策口径：读多写多→分片按数据量、副本 1；纯写日志管道→副本可 0～1 换吞吐；查询重聚合→分片宁多勿少但警惕“碎分片爆炸”（分片总数有集群级上限，每分片有固定堆内存开销）。
- 一个反例要会说：分片数不是越多越快——每分片是一个独立 Lucene 实例，聚合要在分片间汇总，1000 个空分片比 5 个大分片慢得多。

## Q16：任何 MQ 遇到消息积压，一般有哪些处理手段？

### 面试回答

先判性质再动手，通用手段一套：

- 判断：积压是“生产突增”还是“消费变慢／停摆”？看生产速率、消费组 lag、消费耗时与错误率——病因不同药不同。
- 紧急止血：扩消费者实例（上限＝分区／队列数，消费组并行度封顶）；消费能力本身不足就扩线程＋批量化（拉一批处理一批）。
- 分流旁路：消费端只做“落快速存储／转发临时大分区 topic”，事后离线补处理——即“先接住再消化”。
- 生产侧配合：能降级就暂停非核心生产、削峰限流，给下游让出恢复空间。
- 根因修复：查慢的依赖（DB 慢查询、外部接口抖动）、毒消息（反复重试卡死队列→隔离到死信队列人工处理）、消费逻辑重（把非关键动作异步化）。
- 事后动作：积压量与恢复时长要能报数；给 lag 配告警阈值，别让积压到爆发才知道。

## Q17：MySQL 的间隙锁是解决什么问题的？原理是怎样的？

### 面试回答

- 解决的问题：可重复读（RR）下的“范围空洞幻读”——光锁已有行挡不住别人往间隙里 INSERT，两次范围查询之间冒出幻影行。
- 原理：对索引记录之间的开区间加 gap 锁（共享性质的意图锁，彼此兼容）；再配 record lock／next-key lock（记录＋前间隙的组合）把“已存在行＋行缝隙”一起罩住；插入前要拿插入意图锁（insert intention），与落在该间隙上的 gap 锁互斥，于是并发插入被挡或排队。
- 一个例子讲透：`SELECT ... WHERE id BETWEEN 10 AND 20 FOR UPDATE` 会锁住区间内记录及两端间隙，他人插 id=15 阻塞。
- 代价与工程口径：锁范围放大→并发冲突上升、死锁概率升高（两事务各持不相邻 gap 锁再互插对方间隙）；所以不少互联网实践直接用 RC＋row-based binlog 放弃 gap 锁，把防幻觉交给业务条件更新。

## Q18：让你设计一个 RPC 框架，应包含哪些关键部分？要提高传输性能可以在哪些方面优化？

### 面试回答

设计题按“调用方视角一次完整调用”拆模块，每个模块说清“为什么缺它不可”：

- 接口代理层：让用户像调本地方法一样调远程——动态代理把方法调用转成请求（对应用户只写 interface 的 DX）。
- 序列化：对象↔字节（可插拔：JSON 通用、protobuf／Hessian 紧凑；跨语言决定选型）。
- 网络与协议：长连接＋自定义二进制协议头（魔数、版本、消息类型、序列号、长度）解决粘包与请求响应配对；传输走 Netty NIO。
- 服务治理三件套：注册中心（服务发现，心跳与剔除）、路由与负载均衡（随机／轮询／一致性哈希）、容错（超时、重试幂等约束、快速失败／故障转移）。
- 异步化底座：请求发出即返回 future，响应到达按序列号唤醒——不这么设计并发能力被同步阻塞锁死。
- 性能优化按“一次调用的耗时构成”给：序列化换二进制＋schema 预编译；连接复用与多路复用（同一连接并行多请求，解决队头等待）；协议头瘦身与对齐、零拷贝；服务端业务与 IO 线程分离＋线程池隔离；压缩只压大报文；注册信息本地缓存＋长轮询更新，减少寻址 RPC。
- 收尾一句：Dubbo／gRPC 就是把这套骨架按不同生态装配的实例，能对照说明更可信。

## Q19：HTTPS 的加密过程。

### 面试回答

混合加密三步走（TLS 握手）：

- 协商：ClientHello／ServerHello 定 TLS 版本与密码套件；服务端发证书链。
- 验证书：校验签发链到受信根 CA、域名、有效期与吊销状态——公钥的真实性靠 CA 签名链背书，这一步防的是中间人冒充。
- 换密钥：传统 RSA 密钥交换是客户端用证书公钥加密预主密钥；现代 TLS 1.3 用 ECDHE 临时密钥协商（前向安全：长期私钥泄露也解不了历史流量）。
- 之后全部记录用协商出的对称密钥（AEAD）加密＋完整性保护。
- 一句收口：非对称只在握手期解决“怎么安全地共享对称密钥＋对方是谁”，数据传输永远走对称——各用各的长处。

## Q20：HTTP 返回码 302 是什么意思？

### 面试回答

- 302 Found：临时重定向——响应头带 `Location`，浏览器自动对新地址重发请求；“临时”意味着搜索引擎／缓存不应把老 URL 的访问永久改道（那是 301 的语义）。
- 使用场景：登录后跳回原页面、灰度／A-B 临时分流、URL 规范化过渡。
- 细节加分：重定向时方法可能被改写（302 历史上 POST 常变 GET，严格保持语义用 307；两者都不改状态码族还有 308 对应永久）。
- 对比一句：301 永久（会被浏览器缓存、SEO 换权重）／302 临时（可被缓存但不该固化）／304 不是重定向，是协商缓存命中。

## Q21：git merge 和 git rebase 的区别？

### 面试回答

- 合并结果：merge 生成一个合并提交、保留两条真实历史线；rebase 把当前分支的提交逐个“重放”到目标分支顶端，得到线性历史。
- 历史观：merge 忠实记录发生过什么；rebase 改写历史（提交哈希会变）——因此有黄金法则：已推给他人、公共分支上的提交不要 rebase。
- 冲突处理位置：merge 一次解决在合并提交里；rebase 可能每个重放提交都要解决一次。
- 实践口径：个人特性分支追主线用 `rebase`（历史干净、便于 bisect）；特性分支并回主干走 merge／平台 MR 合并（保留线索）；团队统一约定最重要，两者不是信仰之争。
- `--force-with-lease`：rebase 后推送要强推，用带租约版本防覆盖他人提交。

## Q22：API 和 SPI 的区别？

### 面试回答

一句话：看“接口与实现谁是主导”。

- API：服务方定义接口、自己实现，调用方只管用——控制流“调用方→被调方”，实现细节对使用者封闭。
- SPI：框架方只定接口，把实现的选择权外置给第三方——“接口向上、实现向下”，框架运行期按约定装载实现。
- 机制实例：JDK `ServiceLoader`／Spring 自动装配——`META-INF/services`（或 Boot 的 imports 文件）登记实现类，框架按接口查找并加载全部候选；JDBC 驱动、SLF4J 绑定都是经典 SPI。
- 依赖方向加分：SPI 是“依赖倒置”的工程落地——微内核＋插件架构（Dubbo 扩展点同类）都靠它把扩展点从核心里剥出去。
