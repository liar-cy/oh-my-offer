## Q05：为什么用 Spring Session 整合用户登录状态？它是怎么执行的？

**为什么用它**：一句话——把登录态从“单机内存”变成“共享存储”，解决多实例部署下会话不共享和重启丢会话的问题。

- 容器 HttpSession 存在单进程内存里，集群部署要做 session 复制或粘滞，都不省心。
- Spring Session 把 Session 外置到 Redis（或 JDBC），各实例读写同一份，天然共享；重启不踢人。
- 登录态本体仍是服务端会话：客户端 Cookie 里只有会话 ID，配合 HttpOnly／Secure／SameSite 控制暴露面。

**怎么执行**：

- 注册 `SessionRepositoryFilter`（OncePerRequestFilter 包装的 HeaderFilter）包住每个请求，先于业务代码接管会话。
- 请求进来：从 Cookie（默认名 `SESSION`，Base64 编码）／请求头／URL 取 session id，交给 `SessionRepository` 去存储层换回 Session 对象。
- 业务代码操作的是它的包装类；请求结束时 `CommitSessionResponseWrapper` 把会话元数据和 attribute 写回存储，并刷新 TTL。
- 用 Redis 存储时 attribute 要序列化，所以属性必须可序列化、体积要控制。

## Q06：密码用 MD5＋盐值校验有什么风险？让你重新设计加密存储方案怎么设计？

**先纠口径**：密码不是“加密存储”，是“哈希存储”——系统本来就不需要还原密码。

**MD5＋盐的风险**：

- 盐能挡彩虹表和跨用户批量命中，这部分是有效的。
- 但 MD5 太快：库被拖走后，GPU 每秒可算海量候选，对单个弱口令的离线爆破挡不住，盐只是把成本摊到每个用户略高一点。
- 另有实现层风险：盐生成不规范（复用、太短）、比较非常量时间留下时序侧信道。

**重新设计方案**：

- 存储：慢哈希＋每人一把随机盐——BCrypt（cost 可调）起步；更优 Argon2id（内存硬，OWASP 推荐）或 scrypt。
- 再加一层：服务端 pepper 或 KMS 保管，拖库不等于拿到全部秘密。
- 在线防护：登录限流＋失败锁定＋强度校验＋泄露口令库拦截。
- 存量迁移：用 Spring Security 的 `DelegatingPasswordEncoder`，按前缀识别旧哈希，用户登录或改密时渐进重哈希升级，不一刀切强制重置。
- 校验流程一句：取盐与哈希 → 同算法重算 → 常量时间比较 → 通过后签发登录态。

## Q07：数据万象服务的作用是什么？在项目中如何使用的？

**作用**：数据万象（CI）是腾讯云挂在对象存储 COS 上的媒体处理服务——图片存在 COS 里，处理不用自己搭。

- 基础处理：缩略、格式转换、水印、质量变换，多通过 URL 参数或接口在取图时顺带完成。
- 智能类：图片审核（鉴黄鉴暴）、OCR、人脸与人／物识别、质量评分。
- 价值一句话：把“下载回来自己跑处理”变成“存储侧近计算”，省流量、省自建算力。

**项目中如何使用**（按【真实用法】填，框架是四件事）：

- 接了哪些能力：【如上传后触发审核＋缩略图生成】。
- 调用方式：同步接口还是数据万象工作流／事件通知异步回调。
- 结果落地：回调入库后更新图片状态，前端按状态取原图或处理结果。
- 失败兜底：审核或服务异常时的重试与降级口径。

注意：这题答完，面试官常追“它和自建方案怎么取舍”——一句回答：量小或要定制模型就自建，通用图片处理用托管服务更省。

## Q08：如何设计“输入小狗，搜出所有带小狗图片”的定制化搜索？

一句话：把“图里有没有小狗”离线变成可检索的结构，在线只做查询。两条路线叠加：

- 标签路线（保准确）：离线用物体检测／图像打标模型给每张图片生成标签集合（小狗／猫／海边……），存进倒排或库表，查询就是 `label = 小狗` 的精确匹配，可加置信度阈值。
- 语义向量路线（保召回）：用文图双塔模型（如 CLIP 类）把图片编码成向量入库，查询时把“小狗”编码成同空间文本向量做 ANN 检索——没打标签但画面语义相近的图也能召回。

工程链路：上传触发离线打标／向量化（异步队列削峰）→ 标签入索引、向量入 HNSW／IVF → 在线“标签过滤 ∪ 向量召回”合并 → 按相关度与时间排序，叠加相册、权限等业务过滤。

收尾补一句取舍：标签路线可解释、误搜少，但词表外就搜不到；向量路线泛化好，但要阈值和重排兜住精度——所以要两路合并。

## Q09：什么场景需要多级缓存？怎么保证多级缓存和数据库的一致性？

**什么场景用**：单级缓存扛不住时才上多级，典型信号三条：

- 热点集中且读远大于写：Redis 网络往返本身也成了瓶颈，用本地缓存（Caffeine）把最热的一小撮挡在进程内。
- 对尾延迟敏感：不能容忍 Redis 抖动／偶发慢查询，需要进程内兜底。
- 回源成本高：DB 容量有限，需要层层拦截降低回源量。
- 反过来，数据量巨大且访问均匀、或读路径要求强一致的场景，多级缓存收益小、一致性的麻烦大，不如单级或直接读库。

**一致性怎么做**：先立预期——多级缓存买到性能，付出的是“有界不一致”，TTL／版本就是那个“界”。

- 以 DB 为事实源：写事务提交后删除／更新 Redis。
- 再通过失效消息（MQ／Redis pub-sub）或 CDC（canal 订阅 binlog）向各实例广播本地缓存失效，实例按版本号幂等消费。
- 本地缓存用短 TTL 封顶陈旧窗口；强一致的读写绕过本地缓存直接读库。
- 关键点：不同实例不能靠各自的 TTL 保证“同时一致”；失效消息要可重试、有监控。

## Q10：WebSocket 多人协作编辑，100 人同时改同一张图，怎么设计让操作不相互覆盖？

一句话：先拆粒度——“整张图”换成“图上的操作”，再让操作可以定序、可以合并；100 人不需要抢同一把大锁。

- 定权威源：图片的已提交版本放 DB／对象存储，各实例只是接入层；冲突控制围绕“版本＋操作”做。
- 拆操作粒度：把修改拆成细粒度操作（某个图层／选区／画笔笔迹），每个操作带版本号或单调序列。
- 三种冲突模型按业务选：
  - 串行化：同资源操作排队执行（锁或 MQ 单分区），最简单，写冲突少时够用。
  - 乐观版本校验：提交时比对基线版本，失败就拉最新重放本地操作，适合低频冲突。
  - OT／CRDT：高频并发编辑要无损合并时的工业方案，中心化服务器定序（OT）或无中心收敛（CRDT）。
- 广播侧：服务端把已定序的操作增量通过 WebSocket 推给所有人，各端按版本顺序回放，而不是互相覆盖整图快照。

## Q11：具体怎么加锁？用 Redis 还是其它？锁什么、粒度怎样？

**先分清两层锁**：

- 单机进程内：同一实例上多个 WebSocket 线程改同一份内存态，用 `ReentrantLock` 就够。
- 多实例部署：锁必须放共享介质——Redis 分布式锁（SET NX PX＋唯一 token＋Lua 判断后解锁，或直接用 Redisson 看门狗），或 DB 行锁／ZooKeeper，按已有设施选。

**锁什么**：锁“对同一资源的一次写”，不是锁用户、也不是锁整张图。资源键设计成定位到可独立并发的最小单元。

**粒度**：

- 从整图锁细化到 图片 × 图层／区域 × 写操作，粒度越细并发越高。
- 配三件套：锁超时防死锁、持锁时间压到最短（别在锁内做 IO 广播）、拿不到锁快速失败给用户提示，别无界排队。
- 收尾一句：粒度极限是把冲突面缩到零——操作拆得足够细时，锁只是兜底，合并逻辑才是主线。

## Q12：加锁让其它用户阻塞等待，怎么优化？

阻塞的根源是“整段编辑期持锁”。优化方向从“少持、短持、不持”三层给：

- 读写分离：编辑广播不互斥（读写锁／StampedLock），只有合并提交这类临界段需要排他。
- 乐观化：锁换成版本号 CAS——提交时比对基线版本，冲突才处理，不冲突零等待。
- 消息序列化：写操作进按资源 hash 的队列（MQ 单分区／actor 模型），单写者顺序消费，请求方不等锁而是等回执。
- 操作合并：端上把连续小操作攒批提交，降低锁竞争频率；配合 OT／CRDT 让“合并”替代“互斥”。
- 粒度细化：锁区域不锁整图，两个人改不同区域天然并行。

一句收口：阻塞等待是“悲观锁兜底”的代价，真正的协作产品是把冲突面缩小到接近零，再让残留冲突走合并而不是排队。

## Q13：平时有学习过什么新技术吗？虚拟线程场景下加锁用什么锁更好？

**新技术**：按 CAREER-017 的学习闭环答——输入（官方文档／JEP 一手资料）→ 最小可跑验证 → 输出结论，给一个真实例子，别报课单。

**虚拟线程用什么锁**：结论——优先 `ReentrantLock`＋短临界区，或有意的无锁结构；不是禁止 `synchronized`，而是按 JDK 版本说清代价。

- JDK 21～23：`synchronized` 长临界区会钉住（pin）载体线程，虚拟线程阻塞时释放不了 ForkJoinPool 的载体线程，高并发下吞吐被拖垮；`ReentrantLock` 的等待走 `LockSupport.park`，能正常卸载虚拟线程。
- JDK 24 起（JEP 491）：`synchronized` 不再钉住载体线程，但长临界区持线程等 IO 仍然是坏模式，官方口径依然建议缩小临界区或换 `ReentrantLock`。
- 补充：虚拟线程时代不该再“池化线程”，限并发用 `Semaphore`；`ThreadLocal` 要谨慎（大量虚拟线程各带一份会放大内存），可看 Scoped Values。
- 答题时报清自己用的 JDK 版本，这句是加分项。
