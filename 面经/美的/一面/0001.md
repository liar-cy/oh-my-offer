## Q01：查询数据库接口 RT 越来越高怎么处理？

### 面试回答

先定性：“越来越高”是趋势问题，要先定界、再定位。

- 定界层级：是数据库执行慢、锁等待、连接池排队，还是应用侧（GC、线程池、网络）。看接口分段耗时，再和监控里的发布／流量曲线对比，找拐点。
- 数据库侧：查慢查询日志和 EXPLAIN。常见原因有几个——数据量涨上来之后原索引选择性下降、执行计划突变（统计信息过期）、隐式转换或函数包列让索引失效、深分页、锁竞争。
- 对症处理：重建或更新统计信息、补联合索引、改写 SQL、归档冷数据，或者用读写分离分流。

趋势型问题还得回答“怎么防复发”：给 RT 分位数设告警，把慢 SQL 巡检纳入日常。

如果问的是“查询能不能命中联合索引”：

## Q03：Kafka 消息堆积怎么办？

### 面试回答

先看指标定瓶颈，再看现象分成因。

- 要看的指标：lag 增长速率、消费速率、生产速率、最老消息年龄、重投失败率。
- 三种成因要区分开：生产暴涨、消费变慢、消费者掉线或 rebalance。

处理方式对应着来：

- 消费侧先定位慢点：下游 DB／接口、单条处理耗时、GC。
- 能并行就加分区数＋消费者，注意分区是并行度的上限；再调大批量和拉取参数。
- 生产暴涨的，在入口限流削峰。
- 反复失败的消息隔离进死信／暂存区，别让它堵住主线。
- 积压什么时候能消化，按 lag/(μ−λ) 估算清空时间，再决定要不要临时扩容。

事后要补监控告警和容量基线，避免一直在救火。

## Q04：幂等怎么设计的？

### 面试回答

按【项目实际】答；通用组合是这么几条：

- 客户端携带稳定的请求号／业务唯一键。
- 服务端做持久化去重：靠唯一索引，或者一次性 token 的原子核销。重复请求直接返回首次结果。
- 用状态机的条件更新，保证乱序的流转也能判定。
- 去重记录要和业务写入放在同一个事务里，或者放共享存储，这样多实例才有效。
- MQ 消费端同理：用 message_id＋唯一约束做幂等。

补一句边界：前端置灰和内存标记只优化体验，不是正确性保证。

## Q05：分布式锁怎么设计的，SET NX EX 为什么要原子执行？

### 面试回答

设计要点先说命令：`SET key token NX EX ttl`，一条命令同时完成抢占和设过期。

为什么要原子执行：

- 如果拆成 SETNX＋EXPIRE 两步，两步之间进程崩了，就留下一把永不过期的锁，把别人全锁死。
- 单命令没有这个窗口。

其余几条配套：

- value 存本次持锁的唯一标识（uuid＋线程）。解锁时先比对再删，用 Lua 原子执行，防止误删别人的锁。
- TTL 是租约，不是免死金牌。长业务要配看门狗续期＋fencing token（带序号的令牌）。
- Redis 锁属于性能优化型的互斥。强正确性场景还要靠数据库条件写兜底，或者用多数派方案。

## Q06：讲讲 Redisson 看门狗机制。

### 面试回答

先说什么情况下生效：加锁时不指定 lease，或者超过默认 `lockWatchdogTimeout`（30s）的那部分，都会被规范成 30s 租约。

看门狗做的事：

- 后台每约 1/3 周期检查一次，持锁线程是否还存活。
- 存活就用 Lua 原子校验，再把 TTL 重置回 30s。
- 进程崩溃就不再续期，锁自然过期释放，不会死锁。

它解决的是“业务没做完、锁先到期”。

但它不解决 GC 停顿这类极端场景下的短暂双持有——关键写仍然要靠幂等或 fencing。

底层怎么配合：

- RLock 用 Hash 存，field 是 uuid:threadId，value 是重入次数。
- 解锁时判断次数归零才真正删除。

## Q07：流量控制怎么做的？

### 面试回答

按【项目实际】答；通用做法是分层限流：

- 入口网关：按接口／用户／租户做配额限流，算法用滑动窗口或令牌桶，Redis＋Lua 做原子计数。
- 应用侧：线程池和连接池设上限，用有界队列形成背压。
- 下游依赖：各自独立限额，别被一起拖垮。
- 超限时：返回明确的可重试错误码。

算法怎么选：

- 固定窗口实现简单，但有边界突发的问题。
- 滑动窗口更平滑。
- 令牌桶允许配置范围内的突发。
- 漏桶是恒定速率，适合保护慢依赖。

最后一点差别：单机限流和分布式限流，区别在计数存储要不要共享。

## Q08：AI 智能客服的幻觉是怎么产生的，怎么解决？

### 面试回答

先说为什么会幻觉：模型是按“下一个 token 的概率”生成的，不是去查库。具体来源有这几条：

- 训练语料里的知识过时，或者压根不存在这个事实。
- 检索没召回正确的证据。
- 证据不足时，模型仍然倾向于补出一个流畅的答案。
- 提示里有诱导性的措辞。

解决就按“检索”和“生成”分开治理：

- 知识库质量和切块、召回做优化：混合召回＋重排。
- 答案强制引用证据，而且引用要可以校验。
- 证据不足就走拒答或转人工的话术。
- 高风险回答（价格、政策、工单承诺）用规则或接口数据兜底。
- 上线之后用标注样本持续评测“编造率”。

智能客服的特殊点要单独强调：错误答案是直接面向客户的，宁可不答，不可乱答。

## Q09：Transformer 架构的组件和功能。

### 面试回答

按组件报，一个一句职责：

- 分词＋Embedding：把 token 变成向量。
- 位置编码：注入顺序信息，因为自注意力本身是无序的。
- 多头自注意力：用 Q／K／V，让每个位置加权聚合整个序列的信息。这是建模依赖的核心。
- 前馈网络：做逐位置的非线性变换。
- 残差连接＋LayerNorm：让深层训练稳定。
- Decoder 侧的因果掩码：保证只能看到左侧，生成任务用。
- Encoder-Decoder 之间的交叉注意力：给 seq2seq 用。

主流大模型是 Decoder-only：堆叠“因果自注意力＋FFN”，逐 token 自回归生成。

补一句边界：KV Cache 是推理期的优化，不属于训练架构。

## Q10：跨域问题怎么解决？

### 面试回答

先定性：跨域是浏览器的同源限制，协议＋域名＋端口任一不同就算跨域。服务端要理解一句话——请求其实能到达，是响应被浏览器拦住了。

标准解法是 CORS：

- 服务端返回 `Access-Control-Allow-Origin` 等响应头，声明许可范围。
- 非简单请求（自定义头、PUT／DELETE，以及 JSON 的常用场景）浏览器会先发 OPTIONS 预检。要放行对应的方法和头，并设缓存时间。
- 带 Cookie（credentials）时，Origin 不能是 `*`，而且要有 `Allow-Credentials: true`；同时还得防 CSRF。

其他几条路：

- 开发期用 devServer 代理。
- 同主域的子域场景可以降 domain，属于老办法。
- 在网关／Nginx 统一加头，适合集中治理。
- JSONP 只支持 GET，已经基本淘汰。
