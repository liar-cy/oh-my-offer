## Q01：查询数据库接口 RT 越来越高怎么处理？

### 面试回答

“越来越高”是趋势问题，先定界再定位：① 区分层级——是数据库执行慢、锁等待、连接池排队还是应用侧（GC、线程池、网络），用接口分段耗时与监控对比发布/流量曲线找拐点；② 数据库侧看慢查询日志与 EXPLAIN：常见原因是数据量增长后原索引选择性下降、执行计划突变（统计信息过期）、隐式转换或函数包列使索引失效、深分页、锁竞争；③ 对症处理：重建/更新统计信息、补联合索引、改写 SQL、归档冷数据或读写分离分流。趋势型问题还要回答“怎么防复发”：RT 分位数告警、慢 SQL 巡检纳入日常。

## Q03：Kafka 消息堆积怎么办？

### 面试回答

先看指标定瓶颈：lag 增长速率、消费速率、生产速率、最老消息年龄、重投失败率——区分“生产暴涨”“消费变慢”“消费者掉线/rebalance”三种成因。处理：消费侧定位慢点（下游 DB/接口、单条处理耗时、GC），能并行就加分区数＋消费者（注意分区是并行度上限），提高批量与拉取参数；生产暴涨则入口限流削峰；反复失败的消息隔离进死信/暂存区防堵主线；积压消化按 lag/(μ−λ) 估算清空时间决定要不要临时扩容。事后补监控告警与容量基线，避免只救火。

## Q05：分布式锁怎么设计的，SET NX EX 为什么要原子执行？

### 面试回答

设计要点：`SET key token NX EX ttl` 一条命令完成抢占与设过期；必须原子是因为若拆成 SETNX＋EXPIRE 两步，两步之间进程崩溃就留下永不过期的锁死他人——单命令无此窗口；value 是本次持锁唯一标识（uuid＋线程），解锁先比对再删（Lua 原子执行）防误删他人锁；TTL 是租约不是免死金牌，长业务配看门狗续期＋fencing token；Redis 锁是性能优化型互斥，强正确性场景需数据库条件写兜底或多数派方案。

关联专题：[[专题题库/Redis#REDIS-006：Redis 分布式锁如何正确加锁、解锁和续期？|REDIS-006：Redis 分布式锁如何正确加锁、解锁和续期？]]

## Q06：讲讲 Redisson 看门狗机制。

### 面试回答

加锁时不指定 lease 或超过默认 `lockWatchdogTimeout`（30s）的部分会被规范为 30s 租约，Redisson 后台看门狗每约 1/3 周期检查持锁线程是否仍存活，存活就用 Lua 原子校验后把 TTL 重置回 30s；进程崩溃则停止续期、锁自然过期释放，不会死锁。它解决“业务没做完锁先到期”，但不解决 GC 停顿等极端场景的短暂双持有——关键写仍需幂等或 fencing。底层配合：RLock 用 Hash（field＝uuid:threadId，value＝重入次数），解锁判断归零才删除。

## Q07：流量控制怎么做的？

### 面试回答

按【项目实际】答，通用分层：入口网关按接口/用户/租户配额限流（滑动窗口或令牌桶，Redis＋Lua 原子计数），应用侧线程池与连接池设上限、有界队列形成背压，下游依赖独立限额防被拖垮；超限返回明确可重试错误码。算法选择：固定窗口实现简单但有边界突发，滑动窗口更平滑，令牌桶允许配置内突发，漏桶恒定速率适合保护慢依赖；单机限流与分布式限流的差别在计数存储要共享。

## Q08：AI 智能客服的幻觉是怎么产生的，怎么解决？

### 面试回答

产生原因：模型按“下一个 token 的概率”生成而非查库——训练语料里的知识过时/不存在该事实、检索没召回正确证据、证据不足时模型仍倾向补全一个流畅答案、提示里诱导性措辞。解决按检索与生成分开治理：知识库质量与切块召回优化（混合召回＋重排）、答案强制引用证据且引用可校验、证据不足走拒答/转人工话术、高风险回答（价格、政策、工单承诺）用规则或接口数据兜底、上线后用标注样本持续评测“编造率”。智能客服的特殊点：错误答案直接面向客户，宁可不答不可乱答。

## Q09：Transformer 架构的组件和功能。

### 面试回答

组件与职责：分词＋Embedding 把 token 变向量；位置编码注入顺序信息（自注意力本身无序）；多头自注意力用 Q/K/V 让每个位置加权聚合全序列信息，是建模依赖的核心；前馈网络做逐位置非线性变换；残差连接＋LayerNorm 让深层训练稳定；Decoder 侧另有因果掩码保证只能看左侧，生成任务用；Encoder-Decoder 间交叉注意力供 seq2seq。主流大模型为 Decoder-only：堆叠“因果自注意力＋FFN”，逐 token 自回归生成；KV Cache 是推理期优化，不属于训练架构。

## Q10：跨域问题怎么解决？

### 面试回答

跨域是浏览器同源协议限制（协议＋域名＋端口任一不同即跨域），服务端要理解“请求能到达、响应被浏览器拦截”。标准解法是 CORS：服务端返回 `Access-Control-Allow-Origin` 等响应头声明许可范围；非简单请求（自定义头、PUT/DELETE、JSON 常用场景）浏览器先发 OPTIONS 预检，需放行方法、头并设缓存时间；带 Cookie（credentials）时 Origin 不能为 `*` 且要 `Allow-Credentials: true`，同时防 CSRF。开发期可用 devServer 代理；同主域子域场景可降 domain（老办法）；网关/Nginx 统一加头适合集中治理。JSONP 只支持 GET、已基本淘汰。

关联专题：[[专题题库/Web安全#WEBSEC-003：跨域问题是什么，CORS 怎么解决？|WEBSEC-003：跨域问题是什么，CORS 怎么解决？]]
