## Q03：GC 算法有哪些？每种展开谈谈

### 面试回答

先给判活前提：可达性分析，从 GC Roots 出发不可达即可回收。再报四种基础算法，每种带一句代价：

- 标记—清除：不移动对象，但会产生碎片。
- 复制：没有碎片，但要空出一半空间，适合存活率低的年轻代。
- 标记—整理：无碎片不留空洞，代价是移动对象和更新引用，比较贵。
- 分代收集：建立在弱分代假说上，年轻代复制、老年代标记—整理，跨代引用靠记忆集。

如果时间够，补一句回收器演进：Serial／Parallel 吞吐优先全程 STW → CMS 并发标记清除压低停顿 → G1 Region 化＋可预测停顿目标 → ZGC 并发整理、亚毫秒停顿。

## Q04：JVM 的内存区域怎么划分？

### 面试回答

结论：按线程私有还是共享来分，五块区域。

- 线程私有：程序计数器（唯一不抛 OOM 的区域）、虚拟机栈（栈帧装局部变量表、操作数栈）、本地方法栈。
- 线程共享：堆（对象分配与 GC 的主战场，分年轻代／老年代）、方法区（规范概念，HotSpot 用元空间实现，存类元数据与运行时常量池）。
- 补一句堆外：直接内存不是规范里的独立区域，但 NIO 实际在用，OOM 也可能出在它身上。
- 若题目说成“JVM 内存模型”，先确认问的是运行时区域还是 JMM（多线程可见性），别混着答。

## Q05：Spring 有哪些核心特性？展开讲讲

### 面试回答

结论：Spring 的核心是 IoC 和 AOP，Spring Boot 在其上把“从脚手架到上线”标准化。

- IoC：对象创建与依赖装配交给容器，解耦、可替换；Bean 的完整生命周期可被追问。
- AOP：横切逻辑（事务、日志）用代理实现；自调用会让切面失效，是高频追问点。
- 声明式事务：@Transactional，失效场景（自调用、非 public、异常吞掉）要能展开。
- Boot 侧特性：自动装配＋starter 依赖、内嵌容器、约定优于配置、Actuator 生产就绪。
- 每报一个特性带一句它解决什么问题，别背形容词。

## Q06：Redis 从哪些方面可以保证高可用？

### 面试回答

结论：部署模式是主线——从单点到主从、哨兵、Cluster 逐级加固；再补持久化与客户端两条侧线。

- 单实例：无高可用，宕机即不可用，只适合本地开发。
- 主从：数据冗余＋读写分离，但故障切换要人工，写是单点。
- 哨兵：在主从之上自动监控、故障发现、自动 failover，解决“高可用”；仍不扩数据。
- Cluster：16384 哈希槽分片、每分片一主多从自动切换，同时解决容量与高并发。
- 侧线：RDB／AOF 持久化防数据丢失；客户端重试与超时、哨兵节点奇数且 ≥3，是切换成功的工程前提。

## Q07：Redis 的过期删除策略

### 面试回答

结论：过期删除是“到期了怎么清”，内存淘汰是“没到期但内存满了踢谁”，两套机制先分开。

- 惰性删除：访问 key 时检查是否过期，过期则删并返回空；省 CPU，但永不再访问的过期 key 不会释放内存。
- 定期删除：后台周期抽样扫描过期 key，按结果自适应继续扫；不是在到期瞬间全量清理。
- 两者配合兜底内存：数据集到 `maxmemory` 后按 `maxmemory-policy` 淘汰（LRU／LFU／随机／TTL 短优先，分 allkeys 与 volatile 两组作用域）。
- 加分点：LRU／LFU 都是近似采样实现，别说成维护了全局精确链表。

关联专题：[[专题题库/Redis#REDIS-005：Redis 的过期删除与内存淘汰策略有什么区别？|REDIS-005：过期删除与内存淘汰]]

## Q08：项目中使用 RabbitMQ 如何避免消息的重复消费？

### 面试回答

结论：重复消费无法在 MQ 层面根除——消费者确认之前掉线或网络抖动，broker 必然重投；正确做法是接受 at-least-once，在消费端做业务幂等。

- 先说清重复从哪来：手动 ack 模式下未确认消息会自动重入队列；auto-ack 是 fire-and-forget，不重复但会丢。
- 幂等三档，按可靠性排：
  - 数据库唯一约束兜底。
  - 状态机条件更新（`where status=预期前态`）。
  - 已处理标记表与业务写入同事务。
- 点出一个反模式：只用 Redis setnx 判重——标记打了、业务却失败回滚，下一条重复消息会被“判重”吞掉，从重复变丢失。
- 配合动作：用 redelivered 标记／`x-delivery-count` 限制重试次数，反复失败的进死信队列，别无限重投。

## Q10：项目中消息队列的监控怎么做？消息延迟、消息堆积等如何监控和处理？

### 面试回答

结论：盯五个指标——ready 堆积数、unacked 数、最老消息年龄、生产／消费速率、发送确认失败率；采集走 `rabbitmq_prometheus` 插件＋Prometheus＋Grafana 告警。

- 先分类再处理：
  - ready 增长是消费跟不上或掉线。
  - unacked 堆积是消费者拿到消息卡住。
  - 最老消息年龄才代表用户感知的延迟。
- 定位三步：消费端是否活着（consumer 数、错误日志）→ 单条耗时是否变长（下游变慢、锁等待）→ 生产端是否突增（活动、重试风暴）。
- 处置：扩并发前先确认瓶颈不在下游（同一行锁被争用时加消费者更慢）；反复失败的消息隔离进死信队列，防止重投风暴。
- 告警口径：延迟按业务 SLO 定（如“最老消息年龄 >【N 秒】”告警），堆积按增长速率而非绝对值。

## Q11：回顾项目 3，可在哪些地方加入服务监控、接口报错监控？有哪些指标能快速感应并评估影响面？

### 面试回答

结论：按四层找埋点位置——入口接口、业务服务、中间件（MQ／缓存／DB）、资源与 JVM；指标用四个黄金信号收口：错误率、延迟、流量、饱和度。

- 能快速感应的指标：接口错误率与状态码分布、P99 延迟、QPS 突增突降、MQ 堆积与最老消息年龄、慢 SQL 数、GC 停顿时长。
- 报错监控怎么建：日志聚类＋告警，给每个接口定错误率阈值与环比突增规则；traceId 贯穿，报错能下钻到具体下游。
- 影响面评估三要素：该链路流量占比、是否主链路、失败后果（可重试还是资损）；按“核心链路＋用户可感知”优先定级。
- 落到项目 3：【在 XX 接口加错误率告警、在消费链路加堆积告警】，按【真实链路】填写；当时缺失的监控按复盘口径讲，不写成已上线。

## Q12：手撕：力扣 105．从前序和中序遍历序列构造二叉树

### 面试回答

结论：递归还原——前序第一个元素是当前子树的根，在中序里定位根就切出左右子树，两边递归。

- 先用哈希表存“中序值 → 下标”，避免每次线性找根，整体 O(n)。
- 左子树节点数 = 根的中序下标 − 中序区间左端点；用它把前序区间切成左右两段，下标算错是这类题最常见的 bug。
- 前提先口述：节点值唯一；空数组、单节点这些边界要过一遍。
- 与“前序＋中序输出后序”同源，那题只输出不建树，这题要 new 出 TreeNode 返回根。
