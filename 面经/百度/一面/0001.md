## Q01：Linux 中怎么看 CPU 状态和负载？

### 面试回答

我会先用 uptime 或 top 看 1、5、15 分钟负载，再用 top、mpstat -P ALL 1 看总体和各核 CPU，必要时用 pidstat -u 1 定位进程。load average 不是 CPU 百分比，Linux 还计入不可中断睡眠任务；高负载但 CPU 不高时，要结合 vmstat、iostat 和进程状态排查 I/O 或资源等待。

## Q02：I/O 多路复用中 select、poll、epoll 等有什么区别？

### 面试回答

I/O 多路复用的作用是让一个线程同时等待多个文件描述符。`select` 用位图传递集合，受 `FD_SETSIZE` 限制，每次调用后还要重建集合；`poll` 改用数组，没有这个固定上限，但两者都要把关注集合交给内核，并线性扫描就绪项。`epoll` 把关注集合留在内核，`epoll_wait` 只返回就绪事件，因此更适合连接数很多、同时活跃连接较少的场景。它们都是就绪通知，数据仍需要应用自己 `read` 或 `recv`。

## Q03：HashMap 如何扩容，扩容时的并发读写怎么处理？

### 面试回答

以 JDK 8 为例，HashMap 通常在元素数超过阈值后扩为原容量两倍，重新分配桶数组，再迁移节点。由于容量是二次幂，节点按 hash 与 oldCap 的按位与结果留在原索引或移动到原索引加 oldCap。普通 HashMap 本来就不支持并发修改，扩容时读写也没有安全保障；并发场景应使用 ConcurrentHashMap 或统一加锁。

## Q04：MySQL 有哪些日志，为什么同时需要 redo log 和 binlog，如何保持一致？

### 面试回答

MySQL 服务层常见的有错误日志、慢查询日志、通用查询日志和 binlog，InnoDB 还有 redo log 和 undo log。redo log 记录数据页的物理变更，用于崩溃恢复；undo log 保存回滚信息和历史版本；binlog 是服务层的逻辑变更日志，主要用于主从复制和基于备份的时点恢复。开启 binlog 时，MySQL 用内部两阶段提交协调两份日志：先把 redo 写到 prepare 状态，再写 binlog，最后提交 InnoDB 事务。崩溃恢复时，可根据 binlog 中是否有完整事务决定将 prepare 状态的事务提交还是回滚，从而保持两者一致。

## Q05：MySQL 索引用什么数据结构，为什么不用 B 树和 HashMap？

### 面试回答

InnoDB 常用索引采用 B+ 树，非叶节点主要保存导航信息，扇出大、树高低，叶子层有序连接，适合磁盘分页访问和范围扫描。B 树也能用于索引，但内部节点存数据会影响扇出；哈希擅长等值查找，不适合有序遍历和范围查询。不能把 Java HashMap 直接等同于数据库索引。

## Q07：什么是缓存穿透，如何解决，布隆过滤器能完全解决吗？

### 面试回答

缓存穿透是查询不存在的数据，缓存未命中后仍访问数据库。可做参数校验、给不存在结果设置短期空值缓存，再用布隆过滤器拦截确定不存在的 key，配合限流。布隆过滤器存在假阳性，判为“可能存在”的 key 仍可能查不到，所以不能完全消除穿透。数据新增还要同步过滤器并处理旧空值，后端异常不能直接当作不存在缓存。它与热点失效的击穿、大面积失效的雪崩不同。

## Q08：TCP 和 UDP 的区别是什么？

### 面试回答

TCP 是面向连接的可靠有序字节流，提供重传、流量控制和拥塞控制，但不保留消息边界。UDP 是无连接数据报，保留报文边界，协议本身不保证送达、有序或去重。选择取决于业务是否需要这些语义及延迟要求，不能简单说 UDP 一定更快或只能用于不可靠业务。

## Q09：TCP 四次挥手是什么过程，TIME_WAIT 为什么要等待？

### 面试回答

正常关闭时，一方发 FIN，对端 ACK；对端完成发送后再发 FIN，主动关闭方 ACK 并进入 TIME_WAIT。两个方向独立关闭，所以常见四个报文，ACK 与 FIN 也可能合并。TIME_WAIT 通常持续 2MSL，让最后 ACK 丢失时仍能确认重传 FIN，并降低旧连接报文影响后续同四元组连接的风险。

## Q12：手撕：LeetCode 86 分隔链表。

原文手撕 2。完整 Java 实现见专题。

### 面试回答

我会用两条带哨兵的链表，按原顺序把小于 x 的节点接到第一条，其余接到第二条，最后拼接。每次先保存 next 并断开旧链接，避免形成环。这样保留两个分区内部的原相对顺序，时间 O(n)、额外空间 O(1)。
