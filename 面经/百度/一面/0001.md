## Q01：Linux 中怎么看 CPU 状态和负载？

### 面试回答

思路是先看整体负载，再看各核 CPU，最后定位到具体进程。

- 第一步：用 uptime 或 top 看 1、5、15 分钟负载。
- 第二步：用 top、mpstat -P ALL 1 看总体 CPU 和每个核的情况。
- 第三步：必要时用 pidstat -u 1 定位是哪个进程在吃 CPU。

别背错一点：load average 不是 CPU 使用率百分比，Linux 还把不可中断睡眠的任务算进去。

所以负载高但 CPU 不高的时候，不要再盯着 CPU 看，要结合 vmstat、iostat 和进程状态，去排查 I/O 或资源等待。

## Q02：I/O 多路复用中 select、poll、epoll 等有什么区别？

### 面试回答

一句话：三者都是让一个线程同时等待多个文件描述符，区别在于关注集合放哪、就绪项怎么拿。

- `select`：用位图把集合传给内核，容量受 `FD_SETSIZE` 限制，而且每次调用后还要重建集合。
- `poll`：改用数组传递，没有那个固定上限。
- 它俩的共同代价：每次调用都得把关注的集合交给内核，再线性扫描一遍找就绪项。
- `epoll`：把关注集合留在内核里，`epoll_wait` 只把就绪事件返回给应用。

因此 `epoll` 更适合连接数很多、但同时活跃连接比较少的场景。

最后补一句边界：它们都只是就绪通知，数据还是要应用自己用 `read` 或 `recv` 去拿。

## Q03：HashMap 如何扩容，扩容时的并发读写怎么处理？

### 面试回答

以 JDK 8 为例，扩容就是“翻倍、重分配、迁移节点”这几步。

- 触发：元素数量超过阈值。
- 容量：扩成原来的两倍，同时重新分配桶数组。
- 迁移：因为容量一定是二次幂，节点只要看 hash 与 oldCap 的按位与结果，要么留在原索引，要么挪到“原索引加 oldCap”。

并发读写这块，结论是别指望它：普通 HashMap 本来就不支持并发修改，扩容期间的读写也没有任何安全保障。

真要并发，就换 ConcurrentHashMap，或者在外部统一加锁。

## Q04：MySQL 有哪些日志，为什么同时需要 redo log 和 binlog，如何保持一致？

### 面试回答

先把日志分两类说：服务层的和 InnoDB 自己的。

- 服务层：错误日志、慢查询日志、通用查询日志、binlog。
- InnoDB：redo log 和 undo log。

三份关键日志各干什么：

- redo log：记数据页的物理变更，用来做崩溃恢复。
- undo log：保存回滚信息，同时提供历史版本。
- binlog：服务层的逻辑变更日志，主要用于主从复制，以及配合备份做时点恢复。

为什么两个都要：一个管引擎内部的崩溃恢复，一个管服务层记下来的逻辑变更，职责不同。

一致性靠内部两阶段提交来保证，开启 binlog 时顺序是三步：

- 先把 redo 写到 prepare 状态。
- 再写 binlog。
- 最后提交 InnoDB 事务。

崩溃恢复时就看一点：binlog 里这条事务是不是完整的。完整就把 prepare 的事务提交，不完整就回滚，两边因此能保持一致。

## Q05：MySQL 索引用什么数据结构，为什么不用 B 树和 HashMap？

### 面试回答

结论：InnoDB 常用索引用的是 B+ 树。

为什么是它：

- 非叶节点主要放导航信息，所以扇出大、树可以做得很矮。
- 叶子层是有序连在一起的。
- 这两点正好适合磁盘分页访问，也适合范围扫描。

另外两个为什么不用：

- B 树：其实也能拿来做索引，但它内部节点也存数据，会挤占扇出。
- 哈希：等值查找很强，但有序遍历和范围查询做不好。

顺带澄清一句：不能把 Java 的 HashMap 直接等同于数据库索引，不是一回事。

## Q07：什么是缓存穿透，如何解决，布隆过滤器能完全解决吗？

### 面试回答

先给定义：缓存穿透是去查一份根本不存在的数据，缓存自然没命中，于是请求还是打到数据库。

解决办法是几层一起用：

- 入口先做参数校验。
- 查不到结果也写一个短期空值缓存。
- 用布隆过滤器把确定不存在的 key 直接拦掉。
- 再配合限流兜底。

面试官真正问的是“布隆过滤器能不能完全解决”——不能。因为它有假阳性：判成“可能存在”的 key，照样可能查不到，这部分请求还是会走到数据库。

还有两个容易漏的细节：

- 数据新增时要同步更新过滤器，也要处理掉之前存的那些空值缓存。
- 后端异常不能直接当作“数据不存在”写进缓存。

最后区分一下：穿透是查不存在的数据，击穿是热点 key 失效，雪崩是大批 key 一起失效，三者不是一回事。

## Q08：TCP 和 UDP 的区别是什么？

### 面试回答

两者最本质的区别：TCP 面向连接，UDP 无连接。

- TCP：可靠、有序的字节流，自带重传、流量控制和拥塞控制。代价是它不保留消息边界。
- UDP：数据报，保留报文边界。协议本身不保证送达，也不保证有序或去重。

字节流可以理解为“一串连续字节，不告诉你一条消息从哪到哪”；数据报则是一条一条独立投递的。

选型别偷懒：要看业务到底需不需要这些语义、对延迟有什么要求。不能简单说 UDP 一定更快，或者说它只能用在不在乎可靠性的业务上。

## Q09：TCP 四次挥手是什么过程，TIME_WAIT 为什么要等待？

### 面试回答

正常关闭走四步：

- 一方先发 FIN，表示“我这边说完了”。
- 对端回 ACK。
- 对端也发完之后，再发自己的 FIN。
- 主动关闭方回 ACK，然后进入 TIME_WAIT。

为什么是四个报文：两个方向是各自独立关闭的。也要注意 ACK 和 FIN 有可能合并成一条。

TIME_WAIT 为什么要等，通常等 2MSL（MSL 是报文在网络里的最大生存时间），有两个理由：

- 最后那个 ACK 可能丢了，还得能再确认一次重传过来的 FIN。
- 让这条连接遗留的旧报文在路上自然消亡，降低影响后续同四元组新连接的风险。

## Q10：Socket 编程。

原文没有具体设问，这里按基础流程与常见边界作答。

### 面试回答

先说两侧的正常流程：

- 服务端：socket、bind、listen、accept，之后的收发都走 accept 返回的那个新连接描述符。
- 客户端：socket、connect，然后直接收发。
- 一个容易说错的点：监听 socket 和连接 socket 不是同一个东西。

代码里必须处理好的几件事：短读短写、EOF、错误、超时，还有消息边界。

并发连接一多，就用非阻塞 I/O 配 epoll 来管理，而不是让每个连接都阻塞在那儿等。

这里按 atoi 风格来实现，规则是这么定的：

## Q12：手撕：LeetCode 86 分隔链表。

原文手撕 2。完整 Java 实现见专题。

### 面试回答

做法是拆成两条带哨兵（dummy 头节点，省掉判断头插的特例）的临时链表：

- 按原顺序遍历，小于 x 的节点接到第一条。
- 其余的接到第二条。
- 最后把第一条的尾接上第二条的有效头，拼成结果。

写的时候有一个坑：每次摘节点前，先保存 next，再把旧链接断开，不然容易接成环。

这样两个分区内部的相对顺序都保持原样，时间 O(n)，额外空间 O(1)。
