## Q01：RAG 仅接收关键词或业务单号，如何路由知识库并供多个业务 Agent 复用？

原图题号：13、14。

### 面试回答

核心思路是把“路由”和“检索”分成两层，不要搅在一起。

路由层负责回答“该查哪个库”：

- 有业务单号：先走业务系统，解析出租户、业务类型和知识域。
- 只有关键词：结合调用方身份、当前会话、已经授权的业务范围来选候选库。
- 有歧义别硬猜：把候选项返回给上层，让上层确认。

检索层负责查：确定知识域之后，做关键词召回加向量召回，两路结果合并去重，再重排。

多 Agent 复用的做法是：共用同一个检索服务，但每次请求都必须带上租户、知识域和权限条件。

这样做是因为：能力可以复用，数据边界必须逐次带上，否则各业务的内容就会混在一起。

## Q02：项目中的文件下载与文件存储如何落地？

原图题号：15。

### 面试回答

一句话架构：文件本体放对象存储，元数据放数据库。

- 库里存什么：文件 ID、对象键、所有者、大小、校验值、状态。
- 下载链路：先拿文件 ID 查元数据并鉴权，通过后再返回短期有效的签名 URL（带签名的临时下载地址）；也可以由应用服务直接流式转发。
- 大文件：建议分片上传，全部传完再校验大小和摘要。
- 删除：用状态标记加异步清理，来兜住数据库和对象存储之间那段短暂的不一致。

项目里真实用的存储、表结构、鉴权方式，讲的时候换成自己项目的实际情况。

## Q03：pgvector 与 Qdrant 有什么区别？

原图题号：16。

### 面试回答

两者定位不同：一个是扩展，一个是独立服务。

- pgvector：PostgreSQL 的向量扩展。好处是向量和业务表在同一个库里，能直接用 SQL、关联查询和数据库事务一起处理。
- Qdrant：专门的向量检索服务，数据是围绕向量、payload（随向量一起存的附带字段）过滤和检索 API 来组织的。

怎么选：

- 已经有 PostgreSQL，而且关系查询、事务协同的需求很强 → 先评估 pgvector。
- 希望把向量服务单独部署、单独管理 → 评估 Qdrant。

最后别说过头：不能只凭产品类型就说谁更快。要在相同数据、相同召回率和相同过滤条件下，实测延迟、资源和运维成本再下结论。

## Q04：B 端优惠券秒杀改为高 QPS 的 C 端场景，如何整体改造？

原图题号：17。

### 面试回答

我不会一上来就堆机器，先定量再动手：明确峰值流量、可售数量、限领规则、响应时限，然后压测定位瓶颈在哪。

分四层讲改造：

- 服务器层：做成无状态以便水平扩容，加负载均衡和资源监控。
- 代码层：减少同步调用和重复查询，把线程池、连接池和超时都控制好。
- 中间件层：预热活动数据，原子预占库存，用 MQ 削峰，最终扣减的准确性由数据库约束兜住。
- 业务层：入口限流、资格校验、防重复领取、排队反馈、售罄后关闭入口。

还有一条容易被忽略的：这是产品问题，不是纯技术问题。排队最多等多久、失败怎么通知用户、活动开关谁按，都要跟产品和运营确认。

验收指标就三个：成功率、尾延迟、数据正确性。

## Q05：消息队列放在秒杀哪个环节，消费者执行哪些业务逻辑？

原图题号：18、21。

### 面试回答

放哪：放在资格校验、幂等检查、库存预占都做完之后。投递进 MQ 的任务要带上请求 ID、用户、活动、券批次和数量，落库发券交给消费者做。

消费者做什么：

- 先校验任务和预占状态对不对得上。
- 在一个数据库事务里把四件事做完：幂等判定、按条件扣库存、写领取记录、写结果状态。
- 事务提交之后，再确认消息。
- 通知这类外部动作，另外异步处理，不塞进这个事务。

三种结果的处理方式也不一样：

- 重复消息：直接返回已经记下的结果，不重做。
- 暂时失败：重试。
- 永久失败：进可追踪的失败或补偿流程，不能悄悄丢掉。

## Q06：Redis 常见数据类型有哪些，秒杀扣库存选哪一种？

原图题号：19。

### 面试回答

类型先快速过一遍：

- String：值和计数。
- Hash：对象字段。
- List：列表。
- Set：去重。
- Sorted Set（有序集合）：排行榜。
- 另外还有 Bitmap、HyperLogLog、GEO、Stream 这些能力。

扣库存选哪个：单个活动或单个券批次的计数，通常就用 String。

关键是配套做法：用 Lua 脚本把“库存键是否存在、余额够不够、扣减”三步合成一个原子操作。

如果一次要动多个相关字段，也可以用 Hash。

选型诀窍是按访问方式定，不要按名字定。两个误区要说清：

- 单独调 DECR 虽然是原子的，但保证不了余额不变成负数。
- Redis 上的原子，也不等于跨 Redis、MQ、MySQL 的一致性，那是另一回事。

## Q07：Redis 预扣后异步扣 MySQL，MQ 消费失败如何保证一致性？

原图题号：20。

### 面试回答

先把口径定清楚，不然这题没法答：

- Redis 里的数是“可预占额度”。
- MySQL 记的是“最终领取事实”。
- 两边允许存在一段可解释的、处理中的差额，追求的是最终一致。

主流程：

- 每次预占都带唯一请求 ID、数量和状态。
- 消费者用本地事务加幂等约束来扣库存、写领取记录。
- 短暂失败就重试；只有确定做不成了，才按状态机把预占释放掉。

三个必须想到的窗口期：

- 预占成功了，但消息没发出去。
- 落库成功了，但确认丢了，消息被重投。
- 补偿动作和迟到的消费撞在一起，互相竞争。

收敛靠三样东西：可恢复的任务记录、终态互斥、定期对账。

别背错：不能简单地一失败就给 Redis 加一。

## Q08：秒杀高峰消息大量堆积怎么办？

原图题号：22。

### 面试回答

先判断，再加人。第一步是看四个指标：

- 生产速率有多快。
- 消费速率有多快。
- 最老一条消息已经等了多久。
- 失败重试的比例有多高。

然后定位瓶颈落在哪：消费者 CPU、数据库锁、连接池，还是下游调用。

处理方式分两头：

- 消费侧：任务本身能并行的，按活动或库存分片去加消费者，同时调整批量大小和预取。但如果是同一行库存被锁住，盲目加消费者只会更慢。
- 入口侧：
  - 做限流，按业务承诺控制最长排队时间。
  - 反复失败的消息单独隔离出去。
  - 已经受理的用户要给到处理中的状态。

## Q09：Redis 宕机时如何降级并继续校验库存？

原图题号：23。

### 面试回答

顺序是先把门关上，再决定放多少量：

- 第一步：入口做熔断和强限流，别让流量继续往前冲。
- 第二步：按数据库实测能扛的容量，决定要不要保留一小流量领取。

降级后的库存校验落在 MySQL：

- 用带库存下限条件的 UPDATE，配合唯一领取约束。
- 扣减和发券放在同一个事务里完成。
- 超出容量的部分，直接返回稍后重试或者暂停活动。

切过去之前还有个尾巴要收——原来的 Redis 预占和 MQ 在途任务：

- 要么停掉旧路径的新增，把在途的结算完；
- 要么给降级路径划一份独立、跟旧路径不重叠的库存额度。

两条红线不能踩：不能把全部流量直接压到数据库；也不能让各实例靠本地缓存各扣各的库存。

## Q10：MySQL 如何优化高并发库存扣减及热点单行锁排队？

原图题号：24、28。

### 面试回答

先把单条写做对，再谈并发：

- 定位：用主键或合适的唯一索引找到库存行。
- 扣减：执行带 `stock >= quantity` 条件的原地扣减，然后检查影响行数。
- 事务：压到最短，只留必要的扣减和记录写入。
- 防重：用唯一业务键挡住重复领取。
- 观测：盯锁等待和慢 SQL，控制消费并发与连接池大小。

关于排队，要承认一个事实：单行写入本身就要串行，继续扩线程突破不了这条瓶颈。

真要提速只有绕开这一行：

- 按活动或库存桶拆分，各桶分配互不重叠的额度。
- 或者按同一库存键排队，谨慎地合并扣减。

两个听着有理但没用的招要主动说清：读写分离解决不了同一行的写锁竞争，再加几个普通索引也一样解决不了。

## Q12：多个线程修改同一行库存时如何加锁，读写锁及竞争表现有何不同？

原图题号：26、27。

### 面试回答

还是先框定以 InnoDB 为前提。

写这一侧：

- UPDATE 会自动给要改的记录加排他锁。
- 多个事务更新同一行库存，通常就是排队等；持锁事务提交或回滚之后，别的事务才能继续。
- 等太久会出现等待超时。
- 一个边界要说清：单行竞争本身不算死锁，形成循环等待才是死锁。

读写锁的差别（“读”指加锁读）：

- 普通的一致性 SELECT：一般走 MVCC（多版本并发控制，靠历史版本读，不加行锁）。
- `FOR SHARE`：申请共享锁，共享锁之间可以兼容。
- `FOR UPDATE`：申请排他锁，它会跟其他事务在同一记录上的共享锁或排他锁都冲突。

最后一条最容易踩：库里有锁，不等于业务就对了。“先普通查询、再按查到的旧值覆盖回去”这种写法照样会错。

正确做法有两种：要么用条件原地扣减，要么在同一个事务里先做锁定读再改。

## Q13：JDBC 连接池常用核心参数有哪些？

原图题号：29。

### 面试回答

第一句要先反问：用的是哪个连接池？因为 JDBC 本身没有统一的池参数名。

以 HikariCP 为例，核心参数是这几个：

- maximumPoolSize、minimumIdle：池的最大连接数和最小空闲数。
- connectionTimeout：拿连接的等待上限。
- idleTimeout、maxLifetime：空闲回收和连接最长存活时间。
- validationTimeout、keepaliveTime：连通性校验和保活。
- 另外还要检查 autoCommit 和 transactionIsolation 这两个连接属性。

两个容易说错的地方：

- 池多大取决于数据库能扛多少并发、连接被持有多久、有几个实例，不是越大越好。
- 获取连接超时不等于 SQL 执行超时，是两件事。

调优时看的指标：活跃连接数、等待连接的次数、事务耗时，还有数据库本身的负载。

## Q14：手撕：如何合并二维数组中的重叠区间？

原图题号：30。

### 面试回答

开口先确认两件事：区间的开闭约定，以及输入是否合法。

这里我按这样约定：输入是合法闭区间，端点相接也算需要合并，null 或空数组返回空结果。

算法两步：

- 先按左端点升序排序。
- 然后顺序扫描：当前区间的左端点不大于结果里最后一个区间的右端点，就扩展它的右端点；否则把当前区间作为新区间追加。

复杂度：排序 O(n log n)，扫描 O(n)。
