## Q01：RAG 仅接收关键词或业务单号，如何路由知识库并供多个业务 Agent 复用？

原图题号：13、14。

### 面试回答

我会把“路由”和“检索”分成两层。业务单号先通过业务系统解析出租户、业务类型和知识域；只有关键词时，则结合调用方身份、会话和已授权的业务范围选候选库，有歧义就返回候选项让上层确认。确定知识域后，再做关键词召回和向量召回，合并去重后重排。多个 Agent 可以复用同一个检索服务，但每次请求都要携带租户、知识域和权限条件，这样既能复用能力，又不会把各业务的数据混在一起。

## Q02：项目中的文件下载与文件存储如何落地？

原图题号：15。

### 面试回答

常见做法是“文件放对象存储，元数据放数据库”。数据库保存文件 ID、对象键、所有者、大小、校验值和状态；下载时先通过文件 ID 查元数据并鉴权，再返回短期签名 URL，或由应用服务流式转发。大文件建议分片上传，完成后校验大小和摘要；删除则用状态和异步清理处理数据库与对象存储之间的短暂不一致。项目真实使用的存储、表结构和鉴权方式再换成实际内容。

## Q03：pgvector 与 Qdrant 有什么区别？

原图题号：16。

### 面试回答

pgvector 是 PostgreSQL 的向量扩展，便于把向量与业务表放在一起，用 SQL、关联查询和数据库事务处理；Qdrant 是专门的向量检索服务，围绕向量、payload 过滤及检索 API 组织数据。已有 PostgreSQL、关系查询和事务协同需求强时可以先评估 pgvector；希望独立管理向量服务时可以评估 Qdrant。最终要在相同数据、召回率和过滤条件下比较延迟、资源与运维成本，不能仅凭产品类型断言谁更快。

## Q04：B 端优惠券秒杀改为高 QPS 的 C 端场景，如何整体改造？

原图题号：17。

### 面试回答

我会先明确峰值流量、可售数量、限领规则和响应时限，再压测定位瓶颈。服务器层做无状态扩容、负载均衡与资源监控；代码层减少同步调用和重复查询，控制线程池、连接池及超时；中间件层预热活动数据，原子预占库存，通过 MQ 削峰，数据库约束最终扣减；业务层做入口限流、资格校验、防重复领取、排队反馈及售罄关闭。改造要和产品、运营确认排队多久、失败如何通知及活动开关，并以成功率、尾延迟和数据正确性验收。

## Q05：消息队列放在秒杀哪个环节，消费者执行哪些业务逻辑？

原图题号：18、21。

### 面试回答

常见做法是在资格校验、幂等检查和库存预占后，将带请求 ID、用户、活动、券批次和数量的任务投递 MQ，由消费者完成落库发券。消费者校验任务与预占状态，在一个数据库事务中完成幂等判定、条件扣库存、写领取记录和结果状态，提交后再确认消息；通知等外部动作可另行异步处理。重复消息直接返回已记录结果，暂时失败重试，永久失败进入可追踪的失败或补偿流程。

## Q06：Redis 常见数据类型有哪些，秒杀扣库存选哪一种？

原图题号：19。

### 面试回答

Redis 常见类型有 String、Hash、List、Set、Sorted Set，分别用于值与计数、对象字段、列表、去重和排行榜，也有 Bitmap、HyperLogLog、GEO、Stream 等能力。单个活动或券批次的库存计数通常用 String，配合 Lua 把库存存在性检查、余额判断和扣减作为一个原子操作；多个相关字段也可用 Hash。选型关键是访问方式，单独调用 DECR 虽然原子，却不能保证余额不为负，也不等于实现跨 Redis、MQ、MySQL 的一致性。

## Q07：Redis 预扣后异步扣 MySQL，MQ 消费失败如何保证一致性？

原图题号：20。

### 面试回答

我会将 Redis 数值定义为可预占额度，MySQL 记录最终领取事实，两者允许有可解释的处理中差额。每次预占都有唯一请求 ID、数量和状态，消费者用本地事务和幂等约束扣库存、写领取记录；短暂失败可重试，确定无法完成时才按状态机释放预占。还要处理预占成功但消息没发出的窗口、落库成功但确认丢失的重投，以及补偿与迟到消费的竞争，通过可恢复任务记录、终态互斥和定期对账收敛，不能简单失败就给 Redis 加一。

关联专题：[[专题题库/系统设计#SYS-004：Redis 预占与 MySQL 异步扣库存如何实现最终一致？|SYS-004：Redis 预占与 MySQL 异步扣库存如何实现最终一致？]]

## Q08：秒杀高峰消息大量堆积怎么办？

原图题号：22。

### 面试回答

我会先看生产速率、消费速率、最老消息等待时间和失败重试比例，再定位消费者 CPU、数据库锁、连接池或下游调用瓶颈。能并行的任务按活动或库存分片增加消费者，并调整批量与预取；同一库存行被锁住时，盲目加消费者反而更慢。同时在入口限流，按业务承诺控制最长排队时间，隔离反复失败的消息，给已受理用户展示处理状态。

## Q09：Redis 宕机时如何降级并继续校验库存？

原图题号：23。

### 面试回答

先对入口熔断和强限流，再按数据库实测容量决定是否保留小流量领取。可在 MySQL 中用带库存下限条件的 UPDATE 和唯一领取约束，在一个事务内完成扣减及发券；超出容量返回稍后重试或暂停活动。切换前还要处理已有 Redis 预占和 MQ 在途任务，停止旧路径新增并完成结算，或给降级路径划定独立且不重叠的库存额度。不能把全部流量直接压到数据库，也不能靠各实例本地缓存各扣各的库存。

## Q10：MySQL 如何优化高并发库存扣减及热点单行锁排队？

原图题号：24、28。

### 面试回答

先用主键或合适唯一索引定位库存，执行带 stock >= quantity 条件的原地扣减，检查影响行数，并把事务缩短到必要的扣减与记录写入。用唯一业务键防重复领取，监控锁等待和慢 SQL，控制消费并发与连接池。单行写入本身要串行，继续扩线程不能突破这条瓶颈；可以按活动、库存桶分配互不重叠额度，或按同一库存键排队、谨慎合并扣减。读写分离和增加普通索引都不能直接解决同一行的写锁竞争。

## Q11：MySQL 默认事务隔离级别是什么？

原图题号：25。

### 面试回答

以 InnoDB 为前提，MySQL 默认隔离级别是 REPEATABLE READ，也就是可重复读。但具体连接可能被服务器、会话或连接池配置覆盖，排查时要检查实际会话配置。默认隔离级别不意味着所有 SELECT 都加行锁，也不能代替扣库存时的条件更新和业务幂等。

## Q12：多个线程修改同一行库存时如何加锁，读写锁及竞争表现有何不同？

原图题号：26、27。

### 面试回答

以 InnoDB 为前提，UPDATE 会自动对需要修改的记录加排他锁，多个事务更新同一库存行通常排队等待，持锁事务提交或回滚后其他事务才能继续，可能发生等待超时；单行竞争本身不等于死锁，形成循环等待才是死锁。普通一致性 SELECT 通常用 MVCC，FOR SHARE 申请共享锁，FOR UPDATE 申请排他锁，共享锁可兼容，排他锁与其他事务对同一记录的共享或排他锁冲突。数据库有锁也不能保证“先普通查询，再按旧值覆盖”的业务正确，应使用条件原地扣减或在同一事务中先锁定读。

## Q13：JDBC 连接池常用核心参数有哪些？

原图题号：29。

### 面试回答

先确认使用的连接池，因为 JDBC 没有统一的池参数名。以 HikariCP 为例，核心包括 maximumPoolSize、minimumIdle、connectionTimeout、idleTimeout、maxLifetime，以及 validationTimeout、keepaliveTime；还要检查 autoCommit 和 transactionIsolation。池大小取决于数据库可承受并发、连接持有时间和实例数量，连接获取超时不是 SQL 执行超时。调优时看活跃连接、等待连接、事务耗时和数据库负载，不能把连接数越大理解为性能越好。

## Q14：手撕：如何合并二维数组中的重叠区间？

原图题号：30。

### 面试回答

我会先确认区间开闭和输入是否合法。这里约定输入为合法闭区间，端点相接也合并，null 或空数组返回空结果。先按左端点升序排序，依次扫描：当前区间左端点不大于结果末区间右端点时扩展右端点，否则新增区间。排序需要 O(n log n)，扫描 O(n)；为保持输入不变，复制区间后再排序，额外空间 O(n)。完整 Java 实现与边界案例见关联专题。
