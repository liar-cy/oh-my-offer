## Q01：手撕快速排序。

### 面试回答

先讲做法，再讲复杂度和优化点。

三步思路：

- 选一个基准值。
- 用明确的分区规则把数组拆成两部分：基准左边不大于它，右边不小于它。
- 再递归排序左右两个区间。

手写时我会守住两条约定：

- Lomuto 或 Hoare 分区法只选一种。
- 分区和递归边界保持一致，确保每次递归的区间都在变小。

复杂度：平均 O(n log n)，最坏 O(n²)，平均递归栈深度 O(log n)。

优化一句：随机选基准或三数取中，可以降低持续出现极不均衡分区的概率。

## Q02：从输入 URL 到页面渲染经历哪些步骤？

### 面试回答

按“准备 → 拿到响应 → 渲染”三段讲。

准备阶段：

- 先解析 URL，并检查缓存、Service Worker 这些可复用的结果。
- 要联网时解析 DNS，再建立或复用传输连接。
- HTTPS over TCP 还要完成 TCP 与 TLS 握手；HTTP/3 则基于 QUIC。

拿到响应：

- 浏览器发送 HTTP 请求，处理重定向，接收响应。

渲染阶段：

- 解析 HTML 构建 DOM，解析 CSS 构建 CSSOM。
- 执行脚本后形成渲染树，再做布局、绘制和合成。
- 子资源会继续触发请求。

最后一定要补一句：实际链路可能命中缓存或复用连接，不是每次都把整条路重走一遍。

## Q03：HTTP 状态码如何分类，503 和 504 有什么区别？

### 面试回答

先按大类过一遍，再重点说 503 和 504。

- 1xx：信息性响应。
- 2xx：成功。
- 3xx：重定向或缓存协商。
- 4xx：客户端请求有问题。
- 5xx：服务端处理失败。

503 Service Unavailable：

- 意思是当前服务暂时没法处理请求，常见于过载或维护。
- 可以配合 `Retry-After` 告诉客户端什么时候再来。

504 Gateway Timeout：

- 意思是充当网关或代理的那台服务器，等上游响应超时了。

两者都可能由上游故障引起，区分点在一句话：503 强调“服务本身暂不可用”，504 强调“网关等上游超时”。

## Q04：TCP 三次握手的过程是什么？

### 面试回答

三个报文按顺序说清谁发什么：

- 客户端发 SYN，带上自己的初始序列号 x，进入 SYN-SENT。
- 服务端回 SYN+ACK：给出自己的初始序列号 y，同时确认 x+1，进入 SYN-RECEIVED。
- 客户端再发 ACK 确认 y+1，双方进入 ESTABLISHED。

为什么必须是三次：

- 目的是让双方都确认自己的收发能力，并同步初始序列号。
- 只做两次，服务端就没法确认客户端收到了自己的序列号。
- 两次也更难挡掉历史连接的请求造成错误建连。

关联专题：[[专题题库/计算机网络#NET-010：TCP 三次握手如何进行，握手期间能携带数据吗？|NET-010：TCP 三次握手如何进行，握手期间能携带数据吗？]]

## Q05：缓存穿透和缓存雪崩是什么，如何解决？

### 面试回答

这两个不是一回事，分开说定义和解法。

缓存穿透：持续去查一份根本不存在的数据，缓存命不中，请求就反复打到数据库。

- 缓解手段：入口参数校验、短期空值缓存、布隆过滤器、限流。

缓存雪崩：大量 key 集中过期，或者缓存服务整个不可用，导致大批请求同时回源。

- 缓解手段：把 TTL 打散、提高缓存可用性，再用限流、熔断降级和回源并发控制保护数据库。

最后要说清两个残余风险，不然显得只会背方案：

- 布隆过滤器存在假阳性。
- TTL 抖动解决不了 Redis 整体故障。

所以这两类问题都得组合治理。

## Q06：Redis 的过期删除和内存淘汰策略是什么？

### 面试回答

先分清两件事：它们的触发条件不一样。

过期删除，处理的是已经超过 TTL 的 key：

- 惰性删除：访问到这个 key 时才发现它过期了。
- 主动清理：周期性抽样，把过期的 key 清掉。

内存淘汰，处理的是内存不够：达到 `maxmemory` 之后，按 `maxmemory-policy` 腾空间。

淘汰策略可以这么记：

- `noeviction`：不淘汰。
- 面向所有 key 的 LRU、LFU、随机淘汰。
- 只面向带 TTL key 的 LRU、LFU、随机淘汰。
- `volatile-ttl`。

LRU／LFU 分别是“最近最少使用”和“最不经常使用”两种挑法。

怎么选和怎么盯：要看 Redis 是纯缓存，还是还承载着不可丢的状态；上线后要监控淘汰率、命中率和内存余量。

## Q07：Redis 的 RDB 和 AOF 持久化有什么区别？

### 面试回答

两者是“快照”和“操作日志”的区别。

- RDB：存的是某个时刻的数据快照。文件通常更紧凑，适合备份，加载也比较快。代价是故障时可能丢掉最近一次快照之后的写入。
- AOF：记的是写操作，恢复时靠回放。丢多少数据取决于 fsync 策略，代价是更多的写入量和重写开销。

还能一起用：

- 两种持久化可以同时开启。
- 也有混合形式：以 RDB 做基础数据，再加 AOF 增量。

选型口径是三条：能接受多少数据丢失、要多久能恢复、运行成本多大。

## Q08：聚簇索引和非聚簇索引是什么？

### 面试回答

前提是以 InnoDB 来说。

聚簇索引：

- 它决定行数据的存储组织，叶子节点保存完整记录。
- 表通常就是按主键组织的。
- 没有合适主键时，InnoDB 会选一个或生成一个内部的聚簇键。

非聚簇索引，一般指二级索引：

- 叶子节点存的是索引列加聚簇主键值。
- 查询要的列如果二级索引覆盖不住，就得再拿主键去访问聚簇索引，这一步叫回表。

最后两条边界：一个表只有一种聚簇组织，但可以有多个二级索引；不同存储引擎的实现不能一概而论。

## Q09：排查和优化慢 SQL 的思路是什么？

### 面试回答

按“先确认 → 再看执行计划 → 再对症下药 → 最后验证”四步讲。

第一步，先确认慢的是哪一条：

- 手段是监控、调用链和慢查询日志。
- 要定位到具体的 SQL、参数、频率和影响范围。
- 还要先区分清楚：是执行慢、锁等待、连接池等待，还是网络问题。

第二步，看计划：

- 对可复现的 SQL 查 `EXPLAIN`。
- 需要时，在安全环境用 `EXPLAIN ANALYZE` 对比估算和实际的行数、循环、耗时。
- 逐项检查：访问行数、索引选择、连接顺序、排序、临时表、回表，以及统计信息。

第三步，按原因动手：

- 调整 SQL 或索引。
- 减少无用的列和扫描。
- 缩短事务，或者处理锁竞争。

第四步，验证：用有代表性的数据压测，上线后再用监控确认。

一条红线：不能只看到全表扫描就盲目加索引。
