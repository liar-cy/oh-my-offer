## Q02：迁移前的 Workflow 是什么形式，节点是提示词还是代码？

原文题号：2。

### 面试回答

迁移前的 Workflow 长什么样，得按真实项目说清【使用的框架】和【节点图】。

先破一个常见误解：Workflow 不等于一串 Prompt。

- 一个节点可以调模型。
- 也可以是普通代码、工具调用。
- 还能是条件分支或者人工审批。

迁移时东西往哪儿放：

- 可复用的处理经验和操作规则 → 抽成 Skill。
- 能确定执行的校验 → 落到脚本或服务里。
- 状态和权限 → 仍然由运行时管理。

最后留一句判断：业务如果必须严格按固定顺序走，Workflow 就应该保留，Skill 不是它的无条件替代品。

## Q05：Skill 目前只做诊断，还是能够自动修复，安全边界如何划分？

原文题号：5。

### 面试回答

第一句必须按事实来：目前做到哪一档，是【只诊断／提供方案／已支持哪些修复】。

如果只诊断：输出证据、可能原因和操作建议，不要声称已经执行过。

如果支持修复，按时间顺序讲四段：

- 事先：说清允许哪些动作、目标环境、授权范围；权限和参数由宿主和服务端来校验。
- 执行前：检查现状和前置条件，必要时先给一份变更预览。
- 执行后：验证故障是不是真的消失了。
- 全程：记录做了什么，以及怎么恢复。

最后一条底线：高风险动作按实际授权策略处理，不能只靠 Skill 里写一句“注意安全”来控权限。

## Q06：Agent 使用哪类模型，是否支持用户上传截图等多模态场景？

原文题号：6。

### 面试回答

模型的名称、版本、部署方式，以及有没有截图能力，都要填【真实配置】，不能编。

选型看五个维度：任务推理、工具调用、图像理解、时延、成本。

关于“支持上传图片”，有个容易混淆的点：入口能收文件，不等于图像能进模型。还得有下面两条之一：

- 模型本身就支持图像输入的链路；
- 或者先用 OCR（光学字符识别）／视觉工具把图转成文本，再交给文本模型。

截图的价值和局限一起说：它能提供界面报错和布局上的证据，但文本识别会出错，所以要结合日志、错误码和用户描述一起验证。

如果项目其实还没支持截图，就直接说没支持。

## Q09：一次 MCP 调用如何完成，模型、Agent、Client 和 Server 分别做什么？

原文题号：9。

### 面试回答

先说口径：下面是以 MCP 2025-06-18 版本的 tools 调用为例。

准备阶段（这步通常只做一次，可复用，不用每次调用都重来）：

- 宿主建立 Client 与 Server 的连接，初始化时协商双方能力。
- 通过 tools/list 拿到工具定义。
- 把它转换成模型能理解的工具描述。

一次调用的链路，按角色走一遍：

- 模型：提出要用哪个工具、传什么参数。
- Agent 运行时：校验参数和授权。
- MCP Client：发出 tools/call。
- Server：路由到具体工具实现，执行代码或调用业务系统，然后返回结果。
- 宿主：把结果交回模型，继续推理或者作答。

一句话记住分工：模型提意图，Client 发协议请求，Server 和它的后端真正执行。

最后补一句边界：固定的程序也能主动去调工具，协议并不要求每一次调用都由模型来决定。

## Q10：Agent 的上下文一般由哪些内容组成？

原文题号：10。

### 面试回答

上下文里通常有这几类内容：

- 系统和开发者指令。
- 当前用户目标。
- 相关的对话历史。
- 已经加载的 Skill。
- 工具定义和调用结果。
- 文件或者检索到的证据。
- 任务计划和状态。
- 按需召回的记忆。

有一条边界最容易说漏：模型当前真正收到的内容，跟系统外部保存的完整历史是两回事——有文件、有数据库，不代表里面的内容已经在上下文窗口里了。

还有一点要保留：来源和指令层级。外部资料是证据，不能一进来就自动变成高优先级指令。

## Q11：上下文过长时如何继续对话，怎样有重点地压缩？

原文题号：11、12。

### 面试回答

原则是别等窗口撑爆了才动手：在耗尽之前按 token 预算处理，而且要给输出和工具往返留出空间。

顺序上先省“能少带就少带”的，再动历史：

- 文件和工具定义按需加载，不一次全塞。
- 检索结果限制数量，或者分页；冗长的工具输出要缩减。
- 这些还不够，才对旧对话做结构化摘要，然后结合近期消息和外部状态继续会话。

压缩不能一视同仁，分两类列清楚。

该重点保留的：

- 当前目标、用户约束、有效的授权范围。
- 关键事实和各类标识、已经做过的决定、还没完成的事项。
- 失败原因，以及能找回证据的入口。

可以缩掉的：重复的讨论，还有随时能重新读取的长日志。

做摘要时还有三个“别混”：区分已完成和计划中，区分事实和推测，保留工具请求与结果之间的对应关系。关键状态要重新读取、验证之后再继续往下跑。

最后收一句边界：压缩只能降低信息损失的风险，做不到无限次无损对话。

## Q12：OpenCode、Claude Code、Codex、DeepSeek 的上下文机制有什么差异？

原文题号：13。

### 面试回答

先按层次对齐比较对象，不同层的不要硬比：

- OpenCode、Claude Code、Codex：都是带运行循环和上下文管理的编码 Agent 产品。
- “DeepSeek”：原题没说明具体指哪个产品，这里暂按模型 API 来理解。

按 2026-09-13 查到的滚动官方文档，各家机制是：

- OpenCode：有 compaction.auto、prune、reserved 等配置。
- Claude Code：会清理旧的工具输出并按需摘要，还支持用 /compact 指定要关注的内容。
- Codex：有 model_auto_compact_token_limit 这个自动压缩阈值配置。

一句方法论：模型 API 的上下文窗口和缓存能力，不能直接当成 Agent 的摘要、状态恢复、长期记忆机制，这是两层东西。

DeepSeek 具体指什么、内部上下文怎么实现，都还待确认；这里不猜它的压缩算法。

## Q14：Memory 如何检索和更新，用户从北京搬到上海后怎样处理旧记录？

原文题号：15。

### 面试回答

检索分两步，不要一上来就向量相似度：

- 先过滤：按用户身份、记忆类型、有效时间。
- 再召回：结合关键词、语义相关性、可信度，不是只看向量相似度。

北京搬到上海这个例子里，动作要拆开做：

- 用户明确说已经搬到上海：把“当前居住城市”更新为上海。
- 旧那条北京记录：设成失效状态或者写上结束时间。
- 如果业务需要、也允许保留历史：把它作为过去的居住记录留着。

两个不能做的：

- 只说了去上海出差，就不能覆盖居住地。
- 生效日期不明，也不要编一个日期。

写入侧的常规活：去重、冲突判断、版本控制，同时更新检索索引和缓存。

这样做是因为：不然旧的北京记录还会继续被当成现状返回给用户。

最后一句：长期记忆还得支持用户自己纠正和删除。

## Q15：手撕：给定字符串，返回最长回文子串。

原文题号：16。

### 面试回答

思路选中心扩展，因为回文是左右对称的。关键一点：中心不一定是一个字符，也可能是两个字符之间的那道空隙。

怎么写：

- 遍历每一个位置，各以它为中心向两边扩展。
- 奇数长度、偶数长度各扩一次，对应上面两类中心。
- 越界了或者两边字符不同就停。
- 沿途更新最长区间，最后返回这段子串。

为什么正确：所有中心都被检查过，最长的那个回文一定被某次扩展覆盖到。

复杂度：时间 O(n²)，除了返回的字符串本身，辅助空间 O(1)。

我这里的示例约定（用 Java）：按 UTF-16 的 char 比较，null 和空串都返回空串，长度相同的取最先找到的那一段。

要交代一句：这些只是示例约定，原题没有指定字符范围、语言，也没有规定同长怎么取。完整实现见关联专题。
