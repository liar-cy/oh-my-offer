## Q01：MySQL 的事务是什么？有哪些特性？

### 面试回答

先给定义：事务是把多条 SQL 当成一个逻辑工作单元，要么全部生效，要么全部撤销。

边界靠三条语句：START TRANSACTION／COMMIT／ROLLBACK。前提说清楚——InnoDB 下 autocommit 默认开启时，单条语句自己就构成一个事务。

特性就是 ACID 四项：

- 原子性：全做或者全不做。
- 一致性：从一种满足约束的状态，变到另一种。
- 隔离性：并发事务互不干扰，强弱由隔离级别决定。
- 持久性：提交之后不丢。

最后补一句实现层，显得真懂：

- undo log 保原子。
- redo log＋刷盘策略保持久。
- 锁＋MVCC 保隔离。
- 一致性还要靠业务约束，和前面三者一起达成。

## Q02：MySQL 的原子性底层如何实现？

### 面试回答

一句话：原子性靠 undo log。

它是怎么工作的：

- 事务改数据之前，先写 undo 记录，记下“怎么撤销这次修改”。
- 回滚时，按 undo 链逆向把旧版本恢复回来。
- 提交之后 undo 不会立刻删，因为 MVCC 读旧版本还要用它，由 purge 线程延迟清理。

顺手把两个概念分开：

- 原子性＝“要么可见，要么可撤销”。
- 持久性是另一件事，由 redo log（WAL：先写日志再改页）和崩溃恢复保证。

两者配合的关键点，在 redo 里的事务状态标记：

- 崩溃时未提交的事务，用 undo 回滚。
- 已提交但数据页还没落盘的，用 redo 重放。

## Q03：讲一下 MySQL 的 MVCC 机制的实现原理。

### 面试回答

先记住三样东西：隐藏字段、版本链、Read View。

- 隐藏字段：InnoDB 在每行记事务 ID（最后修改它的那个事务）和回滚指针（指向 undo log 里的上一版本）。
- 版本链：靠回滚指针把历史值串起来。
- Read View：做快照读时生成，里面是活跃事务集合、最小／最大 ID、创建者。

读的过程：按可见性规则，沿版本链往下找，找到这个事务应该看到的那个版本。这样读写互不阻塞。

隔离级别的差别，就在 Read View 什么时候建：

- RC：每条语句都新建一个。
- RR：事务首次快照读时建，之后复用——所以 RR 重读的结果是稳定的。

最后一句边界：当前读（FOR UPDATE 等）读的是最新版本并且会加锁，不走快照。

## Q04：MySQL 的覆盖索引、前缀索引、索引下推分别是什么？

### 面试回答

这三个名字都很像，但考察点各不一样，一个一个说。

覆盖索引：

- 查询要的列全在二级索引里，不用回表。
- EXPLAIN 的 Extra 会出现 Using index。
- 注意它是“查询和索引的配合关系”，不是一种索引结构。

前缀索引：

- 只对字符串的前 N 个字符建索引，省空间、写入也快。
- 代价是牺牲区分度，N 用 `COUNT(DISTINCT LEFT(col,n))/COUNT(*)` 来选。
- 还有两条限制：不能用于完整列的排序分组，也做不了覆盖。

索引下推（ICP，5.6+）：

- 场景是联合索引里，后面的列条件没法用来做范围定位。
- 做法是把这个条件下推到存储引擎，在取行之前先在索引层过滤一遍。
- 收益是减少回表次数，Extra 里会出现 Using index condition。

## Q05：如何定位和优化慢 SQL 语句？

### 面试回答

顺序是“先定位，再优化”。

定位这一步：

- 开慢查询日志，用 long_query_time、min_examined_row_limit 收集。
- 按总耗时、次数、扫描行数聚合排序，别只盯着单条最慢的那一条。
- 先分清慢在哪里：数据库执行慢、锁等待、连接池排队，还是网络。

看证据这一步：

- 对目标 SQL 跑 EXPLAIN，必要时在安全环境用 EXPLAIN ANALYZE。
- 重点看访问类型、估算行数，以及 Extra 里的 filesort／临时表／回表。

动手这一步，按证据来：

- 加或改索引。
- 改写查询：深分页、隐式转换、函数包列这几类是常见病因。
- 缩小事务和锁的范围。
- 数据量太大就拆。

收尾：压测并观察上线指标，确认确实有收益、也没有引入写放大之类的回归。

## Q06：使用 EXPLAIN 分析慢 SQL 时，哪些字段比较重要？

### 面试回答

按字段一个一个说清“看它判断什么”。

- `type`：访问类型。const／eq_ref→ref→range 还算正常，看到 index／ALL 要警惕全表扫。
- `key` 和 `possible_keys`：实际用了哪个索引；没用，是要分清选错了还是根本没建。
- `rows` 和 `filtered`：预估扫描行数，和过滤后剩下的比例；两者乘积近似真实处理量。
- `Extra`：Using index 是覆盖，Using index condition 是下推，Using where 是回表后过滤，Using filesort／Using temporary 是排序分组的代价信号。
- `key_len`：联合索引实际用到了多长，能判断左前缀断在哪一列。
- `id／select_type`：看子查询和联合执行的结构。

最后一句要交代口径：EXPLAIN 给的是估算。如果和实际偏差很大，就先更新统计信息，或者结合 EXPLAIN ANALYZE 核对。

## Q07：MySQL 的主从复制数据同步流程是怎样的？

### 面试回答

一句话：三个线程接力，把 binlog 一段段搬过去重放。

同步链路：

- 主库事务提交时写 binlog。
- 主库 dump 线程按位点／GTID，把 binlog 事件发给从库。
- 从库 IO 线程收下来，写进 relay log。
- 从库 SQL 线程读 relay log 重放；要么单线程按序，要么并行复制按组应用。

复制模式要分两档说：

- 默认是异步：主库提交不等从库确认，可能丢最后那点写入。
- 半同步：要求至少一个从库确认收到（落到 relay log），才给客户端返回。

最后落到业务影响：主从 lag 由并行回放能力和网络延迟决定。所以读从库要接受“可能读到旧数据”，读己之写的场景就走主库，或者用 GTID 等待。

## Q08：介绍下 Redis 的常用数据类型。

### 面试回答

答法是“五种基础类型 + 四种扩展能力”，每种都带一个使用场景。

基础五类：

- String：缓存对象 JSON、计数 INCR、分布式锁 SET NX。
- Hash：按字段读写对象。
- List：简单队列、最新动态。
- Set：共同关系、去重、SADD 幂等。
- ZSet（有序集合）：排行榜、延迟队列、滑动窗口。

扩展四种：

- Bitmap：签到。
- HyperLogLog：基数统计，注意有误差。
- GEO：附近的人，底层是基于 ZSet。
- Stream：消息流，带消费组。

收口一句：底层编码会随版本和数据规模变化，别背成固定一对一。

## Q09：项目中如何解决缓存穿透、缓存击穿和缓存一致性问题？

### 面试回答

这题要按项目实际答；下面是通用方案，三个问题分开讲。

穿透，防的是“去查根本不存在的数据”：

- 缓存空值，或者用布隆过滤器前置拦截，再加上入参校验。
- 一条边界：布隆有假阳性，不能保证拦住全部边界情况。

击穿，防的是“热点 key 过期的那一瞬间并发回源”：

- 互斥锁／singleflight：只放一个请求去做重建。
- 热点 key 用逻辑过期，后台异步刷新。
- 或者干脆永不过期，配后台更新。

一致性，原则是以数据库为事实源：

- 顺序是先提交事务，再删缓存。
- 删除失败要重试，并用 TTL 兜底。
- 变更很频繁，再上 binlog 订阅来驱动失效。

收尾时把两件事说全：每个方案各防的是什么问题，以及它残余的窗口在哪。

## Q10：如何使用 Kafka 解决消息丢失问题？

### 面试回答

思路是按三段链路各自加固，不是只调一个参数。

生产端：

- `acks=all`：等 ISR（In-Sync Replicas，跟得上 leader 的那组副本）全部确认。
- 配 retries，再开 `enable.idempotence=true`：幂等去重，重试不会产生重复消息。
- 发送回调里的最终失败要处理，落库做补偿。

broker 端：

- topic 的 `replication.factor≥3`、`min.insync.replicas≥2`。
- 关闭 `unclean.leader.election.enable`：宁可暂时不可用，也不让落后的副本上位丢数据。

消费端：

- 关掉自动提交，等业务真正处理成功之后，再手动提交 offset。

为什么这些够用：Kafka 的持久化靠多副本加 OS 页缓存。所以配置的目标就一句话——任何单点故障都不丢。

## Q11：如何使用 Kafka 解决消息的重复消费问题？

### 面试回答

先承认前提：只要开了重试／at-least-once，就一定可能重复。

重复从哪来，三个来源：

- rebalance 时旧消费者还在处理消息。
- 提交失败导致重放。
- 生产端重试。

根治靠消费幂等，做法是：

- 拿消息里带的稳定业务键，比如订单号＋事件类型。
- 在共享的持久化存储上做唯一约束，或者做条件状态更新。
- 重复消息命中之后，直接返回已有的结果。
- 跨机器的场景，幂等记录不能放在单机内存里。

如果要求“处理和提交”是原子的，可以用 Kafka 的事务性消费（read_committed）。

口径要摆正：先接受“至少一次＋幂等”这个模型，而不是去追求恰好一次。

## Q12：Kafka 发送消息时因网络问题出现消息丢失，如何解决？

### 面试回答

这题的关键是先分两种情况：“发送失败”和“发送结果未知”不是一回事。

让客户端自己能扛住可重试错误：

- `acks=all`＋`retries>0`＋合理的 `delivery.timeout.ms`。
- 这样超时、leader 切换这类可重试错误会自动重发。
- 再开幂等生产者：重发按 pid＋sequence 去重，所以不会产生重复消息。

重试耗尽还是失败：说明消息没有被确认送达。回调里必须落库／进补偿队列，不能只打一行日志。

按业务要求选兜底姿势：

- 允许极小概率重复、但不能丢：用 at-least-once，再加消费幂等。
- 要求更强的场景：用同步 send 等确认。

## Q13：从浏览器输入百度的网址访问网页，网络过程是怎样的？

### 面试回答

这题按层次讲最容易记：解析地址 → 可靠传输 → 加密 → 应用协议 → 渲染。

完整链路一步步走：

- URL 解析。
- DNS：先看浏览器／系统缓存，再问本地 resolver，然后递归／迭代查询，拿到 IP。
- 建立 TCP 连接：走三次握手；HTTPS 还要再做一次 TLS 握手协商密钥。
- 发送 HTTP 请求。
- 服务器处理：可能经过负载均衡、网关、后端服务和缓存。
- 返回响应。
- 浏览器解析 HTML、构建 DOM／CSSOM、加载子资源，最后渲染展示。注意每来一个新域名，又是一条完整的请求链路。
- 结束：断开，或者复用连接（keep-alive／连接池）。

面试官会往每一层里钻，常见的是三处：DNS 的递归和迭代怎么分工、握手的细节、HTTP 的缓存协商。

## Q14：HTTP 和 HTTPS 的区别是什么？

### 面试回答

一句话：HTTPS＝HTTP＋TLS，就是在 HTTP 下面垫了一层 TLS。

四个变化：

- 端口：默认 80→443。
- 明文传输→加密：握手期用非对称／密钥封装协商出对称密钥，之后数据传输走对称加密。
- 无身份验证→有：靠证书链校验服务器身份，也就是 CA 体系，作用是防中间人。
- 成本：多了握手延迟和加解密开销，可以用会话复用、TLS1.3 来减少往返。

证书验证具体看四项：域名、有效期、签发链、吊销状态。

最后分清职责：内容完整性是 TLS 防篡改在管，HTTP 本身不保证。

## Q15：算法：LeetCode 3 无重复字符的最长子串（mid，ACM 模式）。

### 面试回答

做法是滑动窗口，配合一张“字符最后出现位置”的哈希表。

- 右指针往外扩张，每读一个字符就更新它的位置。
- 遇到窗口内的重复字符时，左指针不用一步一步挪，直接跳到“重复字符上次位置＋1”。
- 全程维护 `right-left+1` 的最大值。

复杂度：时间 O(n)，空间 O(字符集)。

ACM 模式的两件事别忘：

- 自己读入（比如整行字符串），再按要求输出长度。
- 动手写之前先跟面试官确认两点：字符集范围、大小写是否敏感。

## Q16：SQL 题：两个事务同时执行，说明执行流程，失败还是成功？

### 面试回答

先把前提复述一遍，这题的结论全绑在前提上：

- 表 t 主键 id 有 1,3,5,10,15,20。
- 事务 A 执行 `SELECT * FROM t WHERE id=7 FOR UPDATE`，而 id=7 并不存在。
- 事务 B 依次 `INSERT` 6、8、11。

RR 隔离级别下的流程：

- A 是主键点查、未命中，于是对 7 应该插入位置的间隙 (5,10) 加 gap lock。A 本身成功。
- B 插 6，需要拿到 (5,10) 内的插入意向锁，和 gap lock 冲突，所以阻塞。
- B 后面的 8、11 是同一个事务里顺序执行的，就被前一条一起拖住等待。

最后成不成，取决于时序，两种结果都要说：

- A 在 B 的 `innodb_lock_wait_timeout`（默认 50s）之前提交／回滚：B 继续，三条全部插入成功。
- 超时了：B 报锁等待超时。这条语句失败，但整个事务要不要回滚，看应用的错误处理怎么写。

两条补充口径：

- 换成 RC：没有 gap lock，A 不锁间隙，B 直接成功。
- id=11 其实落在 (10,15) 这个间隙里，本身跟 A 不冲突，它只是被 B 事务内的前序语句阻塞拖住了。
