## Q01：MySQL 的事务是什么？有哪些特性？

### 面试回答

事务是把多条 SQL 作为一个逻辑工作单元要么全部生效、要么全部撤销，边界是 START TRANSACTION／COMMIT／ROLLBACK（InnoDB，autocommit 默认开启时单语句自成事务）。特性即 ACID：原子性（全做或全不做）、一致性（从一种满足约束的状态到另一种）、隔离性（并发事务互不干扰，由隔离级别决定强弱）、持久性（提交后不丢失）。一句话补充实现：InnoDB 用 undo log 保原子、redo log＋刷盘策略保持久、锁＋MVCC 保隔离，一致性还要靠业务约束与前面三者共同达成。

关联专题：[[专题题库/MySQL#MYSQL-001：MySQL 事务有哪些隔离级别？|MYSQL-001：MySQL 事务有哪些隔离级别？]]

## Q02：MySQL 的原子性底层如何实现？

### 面试回答

靠 undo log：事务修改数据前先写 undo 记录（如何撤销），回滚时按 undo 链逆向恢复旧版本；提交成功后 undo 并非立刻删除，还要服务 MVCC 读旧版本，由 purge 线程延迟清理。原子性＝“要么可见要么可撤销”；持久性是另一件事，由 redo log（WAL：先写日志再改页）与崩溃恢复保证。两者配合点在于 redo 里的事务状态标记——崩溃时未提交的事务用 undo 回滚，已提交但页未落盘的用 redo 重放。

## Q03：讲一下 MySQL 的 MVCC 机制的实现原理。

### 面试回答

InnoDB 在每行隐藏字段记录事务 ID（最后修改它的事务）与回滚指针（指向 undo log 中的上一版本），版本链串起历史值；事务做快照读时生成 Read View（活跃事务集合、最小/最大 ID、创建者），按可见性规则沿版本链找到该事务应看到的版本，读写互不阻塞。RC 每条语句新建 Read View，RR 事务首次快照读建立后复用，所以 RR 重读结果稳定；当前读（FOR UPDATE 等）读最新版并加锁，不走快照。

## Q04：MySQL 的覆盖索引、前缀索引、索引下推分别是什么？

### 面试回答

覆盖索引：查询所需列全在二级索引里，不必回表，EXPLAIN Extra 出现 Using index——是查询与索引的配合，不是某种索引结构。前缀索引：只对字符串前 N 个字符建索引，省空间提写入，但牺牲区分度（用 COUNT(DISTINCT LEFT(col,n))/COUNT(*) 选 N）、不能用于完整列的排序分组和覆盖。索引下推（ICP，5.6+）：联合索引中无法用于范围定位的后续列条件，下推到存储引擎取行前在索引层先过滤，减少回表次数，Extra 出现 Using index condition。

## Q05：如何定位和优化慢 SQL 语句？

### 面试回答

先定位再优化：开慢查询日志（long_query_time、min_examined_row_limit）收集，按总耗时、次数、扫描行数聚合排序而不是只看单条最慢；区分数据库执行慢、锁等待、连接池排队还是网络。对目标 SQL 看 EXPLAIN（必要时安全环境 EXPLAIN ANALYZE）：访问类型、估算行数、Extra 的 filesort／临时表／回表。再按证据处理：加改索引、改写查询（深分页、隐式转换、函数包列）、缩小事务与锁范围、拆分数据量；最后压测并观察上线指标，确认收益且无写放大回归。

## Q06：使用 EXPLAIN 分析慢 SQL 时，哪些字段比较重要？

### 面试回答

重点看：`type`（访问类型，const／eq_ref→ref→range 尚可，index／ALL 警惕全扫）；`key` 与 `possible_keys`（实际用了哪个索引，没用是选错还是没建）；`rows` 与 `filtered`（预估扫描行数和过滤后剩余，乘积近似真实处理量）；`Extra`（Using index 覆盖、Using index condition 下推、Using where 回表后过滤、Using filesort／Using temporary 是排序分组代价信号）；`key_len`（联合索引实际用到多长，判断左前缀断在哪）；`id／select_type` 看子查询与联合执行结构。EXPLAIN 是估算，与实际偏差大时更新统计信息或结合 EXPLAIN ANALYZE 核对。

## Q07：MySQL 的主从复制数据同步流程是怎样的？

### 面试回答

三段线程接力：主库事务提交写 binlog；主库 dump 线程按位点/GTID 把 binlog 事件发给从库；从库 IO 线程接收写入 relay log；SQL 线程读取 relay log 重放（单线程按序或并行复制按组应用）。复制模式默认异步——主库提交不等从库确认，可能丢最后写入；半同步要求至少一个从库确认收到（落 relay log）才返回客户端；并行回放与网络延迟决定主从 lag，业务读从库要接受“读到旧数据”的可能，读己之写场景走主库或 GTID 等待。

## Q10：如何使用 Kafka 解决消息丢失问题？

### 面试回答

按三段链路各自加固：生产端 `acks=all`（等 ISR 全部确认）＋ retries＋`enable.idempotence=true`（幂等去重，重试不产生重复），并处理发送回调里的最终失败（落库补偿）；broker 端 topic `replication.factor≥3`、`min.insync.replicas≥2`、关闭 `unclean.leader.election.enable`，宁可不可用也不让落后副本上位丢数据；消费端关闭自动提交，业务处理成功后再手动提交 offset。Kafka 持久化靠多副本＋OS 页缓存，配置目标是“任何单点故障不丢”。

## Q11：如何使用 Kafka 解决消息的重复消费问题？

### 面试回答

开了重试／at-least-once 就必然可能重复：rebalance 时旧消费者还在处理、提交失败重放、生产重试都造成重复投递。根治靠消费幂等：用消息携带的稳定业务键（订单号＋事件类型）在共享持久化存储做唯一约束或条件状态更新，重复消息命中后直接返回已有结果；跨机器场景幂等记录不能放单机内存。要求处理与提交原子时可用 Kafka 事务性消费（read_committed）。先接受“至少一次＋幂等”模型，而不是追求恰好一次。

## Q12：Kafka 发送消息时因网络问题出现消息丢失，如何解决？

### 面试回答

网络问题下“发送失败”和“发送结果未知”要分开：`acks=all`＋`retries>0`＋合理 `delivery.timeout.ms` 让客户端对超时、leader 切换等可重试错误自动重发；开启幂等生产者后重发按 pid＋sequence 去重，不会产生重复消息。重试耗尽仍失败说明消息未确认送达，回调里必须落库／进补偿队列，不能只打日志。若业务允许极小概率重复换不丢，用 at-least-once＋消费幂等兜底；同步 send 等确认适合强要求场景。

## Q13：从浏览器输入百度的网址访问网页，网络过程是怎样的？

### 面试回答

完整链路：URL 解析→DNS（浏览器/系统缓存→本地 resolver→递归/迭代查询，拿到 IP）→建立 TCP 连接（三次握手；HTTPS 再做 TLS 握手协商密钥）→发送 HTTP 请求→服务器处理（可能经负载均衡、网关、后端服务与缓存）→返回响应→浏览器解析 HTML、构建 DOM/CSSOM、加载子资源（每个新域名又是完整请求链路）、渲染展示→断开或复用连接（keep-alive／连接池）。按层次讲清“解析地址→可靠传输→加密→应用协议→渲染”，并能对每层展开（DNS 递归迭代、握手、HTTP 缓存协商）。

## Q14：HTTP 和 HTTPS 的区别是什么？

### 面试回答

HTTPS＝HTTP＋TLS：默认端口 80→443；明文传输→加密（握手期非对称/密钥封装协商对称密钥，数据传输用对称加密）；无身份验证→证书链校验服务器身份（CA 体系，防中间人）；额外成本是握手延迟与加解密开销，可用会话复用、TLS1.3 减少往返。证书验证看域名、有效期、签发链与吊销状态。内容完整性由 TLS 防篡改，HTTP 本身不保证。

## Q15：算法：LeetCode 3 无重复字符的最长子串（mid，ACM 模式）。

### 面试回答

## Q16：SQL 题：两个事务同时执行，说明执行流程，失败还是成功？

### 面试回答

前提：表 t 主键 id 有 1,3,5,10,15,20；事务 A `SELECT * FROM t WHERE id=7 FOR UPDATE`（id=7 不存在），事务 B 依次 `INSERT` 6、8、11。RR 隔离级别下：A 主键点查未命中，对 7 应插入位置的间隙 (5,10) 加 gap lock，A 成功；B 的 INSERT 6 需要 (5,10) 内的插入意向锁，与 gap lock 冲突→阻塞，B 后续 8、11 因同事务顺序执行而等待。结果取决于时序：A 在 B 的 `innodb_lock_wait_timeout`（默认 50s）前提交/回滚→B 继续，三条全部插入成功；超时→B 报锁等待超时（该语句失败，是否整个事务回滚取决于应用错误处理）。补充口径：RC 下无 gap lock，A 不锁间隙，B 直接成功；id=11 落在 (10,15) 间隙，本身不与 A 冲突，只是被 B 事务内前序阻塞拖住。
