## Q02：相似 Skills 被调用错误如何处理和预防，只有一个 Skill 仍误执行怎么办？

原文题号：4—6。

### 面试回答

先定位错在哪一层，再谈预防：

- 是哪一层错了：选错了 Skill，还是 Skill 选对了、但参数／步骤／工具执行错了。
- 相似 Skill 的预防：`description` 里明确写清适用场景、不适用场景和关键区别。
- 路由策略：先用确定性条件把候选缩小，仍有歧义就去问用户。

只有一个 Skill 的情况，结论是照样要判断：

- 加载了一个也要先做适用性判断，不能默认“有就得执行”。

执行层是最后一道闸：

- 真正调工具前，校验参数、权限和前置条件。
- 执行之后再核对结果。

这样做是因为：防止一次路由判断直接变成不可控的副作用。

## Q03：Skill 如何设计、选择、执行，并适配动态入参？

原文题号：7—10。

### 面试回答

按“设计 → 选择 → 执行”三步说：

- 设计：先定义真实任务、触发与排除条件、输入输出以及步骤；再组织指引、脚本和参考资源。
- 选择：Agent 根据任务挑出候选 Skill，按需加载对应指引。
- 动态入参：绑定用户输入和可信状态里的参数，校验类型、必填和业务前提。
- 执行：校验通过后再调工具，并验证结果。

两条原则：缺参不猜，失败返回结构化信息。

还有一句边界要说清：Skill 的文档规范不代替运行时鉴权，也不规定所有系统都用同一套路由算法。

## Q04：多任务之间如何隔离上下文？

原文题号：11。

### 面试回答

结论：隔离要按身份分层做，而且不能只隔消息历史。

- 命名空间：按租户、用户、会话和任务建立独立的状态命名空间（各自一块互不可见的 key 空间）。
- 加载原则：每次只加载该身份有权访问的记录。
- 共享知识：只读，或者走明确授权。

容易被漏掉的一半：只把消息历史分开还不够，缓存、检索、临时文件、工具会话和回调也必须绑定到任务上。

## Q05：页面结构变化导致 Skill 失效怎么办？

原文题号：12。

### 面试回答

核心思路是把“业务步骤”和“页面定位适配”分开，页面变了只换后者。

- 设计期：业务步骤不写死坐标，优先用角色、可访问名称或稳定的测试标识来定位元素。
- 执行期：执行前确认页面状态，执行后验证业务结果。
- 页面变更后：重新采集结构并修正适配层。

别做的一件事：不要盲目重复点击旧坐标。

## Q06：为什么需要限制 Agent 并发数？

原文题号：13。

### 面试回答

因为一个 Agent 任务不是一次调用。

- 一次任务可能触发多次模型调用和工具调用。
- 并发过大会耗尽连接、内存、浏览器实例和配额。
- 还会放大两件事：成本，以及共享状态之间的竞争。

我怎么做：

- 按租户、任务和下游资源分别限制在途数量。
- 用有界队列、超时和取消形成背压（下游忙不过来时把压力顶回去，而不是继续压）。

## Q07：如何控制 Agent 执行中不暴露密钥？

原文题号：14。

### 面试回答

原则是密钥只在最后一刻出现：

- 存放：密钥放在服务端的凭据系统里。
- 注入：由受控执行器在实际请求下游时才注入。
- 出口：模型上下文、用户响应、日志和异常里只保留必要的脱敏信息。

权限侧再做一层：

- 限制工具权限和可访问的目标。
- 用短期、最小权限的凭据。

最后补一句边界：不能靠 Prompt 里的保密要求去隔离已经暴露给模型或客户端的明文。

## Q08：HTTPS 建立连接的完整流程是什么？

原文题号：15。

### 面试回答

先交代前提：以首次建立 HTTPS over TCP、TLS 1.3 常规证书认证的握手为例。

握手顺序：

- 先完成 TCP 建连。
- 客户端发 ClientHello，里面带版本、算法和密钥共享（key share，客户端预选的密钥交换参数）。
- 服务端回 ServerHello，确定共享密钥参数。
- 之后服务端发送加密的扩展、证书、签名证明和 Finished。
- 客户端验证证书链、主机名、有效期以及握手证明，验证通过再发送自己的 Finished。
- 握手结束，双方用派生出的对称密钥来交换 HTTP 数据。

两句边界，说了显得理解到位：

- 证书是用来做认证的，不是拿证书里的公钥直接加密全部 HTTP 内容。
- 会话恢复、以及 HTTP/3 走的链路跟这条不一样。

关联专题：[[专题题库/计算机网络#NET-002：HTTP 和 HTTPS 有什么区别，证书如何验证？|NET-002：HTTP 和 HTTPS 有什么区别，证书如何验证？]]

## Q09：浏览器输入 URL 到服务端返回页面的完整链路是什么？

原文题号：16。

### 面试回答

链路分三段：浏览器侧解析、网络上拿响应、回来渲染。

- 浏览器解析 URL，先处理缓存和 HTTPS 升级策略。
- 需要联网时解析域名，然后建立或复用连接。
- 以 HTTPS over TCP 为例：经过 TCP 和 TLS 握手后发出 HTTP 请求，服务器返回响应。
- 浏览器解析 HTML 和 CSS、执行脚本，构建页面，再做布局、绘制和合成。

一个纠正口径的点：HTTP/3 用的是 QUIC，不能说所有网页请求都先建一条 TCP 连接。

## Q11：从零设计 Coding Agent 会怎么做？

原文题号：18。

### 面试回答

先定边界，再搭闭环，最后说分工。

- 定边界：先确定编码任务、仓库范围和验收方式。
- 搭闭环：读取与搜索代码 → 生成补丁 → 执行构建测试 → 检查 diff。
- 分工：模型负责提出动作；运行时负责管理上下文、执行权限、任务状态和预算。
- 迭代：每次改动都根据测试结果和实际行为反馈来推进。

## Q14：上一个 Skill 产生敏感信息，如何让下一个 Skill 使用而不让用户接触？

原文题号：23。

原文只写敏感信息，类型与权限关系未知；按服务端内部中间数据、用户无权查看明文的前提作答。

### 面试回答

思路是传引用、不传明文：

- 密钥：由服务端凭据系统保管，执行器在调用目标服务时才注入，尽量不进入模型上下文、用户响应和日志。
- 上一步产出的敏感结果：保存在受控存储里。
- 对外：只向模型和用户返回一个不透明引用（一个看不出内容的句柄）。
- 下一步：获授权的 Skill 由服务端把这个引用解回真实值。

## Q15：基于内存做一个缓存，如何写 AI Coding 流程中的提示词？

原文题号：25（跨图 5—6）。

原文 24“能看到这个代码面板吗”是面试操作确认，保留于流程备注，不计技术问答。

### 面试回答

口述时先说这段提示词包含的四层要求，再把示例念出来：

- 任务与接口：做什么、暴露哪几个方法。
- 前置确认：不明确的条件先让模型列出来，方案定了再写。
- 验证：指定要覆盖的边界用例。
- 交付说明：要求它交代复杂度和限制。

示例提示词：“请在【语言／项目】实现进程内键值缓存，提供 get、put、delete。先确认容量、是否过期、淘汰策略及线程安全要求；不明确的条件先列出，方案明确后实现。验证未命中、覆盖更新和已约定的容量／过期／并发边界，说明复杂度与限制。”

一条边界：原文没有指定语言、LRU 或 TTL，不能默认把本题改成手写 LRU。
