## Q01：算法：LeetCode 146 LRU 缓存（mid）。

### 面试回答

哈希表＋双向链表：哈希表 O(1) 定位节点，链表维护访问顺序，get／put 都把节点移到头部，容量满时删除尾部节点并在哈希表同步移除。注意 get 也要更新热度、put 已存在键要覆盖并前移、淘汰时两个结构同步删除。O(1) 平均复杂度，手写时先封装 moveToHead/remove 再写主逻辑。

## Q02：项目如何实现防止超卖？为什么用 Redis 和 Lua 脚本而不用锁？

### 面试回答

防超卖的本质是“检查库存＋扣减”必须原子且以权威数据为准。项目做法（按【真实实现】填写）：库存预热进 Redis，扣减用 Lua 脚本一次执行“判断余量→扣减”，Redis 单线程执行脚本天然原子，返回成功才继续下单落库；MySQL 侧再用条件 UPDATE（`stock>=n` 影响行数判断）做最终防线。为什么不用锁：悲观锁（synchronized／Redisson）把并发串行化，秒杀热点下吞吐骤降、等待排队；乐观锁版本号高冲突下重试风暴；而“判断＋扣减”本身就是一条可下推的原子操作，Lua 更短、无锁等待、吞吐高。代价：Redis 数据要防丢（持久化＋副本），且它只是预占额度，最终事实仍以数据库为准，需要异步落库与对账。

### 面试回答

## Q04：项目如何保障数据库和缓存的一致性？

### 面试回答

以数据库为事实源：先提交事务再删缓存（cache-aside），删除失败进重试队列，缓存统一 TTL 兜底；变更频繁或有本地缓存时订阅 binlog 广播失效；并发回填旧值用延迟二次删除或 key 版本收敛；强一致读直接走库。按项目说明做到哪一层、能容忍多久的陈旧，不声称瞬时强一致。

## Q05：消息队列发送消息失败怎么处理，有没有脏数据存留，怎么处理？

### 面试回答

发送失败分两类：可重试的暂时故障（网络抖动、broker 切换）按幂等键有限重试；重试耗尽则本地落库（outbox／补偿表）后台补发，业务状态标记“处理中”而不是假装成功。脏数据会有——超时重试可能让同一消息发两遍、业务回滚后先前消息已发出、过期指令迟到。处理：消息带稳定业务 ID＋版本／时间戳，消费端幂等去重并校验当前状态，不符合的丢弃留痕；已发出但业务取消的靠“消费时以数据库终态为准”拦截；定期双向对账补差异。

关联专题：[[专题题库/系统设计#SYS-014：MQ 消息发送延迟或失败如何优化与补偿？|SYS-014：MQ 消息发送延迟或失败如何优化与补偿？]]

## Q06：项目怎么解决缓存击穿问题的？

### 面试回答

热点 key 过期瞬间大量请求打到数据库。项目按【实际方案】答，通用两类：互斥重建——只放一个请求拿锁回源重建，其余等待或返回旧值；逻辑过期——缓存值里内嵌过期时间，物理不过期，发现逻辑过期后由拿到重建权的异步刷新，其他请求直接返回旧数据。再配热点探测与提前刷新、永不过期的活动配置类数据。

## Q07：为什么使用逻辑过期方案，而不用互斥锁？

### 面试回答

两者取舍不同：互斥锁重建期间其他请求阻塞等待，数据库慢或重建失败时线程堆积、延迟尖刺，还要处理锁本身失效；逻辑过期不阻塞——所有请求都能拿到旧值，仅一个异步任务去重建，吞吐与时延平稳，代价是明确容忍一段旧数据。秒杀商品详情这类读多、可短暂陈旧、对时延敏感的场景选逻辑过期；余额、库存这类不能读旧值的不能用它，应走互斥重建＋权威源校验或直接读库。选哪个先问业务能忍多久旧数据。

## Q08：MySQL 的主从复制过程是什么？是同步的吗？

### 面试回答

主库提交写 binlog→dump 线程按位点/GTID 推送→从库 IO 线程落 relay log→SQL 线程重放。默认不是同步：异步复制主库提交即返回，不等任何从库确认，主库宕机可能丢最后事件；半同步要至少一个从库确认收到才返回（超时仍降级异步）；组复制等更强方案有额外代价。所以“主从”默认意味着从库可能读到旧数据，延迟要监控 Seconds_Behind_Source。

## Q09：针对主从同步延迟，如何从业务层设计优化？

### 面试回答

面试官限定从业务层设计（不改中间件底层）：① 读写分离路由——写后立读的关键接口（下单后查订单、支付结果页）强制走主库，用注解／Hint 或事务内自动主库标记实现；② 会话粘性：同一用户写后短时间内的读都路由主库或走缓存；③ GTID／位点等待：需要“读到至少某版本”的读请求先等待复制进度；④ 前端兜底：提交成功页直接展示本地已知数据，稍后再拉列表；⑤ 对账与重试：从库读空结果不立即判定“不存在”，走主库复核一次。核心是按“读己之写”的业务重要性分级，而不是全量读主库。

## Q10：大数据的分页查询会出现什么问题，怎么解决？

### 面试回答

`LIMIT 1000000,20` 会扫描并丢弃前百万行：越翻越慢、I/O 放大；深分页时数据还在变化导致重复／漏行；COUNT(*) 总数统计同样昂贵。解决：游标／seek 分页（`WHERE id>上次末尾 ORDER BY id LIMIT 20`）替代 offset；必须跳页时用延迟关联（覆盖索引先查本页 id 再回表）；限制可翻深度或改“上一页／下一页”交互；总数用估算或异步统计、允许“100+”展示。

## Q11：Redis 分布式锁如何实现？SETNX 的 value 可以随便传吗，有什么要求？

### 面试回答

基本式：`SET key value NX EX ttl`——加锁与过期一条命令原子完成，避免 SETNX 后掉线留下永不过期死锁。value 不能随便传：必须是本次持锁的唯一标识（如 uuid＋线程 ID），解锁时先比对 value 再删（比对＋删除用 Lua 原子执行），否则会误删别人重新获取的锁；只存固定字符串（如 "1"）等于没有属主校验。进一步要求：可重入需要记录持有者与次数（Redisson 用 Hash field）；锁粒度对应业务键；强正确性场景配 fencing token（单调递增版本号）让资源侧拒绝过期持有者的写。

关联专题：[[专题题库/Redis#REDIS-006：Redis 分布式锁如何正确加锁、解锁和续期？|REDIS-006：Redis 分布式锁如何正确加锁、解锁和续期？]]

## Q12：SETNX 实现的锁在业务还没处理完就到达 TTL，怎么办？

### 面试回答

TTL 到期锁被释放、另一客户端拿锁，出现两个“持有者”同时操作。处理：① 看门狗续期——未指定 lease 时后台线程按 TTL 的约 1/3 周期检查持有并延长（Redisson 默认 30s），进程崩溃则停止续期自然过期；② 业务侧把临界区设计成短小、可幂等的操作，TTL 按压测的 P99 加余量设定；③ 关键写入带 fencing token／版本号，资源端拒绝旧持有者，即使真发生双持有也不会写坏；④ 不能靠“把 TTL 设得很大”解决——持锁进程崩溃时会长时间无人能干活。

## Q13：使用 TCP 传输数据时丢包怎么办？

### 面试回答

TCP 自身已有完整机制：序列号＋确认应答发现丢失，超时重传或快速重传（3 个重复 ACK）补发，滑动窗口与拥塞控制（慢启动、拥塞避免、乘性降）控制发送速率避免加剧丢失。应用层要做的是理解语义：TCP 保证有序可靠到达，但“连接没断”不等于“业务请求成功”——半包粘包要自己定界（长度前缀／分隔符），对端进程假死要靠应用层心跳与超时，请求级重试必须幂等（网络超时属结果未知，可能服务端已执行）。

## Q14：HTTP 接口针对可能出现的请求丢失，怎么从业务层设计优化？

### 面试回答

按面试官口径从业务层兜底，分“请求可能没到”“到了但响应没回”“重试放大”三类：① 幂等性——写接口要求携带客户端生成的 requestId／业务唯一键，服务端持久化去重，超时重发不产生重复副作用；② 状态性——把长操作改成“受理＋状态查询”：先返回带受理号的 202／排队结果，客户端轮询或推送拿终态，响应丢失也能恢复认知；③ 超时与重试策略——只对幂等接口自动重试，指数退避＋次数上限，非幂等失败转人工或查询确认；④ 限流与背压——入口与下游分设限额、有界队列，过载返回明确的可重试错误码而不是拖死；⑤ 对账兜底——异步任务与外部回执定期核对，发现“客户端认为丢了但服务端做了”的差异按业务补偿。
