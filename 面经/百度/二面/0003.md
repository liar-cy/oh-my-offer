## Q01：算法：LeetCode 146 LRU 缓存（mid）。

### 面试回答

结构就一句话：哈希表＋双向链表。

- 哈希表负责 O(1) 定位节点。
- 双向链表负责维护访问顺序。
- get／put 都要把节点移到头部；容量满时删掉尾部节点，并在哈希表里同步移除。

三个易错点，写完要逐条回看：

- get 也要更新热度，不是只读。
- put 已存在的键要覆盖并前移。
- 淘汰时两个结构必须同步删。

复杂度平均 O(1)。手写的窍门是先封装 moveToHead／remove 两个小函数，再写主逻辑，不容易漏。

## Q02：项目如何实现防止超卖？为什么用 Redis 和 Lua 脚本而不用锁？

### 面试回答

本质是一句话：“检查库存＋扣减”必须原子，而且要以权威数据为准。

项目做法（按【真实实现】填写）：

- 库存预热进 Redis。
- 扣减用 Lua 脚本一次执行“判断余量→扣减”。Redis 单线程执行脚本，天然原子。
- 脚本返回成功，才继续下单落库。
- MySQL 侧再用条件 UPDATE（`stock>=n`，靠影响行数判断）做最终防线。

为什么不用锁：

- 悲观锁（synchronized／Redisson）把并发串行化，秒杀热点下吞吐骤降、请求排队等待。
- 乐观锁靠版本号，高冲突下会引发重试风暴。
- 而“判断＋扣减”本身就是一条可以下推的原子操作，Lua 更短、无锁等待、吞吐高。

代价也要说：

- Redis 数据要防丢（持久化＋副本）。
- 它只是预占额度，最终事实仍以数据库为准，所以需要异步落库和对账。

## Q03：异步秒杀如何实现的？

### 面试回答

先按【项目实际】说，再给通用链路。

链路顺序：

- 入口做限流和资格校验。
- Redis Lua 预占库存。
- 创建“处理中”订单，带请求号。
- 投递 MQ 后立即返回排队／受理结果。
- 消费者在事务内幂等落库扣减。
- 用户轮询，或者由服务端推送终态。

五个关键点：

- 受理不等于成功，但状态必须可查询。
- 消息可靠性：发送失败要落库补偿。
- 消费幂等。
- 售罄标记提前拦截。
- 超时未终态的订单要取消，并释放额度。

## Q04：项目如何保障数据库和缓存的一致性？

### 面试回答

口径先说清：以数据库为事实源，不承诺瞬时强一致。

主流程（cache-aside，旁路缓存：应用先查缓存、没命中再查库并回填）：

- 先提交数据库事务，再删缓存。
- 删除失败进重试队列。
- 缓存统一设 TTL 兜底，即使漏删也会自己过期。

几个特殊情况的处理：

- 变更频繁，或者上面还有一层本地缓存：订阅 binlog 广播失效消息。
- 并发回填把旧值写回去：用延迟二次删除，或者给 key 带版本号来收敛。
- 要求强一致的读：直接走库。

收尾按项目说：做到哪一层、能容忍多久的陈旧，别声称瞬时强一致。

## Q05：消息队列发送消息失败怎么处理，有没有脏数据存留，怎么处理？

### 面试回答

发送失败先分两类：

- 可重试的暂时故障，比如网络抖动、broker 切换：按幂等键做有限次重试。
- 重试耗尽：本地落库（outbox／补偿表）交给后台补发；业务状态标成“处理中”，而不是假装成功。

脏数据会不会有——会，三种典型：

- 超时重试让同一条消息发出去两遍。
- 业务回滚了，但先前的消息已经发出。
- 过期指令迟到才到。

对应处理：

- 消息带稳定的业务 ID 加版本／时间戳。
- 消费端做幂等去重，并校验当前状态；不符合的丢弃但留痕。
- 已发出但业务取消的，靠“消费时以数据库终态为准”拦下来。
- 定期做双向对账，把差异补掉。

## Q06：项目怎么解决缓存击穿问题的？

### 面试回答

先复述现象：热点 key 过期的那一瞬间，大量请求直接打到数据库。

项目按【实际方案】答；通用就两类：

- 互斥重建：只放一个请求拿锁回源重建，其余请求等待或者返回旧值。
- 逻辑过期：缓存值里内嵌一个过期时间，key 物理上不过期。
- 这种方案下，发现逻辑过期后由拿到重建权的那个请求异步刷新，其他请求直接返回旧数据。

再配两道预防：

- 热点探测加提前刷新。
- 活动配置这类数据设成永不过期。

## Q07：为什么使用逻辑过期方案，而不用互斥锁？

### 面试回答

结论：两者是不同取舍，不是谁一定更好。

- 互斥锁：重建期间其他请求阻塞等待。数据库慢或者重建失败时，线程堆积、延迟出现尖刺，还要额外处理锁本身失效。
- 逻辑过期：不阻塞。所有请求都能拿到旧值，只有一个异步任务去重建，吞吐和时延都平稳。代价是要明确容忍一段时间的旧数据。

怎么选：

- 秒杀商品详情这类读多、可以短暂陈旧、对时延敏感的场景，选逻辑过期。
- 余额、库存这类不能读旧值的，不能用它；走互斥重建加权威源校验，或者直接读库。

开口先问一句业务能忍多久的旧数据，方案自然就定了。

## Q08：MySQL 的主从复制过程是什么？是同步的吗？

### 面试回答

复制流程四步：

- 主库提交时写 binlog。
- dump 线程按位点／GTID（全局事务标识）把日志推送出去。
- 从库 IO 线程把它落成 relay log（中继日志）。
- 从库 SQL 线程重放这些事件。

是同步的吗——默认不是：

- 异步复制：主库提交即返回，不等任何从库确认。主库宕机时可能丢掉最后的事件。
- 半同步：至少要有一个从库确认收到才返回，但超时后仍会降级成异步。
- 组复制这类更强的方案有，但会带来额外代价。

所以“主从”默认就意味着从库可能读到旧数据；延迟要看 Seconds_Behind_Source 这个指标来监控。

## Q09：针对主从同步延迟，如何从业务层设计优化？

### 面试回答

先接住面试官的限定：从业务层设计，不改中间件底层。

- 读写分离路由：写后立读的关键接口（下单后查订单、支付结果页）强制走主库。
- 实现方式：用注解／Hint，或者在事务内自动打主库标记。
- 会话粘性：同一用户写后短时间内的读，都路由主库或者走缓存。
- GTID／位点等待：需要“至少读到某个版本”的读请求，先等复制进度追上。
- 前端兜底：提交成功页直接展示本地已有的数据，稍后再去拉列表。
- 对账与重试：从库读到空结果，不立即判定“不存在”，走主库再复核一次。

核心一句话：按“读己之写”的业务重要性分级，而不是全量读主库。

## Q10：大数据的分页查询会出现什么问题，怎么解决？

### 面试回答

先说会出什么问题：

- `LIMIT 1000000,20` 要扫描并丢弃前一百万行，越翻越慢，I/O 放大。
- 深分页期间数据还在变化，会出现重复行或者漏行。
- `COUNT(*)` 统计总数同样昂贵。

再说怎么解：

- 游标／seek 分页：用 `WHERE id>上次末尾 ORDER BY id LIMIT 20` 替代 offset。
- 必须支持跳页时：用延迟关联，覆盖索引先查出本页的 id，再回表取数据。
- 交互上：限制可翻的深度，或者改成“上一页／下一页”。
- 总数：用估算值或异步统计，允许展示成“100+”。

## Q11：Redis 分布式锁如何实现？SETNX 的 value 可以随便传吗，有什么要求？

### 面试回答

基本式：`SET key value NX EX ttl`。

- 加锁和设过期用一条命令原子完成。
- 这样避免 SETNX 之后进程掉线，留下一把永不过期的死锁。

value 不能随便传，这是第二问的要点：

- 必须放本次持锁的唯一标识，比如 uuid 加线程 ID。
- 解锁时先比对 value 再删；比对加删除要用 Lua 原子执行。
- 不这么做，就会误删别人重新获取到的锁。
- 只存固定字符串（比如 `1`），等于没有属主校验。

再往上的要求：

- 可重入：要记录持有者和重入次数，Redisson 用 Hash 的 field 来存。
- 锁粒度：对应到业务键。
- 强正确性场景：配 fencing token（单调递增的版本号），让资源侧拒绝过期持有者写进来的数据。

## Q12：SETNX 实现的锁在业务还没处理完就到达 TTL，怎么办？

### 面试回答

先把后果说清：TTL 到期锁被释放，另一个客户端拿到锁，就出现两个“持有者”同时操作。

处理办法有这几条：

- 看门狗续期：没指定 lease 时，后台线程按 TTL 的约 1/3 周期检查是否仍持有并延长（Redisson 默认 30s）。
- 这一条的边界是：进程崩溃就停止续期，锁自然过期。
- 业务侧设计：把临界区做成短小、可幂等的操作；TTL 按压测的 P99 再加余量来设。
- 关键写入带 fencing token／版本号：由资源端拒绝旧持有者。这样即使真发生双持有，也不会写坏数据。
- 别指望把 TTL 设得很大：持锁进程崩溃时，会长时间没人能干活。

## Q13：使用 TCP 传输数据时丢包怎么办？

### 面试回答

先给结论：丢包 TCP 自己会处理，应用层要处理的是它的语义边界。

TCP 已有的机制：

- 用序列号和确认应答发现丢失。
- 用超时重传或快速重传（收到 3 个重复 ACK）补发。
- 用滑动窗口和拥塞控制（慢启动、拥塞避免、乘性降）控制发送速率，避免把丢失加剧。

应用层要做的三件事：

- 定界：TCP 保证有序可靠到达，但“连接没断”不等于“业务请求成功”；半包、粘包要自己定界，用长度前缀或分隔符。
- 探活：对端进程假死，靠应用层心跳和超时来发现。
- 重试：请求级重试必须幂等。因为网络超时属于结果未知，服务端有可能已经执行了。

## Q14：HTTP 接口针对可能出现的请求丢失，怎么从业务层设计优化？

### 面试回答

按面试官的口径从业务层兜底。先把问题拆成三类：请求可能没到、到了但响应没回、以及重试被放大。

对应这几类手段：

- 幂等性：写接口要求携带客户端生成的 requestId 或业务唯一键，服务端持久化去重。超时重发不会产生重复副作用。
- 状态性：把长操作改成“受理＋状态查询”。
- 具体做法：先返回带受理号的 202 或排队结果，客户端轮询或推送拿终态；响应丢了也能把认知恢复回来。
- 超时与重试策略：只对幂等接口自动重试，用指数退避加次数上限；非幂等接口失败就转人工或先查询确认。
- 限流与背压：入口和下游分设限额、用有界队列；过载时返回明确的可重试错误码，而不是把请求拖死。
- 对账兜底：异步任务和外部回执定期核对。发现“客户端以为丢了、服务端其实做了”的差异，按业务补偿。
